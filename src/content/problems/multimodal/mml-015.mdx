## Question

"What is a vision encoder and what role does it play in a multimodal model? How is it typically trained? What are the main bottlenecks of large language model inference, and how would you cut memory and latency?"

## Answer

<Depth>
<Fragment slot="short">
<p>The encoder turns pixels into a sequence of patch features that a projector maps into the language model's embedding space; it is the front end that decides how many visual tokens an image becomes and what detail survives. It is pretrained supervised or, more often, contrastively against captions (CLIP), then usually frozen or lightly tuned while the projector and language model learn to use it. In a VLM the bottlenecks are prefill over many visual tokens, the KV cache those tokens occupy for the whole decode, and decode's memory bandwidth. Cut visual tokens first (resolution, crops, merging), then cache encoder outputs and prefixes, then quantize weights and KV cache.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What it is.</strong> A ViT cuts an <em>H</em> × <em>W</em> image into <em>HW</em> / <em>P</em>² patches and runs a transformer over them. Its output is a feature per patch (or per merged group of patches), and that count is the image's length in the language model. Qwen2.5-VL merges 2 × 2 groups of 14 px patches, so one language-model token per 28 × 28 pixels.</p>
<p><strong>How it is trained.</strong> Three recipes in use. Supervised classification on large labelled sets (ViT on JFT-300M); the paper finds ViT generalises poorly without large data. Contrastive image-text training (CLIP: 400 million pairs, symmetric cross-entropy over a 32,768-pair batch), which aligns features with language and is the usual starting point for VLMs. Co-training inside the VLM: Qwen2.5-VL trains its ViT alone first, then with the whole model, and freezes it for post-training. LLaVA freezes a CLIP encoder throughout and trains a projector, then projector plus language model.</p>
<p><strong>Where the time goes.</strong> The encoder runs once per image; full attention costs grow with the square of the patch count, which is why Qwen2.5-VL uses window attention in most layers. The language model's prefill processes every visual token and is compute-bound. Decode is bandwidth-bound: each output token reads the weights and the KV cache, and every visual token stays in the KV cache for the whole answer.</p>
<p><strong>Worked KV figure.</strong> For a scenario model with 28 layers, 4 KV heads of dimension 128, BF16: 2 × 28 × 4 × 128 × 2 bytes = 57,344 bytes per token. A 1,296-token screenshot holds 57,344 × 1,296 = 74.3 MB of KV cache per sequence, so ten concurrent requests with three screenshots each hold 2.2 GB before any text.</p>
</Fragment>

### The optimisation order, with what each costs

1. **Fewer visual tokens.** Lower resolution, crop to the region that matters, or merge tokens. This cuts encoder work, prefill and KV cache together, and it is the only lever that reduces all three. Cost: detail. Measure accuracy by text size before and after.
2. **Do not recompute.** Cache encoder outputs keyed by image hash when the same image is queried repeatedly, and keep the image in a stable prompt prefix so prefix caching reuses its KV. Cost: memory for the cache and an invalidation rule when the encoder changes.
3. **Make each byte cheaper.** Quantize weights and the KV cache. Cost: accuracy that must be re-measured on image tasks, not only text.
4. **Schedule the stages separately.** The encoder is a short compute-bound burst per image; decode is a long bandwidth-bound loop. Batching them separately, or on separate workers, stops one long video encode from stalling every decoding sequence. Cost: a transfer of encoder outputs between stages and a more complex scheduler.

**Where this answer fails.** Cutting visual tokens is the first lever only when visual tokens dominate. For a single small image with a long system prompt and a long answer, the text and decode dominate, and the right first move is prompt caching or a shorter answer. Compute the split before choosing.

## Common mistakes

- Describing the encoder as "turning images into embeddings" without saying that its output length is the image's cost in the language model.
- Naming the encoder as the bottleneck without comparing it with prefill and KV cache over the same visual tokens.
- Listing optimisations without the accuracy cost of each.
- Quantizing and measuring only on text benchmarks.
- Answering the LLM bottleneck half with no connection to images at all.
