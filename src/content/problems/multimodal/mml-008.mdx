## Question

<Callout kind="interview" label="Interview question">
"We need 256K-token sessions for a document product. Compare a hybrid attention-Mamba model with a dense mixture-of-experts model of similar size: what does one 256K sequence cost in cache on each, and what does that do to how many sessions a node holds?"
</Callout>

Published inputs, from each model's `config.json` (checked 2026-10-28):

| field | Jamba-v0.1 | Mixtral-8x7B |
|---|---|---|
| layers | 32 | 32 |
| hidden size, query heads, KV heads | 4,096, 32, 8 | 4,096, 32, 8 |
| attention layers | one every 8 layers (`attn_layer_period` 8, offset 4) | all |
| other layers | Mamba: `mamba_expand` 2, `mamba_d_state` 16, `mamba_d_conv` 4 | none |
| total parameters | 52B (paper) | 46.7B (Jamba paper, Table 1) |

1. Choose the precision you would serve the KV cache and the recurrent state at, and say why.
2. Estimate the cache for one 262,144-token sequence on Jamba, including the Mamba layers. **Enter this figure in GiB.**
3. Do the same for Mixtral, and say how many 256K sessions fit next to the weights on two 80 GB GPUs (scenario hardware), with weight precision of your choice.

## Answer

<Depth>
<Fragment slot="short">
<p>Jamba caches only on its 4 attention layers: 4 × 2 × 8 × 128 values × 2 bytes = 16,384 bytes per token, 4.00 GiB at 262,144 tokens in 16-bit, plus about 8.3 MiB of Mamba state that does not grow. Mixtral caches on all 32 layers: 131,072 bytes per token, 32 GiB. On two 80 GB GPUs with BF16 weights, Jamba holds about eleven 256K sessions and Mixtral one. Any answer from 1.9 to 4.1 GiB counts: 16-bit KV gives 4.0, 8-bit KV gives 2.0.</p>
</Fragment>
<Fragment slot="long">
<p><b>Precision.</b> 16-bit KV is the default most engines ship; 8-bit KV halves it, with a quality check on long-context retrieval. Keeping the recurrent state at 16 bits or 32 bits barely matters here, because the state is small.</p>
<p><b>Jamba.</b> Head dimension is 4,096 / 32 = 128. Attention layers: 32 / 8 = 4. Per token, 4 layers × 2 (key and value) × 8 KV heads × 128 = 8,192 values, 16,384 bytes in 16-bit. Times 262,144 tokens: 4,294,967,296 bytes, 4.00 GiB, the paper's Table 1 figure. Mamba layers: 28, each with an inner width of 2 × 4,096 = 8,192, a state of 8,192 × 16 = 131,072 values and a convolution buffer of 8,192 × 3 = 24,576 values. That is 28 × 155,648 = 4,358,144 values, 8.3 MiB at 2 bytes and 16.6 MiB at 4. Total 4.01 GiB in 16-bit; 2.01 GiB with 8-bit KV.</p>
<p><b>Mixtral.</b> 32 layers × 8,192 values × 2 bytes = 131,072 bytes per token, 32 GiB at 262,144 tokens. Its config's `max_position_embeddings` is 32,768, so a 256K Mixtral session is a memory comparison, not something the released model was built to serve; the Jamba paper's table makes the same comparison.</p>
<p><b>Sessions per node (scenario: two 80 GB GPUs, 149 GiB).</b> BF16 weights: Jamba 52B × 2 bytes = 104 GB, 96.9 GiB; Mixtral 46.7B × 2 = 93.4 GB, 87.0 GiB. Leaving roughly 8 GiB for activations and engine overhead (an assumption; measure it), Jamba has about 44 GiB for cache, so 11 sessions at 4.01 GiB; Mixtral has about 54 GiB, so one session at 32 GiB. With 8-bit weights (48.4 and 43.5 GiB) and 8-bit KV, Jamba reaches about 46 sessions at 2.01 GiB and Mixtral 6 at 16 GiB.</p>
<p><b>Dominant term and what flips it.</b> For Jamba at 256K the weights dominate the node, and the per-session cache is small; for Mixtral the KV cache dominates. The assumption that flips the comparison is context length: at 8,192 tokens Mixtral's cache is 1 GiB per session and both models are weight-bound, so the hybrid's advantage mostly disappears and quality and engine support decide.</p>
<p><b>Failure mode of this estimate.</b> It assumes the engine allocates cache only for attention layers and keeps one state slot per session. An engine that reserves Mamba state for every possible slot up front, or that snapshots state for prefix caching, adds memory the arithmetic ignores; read the engine's allocation report before promising a session count.</p>
</Fragment>

### Which answers are unreasonable

- 32 GiB for Jamba: charging every layer as attention, which ignores the 1:7 layout.
- 16 GiB: using 32 query heads instead of 8 KV heads on the 4 attention layers.
- Hundreds of GiB: multiplying the Mamba state by the token count. The state is overwritten in place; it does not grow with context.

## Follow-ups

- Compute the same figure for Jamba at 140K tokens and compare with the paper's statement that it fits a single 80 GB GPU there. What does that tell you about the paper's weight precision?
- How would you measure the activation and engine overhead you assumed at 8 GiB?

## Common mistakes

- Counting GB and GiB interchangeably: 4,294,967,296 bytes is 4.00 GiB and 4.29 GB.
- Treating the Mamba state as negligible without computing it; here it is, but for Qwen3.8-27B's 48 Gated DeltaNet layers it is 48 × 48 heads × 128 × 128 × 2 bytes = 72 MiB, which matters at short contexts.
- Comparing models at a context length one of them was not released for, without saying so.
