## Question

<Callout kind="interview" label="Interview question">
"Our code-search assistant answers questions over a repository packed into one 256K-token context. A team proposes replacing every attention layer of our 64-layer model with Gated DeltaNet layers, so the KV cache disappears and we can serve four times as many users per GPU. Production long-context models keep some full attention. Why, and what would you build instead?"
</Callout>

Choose an attention fraction and defend it with numbers, using the copying result and at least one shipped hybrid's ratio. Say what the choice costs at 256K and what would make you change it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what fraction of the assistant's questions need an exact identifier, line or signature quoted back from the context.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for per-sequence memory at 256K split into the part that grows with tokens and the part that does not.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether the serving engine supports prefix caching for the proposed layer type.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A recurrent layer keeps a fixed-size state, and "Repeat After Me" proves a fixed state cannot copy arbitrarily long strings while a two-layer transformer can; the same paper finds pretrained transformers far better at copying and retrieving from context. Code search is mostly that task: return the exact function, the exact call site. Every shipped long-context hybrid keeps some attention for this reason, from one layer in eight (Jamba, MiniMax-01) to one in four (Kimi Linear, Qwen3.8-27B). I would propose one attention layer in four, which keeps a quarter of today's KV, and gate the change on exact-recall evaluations from our own repositories.</p>
</Fragment>
<Fragment slot="long">
<p><b>Why attention stays.</b> The recurrence writes each token into a state before it knows the question. Whatever the state dropped cannot be recovered when the question arrives at the end of 256K tokens. Attention keeps every token addressable. The theorem only says a limit exists; at production state sizes the counting bound is millions of tokens, so the decisive evidence is the paper's empirical finding on pretrained models, and the fact that no shipped long-context model in the sources goes all-recurrent.</p>
<p><b>Numbers, with Qwen3.8-27B's published layout as the model.</b> Its 16 gated-attention layers cache 16 × 2 × 4 × 256 × 2 bytes = 65,536 bytes per token, 16 GiB at 262,144 tokens, and its 48 Gated DeltaNet layers hold 48 × 48 × 128 × 128 values, 72 MiB at 2 bytes. An all-attention stack of the same 64 layers and head shape would cache four times as much, 64 GiB. An all-recurrent stack would hold about 96 MiB of state and nothing that grows.</p>
<p><b>Two defensible answers.</b> One in four (the Kimi Linear and Qwen ratio): 16 GiB per 256K sequence on this shape, a fourfold memory cut against all-attention, and the most attention capacity of any shipped hybrid. One in eight (the Jamba and MiniMax ratio): 8 GiB, twice the concurrency again, with half the layers that can retrieve exactly. For code search, where answers are quoted identifiers, I would take one in four and treat one in eight as an experiment. The cost of my choice is half the concurrency the one-in-eight design would give, and far less than the team's all-recurrent proposal promised.</p>
<p><b>The conflict.</b> The team's goal is users per GPU; the product's goal is exact answers. All-recurrent wins the first and is the design most likely to fail the second. Write the decision as: the attention fraction is chosen by an exact-recall evaluation on our repositories at 64K, 128K and 256K, with a pass threshold agreed before the experiment, and the memory saving is whatever the passing ratio gives.</p>
<p><b>Failure mode of the recommendation.</b> At one in four, the attention layers still dominate memory at 256K (16 GiB against 72 MiB of state), so the concurrency gain is four times, not the "no KV cache" the team expected. And if the engine lacks state snapshots, prefix caching for a shared repository context stops working, and each request re-prefills 256K tokens; the compute bill can then exceed the memory saving.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li>The one-in-four model passes exact recall at 128K and loses five points at 256K, and the team says one in eight would have been no worse. Your verification run costs as much as a month of serving; which experiment do you cut, and what risk do you accept in writing?</li>
<li>What would you need to see in production to reverse the decision and move to one in eight?</li>
<li>Two senior engineers disagree: one says retrieval over a chunk index plus a dense model at 32K beats any hybrid for code search. How do you decide between them without deciding by rank?</li>
</ul>

## Follow-ups

- The repository changes on every commit. What does that do to prefix-cache reuse on a hybrid, and how often does the recurrent state have to be recomputed?
- The model scores well on a 256K needle test. Why is that not evidence for the decision, and what test replaces it?
- If the engine keeps recurrent state in 32 bits, how do the numbers above change, and does it alter the ratio you chose?

## Common mistakes

- Treating the copying theorem as the whole argument. The bound is loose at production state sizes; the empirical result on pretrained models carries the weight.
- Promising "no KV cache" for a hybrid. The attention layers still grow with context and dominate memory at long lengths.
- Choosing the ratio by citing a vendor's choice without an evaluation on the product's own task.
- Using a needle-in-a-haystack score as evidence that the hybrid retrieves exactly from long context.
