  solution: |
    import math


    def frequencies(d, base=10000.0):
        if d <= 0 or d % 2:
            raise ValueError("d must be a positive even number")
        return [base ** (-2.0 * i / d) for i in range(d // 2)]


    def rope(x, pos, base=10000.0, _freqs=None):
        d = len(x)
        freqs = _freqs or frequencies(d, base)
        out = [0.0] * d
        for i, theta in enumerate(freqs):
            a = pos * theta
            c, s = math.cos(a), math.sin(a)
            x0, x1 = x[2 * i], x[2 * i + 1]
            out[2 * i] = x0 * c - x1 * s
            out[2 * i + 1] = x0 * s + x1 * c
        return out


    class RopeCache:
        def __init__(self, d, base=10000.0):
            self.freqs = frequencies(d, base)
            self.d, self.base = d, base
            self.keys = []

        def __len__(self):
            return len(self.keys)

        def extend(self, keys):
            start = len(self.keys)
            for offset, k in enumerate(keys):
                if len(k) != self.d:
                    raise ValueError("key has the wrong dimension")
                self.keys.append(rope(k, start + offset, _freqs=self.freqs))

        def scores(self, q, pos=None):
            if pos is None:
                pos = len(self.keys) - 1
            rq = rope(q, pos, _freqs=self.freqs)
            return [sum(a * b for a, b in zip(rq, k)) for k in self.keys]

## Question

<Callout kind="interview" label="Interview question">
"Implement rotary position embeddings for a toy attention head, with a key cache that serves prefill and decode, and show that the score depends only on how far apart the two tokens are."
</Callout>

Write three things in standard-library Python:

1. `frequencies(d, base)`, the `d / 2` angular frequencies `base ** (-2i / d)`.
2. `rope(x, pos, base)`, which rotates each coordinate pair of `x` by `pos` times that pair's frequency. You choose which coordinates form a pair: adjacent coordinates `(2i, 2i + 1)`, or the two halves `(i, i + d/2)`. Pick one and use it everywhere.
3. `RopeCache`, which receives keys in chunks of any size (a prefill chunk of hundreds, then one key per generated token) and returns attention scores for a query at a given position.

Two constraints. The score between a query at position `m` and a key at position `n` must depend on `m - n` and the two vectors only. And the cache has to absorb 20,000 single-token appends at `d = 16` in a few seconds in the browser, so per-append work cannot grow with the length of the cache.

Before you write the cache, decide whether it stores keys rotated or unrotated, and say what each choice costs when the serving engine changes the rotation frequencies with sequence length.

## Answer

**Why the property holds.** Rotating `q` by angle `mθ` and `k` by `nθ` inside one pair and taking the dot product gives `|q||k| cos(φ + (m − n)θ)`, where `φ` is the angle between the unrotated pair vectors. Summed over pairs, the score is a function of the vectors and `m − n`. The RoFormer paper's framing is the same: absolute position goes in through a rotation, and relative position comes out of the dot product. The hidden tests check exactly that, for shifts of up to 100,000 positions, plus the norm, plus "position 0 is the identity". None of them checks the pair layout, because adjacent pairs and half-split pairs both satisfy every invariant. They are not interchangeable for a given set of trained weights, though: a checkpoint trained with one layout and served with the other rotates the wrong coordinates together.

**The offset bug.** A cache that rotates each chunk from position 0 passes every single-chunk test and fails as soon as prefill is followed by decode: the first decoded key lands on position 0 again, the score with every earlier key now reflects the wrong distance, and nothing crashes. The reference solution rotates key `j` at `len(cache) + offset`, and one hidden test compares a cache filled in chunks of 5, 1, 1 and 7 with one filled at once.

**The decision: rotated or unrotated keys.**

- *Store rotated keys* (the reference). Each key is rotated once at append, `d / 2` rotations, and a score is one rotation of the query plus dot products. Cost: the rotation is baked in. If the frequencies change, every cached key is wrong.
- *Store unrotated keys and rotate at read.* The frequencies can change between steps. The YaRN paper says exactly this for its Dynamic scaling, where the scale factor is recomputed from the current length: cache keys before applying RoPE, since the embedding changes with the factor. Cost: every decode step re-rotates every cached key, so a sequence of `n` tokens performs on the order of `n² d / 4` rotations instead of `n d / 2`.

The 20,000-append constraint is there to make the cost of the wrong mix visible. Re-rotating the whole cache on every append, with `d = 16`, is 8 rotations per key per append: about 8 × 20,000² / 2 = 1.6 billion rotations, against 160,000 for rotate-once. Storing unrotated keys and rotating lazily inside `scores` also passes this test, since the test never calls `scores` in the loop; it would fail a test that scored every step.

**The quantity you choose** is where the rotation happens, which follows from one fact about the deployment: whether its scaling is static. For static scaling (a fixed `rope_scaling` block), rotate once at append. For dynamic scaling, store unrotated keys and accept the per-step cost, or bucket the factor so that it changes rarely and re-rotate the cache only at bucket boundaries.

**How the recommended answer fails.** Rotate-once is correct only while the frequencies are fixed for the life of the cache. A team that turns on a dynamic scaling mode in its engine, or that shares cached prefixes between requests served under different `rope_scaling` settings, keeps reading keys rotated with the old frequencies. Scores are silently off for every cached token, and the first symptom is quality loss on long prompts, not an error. The cache key for a reusable prefix has to include the rotation settings.

## Common mistakes

- Rotating each prefill chunk from position 0, which the single-chunk tests never see.
- Testing against one hand-computed output, so a correct implementation with the other pair layout fails and a wrong one with the same layout passes.
- Writing the exponent as `-2 * i // d`: floor division puts every pair after the first on the same frequency, `1 / base`, and the norm and position-0 checks still pass.
- Re-rotating the cache on every append "to keep it simple", which turns decode quadratic.
- Treating the norm check as proof: a rotation by the wrong angle preserves the norm too.
