## Question

<Callout kind="interview" label="Estimate, 20 minutes">
"Here is the Pipecat maintainers' published round trip for a cascaded voice turn. Our agent uses GPT-4.1 and calls a CRM lookup on turns where the caller asks about an order. Estimate the median voice-to-voice latency of one of those turns, tell me which term dominates, and tell me whether we can hit 1,500 ms."
</Callout>

Published inputs (Pipecat primer, June 2026 update, checked 2026-10-28):

| Stage | ms |
|---|---|
| Transport up (mic, encode, network, jitter buffer, decode) | 114 |
| Transcription and endpointing | 300 |
| LLM time to first byte (table) | 650 |
| Sentence aggregation | 20 |
| TTS time to first byte | 120 |
| Transport down (encode, network, jitter buffer, decode, speaker) | 89 |
| GPT-4.1 time to first token, median, measured separately | 536 |

Scenario inputs: TTS streams from the first clause; no filler phrase is played. You choose the CRM lookup's median latency and how long the first inference spends emitting the tool call after its first token. State both.

## Answer

<Depth>
<Fragment slot="short">
<p>About 1,950 to 2,800 ms at the median, so no. The turn makes two inferences: one that emits the tool call and one that writes the answer after the tool returns. With a 400 ms lookup and 100 ms to emit the call, the turn is 114 + 300 + 536 + 100 + 400 + 536 + 20 + 120 + 89 = 2,215 ms. The dominant term is the tool round trip: two times to first token, the call emission and the lookup, 1,572 ms together. Even with a 0 ms tool, two times to first token leave the turn at 1,815 ms.</p>
</Fragment>
<Fragment slot="long">
<p>Start from the table without the LLM row: 114 + 300 + 20 + 120 + 89 = 643 ms of stages that do not change with the tool. Add the first inference: 536 ms to its first token, then the tool-call arguments. A tool call with an order id and a function name is a few dozen tokens; at tens of milliseconds per token for a hosted model, 50 to 300 ms is a reasonable range to choose, and the answer below uses 100. Add the CRM lookup; 200 to 800 ms median is a defensible range for an internal HTTP service called across a region boundary, and the answer uses 400. Add the second inference's time to first token, 536 ms, which also has to prefill the tool result. Then sentence aggregation and TTS as before.</p>
<p>Total: 643 + 536 + 100 + 400 + 536 = 2,215 ms. Across the reasonable choices (50 to 300 ms of call emission, 200 to 800 ms of lookup), the median sits between 1,965 and 2,815 ms. The dominant group is the tool round trip: two times to first token and the lookup add up to more than the whole 1,500 ms target in every reasonable choice.</p>
<p><strong>Can it hit 1,500 ms?</strong> Not as a voice-to-voice median for the answer. Two routes get first audio under target: speak a filler before the tool call (first audio then arrives after the first inference, at about 643 + 536 + a short clause, near 1,200 ms) or remove the tool from the turn by prefetching the caller's orders when the call connects. The first route improves first audio and leaves the answer at about 2.2 seconds; the second removes about 1,000 ms from the answer but only for the lookups you predicted.</p>
<p><strong>Failure mode of the estimate:</strong> it uses medians throughout, and the median of a sum is not the sum of medians when tails are skewed. GPT-4.1's measured P95 time to first token is 1,771 ms; a turn with two inferences has two chances to hit it, so the P95 of tool turns is far above anything this estimate suggests.</p>
</Fragment>

### Which choices are unreasonable

- **A tool latency of zero.** Even an in-process cache lookup has to return through the agent framework; a zero leaves out the term the question asks about.
- **One inference per tool turn.** The model cannot write an answer about an order it has not seen. Forgetting the second time to first token is the most common error and removes 536 ms.
- **Using the table's 650 ms LLM row together with GPT-4.1's 536 ms.** Pick one per inference; adding both double-counts the model.
- **Lookups over 2 seconds as the median.** Possible for a slow API, but then the question is not a budget question; it is a design question about moving the call off the turn.

### The assumption that flips it

Whether the lookup's input is known before the turn. If caller ID maps to an account and the agent prefetches recent orders while the greeting plays, the tool leaves the critical path and the turn is the table's single-inference turn with GPT-4.1, about 1,179 ms (1,293 − 650 + 536). The answer moves from "cannot hit target" to "hits it with room", and the work moves from latency engineering to predicting which data a caller will ask about.

## Follow-ups

- *The CRM team offers a 100 ms cache with five-minute staleness. Address changes made on the same call would read stale. Do you take it?*
- *What would you need to measure in production before trusting this estimate for capacity planning?*
- *A colleague proposes running the first inference speculatively on the interim transcript. Which term does that reduce, and by how much at most?*

## Common mistakes

- Adding the table's total to a tool latency, which counts one inference and the table's LLM row instead of two GPT-4.1 inferences.
- Reporting first audio with a filler as the turn's latency.
- Taking 800 ms or 1,500 ms as a standard rather than a target with a stated start point.
- Treating P95 of the turn as the sum of stage P95s, or as the median plus a margin.
