## Question

<Callout kind="interview" label="Debugging round">
"Our multimodal assistant ignores the photo and answers from the text. Find out why and fix it."
</Callout>

The product, as a scenario: adjusters upload a phone photo of a damaged car with a claim, and the assistant lists the damaged parts. It runs on Claude Haiku 4.5. Since Tuesday's release, adjusters have flagged 40 claims where the assistant's list repeats the policyholder's description from the claim form, including three where the photo shows the front of the car and the form says "rear bumper". You have Tuesday's diff and the text of three flagged conversations. There are no request payload logs, and nobody has compared answers before and after the release on the same claims.

The helper was added in the same release:

```python
# Older turns resend their images on every call; keep only the newest ones.
def drop_old_images(msgs, keep):
    out, seen = [], 0
    for m in reversed(msgs):
        if m["role"] == "user":
            seen += 1
            if seen > keep:
                m = {**m, "content": [b for b in m["content"] if b["type"] != "image"]}
        out.append(m)
    return out[::-1]
```

## Answer

The cause is the interaction between the new message layout and the new helper. The question moved into its own user message after the photo's message, and `drop_old_images(msgs, keep=1)` counts user messages from the end and strips image blocks from all but the newest. The newest user message is now always the text-only question, so the photo is removed from every request. The model receives the claim form and a question that says "answer from the photo" with no photo, and the form is the only evidence it has. Neither the helper nor the call site is wrong in isolation; the helper's notion of "newest" was written for the old one-message layout.

The evidence that would confirm it in minutes: a Haiku 4.5 request with a 1092 × 819 photo should carry ⌈1092 / 28⌉ × ⌈819 / 28⌉ = 39 × 30 = 1,170 visual tokens on top of the text. If a flagged request's `input_tokens` is roughly the text alone, the photo never arrived.

**The rest, ranked for after the fix.**

1. *JPEG quality 55* is the most likely to matter next. Anthropic's guide warns that heavy compression introduces artifacts that hurt performance; fine scratches and panel gaps are the detail at risk. Measure damage-list accuracy at 55 and 85 on the same claims before keeping it.
2. *Text before image* is real but minor. The guide prefers image-then-text and says the other orders still perform well. Restore image-first because it is free, not because it explains anything.
3. *The 1092 px cap* is a smaller change than it looks. On a standard-tier model a 4:3 photo is resized server-side to fit 1,568 tokens anyway, so the old 1568 px setting was mostly undone by the provider; 1,170 tokens against at most 1,568 is a modest loss of detail, and nothing is discarded.

**What to collect, and what to ship without it.** Collect the usage `input_tokens` for flagged requests, one full payload after `drop_old_images`, and a rerun of the 40 flagged claims with photos swapped between claims: if answers do not change with the photo, the model is not using it. Without any of that, ship the helper fix and a test today, because a request that should carry a photo and carries none is wrong regardless of the other evidence:

```python
def drop_old_images(msgs, keep):
    # keep images in the newest `keep` user messages that contain any
    out, kept = [], 0
    for m in reversed(msgs):
        has_image = m["role"] == "user" and any(b["type"] == "image" for b in m["content"])
        if has_image:
            kept += 1
            if kept > keep:
                m = {**m, "content": [b for b in m["content"] if b["type"] != "image"]}
        out.append(m)
    return out[::-1]

def test_current_photo_survives():
    msgs = build_request(claim, photo_bytes, history=[])
    assert sum(b["type"] == "image" for m in msgs for b in m["content"]) == 1
```

Revert quality to 85 until the paired comparison says otherwise, and put the image before the claim text.

**How this fix fails.** "Newest message with images" is still a recency rule. An adjuster who uploads a second photo of the same claim later in the conversation now loses the first one, and the assistant lists only the damage in the latest photo, with no error. The rule should key on the claim: keep every photo attached to the current claim, and drop images only from earlier claims. That costs tokens: each extra photo on Haiku 4.5 adds up to 1,568 per request for the rest of the conversation.

## Follow-ups

- *Your fix keeps every photo of the current claim, and long conversations now cost three times as much. Which photos do you drop, and what failure do you accept in writing?*
- *What would you need to see before deciding quality 55 is safe to keep?*
- *How do you make sure the next helper that edits messages cannot silently remove the image again?* A contract test on the final payload, run in CI, that asserts every claim request with a photo contains at least one image block, plus an alert on requests whose input tokens fall below the computed image cost.

## Common mistakes

- Picking the prompt order because it is the most visible change in the diff and matches advice from the vendor's guide.
- Adding "look carefully at the photo" to the prompt; the photo is not in the request.
- Reading `drop_old_images` alone and concluding it is correct, which it is for the old message layout.
- Fixing the helper without a test on the final payload, so the next layout change breaks it again.
- Reverting the whole release, which also discards the token savings the helper was written for, without learning which change caused the symptom.
