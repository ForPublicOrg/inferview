## Question

<Callout kind="interview" label="Concept, 15 minutes">
"Our voice agent spends about 300 ms after the caller stops talking before the LLM request goes out. Someone proposes sending the request on the interim transcript instead. How much does that save, what does it cost, and when is it wrong?"
</Callout>

Type a short answer before opening the worked one.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask how often the interim transcript at the moment of the pause equals the final transcript on your traffic.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the LLM provider bills for a request cancelled after its first tokens.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>It saves up to the lead time between a stable interim transcript and the endpoint decision, only on turns where the interim matches the final, which is at most the 300 ms. It costs a wasted LLM request on every miss and doubles request rate against provider limits in the worst case. Nothing may be spoken until the endpoint confirms the turn, so it never makes a turn faster than endpointing plus TTS, and it is wrong when the caller adds words after the pause.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The mechanism.</strong> A streaming recognizer emits interim transcripts as audio arrives, and a final transcript when the segment closes. The turn detector decides the turn is over some time after the last word, about 250 ms after the pause in the primer's VAD plus Smart Turn setup. ElevenLabs recommends starting LLM work on stable partials, which hides that endpointing delay: when the endpoint fires, the model has already been working, and time to first token from the endpoint shrinks by the lead.</p>
<p><strong>The saving, computed.</strong> With a lead of L ms and a match rate m, the expected saving per turn is m × L. With L = 200 ms and m = 0.7 (both scenario values to replace with measurements), that is 140 ms on average, all of it on matching turns. Turns that miss take exactly as long as before.</p>
<p><strong>The cost.</strong> Every miss is a full prefill and some generated tokens thrown away, then a second request. Calls per turn go from 1 to 1 + (1 − m), so 1.3 at m = 0.7. That is a 30 percent increase in LLM requests and in prompt tokens if the prompt is not cached, and rate limits are hit 30 percent sooner. If cancelled requests are billed for prefill, a long system prompt makes each miss expensive.</p>
<p><strong>The rule that keeps it safe.</strong> The speculative output is held until the endpoint confirms the turn and the final transcript matches. Otherwise the agent answers "I want to cancel" when the caller was about to say "I want to cancel the extra line, not the account".</p>
<p><strong>Its failure mode.</strong> The match test. An exact string match misses on punctuation and casing and throws away good work; a loose match accepts a final transcript that added a negation. Normalise case and punctuation, then require token equality, and treat any added token after the interim as a miss.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your measured match rate is 45 percent. Is it still worth it, and what would raise the rate?</em> Starting later (a smaller lead) raises m and lowers L; the product m × L has a maximum you find from your own recordings.</li>
<li><em>The model calls a tool in the speculative request. Do you let the tool run before the endpoint confirms?</em> Only for read-only tools; a write must wait for the confirmed transcript.</li>
<li><em>How does speculation interact with a prompt cache?</em> Both requests share the prefix up to the user message, so a cached prefix makes the miss cheap; the user message itself is the only uncached part.</li>
</ul>
</Fragment>
</Depth>

The 140 ms figure is small next to an LLM tail: in the Pipecat primer's measurements, hosted models' P95 time to first token runs from 712 to 1,771 ms. Speculation is a median optimisation. Add it after streaming TTS, model selection on P95 and tool fillers, and only once the match rate is measured on your own callers.

## Follow-ups

- *A colleague wants to speculate on every interim transcript, not only the last stable one. What happens to request rate on a 20-second caller turn?*
- *How do you show in a dashboard that speculation is paying for itself?*
- *What changes if the provider bills cancelled requests only for tokens actually generated?*

## Common mistakes

- Counting the saving on every turn instead of on matching turns only.
- Letting the speculative reply play before the endpoint confirms the turn.
- Running write tools from a speculative request.
- Ignoring the extra request rate against provider limits.
