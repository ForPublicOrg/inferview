## Question

<Callout kind="interview" label="Interview question">
"Your activity uses the default Temporal retry policy, and a step sends a malformed prompt that the provider rejects with a 400. What happens?"
</Callout>

A Temporal Python worker runs one activity per support ticket. The workflow schedules it like this:

```python
summary = await workflow.execute_activity(
    summarize_ticket,
    ticket,
    start_to_close_timeout=timedelta(seconds=120),
)
```

and the activity calls the Anthropic Python SDK:

```python
@activity.defn
async def summarize_ticket(ticket: Ticket) -> str:
    resp = await client.messages.create(
        model=settings.SUMMARY_MODEL,
        max_tokens=1024,
        thinking={"type": "disabled"},
        messages=[{"role": "user", "content": render_ticket(ticket)}],
    )
    return resp.content[0].text
```

At 14:00 a configuration change moves `SUMMARY_MODEL` from `claude-haiku-5-5` to `claude-opus-5-5`. From then on every call returns HTTP 400 `invalid_request_error`. Tickets keep arriving at 3,000 an hour, each starting one workflow. The on-call alert fires when the workflow failure rate goes above 1%.

At 16:00, before anyone has looked, which description of the system is right?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which retry policy fields does the workflow set, and what does Temporal's documentation give for each field left unset?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what Temporal knows about the exception the SDK raised: does it ever see the HTTP status?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Which of the activity timeouts bounds one attempt, and which bounds all attempts together?</p></details>

## Answer

The first option is right. Temporal's default activity retry policy starts at 1 second, doubles each time, caps the interval at 100 seconds (100 times the initial interval) and has unlimited attempts with an empty non-retryable list. The SDK's `BadRequestError` is an ordinary Python exception; Temporal converts it to an Application Failure whose type is the class name and whose `non_retryable` flag is false, so it is retried like a network blip. The only timeout set is Start-To-Close, which bounds one attempt and resets on every retry. Schedule-To-Close, the bound on all attempts together, defaults to infinity. Nothing ends the activity, so no workflow fails, and an alert on workflow failures stays silent while two hours of tickets (2 × 3,000 = 6,000 workflows) pile up as open executions with climbing attempt counts. The backoff reaches its cap after about two minutes (1 + 2 + 4 + ... + 64 = 127 seconds of waits), so all but the newest few minutes of activities retry once every 100 seconds.

The second option applies standard advice, "retry 5xx, generally not 4xx", which AWS's guidance on retries also gives. Temporal has no idea the failure was an HTTP 400. Classification is the activity author's job: list `BadRequestError` in `non_retryable_error_types`, or catch it and raise `ApplicationError(..., non_retryable=True)`.

The third option borrows a default from elsewhere. Many clients stop after three tries, including the Anthropic SDK (two retries, three attempts) for errors it considers transient, which a 400 is not. Temporal's own default has no limit.

The fourth option confuses the two timeouts. A Start-To-Close expiry is itself retried under the policy and the timer starts again, so even an attempt that hung would not end the activity.

Classifying by status code alone is not enough either. A spend limit your own organisation set also returns 400 `invalid_request_error`, and it clears as soon as someone raises the limit, so marking every 400 non-retryable fails thousands of tickets that a page to the budget owner would have saved. Read the error message or type, fail fast on malformed requests, park and page on the spend limit, and set a Schedule-To-Close timeout so no class of error can retry forever. Then alert on activity attempt counts or the age of the oldest open workflow, not only on failures.

## Follow-ups

- *Someone reverts the model at 16:00. What reaches the provider in the next 100 seconds?* All 6,000 pending activities retry within one capped interval and now succeed: 6,000 requests in 100 seconds, about 3,600 a minute on top of live traffic. That is above the Start tier's 1,000 requests per minute for Claude Haiku 5.5 and well under the Scale tier's 10,000, so the organisation's tier decides whether the recovery itself produces a wave of 429s. On a low tier, drain the backlog through a rate-limited path or raise the limit first.
- *Would a workflow retry policy have helped?* No. Workflows have no retry policy by default and adding one reruns the whole workflow; the fault is in the activity's error classification.
- *Where else does the same default bite?* Any activity that calls a model with a deterministic failure: a prompt over the context window, a schema the structured-output feature rejects, or a removed model ID.

## Common mistakes

- Assuming the orchestrator understands HTTP status codes from a library it has never seen.
- Setting maximum_attempts without Schedule-To-Close, so a slow-failing dependency still holds work open for hours.
- Alerting only on workflow failure, which never fires when the failure mode is retrying forever.
- Marking every 400 as permanent and losing work to a budget limit that would have cleared.
