## Question

Design the platform behind a research-assistant product. A user asks a question; a lead agent plans, starts up to five sub-agents in parallel that search and read sources, and writes a report. A run often lasts 30 minutes or more and makes hundreds of model and tool calls. Some tools write to the customer's workspace, such as saving notes to a document.

Constraints (scenario):

- Enterprise customers buy prepaid monthly credit with a hard cap in the contract.
- The billing system updates usage once an hour, and its team will not change that this year.
- The platform team is five engineers.
- The product deploys several times a day.

Cover:

- how a run resumes after a worker crash or a deploy;
- how an engineer replays a run to debug it;
- how the spend cap is enforced in the middle of a run;
- what you alert on.

Pick the numbers you need and defend them. End with what you give up and a rollout plan.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the contract says happens at the cap: is a few cents over a breach, and does the customer want a partial report or nothing?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask an engineer who debugs runs today whether they need to see what the agent saw, or to try a different prompt from the same point. Those are two different tools.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask for the largest input and output token counts of one model call in a run, and the per-token prices on the contract.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Each run is a durable workflow. Every model call and tool call is a step whose result is recorded, and sub-agents are child workflows, so a crash or deploy resumes from the last recorded step instead of restarting a 30-minute run. Runs stay on the code version they started on until they finish, as Anthropic's rainbow deployments do. Debugging gets two tools: a read-only replay that re-renders the run from recorded results at no cost, and a fork from a step that re-executes later calls against sandboxed tools and the platform's own budget. The cap is enforced by a spend ledger that reserves the worst-case cost of each model call before it is made and settles the actual cost after, because the hourly billing system is too late. Alerts cover loops, budget burn, run age and tool-call validation failures, built from decision patterns rather than content.</p>
</Fragment>
<Fragment slot="long">
<p>Resume. Anthropic writes that agents are stateful and errors compound, and that it built systems that resume from where the agent was when errors occurred, because restarts are expensive. A durable workflow gives this directly: the lead agent's loop is workflow code, each model call and tool call is an activity whose result is in the history, and a new worker re-runs the loop against the history and continues from the first unrecorded step. Two costs. Tool calls that write to the customer's workspace run at least once, so a crash after the write and before the result is recorded repeats the write; each such tool takes an idempotency key derived from the run and step. And workflow histories grow with every call, so a run with hundreds of calls stores large model responses in object storage and keeps references in the history.</p>
<p>Deploys. A deploy that changes the loop would break replay for runs in flight. Anthropic uses rainbow deployments, shifting traffic gradually while old and new versions run at once. Here that means new runs start on the new version, running runs finish on the version they started on, and old workers are retired when no run on them remains: at least the longest run duration after the deploy, which a duration cap per run (say 2 hours) makes finite.</p>
<p>Replay is two tools, and conflating them costs money. Replay to see what happened reads the recorded history and re-renders each step with its inputs and outputs: no model call, no tool call. Fork to try a fix starts from a recorded step with changed code or prompt and runs forward. LangGraph's docs say that replay from a checkpoint re-executes later nodes, and that LLM calls and API requests fire again. So a fork runs with write tools pointed at a sandbox, read tools allowed or served from recordings, and its spend charged to an engineering budget, never to the customer's ledger.</p>
<p>Spend cap: the decision with two defensible answers. A soft cap enforced from the hourly billing feed is simple and adds nothing to the call path, but a customer can overshoot by up to an hour of spend: with, as scenario figures, 20 runs in parallel each burning $0.50 a minute, that is 20 × 0.5 × 60 = $600 past a contractual cap. A hard cap needs a real-time ledger in the call path: before each model call, atomically reserve its worst-case cost against the customer's remaining credit; after, settle the actual cost and release the difference. With scenario prices of $3 per million input tokens and $15 per million output tokens, a call with 100,000 input tokens and a max_tokens of 8,000 reserves 0.1 × 3 + 0.008 × 15 = $0.42; six calls in flight hold at most $2.52. I choose the hard cap because the contract says hard; the cost is a ledger write before and after every model call and a run that stops mid-research. When a reservation fails, the lead agent gets one final reserved call to write a partial report from what it has, and the run checkpoints so it can continue after a top-up. The Agent SDK's <code>max_budget_usd</code> is a per-run guard worth setting too, but its docs say it is a client-side estimate that can pass the value and does not count totals restored from a resumed session, so it cannot be the contract's enforcement.</p>
<p>Alerts, from decision patterns rather than content, as Anthropic describes:</p>
<ul>
<li>the same tool called with the same arguments more than a few times in a run;</li>
<li>spend per run above a multiple of that customer's median;</li>
<li>the age of the oldest running run past the duration cap;</li>
<li>the rate of tool calls that fail schema validation or name unknown tools;</li>
<li>resumes that fail, which mean a deploy broke replay.</li>
</ul>
</Fragment>
</Depth>

### What you give up

A ledger round trip on every model call; reports that stop early at the cap instead of finishing; a second worker version running after most deploys; and fork-based debugging that costs real model spend on an engineering budget. Reading what the agent saw needs the recorded model responses, which hold customer content, so access to the replay tool is logged and limited to engineers on a support rotation.

### The failure mode of this design

Reservations leak. A worker that dies after reserving and before settling holds credit that the customer cannot use, and a customer near the cap sees runs refused while the ledger shows unspent credit. Reservations carry an expiry a little longer than the model call timeout, and a reconciliation job releases expired ones and compares the ledger with the hourly billing feed, alerting on any difference above a few dollars. A second, quieter failure: worst-case reservations at $0.42 a call make a customer with $2 of credit left unable to start the six parallel calls a plan wants, so near the cap the lead agent must plan with fewer sub-agents rather than fail.

### Rollout plan

1. Durable runs and the read-only replay tool first, behind a flag per customer, for internal users.
2. Then the spend ledger in shadow mode: reserve and settle without refusing, and compare its totals with the billing feed for two weeks.
3. Then enforcement for one customer who agreed to it.
4. Rollback triggers:
    - ledger and billing totals differing by more than 1 percent in a day;
    - any run refused while the customer had credit;
    - resume failures above zero after a deploy.

## Follow-ups

- *The ledger adds a write before and after every model call, and the latency budget team objects. Which half do you cut, and what risk do you accept in writing?* Reserve in larger chunks, say $5 per run, refilled when spent, so most calls touch no shared state; the accepted risk is that a customer at the cap can be up to one chunk per active run short of their last few dollars of credit, refunded at reconciliation.
- *What would you need to see in production to drop the hard cap for a soft cap?* A contract change that tolerates overshoot, and measured overshoot from the soft-cap simulation in shadow mode below what the customer agrees to. The decision belongs to whoever owns the contract, not to the platform team.
- *Two senior engineers disagree: one wants every run replayable by forking from any step, the other says forks cost too much and leak customer data into engineering budgets. How do you decide without deciding by rank?* Count the incidents in the last quarter that a read-only replay could not explain, and what each fork would have cost; build the fork tool when that count justifies its cost and its access controls.
- *Anthropic reports multi-agent research runs using about 15 times the tokens of chat. A customer's finance team asks why their credit went in a week. What do you show them?* Spend per run broken down by lead agent and sub-agents, from the ledger, next to the run count; and a per-run spend limit they can set below the monthly cap.

## Common mistakes

- Restarting a crashed 30-minute run from the beginning, paying for every model call twice.
- Treating "replay" as one feature, and letting a debugging replay re-run write tools against the customer's workspace.
- Enforcing a contractual cap from a billing feed that updates hourly.
- Using a client-side per-run budget option as the contract's enforcement.
- Deploying new loop code to workers that are still running old runs, so every in-flight run fails to resume.
