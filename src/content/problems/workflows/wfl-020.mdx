## Question

<Callout kind="interview" label="Interview question">
"Build a feature that calls a hosted model. Separate transient from deterministic failures, validate the output in ordered checks, define the failure path. Then: it is costing three times what you projected. What do you do?"
</Callout>

The product, its volumes and its logs are a scenario. An accounts-payable product extracts vendor, invoice number, dates, line items, tax and total from uploaded invoices, about 10,000 a day, on Claude Opus 5.5. Users see the result in the app and approve it. A five-person operations team reviews flagged invoices and can handle 600 a day. Extraction accuracy, measured field by field on a 500-invoice labelled set, is 96%, and product will not ship anything that lowers it.

The plan priced one call per invoice: 6,000 input tokens (2,000 of instructions, about 4,000 of invoice text) and 700 output tokens. Three weeks after launch, a week of logs shows:

```text
                          plan       measured
calls per invoice         1.0        1.9
input tokens per call     6,000      9,000
output tokens per call    700        1,500
first-attempt failures    -          38%  (parse 7%, line items do not sum 22%, value not found in source 9%)
repair loop               -          up to 3 repairs; each appends the previous output and the validator's errors
```

Prices on 28 October 2026, per million tokens: Opus 5.5 $4 input, $0.20 cache read, $20 output; Haiku 5.5 $0.10 input, $0.50 output.

Design the call path, the failure classes, the validation order and the failure path, then handle the overrun. Finance wants the cost back to plan within two weeks.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each status code the provider can return, ask whether the same request can succeed later, and who has to act before it can.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the repair success rate per attempt: of invoices that fail first, how many pass after one repair, after two, after three?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Split the measured cost per invoice into calls, input and output. Which factor moved most from plan?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Classify errors by whether the same request can succeed later: retry rate limits with retry-after, 5xx, 529 and mid-stream errors in one layer with a budget; fail fast on malformed requests and oversize input; park and page on spend limits, which look like one class and behave like the other. Validate cheapest and most fundamental first: truncation, schema, field types, cross-field arithmetic, grounding in the source, policy. Allow one targeted repair, then route to review; never show unvalidated values. The overrun is 3.3x: 1.9 calls per invoice times a call that costs 1.74x plan. Fix the repair loop first, then output length, then cache the instructions; a Haiku cascade goes in as a measured experiment, not a default.</p>
</Fragment>
<Fragment slot="long">
<p><b>The call.</b> Server-side only, with the prompt and model versioned together. Use the provider's structured outputs feature for the schema rather than asking for JSON in prose; the arithmetic below assumes it removes the 7% parse failures, which the first week of traffic has to confirm, since a response cut off at max_tokens can still be incomplete. Set max_tokens from the measured p99 of output length plus a margin, and stream, so a long response does not hit the 10-minute ceiling the SDK guards against. The extraction is a pure function of document, prompt version and model, so store the result under a hash of the three: a retried request or a re-upload reads the stored result instead of paying again.</p>
<p><b>Failure classes.</b></p>
<ul>
<li>Transient, retry with backoff and jitter in one layer: 429 with retry-after (wait that long), 500 api_error, 529 overloaded_error, 504 timeout_error, connection errors, and an error event mid-stream after a 200, which discards the partial output.</li>
<li>Deterministic, fail fast and fix code or input: 400 invalid_request_error for a malformed request, 404 for a wrong endpoint or resource ID, 413 request_too_large (split the document; retrying the same bytes never works), 401 and 403 (page, since every request will fail the same way).</li>
<li>The two that look like one class and are the other: a 429 with error_code enforced_spend_limit_reached has no retry-after and fails until access resumes next month, so stop and page; a 400 that says the organisation's own spend limit was reached clears as soon as someone raises it, so park the work and page the budget owner instead of failing it.</li>
<li>A 200 whose content fails validation is not an API error. It goes to the validation path, never to the retry layer.</li>
</ul>
<p><b>Validation order.</b> Each check assumes the ones before it passed, and the cheapest deterministic checks go first. (1) Stop reason: a response cut off by max_tokens is incomplete, and repairing it with the same limit repeats the cut. (2) Schema, kept even with structured outputs. (3) Field level: dates parse, currency codes are valid, amounts are non-negative. (4) Cross-field: line items sum to the subtotal within rounding, subtotal plus tax equals total, due date is on or after the invoice date. (5) Grounding: every extracted number and the vendor name appear in the source text after normalising separators and case. (6) Policy, for example bank details that must not be stored. Arithmetic before grounding, because a total that does not add up is cheaper to detect than to look up, and its repair is different.</p>
<p><b>Failure path.</b> One repair call that names the failed check and includes only the relevant fields and source span, not the whole conversation so far. If it fails, the invoice goes to the review queue with the draft and the failed checks highlighted, and the user sees "needs review", never the unvalidated values. A provider outage takes the transient path and then the same queue, with the invoice re-run automatically when the provider recovers.</p>
<p><b>The overrun, decomposed.</b> Plan per invoice: 6,000 × $4 per million = $0.024 input plus 700 × $20 per million = $0.014 output, $0.038. Measured per call: 9,000 × $4 per million = $0.036 plus 1,500 × $20 per million = $0.030, $0.066, which is 1.74x plan; times 1.9 calls is $0.125 per invoice, 3.3x. Calls are the largest single factor, and output tokens per call more than doubled. The repair loop drives both input growth (each repair appends the previous output and errors, as Airbnb's migration retries did with validation errors) and call count.</p>
<p><b>Fixes, with the arithmetic.</b> Structured outputs and one targeted repair: with the parse failures gone, 38 − 7 = 31% of invoices still fail first and get one repair, so 1.31 calls. A repair prompt carries the instructions, the failed fields and the relevant source span, about 8,000 tokens (an assumption to check), so input averages (6,000 + 0.31 × 8,000) / 1.31 ≈ 6,500 tokens per call. With output still at 1,500: 1.31 × (6,500 × $4 + 1,500 × $20) per million = 1.31 × $0.056 ≈ $0.073, 1.93x plan. Output is now the dominant term, so measure what the extra 800 tokens are (reasoning, verbose fields, repeated line items) and cut it; at 700: 1.31 × ($0.026 + $0.014) ≈ $0.052, 1.38x. Cache the 2,000-token instruction prefix, read at $0.20 instead of $4 per million: 2,000 × $3.80 per million saves $0.0076 a call, giving 1.31 × ($0.0184 + $0.014) ≈ $0.042, 1.12x. No single lever gets there, and together they still miss plan by about 12%.</p>
<p><b>The decision.</b> Two answers are defensible. Keep Opus and fix the loop, output and cache: about 1.12x plan by this arithmetic, accuracy preserved, shippable in two weeks; it misses the target and depends on the output measurement. Or cascade: Haiku 5.5 first and Opus only when validation fails. A Haiku call at plan size costs 6,000 × $0.10 + 700 × $0.50 per million, about $0.001, so if Haiku passes validation on 60% of invoices, cost is about $0.001 + 0.4 × $0.038 = $0.016, well under plan. Its cost is a new failure mode: validation catches arithmetic and missing values, not a vendor name that is wrong and present in the text, and Instacart reported a cheaper model matching quality on simpler attributes and suffering a 60% accuracy drop on difficult ones. Recommendation: ship the first now, and run the cascade behind a flag on the 500-invoice set, per field, before any traffic moves.</p>
<p><b>How the recommendation fails.</b> Capping repairs at one sends more invoices to review. Before the fix, 38% failed first; structured outputs remove 7 points, leaving 31%. If one repair fixes half, 15.5% of 10,000 is about 1,550 invoices a day against a team that handles 600. The cap and the review capacity conflict, so the repair cap is a quantity to choose from the measured per-attempt success rate: a second repair is worth keeping only if it rescues enough invoices to pay for itself in reviewer time.</p>
<p><b>What you give up and what is written down.</b> A risk note to finance: cost comes down to about 1.12x plan with the current model, under plan only with a cascade that has to prove its accuracy first; the review queue grows until the per-attempt measurement sets the cap. Rollback trigger for each change: field accuracy on the labelled set below 96%, or review volume above capacity for two consecutive days.</p>

## Follow-ups

- *Pushback: finance wants plan cost in two weeks, operations will not take more than 600 reviews a day, and your numbers satisfy neither. Which gives, and what risk do you accept in writing?* Keep a second repair only on the checks whose measured second-attempt success is high, accept a cost somewhat above the 1.12x for the quarter, and write down that reviews are capped at 600 with overflow invoices waiting a day, with the cascade experiment as the path to plan.
- *Reversal: what would you need to see to move all traffic to the Haiku cascade?* Per-field accuracy on the labelled set within a stated margin of Opus on every field, including the hard ones, and a month of production sampling where reviewers find no more corrections on cascade invoices than on Opus invoices.
- *Operating: Opus 5.5 is retired in sixty days and the replacement scores lower on three fields in your labelled set. Which fields ship degraded, and who signs off?* Run the labelled set per field; ship if the regressions sit in fields that validation already routes to review, and get product to sign the accuracy change in writing, with those fields forced to review until the prompt is fixed.
- *Two engineers disagree about grounding: one wants exact string matching, the other a second model call to judge it. How do you decide without deciding by rank?* Run both on the labelled set and compare the false-flag rate (reviewer load) and the missed-error rate; the string match costs nothing per call, so the model judge has to beat it on missed errors by enough to pay for itself.

## Common mistakes

- Retrying every 4xx, or failing every 4xx, without reading the two spend-limit cases.
- Feeding validation failures back into the transport retry layer, which multiplies calls without changing the prompt.
- Repair prompts that append the whole conversation each time, so each attempt costs more than the last.
- Treating the overrun as a model-price problem before decomposing it into calls, input and output.
- Cutting cost with a cheaper model and measuring only overall accuracy, which hides the fields it gets wrong.
