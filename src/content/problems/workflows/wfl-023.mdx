## Question

<Callout kind="interview" label="The round">
"Our expense workflows run on Temporal Cloud. Each one waits for a finance reviewer before it pays. How does the reviewer's approve or reject get into the running workflow?"
</Callout>

What the product team has asked for:

- The reviewer clicks Approve or Reject on a web page.
- A reviewer who submitted the expense themselves, or who clicks after the request was already decided, is told so on the page.
- A double click records one decision.
- The page shows the request's current status when it loads.
- The workflow already waits on a timer for the decision deadline.

Which design fits best?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the page should show in the second after the click, and where that answer comes from.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what ends up in the workflow's history when a decision is refused, and whether anyone cares.</p></details>

## Answer

An Update with a validator. An Update is a synchronous, tracked write: `execute_update` blocks until the handler finishes and returns its result or its error, so the page can say "Approved" or "You submitted this expense" in the same request. The validator runs before the Update is accepted, and the Temporal docs say a rejected Update is not written to History. The submitter check and the already-decided check belong there. For the double click, the UI generates one Update ID when the form loads and reuses it for every click on that form; the server deduplicates Updates by Update ID within a run.

The status on page load is a Query, which reads state and never writes history. The deadline timer stays in the main workflow method: it waits on a condition that the Update handler sets, with the deadline as the timeout.

The cost of this answer. The page now depends on a Worker being up: `execute_update` waits for a Worker to run the validator and the handler, so if the Workers are down at the moment of the click, the reviewer waits. Choose a client timeout, and say what the page shows when it fires. A few seconds is reasonable for a person looking at a spinner; a timeout longer than your gateway's request timeout is not, because the reviewer then sees a gateway error with the decision possibly still in flight. On timeout, show "not recorded yet" and let the reviewer retry with the same Update ID, which makes the retry safe.

Why the wrong picks are tempting. Signal plus Query polling is the pattern the Temporal docs recommend for asynchronous requests, and the docs' comparison says its clients do not depend on the Worker being available, while an Update must wait for the Worker running the workflow to acknowledge it. It is the right answer if the page can say "submitted" and update later. Here it fails two requirements: the sender cannot receive the refusal, and a double click needs an idempotency key you design yourself. The Query that writes state is a mistake people make once: a Query handler may inspect but must not mutate, and because Queries never touch history, a decision written there would be lost on replay. The Update without a validator returns the same error to the page, which is why it looks equivalent; the difference is that every refused attempt is accepted into history first and counts toward the 2,000 Updates one execution may hold on Temporal Cloud.

## Follow-ups

- *A request needs two approvers, and both click within the same second. What does the validator see for the second click, and what does the second reviewer's page show?*
- *The workflow uses Continue-As-New every few hundred events. What happens to Update ID deduplication across the boundary?* The docs say server deduplication is per run, so the workflow carries recent Update IDs into the new run and checks them itself.
- *Your Workers are being redeployed for ten minutes at month end, when most approvals happen. Do you switch to Signals for that window, or accept the waiting page, and who decides?*

## Common mistakes

- Generating a new Update ID per click. The server then sees two different Updates.
- Putting the eligibility checks in the handler and returning a soft "not allowed" result. The refusal is recorded as an accepted Update.
- Polling a Query in a tight loop after a Signal to fake a synchronous answer. It adds load and still cannot tell the reviewer why a decision was ignored.
