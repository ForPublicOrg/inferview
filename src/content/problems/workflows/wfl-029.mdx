## Question

<Callout kind="interview" label="The prompt">
"Tonight's enrichment run has 300,000 product documents. How many batches, how long, and what do you promise the search team at 07:00?"
</Callout>

Your workflow sends each product document to Claude Sonnet 5.5 through the Message Batches API and writes structured attributes that the search indexer reads at 07:00. The run starts at 22:00.

Published limits (Claude docs, checked 2026-10-28): a batch holds at most 100,000 requests or 256 MB, whichever it reaches first. On the Build tier, at most 300,000 batch requests may sit in the processing queue, and a request counts against that limit until the model has processed it. Batches expire if processing does not finish within 24 hours; the docs say most finish within 1 hour. Batch prices for Sonnet 5.5 are $1 input and $5 output per million tokens; standard prices are $2 and $10.

Scenario inputs, measured on last night's run:

| Input | Value |
|---|---|
| Documents tonight | 300,000 |
| Items carried over from last night (expired) | 9,000 |
| Serialized request size, mean | 22,000 bytes |
| Serialized request size, p99 | 64,000 bytes |
| Input tokens per request, mean | 5,500 (1,500 of them the shared instructions and schema) |
| Output tokens per request, mean | 300 |
| Organisation tier | Build |

Estimate how many batches tonight's run needs, packing each batch as full as you judge safe. Then say what you promise the search team at 07:00 and what that promise costs.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for last night's request file size in bytes alongside its request count.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the end-to-end completion time of every batch over the last 30 nights, as a distribution rather than an average.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the search team what the indexer does today with a product whose attributes are a day old, and with a new product that has none.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>About 27 batches, not 4. Tonight is 309,000 requests at 22,000 bytes each, 6.8 GB in all, and the 256 MB cap fills at about 11,600 requests, long before the 100,000-request cap. Packed to 100 percent that is 27 batches; with 20 percent headroom, 34. The queue holds 300,000, so the last 9,000 requests wait until the first batches drain. Duration has no published bound below 24 hours, so the 07:00 promise is per item: every product carries its enrichment date, new products get a synchronous lane with a cap, and existing products keep yesterday's attributes until their batch lands.</p>
</Fragment>
<Fragment slot="long">
<p>Which cap binds. 309,000 requests × 22,000 bytes = 6,798,000,000 bytes. At 256,000,000 bytes per batch, one batch holds 11,636 requests at the mean, so the byte cap binds at about a ninth of the count cap. The count cap would bind only for requests under 256,000,000 / 100,000 = 2,560 bytes, which a document enrichment request never is.</p>
<p>Batches. 6,798 MB / 256 MB = 26.6, so 27 batches packed full. Pack by measured bytes per request, not by count, and the p99 of 64,000 bytes does not matter. The headroom you choose covers what you cannot see: whether the limit is 256 MB or 256 MiB (which gives 26) and how the API counts the request envelope. At 90 percent fill: 30 batches. At 80 percent: 34.</p>
<p>Queue. 309,000 is 9,000 over the Build tier's 300,000-request queue. Submit 25 full batches (290,900 requests) at 22:00 and the last two when the first batches' request counts show room. Submit the carried-over items in the first batch, because they are already a day late.</p>
<p>Duration. The docs give "most within 1 hour" and a 24-hour expiry, and say processing may slow with demand and with your own volume. Neither is a 07:00 guarantee. Your own last 30 nights are the only basis for a promise, and even their p99 is not a bound.</p>
<p>Cost. Per request at batch prices: 5,500 × $1 / 1M + 300 × $5 / 1M = $0.0055 + $0.0015 = $0.007. The night costs 309,000 × $0.007 = $2,163. The same request at standard prices costs $0.014.</p>
<p>The promise, two defensible versions.</p>
<p>Complete by 07:00. At 05:00, cancel unfinished batches (canceled requests are not billed and the batch ends with partial results) and send the rest synchronously. The sync lane shares the organisation's Sonnet 5.5 limits: 5,000,000 input tokens per minute on the Build tier. If online traffic uses 1,500,000 of that at 05:00 (scenario), 3,500,000 × 120 minutes = 420M tokens, or 420M / 5,500 = 76,000 requests, which is a quarter of the night. RPM (636 a minute) and output tokens are far from their limits; input tokens bind. The cost is up to 76,000 × $0.007 = $532 more a night, two hours with most of the organisation's input budget, and a promise that breaks whenever more than a quarter of the night is late.</p>
<p>Per-item freshness. At 07:00 the indexer reads whatever has landed; every row carries its enrichment date and run id; unfinished products keep yesterday's attributes and land within the 24-hour window. The cost is a downstream that must handle mixed freshness, and new products that have no attributes at all until their batch ends.</p>
<p>Recommendation: per-item freshness for existing products, plus a capped sync lane for new products only, because a new product without attributes does not appear in search and an existing one with day-old attributes mostly does. Its failure mode: a catalogue import of 150,000 new products in one night turns the capped lane into most of the run, and it collides with online traffic at the cap. The cap has to be a number in the runbook (say 20,000 requests), with the overflow falling back to the batch path and an alert to the catalogue team.</p>
</Fragment>

Answers from 26 to 36 batches count: 26 if you read the limit as 256 MiB and pack full, 36 at 75 percent fill. The dominant term is bytes per request: total bytes over 256 MB sets the count, and request count barely matters. The assumption that flips the conclusion is request size; under 2,560 bytes per request the 100,000-request cap binds and the answer is 4.

Unreasonable answers: 4 batches, from the request cap alone, which the API rejects at the first oversized batch; anything that packs by request count with a fixed number per batch, because a run with longer documents then fails at create time; and fill below about 70 percent defended as safety, since packing by measured bytes leaves nothing to be safe against beyond the unit question. Splitting into many smaller batches so that results arrive earlier is a separate, defensible choice, because a batch's results are available only when all its requests have ended; it answers a latency question, not this one.

Prompt caching does not change the plan. The docs describe cache hits inside a batch as best effort and report typical hit rates from 30 to 98 percent, so budget the night at full input price and count any cache saving as margin.

## Follow-ups

- *Two senior engineers disagree: one wants a 05:00 cutoff for everything, the other wants batch only. How do you decide without deciding by rank?* Put both through the last 30 nights' completion times and the indexer's staleness cost per product, and pick the one whose worst night is cheaper.
- *An expired item expires again tomorrow. How many nights before it stops being retried, and where does it go?* Choose a number (two re-submissions is reasonable) and send the item to a dead-letter list with its last error, owned by a named team.
- *OpenAI-style flex processing bills at batch prices and can return 429 when capacity is short. Does a lane like that replace the 05:00 sync lane?* For stragglers with hours to spare, it can: batch price, no charge on the 429, retry with backoff. Not for new products due at 07:00, because a 429 at 06:30 leaves only the standard lane.
- *The organisation moves to the Scale tier. What changes in tonight's plan?* The queue holds 500,000, so all 309,000 requests go in at 22:00, and the sync lane gets 10,000,000 input tokens per minute; the batch count does not change, because the byte cap is per batch.

## Common mistakes

- Dividing by 100,000 and never checking the byte cap.
- Treating "most batches finish within 1 hour" as a service level.
- Budgeting the fallback lane in dollars and forgetting that it spends the same rate limit as the online product.
- Promising "complete by 07:00" without saying what happens to the products that are not.
