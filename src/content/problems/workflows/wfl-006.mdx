## Question

<Callout kind="interview" label="Behavioural">
"Tell me about an automated migration you ran where the last part would not automate. How did you get the long tail, and how did you decide to stop automating?"
</Callout>

If you have not run one, answer for this case, which is a scenario: your team moves about 2,000 test files from one testing library to another with a model-driven pipeline. Each file passes through refactor, fix tests, fix lint and types, and advances only when that stage's checks pass. The first sweep finishes in an afternoon with 75 percent of files through every stage. The old library's last supported version stops receiving security fixes in ten weeks, and two product teams have said they cannot spare engineers for the migration.

Say what you did with the 25 percent, what you checked about the 75 percent, the point at which you stopped automating and the number behind it, and what you wrote down.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what "passed" means for a migrated file: which checks ran, and whether anyone compared the new test's assertions with the old one's.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the failures of the remaining files grouped by error signature, with counts.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask who owns a file the pipeline gives up on, and by what date.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Audit the 75 percent before chasing the 25: a pipeline whose gate is "tests pass" can pass by weakening tests, so compare assertion counts and coverage per file and hand-review a sample. Then group the failures by signature and run sample, tune, sweep cycles, as Airbnb did to go from 75 to 97 percent in four days. Stop when a cycle fixes fewer files than the same engineer-days would fix by hand, or when the remaining failures share no pattern; hand the rest to engineers starting from the pipeline's best failed attempt. Write the stop decision and the residual risk down.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What the 75 percent is worth.</strong> The state machine advances a file when its tests, lint and types pass. A model under retry pressure can satisfy that by deleting an assertion, loosening a matcher or skipping a case. So the first action is a check the pipeline did not run: per file, compare assertion count and line coverage of the component under test before and after, flag any drop, and have an engineer read a random sample of passed files. If the sample finds weakened tests, the pass rate is not the success rate, and the gate gets a new stage before any sweep continues.</p>
<p><strong>Getting the tail.</strong> Group the failed files by the first error each stage hit. The largest groups usually share a cause the prompt does not handle: a helper the model never saw, a mocking pattern, a custom matcher. Airbnb's loop was to sample 5 to 10 files from a group, change the prompt or the files pulled into context, rerun the sample, then sweep every remaining file; they report that choosing the right related files mattered more than prompt wording, and that plain retries with the validation errors fed back were effective, with long-tail files retried 50 to 100 times.</p>
<p><strong>When to stop, with the number.</strong> Airbnb's sample, tune and sweep loop moved from 75 to 97 percent of nearly 3,500 files in four days, about 770 files or roughly 190 a day on average. The last just-under-100 files took about another week by hand. The stop rule that generalises: after each cycle, compare files fixed per engineer-day by tuning with files fixed per engineer-day by hand on a sample of the remaining failures. Stop tuning when the first falls below the second, or when a sample of the remaining failures shows no shared cause, since a prompt change then helps only the file it was written for. The average rate overstates the last cycles; what matters is the marginal rate, so record files fixed per cycle, not only the running total. Reasonable thresholds stop somewhere between one and two times the hand rate (tuning also carries over to the next migration); continuing well below the hand rate is sunk cost.</p>
<p><strong>The decision with two defensible answers.</strong> Keep automating the tail: it saves the product teams' time, which they said they do not have, and improves the pipeline for the next migration, at the cost of engineer-days on tooling and a growing risk that the model satisfies checks for odd files in odd ways. Or hand-fix the tail, starting from the pipeline's best failed attempt: predictable, finished before the security deadline, at the cost of asking the product teams for time and of uneven style in the hand-fixed files. With ten weeks to the deadline and two teams refusing time, a mixed answer is usual: the platform team hand-fixes the tail itself, and the product teams review rather than write.</p>
<p><strong>Where this answer fails.</strong> The assertion and coverage audit catches deleted and skipped checks, not changed meaning: a test that asserts on a different element than the original passes the audit. The random sample is the only defence, and it is small; say so when reporting the result.</p>
<p><strong>Written down.</strong> A one-page status note: files migrated, files hand-fixed, the audit method and what the sample found, the stop rule and the cycle numbers that triggered it, the residual risk (tests whose meaning may have changed), and the owner and date for each file still open.</p>
</Fragment>

## Follow-ups

- *Pushback: your audit (coverage runs plus a reviewed sample) costs more engineer time than the tail it protects. Which half do you cut, and what risk do you accept in writing?* Keep the automated assertion and coverage comparison, which is cheap after the first run, and shrink the human sample to the files the comparison flagged plus a small random set; write down that changed-meaning tests outside the sample will reach the main branch.
- *Reversal: what would you need to see to restart automation on the remaining files instead of hand-fixing them?* A new model or a new context source (for example the component's storybook or type definitions) that, on a sample of the remaining failures, fixes a share large enough to beat the hand rate on the next cycle.
- *Two staff engineers disagree: one says stop at 90 percent and hand the rest to the owning teams, the other says push to 99 percent with the pipeline. How do you decide without deciding by rank?* Agree on the measure first (marginal files per engineer-day from the last cycle against a timed hand-fix sample), run one more cycle and one hand-fix day, and let the two numbers decide.
- *The security deadline moves up to four weeks. What changes?* The tail is hand-fixed now by the platform team, the audit shrinks to the automated comparison, and files that cannot be migrated in time are pinned to the old library with a dated exception and an owner.

## Common mistakes

- Reporting the pass rate as the success rate without checking what passing means.
- Tuning prompts file by file once the remaining failures share no cause.
- Deciding when to stop from the average automation rate instead of the last cycle's.
- Leaving the hand-fixed tail without an owner and a date.
- Leaving the stop decision without a named owner and the numbers behind it.
