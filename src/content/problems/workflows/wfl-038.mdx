## Question

Finance operations wants to automate invoice exceptions. An invoice that fails the three-way match against its purchase order and goods receipt gets a model-written summary of the mismatch, the budget owner approves or rejects it in Slack, and the result is written to the ERP, where an approval releases the payment hold. The ERP's weekly payment run pays released invoices under its own controls.

Scenario facts:

- Two operations analysts already run about 30 internal automations on a self-hosted n8n: one instance, default database, no queue mode.
- Another team suggests Dify instead, because its LLM nodes are better.
- Engineering has no capacity until next quarter.
- About 400 exceptions a week are handled by hand today.
- The product manager mentions that "customers would love this summarizer too".

Do you agree to build it in n8n or Dify now? Write the conditions you would attach, and the specific signals that would move it to code. Each signal must be something you could check.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask who will be paged when a run fails at 2 a.m. during quarter-end close, and who can edit the workflow in production.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what happens to a run that is waiting on a Slack approval when the instance restarts or is upgraded. Ask for a test, not an opinion.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the product manager whether "customers" means people outside the company, and ask legal which licence each tool's self-hosted edition is under.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Yes to n8n now, as an internal tool with written conditions. The case for it: the work is internal, operations owns it, there are a handful of steps, and a human approves every decision before the ERP's own payment controls act on it. The conditions: the ERP write is one idempotent call keyed by invoice id; the workflow definition is exported to git and changes are reviewed; restarts mid-approval are tested before launch; and errors route to a branch that reaches a person. It moves to code on checkable signals: any use by people outside the company, any step that pays rather than releases a hold, a second incident from an unreviewed edit, or a requirement for tests in CI. The licences decide the product question on their own: n8n's licence limits use to internal business or non-commercial purposes, and Dify's forbids operating a multi-tenant service from its source without written permission.</p>
</Fragment>
<Fragment slot="long">
<p>The choice turns on durability, testing, versioning, review, tenancy and licence, not on which canvas is nicer.</p>
<p>Two answers are defensible. Agreeing now clears about 400 manual exceptions a week a quarter earlier, with the people who understand the process owning it. The cost is a finance control with no tests in CI and weak change review, run by a team that is not on call for software. Refusing and building it in code next quarter, on the same engine the product uses, gets tests, review, versioning and an owner who is on call. The cost is another quarter of manual work during a close, and a spec written by engineers who do not know the exceptions as well as the analysts do. I take the first because a human approves every decision and the ERP's payment run has its own controls, so the blast radius of a bad run is a wrongly released hold that the payment run still has to pay. If the workflow paid invoices itself, I would take the second.</p>
<p>Durability is the condition to test, not to assume. An approval can wait days in Slack. Start ten runs, restart the instance while they wait, upgrade it once, and count how many complete with the right result. If fewer than ten do, the design changes: store the pending approval in a table keyed by invoice id and make the Slack response start a fresh run that reads it, so no run has to survive a restart.</p>
<p>Scaling has a cost the analysts may not see. If volume or reliability needs more than one instance, n8n's queue mode needs Redis and Postgres, does not support SQLite for that setup, and does not support filesystem binary data, so attachments such as invoice PDFs need S3-style storage. Multi-main is an Enterprise feature for self-hosted installs. That is a platform for someone to run, which is the point where engineering is involved anyway.</p>
<p>Dify's case is its LLM nodes, and its error handling is explicit: LLM, HTTP, Code and Tool nodes default to stopping the whole workflow on failure, with a default value or a fail branch as options. For an approval flow the fail branch to a human queue is the setting to require. Its licence also matters: Dify's modified Apache 2.0 says one tenant is one workspace and forbids operating a multi-tenant environment from the source without written authorization.</p>
<p>The product manager's remark is the strongest signal to move to code, and the licences settle it before any engineering argument does. n8n's Sustainable Use License permits use "only for your own internal business purposes or for non-commercial or personal use". Offering the summarizer to customers inside a paid product is neither, and running it per customer workspace on Dify is the multi-tenant case its licence names. Legal reads both before anyone builds the customer version; the engineering answer is that the customer version is code from day one.</p>
</Fragment>
</Depth>

### The decision memo

> **Decision.** Operations builds invoice-exception approvals in the existing n8n instance for internal use. Review date: end of next quarter.
>
> **Conditions before launch.**
> - The ERP write is a single call keyed by invoice id; a repeated call with the same id changes nothing.
> - The workflow JSON is exported to a git repository on every change; an engineer reviews changes to the ERP step.
> - The ten-run restart test passes.
> - Every node that calls the model or the ERP has a failure path to a named person, not a silent stop.
>
> **Move to code when any of these is true.** Checked monthly by the analyst who owns the workflow; at the review date by engineering.
> - Anyone outside the company uses it, or it is offered in a product.
> - A step pays, credits or refunds money directly rather than releasing a hold.
> - A second production incident is caused by an edit made without review.
> - The audit team asks for test evidence for the control.
> - The workflow passes about 15 steps or calls a second system of record. This number is my choice: it is roughly where a canvas stops being readable in one screen. Anything between 10 and 20 is defensible; "never" is not.
>
> **What we give up.** No automated tests of the summarizer prompt; change history only as good as the export discipline; operations is on call for a finance control during close.

The failure mode of this recommendation is drift. Each month someone adds a step: a currency conversion, a second approver for large amounts, a write to the data warehouse. None of them trips a signal on its own, and a year later the canvas is the system of record for a finance control that nobody in engineering has read. The review date and the step count in the memo exist for this; the memo needs an owner who checks them, or they decide nothing.

## Follow-ups

- *Finance pushes back: the conditions delay launch by three weeks during close. Which condition do you drop, and what risk do you accept in writing?* Drop the git review of non-ERP steps and keep the idempotent ERP write and the restart test; the accepted risk is an unreviewed change to the summary prompt producing misleading summaries, which the approver still reads before deciding.
- *What would you need to see in production to reverse the decision and move it to code before the review date?* A run that released a hold the approver rejected, or two restart losses in a month. Either means the tool's durability or the integration is not holding, and every week of delay adds exceptions handled wrongly.
- *The platform team wants every company workflow on one engine, and operations wants n8n. Two senior people disagree; how do you decide without deciding by rank?* Score both against the same written criteria (durability test result, test coverage, change review, licence, on-call owner) for this workflow, and let the criterion that fails decide; one engine for everything is a preference until it is tied to a failure.
- *Dify's LLM nodes are better for the summary. Can you use Dify for that step only?* Yes, as an internal service that n8n calls over HTTP, which keeps the approval state in one place; the cost is a second platform to patch and a second place where the prompt lives.

## Common mistakes

- Arguing about canvases, node libraries or model support instead of durability, testing, versioning, review, tenancy and licence.
- Reading n8n's or Dify's licence as plain open source and planning the customer version on it.
- Accepting "it has a wait node" as proof that approvals survive restarts, without running the restart test.
- Leaving error handling at the default, so a failed model call stops the run and the invoice sits with no owner.
- Writing move-to-code triggers nobody can check, such as "when it gets complex".
