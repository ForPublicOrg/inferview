## Question

<Callout kind="interview" label="Design discussion">
"For each of these, which pattern do you build: a prompt chain, a router, parallel calls, orchestrator-workers or evaluator-optimiser? Then tell me how your choice fails in production."
</Callout>

1. **Support inbox.** Incoming email for a SaaS product goes to one of four existing teams: billing, account access, bug reports and sales. Each team already has its own prompt, tools and escalation path. A month of hand-labelled email exists.
2. **Release notes in nine languages.** An English changelog becomes release notes in nine languages. Legal requires about 300 product and contract terms to appear exactly as in an approved glossary for each language.
3. **Analytics question.** A finance user asks "why did EMEA gross margin drop last quarter?" against a warehouse of several hundred tables. Which tables, joins and breakdowns are needed depends on what the first queries show.

Give one pattern per system, the reason, the failure mode you would monitor and the cost or latency you accept.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each system, ask whether the list of steps is known before the input arrives.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which of the success criteria a program can check without a model.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For the inbox, request the confusion matrix of a classifier on the labelled month, not its accuracy alone.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Inbox: a router, because the categories are distinct and each already has its own handling; its confusion matrix is the system's error floor, so misroutes between account access and billing are what to watch. Release notes: a chain per language (translate, then a deterministic glossary gate, then a repair step only for the terms the gate flags), not evaluator-optimiser, because the hard criterion is checkable by code; it fails on meaning errors the glossary gate cannot see. Analytics: orchestrator-workers, because the subtasks depend on intermediate results; the plan is model output that needs validation and caps, and it costs many times a single call.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Support inbox: router.</strong> The input falls into distinct classes with separate downstream handling, which is the case routing is for, and the labelled month lets you measure the classifier before shipping. The router's errors bound the whole system: a downstream team cannot fix an email it never receives. Measure the confusion matrix rather than accuracy, because errors are not symmetric: an account-takeover report sent to sales is worse than a pricing question sent to billing. Add an explicit low-confidence route to a human queue, and decide its threshold from how many emails per day that queue can absorb. Failure mode in production: the input mix drifts (a new product launch, a phishing wave) and the classes stop covering it; track the share of low-confidence and human-routed emails per week as the drift signal. Cost: one small-model call per email, a fraction of the downstream handling.</p>
<p><strong>Release notes: chain with a code gate.</strong> Evaluator-optimiser is tempting, since translation is Anthropic's own example of that pattern, but here the criterion legal cares about (exact glossary terms) is checkable by string matching against the glossary. A gate in code is cheaper, deterministic and cannot be talked out of a failure. The chain is translate, gate, and a repair call that receives only the flagged sentences and the required terms, rerun through the gate with a cap of two repairs before a human translator sees it. Run the nine languages in parallel, since they are independent. Failure mode: the gate passes text that uses every required term and still changes the meaning, and inflection in languages such as German or Polish can make an exact-string rule reject correct text. Accept the gate's false rejects into human review and sample passed outputs for a native-speaker check on the first releases. A model reviewer can be added later for fluency, with a different model or a separate rubric prompt, because evaluators favour their own outputs.</p>
<p><strong>Analytics question: orchestrator-workers.</strong> The subtasks (which regions, which product lines, which cost lines) cannot be listed before the first queries return, which is the condition Anthropic gives for this pattern. An orchestrator plans queries, workers run them and summarise, the orchestrator decides whether to dig further. Failure modes: the plan is model output and gets the same validation as a tool call (allowed tables only, read-only role, row and cost limits per query); the orchestrator over-spawns or duplicates work, as Anthropic reports of its early research system with 50 subagents for simple queries; and the final explanation can read well while resting on a wrong join. Cost: Anthropic measured multi-agent runs at about 15 times the tokens of a chat, so cap workers per question and total tokens, and keep a single-agent path for questions a fixed dashboard query already answers.</p>
<p>The choice for each system can be wrong. If the inbox classes overlap heavily (a billing dispute that is also an access problem), routing to one team loses half the request and a chain with an extraction step that tags several intents may be better. If the glossary covers most of the risk but tone matters to marketing, an evaluator step earns its place after the gate, not instead of it.</p>

## Follow-ups

- *The router is 96 percent accurate overall and 70 percent on account-access emails. Ship it?* Not for that class: account access is low volume and high harm, so overall accuracy hides it. Send that predicted class, and anything confused with it, to a human queue until a targeted fix lifts its recall.
- *Legal adds a per-language rule: some terms stay in English in one language and are translated in another. Where does that rule live?* In the glossary data the gate reads, keyed by language, never in the translation prompt alone; the prompt can mention it, the gate enforces it.
- *The analytics orchestrator costs more per question than the analyst on simple questions. What do you change?* Put a router in front: questions that match a known metric and breakdown go to a fixed query template, and only the rest reach the orchestrator; measure the share that takes each path.

## Common mistakes

- Choosing evaluator-optimiser for a criterion a program can check.
- Reporting router accuracy without the per-class confusion matrix.
- Treating an orchestrator's plan as trusted input to tools.
- Picking orchestrator-workers when the steps are known in advance, and paying its token multiple for nothing.
- Naming a pattern without the failure signal you would monitor after launch.
