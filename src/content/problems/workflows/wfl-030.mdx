## Question

<Callout kind="interview" label="The prompt">
"Since the nightly enrichment moved to the batch API, merchandisers report products with another product's attributes. Here is the job and what we have. What happened, and what do you do tonight?"
</Callout>

```python
def build_requests(products):
    reqs = []
    for p in products:
        if not p.description:
            continue  # nothing to enrich
        reqs.append({
            "custom_id": p.sku,
            "params": {"model": MODEL, "max_tokens": 400, "system": SYSTEM,
                       "messages": [{"role": "user", "content": p.description}]},
        })
    return reqs


def run_nightly(products):
    batch = client.messages.batches.create(requests=build_requests(products))
    wait_until_ended(batch.id)
    results = [r for r in client.messages.batches.results(batch.id)
               if r.result.type == "succeeded"]
    for product, r in zip(products, results):
        attrs = json.loads(r.result.message.content[0].text)
        db.upsert_attributes(product.sku, attrs, run_date=today())
```

## Answer

The join is positional. `zip(products, results)` pairs the nth product with the nth succeeded result, and three things break that alignment: the results stream returns in any order (the Claude and OpenAI docs both say so and both tell you to match on `custom_id`), products without a description are in `products` but not in the batch, and errored and expired results are filtered out before the zip. Any one of these misaligns every pair after the first gap. The counts already show two of them: 148,000 products against 142,000 requests (139,880 + 214 + 1,906), so 6,000 products were skipped, and 2,120 requests failed. `zip` also stops at the shorter list, so the last 8,120 products in `products` received nothing, which is one way KB-0042 went stale.

Why the wrong picks are tempting. Raw SKUs as `custom_id` are a real risk: the documented pattern allows letters, digits, hyphens and underscores up to 64 characters, and a SKU with a slash or a dot breaks it. But a rejected request leaves old attributes in place; it cannot put a hose's attributes on a television. A 400-token cap does truncate long attribute lists, but truncated output fails `json.loads`, which raises, stops the loop and leaves everything after it stale. Prompt caching reuses the processed prefix of a prompt, not a previous reply, so it cannot serve one product's answer to another.

Ranking the defects that are really there:

1. Positional join. Explains the symptom, and corrupts data silently.
2. Failures dropped without reconciliation. 2,120 products got nothing last night and nobody knows which ones. Errored requests split in two: an `invalid_request_error` needs the request fixed, anything else can be re-sent as is, and expired requests can be re-sent as is.
3. No `stop_reason` check and an unguarded `json.loads`. One truncated reply aborts the rest of the run.
4. Raw SKUs as `custom_id`. Latent until the first SKU with a slash or more than 64 characters.

The repair has a failure mode of its own: re-joining stored results writes last night's model output, so for any product whose description changed since then, the repair is consistent but stale. Mark repaired rows with the original run_date, not today's, so the next run treats them as due.

```python
def run_nightly(products):
    ledger = {f"r{i}": p for i, p in enumerate(p for p in products if p.description)}
    reqs = [{"custom_id": cid, "params": params_for(p)} for cid, p in ledger.items()]
    batch = client.messages.batches.create(requests=reqs)
    wait_until_ended(batch.id)
    seen, retry, dead = set(), [], []
    for r in client.messages.batches.results(batch.id):
        p, res = ledger[r.custom_id], r.result
        seen.add(r.custom_id)
        if res.type == "succeeded" and res.message.stop_reason == "end_turn":
            attrs = parse_and_validate(res.message.content[0].text)
            if attrs is not None:
                db.upsert_attributes(p.sku, attrs, run_date=today())
                continue
            dead.append((p.sku, "invalid output"))
        elif res.type == "errored" and res.error.error.type == "invalid_request_error":
            dead.append((p.sku, "invalid request"))
        else:
            retry.append(p)  # expired, server error, or cut off at max_tokens
    assert seen == set(ledger), "every request has exactly one result"
    schedule_retry(retry)
    report_dead_letters(dead)
```

Cut-off replies go to the retry list here; re-send them with a larger `max_tokens`, or they truncate again.

## Follow-ups

- *Your fix re-sends expired items the next night. The search team says two nights of staleness is too long for new products. What do you change?* Re-send failed new products through the synchronous API the same night, capped, and report how many hit the cap.
- *The ledger lives in memory. The worker restarts while results are streaming. What happens?* Persist the ledger before creating the batch, and make the write idempotent per (run, custom_id), so re-processing the stream after a restart writes the same rows again.
- *How do you prove the repaired data is right?* Re-run the diff after the repair: zero rows where the written SKU differs from the ledger SKU, and a spot audit of 50 products against their descriptions.

## Common mistakes

- Sorting the results by custom_id and zipping again; skipped and failed items still shift the pairs.
- Re-running the whole night at full cost when the results are stored for 29 days.
- Retrying invalid_request_error items unchanged; they fail the same way every night.
- Fixing the join and leaving `zip`'s silent truncation as the way failures disappear.
