    class Scheduler:
        """Leases runnable tasks to workers, earliest deadline first.

        Time is passed in by the caller and never goes backwards. A lease taken at
        time t lives while now < t + lease_seconds.
        """

        def __init__(self, lease_seconds):
            self.lease_seconds = lease_seconds

        def add(self, task_id, deadline, prereqs=()):
            """Register a task. Raise ValueError for a duplicate id or an unknown prerequisite."""
            raise NotImplementedError

        def lease(self, worker, now):
            """Lease the runnable task with the earliest deadline to worker and return its id, or None."""
            raise NotImplementedError

        def heartbeat(self, task_id, worker, now):
            """Extend worker's live lease on task_id to now + lease_seconds. Return True if extended."""
            raise NotImplementedError

        def complete(self, task_id, worker, now):
            """Mark task_id done if worker may complete it. Return True if accepted."""
            raise NotImplementedError

    import heapq


    class Scheduler:
        def __init__(self, lease_seconds):
            self.lease_seconds = lease_seconds
            self.deadline = {}
            self.waiting_on = {}      # task -> number of prerequisites not yet done
            self.dependents = {}      # task -> tasks that wait on it
            self.done = set()
            self.ready = []           # heap of (deadline, task) for runnable, unleased tasks
            self.holder = {}          # task -> (worker, expires_at) for leased tasks
            self.expiries = []        # heap of (expires_at, task, worker); stale entries are skipped

        def add(self, task_id, deadline, prereqs=()):
            if task_id in self.deadline:
                raise ValueError(f"duplicate task {task_id!r}")
            for p in prereqs:
                if p not in self.deadline:
                    raise ValueError(f"unknown prerequisite {p!r}")
            self.deadline[task_id] = deadline
            self.dependents[task_id] = []
            pending = 0
            for p in set(prereqs):
                if p not in self.done:
                    pending += 1
                    self.dependents[p].append(task_id)
            self.waiting_on[task_id] = pending
            if pending == 0:
                heapq.heappush(self.ready, (deadline, task_id))

        def _reclaim(self, now):
            while self.expiries and self.expiries[0][0] <= now:
                expires_at, task, worker = heapq.heappop(self.expiries)
                if self.holder.get(task) == (worker, expires_at):
                    del self.holder[task]
                    heapq.heappush(self.ready, (self.deadline[task], task))

        def lease(self, worker, now):
            self._reclaim(now)
            while self.ready:
                _, task = heapq.heappop(self.ready)
                if task in self.done or task in self.holder:
                    continue
                expires_at = now + self.lease_seconds
                self.holder[task] = (worker, expires_at)
                heapq.heappush(self.expiries, (expires_at, task, worker))
                return task
            return None

        def heartbeat(self, task_id, worker, now):
            self._reclaim(now)
            held = self.holder.get(task_id)
            if held is None or held[0] != worker:
                return False
            expires_at = now + self.lease_seconds
            self.holder[task_id] = (worker, expires_at)
            heapq.heappush(self.expiries, (expires_at, task_id, worker))
            return True

        def complete(self, task_id, worker, now):
            self._reclaim(now)
            held = self.holder.get(task_id)
            if task_id in self.done or held is None or held[0] != worker:
                return False
            del self.holder[task_id]
            self.done.add(task_id)
            for d in self.dependents[task_id]:
                self.waiting_on[d] -= 1
                if self.waiting_on[d] == 0:
                    heapq.heappush(self.ready, (self.deadline[d], d))
            return True

## Question

<Callout kind="interview" label="Coding round">
"Model pipelines hand out work to a pool of workers. Write the in-process scheduler that decides which task a worker gets next."
</Callout>

Implement `Scheduler(lease_seconds)` with four methods. Time is an argument (`now`, a number that never goes backwards), so the tests can move the clock.

- `add(task_id, deadline, prereqs=())` registers a task. It raises `ValueError` for a duplicate id or for a prerequisite that has not been added.
- `lease(worker, now)` gives `worker` the runnable task with the earliest deadline and returns its id, or `None` when nothing is runnable. A task is runnable when every prerequisite is complete, it is not complete itself, and nobody holds a live lease on it. A lease taken at time `t` is live while `now < t + lease_seconds`.
- `heartbeat(task_id, worker, now)` extends a live lease held by `worker` to `now + lease_seconds` and returns `True`; otherwise it returns `False`.
- `complete(task_id, worker, now)` returns `True` when the completion is accepted and the task is done. A worker holding a live lease can always complete. A worker whose lease passed to another worker cannot. A task completes at most once.

Workers crash without telling anyone; a crashed worker stops sending heartbeats. Execution is at least once: a task may run twice across a crash, but no task is ever leased to two workers whose leases are live at the same time.

Two decisions are yours, and the hidden tests accept either answer as long as the rules above hold: how to break a tie between equal deadlines, and what to do with a late completion from a worker whose lease expired while nobody else took the task. Write your choice and its cost next to the code.

The visible tests end with 40,000 tasks pushed through `add`, `lease` and `complete` in under 5 seconds; the hidden tests add a fan-out and a fan-in of the same size.

## Answer

The reference solution keeps five structures. `ready` is a min-heap of `(deadline, task_id)` holding runnable, unleased tasks. `holder` maps a leased task to `(worker, expires_at)`. `expiries` is a min-heap of `(expires_at, task_id, worker)`. `waiting_on` counts each task's unfinished prerequisites, and `dependents` is the reverse edge list. Every public method first pops the `expiries` entries with `expires_at <= now`; an entry reclaims its task only if `holder` still has exactly that `(worker, expires_at)` pair, so a heartbeat, which pushes a new entry, makes the old one stale without a delete. `lease` pops `ready` until it finds a task that is neither done nor held. `complete` checks the holder, marks the task done and decrements `waiting_on` for each dependent, pushing the ones that reach zero.

Each call costs `O(log n)` amortised, and each completion touches only its own dependents, so prerequisite bookkeeping for the whole graph is `O(V + E)`. A scan that rechecks every task on each `lease` is `O(n)` per call: at 40,000 calls that is 40,000 × 40,000 / 2 = 800 million task visits, far past the test's budget in any Python interpreter.

Requiring prerequisites to exist at `add` time makes the graph acyclic by construction, since an edge always points to an older task, so no cycle check is needed. Prerequisite lists are deduplicated with `set(prereqs)`; counting `len(prereqs)` leaves a task with a repeated prerequisite blocked forever, and the hidden tests include one.

The two policy decisions:

- Tie-break. Breaking ties by `task_id` makes runs reproducible, which matters when a replay of a production trace must hand out the same order. Breaking ties by submission order is fairer to callers who submit early. The heap tuple decides; the tests check only that the returned deadline is the minimum among runnable tasks.
- Late completion with nobody else holding the task. The reference rejects it: the expired lease is reclaimed on the next call, the task goes back into `ready`, and it runs again. That costs a second execution of work that already finished. Accepting it saves the rerun, but `complete` must then also pull the task out of `ready`, and the scheduler has taken a result from a worker it had already declared dead, which is the case where that worker may have been paused rather than crashed and may still be writing.

The constraint conflict is recovery time against duplicate work. A short `lease_seconds` recovers a crashed worker's task quickly but turns every slow run into a duplicate; a long one avoids duplicates and leaves a crashed worker's task idle for the whole lease. Choose it from the measured run time of the task type: without heartbeats, a lease below the p99 run time duplicates at least the slowest one percent of runs; with a heartbeat every third of the lease, the lease can stay short.

A failure mode of this answer: the `expiries` heap grows by one entry per heartbeat and shrinks only as entries come due. A worker heartbeating every second on a 60-second lease keeps about 60 entries per task in the heap. Memory stays bounded by heartbeat rate × lease length × leased tasks, which is fine at this scale; with frequent heartbeats, rebuild the heap from `holder` when stale entries outnumber live ones by a factor you pick.

## Follow-ups

- *What changes to run this against a real database with several scheduler processes?* The in-memory `holder` becomes a row with a lease version. `lease` becomes `SELECT ... ORDER BY deadline LIMIT 1 FOR UPDATE SKIP LOCKED` followed by an update that sets the holder and the expiry from the database clock, never the worker's. `complete` becomes a conditional update on the lease version, and the version doubles as a fencing token that the side-effect target checks, so a worker that paused past its lease cannot write after its successor.
- *Pushback: fencing means every downstream system checks a version you own, and two of them are third-party APIs that cannot. Which guarantee do you drop, and what goes in the runbook?* For those targets, send the idempotency key the API accepts, keyed on the task id; accept in writing that a paused worker can still race inside the provider's key window; and before rerunning a task whose holder expired mid-call, query the target for the outcome.
- *Reversal: what would you need to see in production to switch from rejecting late completions to accepting them?* A measured cost per duplicate run (model spend or downstream rework) that outweighs the rare unsafe acceptance, and lease logs showing that expired-lease completions almost never come from a worker that is still running.
- *The pool is overloaded and some tasks will miss their deadlines whatever you do. Do you keep earliest deadline first?* Under overload it keeps serving tasks that will miss anyway and drags others past their deadlines with them. Admission control (refuse or demote a task whose deadline is closer than its expected run time) or ordering by the cost of a miss can do better; decide from the measured miss cost per task class.

## Common mistakes

- Scanning every task on each `lease`, or rechecking every blocked task on each `complete`.
- Deleting from the middle of a heap on heartbeat instead of leaving the old entry to be skipped.
- Accepting a completion from a worker whose lease has passed to another worker.
- Counting a repeated prerequisite twice, so the task never becomes runnable.
- Using the worker's clock to decide lease expiry once the scheduler is distributed.
