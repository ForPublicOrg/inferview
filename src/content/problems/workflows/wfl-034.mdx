## Question

<Callout kind="interview" label="The prompt, paraphrased from a public question list">
Design the pipeline that takes in a large, mixed collection of documents and indexes it so a model can use it.
</Callout>

The version for this problem (scenario):

- 40 million documents in a wiki, two file stores and a ticketing system: 70 percent born-digital (office files, wiki pages, PDFs with a text layer), 20 percent scanned PDFs, 10 percent spreadsheets and slides. They average 8 pages.
- About 200,000 documents change every day.
- Two engineers. The search cluster that serves retrieval belongs to the platform team and stays; index schema changes go through their review, and their cluster can hold one extra copy of the index at most.
- Every chunk must respect the source system's permissions at query time.
- The backfill budget for model calls is $40,000. The organisation is on the Build tier of the Claude API, and the batch queue is shared with a nightly enrichment job.

Design the pipeline: routing by document type, the backfill, the incremental path, permissions, re-processing, and what you write down for the platform team. Show the arithmetic behind the backfill plan.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Request a sample of 1,000 documents with page counts, text-layer presence and the share of pages with tables.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how a permission change in each source system is exposed: an event, a delta API or nothing.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the nightly enrichment job's owner how much of the batch queue they need and when.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Route by document type: native text extraction for born-digital files, model parsing through the batch API only for scans and table-heavy pages, and spreadsheets parsed as data. Model-parsing everything would cost about $243,000 at Haiku 5.5 batch prices, six times the budget, and output tokens are three quarters of it. Every document version is keyed by source id, content hash and parser version, so re-runs skip unchanged work. Permissions sync on their own path, because a permission change does not change content. The backfill runs below a queue ceiling that leaves room for the nightly job, and the new index is built beside the old one and switched once retrieval evals pass.</p>
</Fragment>
<Fragment slot="long">
<p>The routing decision, with numbers. 40M documents × 8 pages = 320M pages. Sending every page as PDF input: 1,500 to 3,000 text tokens per page plus the page image; the docs do not state the render size, and a page near 1,000 × 1,300 px would be ceil(1,000/28) × ceil(1,300/28) = 36 × 47 = 1,692 tokens. At the midpoint, 2,250 + 1,692 = 3,942 input tokens per page: 320M × 3,942 = 1.26T tokens × $0.05 per million = $63,000. If the model writes out the page's text (about 2,250 tokens, scenario): 720B output tokens × $0.25 per million = $180,000. Total about $243,000.</p>
<p>Routed: born-digital pages (224M) go through native extraction at no token cost. Scans (64M pages) through the model: 64M × 3,942 × $0.05/M = $12,600 input plus 64M × 2,250 × $0.25/M = $36,000 output, $48,600, still over budget. The two defensible ways to close the gap: an OCR engine for scans with the model only on pages that carry tables or forms (if a quarter of scanned pages do, about $12,000), or the model on all scans with older scans deferred to a second budget. The first costs a second parsing path and lower table fidelity on the pages the classifier misses; the second costs recall on old scans until next quarter. I take the first, because the incremental path has to handle new scans the same way anyway.</p>
<p>Throughput, the assumption that flips the schedule. One request per scanned document (8 pages, under the 100-page cap) gives 8M requests. If the backfill may use 200,000 of the 300,000-request queue (the rest is the nightly job's), that is 40 waves. The docs say most batches finish within an hour and expire at 24 hours. At an hour a wave, two days; at a day a wave, forty days. Measure the first five waves before promising a date.</p>
<p>Keys and re-processing. Each document version is keyed by (source, source id) with content hash, parser version and embedding model version. A re-run skips anything whose triple is unchanged, a parser fix re-runs only the documents that parser touched, and an embedding change is a full re-embed into a new index. Uber's TextSense is the shape to copy: a modular interface over OCR and model steps, orchestrated by a workflow engine (Cadence there).</p>
<p>Incremental path. Source change feeds (events or delta APIs) produce about 200,000 changes a day into the same router. Parsed and classified output goes onto a topic that the indexer and the permission sync consume; Grab publishes its classification predictions to Kafka for downstream data platforms, which then ask users weekly to verify the classified tags; that is the pattern for sensitivity labels here.</p>
<p>Permissions. Each chunk carries the source document's principals. A permission change arrives without any content change, so the content-hash key would skip it; permissions sync on a separate path that rewrites principals on existing chunks, and a document whose permission state cannot be read is not indexed.</p>
<p>The platform team's constraint. Their cluster can hold one extra index copy, so the backfill builds the new index beside the old one and switches by alias after retrieval evals pass on a fixed query set, with a rollback to the old alias. That same headroom is spent again at every embedding model change, which is the written risk note: two index rebuilds cannot overlap.</p>
<p>What I give up: table fidelity on scanned pages the classifier misses, two parsing paths to maintain with two engineers, and freshness on the incremental path while a backfill wave holds the queue.</p>
<p>The failure mode of routing: a born-digital PDF with a broken text layer (wrong glyph mapping) passes native extraction and indexes garbage silently. A text-quality check on extracted text (share of printable characters and dictionary words) sends failures to the model path, and retrieval evals are sliced by parsing path so a bad path shows up as its own number.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Finance cuts the model budget to $15,000. Which documents wait, and who signs off?</em> Scans older than a cutoff, chosen with the teams that own those sources; the sign-off names the recall loss on queries about those documents.</li>
<li><em>What would make you model-parse born-digital documents too?</em> A retrieval eval showing that table-heavy born-digital pages answer measurably worse through native extraction, and a token price that fits the budget.</li>
<li><em>The embedding model is retired in 90 days. What happens to the platform team's cluster?</em> A second full index for the re-embed, so no parser-driven rebuild may run in the same window; book it with them now.</li>
</ul>

## Follow-ups

- *Your parsing evals cost more than the incremental path itself. Which half do you cut, and what risk do you accept in writing?* Keep evals sliced by parsing path and drop per-source slices; the written risk is that a quality problem in one source can hide inside its path's average.
- *A password-protected PDF arrives. What happens to it?* The PDF path rejects encrypted files, so it is dead-lettered with its source and owner, not retried.
- *A document is deleted at the source. How long can its chunks stay retrievable, and what enforces it?* A deletion window agreed with the data owners, enforced by the same change feed as edits plus a periodic reconciliation against the source's full listing.

## Common mistakes

- One parsing path for everything, priced on input tokens only.
- Keying re-processing on content alone, so permission changes never reach the index.
- Letting the backfill take the whole batch queue the nightly job also needs.
- Rebuilding the index in place instead of beside the old one.
