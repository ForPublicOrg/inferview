> **Approvals for the ops copilot (v1)**
>
> **Context.** Support staff use the ops copilot, built on the OpenAI Agents SDK, to work tickets. Tools: `lookup_order` (read only), `issue_refund(order_id, amount, reason)` and `change_address(order_id, address)`, both with `needs_approval=True`. When a run reaches either tool it stops with `interruptions`. We have no datastore of our own yet and the launch date is fixed, so v1 keeps approvals stateless.
>
> **Pausing.** When `result.interruptions` is non-empty, the API calls `result.to_state().to_string()`, compresses the string, encrypts it with the app's AES-GCM key and sets it as the cookie `run_state` (HttpOnly, Secure, SameSite=Lax). Encryption means the browser can neither read nor alter the state. Runs with long histories may need the state split across several cookies.
>
> **The approval card.** The UI shows the agent's own explanation of the action ("Refunding order A-1042 because the item arrived damaged") and, under "Details", the tool arguments rendered as Markdown for readability. Buttons: Approve, Reject.
>
> **Who approves.** Any logged-in staff member. The requester may approve their own calls, since they know the ticket best.
>
> **Resuming.** Approve sends `POST /approve` with `{ "decision": "approve", "approved_by": "<email>" }`. The server decrypts the cookie, calls `RunState.from_string`, then `state.approve(item, always_approve=True)` so the reviewer is not asked again for the same tool in this run, and runs the agent from the state. If the run errors after approval, the UI retries the POST with the same cookie; approval is idempotent.
>
> **Run context.** The context object carries the staff member's CRM token so that tools act with that person's permissions.
>
> **Timeouts.** A pending approval expires after 24 hours. On expiry, refunds under $100 are approved so customers are not left waiting; everything else is rejected.

List the flaws before you open the checklist. Then say where the run state should live, and defend one timeout and one escalation interval.

## Answer

The design treats approval as a UI step. It is an authorisation decision, and most of the flaws follow from that one mistake.

**State that proves nothing.** The OpenAI Agents SDK docs say `RunState.from_string()` does not authenticate the snapshot, and that a schema check or a tool-call fingerprint does not either. AES-GCM with one app-wide key does stop the browser editing the bytes, which is why the doc reads as safe. What it does not do is bind the state to a user, a run or a single use. Any cookie the app ever minted decrypts, so an old approved snapshot can be posted again, and a cookie copied from one staff member's browser resumes in another's.

**Replay.** The retry rule makes it routine. The docs say approval permits a tool call to execute and does not guarantee exactly-once execution, and that resuming from an older approved snapshot can execute the tool again. A run that refunded and then failed on its next model call is retried with the same cookie and refunds twice. "Approval is idempotent" is true of the decision and false of the refund.

**Who approves.** The guide OpenAI published on building agents lists large refunds and payments as high-risk actions that warrant human oversight. Oversight by the person who asked for the refund is not oversight. The doc needs a rule per tool and amount band: who may approve, whether the requester is barred, and when a second person is needed.

**Who the approver is.** `approved_by` comes from the request body. The docs say plainly not to take the reviewer's identity from the request body; it comes from the authenticated session.

**What the reviewer sees.** The card leads with the model's explanation. A reviewer who approves "item arrived damaged" has approved a sentence, not `issue_refund(order_id="A-1042", amount=480.00)`. The arguments are under a fold and rendered as Markdown, and the docs say to treat tool names and arguments as untrusted display content and escape them. An argument written by a model that read a customer email can carry markup that hides the real amount or adds a link.

**One approval, many refunds.** `always_approve=True` persists the decision for later calls to the same tool, and the docs say `RunState` stores sticky decisions so that they survive `to_string()` and `from_string()`. After the first approved refund, every later `issue_refund` call while the run continues executes without a card.

**A secret in the cookie.** The run context is serialised with the state, and the docs say to treat it as persisted data and keep secrets out of it. The CRM token now lives in every browser that paused a run, for as long as the cookie does.

**Timeout as approval.** Approving refunds because nobody answered turns reviewer absence into spending. Expiry should escalate, then reject.

**Deploys.** Nothing records which agent definition or SDK version produced the state. A run paused before a deploy resumes against the new tool definitions. The docs suggest storing a version marker with the serialised state.

The cookie size problem is real but secondary; it fails loudly, and the fix for the security flaws removes it.

### Where the state lives: two defensible answers

**Server storage.** A table keyed by run ID with the snapshot, the owner, the pending tool call ID, a hash of its arguments, the approver rule, the agent version, `expires_at` and a status. Approve is a compare-and-set from `pending` to `approved` by an authenticated approver allowed by the rule; the resume takes the row from `approved` to `running`, so a second POST finds nothing to resume. The docs recommend it for browser and mobile approval interfaces: the complete snapshot stays in server storage and the reviewer receives opaque identifiers, which by themselves authorise nothing. It costs the datastore the team said it does not have before launch, plus retention, encryption at rest and a cleanup job.

**A client token, done properly.** Keep a token in the browser, but make it an AEAD envelope over the user ID, run ID, tool call ID, argument hash, expiry and a nonce, and keep a server-side set of spent nonces. No full datastore for snapshots, which meets the deadline. The cost is that it still needs server state (the nonce set), the secret has to come out of the context, the state still has to fit in a cookie, and the approver must be the person holding the browser, which rules out a second approver for refunds.

The server-storage answer is the one I would ship, with the launch scope cut to fit: v1 ships `change_address` behind approval and `issue_refund` disabled until the table exists, if the date cannot move. Its own failure mode: if the refund call goes out and the process dies before the status moves to `done`, the row says `running` and nobody knows whether money moved. The docs' advice is to record the outcome as unknown and not replay automatically. That needs a reconciliation step against the payment system, keyed by an idempotency key derived from the order and the tool call ID.

### Timeout and escalation

Choose the numbers from the support queue, not from a default. If tickets have a same-day reply target, escalate an unanswered refund to the team lead after an interval well inside that target (an hour or two during staffed hours is reasonable) and reject with a customer-facing message at the end of the next business day. A 24-hour expiry with nothing in between is unreasonable for refunds, because the first person who hears about the stall is the customer.

## Follow-ups

- *The launch date is fixed and the table needs a security review that takes two weeks. You ship refunds without approval, refunds disabled, or the client token. Which, and what risk do you accept in writing?*
- *What would you need to see in the first month of approval logs to remove the requester-may-not-approve rule for refunds under some amount?*
- *Support leads say a second approver will double handling time on the busiest day of the year. Two senior engineers disagree about relaxing it for that day. How do you decide without deciding by rank?*
- *A reviewer approves, the refund call times out, and the payment provider has no record of the idempotency key an hour later. What does your system show the customer, and who is paged?*

## Common mistakes

- Accepting the cookie because it is encrypted. Encryption with one app key proves the app made it, not that this user may use it now, once.
- Fixing replay with a "processed" flag inside the snapshot. The old snapshot does not carry the flag.
- Asking for a confirmation dialog in place of an approver rule.
- Treating `needs_approval=True` as the whole design; it is where the run stops, not who may continue it.
