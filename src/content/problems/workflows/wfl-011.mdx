## Question

<Callout kind="interview" label="Interview question">
"Our account-research agent runs as one Temporal workflow per customer and lives for weeks. Some executions are getting history-size warnings. When do you continue-as-new, and what goes into the next run?"
</Callout>

Scenario. Each turn, the workflow calls a model activity with the full transcript as its argument, then runs zero to three tool activities. Users steer the agent with Signals and approve spend with Updates. The workflow also holds a spend counter against a monthly cap per customer, a list of tool calls that wrote to the CRM, and a pending approval when one is open. The transcript grows by about 4 KB a turn.

Say which limit you will hit first, when you continue, and what you carry over and drop.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for one real history and count its events per turn; then ask how many bytes each turn adds to that history, not to the transcript.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which values in workflow state would reset to zero if they were not passed to the new run, and what each reset would allow.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what can arrive while the workflow is deciding to continue.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Size, not event count, binds first, because passing the whole transcript into every model activity records it in history again each turn, so history grows with the square of the turn count. Fix that first: store the transcript outside the workflow and pass a reference. Continue when <code>is_continue_as_new_suggested()</code> says so or at your own lower cap, only at a turn boundary with no handler running. Carry the goal, a compact summary with a pointer to the full transcript, the spend counter, the record of external writes and their keys, any open approval, and the prompt and tool versions. Drop raw tool outputs and the in-history transcript.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Which limit first.</strong> Temporal Cloud caps a history at 51,200 events or 50 MB and warns at 10,240 events or 10 MB. Assume a turn costs about 18 events, three activities and three workflow tasks at three events each; check that against a real history. Event count then reaches the warning near turn 10,240 / 18 ≈ 569 and the limit near 2,844. Size is worse. If the model activity's input at turn k is the transcript, about 4k KB, the inputs recorded after n turns total about 4 × n(n + 1)/2 = 2n(n + 1) KB. Taking 1 MB as 1,024 KB, the 10 MB warning arrives when n(n + 1) = 5,120, near turn 71, and the 50 MB limit when n(n + 1) = 25,600, near turn 160. The 2 MB per-request payload cap would stop a single call at 4k = 2,048, turn 512, long after the history limit.</p>
<p><strong>Fix the growth before tuning the threshold.</strong> Write the transcript to a store keyed by workflow id and turn, and pass the activity a reference and a turn number. History then grows linearly, and the event limit becomes the one you plan around. Continue-as-new is still needed, because a run that lives for weeks will cross 51,200 events and because each new run starts on clean history.</p>
<p><strong>When to continue.</strong> Check <code>workflow.info().is_continue_as_new_suggested()</code> at the end of each turn, and also continue at a cap of your own (every few hundred turns, say), so the behaviour does not depend on the server's threshold. Never continue from a Signal or Update handler; wait in the main loop until all handlers have finished, then continue. Do not continue while an approval Update is in flight.</p>
<p><strong>Carry over.</strong> The goal and the customer's constraints in a structured form, not only in prose. A summary of the conversation plus the reference to the full transcript. The spend counter and the cap period it belongs to: dropping it resets the monthly budget at every continue. The list of external writes with their idempotency keys, or a reference to them, so a retried step in the new run does not write twice. Any open approval with its deadline as an absolute time, not a remaining duration. The prompt and tool-set versions this run was started with. A turn counter that keeps counting across runs.</p>
<p><strong>Drop.</strong> Raw tool outputs, retrieved documents and intermediate plans, all of which can be re-fetched or live in the transcript store. Anything derived from state you are already carrying.</p>
<p><strong>The quantity you choose.</strong> The summary's size. A larger summary keeps more facts and costs input tokens on every turn of the new run; a smaller one is cheap and forgets things. A reasonable choice keeps the structured constraints exact and lets the prose summary be lossy, because the constraints are what the agent must not violate.</p>
<p><strong>Versions.</strong> With Worker Versioning, a Pinned workflow keeps its version across the whole continue-as-new chain, so continuing does not pick up new code; an Auto-Upgrade workflow moves to the current version. Choose that behaviour on purpose, because "the next run will get the new prompt" is false for pinned runs.</p>
<p><strong>Where this answer fails.</strong> A summary drops a constraint the user gave in week one, and the agent violates it in week three with no trace in the new run's history. The transcript store becomes a second source of truth that must be retained as long as the workflow's audit needs, which outlives Temporal's history retention.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What about Signals?</em> Each run is also terminated past 10,000 Signals or 2,000 Updates, so a chatty client can force a continue even when the history is small.</li>
<li><em>How do you test it?</em> Force a continue-as-new every turn in a test environment and assert the spend counter, open approval and write keys survive.</li>
<li><em>Pushback.</em> The summary costs a model call at every continue. Why not carry the last 50 turns verbatim instead?</li>
</ul>
</Fragment>
</Depth>

The conflict here is size against fidelity: every byte carried into the next run is history the new run starts with and input tokens the agent pays for on each turn, and every byte dropped is a fact the agent may need later. The rule that keeps both under control is to carry structured state exactly and prose state by reference.

## Follow-ups

- A user Signal arrives in the same workflow task in which you decide to continue. What happens to it, and how do you make sure it is not lost?
- The spend cap is monthly, but a run can continue across a month boundary. Where does the period live, and who resets it?
- How would you migrate the hundreds of executions that already carry the full transcript in their history?

## Common mistakes

- Raising the continue threshold instead of removing the quadratic growth.
- Carrying the full transcript as the continue-as-new argument, which moves the problem into the 2 MB payload limit.
- Forgetting the spend counter, so each new run gets a fresh budget.
- Calling continue-as-new from a Signal handler.
- Assuming continue-as-new upgrades a pinned workflow to the latest code.
