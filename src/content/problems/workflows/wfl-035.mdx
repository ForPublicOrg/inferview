## Question

<Callout kind="interview" label="The prompt">
"Legal wants every new supplier contract read by a model. Do we send the PDF, or extract the text ourselves? What does one contract cost each way?"
</Callout>

Published inputs (Claude docs, checked 2026-10-28): when you send a PDF, each page typically costs 1,500 to 3,000 text tokens, depending on density, and each page is also converted to an image billed by the image formula, ceil(width / 28) × ceil(height / 28) tokens. A request carries at most 100 pages when the model's context window is under 1M tokens. Claude Sonnet 5.5 costs $2 per million input tokens and $10 per million output tokens.

Scenario inputs:

- Contracts are 200 pages, born-digital, with a text layer.
- A sample shows 24 of 200 pages carry tables (pricing schedules, service levels) that lose their structure in plain text.
- The docs do not say at what size a PDF page is rendered. Assume pages reach the model at about 1,000 × 1,300 px, and check it with the token counting endpoint before you rely on it. In the text path you render the table pages yourself at the same size.
- Each request returns about 3,000 output tokens of extracted terms. Send the contract as two 100-page requests either way.

Estimate the input cost of one contract on the PDF path, in US dollars, choosing a text density inside the documented range and saying why. Then price the text path (your own extracted text for every page, plus a page image for the 24 table pages) and say which you would ship.

## Answer

<Depth>
<Fragment slot="short">
<p>About $1.60 on the PDF path at 2,300 text tokens a page, a choice for dense contract prose inside the documented 1,500 to 3,000. Each page is 2,300 text tokens plus 36 × 47 = 1,692 image tokens: 200 × 3,992 = 798,400 tokens, $1.60. The text path is 200 × 2,300 + 24 × 1,692 = 500,608 tokens, $1.00. The saving, 176 untabled page images or about $0.60 a contract, does not depend on the text density. I would ship the text path for born-digital contracts and keep the PDF path for scans.</p>
</Fragment>
<Fragment slot="long">
<p>Image tokens per page. ceil(1,000 / 28) = 36, ceil(1,300 / 28) = 47, so 1,692 tokens. This is the input you cannot read from the docs; it is a measured number once you run the token counter.</p>
<p>PDF path. Per page, text t plus 1,692. At the documented ends: t = 1,500 gives 200 × 3,192 = 638,400 tokens, $1.28; t = 3,000 gives 200 × 4,692 = 938,400 tokens, $1.88. At t = 2,300, $1.60.</p>
<p>Text path. 200 × t plus 24 × 1,692 = 40,608 image tokens. At t = 2,300: 460,000 + 40,608 = 500,608 tokens, $1.00. The difference between the paths is 200 × 1,692 − 40,608 = 297,792 tokens, $0.60, whatever t is.</p>
<p>Output. Two requests × 3,000 tokens × $10 per million = $0.06 on either path, a few percent of the total.</p>
<p>The decision. At 50,000 contracts a year (scenario), $0.60 is $30,000 a year. Against it: a text extractor and a table-page detector to own, and every table the detector misses is read as flattened text, with no image to recover the structure. The PDF path costs more and has one moving part. For a team that already runs text extraction, the text path pays for itself; for a team that would build it for this, it is close.</p>
<p>The failure mode of the text path: a contract whose pricing schedule is an embedded image on a page the detector marks as text. The extracted text holds nothing for that page and the model answers "no pricing found" with confidence. A cheap guard: route any page with little extracted text but large embedded images to the image fallback.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Legal asks ten questions of each contract over a week. What changes?</em> Caching. With the contract as a cached prefix, cache reads on Sonnet 5.5 are 0.05 times the input price, so after the first question the path choice barely matters; the first read and the cache writes dominate.</li>
<li><em>The contract runs through the batch API. What changes?</em> Every figure halves, and the $0.60 difference becomes $0.30.</li>
<li><em>Half the contracts are scans. What changes?</em> Scans have no text layer, so the text path needs OCR, and the PDF path is the simpler of the two.</li>
</ul>
</Fragment>

Answers from $1.20 to $2.00 count, which covers the documented text range at the stated render size. The dominant term is per-page text, but the term that decides between the paths is image tokens on pages without tables. The assumption that flips the conclusion is render size: if pages reach the model larger than assumed, both the PDF path's cost and the saving grow, up to 4,784 visual tokens a page on the newest models; if most pages carry tables, the saving shrinks to nothing.

Unreasonable answers: about $0.60 to $1.20, from pricing only text tokens on the PDF path and ignoring the page images the docs say are billed; a single 200-page request priced as if the 100-page limit did not apply; and pricing output tokens at the input rate.

## Follow-ups

- *Your table detector costs more engineering time than the saving in its first year. Which half do you cut, and what do you accept in writing?* Drop the detector and send every page with any table-like layout as an image; write down the higher cost per contract and the date you will re-measure it.
- *What measurement would reverse your choice?* An eval on 50 contracts showing that answers about pricing schedules are worse on the text path than on the PDF path, by more than legal accepts.
- *Two engineers disagree about which render size to assume. How do you settle it without deciding by rank?* Send five contracts through the token counting endpoint and use the measured count.

## Common mistakes

- Counting only the documented text tokens for a PDF and forgetting the per-page image.
- Applying the image formula to every page on the text path instead of the table pages only.
- Treating the documented 1,500 to 3,000 range as a measurement of these contracts.
- Sending 200 pages in one request without checking the per-request page limit.
