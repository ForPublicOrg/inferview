## Question

<Callout kind="interview" label="Interview question">
"Fifty tenants share one provider quota. Design admission control so that one tenant's backfill does not starve the others."
</Callout>

The platform is a scenario; the limits are Anthropic's published ones. A document-extraction platform runs every tenant's work on Claude Sonnet 5.5 under one organisation on the Scale tier: 10,000 requests, 10,000,000 input tokens and 2,000,000 output tokens per minute (Claude rate-limits page, checked 28 October 2026). A document costs a 4,000-token cached instruction prefix, about 2,000 uncached input tokens and about 800 output tokens.

Today, every upload goes into one SQS queue. A fleet of 300 workers pulls from it and calls the API; on a 429 a worker waits for `retry-after` and tries again. Interactive uploads from the 49 smaller tenants average 600 documents a minute and peak at 1,200 on weekday mornings; their contracts promise a result within 30 seconds of upload for 95% of documents.

On Monday, tenant 17 submits a backfill of 12 million archived documents, and sales has told them it will be done by Thursday, 72 hours away. Within ten minutes the interactive tenants' results are taking minutes.

Constraints: three engineers and four weeks. SQS and the worker fleet stay; the only shared state you may add is the Redis cluster the platform already runs.

Design the admission control, decide what happens to the backfill, and write the rollout plan.

## Answer

<Depth>
<Fragment slot="short">
<p>Output tokens bind first: 2,000,000 / 800 = 2,500 documents a minute, so the backfill alone needs 80 hours of the whole quota and cannot finish by Thursday on the online API without starving everyone. Put a work-conserving fair scheduler in front of the online quota (per-tenant queues, deficit round robin, a Redis token bucket in output tokens set below the provider's limit, interactive first), and send bulk submissions to the Message Batches API, which has its own limits and half the price. Promise Thursday only after one measured batch says the batch path can do it.</p>
</Fragment>
<Fragment slot="long">
<p><b>Where the ceiling is.</b> Per minute, requests allow 10,000 documents, uncached input allows 10,000,000 / 2,000 = 5,000 (cache reads do not count toward ITPM on Sonnet 5.5), and output allows 2,000,000 / 800 = 2,500. Output tokens are the binding limit, and they are counted as generated, so an admission decision has to estimate them. The backfill needs 12,000,000 / 2,500 = 4,800 minutes, 80 hours, with no interactive traffic at all. With interactive traffic averaging 600 a minute, what is left is 1,900 a minute and the backfill takes 12,000,000 / 1,900 ≈ 6,300 minutes, about 4.4 days. The Thursday promise is not reachable on the online quota at any fairness setting.</p>
<p><b>The decision for the backfill.</b> Three answers are defensible.</p>
<ul>
<li>Online API at leftover capacity, behind the scheduler. Simplest for tenant 17's integration and gives per-document results within minutes, but finishes in about 4.4 days at full price, so the promise is broken in writing on Monday.</li>
<li>Message Batches API. Separate limits (500,000 requests in the processing queue at Scale tier, 100,000 per batch), 50% of standard price, and no load on the online quota. At most five 100,000-request batches can be in flight; if each completes in about an hour, as most do according to the docs, 12 million documents take 120 batch-hours / 5 = 24 hours. If demand slows processing to six hours a batch, it takes 144 hours. Costs: new code for submission, polling and resubmitting expired requests, results arriving in hourly chunks, and a deadline that depends on a provider number you have to measure.</li>
<li>A separate workspace for bulk work with its own lower limits. Configuration only, so it ships this week, but it is a static partition: capacity reserved for bulk sits idle at night, and the organisation limit still applies to the sum.</li>
</ul>
<p>Recommendation: Batch API for the backfill, the scheduler for everything online. Measure one 100,000-request batch on Monday; if it completes within about two hours, the five-in-flight arithmetic gives roughly two days and Thursday holds. If it does not, tell tenant 17 on Monday which date the measurement supports.</p>
<p><b>The online scheduler.</b> Fifty tenants is few enough for one SQS queue per tenant, which the AWS article notes stops scaling only when polling costs grow with tenant count; at thousands of tenants, shuffle-shard each tenant onto two of a few dozen queues instead. A dispatcher takes from the tenant queues in deficit round robin, weighted by plan, and admits a document only when a Redis token bucket denominated in output tokens has room for its estimated output (the tenant's p95 output length, corrected with the actual usage when the response returns). Refill the bucket at a target below the provider's 2,000,000 per minute, because the provider may enforce over shorter intervals and adds acceleration limits on sharp increases; 85 to 90% is a reasonable choice, and the answer has to state its own. Two classes: interactive first, bulk only from what interactive leaves. The scheduler is work-conserving, so bulk work uses the whole quota at night. Excess waits in the queue (throttling, in Inngest's vocabulary) rather than being dropped (rate limiting).</p>
<p><b>Signals.</b> Alarm on the age of the oldest message in each interactive tenant's queue, with the threshold set from the 30-second promise (for example 15 seconds sustained for 5 minutes), not on depth: a backlog of a million bulk documents is normal, a 40-second-old interactive one is not. Any message in the dead-letter queue pages. Read the anthropic-ratelimit-output-tokens-remaining header on responses and shrink the bucket's refill when it runs low, so a wrong estimate corrects itself.</p>
<p><b>How the recommendation fails.</b> The scheduler admits on estimated output. A tenant whose documents suddenly produce three times the usual output overdraws the bucket for the first few minutes, everyone gets 429s, and the workers' retries add to it; the header feedback and a per-tenant cap on in-flight estimated tokens limit the damage but do not remove it. Redis is now on the path of every call: when it is unreachable, workers fall back to a fixed local rate (the target divided by the worker count), which is safe and slow. The batch path fails differently: if processing slows, Thursday slips, and the platform only learns it hours later from batch status.</p>
<p><b>What you give up.</b> Tenant 17 gets results in hourly chunks instead of a stream, and the platform takes on a second execution path with its own failure modes. Interactive tenants give up a little peak capacity to the bucket's headroom. The team gives up roughly half of the four weeks to the scheduler, which is the part that protects against the next noisy tenant, interactive or not.</p>
<p><b>Rollout plan, written down.</b> Week 1: per-tenant queues and the dispatcher in shadow mode, logging what it would admit next to what the fleet actually did; tenant 17's backfill moves to the Batch API with the measured batch as the gate for the date. Week 2: enforce for the bulk class only. Week 3: enforce for all classes. Rollback trigger at each stage: any interactive tenant's oldest-message age above 30 seconds for 10 minutes, or 429s above a chosen share of calls (1% is a reasonable line), flips the enforcement flag off and the workers return to pulling directly.</p>

The arithmetic that anchors the design is the binding limit. Teams that budget in requests per minute see 10,000 RPM and conclude there is four times the headroom there is; for this workload the output-token limit allows a quarter of the request limit. Grab's data-classification pipeline (published 2023, updated July 2024) hit the same shape: every Azure OpenAI deployment shared one account-level quota of 240,000 tokens per minute, and the fix was a rate limiter at the workflow level in front of it, fed from a queue in mini-batches.

## Follow-ups

- *Pushback: tenant 17 is 30% of revenue, refuses batch results and wants the online API and Thursday. Which tenants degrade, by how much, and who signs that in writing?* State the arithmetic: on the online quota the backfill at full speed takes 80 hours with zero interactive traffic, so Thursday is impossible on this tier regardless of fairness. The choices left are a higher limit from the provider (requested Monday, with the peak tokens per minute and cache share), a later date, or degrading 49 tenants, and the last one needs the account owners of those tenants to sign, not engineering.
- *Reversal: what would you need to see in production to drop the scheduler and rely on workspace limits alone?* If bulk work moves permanently to the batch path, interactive peaks stay under about half the output limit, and no tenant can generate more than its workspace share, a static split costs little and removes Redis from the call path. A month of per-tenant peak data decides it.
- *Two senior engineers disagree: one wants per-tenant queues, the other one shared queue with a fair scheduler over Redis sorted sets. How do you decide without deciding by rank?* Replay last month's traffic plus a synthetic 12-million-document backfill through both in a load test and compare the worst interactive tenant's oldest-message age and the operational cost of each; pick the one that meets the promise with fewer moving parts.
- *What happens when the provider is slow rather than rate limiting?* Throughput falls while admission still refills at the target rate, so in-flight calls pile up; cap concurrent in-flight requests per class as well as tokens.

## Common mistakes

- Sizing against requests per minute when output tokens bind first.
- Strict equal shares that leave the quota idle at night while bulk work waits.
- Alarming on queue depth, which is always high during a backfill, instead of the age of the oldest interactive message.
- Letting workers retry 429s on their own after the scheduler admitted them, which turns one overdraft into a retry storm.
- Promising a backfill date from a batch endpoint's typical completion time without measuring it on your own traffic.
