## Question

<Callout kind="interview" label="As asked">
"Estimate the KV cache memory needed to serve a large model. How does it constrain batch size and context length?"
</Callout>

Make it concrete. You serve Llama 3 70B with the KV cache in BF16 (2 bytes per element). Its published architecture: 80 layers, model dimension 8,192, 64 query heads and 8 key-value heads. How much KV cache do **8 concurrent sequences at 32,768 tokens each** need? Give the answer in GB.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Per token, every layer stores one key vector and one value vector for each KV head.</p></details>
<details class="hint"><summary>Hint 2</summary><p>The head dimension is the model dimension divided by the number of query heads.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Use the 8 KV heads, not the 64 query heads; that is the point of grouped-query attention.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Per token: 2 (K and V) x 80 layers x 8 KV heads x 128 head dimension x 2 bytes = 327,680 bytes, 320 KiB. Times 32,768 tokens times 8 sequences = 85.9 GB, which is exactly 80 GiB. That is more than the 70 GB of the model's weights in FP8 and more than one H100's 80 GB on its own.</p>
</Fragment>
<Fragment slot="long">
<p>Head dimension: 8,192 / 64 = 128. Per token per layer: 2 x 8 x 128 = 2,048 elements, 4,096 bytes in BF16. Across 80 layers: 327,680 bytes per token.</p>
<p>One 32,768-token sequence: 327,680 x 32,768 = 10.74 GB. Eight of them: 85.9 GB (10^9 bytes), or 80 GiB (2^30 bytes). Both are correct; say which unit you mean.</p>
<p>The constraint: memory is weights plus KV cache plus runtime overhead. With FP8 weights at about 70 GB on 80 GB GPUs, one GPU has about 10 GB left for cache, roughly 30,500 tokens in total across all users. So this workload needs at least two GPUs with tensor parallelism, or FP8 KV cache (halving it to about 43 GB), or fewer concurrent long sequences. Concurrency times context is the budget: 8 users at 32k costs the same as 64 users at 4k.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What if the model used full multi-head attention?</em> 64 KV heads instead of 8 makes the cache 8 times larger, about 687 GB for the same workload.</li>
<li><em>How does PagedAttention change this number?</em> It does not change the bytes per token; it removes the waste from reserving maximum length up front, so the real cache is close to this estimate instead of several times larger.</li>
<li><em>What about FP8 KV cache?</em> One byte per element halves it to about 43 GB; check accuracy on your evals, because the scales need calibration.</li>
</ul>
</Fragment>
</Depth>

Worked calculation in one line: 2 x 80 x 8 x 128 x 2 x 32,768 x 8 = 85,899,345,920 bytes. The accepted band is 80 to 92 so that answers in GiB (80) and small rounding differences in GB both pass.

## Follow-ups

- *Where does the rest of GPU memory go?* Weights, activations for the current step, CUDA graphs and the engine's own buffers. Engines typically let you set what fraction of memory they may claim.
- *Which models break the formula?* Sliding-window layers cap their cache at the window, and DeepSeek-style multi-head latent attention caches a compressed latent. Read the config.
- *How do you serve 128k-context users at all?* Fewer of them per GPU, FP8 KV cache, more GPUs, or prefix caching when many users share the long prefix.

## Common mistakes

- Using 64 query heads instead of 8 KV heads, which gives an answer 8 times too large.
- Forgetting the factor of 2 for keys and values, or the 2 bytes per BF16 element.
- Deriving head dimension as hidden size over heads for every model. It works here, but Qwen3-32B sets head_dim to 128 where that division would give 80.
- Mixing GB and GiB without saying so.
