checklist:
  - Separates the model change from the serving change, or states in writing why they ship together and how a regression will be attributed
  - Runs quality probes per accelerator build and per serving configuration, not one probe set for the fleet
  - Includes probes that detect a broken implementation on a single sample, such as unexpected scripts or invalid code syntax, not only aggregate benchmark scores
  - Computes how many probe requests a canary needs to see a defect at the rate it cares about, and sizes the canary from that
  - Compares canary against a concurrent control population with the same traffic, not against last week
  - Names rollback triggers as measurable thresholds, and says which roll back automatically and which page a human
  - Names one owner who holds rollback and states who can halt the rollout without that owner's agreement
  - Treats routing and load-balancing changes as releases that go through the same canary
  - Keeps quality probes running on production after the rollout ends, so a later configuration change is caught
  - Plans for the privacy limit on reading prompts, for example with synthetic probes and an opt-in feedback channel
  - States what the launch date gives up if a trigger fires late, and who signs off on launching with a known regression
  - States a failure mode of the pipeline itself, such as a probe set the bug does not touch

## Question

<Callout kind="interview" label="Workflow round, 40 minutes">
"A new version of our model goes out to the serving fleet in ten days. Write the release pipeline: what gets canaried, on what signal, what rolls it back, and who owns the decision."
</Callout>

The setting (scenario):

- The model is served on two accelerator builds, GPU and TPU, in three regions. Each build has its own kernels and compiler.
- The release carries the new weights and, from the performance team, a faster sampling kernel on the TPU build that they measured at 4% more throughput.
- The marketing launch date is public. Offline evals of the new weights passed last week on the GPU build only.
- Engineers cannot read production prompts unless a user submitted them as feedback.
- Today the fleet's canary watches error rate and latency for an hour, then the release goes to 100%.
- Last quarter a load-balancer change, shipped as a configuration edit outside the release process, sent a share of traffic to replicas with the wrong context-length configuration for a week before anyone connected the reports to it.

Design the pipeline as steps, state and approvals. Give the rollback triggers, their thresholds and the owner of each decision, and say what the launch date gives up. Then open the checklist and tick what your design covers.

## Answer

<Depth>
<Fragment slot="short">
<p>Split the release in two: the TPU sampling kernel ships first, on the current weights, and the new weights ship after it on both builds, each through the same pipeline. Every stage compares a canary population with a concurrent control on quality probes run per build: single-sample detectors (unexpected scripts, broken code syntax, truncated structured output), a fixed probe set graded against the control, and the error and latency SLIs. The canary is sized so the probes see the smallest defect rate we care about with high probability, which at 1% means hundreds of probe requests per build per stage, not an hour of passive traffic. Rollback is automatic on a single-sample detector, and paged on a graded-probe gap. The inference release captain holds rollback; the quality team can halt any stage. Routing and load-balancing changes go through the same pipeline. The launch date gives up the kernel's 4% if the kernel's canary has not finished.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why error rate and latency are not enough.</strong> Anthropic's 2025 postmortem lists three bugs that degraded answers without raising errors: requests routed to servers with the wrong context configuration, a TPU misconfiguration that produced characters from the wrong script, and a compiler bug in approximate top-k that sometimes dropped the most likely token. Benchmarks, safety evals and canaries missed them, partly because the model recovers from isolated mistakes. Each fits the scenario here: a TPU-only kernel change, offline evals that ran on GPU only, and a configuration edit that bypassed the release process.</p>

<p><strong>Decision 1: one release or two.</strong> Two defensible answers.</p>
<ul>
<li><em>Ship the kernel and the weights separately.</em> A regression is attributable to one change, and the kernel is tested against weights whose behaviour is known. The cost: two pipelines' worth of canary time inside ten days, and the kernel's 4% may miss the launch.</li>
<li><em>Ship them together.</em> One canary, the launch gets both. The cost: a quality gap on TPU cannot be attributed to the weights or the kernel without a second experiment, which is the one that would then run under incident pressure.</li>
</ul>
<p>I split, kernel first, because the TPU build has the change nobody has evaluated. If the kernel canary has not passed by day 6, the weights ship without it and the kernel waits. I give up 4% throughput at launch, in writing.</p>

<p><strong>The quantity you choose: probe volume per stage.</strong> A canary only sees what its traffic and probes touch. To see at least one failure from a defect that hits a fraction p of requests with 95% probability, the probes need n with (1 - p)<sup>n</sup> at most 0.05, so n is at least ln(0.05) / ln(1 - p), about 3 / p. At p = 1% that is 299 probe requests per build per stage; at 0.1%, 2,995. The 2025 routing error began at 0.8% of requests. A one-hour canary at 5% of traffic sees plenty of requests but no graded answers, because nobody can read them. So the probes are synthetic, run per build and per region, and their count is chosen from the defect rate the team is willing to miss; 1% is defensible for a first stage and 0.1% for the last. A detector that fires on a single sample (wrong script, unparseable code, a JSON answer that fails its schema) needs only to be hit once, which is why it carries the automatic rollback.</p>

<p><strong>The pipeline.</strong></p>
<ol>
<li><em>Build gate.</em> Offline evals on both builds, not one, plus a differential run of a fixed prompt set between the new build and the current one at temperature 0, flagging prompts whose answers diverge beyond a tolerance. Owner: model team signs quality; inference team signs the build.</li>
<li><em>Stage 1, one replica per build per region.</em> Synthetic probes at the stage-1 volume, compared with control replicas on the current release. Single-sample detectors armed. Minimum duration: long enough to run the probes and one peak hour.</li>
<li><em>Stage 2, 5% of traffic per build by stable hash of account.</em> Probe volume raised to the 0.1% level. SLIs compared canary against control, broken down by population as the SRE workbook advises, because a defect in 5% of traffic is a fifth of its size in fleet-wide numbers.</li>
<li><em>Stage 3, 50%, then 100%.</em> Same triggers. The previous release stays deployable for the rollback window.</li>
<li><em>After the rollout.</em> The probe set keeps running on production replicas, continuously, per build. This catches the class of bug that arrives after the release: a load-balancer change, a compiler upgrade, a configuration edit.</li>
</ol>
<p>State: the release record holds the stage, the probe results per build and region, the approvals and the rollback point. Any routing, load-balancing or serving-configuration change creates a release record and enters at stage 1; there is no configuration path around the pipeline.</p>

<p><strong>Rollback triggers.</strong></p>
<ul>
<li>Automatic: any single-sample detector firing on the canary at a rate above control's; any request served by a replica whose configuration does not match its class; error rate above control by the SLO's burn threshold.</li>
<li>Paged, decided within 30 minutes: graded probe score on the canary below control by more than the probe set's measured run-to-run noise; a rise in user feedback (thumbs-down, bug reports) attributable to the canary population.</li>
</ul>

<p><strong>Owners.</strong> The inference release captain owns the pipeline and holds rollback. The quality team owns the probes and can halt any stage without the captain's agreement. Launching with a known regression needs the model team lead and the product owner to sign the risk note.</p>

<p><strong>The constraint conflict.</strong> The launch date against measured quality: the pipeline adds days, and if a paged trigger fires on day 9, the launch ships the old weights or slips. I write that choice down before day 1: the date moves, or the launch uses the current model, and the product owner decides which.</p>

<p><strong>How this pipeline fails.</strong> It catches what the probes touch. A defect that needs a batch size, a context length or a configuration the probes never produce passes every stage, as the top-k bug depended on batch size and model configuration. The mitigation is partial: vary probe length and send probes while replicas are under production load, not to idle canaries, and treat a cluster of user reports on one build as a trigger even when the probes are clean.</p>
</Fragment>

## Follow-ups

- *Pushback: running probes at the 0.1% level on every build and region triples the release time, and the performance team ships kernels weekly. Which half do you cut, and what risk do you accept in writing?* Keep the 0.1% volume for weights and for any change to sampling or numerics; run kernel changes that do not touch numerics at the 1% level, and write down that a defect between 0.1% and 1% can reach full rollout before the continuous probes catch it.
- *Reversal: what would you need to see in production to stop splitting kernel and model releases?* A quarter of releases where the differential run predicted every regression the canary found, so attribution no longer needs separate releases.
- *Operating: the continuous probes start failing at 0.3% on TPU in one region, two weeks after the launch, and nothing has been deployed there. Who acts, and what do they roll back?* The release captain treats the last configuration or routing record for that region as the suspect, and if there is none, drains TPU traffic in that region to GPU while the quality team narrows the probe failures by batch size and context length.
- *Two senior engineers disagree: one wants the automatic rollback on graded probes too. How do you decide without deciding by rank?* Replay the last quarter's releases through the proposed trigger and count false rollbacks against the defects it would have caught earlier.

## Common mistakes

- Treating error rate and latency as the canary's quality signal.
- Running offline evals on one accelerator build and shipping on two.
- Bundling a numerics-changing kernel with new weights, so a regression cannot be attributed.
- Sizing the canary by traffic percentage and time instead of by the defect rate it must detect.
- Comparing the canary with last week instead of a concurrent control.
- Letting routing and configuration changes skip the pipeline.
- Ending the probes when the rollout reaches 100%.
