## Question

<Callout kind="interview" label="As reported by a candidate">
"Design an inference batching system for a single GPU handling up to 100 inputs per batch while users wait synchronously."
</Callout>

The case, constructed for this problem:

- One GPU serves a reranking model behind an existing Python HTTP service. Callers block on the response.
- The team profiled one forward pass on this GPU, with inputs padded to 512 tokens, at 20 ms + 0.6 ms per input in the batch, up to 100 inputs.
- Traffic peaks at 900 requests per second and falls to 20 at night. The objective is a server-side p99 of 250 ms.
- Callers use a client library owned by another team. It times out at 1 second and retries a 429 or a timeout immediately, up to three times. That team will not change it this quarter.
- You have one engineer and two weeks, and the HTTP service stays in Python.

Design the component between the HTTP handlers and the GPU: how requests form batches, when a batch runs, how results reach the right caller, and what happens above capacity. Choose and defend the queue limit. Then say what changes when the same GPU serves text generation instead. Write the rollout plan with its rollback triggers.

## Answer

<Depth>
<Fragment slot="short">
<p>Handlers put (input, future, deadline) on a bounded queue and block on the future. One worker owns the GPU: whenever it is idle it takes everything queued, up to 100, runs it, and completes each future. Batches form on their own while the GPU is busy, so there is no wait timer: at 900 requests per second the profile settles at about 39 inputs per batch and 43 ms per batch, well inside 250 ms. The capacity is 1,250 requests per second at batch 100; above it, the queue admits a request only if the batches ahead of it fit its deadline, which works out to 199 queued requests at the profiled numbers, and rejects the rest with a cheap 429 that the retrying client cannot turn into GPU work. For generation, the batch becomes iteration-level: requests join and leave the running set every step, with KV memory and a per-step token budget as the limits, and a synchronous caller with a 1-second timeout can only be served for short outputs. What I give up: requests above capacity fail fast instead of succeeding slowly.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The capacity, computed.</strong> A batch of <em>b</em> takes 20 + 0.6<em>b</em> ms. At <em>b</em> = 100 that is 80 ms, so the GPU's ceiling is 100 / 0.080 = 1,250 requests per second; at <em>b</em> = 1 it is 48.5. The fixed 20 ms is the weights' cost per pass, paid once per batch; this is the reason batching pays, and Databricks' measurement on an A100 shows the same shape for a language model (14 times the throughput for 4 times the latency at batch 64).</p>
<p><strong>The decision: when to run a batch.</strong> Two answers are defensible.</p>
<ul>
<li><em>Run whenever the GPU is idle.</em> The worker takes whatever is queued the moment the previous batch finishes. Under load the batch size finds its own level: at 900 per second, <em>b</em> = 900 × (0.020 + 0.0006<em>b</em>) gives <em>b</em> ≈ 39 and a 43 ms batch, so the worst case is a request that arrives just after a batch starts and waits for it, then for its own: about 87 ms. At night a request runs alone in about 21 ms. The cost: at low load the GPU runs many small, inefficient batches. On a dedicated GPU nobody pays for that.</li>
<li><em>Wait up to a window (say 10 ms) for the batch to fill.</em> Fewer, larger batches at low and middle load. The cost: every request at night pays up to 10 ms for nothing, and the window has to be retuned when the profile changes. It wins when the GPU is shared with another model, or when GPU-seconds are billed, because then the idle time has a buyer.</li>
</ul>
<p>Here the GPU is dedicated and the objective is latency, so I would run whenever idle and keep the window as a setting at zero.</p>
<p><strong>The quantity: the queue limit.</strong> Above 1,250 per second the queue grows without bound unless something rejects. Under saturation a request with <em>Q</em> requests ahead of it waits up to 80 ms for the batch in flight, then runs in batch number ceil((<em>Q</em> + 1) / 100) after it, each 80 ms. Two batches fit 250 ms (80 + 160 = 240 ms) and three do not, so the request must be among the first 200 queued: <em>Q</em> ≤ 199. I would not ship 199 as a fixed count, for the reason in the failure mode below; I would admit a request only if the in-flight batch plus the batches ahead of it, at the measured batch time, fit its deadline, which gives 199 at the profiled numbers and less when batches slow down. A limit from 100 to 200 is reasonable here; below 100 rejects requests that would have made it, which matters with a client that retries. A limit of 1,000 is not: the request at position 1,000 waits for the batch in flight and 11 more, 960 ms, and the client gives up at 1 second and retries into a longer queue.</p>
<p><strong>The constraint conflict: rejection against a client that retries.</strong> At 1,500 per second offered, 250 per second are rejected, and the client turns each into up to three more attempts at once. The GPU still does 1,250 per second; what must not happen is the retries reaching it. So the rejection is taken before the body is parsed or tokenized, costs microseconds, and carries <code>Retry-After</code> for the day the client honours it. A request whose deadline passes while queued is dropped before it reaches the GPU, because its caller has already gone.</p>
<p><strong>Results to the right caller.</strong> Each queue entry carries its own future; the worker completes futures in input order after the batch returns, or sets the exception on every future in the batch if the pass fails. A failing input is found by splitting the batch in halves and rerunning, and quarantined so one bad request does not fail 99 others every time it is retried.</p>
<p><strong>Generation on the same GPU.</strong> A batch that runs until its longest member finishes leaves finished slots idle, so the worker switches to iteration-level scheduling: the running set holds up to 100 sequences, each step computes one token for each running sequence plus a chunk of new prompts under a per-step token budget, and a finished sequence's slot and KV blocks go to the next waiting request on the next step. Admission is bounded by free KV blocks, not by the count of 100. The budget trades time to first token against the gap between tokens. The harder constraint is the client: a synchronous caller with a 1-second timeout gets an answer only if time to first token plus output length times inter-token latency fits in a second. At an illustrative 25 ms between tokens, that is fewer than 40 output tokens. Longer outputs need streaming or an asynchronous job, which is the other team's change, so I would write that down rather than design around it.</p>
<p><strong>Where this design fails.</strong> The 199 assumes every batch costs what the profile says, and the profile padded every input to 512 tokens. With real inputs, one 512-token input pads a batch of short ones to its length; with length-bucketed batches, a bucket of long inputs costs more per input than the profile. Either way the batch time rises when long inputs cluster, a fixed count of 199 admits requests that will miss 250 ms, and the first sign is p99 rising with the queue limit never reached. The deadline-based check uses the measured batch time over the last few seconds, so it shrinks the effective limit when batches get slower; bucketing by length keeps one long input from inflating a batch of short ones.</p>
<p><strong>What I give up.</strong> Callers above capacity get a fast 429 and their own retries instead of a slow success. GPU efficiency at night. Priorities between callers, which this design does not have.</p>
<p><strong>Rollout plan.</strong> Week 1: build the worker, the queue and deadline admission behind a flag, with a fake model and a fake clock in tests for batch formation and rejection; replay a recorded hour of traffic against a staging GPU. Week 2: shadow production traffic at 10%, then serve 10%, 50% and 100% over three days. Rollback triggers, each reverting to the previous path: server-side p99 above 250 ms for 10 minutes at under 1,000 requests per second offered; any request completed with another request's result (checked by echoing a request id through the batch); a 429 rate above 1% while offered load is under 1,000 per second, which means admission is wrong rather than the GPU being full. The risk note names the retrying client as an accepted risk until next quarter.</p>
</Fragment>

### Sketch

```python
import queue, time
from concurrent.futures import Future

class Batcher:
    def __init__(self, model, max_batch=100, deadline_s=0.25):
        self.q = queue.Queue()
        self.model, self.max_batch, self.deadline_s = model, max_batch, deadline_s
        self.batch_s = 0.080               # full-batch time, updated from measured batches

    def submit(self, x):
        batches_ahead = 1 + (self.q.qsize() + 1 + self.max_batch - 1) // self.max_batch   # in flight + up to its own
        if batches_ahead * self.batch_s > self.deadline_s:
            raise Overloaded()             # HTTP 429 with Retry-After, before parsing the body further
        fut = Future()
        self.q.put((x, fut, time.monotonic() + self.deadline_s))
        return fut.result(timeout=self.deadline_s)

    def worker(self):
        while True:
            batch = [self.q.get()]         # idle: block for the first request
            while len(batch) < self.max_batch:
                try:
                    batch.append(self.q.get_nowait())   # take what queued while the GPU was busy
                except queue.Empty:
                    break
            now = time.monotonic()
            live = [b for b in batch if b[2] > now]
            ...                            # run live inputs, set each future, update batch_s
```

## Follow-ups

- *Two callers send 30% of the traffic each and one of them bursts. How do you stop one caller's burst from filling the queue for the other?*
- *How do you test the batch formation and the admission rule without a GPU?* A fake model whose run time follows the profile and a fake clock, so batch sizes and rejections are exact for a scripted arrival pattern.
- *The second GPU arrives next month. What routes between the two, and what signal does the router use?*

## Common mistakes

- Waiting only for a full batch, so a lone request at night waits forever.
- An unbounded queue, which turns overload into timeouts for everyone instead of fast rejections for some.
- A queue limit set as a count from a padded profile and never revisited.
- Letting rejected requests reach tokenization or the GPU, so client retries add load where capacity is shortest.
- Static batches for text generation, so short outputs wait for long ones.
- Promising a synchronous response for generation without checking output length against the caller's timeout.
