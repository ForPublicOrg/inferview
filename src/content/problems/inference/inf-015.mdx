## Question

<Callout kind="interview" label="As published">
"Design an LLM inference API" with streaming and batch modes, several model sizes, about 1,000 requests per second at peak, TTFT under 500 ms and at least 30 tokens per second per stream.
</Callout>

The prompt's numbers: 10 million calls per day, about 1,000 requests per second at peak, TTFT under 500 ms, at least 30 output tokens per second per streaming request. Customers can choose between a small and a large model. The interviewer will follow up on autoscaling when loading a model takes minutes, and on serving per-customer fine-tuned adapters. These are interview assumptions, not industry data.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Turn "at least 30 tokens per second" into a per-step latency budget, then into a batch size per replica.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Batch requests have no latency target. How can they help the streaming fleet?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Slow model loads mean spare capacity has to exist before the spike, not after it.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A gateway (auth, per-tenant token limits, routing by model and mode) in front of per-model pools of inference replicas running continuous batching with paged KV cache. Streaming requests go to the pools directly; batch jobs go to a durable queue drained into spare capacity. SLOs on TTFT and per-request ITL; the 30 tokens per second target means ITL under 33 ms, which caps the batch per replica, found by load test. Size pools with Little's law at peak, autoscale on queue depth, hold warm spare replicas for spikes shorter than a model load, and pack adapters onto shared base-model replicas with adapter-aware routing.</p>
</Fragment>
<Fragment slot="long">
<p>Numbers first. 10 million a day averages 116 requests per second, so the 1,000 peak is about 8.6 times the average: a large night-time trough the batch mode can use. 30 tokens per second means at most 33 ms per decode step for every stream in a batch; the load test finds the largest concurrency per replica with p99 ITL under that, per model size. TTFT under 500 ms covers queueing plus prefill, so queues must stay short and long prompts need chunked prefill or their own pool.</p>
<p>Capacity. Little's law: requests in flight = arrival rate x time in system. If a mean streamed response takes 8 s, peak needs about 8,000 concurrent sequences across the fleet; divide by measured concurrency per replica times a headroom factor to get replicas per pool. Re-run when prompt or output lengths shift.</p>
<p>API. Streaming over SSE with OpenAI-compatible request shapes; batch as an upload of request files with a job id, a completion window and results written to storage. Idempotency keys on batch submission. Usage in every response for billing.</p>
<p>Request path. Gateway authenticates, checks the tenant's token bucket (reserve prompt plus max_tokens, settle after), picks the pool by model, and routes to the replica with the shortest queue, preferring replicas that already hold the tenant's prefix or adapter. Replicas run continuous batching, paged KV cache, prefix caching and chunked prefill with a token budget chosen for the ITL target.</p>
<p>Autoscaling. Signal: waiting requests and batch size (GKE's recommendation), with KV cache usage as a second trigger; never GPU utilisation alone. Because a replica takes minutes to load, keep warm spare replicas sized for the largest spike that can arrive within one load time, scale ahead of known daily peaks, scale in slowly, and shed lower tiers with 429 before the TTFT SLO breaks. Batch jobs soak up the trough and are paused first when streaming traffic rises.</p>
<p>Adapters. Serve per-customer LoRA adapters on shared base-model replicas, load them on demand with an LRU of resident adapters, and route by adapter so requests land where the adapter is loaded; cold adapter loads count against TTFT, so popular adapters stay pinned.</p>
<p>SLOs and operations. SLIs: share of requests with TTFT under 500 ms, share with p99 ITL under 33 ms, success rate. Error budget is 100% minus the SLO; spend it on deploys deliberately, with canaries that compare latency, output length and eval scores before widening.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>One customer sends 30% of all traffic. What changes?</em> Per-tenant limits and possibly a dedicated pool, so their spikes cannot breach other tenants' SLOs.</li>
<li><em>How do you roll out a new model version?</em> Load it on a canary pool, shadow or split a small share of traffic, compare TTFT, ITL, tokens per request and eval results, then shift traffic by routing, keeping the old pool warm until the error budget is safe.</li>
<li><em>Region failure?</em> A second region with enough headroom for the critical tiers, and a declared degraded mode (smaller model, lower max_tokens) for the rest.</li>
</ul>
</Fragment>
</Depth>

What the interviewer is checking: the 30 tokens per second target translated into a per-step budget and a measured concurrency, capacity derived with stated assumptions rather than guessed, the right autoscaling signal, an explicit answer to slow model loads, and batch mode used to fill the trough rather than built as a separate system.

## Follow-ups

- *Small and large models: separate fleets or shared GPUs?* Separate pools by default, since each replica serves one model; consider packing small models several per GPU if their traffic is low.
- *What is the first dashboard you build?* TTFT and ITL percentiles per pool, queue depth, batch size, KV usage, preemptions, and error rate per tenant tier.
- *How do you price it?* Per input and output token, with a discount for batch that reflects using otherwise idle capacity.

## Common mistakes

- One "latency" SLO that mixes TTFT and inter-token latency.
- Autoscaling on GPU utilisation.
- Capacity numbers with no stated per-replica concurrency or response time behind them.
- Treating batch mode as a separate fleet instead of trough filler.
- Ignoring adapter placement, so every request for a fine-tuned model pays a cold load.
