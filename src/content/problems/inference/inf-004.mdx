## Question

<Callout kind="interview" label="As reported by a candidate">
"Trace a prompt through an LLM inference engine, using a vLLM-style paged-KV architecture as the reference."
</Callout>

Walk from the HTTP request to the last streamed token: admission, prefill, decoding, PagedAttention, the block table and continuous batching. The interviewer will stop you to ask three things: why contiguous per-request allocation wastes memory, how block tables allow non-contiguous storage, and what changes when requests finish at different times or a long prompt enters an active batch.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Think of the KV cache as a heap and the block table as a page table.</p></details>
<details class="hint"><summary>Hint 2</summary><p>The scheduler runs once per decode step, not once per request.</p></details>
<details class="hint"><summary>Hint 3</summary><p>A long prompt can be processed in pieces across several steps.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The request is tokenized and queued. Each step, the scheduler admits waiting requests if enough free KV blocks exist, and runs one forward pass over a batch that mixes prefill tokens for new requests and one decode token for each running request. Prefill writes keys and values into fixed-size blocks listed in the request's block table; each decode step appends a token and takes a new block only when the last one fills. When a request finishes, its blocks return to the free list and a waiting request takes its slot on the next step.</p>
</Fragment>
<Fragment slot="long">
<p>Admission: the API server tokenizes the prompt and hands it to the engine's queue. The scheduler checks free blocks against the prompt length and the batch's token budget. If memory is short, the request waits; if running requests later outgrow memory, the scheduler preempts one, frees its blocks, and in vLLM V1 recomputes it when it is readmitted.</p>
<p>Prefill: the prompt's tokens run through the model in one pass (or in chunks under chunked prefill). For every layer, keys and values for each token are written into the request's blocks. With 16-token blocks, a 40-token prompt holds 3 blocks, the last one half full. The first output token comes out of this pass, so its latency is queue time plus prefill time.</p>
<p>PagedAttention and the block table: the block table maps logical block i of the request to a physical block anywhere in the KV pool, like a page table. The attention kernel reads keys and values through that table, so a request's cache does not need to be contiguous. Contiguous per-request allocation had to reserve the maximum length up front because the final length is unknown; the vLLM paper measured only 20.4% to 38.2% of KV memory holding real token states in such systems. Paging wastes at most the unfilled part of each request's last block.</p>
<p>Decoding with continuous batching: each step runs one token for every running request. A request that emits an end token or hits max_tokens is removed after that step, its blocks are freed, and the scheduler fills the slot from the queue on the next step. No request waits for the slowest member of a batch.</p>
<p>A long prompt entering an active batch: its full prefill in one step would stall every running decode. Chunked prefill splits it across steps under a per-step token budget, so decodes keep flowing while the long request's first token arrives a little later.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What happens to blocks shared by parallel samples?</em> They are reference counted; a sample that writes into a shared partial block gets its own copy first (copy-on-write).</li>
<li><em>Where does prefix caching fit?</em> Full blocks are hashed by their tokens and their prefix, so a new request whose prompt starts the same way reuses existing blocks and skips that part of prefill.</li>
<li><em>What does the kernel pay for paging?</em> An indirection per block when reading keys and values; the memory saved buys a larger batch, which outweighs it.</li>
</ul>
</Fragment>
</Depth>

A useful way to structure the walk-through is by the three resources involved: the queue (admission, preemption), the KV pool (blocks, block tables, freeing) and the step (one batched forward pass mixing prefill and decode tokens). Interviewers following this question are checking that you know the scheduler decides per step, that memory is allocated per block rather than per request, and that "finish at different times" is exactly the case continuous batching was built for.

## Follow-ups

- *How do you pick the block size?* Smaller blocks waste less in the last block and share prefixes at finer grain; larger blocks mean fewer table entries and more efficient kernels. vLLM defaults to 16 tokens.
- *Recompute or swap on preemption?* vLLM V1 recomputes by default and removed CPU swapping; swapping can win for very long contexts on fast host links.
- *What would you put on a dashboard for this engine?* Waiting and running requests, KV cache usage, preemptions, TTFT and ITL percentiles.

## Common mistakes

- Describing PagedAttention as a faster attention formula. It is an allocator and memory layout; the kernel reads through the block table.
- Crediting continuous batching to vLLM. Iteration-level scheduling was published in Orca; vLLM's contribution was the paged memory that lets the batch grow.
- Saying the batch is fixed for the lifetime of the requests in it.
- Forgetting that the first output token is produced by the prefill pass.
