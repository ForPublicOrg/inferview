## Question

<Callout kind="interview" label="As reported by a candidate">
"Trace a prompt through an LLM inference engine, using a vLLM-style paged-KV architecture as the reference."
</Callout>

The candidate report lists three follow-ups: why contiguous per-request KV allocation wastes memory, how block tables allow non-contiguous storage, and what changes when requests finish at different times or a long prompt enters an active batch. Answer them against this engine state, constructed for the problem:

- Block size 16 tokens, a KV pool of 2,048 blocks, `max_num_batched_tokens` 2,048, chunked prefill and prefix caching on, first-come-first-served scheduling. The scheduler serves running requests before waiting ones, as vLLM V1 does.
- Running and decoding at step *t*: **A** with 1,500 tokens of context, whose first 1,024 tokens are the product's system prompt; **B** with 300 tokens; **C** with 40 tokens.
- Waiting, in this order: **D**, a 6,000-token prompt that starts with the same 1,024-token system prompt; **E**, a 200-token prompt.

Walk D from the HTTP request to its last streamed token. For steps *t*, *t*+1 and *t*+2, give the tokens each request is scheduled, the blocks D and E take, and the step in which D and E produce their first tokens. Then choose a block size for this deployment and defend it against one smaller and one larger choice.

## Answer

<Depth>
<Fragment slot="short">
<p>D is tokenized, queued, and admitted when the step's budget has room. Its first 1,024 tokens match 64 full blocks A already holds, so D starts with them in its block table and computes from token 1,025. Each step spends the budget on A, B and C's decode tokens first, then on D's prefill in chunks of up to 2,045 tokens: D finishes its prompt and emits its first token in step <em>t</em>+2, and E is admitted with the 1,159 tokens left in that step and emits its first token in the same step. Blocks come from the free pool one at a time as tokens are written, so the five requests hold 440 of 2,048 blocks. I would keep 16-token blocks here: 128-token blocks would waste about 39% of the pool in partly filled last blocks at 200 running sequences, against about 5% at 16.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Admission.</strong> The API server tokenizes D and hands it to the engine's waiting queue. A scheduling decision in vLLM V1 is a map from request to the tokens it computes this step; prefill and decode are the same operation with different counts.</p>
<p><strong>Step <em>t</em>.</strong> Running requests go first: A, B and C each get one decode token, 3 tokens in all, and none of them crosses a block boundary (A writes its 1,501st token into its 94th block, which has room). 2,045 tokens of budget remain. D is next in the waiting queue. The prefix cache matches its first 64 blocks against the blocks A holds: each full block is keyed by its tokens and its parent's key, so a match means the whole prefix matches, not only that block. D's block table starts with those 64 physical blocks, their reference counts go to 2, and D's computed count starts at 1,024. D is scheduled 2,045 tokens, bringing it to 3,069 computed tokens, which need 192 blocks: 128 new ones from the free list. E gets nothing: the budget is spent.</p>
<p><strong>Step <em>t</em>+1.</strong> D is now a running request with a partial prefill. A, B and C get their decode tokens, D gets the next 2,045, reaching 5,114 tokens in 320 blocks (128 more). E waits again.</p>
<p><strong>Step <em>t</em>+2.</strong> D has 886 prompt tokens left. It takes them, completes its prompt, and the same forward pass produces its first output token. 1,159 tokens of budget remain, so E is admitted and computes its whole 200-token prompt in 13 blocks, and emits its first token in step <em>t</em>+2 as well. Without the prefix cache, D would need the 1,910 tokens it has left in step <em>t</em>+2, E would get a 135-token chunk, and E's first token would slip to step <em>t</em>+3.</p>
<p><strong>Decoding and finishing.</strong> From then on every step gives D one token, and D takes a new block only when its last block fills, every 16 tokens. Tokens stream as they are produced. When D emits its end token or reaches its limit, it leaves the running set after that step, its blocks' reference counts drop, and the 64 shared blocks stay with A. A waiting request takes the freed slot on the next step: requests finishing at different times is the case iteration-level scheduling, from Orca, was built for.</p>
<p><strong>Why contiguous allocation wastes memory.</strong> A contiguous allocator does not know the final length, so it reserves the maximum. At a <code>max_model_len</code> of 8,192, each request reserves 512 blocks' worth of slots; four requests take 2,048 and the fifth does not fit, while paging holds all five in 440 blocks (21% of the pool). C, at 41 tokens, would sit in a reservation that is 0.5% used. That is the reserved waste; the allocator's own gaps between reservations add external fragmentation. The PagedAttention paper reports that only 20.4% to 38.2% of KV memory held token states in the systems it measured.</p>
<p><strong>How block tables allow non-contiguous storage.</strong> The block table maps logical block <em>i</em> of a sequence to any physical block in the pool, a page table for KV. The attention kernel reads keys and values through it, so a sequence's blocks can sit anywhere, two sequences can point at the same physical block, and the only waste is the unfilled tail of each sequence's last block.</p>
<p><strong>A long prompt entering an active batch.</strong> D's 4,976 uncached tokens in one step would make A, B and C wait for the whole prefill before their next token; the Sarathi-Serve paper measured hybrid batches carrying whole prefills at up to 28.3 times the time between tokens of a decode-only batch. Chunking bounds every step at 2,048 tokens, and the vLLM docs describe decodes being batched before any prefill. The price is D's time to first token, which now spans three steps, and E's, which waits behind D.</p>
<p><strong>The block size.</strong> Partly filled last blocks waste about (block size - 1) / 2 slots per sequence on average. The pool holds 32,768 token slots; at 200 running sequences that is 1,500 slots (4.6%) at 16 tokens per block and 12,700 slots (38.8%) at 128. Smaller blocks also share prefixes at a finer grain, since only full blocks are cached. Larger blocks mean fewer table entries and better kernel efficiency: the paper found blocks that are too small underuse the GPU when reading KV, and that swapping costs more than recomputation at small block sizes, with the two comparable from 16 to 64. It found 16 to 128 best on ShareGPT and 16 or 32 on the shorter Alpaca sequences, and vLLM defaults to 16. For this workload, mostly short sequences with one long shared system prompt, 16 or 32 is defensible. 128 is not at this pool size, and 1 or 2 would spend the kernel's time on table lookups.</p>
<p><strong>Where this model of the engine breaks.</strong> The trace assumes the system prompt blocks are held by A. If A had finished and the pool were under pressure, those blocks would be free and evictable, and D would hit only the ones not yet reused. A trace that promises a cache hit has to say which blocks were still resident.</p>
</Fragment>

## Follow-ups

- *Pushback: the team wants block size 64 to cut kernel time on long documents, and the chat traffic is 90% of requests. What do you measure before agreeing, and what waste do you accept in writing?*
- *Reversal: what would you need to see in production to move from 16-token to 32-token blocks?* Kernel time per decode step falling by more than the extra tail waste costs in batch size, measured at peak running sequences.
- *What goes on the dashboard for this engine?* Running and waiting counts, KV blocks in use, prefix-cache hit rate, preemptions per minute, and percentiles of time to first token and inter-token latency, with prompt length as a dimension.

## Common mistakes

- Describing PagedAttention as a faster attention formula. It is an allocator and a memory layout; the kernel reads through the block table.
- Crediting iteration-level scheduling to vLLM. Orca published it; PagedAttention made the memory side cheap enough to batch widely.
- Letting D's whole prefill run in one step, which stalls every decode in the batch.
- Assuming a prefix-cache hit without saying the blocks are still resident, or that a hit on one block is enough when the key covers the whole prefix.
- Forgetting that the step that computes a prompt's last token also emits the first output token.
