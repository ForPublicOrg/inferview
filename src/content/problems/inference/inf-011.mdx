## Question

<Callout kind="interview" label="As asked">
"You quantized your LLM, but accuracy dropped significantly. How do you minimize quantization loss?"
</Callout>

The version here. A team moved a 70B dense chat model from BF16 to 4-bit weights so that it fits on half the GPUs. The release changed three things at once:

```yaml
weights:
  method: gptq
  bits: 4
  group_size: 128
  desc_act: true
  calibration: 128 random 2,048-token segments of C4
kv_cache_dtype: fp8_e4m3
kv_cache_scales: none
```

The eval report, all slices greedy, scored by the same graders before and after:

The release owner signed off on the perplexity row and the three English slices. Which explanation accounts for the collapse on one slice, and what do you collect before re-releasing?

## Answer

GPTQ quantises a layer by choosing rounded weights that minimise the squared error of the layer's output, WX, on the calibration inputs X. When it rounds one weight it updates the remaining weights to compensate, and the compensation uses the calibration inputs' statistics. Error ends up in the input directions that the calibration set rarely exercises. Here the calibration set is the GPTQ paper's own default: 128 random 2,048-token segments of C4, generic English web text. Korean and Japanese tokens drive activation patterns that set barely covered, so their outputs absorb error the English slices never see. The table fits that: English perplexity moved by 0.06, three English slices moved 1 or 2 points, and the one slice far from the calibration distribution lost 19.

The evidence is circumstantial, and three changes shipped together. Collect, in this order:

1. One eval run with the 4-bit weights and a BF16 KV cache. This separates the weight change from the cache change in one run.
2. Per-layer output error on held-out Korean and Japanese prompts against held-out English prompts. If the weights are the cause, the gap concentrates in specific layers.
3. A re-quantisation calibrated on a sample of production prompts in proportion to served traffic, including Korean and Japanese, then the same slice.
4. AWQ on the same model as a comparison. Its authors argue it does not overfit the calibration set because it fits no reconstruction, and that claim is worth testing on this slice rather than assuming.

Without those runs, keep Korean and Japanese traffic on the BF16 deployment and ship the 4-bit model for the English traffic it passed on. Treat the KV change as unreviewed. If the weight-only run still fails after recalibration, keep the most affected layers at higher precision. FP8 weights are the fallback that costs back half the memory saving.

Ranking the real defects:

1. **Calibration data that does not cover the served traffic.** This explains the symptom.
2. **An FP8 KV cache with no calibrated scales.** The vLLM documentation sets every scale to 1.0 without calibration and recommends dataset calibration. It is a real defect and shipped in the same release, so attribution is impossible until it is ablated. It does not explain this pattern: the long-document slice, which reads the most cached keys and values, lost 2 points.
3. **Signing off on perplexity and English slices.** This is the process defect that let the first two through.

Why the others tempt:

- Coarse groups are the classic cause of 4-bit damage, but they would hurt every slice. The GPTQ paper reports group size 128 within 0.1 to 0.3 perplexity of uncompressed at 3 bits on its 175B models, so at 4 bits it is not the first suspect.
- "The slice is too small" is a reflex worth checking. At 300 items and about 0.7 accuracy, the standard error of each score is about √(0.7 × 0.3 / 300) = 0.026, so the difference has a standard error near 0.037, and 0.19 is about five of them.

## Follow-ups

- *The recalibrated model recovers the slice to 0.79 but costs 0.01 on English support. Ship it?*
- *How big should the calibration set be, and drawn from where?* Sampled from production prompts in the proportions you serve, with every language and task family present. Then check that adding more samples no longer moves the weakest slice.
- *Which eval would have caught this before sign-off?* A slice per language and task family that the product serves, gated individually, not one averaged score and not perplexity on English text.

## Common mistakes

- Signing off on perplexity, which here moved by 0.06 while one product slice lost 19 points.
- Shipping weight and KV-cache quantisation in one release, so no eval can say which one did the damage.
- Blaming the bit width and returning to BF16 without trying a calibration set that matches the traffic.
- Dismissing a large drop on a small slice as noise without computing the standard error.
