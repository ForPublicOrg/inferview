## Question

<Callout kind="interview" label="Capacity review">
"Legal wants whole contracts in context, up to 256K tokens. Put every attention design we could run on one table, then tell me whether this tier moves to a hybrid."
</Callout>

Published configs, one per design:

| Design | Model and source | Attention shape |
|---|---|---|
| Multi-head | LLaMA 65B, Table 2 of the paper | 80 layers, dimension 8,192, 64 heads |
| Grouped, 8 KV heads | Llama 3 70B, Table 3 | 80 layers, dimension 8,192, 64 query heads, 8 KV heads |
| Latent (MLA) | DeepSeek-V3 config.json | 61 layers, kv_lora_rank 512, qk_rope_head_dim 64 |
| 1:7 attention to Mamba | Jamba v0.1 config.json | 32 layers, one attention layer in every 8, hidden 4,096, 32 heads, 8 KV heads; Mamba layers with d_state 16, d_conv 4, expand 2 |

Compute, in BF16: the cache bytes per token for each design, and the cache one 256K sequence (262,144 tokens) needs. Then the number to give: **one 8 x H100 80 GB node runs the Jamba v0.1 design as a single tensor-parallel replica with BF16 weights (52B parameters); how many 256K sessions fit?** Choose your runtime reserve per GPU, and decide whether and how to count the Mamba layers' state. Finally: the tier today runs Llama 3 70B at its 128K limit and splits longer contracts; do you move it?

## Answer

<Depth>
<Fragment slot="short">
<p>Bytes per token in BF16: multi-head 2,621,440; grouped 327,680; latent 70,272; hybrid 16,384. At 262,144 tokens: 687 GB, 85.9 GB, 18.4 GB and 4.3 GB. The node fits about 105 to 117 hybrid sessions, against 6 for the grouped 70B and none for the latent model, whose 671 GB of FP8 weights exceed the node. The hybrid's saving comes from having 4 attention layers out of 32, not from a smaller attention layer: per attention layer it stores the same 4,096 bytes as Llama 3 70B. I would move only the 256K tier, and only after the hybrid matches the current setup on whole-document tasks from our own contracts at 128K and beats split-and-retrieve at 256K; the dominant term for the decision is accuracy at length, not memory.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Per token, from the configs.</strong> Element counts per token follow DeepSeek-V2's Table 1; times 2 bytes.</p>
<ul>
<li><em>Multi-head, LLaMA 65B:</em> head dimension 8,192 / 64 = 128. 2 x 80 x 64 x 128 = 1,310,720 elements, 2,621,440 bytes (2.5 MiB).</li>
<li><em>Grouped, Llama 3 70B:</em> 2 x 80 x 8 x 128 = 163,840 elements, 327,680 bytes. Exactly 8 times smaller, because only the KV head count changed.</li>
<li><em>Latent, DeepSeek-V3:</em> (512 + 64) x 61 = 35,136 elements, 70,272 bytes. One shared latent per layer plus the decoupled RoPE key, which has to be cached because RoPE blocks absorbing the up-projection into the query.</li>
<li><em>Hybrid, Jamba v0.1:</em> 32 layers with attention every 8th, so 4 attention layers. Head dimension 4,096 / 32 = 128. 2 x 4 x 8 x 128 = 8,192 elements, 16,384 bytes.</li>
</ul>
<p><strong>At 262,144 tokens.</strong> 687 GB, 85.9 GB, 18.4 GB and 4.29 GB. The hybrid figure is 4 GiB, which matches the 4 GB the Jamba paper reports at 256K; its 128 GB for LLaMA-2 6.7B is the same multi-head arithmetic at 32 layers.</p>
<p><strong>The state the hybrid keeps instead.</strong> The 28 Mamba layers hold a fixed state per sequence: channels times state size, (expand 2 x 4,096) x 16 = 131,072 elements per layer for the scan, plus a convolution buffer of up to d_conv = 4 inputs per channel, 32,768. That is 28 x 163,840 = 4.6 million elements, 18.4 MB if the engine keeps it in FP32 and 9.2 MB in BF16. At 256K it is 0.4% of the session, so leaving it out is a reasonable choice there. At short lengths it is not: the state equals the KV cache at 18.4 MB / 16,384 = 1,120 tokens (560 in BF16), so for chat traffic the hybrid's advantage mostly disappears.</p>
<p><strong>The number.</strong> 640 GB on the node, 104 GB of BF16 weights, a reserve of 4 to 10 GB per GPU (32 to 80 GB). Per session 4.295 GB plus 0.018 GB of state, 4.31 GB. (640 - 104 - 32) / 4.31 = 117; (640 - 104 - 80) / 4.31 = 105. The band of 100 to 120 admits any reserve in that range, with or without the state. Unreasonable: counting a cache in all 32 layers (34.4 GB per session, 13 or 14 sessions), using the query-head count, or splitting the node into two four-GPU replicas without saying so, which pays for the weights twice.</p>
<p><strong>The other designs on comparable hardware.</strong> Grouped 70B with FP8 weights on the same node: (640 - 70 - 32 to 80) / 85.9 = 5.7 to 6.3, so about 6 sessions, and its trained context is 128K, so 256K is a yardstick rather than a deployment. Latent: per token it is 4.7 times smaller than the grouped 70B, but its 671 GB of FP8 weights do not fit 640 GB at all; on an 8 x H200 node (1,128 GB) it holds (1,128 - 671 - 32 to 80) / 18.4 = 20 to 23 sessions, and its published context is 128K. Multi-head at 256K needs more than a node for one session. For the latent model the dominant term is weights, for every other design it is cache.</p>
<p><strong>The decision.</strong> Two answers are defensible.</p>
<ul>
<li><em>Move the 256K tier to a hybrid.</em> About 18 times the sessions per node of the grouped 70B, and whole contracts in one context. The cost: a different model whose accuracy on these contracts is unmeasured, a new engine path for recurrent state, and an eval and migration the team pays for once.</li>
<li><em>Stay on the grouped 70B at 128K and split longer contracts with retrieval.</em> Known quality on the tasks the tier already serves. The cost: 6 sessions per node at full length, and every question that needs the whole contract (all indemnity clauses, every party's obligations) depends on retrieval finding every piece.</li>
</ul>
<p>The conflict is cost per session against accuracy at length. Memory favours the hybrid by an order of magnitude, so the decision rests on the accuracy test: paired comparisons on the team's own contracts, binned at 32K, 128K and 256K, with aggregation, multi-hop and follow-up questions as well as single-fact lookups, because HELMET found needle results do not reliably predict downstream performance. I move only if the hybrid at 256K beats split-and-retrieve on whole-document questions and stays within noise at 128K.</p>
<p><strong>How the recommendation fails.</strong> The hybrid's per-session saving assumes one long session holds one state. Follow-up questions on the same contract want the document prefix cached. A paged KV cache can be shared at any block boundary, but a recurrent state summarises every token before it and cannot be rewound, so reuse works only at positions where the engine saved a copy of the state. If the engine saves none, every follow-up re-runs the 256K prefill, and the capacity gain turns into a prefill bill. Check how the serving engine caches hybrid prefixes before quoting the 18 times.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not convert the grouped 70B to latent attention instead of changing models?</em> The cache would shrink about 4.7 times per token, but the conversion is a training project and the accuracy test is the same one.</li>
<li><em>Does FP8 KV change the table?</em> It halves every cache row and leaves the ratios and the latent model's weight problem unchanged.</li>
</ul>

## Follow-ups

- *Pushback: the eval to prove the hybrid on contracts costs six weeks of the two engineers who would otherwise build better retrieval for split documents. Which do you fund, and what risk do you accept in writing?*
- *Reversal: the hybrid ships. What would you need to see in production to move the tier back?* Whole-document answers rated worse than the split baseline in a paired sample, or a follow-up re-prefill rate high enough that sessions per node fall below what the 70B served.
- *Two staff engineers disagree: one says per-token cache decides architecture, the other says weights do. How do you settle it without deciding by rank?* Compute sessions per node for each candidate at the tier's real length distribution, which puts both terms in one number.
- *The tier's median contract is 20K tokens and only 5% exceed 128K. Does the decision change?*

## Common mistakes

- Counting a cache in every layer of the hybrid instead of the 4 attention layers.
- Comparing per-token cache across designs while ignoring that the latent model's weights do not fit the node.
- Quoting 256K figures for models trained to 128K as if they were deployable.
- Leaving out the decoupled RoPE key in the latent cache, which gives 512 instead of 576 elements per layer.
- Deciding on memory alone and testing long-context accuracy with needle retrieval.
