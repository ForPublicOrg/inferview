## Question

<Callout kind="interview" label="As asked">
"Do the roofline math: how many tokens/sec can one H100 produce for a 70B model at batch size 1?"
</Callout>

Assumptions so the model fits on one GPU: the 70B model's weights are in FP8, one byte per parameter, about 70 GB. The H100 SXM has 80 GB of HBM at 3.35 TB/s and 1,979 dense FP8 TFLOPS. One user, a 1,000-token context, KV cache in BF16 at 327,680 bytes per token. Give an **upper bound** on decode tokens per second.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Each decode step must read every weight once. How long does reading 70 GB take?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Check the compute side too: about 2 FLOPs per parameter per token.</p></details>
<details class="hint"><summary>Hint 3</summary><p>The KV cache for 1,000 tokens is a third of a gigabyte. Does it matter here?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Memory: each step reads about 70 GB of weights plus 0.33 GB of KV cache, so at least 70.3 / 3,350 s = 21.0 ms per token, at most about 48 tokens per second. Compute: 140 GFLOPs per token at 1,979 TFLOPS is 0.07 ms, 300 times less. Decode at batch 1 is bandwidth bound, and the realistic number is lower because real kernels reach only part of peak bandwidth.</p>
</Fragment>
<Fragment slot="long">
<p>Bytes per step: 70e9 bytes of weights, plus 1,000 x 327,680 = 0.33e9 bytes of cache. Time at 3.35e12 bytes per second: 70.33e9 / 3.35e12 = 21.0 ms. One token per step at batch 1, so at most 47.6 tokens per second.</p>
<p>FLOPs per token: 2 x 70e9 = 1.4e11. At 1.979e15 FLOPs per second: 0.071 ms. The compute floor is about 300 times below the memory floor, so FLOPs are irrelevant at batch 1.</p>
<p>Reality check: kernels rarely sustain peak bandwidth. Databricks' example runs at 50% model bandwidth utilisation; at 50% the answer would be about 24 tokens per second. State the bound, then say what you would measure.</p>
<p>What would raise it: more bandwidth (an H200 at 4.8 TB/s gives about 68), fewer bytes (4-bit weights at about 39 GB give about 85), tensor parallelism across two GPUs (each reads half the weights, minus communication), or speculative decoding (several tokens per weight read).</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>And at batch 8?</em> The weight read is shared, so the step only grows by the extra KV reads: (70 + 8 x 0.33) GB / 3.35 TB/s is 21.7 ms, so up to about 369 tokens per second in total while each user slows slightly. Batch 32 at this context would need about 80.5 GB and no longer fits next to the weights.</li>
<li><em>Would BF16 weights work on one H100?</em> No: 140 GB does not fit in 80 GB. You would need two GPUs, and the per-GPU read is the same 70 GB.</li>
<li><em>Why not use the sparse TFLOPS figure?</em> Sparse numbers need structured-sparse weights; dense models get half.</li>
</ul>
</Fragment>
</Depth>

Worked calculation: (70e9 + 1,000 x 327,680) / 3.35e12 = 0.0210 s per step, so 1 / 0.0210 = 47.6 tokens per second. Without the KV term it is 47.9. The band of 40 to 55 accepts either, and rejects answers that came from the compute side (thousands of tokens per second) or from BF16 weights that do not fit.

## Follow-ups

- *How would you measure the real number?* Run one request with a fixed prompt and long output, record inter-token latency, and compute achieved bandwidth from bytes per step over ITL.
- *What dominates at a 128k context?* The KV cache: 128k x 327,680 bytes is about 43 GB per step, comparable to the weights.
- *Is the answer different for a mixture-of-experts model with 70B total parameters?* Yes. Only the active experts are read per token at batch 1, so the bound is set by active parameters.

## Common mistakes

- Dividing FLOPs by TFLOPS and answering in the thousands of tokens per second.
- Using BF16 weights on one 80 GB GPU without noticing they do not fit.
- Treating the bound as a forecast instead of a ceiling.
- Quoting the sparse TFLOPS number as if it applied.
