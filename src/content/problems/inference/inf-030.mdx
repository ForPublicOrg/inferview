## Question

<Callout kind="interview" label="Incident replay">
Replay the six weeks behind Anthropic's 17 September 2025 postmortem of three infrastructure bugs that degraded Claude's answers with no change to any model. At each checkpoint, commit before the next event appears. Then the staff question: you run serving for a model API on three hardware platforms. For each of the three bugs, name the instrument that would have caught it on the first day. You can fund one this quarter; which, and what does it miss?
</Callout>

The events are from the postmortem, in order. Each checkpoint asks what you would have believed or done with only the events above it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each bug, ask which requests it touched: which platform, which model, which server pool, and whether the same user would hit it twice.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each candidate instrument, ask what it reads (a log field, an output, a logit) and how often it fires on a healthy system.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the privacy rules let an engineer read during an incident, and which instruments need no user content at all.</p></details>

## Answer

What the postmortem says. Three unrelated bugs overlapped. A routing error sent some Sonnet 4 requests to servers configured for the upcoming 1M-token context window from 5 August, 0.8% at first, then 16% in the worst hour after a 29 August load-balancing change; because routing is sticky, about 30% of Claude Code users with requests in the period had at least one misrouted message, and some had many. A TPU server misconfiguration from 25 August occasionally gave high probability to tokens that rarely fit, putting Thai or Chinese characters into English answers and syntax errors into code, on the first-party API only. A change to token selection the same day triggered a latent XLA:TPU compiler bug in approximate top-k under mixed precision, at certain batch sizes only. Detection was slow because evals did not capture the degradation (Claude often recovers from isolated mistakes), privacy controls limited what engineers could read, and the symptoms differed by platform and rate. Anthropic's commitments: more sensitive evals, quality evals run continuously on production systems, and faster debugging tools for community feedback that keep user data private.

<Depth>
<Fragment slot="short">
<p>Each bug needs a different instrument, and two of them need no model judgement at all. The routing error: a per-request assertion that the serving pool's configuration matches the request's context class, logged and counted; it fires on the first misrouted request with no false positives. The TPU corruption: a check on sampled outputs for characters outside the scripts expected in context, which is what Anthropic added to deployment. The top-k miscompile: a differential check that compares the approximate top-k result against exact top-k on sampled decode steps and counts any step where the most probable token went missing. If I fund one, it is continuous probes against each production server pool, because it is the only instrument that sees all three as degraded answers; it misses the low-rate phase of each bug unless it runs thousands of probes a day per pool.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why the probes need volume, computed.</strong> A probe is a fixed prompt with a graded answer, sent to a specific pool. Suppose a probe that lands on a misrouted server fails half the time, since the model often recovers; that 50% is your assumption, and 30% is just as defensible. At the 0.8% misroute rate, a probe fails because of the bug with probability 0.008 × 0.5 = 0.004, and seeing at least one such failure with 95% probability takes ln(0.05) / ln(0.996) ≈ 747 probes. At the worst hour's 16% it takes ln(0.05) / ln(0.92) ≈ 36. That is the easy half. The hard half is the baseline: if healthy probes fail 2% of the time from grading noise, the bug raises that to 2.4%, and telling 2.4% from 2.0% with the usual 95% confidence and 80% power takes about 2.8² × (0.02 × 0.98 + 0.024 × 0.976) / 0.004² ≈ 21,000 probes per arm. Noisy evals were one of the reasons the postmortem gives for slow detection, and this is the arithmetic behind it.</p>
<p><strong>The decision: one instrument this quarter.</strong></p>
<ul>
<li><em>Continuous production probes per pool and platform.</em> Catches all three bugs as what users see, and needs no access to user traffic, which is what the privacy rules allowed. Cost: probe traffic at the volumes above for every pool, model and platform, a grader whose own noise sets the floor, and days of data before a low-rate bug is visible.</li>
<li><em>Exact checks per serving layer.</em> The routing assertion, the unexpected-character check and the top-k differential each run on metadata, outputs or logits, have near-zero baseline noise, and fire on the first bad request. Cost: three separate pieces of work owned by three teams, the differential check costs compute on every sampled step, and each catches only the class of bug it was written for. The next bug that corrupts answers some other way passes all three.</li>
</ul>
<p>I would fund the probes first, scoped to the platforms and pools where traffic concentrates, with the routing assertion added because it is a few lines in the router and would have caught the costliest bug by user count on 5 August. The constraint conflict is privacy against debuggability: the instruments that read user traffic would have been fastest, and they are the ones the privacy rules restrict, so the plan has to work from synthetic probes and from data that contains no user content.</p>
<p><strong>Where the recommendation fails.</strong> Probes see the system that serves the probe. With sticky routing, a probe client that always lands on a healthy server reports health while 16% of real requests are misrouted; probes have to be spread across every server, or pinned to each in turn, or they inherit the same stickiness that hid the bug from most users. The second failure is mixed precision: the top-k bug appeared only at certain batch sizes, and a probe sent at 3 a.m. into a nearly empty batch may never reach one. Run probes inside real traffic, not in a quiet window, and record the batch size each probe was served in.</p>
</Fragment>

## Follow-ups

- *Pushback: the probe budget you need is about 21,000 graded probes per pool per comparison, across three platforms and several models. Finance funds a tenth of that. Which pools go unprobed, and what risk do you write down for them?*
- *Reversal: what would you need to see in a quarter of incidents to move the budget from production probes to exact checks per layer?*
- *Two senior engineers disagree: one says the top-k fix should have stayed approximate with the batch sizes pinned, to keep the efficiency; the other says exact top-k is the only safe choice. How do you decide without deciding by rank?*

## Common mistakes

- Looking for one cause because the reports arrived together. Three bugs with three start dates, platforms and rates looked like one vague regression.
- Treating flat benchmarks as evidence of health when the model recovers from isolated bad tokens.
- Proposing more user-traffic review as the detector without saying what the privacy rules permit.
- Probing from one client and trusting the result on a system with sticky routing.
- Proposing an instrument without saying how often it fires on a healthy system.
