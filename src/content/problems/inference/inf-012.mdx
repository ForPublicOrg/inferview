## Question

<Callout kind="interview" label="Adapted from">
"When does prefix caching help?"
</Callout>

A support assistant sends every request with these parts: a 2,500-token system prompt shared by all customers, 1,500 tokens of tool definitions shared by all customers, an 800-token account summary that is the same for every request from one customer, the conversation so far, the new user message, and the current time. The serving engine (or the hosted API) caches exact prefixes. Which layout gets the most cache reuse?

## Hints

<details class="hint"><summary>Hint 1</summary><p>A cached block matches only if everything before it matched too.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Order the parts from most widely shared to least.</p></details>

## Answer

The prefix cache is keyed on the exact token sequence from the start of the prompt. vLLM hashes each full block from its parent block's hash plus its own tokens, so a single changed token invalidates its block and every later block. Hosted APIs work the same way: Anthropic builds the prefix in the order tools, system, messages and invalidates everything after a change; OpenAI routes by a hash of the initial tokens.

So the layout should run from the most widely shared content to the least: system prompt and tools (all customers), account summary (one customer), conversation (one thread), new message and time (one request). In the correct layout, a request from a new customer still reuses the first 4,000 tokens, a follow-up in the same conversation reuses everything up to the new message, and the timestamp costs nothing because nothing comes after it.

Why the others tempt. A timestamp or greeting at the top feels natural for a system prompt, and it silently turns every request into a cache miss. Putting per-customer context early looks like grouping "context" together, but it fences off the shared tools. Sorting tools by relevance is a real prompt-engineering idea that conflicts directly with caching. The "any substring" belief comes from thinking of the cache as a content store rather than a prefix tree.

## Follow-ups

- *How would you verify hits in production?* Log cached input tokens per request (both major APIs return them, and vLLM exports prefix cache hits and queries) and alert when the ratio drops.
- *Does a 300-token prompt benefit?* Not on hosted APIs with a minimum cacheable length, such as OpenAI's 1,024 tokens for newer models; Anthropic skips caching below its minimum without an error.
- *Where does the time go if the model needs it early?* Put it in the latest message; models read the whole context anyway.

## Common mistakes

- Personalising the first line of the system prompt.
- Changing tool definitions or their order between requests.
- Assuming a cache hit happened because caching is enabled, without checking the usage fields.
