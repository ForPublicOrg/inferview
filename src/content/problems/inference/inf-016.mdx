  solution: |
    def verify(draft, q, p, u, sample):
        # Policy: a drafted token the draft reported at probability 0 is rejected, since the ratio p/q is undefined.
        # Policy: when p and q agree to rounding error the residual has no mass; the target distribution is used instead.
        out = []
        for i, x in enumerate(draft):
            qx, px = q[i][x], p[i][x]
            if qx > 0 and (px >= qx or u[i] * qx < px):
                out.append(x)
                continue
            residual = [a - b if a > b else 0.0 for a, b in zip(p[i], q[i])]
            if sum(residual) <= 0.0:
                residual = p[i]
            return out + [sample(residual)]
        return out + [sample(p[len(draft)])]

## Question

<Callout kind="interview" label="As reported by a candidate">
"Implement and benchmark speculative decoding: normal and speculative decoding with correct proposal verification, rejection, sampling, EOS, positions and KV cache state, then a fair speed benchmark."
</Callout>

The full prompt is an hour of work. This version isolates the part that decides whether the output is still the target model's: the verification of one round for one sequence. The draft model proposed `k` tokens. For each position `i` you have the draft's distribution `q[i]` and the target's `p[i]`, all from one target forward pass, plus `p[k]` for the position after the draft.

Implement `verify(draft, q, p, u, sample)` so that the tokens it emits are distributed exactly as if the target had sampled them one at a time. Randomness enters only through `u` and `sample`, which keeps the tests deterministic. `sample` takes non-negative weights that need not sum to 1, so normalising is your choice.

The constraint: the tests pass distributions as read-counting sequences over a 50,000-token vocabulary. A round may read at most 4 entries per accepted position, plus one pass over whatever the final token needs (at most 3 times the vocabulary in total for that token). At a real vocabulary size, a verifier that builds a residual or a normalised copy for every position spends its time on work the accepted positions never needed.

Two cases are yours to decide, and the docstring asks you to state the choice:

- `q[i][draft[i]] == 0`. The draft reported zero probability for a token it then proposed. This happens when the sampler that drew the token and the distribution that was logged disagree, for example a top-k filter applied after the probabilities were recorded.
- A residual `max(0, p[i] - q[i])` with no mass. In exact arithmetic a rejection implies some mass, but `p` and `q` that agree to rounding error can still produce a rejection when `u` is close to 1.

The hidden tests accept any policy that never emits a token the target gives probability 0 and keeps the emitted tokens distributed as `p`.

## Answer

The reference walks the draft in order. An accepted position reads two numbers, `q[i][x]` and `p[i][x]`, and accepts when `p >= q` or `u * q < p`, which is `u < p / q` without a division. The first rejection builds the residual once, falls back to `p[i]` if the residual has no mass, and returns. If every draft token survives, the last distribution `p[k]` is passed to `sample` without being copied. That keeps a fully accepted round of 8 positions at 16 reads, against the 800,000 a verifier makes when it builds a residual for each position at a 50,000-token vocabulary.

Why the output follows the target. For one position the chance of emitting x by acceptance is q(x) min(1, p(x)/q(x)) = min(p(x), q(x)). The chance of a rejection is 1 minus the sum of min(p, q), which equals the sum of max(0, p - q), the residual's total mass. So the rejection path emits x with probability max(0, p(x) - q(x)), and the two paths add to p(x). Accepted tokens are independent across positions given the context, which is why the hidden tests also check the second position and the mean accepted length, alpha + alpha² + alpha³ for three positions where alpha is the overlap of the two distributions.

The two edge cases, and the decision in them. Rejecting a token with `q = 0` is the conservative choice: the residual then contains every token where `p > 0`, and the round still makes progress. Accepting it whenever `p > 0` is also defensible, because a draft that proposed a token it claims it could not have drawn is evidence the logged `q` is wrong, and rejecting would bias away from tokens the target likes. The cost of rejecting is a lower acceptance rate on exactly the inputs where logging is broken; the cost of accepting is a silent change to the output distribution. For the empty residual, the reference samples from `p[i]`, which is exact when `p` and `q` are equal; the alternative is to raise, which turns a numerical near-tie into a failed request. Neither choice is free: sampling from `p` hides the case where `q` is systematically wrong, so a production verifier would count these fallbacks and alert on them.

The constraint conflict sits outside this function. Exact verification keeps the target distribution, and that costs acceptance rate. Relaxed acceptance rules, such as the FLy verification vLLM lists as lossy, accept more tokens and stop being the target model. Whether that trade is acceptable depends on whether anyone downstream compares outputs against the target, for example an eval suite or a regulator-facing claim that the deployed model is the one evaluated.

The failure mode of this reference: it is correct per sequence and slow per batch. A real engine verifies every sequence in the batch in one tensor operation, where early exit is a mask rather than a `return`, and the fallback branch becomes a data-dependent path that a fused kernel has to support. A float32 sum over a large vocabulary can also leave a residual of tiny positive mass from rounding alone, so the fallback fires less often than it should; the hidden tests use an exact tie, and a production test would add near-ties.

## Follow-ups

- *Your fallback samples from `p` when the residual has no mass. Logs show it firing on 0.3% of rejections after a draft-model upgrade. Do you keep the fallback, or fail those requests, and what do you write down as the accepted risk?*
- *What would you need to see to switch from exact rejection to a relaxed acceptance rule that accepts more drafts?* An eval suite run against both, on the tasks the product serves, showing no regression beyond its noise, plus agreement from whoever owns the claim that the served model is the evaluated one.
- *Two engineers disagree: one wants verification on the GPU fused with the target's sampling, the other wants it on the CPU so it can be audited. How do you decide without deciding by rank?* Measure the round time both ways at production batch sizes and check the CPU path against the GPU path with the convergence test above on recorded distributions.
- *What changes to run this in a real engine?* Batched tensors with a per-sequence accepted length, KV cache entries for rejected positions rolled back or masked, positions for the next round starting after the accepted tokens plus the correction, EOS inside the accepted prefix ending the sequence there, and greedy decoding reduced to "accept while the draft token equals the target argmax".

## Common mistakes

- Comparing `u` against `p[i][x]` alone instead of the ratio, which over-accepts tokens the draft favours.
- Resampling from `p` after a rejection instead of the residual, which gives tokens the draft already proposed a second chance and skews the output toward them.
- Building the residual or a normalised copy for every position, which costs a pass over the vocabulary per position on rounds that accept everything.
- Dividing by `q[i][x]` without deciding what a zero means, and dividing by the residual's total without deciding what an empty residual means.
- Forgetting the bonus token from `p[k]`, which caps a round at `k` tokens and loses the cheapest token the target pass already paid for.
