  solution: |
    def verify(draft, q, p, u, sample):
        out = []
        for i, x in enumerate(draft):
            if q[i][x] > 0 and u[i] < min(1.0, p[i][x] / q[i][x]):
                out.append(x)
                continue
            residual = [max(0.0, pi - qi) for pi, qi in zip(p[i], q[i])]
            total = sum(residual)
            return out + [sample([r / total for r in residual])]
        return out + [sample(p[len(draft)])]

## Question

<Callout kind="interview" label="As reported by a candidate">
"Design normal and speculative decoding with correct proposal verification, rejection, sampling, EOS, positions and KV cache state, then build a fair speed benchmark."
</Callout>

The full prompt is a long exercise. This version isolates the part that decides whether the output is correct: the verification step. A draft model has proposed `k` tokens. For each position `i` you have the draft's distribution `q[i]` (the one `draft[i]` was sampled from) and the target model's distribution `p[i]`, all from one target forward pass, plus `p[k]` for the position after the draft.

Implement `verify(draft, q, p, u, sample)`:

- Go through the draft in order. Accept `draft[i]` if `u[i] < min(1, p[i][x] / q[i][x])`.
- At the first rejection, stop. Append one token sampled from the residual distribution `max(0, p[i] - q[i])`, normalised to sum to 1, and return.
- If every draft token is accepted, append one bonus token sampled from `p[k]`.
- Randomness comes in through `u` and `sample`, so the tests are deterministic.

The result is always the accepted prefix plus exactly one token from the target, so every call makes progress.

## Hints

<details class="hint"><summary>Hint 1</summary><p>The comparison is against p over q for the drafted token only, not against the whole distribution.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Rejection can only happen where p is below q for the drafted token, so the residual always has some mass.</p></details>
<details class="hint"><summary>Hint 3</summary><p>The bonus distribution is the last entry of <code>p</code>, which has one more entry than the draft.</p></details>

## Answer

The reference solution walks the draft, accepts while `u[i]` is below the ratio, and returns early on the first rejection with a sample from the normalised residual. If the loop finishes, it samples once more from `p[k]`.

Why the output follows the target distribution: for a single position, the probability of emitting token x is the chance the draft proposes x and it is accepted, q(x) min(1, p(x)/q(x)) = min(q(x), p(x)), plus the chance of a rejection times the residual's probability of x. The total rejection probability is 1 minus the sum of min(p, q), which equals the sum of max(0, p - q), so the second term is exactly max(0, p(x) - q(x)). The two terms add to p(x). The last test checks this empirically with 40,000 draws, and the lesson's snippet shows the same for a four-token vocabulary.

The bonus token matters for speed: when all `k` drafts are accepted the target pass already computed `p[k]`, so sampling from it gives one more token for free, which is why a round yields between 1 and `k + 1` tokens.

What the full exercise adds: after verification, the KV caches of both models must be rolled back to the accepted length (the rejected positions' entries are invalid), positions for the next round start after the accepted tokens plus the correction, and an EOS token anywhere in the accepted prefix ends generation there. A fair benchmark compares against plain decoding of the same target with the same sampling settings, warms up both, reports tokens per second and acceptance rate at several batch sizes, and checks that outputs match in distribution (greedy outputs should match exactly).

## Follow-ups

- *What is the acceptance rate for a given draft and target?* For one position it is the sum over tokens of min(p, q), the overlap of the two distributions.
- *How does greedy decoding simplify this?* p and q become one-hot; accept while the draft token equals the target's argmax.
- *Why does Medusa's typical acceptance not preserve the distribution?* It accepts tokens the target finds plausible enough, rather than using the exact rejection rule, trading fidelity for speed.
- *What happens to throughput at large batch?* Verification costs `k + 1` positions of compute per sequence; when the step is compute bound, rejected positions are wasted work.

## Common mistakes

- Comparing against `p[i][x]` alone instead of the ratio, which over-accepts tokens the draft favours.
- Resampling from `p` instead of the residual after a rejection, which double-counts tokens the draft already had a chance to propose.
- Continuing after the first rejection.
- Forgetting the bonus token, or forgetting to return a token at all on rejection.
