## Question

<Callout kind="interview" label="As asked">
"What are the cost trade-offs between self-hosted and API-based AI inference?"
</Callout>

Put a number on it first. A feature sends requests of 2,000 input tokens and 300 output tokens, with no prompt caching.

- **API option:** gpt-6.1-sol at list price, $2.00 per million input tokens and $10.00 per million output tokens (checked 28 October 2026).
- **Self-host option:** an open-weight model that passed your evals for this feature, on 2 GPUs reserved around the clock. Your cloud quote is **$4.00 per GPU-hour**. This is an illustrative input for the exercise, not a sourced market price; use your own quote in real life. A load test shows the pair sustains 5 requests per second within your latency objective. Use 730 hours per month.

At what monthly request volume does the self-hosted option cost the same as the API? Answer in millions of requests per month, counting only these two costs.

## Hints

<details class="hint"><summary>Hint 1</summary><p>The API cost is per request; the self-host cost is per month regardless of traffic.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Price per request: input tokens times input price plus output tokens times output price, each per million.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Then check the answer against the capacity of the two GPUs.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>API: 2,000 x $2 / 1M + 300 x $10 / 1M = $0.004 + $0.003 = $0.007 per request. Self-host: 2 GPUs x $4 x 730 hours = $5,840 per month, whatever the traffic. Break-even: $5,840 / $0.007 = about 834,000 requests a month, 0.83 million. Below that the API is cheaper; above it the GPUs are, up to their capacity, before counting people, on-call and the quality gap.</p>
</Fragment>
<Fragment slot="long">
<p>Capacity check: 5 requests per second x 3,600 x 730 = 13.1 million requests a month at full load, so break-even arrives at about 6% of capacity. That looks like an easy win for self-hosting, and it is where the real discussion starts.</p>
<p>Peak versus average: you size GPUs for peak. If peak is several times the average, the monthly volume you can actually serve on two GPUs is much lower than 13.1 million, and you need more GPUs (raising the fixed cost) or overflow to the API.</p>
<p>The API side gets cheaper than list: if 1,500 of the 2,000 input tokens were a cached prefix at $0.10 per million, the request costs $0.00415 (ignoring the occasional cache write), moving break-even to about 1.4 million. Offline work on the Batch tier at half price moves it to about 1.67 million.</p>
<p>Costs not in the model: engineers to run the serving stack, on-call, upgrades, evals for every model change, redundancy (a second region or at least N+1 GPUs), and the quality gap if the open model is weaker on hard cases. Reasons that are not about cost: data residency, latency control, fine-tuned models, and independence from a provider's rate limits.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What if traffic is spiky?</em> Hybrid: self-host the steady base load, overflow peaks to the API through the gateway.</li>
<li><em>What input would you most want to verify?</em> The measured throughput at the latency objective with production-like prompt lengths; it decides how many GPUs the fixed cost really needs.</li>
<li><em>How does a newer tokenizer change the comparison?</em> Compare cost per request on your data, not price per token, since vendors' tokenizers produce different counts for the same text.</li>
</ul>
</Fragment>
</Depth>

Worked calculation: per-request API cost = (2,000 x 2.00 + 300 x 10.00) / 1,000,000 = $0.0070. Monthly fixed cost = 2 x 4.00 x 730 = $5,840. Break-even = 5,840 / 0.0070 = 834,286 requests, 0.83 million. The accepted band of 0.75 to 0.92 million allows for rounding hours per month (720 to 744) and the per-request cost.

## Follow-ups

- *When would you self-host even at a loss?* When data cannot leave your environment, or when you need a fine-tuned model the API cannot serve.
- *How would you present this to finance?* As cost per request or per resolved task at forecast volume, with the break-even line and the assumptions listed.

## Common mistakes

- Comparing the API price per token with the GPU price per hour without converting either to cost per request.
- Using capacity at 100% utilisation as the volume you will actually serve.
- Ignoring the API's own discounts (caching, batch) and the self-host's people costs.
- Treating an illustrative GPU price as a market fact.
