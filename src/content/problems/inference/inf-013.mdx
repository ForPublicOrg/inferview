## Question

<Callout kind="interview" label="Estimate, 20 minutes">
"Finance wants to know at what volume we should stop paying per token and run this ourselves. Give me a number, and tell me when it stops being true."
</Callout>

An interactive feature runs on Claude Sonnet 5.5. Each request sends 2,000 input tokens and gets 300 output tokens; nothing is cached today.

Published inputs, checked 28 October 2026:

- Claude Sonnet 5.5: $2 per million input tokens, $10 per million output tokens.
- Lambda on-demand H100 SXM in an 8-GPU instance: $3.99 per GPU-hour. The page carries no effective date.

Scenario inputs, specific to this problem:

- An open-weight model passed the feature's eval set. Served with vLLM on one 8x H100 node, it sustains 40 requests per second at the feature's latency objective in a load test with production prompt lengths.
- The feature's availability objective rules out a single node: losing one node must not take the feature down. You run two nodes around the clock, 730 hours a month.
- A fully loaded engineer costs $240,000 a year. Running the serving stack (upgrades, on-call, capacity, evals for each model change) takes some share of an engineer; you choose the share and defend it.

At what monthly request volume do the two options cost the same? Answer in millions of requests per month.

## Answer

<Depth>
<Fragment slot="short">
<p>API cost per request: 2,000 × $2 / 1M + 300 × $10 / 1M = $0.004 + $0.003 = $0.007. Fixed self-host cost: 2 nodes × 8 GPUs × $3.99 × 730 h = $46,603 a month, plus people. At half an engineer ($10,000 a month) the break-even is $56,603 / $0.007 ≈ 8.1 million requests a month; a quarter to a whole engineer gives 7.4 to 9.5 million. The dominant term is GPU rent, not people. The assumption that flips the answer is the API price the self-hosted model is compared with: if Haiku 5.5 passes the same evals, the API costs $0.00035 a request and the break-even moves to about 162 million, past what two nodes can serve.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The fixed side.</strong> 2 × 8 × 3.99 × 730 = $46,603.20 a month whatever the traffic. People: $240,000 / 12 = $20,000 a month per engineer. A quarter of an engineer ($5,000) is the floor for two nodes with on-call; a whole engineer ($20,000) is reasonable if this is the organisation's first self-hosted model and there is no serving platform to share. Zero is not a reasonable choice: a model change without someone to run its evals and roll it out is a model that is never upgraded.</p>
<p><strong>The break-even.</strong> ($46,603 + people) / $0.007: 7.37 million at a quarter, 8.09 million at a half, 9.51 million at a whole engineer. GPU rent is 70% to 90% of the fixed cost across those choices, so it is the term to get right; the people share moves the answer by about 30% end to end.</p>
<p><strong>Capacity check.</strong> One node at 40 requests per second for 730 hours is 40 × 3,600 × 730 = 105 million requests a month at full load. You size for peak, and with two nodes for redundancy, one node has to carry peak alone. At a peak-to-average ratio of 3, that is 105 / 3 ≈ 35 million a month. The break-even sits at about a quarter of what the pair can serve, so capacity is not the constraint here.</p>
<p><strong>When it flips.</strong> Three assumptions move the line, and the first is the one that decides it.</p>
<ul>
<li><em>The hosted model you compare against.</em> The open-weight model was compared with Sonnet 5.5 because that is what runs today. If Claude Haiku 5.5 passes the same eval set, the API request costs 2,000 × $0.10 / 1M + 300 × $0.50 / 1M = $0.00035, and the break-even at half an engineer is $56,603 / $0.00035 ≈ 162 million a month, well past the 35 million the pair can serve. The comparison is with the cheapest hosted model that passes your evals, not with the model you started on.</li>
<li><em>Caching on the API side.</em> If the first 1,500 tokens are a fixed instruction block and caching hits, the request costs 500 × $2 / 1M + 1,500 × $0.10 / 1M + $0.003 = $0.00415, ignoring the occasional cache write, and the break-even moves to about 13.6 million.</li>
<li><em>Time.</em> Epoch AI measured the price of reaching a fixed capability falling between 9x and 900x a year, depending on the threshold. That is a price for the cheapest model to reach a benchmark score, not a cut to Sonnet 5.5's list price, but it is the right prior for how fast a cheaper hosted model passes your eval. At the slow end, a 9x cheaper qualifying API puts the break-even near 73 million, also past the pair's capacity.</li>
</ul>
<p>So the number for finance is "about 8 million requests a month against today's model, recomputed whenever a cheaper hosted model passes the eval set or a price changes, and at least each quarter".</p>
<p><strong>Where this estimate fails.</strong> The load test's 40 requests per second is the number everything rests on, and it was measured with today's prompt lengths. If the feature's prompts double, throughput per node falls, the pair's capacity falls with it, and at some point a third node is needed, which moves the fixed cost by half again. The estimate also counts no quality gap: if the open-weight model fails cases that Sonnet 5.5 passes and those cases cost support time, that cost belongs on the self-host side.</p>
</Fragment>

<ul>
<li><em>Pushback: the platform lead says your people share is too low because the first self-hosted model always takes a full engineer for six months. Does the decision change, and at what volume would it?</em></li>
<li><em>Reversal: you self-host at 20 million a month. What would you need to see to move back to the API?</em> A hosted model that passes the eval set at a per-request cost that puts the break-even above the current volume, measured on your own prompts, not on list price per token alone.</li>
<li><em>Traffic is spiky. Is there a third option?</em> Self-host the steady base load and send the peak to the API through the gateway, which needs the gateway to route by capacity and the two models to pass the same evals.</li>
</ul>

Worked calculation: per request (2,000 × 2.00 + 300 × 10.00) / 1,000,000 = $0.0070. Fixed 2 × 8 × 3.99 × 730 = $46,603.20, plus $5,000 to $20,000 of people. Break-even 51,603.20 / 0.007 = 7.37 million to 66,603.20 / 0.007 = 9.51 million. The accepted band, 7.3 to 9.6 million requests a month, covers a quarter to a whole engineer. Answers below it usually leave people out (6.66 million) or run one node against an objective that rules it out; answers well above it usually add a third node that the capacity check shows is not needed (3 × $23,301.60 plus half an engineer gives about 11.4 million).

## Follow-ups

- *Your volume is 12 million a month and growing 10% a month. When do you start the migration, given that it takes a quarter to build and staff?*
- *Which input would you most want to measure again before signing a reserved GPU contract?* Throughput at the latency objective with next quarter's prompt lengths, since it decides how many nodes the fixed cost has to cover.
- *A new tokenizer on the hosted side produces more tokens for the same text. What changes in the comparison?* Compare cost per request measured on your traffic, not price per million tokens, since the token count itself moved.

## Common mistakes

- Comparing price per million tokens with price per GPU-hour without converting both to cost per request.
- Treating the load test's full-load throughput as the volume the fleet will serve, with no peak and no redundancy.
- Leaving people and on-call out of the fixed cost.
- Comparing the open-weight model with the hosted model in use today rather than the cheapest hosted model that passes the same evals.
- Quoting a GPU price without its source and the date it was checked.
