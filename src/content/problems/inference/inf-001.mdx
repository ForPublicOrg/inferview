## Question

<Callout kind="interview" label="As asked">
"Why is prefill compute-bound and decode memory-bandwidth-bound? What does that mean for how you serve a model?"
</Callout>

Answer as you would in the room: the mechanism, a number that shows it, and one consequence for serving. Assume a dense 70B-class model on one H100 SXM.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Count how many tokens share each weight that is read from memory in each phase.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Divide the GPU's dense FLOPs by its memory bandwidth to get the ridge point, then compare.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Which phase gets cheaper per token when you add more requests to the batch?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Prefill pushes every prompt token through each weight in one pass, so each byte read from memory feeds hundreds or thousands of FLOPs and the arithmetic units are the limit. Decode produces one token per step per sequence, but still has to read every weight each step, so each byte feeds only a couple of FLOPs and memory bandwidth is the limit. The consequence: batch decode to share the weight read across many sequences, and keep long prefills from stalling decodes.</p>
</Fragment>
<Fragment slot="long">
<p>Arithmetic intensity is FLOPs per byte moved. A forward pass costs about 2 FLOPs per parameter per token. In BF16 a weight is 2 bytes, so a pass over N tokens has an intensity of about N FLOPs per byte for the weight matmuls.</p>
<p>The H100 SXM's ridge point is dense BF16 FLOPs over bandwidth: 989.5 TFLOPS / 3.35 TB/s, about 295 FLOPs per byte. A 2,000-token prefill sits near 2,000, far above the ridge: compute bound. A decode step at batch 1 sits near 1, about 300 times below the ridge: bandwidth bound. Decode at batch B sits near B for the weights, but each sequence's KV cache is read for that sequence alone, so the attention part never gains from batching.</p>
<p>In time: 70 GB of FP8 weights read at 3.35 TB/s floors a decode step at 20.9 ms, while a 2,000-token prefill needs 2.8e17 FLOPs, at least 141 ms at 1,979 dense FP8 TFLOPS. Seven decode steps' worth of time processes two thousand prompt tokens.</p>
<p>Serving consequences: continuous batching to raise decode intensity; quantization helps decode most because it cuts bytes read; chunked prefill or disaggregation so compute-heavy prefills do not stall bandwidth-bound decodes; and memory bandwidth, not TFLOPS, as the first spec to compare for decode-heavy traffic.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>At what batch size does decode become compute bound?</em> From the weight term alone, around the ridge point, a few hundred in BF16 on an H100; the KV term pushes that further out, and memory usually runs out first.</li>
<li><em>Is a very short prompt's prefill compute bound?</em> No. A 20-token prompt has intensity near 20, below the ridge. The rule is about tokens per byte, not about the phase name.</li>
<li><em>What metric shows decode is bandwidth bound in production?</em> Model bandwidth utilisation: (weight bytes + KV bytes) / TPOT, divided by peak bandwidth.</li>
</ul>
</Fragment>
</Depth>

The worked numbers above use NVIDIA's dense figures, half of the sparse numbers printed on the product page, and assume perfect kernels, so they are bounds rather than predictions. The point an interviewer listens for is the ratio of tokens processed per byte of weights read: prefill has many, decode has one per sequence. Everything else follows from it, including why a GPU in decode can show low compute utilisation while users wait, and why Databricks saw throughput rise about 14 times when batch 64 raised latency only about 4 times.

## Follow-ups

- *Does a mixture-of-experts model change the answer?* At batch 1 decode reads only the active experts, so fewer bytes per step; at larger batches tokens route to different experts and more of the weights are read.
- *Why does FlashAttention not fix decode?* It reduces memory traffic for attention activations; decode is limited by reading weights and the KV cache, which it still has to read.
- *Which hardware number would you compare first for a chat product?* Memory bandwidth and capacity, then FLOPs.

## Common mistakes

- Saying decode is slow "because attention is quadratic". With a KV cache, per-step attention work grows linearly with context, and at short context the weight read dominates.
- Quoting NVIDIA's sparse TFLOPS as dense, which doubles the ridge point.
- Forgetting the KV cache term, which grows with batch and context and never benefits from sharing.
- Treating "compute bound" as a property of the phase rather than of tokens per byte.
