## Question

<Callout kind="interview" label="As asked">
"Why is prefill compute-bound and decode memory-bandwidth-bound? What does that mean for how you serve a model?"
</Callout>

Then the interviewer makes it a decision. Llama 3 70B runs with FP8 weights (about 70 GB) on two H100 SXM GPUs with tensor parallelism, BF16 KV cache at 327,680 bytes per token. The traffic, a scenario: a retrieval assistant whose prompts average 6,000 tokens, of which 1,500 are a system prompt shared by every request, and whose answers average 300 tokens. At peak, p95 time to first token is 1.5 s against a 1 s target, while inter-token latency is inside its 40 ms target. There is budget for one of these this quarter:

1. Move the same deployment to two H200s.
2. Raise the engine's maximum running batch from 32 to 64.
3. Turn on prefix caching for the shared system prompt.
4. Turn on chunked prefill with a budget of 2,048 prompt tokens per engine step.

Explain the mechanism with arithmetic intensity, give the prompt length at which a prefill on this hardware stops being bandwidth-bound, and say which phase each change speeds up and by roughly how much, before anyone benchmarks it. Then pick one.

Published inputs: H100 SXM 80 GB, 3.35 TB/s, 1,979 dense FP8 TFLOPS (NVIDIA prints 3,958 with sparsity). H200 SXM 141 GB, 4.8 TB/s, the same tensor TFLOPS.

## Answer

<Depth>
<Fragment slot="short">
<p>A step reads every weight once and pushes some number of tokens through it. With FP8 weights each byte read feeds 2 FLOPs per token, so a step over T tokens runs at about 2T FLOPs per byte. The H100's FP8 ridge is 1,979e12 / 3.35e12 = 591 FLOPs per byte, so a step turns compute-bound near T = 300 tokens. A 6,000-token prefill sits 20 times above the ridge; a decode step at batch 32 sits near 64, nine times below, and its KV reads are per sequence and never shared. Here the prefill floor is about 0.2 s, so a 1.5 s p95 TTFT is mostly waiting. Prefix caching is the only option that removes prefill work (a quarter of it). The H200 speeds decode up to 1.43 times and leaves prefill execution unchanged. Batch 64 does not fit in the KV memory. Chunked prefill protects ITL and does not cut TTFT. I would fund prefix caching if the TTFT split shows prefill execution and queueing behind prefills, and the H200 only if it shows waiting for KV memory.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The threshold, derived.</strong> About 2 FLOPs per parameter per token (Kaplan's 2N). FP8 stores a parameter in one byte, so T tokens per step give 2T FLOPs per byte of weights. Ridge 591 means T above about 295 is compute-bound. In BF16 the bytes double and the ridge halves to about 295 FLOPs per byte, with intensity T, so the threshold is the same 300 tokens: on an H100 the precision moves both sides. On an H200 the BF16 ridge is 989.5e12 / 4.8e12 = 206, so the threshold falls to about 200 tokens. The chosen number is a band: anything from 200 to 600 tokens is a reasonable estimate depending on precision and GPU; quoting the sparse TFLOPS (which doubles the ridge) or thinking in model FLOPs without the bytes is not.</p>
<p><strong>The phases, in time.</strong> Prefill: 6,000 x 2 x 70e9 = 8.4e14 FLOPs over two GPUs at 3,958e12 dense FLOPs per second, a floor of 0.21 s. Attention adds 2 x n_layer x n_ctx x d_attn per token, 2 x 80 x 6,000 x 8,192 = 7.9e9 against 1.4e11 for the weights, so 6% at this length. Decode at batch 32 with prompts and answers of 6,300 tokens: each GPU reads 35 GB of weights plus half of 32 x 6,300 x 327,680 = 66 GB of KV, 68 GB per step, at least 20.3 ms. That is why ITL meets 40 ms while kernels reach 50 to 60% of peak bandwidth.</p>
<p><strong>The four changes.</strong></p>
<ul>
<li><em>Two H200s.</em> Decode step up to 4.8 / 3.35 = 1.43 times faster, 20.3 ms to 14.2 ms. Prefill execution does not change, since the tensor FLOPs are the same. TTFT improves only through what the extra 61 GB per GPU does to admission.</li>
<li><em>Batch 64.</em> KV memory left after weights and about 5 GB of runtime reserve per GPU is 2 x 40 = 80 GB, 244,000 tokens. Batch 32 at 6,300 tokens needs 202,000; batch 64 needs 403,000. The engine will admit about 38 sequences and preempt or queue the rest, so the setting does almost nothing on H100s. On H200s it fits (about 616,000 tokens of room).</li>
<li><em>Prefix caching.</em> 1,500 of 6,000 prompt tokens no longer pass through the weights: prefill FLOPs and time fall by a quarter, 0.21 s to 0.16 s, and the freed compute shortens the queue of prefills at peak. Decode is unchanged.</li>
<li><em>Chunked prefill.</em> No FLOPs saved. A step that would have carried a 6,000-token prefill now carries 2,048 prompt tokens next to the running decodes, so decodes stall less and ITL p99 improves. A long prompt now spans three steps, so its own TTFT can rise.</li>
</ul>
<p><strong>The decision and the conflict.</strong> The 0.21 s floor against a 1.5 s p95 says most of TTFT is waiting, and the remedy depends on which queue. Waiting behind other prefills: prefix caching removes a quarter of the compute that queue is made of, for no hardware. Waiting for KV memory to admit a request: the H200 move, which buys capacity and decode speed at the price of new hardware. The conflict is TTFT against ITL and cost: chunked prefill would spend ITL headroom the product currently has, and the H200 spends budget on decode speed nobody asked for.</p>
<p><strong>How the recommendation fails.</strong> Prefix caching only pays when the cached blocks survive. At peak, KV memory is nearly full, and an engine that evicts cached prefix blocks under pressure loses the hit rate exactly when TTFT is worst. If the staging replay shows a peak hit rate well below 100% for a prompt every request shares, the saving shrinks with it, and the real fix is KV capacity.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your TTFT split shows 80% waiting for KV memory. Do you still fund prefix caching?</em> Not first. It frees some blocks (one shared copy of the prefix instead of one per request), but admission is memory-bound; FP8 KV cache or the H200 addresses that.</li>
<li><em>Is a 40-token prompt's prefill compute-bound?</em> No. At 2 x 40 = 80 FLOPs per byte it is below the ridge, so short prompts are cheap and bandwidth-bound like decode.</li>
<li><em>How would you show decode is bandwidth-bound in production?</em> Model bandwidth utilisation: (weight bytes + KV bytes read per step) / measured ITL, divided by peak bandwidth.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *A mixture-of-experts model replaces the dense one. Does the 300-token threshold hold?* No. At small batches each token reads only its active experts, and at large batches tokens route to different experts, so the bytes read per step grow with batch and the intensity per expert is lower than the batch size suggests.
- *Why does FlashAttention not speed up decode the way it speeds up prefill?* It removes reads and writes of the attention matrix; a decode step still has to read every weight and the whole KV cache of every sequence.
- *What would make you pick chunked prefill despite the TTFT cost?* An ITL p99 target that long prompts break; the trade is then explicit in the SLO.

## Common mistakes

- Saying decode is slow because attention is quadratic. With a KV cache the per-step attention work is linear in context, and at 6,000 tokens it is 6% of the FLOPs.
- Using NVIDIA's sparse TFLOPS as dense, which doubles the ridge and the threshold.
- Raising the batch limit without checking that the KV cache for that batch fits.
- Treating compute-bound as a property of the phase name rather than of tokens per byte: short prefills are bandwidth-bound.
- Reading a 1.5 s TTFT as slow prefill when the roofline floor is 0.2 s.
