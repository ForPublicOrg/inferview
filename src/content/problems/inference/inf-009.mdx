  solution: |
    import time

    class TokenBudget:
        def __init__(self, tokens_per_minute, burst=None, clock=time.monotonic):
            self.rate = tokens_per_minute / 60.0
            self.capacity = burst if burst is not None else tokens_per_minute
            self.level = float(self.capacity)
            self.clock = clock
            self.last = clock()

        def _refill(self):
            now = self.clock()
            self.level = min(self.capacity, self.level + (now - self.last) * self.rate)
            self.last = now

        def available(self):
            self._refill()
            return self.level

        def try_reserve(self, prompt_tokens, max_tokens):
            self._refill()
            need = prompt_tokens + max_tokens
            if need > self.level:
                return None
            self.level -= need
            return need

        def settle(self, reserved, prompt_tokens, output_tokens):
            self._refill()
            # Refund unused output; if actual use beat the reservation, the level goes negative and pays it back later.
            self.level = min(self.capacity, self.level + reserved - (prompt_tokens + output_tokens))

## Question

<Callout kind="interview" label="As listed">
"Implement a token-bucket rate limiter for an LLM API where cost scales with tokens, then make it distributed."
</Callout>

A request-count limit is the wrong unit for a model API: one request can use 50 tokens and the next 50,000. Implement a per-tenant limiter charged in tokens.

- The bucket refills continuously at `tokens_per_minute / 60` tokens per second, up to `burst` (default: one minute's worth). It starts full.
- The output length is unknown when the request arrives, so `try_reserve(prompt_tokens, max_tokens)` reserves the worst case. If the bucket does not hold that much, return `None` and take nothing; the gateway answers 429.
- After the call, `settle(reserved, prompt_tokens, output_tokens)` refunds what was not used. Token counts reported by the provider can exceed your estimate (your prompt count may have been approximate), in which case settle charges the difference even if the level goes below zero, and the tenant waits for the refill.
- The clock is injected so tests can control time.

Then be ready to talk through the distributed version.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Refill lazily: on every call, add elapsed seconds times the rate, cap at the burst, and remember the time.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Settle is one formula: level plus reserved minus actual, capped at the burst.</p></details>
<details class="hint"><summary>Hint 3</summary><p>A request larger than the burst can never be admitted, however long it waits. That is a correct outcome, not a bug to work around.</p></details>

## Answer

The reference solution stores the rate per second, the capacity, the current level and the time of the last refill. `_refill` runs at the start of every public method, so the level is always current without a background thread. `try_reserve` compares the worst case with the level and either subtracts it or returns `None` without side effects, so a rejected request costs the tenant nothing. `settle` adds back the reservation and subtracts the real usage in one step, capped at the capacity; when usage beat the reservation the result is negative, and the next reservations fail until the refill pays the debt back, which is what the last tests check.

Reserving the worst case is conservative. If tenants set `max_tokens` far above what they use, the limiter admits fewer concurrent requests than the true usage would allow. Two common fixes: cap `max_tokens` at the gateway, or reserve an estimate (for example the tenant's recent p95 output length) and accept occasional overshoot that settle charges back.

**Distributed.** With several gateway replicas, the bucket has to live in shared state. The usual design keeps level and last-refill time in Redis and runs refill-and-reserve as one atomic operation (a Lua script or a transaction), with settle as another. Each call then costs a round trip to Redis. The alternative is to split the rate: each of N replicas gets 1/N of it locally, with no coordination, at the price of unfairness when load is uneven across replicas. Either way, decide what happens when the shared store is down. LiteLLM's docs, for example, describe the global budget failing open without its database and offer fail-closed options; for a spend limit, failing open is the risky choice.

## Follow-ups

- *What should the 429 carry?* A Retry-After computed from the shortfall divided by the refill rate.
- *How do you handle streaming responses?* Count output tokens as they stream and stop at the reservation, or settle at the end and accept a bounded overshoot.
- *How do reservations leak, and how do you stop it?* A gateway crash between reserve and settle; store reservations with an expiry so they return to the bucket.
- *Tokens per minute or dollars per month?* Both: the bucket protects capacity in the short term, and a dollar budget per period protects spend.

## Common mistakes

- Charging requests instead of tokens.
- Charging only after the call, which lets one burst of large requests overshoot the limit by a wide margin.
- Letting a rejected `try_reserve` consume tokens.
- Refilling past the burst size after a long idle period.
- Clamping the level at zero in settle, which forgives usage the tenant really consumed.
