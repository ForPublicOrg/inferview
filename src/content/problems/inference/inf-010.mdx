## Question

<Callout kind="interview" label="As asked">
"Design an AI gateway/proxy for managing LLM access across an organization."
</Callout>

Around 40 internal teams call models from three hosted providers and one self-hosted cluster. Today each team has its own provider keys. Security wants keys out of application code and a record of what data goes where. Finance wants spend by team and by customer. Platform wants one place to fail over when a provider has an outage. Design the gateway: the request path, the data it stores, routing and failure handling, and how it stays out of the way of latency.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Walk one request through the gateway in order and list what each stage needs to know.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Limits and budgets must be in tokens or dollars, and the output size is unknown when the request arrives.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Decide what the gateway does when its own dependencies (the budget store, the log pipeline) are down.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A stateless proxy fleet with one OpenAI-compatible endpoint. Per request: authenticate the calling service and attach team, feature and customer tags; check token rate limits and dollar budgets by reserving the worst case; apply data policy (which providers this data may go to, redaction); route to a model and provider with health-aware fallbacks; stream the response; then settle usage and write one usage record with token counts by type and the dated price. Provider keys live only in the gateway's secret store. Budgets and limits live in a fast shared store; usage records go to an append-only pipeline for cost reports.</p>
</Fragment>
<Fragment slot="long">
<p>Request path. Caller identity comes from service credentials (mTLS or workload identity), not shared API keys, and every request must carry a feature tag and, for customer-facing calls, a customer id. Policy decides allowed models and providers per team and per data classification; for example, regulated data may go only to the self-hosted cluster. Optional redaction runs here.</p>
<p>Limits. A token bucket per team and per customer, charged in tokens, reserving prompt tokens plus max_tokens before the call and settling with the provider's reported usage after it. Dollar budgets per period sit on top, with alerts at fixed fractions and an agreed behaviour at the cap: block, downgrade, or allow and report. Keep counters in Redis with atomic operations. Choose the failure mode explicitly: LiteLLM's docs, for example, note that its global budget fails open without its database; for spend limits on customer traffic, fail closed or at least alert.</p>
<p>Routing. Logical model names map to deployments. Route by policy first, then health and cost: per-deployment error rates with a cooldown after repeated failures, and fallbacks to an equivalent model on another provider. A fallback to a different model changes outputs, so the mapping is owned by the team and covered by evals. Offline traffic is routed to batch APIs at half price, since nobody is waiting on it.</p>
<p>Caching. The gateway cannot make provider prompt caching hit by itself, but it can measure it (cached input tokens per request) and enforce prompt layout rules: stable content first, nothing volatile at the top. An exact-match response cache is safe for deterministic calls; semantic caching needs per-use-case approval because a near match can be a wrong answer.</p>
<p>Observability and cost. One usage record per call: caller, tags, model, provider, input, cached input and output tokens, latency (TTFT and total), status, and cost from a dated price table. Cost per team or per customer is then a query. Log prompts and responses only where policy allows, with retention limits.</p>
<p>Latency and availability. The gateway adds a network hop, so keep it stateless, deploy it close to callers, stream responses without buffering, and keep the policy and price tables in memory. It is a critical dependency: run it replicated, with a documented degraded mode.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A provider is down for an hour. What happens?</em> Health checks put its deployments in cooldown, traffic moves to the fallback mapping, teams without an approved fallback get clear errors, and the incident record shows which teams were degraded.</li>
<li><em>How do you stop the gateway becoming a bottleneck for new models?</em> Self-service configuration with review: a team adds a model mapping and its eval results, the platform team approves.</li>
<li><em>Build or buy?</em> Open-source proxies cover routing, budgets and logging; the organisation-specific parts are identity, data policy and the cost pipeline into finance's systems.</li>
</ul>
</Fragment>
</Depth>

What separates strong answers: tokens as the unit of every limit, reserve-then-settle because output length is unknown, explicit failure modes for the budget store, data policy enforced per request rather than by convention, and fallbacks treated as model changes that need evaluation. Weak answers describe an HTTP reverse proxy with request-count rate limits and a cache.

## Follow-ups

- *How do you attribute spend inside one team's service to its customers?* Require a customer id on customer-facing calls and reject untagged calls in production.
- *How do you migrate 40 teams?* Start in pass-through mode with logging only, then enforce tags, then limits, then remove direct provider keys.
- *What do you alert on?* Budget burn rate, cache hit rate dropping, error rate per provider, TTFT p99, and fallback activation.

## Common mistakes

- Rate limiting by request count.
- Charging budgets only after the call.
- Silent fallbacks to a different model with no evaluation or record.
- Logging full prompts everywhere without a data policy.
- Making the gateway stateful, so it cannot scale horizontally.
