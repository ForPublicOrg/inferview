## Question

<Callout kind="interview" label="Design round, 45 minutes">
"Product, security and finance each want something from a model gateway, and they want different things. Design it, tell me who does not get what they asked for, and write down what you would send them."
</Callout>

What you learn by asking (scenario):

- 40 product teams call three hosted providers and one self-hosted vLLM cluster. Each team holds its own provider keys and calls the providers' SDKs directly, using provider-native features: prompt-cache breakpoints, the Responses API, batch jobs, structured outputs.
- **Security**: an audit finding requires provider keys out of application code within 90 days. Security also wants every prompt and response stored for a year for investigations, and a record of which data classes went to which provider.
- **Finance**: monthly spend per team and per customer, and a hard cap per team that blocks calls at the cap.
- **Product teams**: no client rewrite this quarter, no latency their users can see, and new provider features on the day they ship. The tightest team's objective is 800 ms p99 time to first token.
- **Platform**: four engineers own the gateway. Several customer contracts forbid retaining customer content beyond 30 days.

Cover the request path, what the gateway owns and what stays in the product, budgets and their failure modes, logging, and the migration. Choose the gateway's added-latency budget and the prompt-log policy, and defend both. State what each owner gives up, and write the decision memo you would send.

## Answer

<Depth>
<Fragment slot="short">
<p>A stateless pass-through gateway in front of each provider's own API: teams change a base URL and drop their keys, and the gateway authenticates the calling service, injects the provider key, applies data-class policy, meters tokens from the provider's usage fields at a dated price, and streams the response through untouched. No translation layer in v1, so no client rewrite and no feature lag, at the cost of no cross-provider failover. Budgets alert at fixed fractions and at the cap stop only what the team marked as stoppable; customer-facing calls get a soft cap and a page to the owner. Content logging is off by default, metadata always, content for 30 days only for data classes and teams that opt in. Security gets keys out in 90 days and a provider-by-data-class record, not a year of prompts; finance gets attribution, not universal hard caps; product gets no rewrite, but loses direct keys.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Pass-through or a unified API.</strong> This is the main decision, and both answers are defensible.</p>
<ul>
<li><em>Pass-through.</em> The gateway exposes each provider's native paths. Teams change a base URL and remove keys; the gateway reads the usage block on every response for metering. Nothing about request bodies changes, so cache breakpoints, the Responses API and batch jobs keep working, and a provider feature works the day it ships. The cost: no cross-provider failover or routing from the gateway, because it does not translate; failover stays each team's job.</li>
<li><em>A unified API.</em> One OpenAI-compatible endpoint with translation to every provider, which is what makes gateway-owned failover and routing possible. The cost: every team rewrites its client, which this quarter rules out, and every provider feature waits for the translation. Translation also changes behaviour silently: OpenRouter's documentation says that unless a request requires every parameter, a provider may receive it and ignore the parameters it does not support. A structured-output schema dropped on a failover is an outage that looks like success.</li>
</ul>
<p>The constraint conflict is the 90-day audit deadline against product's no-rewrite condition, and only pass-through meets both. A unified endpoint can come later, for new teams and for the teams that want failover.</p>
<p><strong>What the gateway owns.</strong> Caller identity from workload credentials, never a shared key. Provider keys. The data-class policy: each calling service declares the classes it sends, and the gateway refuses a class on a provider not approved for it, so the self-hosted cluster is the only route for regulated data. Metering and attribution: every request carries team, feature and, on customer-facing calls, a customer id, rejected if missing once enforcement starts. Token rate limits per team. The usage record: caller, tags, provider, model, input, cache-write, cache-read and output tokens, time to first token, status, price-table version and cost. <strong>What stays in the product:</strong> prompts, model choice, failover between providers, evals, and the decision about what a user sees when a call is refused.</p>
<p><strong>Budgets.</strong> A hard block on a customer-facing feature turns a finance control into an outage on the last day of the month. Each team marks its traffic: batch and internal tools are stoppable at the cap; customer-facing calls keep running past it, page the owning lead at 80% and 100%, and land on finance's monthly report as overage. The budget store has a failure mode to choose: LiteLLM's budgets, for example, are enforced against spend read from its database and do not cap anything without it, with a fail-closed option that returns 503. For stoppable traffic I fail closed; for customer-facing traffic I fail open with an alert, since the provider's own spend cap remains behind the gateway. That cap answers 429 with no retry-after, so the gateway translates it into an error the caller will not retry.</p>
<p><strong>Logging.</strong> Security asked for every prompt for a year; contracts forbid content beyond 30 days for some customers. Metadata (the usage record plus data classes and policy decisions) is kept for every call for a year, which answers "which data went to which provider". Content is off by default, on for 30 days for teams that opt in and for data classes security names, and stored in the customer's region where a contract requires it. The number I would defend is 30 days, the strictest contract; a year breaks contracts, and zero leaves security with nothing to investigate prompt-injection reports with.</p>
<p><strong>Latency.</strong> The gateway adds one hop in the request path and nothing in the streamed path: no buffering, policy and price tables in memory, metering after the response. I would set the added-latency budget at 5% of the tightest objective, 0.05 × 800 ms = 40 ms at p99, measured from the caller's side. A budget near zero cannot be met with any hop; a budget of 200 ms would be a quarter of the tightest team's objective.</p>
<p><strong>The decision memo, as sent.</strong></p>
<ul>
<li>Decided: pass-through gateway, live for all teams within 90 days; keys removed from application code by day 90; metadata for every call kept a year; content off by default, 30 days where enabled.</li>
<li>Security gives up a year of content; gets keys out, a provider-by-data-class record, and content for named classes. Finance gives up universal hard caps; gets attribution by team, feature and customer, and caps on stoppable traffic. Product gives up direct provider keys; gets no rewrite and no feature lag.</li>
<li>Rollout: weeks 1 to 4 in shadow (teams call through the gateway with their own keys, metering only); weeks 5 to 8 gateway keys and tag enforcement, team by team; weeks 9 to 12 provider keys revoked.</li>
<li>Rollback per team, to direct keys held in escrow for 30 days, if: added p99 latency exceeds 40 ms for a day; any request is refused for a policy error the team did not cause; metered cost differs from the provider's invoice by more than an agreed tolerance for the month.</li>
</ul>
<p><strong>Where this design fails.</strong> Metering from response usage fields misses what never returns a usage block. A stream the client abandons halfway may never deliver its final usage chunk; the OpenAI SDK's own type docs say an interrupted stream may not include it, and a caller that did not set <code>include_usage</code> gets none at all. The gateway has to inject <code>include_usage</code>, count streamed tokens itself as a fallback, and reconcile against the provider's invoice each month. The second failure is pass-through itself: a new provider endpoint the gateway does not recognise either passes unmetered or is refused, and either choice upsets someone, so the default (refuse, with a fast path to add it) goes in the memo too.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Pushback: security's CISO says metadata is not enough and will block the audit closure without a year of content. Which contract risk do you accept in writing, or which investigation capability do you give up?</em></li>
<li><em>Reversal: what would you need to see to add a unified endpoint and gateway-owned failover?</em> Teams asking for failover after a provider outage, an eval set per logical model that a fallback has to pass, and a translation layer tested against every provider parameter those teams send.</li>
<li><em>Two senior engineers disagree: one says customer-facing calls must also hard-stop at the cap or budgets mean nothing, the other says a finance control must never cause an outage. How do you decide without deciding by rank?</em> Look at last quarter's overages: how many, how large, and whether the soft cap's page reached someone who acted.</li>
</ul>

## Follow-ups

- *You have four engineers and 90 days. Which part of this design do you cut first if week 6 slips, and what does the audit finding say about it?*
- *A team wants semantic caching in the gateway for its FAQ feature. Do you build it, and under what conditions?* Only per feature, opted in, with an eval of near-match answers, because a near match served as an answer is a wrong answer the team did not write.
- *What do you alert on in the first month?* Metered cost against the provider's daily usage, the share of requests missing tags, added p99 latency per region, and refusals by policy rule.

## Common mistakes

- Building a translation layer first and asking 40 teams to rewrite against it inside an audit deadline.
- Hard-stopping customer-facing traffic at a budget cap and discovering it on the last day of the month.
- Promising security a year of content against contracts that forbid it.
- Metering streamed responses only from the final usage chunk.
- Treating fallback to another provider's model as an availability feature rather than a behaviour change that needs its own evaluation.
- Leaving the gateway's own dependencies, the budget store and the log pipeline, without a stated failure mode.
