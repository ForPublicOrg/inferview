## Question

<Callout kind="interview" label="As asked">
"Your LLM endpoint's p99 latency doubled after a deploy with no model change. How do you diagnose it?"
</Callout>

The endpoint streams chat responses from a vLLM deployment. Traffic is mostly short prompts with an occasional long document pasted in. After Tuesday's deploy, users report answers "freezing for a moment" mid-stream. The deploy diff:

```diff
-image: serving-base:2026.10.1
+image: serving-base:2026.10.2
 engine:
   model: same weights, same revision
-  max_num_batched_tokens: 2048
+  max_num_batched_tokens: 16384     # "raise throughput", per the change request
   enable_prefix_caching: true
 log_level: info
```

## Answer

The pattern is a tail-only inter-token regression with better throughput and better TTFT, and only one change in the diff affects what goes into a step. With chunked prefill, the per-step token budget caps how many prompt tokens join each step alongside the decodes. At 2,048, a long pasted document is processed over several light steps and streaming users barely notice. At 16,384, most of it lands in one or two heavy steps, and every running sequence waits for those steps before getting its next token. That is the "freeze" users describe, and it shows at p99 because long prompts are occasional. vLLM's tuning docs describe exactly this trade: a smaller `max_num_batched_tokens` gives better inter-token latency, a larger one better TTFT and throughput.

Diagnosis steps you would describe in the room: compare percentiles, not means; split TTFT from ITL; line up the regression with the deploy and read the diff; check the engine's own metrics (queue, KV usage, preemptions, prefix hits) to eliminate memory and caching; then confirm by replaying traffic with a few long prompts against both budget values.

Fix: revert to a budget chosen from the ITL objective, or a middle value, and if long documents are frequent, route them to separate replicas or use prefill-decode disaggregation. Record the ITL objective next to the setting so the next "raise throughput" change is checked against it.

Why the others tempt. Prompt changes that break prefix caching are a classic cause of latency regressions, but the hit rate did not move. Preemption storms do cause stalls, but the counter is at zero. A slower library is plausible whenever an image changes, but it would move p50 and throughput too. Scale-in is ruled out by the replica and queue rows.

## Follow-ups

- *How would you have caught it before users did?* A canary with an SLO check on p99 ITL, and a load test that includes long prompts.
- *Why did TTFT improve?* Long prompts finish prefill in fewer steps, so their first token arrives sooner, and short prompts are admitted with more room per step.
- *What if you need both good TTFT and good ITL?* Separate pools for prefill and decode, which is the case for disaggregated serving.

## Common mistakes

- Looking at mean latency, which barely moved.
- Treating "no model change" as "no behaviour change"; engine settings change latency as much as weights do.
- Rolling back the whole deploy without identifying the line, so the next attempt repeats it.
