## Question

<Callout kind="interview" label="Concept, 25 minutes">
Your team turned on Claude Code's sandbox for an internal agent that fixes failing tests in a service repository. The sandbox's allowed domains are github.com and registry.npmjs.org. The developer machines hold a deploy key in ~/.ssh, and the agent's shell has a GitHub personal access token in its environment so it can push branches. Security asks one question before rollout to forty engineers on Monday, two working days away: name three ways this agent can still leak a secret, the control for each, and which of them you close before Monday.
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which of the agent's tools run inside the sandbox and which run beside it.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask security what a request to an allowed domain can carry, and whether anything on the path reads the body.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the agent's settings file and the permission mode the engineers will run it in.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The sandbox wraps shell commands and stops new destinations; it does not stop the agent reading secrets or sending them to a destination it already allows. Three leaks: a shell command reads ~/.ssh (reads are allowed by default) and pushes it to an attacker's repository on github.com, which the proxy allows by hostname without reading the TLS body; the Read and WebFetch tools sit outside the sandbox, so a secret read with Read can leave through WebFetch whatever the domain list says; and the token in the environment is in every sandboxed process and leaves through the same allowed domain. Before Monday I would deny reads of credential files, set allowUnsandboxedCommands to false and failIfUnavailable to true, add permission rules for Read and WebFetch, and swap the personal token for a short-lived, repository-scoped one. The git proxy that keeps the token out of the sandbox entirely comes after Monday.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Leak 1: an allowed domain is a destination for anything.</strong> Claude Code's sandbox allows reads of most of the machine, including ~/.ssh and ~/.aws/credentials, unless the configuration narrows them. Its proxy allows or refuses by the hostname the client supplies and, by default, does not terminate TLS, so it never sees what a request carries. The documentation warns that a broad domain such as github.com can be an exfiltration path and that domain fronting can reach hosts off the list. An injected instruction in an issue the agent reads can make it run a command that reads the deploy key and pushes it to the attacker's own repository with the agent's token, or creates a gist. Control: deny reads of credential paths with the sandbox's credentials setting, so the file never reaches the process, and keep the domain list to what the task needs.</p>
<p><strong>Leak 2: the tools beside the sandbox.</strong> The sandbox isolates shell commands and their children. Read, Edit, Write, WebFetch and WebSearch follow permission rules instead: a denyRead entry does not stop the Read tool, and allowedDomains does not limit WebFetch. Command hooks and local MCP servers run with the user's full access. So the model can read a key with Read and put it in the query string of a WebFetch to any host. Control: permission deny rules for Read on credential paths and for WebFetch outside an allowlist, or run the whole Claude Code process inside a boundary (the sandbox runtime or the dev container) so the tools inherit it.</p>
<p><strong>Leak 3: the secret is already inside.</strong> A token in the environment is in every sandboxed process. It leaves through an allowed domain, through the transcript, or in a commit if the agent writes it into a test fixture. Control: keep the credential out of the sandbox. Claude Code on the web does this with a proxy outside the sandbox that checks the scoped credential and the push target and only then attaches the real token. Until that exists, a short-lived token scoped to the one repository bounds the damage, and secret scanning on the agent's output, which GitHub runs on its cloud agent before it completes a pull request, catches the commit case.</p>
<p><strong>Two configuration gaps that widen all three.</strong> When a command fails in the sandbox, Claude can retry it with dangerouslyDisableSandbox; in bypassPermissions mode that retry runs unsandboxed with no prompt. And if the sandbox cannot start, because bubblewrap is missing on a Linux machine for example, Claude Code runs commands without it by default. Set allowUnsandboxedCommands to false and failIfUnavailable to true.</p>
</Fragment>

### What goes in before Monday, and the decision behind it

Two plans are defensible for the token, and they cost different things.

- **Keep a token in the sandbox, but make it small.** Replace the personal token with one scoped to the single repository, with contents write and nothing else, and a lifetime you choose. Add the deny rules, the two settings and the Read and WebFetch permission rules. All of it is configuration and fits in two days. The cost: a token is still inside. An injected agent can push to any branch that token can write, or read anything the repository holds, through github.com.
- **Take the token out now.** Put a proxy outside the sandbox that accepts git operations, checks that a push targets the agent's own branch, and attaches the credential, as Claude Code on the web does. Nothing inside can leak it. The cost: two days is not enough to build, test and roll it out to forty machines, and a half-built proxy that breaks pushes will be turned off by the first engineer it blocks.

The conflict is the deadline against the residual risk. I would ship the first plan on Monday with the second as the next milestone, and write down the risk in between: an injected agent can push to the repository and read its contents for the token's lifetime. The lifetime is the number to defend. One working day bounds a leaked token to the day it leaked, which is long enough that an agent run never fails halfway on expiry and short enough that nobody has to chase a revocation after hours. Shorter, an hour or two, means failed pushes on long runs unless the harness refreshes the token. A 90-day personal token with access to every repository the engineer can see is the unreasonable choice, and it is what the setup has today.

### Where the recommended plan fails

The credential deny rule covers the paths you list. A key copied into the repository, a token in a .env file inside the working directory, or credentials in a tool's cache directory are not on the list and are readable. The domain list still contains github.com, and the TLS limitation still applies, so an injected agent can still send repository contents out through it. The plan narrows what can leak; it does not close the channel. Closing the channel is the proxy, plus a TLS-terminating proxy if the threat model includes data and not only credentials.

### What you give up

With the reads denied, tests that depend on local cloud credentials stop working in agent runs. With unsandboxed retries off, commands that need the network outside the list fail instead of asking. The sandbox reduced prompts by 84% in Anthropic's internal use (vendor-reported); each new deny turns some of those back into failures the engineer has to handle.

## Follow-ups

- *Your Monday plan leaves a token inside for two weeks. Security wants the agent to stay off until the proxy is ready. How do you settle it without deciding by seniority?*
- *Hooks run with full access. One of your hooks posts tool input to a logging service. What does that hook see, and what do you change?*
- *The agent also needs npm publish rights for one package. Does that credential go through the same proxy, and what does the proxy check?*

## Common mistakes

- Treating "network allowlist" as "cannot exfiltrate", when the allowlist contains a host that accepts writes from anyone with a token.
- Assuming every tool runs inside the sandbox, so a denyRead entry is expected to stop the Read tool.
- Leaving the default fallback that runs commands unsandboxed when the sandbox cannot start.
- Fixing leaks by deleting the token from the environment without giving the agent another way to push, which leads engineers to paste it back in.
