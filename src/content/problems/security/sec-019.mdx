## Question

<Callout kind="interview" label="Multiple choice">
You own the isolation boundary for a hosted Python interpreter that runs code written by any customer's users, with sessions from many tenants packed onto each host. Most sessions load pandas and NumPy and work on uploaded files. The platform runs on a managed Kubernetes service whose node pools are general-purpose cloud virtual machines, and the platform team will not run bare-metal nodes this year. The security review requires that a kernel bug reachable from tenant code is not, on its own, a path into another tenant's session. Which boundary meets the requirement on this platform?
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the platform team which node types the cluster can schedule onto and what each one exposes to a pod.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each option, ask which component answers a system call from tenant code, and whether every tenant on the host shares that component.</p></details>

## Answer

The gVisor sandbox. gVisor's Sentry implements the Linux interface in user space and, in its own documentation, does not pass system calls through to the host kernel. Tenant code that wants a host kernel bug has to break the Sentry first. It runs as an ordinary runtime class on ordinary nodes, with no hardware virtualisation. The cost is the one the option names: gVisor documents higher per-system-call overhead and poor performance for system-call-heavy workloads. Anthropic's deployment guide reports about 0% overhead for CPU-bound code and up to 10 to 200 times for file I/O with heavy open and close patterns (vendor-reported). A NumPy loop pays almost nothing. Importing pandas, which opens many small files, pays the most. Measure that import before you set the cold-start budget.

Why each wrong option is tempting:

- **The hardened container.** Dropping capabilities, a read-only root and the default seccomp profile all shrink what tenant code can reach, and many teams treat that as a boundary. It is still one kernel shared by every tenant on the host. The runc escape in CVE-2024-21626 did not need a blocked system call: a leaked file descriptor gave a container process a working directory in the host's filesystem. Runc releases from v1.0.0-rc93 through 1.1.11 were affected.
- **The seccomp filter that checks paths.** Engineers who have written seccomp profiles know a filter sees the arguments of `open()`, and assume that includes the path. The filter sees the pointer, and BPF programs may not dereference pointers. The kernel documentation also says, in so many words, that system call filtering is not a sandbox; it is a tool for building one.
- **The microVM.** A microVM is the strongest boundary of the four, so it looks like the safe answer. Firecracker creates and runs guests through KVM, and every platform in its README's tested list is a bare-metal instance. General-purpose cloud VMs do not offer KVM to a pod unless the provider supports nested virtualisation, which the stem's node pools do not promise. The second half fails too: Firecracker's design document says it does no network traffic filtering and that guest egress must be filtered at the host. A rate limiter bounds throughput; it does not decide destinations.

## Follow-ups

- *The platform team offers a bare-metal node pool after all, at a higher price per core. What would you need to measure before moving from gVisor to microVMs, and what does the move change for egress?*
- *Cold start with pandas preloaded is over your budget under gVisor. Do you keep warm sandboxes per tenant, preload into a snapshot, or relax the requirement, and what does each cost?*
- *A customer asks why their workload is slower than on their laptop. Which measurement do you show them, and which part of the overhead can you remove without changing the boundary?*

## Common mistakes

- Treating a stack of container hardening flags as equivalent to a separate kernel.
- Assuming a seccomp filter can enforce file paths.
- Choosing a microVM without asking where KVM comes from, and then treating the VMM as the network policy.
- Quoting gVisor's overhead as one number; it ranges from negligible to large depending on how much of the workload is system calls.
