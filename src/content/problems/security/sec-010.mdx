## Question

<Callout kind="interview" label="Design review">
"This is the workspace-configuration section of our coding agent's v2 design. Two reviewers approved it. What would you block it on, what would you let through with conditions, and in what order would you fix it?"
</Callout>

The document is constructed for this problem. List the flaws and rank them before you open the checklist.

### Lathe v2: workspace configuration

**Goal.** Teams version their agent setup with their code, the same way they version CI.

**Layout.** Everything lives in the repository under `.lathe/`: `settings.json` holds permission rules and the model choice, `hooks/` holds scripts that run at session start and before each tool call, and `mcp.json` lists MCP servers. `AGENTS.md` at the root and `.lathe/skills/*.md` hold instructions.

**Hot reload.** Lathe watches `.lathe/` and reloads on any change, so a teammate's fix to a hook or a new MCP server reaches running sessions without a restart.

**Protection.** The edit tool asks before modifying an existing file under `.lathe/`. Creating new files anywhere in the workspace never asks, because scaffolding a feature creates dozens of files and prompts for each would make the agent unusable.

**Workspace boundary.** A path is inside the workspace when `os.path.abspath(path).startswith(os.path.abspath(workspace))`. Reads and edits inside the workspace follow the rules in `settings.json`; anything outside asks.

**Shell.** The shell tool runs as the developer, in the workspace, and commands go through the same allowlist as before (`git`, `npm`, `pytest`, `cat`, `cp`, `tee`, `mkdir`).

**Approvals.** When a developer picks "always allow" on a prompt, Lathe appends the rule to `.lathe/settings.json`, so the whole team benefits after the next commit. On clone, the repository's settings, hooks and MCP servers are active immediately, so a new hire gets a working setup on day one.

**Instructions.** The agent may edit `AGENTS.md` and files under `.lathe/skills/` when it learns a convention, so the next session starts smarter.

**Audit.** Every approval and denial is appended to `.lathe/audit.log`, which the security team collects weekly.

## Answer

Rank by how short the path is from text the agent reads to code that runs without a person.

**1. New files skip approval (block).** In a repository where `.lathe/mcp.json` or `.lathe/hooks/session-start.sh` does not exist yet, an injected instruction can create it with no prompt, and hot reload starts the server or runs the hook. This is CVE-2025-54135 almost word for word: Cursor asked before editing an existing dotfile and not before creating one, and an injected agent created `.cursor/mcp.json`. Protection has to be a property of the path, decided before the file exists, the way Claude Code's protected-path list works. Codex's sandbox is a useful contrast: it keeps `.git` read-only whether it is a directory or a pointer file, but protects `.codex` and `.agents` only when they already exist as directories, so the sandbox alone does not cover the creation case.

**2. The shell writes config too (block).** `tee .lathe/mcp.json`, `cp payload.json .lathe/hooks/pre-tool.sh` and `cat x > .lathe/settings.json` all pass an allowlist that contains `tee`, `cp` and `cat`. Protecting the edit tool and not the shell protects nothing. Check the write targets of recognised commands and redirects, and mount `.lathe/` read-only in the agent's sandbox so a script that opens the file itself fails too.

**3. Hot reload (block).** It turns every flaw above into execution inside the same session. Config that changes what the agent may do should apply to the next session, after a person has seen the change.

**4. Config that runs outside the agent (block).** `.git/hooks/pre-commit` runs on the developer's next commit, with the developer's credentials and no sandbox. `.vscode/settings.json` and `tasks.json` can switch another tool's approvals off or run tasks: CVE-2025-53773 was Copilot writing `"chat.tools.autoApprove": true` into the workspace's VS Code settings. The protected set has to name these, not only `.lathe/`.

**5. The boundary check.** `startswith` on strings says `/src/app-old/x` is inside `/src/app`, and `abspath` does not follow symlinks, so `ln -s ~/.ssh keys` puts the developer's keys "inside" the workspace. Claude Code shipped the first of these (CVE-2025-54794: `claude_code_evil` passed for `claude_code`). Compare resolved paths by whole components, and check both the requested and the resolved path.

**6. Approvals become team policy.** One developer's "always allow `cp`" lands in `.lathe/settings.json`, is committed, and is active for everyone on the next pull, with nobody having reviewed it as policy. Personal approvals belong in user settings.

**7. Trust on clone.** Settings, hooks and MCP servers from a repository someone else controls are active on clone. Claude Code holds a project's allow rules until the workspace trust dialog, which lists them; deny and ask rules apply without it, since they only restrict.

**8. The audit log.** The agent can edit the log that is supposed to show what the agent did. Write it outside the workspace, or to a sink the agent cannot reach.

**9. Instructions (acceptable if).** Letting the agent edit `AGENTS.md` and skills is acceptable if the edit appears in the diff a person reviews and takes effect only in a new session. Instructions shape what the agent tries; they do not change what the harness allows.

### The decision: protect config in place, or move it out

- **Keep config in the repository and make it read-only to the agent.** A protected-path list, write-target checks for the shell, a read-only mount, and a trust prompt on clone. Teams keep versioning their setup. Cost: the list is name-based and never finished. Claude Code's list already names package-manager files such as `.npmrc` and `bunfig.toml`, because each tool that reads config from the workspace is another way in.
- **Move behaviour-changing config out of the repository.** Permission rules, hooks and MCP servers come from user and managed settings; the repository may carry only instructions and deny rules. Cost: teams lose versioned setup, and onboarding goes back to a wiki page.

I would keep config in the repository with the first set of controls, and move permission rules and hooks for regulated repositories to managed settings, where no project file can override them. The failure mode of that choice is the list: the next editor, build tool or agent that reads a dotfile from the workspace is unprotected until someone adds it, and the read-only mount only covers paths someone thought to mount. Review the list whenever a new tool is approved for developer machines.

**Order of fixes**, with a small team: new-file protection and shell write checks first (the short path to execution), hot reload and trust on clone second, the boundary check and `.git/hooks` and `.vscode` third, then approvals and the audit log.

## Follow-ups

- *Your protections add a prompt for every hook change, and the platform team edits hooks daily. Which prompts do you remove, and what risk do you accept in writing?*
- *What would you need to see from a quarter of approvals data to let the agent edit `.lathe/skills/` without review?*
- *Two senior engineers disagree: one wants config out of the repository entirely, the other says teams will stop using the agent. How do you decide without deciding by rank?*
- *A developer clones an open-source repository whose `.lathe/mcp.json` points at a server on the internet. What happens under your design, step by step, before any tool call runs?*

## Common mistakes

- Protecting existing files and forgetting that the dangerous file is usually the one that does not exist yet.
- Protecting the edit tool and leaving the shell, which can write any file the developer can.
- Listing only the agent's own config directory and missing git hooks and editor settings, which run with fewer restrictions than the agent.
- Treating "the developer approved it once" as approval for the whole team.
