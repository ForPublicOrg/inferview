## Question

<Callout kind="interview" label="Design round, 45 minutes">
"Describe how you would detect a prompt injection attack at the infrastructure level, not only in the application."
</Callout>

The setting, when you ask (scenario):

- About 40 internal agents built by different teams. Every model call goes through a shared LLM gateway, every tool call through a tool gateway (an MCP proxy), and every outbound HTTP request through an egress proxy. Traces exist but carry only timing and token counts today.
- Volume: about 200,000 tool calls and 60,000 retrieved documents a day across the fleet.
- The SOC can triage about 20 alerts a day for this whole surface.
- The privacy team does not allow full prompts and completions in the general log pipeline; they contain employee and customer data.
- Your team is four platform engineers for a quarter. Application teams will not change their code this quarter.

Design the detection: what you collect, where, what fires an alert, what happens after it fires, and what you write down about what it cannot see.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which tools in the fleet can change state or send data out, and which agents call them on outside content as part of their normal work.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request a day of tool-call and egress volume per agent, so you can price each candidate rule in alerts.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the privacy team permits: hashes, fingerprints, sampled content, and for how long.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Detect the consequence, not the text. An injection that matters has to cross one of the three gateways: a consequential tool call or an outbound request. So join the gateways on one trace id, record which untrusted sources entered each context, and alert when a consequential action follows untrusted input and its arguments or URL carry data the user did not supply. Plant canary tokens in sensitive stores; any canary in egress is a high-confidence page. A text classifier on retrieved content feeds the score and never alerts alone, because adaptive attacks beat detectors. Price every rule in alerts per day against the SOC's 20, keep content out of the general logs with fingerprints, and write down that text-only harm, such as a misleading answer, never crosses a gateway and is invisible here.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What to collect, at which gateway.</strong> CoSAI's telemetry list is the starting schema: identity, model and version, token usage, retrieved documents, tool calls and a trace or session id. The platform-level addition is provenance. The LLM gateway sees every message that enters a context and can tag each one by origin: user turn, system prompt, tool result from an internal source, tool result from outside content (mail, web, tickets). The tool gateway records each call with its arguments and the trace id. The egress proxy records host, path and query with the trace id, which the gateways propagate in a header. None of this needs application code changes.</p>
<p><strong>Privacy.</strong> Content does not go into the general log. The gateway stores, per context message, an origin tag and a set of hashed n-gram fingerprints; per tool call and egress request, fingerprints of the arguments and URL. Matching "this URL contains text from that retrieved document" works on fingerprints. Full content goes to a restricted store with short retention, opened under an incident ticket.</p>
<p><strong>Pricing the rules.</strong> The SOC's 20 alerts a day against 200,000 tool calls means a paging rule may fire on at most 20 / 200,000 = 1 in 10,000 calls. A classifier that flags 2 percent of retrieved documents (scenario) produces 0.02 × 60,000 = 1,200 flags a day, sixty times the budget, before counting its misses. So no single weak signal pages anyone. The rules that fit:</p>
<ul>
<li><strong>Canary hit</strong>: unique tokens planted in sensitive stores (a fake customer record, a fake secret in a vault path agents can read, a marker in each system prompt) that appear in egress or in an argument to an outbound tool. Near-zero false positives; it catches only exfiltration of canary-bearing data.</li>
<li><strong>Provenance match on a consequential action</strong>: in a trace where outside content entered the context, a send, write, payment or fetch whose arguments or URL contain fingerprints of a sensitive document, or a recipient or host that appears in the outside content and not in the user's turn. This is CaMeL's data-flow idea used for detection instead of enforcement.</li>
<li><strong>New edge per agent</strong>: an agent calling a tool, or reaching a host, it has never used in its 30-day baseline, after outside content entered. Cheap and noisy; it goes to a daily hunting queue, not a page.</li>
</ul>
<p>The quantity to choose is the threshold for the provenance rule, such as the share of a URL's or argument's fingerprints that must match sensitive content. Reasonable choices are set by replaying a week of traces and picking the threshold that fits the alert budget with the canary tests still firing; a threshold chosen without that replay is a guess about the SOC's week.</p>
<p><strong>The decision with two defensible answers: block or detect.</strong> Inline at the tool gateway, the provenance rule can hold the call for approval instead of alerting. That stops the exfiltration rather than reporting it, at the cost of latency on every consequential call and of breaking agents that legitimately act on outside content (a support agent replying to the customer who wrote the ticket fires the recipient rule on every turn), with no application team available to fix them this quarter. Out of band, nothing breaks and nothing is slowed, at the cost of detecting after the data left. My choice: inline only for canary hits and for egress to hosts first seen in the fleet, which are rare and high-confidence; out of band for the rest, with per-agent exemptions written down.</p>
<p><strong>Allowlists are not detection.</strong> EchoLeak sent data out through Teams and SharePoint URLs, hosts any enterprise allowlist contains. The egress rule therefore looks at what is in the URL, not only at the host.</p>
<p><strong>After the alert.</strong> CoSAI's playbook routes by vector: for a user-input vector, quarantine the session; for retrieved content, re-score or remove the document from the index, and find every other trace that retrieved it; for a changed agent configuration, take the agent offline. Then alert and record. The retrieved-document case is the one the platform makes cheap: the fingerprint index answers "which sessions saw this document" in one query.</p>
<p><strong>The constraint conflict.</strong> Visibility against privacy, and coverage against an alert budget. Every content field logged improves detection and widens who can read customer data; every rule added widens coverage and eats the SOC's 20.</p>
<p><strong>Failure modes of this design.</strong> Fingerprint matching misses transformed exfiltration: data summarised, translated or encoded in base64 before it leaves. Canary hits catch some of that only if the canary itself survives the transformation. Agents whose job is acting on outside content get exemptions, and an exemption is a blind spot an attacker will find. And text-only harm, a wrong answer or a phishing message shown to the user, crosses no gateway at all; CaMeL draws the same line for prevention.</p>
<p><strong>What I write down.</strong> A detection coverage note for the SOC: the three rules with their measured alert rates from the replay, what each cannot see, the exemption list with an owner per agent, the retention and access rules agreed with privacy, and the playbook per vector.</p>
<p><strong>What you give up.</strong> Real-time blocking for most rules, full content for analysts, and coverage of text-only attacks.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not log full prompts and let the SOC search them?</em> It widens access to customer data for every analyst, and the privacy team has said no; fingerprints answer the questions detection needs.</li>
<li><em>How do you know the rules still fire after a gateway change?</em> A scheduled synthetic attack per rule: a test agent reads a seeded document and tries to send its canary out; the alert must arrive within the stated time.</li>
</ul>

## Follow-ups

- *Pushback: the fingerprint index costs more storage and engineering than the rest of the design together. Which half do you cut, and what risk do you accept in writing?* Keep canaries and the new-edge rule, which need only tool and egress logs; drop argument fingerprints and write down that exfiltration of non-canary data through a known host and tool is not detected.
- *Reversal: what would you need to see to move the provenance rule from out of band to inline blocking?* A month of replays in which its fires per day fit the approval capacity and none of the fires came from an exempted business flow, plus the owners of the five busiest agents agreeing to the latency.
- *Two staff engineers disagree: one wants a commercial injection classifier at the gateway as the primary signal, the other refuses. How do you decide without deciding by rank?* Run it for a week in shadow, count its flags against the 20-alert budget, and red-team it with an attacker who can query it; let flags per day and the adaptive success rate decide its weight.
- *The SOC's budget drops to 5 alerts a day. Which rule loses its page, and who signs?* The provenance rule pages only above a higher threshold and the rest goes to daily hunting; the SOC lead signs the longer time to detection.

## Common mistakes

- Running a text classifier on every prompt and calling it detection, then drowning the SOC.
- Treating an egress allowlist as the exfiltration control.
- Logging full prompts to a general pipeline to make detection easy.
- Designing per-application detectors when the gateways already see every call.
- Leaving out what the design cannot see, so a quiet SOC is read as safety.
