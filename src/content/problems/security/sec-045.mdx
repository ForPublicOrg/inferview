checklist:
  - Separates an always-on metadata record from an opt-in content tier, each with its own retention, encryption keys and access path
  - Records on every model call the requested and responded model, the prompt template and system prompt versions as hashes, and the conversation and run ids
  - Records each tool call with name, call id, structured arguments with field-level redaction, result status and resource ids, and the policy rule that allowed, denied or asked
  - Records each approval with the approver, what the approver was shown and when, linked to the tool call it approved
  - Removes token passthrough from the CRM MCP server and records both the user as subject and the agent as actor on every downstream call
  - Sizes the content tier from the traffic, storing new messages per call and retrieved documents once by content hash rather than the full context on every call
  - Sets retention per tier with a written purpose, and reconciles minimisation with the six-month deployer duty where a customer's use is high-risk
  - Encrypts content per tenant so erasure and expiry are key destruction, and states how erasure requests interact with a legal hold
  - Makes the log append-only and tamper-evident, and logs and approves every investigator's read of the content tier
  - States that a hash proves a known document was seen but cannot reconstruct injected text that has since been deleted, and keeps content accordingly
  - Treats logged content as untrusted input to any AI tool used in an investigation
  - Ships a test that reconstructs one agent run, including who approved what, from the logs alone

## Question

<Callout kind="interview" label="Workflow, 45 minutes">
"Design the audit log for our agents. After an incident, an investigator has to reconstruct what the agent saw, what it did, on whose authority and who approved it. Our data protection officer has already told us the log must not become a second copy of every customer conversation."
</Callout>

The platform (scenario):

- A sales assistant that acts for employees of 1,200 customer companies, most of them in the EU. It reads and updates a CRM through an MCP server the company operates, drafts and sends email after the user approves, and retrieves from the customer's document store.
- The CRM MCP server forwards the user's CRM OAuth token unchanged to the CRM API.
- 2 million agent runs a month. A run averages 14 model calls and 9 tool calls; the context reaches about 30,000 tokens by the late calls, and each call adds about 2,000 new tokens.
- Today the platform logs model latency and token counts, nothing else. Content logs were never turned on.
- Security asks for every prompt and tool result for two years. The data protection officer cites minimisation and storage limitation. One customer's counsel says their use case is credit-related and asks whether the logs meet the six-month deployer duty in the AI Act.
- Two engineers, six weeks.

Design the log: what is recorded for each model call, tool call and approval; where content goes and for how long; who can read it; and what you write down for security, the data protection officer and the customer's counsel.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask an investigator from the last security incident which questions the current logs could not answer, and which of those needed the text of a prompt rather than its metadata.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the CRM's own audit log for one agent run, and check whose name it shows on the update.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the storage team the cost per terabyte-month, and the data protection officer which purposes she would accept for each retention period.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Two tiers. A metadata record that is always on, holds no free text, and lives long: for every model call the model versions, prompt and system prompt hashes and ids; for every tool call the name, call id, redacted structured arguments, result status and resource ids, and the policy rule that decided; for every approval who approved what they were shown. A content tier that is encrypted per tenant, stores new messages and retrieved documents once by hash, expires in 30 days and is read only through an approved, logged investigation. Fix token passthrough first, because no log design recovers an identity the CRM never saw: exchange the user's token for one that names the agent as actor. Then write the retention rule, the access policy and a test that reconstructs a run from the logs.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The metadata record.</strong> Follow the OpenTelemetry GenAI conventions where they exist, so the fields are the ones tools already read. Per model call: <code>gen_ai.request.model</code> and <code>gen_ai.response.model</code> (the requested alias and the snapshot that answered), the conversation and run ids, the prompt template version and a hash of the rendered system prompt, token counts, and a guardrail verdict if one ran. Per tool call: <code>gen_ai.tool.name</code>, <code>gen_ai.tool.call.id</code>, the arguments as structured fields with free text replaced by a keyed hash and identifiers kept (CRM record ids, recipient domains, amounts), the result as status, size and resource ids, and the policy decision: rule id and allow, deny or ask. Per approval: the approver, the rendered text they were shown and the time, joined to the call id. CoSAI's baseline asks for exactly this set of tool usage, configuration versions and authorisation events, and none of it is a customer conversation.</p>
<p><strong>Identity: the defect no log fixes.</strong> The MCP server forwards the user's token, so the CRM's audit log records the user editing the record, and the agent is invisible downstream. The MCP security guidance names this: with passthrough, downstream logs show a different identity than the one acting, which hampers investigation. Exchange the user's token for one issued to the MCP server, carrying the user as <code>sub</code> and the agent as <code>act</code>, as RFC 8693 defines; every downstream record then carries both, and the platform's record joins on the call id.</p>
<p><strong>The content tier, sized.</strong> The OpenTelemetry conventions make content opt-in and offer <code>*_ref</code> attributes that point to external storage, which is the shape here: spans carry a reference, content lives in a separate store. Logging the full input of every call duplicates the conversation each turn: 14 calls at up to 30,000 tokens is up to 420,000 tokens a run, about 1.7 MB at an assumed 4 bytes per token, or 3.4 TB a month. Logging only what each call adds, 14 × 2,000 = 28,000 tokens, is about 112 KB a run and 224 GB a month; retrieved documents go in once, keyed by content hash, since the same chunks recur across runs. The metadata record, at an assumed 1.5 KB for each of 23 spans, is about 35 KB a run and 69 GB a month.</p>
<p><strong>The decision with two defensible answers: content on by default for 30 days, or off by default.</strong> Off by default with capture switched on per tenant during an investigation satisfies the data protection officer completely, and its cost is the first incident: an injection that arrived in a document since deleted can never be reconstructed, because CoSAI's point holds that outputs do not reproduce from the same input and a hash cannot be reversed into the injected text. On by default with 30-day retention keeps about 224 GB of personal data at any time, behind per-tenant keys, and costs a standing breach target and a larger scope for every access request. I take on by default, 30 days, encrypted per tenant, because an investigation usually starts within days of the event and the metadata record keeps the long tail. Retention is a choice: 14 to 90 days is defensible for the content tier given a stated detection time; two years of content, as security asked, fails minimisation unless a specific purpose needs it.</p>
<p><strong>Retention, written down.</strong> Metadata: 13 months, purpose security investigation and year-over-year comparison. Content: 30 days, purpose incident reconstruction, extended only by a legal hold on a named investigation. For the credit-related customer, if their use is high-risk, Article 26(6) sets at least six months for logs under the deployer's control, unless data protection law provides otherwise; the metadata tier meets it, and a per-tenant setting extends content for that tenant with their DPO's sign-off. As checked on 28 October 2026, the obligation applies to Annex III systems from 2 December 2027, so it is a design input, not this quarter's deadline.</p>
<p><strong>Access, erasure, integrity.</strong> Content is encrypted with a per-tenant key; expiry and erasure are key destruction, and an erasure request against content under legal hold is recorded and executed when the hold ends. The store is append-only with a hash chain per day, and every read of the content tier needs an investigation id and an approver, and is itself a record in the metadata tier. Any AI tool used to search the logs reads attacker-written text, so it runs without tools and its findings are checked against the raw records.</p>
<p><strong>The constraint conflict.</strong> Forensic completeness against minimisation, under a six-week deadline: every field that helps the investigator is a field the data protection officer has to justify, and two engineers can build the metadata record, the token exchange and the content tier, but not per-field redaction rules for every tool, so the first version redacts by type (all free-text arguments hashed) and refines per tool later.</p>
<p><strong>Failure modes of this design.</strong> Hashing free-text arguments makes the metadata record safe and useless for one class of question: what did the agent write in that email? That answer is in the content tier for 30 days and then gone. The keyed hash, if the key is shared across tenants, lets someone with the key test guesses across customers, so it is per tenant. And the reconstruction test is what keeps this honest: if a run cannot be replayed from the logs alone, including who approved what, the schema has drifted.</p>
<p><strong>What you give up.</strong> Content older than 30 days for any incident detected late, a measurable storage bill, and a token exchange that adds a hop to every CRM call.</p>
</Fragment>

<ul>
<li><em>Why not log only hashes of prompts and keep no content at all?</em> A hash proves a known text was present; it cannot tell the investigator what an injected document said once that document is gone.</li>
<li><em>An investigator asks to read a tenant's content without an incident ticket, to look for patterns. What happens?</em> The read needs an investigation id and an approver; pattern work runs on the metadata tier, which holds no conversation text.</li>
</ul>

## Follow-ups

- *Pushback: the token exchange takes one of the two engineers for four of the six weeks. Which half do you cut, and what risk do you accept in writing?* Keep the exchange and defer per-tool redaction rules; the written risk is that the metadata tier hashes all free text for a quarter and investigators lean on the 30-day content tier.
- *Reversal: what would you need to see to turn the content tier off by default?* A quarter of investigations where the metadata tier answered every question, or a regulator's finding against standing content capture.
- *Security and the data protection officer still disagree on 30 days against 90. How do you decide without deciding by rank?* Measure detection time over the last year of incidents; retention covers the 90th percentile of time from event to investigation, and both sign that number.

## Common mistakes

- Capturing the full input of every model call, which stores the same conversation many times over.
- Logging tool arguments as free text, which turns the audit log into the personal-data store the officer warned about.
- Designing the log while the MCP server passes the user's token through, so downstream records never show the agent.
- Recording that an action was approved without recording what the approver was shown.
- Treating two years of content as the safe default, without a purpose that requires it.
