## Question

<Callout kind="interview" label="Concept">
Your platform team mirrors open-weight and vendor models into an internal registry. A security lead proposes one rule: every model is signed with Sigstore model signing and ships with a bill of materials, and signed means approved for production. What belongs in a model's bill of materials, what does a valid signature prove about the weights, and where in the path from vendor to pod would you verify it?
</Callout>

The scenario's facts, invented for this problem: the largest model in the registry is a 70B-parameter checkpoint in bf16 across 30 safetensors shards, served by a fleet that scales from 20 to 200 pods in a traffic spike, each pod pulling the model from object storage at start. Choose whether each pod re-verifies the weights at start, and defend the cost.

Type your answer before opening the worked one: the bill of materials, the list of what a signature proves and does not, and where verification happens.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which files the serving stack reads when it loads a model, and which of them can change what the model does without changing a weight.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask the security lead what identity a valid signature must come from, and who in the company can obtain a certificate for that identity.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Measure the hash throughput of one core on a serving node and the read throughput of the model volume, then ask how many pods start at once in a spike.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The bill of materials lists every file the loader reads, by digest, not only the weights: shards and their index, config, generation config, tokenizer files, the chat template and any custom modelling code. It adds the base model by digest, the training code commit and framework versions, the datasets by identifier and hash where the producer will give them, the eval runs with their eval-set versions, the format and loader flags, and the licence. A valid signature proves that these bytes are the bytes some identity signed, and with Sigstore that the signing was logged. It proves who only if the verifier pins the identity and issuer. It does not prove the BOM's claims are true, that the training data was clean, that no backdoor was trained in, or that the format is safe to load. I verify the publisher's signature once at intake, convert and test there, re-sign with the intake pipeline's identity, and have pods check the intake signature against a content-addressed copy instead of re-hashing 140 GB at every start.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What the bill of materials covers.</strong> The test for an entry is whether changing it changes what the deployed model does or what runs when it loads. Weights obviously qualify. So does the chat template: CVE-2024-34359 was remote code execution in llama-cpp-python 0.2.30 to 0.2.71, which rendered a model's chat template with a sandbox-less Jinja2 environment. So does modelling code loaded with <code>trust_remote_code=True</code>, which runs Python from the model repository; Transformers' own docs say to pin a revision so the code cannot change under you. Tokenizer files and the generation config change behaviour without touching a weight. Then the lineage that a reviewer needs to reason about risk: base model digest, adapter digests, training code commit, framework and CUDA versions, dataset identifiers and hashes, eval results tied to an eval-set version, and the serialization format. CycloneDX's ML-BOM has places for datasets, models, configuration and dataset provenance; the format matters less than the rule that the signed manifest covers the same file list the BOM describes.</p>
<p><strong>What the signature proves.</strong> Model signing v1.0 signs a manifest of (path, digest) pairs for the model directory, wrapped in an in-toto statement, a DSSE envelope and a Sigstore bundle. With the Sigstore flow, the signer gets a short-lived certificate bound to an OIDC identity and the event goes into a transparency log. Verification recomputes the manifest and checks the signature against an identity and identity provider the verifier supplies. So a valid signature shows these files have not changed since that identity signed them, and the transparency log lets the owner of the identity see every signature made in its name.</p>
<p><strong>What it does not prove.</strong> The OpenSSF specification says it directly: signing only verifies that a model has not changed since it was signed, and is not a guarantee of quality, fairness or behaviour. Three gaps matter in production. A Sigstore signature from an unpinned identity proves nothing, because anyone can obtain a certificate for their own identity; the policy is the pinned identity, not the cryptography. A signed BOM is an attributable claim, not a verified one: ChainDrop's poisoned npm releases in August 2026 carried valid SLSA provenance, because the project's own workflow built a commit the attacker had pushed. And a signature says nothing about what training put in the weights: Sleeper Agents found trained-in backdoors persisting through supervised fine-tuning, RL and adversarial training. Format safety is a fourth gap: a signed pickle still runs code at load, and a signed safetensors file can still hold NaN or infinite values, which the format does not check.</p>
<p><strong>The decision with two defensible answers: where to verify.</strong></p>
<ul>
<li><strong>Every loader verifies the publisher's signature</strong> against the publisher's pinned identity. The chain from producer to pod is unbroken and nothing in your pipeline can forge it. The costs: every service carries each vendor's identity policy, a vendor's identity change breaks loads across the fleet, and any conversion (pickle to safetensors, quantization, merging an adapter) produces bytes the vendor never signed.</li>
<li><strong>Intake verifies once and re-signs.</strong> The intake pipeline verifies the publisher's signature against the pinned identity, scans, converts to safetensors, runs the eval suite, writes a BOM that includes the publisher's bundle, and signs the result with its own workload identity. Pods verify one identity. The cost is that the intake identity now vouches for everything in production, so its compromise is a fleet-wide compromise.</li>
</ul>
<p>The conflict is cold-start latency and operability against an unbroken chain to the producer. I choose intake re-signing, keep the publisher's bundle in the BOM for audit, and make the intake signing identity a CI workload identity that no person can use, with an alert on any transparency-log entry for that identity that does not match an intake run.</p>
<p><strong>The quantity: re-hash at every pod start or not.</strong> 70 × 10<sup>9</sup> parameters × 2 bytes is 140 GB, or about 130 GiB. Python's <code>hashlib</code> SHA-256 ran at about 1.6 GiB/s on one core of the machine this answer was written on (measured 2026-10-28), so one core takes about 130 / 1.6 ≈ 81 s; 30 shards hashed in parallel on 8 cores take about 10 s if storage can feed about 13 GiB/s, which is the number to measure. In a spike, 180 new pods each read the full 140 GB again just to hash it, and a server that memory-maps weights lazily loses that advantage. Re-hashing at start is defensible for a fleet of a few pods that rarely scales; at this fleet's scale I verify at intake and at volume build, address the model by its manifest digest, and have the pod check the intake signature over that digest, which costs milliseconds. The failure this accepts is a modified file on a node's local cache after the volume was built, which a periodic background re-hash on each node can catch.</p>
<p><strong>Failure modes of the recommendation.</strong> Intake re-signing turns one pipeline into the trust root, so its bugs become production's: an eval suite that misses a regression or a converter that changes a tokenizer file gets signed as approved. And "signed means approved" is the rule the security lead proposed; under intake re-signing it becomes true only for the intake identity, so the BOM has to record what intake checked, so that approved has a stated meaning.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The vendor signs with a key, not Sigstore, and publishes the public key on its website. What changes?</em> Key distribution becomes your problem: pin the key out of band, record its fingerprint in the BOM, and agree a rotation procedure, since there is no transparency log to show signatures made with a stolen key.</li>
<li><em>Your converter quantizes to FP8 at intake. What does the BOM say about the relation between the signed vendor files and the quantized ones?</em> The vendor's manifest digest, the converter's version and arguments, and the eval results of the quantized model, because the quantized files were never signed by the vendor.</li>
<li><em>Why not sign only the weight shards, which are the large files?</em> Because the chat template, the tokenizer and any modelling code change behaviour or run at load, and they are the cheap files to tamper with.</li>
</ul>
</Fragment>

## Follow-ups

- *Verification at intake adds two days to every model update and the product team ships a vendor fine-tune every week. Which intake checks do you drop for a weekly update, and what risk do you accept in writing?*
- *What would you need to see in a quarter of operation to move verification from intake to every loader?*
- *Two senior engineers disagree: one wants a model with a valid vendor signature and a clean scan in production the same day, the other wants it held until the eval suite has run. How do you decide without deciding by rank?*
- *The transparency-log monitor fires on a signature by the intake identity at 03:00 with no intake run. What do you do in the first hour?*

## Common mistakes

- Signing the weight shards and leaving out the chat template, tokenizer, configuration and modelling code.
- Verifying that a signature is valid without pinning the identity and issuer it must come from.
- Treating a signed bill of materials as true rather than as attributable.
- Reading a signature as a statement about training data or backdoors.
- Re-hashing the full model at every pod start without computing what it costs in a scale-up.
