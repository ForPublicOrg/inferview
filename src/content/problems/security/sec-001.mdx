checklist:
  - Draws every outbound channel, including fetch query strings, images and links rendered in the client, and invites with external attendees, not only the send tool
  - Treats the inbox and the calendar as attacker-writable, so any session with mailbox access also processes untrusted input
  - Builds the capability table per session type (triage, reply, schedule, research) and marks the sessions that hold all three legs

## Question

<Callout kind="interview" label="Workflow, 50 minutes">
"Our assistant reads the user's mail and calendar, can fetch a URL, can send mail and can create calendar invites. Security review is in three weeks. Take it from a data-flow diagram to a test for every control, and tell me which controls hold by construction and which only lower a rate."
</Callout>

The system (scenario):

- 3,000 employees in the pilot. The assistant runs as one agent loop with six tools: `search_mail`, `read_thread`, `read_calendar`, `fetch_url`, `send_mail`, `create_invite`. It calls the mail and calendar APIs with one delegated token that carries read and send scopes for both.
- The client is a side panel in the mail app. It renders the assistant's output as markdown, including images and links.
- Pilot telemetry: per user per day, about 6 assistant-drafted sends and 2 invites; 30 percent of both have at least one external recipient.
- Product's goal for launch: the assistant schedules meetings requested by email "without asking every time". The product lead considers a confirmation on every action a launch blocker.
- Two engineers, three weeks. The model vendor and the mail platform cannot be changed.

Produce the five artefacts: the data-flow diagram with its trust boundaries, a capability table per session type, the architecture change, a control per boundary labelled by construction or by rate, and a test per control. Say what goes in the document the security reviewer signs.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the side panel does with an image reference or a URL in the assistant's output, and what the fetch tool sends to the host it calls.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask who can put text into a user's inbox and calendar without the user's consent.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the reviewer what evidence they accept for a control: a test result, a measured rate on a named attack set, or a design statement.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Draw the boundaries first, and the outbound channels turn out to be five, not one: send, invite, fetch, and images and links in the panel. Because anyone can email or invite the user, every session with mailbox access also processes untrusted input, so the leg to remove is almost always outbound communication. Split the single loop into four session types whose tool lists and token scopes the orchestrator sets: triage (no outbound at all, images off), reply (sees one thread, the user presses send), schedule (recipients checked in code, external invites confirmed), research (fetch, but no mailbox). Label tool lists, scopes, recipient checks and rendering as by construction and test them deterministically; label the classifier, delimiters and the model's own training as rate controls, measure them on a sized suite, and write down that an adaptive attacker beats the measured rate.</p>
</Fragment>
<Fragment slot="long">
<p><strong>1. Data-flow diagram.</strong> Components, following CoSAI's agentic pattern: the side panel (application interface), the orchestrator (executor), the model API, the mail and calendar APIs (tools and information sources), the fetch tool, and the trace store. Trust boundaries: panel to orchestrator; orchestrator to model vendor; orchestrator to mail and calendar with a delegated token; orchestrator to the internet through fetch; panel to the internet through rendered images and links; orchestrator to the trace store, which ends up holding mail content from every user. Untrusted data enters at three places: message bodies and attachments from any sender, invite titles and descriptions from any organiser, and fetched pages. Outbound channels: <code>send_mail</code>, <code>create_invite</code> (an invite is a message to its attendees), <code>fetch_url</code> (the query string is a payload), image loads in the panel (no click needed) and links the user clicks.</p>
<p><strong>2. Capability table, today.</strong> One loop with every tool makes every session [A][B][C]. Scored per session type the product actually has:</p>

<p>The point the original design misses: B implies A here. The private data is mail, and mail is written by outsiders, so "only process trusted input" is not a leg this product can drop.</p>
<p><strong>3. Architecture change, one leg per session.</strong> The orchestrator picks the session type from the user's action in the panel, before the model sees any mail, and mints a token and a tool list for that type.</p>
<ul>
<li>Triage, [AB]: read-only token, no outbound tool, and the panel renders text only: no images, links shown as plain text with the host visible.</li>
<li>Reply, [AB] with a human on C: the session reads the one thread the user opened, with no <code>search_mail</code>, so what it can leak is what the thread's participants already have. It writes a draft; the user presses send in the mail client.</li>
<li>Schedule, [ABC] under supervision: plan-then-execute. Attendees come from the thread's From and Cc headers or from names the user typed, checked in code; the model fills only the title, time and a short body. Internal-only invites go out without a prompt; any external attendee requires a confirmation that shows the attendee list and the body.</li>
<li>Research, [AC]: a fresh context with no mailbox scope. What it hands back is shown to the user, who copies what they want; it is never injected as free text into a session that holds B.</li>
</ul>

<p><strong>5. A test per control.</strong> Construction controls get deterministic tests in CI: a triage session that asks for <code>send_mail</code> is refused by the orchestrator, not by the model; a call to the send endpoint with the triage token returns 403; a headless render of output containing a markdown image on an outside host makes zero requests; <code>fetch_url</code> with a URL that is not in the user's message is refused; <code>create_invite</code> with an attendee not in the headers is refused. None of these results depends on the model. Rate controls get an injection suite run against the deployed configuration, reporting attack success per session type. Its size is a choice: to claim a success rate under 5 percent at 95 percent confidence with zero successes observed, you need 0.95<sup>n</sup> ≤ 0.05, so n ≥ ln 0.05 / ln 0.95 = 58.4, which is 59 cases per session type; a 1 percent bound needs 299. Either is reasonable for a regression gate. Neither is a security claim: Nasr et al. took 12 published defences from near-zero reported rates to above 90 percent for most of them with adaptive attacks. The rate goes in the document as "measured on this suite", with the suite named.</p>
<p><strong>The decision with two defensible answers: scheduling.</strong> Option one, confirm every invite. At 2 invites per user per day for 3,000 users that is 6,000 prompts a day, and the product lead's blocker. Option two, the design above: code-checked recipients and a confirmation only when an attendee is external, 30 percent of invites, or about 1,800 prompts a day. Its cost is a residual risk that survives perfect recipient checks: the model writes the invite body, so an injected email can make the assistant send a convincing phishing invite to colleagues. The CaMeL paper puts this class, text-to-text attacks with no data-flow consequence, outside what provenance checks stop. A third option, a dual-LLM or CaMeL-style interpreter, would constrain parameters too, but the paper's median overhead is about 2.8 times the tokens and the interpreter is more than two engineers can build and test in three weeks. I take option two now and defer the interpreter.</p>
<p><strong>The constraint conflict.</strong> Autonomy against safety, under a deadline: every leg removed costs a feature someone asked for (search inside a reply, auto-scheduling with partners), and every confirmation added costs the adoption that justifies the project.</p>
<p><strong>Failure modes of this design.</strong> Confirmations get clicked without reading; Meta's own caveat about the Rule of Two is a user who blindly confirms a warning, and CaMeL names approval fatigue. The reply session leaks nothing new to the thread's participants, which is the point, but if the attacker is a participant, any secret a colleague pasted into that thread is in reach. And the session type is chosen from the panel action, so a later feature that adds a tool to an existing type quietly restores the third leg; the tool-list test must fail on any change to a list, not only on <code>send_mail</code>.</p>
<p><strong>What goes in the signed document.</strong> The diagram, the capability table before and after, the control table with labels, the test list with links to CI, the injection suite's name and its measured rates per session type, and three accepted risks with owners: phishing text in internal invites (product owner), unread confirmations for external invites (product owner), adaptive attacks against the rate controls (security). Rollback triggers: any confirmed exfiltration through a channel the document says is closed; any construction test failing in CI blocks the release; an attack success rate above the stated bound for a session type disables auto-scheduling for that type.</p>
<p><strong>What you give up.</strong> Search inside replies, auto-scheduling with external attendees without a prompt, images in the panel, and fetching links found in mail.</p>

## Follow-ups

- *Pushback: the construction tests and the injection suite together cost more than the scheduling feature this quarter. Which half do you cut, and what risk do you accept in writing?* Keep every construction test, since they are cheap and they back the claims in the document; cut the suite to the schedule session and write down that triage and reply rates are unmeasured.
- *Reversal: what would you need to see to let the schedule session invite external attendees without a confirmation?* A parameter-level control, such as a quarantined model that can only return a time and a title in a fixed schema, plus a quarter of production traces where no invite body carries content from outside its thread.
- *Two staff engineers disagree: one wants research merged back into reply because users paste links into threads, the other refuses. How do you decide without deciding by rank?* Count how often pilot users fetch a link from inside a reply, and price the merge as a session with all three legs and a confirmation on every send; let that cost meet the usage number.
- *The vendor retires the model in sixty days and the replacement raises attack success on the schedule suite from 2 of 59 to 9 of 59. Do you ship it, and who signs?* The construction controls do not change with the model, so ship with every invite back on confirmation, and have security sign the new rate as a dated exception.

## Common mistakes

- Treating `send_mail` as the only outbound channel and missing images in the panel, query strings in fetch, and invites.
- Choosing "untrusted input" as the leg to drop, when the sensitive data is itself written by outsiders.
- Counting the classifier or the system prompt as a boundary in the control table.
- Testing a rate control by asserting that one attack fails, then reporting the pass as proof.
- Restricting recipients and believing that also restricts what the body says.
