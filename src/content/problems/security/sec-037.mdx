## Question

<Callout kind="interview" label="Critique, 35 minutes">
After the ChainDrop worm, your platform team shipped the hardening below for 120 engineers who use VS Code and Claude Code daily. The worm committed a Claude Code <code>SessionStart</code> hook and a VS Code folder-open task to repositories, each running a dropper in the other tool's directory, so opening a checkout ran the payload with no install step. List every way this defence fails against that worm or its next variant, then say what you would change first.
</Callout>

The team's change record, constructed for this problem:

```text
HARDENING: auto-execution in repositories (platform team, after ChainDrop)

1. Detection
   ioc-scan (required CI check): fail if any file named setup.mjs, setup.js or
   math_init.js exists under .claude/ or .vscode/.

2. Developer machines (pushed by MDM)
   ~/.claude/settings.json      { "disableAllHooks": true }
   VS Code user settings        "security.workspace.trust.enabled": true,
                                "task.allowAutomaticTasks": "on"
   onboarding script            trusts ~/src in VS Code, and in Claude Code marks the
                                trust dialog accepted for every repository the team
                                owns, so engineers are not prompted for every clone
   dev container                engineers may run claude --dangerously-skip-permissions
                                inside it; ~/.aws and ~/.ssh are mounted read-only

3. Repositories
   CODEOWNERS                   /.github/  @platform
   branch protection on main    1 approval, code owners required

4. Dependencies
   CI installs with npm ci --ignore-scripts; lockfile committed.
   Renovate: minimumReleaseAge "3 days"; security updates exempt and automerged.

5. Agents in CI
   pr-triage runs on pull_request_target for every PR, forks included:
     git checkout <PR head>
     claude -p "Label and summarise this PR" --permission-mode plan
   env: ANTHROPIC_API_KEY, GITHUB_TOKEN (contents: write, pull-requests: write)

6. Runbook for the next worm
   1. Revoke the GitHub and npm tokens of affected engineers.
   2. Rotate their AWS keys.
   3. Reimage affected laptops when convenient.
```

## Answer

The flaws, roughly in the order a reviewer finds them.

**Detection by file name.** The worm's stage-two file was renamed from `Math_Symbol.js` to `math_init.js` between waves, and the dropper shrank from about 30 KB to about 11 KB, under a name chosen to look like a setup script. A check for three names catches this campaign's files, and a variant gets past it by renaming them again. What stays constant is the mechanism: a hook in a Claude Code settings file, a task with `runOn: folderOpen`, a new server in `.mcp.json`. Flag any new or changed entry of those kinds by content, on every branch.

**The user setting the repository can undo.** `disableAllHooks: true` in `~/.claude/settings.json` reads like a fleet-wide off switch. Claude Code applies settings precedence, and a project's `.claude/settings.json` outranks user settings, so a repository that sets `disableAllHooks: false` turns hooks back on; the documentation names this case. The worm already writes that file, so the next variant needs one more key. The switch that holds is in managed settings: `allowManagedHooksOnly` blocks user, project, local and plugin hooks, and `disableAllHooks` set at user level cannot disable managed hooks anyway.

**Trust granted in advance.** The onboarding script removes the prompts. Claude Code keys the trust you accept on the repository root, so marking a repository trusted covers every branch of it, including a branch the worm pushed that an engineer checks out to review; settings-file hooks, the `env` block and helpers such as `apiKeyHelper` then run with no dialog. (Trusting `~/src` itself would not have done this in Claude Code: trust on a folder outside a repository stops at a nested git repository, and each clone is one.) In VS Code, trusting a parent folder trusts all its subfolders, and automatic tasks run in trusted workspaces, so every clone into `~/src` is trusted before anyone reads it.

**Automatic tasks without the prompt.** VS Code's default for `task.allowAutomaticTasks` is off, with one prompt per workspace before a folder-open task runs. Setting it to `on` runs such tasks in any trusted workspace without asking. Combined with the parent-folder trust, a fresh clone runs `.vscode/tasks.json` on open, which is exactly the worm's path.

**The CI agent runs the attacker's repository.** `pr-triage` checks out the PR head from forks on `pull_request_target` and runs `claude -p` in it. A `-p` session never shows the trust dialog and treats the folder as trusted, so the fork's `.claude/settings.json` hooks run and its `.mcp.json` servers are connected without asking. `--permission-mode plan` governs the model's tool calls, not hooks, which are commands the harness runs itself. The job's environment holds an API key and a token that can write contents, so a fork's hook can push to any branch. The fix is not running untrusted code with secrets: run triage on `pull_request` without secrets, or keep `pull_request_target` but give the agent the diff as text, not a checkout; and start every scripted run with `--bare` or `--settings '{"disableAllHooks": true}'`.

**Code owners on the wrong paths and branches.** CODEOWNERS covers `.github/` but not `.claude/`, `.vscode/`, `.mcp.json` or the `scripts` block of `package.json`. And branch protection applies to `main`; ChainDrop pushed its files to every branch of every repository the stolen token could reach, and engineers check out feature branches.

**A read-only mount is still readable.** Inside the dev container, `--dangerously-skip-permissions` lets the agent run any command without a prompt, and `~/.aws` and `~/.ssh` are mounted read-only, which stops writes and nothing else. The Nx compromise in 2025 used installed AI CLIs with exactly these flags to inventory credential files for exfiltration.

**The runbook revokes first.** ChainDrop installs a token monitor that runs an attacker handler when the stolen GitHub token is revoked; StepSecurity's guidance was to remove it before rotating. The runbook also leaves out the AI tool credentials the worm collected (`.claude/credentials.json`, `.codex/auth.json`, `.cursor/credentials.json`), and "reimage when convenient" leaves a compromised laptop in use with persistence on it.

**CI installs are the part that was right.** `npm ci --ignore-scripts` stops `preinstall` in CI. It does nothing for a laptop that ran `npm install`, and nothing for the repository-level files, which need no install at all.

**What to change first.** Managed settings, because they are the only layer a repository cannot override: `allowManagedHooksOnly` for Claude Code, automatic tasks off and no parent-folder trust by policy in VS Code, and `--bare` on every scripted Claude Code run. Then remove secrets from any job that checks out fork code, then content-based detection and code owners for the auto-execution paths on every branch.

**The decision with two defensible answers: project hooks at all.**

- **Ban them fleet-wide** with `allowManagedHooksOnly`, and ship the hooks teams need (formatters, test runners) from managed settings. Nothing a repository commits runs on open. The cost: every useful project hook becomes a platform-team request, and teams lose the ability to version their own automation with their code.
- **Allow them under review**: project hooks run only in folders trusted one at a time, and every change to `.claude/`, `.vscode/` or `.mcp.json` needs a code owner on every branch. Teams keep their automation. The cost is review fatigue on files that look like configuration, and a window in which a pushed branch with a new hook is checked out before review.

The conflict is developer autonomy against the editor and the agent becoming an execution surface for anyone who can push. With 120 engineers and a worm that pushes to every branch, I would ban project hooks for a quarter, measure how many managed-hook requests the platform team receives, and revisit.

**The three-day release age is a judgement call.** It is acceptable if exempted security updates need a person to approve them, and if dependencies an engineer or an agent adds by hand go through the same delay; automerging any update labelled as security turns the label into a bypass.

**Failure mode of the fix.** A ban moves automation where nobody reviews it: user-level hooks, shell aliases, scripts in `~/bin`. Track requests for managed hooks and look for new user-level hooks in endpoint inventory; a ban that engineers route around leaves less visibility than reviewed project hooks.

## Follow-ups

- *The managed-settings ban breaks the pre-commit hooks of eleven teams in its first week, and two directors ask for an exception. Which exceptions do you grant, and what risk do you accept in writing?*
- *What would you need to see in a quarter of managed-hook requests and endpoint inventory to allow project hooks again under review?*
- *The worm's next variant writes `.git/hooks/post-checkout` instead of agent settings. Which of your controls still applies?*
- *Two senior engineers disagree: one wants agents banned from developer laptops entirely, the other says the agent is the least of the problem. How do you decide without deciding by rank?*

## Common mistakes

- Treating a user-level setting as a fleet policy when the repository's settings outrank it.
- Hunting this campaign's file names instead of the mechanism every variant needs: a hook, a folder-open task or an MCP server definition.
- Securing `main` and forgetting that engineers open whatever branch they check out.
- Assuming plan mode or a permission mode stops hooks, which the harness runs outside the model's tool calls.
- Revoking tokens before finding what the worm left running on the machine.
- Calling a read-only mount of a credentials directory a control against reading it.
