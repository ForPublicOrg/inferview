## Question

<Callout kind="interview" label="Design review">
"This is the readiness doc for our first public MCP server. Two reviewers signed it off last week and launch is in three weeks. Review it: what is wrong, how bad is each problem, and what blocks the launch?"
</Callout>

The document below is constructed for this problem, not taken from a real company. Read it once as a reviewer would, list the flaws and rank them, and set the access-token lifetime you would accept for this server, with a reason. Then open the checklist.

### Ledgerline MCP server: production readiness

**Purpose.** Let customers' agents work with their Ledgerline invoicing data: search invoices, draft and submit invoices, approve payments, and export the ledger. Protocol revision 2026-07-28 over Streamable HTTP at `https://mcp.ledgerline.example/mcp`. About 1,200 customer organisations share one deployment.

**Authorisation.** Clients discover us through `/.well-known/oauth-protected-resource/mcp`. The document lists two authorisation servers: our login service, `https://login.ledgerline.example`, and `https://idp.partner.example`, so that users of our largest reseller can sign in with their existing accounts. `scopes_supported` lists all nine of our scopes (`invoices:read`, `invoices:write`, `payments:read`, `payments:approve`, `ledger:export`, `admin:users`, `admin:billing`, `webhooks:manage`, `offline_access`). An unauthenticated request gets `401` with `resource_metadata` and no `scope`, so clients ask for everything once and users see one consent screen.

**Token validation.** We validate JWTs locally: the signature against each issuer's key set (cached for an hour), and `exp`. Any token from our login service works, so the access token the web app already holds is reused by our own desktop agent with no second sign-in. Access tokens live 24 hours to keep agents from prompting users during long jobs. Every authorisation failure, including a missing scope, returns `401` so the client re-authenticates and picks up the right scopes.

**Tenancy.** Search tools take an `org` argument, which clients fill in from the user's workspace settings; we check that the org exists before querying. For partner users, the org comes from the partner token's `org` claim.

**State.** The protocol no longer has sessions, so multi-step drafting uses a handle. `create_draft` returns `draft_id`, the base64 of `<tenant_id>:<sequence>`. `add_line`, `set_customer` and `submit_draft` take the `draft_id`, decode the tenant from it and operate on that draft. Only the agent that created a draft knows its id, so the id itself is the access check.

**Downstream calls.** `approve_payment` calls the internal Payments API. We forward the caller's `Authorization` header unchanged, so Payments applies its own per-user rules and its audit log shows the real user.

**Tools.** Tool names, descriptions and schemas are loaded at startup from the `tool-descriptions` repository, which the solutions team edits to tune agent behaviour; a watcher reloads them within a minute and we emit `notifications/tools/list_changed`. `tools/list` results carry `cacheScope: "public"` and `ttlMs: 3600000` so our CDN can absorb list traffic. Enterprise tenants also see `export_ledger`.

**Operations.** Request logs keep full headers and tool arguments for 30 days to debug agent behaviour. Rate limit: 600 requests a minute per IP address.

## Answer

Rank by what one attacker with one token, or one guessed value, can do across tenants.

**1. Any Ledgerline token is accepted (blocker).** The server checks signature and expiry, never `aud`. The spec requires the server to validate that the token was issued for it as the audience and to reject anything else. Here, a token issued to the web app, or to any internal API that trusts the same login service, opens every MCP tool, and a token leaked from any of those systems is an MCP credential. The "no second sign-in" convenience is the bug described as a feature.

**2. The caller's token is forwarded to Payments (blocker).** This is token passthrough, which the spec forbids by name. It works today only because Payments also skips its audience check, so the two flaws hold each other up: fix the first alone and `approve_payment` breaks; fix neither and a token stolen from anywhere approves payments, with Payments' audit log showing a request that looks legitimate.

**3. The draft handle is the access check, and the tenant (blocker).** `base64(tenant_id:sequence)` is not a secret: decode one of your own and you know the format of every other tenant's. Because the tenant is read from the handle, not the token, a caller in tenant A who sends tenant B's handle edits B's draft. The spec says possession of a state handle must not be treated as authentication, and suggests keying state as `<user_id>:<handle>` with the user from the verified token. Fix: random handles from a secure generator, stored with the owner and tenant from the token, and a lookup that returns not-found for any other principal.

**4. The tenant for search comes from an argument.** "We check that the org exists" checks the wrong thing. The tenant must come from the verified token; the argument at most selects among orgs that token is entitled to.

**5. The partner's authorisation server is trusted for every tenant.** Listing a second issuer in `authorization_servers` is allowed. Taking `org` from that issuer's tokens without restricting which orgs it may name lets the partner, or anyone who compromises its IdP, mint a token for any of the 1,200 tenants. Map each issuer to the tenants it may assert, and reject the rest; better, federate the partner's sign-in into the Ledgerline login service so there is one issuer.

**6. Scopes: everything up front, and the wrong status.** Publishing all nine scopes and challenging without `scope` means every agent token carries `payments:approve`, `admin:users` and `ledger:export`. The spec lists exactly this as a common mistake, and says servers should not list `offline_access` at all, since refresh tokens are not a resource requirement. Start with `invoices:read` and `invoices:write`, and answer the first `approve_payment` or `export_ledger` call with `403`, `error="insufficient_scope"`, the needed scopes and `resource_metadata`, in one challenge. The "401 for everything" rule breaks this: a client that gets 401 for a valid token assumes the token is bad, not that it needs more scope.

**7. Tool descriptions change live, without review.** A description is model input. Invariant Labs showed that hidden text in a description can make the agent read local files and that a server can change descriptions after the user approved them. Here the server operator is the rug-pull risk: one edit in `tool-descriptions` changes the behaviour of every connected agent within a minute. Descriptions should ship only with reviewed releases, in a deterministic order, with a published hash so clients can pin them.

**8. A per-tenant catalogue marked public.** Enterprise tenants see `export_ledger`; with `cacheScope: "public"` and a one-hour `ttlMs`, the CDN can serve one tenant's catalogue to another. Mark tenant-dependent lists `private`, or make the catalogue identical for everyone and enforce entitlements at call time.

**9. Logs hold credentials and customer data.** Thirty days of full `Authorization` headers is a store of live tokens, the theft path the spec's security considerations name. Redact the header, log the token's `jti`, `sub` and tenant, and log tool arguments by field, with amounts and names hashed or dropped.

**10. Rate limits per IP address.** Agents run in a few cloud regions, so one IP is many tenants, and one tenant can spread across many IPs. Limit per tenant and per user from the token.

### The judgement call: local validation and token lifetime

Validating JWTs locally with a key set cached for an hour is acceptable if access tokens are short-lived, because revocation then takes effect within one token lifetime without a call to the login service on every request. At 24 hours it is not acceptable: a user removed from a tenant keeps a working agent token for up to a day. The lifetime you were asked to set: 5 to 15 minutes is defensible for a server that can approve payments; refresh traffic rises in proportion (one refresh per active agent every 5 to 15 minutes), which is cheap next to a day of revocation lag. One minute is defensible only if the login service is sized for that refresh rate. Long jobs are a refresh-token problem, not an access-token one.

### The decision: how Payments is called once passthrough is gone

Two answers are defensible, and the launch date decides between them.

- **Token exchange.** The MCP server sends the caller's token as `subject_token` to the login service's token endpoint with `resource` set to Payments, and gets a short-lived Payments token for the same user (RFC 8693). Payments keeps its per-user rules and its audit log stays truthful. Cost: the login service must support token exchange, Payments must start validating audience, and every `approve_payment` adds a token request unless the exchanged token is cached per user until it expires.
- **A service credential.** The MCP server gets its own token for Payments and enforces the user's and tenant's permissions itself before each call, passing the verified user id for the audit log. Cost: the MCP server becomes a deputy holding payment authority for all 1,200 tenants, Payments' per-user rules no longer protect anything, and a compromise of the MCP server is a compromise of every tenant's payments.

I would use token exchange if the login service supports it within the three weeks, and otherwise launch with `approve_payment` disabled rather than ship the service credential, because the credential's blast radius is every tenant. The risk written down: agents cannot approve payments at launch, which the product owner signs. The failure mode of token exchange: caching exchanged tokens per user to save latency brings back revocation lag, and a cache keyed by user alone, not by user and tenant, would hand one tenant's Payments token to a request from another tenant of the same user.

Blocks the launch: 1, 2, 3, 4 and 5. Fix before general availability: 6 to 10.

## Follow-ups

- *Pushback: the login team says token exchange is a quarter away, and sales has promised payment approval at launch. Which do you cut, and what do you put in writing?*
- *Reversal: what would you need to see in a month of production logs to move `payments:approve` from step-up to the initial scope set?*
- *Two senior engineers disagree: one wants per-user draft handles, the other wants drafts shared across a tenant so a colleague can finish one. How do you decide without deciding by rank?*
- *The partner refuses to federate and insists its IdP stays in `authorization_servers`. What exactly do you check on each of its tokens, and what does that cost you each time a reseller customer is added?*

## Common mistakes

- Reading "signature and expiry checked" as token validation and moving on.
- Praising the forwarded header because Payments sees the real user.
- Treating an unguessable handle as the fix; a random handle still needs an owner check against the verified token.
- Flagging the second authorisation server as forbidden; listing several is allowed, trusting each for every tenant is the flaw.
- Proposing to redact logs while leaving 24-hour tokens, so the next leak is still a day long.
