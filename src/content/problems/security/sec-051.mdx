## Question

<Callout kind="interview" label="The prompt">
"Our risk committee adopted the NIST AI RMF and wants to see it in how we ship. Here is our release process for the reply-drafting assistant. Map the four functions onto it, name the artefact each one leaves behind, and tell me where the mapping breaks. Then give me the rule for turning the feature off."
</Callout>

The release process (scenario):

- The assistant drafts replies for 300 support agents, about 40 drafts per agent per day. Agents edit or discard drafts before sending.
- A change is one of: a prompt edit (about weekly), a model version change by the vendor (a few times a year), a new retrieval source (rare).
- Every change goes through a pull request, an offline eval in CI on a golden set, a canary to 5 percent of agents for a day, then full rollout. One on-call rotation covers the service.
- Over the last eight weeks, 20 percent of drafts were heavily edited (more than half the text changed) before sending.

Choose the trigger that disables the assistant, with its threshold and the volume of data it needs, and defend both.

## Answer

<Depth>
<Fragment slot="short">
<p>Govern is not a release stage; it is the inventory entry, the named owner and the vendor policy that every release reads, and the inventory entry should be updated by the pipeline when the model version changes. Map is the design document's context section and risk list, revisited when a retrieval source is added. Measure is the CI eval report and the security tests per change, plus a check that the golden set still predicts production. Manage is the release decision record, the kill switch with a written trigger and owner, and the monitoring plan. The mapping breaks because the RMF says the functions can run in any order and are not a checklist: the canary is Measure and Manage at once, and production monitoring feeds Map. My trigger: disable on any confirmed draft containing another customer's data, and roll back when the heavy-edit rate on the canary exceeds 25 percent over a day, which one canary day can detect if each canary agent is compared with that agent's own baseline.</p>
</Fragment>

<p><strong>Where the mapping breaks.</strong> The Core says its actions are not a checklist or an ordered set of steps. Forcing Govern, Map, Measure and Manage into four sequential gates adds a meeting per function to a weekly train. The canary measures and decides in the same step. Production monitoring is Measure, but what it finds (agents pasting order data into prompts, say) is new context for Map. And Measure 4, measuring whether the measurements work, has no home in a release process at all, which is why the golden set drifts away from production unnoticed.</p>
<p><strong>The trigger, with the arithmetic.</strong> Two triggers, because the two harms differ.</p>
<ul>
<li>Any confirmed draft containing another customer's data disables the assistant for everyone, with no threshold. One instance is an incident.</li>
<li>Quality: roll back when the heavy-edit rate on the canary exceeds 25 percent for a day, against the eight-week baseline of 20 percent. The canary sees 5 percent of 300 agents × 40 drafts = 600 drafts a day. Treating the baseline as known, the standard error at 20 percent is √(0.2 × 0.8 / 600) = 0.016, so a 5-point rise is about 3 standard errors: one canary day is enough. At full rollout, 12,000 drafts a day give a standard error of 0.0037, so the same rise is about 14 standard errors and shows within the first few hours of a working day.</li>
</ul>
<p>This treats the 600 drafts as independent. They come from 15 agents, and how heavily an agent edits is partly a habit of that agent, so drafts from one agent are correlated and the pooled canary rate can move 5 points because of which 15 agents were picked. The canary therefore compares each canary agent's rate with that agent's own eight-week rate, a paired comparison that removes the between-agent spread; if the paired differences are still noisy at 15 agents, the canary needs more agents, not more days.</p>
<p>A 3-point threshold would be defensible too, at a cost in canary time: for 3 points to be 3 standard errors the standard error must be 0.01, which needs 0.16 / 0.01² = 1,600 drafts, nearly three canary days per change. A 2-point threshold needs 0.16 / 0.0067² ≈ 3,600 drafts, six days, and the weekly train would never leave the canary. Neither the 20 percent baseline nor the threshold is a NIST number; both are ours and go in the monitoring plan.</p>
<p><strong>The constraint conflict.</strong> The committee wants a human decision per release; the prompt ships weekly. I would have the committee sign the change classes and their gates once, and have the pipeline record each release against those gates, with a human review only for model version changes and new retrieval sources.</p>
<p><strong>Failure mode of this answer.</strong> The inventory entry and the trigger both rest on things that move: the vendor can ship a new model behind an alias, and the edit-rate baseline shifts when agents change how they work. If the gateway does not pin the version and write it into the inventory, Govern documents a model that is no longer running; if nobody re-baselines the edit rate, the trigger either fires on noise or never fires.</p>

## Follow-ups

- *The vendor moves the model behind your alias and the heavy-edit rate goes from 20 to 23 percent across the whole fleet. Your trigger does not fire. What do you do, and which function owns the response?*
- *An auditor asks for evidence that Govern happened last quarter. What do you show that was not created for the auditor?*
- *Support leadership says a kill switch that turns the assistant off for everyone punishes 300 agents for one bad draft. What would let you scope it narrower, and what does that cost?*

## Common mistakes

- Turning the four functions into four sequential approval gates on every change.
- Citing the Cyber AI Profile as final guidance.
- Naming "governance" as the artefact for Govern, instead of an inventory entry, an owner and a policy a release can be checked against.
- Choosing a trigger threshold without working out how many drafts the canary needs to see it.
