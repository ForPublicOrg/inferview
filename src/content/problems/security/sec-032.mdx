## Question

<Callout kind="interview" label="Design review, 30 minutes">
The platform team wants this merged before the quarterly audit. Read the note and the config, list every problem you would raise in review, then say what you would approve instead and what it gives up.
</Callout>

The company and its numbers are a scenario. A B2B assistant answers employees' questions over their companies' documents, through a Google Drive connector that fetches with each user's own permissions. Tenants bring their own model provider keys. A third of the tenants are in the EU and have data-residency commitments in their contracts.

> **Telemetry for audit, v1.** Every model call is traced with full prompts, outputs, tool arguments and tool results, in every environment, so any answer can be audited and any bug reproduced. A Presidio-based scrubber removes personal data before export, so the traces contain no personal data and the GDPR does not apply to them. Our tracing helper wraps the model client and records the call's full keyword arguments, so a trace can be replayed exactly. Staging is refreshed weekly from a production snapshot, so staging traces look like production. Traces are kept 400 days to cover the annual audit cycle. All engineers can read traces (SSO group `eng-all`), so on-call never waits for access. The trace viewer renders message content as Markdown for readability. This also meets the EU AI Act, which requires logging of inputs and outputs. Deletion requests are handled as today: we delete the user's row and their conversations.

```yaml
# observability/otel.yaml, applied to dev, staging and prod
env:
  OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT: "true"
  OTEL_TRACES_SAMPLER: always_on
processors:
  pii_scrubber:
    engine: presidio
    entities: [EMAIL_ADDRESS, PHONE_NUMBER, CREDIT_CARD, IBAN_CODE]
exporters:
  otlphttp:
    endpoint: https://otlp.us1.observability-vendor.example
retention_days: 400
```

## Answer

The note confuses two things: an **audit record** (who asked, in which tenant, which model and prompt version answered, which tools ran with what effect, who approved) and a **content archive** (the text of everything). Audits need the first for a long time. Debugging needs the second, briefly and for a few people. The design builds the second, keeps it like the first, and copies it everywhere.

The problems a first read catches:

- **Content capture is on by default, everywhere.** The OpenTelemetry GenAI conventions call instructions, messages and outputs sensitive and say instrumentations should not capture them without an explicit opt-in; the instrumentation's own default is off, and this config turns it on in dev, staging and prod alike.
- **"No personal data, so GDPR does not apply."** Presidio states it gives no guarantee of finding all sensitive information, and the config asks for four entity types. Names, health details, salaries and addresses in free text pass through. A probabilistic detector can reduce what leaks; it cannot carry a claim that nothing does.
- **400 days of content.** Storage limitation and data minimisation ask for the least data for the shortest time the purpose needs. The audit cycle justifies keeping the audit record for 400 days, not the text.
- **Residency.** The exporter points at the vendor's US region, while a third of tenants have EU commitments. Telemetry is usually the first copy of customer data outside the promised region, and the model provider's residency setting does nothing for it.

The problems a senior reviewer tends to miss on first read:

- **The kwargs include the tenants' provider keys.** Tenants bring their own keys, so the client is called with `api_key=...`, and the helper records the full keyword arguments. Braintrust's LiteLLM instrumentation did exactly this from 0.2.0 to 0.27.x, and its fix does not remove keys already in traces.
- **Traces flatten document permissions.** The Drive connector fetched each document with one user's permissions; the tool result now sits in a trace that every engineer can read. The trace store has become the most permissive copy of every customer's documents.
- **Staging gets production content.** A weekly snapshot plus capture-on means staging traces hold customer data under staging's access rules.
- **The trace viewer renders model output.** Model output that carries an injected Markdown image fires its request inside an engineer's browser when they open the trace, with an engineer's session nearby. The viewer is an output sink like any other.
- **Erasure stops at the database.** Deleting the user's row and conversations leaves their content in the vendor backend and in staging for 400 days, and nothing indexes spans by user, so a request under Article 17 cannot be honoured.
- **The AI Act claim.** Article 12 asks high-risk systems to allow automatic recording of events relevant to risk and monitoring; it names input data only for the biometric identification case. It does not require full inputs and outputs, and this system may not be high-risk at all.

**What I would approve.**

1. An audit record on every call, kept for the audit cycle: tenant, user, time, model and version, prompt template id and hash, tool names with redacted arguments and their effects, approval ids, token counts and outcome. No message content, no keyword arguments, an allowlist of recorded fields rather than a dump with a blocklist.
2. Content capture off by default. In production, an opt-in per tenant (some tenants will want it for their own review) and a sampled debug mode turned on per incident, writing content to a separate store in the tenant's region, with spans holding references only, access for named on-call roles with every read logged, and retention of 14 to 30 days. The range is a choice: long enough to debug a report that arrives a week late, short enough that the store is not an archive.
3. Development and staging on synthetic data only, and no production snapshots.
4. A trace viewer that shows content as escaped text.
5. Erasure that reaches the content store by user and tenant index, and expires it anyway.

**What it gives up.** Reproducing an answer from three months ago becomes impossible unless the tenant opted in. On-call loses instant access and waits for a role grant, which is minutes during an incident and a real cost at 3 a.m. Some bugs that only reproduce on real data will now take longer to find.

**Where the replacement fails.** The audit record's "redacted arguments" still carry whatever the redaction misses: a tool argument such as a search query is free text written by a user, and it lands in the long-lived record. The record needs its own field allowlist per tool, and review when a tool is added, or the 400-day store quietly becomes the content archive again.

## Follow-ups

- *An enterprise tenant's security team demands full transcripts for 7 years in their own bucket. Does that change your design or just add an export?*
- *The audit is in three weeks and the replacement takes six. What do you ship first, and what do you write down about the gap?*
- *What would you need to see in incident reviews to shorten content retention from 30 days to 7?*

## Common mistakes

- Treating redaction as the control that makes full capture safe.
- Fixing retention and residency and missing the credentials in the keyword arguments.
- Approving all-engineer access because traces are "internal".
- Rendering model output in internal tools with less care than in the product.
