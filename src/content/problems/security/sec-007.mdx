## Question

<Callout kind="interview" label="Identity round">
Dana asks the company's expense agent to file her conference receipts and reimburse her. The agent calls the expense MCP server over HTTP with an access token Dana granted it, and the expense server then calls the ledger API to post the reimbursement. Security has signed off on three properties: the ledger refuses anything Dana could not do herself; an investigator can tell from the ledger's own log which calls an agent made and through which service; and a token lifted from the expense server's memory is useless anywhere except the ledger. What should the expense server present to the ledger?
</Callout>

The ledger is an OAuth resource server behind the same corporate authorization server as the expense server. The authorization server supports token exchange.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the ledger team which claims their authorization code reads today, and which claims their log writes for each request.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask security whose identity they expect to see in the ledger's log line when an agent posts a payment for Dana.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the audience value in the token Dana's agent sends to the expense server, and compare it with what the ledger checks.</p></details>

## Answer

Token exchange with delegation semantics. The expense server sends the authorization server Dana's token as `subject_token`, its own credential as `actor_token`, and the ledger as `audience` or `resource`. The token that comes back carries `sub` for Dana and an `act` claim naming the expense server, and its audience is the ledger only. The ledger checks Dana's rights as before, writes both identities to its log, and a copy of the token stolen from the expense server cannot be replayed at the payroll API.

Why each wrong option is tempting:

- **Passthrough** looks like the cheapest way to keep "the ledger refuses what Dana cannot do", because the ledger already understands Dana's token. The MCP specification forbids it outright: servers must not accept or transit tokens issued for anything other than themselves. Dana's client sent that token with the expense server as its `resource`, so a ledger that validates audience refuses it; a ledger that does not validate audience accepts a token meant for some other service, which is worse.
- **Impersonation** is the option most teams ship, because the ledger needs no change. It fails the audit requirement: RFC 8693 says the impersonating party is treated as the subject, so the ledger's log reads "Dana", and the only record that an agent was involved is in the authorization server.
- **A service account plus a user header** is how many internal platforms worked before token exchange was available. It turns the expense server into a deputy that can claim to be anyone, and the ledger's checks run against a header nobody signed.
- **One wide token** avoids an exchange per hop. RFC 8693 notes that several targets request the Cartesian product of their scopes; that token is exactly what a thief wants.

### The decision behind the pick

Delegation and impersonation are both defensible; the stem's second requirement decides between them.

- **Delegation.** Costs: the ledger has to read `act` and record it, which is a code change in someone else's service; and the authorization server needs a policy for which actors may exchange which subjects' tokens for which audiences (the `may_act` claim is one way to state it). In return the ledger can apply agent-specific rules, such as a lower reimbursement limit when `act` is present.
- **Impersonation.** Costs: attribution moves out of the ledger. An investigator joins the ledger's request to the authorization server's exchange log by token id, and that join breaks the day exchange logs are retained for less time than ledger logs. Pick it when the ledger cannot change before launch, and write the retention dependency into the risk register.

One quantity is yours: the lifetime of the exchanged token. With a lifetime of T minutes and tokens cached per user and audience, the expense server performs at most 60 / T exchanges per active user per hour, and a stolen token is useful for at most T minutes. At T = 5 that is 12 exchanges per user-hour; at T = 60 it is one exchange and an hour of exposure. Anything between 5 and 15 minutes is easy to defend; matching the lifetime of Dana's original token gives back most of what the exchange bought.

The constraint conflict is the deadline against the audit requirement: the ledger change is the slow part, and it is in another team's plan.

### Where the recommended answer fails

The `act` claim only records the hop that asked for the exchange. If Dana's agent runtime calls the expense server, which calls a reconciliation service, which calls the ledger, the ledger sees the reconciliation service as the current actor, and RFC 8693 says the nested actors behind it are informational only. The ledger can log the agent but cannot base a decision on it. And the exchange concentrates risk in the expense server: for the lifetime of the user tokens it holds, a compromised expense server can mint ledger tokens for every user who called it in that window. The authorization server's exchange policy, short subject-token lifetimes and per-actor rate limits on exchange are what bound that, and none of them is free.

## Follow-ups

- *The ledger team says reading `act` is a quarter of work and the launch is in three weeks. Do you ship impersonation, and what exactly do you write down as accepted risk?*
- *What would you need to see in a month of exchange logs to move the exchange from the expense server into the agent runtime, so the agent itself is the actor?*
- *A second agent starts calling the expense server on behalf of the first. Whose identity is in the outermost `act` claim at the ledger, and what can the ledger still enforce about the first agent?*
- *The ledger returns 403 with `insufficient_scope` for reimbursements above a limit. Who completes the step-up, Dana or the agent, and where does the prompt appear so the agent cannot answer it?*

## Common mistakes

- Treating "the token is Dana's" as proof the call is Dana's. A token proves who granted authority, not who used it.
- Validating signature and expiry at the ledger but not audience, which is what makes passthrough work at all.
- Assuming nested `act` claims give a full chain the ledger can enforce on.
- Exchanging once at sign-in for a long-lived downstream token, which turns the exchange into a slower way to issue a wide token.
