## Question

<Callout kind="interview" label="The prompt">
"Two customers sign next month. One contract says their data is processed and stored only in the United States; the other, a German bank's, says only in the EU. An engineer proposes adding `inference_geo: "us"` to every Claude API request and calling it done. What does that setting control, what does the other residency setting control, what do you actually ship, and what do you tell the bank?"
</Callout>

The numbers are a scenario. The product runs on Claude Opus 5.5 through the Claude API, in one workspace, at $60,000 a month in tokens. The US customer is expected to bring 15% of that traffic. Request and response bodies are traced to an observability vendor whose EU region the company chose last year.

Decide how much traffic to pin and defend the number, including what it costs.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the customers' counsel whether "processed" in each contract covers inference only, or also storage, logs and telemetry kept by you and your vendors.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which API keys, batch jobs and eval pipelines send this customer's data today, and from which workspace each key comes.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the current per-request cache hit rate on the shared system prompt before you split anything.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The two settings are independent. <code>inference_geo</code> decides where the model runs for a request; workspace geo decides where Anthropic stores data at rest and runs endpoint processing such as image transcoding and code execution. The engineer's change covers inference only, costs 1.1x on all traffic, and still depends on every caller remembering it. I would pin only the US customer's traffic, through a dedicated workspace whose default and allowed geo are <code>us</code>, which costs about $900 a month. For the bank, neither setting offers an EU option today, so the Claude API cannot meet that clause as written; that is a conversation with the bank and counsel, not a parameter.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Inference geo.</strong> A per-request field on <code>POST /v1/messages</code> with two values: <code>global</code>, the default, where inference may run in any available geography for performance and availability, and <code>us</code>. A workspace can set <code>default_inference_geo</code>, used when a request omits the field, and <code>allowed_inference_geos</code>, which makes a request for any other geo fail. The response's <code>usage.inference_geo</code> reports where the request actually ran. It works on Claude 4.6 and later models; older models return a 400 when the field is present. It applies on the first-party API, Claude Platform on AWS and Anthropic-managed Claude on Google Cloud, not through the OpenAI SDK compatibility endpoint, and on Bedrock and Google-managed Vertex the region comes from the endpoint instead.</p>
<p><strong>Workspace geo.</strong> Chosen when a workspace is created and fixed afterwards. It covers data at rest and endpoint processing. Today the only value is <code>us</code>, so every workspace already stores at rest in the US.</p>
<p><strong>What neither covers.</strong> Everything you hold. The traces of request and response bodies in the observability vendor's EU region are customer data outside the US, whatever the API does. So are your own logs, caches and the vector store. OpenTelemetry's GenAI conventions treat message content as sensitive and opt-in for this reason.</p>
<p><strong>What I ship for the US customer.</strong> A new workspace for US-restricted traffic, with <code>default_inference_geo: "us"</code> and <code>allowed_inference_geos: ["us"]</code>, and API keys from it used for every path that carries this customer's data: online requests, batch jobs, evals on their data. A forgotten parameter then falls back to <code>us</code>, and a request for <code>global</code> fails loudly. The application logs <code>usage.inference_geo</code> per request and alerts on any value other than <code>us</code> for that tenant. Their traces are turned off or written to a US-region store.</p>
<p><strong>What I tell the bank.</strong> As of 2026-10-28 the Claude API offers no EU inference geo and no EU workspace geo. The options are a platform where the region is set by the endpoint, checked for both inference and at-rest location before anything is promised, or a contract that names what is processed where. Saying yes because one setting has the word "geo" in it is how a residency clause gets breached.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Splitting the workspace splits the prompt cache, because caches are isolated per workspace. If the US tenant's cache hit rate falls from most requests to few, which cost dominates, and does it change your answer?</em></li>
<li><em>Sales wants to promise the bank EU residency "by Q2" on the expectation that an EU option ships. What do you put in writing, and who signs it?</em></li>
<li><em>A shared rate limit across geos means a spike from global traffic can throttle the US workspace. What do you monitor, and what do you do when it happens?</em></li>
</ul>

### The number you were asked to choose

| Scope pinned to `us` | Extra cost a month | What it buys |
|---|---|---|
| Only the US customer's traffic, 15% | $60,000 × 0.15 × 0.10 = $900 | Meets the inference half of that contract |
| Everything | $60,000 × 0.10 = $6,000 | Nothing contractual for anyone else, and gives up global routing's availability |
| Nothing, with a promise to add the parameter later | $0 | A breach on the first request |

The 1.1x applies to cache reads and writes too, so the $900 moves only with the US tenant's own spend. The split workspace adds a separate cost: the US tenant's requests no longer read the shared workspace's cache, so its system prompt is written again in the new workspace and read at the cache rate only after that. Pinning everything is reasonable only if you expect most new contracts to carry a US clause and want one code path; it is unreasonable as a way to avoid deciding which traffic belongs to which customer, because that routing is needed anyway for traces and logs.

The conflict is cost and availability against compliance: global routing exists for performance and availability, and every pinned request gives some of that up.

**Where this fails.** The pin is only as good as the key inventory. A nightly eval job that samples production conversations and runs them through the old workspace's key sends this customer's data to global inference with no error, because that workspace allows it. The alert on `usage.inference_geo` catches it only if the job logs usage the way the application does.

## Follow-ups

- *Six months in, Anthropic adds an EU inference geo. What changes in your design for the bank, and what still does not?*
- *Counsel says "processed" includes your vendor's traces. Do you drop content from traces for every tenant, or route by tenant, and what does each cost the on-call engineer debugging a bad answer?*
- *What would you need to see to move the US customer back into the shared workspace?*

## Common mistakes

- Treating `inference_geo` as covering storage, or workspace geo as covering inference.
- Pinning per request in application code with no workspace default or allowed list, so one missed call path breaks the contract silently.
- Forgetting your own traces, logs and caches, which are usually the first copy of the data outside the promised region.
- Promising the EU customer what the API does not offer on the date you sign.
