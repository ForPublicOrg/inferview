## Question

<Callout kind="interview" label="The prompt">
"How would you build a secrets management system for a fast-growing research org where developers move quickly?"
</Callout>

The interviewer adds constraints, which are a scenario:

- The research org went from 150 to 450 people in a year and plans to double again.
- Today, cloud access keys live in ~/.aws/credentials on laptops and in .env files in repositories; API keys for datasets and model providers are pasted into notebooks; CI uses repository secrets; training jobs run for up to five days on a shared cluster.
- Most researchers run coding agents on their laptops, some with approval prompts turned off.
- The head of research says that anything adding a step to launching an experiment will be routed around within a week. An auditor wants evidence of rotation and access review in six months.
- Four security engineers.

Design the system, choose the numbers, and write the rollout plan you would take to the head of research.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for an inventory: which credential types exist, who holds each, and which systems could accept a federated identity instead of a stored key.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how long the longest training job runs and what it does today when a credential stops working halfway.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the head of research which step of launching an experiment people already complain about, and measure how long it takes.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Get stored secrets off laptops and out of agents' reach, ordered by blast radius, without adding a step to launching an experiment. Cloud access moves to short-lived credentials issued from single sign-on for people and from workload identity for jobs and CI, so there is no key to steal from a laptop. Third-party keys that cannot be federated live in a central store and reach the code that uses them through a proxy or a renewal agent, not through a file. Coding agents never get a credential in their environment. Scanning catches what leaks anyway. The cost is a broker on the critical path of every experiment and a migration that touches every tool; the design puts most of the work on the platform team, not on researchers.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Inventory first.</strong> A scan of repositories, CI and a sample of laptops, grouped by credential class: cloud keys, data and model API keys, CI tokens, SSH and signing keys. The order of work follows blast radius times count, and cloud keys usually lead on both.</p>
<p><strong>People.</strong> The CLI that researchers already use gets its credentials from single sign-on, valid for a working day, cached in the OS keychain rather than a plaintext file. The login happens once a day, which replaces a step (finding the key) rather than adding one.</p>
<p><strong>Jobs and CI.</strong> Training jobs get a workload identity from the cluster and exchange it for short-lived cloud credentials; a sidecar renews them. CI moves from repository secrets to OIDC federation, which GitHub documents as a short-lived token valid for a single job and matched against the repository and environment in the cloud's trust policy.</p>
<p><strong>Keys that cannot federate.</strong> Dataset and model provider keys go into a central store with an owner, a scope and an expiry. Where the store can mint them dynamically, they carry a lease that must be renewed and can be revoked immediately or by prefix after an intrusion, which is how Vault documents leases. Where the provider only offers a static key, code gets it through a proxy that injects it on the way out, the pattern Anthropic's deployment guide recommends and Managed Agents implements with placeholders substituted at egress.</p>
<p><strong>Agents.</strong> The Nx compromise in August 2025 is the case to design against. The project's advisory says the postinstall script collected credentials and posted them, encoded, to a repository it created under the victim's own GitHub account; StepSecurity's analysis of the payload found it drove locally installed AI CLIs with their approval prompts disabled to build the inventory of credential files. An agent's session gets no credential in its environment and cannot read the keychain; anything it needs goes through the proxy, scoped to the hosts it needs.</p>
<p><strong>Detection.</strong> Push protection and secret scanning on every repository, alerts on credentials used from unexpected networks, and a revocation runbook that has been rehearsed.</p>
</Fragment>

### The decision with two defensible answers

- **Federate first: short-lived credentials everywhere they can be issued.** A stolen laptop file or an agent's environment holds nothing that works tomorrow. The cost: every tool and job has to learn the new path, multi-day jobs need renewal that works under load, and the broker becomes a dependency of every experiment. With four engineers, the first six months go to cloud access alone.
- **Vault first: move the existing static secrets into a central store with rotation and scanning.** Faster to roll out, works with every tool that reads an environment variable, and gives the auditor rotation evidence quickly. The cost: the same keys still land on laptops and in agents' environments, valid until the next rotation, which is the exposure Nx exploited.

The conflict is research velocity against how long a leaked credential stays useful. I would federate cloud access first, because those keys have the largest blast radius and the federation path exists for them, and put third-party keys in the store with rotation in the meantime. The auditor gets rotation evidence from the store and the federation logs; the head of research gets a launch path that has one login a day instead of a key file.

### The number to choose: credential lifetime for long jobs

The job credential's TTL is a trade between how long a stolen token works and how long the broker can be down before a job loses access. With renewal at half the TTL, a running job tolerates a broker outage of about TTL / 2 before its credential expires. Suppose the broker's target is to recover from any outage within 30 minutes (a scenario figure the platform team would commit to). A TTL of 1 hour then gives a 30-minute buffer, and a five-day job renews 5 × 24 × 2 = 240 times, which is negligible load. A TTL of 15 minutes leaves a 7.5-minute buffer and turns a routine broker restart into failed jobs. A TTL equal to the job length, five days, gives no reason to have a broker at all. I would choose 1 hour; anything from 1 to 4 hours is reasonable depending on the broker's measured recovery time, and the jobs should checkpoint so that a lost credential costs a restart, not five days.

### What you give up

A researcher on a plane without network cannot get new cloud credentials after their day-long session ends. Some dataset clients that sign requests with the key, as AWS SigV4 does, cannot use egress substitution and need a different path; the vaults documentation says so of its own placeholders. The platform team owns a service that, when it fails, stops experiments.

### Where this fails

The broker is now the most valuable target and the most critical dependency in the org. An outage longer than the buffer stops every renewal; a compromise issues credentials for anything. The trust policies that map a job or a workflow to a role are code, and they drift: GitHub's documentation notes that repositories created after 2026-07-15 use a new default subject format, so a trust condition written for the old format silently stops matching new repositories, and the fix people reach for under deadline is a wildcard. Review trust policies like code and test them against a new repository before the change lands.

### Rollout plan and rollback triggers

**Month 1.** Inventory; push protection on every repository; secret scanning with alerts to owners; rehearse revoking a leaked key end to end.

**Months 2 to 3.** Single sign-on credentials for the cloud CLI; workload identity for new training jobs; OIDC for CI, one team at a time. Static cloud keys stop being issued.

**Months 4 to 6.** Remaining jobs migrated; static cloud keys revoked; third-party keys in the store with owners and expiry; egress proxy for keys used by notebooks and agents.

**Rollback triggers,** any one of which pauses the migration for that team:

- Job failures attributed to credential expiry above the team's previous weekly failure rate.
- Median time from code to a running experiment up by more than the team agreed to accept at kickoff.
- Any new static cloud key found by scanning in a migrated team, which means the new path is being routed around.

## Follow-ups

- *A researcher's laptop is stolen on day 40, before their team migrates. Walk through the next hour.*
- *The org adopts a hosted coding agent that runs in the vendor's cloud and needs to push to your repositories. Where does its credential live?*
- *Your auditor asks for proof that a revoked credential cannot be used. What evidence do you produce?*

## Common mistakes

- Buying a vault and moving the same long-lived keys into it, so the keys still reach every laptop and agent.
- Making the secure path slower than the old one, so researchers route around it, as the head of research predicted.
- Choosing a TTL without asking how long jobs run or how long the broker can be down.
- Treating coding agents as the developer, with the developer's credentials in the session's environment.
- Leaving trust policies unreviewed after the first rollout.
