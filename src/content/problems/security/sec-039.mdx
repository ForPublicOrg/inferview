## Question

<Callout kind="interview" label="Design, 40 minutes">
"We ship an agent every week and our only security testing is a red-team run someone does by hand before big launches. Wire security into CI/CD: what runs on every PR, what runs per release, what runs nightly, and what blocks a merge."
</Callout>

The system (scenario):

- A support agent for a billing product. Tools: `lookup_account`, `issue_credit` (the orchestrator caps one call at $500), `update_contact_email`, `search_kb`. Replies render as markdown in the customer's browser.
- Five product engineers and one security engineer at half time. About 20 PRs a week touch prompts, tool definitions, the orchestrator or the renderer. Releases go out every Tuesday.
- The PR pipeline takes 8 minutes today and the engineering director caps it at 12. She also says that a gate which fails at random gets disabled within a month, so nothing probabilistic may block a merge.
- The security engineer wants the injection success rate to block releases. The last manual run with promptfoo produced 400 cases, and 12 succeeded.
- The security eval budget is $1,500 a month in model calls.

Say which suite runs where, what each one blocks, how you set any threshold that depends on a rate, and what you write down for the director and the security engineer to sign.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each control in the agent, ask whether its result changes when the model changes. Which of them could you test with no model at all?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask the security engineer which cases the next run will contain, compared with the last one.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the per-case results of the last run, and ask the director how many Tuesdays a year she would accept losing to a block that turns out to be noise.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Split by what each suite tests, and the cadences follow. Every PR runs deterministic tests of the controls, with a scripted model that emits the forbidden tool call, so the result cannot flake and any failure blocks the merge. Every release runs a frozen battery of known attacks against the release candidate and blocks the release when successes exceed a threshold computed from the baseline: with 12 of 400 last time, block at 19 or more. Nightly runs adaptive attacks that never block anything automatically; the security engineer triages each finding within a day, and a confirmed bypass of a code control blocks the next release by a written decision. Each confirmed finding becomes either a new deterministic test or a new frozen case.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Per PR: test the controls, not the model.</strong> The agent's real boundaries are in the orchestrator: the tool list per session, the $500 cap on <code>issue_credit</code>, the check that <code>update_contact_email</code> only runs for the authenticated account, and a renderer that never loads external images. None of these should depend on what the model says, so their tests replace the model with a script. The script emits <code>issue_credit</code> for an account the session does not own and the test asserts a refusal; it emits a markdown image pointing at an outside host and a headless render asserts zero outbound requests; it emits <code>update_contact_email</code> after a tool result that contains instructions, and the test asserts the call needs the session's verified account. These run in seconds, fit inside the 12 minutes, and a failure means a control is broken, so it blocks the merge. The director's rule holds because nothing here is probabilistic.</p>
<p><strong>Per release: a frozen battery with a computed threshold.</strong> <code>promptfoo redteam run</code> generates cases and saves them to <code>redteam.yaml</code>. If each release regenerates, two releases are measured on different tests and a change in the rate means nothing, so commit the generated file and run the same cases every Tuesday against the release candidate's deployed configuration, alongside the garak probes that match the product (encoding and injection probes, not toxicity). Regenerate quarterly and rebaseline on the old release before switching.</p>
<p>The threshold is a choice, made in front of both signatories. Treat the last result, 12 of 400 or 3 percent, as the true rate. Under a binomial with n = 400 and p = 0.03, the chance of 19 or more successes is 3.5 percent and of 18 or more is 6.0 percent, so blocking at 19 means about one false block every 28 releases. The same rule catches a doubling to 6 percent with probability 0.88 and a rise to 4 percent with probability 0.25. A reasonable range is blocking somewhere from 18 to 20; at 17 the false-block rate is 9.8 percent and below that it passes 10, which earns the gate the treatment the director predicted, and at 21 or above a doubling slips through more than a fifth of the time (23.5 percent at 21). One category has no threshold: any success in a case the design says is impossible, such as a credit to an account the session does not own, is a control bug, so it gets a deterministic test and blocks like one.</p>
<p><strong>Nightly: adaptive attacks that inform, not gate.</strong> Static strings understate risk: Nasr et al. took 12 published defences from near-zero reported success to above 90 percent for most with adaptive search. The nightly job adapts AgentDojo's structure (user tasks plus injection cases in tool results) to this agent's four tools and runs multi-turn strategies from promptfoo or PyRIT (now at github.com/microsoft/PyRIT; the Azure repository was archived on 27 March 2026). It reports per-tool attack success and every transcript where a tool call changed state. Split the $1,500: the release battery's cost is fixed by its size, and the rest is the nightly search budget, which is the knob to turn when money is short.</p>
<p><strong>The decision with two defensible answers: a real-model sample in the merge gate.</strong> Option A adds 50 live injection cases to every PR that touches a prompt, so a regression is caught on the PR that caused it. Its cost, computed: at a 3 percent true rate, blocking at 4 or more of 50 fails 6.3 percent of clean PRs, and across 20 PRs a week the chance of at least one false block is 73 percent, while a doubling to 6 percent is caught only 35 percent of the time. Option B, the design above, keeps the merge gate deterministic and accepts that a prompt change merged on Wednesday shows its effect on the next Tuesday, with a bisect over a week of commits. I take B, and make the bisect cheap: the release job runs the battery against each prompt-touching merge since the last release when the gate fires.</p>
<p><strong>The constraint conflict.</strong> Pipeline latency and gate reliability against detection: every case added to a blocking gate raises either the false-block rate or the runtime, and the release battery is the only place where n is large enough for a rate to mean something.</p>
<p><strong>Failure modes of this design.</strong> The frozen battery goes stale in two ways: a new tool ships and no case targets it, and the vendor's next model is trained against public attack sets, so the battery rate falls while adaptive success does not. Watch the gap between the battery rate and the nightly adaptive rate; a widening gap means the battery is measuring the model's familiarity with promptfoo, not the agent's risk. And a nightly finding on Monday night against a Tuesday release depends on one half-time engineer reading it in time, so the runbook names a deputy.</p>
<p><strong>What goes in writing.</strong> A gate table (suite, trigger, owner, blocks what, threshold and its false-block rate), the rebaseline procedure, and the override rule: a release block can be overridden only by the security engineer and the engineering director together, in a ticket that names the accepted rate and expires at the next release. What you give up: per-PR detection of model-behaviour regressions, and any claim that the release threshold bounds what an adaptive attacker achieves.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The frozen battery stops finding anything after two quarters. Is that good news?</em> Only if the nightly adaptive rate fell with it; if not, the battery is stale and the quarterly regeneration is overdue.</li>
<li><em>Why not run the adaptive suite per release and block on it?</em> Its rate depends on the search budget spent that night, so two runs on the same release disagree; it finds bypasses, it does not measure a stable rate.</li>
</ul>

## Follow-ups

- *Pushback: the release battery plus the nightly search costs $2,600 a month against a $1,500 budget. Which half do you cut, and what risk do you accept in writing?* Keep the battery, which backs the release gate, and halve the nightly search, writing down that adaptive coverage of `update_contact_email` drops to weekly.
- *Reversal: what would you need to see to put a real-model sample into the merge gate after all?* A prompt-caused regression that reached production and cost more than a quarter of false blocks would, or a per-case noise level low enough that 50 cases separate 3 from 6 percent with a false-block rate the director accepts.
- *The model is retired in sixty days and the replacement scores 31 of 400 on the battery against 12 for the current one. Do you ship, and who signs?* Above the threshold, so not by default; the deterministic suite still passes, so ship with `issue_credit` behind human approval for the new model and a dated exception signed by the security engineer and the director.
- *Two senior engineers disagree about adding toxicity probes to the release gate. How do you decide without deciding by rank?* Count incidents and support tickets where harmful text was the harm; if the product has none, the probes run nightly and report, and the gate stays scoped to what the controls protect.

## Common mistakes

- Running a live-model injection suite on every PR and blocking on it, then watching the gate get disabled.
- Regenerating the red-team cases for each run and comparing rates across different test sets.
- Picking a blocking threshold without computing its false-block rate or its chance of catching a real regression.
- Reporting the battery's success rate as the agent's security level, when adaptive attacks routinely beat static ones.
- Testing the credit cap by asking the model nicely to exceed it, instead of having a scripted model emit the call.
