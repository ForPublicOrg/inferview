## Question

<Callout kind="interview" label="Concept">
Your MCP client lets users add any server by URL, so it runs authorisation flows against many authorisation servers. It already sends PKCE with S256 and the `resource` parameter on every flow. A reviewer proposes deferring the `iss` check on authorisation responses to next quarter, because "PKCE already binds the code to our client". Explain why that is wrong, what the issuer check adds, what it still does not cover, and how long the client should keep the record that holds the expected issuer.
</Callout>

Type your answer before opening the worked one: the attack in steps, what PKCE does and does not bind, the check, its gap, and the lifetime with a reason.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the reviewer which party the code verifier is sent to, and how the client decides that party's address.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the share of authorisation servers your users connect to whose metadata sets <code>authorization_response_iss_parameter_supported</code>.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask product how long users take from clicking connect to finishing consent, including a second factor.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>PKCE proves that whoever redeems a code started the flow. In a mix-up, the client itself redeems the code, at the wrong token endpoint, and sends the verifier along with it, so PKCE is satisfied for the attacker. The issuer check makes the authorisation response say which server issued the code, and the client compares that, by exact string, with the issuer it recorded for this flow before redirecting. It fails only when the honest server sends no <code>iss</code> and does not advertise it; there the specification lets the client proceed, and the fallback is a distinct redirect URI per issuer. The record lives about 10 minutes.</p>
</Fragment>
<Fragment slot="long">
<p><b>The attack.</b> The client knows two authorisation servers: an honest one, H, and one run by an attacker, A, reached through an MCP server the user added. The user starts a flow with A. The client records "this flow is with A" and redirects the browser to A's authorisation endpoint. A immediately redirects the browser to H, swapping in the client's client id for H. The user, who has an account at H, approves. H sends a code to the client's redirect URI. The client looks up the flow, sees A, and posts the code with the verifier to A's token endpoint. A now holds a code for H and the verifier that goes with it, and redeems both at H. RFC 9700 section 4.4 gives these steps.</p>
<p><b>What PKCE binds.</b> The verifier binds the code to the party that holds the verifier. That stops someone who steals a code in transit, because they lack the verifier. In a mix-up nothing is stolen in transit: the client hands over both, voluntarily, because it is wrong about who issued the code. The <code>resource</code> parameter does not help either; it scopes the token H issues, and A redeems at H with the same parameters the client would have used.</p>
<p><b>What the issuer check adds.</b> H includes <code>iss</code> in the response. The client compares it with the issuer stored in the per-flow record, the same record that holds the verifier and the state, filled in from metadata whose own <code>issuer</code> was validated against the URL it came from. H's response says H; the record says A; the client stops before any code or verifier leaves. Two details carry the weight. The comparison is a plain string comparison, with no case folding or trailing-slash normalisation, because normalising is how two identifiers that should differ end up equal. And the expected issuer must be per flow, not a field on the client: a client with several flows in flight would otherwise compare against whichever flow started last. RFC 9700 adds that storing the authorisation endpoint is not a substitute, since an attacker can publish an honest authorisation endpoint next to its own token endpoint.</p>
<p><b>What it does not cover.</b> If H neither sends <code>iss</code> nor advertises <code>authorization_response_iss_parameter_supported</code>, the client has nothing to compare, and the specification's table says proceed. The attack then works. This is the constraint conflict: rejecting every response without <code>iss</code> is safe and breaks every server that has not deployed RFC 9207, which today is allowed to omit it, since the specification only says servers SHOULD send it and expects to raise that to MUST in a later revision. The fallback for those servers is a distinct redirect URI per issuer, with the client checking that a response arrived at the URI of the issuer it expected. RFC 9700 ranks it below <code>iss</code>: it needs a registration per issuer and fails when one registration serves many issuers.</p>
<p><b>The record's lifetime.</b> The specification's example lifetime for a single-use state is 10 minutes; 5 to 15 is reasonable. It must cover sign-in, a second factor and consent. A minute fails real users. Hours keep records alive that only an attacker will complete, and in a hosted client they accumulate.</p>
<p><b>Failure mode of the recommendation.</b> The check is only as good as the recorded issuer. If the client takes the expected issuer from the metadata document without validating that document's <code>issuer</code> against the URL it fetched, an attacker who serves H's identifier from its own host makes the record say H and the check passes. The specification says the validation "provides no protection" in that case.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your client only ever talks to one authorisation server. Do you still need the check?</em> RFC 9207 says a single-server client is not vulnerable to mix-up; the check becomes necessary the day users can add servers by URL.</li>
<li><em>An honest server returns <code>iss</code> but its metadata does not advertise it. What does the client do?</em> Compare it anyway; the specification applies the comparison to any present <code>iss</code>, so servers that send it before updating their metadata are covered.</li>
</ul>

## Follow-ups

- *Product says per-issuer redirect URIs mean a new registration for every server users add. Is that true with Client ID Metadata Documents, and what does it cost if it is?*
- *What would you need to see before rejecting every response without `iss`, including from servers that do not advertise it?*
- *An error response arrives with a mismatched `iss` and an `error_description` asking the user to re-enter their password at a link. What does the client show?*

## Common mistakes

- Treating PKCE as proof that the code reaches the right party; it proves only that the same party started and finished the flow.
- Comparing `iss` after lowercasing or trimming a trailing slash.
- Keeping one "expected issuer" on the client object instead of one per flow.
- Recording the expected issuer from unvalidated metadata.
- Rejecting every response without `iss`, then discovering which servers broke from support tickets.
