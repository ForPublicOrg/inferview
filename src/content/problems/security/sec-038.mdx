## Question

<Callout kind="interview" label="Interview question">
Your fine-tuning service lets customers upload LoRA adapters as <code>.pt</code> files written by <code>torch.save</code>. The loader image pins <code>torch==2.5.1</code>, and every upload goes through <code>torch.load(path, weights_only=True, map_location="cpu")</code> in the same process that holds the service's object-store credentials. A security reviewer asks what is true of this call.
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which PyTorch release the security advisories on <code>torch.load</code> list as patched, and compare it with the pin.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the current <code>torch.load</code> documentation says about untrusted files, on the latest release, with the flag set.</p></details>

## Answer

The third option is right. CVE-2025-32434, published in April 2025, is remote command execution through `torch.load` with `weights_only=True` in PyTorch 2.5.1 and earlier, patched in 2.6.0 with a CVSS v4.0 score of 9.3. The advisory says the finding contradicts the common view that the flag makes a load safe. On this pin, a crafted adapter runs code in a process that holds object-store credentials. Upgrading removes this bypass. It does not turn an unpickler into a parser for untrusted input: the 2.14 documentation for `torch.load` still says never to load data from an untrusted source, and the 2.6.0 release notes suggest safetensors for checkpoints you do not trust.

The change that removes the risk is a format change, not a version change. Accept adapters only as safetensors, whose header is JSON and whose body is raw tensor bytes, so loading cannot import anything. If `.pt` uploads must stay for existing customers, convert them in a separate worker with no credentials and no network, on a patched PyTorch, and pass only the safetensors output to the service. The cost is a conversion step and a support burden for customers whose adapters use types the restricted unpickler rejects.

The first option is the belief the advisory contradicts. It describes what the flag is meant to do: limit the unpickler to tensors, primitive types, dictionaries and types registered with `add_safe_globals`. Intent and implementation differed until 2.6.0.

The second option is right about a newer release and wrong about this one. The default flipped to `weights_only=True` in 2.6.0, closing a deprecation that began in 2.4. In 2.5.1 a call without the argument uses the full unpickler, so the flag is the only restriction this code has, and it was the restriction that failed.

The fourth option confuses where the tensors live with what gets unpickled. Since 1.6.0, `torch.save` writes a ZIP64 archive: storages go in `data/`, and the object graph that references them is `data.pkl`, a pickle. Every `torch.load` of that archive unpickles `data.pkl`.

The fifth option treats a scanner as equivalent to the loader. A scanner parses the bytes with its own code and the loader with another; any place they disagree is an evasion. In early 2025, ReversingLabs found models on Hugging Face whose pickle stream broke right after the payload, and Picklescan reported the error without the dangerous import before it. A scanner is worth running as a filter; it is not a property of the call.

## Follow-ups

- *Two hundred enterprise customers have `.pt` adapters in production and the upgrade to 2.6 breaks 3% of them on types the restricted unpickler rejects. Do you add those types with `add_safe_globals`, or require conversion, and what do you write down about the risk of each?*
- *What would you need to see in the loader's process before you accepted `.pt` uploads again on a patched release?* Network egress denied, no credentials in its environment or on its filesystem, and a parent that receives only tensors, so a bypass found next year runs in a process with nothing to take.
- *The reviewer asks for the same answer about `numpy.load` on `.npy` uploads. What do you check?*

## Common mistakes

- Treating `weights_only=True` as a sandbox rather than as a restricted unpickler with its own bugs.
- Assuming a pinned image inherits the newer default.
- Upgrading PyTorch and closing the finding without changing what process loads customer files and what it can reach.
- Treating a clean scanner result as permission to load an untrusted pickle.
