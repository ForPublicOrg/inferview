## Question

<Callout kind="interview" label="Incident replay">
Replay the two weeks behind AWS security bulletin AWS-2025-015. At each checkpoint, commit to a call before the next event appears. Then answer the staff question: name the build control and the agent control that would each have stopped this release, say which one you would fund first if you could fund only one this quarter, and say what each misses.
</Callout>

The repository events and their UTC times come from Zenity Labs' reconstruction of GitHub data; the cause, the impact and the customer actions come from AWS's bulletin. ## Answer

What the published record says. A GitHub token in the extension's CodeBuild configuration had broader access than the build needed. An outside account used it to commit a prompt to a file on a tag and a downloader to the packaging script on master; the downloader pulled the prompt into the source only when the build stage was production. Version 1.84.0 shipped with it on 17 July 2025. The payload would have run the Amazon Q CLI with every tool trusted and no interaction, with a prompt to wipe the machine and delete cloud resources; AWS found it could not run because of a syntax error. AWS revoked and replaced the credentials, removed the code, released 1.85.0, pulled 1.84.0 from distribution and told customers to remove every copy, forks included. How the commits reached master is still listed as unresolved in the public reconstruction.

<Depth>
<Fragment slot="short">
<p>The build control: no long-lived credential with write access to the repository in the build at all; the build gets a short-lived, read-only token, and only a separate release identity, behind protected branches and tags, can write. That alone stops this release. The agent control: when the agent CLI is called without interaction, it refuses to pre-approve every tool and has no cloud credentials unless a policy grants them. Fund the build control first. The attacker already had code running inside a trusted extension; the agent was the payload they chose, and any shell command would have done the same, so the agent control would only have stopped this particular payload.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Build controls, in the order they would have stopped it.</strong> First, credentials: the token that pushed the commits was in the build configuration with write access. A build that reads source needs read access; writes to the repository go through a separate release identity with its own audit trail, and every token is short-lived and scoped to one repository. Second, refs: a protected tag and a branch ruleset that apply to automation accounts as well as people, so a push to master without a reviewed pull request fails. Third, hermetic packaging: a packaging script that downloads source from a mutable ref (a tag) during the build means the reviewed tree and the shipped artefact differ. The release job should build from one commit, fetch nothing from the repository at package time, and diff the packaged sources against that commit, failing on any file that is not in it.</p>
<p><strong>Agent controls.</strong> The payload was one CLI call with every tool trusted and no interaction. An agent CLI can refuse that combination unless an administrator policy allows it, ask for approval on destructive commands whatever flags the caller passes, and run without cloud credentials unless a profile is granted per task. These stop prompt-borne payloads from any source, including instructions planted in repository files that a developer asks the agent to read, which is the broader reason to build them.</p>
<p><strong>The decision with two defensible answers.</strong> Option A, fund the build controls: they stop this attack and every other change pushed with a leaked build token, whatever the payload; they cost release engineering time, and stricter rulesets slow every release that automation used to push directly. Option B, fund the agent controls: they stop the class of attack where text, not code, makes the agent destructive, which the build controls never see; but in this incident the attacker had code execution in the extension host, which VS Code runs with the user's permissions, so a plain shell command would have bypassed them. I fund A first because B does not cover this case, and schedule B for the injection risk it does cover.</p>
<p><strong>The quantity to choose: token lifetime.</strong> A build token valid for the length of one job, minutes, leaves a stolen copy useless before anyone can script against it; one valid for a day still allows a push hours after the build ends. Anything up to the job's maximum runtime is reasonable; a token that outlives the job is the defect in this incident.</p>
<p><strong>The constraint conflict.</strong> Release speed against integrity: automatic releases from automation accounts are what let a small team ship weekly, and every ruleset that makes automation go through review adds latency to every release.</p>
<p><strong>Failure modes of the recommendation.</strong> Rulesets are only as good as their exemptions, and automation accounts are the usual exemption; the release identity that keeps write access becomes the next token to steal, so it lives in the release system only, with no copy in any build configuration. And a hermetic-build diff catches files fetched at package time but not a malicious change merged through a real review, which needs the agent controls and human review to catch.</p>
</Fragment>

<li><em>The attacker's code was gated on the production stage. What test would have caught that gate?</em> A release job that builds the production artefact and diffs it against the reviewed commit, rather than a test build with a different stage.</li>
<li><em>Why does the bulletin ask customers to check forks and derivative copies?</em> The malicious code stays in every copy of 1.84.0, and a fork built from it never receives the marketplace update.</li>

## Follow-ups

- *Pushback: release engineering says protected tags and reviewed merges for automation will slow weekly releases by a day. Which half of the build controls do you cut, and what risk do you accept in writing?* Keep the scoped, short-lived tokens and the hermetic diff, defer the rulesets for automation, and write down that a stolen release identity can still push.
- *Reversal: what would you need to see to fund the agent controls ahead of the build controls?* An incident or red-team result where repository text, not code, made the agent run a destructive command on a developer machine, and a build already on short-lived scoped tokens.
- *The fix shipped on 19 July, and the bulletin appeared on 23 July, after the press. Two senior people disagree about whether to publish before the press asks. How do you decide without deciding by rank?* Count the installs still on 1.84.0 each day without a bulletin, since only a bulletin reaches forks and copies that never auto-update, and set that against the cost of disclosing before the cause is known.

## Common mistakes

- Treating the incident as a prompt-injection problem and proposing a better system prompt or classifier.
- Calling the extension sandboxed; the extension host has the user's permissions.
- Rewriting history or reverting the commit and treating that as the remediation, while the token and the installed copies remain.
- Telling customers to update only, when forks and copies without auto-update keep 1.84.0.
- Assuming a test build would have caught it, when the payload only entered the production packaging stage.
