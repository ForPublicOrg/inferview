## Question

<Callout kind="interview" label="Critique, 35 minutes">
"Our SOC 2 Type II observation period starts in six weeks and, for the first time, the contract Q&A feature is in scope. GRC approved this evidence pack last week. You are the staff engineer who has to sign the system description. List what is wrong with it, rank it, and say what you would fix before the period starts."
</Callout>

The feature (scenario): customers upload contracts; the app stores them in the vendor's vector stores, retrieves passages for a question, and calls the vendor's Responses API. Product managers tune the system prompt in the feature-flag service. Traces with full prompts go to an LLM observability vendor. The auditor has proposed a six-month observation period and has not said which AI evidence it will ask for.

```text
EVIDENCE PACK: Contract Q&A                          v3, approved by GRC 2026-10-14

1 Model governance
  1.1 Model card (owner: product). Model: vendor flagship, alias "flagship-latest".
      Purpose, limitations, launch evaluation (see 5.1). Signed 2026-03-02.
  1.2 Change management: all model and feature changes follow CHG-01
      (pull request, one approval, CI green). Evidence: sample of 25 merged PRs.
  1.3 AI acceptable use policy, acknowledged annually by all staff (98% complete).

2 Monitoring
  2.1 Dashboards: p95 latency, token spend, error rate, thumbs-down rate (monthly export).
  2.2 Quality review: monthly meeting on thumbs-down samples, notes attached.

3 Data and privacy
  3.1 Subprocessors: cloud provider, model vendor (SOC 2 Type II report on file, 2026-09).
      Vendor statement: "API data is not used for training and is not retained."
  3.2 Data flow diagram: customer, app, model vendor, back through app to customer.
  3.3 Encryption at rest for the application database (AES-256).

4 Access
  4.1 Quarterly access review: production database, cloud console, CI.

5 Testing
  5.1 Launch evaluation: 92% correct on 200 contract questions (2026-02-26).
  5.2 Annual penetration test of the web application (2026-07); no high findings.

6 Incidents
  6.1 Company incident response plan (applies to all systems).
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the model field in the vendor's API response said on 1 March and on 1 October, and where that value is recorded.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask who can change the production system prompt, through what tool, and what record that tool keeps.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which API objects the integration creates at the vendor, and request the retention setting of each.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The pack documents the feature as it was designed in March and cannot show what it did on any day since. Ranked: the model is an alias, so vendor updates change production with no change record; the prompt changes in a flag service outside CHG-01; there is no per-inference record of model version, prompt, retrieved passages and outcome, so no answer can be reconstructed; the retention statement is wrong for this integration, which keeps contracts in vendor vector stores until deleted and uses a 30-day application state by default; the observability vendor receives full prompts and is on no subprocessor list or access review. Below those: a one-time eval with no link to changes, monitoring with no change tickets, a pen test that skipped injection through uploaded contracts, and an incident plan with no AI incidents and no kill switch. Fix the first five before the period starts; they are the ones a sample will hit.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why "approved" is not the bar.</strong> There are no AI-specific Trust Services Criteria, and auditors choose their own AI evidence requests, so the pack has to hold up against the requests the CSA note says auditors make in practice: change records with approvals, per-inference logs, drift monitoring tied to change tickets, and the vendor's retention configuration. This pack has the documents and none of the records.</p>
<p><strong>Flaws, ranked by what a six-month sample would expose.</strong></p>
<ol>
<li><strong>The alias (1.1, 1.2).</strong> "flagship-latest" moves when the vendor moves it. Every vendor update is a production change with no PR, no approval and no eval, and CHG-01's PR sample cannot show it. The model card's launch evaluation describes a model that may no longer be serving.</li>
<li><strong>Prompts outside change management (1.2).</strong> The system prompt lives in the flag service and product managers edit it. CHG-01 covers merged PRs, so the most frequent behavioural change in the feature has no approval record. The sample of 25 PRs is accurate and irrelevant.</li>
<li><strong>No per-inference record (2.1).</strong> Aggregates cannot answer "which model and prompt version produced this answer for this customer on this date, from which passages". That question is what a customer complaint or an exception in the sample turns into.</li>
<li><strong>The retention statement (3.1).</strong> "Not retained" is wrong for this integration. Uploaded contracts sit in vendor vector stores, kept until deleted; Responses API application state is kept 30 days by default; abuse monitoring logs up to 30 days. "Not used for training" is right; the two claims were merged into one sentence.</li>
<li><strong>The missing subprocessor (3.1, 3.2, 4.1).</strong> The observability vendor receives full prompts, which contain contract text. It is not on the subprocessor list, not in the data flow diagram and not in the access review, and whoever has access to its UI can read customer contracts.</li>
<li><strong>One evaluation, in February (5.1).</strong> 92 percent on 200 questions is a launch fact. Without a rerun tied to each model or prompt change, it says nothing about the period being audited.</li>
<li><strong>Monitoring with no change tickets (2.1, 2.2).</strong> A thumbs-down spike can be matched to nothing, because no change is recorded for the alias or the prompt.</li>
<li><strong>Pen test scope (5.2).</strong> A web application test with no high findings says nothing about instructions inside an uploaded contract that steer answers, or about retrieval returning another customer's passages.</li>
<li><strong>Incident plan (6.1).</strong> No definition of an AI incident (cross-customer passage in an answer, a materially wrong clause summary), no kill switch, no owner.</li>
<li><strong>Policy without inventory (1.3).</strong> 98 percent acknowledged a policy; nobody knows which AI tools staff paste contracts into. The CSA note's point is that a report can be accurate and silent on this.</li>
</ol>
<p><strong>The decision with two defensible answers: the model version.</strong></p>
<ul>
<li>Pin a dated model version and treat each upgrade as a change under CHG-01 with an eval run. Cost: vendor fixes arrive only when someone does the upgrade, and the vendor's retirement dates force that work on its schedule.</li>
<li>Keep the alias, but record the model field from every response, and open an automatic change record with a post-hoc eval run whenever it changes. Cost: the change is detected after customers have seen it; an auditor may record it as an unapproved change, and the system description has to say this is the control.</li>
</ul>
<p>I pin. Six weeks before a period starts, a control the auditor can test by sampling PRs is worth more than vendor fixes arriving a few weeks sooner. If the vendor's upgrade cadence turns out to be faster than the team can eval, revisit.</p>
<p><strong>The prompt.</strong> Moving it into the repository puts it under CHG-01 at the cost of product managers needing an engineer per edit. Keeping it in the flag service is acceptable if the service enforces a second approver, keeps an immutable change history with the diff, and triggers the eval run; that history is the evidence.</p>
<p><strong>The quantity: inference-record retention.</strong> The record (timestamp, tenant, request id, model version, prompt version, passage ids, a prompt hash, outcome, latency) must outlive the observation period plus the auditor's fieldwork. The period is six months; fieldwork length is a question for the auditor, and I assume two months, so eight months. The redacted prompt text is the conflict: kept that long, it sits in the scope of every customer deletion request. I keep text for 30 days and metadata for eight months, and rely on the passage ids and prompt version to reconstruct an answer. That is acceptable only if contract versions in the application database are retained long enough for the ids to resolve.</p>
<p><strong>Failure mode of the recommended fix.</strong> Pinning moves the risk to the vendor's retirement date: a forced migration lands inside the observation period with no time for a full eval, and the team ships under an exception. Plan the exception process now: who signs, which evals are the minimum, and how it is recorded.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The vendor's SOC 2 report is on file. Is that enough for the subprocessor?</em> It is acceptable if its scope covers the API services this feature uses and the complementary user entity controls it lists are mapped to your own controls; otherwise it covers someone else's use of the vendor.</li>
<li><em>Would AIUC-1 certification replace this pack?</em> It is a separate, vendor-run standard with its own audits; it can add evidence for customers who ask for it, but the SOC 2 auditor tests the controls in your system description.</li>
</ul>

## Follow-ups

- *Pushback: per-inference records and an eval run per prompt change cost more engineering time in the next six weeks than the feature's roadmap. Which do you cut, and what exception do you write into the system description?*
- *Reversal: what would you need to see from the vendor to go back to the alias?*
- *GRC says the auditor has not asked for any AI evidence and fixing this now invites findings. Two staff engineers disagree with each other about whether to fix it before the period. How do you decide without deciding by rank?*
- *The vendor retires your pinned version in sixty days, inside the observation period, and the replacement drops 9 of the 200 launch questions. Do you ship it, and who signs?*

## Common mistakes

- Treating the model card as change management because it names the model.
- Reading "not used for training" and "not retained" as the same claim.
- Reviewing the subprocessor list without checking it against where prompts actually go.
- Asking for full prompt logging for the whole period without pricing it against deletion requests.
- Accepting a launch evaluation from February as evidence for a period that starts in December.
