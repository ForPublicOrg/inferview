## Question

<Callout kind="interview" label="Concept, staff">
Leadership wants the tools of every internal team reachable from the company's own agents and from two vendor coding agents, over remote MCP on the 2026-07-28 revision. Explain what a request looks like on the wire and what the authorisation model asks of each party. Then decide: does each MCP server validate tokens itself, or does one gateway in front of all of them? Name the production risks your choice leaves open, and choose the access-token lifetime.
</Callout>

The estate, a scenario: 30 MCP servers owned by 9 teams; 6 of them call third-party SaaS APIs on the user's behalf. The corporate identity provider supports resource indicators (RFC 8707) and does not support token exchange (RFC 8693) this year. Platform security is two engineers. Launch is in eight weeks.

Type your answer before opening the worked one.

## Answer

<Depth>
<Fragment slot="short">
<p>On the wire, each JSON-RPC message is its own POST to one endpoint, answered with JSON or a per-request SSE stream; there are no sessions, and every request carries its protocol version and capabilities. Each MCP server is an OAuth resource server: it publishes protected-resource metadata, the client obtains a token for that server's URI with PKCE, <code>resource</code> and an issuer check, and the server accepts only tokens whose audience is itself. I would keep audience validation in every server, through one shared library and a conformance test in CI, and put a thin gateway in front for Origin, header checks, rate limits and audit, holding no tokens of its own. Tokens live 10 minutes. What stays open: the six SaaS-calling servers until each has its own upstream credential, tool descriptions as model input, and agents combining private data with untrusted content, which no token check stops.</p>
</Fragment>
<Fragment slot="long">
<p><b>The wire.</b> Streamable HTTP exposes one endpoint that accepts POST. Every JSON-RPC message is a new POST with an <code>Accept</code> header listing JSON and SSE; the server answers with one JSON object or an SSE stream scoped to that request, carrying progress and log notifications before the result. The 2026-07-28 revision removed the <code>initialize</code> handshake and <code>Mcp-Session-Id</code>: each request carries its protocol version and client capabilities in <code>_meta</code>, servers implement <code>server/discover</code>, change notifications come on a <code>subscriptions/listen</code> stream, and a broken stream loses the in-flight request, which the client re-issues. Requests mirror body fields into <code>MCP-Protocol-Version</code>, <code>Mcp-Method</code> and <code>Mcp-Name</code> headers, and a server that reads the body must reject a mismatch with 400 and <code>HeaderMismatch</code>. That rule exists for gateways: a proxy that routes or rate-limits on the header while the server acts on the body is a split-brain the attacker chooses. Servers must validate <code>Origin</code> and answer an invalid one with 403. Stdio servers sit outside all of this and take credentials from the environment.</p>
<p><b>The authorisation model.</b> The MCP server publishes protected-resource metadata naming its authorisation server and answers an unauthenticated request with 401 and <code>resource_metadata</code>, optionally with the scopes it needs. The client fetches the authorisation server's metadata and checks that its <code>issuer</code> matches the URL it built; registers by Client ID Metadata Document (preferred), pre-registration, or Dynamic Client Registration, which this revision deprecates; runs the code flow with PKCE S256, sending <code>resource</code> set to the server's canonical URI in both requests; checks <code>iss</code> on the response; and sends the token in the <code>Authorization</code> header on every request, never in a query string. The server validates audience and issuer, answers missing scope with 403 <code>insufficient_scope</code>, and never forwards the token it received. When it calls another API it uses a separate token from that API's authorisation server.</p>
<p><b>The decision: per-server validation or a gateway.</b> Both are defensible. A gateway that validates every token gives two security engineers one place to enforce and audit. Its cost here is specific: with no token exchange, the gateway either forwards the user's token to the servers behind it, which is passthrough and requires those servers to accept a token whose audience is the gateway, or it signs its own internal assertions, which makes it an issuer for 30 services and the most valuable thing to compromise. Per-server validation keeps the audience boundary where the specification puts it: the identity provider issues a token per server URI, so a token stolen from one server's logs opens only that server. Its cost is 30 implementations across 9 teams. I take per-server audiences, remove the implementation cost with one validation library that every server must use, and enforce it with a conformance test in each server's CI that sends a token for another audience, a token from another issuer, an expired token, and a token lacking scope, and fails the build unless each is refused with the right status. The gateway stays, without tokens: Origin validation, header-body checks, per-user rate limits from the token's subject, and an audit log that records the token's identifier, never the token. The constraint conflict is the deadline against the boundary: a token-validating gateway ships in less than eight weeks; per-server audiences need every team to adopt the library.</p>
<p><b>The six SaaS-calling servers.</b> Without token exchange each needs its own OAuth client registration at the SaaS provider and per-user consent there, with the tokens stored per user and tenant. If a team has been forwarding the corporate token, or using one shared SaaS key for every user, its server does not launch until that changes; a shared key makes the server a deputy that acts for anyone who reaches it.</p>
<p><b>Token lifetime.</b> Ten minutes; 5 to 15 is reasonable. Each server validates locally against a cached key set, so revocation takes effect within one lifetime with no call to the identity provider per request. A day leaves offboarded users with working agent tokens. One-minute tokens mean ten times the refresh traffic of ten-minute tokens, for nine minutes less revocation lag.</p>
<p><b>Risks the design leaves open.</b> Tool descriptions are model input, so a team that edits one changes every connected agent's behaviour, and a vendor agent connected to an outside server can be steered by that server's description (Invariant Labs' tool poisoning and shadowing): descriptions ship only with reviewed releases, with a published hash. State handles replace sessions and must be bound to the user from the token. Clients fetching discovery URLs can be pointed at internal addresses (SSRF), and the identity provider fetching Client ID Metadata Documents has the same exposure. A developer's local server or inspector without authentication is reachable from a browser, as CVE-2025-49596 showed for MCP Inspector. And the agent-level risk that no part of this model touches: in the GitHub MCP case, a correctly authorised token did exactly what an injected issue told the agent to do. Narrow scopes and one-resource-per-session policies shrink that; authorisation does not remove it.</p>
<p><b>Failure mode of the recommendation.</b> The library drifts. A team pins an old version, or wraps the check in a feature flag during an incident and never removes it, and the server keeps passing review because it imports the library. The conformance test is the control, which is why it runs against the deployed server in CI, not against the library's unit tests.</p>
<p><b>What you give up.</b> One switch at the gateway that revokes everything at once, and a single consent: users authorise each server they use separately, since each server needs its own token.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not let one token name all 30 servers in <code>aud</code>?</em> It makes every server's logs a credential for the other 29, which is the blast radius the per-server audience exists to remove.</li>
<li><em>Where does the vendor coding agent register?</em> As a client of your identity provider, with its own client id, so its tokens can be scoped and revoked apart from your agents'.</li>
</ul>

## Follow-ups

- *Pushback: three teams say the shared library and its conformance test will cost them the launch date. Which servers do you let ship behind the token-validating gateway, and what do you accept in writing?*
- *Reversal: the identity team announces token exchange next quarter. What would you need to see to move the six SaaS-calling servers, or all 30, behind a gateway that exchanges tokens?*
- *Two senior engineers disagree: one wants 30 audiences, the other wants one audience per team, nine in all. How do you decide without deciding by rank?*
- *A vendor's coding agent starts calling `tools/list` on every server every few seconds. What in the 2026-07-28 revision lets you push that back, and what must you mark private?*

## Common mistakes

- Describing the 2025 transport: sessions, `initialize`, a GET stream and resumable SSE are gone in 2026-07-28.
- Calling a gateway that forwards the user's token "centralised auth"; it is passthrough with extra steps.
- Listing OAuth as the answer to prompt injection; a valid token carries out an injected instruction as faithfully as a real one.
- Treating stdio servers as covered by the HTTP authorisation rules.
- Leaving out the upstream credential of servers that call third-party APIs.
