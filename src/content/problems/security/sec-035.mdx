## Question

<Callout kind="interview" label="Design round, 40 minutes">
A Python dependency in your training pipeline was found to contain malicious code. Walk through your response: what you do in the first hour, how you find out what it touched, and which checkpoint you resume the run from.
</Callout>

The scenario's facts, invented for this problem. It is Monday 09:00. PyPI has removed `tensorshard-io` 3.2.1, a transitive dependency of your data-loading library, and the maintainers' advisory says the version runs a payload at import that reads environment variables and files under `$HOME` and sends them out in DNS queries, the pattern of the torchtriton compromise in 2022. Your training image is rebuilt nightly from a requirements file with version ranges, through an internal mirror that proxies PyPI. Thursday night's build picked up 3.2.1.

- Since Friday, three kinds of job have run on that image: nightly data preparation, which writes tokenized shards to the dataset bucket; eval jobs; and a fine-tuning run on 256 GPUs.
- The fine-tuning run is on day 11 of 21. It was restarted on Friday at 02:00 from a checkpoint written on Thursday at 18:00 on the old image. Since the restart it has written a checkpoint every 6 hours.
- One service account runs all three kinds of job. It can write the checkpoint and dataset buckets, holds a token that can push models to the internal hub, and has a cloud credential for the cluster.
- Training nodes resolve any DNS name.
- Another team has the cluster from day 22.

Choose the checkpoint to resume from and how long you are willing to pause the run before deciding.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask whether anyone has the payload itself, and whether it only sends data out or can also fetch and run more code.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the DNS resolver logs from the training nodes since Thursday and the storage audit logs for the checkpoint and dataset buckets, by principal and time.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether data preparation is deterministic: given the same raw inputs and code, does it write byte-identical shards?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>First hour: stop new jobs on the bad image, pause the training run, block 3.2.1 at the mirror, cut DNS egress from the training nodes to anything but internal resolvers, and rotate the service account's credentials, the hub token and any keys on the nodes, after checking the payload for anything that reacts to revocation. Then scope from evidence: which images contain 3.2.1, which jobs ran them, what the DNS and storage logs show. The checkpoint decision turns on what the payload can do. If analysis shows a fixed exfiltration payload with no second stage and the bucket logs show no unexpected writes, resume from the latest checkpoint on a clean image and write down the residual risk. If it can fetch code, or analysis is not done within a day, roll back to Thursday 18:00 and accept the overrun. Data shards written since Thursday are regenerated on a clean image and compared by hash before any training reads them again.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Contain before scoping.</strong> The payload ran with the job's identity, so the credentials it could read are the incident. Rotate the service account's keys, the hub token and the cloud credential, and treat SSH keys and anything else under <code>$HOME</code> on the nodes as read. Check the payload, or the advisory, for persistence before revoking anything: ChainDrop installed a token monitor that runs a handler when its stolen token is revoked, and StepSecurity's guidance was to remove it first. Restrict DNS on the training nodes to internal resolvers that do not forward arbitrary names. Blocking HTTP egress alone does nothing here, because torchtriton's binary sent its data in DNS queries. Pin the mirror to refuse 3.2.1 and stop the nightly image build until the requirements are pinned.</p>
<p><strong>Scope from evidence, and say what is missing.</strong> List every image digest built since Thursday that contains the package, from the build logs or by scanning the images, and every job and node that ran one. The resolver logs show which nodes made lookups to the advisory's domains and when; the hub's audit log shows whether the token pushed anything; the cloud audit log shows what the credential did. The storage logs show writes to the checkpoint and dataset buckets by principal and time. Every legitimate write comes from the same service account, so the logs can show a write at a time no checkpoint was due, but not which code inside the job made it. What you cannot get without the payload: whether it had a second stage. Ask the maintainers or the registry for the malicious wheel and analyse it in an isolated environment; until then, assume it could do anything the service account could.</p>
<p><strong>The data shards are the cheap decision.</strong> Data preparation since Thursday night wrote shards with an identity that could have altered them. Anthropic's poisoning study found 250 documents enough to plant a narrow backdoor in models up to 13B parameters in its setup, so "only a few documents changed" is not a comfort. Regenerating the shards from raw inputs on a clean image costs hours. If data preparation is deterministic, byte-identical output proves the stored shards were not altered and the fine-tuning run's data is clean; if it is not, replace the stored shards with the regenerated ones and record that the run trained on shards that cannot be verified.</p>
<p><strong>The decision with two defensible answers: which checkpoint.</strong></p>
<ul>
<li><strong>Roll back to Thursday 18:00</strong>, the last checkpoint written on the old image. Nothing the payload did can be in it. The cost, computed: the run restarted on Friday at 02:00 and it is Monday 09:00, so 79 hours of progress are lost, or 79 × 256 = 20,224 GPU-hours. Ten days of work remained; now about 10 + 79 / 24 ≈ 13.3 days remain, past the other team's booking by about 3.3 days.</li>
<li><strong>Resume from the latest checkpoint</strong> on a clean image. The loss is the hours of the pause. The cost is a risk you cannot fully remove: a payload with write access to the checkpoint bucket could have altered weights, and a checksum the job wrote with the same identity proves nothing.</li>
</ul>
<p>The conflict is a deadline against the integrity of the weights. The evidence that separates the two is the payload analysis. I pause for at most 24 hours, which costs 256 × 24 = 6,144 GPU-hours, under a third of the rollback, while the payload is analysed and the bucket logs reviewed. If the payload is a fixed exfiltration routine, as torchtriton's was, and no checkpoint object was written outside the 6-hour schedule, I resume from the latest checkpoint and record the residual risk. If it can download code, or the analysis is not finished in 24 hours, I roll back and negotiate the booking. A pause of a few hours to a few days is defensible; resuming at once without the analysis is not, and neither is rolling back by reflex when the evidence could have saved three days.</p>
<p><strong>Failure mode of the recommendation.</strong> Payload analysis sees the sample you were given. If the package fetched a second stage from a server that served different code to different victims, the copy you analyse can be clean while yours was not, and the absence of off-schedule writes covers only writes the logs recorded. The decision memo has to say that the resume rests on that analysis, and the eval suite has to compare the resumed run against the Thursday checkpoint on behaviour, with any unexplained divergence as a trigger to roll back.</p>
<p><strong>What you give up.</strong> Under the recommendation, a day of the run for evidence, and a residual risk in writing if you resume. Under the preventive changes below, the convenience of nightly images that pick up new releases, and some build time.</p>
<p><strong>What changes afterwards.</strong> A lockfile with hashes and pip's hash-checking mode, which is all-or-nothing and requires every requirement pinned; wheels only, with <code>--only-binary :all:</code>, so installs do not run build scripts; a minimum release age at the mirror, so a version removed within days never reaches a build; one index per package name, so a public package cannot shadow an internal one as torchtriton did; DNS and network egress from training nodes limited to what training needs; separate short-lived identities for data preparation, training and model publishing; and checkpoints written to a bucket with object versioning, their digests recorded by the scheduler under an identity the job cannot use.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The malicious version was published through the project's own trusted-publishing workflow. Do signatures or attestations help?</em> They show which workflow built it, not that the commit was authorized; the Ultralytics releases were published that way. A minimum release age and hash pins are what keep such a version out of your build.</li>
<li><em>Who decides on the rollback?</em> The run's owner and security together, with the decision memo naming the evidence and the residual risk.</li>
<li><em>Eval jobs ran on the same image. Does that change anything?</em> Their credentials are in scope, and any eval result produced since Thursday is suspect, which matters if a promotion decision used one.</li>
</ul>
</Fragment>
</Depth>

### The written artefact

The decision memo, Monday 13:00, to the run's owner, security and the team that has the cluster next.

- **Facts:** `tensorshard-io` 3.2.1 in images built since Thursday night; data preparation, evals and the fine-tuning run used them; credentials of the shared service account rotated at 10:15; DNS restricted at 09:40.
- **Unknowns:** whether the payload has a second stage; whether any checkpoint or shard was altered.
- **Decision:** the run is paused until Tuesday 09:00. Resume from the latest checkpoint if payload analysis finds no second stage, the bucket logs show no off-schedule writes, and regenerated shards match by hash. Otherwise roll back to Thursday 18:00: about 13.3 days of work from Tuesday against 9 days of booking left, so ask the next team for about 4.3 more days.
- **Rollback triggers after a resume:** a second stage found in any later sample of the package; a write to the checkpoint bucket outside the schedule since Friday; an eval divergence from the Thursday checkpoint beyond the run's normal variance.
- **Owners and dates** for each preventive change.

## Follow-ups

- *Rolling back costs the other team more than three days of their booking and they have a launch. Which do you protect, and what risk do you accept in writing if the run resumes from a checkpoint you could not verify?*
- *What would you need to see in the payload analysis to resume from the latest checkpoint without a pause next time?*
- *The ML lead says hash-pinned lockfiles slow research down because every new dependency needs a review. Two senior engineers disagree on whether research images get an exception. How do you decide without deciding by rank?*
- *A model trained on this run is already serving customers from a checkpoint written on Saturday. What do you do with it today?*

## Common mistakes

- Rotating credentials before checking for persistence that reacts to revocation.
- Blocking HTTP egress and missing DNS exfiltration.
- Trusting checksums written by the identity that was compromised.
- Treating the dataset as clean because the payload was described as exfiltration only.
- Deciding the checkpoint by reflex in either direction instead of naming the evidence that would separate the options and a time limit for getting it.
