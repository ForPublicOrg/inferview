## Question

You serve Llama 3.1 70B in bf16. Its config: 80 layers, 64 query heads, 8 key-value heads, head dimension 128. You want 8 concurrent requests, each with up to 32,768 tokens of context.

Estimate the KV cache memory for the full batch, in GiB (2^30 bytes). Then say how it compares with the weights and what you would change if it does not fit.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Per token: one key and one value, per KV head, per layer, each head_dim values of 2 bytes.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Use the 8 KV heads, not the 64 query heads.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Per token: 2 (key and value) × 80 layers × 8 KV heads × 128 × 2 bytes = 327,680 bytes, 320 KiB. One 32,768-token sequence: 320 KiB × 32,768 = 10 GiB. Eight of them: 80 GiB. That is on top of about 140 GB of bf16 weights, so the cache, not the weights, is what decides how many long requests fit.</p>
</Fragment>
<Fragment slot="long">
<p>Formula. KV bytes per token = 2 × layers × KV heads × head_dim × bytes per value = 2 × 80 × 8 × 128 × 2 = 327,680 bytes. Per sequence: 327,680 × 32,768 = 10,737,418,240 bytes = 10 GiB. Batch of 8: 80 GiB. The accepted band is 70 to 90 GiB.</p>
<p>The GQA effect. With 64 KV heads, one per query head, the same batch would need 8 times as much, 640 GiB. Grouped-query attention is why this is a serving problem and not an impossibility.</p>
<p>Next to the weights. 70 billion parameters × 2 bytes ≈ 140 GB. Weights plus a full cache for this batch is about 140 GB + 86 GB (80 GiB), so it needs several GPUs whichever way you shard it.</p>
<p>If it does not fit. Cap context per request or per tenant; quantize the KV cache to 8 bits (halves it, with a quality check); use paged KV allocation so memory is reserved per block as sequences grow rather than for the maximum length up front; reuse shared prefixes across requests; or pick a model whose attention caches less per token (MLA, sliding-window layers).</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why does the cache limit throughput?</em> Batch size sets how many tokens per forward pass the GPU decodes; if the cache for more sequences does not fit, the batch cannot grow.</li>
<li><em>Does the average request need the full 32K?</em> Usually not, which is why paged allocation matters: reserving the maximum per request wastes most of it.</li>
<li><em>How does an MoE model change this?</em> Experts affect weights and compute, not the KV cache; the cache depends only on the attention configuration.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *How does this change for a model with alternating sliding-window layers?* Only full-attention layers grow with context; sliding layers stop at their window. Apply the formula per layer type.
- *Where would you read the numbers for a new model?* The config: number of layers, key-value heads and head dimension, plus the attention type of each layer.

## Common mistakes

- Using the 64 query heads instead of the 8 KV heads, which gives 640 GiB.
- Forgetting the factor of 2 for keys and values.
- Mixing GB and GiB: 80 GiB is about 85.9 GB.
