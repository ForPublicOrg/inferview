## Question

You serve Llama 3.1 70B with a bf16 KV cache. From its published config: 80 layers, 64 query heads, 8 key-value heads, head dimension 128 (checked 2026-10-28).

The batch you are sizing (a scenario): 16 concurrent requests. Four are document-analysis requests with 100,000 tokens of prompt each; twelve are chat requests with 8,000 tokens each. Every request may generate up to 1,024 tokens.

Estimate the KV cache this batch needs, in GiB, choosing and stating how you count the generated tokens and how memory is reserved. Then say what the same batch would need if the model had one key-value head per query head, and which requests decide whether it fits.

## Answer

<Depth>
<Fragment slot="short">
<p>Per token: 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes, 320 KiB. Prompts: 4 × 100,000 + 12 × 8,000 = 496,000 tokens, which is 151.4 GiB. Budgeting the full 1,024 output tokens for all 16 adds 16,384 tokens and brings it to 156.4 GiB. With 64 key-value heads it is 8 times as much, about 1.2 TiB. The four long requests hold 81% of the tokens, so they decide whether the batch fits.</p>
</Fragment>
<Fragment slot="long">
<p>The per-token cost. One key and one value per key-value head per layer: 2 × 80 layers × 8 heads × 128 values × 2 bytes = 327,680 bytes. The query head count does not enter, which is the point of grouped-query attention.</p>
<p>The token count is the assumption you choose. Prompt tokens only: 496,000 tokens × 327,680 bytes = 162,529,280,000 bytes = 151.4 GiB. Prompt plus the full output budget: 512,384 tokens = 167,897,989,120 bytes = 156.4 GiB. Both are reasonable: the first matches an engine that admits on prompt length and preempts when the cache fills, the second an engine that reserves the output budget at admission. Rounding up to whole pages changes little: with 256-token pages, the minimum FlashAttention's paged cache accepts, each request wastes under one page, at most 16 × 255 tokens, about 1.2 GiB. The accepted band is 145 to 165 GiB.</p>
<p>The unreasonable choices. Reserving the config's maximum of 131,072 positions per request gives 16 × 40 GiB = 640 GiB, which is what static per-request allocation costs and why paged allocation exists. Using the 64 query heads instead of the 8 key-value heads gives about 1,211 GiB: that is the multi-head answer, and it is the second half of the question, not this model.</p>
<p>The dominant term. The four 100,000-token requests are 400,000 of 496,000 prompt tokens, 81%, or 122 GiB on their own. The assumption that flips the conclusion is the document class's length: at 32,000 tokens each, the batch drops to 224,000 tokens, 68.4 GiB, less than half. The 70 billion parameters in bf16 are about 140 GB on top of the cache in every case.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The weights take 140 GB and you have 8 GPUs of 80 GB each. How many document requests can run at once, and which class do you preempt when they collide?</em> Fit the arithmetic to the hardware first, then state the policy: preempting the chat requests keeps throughput, preempting a document request wastes its prefill.</li>
<li><em>Would you quantize the cache to 8 bits to fit the batch?</em> It halves every figure above. Only after an evaluation on the long-document task, because the cost of error is paid in the requests that are hardest to check.</li>
<li><em>What would you need to see in production to stop reserving the output budget at admission?</em> The distribution of generated lengths per class and the preemption rate when you admit on prompt length alone.</li>
</ul>

The arithmetic in one line: 327,680 bytes × 496,000 tokens / 2^30 = 151.4 GiB, and 327,680 × 512,384 / 2^30 = 156.4 GiB.

The comparison with full multi-head attention is the reason the question exists. Eight times the cache means the same batch would need about 1,211 GiB before outputs, so a 70B model with one key-value head per query head could not serve four 100,000-token documents concurrently on any single node. Grouped-query attention turned a long-context batch from impossible into a capacity-planning problem.

## Follow-ups

- *How does the answer change for a model whose layers alternate between a 128-token sliding window and full attention?* Only the full layers grow with context; the windowed layers stop at 128 positions, so the estimate roughly halves for a 50:50 split. Read the layer types from the config before applying the formula.
- *Where does a mixture-of-experts model change this estimate?* It does not: experts change the weights and the compute per token, and the cache depends only on the attention layers.

## Common mistakes

- Multiplying by the 64 query heads instead of the 8 key-value heads.
- Dropping the factor of 2 for keys and values.
- Sizing every request at the model's maximum context.
- Mixing GB and GiB: 151.4 GiB is 162.5 GB.
