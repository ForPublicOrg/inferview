## Question

<p class="tiny">Reported as a technical screen topic (candidate report, linked above). The code and log are written for this problem.</p>

A GRPO loop for a maths model with a verifiable reward. Completions are padded to a fixed length, so tensor shapes match across steps.

```python
old_logp = None
for step in range(1, num_steps + 1):
    prompts = next(loader)
    groups = [policy.sample(p, n=8) for p in prompts]            # fresh rollouts, current weights
    rewards = [[verify(p, a) for a in g] for p, g in zip(prompts, groups)]
    adv = group_normalise(rewards)                                # (r - mean) / (std + eps) per group
    mask = completion_mask(groups)
    if old_logp is None:
        old_logp = policy.logprob(groups).detach()
    for epoch in range(2):
        logp = policy.logprob(groups)
        ratio = (logp - old_logp).exp()
        per_tok = -torch.min(ratio * adv, ratio.clamp(0.8, 1.2) * adv)
        loss = ((per_tok * mask).sum(-1) / mask.sum(-1)).mean()
        loss.backward(); opt.step(); opt.zero_grad()
        log(step=step, epoch=epoch, ratio_mean=ratio.mean(), clip_frac=clip_fraction(ratio),
            mean_len=mask.sum(-1).float().mean())
```

## Answer

The importance ratio is the probability of each sampled token under the policy being trained over its probability under the policy that sampled it. On epoch 0 of a fresh batch those are the same weights, so the ratio is exactly 1. `old_logp` is assigned only while it is `None`, which is step 1. From step 2 the loop divides by step 1's log-probabilities of step 1's completions, padded to the same shape so nothing crashes. The ratio now compares log-probabilities of unrelated sequences, about half the tokens sit outside the 0.8 to 1.2 band, clipped terms with the advantage's sign get zero gradient, and reward stops moving.

```diff
-    if old_logp is None:
-        old_logp = policy.logprob(groups).detach()
+    old_logp = policy.logprob(groups).detach()      # the weights that sampled this batch
```

Add an assertion that epoch 0's ratio mean is within a small tolerance of 1 on every step; this turns the whole class of bug into a crash on step 2.

**Ranking the rest.** Second: the per-sequence length normalisation. Dividing each completion's summed loss by its own length gives each token of a long completion a smaller weight, so a long wrong answer is penalised less per token than a short one; Dr. GRPO identifies this as a bias in the GRPO objective that inflates response length, strongest on incorrect outputs. The log's mean length rising from 612 to 731 is consistent with it but not proof, because the stale ratio also randomises updates. Third: the 31% of groups with identical rewards, which waste rollouts without corrupting anything. The two epochs are not a defect; DeepSeekMath's own run used one update per exploration stage, and two is a defensible choice that the clip exists to make safe.

**What the evidence lacks.** The log aggregates over correct and incorrect completions, so it cannot separate the length bias from noise. Before changing code: log length by correctness, log the epoch-0 ratio per step, and confirm on one batch that `policy.logprob` at sampling time matches the value the loop uses. Without those, fix the stale ratio and treat the length trend as unexplained.

**One fix per run or both.** Two defensible answers. Fix only the ratio, rerun, then decide on length normalisation from the new length-by-correctness curve: clean attribution, one extra run. Fix both now: saves a run on a tight compute budget, but if length or reward behaves oddly afterwards you cannot tell which change did it, and changing the normalisation also changes the effective learning rate per token. With the budget for one more run I fix the ratio alone, because it is certain and the length fix is a hypothesis. Failure mode of that choice: the length drift was hurting reward too, the rerun looks only partly healthy, and the team spends a second run discovering it; the mitigation is to log length by correctness in the rerun so the second decision is made on day one of it.

**Why the wrong choices are tempting.** Each names a real phenomenon. Multiple epochs do move the ratio, on epoch 1. Sampler and trainer numerics do differ when rollouts come from a separate inference engine, as small deviations everywhere. Length normalisation is a documented bias. Only the stale denominator explains a wrong epoch-0 ratio.

## Follow-ups

- The fix is in and epoch 0 reads 1.00 on every step, but clip fraction at epoch 1 is 0.35. Do you lower the learning rate, drop to one epoch, or widen the clip, and what do you give up with each?
- Rollouts move to a separate inference engine and epoch 0 now reads 0.97 to 1.03. What would make you correct for that mismatch instead of tolerating it?
- A colleague says the length growth is the model learning to reason and should not be "fixed". What measurement settles it without deciding by seniority?

## Common mistakes

- Reading a high clip fraction as a learning rate problem and lowering it.
- Computing `old_logp` with gradients attached, which makes the ratio's gradient wrong even when its value is right.
- Logging only mean reward, which hides the ratio, clip and length statistics that locate the bug.
- Shipping both fixes in one run and then attributing the result to whichever one the team believed in.
