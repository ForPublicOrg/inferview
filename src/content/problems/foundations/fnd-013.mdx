## Question

<p class="tiny">Reported as a technical screen question: debug a GRPO training loop and explain the importance ratio. The code and log below are written for this problem.</p>

A GRPO loop for a maths model with a verifiable reward. Sequences are padded to a fixed length, so tensor shapes match across steps.

```python
old_logp = None
for step in range(1, num_steps + 1):
    prompts = next(loader)
    groups = [policy.sample(p, n=8) for p in prompts]            # fresh rollouts, current weights
    rewards = [[verify(p, a) for a in g] for p, g in zip(prompts, groups)]
    adv = group_normalise(rewards)                                # (r - mean) / (std + eps) per group
    if old_logp is None:
        old_logp = policy.logprob(groups).detach()
    for epoch in range(2):
        logp = policy.logprob(groups)
        ratio = (logp - old_logp).exp()
        loss = -torch.min(ratio * adv, ratio.clamp(0.8, 1.2) * adv).mean()
        loss.backward(); opt.step(); opt.zero_grad()
        log(step=step, epoch=epoch, ratio_mean=ratio.mean(), clip_frac=clip_fraction(ratio))
```

The log:

```text
step 1  epoch 0  ratio_mean 1.00  clip_frac 0.00
step 1  epoch 1  ratio_mean 1.03  clip_frac 0.04
step 2  epoch 0  ratio_mean 0.71  clip_frac 0.46
step 2  epoch 1  ratio_mean 0.69  clip_frac 0.49
step 3  epoch 0  ratio_mean 1.42  clip_frac 0.52
groups with identical rewards (all 0 or all 1): 31%
mean reward: flat after step 2
```

What is the root cause of training stalling?

## Hints

<details class="hint"><summary>Hint 1</summary><p>On the first optimisation step over freshly sampled rollouts, what must the ratio between the current policy and the sampling policy be?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which lines run on every step, and which run only once?</p></details>

## Answer

The importance ratio is the probability of each sampled token under the policy being trained divided by its probability under the policy that generated it. Before any update on a fresh batch, those are the same weights, so the ratio is exactly 1 at epoch 0. Here `old_logp` is set only when it is `None`, which is only on step 1. From step 2 on, the loop divides by log-probabilities of step 1's sequences under step 1's weights, so the ratio is meaningless, most tokens hit the clip range (clip fraction near 0.5), clipped terms have zero gradient, and learning stalls.

The fix is to compute `old_logp` from the sampling policy for every new batch, before the epoch loop:

```diff
-    if old_logp is None:
-        old_logp = policy.logprob(groups).detach()
+    old_logp = policy.logprob(groups).detach()      # same weights that sampled this batch
```

Then assert in the training loop that epoch 0's ratio mean is 1 within a small tolerance; it turns this whole class of bug into a crash on step 2.

Why the wrong choices are tempting. Multiple epochs do move the ratio, which is exactly why PPO-style objectives clip it, but the drift appears on later epochs, not epoch 0. Sampler and trainer numerics are a real and common source of small mismatches when rollouts come from a separate inference engine, and they show up as ratios slightly off 1 everywhere. All-equal groups are a real GRPO weakness (zero advantage, wasted compute), but they reduce signal; they do not change the ratio.

## Follow-ups

- *Explain the clip.* min(ratio × A, clip(ratio, 1 - ε, 1 + ε) × A) stops one batch from moving the policy too far: once the ratio leaves the band in the direction the advantage favours, the gradient for that token is zero.
- *What would you do about the 31% of all-equal groups?* Filter or resample prompts that are always solved or never solved, or raise the group size for hard prompts, so each batch carries signal.
- *What other GRPO pitfalls would you check?* Length bias in how the loss is averaged over tokens, which Dr. GRPO documents, and a KL penalty or reference model that is accidentally the current policy.

## Common mistakes

- Reading a high clip fraction as "learning rate too high" and lowering it.
- Computing `old_logp` with gradients attached, which makes the ratio's gradient wrong.
- Logging only the mean reward, which hides the ratio and clip statistics that show the bug.
