## Question

A team's design review excerpt and dashboard for an invoice extraction service. It was approved last quarter. Review it as if you were on the approving panel: list every problem you find before opening the checklist.

```text
Invoice extraction v2: design notes (excerpt)

Model: hosted, structured outputs with a strict JSON schema (output_config.format).
Request: max_tokens=300, schema below, invoice text in the user turn.

Schema (abridged):
  reasoning            string   "Think step by step about the invoice before extracting."
  vendor               string
  invoice_date         string | null   format: date
  currency             enum ["USD", "EUR", "GBP", "INR"]
  total                number   minimum: 0   (SDK helper moved this into the description)
  line_items           array of { description: string, amount: number }

Downstream: posting service does RATES[obj["currency"]] and writes line items to the ledger.

Quality: since launch, schema validity is 100% (target 99.5%). Validity is measured over
responses with stop_reason "end_turn"; other stop reasons are logged as transport errors
and retried once.

Invoices: median 8 line items, largest seen 200.
Decision: no separate accuracy eval is needed; the schema guarantees correct structure and
the model is a frontier model.
```

## Answer

The headline flaw is that the metric cannot fail. Strict schema decoding removes every token that cannot extend a schema-valid output, so any response that finishes normally matches the schema. Measuring validity over responses with `stop_reason: "end_turn"` restricts the metric to exactly the responses that are valid by construction, and files the ones that can be invalid, refusals and `max_tokens` stops, under transport errors. The dashboard is 100% for the same reason a type checker never reports runtime errors.

The second-read flaws are in the details. `max_tokens=300` covers the median invoice; an invoice with 200 line items needs more than one token per line item, so large invoices truncate, and they are the ones worth the most. The first property asks the model to think step by step, and Claude's documentation says reasoning-style properties can trigger a `reasoning_extraction` refusal, recommending a short explanation instead. The posting service looks currencies up exactly, and enum casing is not guaranteed. The `minimum: 0` on totals is unsupported by the grammar compiler, and the SDK moved it into a description, so nothing enforces it.

Then the missing measurement. Nothing in the design measures whether the vendor, the date, the total or the line items are right, and the schema cannot express the one rule an accountant checks first: line items sum to the total. A null `invoice_date` on an invoice that has a date is schema-valid and wrong. And whether the constraint changes accuracy is disputed in public: Tam et al. reported lower reasoning accuracy under format restrictions, and dottxt's rerun with matched prompts found the opposite. Which applies to this model and these invoices is a measurement the team has not made.

The judgement call is the metric itself. Schema validity is a reasonable health metric for the plumbing, catching a schema the provider stopped accepting or a client bug, if it is reported next to the refusal and truncation rates and next to field accuracy. As the quality metric, it is a number that reports the decoder's guarantee back to the team.

## Follow-ups

- *The team has two weeks and one engineer. Which three checklist items do they fix first, and why those?*
- *Field accuracy on 300 audited invoices comes back at 97% on totals and 88% on line items. What do you change in the design, and what number goes on the dashboard instead of validity?*
- *Splitting large invoices into chunks fixes truncation but means line items from two calls must be merged. What can go wrong in the merge, and how would you test it?*

## Common mistakes

- Stopping at "validity is not accuracy" and missing that the denominator excludes the failures.
- Treating the retry on non-end_turn stops as a fix, when a deterministic truncation or a refusal fails the same way on retry.
- Asking for a larger max_tokens without asking how the output length scales with line items.
- Accepting the constraint as free on accuracy because the model is a frontier model.
