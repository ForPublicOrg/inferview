## Question

A compliance team embeds policy clauses to find conflicting rules across 40,000 documents. Their embedder, a bi-encoder fine-tuned with in-batch negatives on question and answer pairs, gives a cosine of 0.94 between "Contractors may access production data after manager approval" and "Contractors may not access production data, even with manager approval". The pair is flagged as a near-duplicate and merged. The scenario numbers are illustrative.

Explain why the model scores this pair so high, from how it was trained. Then propose a mitigation for this use and state its cost in latency and in labels.

## Hints

<details class="hint"><summary>Hint 2</summary><p>Ask whether the same index also serves search, where a query about a rule should retrieve both versions of it.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The loss rewards whatever separates a positive from the other passages in the batch, and those passages differ in topic, entities and vocabulary, not polarity. A sentence and its negation share topic and nearly every token, and the training data almost never placed one as the other's negative, so nothing in the gradient pushed them apart. For conflict detection I would score candidate pairs with a cross-encoder trained on contradiction, keeping the embedder only to find candidates; the cost is one cross-encoder pass per candidate pair and a few hundred labelled pairs to validate it.</p>
</Fragment>
<Fragment slot="long">
<p>Why. With in-batch negatives, each query's negatives are the positives of the other queries in the batch. In a batch of 128 random question and answer pairs, the closest negative is usually a passage on another subject. The loss is lowered fastest by encoding subject, entities and domain vocabulary, and a pooled representation of a sentence with one extra "not" barely moves along those directions. The model never had to separate "may" from "may not" to lower its loss, so it did not learn to. NevIR measured the result on retrieval: most models rank negation pairs at or below chance, and bi-encoders do worst.</p>
<p>The question is also asking the model for something it was not trained to answer. Retrieval training makes "relevant to the same question" close, and both clauses are relevant to "can contractors access production data?". For search, high similarity here is the right behaviour. For conflict detection it is the wrong one, so the fix belongs in the conflict pipeline, not in the shared embedder.</p>
<p>Two defensible mitigations:</p>
<ul>
<li><strong>Cross-encoder over candidate pairs.</strong> Keep the embedder to find candidates above a cosine threshold, then score each pair with a cross-encoder that reads both clauses together, trained or validated on contradiction. NevIR ranks cross-encoders best on negation. Cost: one forward pass per candidate pair. This is a batch job, so latency is throughput: 40,000 documents with an assumed 20 candidates each is 800,000 pair scores per full run, and incremental runs score only new clauses against their candidates. Labels: an off-the-shelf contradiction model needs only a validation set.</li>
<li><strong>Fine-tune the embedder with negation hard negatives.</strong> Generate negated versions of clauses, verify them, and add them as hard negatives. Cost: a few thousand verified pairs, a re-embed of the corpus, and a second index if search must keep the old behaviour, because the change makes "may" and "may not" far apart for search queries too. NevIR found fine-tuning on negation helps and still leaves a large gap.</li>
</ul>
<p>I would take the first. It keeps search unchanged, and its cost scales with candidates rather than with the corpus. The second is right when there is no budget for a second model in the pipeline and the embedder serves conflict detection only.</p>
</Fragment>

<li>Legal wants every merge reviewed by a person and engineering wants none. How do you set the threshold for automatic merge without deciding by rank?</li>

Labels, computed. To estimate the rate at which flagged pairs truly conflict within ±5 points at 95% confidence, the worst case needs 1.96² × 0.25 / 0.05² ≈ 384 labelled pairs. Label them before and after the change, from the same sampling frame, so the comparison is paired.

The constraint conflict is recall against reviewer load. A low cosine threshold for candidates sends more pairs to the cross-encoder and to reviewers; a high one misses conflicts phrased differently. Set it from the labelled sample: the threshold that keeps an agreed share of known conflicts, and the reviewer volume that follows from it.

The failure mode of the recommended answer: a cross-encoder trained on general contradiction data reads polarity well and scope poorly. "Contractors may not" against "staff may" is a scope difference, not a contradiction, and it will be flagged or missed depending on how the training data treated quantifiers. The validation set has to include scope and exception pairs, not only negations, or the measured accuracy overstates what reviewers will see.

## Follow-ups

- Search users complain that "can contractors access production data" now returns only the permissive clause. What changed, and which mitigation caused it?
- The embedder vendor ships a version that "understands negation". What evidence would you require before removing the cross-encoder?
- What other phenomena share the same root cause as negation in this training setup? Pick one your corpus has and say how you would test it.

## Common mistakes

- Blaming cosine similarity instead of the training objective; another metric over the same vectors has the same problem.
- Fine-tuning the shared embedder for conflict detection and breaking search for a use that did not need the change.
- Validating on negation pairs only and shipping a model that fails on scope and exceptions.
