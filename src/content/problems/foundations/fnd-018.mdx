## Question

You run a document-review feature on Claude Opus 4.6. The prices below are Anthropic's published list prices, checked 28 Oct 2026; every other number is a scenario input.

| Input | Value |
| --- | --- |
| Requests per month (scenario) | 3,000,000 |
| Static prefix per request: system prompt and tool definitions, measured on Opus 4.6 (scenario) | 6,000 tokens |
| Dynamic input per request (scenario) | 1,500 tokens |
| Output per request (scenario) | 400 tokens |
| Peak traffic (scenario) | 400 requests per minute |
| Prompt caching today | none: the prefix embeds a timestamp, so no two requests share it |
| Opus 4.6 and Opus 4.7 prices (published) | $5 per million input, $6.25 per million 5-minute cache writes, $0.50 per million cache hits, $25 per million output |
| Build tier limit, shared by every Opus 4.x model (published) | 5,000,000 input tokens per minute, 1,000,000 output tokens per minute |

Product wants Opus 4.7 because it wins on your review eval (scenario). Anthropic says Claude 4.7 and later use a tokenizer that produces approximately 30% more tokens for the same text, and that the increase depends on content. Finance will approve the migration only if the monthly bill does not rise.

Estimate the monthly bill after migrating with no other change, the input-token headroom at peak before and after, and the cache hit rate on the prefix at which the migration costs the same as today, once the timestamp is moved out of the prefix so it can be cached. State the token multiplier you assume.

<details class="hint"><summary>Hint 1</summary><p>Ask for the token counts of a sample of real requests under both model IDs, so the multiplier is measured on your content rather than taken from a vendor average.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>At a 1.3 multiplier the bill rises from $142,500 to $185,250 a month, because every token category grows and the prices are identical. Peak uncached input goes from 3.0M to 3.9M tokens per minute against a 5M limit. With the prefix cached, the migration breaks even at about a 54% hit rate on the prefix; the band for multipliers from 1.2 to 1.35 is 45% to 57%. The dominant term is the prefix, 6,000 of 7,900 tokens per request.</p>
</Fragment>
<Fragment slot="long">
<p>Today, per request: (6,000 + 1,500) × $5 / 1M + 400 × $25 / 1M = $0.0375 + $0.0100 = $0.0475. Times 3M requests is $142,500 a month.</p>
<p>After migrating with multiplier r = 1.3 and no other change, every count scales: 9,750 input tokens and 520 output tokens, $0.04875 + $0.0130 = $0.06175 per request, $185,250 a month, up $42,750. Prices did not change; the unit did.</p>
<p>Break-even with caching. The new prefix is 7,800 tokens. A hit costs $0.50 per million and a miss is now a cache write at $6.25, so with hit rate h the prefix costs 7,800 × (0.50h + 6.25(1 − h)) / 1M. The dynamic input (1,950 tokens, $0.00975) and output ($0.0130) are not cacheable. Setting the total equal to $0.0475 leaves $0.02475 for the prefix: 6.25 − 5.75h = 24,750 / 7,800 = 3.173, so h = 0.535. At r = 1.2 the same arithmetic gives 0.447; at r = 1.35, 0.574. Even at r = 1.0 caching needs a 22% hit rate to pay for its own writes.</p>
<p>Headroom. Today peak uncached input is 7,500 × 400 = 3.0M tokens per minute, 60% of the 5M limit. After migration without caching it is 9,750 × 400 = 3.9M, 78%. With caching at the break-even rate only writes and dynamic input count: (1,950 + 7,800 × 0.465) × 400 = 2.23M, 45%. Output at peak goes from 160,000 to 208,000 tokens per minute against 1,000,000. The Opus 4.x limit is shared across 4.5 to 4.8, so a canary on 4.7 draws from the same bucket as production on 4.6.</p>
<p>The decision. Two answers are defensible. Migrate with the cache restructure: it pays for itself above roughly 54% hits, buys the eval gain, and lowers rate-limit pressure; the cost is an engineering change to the prompt and a bill that now depends on traffic shape. Or keep 4.6 for this feature and move only the review types where the eval gain is large: the bill stays flat and nothing new can fail, at the cost of running two models and their prompts. The recommended path is the first, with a rollback trigger: if the measured hit rate stays below the break-even for a week, route the low-value review types back to 4.6.</p>
<p>The failure mode of that recommendation is the 5-minute TTL. A 54% average can hide a night shift where traffic per prefix falls below one request per five minutes, every request writes, and each prefix token is billed at 1.25 times the uncached rate on top of the 30% more tokens. Measure the hit rate by hour, not by month, and check whether a 1-hour write ($10 per million) is cheaper for the low-traffic hours.</p>
<p>Unreasonable choices: a multiplier of 1.0, which ignores the vendor's own statement; pricing misses at the base input rate once caching is on; caching the dynamic input; and using the 30% figure without counting tokens on your own documents under both model IDs, since the vendor says the increase depends on content.</p>
</Fragment>

## Follow-ups

- *Pushback:* "The cache restructure is a two-sprint change to a prompt three teams edit. Why not ship 4.7 now and fix cost later?" Answer with the monthly delta and who signs for it in the meantime.
- *Reversal:* the hourly hit rate is below break-even for eight hours a day. Do you route those hours to 4.6, buy 1-hour cache writes, or accept the cost, and what is each worth per month?
- *Operating:* two other features share the Opus 4.x rate limit and neither has caching. Whose headroom does your migration consume, and how do you tell them before it lands?

## Common mistakes

- Comparing price per token across the two models and concluding nothing changes.
- Forgetting that cache misses become writes priced above the uncached input rate.
- Taking the vendor's approximate multiplier as a constant instead of counting tokens on your own traffic with both model IDs.
- Reading a monthly average hit rate as if it held at every hour of the day.
