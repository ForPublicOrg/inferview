## Question

Scenario: you turn on structured outputs with a JSON schema for a ticket classifier, `category` as an enum of 12 values and `priority` as an integer. A teammate says, "Great, now the classifier can't be wrong." Which statement about constrained decoding is correct?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Where in the generation loop does the constraint act: before sampling each token, or after the response is finished?</p></details>
<details class="hint"><summary>Hint 2</summary><p>What happens if the response runs out of output tokens halfway through the object?</p></details>

## Answer

Constrained decoding edits the sampling step. The schema is compiled into a grammar; at each step the engine computes which tokens can extend the output so it still matches, and sets every other token's logit to minus infinity. A response that finishes therefore matches the grammar. XGrammar and similar engines make this fast by checking most of the vocabulary ahead of time and only a smaller context-dependent set at runtime.

It guarantees the shape, not the content. If the model's preferred continuation is ruled out, the mask picks among valid tokens, and the label it lands on can be wrong. Claude's documentation also lists ways the response can still miss the schema: the model refuses, or generation stops at max_tokens partway through the object. Some schema features are not supported by the grammar compiler. So the teammate is wrong twice: the category can be wrong, and the parse can still fail on truncation.

Why the wrong answers are tempting. "Values unchanged" assumes the mask only blocks garbage the model would never pick. "Fine-tuned on first use" mistakes the one-time grammar compile for training. "Retry until it parses" describes the technique many teams used before constrained decoding existed, and it still has a place for validation that a grammar cannot express.

## Follow-ups

- *How do you measure whether the classifier is right?* An eval set with gold labels; structured outputs make scoring easy, they do not replace it.
- *Can constraining the format lower accuracy?* It can when the format forces the model away from how it would naturally answer. Compare accuracy with and without the constraint on your eval.
- *What do you still validate in code?* Business rules the schema cannot express, such as a priority that must match the category, plus the truncation and refusal cases.

## Common mistakes

- Treating structured outputs as a correctness guarantee.
- Not handling the max_tokens and refusal cases, so the parser crashes in production.
- Using a prefilled assistant turn to force JSON; current Claude models reject it.
