## Question

Scenario: a support-ticket router calls a hosted model with a strict JSON schema: `category` is an enum of 14 values, `priority` an integer, `summary` a string, all required. The downstream consumer parses the response and does `ROUTES[obj["category"]]`. Which statement describes what the constraint guarantees about the responses the consumer will see?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which stop reasons the API can return with a 200 status for a structured request.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for a sample of responses whose category failed the dictionary lookup, and compare them character by character with the enum.</p></details>

## Answer

Constrained decoding compiles the schema into a grammar and, before each token is sampled, removes every token that cannot extend a string the grammar accepts. A response that runs to completion therefore matches the schema: the fields are present and each enum value is one of the declared strings as the grammar compiled them. Three things sit outside that guarantee. The values are whatever the masked distribution favoured, so a wrong category is as well-formed as a right one. A refusal returns with `stop_reason: "refusal"`, is billed, and may not match the schema. A `max_tokens` stop cuts the object off mid-way.

The consumer in the question has a fourth exposure that is specific to Claude's implementation: the documentation says the casing of enum and const strings is not guaranteed and recommends comparing case-insensitively. An exact dictionary lookup on `category` can fail on a response the API considers schema-valid.

Why the wrong options are tempting. "Valid JSON but missing fields" is accurate for JSON modes that only enforce syntax, which many teams used before strict schemas, and some providers still offer both. "Enum values exactly as declared" follows from how a grammar mask works in general, and is wrong for this provider in writing. "Refusals as empty objects" is what a team would design if it owned the API; the provider chose to let safety behaviour override the schema and to mark it in the stop reason.

## Follow-ups

- *The router drops any response it cannot parse. Where do refusals and truncations go instead, and who sees them?*
- *Category accuracy on the eval is 91% with the schema and 93% when the model answers in free text that you parse. Which do you ship, and what would change your mind?*
- *You move to a self-hosted engine with a different grammar backend. What do you re-test before trusting the same schema?*

## Common mistakes

- Treating schema validity as accuracy.
- Comparing enum values exactly.
- Handling only the success path, so refusals and truncations become parser exceptions in production.
