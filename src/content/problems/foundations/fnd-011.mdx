## Question

Scenario: a company has a support assistant on a hosted frontier model. Product asks for three things:

1. Answer questions from 3,000 help articles, which change weekly.
2. Answer in the house tone and always end with a structured JSON block the ticketing system parses.
3. Cut cost, because the assistant now handles a large share of all tickets.

The proposal on the table is "fine-tune a model on the help articles". Design the approach. For each requirement say whether it is a prompting, retrieval or fine-tuning problem, what you would build first, and what evidence would make you change course.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Separate knowledge (facts that change) from behaviour (tone, format, a narrow skill).</p></details>
<details class="hint"><summary>Hint 2</summary><p>What is the cheapest change that could pass your eval, and how would you know?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Fine-tuning a smaller model is also a cost lever, not only a quality lever.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The articles are knowledge that changes weekly, so they belong in retrieval, not in weights: retraining every week to keep facts fresh is slow, lossy and hard to audit. Tone and the JSON block are behaviour: start with a prompt plus structured outputs, and fine-tune only if the eval shows the prompt cannot hold them. Cost is where fine-tuning earns its place: once retrieval and the format are stable, distil the behaviour into a smaller model with LoRA, keep retrieval for the facts, and route hard tickets to the large model.</p>
</Fragment>
<Fragment slot="long">
<p>Step zero is an eval set: a few hundred real tickets with the right article, an acceptable answer and the expected JSON, scored on correctness, citation of the right article, tone and schema validity. Every later decision is "did this move the eval".</p>
<p>Requirement 1, the articles: retrieval. Index the articles, retrieve the relevant chunks per question and put them in the prompt with an instruction to answer from them and cite. Updates are a re-index, minutes not weeks, and you can show which article an answer came from. Fine-tuning on the articles would bake in a snapshot, cannot cite, and still hallucinates on details the weights store imperfectly.</p>
<p>Requirement 2, tone and JSON: prompting first. A system prompt with tone rules and a handful of examples, plus the provider's structured-output mode so the JSON block is constrained by a schema rather than hoped for. Put the static prefix (instructions, examples, schema) first so it can be cached, since cached prefix reads are billed at a fraction of the base input price. Fine-tune for tone only if the eval shows drift the prompt cannot fix.</p>
<p>Requirement 3, cost: this is where fine-tuning fits. With retrieval and format settled, collect the large model's good answers (filtered by the eval) and run SFT on a much smaller model, which is the distillation pattern DeepSeek used to make small models from R1. LoRA keeps the training cheap: the 2025 LoRA Without Regret results show it matching full fine-tuning on small and medium datasets when applied to all layers, and QLoRA fine-tuned a 65B model on one 48 GB GPU. Serve the small model behind a router that escalates low-confidence or schema-failing tickets to the large one.</p>
<p>What would change my mind. If retrieval recall is fine but answers still misstate facts, the problem is reading, not retrieving, and a stronger model helps more than fine-tuning. If the small model fails a whole category, route that category instead of retraining. If the domain has vocabulary the base model mangles, a small fine-tune on in-domain text can help retrieval and generation, measured on the eval.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How do you keep the fine-tuned model from going stale?</em> It holds behaviour, not facts, so it only needs retraining when the format or tone rules change; facts stay in the index.</li>
<li><em>How does the plan fail?</em> The distilled model copies the large model's mistakes. Filter training examples through the eval, not just through "the large model said it".</li>
<li><em>What is the alternative to fine-tuning for cost?</em> A cheaper hosted model with the same prompt, and prompt caching. Try it first; it costs an afternoon.</li>
</ul>
</Fragment>
</Depth>

The decision in one line per requirement: changing facts go to retrieval, format and tone go to prompts and constrained outputs first, and fine-tuning is for making a stable behaviour cheaper or more reliable once the eval says the prompt is the limit.

## Follow-ups

- *What data volume would you want before fine-tuning?* Enough examples that a held-out slice of them shows a gain over the prompted base model; start with a few hundred filtered examples and grow while the held-out score improves.
- *Privacy changes the answer how?* If tickets cannot leave your infrastructure, an open-weight model, possibly fine-tuned, may be required rather than optional.

## Common mistakes

- Fine-tuning on documents to "teach facts" and then fighting staleness and hallucinated details.
- Skipping the eval set, so the choice is made on demos.
- Fine-tuning for JSON format when constrained decoding already guarantees the shape.
- Treating fine-tuning as a quality lever only and missing its main use: making a narrow behaviour cheaper.
