## Question

Scenario: a team replaced its embedding model with EmbeddingGemma and, to save memory, kept only the first 256 of its 768 dimensions. They rebuilt the index on Monday. Since then, recall at 10 on their labelled query set dropped from 0.81 to 0.64, and reviewers say long boilerplate pages (terms of service, release notes) keep appearing in the top results.

The pipeline:

```python
DOC_PREFIX = ...     # document prompt from the model card
QUERY_PREFIX = ...   # query prompt from the model card

def embed_docs(texts):
    vecs = model.encode([DOC_PREFIX + t for t in texts])   # 768 dims, unit length
    return [v[:256] for v in vecs]                          # Matryoshka: keep 256

def embed_query(q):
    v = model.encode([QUERY_PREFIX + q])[0]
    return v[:256]

index = VectorIndex(metric="dot", dims=256, kind="hnsw", ef_search=64)
```

What they checked:

```text
corpus documents:            2,400,118
vectors in rebuilt index:    2,400,118   (index created Monday, empty before backfill)
norms of 1,000 stored docs:  min 0.78, median 0.89, max 0.97
brute-force top 10 vs HNSW top 10 on 50 queries: identical on 50 of 50
```

Which cause best explains the drop?

## Answer

The vectors were truncated without re-normalising. Each 768-dimension vector had length 1, but its first 256 values hold only part of that length, and how much varies by document: here between 0.78 and 0.97. The index ranks by dot product, and a dot product scales with the document's length, so documents that happened to keep more of their norm in the first 256 dimensions get a boost unrelated to relevance. EmbeddingGemma's card says to re-normalise after truncating, as do OpenAI's docs for manual shortening; gemini-embedding-2 is the exception that does it for you.

The fix is one line in both paths: divide each truncated vector by its norm before writing or querying, then rebuild the index. The query side matters less for ranking (one query's norm scales every score equally) but should be normalised too so scores are comparable across queries and thresholds keep working.

Why the other choices are tempting. Mixed vector spaces is the classic upgrade bug, ruled out because the index was empty before the backfill and the counts match. A missing query prefix is the second classic, ruled out by the code. ef_search is a real knob, ruled out because exact search returns the same results, which proves the approximate index is not the problem.

## Follow-ups

- *How would you catch this before it shipped?* An ingestion assertion that every vector's norm is 1 within a small tolerance, plus the recall check on the labelled set before switching reads.
- *Is 256 dimensions a reasonable choice once fixed?* Measure recall at 768, 512 and 256 on the labelled set; the card lists all three as supported truncations, and the right one is the smallest that keeps recall.
- *What if the index metric were cosine?* Cosine divides by the norms, so this bug would not have changed rankings. That is a reason to prefer cosine when you are not sure every writer normalises.

## Common mistakes

- Blaming the new model and rolling back without checking norms.
- Tuning the HNSW parameters first, which costs latency and fixes nothing here.
- Re-normalising only the queries.
