## Question

A team moved its document search from embedding model A to model B. Both output 1,024 dimensions, so the existing index accepted the new vectors without errors. All numbers below are from this scenario.

```yaml
# shared config, read by the ingest workers, the backfill job and the query service
embedding:
  model: model-b            # was model-a until Tuesday's deploy
  dims: 1024
index:
  name: docs-v1
  metric: cosine
  kind: hnsw
query_cache:
  key: sha256(query_text)
  ttl_hours: 24
```

```python
def backfill(batch):
    vecs = embed([c.text for c in batch])           # uses config.embedding.model
    index.upsert([(c.id, v, {"source": c.source}) for c, v in zip(batch, vecs)])
```

What they checked on Wednesday:

```text
chunks in corpus:                   3,200,000
backfill progress:                  38% (started Tuesday after the deploy)
recall@10, 500 labelled queries:    Monday 0.78   Tuesday 0.49   Wednesday 0.53
recall@10, cache misses only (Wed): 0.52
exact vs HNSW top 10, 50 queries:   identical on 48 of 50
model B on a separate index of a 5% corpus sample, same queries restricted to it:
                                    model B 0.81   model A 0.78
```

Which cause best explains the drop? Then say what you would do today and how you would run the migration again.

## Answer

The index holds two embedding spaces. Model A and model B were trained separately, so dimension k of one has no relationship to dimension k of the other, and a cosine between a B query and an A document is a number with no meaning. On Tuesday the query service switched to B through the shared config while 100% of documents were still A vectors; the backfill then started overwriting them in place. Recall tracks the backfill: lowest when almost nothing was migrated, slightly better at 38%. Matching dimensions are what let the bug ship, because a 1,024-dimension B vector is a valid write to a 1,024-dimension A index. Nothing in the upsert records which model wrote the vector, so the mix cannot be filtered out by a query.

What to do today. Stop the backfill, because every batch it writes makes the A index worse for A queries. Then choose:

- If a snapshot of docs-v1 from Monday exists, restore it, add ingest-time changes since Monday from the change log re-embedded with A, and pin the query service back to A. Recall returns to Monday's level within the restore time.
- If no snapshot exists, the 38% of documents now holding B vectors must be re-embedded with A before A queries can find them, or the team accepts reduced recall until a clean B index is ready.

How to run the migration. Build docs-v2 as a separate index, named for its model, with the model id and preprocessing version stored on every vector. Pin each writer and the query service to an explicit model per index rather than a shared default. Dual-write new and changed documents to both indexes from the moment the backfill starts, so docs-v2 is complete when the backfill catches up. Evaluate docs-v2 on the labelled queries, then move reads by flag, a fraction of traffic first, with the query cache key including the model id. Keep docs-v1 and dual-writes running for a rollback window, then delete docs-v1.

Costs, computed. A second copy at 1,024 float32 values is 3,200,000 × 1,024 × 4 bytes = 13.1 GB of raw vectors, before the HNSW graph. Re-embedding at an assumed 300 tokens per chunk is 960 million tokens; at text-embedding-3-small's listed $0.02 per million tokens, that is $19.20. The storage and the dual-write window cost more than the embedding calls.

The failure mode of this plan is the dual-write window: a document updated during the backfill is written to docs-v2 by the dual-write and then overwritten by an older copy from the backfill if the backfill reads from a snapshot. Order the backfill by a version or timestamp and skip any document whose docs-v2 copy is newer.

Why the wrong choices are tempting. The cache bug is real: cached A vectors would keep scoring against B documents for up to 24 hours after any switch, so the cache key needs the model id. It is not this incident, since cache misses alone show the same recall. HNSW degradation under heavy upserts is a real operational issue, ruled out because exact search returns the same results. A model that underperforms off-benchmark is the obvious suspect after any upgrade, ruled out by the 5% sample index.

## Follow-ups

- The corpus is 300 million chunks and a full re-embed takes nine days. What do you serve during those nine days, and what recall do you promise?
- Could you query both indexes, each with its own query embedding, and merge? What breaks when you merge by score, and what does merging by rank cost?
- Model B returns 1,024 dimensions and you want 512 to halve storage. What has to be true of B before you truncate, and what extra step does truncation need?

## Common mistakes

- Rolling the query service back to A while the backfill keeps writing B vectors.
- Treating equal dimension counts as compatibility.
- Leaving the model id out of the stored metadata and the query cache key, so the next mix is detectable only by a drop in recall.
