## Question

Scenario: a team self-hosts an open-weight model on vLLM and runs a 200-case regression suite every night at temperature 0. Most nights all 200 pass. Some nights two or three fail, and they are different cases each time. Nobody changed the prompt, the model or the code.

What the on-call engineer found:

```text
nightly run (shared server, live traffic):  case 117 output differs from golden
replay case 117 alone, 20 times:             20 of 20 identical, match golden
replay case 117 with 64 concurrent dummies:  6 of 20 differ
first differing token in the 6 failures:     token 41, 41, 41, 39, 41, 41
logprobs at token 41 (golden run):           " approved" -0.6912, " denied" -0.6951
```

Which cause explains the flaky failures?

<details class="hint"><summary>Hint 2</summary><p>Look at how close the two candidate tokens are at the first differing position.</p></details>

## Answer

The kernels are not batch-invariant. Floating-point addition is not associative, so summing the same numbers in a different order gives slightly different low bits, and the reduction order inside matrix multiplication, attention and normalisation kernels depends on the batch size. The batch size depends on how many other requests the server is handling. At token 41 the two best tokens are 0.0039 apart in log-probability, so a tiny change in the logits flips the argmax, and every token after it follows the new path.

This is the mechanism Thinking Machines measured in 2025: 1,000 temperature-0 runs of one Qwen3 model gave 80 distinct completions, all identical for 102 tokens. With batch-invariant kernels all 1,000 matched.

What to do, in order of cost. Make the eval robust: score the property that matters (approved or denied is a real decision here, so this case needs a better prompt or a constrained output, not luck), run flaky cases several times and track the pass rate. Look at near-ties: a logprob gap of 0.004 at a decision token means the model is uncertain, which is a product problem in itself. If bit-identical replay is a hard requirement on a self-hosted stack, use batch-invariant kernels and pay the throughput cost.

Why the wrong choices are tempting. "GPU randomness" is the folk explanation. "Server ignores temperature" happens with misconfigured clients, but would show early, frequent divergence even alone. "Prompt cache" sounds plausible because caches cause staleness, but prefix caches store keys and values, not answers.

## Follow-ups

- *Does the same apply to hosted APIs?* The mechanism does, and on current hosted reasoning models you often cannot set temperature at all: Claude rejects non-default values on current models, and OpenAI asks callers to drop it when reasoning is on.
- *How do you design the eval now?* Several runs per case, a pass-rate threshold per case, and alerts on changes in the rate over time rather than single failures.
- *Would a seed help?* Not for greedy decoding; nothing is being sampled. Seeds matter when temperature is above 0.

## Common mistakes

- Filing it as hardware randomness and closing the ticket.
- Retrying until the test passes, which hides that the model is close to a coin flip on a real decision.
- Promising determinism on a hosted API by setting temperature 0.
