## Question

Scenario: you classify incoming support messages into one of 12 categories, 1,000,000 messages a day. Each request is about 500 input tokens (instructions, the label list and the message) and the answer is a label of about 5 tokens. A frontier model gets 96% on your 300-message labelled set today.

Design the model choice. Compare a frontier hosted model, a small hosted model and a self-hosted open-weight model on quality, cost and latency, and say how you would decide and how you would roll out.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Work out daily input and output tokens first, then price them.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Does a 12-way classification need a reasoning phase?</p></details>
<details class="hint"><summary>Hint 3</summary><p>The comparison that matters is cost per correct label at the accuracy you need, not price per token.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Token math first: 500M input and 5M output tokens a day. At the frontier price of $4 / $20 per million that is about $2,100 a day; at a small model's $0.10 / $0.50 it is about $52.50. I would test the small hosted model and a small open-weight model on the labelled set, constrain the output to the 12 labels, and route only low-confidence messages to the frontier model. The winner is the cheapest setup that holds the accuracy target on our data, pinned to a snapshot and rolled out behind a flag.</p>
</Fragment>
<Fragment slot="long">
<p>Volume. 1,000,000 × 500 = 500,000,000 input tokens and 1,000,000 × 5 = 5,000,000 output tokens per day.</p>
<p>Hosted prices, checked 28 Oct 2026. Claude Opus 5.5 at $4 / $20: 500 × $4 + 5 × $20 = $2,100 per day, about $63,000 over 30 days. gpt-6-luna at $0.10 / $0.50: 500 × $0.10 + 5 × $0.50 = $52.50 per day, about $1,575 over 30 days. Two corrections before trusting either: count tokens in each vendor's own tokenizer, because the same prompt is a different number of tokens, and account for reasoning tokens, which are billed as output. A model that thinks for 200 tokens before a 5-token label has 41 times the output you priced. For a 12-way label, use the lowest effort setting the model allows or a non-reasoning model.</p>
<p>Self-hosted. An open-weight model such as gpt-oss-20b (3.6B active parameters, runs within 16 GB, Apache 2.0) can serve this on one GPU per replica. Its cost is GPU-hours, which you get by measuring throughput on your prompts and dividing daily volume by it; there is no per-token price to read off a page. It buys data control and fixed cost, and costs you an inference stack to operate. It also allows fine-tuning on your labels, which can lift a small model on a narrow task; the labelled set tells you whether it did.</p>
<p>Decision. Run every candidate on the 300-message set, with the output constrained to the label list, several runs each, and report accuracy per category, not just overall. Then a router: small model first; escalate to the frontier model when the label probability is low or the category is one the small model is weak on. If 10% escalate, the blended cost is roughly the small model's plus a tenth of the frontier's. Leaderboards do not enter into it; they are shaped by things unrelated to your 12 labels.</p>
<p>Rollout. Pin the exact snapshot id, shadow the new setup on live traffic, compare its labels with the current model's, review disagreements, then switch behind a flag with the old path kept for rollback.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Is 300 messages enough?</em> Each message is a third of a percentage point; a 1 to 2 point difference between models is within noise. Grow the set, especially for rare categories.</li>
<li><em>When would you skip LLMs entirely?</em> If a fine-tuned small encoder classifier on your labels matches the accuracy, it is cheaper and faster still. Test it as a candidate.</li>
<li><em>How do you catch drift after launch?</em> Sample a few hundred labels a week for human review and track the escalation rate; a rising rate is an early warning.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *What latency target changes the answer?* A tight per-message budget favours a small model close to the caller, possibly self-hosted in the same region.
- *How would prompt caching change the cost?* The instructions and label list are a static prefix repeated on every call; caching it cuts the price of most of the 500 input tokens.

## Common mistakes

- Picking by leaderboard rank.
- Comparing price per token across vendors without re-counting tokens.
- Forgetting reasoning tokens when pricing a short-output task.
- Reporting overall accuracy only, which hides a failing category.
