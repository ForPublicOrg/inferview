    import math, random

    def ref(Q, K, V, nq, nkv):
        g = nq // nkv
        out = []
        for t in range(len(Q)):
            row = []
            for h in range(nq):
                q = Q[t][h]
                s = [sum(a * b for a, b in zip(q, K[j][h // g])) / math.sqrt(len(q)) for j in range(t + 1)]
                m = max(s)
                w = [math.exp(x - m) for x in s]
                z = sum(w)
                row.append([sum(w[j] * V[j][h // g][c] for j in range(t + 1)) / z for c in range(len(V[0][0]))])
            out.append(row)
        return out

  solution: |
    import math

    def _attend(q, keys, values, scale):
        scores = [scale * sum(a * b for a, b in zip(q, k)) for k in keys]
        m = max(scores)
        w = [math.exp(s - m) for s in scores]
        z = sum(w)
        return [sum(w[j] * values[j][c] for j in range(len(values))) / z for c in range(len(values[0]))]

    def _group(n_q_heads, n_kv_heads):
        if n_kv_heads < 1 or n_q_heads % n_kv_heads:
            raise ValueError(f"{n_q_heads} query heads cannot share {n_kv_heads} key-value heads evenly")
        return n_q_heads // n_kv_heads

    class GQACache:
        def __init__(self, n_q_heads, n_kv_heads, head_dim):
            self.group = _group(n_q_heads, n_kv_heads)
            self.n_q, self.n_kv = n_q_heads, n_kv_heads
            self.scale = 1 / math.sqrt(head_dim)
            self.keys = [[] for _ in range(n_kv_heads)]      # keys[g][t]: one vector per KV head, never per query head
            self.values = [[] for _ in range(n_kv_heads)]

        def __len__(self):
            return len(self.keys[0])

        def step(self, q, k, v):
            for g in range(self.n_kv):
                self.keys[g].append(list(k[g]))
                self.values[g].append(list(v[g]))
            return [_attend(q[h], self.keys[h // self.group], self.values[h // self.group], self.scale) for h in range(self.n_q)]

    def full_attention(Q, K, V, n_q_heads, n_kv_heads):
        group = _group(n_q_heads, n_kv_heads)
        scale = 1 / math.sqrt(len(Q[0][0]))
        return [
            [_attend(Q[t][h], [K[s][h // group] for s in range(t + 1)], [V[s][h // group] for s in range(t + 1)], scale) for h in range(n_q_heads)]
            for t in range(len(Q))
        ]

## Question

<Callout kind="interview" label="Coding round">
Implement single-layer causal attention with grouped-query heads two ways: a full recompute, and a decode cache that takes one position at a time. The decode output at every step must match the recompute. Then tell me what you would change before this ran inside a serving engine.
</Callout>

Plain Python, standard library only.

- `GQACache(n_q_heads, n_kv_heads, head_dim)` holds the keys and values of one layer. `step(q, k, v)` receives the new position's `n_q_heads` query vectors and `n_kv_heads` key and value vectors, appends the keys and values, and returns `n_q_heads` output vectors.
- Query head h reads key-value head `h // (n_q_heads // n_kv_heads)`. A head layout that cannot be grouped evenly is a configuration error.
- `full_attention(Q, K, V, n_q_heads, n_kv_heads)` recomputes every position causally from scratch and returns `out[t][h]`.
- Scores are scaled by 1/√head_dim. Queries with components in the tens must not overflow.
- Memory: after T steps the cache holds keys and values for `n_kv_heads` heads and nothing else that grows with T. The checker counts the floats reachable from the cache object.

How you store the cache, and how you reject a bad layout, is yours to choose. The hidden tests compare every decode step with an independent recompute at several head layouts and check the memory bound.

## Answer

The reference stores one list of key vectors and one list of value vectors per key-value head. `step` appends the new position, then for each query head attends over the list of its group, so step t does O(t × head_dim) work per query head and never revisits earlier queries. The decode output equals row t of the recompute because causal row t reads keys 0 to t only, and the key and value of a position depend on that position's input alone. Nothing in a causal layer lets a later token change an earlier key, which is the whole reason the cache is valid.

The memory bound is what grouped-query attention is for. The common shortcut is to expand keys and values to one copy per query head as soon as they arrive, which is what Hugging Face's `repeat_kv` does inside the eager attention path; done inside the cache, it multiplies the stored floats by `n_q_heads / n_kv_heads`, 4 for Llama 3.1 8B's 32 query heads over 8 key-value heads, and fails the hidden check. Storing queries, scores or past outputs fails it too.

The stability requirement is the row maximum subtracted before `exp`. The hidden case with magnitudes near 60 gives scaled scores in the thousands; without the subtraction `math.exp` raises `OverflowError`.

Two storage layouts are defensible, and the choice is the one a serving engine makes.

- **Append per position (the reference).** Memory tracks the real sequence length, and a request that stops early wastes nothing. Cost: in a real engine the tensor equivalent is a reallocation and copy as the cache grows, and scattered storage defeats a fused kernel.
- **Preallocate to the maximum length.** One contiguous buffer per head, written in place; the decode kernel reads one strided block. Cost: every request reserves its maximum context up front, so a server that admits 128K-token requests reserves 16 GiB per sequence for Llama 3.1 8B in bf16 (2 × 32 × 8 × 128 × 2 bytes per token × 131,072 tokens) whether the request uses it or not.

The constraint conflict is memory utilisation against kernel simplicity, and engines resolved it with fixed-size pages: FlashAttention's `flash_attn_with_kvcache` accepts a block table from version 2.5. Recommendation for this exercise: append per head, because the tests measure correctness and live memory. Failure mode of that recommendation: the per-position lists are Python objects, so the real memory is several times the float count, and a cache that is correct under this checker would still not meet a byte budget. A page table fixes waste at the cost of a gather on every step and a page-size choice that leaves up to one partly used page per sequence.

Equality is within a tolerance, not bitwise, once the two paths sum in different orders. Here both paths call the same `_attend`, so they agree exactly; a fused prefill kernel and a split-K decode kernel do not.

## Common mistakes

- Expanding keys and values to one copy per query head inside the cache, which spends the memory GQA saved.
- Grouping heads by `h % n_kv_heads` instead of contiguous groups. Both run; only one matches checkpoints trained with contiguous grouping.
- Recomputing all keys and values every step and taking the last row, which is correct and quadratic per step.
- Comparing decode with recompute bitwise in a test suite that will later run a fused kernel.
