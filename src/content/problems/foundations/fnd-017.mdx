## Question

"We want to move our document-review step to a reasoning model because it scores better on our eval. The step has a p95 latency budget of a few seconds and a fixed monthly budget. What changes when you put a reasoning model in that path, and how do you keep it inside both budgets?"

## Hints

<details class="hint"><summary>Hint 1</summary><p>Where do the hidden reasoning tokens show up: in latency, in the bill, in the context window, or all three?</p></details>
<details class="hint"><summary>Hint 2</summary><p>What is the difference between a hard limit on output tokens and an effort setting?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A reasoning model spends extra output tokens thinking before it answers. Those tokens are generated one at a time, so they add latency; they are billed as output; and they occupy context. Output length now depends on the effort setting and the difficulty of the input, not just on the answer, so p95 latency and cost per request get a long tail. I would set the lowest effort that holds the eval score, cap output tokens with a margin, route only hard documents to high effort, and track latency and reasoning tokens per request.</p>
</Fragment>
<Fragment slot="long">
<p>What changes. All three major APIs bill thinking as output tokens. OpenAI's reasoning tokens are not visible but still occupy context, and its guide suggests reserving at least 25,000 tokens for reasoning and output when you start. Generation is sequential, so time to the final answer grows with the reasoning length. Effort is a soft knob (OpenAI reasoning effort, Claude effort levels with adaptive thinking, Gemini thinking_level); the output token limit is the hard ceiling, and hitting it can end a response before any visible output, which your code has to treat as a failure, not as an empty answer.</p>
<p>Why it can be worth it. Test-time compute trades latency for quality: Snell et al. found a smaller model with extra test-time compute beating a 14 times larger model on problems where the small one already had some success. That is the bet you are making, so measure it on your eval rather than assuming it.</p>
<p>Keeping inside the budgets. Measure the distribution of reasoning tokens and latency at each effort level on the eval set, then pick the lowest effort that holds the score. Route: classify documents as routine or hard, cheapest path first. Set the output cap with margin above the observed p99 and alert when responses hit it. Stream the final answer if the caller can use partial output. Put the static instructions first so the prefix can be cached. Budget per request, not per token, because effort changes tokens per request.</p>
<p>One more caution. Visible reasoning is a summary or hidden, and it is often not a faithful account of how the model reached its answer; Anthropic found Claude 3.7 Sonnet mentioned a hint it had used about a quarter of the time. Do not build audit or compliance logic on the thinking text.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you set the output cap?</em> From the measured distribution at the chosen effort, with margin, and with a metric for how often it is hit.</li>
<li><em>When is a reasoning model the wrong choice?</em> Short-label tasks and tight interactive latency, where a non-reasoning or lowest-effort setting gets the same score.</li>
<li><em>How does this affect your eval?</em> Run each case several times at the chosen effort, since reasoning length varies, and track pass rate and latency together.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *What is the difference between max_tokens and effort?* The first is a hard stop that can truncate; the second is guidance that shifts how long the model tends to think.
- *Can you see what the model reasoned about?* Partly at best: a summary or nothing, depending on the vendor, and not necessarily faithful.

## Common mistakes

- Pricing a reasoning model on visible output tokens only.
- Setting a tight max_tokens to control cost and then shipping truncated or empty responses.
- Treating the thinking text as an audit log.
