## Question

<Callout kind="interview" label="Technical screen">
Explain FlashAttention, the KV cache and RoPE. For each, say which term of a serving cost model it changes and where it would appear in a profile. Then: your 64K-context endpoint has a slow time to first token on long prompts and a decode batch that stops growing well before the GPUs are busy. You get one of the three areas to invest in this quarter. Which, and what would change your mind?
</Callout>

The endpoint (a scenario): Llama 3.1 8B in bf16 on H100s, a 2,000-token system prompt shared by every request, user documents from 1K to 60K tokens.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for a profile of one long prefill and one decode step at a full batch, split by kernel.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which attention kernel version the engine runs today and on which GPU.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what share of prompt tokens are identical across requests and at the same positions.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>FlashAttention computes exact attention in on-chip tiles so the n × n scores never go to HBM; it changes the prefill attention term from memory traffic to compute and shows as one fused kernel instead of matmul, softmax, matmul. The KV cache stores keys and values so decode does linear work per token; it sets resident memory per token, 128 KiB for this model, and shows as allocator memory and as decode attention time growing with context. RoPE rotates queries and keys by position; its kernel cost is negligible, but because cached keys are already rotated, a cached prefix is reusable only at the same positions. For this endpoint I would invest in the cache: prefix caching for the shared 2,000 tokens and paged allocation, because the batch limit is memory. If the long-prompt profile shows attention kernels below 35% of peak, the kernel upgrade comes first.</p>
</Fragment>
<Fragment slot="long">
<p><b>FlashAttention.</b> The standard kernel writes the score matrix to HBM, reads it for the softmax, writes the weights and reads them again for the product with V. FlashAttention keeps one tile of queries in SRAM, streams key and value tiles past it with a running maximum and normaliser, and writes only the output. It is exact and does at least as much arithmetic. In the cost model it moves the prefill attention term toward its compute floor, O(n² d) per head, and removes an O(n²) memory term. In a profile, the attention kernels in prefill change from several to one, and the time share they take at 60K tokens is the number to watch. The FlashAttention-3 paper reports that FlashAttention-2 reaches 35% utilisation on H100, and its own FP16 kernel up to 75%, a 1.5 to 2.0 times speedup.</p>
<p><b>The KV cache.</b> Each layer stores the key and value of every past token so a decode step computes one new query against them. Per token: 2 × 32 layers × 8 KV heads × 128 × 2 bytes = 131,072 bytes, 128 KiB. A 60,000-token session holds 7.3 GiB (60,000 × 128 KiB), so the cache, not the weights, sets how many sessions decode together. In a profile it shows twice: as resident memory in the allocator, and as decode attention time that grows linearly with context, because every step reads the whole cache. Decode at long context is a bandwidth problem; Flash-Decoding exists because a single long row leaves most of the GPU idle unless the cache is split along the sequence.</p>
<p><b>RoPE.</b> Queries and keys are rotated by an angle set by absolute position, so the score depends on the distance between tokens. The rotation is an elementwise operation, usually fused into the projection or the attention kernel, and almost invisible in a profile. What it changes is reuse and range. Keys are cached after rotation, so a cached prefix can be reused only by a request that has the same tokens at the same positions; the shared 2,000-token system prompt qualifies, a shared document placed after a per-user preamble does not. And the context range is a RoPE setting: Llama 3.1's config stretches 8,192 original positions by a factor of 8 to 131,072, which changes quality at the far end, not cost.</p>
<p><b>The decision.</b> Two answers are defensible. Invest in the cache: prefix caching for the shared prompt removes 2,000 tokens of prefill from every request and 250 MiB (2,000 × 128 KiB) of duplicated cache per session, and paged allocation stops reserving 64K per session. Cost: a cache-aware scheduler and eviction policy, and a hit rate that depends on product teams not editing the system prompt per user. Or invest in the kernel: moving from FlashAttention-2 to FlashAttention-3 targets the slow first token directly. Cost: it does nothing for the decode batch limit, and FP8 attention needs its own quality check. The constraint conflict is first-token latency on the long requests against throughput on all of them. I would take the cache, because the batch limit is the larger cost and is memory, and the shared prefix is a free win.</p>
<p><b>Failure mode of the recommendation.</b> Prefix caching makes the first token fast for requests that hit and unchanged for those that miss, so the latency distribution splits in two and an average hides it; and one per-user string at the top of the system prompt turns the hit rate to zero without any error. Monitor the hit rate as an alert, not a dashboard.</p>
</Fragment>

The three mechanisms land in three different places: FlashAttention in prefill compute time, the KV cache in resident memory and decode bandwidth, RoPE in what can be reused and how far the model can read. A cost model that has one line for "attention" cannot tell you which to fix.

## Follow-ups

- *Your decode batch is limited by memory at 24 concurrent 60K sessions. Is an 8-bit KV cache or a model with a smaller cache per token the better lever, and who has to sign off on each?*
- *A colleague says FlashAttention makes long prompts linear in cost. Which measurement settles it in front of the team?*
- *Placing the shared document before the per-user preamble would make it cacheable. What does that change in the model's behaviour, and how would you test it before shipping?*

## Common mistakes

- Saying FlashAttention reduces the KV cache. It changes how scores are computed, not what is stored for decode.
- Treating RoPE as a cost item. Its cost is in reuse and long-context quality.
- Assuming any repeated text is a cache hit, regardless of where it sits in the prompt.
- Calling the KV cache a prefill optimisation. Prefill computes it; decode is what it saves.
