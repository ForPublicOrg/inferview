  solution: |
    from collections import Counter

    def train_bpe(word_freqs, num_merges):
        vocab = {tuple(w) + ("</w>",): f for w, f in word_freqs.items()}
        merges = []
        for _ in range(num_merges):
            pairs = Counter()
            for symbols, freq in vocab.items():
                for pair in zip(symbols, symbols[1:]):
                    pairs[pair] += freq
            if not pairs:
                break
            best = min(pairs, key=lambda p: (-pairs[p], p))
            merges.append(best)
            vocab = {merge(symbols, best): freq for symbols, freq in vocab.items()}
        return merges

    def merge(symbols, pair):
        out, i = [], 0
        while i < len(symbols):
            if i + 1 < len(symbols) and (symbols[i], symbols[i + 1]) == pair:
                out.append(symbols[i] + symbols[i + 1])
                i += 2
            else:
                out.append(symbols[i])
                i += 1
        return tuple(out)

    def encode(word, merges):
        symbols = tuple(word) + ("</w>",)
        for pair in merges:
            symbols = merge(symbols, pair)
        return list(symbols)

## Question

<Callout kind="interview" label="The round, as public question lists describe it">
"Implement byte-pair encoding: training and encoding, from scratch." It appears in public interview question lists and in a candidate report from a technical screen.
</Callout>

Write two functions.

`train_bpe(word_freqs, num_merges)` takes a dictionary from word to count, for example `{"low": 5, "lower": 2, "newest": 6, "widest": 3}`, which is the toy corpus from the original BPE paper. Split every word into characters and append an end-of-word symbol `"</w>"`. Then, up to `num_merges` times: count every adjacent pair of symbols, weighting each pair by the count of the word it appears in; pick the most frequent pair; merge it everywhere into one symbol; record it. On a tie, pick the pair that sorts first as a tuple of strings. Stop early when no pairs are left. Return the merges in order.

`encode(word, merges)` splits a word the same way and replays the merges in the order they were learned.

Python standard library only. The tests run in your browser.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Keep the corpus as a dictionary from a tuple of symbols to its count, so each distinct word is processed once per merge.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For the tie rule, `min(pairs, key=lambda p: (-pairs[p], p))` picks the highest count and then the smallest pair.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Write one `merge(symbols, pair)` helper that scans left to right and use it for both training and encoding.</p></details>

## Answer

The reference solution keeps the corpus as a mapping from a tuple of symbols to a count. Each round it counts pairs with a `Counter`, adding the word's frequency rather than 1, picks the best pair with the tie rule, and rebuilds the mapping with that pair merged. `encode` applies the merges in training order, which is the detail interviewers check most: a merge learned later can depend on one learned earlier, so applying them longest-first or in any other order gives different splits.

On the toy corpus the first three merges are `e+s`, `es+t` and `est+</w>`. Pairs `e,s` and `s,t` both occur 9 times (6 in newest plus 3 in widest), and the tie rule picks `e,s`, which matches the order in the paper. Then `l+o` and `lo+w` at 7 (5 in low plus 2 in lower).

An unseen word such as "lowest" still encodes, into `low` and `est</w>`, because it is built from learned pieces. Characters never seen in training stay as single symbols. In byte-level BPE, which production tokenizers use, the base alphabet is the 256 byte values, so nothing is ever out of vocabulary; rare text just becomes more tokens.

Complexity: each merge round scans the whole corpus, so training is O(merges × corpus symbols). Production trainers keep pair counts in a priority queue and update only the words that contain the merged pair.

## Follow-ups

- *How does encoding scale to a 100,000-merge vocabulary?* Replaying every merge is slow. Real encoders look up each adjacent pair's merge rank and repeatedly merge the lowest-ranked pair present, which gives the same result.
- *Why byte-level instead of characters?* A byte alphabet of 256 symbols covers every string, so there is no unknown-token case.
- *What does the end-of-word marker buy you?* "est" at the end of a word and "est" inside a word become different symbols. GPT-style tokenizers get a similar effect by keeping the leading space inside the token.

## Common mistakes

- Counting each distinct word once instead of weighting by its frequency.
- Encoding by greedy longest match instead of replaying merges in training order.
- Mutating the dictionary while iterating over it.
- Forgetting to stop when no pairs remain, which raises on an empty `Counter`.
