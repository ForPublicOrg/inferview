## Question

<Callout kind="interview" label="Design review">
The kernel section of a capacity plan for a 64K-context service lists five statements about FlashAttention (versions 1 and 2) that the plan's cost model relies on. Exactly one of them is false. Which one?
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each statement, ask which measurement would refute it: a FLOP counter, a memory profiler, or a numerical diff against a reference kernel.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the backward pass has to do when the forward pass did not keep something.</p></details>

## Answer

The false statement is the one about arithmetic. FlashAttention computes the same softmax attention as the standard kernel, but in tiles held in on-chip SRAM, so the n × n score matrix is never written to or read back from high-bandwidth memory. The backward pass needs those scores, so it recomputes them from the stored inputs and the per-row softmax statistics. That recomputation adds floating-point operations; the paper reports that the kernel still runs faster because attention at these sizes is limited by memory traffic, not by arithmetic. FlashAttention-2 kept the same algorithm and reports 50 to 73% of the A100's theoretical peak FLOPs/s against 25 to 40% for the first version, by reorganising the work, not by removing any of it.

Why the true statements get picked. "Not an approximation" sounds too good when a kernel is several times faster, and engineers who have seen sparse or low-rank attention variants assume this is one of them; it is exact, and the only difference is summation order. Recomputation in the backward pass sounds wasteful, so it is read as a claim about an optional mode; it is the design. The quadratic statement is doubted because "FlashAttention made long context cheap" is a common summary; it made long context fit in memory and run closer to peak, and the O(n² d) work in Table 1 of the 2017 paper is unchanged. The linear-memory statement is the paper's own claim and holds because only the row statistics persist between tiles.

What it changes in the capacity plan: compute per prefill token still grows with context, so a cost model that drops the quadratic term after adopting the kernel underestimates long-prompt cost. Memory for attention scores drops out of the plan, which is why the KV cache, not the score matrix, is the long-context memory term.

## Follow-ups

- *The plan's author says the quadratic term is negligible below 32K tokens for this model. What would you compute to check, and from which config fields?*
- *A numerical diff against the reference kernel shows differences in the fourth decimal of bf16 outputs. Do you block the rollout, and what would you need to see to approve it?*
- *The service moves to H100s. Which of the five statements would you re-check against the FlashAttention-3 paper, and why only that one?*

## Common mistakes

- Treating FlashAttention as an approximate attention method.
- Removing the quadratic compute term from a long-context cost model after adopting the kernel.
- Reading "fewer HBM accesses" as "fewer operations".
