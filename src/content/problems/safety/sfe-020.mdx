## Question

<Callout kind="interview" label="Design round, 45 minutes">
Design a red-team exercise to find the security risks that AI-generated code has introduced into your production codebase. Say what you look for, how you find it, what counts as a finding, what you give up, and what you hand to leadership at the end.
</Callout>

The constraints (constructed for this problem):

- Three security engineers for six weeks.
- Last quarter 9,000 pull requests merged into the monorepo, which holds the payments and customer-data services. About 35 percent carry a coding agent's co-author trailer. Engineers also use editor completions, which leave no trace in the history.
- A static analysis scanner already runs in CI, and its findings are triaged weekly.
- Leadership will not restrict agent use during the exercise.
- The VP of engineering asks that no finding be reported against a named team.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what leadership will do with the result: change a policy, fund a control, or answer a board question.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which of last quarter's pull requests could have been agent-written without saying so, and how you would know.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the scanner's finding rate per merged pull request for last quarter, and how many of those findings were confirmed.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Do not try to prove that agent-written code is worse; six weeks of three people cannot measure that by review. Red-team the surfaces where agent mistakes are exploitable, with hypotheses specific to how agents fail: dependencies that did not exist before the pull request, handlers that skip the ownership check, tests and checks loosened to make a change pass, secrets in fixtures, string-built queries and commands, and agent configuration committed to the repository. Use the co-author trailer to prioritise, never to scope. A finding is something exploitable in staging or a concrete code path to it; every confirmed class becomes a CI check. Hand leadership an exercise report by risk class, not by team, with the checks that now run.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The decision: measure or attack.</strong> Two answers are defensible.</p>
<ul>
<li><strong>Measure.</strong> Sample agent-attributed and unattributed pull requests, review both, and compare the rate of security defects. It answers the question leadership will ask. Cost: suppose 2 percent of pull requests carry a security defect and you want to detect a doubling to 4 percent with 80 percent power at the 5 percent level. That needs about 1,140 pull requests per group, 2,280 reviews; at an hour each that is 3.2 times the 720 hours the team has. And the groups are not clean: completions leave no trace, and the trailer can be switched off (Claude Code's <code>attribution</code> setting hides it), so the unattributed group contains agent code too.</li>
<li><strong>Attack.</strong> Pick the risk classes agents plausibly introduce, find every instance in the codebase regardless of who wrote it, and try to exploit each in staging. It finds exploitable problems and leaves checks behind. Cost: it cannot say whether agents made things worse.</li>
</ul>
<p>I would attack, and run the measurement only where it is nearly free: the scanner's findings per merged pull request, split by trailer, over the whole quarter. That is cheap because it is automated, and it is labelled for what it is, a comparison of what the scanner sees between two leaky groups. The conflict is the budget against the question leadership wants answered; I trade the answer to "is it worse" for an answer to "what can be exploited, and is it now checked".</p>
<p><strong>The hypotheses, each with a way to find candidates.</strong> The published evidence is old or narrow: Pearce et al. found about 40 percent of 1,689 Copilot programs vulnerable in 2021 scenarios built around high-risk CWEs, and Perry et al. found assisted participants wrote less secure code while believing it more secure. Neither measures 2026 agents in this codebase, so they are sources of hypotheses, not estimates.</p>
<ul>
<li><strong>Dependencies that should not exist.</strong> Spracklen et al. report hallucinated package names in at least 5.2 percent of commercial models' samples on average and 21.7 percent of open-source models', 205,474 unique names in all. List every dependency added last quarter and flag any first published on its registry shortly before the pull request, with one maintainer and few downloads. These are cheap to check exhaustively.</li>
<li><strong>Missing ownership checks.</strong> Handlers added or changed last quarter that take an object id. In staging, call each with an id belonging to another tenant.</li>
<li><strong>Loosened checks.</strong> Diffs that skip or delete tests, weaken assertions, widen CORS, disable certificate verification or catch and ignore an authorization error. An agent told to make a build pass has a direct incentive to do these.</li>
<li><strong>Secrets and fixtures.</strong> Credentials copied into tests, examples and configuration.</li>
<li><strong>Injection sinks.</strong> SQL, shell and template strings built from input in new code paths.</li>
<li><strong>Agent configuration in the repository.</strong> Committed hooks, permission files and tool server definitions, which run with the next engineer's agent and credentials.</li>
</ul>
<p><strong>The schedule.</strong> Week 1: rules of engagement, candidate queries for each class, the scanner comparison. Weeks 2 to 4: exploit attempts in staging, highest-impact services first, the trailer used to order candidates within a class. Week 5: each confirmed class becomes a check (a scanner rule, a dependency-age gate, a lint on test deletions in the same diff as a fix). Week 6: retest, report.</p>
<p><strong>What counts as a finding.</strong> A path from an input an attacker controls to an impact, demonstrated in staging or traced in code with the file and line, with a severity and an owner service. A pattern with no reachable path is a hardening item, tracked separately. The VP's request is met by reporting by class and service, and it costs one thing: without team-level data you cannot target training, and you say so.</p>
<p><strong>Where this fails.</strong> The exercise finds what its hypotheses predict. An agent-introduced class nobody listed, such as a business rule implemented subtly wrong in a refund path, gets no query and is missed. Ordering by trailer biases the work towards teams that leave the trailer on, which may be the teams most careful about agent output. And the checks written in week 5 go stale as agents change; a dependency-age gate catches today's hallucinated names and nothing about tomorrow's typosquats with real download counts.</p>
<p><strong>What you give up.</strong> Any claim about whether agents made the codebase less secure. Per-team findings. Depth on code paths outside the six classes. The agents' own permissions and sandboxing, which deserve their own exercise and are named as out of scope.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The CTO wants one number: is agent-written code more or less secure than ours? Your plan does not produce one. What do you say, and what would it cost to produce one that you would sign?</em></li>
<li><em>What result from this exercise would make you recommend restricting agent-written changes in the payments service?</em> Confirmed exploitable findings concentrated in a class the new checks cannot catch, such as missing ownership checks, recurring after the checks ship.</li>
<li><em>Two senior engineers disagree: one says to scope the exercise to trailer-attributed changes only, the other says attribution is irrelevant. How do you decide without deciding by rank?</em> Measure how leaky attribution is first: sample unattributed pull requests and ask their authors whether an agent wrote them.</li>
</ul>

### The written artefact

Rules of engagement, signed by the heads of security and engineering before week 2.

- **Scope:** code merged last quarter in all services; exploit attempts only in staging; production data is never read or written.
- **Stop condition:** a finding exploitable in production goes to incident response within the hour and leaves the exercise.
- **Reporting:** by risk class and service, never by team or engineer; agent attribution reported only in aggregate.
- **Outputs:** confirmed findings with severity and owner service, the checks added to CI with their false-positive rate on last quarter's history, and a list of what was not tested.
- **Accepted risk, in writing:** classes outside the six hypotheses are untested; the scanner comparison by trailer is not a measure of agent code quality.

## Follow-ups

- *Halfway through, you find dependencies added last quarter that did not exist on the registry a week before their pull request. One is installed in production. What do you do in the next hour, and who decides?*
- *Your dependency-age gate blocks a legitimate new internal package every week. Do you keep it, loosen it, or replace it, and what do you accept in writing?*
- *Six months later the agent share is 70 percent. Which part of this exercise do you rerun, and which part do you retire?*

## Common mistakes

- Scoping by the co-author trailer, as if unattributed code were human-written.
- Promising leadership a comparison of defect rates without sizing the sample it needs.
- Treating the 2021 and 2022 studies as estimates for current agents.
- Ending with a findings list and no checks, so the same classes come back next quarter.
- Reporting by team, which turns the exercise into a performance review and teaches engineers to remove the trailer.
