## Question

<Callout kind="interview" label="Concept">
"Legal wants a complete record of every prompt and response for dispute handling. Our tracing is already OpenTelemetry with the GenAI conventions, and turning on content capture is one environment variable. Do we flip it? If not, what do we do instead, and who can read what?"
</Callout>

The setup, as a scenario: a support assistant for EU and US business customers, with an agent that calls a CRM lookup tool and a retrieval tool. Traces go to a hosted tracing vendor that keeps them 30 days; all forty engineers can read them; traces are head-sampled at 10%. Content capture is at its default, off. Counsel asks for two years of records. The privacy team handles erasure requests and wants nothing new holding PII.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what share of conversations the tracing backend receives today, and what legal needs when a dispute names one specific conversation.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which places a customer's address can come to rest after one CRM lookup, and who can read each of them.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask counsel whether a record that can be deleted on an erasure request still serves their purpose, and who decides when the two conflict.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Do not make the tracing backend the legal record. Telemetry is sampled and best-effort: with 10% head sampling, content on spans covers about one conversation in ten, kept 30 days, readable by forty people, which fails legal and privacy at once. Write the record from the application into its own store, in region, encrypted, readable by legal with audited break-glass access for engineers, with retention and erasure handled per user. Keep production telemetry at NO_CONTENT and put the conversation and message ids on spans so the two can be joined. If engineers need content to debug, give them a separate, short-lived, redacted path rather than turning the vendor into a copy of the record.</p>
</Fragment>
<Fragment slot="long">
<p><b>What the variable does.</b> <code>OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT</code> defaults to <code>NO_CONTENT</code> and accepts <code>SPAN_ONLY</code>, <code>EVENT_ONLY</code> and <code>SPAN_AND_EVENT</code>. Flipping it puts input and output messages, system instructions, tool call arguments and results, and retrieval query text onto telemetry. Those tool results are where the CRM lookup's customer address lands, so the trace holds PII the user never typed. Tool definitions are not governed by the flag and go out either way, which matters if anyone has put real customer examples in a tool description.</p>
<p><b>Why it fails legal.</b> Attributes ride on spans, and spans exist for the sampled 10%. The conventions do describe an upload hook that runs regardless of the sampling decision and records reference attributes such as <code>gen_ai.input.messages_ref</code> pointing at stored content, but they leave retention, access and the storage layout to you, and the hook sits behind a bounded in-process queue (default size 20). A record that legal relies on in a dispute should not depend on an instrumentation library's queue behaviour, which the conventions do not specify when the queue is full.</p>
<p><b>Why it fails privacy.</b> Thirty-day retention is too short for legal and too long for content forty people can read. An erasure request then has to reach a vendor's trace store, keyed by trace id, not by customer.</p>
<p><b>What to build.</b> The application writes the conversation record (messages, tool calls with arguments and results, the model and prompt version) from the same objects it sends to the model, through a durable outbox so a crash does not lose it. The store lives in the customer's region, encrypts at rest, grants read to legal, and gives engineers time-limited access with a reason and an audit entry. Retention is counsel's number; erasure finds records by user id, and counsel decides which records are under legal hold. Spans carry the ids, not the content.</p>
<p><b>Debugging.</b> If engineers need content, a redacted copy with short retention (seven to fourteen days is defensible; long enough to cover a week of incidents) in a restricted store, never in the vendor's general UI. Redaction is partial: Presidio states it cannot guarantee finding everything. Hashing an identifier is not anonymisation when the value space is small: there are at most ten billion ten-digit phone numbers, so anyone with the hash can hash every candidate. Use a keyed hash or a tokenisation service, and treat the output as personal data still.</p>
<p><b>Two defensible designs.</b> The application-written record above costs a second write path, and engineers lose content in their normal tools. The alternative is the conventions' upload hook writing to a restricted, in-region bucket, with refs on spans: one mechanism serves debugging and legal, and the content never enters the vendor. Its cost is that the legal record now depends on telemetry plumbing, so every instrumentation upgrade is a change to a legal record, and the GenAI conventions are still marked Development, so attribute names can change between releases. I would build the application record and keep the hook for the debugging copy.</p>
<p><b>Where the recommended design fails.</b> The application records what it passed to the client library. If an agent framework adds messages of its own (a retry with a repair prompt, a tool result it summarised), the record and what the model saw diverge, and legal holds a record of the wrong conversation. Write the record at the lowest layer you own, ideally the model gateway, and test that a replay from the record reproduces the request byte for byte.</p>
</Fragment>

## Follow-ups

- *A tool parameter carries an email address and the MCP server marks it with `x-mcp-header` so the gateway can route on it. What is wrong?* Header values are visible to every intermediary and land in their logs; the MCP spec says not to mark PII that way.
- *The evaluation team wants a golden set built from production conversations. Which store do they draw from, and what happens to the set when a user is erased?*

## Common mistakes

- Flipping content capture on and calling the trace store the legal record, without noticing it holds the sampled tenth.
- Redacting the prompt and forgetting tool arguments and tool results, which is where looked-up PII arrives.
- Treating a plain hash of a phone number or email as anonymous.
- Giving every engineer the same access to content as legal because it is the same data.
- Writing the record from the application while an agent framework adds messages the record never sees.
