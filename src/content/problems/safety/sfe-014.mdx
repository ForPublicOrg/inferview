## Question

<Callout kind="interview" label="As an interview question list phrases it">
"How do you handle PII in LLM inputs and outputs?"
</Callout>

Answer for a product that sends user messages to a third-party model API, logs requests for debugging, and traces agent runs in a vendor observability tool.

## Hints

<details class="hint"><summary>Hint 1</summary><p>List every place the data comes to rest, not just the prompt. The logs and traces usually keep the full text.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Is a hashed phone number anonymous? How many ten-digit numbers are there?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Map where PII flows (the prompt, the model vendor, your logs, your traces, any eval set built from traffic, the model's own output) and minimise at each. Collect only what the task needs, redact before data leaves your boundary and before it is logged or traced, treat detection as probabilistic (Presidio itself gives no guarantee), and keep data in the promised region, including the region of your model and tracing vendors. Hashing is not anonymisation for low-entropy values such as phone numbers, because anyone can hash every candidate. Never put PII in URLs or headers.</p>
</Fragment>
<Fragment slot="long">
<p>Inventory. PII appears in more places than people list: the prompt sent to the model vendor, request logs, agent traces, datasets someone built from production traffic, caches, and the model's answers (it can emit PII from context or training). Each is a disclosure surface, OWASP LLM02.</p>
<p>Minimise. Collect and send only fields the task needs. Redact or tokenise before text leaves your boundary, and redact the logs and traces on a separate path, because they usually store the raw prompt and are read by more people than production.</p>
<p>Detect, knowing it is partial. Presidio combines named-entity recognition, regex, checksums and context words and states it cannot guarantee finding everything. A regex with a Luhn check catches a formatted card and misses a spelled-out email or an unusual name. So redaction is defence in depth, not the control; access limits and minimisation are.</p>
<p>Hashing is not anonymisation for low-entropy identifiers. There are at most ten billion ten-digit phone numbers, so anyone with the hash can hash every candidate and recover it; the same holds for emails drawn from a known list. If you must join on a value, use a keyed hash (HMAC with a secret you hold) or a tokenisation service, and still treat the result as personal data.</p>
<p>Residency and transport. Keep data in the region customers were promised, which includes choosing a model and a tracing vendor that process in that region. Never place PII in a URL query string or a request header, where it lands in logs and proxies; the MCP tools spec says the same for tool parameters mirrored into headers.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Redact before or after the model call?</em> Before, for anything leaving your boundary. If the model needs a value to do its job, pass a token and resolve it in your code after the response.</li>
<li><em>How do you let support debug without seeing PII?</em> Redacted logs by default, with raw access gated, time-limited and audited.</li>
<li><em>The model echoes a user's email back. Is that a leak?</em> To that same user, usually fine; an output guard still helps catch cases where it emits someone else's.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *A regulator asks where the data is processed. What do you check?* Your region, the model vendor's region, the tracing vendor's region, and any backup or cache in between.
- *Can you use production traffic to build an eval set?* Only after redaction and with a legal basis; raw traffic in a dataset is the same disclosure surface as a log.

## Common mistakes

- Redacting the prompt but logging the raw request.
- Treating a hash of a phone number or email as anonymous.
- Putting user identifiers in URL query strings or headers.
- Assuming Presidio or a regex catches all PII.
