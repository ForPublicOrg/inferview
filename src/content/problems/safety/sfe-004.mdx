## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"What security risks does MCP introduce?"
</Callout>

Your company's internal coding assistant supports MCP. Engineering leadership wants every engineer to be able to connect any server they like, local or remote; the security team can review only a handful of servers a month (scenario). Answer for the security review: the risks, the control for each from the 2026-07-28 specification or your own client, and the policy you would adopt. One quantity is yours: how often the client re-checks a server's tool definitions against what was approved.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the approval dialog in your client shows: the tool name, its full description, the full arguments of each call?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the list of servers engineers have already connected and which credentials each one holds.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether the remote servers are run by the company or by third parties, and who can change their code.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>MCP brings third-party text and third-party code into a session that already holds credentials. Tool descriptions and tool results are model input, so a server can carry instructions (tool poisoning), change them after approval (rug pull) or steer another server's tools (shadowing). Combining servers can assemble the lethal trifecta from parts that are each harmless. Remote servers add OAuth risks the spec names: confused deputy, token passthrough (forbidden), SSRF during metadata discovery, state handle hijacking. Local servers run arbitrary commands with the engineer's privileges. My policy: open connection for read-only servers inside a sandbox, review only for servers that hold write or outbound capability, and a session rule that no session combines untrusted-content servers with outbound-capable ones.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Text as attack surface.</strong> Invariant Labs showed in April 2025 that the model reads full descriptions while the user sees a short name; a malicious <code>add</code> tool told the model to read <code>~/.ssh/id_rsa</code> and pass it in a parameter, and a second variant told the agent to send every <code>send_email</code> to the attacker even when the user named another recipient, without the malicious tool ever being called. Tool results are the same channel: a server that reads issues, tickets or web pages returns attacker text on every call.</p>
<p><strong>Composition.</strong> GitHub's MCP server had no code flaw in Invariant's May 2025 case; an over-broad token plus a public issue was enough to put private repository data in a public pull request. Supabase's case was one server with all three legs through elevated database access that bypasses row-level security. The unit of review is the session's combined capability, not the server.</p>
<p><strong>Authorisation, per the 2026-07-28 security page.</strong> Confused deputy: a proxy with a static client ID and a consent cookie lets an attacker skip consent; proxies MUST implement per-client consent, exact redirect URI matching and single-use <code>state</code>. Token passthrough: servers MUST NOT accept tokens not issued for them. SSRF: a malicious server can point OAuth discovery URLs at <code>169.254.169.254</code> or internal hosts; clients deployed on servers block private ranges or use an egress proxy. Authorization URLs: clients MUST reject <code>javascript:</code> and similar schemes and MUST NOT open URLs through a shell. State handles: the current revision has no protocol sessions, so servers MUST NOT treat a handle as authentication and should bind it to the verified user. Scope minimisation: start with read scopes and step up.</p>
<p><strong>Local servers.</strong> A stdio server is a program with the engineer's permissions. A client offering one-click install MUST show the exact command, untruncated, and get approval; the spec recommends running it sandboxed with minimal default privileges and restricted file system and network access.</p>
<p><strong>The policy decision.</strong> Two defensible answers. A: an allowlist registry, nothing connects until reviewed. Cost: with a review capacity of a handful a month, engineers route around it with unofficial installs, which is worse than no registry. B: open connection with runtime controls. Cost: you accept unreviewed text in sessions. I take B for read-only servers (sandboxed, no outbound network, scoped read tokens) and A for any server holding write scope, send capability or production credentials, plus the session rule above enforced by the client.</p>
<p><strong>Re-checking definitions.</strong> Hash each tool's name, description and schemas at approval and compare on every <code>tools/list</code> response, including after each list-changed notification. It costs a hash per listing. A daily scan is the unreasonable choice: a rug pull lands between scans and is used in the same afternoon.</p>
<p><strong>Where it fails.</strong> Hash pinning catches changed descriptions, not changed behaviour: a remote server's code can change server-side with identical definitions, and its results can carry instructions on any call. Pinning a remote server pins its interface, not its code. That is why the session rule, not the hash, is the control that holds.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Are tool annotations such as read-only a control?</em> No; the tools page says clients MUST treat them as untrusted unless the server is trusted. Read-only has to come from the token's scope.</li>
<li><em>What does MCP itself guarantee at runtime?</em> Little: a human SHOULD be able to deny calls, clients SHOULD show inputs before calling, servers MUST validate inputs and enforce access control. Enforcement lives in your client and your servers.</li>
<li><em>How is this different from a VS Code extension?</em> The same supply-chain risk, plus text from the extension steering a model that holds the other extensions' tools.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *An engineer wants a community server that wraps the production database. What do you require?* A read-only role scoped to one schema, no write tools, a sandboxed process, and no outbound-capable server in the same session.
- *Leadership says the session rule blocks the workflow "read the ticket, then open a PR". How do you keep the workflow without the combination?* Split it: one session reads tickets and writes a plan to a file; a fresh session without ticket access implements it, and a human reviews the PR before it is public.
- *What would make you move a server from the reviewed tier to the open tier?* A scoped token that cannot write or reach the network, verified in the token and the sandbox, not in the server's own claims.

## Common mistakes

- Listing only classic supply-chain risk and missing that descriptions and results are prompts.
- Describing "MCP session hijacking" as current; the 2026-07-28 revision has no protocol sessions, and the risk is now state handles.
- Trusting annotations or server-declared scopes.
- Reviewing each server alone instead of the capabilities combined in one session.
- Believing a pinned version of a remote server pins its behaviour.
