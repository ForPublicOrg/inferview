## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"What security risks does MCP introduce?"
</Callout>

Your company wants to let employees connect any MCP server to the internal coding assistant. Answer for the security review.

## Hints

<details class="hint"><summary>Hint 1</summary><p>A tool description is text. Who writes it, and who reads it?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Think about what happens when two servers are connected at once.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Remote servers use OAuth. What can go wrong when a server sits between a client and another API?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>MCP adds third-party text and third-party code to the agent. Tool descriptions are model input, so a server can hide instructions in them (tool poisoning), change them after approval (rug pull), or influence how other servers' tools are used (shadowing). Combining servers can assemble the lethal trifecta from parts that are each harmless. Remote servers add OAuth risks such as the confused deputy and token passthrough, which the spec forbids, and local servers run arbitrary commands on install. Controls: an allowlist of reviewed servers with pinned descriptions, least-privilege tokens, per-session scoping, approval that shows full arguments, and sandboxing for local servers.</p>
</Fragment>
<Fragment slot="long">
<p>Tool metadata as injection. Invariant Labs showed in April 2025 that the model reads full tool descriptions while the user usually sees a short name. A malicious description can tell the model to read local files and pass them in a parameter. Variants: the rug pull, where a description changes after the user approved the server, and shadowing, where one server's description changes how the agent uses another server's tools. The MCP tools page says clients must treat annotations from untrusted servers as untrusted.</p>
<p>Composition. Each server may be fine alone. A server that reads public issues plus one that can write to repositories plus a token that reaches private repositories is the GitHub MCP case from May 2025: no code bug, just an over-broad token and untrusted text in the same session. Supabase's case showed a single server with all three legs, through a key that bypasses row-level security.</p>
<p>Authorisation. The 2026-07-28 security page lists the confused deputy (a proxy with a static client ID that lets an attacker skip consent; fix with per-client consent, exact redirect URI matching and single-use state), token passthrough (forbidden: servers must not accept tokens issued for something else), SSRF during OAuth metadata discovery (block private address ranges), and scope minimisation. It also covers state handle hijacking; the current revision has no protocol sessions, so "session hijacking" describes older revisions.</p>
<p>Local servers. A stdio server is a program on the developer's machine with their permissions. One-click install should show the exact command, and the server should run sandboxed.</p>
<p>Controls for the review: an internal registry of approved servers with pinned versions and hashed descriptions (alert on change), per-server least-privilege credentials, a policy that untrusted-content servers and outbound-capable servers do not share a session, approval prompts that show every argument, and logs of every call.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you detect a rug pull?</em> Hash each tool's name, description and schema at approval time and compare on every listing; a change requires re-approval.</li>
<li><em>Are tool annotations like "read-only" a control?</em> No. They are hints from the server, untrusted unless the server is.</li>
<li><em>What does MCP itself guarantee?</em> Very little at runtime. The spec says a human should be able to deny calls and servers must validate inputs and enforce access control; enforcement is your client and your servers.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *An employee wants a community server that wraps the production database. What do you require?* A read-only role scoped to one schema, no write tools, and no outbound tools in the same session.
- *How is this different from installing a VS Code extension?* Same supply-chain risk, plus a new one: the extension's text steers a model that holds other tools.

## Common mistakes

- Listing only classic supply-chain risk and missing that descriptions are prompts.
- Describing "MCP session hijacking" as current; the 2026-07-28 revision removed protocol sessions.
- Trusting annotations or server-declared scopes.
- Treating each server in isolation instead of the combined capabilities in one session.
