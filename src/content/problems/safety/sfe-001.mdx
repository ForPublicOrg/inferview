## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"Walk me through what happens when your RAG bot ingests a document an attacker controls."
</Callout>

The system: an internal assistant answers employee questions from one shared document index. Any employee can upload to the index, and a connector also ingests files that contractors and customers send to shared mailboxes. The assistant has one tool, `crm_search(query)`, which runs with the asking employee's CRM permissions, and the chat window renders Markdown. Sales leadership will not give up `crm_search`; it is the reason the assistant exists.

Walk the paths from the attacker's document to harm, name the control for each, and say which control you would ship first. One quantity is yours to choose: how long retrieval provenance (which chunks fed which answer) is kept.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the ingestion pipeline records about each file: uploader, source mailbox, time, and whether any of it reaches the retrieval step.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the full list of things the client does with a reply besides displaying text.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how long a document stays in the index and how long the team took to notice the last bad answer.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Once retrieved, the attacker's chunk sits in the same token stream as the system prompt and the question, so the attacker steers every answer that retrieves it. Three paths matter: false answers with the assistant's authority, a phishing link presented as the official one, and exfiltration of CRM data through anything that makes a request, including a rendered image. The session holds all three trifecta legs and sales will not remove the CRM leg, so I remove the way out first: no rendered external images, links shown with their real host, no write tools. Then I record provenance at ingestion so untrusted chunks can be kept out of CRM-capable sessions.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Paths.</strong> Ingestion chunks and embeds the file like any other; unless the pipeline stores uploader and source, the contractor's file and the HR handbook are indistinguishable at query time. The attacker can write the document to rank for chosen queries by repeating their terms. At retrieval the chunk lands next to the system prompt; OWASP LLM01:2025 lists this case (scenario 4, an altered document in a RAG repository) and says RAG does not fully mitigate injection. From there: (1) integrity, a wrong expense limit or a wrong escalation contact; (2) phishing, a link presented as the official form; (3) exfiltration, an instruction to call <code>crm_search</code> and put the result into an image URL or a link. A rendered image needs no click, which is why it ranks above links.</p>
<p><strong>The decision.</strong> Two defensible designs, given that <code>crm_search</code> stays.</p>
<p>A. Remove the exit. Render no external images (CSP <code>img-src</code> limited to your own hosts), show links as text with the host visible, keep the assistant free of any tool that writes or sends. Cost: no inline images or clickable citations from the model, and integrity attacks (false answers, phishing text) are untouched. It is a client and header change.</p>
<p>B. Remove the untrusted input from CRM-capable sessions. Tag every chunk with a trust tier at ingestion (employee upload, external mailbox) and either filter external-tier chunks out of retrieval when the session holds <code>crm_search</code>, or run two assistants. Cost: recall drops for questions whose only answer is in external files, and the connector has to carry source metadata it may not carry today. This is the Rule of Two applied per session.</p>
<p>I ship A first because it closes the highest-severity path without touching recall, then B for the external-mailbox connector. "Any employee can upload" means the employee tier is not trusted either: one compromised or careless account writes to it, so B narrows the problem and does not close it.</p>
<p><strong>Retention of provenance.</strong> Log the chunk IDs behind every answer. A poisoned document can be retrieved at any time while it is indexed, so retention has to cover the document's time in the index plus the time to notice. If documents stay indexed indefinitely, a fixed 30-day window means the answers it influenced in its second month are unrecoverable. Reasonable choices: tie log retention to index retention, or keep the full log for a bounded window and a small per-document "answers that retrieved it" index for as long as the document exists. A window shorter than the team's time to detect is the unreasonable choice.</p>
<p><strong>Where the recommendation fails.</strong> Design A does nothing for the integrity path: the assistant will still state the attacker's expense policy with confidence, and that is often the more likely real harm. Trust tiers fail when the attacker reaches the trusted tier, for example by getting an employee to re-upload the file, which launders its tier. The tier has to follow the content (hash and first origin), not the last uploader.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Would "documents are data, not instructions" in the system prompt help?</em> It changes the rate on a test set and enforces nothing; OWASP says it is unclear whether fool-proof prevention exists.</li>
<li><em>Which OWASP entries apply?</em> LLM01, LLM04, LLM05 and LLM08 in the 2025 numbering; a secondary source reports them as LLM01, LLM05, LLM10 and LLM09 in the 2026 edition, so cite the year with the number.</li>
<li><em>How do you find the poisoned document after a report?</em> From the chunk IDs logged with the bad answers; remove it, re-index, and use the per-document index to list every other answer it fed.</li>
</ul>
</Fragment>

## Follow-ups

- *The index becomes customer-facing and customers upload the documents. What changes?* Every chunk is untrusted and the other customers' data becomes the private leg; per-tenant indexes and per-tenant sessions become the baseline, not an option.
- *Sales says the image block broke the pipeline charts their dashboards embed. What do you allow, and what risk do you write down?* Images from one host you control that serves only files your own systems generated, never a host that accepts uploads or forwards requests; the written risk is that any future upload feature on that host reopens the channel.
- *An ingestion-time classifier flags a share of external files. Do you quarantine them?* Only with a staffed review queue and a measured precision on a labelled sample; an unreviewed quarantine is a silent recall loss that gets switched off.

## Common mistakes

- Treating "internal" documents as trusted when anyone can upload them.
- Leaving rendered Markdown off the list of outbound channels.
- Proposing only an input classifier or a stronger system prompt.
- Logging answers but not the chunk IDs behind them, so the poisoned file cannot be traced.
