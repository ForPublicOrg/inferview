## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"Walk me through what happens when your RAG bot ingests a document an attacker controls."
</Callout>

Assume an internal assistant that answers employee questions from a shared document index. Anyone in the company can upload to the index, and contractors and customers can send files that end up there. The assistant can also search the CRM and render Markdown in its chat window.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Follow the document's text from ingestion to the moment the model reads it. What does the model know about who wrote it?</p></details>
<details class="hint"><summary>Hint 2</summary><p>List what the assistant can do besides answering: which tools, which renderers, whose permissions.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Separate what the attacker can make the model say from what they can make the system do.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The document's text becomes part of the prompt whenever it is retrieved, and the model cannot reliably tell its content from instructions. So the attacker gets to influence every answer that retrieves it: they can plant false facts, steer users to a phishing link, or, if the assistant can read private data and send anything out (a tool or even a rendered image URL), instruct it to leak that data. Defences are structural: trust labels and access rules at ingestion, no outbound channel in the same session as untrusted text, and output handling that renders nothing that fetches.</p>
</Fragment>
<Fragment slot="long">
<p>Ingestion: the file is chunked and embedded like any other. Nothing in a typical pipeline records who uploaded it or whether they are trusted, so a contractor's file and the HR handbook look the same at query time. The attacker can also write the document to rank well for chosen queries, by repeating the terms people search for.</p>
<p>Retrieval: when a question matches, the chunk lands in the context next to the system prompt. OWASP's LLM01:2025 calls this indirect prompt injection and notes that retrieval does not fully mitigate it.</p>
<p>Effects, from least to most severe. Integrity: false answers with the authority of the internal assistant ("the expense limit is now X"). Phishing: a link the assistant presents as the official form. Exfiltration: if the same session can read the CRM and has any way out, an instruction in the chunk can ask the model to include CRM data in a link or image URL, and a rendered image sends it with no click. That is the lethal trifecta: private data, untrusted content and a way out.</p>
<p>Defences: record provenance at ingestion and show it to the model and to the user; restrict who can write to indexes that feed high-trust answers; filter retrieval by the asker's permissions; in sessions that include untrusted chunks, remove tools that reach private data or send anything; render Markdown with external images disabled and a CSP that blocks unknown hosts; log retrieved chunk IDs with every answer so a poisoned document can be traced and removed. A classifier on ingested text helps as a rate reducer, not a boundary.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you find the poisoned document after the fact?</em> Every answer logs the chunk IDs it used; search those logs for the chunks behind the bad answers, then remove and re-index.</li>
<li><em>Does a "documents are data, not instructions" line in the system prompt help?</em> A little, and it is not a control. The model weighs it against the document's own instructions.</li>
<li><em>Which OWASP entries apply?</em> LLM01 Prompt Injection, LLM04 Data and Model Poisoning, LLM05 Improper Output Handling, LLM08 Vector and Embedding Weaknesses (2025 numbering).</li>
</ul>
</Fragment>
</Depth>

The strongest answers draw the line between what the model says and what the system does. Saying false things is bad and partly unavoidable; doing things with the user's permissions is where structure has to stop it.

## Follow-ups

- *The index is customer-facing and customers upload the documents. What changes?* Every chunk is untrusted, so the session must never hold another customer's data or an outbound tool; per-tenant indexes become the default.
- *Can you detect injected instructions at ingestion?* Partly. A classifier flags obvious ones, but text that reads like a policy update is hard to tell from a real one. Treat detection as triage for human review.

## Common mistakes

- Answering only with input filtering or a stronger system prompt.
- Forgetting rendered Markdown as an outbound channel.
- Treating "internal" documents as trusted when anyone can upload them.
- Describing the attack and never naming who can write to the index.
