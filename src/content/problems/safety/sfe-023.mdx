## Question

<Callout kind="interview" label="Critique, 30 minutes">
"Here is the design note for our travel assistant's booking feature. It claims Rule of Two compliance. List what is wrong, most serious first, then tell me which property you would drop and what the product loses."
</Callout>

The design note, as submitted by the team (scenario):

```text
Travel assistant v2: booking
Rule of Two: we are [AB]. We drop C.

Session start
  Load the traveller profile into context: name, passport expiry, loyalty
  numbers, home airport, saved card (token + last 4 digits).
  Load memory notes from earlier sessions.

Tools
  search_hotels(city, dates)       partner inventory API
  search_flights(from, to, dates)  partner inventory API
  fetch_page(url)                  reads any web page (reviews, blogs, maps);
                                   the model may build the URL, e.g. adding
                                   ?checkin=...&guests=... for a deep link
  book(property_id, dates, card)   charges the card
  save_note(text)                  stores a memory note for future sessions

C is dropped because:
  book() needs a human confirmation. The model writes a one-line summary
  ("Book Hotel Lumiere, 12 to 14 June, 184 EUR") and the user taps Confirm.
  Bookings under 150 EUR are auto-confirmed to reduce friction.

Extra safety
  Every fetched page is screened by a prompt-injection classifier;
  pages flagged are dropped from context.

Rendering
  Answers render as Markdown, so hotel photos from pages show inline.
```

List the flaws before opening the checklist.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what a server learns when the assistant fetches a URL the model wrote.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request three real confirmation cards from the beta and the raw book() arguments behind each.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what share of beta sessions never booked anything, and what the profile was used for in them.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The note claims [AB] and has all three legs. fetch_page on a URL the model builds is an outbound channel, inline images are another, and auto-confirm under 150 EUR is a state change no person sees, so C is present before booking is even discussed. The confirmation that is meant to remove C is a sentence written by the model that just read the attacker's page. Memory notes written from pages carry untrusted text into future sessions, so a fresh session is not fresh. I would keep Meta's choice for a travel assistant, [AB], and make it true: fetch only URLs returned by the inventory API, render no remote images, confirm every booking from a card built from trusted state, and load the card only at booking. The product loses one-tap small bookings and deep links the model builds.</p>
</Fragment>
<Fragment slot="long">
<p><strong>1. fetch_page is C.</strong> A GET to <code>blog.example/?q=</code> plus the passport expiry sends the passport expiry. Meta's travel example limits web requests to URLs returned from trusted sources, not URLs the agent constructs, for this reason. The deep-link feature in the note is exactly the construction it rules out. This is the flaw a reviewer misses on first read, because the note lists fetch_page under reading.</p>
<p><strong>2. The confirmation card is model text.</strong> "Book Hotel Lumiere, 12 to 14 June, 184 EUR" is written by the same context that read the page. An injected page can make the summary describe one booking while the arguments describe another (another property id, other dates, a non-refundable rate). The card must be rendered by code from the book() arguments and the inventory API's record of that property, and the model's sentence, if shown, is labelled as such.</p>
<p><strong>3. Auto-confirm under 150 EUR is autonomous C.</strong> With untrusted pages and the saved card in context, this is the configuration the rule says should not run without supervision. An attacker who can only trigger bookings under 150 EUR can still trigger many.</p>
<p><strong>4. The profile is loaded into every session.</strong> Passport expiry and loyalty numbers sit next to every blog post the assistant reads, including sessions that only research. Meta allows a one-way move within a session: research as [A] with no private data, then load the profile when the user asks to book. Loading it lazily also shrinks what any leak can contain.</p>
<p><strong>5. Memory notes are untrusted input with a long life.</strong> save_note(text) from a session that read pages stores attacker-shaped text that every later session loads at start. The rule's escape hatch is a fresh context window, and memory removes it. This is the second flaw reviewers miss, because memory sits under "session start" and reads as configuration.</p>
<p><strong>6. Inline images are a zero-click request.</strong> A page can put an image URL carrying data into the answer, and the client fetches it when the answer renders. EchoLeak used auto-fetched images in a production assistant. Remote images from pages are removed or proxied from an allowlist of the inventory partners' image hosts.</p>
<p><strong>7. The classifier is not why it is safe.</strong> It lowers the rate of injected pages reaching context; EchoLeak evaded one in production. Keep it, and remove it from the note's argument.</p>
<p><strong>8. The judgement call.</strong> Human confirmation of every booking is acceptable if the card is built from trusted state, shows the property, dates, total and refund terms, and the team monitors confirmation behaviour (time from card shown to tap). As written, with a model-written card and an auto-confirm threshold, it is not.</p>
<p><strong>Which property to drop: two defensible answers.</strong></p>
<ul>
<li><strong>Drop C, as Meta does: [AB].</strong> Untrusted pages and the profile together, every booking confirmed from a trusted card, fetches limited to inventory-returned URLs, no remote images. The product loses one-tap small bookings, deep links the model builds, and fetching arbitrary pages the user pastes unless the user confirms each fetch. Cost in friction: one tap per booking, which beta data on abandonment at the card will price.</li>
<li><strong>Drop B in the research session: [AC], then [BC] for booking.</strong> Research browses freely with no profile and no card, and may follow links. Booking happens in a new session that receives only what the user selected (an inventory property id and dates) and the profile, with no page text: no A. The product loses an assistant that remembers the reviews when the user asks a question during checkout, and the handover between sessions has to be built. Its gain is that fetching stays flexible where the product's value is.</li>
</ul>
<p>The constraint conflict is autonomy and friction against the one guarantee the note claims. I would ship [AB] now, because it needs removals rather than a new session boundary, and design the split for the next release if beta users paste many arbitrary URLs.</p>
<p><strong>Where the recommended design fails.</strong> Users confirm without reading; Meta names a user confirming a warning without reading as the way such designs still fail. A trusted card cannot help when the inventory record itself is wrong or the price changes between search and confirm. And a fetch restricted to inventory-returned URLs still reaches whatever the partner returns; if a partner's listing text is attacker-written, it is A arriving through a trusted pipe.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Is a deep link with check-in dates in the query really a leak?</em> The dates alone are low value; the point is that the channel accepts whatever the model writes, and the model's writer can be the page.</li>
<li><em>What about the 150 EUR threshold as a rate limit rather than a control?</em> A per-day cap on bookings bounds the loss from a failure; it does not stop the failure, so it belongs next to confirmation, not instead of it.</li>
</ul>
</Fragment>

## Follow-ups

- *Pushback: product shows that the confirmation step costs a measurable share of small bookings. What do you offer instead of auto-confirm, and what risk do you put your name to?*
- *Reversal: what would you need to see from the beta to move from [AB] to the split research and booking sessions?*
- *A partner's hotel description contains an injected instruction. Which of your controls still holds, and which assumes the partner's text is clean?*

## Common mistakes

- Accepting "we drop C" from the tool list without asking which calls send anything anywhere.
- Treating a confirmation tap as a control without asking who wrote the text the user is confirming.
- Looking only at the current session and missing memory as a path from one session's pages into the next.
- Arguing the classifier is useless and deleting it, instead of moving it out of the safety argument.
