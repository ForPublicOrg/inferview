## Question

<Callout kind="interview" label="Coding">
Write an output guardrail <code>guard_output(text, canary)</code>. If the system-prompt canary appears, block the whole reply. Otherwise redact email addresses as <code>[EMAIL]</code> and Luhn-valid card numbers as <code>[CARD]</code>, while leaving numbers that fail the Luhn check (order numbers, phone numbers) untouched.
</Callout>

The Luhn check is what separates a card number from an order number of the same length, so the guard needs it to avoid redacting every long number.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Check the canary first and return early; a leak means the reply should not go out at all.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Match candidate card numbers with a regex, strip the separators, and only replace when the digits pass Luhn.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Luhn doubles every second digit from the right; a doubled result over 9 has 9 subtracted.</p></details>

## Answer

The guard blocks on the canary, then redacts emails with a regex, then redacts card candidates only when their digits pass Luhn. The card regex matches 13 to 19 digits with optional single spaces or dashes between them; the Luhn function decides whether a match is really a card. That is why `4111 1111 1111 1111` is redacted and `1234 5678 9012 3456` is kept.

```python
import re

EMAIL = re.compile(r"\b[\w.+-]+@[\w-]+(?:\.[\w-]+)+\b")
CARD = re.compile(r"\b\d(?:[ -]?\d){12,18}\b")

def luhn_ok(digits):
    total, parity = 0, len(digits) % 2
    for i, ch in enumerate(digits):
        d = int(ch)
        if i % 2 == parity:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0

def guard_output(text, canary):
    if canary in text:
        return {"action": "block", "text": ""}
    text = EMAIL.sub("[EMAIL]", text)
    def card(m):
        digits = re.sub(r"\D", "", m.group(0))
        return "[CARD]" if luhn_ok(digits) else m.group(0)
    return {"action": "allow", "text": CARD.sub(card, text)}
```

This is one layer. A spelled-out email ("jane dot doe at corp dot example"), a name, or a card number split across a sentence all pass. Presidio, a production PII tool, says plainly that it cannot guarantee finding everything. Treat the regex guard as cheap defence in depth behind access control and data minimisation, not as the thing that keeps PII out.

## Follow-ups

- *How would you add names and addresses?* A named-entity model such as Presidio's, accepting its false positives and negatives; regex is not enough for free-form PII.
- *Blocking on the canary is coarse. Better?* Alert and block, then investigate; a canary in the output means the prompt leaked, which is worth stopping the reply over.
- *Where does this run relative to streaming?* An output guard has to see the text, so with streaming you buffer or check chunks; it cannot overlap generation.

## Common mistakes

- Redacting every long digit run, so order and phone numbers disappear.
- Skipping the Luhn check and matching "card-like" numbers by length alone.
- Treating the regex guard as sufficient for PII compliance.
