    import re


    def guard_output(text, secrets):
        """Check a model reply before it is shown.

        Return {"action": "block", "text": ""} if any string in `secrets` appears in
        `text`. A secret still counts when the reply changes its letter case or puts
        spaces, hyphens, dots, underscores, slashes or zero-width characters
        (U+200B, U+200C, U+200D, U+2060, U+FEFF) between its characters. Secrets are
        at least 12 characters of letters, digits, hyphens and underscores.

        Otherwise return {"action": "allow", "text": redacted}:
        - every email address becomes [EMAIL];
        - a card number is a maximal run of digits in which neighbouring digits are
          separated by nothing or by one space or one hyphen, with 13 to 19 digits,
          passing the Luhn check. Replace it with text that starts with "[CARD",
          ends with "]" and shows at most its last four digits; whether it shows
          them is your choice.
        - runs of 13 to 19 digits that fail Luhn, and shorter runs, stay as they
          are. How you treat a run of more than 19 digits is your decision.
        - everything else is unchanged.

        Replies can be 200,000 characters long and contain minified code, base64
        and dotted identifiers. Each call has a budget of 0.5 seconds.
        """
        raise NotImplementedError

## Question

<Callout kind="interview" label="Coding, 35 minutes">
"Write the output guard that runs on every reply before the user sees it. It blocks the reply if one of our secrets leaks, in any spelling the model might produce, and it redacts email addresses and card numbers without eating order numbers. It runs on the request path."
</Callout>

The contract is in the starter's docstring. Two parts of it are yours to decide: what a redacted card looks like (with or without its last four digits), and what to do with a run of more than 19 digits. The tests check properties of the output, not one exact string, except where the docstring fixes the format.

The budget matters as much as the rules. Replies can run to 200,000 characters, and they contain things a regex author does not picture: minified JavaScript, base64, long dotted package names. Each call gets 0.5 seconds.

## Answer

```python
import re

EMAIL = re.compile(r"[A-Za-z0-9._%+-]{1,64}@[A-Za-z0-9-]{1,63}(?:\.[A-Za-z0-9-]{1,63})+")
DIGIT_RUN = re.compile(r"\d(?:[ -]?\d)*")


def luhn_ok(digits):
    total = 0
    for i, ch in enumerate(reversed(digits)):
        d = int(ch)
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0


def _squash(s):
    return "".join(ch for ch in s.casefold() if ch.isalnum())


def _card(m):
    run = m.group(0)
    digits = re.sub(r"\D", "", run)
    if 13 <= len(digits) <= 19 and luhn_ok(digits):
        return "[CARD-" + digits[-4:] + "]"
    return run


def guard_output(text, secrets):
    flat = _squash(text)
    for s in secrets:
        if _squash(s) in flat:
            return {"action": "block", "text": ""}
    text = EMAIL.sub("[EMAIL]", text)
    return {"action": "allow", "text": DIGIT_RUN.sub(_card, text)}
```

**Secrets.** Every variant in the contract (case, separators, zero-width characters) disappears if both the reply and the secret are reduced to their case-folded letters and digits. One linear pass over the reply, then a substring search per secret, which is the cheapest structure available: the search runs in C, and a list of fifty secrets costs fifty scans of one string rather than fifty regular expressions with optional separators between every character. The check runs before redaction, so a secret that looks like an email or a number is not hidden from it by the redactor. Squashing also deletes word boundaries, so a secret could in principle be assembled from adjacent words; at 12 or more characters of random letters and digits that does not happen by accident, and a short or dictionary-like secret would make this check noisy.

**Emails, and the budget.** The obvious pattern, `[\w.+-]+@...`, is correct and quadratic. On a run of characters the local-part class accepts but with no `@` in it, such as `a.a.a.a...`, the engine starts a match at every position, consumes to the end of the run, finds no `@` and backtracks. Measured on CPython 3.12 for this problem, 20,000 characters took 0.92 s and 40,000 took 4.3 s; 24,000 characters is the visible test. RFC 5321 caps the local part at 64 octets, so `{1,64}` bounds the work per start position, and the 20,000-character input takes about 3 ms. The bound is a chosen number with a source; 128 or 256 would also be defensible if your users have odd addresses, and the cost is linear in the bound. An over-long local part is partly redacted, which leaves its first characters in the reply; the alternative, anchoring the match on the left, leaks the whole address.

**Cards.** A run is found first and judged second: the regex finds maximal digit runs with single-space or single-hyphen separators, and the Luhn check decides whether a run of 13 to 19 digits is a card. Searching for "13 to 19 digits" directly with a regex would let the engine pick a window inside a longer run. Keeping the last four digits is the usual receipt convention and still passes the tests; dropping them is also allowed.

**Runs longer than 19 digits.** The reference leaves them alone. The other policy, redacting any run that contains a Luhn-valid window of 13 to 19 digits, catches a card glued to another number but redacts almost every long number: in a simulation over 100,000 random 20-digit runs, 97.2% contained at least one such window. The conflict is recall against usefulness, and which side wins depends on whether long numbers in your replies are tracking ids that support needs or something worse.

**Where this guard fails.** A card followed by another number with one space between (`4111 1111 1111 1111 2 units`) becomes one run of 17 digits, fails Luhn and goes out unredacted, and so does a card written with double spaces. A secret encoded as base64, split across two replies, or written with a Cyrillic letter that looks Latin passes the squash, because those are not the variants it removes. An email spelled out in words passes. Presidio, which combines named-entity recognition, patterns and checksums, states that it cannot guarantee finding everything either, and OWASP's injection cheat sheet says output keyword filtering is not sufficient on its own. The guard is a cheap layer behind the controls that matter: secrets the model never sees, and PII kept out of the context unless the task needs it.

## Follow-ups

- *The reply streams. What changes?* The guard has to see text before the user does, so you hold back a tail long enough to contain a secret or a card. Zero-width characters make a spelled-out secret unbounded in length, so the held-back tail needs a cap, and a secret padded past it gets through; the alternative is to buffer the whole reply on routes where secrets are reachable.
- *Where does this run in a real client: the application, the model gateway, or both?* In the gateway it covers every application but sees only the reply, not which secrets the calling application holds; decide who owns the secret list.
- *A secret leaks in a reply you blocked. What else do you do?* Rotate it: the model produced it, so it was in the context or in a tool result, and the next spelling may not be one you catch.
- *Product wants the card's last four digits kept and security wants none. What evidence settles it?*

## Common mistakes

- Writing the email pattern with an unbounded local part and testing it only on short, friendly replies.
- Matching the secret exactly, or with `.lower()` only, so a spaced or hyphenated spelling goes out.
- Running the Luhn check on a regex window instead of on the whole run, so a card number is found inside an order id.
- Redacting before checking for secrets, so the redactor hides the evidence of a leak.
- Treating the guard as the PII control rather than as one layer behind data minimisation.
