## Question

<Callout kind="interview" label="Concept, 25 minutes">
"We have a 400-prompt injection suite from last year and our agent blocks 398 of them. The security lead says that number means nothing. How would you measure whether our prompt-injection defences work, and why is a fixed attack set not enough? You have one engineer for a quarter and a release every two weeks."
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the suite counts as a success for the attacker: text the model printed, or something that happened in a tool.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask whether any of the 400 prompts were written after the current defences were built, and by whom.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the list of tools the agent can call that change state or send data, and which of them have a deterministic check in front.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Measure effects, not text: the unit is an attack goal (exfiltrate this record, send this email, change this setting), and success is the goal's effect appearing in a ledger of tool calls and outbound requests. Report attack success at a stated attacker budget, against an attacker that adapts to the defence, next to utility with and without attack. A fixed set measures how well the defences fit last year's strings: Nasr et al. took 12 defences that reported near-zero success and got most above 90 percent with adaptive attacks. Then split the controls: deterministic ones get unit and property tests that must pass every release; probabilistic ones get a rate with its budget, which is a lower bound on what a real attacker achieves.</p>
</Fragment>
<Fragment slot="long">
<p><strong>1. What "398 of 400" counts.</strong> If the suite grades the model's text (a refusal, the absence of a phrase), it measures behaviour, not security. The ground truth is the effect: a fake mailbox that records sends, a fake HTTP sink that records requests, a fake database that records writes. An attack that the model "refuses" while its tool call already went out is a success; an injected instruction the model repeats in its answer with no effect is not.</p>
<p><strong>2. Why a fixed set is not enough.</strong> A defence built or tuned after the set was written is tested on its training data. An attacker chooses the next attempt after seeing the last one; a fixed set never does. Nasr et al.'s result is the measured gap: defences reporting near-zero success, beaten above 90 percent for most when the attack was tuned per defence with search, reinforcement learning or people. AgentDojo was built as an extensible environment rather than a static suite for that reason, and Anthropic's browser-agent numbers come from an adaptive Best-of-N attacker with 100 attempts per environment, not from a list.</p>
<p><strong>3. The budget is part of the number.</strong> If one attempt succeeds with probability p and attempts are independent, k attempts succeed at least once with probability 1 − (1 − p)<sup>k</sup>. At p = 0.01: 10 attempts give 1 − 0.99<sup>10</sup> ≈ 0.096, and 100 attempts give 1 − 0.99<sup>100</sup> ≈ 0.634. A rate without the attacker's budget is not comparable to anything, and independence is generous to the defence: an adaptive attacker's attempts are correlated toward the weak spot.</p>
<p><strong>4. What I would build with one engineer for a quarter.</strong></p>
<ul>
<li><strong>Weeks 1 to 3: the harness.</strong> Fake tools with an effect ledger; attack goals written per tool that sends or changes state; injection points in every channel untrusted text enters (web pages, inbound mail, tool results, retrieved documents, memory). Every case also runs without the injection, so utility is measured on the same tasks.</li>
<li><strong>Weeks 4 to 6: deterministic controls as tests.</strong> Egress allowlists, destination checks, render rules, permission gates: each gets unit and property tests that assert the control holds for every input, not a rate. These run on every release and must pass.</li>
<li><strong>Weeks 7 to 12: an adaptive loop.</strong> An attacker model rewrites the injection after each failure, with the defence's output as feedback, for a fixed budget per goal; plus two days a quarter of human red-teaming, which Anthropic reports finds vectors automated systems miss.</li>
</ul>
<p><strong>5. The quantity I choose: how many attempts make a claim.</strong> To say "below 1 percent per attempt" with 95 percent confidence after observing zero successes, n must satisfy 0.99<sup>n</sup> ≤ 0.05, so n ≥ ln 0.05 / ln 0.99 = 298.07, so 299 attempts per goal class. At five goal classes that is 1,495 agent runs per release, which a release every two weeks can afford if the runs are cheap; I would run the full adaptive budget weekly and a 300-attempt regression slice per release. A team that cannot afford 300 per class should say "below 5 percent" (n ≥ 59) rather than shrink the sample and keep the claim.</p>
<p><strong>6. The decision, with two defensible answers.</strong></p>
<ul>
<li><strong>Spend the quarter on the adaptive attacker.</strong> It produces the number the security lead believes and finds new classes. Its cost: the deterministic controls stay untested as properties, and the adaptive rate is a lower bound on what a better attacker gets.</li>
<li><strong>Spend it on deterministic controls and their tests.</strong> It produces guarantees that hold whatever the attacker does, for the tools those controls cover, and CaMeL shows the form: a utility cost (77 against 84 percent of AgentDojo tasks) instead of an attack rate. Its cost: whatever runs without such a control is measured only by the old suite.</li>
</ul>
<p>The constraint conflict is one engineer's quarter against coverage, and the release cadence against campaigns that take days. I would do the harness and the deterministic tests first, because they make every later number meaningful and catch regressions on every release, and start the adaptive loop in week 7 against the tools with no deterministic control.</p>
<p><strong>Where this measurement fails.</strong> The ledger sees only the effects someone modelled; an exfiltration path nobody faked (a rendered image, a DNS lookup) scores as safe. The adaptive attacker is ours, built in a quarter, and the published gap between static and adaptive results says a stronger attacker will do better, so the rate is reported as "at least". And utility can fall without anyone noticing if the dashboard shows only the attack column.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Is refusal rate ever useful?</em> As a utility signal on benign tasks with injected noise: a defence that refuses half the legitimate work has a cost the attack column hides.</li>
<li><em>Should the suite be public?</em> A public suite becomes training data for the defence; keep a private held-out set and rotate it.</li>
</ul>

## Follow-ups

- *Pushback: the adaptive campaign costs more compute per quarter than the feature it protects. Which half do you cut, and what do you write in the risk register about what is no longer measured?*
- *Reversal: what result from the adaptive loop would make you remove a probabilistic layer, such as the injection classifier, instead of tuning it?*
- *The model vendor ships a new version in sixty days and your attack success rate on it is three times the current one, while utility is up. Who decides whether it ships, and on what number?*

## Common mistakes

- Grading the model's words instead of the tool calls and requests that happened.
- Reporting a rate without the attacker's budget, the number of attempts, or the confidence bound.
- Treating last year's suite as a benchmark for defences that were tuned on it.
- Measuring deterministic controls as rates, when they should be tested as properties that hold for every input.
