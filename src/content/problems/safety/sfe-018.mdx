## Question

<Callout kind="interview" label="As a vendor's compilation of candidate reports phrases it">
"How would you threat-model an LLM inference API that receives untrusted user input at scale?" A third-party prep site lists this among questions candidates report from Anthropic security engineer interviews; it is a candidate report, not a confirmed question.
</Callout>

The API you are given (scenario): a public, pay-as-you-go endpoint serving one family of models on a shared GPU fleet. Requests carry text and image URLs that the API fetches; responses can include top-k logprobs; automatic prefix caching is on and shared across all traffic on a replica, which the serving team chose for its hit rate; customers include SaaS companies that serve many of their own end users through one API key. Every request is logged in full for 30 days for abuse review.

You have one quarter and two security engineers. The serving team will not rewrite the scheduler this quarter. Produce the threat model (assets, adversaries, entry points, threats with controls), make the calls the serving and finance teams will dispute, and write the risk note you would send them. You choose the logprob exposure and the cache isolation key.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what a new account costs an attacker and how fast it can be created; that sets who your adversary is.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the prefix cache hit rate by tenant, and what share of hits come from prefixes shared across tenants.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which customers use logprobs, and for what: classification, evals, or something that needs many alternatives per position.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The assets are other tenants' prompts and outputs, the model weights and architecture, the fleet's capacity and the provider's bill, and the hosts that fetch URLs. The adversary is any paying customer, because accounts are cheap, plus a co-tenant on shared hardware. The serious threats are cross-tenant leakage through the shared prefix cache (timing reveals whether someone else sent a prefix), model extraction through logprobs, denial of wallet through long inputs, SSRF through the image fetcher, and the 30-day full-text log as the largest store of customer data. I key the cache by organisation and offer a per-request salt for SaaS customers' end users, cap logprobs and never combine them with logit bias, admit requests by token cost, fetch images through an egress proxy, and cut the log to what abuse review needs. The cache change costs hit rate; that is the argument with finance.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Entry points and threats, ranked by what an attacker gains.</strong></p>
<p>1. Shared prefix cache. A cached prefix returns its first token faster. If the cache is shared across tenants, an attacker who guesses a prefix (a competitor's system prompt, a document template, a name inside a prompt) can test it by timing. This is not hypothetical: the 2025 audit reports global cache sharing at seven API providers, detected by timing alone. Controls: key the cache by tenant. Anthropic documents organisation and, on its own API, workspace isolation; vLLM supports a per-request <code>cache_salt</code> mixed into the first block's hash.</p>
<p>2. Model extraction. The "Stealing Part of a Production Language Model" paper recovered the embedding projection of two production models for under $20 using logit bias with top-k logprobs, and the paper lists refusing the two in one request as a mitigation. Controls: cap k, never allow logit bias and logprobs together, rate-limit logprob requests per key, and watch for query patterns that sweep the vocabulary.</p>
<p>3. Unbounded consumption. Request-count rate limits miss the point when one request can carry a full context window: prefill cost scales with input tokens. Controls: admission and quotas in tokens (input plus <code>max_tokens</code>), per-key concurrency, timeouts, and per-account spend caps so a stolen key is a bounded loss (OWASP LLM10:2025 lists denial of wallet and variable-length input floods).</p>
<p>4. The image fetcher. A URL the API fetches is SSRF from inside the fleet: cloud metadata at <code>169.254.169.254</code>, internal admin endpoints, redirects and DNS rebinding. Controls: fetch through an egress proxy that blocks private and link-local ranges, validate every redirect hop, pin the resolved address between check and use, cap size and decode time. Image decoders are parsers of untrusted bytes; run them in a sandboxed process separate from the GPU workers.</p>
<p>5. Co-tenancy below the API. Continuous batching puts several tenants' sequences in one batch on one GPU. The scheduler isolates them logically; the hardware may not. LeftoverLocals (CVE-2023-4969) showed GPU local memory readable by a co-resident process on some Apple, AMD and Qualcomm parts, not on NVIDIA by the vendor's statement. Controls: no customer code on serving GPUs, a hardware inventory checked against such advisories, and dedicated replicas for tenants who contract for them.</p>
<p>6. Logs. Thirty days of full prompts and outputs is the largest pool of customer data you hold and the one most employees can reach. Controls: log metadata and classifier verdicts by default, keep full text only for flagged requests, restrict and audit access.</p>
<p>7. Prompt injection. At this layer the API does not know the customer's trust boundaries, so it cannot fix injection for them. Provider-side classifiers are probabilistic; Anthropic's own containment post says any probabilistic defence has a non-zero miss rate. What the API owes customers is tools to enforce boundaries (structured tool calls, per-request isolation) and honest documentation.</p>
<p><strong>The calls the other teams will dispute.</strong></p>
<p>Cache isolation key. A: per organisation. Cost: tenants who share a popular prefix (a public framework's system prompt) no longer share its cached KV, so hit rate and GPU cost move the wrong way; the hint asks for the cross-tenant share of hits because that share is the cost. B: global sharing only for prefixes the provider publishes or that many unrelated tenants send, per organisation otherwise. Cost: a classifier of "public" prefixes that can be wrong, and a residual leak when it is. I choose A this quarter because it needs no scheduler rewrite, only a different hash input, and revisit B with measured hit rates. Per organisation is not enough for SaaS customers: their end users share one key and one cache, so one end user can time another's prompts. Expose a salt parameter and document that multi-user customers must set it per end user.</p>
<p>Logprob exposure. The reader chooses k. Reasonable: a small top-k that covers classification and calibration use, with logit bias refused in the same request, decided from what the customers in the hint actually use. Unreasonable: full-vocabulary logprobs, which hand the attack its ideal input, or removing logprobs entirely without asking the eval and classification customers who depend on them.</p>
<p><strong>What I give up.</strong> Some cache hit rate and its GPU cost; logprob features some customers asked for; full-text logs that made abuse investigations easy.</p>
<p><strong>Where it fails.</strong> Cache isolation by organisation closes cross-tenant timing, not other timing channels: batch composition and queueing delay also depend on other tenants' load; I have no measurement showing whether they leak content, so the note lists them as open, not closed. The salt protects only customers who set it; a SaaS customer who does not read the documentation still exposes their users to each other, so the default for keys with many end users should be enforced by account configuration, not left to each request.</p>
<p><strong>The risk note.</strong> Accepted for this quarter: residual timing channels other than the prefix cache; co-tenancy risk on current NVIDIA hardware per the vendor's statement. Mitigated: cross-tenant cache timing, logit-bias extraction, SSRF, denial of wallet. Rollout: per-organisation cache keys behind a flag, compared on hit rate and p50 time to first token for two weeks; rollback if the GPU cost increase exceeds the budget finance signs in advance, in which case the next step is B, not global sharing.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How do you detect prompt injection at the infrastructure level?</em> You mostly cannot see it as injection; you see its effects. Unusual tool-call patterns, sudden URL fetches in outputs, or repeated near-identical prompts with small variations (a resampling attack) are measurable at the API.</li>
<li><em>What would you put in front of the image fetcher first if you had a week?</em> The egress proxy that blocks private and link-local ranges; it covers metadata theft whatever the parser bugs are.</li>
<li><em>Which of these threats does a jailbreak classifier address?</em> None of the first six; it addresses content policy, which is a different asset.</li>
</ul>

## Follow-ups

- *Pushback: finance shows the per-organisation cache key raises GPU cost by more than the security budget. Which half do you cut, and what risk do you accept in writing?* Keep isolation for every request that carries customer-specific text after the shared prefix and allow sharing only for exact provider-published prefixes; the written risk is that timing then reveals that someone recently sent a given published prefix, which says which framework is in use, not what any tenant wrote after it.
- *Reversal: what would you need to see to turn global prefix sharing back on?* A measured timing experiment against your own fleet showing the hit and miss distributions are indistinguishable at realistic load, repeated after each scheduler change; a statement that the leak is "theoretical" is not evidence, since the 2025 audit measured it at seven providers.
- *Two senior engineers disagree: one wants logprobs removed, the other wants them unchanged because an eval customer depends on them. How do you decide without deciding by rank?* Ask the customer what they compute, measure whether a capped k answers it, and price the extraction risk at the capped k with logit bias excluded; the decision is whichever leaves the smaller written residual risk for the same customer need.
- *Operating: a regulator asks where customer prompts are stored and for how long.* The 30-day full-text log is the answer you do not want to give; that is the reason to change it this quarter rather than next.

## Common mistakes

- Treating the threat model as a list of jailbreaks and leaving out tenancy, caching and the fetcher.
- Rate-limiting by request count when cost scales with tokens.
- Isolating the cache by organisation and forgetting that a SaaS customer's end users share one organisation.
- Exposing logit bias and logprobs together because each was safe to ship alone.
- Keeping full-text logs by default and calling them an abuse control.
