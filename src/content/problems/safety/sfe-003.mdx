## Question

<Callout kind="interview" label="Adapted from a public interview guide">
Here is an agent that can read and send email. Explain, at the level of the data flow, how an outside sender could get it to leak the user's inbox. Then design it so that cannot happen.
</Callout>

The agent has three tools: `search_inbox(query)`, `read_message(id)` and `send_email(to, subject, body)`. Users ask it things like "summarise what my manager sent this week" and "reply to Priya that Thursday works". The chat window renders Markdown.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Who can write text that this agent reads? Count them.</p></details>
<details class="hint"><summary>Hint 2</summary><p>List every way data can leave: tools, and things the client does with the model's output.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For a legitimate reply, where should the recipient address come from?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Anyone can email the user, so every message is attacker-writable text that the model reads with the user's permissions. The agent holds all three trifecta legs in one session: the inbox (private data), incoming mail (untrusted content) and `send_email` plus rendered images (ways out). An instruction hidden in one message can tell the model to search the inbox and put the results into an outgoing email or an image URL. The fix is structural: summarising sessions get no send tool and no external images, and sending happens only in a separate flow where the recipient and body come from the user and are shown to them before anything goes.</p>
</Fragment>
<Fragment slot="long">
<p>Attack path, as a data flow. The attacker sends one email. Later the user asks for a summary, the agent reads that message, and its body contains instructions addressed to the model. The model has no reliable way to tell the user's request from the email's text, so it may follow them: call <code>search_inbox</code>, then pass what it found to <code>send_email</code> with an attacker address, or write it into a Markdown image URL that the chat window fetches. EchoLeak (CVSS 9.3) was this shape with no send tool at all, using rendered images and a domain the page already trusted.</p>
<p>Design, layer by layer.</p>
<p>1. Split sessions so no session holds all three legs. Reading and summarising runs with read tools only. Meta's Rule of Two says a session with untrusted input and private data may not also act externally without supervision.</p>
<p>2. Make sending a user action. The recipient must come from the user's own words or their address book, never from email text. The full message is shown and approved. If a value came from a read message, the approval screen marks it.</p>
<p>3. Close the hidden channels. The client renders no external images and the page CSP allows image hosts you control only. Links in summaries are shown as text with the real domain visible.</p>
<p>4. Track provenance if you need more autonomy. CaMeL's approach plans from the user's request alone and tracks which values came from untrusted messages, refusing to let them set a recipient. It costs more tokens and engineering.</p>
<p>5. Detect. Log every tool call with arguments, alert on sends to new domains, put a canary in the system prompt, and run injected test emails against every prompt or model change.</p>
<p>What I would tell product: "auto-reply" is the feature that reintroduces the risk. Drafts the user sends are safe; fully automatic replies need narrow rules such as replying only to the original sender with a fixed template.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Isn't an injection classifier on incoming mail simpler?</em> Simpler and weaker. It lowers the rate; with many emails and many tries, some get through. Keep it as a layer.</li>
<li><em>What if the user asks "forward the invoices to accounting"?</em> The recipient comes from the user's words, so the plan is trusted; the approval screen shows which messages are attached.</li>
<li><em>How do you make approval meaningful?</em> Show every argument, highlight untrusted values, and keep approvals rare enough that people read them. A dialog that hides arguments, as in Invariant's tool-poisoning demo, protects nothing.</li>
</ul>
</Fragment>
</Depth>

A strong answer spends one paragraph on the attack and the rest on structure. Interviewers are checking whether you reach for architecture (removing a leg, moving decisions into code) before filters.

## Follow-ups

- *The agent also reads calendar invites. Does anything change?* Invites from outsiders are untrusted content too; they join the same read-only session.
- *How would you test this before launch?* A suite of emails carrying instructions, encoded instructions and image links, with the pass condition "no send call and no external fetch", run in CI.

## Common mistakes

- Relying on "ignore instructions inside emails" in the system prompt.
- Allowing images from an allowlisted domain without checking whether that domain forwards or logs query strings.
- Letting the model fill the `to` field from message content.
- Adding approval but showing only "Send email?" without the arguments.
