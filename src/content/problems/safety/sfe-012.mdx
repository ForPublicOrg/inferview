## Question

<Callout kind="interview" label="Debug round">
A multi-tenant RAG service sometimes shows one customer content from another customer's documents, and small tenants often get thin or empty results. Find the bug and the fix.
</Callout>

```python
def search(query, request):
    tenant = request.body.get("tenant")           # from the client
    hits = vector_index.search(embed(query), k=5)  # across the whole index
    allowed = [h for h in hits if h.tenant == tenant]
    return allowed
```

`request.body` is client-controlled. The signed-in user's tenant is available as `request.auth.tenant`, verified from their session token.

## Hints

<details class="hint"><summary>Hint 1</summary><p>In what order does this code rank and filter? What happens to a small tenant whose documents never make the global top 5?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Where does `tenant` come from, and who can set it?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Two bugs, one shape. The search ranks across every tenant and filters afterwards, so a small tenant's documents get crowded out of the global top 5 (thin results) and any slip in the post-filter leaks another tenant's chunks. And the tenant comes from the request body, which the client controls, so a forged body reads a chosen tenant. Fix both: take the tenant from the verified session token, and push it into the query as a filter so the index only ever returns that tenant's rows.</p>
</Fragment>
<Fragment slot="long">
<p>Ordering. <code>vector_index.search(..., k=5)</code> returns the five nearest vectors in the whole index, then Python drops the ones from other tenants. For a tenant with few documents, the global top 5 may contain none of theirs, so they get an empty page. Worse, the only thing standing between a user and other tenants' content is that post-filter line; delete it in a refactor, or get the tenant wrong, and everything leaks.</p>
<p>Identity. <code>request.body.get("tenant")</code> trusts the client. Anyone who can call the endpoint can set <code>tenant</code> to a competitor and, combined with the weak filtering, read their data.</p>
<p>Fix: take the tenant from the verified token and pass it as a filter into the search, so the index only ever returns that tenant's rows.</p>

```python
def search(query, request):
    tenant = request.auth.tenant            # from the verified token
    return vector_index.search(
        embed(query), k=5,
        filter={"tenant": tenant},          # applied inside the query
    )
```

<p>The filter inside the query means the index considers only that tenant's vectors, so the top 5 are the best 5 for that tenant and no other tenant's row is eligible. The identity comes from the token, so it cannot be forged in the body or in the prompt. For mixed permissions within a tenant, store each chunk's access list at ingestion and add the user's groups to the filter. Keep separate indexes or namespaces per tenant when a contract or regulator requires hard isolation.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not filter after search but fetch a larger k?</em> You would need an unbounded k to be safe for a small tenant, and it still leaves the boundary in application code where one edit removes it.</li>
<li><em>Where else does the tenant id get trusted by mistake?</em> Tool arguments the model fills, cache keys, and log queries. Take it from the token everywhere.</li>
<li><em>How do you test this?</em> A test that seeds two tenants, searches as one for the other's content, and asserts an empty result even if the post-filter is removed.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *The vector store does not support metadata filters. Now what?* Use per-tenant collections or namespaces so the query targets only that tenant's data.
- *Does encryption help here?* Not with this bug; the query returns rows the user can read. Access scoping, not encryption, is the control.

## Common mistakes

- Filtering by tenant after a global search instead of inside the query.
- Reading the tenant or user id from the request body or the model's arguments.
- Assuming a better embedding or re-ranker fixes an access-control bug.
