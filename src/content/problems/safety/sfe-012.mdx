## Question

<Callout kind="interview" label="Debug round">
"A customer says our assistant quoted another customer's refund policy to them. Here is the service, the last deploy and what we have. Which defect explains it, what else is wrong, and what do you do in the next hour?"
</Callout>

A multi-tenant document assistant. Every tenant's chunks live in one vector index.

```python
ANSWERS = TTLCache(maxsize=50_000, ttl=3600)

def handle(request):
    user = auth.verify(request.headers["Authorization"])   # signed session token
    question = request.json["question"]
    key = "ans:" + sha256(normalise(question).encode()).hexdigest()
    if key in ANSWERS:
        return ANSWERS[key]
    chunks = retrieve(question, tenant=user.tenant_id)
    log.info("retrieval", tenant=user.tenant_id, ids=[c.id for c in chunks])
    reply = llm.generate(build_prompt(question, chunks))
    ANSWERS[key] = reply
    return reply

def retrieve(question, tenant):
    hits = index.query(vector=embed(question), top_k=20,
                       namespace="prod", include_metadata=True)
    mine = [h for h in hits.matches if h.metadata["tenant"] == tenant]
    return rerank(question, mine)[:5]

def ingest(tenant, filename, text):
    for n, chunk in enumerate(split(text)):
        index.upsert(namespace="prod", vectors=[{
            "id": f"{filename}#{n}",
            "values": embed(chunk),
            "metadata": {"tenant": tenant, "text": chunk},
        }])
```

Last Tuesday's deploy made three changes: `top_k` went from 10 to 20, `normalise()` now lowercases and strips punctuation, and the `ANSWERS` cache was added to cut model spend.

What you have:

- Globex's ticket: at 14:02 UTC the assistant answered "What's the refund window for annual plans?" with a 45-day window and the phrase "Initech annual subscriptions". Globex has no such document.
- Globex has retrieval log lines all day, but none between 13:55 and 14:10.
- The on-call engineer checked the index: every chunk whose text mentions Initech carries `tenant: initech`.
- Separately, since Tuesday Globex says questions about its employee handbook often come back with "I could not find that in your documents".

## Answer

<Depth>
<Fragment slot="short">
<p>The answer cache. Its key is the normalised question with no tenant in it, so the first tenant to ask a common question writes an answer grounded in its own documents, and every other tenant asking within the hour reads it back. A hit returns before retrieval, which is why Globex has no retrieval log line at 14:02. Two more defects are real but did not cause this leak: the tenant filter runs after a global top-20 search, which starves small tenants and leaves one line of Python as the boundary, and chunk ids built from file names let one tenant's upload overwrite another's chunks, which is the likeliest cause of Globex's missing handbook answers.</p>
</Fragment>
<Fragment slot="long">
<p><b>The leak.</b> The cache was keyed for the single-tenant case: same question, same answer. In a multi-tenant system the answer is a function of the question and the documents the asker may read, so the key must carry both, or grounded answers must not be cached at all. Tuesday's <code>normalise()</code> change did not cause the leak but widened it: more questions now collide on the same key. The evidence is consistent but not proof. To confirm it, check that the provider has no request for Globex at 14:02, and find an Initech request in the hour before with the same normalised question. Then add the writer's tenant to each cache value and count reads where the reader's tenant differs; that count is also the size of the incident.</p>
<p><b>The next hour, without waiting for proof.</b> Turn the answer cache off and purge it. The cost is the model spend and latency the cache was added to save, and it is the only change that stops the leak whatever the remaining evidence shows. Notify affected tenants once the cross-tenant read count exists, not before.</p>
<p><b>The fix.</b> Key on tenant, the user's permission scope, the corpus version and the normalised question, or cache retrieval results per tenant instead of answers. Tenant alone is not enough when documents inside a tenant have different readers: Microsoft's Copilot documentation states the rule, only data the individual user can at least view, and a tenant-wide key would serve HR's answer to an intern.</p>
<p><b>Second, the shared namespace with a post-filter.</b> With every tenant in <code>prod</code>, a top-20 search returns the 20 nearest chunks across all tenants; when a large tenant's chunks fill them, the filter leaves Globex with few or none, and Tuesday's increase from 10 to 20 only softened that. It also means the only thing between tenants is the list comprehension. Pinecone's guidance is one namespace per tenant, with reads and writes that always target a single namespace; with a filter instead, every query scans the whole namespace, 1 RU per GB, so the shared layout is also the expensive one.</p>
<p><b>Third, file-name ids.</b> An id made of the file name and the chunk number is global, so any tenant uploading <code>handbook.pdf</code> replaces chunk records of every other tenant's <code>handbook.pdf</code>, metadata included. That is a cross-tenant write: Initech can delete Globex's knowledge without either noticing. Ids must include the tenant and a document id the server assigns, and per-tenant namespaces make the collision impossible.</p>
<p><b>The failure mode of the fix.</b> Keying the cache on tenant and permission scope cuts its hit rate, possibly to the point where it no longer pays for itself, and a scope that is computed wrong (stale group membership) recreates the leak inside a tenant. Measure the hit rate per tenant after the change before deciding the cache is worth keeping.</p>
</Fragment>

**Why the correct choice is correct.** It is the only defect on the path that served Globex's request: a cache hit, no retrieval, no model call, an answer generated from another tenant's documents.

**Why the others are tempting.** The post-filter looks like the classic multi-tenant bug and is the reason for Globex's thin results, but it filters correctly. The file-name ids are a genuine cross-tenant bug and change what Globex can find, but in the wrong direction for this symptom. The provider cache is a real, published concern, and an engineer who has read about it reaches for it first; it leaks timing, not text, and this request never reached the provider.

## Follow-ups

- *Your fix keys the cache on permission scope. Group membership changes; how long can a cached answer outlive a revoked permission, and who signs off on that window?*
- *A tenant asks for proof that no other tenant saw its data during the incident. What can you prove from the logs you have, and what can you not?*
- *Where else in this service does an identifier cross tenants?* Log fields, trace attributes, evaluation sets built from traffic, and any tool whose arguments the model fills.

## Common mistakes

- Fixing the post-filter and declaring the leak closed, because it is the bug everyone expects in multi-tenant retrieval.
- Adding the tenant to the cache key and forgetting per-user permissions inside the tenant.
- Waiting for proof before turning the cache off, while the leak keeps serving answers.
- Treating the file-name collision as a data-quality issue rather than one tenant writing into another's data.
