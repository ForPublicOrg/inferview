## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"A product team wants to give the support agent write access to the payments database to speed up refunds. Talk them out of it, or tell me the guardrails that would make it acceptable."
</Callout>

The support agent reads customer messages, which anyone can send, and answers billing questions. The ask is a direct `UPDATE` capability on the payments tables.

## Hints

<details class="hint"><summary>Hint 1</summary><p>What is the smallest capability that still solves "speed up refunds"?</p></details>
<details class="hint"><summary>Hint 2</summary><p>The agent already reads untrusted text. What does adding a write to money give an injected instruction?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Which of these actions must be reversible or idempotent, and how?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Direct write access is excessive agency: the agent reads attacker-writable messages, so an injection could issue or alter refunds, and a hallucinated amount could do it by accident. Do not grant table writes. Instead expose one narrow operation, <code>issue_refund(order_id, amount)</code>, whose code validates that the order belongs to the customer, caps the amount at the refundable balance, is idempotent on a key, and logs. Refunds above a threshold need human approval that shows the real arguments. That gives the speed without handing the model a write to money.</p>
</Fragment>
<Fragment slot="long">
<p>Why to refuse the raw capability. The agent sits in the lethal-trifecta zone already: untrusted input (customer messages) and, with a DB write, the ability to change state. An injected instruction in a support message could move money, and even with no attacker a wrong amount or wrong order from the model writes straight to payments. OWASP calls this excessive agency, LLM06.</p>
<p>The counter-proposal, as a tool firewall. Replace "write to the table" with a single function the model can call:</p>
<p>1. Scope: <code>issue_refund(order_id, amount)</code> and nothing else. No arbitrary SQL, no other tables.</p>
<p>2. Validate in code against identity: the order must belong to the signed-in customer (from the session token, not from the message), the amount must not exceed the order's refundable balance, and the currency and status must be right. These checks live in the tool, not in the prompt.</p>
<p>3. Idempotency: derive a key from the conversation and order so a retry after a timeout does not refund twice, and the tool returns the first result for a repeated key.</p>
<p>4. Human approval for the risky slice: refunds over a threshold, or to a changed payee, require a person who sees the order, the amount and the balance before approving. The MCP tools guidance is the general form: a human should be able to deny the call and see the inputs first.</p>
<p>5. Limits and audit: a per-day refund cap per agent session, rate limits, and a log of every call with arguments and outcome, alerting on unusual volume.</p>
<p>What I would say to product: this is faster than the old manual path for the common small refund, and it keeps the blast radius of a bad instruction to one validated, reversible-by-policy, logged operation instead of the whole payments table.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>They say approval is too slow.</em> Auto-approve only the low-risk slice (small amount, unchanged payee, order owned by the customer) and keep approval for the rest; measure what fraction that covers.</li>
<li><em>How do you stop a refund to an attacker's account?</em> The payee is the order's original payment method, taken from the record, never from the message.</li>
<li><em>What if the DB has no refundable-balance field?</em> Add it, or compute it from prior refunds; without it the amount cap cannot be enforced, which is itself a reason to refuse the raw write.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *Could you use database row-level permissions instead of a tool?* You still want the validation and idempotency logic somewhere; a stored procedure with the same checks is the same idea in the database.
- *How is this different from a human agent with write access?* A human is not steered by text in the ticket; the model is, so the model needs the checks in code that a trained human applies by judgement.

## Common mistakes

- Granting the write and relying on the system prompt to constrain it.
- Validating the order ID but taking it, or the customer identity, from the message instead of the session.
- Forgetting idempotency, so a retry double-refunds.
- Putting approval on every refund until staff click through without reading.
