## Question

<Callout kind="interview" label="Debug round">
An agent triages new GitHub issues against a checkout of the repository. Its only tool runs shell commands behind an allowlist of read-only programs. Yesterday the host's flow log recorded a connection from the agent's container to an address nobody recognises, during a run on an issue opened by an outside account. Which defect explains how a tool with no network program on its allowlist produced that connection? Rank the others.
</Callout>

The tool, as deployed (constructed for this problem):

```python
# agent/tools/shell.py
import shlex
import subprocess

ALLOWED = {"ls", "cat", "grep", "git"}
GIT_READ_ONLY = {"status", "diff", "log", "show"}


def check(cmd: str) -> bool:
    parts = shlex.split(cmd)
    if not parts or parts[0] not in ALLOWED:
        return False
    if parts[0] == "git" and parts[1] not in GIT_READ_ONLY:
        return False
    return True


def run_command(cmd: str, workdir: str) -> str:
    if not check(cmd):
        audit("run_command", bin=cmd.split()[0], decision="deny")
        return "blocked: command not allowed"
    audit("run_command", bin=shlex.split(cmd)[0], decision="allow")
    out = subprocess.run(cmd, shell=True, cwd=workdir,
                         capture_output=True, text=True, timeout=30)
    return out.stdout + out.stderr
```

The runner's service definition:

```yaml
agent-runner:
  image: triage-agent:2026.10.21
  volumes: ["/srv/checkouts:/work"]
  networks: [default]
```

The evidence you have. The audit log for the run, the host's flow log, and nothing else: transcripts are kept only as the final triage comment, which reads normally.

```text
audit  10:41:02 run_command bin=git  decision=allow
audit  10:41:05 run_command bin=grep decision=allow
audit  10:41:09 run_command bin=cat  decision=allow
audit  10:41:15 run_command bin=grep decision=allow
flow   10:41:16 agent-runner-3 -> 203.0.113.52:443 tcp bytes_out=2318
```

The checkout contains a `.env` with staging credentials, which is not in `.gitignore` for that directory.

## Answer

**The cause.** The check and the executor read different things. `check` looks at `shlex.split(cmd)[0]`; `subprocess.run(cmd, shell=True)` gives the whole string to `/bin/sh`, which honours `;`, `&&`, `|`, newlines and `$(...)`. A command that starts with `grep` and continues after a separator passes the check on its first word and runs both halves. The audit line has the same blind spot: it records `bin=grep` because it logs the token the check read, which is why the log shows only allowed programs a second before the connection. An instruction hidden in the issue body is the likely source of the string, and the most plausible reading of 2,318 bytes out after a `cat` and a `grep` is the contents of `.env`.

**Why the others are tempting, in rank order.**

1. Open egress is the second defect and the reason the damage happened. With a network-denied container the chained command would have run and failed. Fixing it alone leaves arbitrary execution inside the container, which can still delete the checkout or tamper with the triage comment.
2. Unconfined paths for `cat` and `grep` are a real gap: `cat /proc/self/environ` would show the runner's own environment, which may hold more than `.env` does. It did not move any bytes out.
3. The `git` branch has two smaller defects: a bare `git` raises `IndexError` on `parts[1]`, and the read-only subcommands still take options that write files, such as `--output=<file>`. Neither starts a network program.
4. The quoting theory is a denylist intuition. An allowlist refuses every token that is not exactly one of its four names, quoted or not.

**What the evidence does not show, and what to collect.** You do not have the command strings, so the chaining is the only mechanism in this code that fits, not an observed fact. Collect the full argument vectors of every process the container started (from the container runtime or host process accounting, if it was on), the issue body as fetched, and whether the destination resolves to anything you own. Without them, act on the reading above: rotate every credential in that `.env` and anything reachable from the runner's environment, deny egress on the runner now, and pause the agent on issues from outside accounts until the fix ships.

**The fix.** Stop passing strings to a shell. The model supplies an argument list; the tool checks the program and every argument, and runs without a shell:

```python
import os
import subprocess

ALLOWED = {"ls", "cat", "grep", "git"}
GIT_READ_ONLY = {"status", "diff", "log", "show"}


def _inside(path, root):
    full = os.path.realpath(os.path.join(root, path))
    return full == root or full.startswith(root + os.sep)


def check(argv, root):
    if not argv or argv[0] not in ALLOWED:
        return False
    if argv[0] == "git":
        if len(argv) < 2 or argv[1] not in GIT_READ_ONLY:
            return False
        return not any(a.startswith(("--output", "--ext-diff", "-c", "--exec-path")) for a in argv[2:])
    return all(a.startswith("-") or _inside(a, root) for a in argv[1:])


def run_command(argv, workdir):
    root = os.path.realpath(workdir)
    if not check(argv, root):
        audit("run_command", argv=argv, decision="deny")
        return "blocked: command not allowed"
    audit("run_command", argv=argv, decision="allow")
    out = subprocess.run(argv, shell=False, cwd=root, capture_output=True, text=True, timeout=30)
    return out.stdout + out.stderr
```

With `shell=False` a `;` is an ordinary argument to `grep`, so chaining is gone. The audit records the whole argument vector. The option checks are the weak part: the git list is a denylist inside an allowlist and will miss options, and options name files too (`grep -f /path` reads its patterns from anywhere), which the path check skips. That is the part that needs a sandbox behind it. Run the container with no network, the checkout mounted read-only, and no credentials in it: argument checks narrow what a fooled agent can ask for, and the sandbox bounds what it gets when the checks miss.

## Follow-ups

- *The triage agent now needs to run the project's test suite. What happens to this design, given that a test run executes code from the repository the issue author may control?*
- *Product asks to keep `shell=True` because the model writes better pipelines with it. What do you offer instead, and what do you require if they insist?*
- *How do you test the fix so it stays fixed?* Regression cases that pass separators, substitutions and newlines as arguments and assert that no second process starts, plus a run in the network-denied container that asserts a connection attempt fails.

## Common mistakes

- Adding `;` and `|` to a blocklist while keeping the shell; newlines, backticks and `$(...)` still chain.
- Logging the token the check read instead of the command that ran, so the audit trail cannot show a bypass.
- Treating egress as the cause and closing it, while the agent can still run anything inside the container.
- Validating the program and not its arguments.
