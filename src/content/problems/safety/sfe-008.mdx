## Question

<Callout kind="interview" label="Debug round">
A toy agent has one tool that runs shell commands behind an allowlist. The intent is that it can only run `ls` and `cat`. Show where an agent (or an injected instruction) could run something else, and fix it.
</Callout>

```python
import shlex, subprocess

ALLOWED = {"ls", "cat"}

def run_command(cmd: str) -> str:
    first = shlex.split(cmd)[0]
    if first not in ALLOWED:
        return "blocked"
    result = subprocess.run(cmd, shell=True, capture_output=True, text=True, timeout=5)
    return result.stdout
```

The model chooses the string passed as `cmd`. Pick the root cause, then read the fix.

## Hints

<details class="hint"><summary>Hint 1</summary><p>What does the allowlist actually inspect, and what does the shell actually execute?</p></details>
<details class="hint"><summary>Hint 2</summary><p>How does a shell treat a string with a `;` or a `|` in it?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The check reads only the first word and then runs the whole string through a shell with <code>shell=True</code>. A string that starts with an allowed word and chains a second command after a separator passes the check and still runs, because the shell interprets the separator. The fix is to stop using a shell and stop matching strings: take an argument list, allowlist the binary and validate every argument, run with <code>shell=False</code>, and sandbox the process.</p>
</Fragment>
<Fragment slot="long">
<p>The bug is the gap between what is checked and what is run. <code>shlex.split(cmd)[0]</code> returns the first token; <code>subprocess.run(cmd, shell=True)</code> hands the entire string to <code>/bin/sh</code>, which honours separators such as <code>;</code>, <code>&amp;&amp;</code> and <code>|</code>. So a command that begins with <code>ls</code> and continues after a <code>;</code> satisfies the allowlist on its first word and executes both parts. This is the same class as Claude Code's rule about compound commands: a rule must match every subcommand, not the prefix, which is why its permission engine splits on shell separators and evaluates deny before ask before allow.</p>
<p>The fix takes an argument list instead of a string, so there is no shell to interpret separators:</p>

```python
import subprocess

ALLOWED = {"ls", "cat"}

def run_command(argv):
    if not argv or argv[0] not in ALLOWED:
        return "blocked"
    if argv[0] == "cat" and any(a.startswith("-") or "/" in a or ".." in a for a in argv[1:]):
        return "blocked"   # validate arguments, not just the binary
    result = subprocess.run(argv, shell=False, capture_output=True, text=True, timeout=5)
    return result.stdout
```

<p>The call site passes <code>["ls", "docs"]</code>, never a string. With <code>shell=False</code> there is no shell to interpret separators, so chaining is impossible; the argument checks stop path traversal and option injection for <code>cat</code>. For anything beyond a couple of read-only commands, run it in a sandbox with no network and a read-only filesystem, so a bypass is still contained.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not just reject strings containing <code>;</code> and <code>|</code>?</em> Blocklists miss newlines, backticks, <code>$()</code>, and quoting tricks. Remove the shell instead of trying to sanitise for it.</li>
<li><em>Where does the deny, ask, allow order matter?</em> When rules overlap: a deny on <code>curl</code> must win over an allow on a broad pattern, and it must apply to every subcommand.</li>
<li><em>Is argument validation enough without a sandbox?</em> No. It reduces the attack surface; the sandbox bounds the damage if your validation has a gap.</li>
</ul>
</Fragment>
</Depth>

## Follow-ups

- *The tool needs to run `git`, which takes many subcommands. How do you allowlist that?* Allowlist specific `git` subcommands and flags explicitly, as an argument-level policy, not the `git` binary alone.
- *How would you test the fix?* Assert that an argv with a separator token is passed through literally (and fails as a bad path), and that no string form is accepted by the call site.

## Common mistakes

- Keeping `shell=True` and adding a blocklist of separators.
- Validating the binary and not the arguments (path traversal through `cat ../../etc/passwd`).
- Assuming an allowlist removes the need for a sandbox.
