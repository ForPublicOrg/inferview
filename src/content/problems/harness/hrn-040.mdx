checklist:
  - Separates the artefacts by owner and states who may write each one, with the agent limited to status and evidence fields in the feature list
  - Enforces the ownership rules with a check outside the model (a pre-push guard or branch protection), not only with prompt text
  - Chooses a structured format for the state the harness must parse and free text only for advisory notes, with a reason for each
  - Writes a session protocol that starts by reading state and running a smoke test of features already passing, and ends with a commit, a status change with evidence, and a progress entry
  - Decides how product edits to the feature list reach a running night of sessions without colliding with the agent's own edits
  - Chooses how many features a session takes from the turn cap and the measured turns per feature, and shows the arithmetic
  - Bounds the start-of-session smoke test as the number of passing features grows, for example with a deterministic sample plus the features touched by recent commits
  - Keeps QA-owned tests read-only to the agent and gives it a way to flag a broken test instead of editing it
  - Says what happens when the smoke test finds a regression, before any new feature work
  - States a failure mode of the design, such as the agent marking a feature passing on weak evidence it produced itself
  - Writes a rollout with rollback triggers and states what the design gives up
  - "Judgement call: letting the agent edit init.sh is acceptable if every change to it is flagged for the morning review"

## Question

<Callout kind="interview" label="Workflow design, 45 minutes">
A coding agent will build an internal application over three weeks of unattended nights, one fresh context window per session. Design what persists between sessions, in what format, and who may edit each piece. Then write the protocol every session follows, and the rollout.
</Callout>

Scenario, not a measured system. The application is a vendor-onboarding portal for procurement. Product has broken the specification into 180 user-visible features. Each night the harness starts sessions back to back from 20:00 to 06:00; a session ends at 150 turns or $25 of spend, whichever comes first. The agent pushes to `agent/nightly`; humans merge to `main`.

A pilot week measured these numbers (scenario numbers):

| Measurement | Value |
|---|---|
| Turns to orient at session start (read state, start the app, check it runs) | 10 |
| Turns per feature, median | 35 |
| Turns per feature, 90th percentile | 120 |
| Browser end-to-end check, per feature | 40 seconds |

The people and systems around it:

- Two engineers review the night's work each morning, one hour each.
- The product manager reprioritises and adds features twice a week, sometimes in the evening while sessions are running.
- QA owns the end-to-end suite in `e2e/`. The agent may run it and must not change it.
- CI runs unit tests only and its configuration will not change this quarter.

## Answer

<Depth>
<Fragment slot="short">
<p>Four artefacts, each with one writer. A feature file per feature in the repository, JSON, where product owns the description, steps and priority and the agent may change only the status and its evidence. An append-only progress log the agent writes and nobody parses. A notes file humans write and the agent only reads. And the git history. A guard in the agent's push step rejects any commit that edits a field or path the agent does not own. Each session orients, smoke-tests what already passes, takes one feature, verifies it end to end, commits, flips the status with evidence, appends progress and exits.</p>
</Fragment>
<Fragment slot="long">
<p><b>What persists, and why each format.</b> The harness and the guard parse the feature list, so it is structured. Anthropic's long-running harness uses JSON for the same reason and reports the model is less likely to change or overwrite JSON than Markdown. The progress log is read only by the next session as advice, so free text is fine; the truth about progress is the feature statuses, the tests and the commits, never the log. The notes file is where a human tells the agent something ("the vendor tax ID is validated server-side, do not add a client check"); keeping it apart from the agent's log keeps the agent from editing a human's instruction. Plans and decisions that span sessions go in a checked-in decisions file, as OpenAI's harness team does with its execution plans and decision logs, so a later session does not reopen a settled choice.</p>
<p><b>One file per feature or one list.</b> Both are defensible. One list, as Anthropic used, is one read for the agent and one diff for the reviewer. The cost here is the product manager: an evening edit to a 180-entry file and the agent's status flips on the same file will conflict on many nights. One file per feature (<code>features/F-0123.json</code>) puts those edits on different files and lets the guard check ownership file by file; the cost is a listing step for the agent and a less readable morning diff. With a product manager editing during the night, I pick one file per feature. Product edits go through pull requests to <code>main</code>, and each session merges <code>main</code> into <code>agent/nightly</code> as its first step, so an edit reaches the agent within one session.</p>
<p><b>Who may edit what, enforced.</b> The guard runs in the harness before every push. It rejects a commit that changes any feature field other than <code>passes</code> and <code>evidence</code>, adds or deletes a feature file, or touches <code>e2e/</code>, <code>notes-from-humans.md</code> or the CI configuration. Anthropic's prompt calls removing or editing tests unacceptable; here that sentence becomes a rejected push. Branch protection on <code>main</code> is the second line, because a guard inside the agent's own container is code the agent could in principle change. The agent may add new tests in <code>e2e-proposed/</code> for QA to adopt. When it believes a QA test is wrong, it writes the case to the progress log, marks the feature blocked, and moves on.</p>
<p><b>The quantity: features per session.</b> Orientation costs 10 turns. One feature per session spends 10 of a median 45 turns, 22%, on orientation. Two features would cut that to 10 of 80, 12.5%, but a 90th-percentile feature started second needs 10 + 35 + 120 = 165 turns, over the 150 cap. After a median first feature the second has 105 turns left, and every feature above the 90th percentile needs more than that, so at least one two-feature session in ten would end mid-feature with uncommitted work. I take one feature per session, and allow a second only when the first finished within 20 turns (10 + 20 + 120 = 150 still fits). Reasonable choices sit between strict one-per-session and that rule; two or more unconditionally ignores the 90th percentile.</p>
<p><b>The smoke test has to stay bounded.</b> Running every passing feature's browser check at session start costs 40 seconds each: at 180 features that is 7,200 seconds, two hours of every session. The C compiler harness hit the same wall and added a <code>--fast</code> flag that runs a deterministic 1% or 10% sample. I run the features touched by the last five commits plus a 10% sample seeded by the session number; at 180 features the sample is 18 checks, 12 minutes. The full suite runs once a night in a separate job whose failures land in the notes file.</p>
<p><b>The session protocol.</b> Merge <code>main</code>. Read the notes, the tail of the progress log, <code>git log</code> and the feature statuses. Run <code>init.sh</code> and the smoke test. If anything that was passing now fails, set it back to failing with the failure as evidence and fix it before new work. Otherwise pick the highest-priority failing feature, implement it, verify it through the browser, commit, set <code>passes</code> with evidence (the commit and the test run identifier), append a short progress entry and exit. A session that reaches the cap commits its work in progress to a branch named for the feature and leaves the status alone.</p>
<p><b>The conflict.</b> Autonomy against correctness: the agent grades its own work. Anthropic reports that without prompting the model marked features complete after unit tests or curl checks and missed end-to-end failures. Requiring a browser run as evidence closes part of that gap, not all of it.</p>
<p><b>Failure mode of this design.</b> The guard enforces who writes which field, not whether the evidence is true. An agent can run a browser check that never exercises the feature's steps and attach a real run identifier to it. The morning review samples flipped features, and a QA-owned end-to-end test, when one exists for the feature, is the evidence that counts. A second failure: the progress log grows by one entry per session, and by the third week a session that reads the whole log spends its orientation turns on entries about finished features; roll older entries into a dated summary each morning.</p>
<p><b>What you give up.</b> About a fifth of every session's turns on orientation, product edits that wait up to one session, and nights where a disputed QA test blocks a feature until a person looks at it.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not one long session with compaction?</em> Anthropic found compaction alone did not always pass clear instructions to the next context; a fresh session reading files it can trust does.</li>
<li><em>Who may delete a feature?</em> Product, by pull request; the guard rejects deletions from the agent's branch.</li>
<li><em>What does the agent do with a merge conflict on a feature file?</em> Take <code>main</code>'s version of every human-owned field, and keep its own status only if its evidence commit is still in the history.</li>
</ul>

### The written artefact

The state contract, one page, filed in the repository as `docs/agent-state.md` and linked from AGENTS.md.

| Artefact | Format | Writer | Reader | Enforced by |
|---|---|---|---|---|
| `features/F-*.json` | JSON, one feature per file | Product (description, steps, priority); agent (`passes`, `evidence`) | Agent, guard, reviewers | Pre-push guard, branch protection |
| `progress.md` | Append-only text, rolled up daily | Agent | Next session | Guard rejects edits to existing entries |
| `notes-from-humans.md` | Text | Engineers, QA, product | Agent | Guard rejects agent edits |
| `docs/decisions.md` | Dated entries | Agent proposes, engineers approve | Agent, reviewers | Morning review |
| `e2e/` | Tests | QA | Agent runs them | Guard rejects agent edits |
| `init.sh` | Shell | Agent and engineers | Every session | Changes flagged in the morning review |

Rollout. Night one runs a single session with an engineer watching the first ten minutes. Week one runs full nights on the first 20 features. Roll back to supervised sessions if, in any week, more than two features the agent flipped fail QA's end-to-end suite the next morning, or if the guard rejects more than five pushes in one night, which means the protocol and the guard disagree.

## Follow-ups

- *Pushback: the morning review of flipped features takes both engineers' full hour and they want to drop it. Which half do you cut, and what risk do you accept in writing?*
- *Reversal: what would you need to see in a week of logs to let sessions take two features unconditionally?*
- *Two senior engineers disagree: one wants the feature list in the issue tracker the product manager already uses, the other wants it in the repository. How do you decide without deciding by rank?*
- *Operating: QA's suite has eight flaky tests and the agent marks those features blocked every night. Who fixes them, and what does the agent do until then?*

## Common mistakes

- Telling the agent in the prompt not to edit tests and calling that enforcement.
- One shared Markdown file for progress, features and human instructions, which the agent then rewrites.
- A smoke test that runs every passing feature, which grows until it is most of the session.
- Treating the progress log as the source of truth for what is done, instead of the statuses, tests and commits.
- Letting a session start new work on top of a regression the smoke test found.
