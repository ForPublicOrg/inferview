## Question

<Callout kind="interview" label="The prompt">
"Design an AI coding agent for our engineers. Walk me through how it builds each model call, what tools it has, how it manages context, what it is allowed to do, how it knows it is done, and what stops it. Then tell me what you would build and what you would rent."
</Callout>

The operating constraints are a scenario, given by the interviewer:

- A Python and TypeScript monorepo, with CI on self-hosted runners that the platform team will not rewrite this year.
- Legal requires zero data retention with the model provider for anything containing source code.
- Security allows no network egress from wherever agent commands run, except an internal package mirror. A staff security engineer opposes any merge that a person has not approved.
- Four engineers and twelve weeks to a pilot with two product teams: the agent picks up a ticket or a failing test, works on a branch, and opens a pull request.
- The director wants a hard cost ceiling per task, and a number for it in the design.

Write the design, choose the numbers you are asked for, and end with a one-page decision memo on build versus rent with a rollout plan and rollback triggers.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask legal whether conversation state held by the provider between requests counts as retention under the terms they signed.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Rent the loop, build the outer harness. For the pilot I would run an existing harness without a terminal (the Claude Agent SDK, or the open-source Codex harness, chosen by which model family wins on our own tasks) inside our own container on the CI runners, with egress limited to the package mirror, a stateless request path for zero data retention, deny-by-default permissions because nobody is there to answer a prompt, a Stop check that runs the affected tests, and turn and spend caps the harness enforces. We own the sandbox, the hooks, the eval set and the telemetry; the vendor owns request assembly, caching and compaction. The cost is control over the request and the upgrade cadence, which I accept for twelve weeks and revisit with data.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Request assembly.</strong> Static first, changes appended. Instructions and tool definitions form a prefix that does not change within a run; repository guidance (a short `AGENTS.md` or `CLAUDE.md` that points into `docs/`) and environment context follow as messages; the conversation is appended. Configuration changes arrive as new messages, never as edits to earlier ones, which is how Codex keeps its cache. Zero data retention rules out provider-held conversation state such as `previous_response_id`, so every request resends the history, and prefix caching is what keeps that affordable.</p>
<p><strong>Tools.</strong> Read, search, edit and a shell, plus one internal MCP server for the ticket system with a read-only token. Each result is capped with a saved-file fallback. Read-only calls run together; edits and shell commands run in order.</p>
<p><strong>Context.</strong> Compaction keeps the ticket text and acceptance criteria verbatim, keeps recent turns, summarises the middle, and re-reads the guidance files. A run that needs more than one compaction is a signal the ticket was too large, and that run is counted.</p>
<p><strong>Permissions and sandbox.</strong> Commands run in a container per run with the checkout mounted, no credentials beyond a branch-scoped token, and egress only to the mirror. Inside it, a parsed allowlist (test runners, linters, package install from the mirror, git without push to protected refs) and deny for everything else, since an unattended run must not wait on a prompt. Push is allowed to the agent's own branch only; branch protection keeps the person-approved merge the security engineer asked for.</p>
<p><strong>Verification.</strong> A Stop check runs the tests the change touches plus the linters, and sends failures back to the agent with a cap on consecutive continuations. The pull request carries the evidence: the commands run, their results and the diff summary, generated by the harness rather than written by the model.</p>
<p><strong>Budgets.</strong> A turn cap and a spend cap per task, both enforced by the harness; the spend check runs after each response, so the cap is a ceiling minus one response's cost. The numbers come from the hand-run sample in Hint 2.</p>
<p><strong>Build versus rent.</strong> Building our own loop buys model portability and full control over request assembly and telemetry; mini-swe-agent shows the core loop can be about 100 lines. What takes the months is everything around it: the permission parser, compaction, caching discipline, tool ergonomics, and the eval that says whether any of it helped. Renting the loop gets the pilot running in weeks and leaves our four engineers on the parts only we can build: the sandbox, the policy, the Stop check and the evals.</p>
</Fragment>

### The numbers you were asked to choose

None of these can be read off a vendor page; each comes from the pilot sample in Hint 2, and the design says so.

- **Spend cap per task.** Run 30 to 50 representative tasks by hand with the chosen harness and record cost per task. Set the cap near the 95th percentile of successful runs, so the cap stops the runaways and not the hard-but-healthy tasks. A cap at the median kills half the successes; no cap leaves the director without the ceiling they asked for. Because the Agent SDK checks spend after each response, the effective ceiling is the cap plus one response.
- **Turn cap.** The same method on turns, with the extra turn for a final answer: the Agent SDK counts that last text-only response as a turn, and a run without room for it ends with no response at all.
- **Tool-result budget.** Claude Code's default for Bash is about 30,000 characters inline with the rest saved to a file. Start there, and lower it if traces show test logs crowding out the task.
- **Consecutive Stop-check continuations.** Claude Code caps them at eight. For CI, fewer: three failed attempts at the same test with no new edits is a run to stop and report.

### Build or rent: the two defensible answers

| | Rent the loop (Agent SDK or the open-source Codex harness) | Build the loop on the raw API |
|---|---|---|
| Time to pilot | Weeks; the team works on sandbox, policy and evals | Most of the twelve weeks goes into the loop, compaction and the permission parser |
| Request assembly and caching | The vendor's; tuned for its models, opaque in places | Ours, and so are its cache bugs |
| Models | Tied to the harness's model family | Any provider that meets the retention terms |
| Upgrades | A new version can change the system prompt and tools, which changes behaviour and rebuilds the cache | Only when we change it |
| Data | Transcripts land where the harness writes them, for example Claude Code's local JSONL session files, so the container must be ephemeral or the files collected under our retention policy | Wherever we put them |

### What you give up

With the rented loop we give up control over how each request is built and over when that changes: an upgrade can move pass rates, so versions are pinned and upgraded only after the eval set runs. We give up model choice for the pilot. The security engineer's rule means no auto-merge, so the agent's throughput is bounded by review capacity, and the pilot will show it.

### Decision memo and rollout plan

**Decision.** Rent the loop for the pilot, with an adapter boundary (task in; branch, transcript, cost and evidence out) so a self-built loop can replace it without touching CI. Revisit at week 12.

**Rollout.** Weeks 1 to 4: sandbox, policy, Stop check, evals on 40 recorded tasks. Weeks 5 to 8: one team, agent opens pull requests, people merge. Weeks 9 to 12: second team; measure.

**Rollback triggers,** any one of which pauses the pilot:

- Any write outside the run's checkout or any egress attempt other than the mirror, from the sandbox audit log.
- Agent pull requests reverted after merge at a higher rate than the same team's human pull requests over the same weeks.
- Spend per merged pull request above the ceiling the director signed, two weeks running.
- The share of runs ending on a refused command rising after an allowlist change, which means the policy and the work have drifted apart.

**The failure mode of this design.** The outer harness assumes the vendor's inner harness behaves the same tomorrow. A harness upgrade that changes compaction or tool definitions can shift pass rates without any change on our side, and a pinned version eventually stops supporting the model we need. The pinned version and the eval gate on upgrades are the mitigation, and the week-12 review is where the build option comes back with real numbers.

## Follow-ups

- *Legal reads the terms again and says provider-held conversation state is fine. Does anything in your design change?* Payloads could shrink with provider-held state; the cache already keeps resends cheap, so I would measure before switching.
- *A team asks for network access to call a staging API in tests. What do you change, and what do you write down?*
- *The pilot's merged pull requests are mostly one-line fixes. Is the agent working, or is ticket selection flattering it?*

## Common mistakes

- Drawing the loop and stopping, with no answer for what the agent may run unattended.
- Letting an unattended run ask for approval, which in CI means it either hangs or someone auto-approves.
- A spend limit that is a dashboard rather than a cap the harness enforces.
- Choosing "build" for control without counting the months that go into compaction, permissions and caching.
- Choosing "rent" without pinning versions, then debugging a behaviour change that came from an upgrade.
