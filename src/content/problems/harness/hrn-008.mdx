## Question

<Callout kind="interview" label="Design round, 45 minutes">
You own the internal coding agent. Procurement requires that it runs on models from three vendors: Anthropic, OpenAI, and an open-weight model your infrastructure team serves. The security team will approve production use only if every action the agent takes is checked against rules they can read, and every decision is logged with the rule that allowed it. Choose the tool set.
</Callout>

Operating constraints: your platform team is three engineers for one quarter. Every agent action already runs in a container sandbox that the infrastructure team owns and will not rebuild this year; it restricts writes to the workspace and blocks network by default. You have 200 internal tasks with tests that you use as an eval set.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask security what they mean by "an action": the command string the model wrote, or the effect on files and the network.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for each vendor's documented edit tool, and whether anyone has measured your tasks with each vendor on each format.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what a difference in pass rate on 200 tasks has to be before it is more than noise.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A small typed core that every vendor's calls are translated into: read, search, list, edit and run, where run takes an argument vector, plus a shell tool that requires approval. Each vendor keeps the edit format it is documented with (string replacement for Claude, V4A patches for OpenAI's apply_patch) and an adapter turns both into one internal edit with a path and a diff. The policy engine and the audit log see only the internal actions. The sandbox stays the containment boundary, and a per-step diff of the workspace is logged so that a file changed through the shell is still audited.</p>
</Fragment>
<Fragment slot="long">
<p>The options, each with its cost.</p>
<p><strong>Bash only</strong>, as in mini-swe-agent: about 100 lines, no dependence on tool calling, runs on any model, and the project claims over 74% on SWE-bench Verified. It is the cheapest to build and the most portable. The cost lands on security: every action is a shell string, and a rule over shell strings is a shell parser. Compound commands, redirects, subshells and <code>python -c</code> all carry effects the rule cannot see from the command's first word. The audit log would record commands, not intents, and edits would be <code>sed</code> and heredocs with no structured diff.</p>
<p><strong>Bash plus a string-replacement editor</strong>, the two-tool scaffold Anthropic used for its Claude 4 SWE-bench numbers (72.5% for Opus 4, 72.7% for Sonnet 4, vendor-reported). Edits become structured: a path, the old text and the new text, which security can write path rules against and log as diffs. Reads, searches and execution still go through bash, so the audit problem is halved, not solved. OpenAI documents a different edit tool, apply_patch with V4A diffs, so one of three vendors is on a format it was not documented with unless you adapt.</p>
<p><strong>A broad typed set</strong>, as in Claude Code: Read, Grep and Glob need no permission inside the working directory, Bash needs permission except for a built-in list of read-only commands, and rules can be scoped by argument. Every tool is a separate rule surface, which is what security asked for. The costs: every definition is paid on every request, each tool's name and schema has to work for three model families, and three engineers have to maintain and evaluate all of it.</p>
<p><strong>Code as the action space</strong>, where the model writes a program that calls tools. Anthropic reports a 37% token reduction from programmatic tool calling on complex research tasks. One action is now a program, which is the hardest case for a rule security can read.</p>
<p>My choice: the typed core of five tools plus an approval-gated shell, with vendor-native edit formats behind an adapter. The policy engine evaluates the internal action, for example <code>edit(path="billing/repo/invoices.py", diff=...)</code> or <code>run(argv=["pytest", "-q"])</code>, so security reviews one rule language whatever the vendor. Run takes an argument vector because a rule over <code>argv[0]</code> and flags is checkable and a rule over a shell string is not; a task that needs pipes or redirects goes through the shell tool and an approval.</p>
<p>The quantity I chose: a vendor may use a non-native edit format only if its pass rate on the 200 tasks drops by less than 8 points against its native format, measured on the same tasks. At a pass rate near 60%, the standard error of one proportion on 200 tasks is √(0.6 × 0.4 / 200) ≈ 3.5 points, and of the difference between two independent runs about 4.9 points, so a gap under about 10 points is not distinguishable from noise unless the comparison is paired task by task. Pairing on the same tasks narrows that, which is why 8 points is my threshold and not 3. A threshold under 5 points on 200 tasks would act on noise.</p>
<p>Failure mode of this design. The model can route around the typed tools: <code>run(["python", "-c", "open('x.py','w').write(...)"])</code> edits a file without passing the edit rule. The typed rules are the audit layer, not the containment. That is why the sandbox's write scope stays the enforcement and why each step logs a diff of the workspace, so the audit records what changed on disk whichever tool changed it. The second failure: adapters drift when a vendor revises its edit format, and the first sign is a quiet drop in pass rate for one vendor.</p>
<p>What you give up: the bash-only design's portability and size, some peak performance for whichever vendor would do best with its own full tool set, and three engineers' time on adapters instead of features.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Security says the typed tools are theatre if <code>run</code> can write files. Do you remove the escape route or retract the claim?</em> Retract the claim and say so in writing: the typed rules make actions legible; the sandbox and the workspace diff make them safe.</li>
<li><em>What would you need to see to switch to bash only?</em> Policy and audit moved entirely to effects (workspace diffs, sandbox network and process logs) and accepted by security, plus eval results where the typed core shows no gain over bash on any vendor.</li>
<li><em>The open-weight model's tool calling breaks on nested JSON arguments. What do you change, and for which vendor only?</em> Flatten its schemas behind the same adapter; the internal action and the rules do not change.</li>
</ul>

### The written artefact

A decision memo, one page, filed with the security review.

- **Decision:** typed core (read, search, list, edit, run with argv) plus an approval-gated shell; vendor-native edit formats behind one internal edit action; policy and audit on internal actions; workspace diff logged per step.
- **Not chosen:** bash only (rules over shell strings cannot be audited), a broad typed set (more surface than three engineers can evaluate on three vendors), code as action space (one action is a program).
- **Accepted risk:** a file change made through `run` bypasses the edit rule; it is contained by the sandbox write scope and recorded by the workspace diff.
- **Rollback triggers:** a vendor's pass rate on the 200 tasks falls more than 8 points below its native-format baseline on two consecutive weekly runs (move that vendor to its native tool set); more than 5% of file changes in the audit come from `run` rather than `edit` in a week (the typed edit is failing the model; investigate before tightening); the shell approval rate exceeds the reviewers' capacity (move the commonest approved shell patterns into typed tools).

## Follow-ups

- *Your adapters and per-vendor evals cost more engineer time than the agent's features this quarter. Which half do you cut, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants each vendor on its own full native tool set, the other wants your typed core everywhere. How do you decide without deciding by rank?*
- *OpenAI's model is retired in sixty days and its replacement fails your edit adapter on 12 of 40 smoke tasks. Do you ship it degraded, hold the old model, or route those tasks to another vendor, and who signs off?*
- *Security now wants every read logged too. What does that cost in log volume and tokens, and what would you push back on?*

## Common mistakes

- Treating per-tool permission rules as containment. A model with any execution tool can produce any effect the sandbox allows.
- Forcing one edit format on every vendor without measuring each vendor on it.
- Writing allow rules over shell strings, such as allowing anything that starts with `npm`, and calling them audited.
- Comparing pass rates from a single run of 200 tasks and acting on a 3-point difference.
