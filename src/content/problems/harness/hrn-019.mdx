## Question

<Callout kind="interview" label="Multiple choice">
A Claude Code session in a monorepo has been running for two hours. Auto-compaction is about to fire. Which of the four instructions below is no longer in Claude's context right after compaction, before Claude reads or edits another file?
</Callout>

What happened before compaction, in order (Claude Code as documented on 2026-10-28):

1. The session started in the repository root. The root `CLAUDE.md` (90 lines) holds the build, test and lint commands and says that amounts are stored in integer minor units.
2. In plan mode, Claude wrote and you approved a plan for adding partial refunds.
3. You ran `/release-notes`, a skill whose `SKILL.md` is about 3,000 tokens.
4. Claude edited `services/payments/refunds.py`. That loaded `.claude/rules/payments.md`, which has `paths: ["services/payments/**"]` and says that every refund must go through `RefundLedger.record()` and never write to the `refunds` table directly.
5. Forty more turns of work, mostly in `services/notifications/`.

The next task is a reconciliation script in `tools/reconcile/`, which writes refunds.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each instruction, ask how it entered the context: through the session's startup context, from a file on disk, or as a message in the conversation.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which of the four the harness can find again on disk without anything happening in the conversation first.</p></details>

## Answer

The payments rule is gone. A rule with `paths:` frontmatter does not sit in the startup context: it is loaded into message history at the moment Claude reads, writes or edits a matching file. Compaction summarises message history, so the rule becomes whatever the summary kept of it, and Claude Code reloads it only when Claude next touches a file under `services/payments/`. The reconciliation script lives in `tools/reconcile/`, which the glob does not match, so Claude can write to the `refunds` table directly without the rule ever coming back. Nothing errors; the rule simply is not there.

The other three survive, each by a different mechanism:

- **Project-root CLAUDE.md** is re-read from disk and re-injected. If you edited it during the session, compaction is when the edit starts to apply, because a mid-session edit to the root file is not picked up until `/clear`, `/compact` or a restart.
- **The skill body** is re-injected, capped at 5,000 tokens per skill and 25,000 tokens across all invoked skills, oldest dropped first. At about 3,000 tokens this one fits. A 9,000-token skill would come back truncated to its start, so whatever sits at the bottom of a long `SKILL.md` is the part at risk.
- **The plan** lives in a file and is re-injected from disk.

Why the wrong picks are tempting. "Read once at session start" is true of the root file and is the reason a mid-session edit does not apply, so it is easy to extend that to "and therefore lost at compaction". Skills and the plan both arrive as conversation messages, which is the right model for the cache and the wrong one for compaction, because Claude Code treats both as content it can find again.

### What to do about it

The rule sits in the wrong mechanism for the work it guards. Writes to `refunds` happen outside `services/payments/`, so the path scope describes where the code lives, not where the risk is. Two defensible fixes, with different costs:

- **Drop `paths:` or move the rule into the root file.** It then survives every compaction and applies in `tools/reconcile/`. Cost: its tokens are in every request in every session, including the ones that never touch money. For a two-line rule that cost is small; for a 200-line rules file it is not, so pick a size you would accept in every request (a few hundred tokens is a reasonable ceiling) and keep only the lines that pass it unscoped.
- **Enforce it outside the prompt.** A `PreToolUse` hook, a lint or a database grant that rejects direct writes to `refunds` from anything except the ledger. Cost: someone writes and maintains the check, and it fires on legitimate migrations unless it has an exception path.

The constraint conflict is context cost against persistence. My pick is both: keep a one-line unscoped pointer ("refunds go through `RefundLedger.record()`; see `.claude/rules/payments.md`") and add the database or lint check, because a rule that matters this much should not depend on what the model remembers. Failure mode of that recommendation: the one-line pointer survives but the detail behind it does not, so Claude knows the rule exists and does not read the file before writing; the enforcement check is what catches that case.

## Common mistakes

- Assuming everything that was in context before compaction is equally at risk. Startup content and files on disk come back; content that arrived because of a conversation event comes back only when the event happens again.
- Writing a "Compact Instructions" section and treating that as a guarantee. It steers the summary; it does not re-inject a rule verbatim.
- Choosing path scopes by directory layout when the rule is about a resource that code outside the directory can also touch.
