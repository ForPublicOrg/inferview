## Question

<Callout kind="interview" label="Design round">
"Our root AGENTS.md has grown to about a thousand lines, and the agents ignore half of it. Redesign how the repository's knowledge reaches agents, and make it stay correct without someone policing it."
</Callout>

The situation, as a scenario:

- A monorepo of about 60 packages owned by four teams. Engineers use Codex, Claude Code and Cursor; none of the three can be dropped this year.
- The root `AGENTS.md` is about 1,000 lines and 52 KB: a product overview, a directory tour, style rules, release and incident procedures, per-package conventions, and around 40 lines starting with NEVER or ALWAYS. Three packages also have their own `AGENTS.md`.
- The staff engineer who wrote most of it uses it to onboard new hires and does not want it split up.
- You have one quarter. Any check you add to CI must fit in the two minutes the CI owners will allow.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Before redesigning, ask how "ignore" was measured: is the ignored half not followed, or never loaded? Request each tool's view of what it loaded for one session.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each NEVER and ALWAYS line, ask whether a program could check it.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which incidents in the last quarter would have been prevented by a line that is in the file today.</p></details>

## Answer

<Fragment slot="short">
<p>Part of the "ignored" half is never loaded: Codex stops adding instruction files at 32 KiB by default, so a 52 KB root file leaves no room for the nested files that are supposed to override it. The rest is a single file doing six jobs. I would replace it with a root map of about 100 lines, nested AGENTS.md files per package, a docs tree as the system of record, rules a program can check promoted into lints whose messages tell the agent how to fix the violation, and CI checks on size, links and freshness, plus a gardening job that opens fix-up pull requests. Every line left in an AGENTS.md has to be something the agent cannot read from the code.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Measure first.</strong> Codex concatenates root to working directory and stops at <code>project_doc_max_bytes</code>, 32 KiB by default; at 52 KB the root file alone passes it, so the three package files are not added and their overrides never apply (the docs do not say whether the root file itself is cut partway, but their troubleshooting section lists truncated instructions as a symptom). Claude Code reads AGENTS.md whole when there is no CLAUDE.md, and its docs recommend staying under 200 lines because adherence falls with length. Cursor combines nested AGENTS.md files with the root. So "ignored" means different things per tool, and the first artefact is a table of which lines each tool loaded in one real session per tool.</p>
<p><strong>Sort every line by job.</strong> Inferable from the code (the directory tour, style rules the formatter enforces): delete; the ETH study found overviews did not help agents find files and context files raised cost by about 20%. Decisions and background (the product overview, why the event bus is not used for billing): <code>docs/design-docs/</code>, linked from the map. Procedures (release, incident response): <code>docs/runbooks/</code>, and for Claude Code also skills, which load only when used. Package conventions: the package's own AGENTS.md. Zero-exception rules: lints, structural tests, branch protection or hooks. What remains in the root: commands, the map of where things are documented, and the few cross-cutting facts the code does not show.</p>
<p><strong>Enforce it mechanically</strong>, in under two minutes of CI. A size check: root AGENTS.md at most 120 lines, and for every package the root-to-package chain under 24 KiB, which leaves a margin under Codex's default. A link check: every path and doc reference resolves. An executable-commands check: the commands block is parsed and each command runs with a dry-run flag. A freshness check: every doc declares an owner and the paths it describes, and is flagged when those paths have changed in more than a chosen number of merged pull requests since its last-verified date; 20 is a reasonable start for this repository. Rules promoted to lints carry remediation text in their error message, the way OpenAI's harness team writes its custom lints. A weekly gardening agent reads flagged docs against the code and opens fix-up pull requests to the owning team.</p>
<p><strong>Prove it with an eval.</strong> Twenty to forty real tasks per team, run with the old file and the new layout, comparing success, steps and cost per task. A drop in cost with no drop in success is the result to expect; a drop in success on one team's tasks names the line that was load-bearing.</p>
</Fragment>

### Two defensible designs

**Tool-neutral.** A root AGENTS.md map, nested AGENTS.md per package, `docs/` as the system of record, lints for rules. All three tools read AGENTS.md, so there is one source and one review path. Cost: scoping is by directory only, so a convention about all database migrations, wherever they live, cannot be targeted; and no tool's richer mechanism (path globs, on-demand skills, rules applied when the agent judges them relevant) is used.

**One source, compiled per tool.** Rule files in `docs/agent-rules/` with frontmatter for scope, compiled by a script into `.claude/rules/*.md` with `paths:`, `.cursor/rules/*.mdc` with `globs`, and nested AGENTS.md for Codex. Better targeting. Cost: a generator to maintain and three outputs to test, and the semantics differ under the same frontmatter: a Claude Code path-scoped rule is summarised away at compaction until a matching file is touched again, and a Cursor rule applied by description loads only when the agent decides it is relevant.

I would ship the tool-neutral design this quarter, because four teams have to migrate their content and one format is what fits the deadline, and build the compiler only for rules the eval shows are missed under directory scoping.

### The constraint conflict, and the staff engineer

Onboarding and agent context want different documents. Humans read a narrative once; agents pay for every line on every request. The resolution I would write into the decision memo: the narrative moves intact to `docs/onboarding.md`, owned by the staff engineer, linked from the map, so nothing is lost for humans; the agent files hold only what passes the "cannot infer" test. What you give up: a single file that is both, and the guarantee that an agent sees a fact without choosing to open a doc.

### The decision memo, in outline

- Decision: root map of at most 120 lines, nested package files, docs tree, lints for checkable rules, CI checks for size, links, commands and freshness.
- Rejected: raising the Codex byte limit (keeps cost and noise); per-tool files maintained by hand (three copies drift).
- Rollout: one team's packages first, then the rest over six weeks; the old file stays in `docs/` for reference, not loaded.
- Rollback triggers: success on the eval tasks falls for any team, or the same correction appears in agent reviews three times in a week for a rule that was removed.

### Where this fails

Progressive disclosure depends on the agent choosing to open the right doc. A rule that moved from the root file into `docs/` is now read only if the agent decides it is relevant, and the failure is silent: the agent does not know what it did not read. Watch read counts for linked docs against the tasks that needed them, and promote anything that is skipped and matters into a package AGENTS.md or a lint. The second failure is noise: a freshness check that flags too often produces gardening pull requests nobody reviews, and the checks become ignored the way the file was.

## Follow-ups

- *The CI owners say the commands check flakes twice a week and want it removed. Do you drop it, and what risk do you accept in writing?*
- *What would you need to see in the eval to give the compiled per-tool design the next quarter?*
- *Two team leads disagree about whether security rules belong in the root map or only in lints. How do you decide without deciding by rank?*
- *One of the three tools changes its default instruction-file limit next month. What in your design depends on it, and what tells you it changed?*

## Common mistakes

- Splitting the file into `@` imports and calling it shorter. Claude Code loads imported files together with the file that imports them, so the context cost is unchanged.
- Moving NEVER rules into a docs page instead of a check, which makes them less visible and no more enforced.
- Redesigning without first finding out which lines each tool actually loaded.
- Writing freshness checks with no owner field, so every flagged doc is everyone's problem.
