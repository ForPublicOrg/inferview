## Question

<Callout kind="interview" label="Design round, 45 minutes">
Sixty product engineers on one monorepo want to run coding agents in parallel, several each, some of them unattended. You run the platform team. Decide where the agents run, what a change must pass before a person reviews it, how context is kept apart between agents, and how you will know whether the tokens are worth it.
</Callout>

Scenario numbers, not measurements of a real company:

- The model budget for agents is $40,000 a month.
- CI has 40 runners, a full run takes 35 minutes, and the pool will not grow this quarter. Human pull requests use about 60% of it during the working day.
- Security will not allow production credentials on any host where an agent runs, and wants network egress from agents limited to an allowlist.
- Every merge to `main` needs a human approval. That will not change.
- Your platform team is three engineers.

A two-week pilot with ten engineers measured:

| Measurement | Value |
|---|---|
| Agent task cost, mean / median / 90th percentile | $6.50 / $3.20 / $18 |
| Tasks that end in a merged PR | 46% |
| CI runs per agent task (every push triggers one) | 1.8 |
| Reviewer time per agent PR, median | 14 minutes |
| Agent task wall time, median | 40 minutes |

<details class="hint"><summary>Hint 1</summary><p>Work out which of the budget, the CI pool and reviewer time runs out first at sixty engineers.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>CI binds first, not tokens. Unattended agents run in cloud sandboxes that never hold credentials; interactive agents may use local worktrees with a checked list of what may be copied into them. Every change passes a gate inside its own sandbox (build, affected tests, lint, protected paths, a fresh-context review) before it is allowed to open a PR and touch shared CI. One task is one session, one checkout and one PR; no two agents write the same task. The measure is cost per merged PR including abandoned runs, read next to reviewer minutes and reverts.</p>
</Fragment>
<Fragment slot="long">
<p><b>Which constraint binds.</b> Budget: $40,000 / 60 engineers / 21 working days ≈ $31.75 per engineer per day, or 31.75 / 6.50 ≈ 4.9 tasks. CI: 40 runners × 480 minutes / 35 minutes ≈ 548 runs per working day, of which 40% is about 219 for agents. At 4.9 tasks and 1.8 runs each, sixty engineers would need 60 × 4.9 × 1.8 ≈ 529 runs. CI caps agents at 219 / 1.8 ≈ 122 tasks a day, about 2 per engineer, well under what the budget allows. Reviewers: 2 tasks a day at 46% merged is about 0.9 agent PRs per engineer a day, near 13 minutes of review at the 14-minute median, more if unmerged PRs also reach review. The design question is therefore how to spend less shared CI per task, and the token budget is a secondary cap.</p>
<p><b>Where agents run: two defensible answers.</b> Local worktrees (<code>claude -w</code>) cost nothing to build and start fast. Their costs: an agent inherits the engineer's network and whatever credentials are on the laptop, <code>.worktreeinclude</code> exists precisely to copy files such as <code>.env</code> into every worktree, each worktree reinstalls dependencies, and an unattended run stops when the laptop sleeps. Cloud sandboxes keep credentials out (Anthropic's Managed Agents uses the git token at sandbox start to clone and wire the remote, so the agent never handles it), enforce the egress allowlist in one place, and run unattended. Their costs: three engineers build and run the service, and container start time is user-visible; Anthropic reports that provisioning containers only when a session needs one, with inference starting before any container exists, cut p50 time to first token by roughly 60%, which shows how much an up-front container start costs. My split: sandboxes for anything unattended or background; local worktrees for interactive sessions, with a check in the repository that fails if <code>.worktreeinclude</code> lists anything outside an approved set.</p>
<p><b>The gate before a PR exists.</b> In the sandbox, before a PR is opened: the build, the tests affected by the diff, lint, a check that protected paths (CI configuration, lockfiles, auth code) are untouched, a diff-size cap, and a review against the task statement in a fresh context that never saw the agent's reasoning, as <code>/code-review</code> does. An agent that fails the gate iterates inside its own budget or abandons with a note. Only gate-passing changes open a PR, and the PR triggers shared CI once. If the gate brings shared runs per task from 1.8 to 1.0, the same 219 runs carry 219 tasks a day, about 3.6 per engineer. The cost moves to the sandboxes: affected tests run there on compute you pay for, not on the pool.</p>
<p><b>Context isolation.</b> One task, one session, one checkout, one PR. Parallelism is across independent tasks, never several writers inside one task: Cognition's point is that each action carries implicit decisions and parallel writers make conflicting ones, and the C compiler run showed the extreme case, sixteen agents on one kernel bug overwriting each other until GCC was used as an oracle to give them different files. Subagents are for read-only investigation that returns a summary. Mechanical changes across many files use fan-out where each unit is its own worktree and PR, as <code>/batch</code> does with 5 to 30 units.</p>
<p><b>The quantities I chose.</b> A concurrency cap of three running agents per engineer and a per-task budget of $25. At 3.6 tasks a day and 40 minutes each, an engineer averages 3.6 × 40 / 480 ≈ 0.3 agents running, so the cap only bites on bursts; three lets an engineer start a morning batch without one person's burst taking the pool. $25 sits above the pilot's 90th percentile of $18, so it stops runaways without cutting normal tasks. A cap of one would idle most engineers' mornings; a cap of ten would let six people take the whole CI share before noon.</p>
<p><b>Token return.</b> Cost per merged PR, counting abandoned runs: 6.50 / 0.46 ≈ $14. Read it next to reviewer minutes per merged PR and reverts within 14 days, per task type, because the cost per PR is meaningless if review time or reverts climb. OpenAI's harness team reports 3.5 merged PRs per engineer per day, but with a repository built for agents from the first commit; treat it as a ceiling seen under heavy investment, not a target.</p>
<p><b>The conflict.</b> Throughput against shared capacity and security: more agents per engineer means more runs on a pool humans also need, and local worktrees are the fast path that security has to trust. <b>Failure mode of this design.</b> Affected-test selection misses a dependency, the gate passes, and the breakage surfaces in shared CI or, worse, after merge; the gate then gives false confidence while still costing sandbox compute. Track how often a gate-passing PR fails shared CI, and widen test selection for the paths where it does. A second failure: cost per merged PR is easy to improve by splitting work into smaller PRs, which moves cost to reviewers.</p>
<p><b>What you give up.</b> Engineers wait for sandbox start on unattended work, the platform team spends the quarter on sandboxes and the gate instead of other work, and agents get about 3.6 tasks a day each instead of the 4.9 the budget would buy.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not raise the per-engineer cap and let CI queue?</em> Human PRs share the queue, so agent bursts become human wait time; the gate is how agents stop spending a resource they do not pay for.</li>
<li><em>When would you let two agents work on one task?</em> When the task splits into parts that share no decisions, which in practice means a fan-out of independent units, not two writers on one change.</li>
</ul>

### The written artefact

A decision memo for engineering leadership and security.

- **Decision:** cloud sandboxes for unattended agents, local worktrees for interactive ones with an approved `.worktreeinclude` list; an in-sandbox gate before any PR; one task per session, checkout and PR; three running agents per engineer and $25 per task.
- **Not chosen:** local worktrees for everything (credentials and egress outside security's control), several writers per task (conflicting decisions), shared CI as the first check (the pool is the binding constraint).
- **Accepted risk:** the gate's affected-test selection can miss a breakage that only full CI or production finds.
- **Rollout:** the pilot's ten engineers move to sandboxes in week one; twenty more in week three; everyone in week five.
- **Rollback triggers:** agent runs take more than 40% of CI minutes on any two days in a week (cut the concurrency cap to two); more than 15% of gate-passing PRs fail shared CI over a week (stop opening agent PRs until selection is fixed); reverts of agent PRs within 14 days exceed reverts of human PRs over a month (review the task types agents may take by default).

## Follow-ups

- *Pushback: the sandbox service takes your three engineers the whole quarter. Which half do you cut, and what risk do you accept in writing?*
- *Reversal: what would you need to see in a month of data to let unattended agents run in local worktrees?*
- *Two senior engineers disagree: one wants agents to open PRs immediately and let CI be the gate, the other wants your in-sandbox gate. How do you decide without deciding by rank?*
- *Finance sees $14 per merged PR and asks for the number per team. Two teams are at $60. What do you look at before you change anything?*

## Common mistakes

- Sizing parallel agents from the token budget and never checking the CI pool or reviewer time.
- Treating a worktree as isolation. It separates files; it shares the engineer's network, credentials and machine.
- Splitting one task across parallel writers to finish it sooner.
- Measuring cost per merged PR without the abandoned runs, which hides half the spend.
- Calling a gate a quality check when it runs only the tests an agent chose to run.
