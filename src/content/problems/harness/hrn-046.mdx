## Question

<Callout kind="interview" label="Design discussion">
"Our coding agent's benchmark score went up four points this week. The harness team wants it in Thursday's launch review as their win. Is it?"
</Callout>

The team and its numbers are a scenario; the benchmark and the published effects are real. The team runs its coding agent on Terminal-Bench 2.0 (89 tasks), five trials per task, with the same pinned model snapshot every time.

```text
run          harness  cluster                                   passes / trials   infra errors   posted score
last month   v1       old: limits pinned at each task's spec    183 / 445         24             41.1%
this week    v2       new: guaranteed spec, limit at 3x spec    201 / 445          3             45.2%
```

Harness v2 changed two things: compaction now triggers earlier, and the test-running tool runs a project's test files in parallel. The posted score counts infra errors (pod evictions, out-of-memory kills) as failures. The old cluster is deleted on Friday. This week's eval budget has room for about 900 more trials.

Say how much of the four points you would attribute to the harness, the infrastructure and noise from what is on the page, then design the run you would do before Thursday and the claim the team can make with it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask how the posted score treats infra errors, and recompute both scores the other way before arguing about the gap.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which change in v2 could need more memory or CPU than v1 did.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what claim the launch review needs: v2 beats v1, or v2 beats v1 on the hardware customers will run it on.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Nothing on the page attributes the four points. Half of it disappears when infra errors are dropped instead of scored as failures (43.5% against 45.5%), the rest is inside a binomial band of about ±6.5 points for an unpaired difference, and the cluster change is one Anthropic measured moving Terminal-Bench by up to 6 points with the model fixed. Before Thursday, spend the 890 trials on v1 and v2 interleaved on the new cluster and compare them paired by task; that supports "v2 beats v1 on the new cluster" and nothing about the old one. The cost is that the infrastructure share is never measured, and v2's parallel test runner is the change most likely to interact with memory limits.</p>
</Fragment>
<Fragment slot="long">
<p><b>What the numbers on the page say.</b> Rescore with infra errors dropped: last month 183 / (445 − 24) = 43.5%, this week 201 / (445 − 3) = 45.5%. Two of the four points are the old cluster's infra errors, which say nothing about either harness. On what is left, a binomial interval on 445 trials near 43% is 1.96 × √(0.43 × 0.57 / 445) = ±4.6 points per run, and the difference of two independent runs is ±6.5 points (√2 × 2.35 × 1.96). A 2-point gap, or a 4-point one, is inside it. Pairing by task can narrow that band a lot, but only for two arms run on the same tasks under the same conditions, which these two runs were not.</p>
<p><b>Why the cluster matters on its own.</b> Anthropic ran one model on Terminal-Bench 2.0 under six resource configurations. Infra errors fell from 5.8% at strict 1x limits to 2.1% at 3x, and success moved within noise over that range; uncapped resources scored 6 points above 1x. The team's move from pinned limits to a 3x limit is the range where Anthropic saw mostly infra errors change, which matches the rescoring above, but that was Anthropic's harness on Anthropic's cluster, so it is a prior, not a measurement of this team's setup. The interaction is the real risk: v2's parallel test runner uses more memory at once than v1, so v2 may gain more from the 3x limit than v1 does, and on the old cluster it might have lost points to out-of-memory kills.</p>
<p><b>The decision: which run to buy with 890 trials.</b> Two designs are defensible.</p>
<ul>
<li><em>Interleaved head-to-head on the new cluster.</em> Run v1 and v2 on all 89 tasks, five trials each, alternating arms so both see the same hours and the same API conditions, same model snapshot, same task-set version, configuration recorded with each trial. Compare per-task pass rates paired by task, report infra errors per arm. It answers the launch question cleanly for the cluster the product will run on. It costs any measurement of the infrastructure effect, and the 2x2 is never filled.</li>
<li><em>Fill the 2x2 before the old cluster is deleted.</em> Run v1 on the new cluster and v2 on the old one, 445 trials each, and read harness, infrastructure and their interaction from four cells. It is the only chance to measure the interaction, which is the question the parallel test runner raises. It costs a clean comparison: the two cells from last month ran in a different time window, so every contrast that uses them carries a time-of-day and API-drift confound that no amount of trials removes.</li>
</ul>
<p>Choose the first for Thursday. The claim the team can make is narrow and true: on the new cluster, with the model held fixed, v2's pass rate differs from v1's by the paired difference, with its interval, and with infra errors reported per arm. If the interval includes zero, the claim is that v2 is not worse, which is enough to ship a harness that is cheaper or simpler. Write down a decision rule before the run: for example, call v2 better only if the paired 95% interval excludes zero and the infra-error rates of the two arms are within a point of each other. A gap that clears the interval but sits under 3 points is reported with the configuration attached, because that is where Anthropic says leaderboard gaps stop being trustworthy across setups.</p>
<p><b>How the recommendation fails.</b> It answers the question for one cluster. Customers who run the harness on laptops or in their own CI with tight memory are closer to the old cluster than the new one, and that is exactly where v2's parallel test runner can fail; the interleaved run will not show it. Mitigate after the launch with a small targeted run: v1 and v2 interleaved at the task spec's limits on the tasks whose test suites are largest, since those are where the interaction would show. The other failure is reading the paired interval as covering everything: it covers trial noise on these 89 tasks, not a model snapshot that changed server-side or a task-set update between runs.</p>
<p><b>What is written down.</b> A one-paragraph result note: configuration of both arms, trials, paired difference and interval, infra errors per arm, the decision rule fixed before the run, and the sentence "the infrastructure share of last month's gap was not measured".</p>

## Follow-ups

- *Pushback: the budget is cut to 445 trials. Which arm do you run, and what risk do you accept in writing?* Run v1 alone on the new cluster and compare it with this week's v2 run: same cluster and configuration, a few days apart. Accept in writing that a drift in API latency or cluster load between the two runs is inside the result, and compare per task anyway, because the task set still pairs.
- *Reversal: what would make you accept the posted four points without a new run?* Both runs on the same cluster and configuration, interleaved or in the same window, with infra errors scored the same way, and a paired interval that excludes zero. None of that holds here, so nothing short of a new run settles it.
- *The infra lead wants the new cluster uncapped. What does that change?* Anthropic saw uncapped resources lift success 6 points over 1x on Terminal-Bench 2.0, so uncapped scores stop being comparable with anyone who publishes at the task spec. Keep the 3x limit for the comparison runs, report the multiplier with every score, and run uncapped only as a labelled ceiling.
- *Two senior engineers disagree: one wants the 2x2 for the record, the other wants the clean head-to-head. How do you decide without deciding by rank?* Ask which decision each result would change. If no plausible 2x2 result changes Thursday's launch call, the head-to-head wins this week, and the interaction question gets its own small run at tight limits.

## Common mistakes

- Arguing about a four-point gap before checking how each run scored infra errors.
- Treating two runs a month apart as a paired comparison because they share a task set.
- Reading Anthropic's resource results as this team's numbers.
- Claiming "v2 is better" when the measurement supports "v2 is better on this cluster".
- Choosing the decision rule after seeing the result.
