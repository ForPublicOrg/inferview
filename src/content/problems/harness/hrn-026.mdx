## Question

<Callout kind="interview" label="Design round">
Your platform team runs Claude Code headless in CI: when a pull request gets the <code>agent-fix</code> label, a job runs the agent to make the failing checks pass and push to the branch. Design the runaway controls: turn caps, dollar caps, what happens on repeated permission denials, and the alert that fires first when a run or the whole fleet starts to run away.
</Callout>

The situation, constructed for this problem:

- Two engineers own the job across 30 repositories. It runs about 400 times per weekday, spread over a ten-hour working day, on an API key in one Console workspace.
- Over the last 30 days, successful runs cost $0.80 at the median, $3.10 at p95, $6.40 at p99 and $11.20 at most, with a mean of $1.10. Turn counts: p99 of 34.
- Finance has set a hard monthly budget of $15,000 for this work and wants no surprises.
- Security wants `dontAsk` with an explicit tool list. The product team wants `auto`, because it fixes more pull requests that need network access.
- Last week one job used all 240 turns its wrapper allows, on a pull request whose tests need a database the sandbox cannot reach.

The current job:

```bash
claude -p "$TASK" --permission-mode auto --max-turns 60 --output-format json > out.json
for i in 1 2 3; do
  [ "$(jq -r .subtype out.json)" = "success" ] && break
  claude -p "Continue where you left off." --resume "$(jq -r .session_id out.json)" \
    --permission-mode auto --max-turns 60 --output-format json > out.json
done
```

The repository's `.claude/settings.json` has a Stop hook that runs the test suite and exits 2, sending Claude back to work, until the tests pass.

## Answer

<Depth>
<Fragment slot="short">
<p>Every control in the current job resets before it bites. Each resume starts a new turn count and, if a dollar cap is added, a new budget, because restored totals do not count toward <code>--max-budget-usd</code>. The Stop hook's eight-continuation cap resets on every tool call, and a test-fixing agent calls a tool between every block. In <code>-p</code>, auto mode's denial thresholds do not stop the run. So: a per-run dollar cap of about $8 that the wrapper carries across resumes, a 45-turn cap, at most one resume, a Stop hook that counts its own blocks, a stream watcher that interrupts a run after repeated denials, a burn-rate alert on the workspace, and the workspace spend limit as the backstop.</p>
</Fragment>
<Fragment slot="long">
<p>Why the current job ran 240 turns. Four sessions of 60 turns each, because each resume gets its own <code>--max-turns</code>. Inside each, the database calls were denied by the classifier and the run carried on, because in a non-interactive run there is no prompt to fall back to. Each time Claude tried to stop, the Stop hook sent it back to work; each time it ran a command, the hook's continuation count went back to zero.</p>
<p>The per-run dollar cap is the quantity to choose. At $8, the cap sits between p99 ($6.40) and the largest successful run ($11.20), so it stops fewer than 1 percent of runs that would have succeeded, at most about 88 a month out of roughly 8,800. A cap at p95 ($3.10) would kill about 440 a month that would have succeeded, and each needs an engineer. Anything from about $7 to $12 is defensible; below p99 the cap becomes a quality decision, not a safety one. Set the flag about $0.50 under the number you mean, because the check runs after each response and a running subagent can add to the overshoot.</p>
<p>The cap has to survive the resume. The wrapper sums <code>total_cost_usd</code> across the original run and the resume, and passes the remainder as the resume's <code>--max-budget-usd</code>. Allow one resume, only after <code>error_max_turns</code>, never after <code>error_max_budget_usd</code>.</p>
<p>The Stop hook keeps its own count. Key a counter file by <code>session_id</code>, block at most three times, then let the run stop with a summary that says the tests still fail. Run with <code>--bare</code> and pass the hook through <code>--settings</code> from the CI repository, so a pull request cannot edit the controls that police it: without <code>--bare</code>, a <code>-p</code> run executes whatever hooks the branch's <code>.claude/settings.json</code> contains.</p>
<p>Denials. Security's <code>dontAsk</code> plus an explicit tool list is the default: denials are deterministic and the run never waits. Pull requests that need the network go to a second job with <code>auto</code> and a narrower set of repositories, owned by the product team. In both, a watcher reads <code>--output-format stream-json</code> and sends SIGINT after the same tool is denied five times in a run, which ends the turn and records a result; SIGTERM would exit with 143 and record nothing.</p>
<p>The fleet. Per-run caps do not bound the fleet: 400 runs at $8 is $3,200 a day. The month's expected spend is 400 × 22 × $1.10 ≈ $9,680, leaving about $5,320 of headroom, which a fleet-wide loop would spend in under two days. So set the workspace spend limit at $15,000 as the hard stop, and alert before it.</p>
<p>The alert that fires first is per run, not per invoice: the watcher's denial count and the hook's block count fire within minutes of a loop starting. Next, the share of runs ending in <code>error_max_budget_usd</code> or <code>error_max_turns</code> per hour, paging when it passes 5 percent (two of the 40 runs an hour that 400 over ten hours gives, against an expected rate under 1 percent). Next, trailing-hour spend at three times the same hour last week. The workspace limit is last, and when it trips every agent stops at once.</p>
<p>What you give up. Runs that would have succeeded above $8 now fail and go to a person; pull requests that need the network are fixed by a smaller job with its own owner; and a hard workspace limit can stop all agent work late in a busy month. Failure mode of the recommendation: the budget is a client-side estimate that can differ from the bill, so caps tuned on the estimate can drift from what finance sees; reconcile the estimate against the Console's cost reporting weekly and move the caps if they diverge.</p>
</Fragment>

<ul>
<li><em>Finance asks for a guarantee that the month never exceeds $15,000. What can you guarantee, what is the cost of the guarantee, and who decides whether to raise the limit on day 25?</em></li>
<li><em>What would you need to see in a month of cap-ending runs to raise the per-run cap to $12?</em> A large share of capped runs that a person then finishes with a small change, meaning the agent was close; if capped runs mostly need a rewrite, the cap is doing its job.</li>
<li><em>The product team says the denial watcher kills runs that would have recovered after the fifth denial. How would you test that claim with data you already collect?</em></li>
</ul>

The written artefact is the decision note the two engineers file with finance and security:

```text
Decision: runaway controls for agent-fix (CI, headless)
Per run:   --max-turns 45; --max-budget-usd 7.50 (intended cap $8, headroom for overshoot)
Resume:    at most one, only after error_max_turns, budget = 7.50 minus spend so far
Stop hook: blocks at most 3 times per session (own counter); runs with --bare and CI-owned --settings
Denials:   dontAsk + explicit tools by default; auto only in the network job;
           SIGINT after 5 denials of one tool in a run
Alerts:    per run: denial and block counters; per hour: capped-run share above 5 percent;
           trailing-hour spend above 3x the same hour last week; workspace limit $15,000
Accepted:  up to about 1 percent of runs that would have succeeded are stopped and handed to a person
Rollback:  if the success rate drops more than 5 points against the previous four weeks, or capped
           runs exceed 3 percent for five working days, restore the previous turn cap and review
Owners:    platform team (caps, watcher), product team (network job), finance (workspace limit)
```

## Follow-ups

- *Your controls now cost more engineering time than the runaways did: two engineers spend a day a week on capped runs. Which control do you remove first, and what risk do you accept in writing?*
- *Security and product still disagree on `auto` for the main job. How do you decide without deciding by rank, and what experiment settles it in two weeks?*
- *A model upgrade raises median run cost by 40 percent overnight. Which of your alerts fires, which caps start killing good runs, and what do you change first?*

## Common mistakes

- Setting `--max-budget-usd` and keeping the resume loop, which hands every resume a fresh budget.
- Relying on the Stop hook's built-in cap. It counts consecutive continuations and resets on every tool call, which a test-fixing agent makes between every block.
- Assuming auto mode's three-in-a-row and twenty-total thresholds stop a headless run. They pause a terminal session; in `-p` the action is denied and the run continues.
- Setting per-run caps and calling the fleet bounded. The fleet's exposure is the cap times the run count, and the only fleet-wide stop is the workspace limit.
- Running `-p` without `--bare` on branches you do not control, so the pull request decides which hooks and MCP servers the agent runs.
