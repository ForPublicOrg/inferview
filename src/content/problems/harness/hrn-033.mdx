## Question

<Callout kind="interview" label="Interview question">
"An engineer wants bypass permissions within reach for later, so they start Claude Code in a terminal with <code>--allow-dangerously-skip-permissions</code>, then press Shift+Tab into plan mode and ask for a plan to split <code>billing/invoice.py</code>. While Claude is planning, what stands between it and an edit to that file?"
</Callout>

The project's settings, as of the session, checked against Claude Code's documentation on 2026-10-28:

```json
{
  "permissions": {
    "deny": ["Bash(git push --force *)"],
    "ask": ["Bash(npm publish *)"]
  }
}
```

The organisation's plan includes auto mode, and nobody has changed `useAutoModeDuringPlan`. The engineer has not pressed Shift+Tab a second time.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the launch flag changed about the session even though the mode in use is plan.</p></details>
<details class="hint"><summary>Hint 2</summary><p>When the documentation lists several cases for one situation, ask whether they combine or the first match wins.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether the answer would differ for the same flags in a <code>-p</code> run or an Agent SDK session.</p></details>

## Answer

The first option is right. Claude Code's documentation says that in interactive terminal sessions with bypass permissions available, it does not enforce plan mode's blocks. Claude is still instructed to plan without editing, but an edit or shell command it attempts runs without a prompt. What still holds: explicit ask rules prompt, recognised `rm` and `rmdir` removals of critical paths prompt, and deny rules block in every mode. None of the rules in this project names an edit to `billing/invoice.py`, so the instruction is all that remains. The launch flag never switched the session into `bypassPermissions`; making the mode available was enough.

The second option describes what the name leads people to expect. Claude Code's plan mode is a permission mode that gates calls, so the edit tool is offered and its calls are judged; in this session they are let through.

The third option is the most tempting. With auto mode available and `useAutoModeDuringPlan` on, the classifier does review shell commands during planning, in sessions where bypass is not available. The documentation lists the cases in order and the first match applies; the bypass-available case is first, and in it neither the classifier nor a prompt applies.

The fourth option is the documented behaviour almost everywhere else: without bypass available, and in `-p` runs, Agent SDK sessions and the VS Code extension's chat panel, plan mode keeps its blocks. It is wrong only for this session's combination of an interactive terminal and the flag.

The fifth option confuses two layers. The sandbox limits what any process may write, independent of mode; it does not switch to a read-only planning mount.

What this means for a team: a launch flag added for convenience changes the meaning of a mode people use for safety. If plan mode is part of a review process, disable bypass with `permissions.disableBypassPermissionsMode` in managed settings, or put the edits that must never happen in deny rules, which hold in every mode. Deny rules over paths are still rules over what Claude attempts; a Python script it runs can write the file, which is the sandbox's job.

## Follow-ups

- *Your team uses plan mode as the gate before an agent touches the payments service. Do you disable bypass across the organisation, or add deny rules for the payments paths, and what does each cost the engineers who use bypass in containers?*
- *Would the answer change for the same command line run with <code>-p</code> in CI?* Yes: plan mode keeps its blocks wherever Claude Code runs without an interactive terminal.
- *What would you need to see before relying on the model's instruction-following as the only thing between planning and editing?*

## Common mistakes

- Assuming the flag does nothing until bypass mode is selected.
- Treating plan mode as a reduced tool set rather than a permission mode.
- Reading the documented cases as layers that all apply, rather than an ordered list where the first match wins.
- Relying on plan mode, rather than deny rules or the sandbox, to keep a file untouched.
