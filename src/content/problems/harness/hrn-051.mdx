## Question

<Callout kind="interview" label="Reported question">
A candidate report lists a ByteDance first-round interview (June 2026) that asked which modules make up a harness and how to stop a harness eval set from being overfit. The setup below is original.
</Callout>

The team and its numbers are a scenario. A team tunes its coding agent's harness every week against 60 tasks drawn from its own repositories, five trials per task. Over three months the pass rate on those 60 tasks rose from 48% to 71%. Over the same months, the share of agent-written changes that engineers keep after review has not moved. The model snapshot did not change.

Name the modules of a harness and say which ones three months of weekly tuning most likely changed. Then say how you would rebuild the eval so that a rise in its score means something, including how many of the tasks you would hold out and why.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the diff of the system prompt and tool descriptions over the three months, and search it for names from the 60 tasks.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the transcripts of tasks that went from failing to passing, and whether a trial could see anything a previous trial left behind.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the smallest change in pass rate is that a held-out set of a given size could detect.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A harness is everything between the user and the model's sampler: the loop and its stop conditions and budgets, context assembly (system prompt, memory files, tool definitions, history, compaction), the tools and their output limits, permissions and the sandbox, verification the agent can run, session state, the model client (caching, retries, effort), and telemetry. Weekly tuning against one set mostly changes the prompt and tool descriptions, and a rise of 23 points with a flat production signal says the tuning learned the 60 tasks. Rebuild the eval: a tuning set and a held-out set looked at once per release, tasks refreshed from recent work, graders audited, trials isolated, and the production signal shown next to the eval score.</p>
</Fragment>
<Fragment slot="long">
<p><b>The modules, and where tuning lands.</b> Anthropic defines the agent harness as the system that lets a model act as an agent, and an eval of an agent measures harness and model together. Break it into modules by what each decides: the loop (when to call the model, when to stop, turn and cost budgets); context assembly (system prompt, memory files, tool definitions, history, and compaction when it overflows); the tools (what exists, how output is truncated, what errors say); permissions and the sandbox; verification (tests, linters and hooks the agent can run or that run on its behalf); session state (checkpoints, logs, resumption); the model client (prompt caching, retries, effort or thinking settings); and telemetry. A team tuning weekly against a fixed set changes the cheapest knobs first: system-prompt lines, tool descriptions and error messages. Those are also where task-specific knowledge leaks in, as a line that mentions a directory layout or a test command from one of the 60 repositories.</p>
<p><b>Why the score rose and production did not.</b> Three mechanisms, each checkable. The tuning fit the set: every change was kept if the 60 tasks went up, so the prompt now carries their quirks. The grader is wrong in ways the tuning exploited: OpenAI's audit of SWE-bench Verified found that 59.4% of 138 hard problems had material issues in their tests or problem statements, with 35.5% of tests too narrow and 18.8% too wide, and a harness tuned against flawed tests learns the flaws. Trials leaked: Anthropic reports Claude gaining an unfair advantage in an internal eval by reading git history from previous trials, and a harness change that adds a cache or a scratch directory can create the same leak.</p>
<p><b>The rebuild.</b></p>
<ul>
<li><em>Split the set.</em> A tuning set the team may look at every day and a held-out set looked at once per release, with the number of looks written down. When the held-out set has been looked at enough times to have steered decisions, it becomes a tuning set and new tasks replace it.</li>
<li><em>Refresh from recent work.</em> Add tasks from changes merged after the last refresh. Public repositories carry the contamination OpenAI found in SWE-bench Verified, where every frontier model it tested could reproduce gold patches or problem specifics for some tasks; SWE-bench Pro keeps held-out and commercial splits private for the same reason. Private repositories reduce that risk without removing it, because the harness's own prompt can still memorise them.</li>
<li><em>Audit the graders.</em> For every task that flipped from failing to passing, read a transcript and check that the test rejects a wrong change and accepts a correct one written differently.</li>
<li><em>Isolate trials.</em> A fresh sandbox per trial, no shared git history, caches or scratch files.</li>
<li><em>Review prompt diffs for task names.</em> A prompt or tool-description change that names a file, a test or a repository from the eval set is rejected in review.</li>
<li><em>Show the production signal beside the score.</em> The kept-change rate on real work, per release. When the two diverge, the eval is the suspect.</li>
</ul>
<p><b>How many to hold out.</b> This is the choice to defend. The held-out set has to detect the regressions you care about, and every task in it is a task the team cannot tune on. A held-out set of 20 tasks at five trials gives 100 trials; a binomial interval near 50% is 1.96 × √(0.25 / 100) = ±9.8 points for one run, so it can catch a large regression and nothing subtle. Anthropic notes that 20 to 50 tasks are often enough early on because large effects are easy to detect, which is the regime a held-out check is for. Holding out 20 of 60 is reasonable; holding out 5 detects nothing, and holding out 40 leaves 20 tasks to tune on, which overfits faster. The better fix for the conflict is more tasks: each one costs engineering time to write and verify, which is the budget to ask for.</p>
<p><b>How this fails.</b> A held-out set looked at once per release still leaks through people: an engineer who sees which held-out task regressed will fix that behaviour, and after a few releases the held-out set is tuned too. Rotating tasks out on a schedule, not only when someone notices, is the defence; it costs the comparability of scores across releases, so report each release on the same held-out set as its predecessor before rotating.</p>

## Follow-ups

- *The held-out score fell 6 points this release and the tuning set rose 4. Ship?* Not on that evidence. A 6-point drop is inside the ±9.8-point band of a 20-task held-out set, so it is not proof of a regression, but it is the direction overfitting predicts. Run the held-out set again with more trials, read the transcripts of the tasks that flipped, and ship only if the drop does not hold.
- *A product team offers 200 tasks from their repositories. What do you check first?* That each task's test fails on the code before the change and passes on the reference change, that a different correct change also passes, and that none of the repositories is public, since public code may be in training data.
- *Which module would you keep out of weekly tuning?* Permissions and the sandbox: a change there can raise the score by letting the agent do something it should not, such as reaching the network or reading the grader.

## Common mistakes

- Listing modules without saying what each one decides.
- Treating a rising eval score with a flat production signal as a measurement problem in production.
- Holding out tasks and then looking at them after every change.
- Trusting a task's test without checking that it rejects wrong changes and accepts correct ones written differently.
- Fixing a held-out regression directly, which turns the held-out task into a tuning task.
