## Question

<Callout kind="interview" label="Estimate, 25 minutes">
Anthropic published the totals for the C compiler its agent team wrote. From those totals, work out the tokens and cost of one session. Then estimate what the same build would have cost with an agent half as efficient, and say which assumption moves that number most.
</Callout>

Published inputs (Anthropic, 2026-02-05): 16 agents in parallel, nearly 2,000 Claude Code sessions across two weeks, 2 billion input tokens, 140 million output tokens, a total just under $20,000, all on Claude Opus 4.6.

Prices for Opus 4.6 per million tokens (Anthropic pricing docs, checked 2026-10-28): $5 base input, $6.25 for a 5-minute cache write, $10 for a 1-hour cache write, $0.50 for a cache read, $25 output.

"Half as efficient" is yours to define: it means the agent spends twice the effort for the same accepted work, and you choose where that effort shows up. Give the half-as-efficient total in thousands of dollars.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Price the output tokens first. What share of the total is left for everything on the input side?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Try pricing the 2 billion input tokens at each input rate on the list. Which reading of "input tokens" reproduces the published total?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether a less efficient agent runs more sessions or longer ones, and request requests per session and context length per request from the logs.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Per session: about 1 million input tokens, 70,000 output tokens and $10. Output costs $3,500, 17.5% of the total, so the input side is the dominant term at $16,500. An agent that needs twice as many sessions costs about $40,000. One that needs twice as many requests per session costs more, about $48,000 to $53,000, because the re-read part of the input grows with the square of the session length. Where the inefficiency shows up, more sessions or longer ones, is the assumption that moves the answer most.</p>
</Fragment>
<Fragment slot="long">
<p><b>Per session.</b> 2,000,000,000 / 2,000 = 1,000,000 input tokens; 140,000,000 / 2,000 = 70,000 output tokens; $20,000 / 2,000 = $10. Per agent, 2,000 / 16 = 125 sessions in 14 days, about 9 a day, so a session lasts at most 24 / 9 ≈ 2.7 hours if the agents ran around the clock.</p>
<p><b>Output, then the input side.</b> 140M × $25 = $3,500, which is 17.5% of $20,000. The input side is $16,500, or $8.25 per million of the 2 billion published input tokens, 1.65 times the base rate.</p>
<p><b>The assumption you choose: what the 2 billion counts.</b> Price all 2 billion at each rate: base $10,000 (total $13,500), 5-minute writes $12,500 ($16,000), 1-hour writes $20,000 ($23,500), cache reads $1,000 ($4,500). Cache reads cannot be most of the 2 billion, or the total would be far below $20,000. Yet a Claude Code session re-sends its whole conversation on every request, and 1 million tokens per session would allow only 100 requests averaging 10,000 tokens of context, which is small for hours of work in a 100,000-line codebase. The reading I take is that the 2 billion are uncached and cache-written tokens, and cache reads are on top. Then, with the 2 billion priced between $5 and $6.25, reads cost $16,500 − $10,000 = $6,500 down to $16,500 − $12,500 = $4,000, which is 8 to 13 billion read tokens, 4 to 6.5 million per session. The other reading, all 2 billion as cache writes with about 53% at the 1-hour rate (10 × 0.53 + 6.25 × 0.47 ≈ 8.25) and almost no reads, also reproduces $20,000; I reject it because a multi-hour agent session with almost no cache reads would be a broken cache, not a normal run. Both readings agree on the total and on the next step's first case.</p>
<p><b>Half as efficient, case A: twice the sessions.</b> Each session looks the same and half of them produce nothing that lands. Everything doubles: $40,000, 4,000 sessions, four weeks with 16 agents or two weeks with 32.</p>
<p><b>Case B: twice the requests in each session.</b> Output doubles. New context, the tokens written once, doubles. Re-reads quadruple: twice as many requests, each reading a context that is on average twice as long. With the new tokens costing X and reads R = $16,500 − X:</p>
<ul>
<li>new tokens at $5: X = $10,000, R = $6,500, total 2 × 3,500 + 2 × 10,000 + 4 × 6,500 = $53,000;</li>
<li>new tokens at $6.25: X = $12,500, R = $4,000, total 7,000 + 25,000 + 16,000 = $48,000.</li>
</ul>
<p>If sessions compact at a fixed size, the reads grow less than fourfold and case B falls toward $40,000. So the band is $40,000 to $53,000, and the dominant term in the growth is the re-read input, not the output the agent writes.</p>
<p><b>The decision this feeds.</b> Suppose a model at 40% of Opus 4.6's per-token price is measured as half as efficient on your tasks (a scenario, not a published result). In case A it costs 0.4 × $40,000 = $16,000, cheaper than $20,000, and takes four weeks instead of two unless you double the agents. In case B it costs 0.4 × $48,000 to $53,000 ≈ $19,000 to $21,000, the same money for twice the calendar time. Both answers are defensible: the cheaper model if the deadline can move and the inefficiency shows up as more sessions; the stronger model if the deadline is fixed, because doubling agents to hold two weeks is the move the C compiler run showed does not always help, when every agent hits the same blocking bug. The constraint conflict is cost against the deadline.</p>
<p><b>Failure mode of this estimate.</b> "Half as efficient" measured on a pilot of short tasks does not transfer to the phase that dominated this build's difficulty, one large integration target. An agent that is half as efficient on small tasks can be far worse on a task that does not split, and the estimate above assumes the ratio holds across the whole build.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Where would you look in the logs to tell case A from case B?</em> Requests per session and context length at each request, by session; case A shows more sessions of the same shape, case B longer ones.</li>
<li><em>What would the build cost on Claude Code's one-hour cache instead of five-minute?</em> Every write costs $10 instead of $6.25 per million; the reads are unchanged. Whether that pays depends on how often a session sits idle for more than five minutes, which the published totals do not say.</li>
</ul>

### Choices that are not reasonable

- Doubling only the output: $3,500 more, about $23,500. Every output token is read back as input on each later request, so output growth drags input growth with it.
- Treating all 2 billion as cache reads. Priced that way the build costs $4,500, which contradicts the published total.
- Quadrupling all the input in case B, about $73,000. Tokens written once grow with the number of requests; only re-reads grow with its square.
- Dividing instead of multiplying, $10,000, by reading "half as efficient" as "half the tokens".

## Follow-ups

- *Pushback: finance says your band of $40,000 to $53,000 is too wide to approve. Which assumption do you measure first, and what does that measurement cost?*
- *Reversal: what result from a one-day pilot would make you choose the cheaper model even with a fixed two-week deadline?*
- *Operating: halfway through, spend is on track for $35,000 against a $25,000 approval. Do you stop agents, switch models or narrow scope, and who signs off?*

## Common mistakes

- Dividing $20,000 by 2 billion tokens to get a per-token input price, which counts output dollars as input.
- Assuming cost scales linearly with inefficiency in every case. It does when sessions multiply, not when they lengthen.
- Pricing the build without the cache, which no harness running multi-hour sessions does.
- Holding the deadline by doubling agents without asking whether the work splits.
