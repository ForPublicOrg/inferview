## Question

<Callout kind="interview" label="Estimate, 20 minutes">
Your repository has a 600-line developer-written `AGENTS.md`. A colleague cites the ETH Zurich study and says context files raise inference cost by over 20% without improving success, so the file should go. Price what the file costs the team per month, then say what result from your own measurements would justify keeping it.
</Callout>

Published inputs (Gloaguen et al., arXiv 2602.11988, v3 dated 2026-09-29): with LLM-generated context files, average cost per task rose by about 20% on SWE-bench Lite and 23% on the paper's CTXbench; with developer-written files, cost rose by at most 19%. Claude Code with Sonnet-4.5 cost $1.30 per SWE-bench Lite task without a file and $1.51 with an LLM-generated one. Developer-written files changed success by +2.4 points on average across four agent and model pairs, with p = 0.21 against no file.

Scenario inputs, not measurements: 80 engineers, 21 working days a month, each starting about 6 agent tasks per working day. Last month's billing shows an average of $2.10 per agent task. A loaded engineer hour costs $120.

Give the extra spend per month in US dollars. Which cost increase applies to your file is yours to choose and defend.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask whether the file in the study that matches yours was written by a model or by developers, and which cost figure goes with it.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request what happens to an agent task that fails in your team: who notices, and how many minutes it takes them to redo or repair it.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how many paired tasks you would need to detect the success change your break-even implies.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The team runs 80 × 6 × 21 = 10,080 tasks a month at $2.10, about $21,170. At a 20% increase the file costs about $4,230 a month, or $0.42 a task. The token bill is not the dominant term: if a failed task costs an engineer 25 minutes ($50), the file pays for itself at a success gain of 0.84 percentage points, which no team can measure on aggregate success. Keep the lines whose effect you can measure on a specific failure class, and cut the rest.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The monthly bill.</strong> 10,080 tasks × $2.10 = $21,168 of agent spend. The paper's figure for developer-written files is "at most 19%"; the Sonnet-4.5 pair on SWE-bench Lite went from $1.30 to $1.51, which is 16%, but that was with a generated file; the averages for generated files are 20% and 23%. Choosing 16% gives $3,387, 19% gives $4,022, 23% gives $4,869. The accepted band, $2,000 to $5,000, also admits a 10% increase for a file you have already trimmed ($2,117).</p>
<p><strong>Where the extra cost comes from.</strong> Not mostly from the file's own tokens. The paper attributes it to behaviour: 2.45 to 3.92 more steps per task, more test runs and more exploration, because the agent follows what the file tells it to do. That matters for the fix: shortening the file reduces cost through the instructions you delete, not through the bytes.</p>
<p><strong>Break-even.</strong> Extra cost per task at 20% is $2.10 × 0.20 = $0.42. A task that succeeds instead of failing saves the engineer minutes spent noticing, diagnosing and redoing it. At 25 minutes and $120 an hour that is $50, so the break-even success gain is 0.42 / 50 = 0.84 points. At 10 minutes ($20) it is 2.1 points; at 60 minutes ($120) it is 0.35. Over a month, a one-point gain is about 101 tasks × $50 = $5,040, more than the file costs.</p>
<p><strong>Can you measure that?</strong> At a 70% success rate, an unpaired comparison needs about (1.96 + 0.84)² × (0.70 × 0.30 + 0.71 × 0.29) / 0.01² ≈ 32,600 tasks per arm to detect one point. Paired on the same tasks with 10% of pairs discordant, McNemar needs about 7,800 pairs. Neither is realistic for a team-specific file. The published evidence does not settle it either: +2.4 points on average with p = 0.21, and the Sonnet-4.5 pair went from 73.2 to 70.3 with the developer file on CTXbench.</p>
<p><strong>The result that would justify keeping it.</strong> Measure per instruction, not per file. The paper shows instructions are followed: a tool named in the file was used 1.6 times per task against under 0.01 when not named. So for each section, name the failure it prevents (CI runs with the wrong package manager, edits to generated code, migrations without review), count that failure in a month of traces, and run a small paired eval on tasks that exercise it, with and without the section. Keep the sections that remove a counted failure; delete overviews and anything the agent can read from the code.</p>
<p><strong>Failure mode of this approach.</strong> Per-section evals miss interactions: two sections that each look harmless can together send the agent into longer test loops. Recheck the whole file's cost per task after each trim, from billing, not from the eval.</p>
</Fragment>

<li><em>Your colleague says that 0.84 points is within noise and the file should go until it is proven.</em> The cost side is measured and the benefit side is not, so the burden argument is fair for the overview sections; it is weaker for a line that prevents a failure you can count in traces.</li>
<li><em>The model changes next quarter and per-task cost halves.</em> The token cost halves; the break-even halves with it, and the per-instruction evals have to be rerun because instruction-following changes with the model.</li>

### Choices that are not reasonable

- Pricing the file as its tokens times requests times the input price. With caching the file's own tokens are a small part of each request, and the paper measures the increase as extra steps and exploration; this method gives a much smaller number and the wrong fix.
- Using the paper's $1.30 per task when your own billing says $2.10. SWE-bench Lite tasks are not your tasks; at $1.30 and 10% the estimate falls to $1,310.
- Applying 23% without saying it is the generated-file average on a different benchmark. The developer-file figure is the closer match for a file your team wrote.
- Treating "no general success gain" as "no gain for any line". The study averages over files and repositories; it says nothing about the single instruction that stops your agent from editing generated code.

The dominant term is engineer time on failed tasks, not tokens. The assumption that flips the conclusion is the minutes a failed task costs: above about 50 minutes the break-even falls under half a point, and a file with a few high-value lines is easy to justify; below 10 minutes, cut hard.

## Follow-ups

- *Finance asks for the number with an error bar. Which of your inputs dominates the uncertainty, and how would you narrow it in a week?*
- *Half the file is a repository overview that new engineers also read. The staff engineer who wrote it objects to deleting it. How do you decide without deciding by rank?*
- *What would you need to see in a month of traces to delete the file entirely?*

## Common mistakes

- Stopping at the monthly bill. The question is whether the file pays for itself, which needs the value of a failure avoided.
- Proposing an aggregate A/B on success without computing the sample size it needs.
- Treating the paper's cost increase as a property of file length. It is a property of what the file makes the agent do.
