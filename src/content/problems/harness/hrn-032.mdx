## Question

<Callout kind="interview" label="Design round, 45 minutes">
Design the permission and security model for an internal coding agent, and decide when a long-running task should stop on its own. Say what you give up, and write the rollout plan you would send to security.
</Callout>

The operating constraints, which belong to this scenario:

- About 800 engineers. The agent runs interactively on laptops and as background tasks of up to six hours on CI runners, with nobody watching.
- One monorepo holds service code, infrastructure-as-code and the CI pipeline definitions.
- Security's condition for approval: no agent action reaches production without a human.
- The CI system and its deploy credentials cannot be changed this year. The runners that host background tasks hold those credentials today.
- The platform team is four engineers for one quarter.
- From a pilot of background tasks: among tasks that succeeded, the longest run of turns without a new passing test had a p95 of 30 turns.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask security which threat they are designing against first: the agent overreaching on a real request, an honest mistake, or text it read telling it what to do.</p></details>
<details class="hint"><summary>Hint 2</summary><p>List every file in the monorepo that changes what the agent, CI or an allowed command will execute next, and ask who can write each one.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the pilot's failed tasks too: how many turns did they spend after their last real progress, and what did those turns cost?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Containment first, then decisions. Every agent action runs in an OS sandbox or VM with workspace-only writes, network denied except through an allowlist proxy, and no long-lived credentials inside; the background runners get a separate pool without the deploy credentials. The agent cannot write the files that configure itself, CI, or the commands it is allowed to run. Deny rules cover the irreversible actions in every mode; actions that need to leave the sandbox prompt on laptops and pause the task on runners. A task stops early on any of four signals (budget, repeated denials, no progress, scope drift), and stopping means a checkpoint and a handoff, never a silent retry.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Containment.</strong> The sandbox is the layer that holds when every decision above it is wrong. On laptops, the harness's OS sandbox: writes limited to the workspace, network denied by default. Anthropic reports that sandboxing cut its permission prompts by 84%, which matters because the remaining prompts are the ones a person still reads. On runners, each task gets a VM with an egress proxy that allows the package registry and the internal Git host and nothing else. The deploy credentials stay on the existing runner pool, which cannot change this year; background agent tasks run on a new pool without them. That is the one piece of new infrastructure the quarter has to fund.</p>
<p><strong>The agent must not grant itself permissions.</strong> The files an agent can write are the files that configure the agent. Cursor's CVE-2025-54135 is the failure case: in versions below 1.3.9, creating a new dotfile needed no approval, so an injected agent could create <code>.cursor/mcp.json</code> and reach code execution. Anthropic describes the other half: project settings were read before the trust prompt, so a committed hook could run on clone. In this monorepo the protected set is wider than the harness's own list: the agent's config (<code>.claude</code>, <code>.codex</code>, <code>.mcp.json</code>), <code>.git</code> and its hooks, the CI pipeline definitions, and the files that decide what an allowed command runs, such as <code>package.json</code> scripts and the <code>Makefile</code>. Edits to those go through a human-reviewed pull request, not a prompt in the session. Managed settings disable <code>bypassPermissions</code>, and project settings cannot raise the mode.</p>
<p><strong>The decision layer: two defensible answers.</strong></p>
<ul>
<li><strong>Manual approval for anything that leaves the sandbox.</strong> Predictable and easy to explain to security. Cost: prompt fatigue; Anthropic reports that users approve about 93% of prompts.</li>
<li><strong>An independent approver for those actions</strong>, a classifier that sees the user's messages and the tool calls but not tool results. Fewer interruptions. Cost: Anthropic reports 17% of 52 real overeager actions approved and 0.4% of benign actions blocked, on its own traffic, plus a model call per reviewed action.</li>
</ul>
<p>On laptops I would start with the approver, inside the sandbox and the deny rules, because a miss there is bounded by what the sandbox lets out. On runners there is nobody to prompt, so the background agent runs in a deny-by-default mode (<code>dontAsk</code> in Claude Code's terms) with narrow allow rules; an action outside them fails, and the task pauses for a human instead of the agent searching for another route. Security's production condition is met by placement, not by the approver: nothing in either environment holds a credential that reaches production.</p>
<p><strong>When a long task stops.</strong> Four signals, each with a chosen threshold.</p>
<ul>
<li><strong>Budget.</strong> Six hours of wall clock and a token budget per task, set from the pilot's cost distribution.</li>
<li><strong>Repeated denials.</strong> Three consecutive denials stop the task; this is the default both Anthropic (3 consecutive or 20 total) and Codex's auto-review (3 consecutive or 10 in the last 50) publish. An agent that is denied three times in a row is trying to do something the policy forbids, and more attempts are the risk, not the cure.</li>
<li><strong>No progress.</strong> Stop after 45 turns without a new passing test, counted against the test list fixed when the task started. 45 is 1.5 times the pilot's p95 of 30 for successful tasks, so it cuts fewer than one successful task in twenty while ending a stuck task well before the six-hour budget. Anything from about 1.2 to 2 times the p95 is defensible; a threshold below the p95 kills more than one success in twenty, and no threshold at all lets a stuck task spend its whole budget.</li>
<li><strong>Scope drift.</strong> Edits outside the paths the task's plan named pause the task for approval rather than stopping it.</li>
</ul>
<p>Stopping writes a checkpoint: the work-in-progress branch, the test results, and a summary of what was tried and why it stopped, then hands the task to the person who filed it. It never restarts the task from scratch on its own.</p>
<p><strong>Where this design fails.</strong> The no-progress signal can be gamed and can misfire. An agent that deletes or skips a failing test makes the failing count drop, which is why progress is measured against the test list fixed at the start. A large migration whose tests only pass at the end shows no progress for a long time and gets stopped; those tasks need a per-task override that a person signs. On the containment side, the egress allowlist includes the package registry, and a typosquatted package passes every layer above.</p>
<p><strong>What you give up.</strong> Background tasks cannot deploy or touch production, so the agent stops at a pull request. Engineers lose bypass mode on their laptops. Some long tasks are stopped that would have finished. The quarter's budget goes to a runner pool and a proxy, not to features.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Security accepts the design but asks why the approver is trusted at all on laptops. What do you say it is for, and what is it not for?</em> It decides when to interrupt a person; the sandbox and the absence of production credentials decide what can happen.</li>
<li><em>Which file in your protected set will engineers complain about first?</em> <code>package.json</code>, because dependency bumps are routine agent work; split the scripts block from dependencies with a check in review rather than dropping the protection.</li>
</ul>

### The written artefact

A rollout plan, filed with the security review.

- **Phase 1 (weeks 1 to 4):** new runner pool without deploy credentials, egress proxy, managed settings that disable bypass and protect the agent, CI and script files. Background tasks run only on the new pool.
- **Phase 2 (weeks 5 to 8):** approver on laptops for out-of-sandbox actions, deny rules for force pushes, history rewrites and cloud CLI writes; the early-stop policy on runners with the thresholds above.
- **Phase 3 (weeks 9 to 13):** weekly sample of 200 approver decisions labelled by the platform team to measure the miss rate on our own traffic.
- **Rollback triggers:** any agent action observed reaching a production system (stop all background tasks, revert to the previous pool policy); the labelled miss rate above 30% for two consecutive weeks (move laptops to manual approval); more than 10% of successful tasks in a week stopped by the no-progress rule (raise the threshold to 2 times the p95 and review the override process).
- **Accepted risk:** a typosquatted package from the allowed registry runs inside the sandbox with the task's workspace and network allowlist.

## Follow-ups

- *Your containment work costs the whole quarter and the product team wanted the agent to open deploy pull requests by then. Which half do you cut, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants manual approval everywhere until the approver's miss rate is measured on your traffic, the other says prompts will be rubber-stamped and the approver should ship now. How do you decide without deciding by rank?*
- *What would you need to see in production to let background tasks keep going after three consecutive denials?*
- *A team's legitimate refactor is stopped at turn 45 four nights in a row. What do you change, and for whom?*

## Common mistakes

- Treating the permission rules or the approver as the security boundary, with the runner's production credentials still in reach.
- Protecting the harness's own config and forgetting the CI definitions and package scripts that an allowed command executes.
- Using a prompt as the control on a runner where nobody is there to answer it.
- Measuring progress by the number of failing tests, which the agent can lower by deleting tests.
- Restarting stopped tasks automatically, which turns an early stop into a slower loop.
