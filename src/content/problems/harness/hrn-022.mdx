## Question

<Callout kind="interview" label="Debug round">
Your team's coding agent is an in-house harness on the Claude API. On Tuesday the CI team upgraded its <code>ci-tools</code> MCP server from 2.3.2 to 2.4.0. Since then the daily prompt-cache hit rate for agent sessions has fallen from 0.93 to 0.04, and input spend per session has gone up about ninefold. Which defect explains why nearly every request now misses? Rank the others.
</Callout>

From the ci-tools 2.4.0 changelog:

```text
- run_pipeline's description now lists the pipelines running on the repository, so agents
  stop starting duplicate runs.
- The server sends notifications/tools/list_changed whenever that list changes.
```

The harness code that touches tools:

```python
# harness/mcp_hub.py
class McpHub:
    def __init__(self, servers):
        self.servers = servers
        self.tools = {}                                  # server name -> tool definitions

    async def start(self):
        for pending in asyncio.as_completed([s.connect() for s in self.servers]):
            srv = await pending
            self.tools[srv.name] = await srv.list_tools()
            srv.on("notifications/tools/list_changed", self._refresh(srv))

    def _refresh(self, srv):
        async def handler(_msg):
            self.tools[srv.name] = await srv.list_tools()
        return handler

    def tool_defs(self):
        return [to_api_tool(name, t) for name, ts in self.tools.items() for t in ts]
```

```python
# harness/loop.py
def build_request(session):

        "tools": BUILTIN_TOOLS + session.hub.tool_defs(),
        "system": session.system_prompt,
        "messages": with_cache_breakpoint(session.messages),   # cache_control on the last block

```

## Answer

The cache misses because the harness treats the tool list as live state and writes it into every request. Each `notifications/tools/list_changed` makes `_refresh` fetch the list again, `tool_defs()` returns the new list, and the next request's `tools` block differs from the last one. Tools are the first level of the cache hierarchy, so a change there invalidates the system prompt and the whole conversation behind it. Before 2.4.0 the server never announced a change, so the bug was latent; with a description that tracks running pipelines, a busy repository announces a change every minute or so, and every request after one is a full write. On Opus 5.5 a miss writes the reused tokens at $5 per million instead of reading them at $0.20, 25 times the price, and request 10 alone costs $0.35 of input instead of about $0.02. Averaged over a session, a 0.93 hit rate prices input at 0.93 × $0.20 + 0.07 × $5 = $0.54 per million tokens and a 0.04 hit rate at $4.81, which is the ninefold rise.

The ranking.

- **Second, a real defect on the server side: live state in a tool description.** It is the trigger, not the cause. Moving the running-pipeline list into a tool result (a `ci__list_running` tool, or a refusal from `run_pipeline` when the branch already has a run) fixes this server and leaves the harness waiting for the next server that changes a description.
- **Third, a real harness defect with a different symptom: connection order.** `asyncio.as_completed` fills the dict in whichever order the servers answer, so two sessions rarely send the same tool block and never share a cached prefix. Within a session the order is fixed, because reassigning an existing key keeps its position. Fix it by sorting servers and tools by name.
- **Ruled out: unstable order from the server.** It would produce this symptom, and it is the bug Codex hit in its first MCP support, but the diff shows the same 14 tools in the same order.
- **Ruled out: TTL expiry.** Requests are under a minute apart and each hit refreshes the entry.

The evidence is incomplete. The log hashes only the tools block, so a second change in the system prompt (a timestamp, a pipeline count) would look the same from here; log a hash per level for a day. Ask for the hit rate of sessions that never connect `ci-tools`: if it also fell on Tuesday, something else shipped that day. Without either, the timestamps are enough to act: every miss in the log follows a notification, and every hit precedes one.

The fix is a decision with more than one defensible answer.

- **Freeze the tool list for the conversation.** Keep the list from the first request; when a server announces a change, diff the new list against it. Append a short message to the conversation naming tools added or removed, the pattern Codex uses for mid-conversation configuration changes, and return an error that names the removal when the model calls a tool that is gone. Cost: new tools cannot be called until the next compaction or session, and descriptions go stale.
- **Apply a change only when names or schemas change, and only at a natural rebuild.** Description-only changes are dropped; real changes wait for the next compaction, or for the first request after the cache has expired anyway. Cost: one full write per real change, and a delay before the model can use a new tool.
- **Defer MCP tools behind a tool search tool.** The prefix holds only the search tool; definitions are appended inline when found, which is how Claude Code keeps its cache when a server connects mid-session. Cost: a tool search to build and own, and a new failure mode where the right tool is not found.

The constraint conflict is freshness against cost: the CI team added the live list for a real reason, duplicate pipeline runs, and the harness needs its prefix stable. My recommendation is the first fix with the second's rule for schemas, plus a request to the CI team to move the running-pipeline list into a tool result, which serves their goal better than a description the model may have read twenty minutes ago.

Failure mode of the recommendation. A server can change a tool's behaviour while keeping its name and schema, with the change stated only in the description ("now requires an approval token"). A frozen list leaves the model working from the old contract until the next rebuild, and the first sign is a run of tool errors. Count tool errors per tool per session after the change; a spike on one tool means its description carried meaning you dropped.

## Follow-ups

- *The CI team refuses to move the live list out of the description: duplicate runs cost them more than your cache misses cost you. What number would you put in front of both teams, and who decides?*
- *After freezing the list, a security reviewer points out that freezing also blocks a server from changing a tool's description mid-session to inject instructions. Do you now freeze even across compactions, and what do you give up?*
- *Your clients move to MCP 2026-07-28, where they opt in to tool-list notifications through `subscriptions/listen`. Do you subscribe at all during a conversation, and what would you need to see in production to start?*
- *Two senior engineers disagree: one wants tool search for every MCP server, the other wants a frozen list and nothing else. How do you decide without deciding by rank?*

## Common mistakes

- Sorting the tools and calling it fixed. The order was never the problem; the content changes with every notification.
- Moving the tools after the system prompt. The API orders the hierarchy as tools, system, messages regardless of where the fields appear in the request body.
- Ignoring `list_changed` entirely without handling removed tools, so the model keeps calling a tool that no longer exists and receives an unexplained protocol error.
- Blaming the CI team's upgrade and stopping there. The next server that updates a description will cause the same incident.
