## Question

<Callout kind="interview" label="Debug round">
Last week your team moved the coding agent's shell tool into a sandbox. Since then, about one run in eight on a repository without a lockfile ends with <code>error_max_budget_usd</code>. In those runs the agent runs the same install command over and over and tries nothing but waiting and rerunning it. Which defect explains why the agent keeps rerunning the install instead of changing its approach? Rank the others.

## Answer

The model behaved sensibly on the evidence it had. `EAI_AGAIN` is the resolver's code for a temporary failure, and "temporary" invites a retry. The sandbox knew better: it blocked the socket and recorded the block in `proc.denials`, but `run_shell` builds the result from the exit code and the output alone, so the one fact that would have changed the model's plan never reached it. Cursor reported the same pattern after shipping its sandbox: agents retried the same command without changing permissions until the Shell result named the sandbox constraint behind the failure.

The ranking. The loop guard is a real second defect: it compares the whole argument dict, the model rewrites `description` on every call, so three identical commands never count as repeats. Fixing it would have stopped the loop at turn 18, the first call with three plain `npm install` calls already in its window, instead of turn 37, which saves money and still fails the task, because the agent still does not know what is wrong. The resolver theory is ruled out by the setup script, which reached the same registry from the same image before the sandbox started. The budget overshoot is documented behaviour: the cap is checked when each response arrives, so a run can pass it by one response.

The evidence is incomplete. Without the denial records you are inferring the block from the setup script and the timing of the change. The first thing to collect is `proc.denials` for one failing call, or to rerun the same command in the same sandbox with `network="allow"` in a throwaway workspace. Without either, ship the result fix anyway: it is cheap and harmless when there are no denials to report.

The fix is a decision with more than one defensible answer.

- **Name the constraint in the result.** When `proc.denials` is not empty, append one line: what was blocked, by which rule, and how to proceed (request network access, or use the vendored packages). This keeps the sandbox strict and makes the error instruct. Cost: every network need becomes an approval request, and approval prompts pile up for the person watching.
- **Allow the registry through an egress proxy for install commands.** The install succeeds without a prompt. Cost: an open egress path that a prompt-injected agent can also use, plus a proxy and allowlist to run and audit; security has to sign off.
- **Install dependencies when the environment is built.** No network at run time at all. Cost: it fails exactly on the repositories in this incident, the ones without a lockfile, and goes stale when dependencies change mid-task.

The constraint conflict is autonomy against egress. My recommendation is the first fix everywhere, because a tool result that hides the reason for a failure is wrong whatever the policy, plus build-time installs for repositories with a lockfile; the proxy only with a written security review. Fix the loop guard as well, comparing `command` only, so the next uninformative result ends the loop within four calls instead of twenty-four.

Failure mode of the recommendation. Attaching denials to results depends on attributing each denial to the right command. With background processes or two commands in flight, a denial can land on the wrong result and send the model chasing a network problem in a command that failed for another reason. And once results suggest escalation, the model may request it for every network error, including a registry that is genuinely down. Only suggest escalation when a denial was recorded for that call, and track escalation requests per run after the change.

## Follow-ups

- *Security objects that naming the blocked operation in the result teaches the model how the sandbox works. Do you hide it, and which failure rate do you accept in writing in exchange?*
- *After the fix, approval requests per run triple and the people watching start approving without reading. What would you need to see in a week of traces to switch to the registry proxy instead?*
- *Two senior engineers disagree: one wants the loop guard to end the run, the other wants it to inject a warning and continue. How do you decide without deciding by rank?*
- *The tracing pipeline drops `proc.denials`. What else do you lose for incident review, and what is the smallest change that keeps it?*

## Common mistakes

- Blaming the model for retrying. The result told it the failure was temporary.
- Fixing the loop guard and calling it done. The run fails sooner and costs less; it still fails.
- Mapping every `EAI_AGAIN` or connection error to "sandbox" in the result text. A real outage then looks like a policy block, and the model asks for permissions it does not need.
- Granting the network to the whole shell tool to make the symptom go away, which removes the reason for the sandbox.
