## Question

<Callout kind="interview" label="Multiple choice">
A developer is 90 minutes into a Claude Code session on Opus 5.5 with an API key, with about 180K tokens of context and a request every minute or so. Tool search is on, the default on this model. Which one of these makes the next request reprocess the whole conversation instead of reading it from the cache?
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each action, ask whether it changes any byte of the request before the newest message, or changes what the cache is keyed on.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask when Claude Code reads each input in the list: once at session start, on demand, or on every request.</p></details>

## Answer

Switching models. The cache is keyed on the model as well as the prefix, so the first Sonnet 5.5 request reads nothing and writes all 180K tokens: 180K × $2.50 per million = $0.45, where a warm Opus request would have read them for 180K × $0.20 per million = $0.036. Switching back later is usually a second full write, on Opus at $5 per million: the Opus entry survives only if the detour was shorter than its lifetime and short enough to stay within the API's 20-position lookback. While the cache is warm, Claude Code asks you to confirm the switch.

Why each wrong option is tempting:

- **CLAUDE.md.** It is in the prefix, so editing it looks like editing the prefix. Claude Code holds the version it read at session start and keeps sending that, which is also why the new rule does nothing until `/clear`, `/compact` or a restart. The consequence that matters more in practice is the second half: the session keeps working without the new rule until one of those happens.
- **A new MCP server.** With tools loaded upfront, a new server's definitions do change the first level of the prefix and invalidate everything. Tool search changes that: the first request's list is kept, and late tools arrive as deferred definitions. The same action on a provider without tool search would be the right answer.
- **`/rewind`.** It rewrites history, which sounds like a new prefix. It truncates to content the cache was built from, and every turn since has kept that entry warm, so the next request is a hit.
- **Permission mode.** Codex inserts a new permissions message when the approval mode changes because the mode is described in its prompt, so engineers who know that harness expect a miss. In Claude Code the mode changes nothing in the request, except when plan mode under `opusplan` switches between Opus and Sonnet.

## Follow-ups

- *The developer wants Sonnet for a 15-request stretch of routine edits at 180K tokens of context. Choose the stretch length at which the switch pays for its two rewrites, and say what you assumed about context growth.*
- *Your team pins CLAUDE.md rules that must take effect immediately during incident response. Given that a mid-session edit does not apply, what do you do instead, and what does it cost the cache?*
- *On which providers or configurations would the MCP option become the right answer, and how would you detect that from usage logs?*

## Common mistakes

- Answering CLAUDE.md, and missing the more important fact that the edit does not apply.
- Assuming a switch and a switch back cost one miss. Each model keeps its own entry, and the old one rarely survives the detour.
- Generalising one harness's cache rules to another: Codex and Claude Code treat permission changes and late tools differently.
