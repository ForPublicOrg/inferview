## Question

<Callout kind="interview" label="Debug round">
Your long-running coding harness follows the design Anthropic published: an initializer writes a feature list with a <code>passes</code> field per feature, and each coding session takes one feature, sets <code>passes</code> to true when it is done, and commits. Agents were marking features done that failed end to end, so a month ago you added a Stop hook that runs the end-to-end tests of any feature the session flipped to passing. Last week the agent marked 41 features as passing and QA, clicking through each by hand, found 14 that do not work. Which defect explains most of them? Rank the others.
</Callout>

The hook, registered as the only Stop hook with no `timeout` set:

```python
#!/usr/bin/env python3
# .harness/stop_check.py
import json, subprocess, sys
from harness.features import newly_passing
from harness.hooklog import log

def main():
    event = json.load(sys.stdin)
    if event.get("stop_hook_active"):
        sys.exit(0)
    flipped = newly_passing("feature_list.json", base="HEAD~1")
    log(event["session_id"], flipped=flipped)
    if not flipped:
        sys.exit(0)
    ids = "|".join(f["id"] for f in flipped)
    r = subprocess.run(["npx", "playwright", "test", "--grep", ids],
                       capture_output=True, text=True,
                       timeout=900)                    # the full e2e suite can take 12 minutes
    if r.returncode != 0:
        print(r.stdout[-4000:], file=sys.stderr)
        sys.exit(2)
    sys.exit(0)

main()
```

The hook log for one session (a wrapper records each invocation's exit code and duration), constructed for this problem:

What else you know about last week:

- 15 sessions show two hook invocations, the second of them under a tenth of a second; QA failed 12 of those 15 features.
- 26 sessions show one invocation; QA failed 2 of those features. Four of the 26 logged `flipped=[]`, one of which QA failed.
- No invocation ran longer than 288 seconds.
- The agent tests features itself through Puppeteer MCP before setting `passes`.
- Transcripts are kept for 3 of the 41 sessions. In s-212, between the two stops, the agent edited the delete handler, ran the unit tests, clicked through the flow in Puppeteer and wrote "verified in the browser".

## Answer

The hook lets every second stop through. `stop_hook_active` is true whenever Claude Code is already continuing because a Stop hook blocked, so the stop that ends the continuation a block started always carries it. The early return was meant to prevent an endless loop, and it turned the check into a speed bump: the first stop is blocked with the failing output, the agent does something, and the next stop is released without a test. The 0.04-second second invocations are that early return. Twelve of the fourteen QA failures are in the fifteen sessions where this happened. In s-212 the agent's "something" was a browser check in a tool that cannot see the confirm dialog that broke the feature, so it believed its own fix.

The ranking. Comparing with `HEAD~1` is a real defect: when the agent commits its progress notes after the feature-list commit, the flip sits in the earlier commit and the hook tests nothing. It explains the four `flipped=[]` sessions and one failure. The Puppeteer limit on native dialogs is real and documented by Anthropic; it explains why the agent's own checks are optimistic, which is the reason the hook exists, but the hook's Playwright run caught the same dialog failure in s-212, so it lets features through only in combination with the released stop. The one failure among the 22 sessions where the suite ran and passed points at the tests, not the hook: a test that does not exercise the broken path. The timeout mismatch is real and latent: Claude Code cancels a command hook at 600 seconds by default and a cancelled Stop hook renders no decision, so once the full suite passes ten minutes the stop goes through untested. No run took longer than 288 seconds last week, so it is not this week's cause; set the hook's `timeout` above the suite's, or run only the flipped features' tests, before it becomes one.

The evidence is incomplete. Transcripts exist for 3 of 41 sessions, so for most of the 15 two-stop sessions you do not know whether the agent fixed anything between stops. What to collect: rerun the end-to-end tests for all 41 features at the current commit, which takes one suite run and separates fixed from not fixed; log `stop_hook_active` and the flipped list on every invocation; keep transcripts for every session for a month. Without them, act anyway: set `passes` back to false on every feature whose session had a released second stop, and let the next sessions redo them.

The fix is a decision with two defensible answers.

- **Keep the check in the session, and use the flag correctly.** Run the tests on every stop. When `stop_hook_active` is true and the tests still fail, do not release the claim: set `passes` back to false for the failing features, commit that, and then let the session end. The docs' advice to check the flag is about not blocking forever on a condition that will never resolve; it is not a licence to skip the check. Cost: sessions that loop on a hard feature spend turns until the eight-continuation cap or the budget, and the hook now writes to the agent's file, so it and the agent can race on the same commit.
- **Take `passes` away from the agent.** The coding agent may propose a feature as done; a separate evaluator step after the session runs the end-to-end tests, and only the harness writes `passes`. That is the generator and evaluator split from Anthropic's later harness post, where tuning a standalone evaluator to be sceptical proved far more tractable than making the generator critical of its own work. Cost: a session no longer knows within itself whether it succeeded, a failed evaluation needs a new session with the failure attached, and the evaluator step adds minutes per feature.

The conflict is feedback speed against who holds the pen. I would do both: the in-session hook as a fast first check that sends the agent back with the failure, and the harness as the only writer of `passes`, so no path through the session can mark a feature done. Add the ten-minute timeout fix and replace the `HEAD~1` comparison with a comparison against the commit the session started from, which the harness records.

Failure mode of the recommendation. The evaluator is only as strict as the tests it runs, and those tests were written by the initializer agent from each feature's steps; a feature whose test never exercises the confirm dialog passes the evaluator as it passed the hook. Anthropic's evaluator approved work after finding real issues until it was tuned against a person's judgement. Keep QA's weekly click-through on a sample and count the features the evaluator passed and QA failed; that number, not the hook's pass rate, is the harness's quality.

## Common mistakes

- Blaming the model for marking features done. It was sent back once, believed its fix, and the harness let it through.
- Deleting the `stop_hook_active` check without a way to end a session that cannot pass, so sessions spin until the eight-continuation cap or the budget ends them with the claim still in place.
- Treating "verified in the browser" in a transcript as evidence. The agent's browser tool and the failing flow are the documented blind spot.
- Fixing only the `HEAD~1` comparison because it is visible in the code, and leaving the release on the second stop that accounts for most of the failures.
