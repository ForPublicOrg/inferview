## Question

<Callout kind="interview" label="Critique, 30 minutes">
Your platform team enforces a layering rule with a custom lint, the way OpenAI's harness team describes doing. Coding agents keep merging changes that violate it. Below are the rule, the runner configuration and two agent runs. List every flaw you find, then rewrite the message so that an agent that reads only the message fixes the violation correctly.
</Callout>

The rule. Within each domain package, code may import only from its own layer or an earlier one, in the order types, config, repo, service, runtime, ui. Cross-cutting concerns (auth, telemetry, feature flags) come in through the domain's `providers` module.

```python
# tools/lint/layers.py
import ast

LAYERS = ["types", "config", "repo", "service", "runtime", "ui"]

def check(path, tree):
    src = layer_of_path(path)                 # "billing/repo/invoices.py" gives "repo"
    if src is None:
        return
    for node in tree.body:
        if isinstance(node, (ast.Import, ast.ImportFrom)):
            dst = layer_of_import(node)       # "billing.service.pricing" gives "service"
            if dst and LAYERS.index(dst) > LAYERS.index(src):
                yield Violation(path, node.lineno, "LAYER001",
                                "Layer violation. See https://wiki.internal/arch/layers")
```

```toml
# lint.toml
[rules.LAYER001]
mode = "warn"                 # rollout: report, do not fail, until the backlog is cleared
honour_noqa = true
```

CI runs `make ci`, which installs dependencies, runs the tests, then runs `make lint` with `--strict`, which fails on warnings. A failing CI log for this repository is about 14,000 lines.

Run A, abridged (constructed for this problem):

```text
Bash   make ci                        -> exit 2, head-and-tail excerpt: dependency install lines,
                                         "[... 612,407 of 622,118 characters omitted ...]",
                                         final test summary "1,204 passed", "make: *** [ci] Error 2"
agent  "Tests pass; CI failed after them. Running lint locally."
Bash   make lint                      -> exit 0
                                         billing/repo/invoices.py:12: LAYER001 Layer violation.
                                         See https://wiki.internal/arch/layers (warning)
WebFetch https://wiki.internal/arch/layers -> error: network access is blocked in this environment
agent  "The page is unavailable. Moving the import to where it is used."
Edit   billing/repo/invoices.py       (import of billing.service.pricing moved inside apply_discount)
Bash   make lint                      -> exit 0, no output
agent  "Lint is clean. Pushing."      -> CI green, merged
```

Run B, on another task, ends with this line added to `billing/runtime/jobs.py` and a green CI:

```python
from billing.ui.formatters import money  # noqa
```

## Answer

The flaws, in roughly the order a reviewer finds them.

**The message carries no remediation.** "Layer violation" names neither layer, the order, nor a fix. OpenAI's harness team makes the opposite choice on purpose: because their lints are custom, they write the messages to inject the remediation into the agent's context. An agent told only that something is wrong will make the smallest change that silences the check, which is what Run A did.

**The pointer is dead for the agent.** The link goes to an internal wiki, and the agent's sandbox has no network. The one place the remediation lives is the one place the agent cannot read.

**The rule has a hole the agent found.** `check` walks `tree.body`, the top-level statements only. Moving the import inside `apply_discount` keeps the dependency and passes the lint. This is the flaw a human reviewer misses because people rarely write function-local imports to dodge a linter; an agent searching for the smallest change that passes finds it in one step. Walk the whole tree with `ast.walk`, and add a structural test that imports each layer's modules in isolation.

**Suppression is free.** `honour_noqa = true` with a bare `# noqa` lets any rule be silenced with no rule ID and no reason. Run B is the result.

**Warn mode reports success.** Locally, `make lint` exits 0, so the harness treats the result as valid and the violation arrives as a line of text inside a success. CI runs `--strict` and fails. The agent sees two different answers to the same question.

**The CI failure never reached the agent.** The failing `make ci` output is far past the failure budget, so the agent received the head and the tail: install lines at the top, the test summary and the make error at the bottom. The lint lines sat in the omitted middle. The agent's inference that tests passed and something after them failed was correct, and it had to guess the rest.

The rewritten message, generated from `LAYERS` so it cannot drift from the rule:

```text
billing/repo/invoices.py:12 LAYER001 imports billing.service.pricing.
In billing, code may import only from its own layer or an earlier one: types, config, repo, service, runtime, ui.
This file is in repo, which comes before service, so the import goes the wrong way.
Fix: move the code that needs billing.service.pricing into billing/service/, or have the caller in service pass the value in.
For auth, telemetry or feature flags, import from billing.providers instead.
Imports inside functions are checked too. Suppressing LAYER001 requires "# noqa: LAYER001 reason=<why>" and is reviewed.
```

Where the rule runs is a decision with two defensible answers.

- **An edit-time guard**, as in SWE-agent: the edit that introduces the import is rejected with the message, and the agent fixes it while the context is fresh. SWE-agent's ablation reports 18.0% resolved with its lint guardrail against 15.0% without, on SWE-bench Lite with GPT-4 Turbo; that guardrail checks syntax, not architecture, so read it as evidence that rejecting at edit time helps, not as a number for this rule. Cost: a multi-step refactor that passes through a violating intermediate state gets blocked at every step, and every edit pays for a lint run.
- **A strict pre-push step in the agent's own loop, with CI as the backstop.** The agent sees the message once per push, in a short output it can read whole. Cost: a later fix, after the agent has built more code on the wrong dependency.

The conflict is feedback speed against freedom to pass through broken intermediate states. I would run the rule strict in the agent's pre-push step with the rewritten message, keep CI as the backstop, and print lint failures last in `make ci` so they land in the tail of any excerpt. The edit-time guard is the better choice if traces show agents building several files on top of a violation before the pre-push check catches it.

What you give up, and the failure mode. A message that prescribes a fix will be followed literally. "Move the code into service" is wrong when the right fix is to delete the dependency, and the agent will move it anyway. A message that names a fix also has to stay true when the rule changes, which is why it is generated from `LAYERS` and has a test of its own. And the longer message costs context: a refactor that trips the rule sixty times puts sixty copies into the next turn, so group violations by file and print the explanation once.

## Follow-ups

- *Your rewritten messages are six lines each and a migration PR trips the rule 200 times. Which part of the message do you keep for each violation, which part once, and what do you accept losing?*
- *Two senior engineers disagree: one wants a codemod that rewrites the import automatically, the other wants the agent to fix it from the message. How do you decide without deciding by rank?*
- *What would you need to see in traces to move the rule from the pre-push step to an edit-time guard?*
- *Security asks why the sandbox blocks the wiki at all. Do you allow it, mirror the page into the repository, or inline everything, and what does each cost when the page changes?*

## Common mistakes

- Rewriting only the message. The function-local import and the bare `noqa` still let a well-informed agent pass with the violation in place.
- Treating Run A as the model ignoring instructions. It never received them: the doc was unreachable, local lint reported success and the CI excerpt cut the lint lines.
- Writing a message that dumps the whole architecture document into every violation.
- Making warn mode fail locally but not in CI, or the reverse, so the two disagree again in another form.
