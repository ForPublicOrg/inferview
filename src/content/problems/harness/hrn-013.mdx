## Question

<Callout kind="interview" label="Concept">
When the model asks for several tool calls in one turn, the Claude Agent SDK runs the read-only ones concurrently and the ones that modify state one at a time, and a custom tool runs sequentially unless its author sets <code>readOnlyHint</code>. Why is that split the right default? A teammate marked two internal tools read-only to speed the agent up: <code>repo_sync</code>, which runs <code>git fetch</code> to make sure branches are current, and <code>run_tests</code>, which runs the suite and returns the summary. What breaks, and how would you have caught it?
</Callout>

Type your answer before opening the worked one: the reason for the split, the failures for each tool, and the concurrency limit you would set for read-only calls in one turn.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the tools' owner for every path, process and external system each tool touches during one call, from a trace rather than from its description.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how often the model issues the same call twice in one turn in your traces.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask who wrote each tool's annotations and what checks them.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Reads of a workspace commute, so running them together changes latency and nothing else; writes do not, because each one's precondition depends on the state the previous one left. A tool that writes while claiming to read gets run concurrently with itself and with real reads: two <code>git fetch</code> calls contend for the same repository locks and one fails, two test runs share caches, ports and output files, and a read issued alongside them sees the state before or after at random. The hint is a claim by the tool's author, so trust it only for tools you own and test, and default everything else to sequential.</p>
</Fragment>
<Fragment slot="long">
<p>Why the split. A turn with several tool calls is a batch the model wrote without seeing any of the results. If every call in the batch only reads, any interleaving gives the same results, and running them concurrently is free latency: Anthropic reports research time cut by up to 90% for complex queries with parallel subagents that each use three or more tools in parallel, and Cognition trains SWE-grep to issue eight parallel calls per turn. If a call writes, order matters. An Edit's string replacement is only valid against the file it was planned on; two writes to one file race; a command's effect depends on what ran before it. Sequential execution in the order the model emitted is the only interleaving the model could have reasoned about. Custom tools default to sequential because the SDK cannot know what an unknown tool touches, and a wrong "sequential" costs latency while a wrong "concurrent" costs correctness.</p>
<p><code>repo_sync</code> marked read-only. <code>git fetch</code> updates remote-tracking refs and takes locks inside <code>.git</code>. The model often calls it more than once in a turn, for example once per branch it wants to inspect. Run concurrently, one fetch fails on a lock held by the other, or both succeed and a concurrent <code>git log</code> sees refs from before or after the update depending on timing. The failure is intermittent, which makes it expensive: the trace shows a lock error the model then tries to fix.</p>
<p><code>run_tests</code> marked read-only. A test run writes caches, coverage data, build output and temporary databases, and may bind fixed ports. Two concurrent runs, or one run alongside a read of a generated file, give results that depend on scheduling: a test that passes alone fails when its port or fixture database is taken, and the agent goes after a bug that does not exist. It also slows itself down: two full suites on one machine compete for the same cores.</p>
<p>The trust question. The MCP specification says clients must treat annotations as untrusted unless they come from trusted servers. That covers third-party servers; the case above is worse because the tools were yours and the hint was set to win latency. A hint should be set by the tool's owner and checked by a contract test: run the tool in a sandbox that records file writes, lock files and outbound non-GET requests, and fail the build if a read-only tool produces any.</p>
<p>The concurrency limit is a choice. I would cap read-only calls at eight per turn, matching what SWE-grep was trained to issue, and lower it per tool where a backing API has a rate limit the fan-out would hit. Four is as defensible for an agent that mostly reads large files, where the bottleneck is context, not latency. Unlimited is not: a fan-out of thirty searches can trip rate limits and fill the next request with thirty results.</p>
<p>Failure mode of this answer. Defaulting unknown tools to sequential gives up real speed on third-party read APIs that are honest about their hints, and a contract test only catches the side effects you thought to record; a tool that writes to a remote system through a GET request passes it. The latency against correctness trade-off is real, and for a third-party tool the honest position is that the hint is that party's claim, so the decision to trust it is yours and should be written down.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The model emitted a read, a write and a read of the same file in one turn. What does each read see?</em> The SDK docs say read-only tools can run concurrently and state-changing tools run sequentially; they do not promise an order between a read and a write in one batch, so neither the model nor your tests should depend on one. A harness that wants the guarantee can split a batch at the first write.</li>
<li><em>Would you make <code>repo_sync</code> idempotent instead of sequential?</em> Idempotent does not mean safe to run concurrently; two fetches are idempotent in result and still contend for locks.</li>
<li><em>What would you log to find hint violations in production?</em> Per call: the hint, whether it ran concurrently, and the workspace diff around it; a read-only call with a non-empty diff is a violation.</li>
</ul>
</Fragment>

## Follow-ups

- *Your contract test sandbox doubles CI time for the tools repository. Which tools do you test on every change and which nightly, and what risk do you accept?*
- *A vendor MCP server marks every tool read-only, including one that deletes a deployment. What do you change in the client, and what do you tell the vendor?*
- *Parallel reads cut median task time but raise token use, because the model reads more files than it needs. How do you decide which to optimise for?*

## Common mistakes

- Equating "read-only" with "does not change what the user cares about". Locks, caches and lock files are writes for concurrency purposes.
- Treating the annotation as a permission. In the Agent SDK it changes scheduling; permission comes from allow and deny rules and the permission mode.
- Fixing the lock errors with retries in the tool, which hides the concurrency bug and keeps the doubled work.
