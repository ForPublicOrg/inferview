## Question

<Callout kind="interview" label="Debug, 15 minutes">
An engineer runs the same task in Codex and in Claude Code on the same repository. Both agents propose the same command. Codex runs it without asking; Claude Code stops and asks. The engineer expected the two configurations to be equivalent. Which explanation accounts for the difference?
</Callout>

The command both agents proposed:

```bash
npm test -- --runInBand && npm run lint
```

The repository's `.claude/settings.json`:

```json
{
  "permissions": {
    "allow": ["Bash(npm test)", "Bash(npm run lint)", "Bash(git status)", "Bash(git diff *)"],
    "ask": ["Bash(git:* push)"]
  }
}
```

The engineer's `~/.codex/rules/default.rules`:

```python
prefix_rule(pattern=["npm"], decision="allow")
prefix_rule(pattern=["git", ["status", "diff", "log"]], decision="allow")
prefix_rule(pattern=["git", "push"], decision="prompt", justification="pushes need a human")
```

What else the engineer reports: Claude Code was in Manual mode, the `default` setting. Earlier in the same Claude session, `npm run lint` on its own ran without a prompt. The engineer did not save the Codex session log and does not remember which approval mode it was in.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each harness, ask what one rule matches: the exact text, the text followed by anything, or a prefix of the argument list.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the earlier unprompted run in the Claude session tells you about which settings were loaded.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the output of Codex's own rule checker on this command, and the rule list Claude Code shows in <code>/permissions</code>.</p></details>

## Answer

The first explanation is right. In Claude Code, a Bash rule without a `*` matches only that exact text; its documentation's example is `Bash(npm run build)`, which does not match `npm run build --watch`. Claude splits the command into `npm test -- --runInBand` and `npm run lint`. The second part matches `Bash(npm run lint)`. The first matches nothing, and a compound command runs without a prompt only when every part is allowed, so Claude asks. Codex also splits the chain, because it is plain words joined by `&&`, and its pattern `["npm"]` is a prefix of both parts' argument lists, so both are allowed and the command runs outside the sandbox without a prompt.

The second option describes a harness that refuses all compound commands. Claude Code does the opposite: it documents `cd packages/api && ls` running without a prompt when each part qualifies.

The third option has Codex's behaviour backwards for this input. Codex evaluates a script as one unit only when it contains redirection, substitution, variables, wildcards or control flow; this one has none. And the lint part does match an exact Claude rule, which the earlier unprompted run confirms.

The fourth option names a real mechanism: project allow rules apply only after the trust dialog is accepted. The evidence rules it out, because the same session already ran `npm run lint` from a project allow rule.

**The evidence is incomplete.** Nobody ran either harness's own checker. Before telling the engineer anything, collect `codex execpolicy check --pretty --rules ~/.codex/rules/default.rules -- npm test -- --runInBand` and the same for `npm run lint`, which prints the strictest decision and the matching rules, and the rule list from Claude's `/permissions`. Without them, the explanation still stands on the two documented matching semantics, and the fix is testable in a minute: change the Claude rule to `Bash(npm test *)` and rerun.

**The defects worth more than the symptom, ranked.**

1. **`prefix_rule(pattern=["npm"], decision="allow")` is the serious one.** It runs every npm command outside the Codex sandbox without a prompt: `npm publish`, `npm exec`, and `npm install` with its install scripts. The symptom made Codex look like the better-configured harness; it is the less safe one. Narrow it to the scripts the team runs, such as `["npm", "test"]` and `["npm", "run", ["lint", "build"]]`.
2. **`Bash(git:* push)` never matches.** Claude Code recognises `:*` only at the end of a pattern; in the middle, the colon is a literal character. In Manual mode a push still prompts, because nothing allows it. In auto mode an explicit ask rule would force a prompt, and without one the push goes to the classifier instead. The intended rule is `Bash(git push *)`.
3. **The Claude fix has its own cost.** `Bash(npm test *)` allows whatever follows `npm test`, and the test script itself is whatever `package.json` says, which the agent can edit. That holds for the Codex rule too; neither rule is a boundary around what `npm test` runs.

## Follow-ups

- *The team wants one source of truth for both harnesses. Do you generate both rule files from one list, and what does each harness's matching semantics force you to give up?*
- *After the fix, a reviewer asks why `npm test *` is allowed when the agent can rewrite the test script. What do you answer, and what control actually covers it?*
- *A Codex allow decision runs the command outside the sandbox. What would you need to see in your traces before granting that to `npm test` at all?*

## Common mistakes

- Concluding that Codex is configured correctly because it did not prompt.
- Fixing only the Claude rule and leaving `["npm"]` as a blanket allow.
- Assuming `:*` and ` *` are interchangeable anywhere in a Claude pattern.
- Reasoning from memory of either harness without running its own rule checker.
