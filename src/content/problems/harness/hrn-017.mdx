## Question

<Callout kind="interview" label="Debug round">
Your team runs an unattended migration agent overnight on a harness you own. Last night's run spent its last three hours rewriting a package it was told not to touch, and its progress notes describe that work as the obvious next step. Using the evidence below, which defect explains why the agent turned to `shared/` after its fifth hour? Rank the others, and say what you would collect next.
</Callout>

The task message, as sent at 00:00:

```text
Migrate every service under services/ from clientlib v1 to v2. Do not modify anything
under shared/: the platform team owns it and is migrating it separately. Done means
checks 1 to 14 in tasks.json pass.
```

Last week's changes to the harness and the task template (three commits, combined):

```diff
 # harness/run.py
 def start_run(task):
     events = [
         system_event(SYSTEM_PROMPT),
+        env_event(repo_snapshot(max_tokens=6_000)),
         user_event(task.prompt),
     ]
     return Run(events=events, condenser=CONDENSER)

-CONDENSER = Condenser(max_events=120, keep_first=2, summarizer=LARGE_MODEL)
+CONDENSER = Condenser(max_events=120, keep_first=2, summarizer=SMALL_MODEL)
```

```diff
 # templates/migration/tasks.json
+  {"id": 15, "check": "rg -l 'clientlib\\.v1' --type py . | wc -l  ==  0", "passes": false},
```

The condenser is modelled on OpenHands' summarising condenser: the first `keep_first` events are kept verbatim, and past `max_events` the middle is replaced by one summary event. In this harness, the next condensation summarises that summary event together with everything after it.

The condensation log (summary excerpts as stored):

```text
01:48  condensation 1  forgotten 61 events  summary 1,900 tokens
       "Task: migrate services/* from clientlib v1 to v2. Constraint: shared/ is owned by
        the platform team; do not modify. Done = checks 1-14 pass. Completed: orders, billing..."
03:22  condensation 2  forgotten 60 events  summary 1,400 tokens
       "Migrating services to clientlib v2, keeping changes within services where possible.
        9 of 14 services done. Check 15 still failing."
05:06  condensation 3  forgotten 60 events  summary 1,100 tokens
       "Migration to clientlib v2 nearly complete (13 of 14 services). Remaining: check 15
        fails because v1 shims remain in shared/compat.py."
```

`PROGRESS.md`, written by the agent (excerpt):

```text
## Goal
Migrate services to clientlib v2 and get all checks passing.
## Log
02:05  check 15 fails only on shared/compat.py. Out of scope (platform team owns shared/). Leaving it.
04:40  services/search migrated; 13 of 14 services done.
05:08  read tasks.json and PROGRESS.md after context refresh.
05:31  Next: remove v1 shims from shared/compat.py so check 15 passes.
06:12  shared/compat.py rewritten for v2; updated 3 callers in services/.
```

What you do not have: the condensations' `forgotten_event_ids` (the log viewer shows counts only), the summariser prompt, and any run from before last week with more than one condensation.

## Answer

The scope rule stopped being part of the context and became part of a summary. Before last week the run started with two events, the system prompt and the task, and `keep_first=2` kept both verbatim for the whole run. The snapshot commit inserted a 6,000-token environment event in second place, nobody changed `keep_first`, and the task became event 3, inside the span the condenser summarises. From then on each condensation summarised the previous summary plus new work. The log shows the decay: condensation 1 carries the constraint verbatim, condensation 2 turns it into "where possible", condensation 3 drops it and names `shared/compat.py` as remaining work. Twenty-five minutes later the agent plans exactly that.

The ranking:

1. **The task is no longer pinned.** Explains the timing and the content of the change. The defect is not on any one line: the snapshot insertion and the unchanged `keep_first` are each harmless alone.
2. **Check 15 contradicts the task.** It scans the whole repository, so it fails on `shared/` by construction, and the feature list tells every later context that the job is unfinished. It is why the agent chose `shared/` once the scope was gone; it is not why the scope was gone, because at 02:05 the agent read the same failing check and correctly left it.
3. **The smaller summariser.** Plausibly makes each summary lossier and the decay faster, but the old model would also be summarising its own summaries. Ablate it rather than argue it.
4. **The agent-written progress file.** Its Goal line never had the scope rule and reads like an instruction to make all checks pass, so the 05:08 re-read reinforced the wrong goal. It was the same at 02:05.

What to collect. First, `forgotten_event_ids` for condensation 1 from the raw event store: if they start at event 2 (zero-based), the task was summarised away at 01:48 and the diagnosis is confirmed. Second, replay condensations 2 and 3 from the stored events with the old summariser, to size the third cause. Without either, the diagnosis rests on the arithmetic of `keep_first` and the timing of the commit, which is enough to act on, because pinning the task is cheap and harmless if it turns out not to be the cause.

### The fix, and the decision inside it

Fix check 15 to scan `services/` only, whatever else you choose. Then decide how the goal survives condensation. Three defensible answers:

- **Pin by role, not by position.** The condenser keeps every message from the task author verbatim, tagged at creation, instead of the first N events. Cost: those tokens are in every request for the whole run, and in a long run with many human messages the pinned set grows; you choose a budget (a few thousand tokens is reasonable here) and alert when it is exceeded.
- **Re-read a human-written goal file from disk after every condensation.** A `GOAL.md` with scope, non-goals and the definition of done, which the agent cannot write to, injected after each summary the way Claude Code re-injects the root `CLAUDE.md`. Cost: a second source of truth that a human must update if the scope changes mid-run.
- **Context reset with a structured handoff** instead of in-place summarisation. A fresh agent starts from the goal file, the progress file and the git log. Cost: orchestration, latency and the re-reading tokens at each reset, and it only moves the problem if the handoff omits the scope.

The constraint conflict is context budget against fidelity: the 6,000-token snapshot was added to help orientation, and pinning both it and the task costs every request. I would pin the task by role, add the read-only goal file, and enforce the scope as a deny rule on writes under `shared/` for this run, so the constraint stops depending on memory at all. Then add a goal-survival test: a recorded run replayed with condensation forced every 20 events, asserting after each one that the task text is in the view byte for byte and that the agent answers "what is out of scope?" correctly.

Failure mode of that recommendation. A pinned original task stays authoritative after a human changes the scope. If at hour three someone writes "platform agreed, migrate `shared/compat.py` too" and that message is summarised away, the pinned "do not modify `shared/`" and the deny rule both win, and the agent refuses work it was asked to do. Scope changes have to go through the goal file and the permission rules, not through a chat message.

## Follow-ups

- *Pinning both the task and the 6,000-token snapshot puts about 7,000 tokens into every request for the whole night. The platform lead wants the snapshot dropped instead. Which do you cut, and what do you accept in writing?*
- *What would you need to see in a month of overnight runs to drop the deny rule and rely on the pinned task alone?*
- *Two senior engineers disagree: one wants context resets for every run over four hours, the other wants compaction with pinning. How do you decide without deciding by rank?*
- *The model is replaced next month. Which parts of this fix do you re-test, and how?*

## Common mistakes

- Blaming the cheaper summariser because it is the change with "model" in it. The task should not have depended on any summary.
- Fixing check 15 and stopping. The next run loses its scope the same way and drifts somewhere else.
- Treating the agent's progress file as the record of the goal. It records what the agent believes, which is the thing that drifted.
- Raising `keep_first` to 3 and moving on. The next event someone inserts at the start breaks it again; pin by role.
