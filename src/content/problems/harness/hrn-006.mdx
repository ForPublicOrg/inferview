## Question

<Callout kind="interview" label="The prompt, as a candidate report describes it">
"Compare your agent with Claude Code and Codex. How does each one assemble context, load skills and checkpoint? What would you copy?" A candidate reported a ByteDance first round that put their own project side by side with Claude Code and Codex and then went deep on these three points.
</Callout>

If you have no agent of your own, defend this one, which a team built last year:

- **Context.** Each turn, the system prompt is rebuilt from a template that includes the full repository guidelines file, re-read from disk so edits apply at once.
- **Skills.** All 40 of the team's skills are inlined, bodies included, into the system prompt at session start, "so the model always knows how".
- **Checkpoints.** After every turn, the harness commits the working tree to a hidden branch, so any turn can be restored.

Compare it with Claude Code and Codex on each axis, say what you would copy and what you would keep, and choose a size budget for the skill list.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the cache read share per turn in a long session, and for how often the guidelines file changes during a session.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what share of the files the agent changes are changed by shell commands rather than by its edit tool.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how often, in recorded sessions, the agent used a skill whose body was in its context, and how often it used none.</p></details>

## Answer

<p>Copy the context discipline and the skill loading; keep the git checkpoints, but say what they cost. Both Claude Code and Codex build a stable prefix once and append changes, so re-reading the guidelines into the system prompt every turn turns each edit into a full cache miss; both load skills progressively, names and descriptions first and bodies on demand, where ours spends the window on forty bodies. On checkpoints ours is broader than Claude Code's, which snapshots only files its edit tools touch, but it pays a snapshot of the whole tree every turn and still cannot undo anything outside the repository. I would cap the skill list at about 2% of the window, as Codex does.</p>

<Fragment slot="long">
<p><strong>Context assembly.</strong> Codex sends instructions, tools and an input list: a developer message describing the sandbox, optional developer instructions, a user message with the `AGENTS.md` chain from the git root to the working directory (up to 32 KiB by default) and the skill metadata, an environment message with the working directory and shell, then the user's message. The chain is built once per run, and later changes to the sandbox, approval mode or directory are appended as new messages. Claude Code orders its request as system prompt and tools, then project context (`CLAUDE.md`, the first 200 lines or 25 KB of auto memory, unscoped rules), then the conversation; plan mode, skills and output-style changes are appended as messages, and `CLAUDE.md` is read at session start, so an edit made mid-session applies only after `/clear`, `/compact` or a restart. Ours rebuilds the system prompt each turn, so any edit to the guidelines invalidates every cached token behind it. The constraint conflict is instruction freshness against cache stability: both vendors chose stability and accept that a running session follows the old file until it compacts or restarts. I would copy that, and keep one escape hatch: an explicit "reload guidelines" action that appends the new text as a message.</p>
<p><strong>Skill loading.</strong> Both follow the Agent Skills pattern: name and description at start, the `SKILL.md` body when the skill is chosen, resources on demand. Codex caps the startup list at 2% of the context window (8,000 characters when the window is unknown), shortens descriptions first and drops skills with a warning when it overflows. Claude Code injects an invoked skill's instructions as a message at that point, so loading one never touches the cached prefix. Ours inlines forty bodies. With the spec's guidance, the arithmetic: metadata is about 100 tokens a skill, so 40 skills is about 4,000 tokens; a body under the recommended 5,000 tokens could cost up to 40 × 5,000 = 200,000 tokens if every body were near the limit. Even at a fraction of that, the bodies crowd out the task. Copy progressive loading.</p>
<p><strong>Checkpoints.</strong> Claude Code snapshots a file before its edit tools change it, makes a checkpoint per prompt, keeps snapshots for the 100 most recent checkpoints, and documents its limits: a file changed only by a shell command is not tracked, most subagent edits are not restored, and nothing remote can be undone. The sources used here do not document Codex's current undo behaviour, so I would not claim one in the room. Ours commits the whole tree each turn, which catches shell-made changes that Claude Code misses, at the price of a snapshot per turn on a large repository and the same blindness to databases, deployments and pushed branches.</p>

### The checkpoint decision

Two defensible designs, and the measurement that picks between them is Hint 2.

- **Snapshot the whole tree every turn (ours).** Restores shell-made changes and generated files. Costs a full-tree operation per turn, grows the repository's object store, and needs care with ignored and large files. Pick it when much of the agent's work runs through the shell: code generators, formatters, migrations.
- **Snapshot files before each edit-tool write (Claude Code's).** Cheap and exact for the agent's own edits; a file only a shell command changed stays as it is, which Claude Code's docs tell users to handle with git. Pick it when the edit tool does most of the writing and the shell mostly runs tests.

Neither undoes a migration run against a shared database or a pushed branch. That limit is the reason those actions sit behind permission rules rather than behind checkpoints.

### Choosing the skill-list budget

The budget is a share of the window for something present on every request. Codex's 2% is a reasonable default: on an assumed 200,000-token window that is 4,000 tokens, which fits 40 skills at the spec's 100 tokens of metadata each. Reasonable choices run from about 1% to a few percent; well above that, the list competes with the task, and an uncapped list grows with every skill a team adds. Whatever the cap, the overflow rule has to be stated: shorten descriptions first, and when a skill must be dropped, warn the user, as Codex does, instead of dropping it silently.

### The failure mode of copying progressive loading

Progressive loading moves the risk from the context window to the description. A skill whose description does not match how people phrase the task is never loaded, and nothing errors. Copying it means also measuring skill selection: replay recorded tasks and count how often the expected skill was loaded, and give critical skills explicit invocation.

## Follow-ups

- *An interviewer pushes back: "Inlining the bodies means the model never fails to find a skill. You traded a visible cost for an invisible failure." How do you answer, with which measurement?*
- *Codex avoids `previous_response_id` to stay stateless and support zero data retention. Would you copy that, given your agent has no retention requirement?*
- *Two engineers disagree on checkpoints: one wants git snapshots, the other edit snapshots. How do you decide without deciding by rank?* Measure the shell share of changed files on recorded sessions, and the snapshot time per turn on the largest repository.

## Common mistakes

- Saying Claude Code applies `CLAUDE.md` edits immediately, or that editing it mid-session breaks the cache; neither is true for the project-root file.
- Describing checkpoints as a full undo; Claude Code's do not cover shell-only changes, subagent edits or anything remote.
- Inventing a Codex checkpoint mechanism to complete the comparison instead of saying the sources do not cover it.
- Comparing on features without a cost for each: cache reads, tokens on every request, snapshot time.
