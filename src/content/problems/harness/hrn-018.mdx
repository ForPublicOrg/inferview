## Question

<Callout kind="interview" label="Concept round">
"Our coding agent finds code with grep and file reads. The platform team wants to add an embedding index of the monorepo. Should we? What would you measure on our own codebase to decide?"
</Callout>

The repository, as a scenario: about 40,000 files across four languages, roughly 300 merged pull requests a week, and a rule from security that source code and anything derived from it must not leave the company's network. Agents run in ephemeral sandboxes with a fresh checkout per task.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for a sample of the queries the agent actually runs in its first few turns, and how many of them contain an identifier that appears in the code.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how stale an index can be before it misleads the agent, given 300 merges a week and uncommitted edits during a task.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the ground truth you would score against: where would you get the files a task should have found?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>It is a choice between a lexer over the working tree and an index built ahead of time. Grep is exact, always current, transparent and costs no infrastructure, and it fails on vocabulary mismatch and on the turns it burns finding a starting point. An index answers paraphrased questions in one call and goes stale, needs a pipeline, and here would have to run inside the network. I would not add it on the strength of vendor numbers; I would build a retrieval eval from our merged pull requests, measure file recall, precision, turns and tokens to the first correct file for grep alone and grep plus index on the same queries, and add the index only if it wins on the queries where grep fails.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What each method is good at.</strong> Exact identifiers, error strings, paths and the state of the working tree, including the agent's own uncommitted edits, are grep's ground: a symbol either appears or it does not. A question in the user's words ("where do we decide a refund is partial?") when the code says <code>reverse_charge</code> is the index's ground. Anthropic's guidance (2025-09-29) is to start with agentic search and add semantic search only for speed or more variations, describing semantic search as less accurate, harder to maintain and less transparent. Cursor reported on 2025-11-06 that semantic search gave on average 12.5% higher accuracy on its own benchmark (6.5% to 23.5% by model) and a 2.6% retention gain on codebases with 1,000 or more files, best in combination with grep; those are the vendor's own numbers, and Cursor's current search docs (checked 2026-10-28) describe a local grep index and say no codebase embeddings are stored for search. A third option sits between the two: a structural map. Aider ranks tree-sitter definitions and references with PageRank personalised towards the files and identifiers in the chat, and fits the result into a 1,000-token budget by default.</p>
<p><strong>What grep costs.</strong> Turns and context. Cognition reported agents spending over 60% of the first turn retrieving context and agentic search taking 10 to 20 serial turns, which is why it trained a model that issues up to eight searches in parallel. Every irrelevant match read is context the agent carries afterwards.</p>
<p><strong>What the index costs here.</strong> The embedding model and vector store must run inside the network, so the hosted options are out. With 300 merges a week and a fresh checkout per task, the index is always behind the branch the agent is on and never contains its uncommitted edits, so results need a freshness check against the working tree before the agent trusts them. And it is another system with an owner, a rebuild schedule and failure modes.</p>
<p><strong>The measurement.</strong> Build the eval from history: for each merged pull request with a linked issue, the issue text is the query and the files the PR changed are the ground truth. Sample 200 of them across the four languages. Run grep alone and grep plus index on the same queries and record file recall at the point the agent starts editing, precision of what it read (Cognition weights precision over recall with F-beta at 0.5, on the argument that polluted context hurts more than a missed file the agent can still find), turns and tokens to the first correct file, and wall time. Two hundred is enough for a paired comparison: what matters is the discordant queries, and if the index finds 30 files that grep misses while grep finds 10 the index misses, McNemar's statistic is (30 − 10)² / 40 = 10, well past the 3.84 needed at 5%. Split results by whether the issue text contains an identifier from the diff; that split predicts the answer better than the repository size does.</p>
<p><strong>Recommendation.</strong> Ship a structural map and parallel grep first, because both work inside the sandbox with no new infrastructure, then run the eval. Add a local index only if it wins on the no-identifier queries by a margin that pays for its pipeline. The constraint conflict is recall on vague queries against freshness, privacy and operating cost.</p>
<p><strong>Where this goes wrong.</strong> The eval set is biased towards grep: issues that led to a merged PR are often written by engineers who name the function, while the vague questions an index helps with tend to come from people who never filed an issue. Add a slice of queries written from product language, or drawn from agent traces where the first five searches returned nothing.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Grep wins overall, but the index wins on the queries without identifiers. Which do you ship?</em> Grep by default, with the index behind a tool the agent calls when its searches come back empty, and log how often that happens.</li>
<li><em>What changes for a code-review agent that reads a diff instead of a task description?</em> The diff gives it identifiers, which favours grep and the structural map over embeddings.</li>
<li><em>How do you keep the index from returning code that was deleted on this branch?</em> Verify every hit against the working tree before showing it, and drop hits whose file or span no longer matches.</li>
</ul>

## Follow-ups

- *The platform team says the index is already built for the IDE, so it costs nothing to add. What does it cost the agent, and who pays when it is stale?*
- *Your eval shows a 3-point recall gain from the index and 40% more tokens per task. Do you ship it, and what number would change your mind?*
- *What would you need to see in a month of agent traces to remove the index after you add it?*

## Common mistakes

- Quoting the 12.5% figure as a property of embeddings. It is one vendor's result on its own benchmark and models, and that vendor's current docs describe a grep index.
- Measuring recall only. Precision is what keeps irrelevant code out of the context the agent reasons over.
- Scoring against a hand-written list of "relevant files" instead of the files a merged change actually touched.
- Forgetting that the agent's own edits exist only in the working tree.
