## Question

<Callout kind="interview" label="Debug round">
Your team's coding agent handles migrations under twenty minutes well. On longer runs, from about half an hour in, it starts migrating modules it has already finished and breaks some that were green. Which defect explains the rework? Rank the others, and say what you would collect next.
</Callout>

The harness, built on an agent SDK with automatic compaction. The model's window is 200,000 tokens (scenario configuration):

```python
agent = Agent(
    model=MODEL,
    system_prompt=open("prompts/system.md").read(),
    compaction=Compaction(trigger_tokens=190_000, keep_recent_files=5),
    tools=[read, edit, bash, grep],
)
task = (
    "Migrate these modules from httpx_v1 to client_v2, one commit per module, "
    "and tick each one off as you finish it:\n" + checklist(MODULES)
)
agent.run(task, max_turns=400)
```

One run, from the tracing store (constructed for this problem). `ctx` is the context size at that turn:


What you do not have: the text of the compaction summary. The tracing store keeps its token count and drops its content. The run's cache hit rate fell from 0.91 before minute 29 to 0.40 after it.

## Answer

The failures follow the compaction event, not the context size. The agent committed correct work at 163,300 tokens and went wrong at 41,800, three turns after the window was rebuilt from a 3,100-token summary. Before compaction, the record of what was finished was the agent's own "done [x]" lines in the conversation; the task asked it to tick modules off, and the only place a tick existed was the history that compaction replaced. Turn 89 shows what survived: billing "still had a failing test", which is the state at minute 4, not minute 12. The agent did not check `git log`, which would have shown the billing commit, because nothing told it the summary could be wrong. It re-migrated a migrated module, broke it at minute 36, found out at minute 41 and reverted at minute 52.

The ranking.

- **Test output size** is a real defect and the reason compaction came at minute 31 at all: two full runs are about 64,000 tokens of a 200,000-token window. Printing a summary line and writing the full log to a file, as the C compiler harness did, would push the first compaction later and make each one cheaper to summarize. It would not stop the first compaction from losing the ticks.
- **The payments rules** are a real defect with their own symptom. The rules entered the history when the agent read `AGENT_RULES.md` at turn 24, and compaction summarized them away; the edit at minute 58 bypasses `payments.retry.call`. Rules that must survive compaction belong in the always-loaded system prompt or a file re-injected after compaction, which is the distinction Claude Code's documentation draws between root and path-scoped instructions.
- **The cache** explains the bill, not the behaviour. The hit rate fell because compaction rewrote the prefix; the model sees the same tokens warm or cold.
- **"Context rot"**, the answer the source question bank gives, predicts gradual decline with size. This run declined in one step at the compaction event, at small context.

What the evidence does not settle. Without the summary text you are inferring that it dropped or garbled the ticks. Collect the summary for one failing run (turn on retention for compaction summaries, or rerun compaction on a stored transcript) and compare it with `git log`. Do not wait for it: the fix below is right whether the summary dropped the ticks or carried them wrongly.

**The fix is a decision with more than one defensible answer.**

- **An agent-written progress file** that the harness re-injects after every compaction. Cheap and general. Cost: the file says what the agent believes, which can be as wrong as a summary.
- **Harness-derived state.** After each compaction the harness computes the state itself, here a module is done when it has no `httpx_v1` import and its tests pass, and injects "done: billing, ledger, invoices; remaining: ...". Authoritative. Cost: a done-check per task type, which someone writes and maintains.
- **No compaction at all:** a fresh session per module that reads `git log` and the module list first, as Anthropic's long-running harness does. Cost: an orientation step per module, fourteen of them.

The constraint conflict is generality against correctness: the progress file works for any task and can be wrong; the derived state is right and works only where "done" can be computed. For migrations I take harness-derived state, because "done" is mechanical here, and keep the agent-written file for tasks where it is not. The quantity to choose is when to stop compacting and start fresh: I would compact at most once per module and start a fresh session if a module crosses the trigger twice, because a second compaction inside one module means the module's own work no longer fits.

Failure mode of the recommendation. The done-check is a proxy. A module with no `httpx_v1` import and green tests can still be half migrated (a call path the tests do not cover), and the harness will tell the agent, with authority, that it is finished. Add the check's blind spots to the module's review notes, and sample derived-done modules in review.

## Follow-ups

- *Pushback: the done-check for each task type costs a day of engineering, and you run thirty task types. Which ones get it, and what risk do you accept in writing for the rest?*
- *Reversal: what would you need to see in traces to drop compaction entirely and start a fresh session per unit of work?*
- *Two senior engineers disagree: one wants to raise the trigger to 400,000 tokens on a 1M-token model, the other wants smaller test output. How do you decide without deciding by rank?*
- *The compaction summary turns out to list billing as done. What does that change in your ranking?*

## Common mistakes

- Calling it context rot because the run is long, without lining the failures up against the compaction event.
- Fixing the test output and declaring the problem solved; the first compaction still loses the ticks.
- Asking the model to keep better notes in the conversation, which compaction summarizes like everything else.
- Treating the cache hit rate as a quality signal.
