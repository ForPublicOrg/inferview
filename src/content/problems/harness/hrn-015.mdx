## Question

<Callout kind="interview" label="Critique, 30 minutes">
Below is the `CLAUDE.md` at the root of a TypeScript monorepo. Two senior engineers approved it last quarter. Since then, agents have edited generated files, run a 25-minute test suite at the end of every small task, and committed float arithmetic in a currency helper. List every flaw you find, then rewrite the file.
</Callout>

The file, 310 lines; elided ranges are described in parentheses.

  1  # Ledgerline monorepo
  2
  3  IMPORTANT: READ THIS ENTIRE FILE BEFORE DOING ANYTHING. YOU MUST FOLLOW EVERY RULE.

## Answer

### The flaws, in the order they caused the incidents

**The generated-files rule never reaches the model.** Lines 246 to 249 are a block-level HTML comment, and Claude Code strips those before injecting the file. The author used the comment to signal "this is for agents" and achieved the opposite. It is the rule in the file that the agent can least infer, and it is the one incident in the brief with no other explanation. Both reviewers read it; neither knew the stripping rule.

**The test instructions are wrong as well as late.** Line 299 says `npm test` in a pnpm workspace, and line 301 asks for the root script, which runs every package's unit and integration tests, at the end of every task: that is the 25-minute suite. There is no command for one package or one file, which is what the agent needs while it works. Line 300 is the integration-test precondition, also at the bottom.

**The money rule competes with 300 lines and with the code.** It is in the file, plainly stated, and the agent still copied float arithmetic, because `packages/billing-v1/` is full of it and nothing says that package is legacy. The file spends 230 lines on what the agent can read and none on the misleading code it cannot judge.

**Lines 7 and 12 to 236 restate the repository.** The layout, the dependency list and the style rules duplicate the directory tree, the `package.json` files and the lint config. And line 7 is not a link: `@docs/architecture.md` outside backticks is an import, so 700 more lines load into every session. The ETH study found repository overviews did not help agents find files faster, while context files raised steps and cost.

**Capitals.** Lines 3, 145, 243 and the rest. Current models follow a plainly worded line, and piling on emphasis makes them over-apply the rule. Line 3 in particular tells the agent that everything is equally important.

**Zero-exception rules written as advice.** "Never commit to main" is branch protection plus a deny rule; "always lint before committing" is a hook or CI. CLAUDE.md is delivered as context with no guarantee of compliance.

**Personal content in a team file.** Line 291 points every engineer's agent at one person's staging database. That belongs in `CLAUDE.local.md`, which is gitignored, and the URL should not be in the repository at all.

**The length is not the mechanism people think.** A root CLAUDE.md is loaded whole up to 4 MiB, so line 300 is in context; the 200-line truncation applies to auto memory's `MEMORY.md`. The cost of 310 lines is tokens on every request and lower adherence, not invisibility.

### The rewrite

```markdown
# Commands
- Install: pnpm install
- Test one package: pnpm --filter <package> test
- Test one file: pnpm --filter <package> vitest run <path>
- Integration tests: docker compose up -d, then pnpm --filter <package> test:int
- Lint and typecheck: pnpm lint && pnpm typecheck

# Code you must not copy
- packages/billing-v1/ is still deployed and uses floats for money. Do not copy it:
  new code keeps amounts in integer minor units.
- packages/sdk/src/generated/ is produced by pnpm codegen from openapi/ledgerline.yaml.
  Change the spec and regenerate; never edit the generated files.

# Decisions not visible in the code
- Currency conversion goes through packages/fx; do not call the rates API directly.
- Release history and incidents: docs/incidents.md (read it when touching billing runs).

# Compact instructions
- Keep the package being changed, the failing test names and any decision about money handling.
```

Under 25 lines. The architecture document stays in `docs/`, referenced in backticks if at all. Style rules stay in ESLint and Prettier, which already enforce them.

### Two decisions with more than one defensible answer

**Tests before finishing.** A `Stop` hook that runs the tests for the packages the session changed, exiting 2 on failure, enforces the check every time. Cost: a hook to maintain, a mapping from changed files to packages, and a run that cannot end while an unrelated flaky test fails; the docs cap consecutive blocks, after which the turn ends anyway. A CLAUDE.md line costs nothing to maintain and works most of the time, not every time. I would take the hook for package tests and leave the full suite to CI, because the 25-minute run is the incident.

**The generated-files rule.** In text, it reaches the model and explains how to make the change correctly. As a `PreToolUse` hook that blocks edits under `generated/`, it is enforced, and the block message can say to edit the spec and run codegen. Cost of the hook: the codegen command itself writes those files, so the hook must match edit tools, not the shell, or it blocks the fix. I would do both: the line explains, the hook enforces.

The constraint conflict throughout is persistence against context cost. Every line kept is paid on every request; every line moved to a hook, a lint or a path-scoped rule is cheaper but either rigid or, for path-scoped rules, summarised away at compaction until a matching file is touched again.

### Failure mode of the rewrite

Cutting 290 lines removes some that were the only written record of a decision, such as an incident note explaining why a retry was disabled. Before deleting, move anything that is a decision rather than a description into `docs/` and check it against the code; after the rewrite, watch a week of sessions for the same correction made twice, which is the signal that a line was load-bearing.

## Follow-ups

- *The engineers who approved the file say the overview is how new hires learn the codebase. Do you keep it in CLAUDE.md, and what do you accept in writing if you do?*
- *After the rewrite, agents start running `pnpm codegen` for every API change, including ones that should not touch the spec. What do you change, and where?*
- *What would you need to see in session logs to move the money rule out of the root file and into a lint?*

## Common mistakes

- Reading the HTML comment as a rule because a human reads it as one.
- Treating `@path` as a hyperlink.
- Fixing the capitals and the length and leaving the wrong test command in place.
- Moving every rule into hooks. Each hook fires sometimes when it should not, and someone maintains it; the docs' own guidance is to keep the enforced set small.
