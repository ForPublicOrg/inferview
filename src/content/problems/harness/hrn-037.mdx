## Question

<Callout kind="interview" label="Concept">
You are building an agent that fixes bugs filed against your services. One design gives it a static specification: the bug report, the API contract and the design doc, and it returns a patch with an argument that the patch meets them. The other gives it dynamic feedback: an environment where it can reproduce the bug, run tests and observe the result. Which do you build first, and why? One bug in the backlog is intermittent; it failed in 3 of 10 runs when the reporter tried it. How many clean runs would you require before the agent may call that bug fixed?
</Callout>

Type your answer before opening the worked one: the choice, what each design gets wrong, and the number of runs with how you got it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the agent can run today in each service's repository, and how long it takes to bring one service up from a clean checkout.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how sure you need to be that a fixed intermittent bug is not just a lucky streak, and how sure you are of the 3-in-10 rate.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask who can change the tests and the reproduction once the agent has them.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Build the environment first, but use the specification to write its first check. A specification says what correct means; it cannot tell the agent whether its patch achieves it, and an agent with nothing to run stops when the work looks done. The useful order is: turn the bug report into a reproduction that fails on the current code, fix until it passes, then run the existing tests. The specification decides which reproduction is right and which tests are wrong. Static review alone is the fallback for bugs you cannot reproduce. For the intermittent bug, nine clean runs give about 95% confidence at a 30% failure rate, but 3 failures in 10 is a weak estimate of that rate, so I would require about 30.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why feedback beats a static argument.</strong> The agent loop is gather context, act, verify, repeat, and the verify step needs something that comes back pass or fail. Anthropic's Agent SDK post ranks rules-based feedback first and calls a model judging its own output generally not very robust. A patch plus an argument that it meets the contract is a model judging its own output. Claude Code's guidance says the same from the other side: without a check to run, "looks done" is all the agent has, and the reviewer becomes the test suite.</p>
<p><strong>Why the specification still matters.</strong> Feedback is only as good as the check. OpenAI's audit of 138 SWE-bench Verified problems found 35.5% had narrow tests that reject correct fixes and 18.8% had wide tests that check behaviour the description never asked for. A pure feedback design optimises for whatever the tests happen to check. And an agent that can edit its checks will: Anthropic's take-home received sub-1300-cycle submissions in which a model had modified the tests. The specification is what lets a person or a second agent say that a test is wrong, or that a reproduction tests the wrong thing.</p>
<p><strong>The decision with two defensible answers.</strong> Environment first costs real engineering: a reproducible build per service, seeded data, fakes for external systems, and a sandbox with no production credentials. On a fleet of services that is weeks before the agent fixes anything, and some bugs (production-only data, hardware, third-party behaviour) never reproduce. Specification first ships in days and covers every bug, at the cost of having no closed loop: every patch needs a careful human review, which is the bottleneck you were trying to remove. My choice is environment first for the services with the most bug reports, specification-first with mandatory review for the rest, and a rule that a bug the agent cannot reproduce in a fixed budget goes back to a person with its attempt attached.</p>
<p><strong>The number of runs, computed.</strong> If the bug fails on a run with probability <em>p</em> and the fix did nothing, the chance of <em>n</em> clean runs in a row is (1 − <em>p</em>)<sup><em>n</em></sup>. For 95% confidence that a lucky streak is not what you are seeing, (1 − <em>p</em>)<sup><em>n</em></sup> ≤ 0.05. At <em>p</em> = 0.3: <em>n</em> ≥ ln 0.05 / ln 0.7 ≈ 2.996 / 0.357 ≈ 8.4, so 9 runs. But 3 failures in 10 runs is consistent with a true rate well below 0.3; at <em>p</em> = 0.1, <em>n</em> ≥ 2.996 / 0.105 ≈ 28.4, so 29 runs. I would require 30, or first rerun the reproduction 30 times on the unfixed code to measure the rate, which costs the same and tells you more. Anywhere from 9 (if you trust the rate) to about 30 is defensible; one or two clean runs are not, since a 30% bug passes two runs about half the time (0.7 × 0.7 = 0.49).</p>
<p><strong>Failure modes of the recommendation.</strong> The reproduction can be wrong in the same way as the patch: an agent that writes both can write a test that fails for an unrelated reason and a patch that makes that reason go away. So the reproduction is committed and shown failing before the fix starts, and a reviewer reads it against the bug report. Flaky suites give false signals in both directions; the Large Language Monkeys authors found 34 of 300 SWE-bench Lite problems had flaky tests that sometimes fail even the correct fix, and ran each suite 11 times with a majority vote. And the environment narrows what the agent sees: Anthropic's long-running harness found its agent marking features done after unit tests or <code>curl</code> checks that did not exercise the feature end to end, and its browser tool could not see native alert dialogs at all.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The environment takes 25 minutes to build per service. Does that change the answer?</em> It changes the unit: build once per service and snapshot, so each bug pays seconds; if snapshots are not possible, the budget per bug decides which services get an environment.</li>
<li><em>The agent writes the reproduction and the fix. Who checks the reproduction?</em> It is committed first and run on the unfixed code; a reviewer, or a separate agent with only the bug report, judges whether it captures the report.</li>
<li><em>What would make you go specification-first everywhere?</em> Measured data showing review time per agent patch is no higher without an environment, which would mean the environment is not catching anything reviewers would have missed.</li>
</ul>
</Fragment>

## Follow-ups

- *Your 30-run rule costs an hour of runner time per intermittent bug and the backlog has two hundred of them. Which do you verify fully, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants the agent to rewrite tests it judges wrong against the spec, the other wants it to stop and ask. How do you decide without deciding by rank?*
- *What would you need to see in a month of results to stop requiring a committed failing reproduction before a fix?*

## Common mistakes

- Choosing one design outright. The specification decides what correct means and the environment tells the agent whether it got there; a bug-fix agent needs both, in that order of authority.
- Accepting one clean run of an intermittent bug as proof of a fix.
- Letting the agent write the reproduction after the fix, so the reproduction is shaped by the patch.
- Treating a green suite as meeting the specification when the audit numbers show how often tests and descriptions disagree.
