## Question

Replay the seven weeks behind Anthropic's 23 April 2026 postmortem on Claude Code quality. At each checkpoint, commit to a call before the next event appears. Then answer the staff question: you run the harness team for a coding agent, and you can add one release gate this quarter. Which one would have caught the costliest of these changes first, and what does it miss?
</Callout>

## Answer

What the postmortem says. Three changes overlapped. The effort default moved from high to medium on 4 March and was reverted on 7 April. A change meant to clear old reasoning once, from sessions idle for over an hour, cleared it on every later turn instead; it shipped on 26 March and was fixed on 10 April in v2.1.101. A system prompt limit on verbosity shipped on 16 April and was reverted on 20 April after a broader ablation found a 3 percent drop on two models. Each hit different traffic on a different schedule, so together they looked like broad, inconsistent degradation, and internal usage did not reproduce them. Anthropic's commitments: more staff on the exact public build, its improved Code Review tool for customers, a broad per-model eval suite and line-by-line ablations for every system prompt change, tooling to review and audit prompt changes, model-specific changes gated to the model they target, and soak periods, broader evals and gradual rollouts for anything that could trade against intelligence.

Why the clearing bug was the costliest. Thinking blocks from earlier turns are part of the cached prefix, and the API's caching docs list dropped thinking blocks among the changes that invalidate the messages level of the cache; only the tools and system prompt still match. A change that drops a different block on each request does that every turn, which is what the postmortem means by repeated cache misses. That is a cost bug and a quality bug from one behaviour, and the cost half left a trace in data the harness already had: cache reads and writes per request.

<Fragment slot="short">
<p>A cache-health gate on the release cohort, split by session state: the share of input read from the cache on requests after a session resumes from idle, compared with the previous release. The clearing bug would have dropped that share, for every affected session from the first day, to roughly the share of the system prompt and tools in the input, while every other metric looked normal. It misses the other two changes: lower effort reduces tokens, and the verbosity limit changes output, not the prefix.</p>
</Fragment>
<Fragment slot="long">
<p>The options, each with what it costs. A per-model broad eval with prompt ablations catches the verbosity limit (that is how it was found) and probably the effort change, but costs eval compute and days on every prompt change, and it misses the clearing bug unless the eval includes sessions resumed after an hour of idle time, which almost no suite does. Putting staff on the exact public build removes the masking, at the cost of staff no longer testing internal experiments early. Full-repository code review by a stronger model found the clearing bug in the back-test, but it is one more reviewer with false positives, and nothing guarantees it finds the next one. A cache-health gate reads data that every response already returns.</p>
<p>The threshold is yours to choose. On a warm request in a long session, only the new turn is written, a few percent of the input. In the hrn-021 session, for example, a request at 100K of context writes 2K, so it reads 98 percent. Flag a resumed session when its second and later requests read less than 80 percent of their input; alert when the flagged share of resumed sessions in the new release's cohort is more than twice the previous release's. The 80 percent leaves room for large tool results; the cohort comparison absorbs the full rewrite that every upgrade causes on the first request.</p>
<p>The constraint conflict is release cadence against coverage: each gate here adds hours or days to a change, and the team can afford one this quarter. The cache gate is cheapest and catches the only change with a cost signature. What you give up: the two changes that cost quality without changing the prefix go through, so the next prompt change still needs the eval gate, and the plan has to say so.</p>
<p>Failure mode of the recommendation. The gate needs sessions to resume from idle on the new build before it can fire, which in a staged rollout can take a day of real usage, and a release that changes the system prompt on purpose will trip it for one request per session. Write the rollback trigger next to the alert: a flagged share above twice the baseline for six hours rolls the release back without a meeting.</p>

## Follow-ups

- *Leadership asks why it took more than a week to find a bug that broke the cache on every turn. What would your dashboards have needed in March for it to take a day?*
- *Your verification costs three times the change it guards: ablating every system prompt line on every model blocks the team's weekly release. Which half do you cut, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants staff forced onto the public build, the other wants internal experiments to stay ahead of it. How do you decide without deciding by rank?*

## Common mistakes

- Treating the three changes as one regression and looking for a single cause. Each had its own dates, models and traffic.
- Reading faster usage drain as evidence of heavier thinking. Lower effort cuts tokens; it was the cache that drove the bill up.
- Choosing a gate that runs on fresh sessions only. The costliest bug needed an hour of idle time to start.
- Picking a gate without saying which of the three changes it would have missed.
