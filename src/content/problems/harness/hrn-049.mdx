    import math
    from collections import defaultdict

    # Policy: an infra-error trial is dropped from the pass counts, because it measured the cluster and not the agent.
    # Its cost and turns stay in the totals, and the infra-error rate is reported next to the score so a reader can see
    # when the drop is hiding something. A task with no usable trials left is left out of the score.
    Z = 1.96


    def _all_pass(n, c, k):
        # C(c, k) / C(n, k) as a running product: no big integers, no overflow at large n.
        if c < k:
            return 0.0
        r = 1.0
        for i in range(k):
            r *= (c - i) / (n - i)
        return r


    def _check(counts, k):
        if k < 1 or not counts:
            raise ValueError("need k >= 1 and at least one task")
        for task, (n, c) in counts.items():
            if n < k:
                raise ValueError(f"task {task!r} has {n} trials, fewer than k={k}")


    def pass_hat_k(counts, k):
        _check(counts, k)
        return sum(_all_pass(n, c, k) for n, c in counts.values()) / len(counts)


    def pass_at_k(counts, k):
        _check(counts, k)
        return sum(1.0 - _all_pass(n, n - c, k) for n, c in counts.values()) / len(counts)


    def _counts(records):
        counts = defaultdict(lambda: [0, 0])
        for r in records:
            if r.get("infra_error"):
                continue
            cell = counts[r["task"]]
            cell[0] += 1
            cell[1] += 1 if r["ok"] else 0
        return {t: (n, c) for t, (n, c) in counts.items() if n}


    def summarize(records, k):
        counts = _counts(records)
        trials = len(records)
        infra = sum(1 for r in records if r.get("infra_error"))
        successes = sum(c for _, c in counts.values())
        total_cost = sum(r["cost"] for r in records)
        return {
            "tasks": len(counts),
            "trials": trials,
            "infra_error_rate": infra / trials if trials else 0.0,
            "pass_hat_k": pass_hat_k(counts, k),
            "pass_at_k": pass_at_k(counts, k),
            "mean_cost": total_cost / trials if trials else 0.0,
            "mean_turns": sum(r["turns"] for r in records) / trials if trials else 0.0,
            "cost_per_success": total_cost / successes if successes else None,
        }


    def compare(a_records, b_records, k=1):
        a, b = _counts(a_records), _counts(b_records)
        common = sorted(set(a) & set(b))
        if len(common) < 2:
            raise ValueError("need at least two tasks run under both variants")
        _check({t: a[t] for t in common}, k)
        _check({t: b[t] for t in common}, k)
        d = [_all_pass(*b[t], k) - _all_pass(*a[t], k) for t in common]
        mean = sum(d) / len(d)
        var = sum((x - mean) ** 2 for x in d) / (len(d) - 1)
        half = Z * math.sqrt(var / len(d))
        if abs(mean) <= half:
            verdict = "inside_noise"
        else:
            verdict = "b_better" if mean > 0 else "a_better"
        return {"diff": mean, "half_width": half, "verdict": verdict}

## Question

<Callout kind="interview" label="Coding round">
"Our harness team reruns the benchmark after every change and posts the score. Write the code that turns raw trials into the numbers they post, and make it refuse to announce a win that is noise."
</Callout>

Each trial is a record: `task`, `ok`, `cost` in dollars, `turns`, and `infra_error: True` when the sandbox or the cluster failed rather than the agent (those trials also have `ok` False). Tasks can have different numbers of trials, because reruns and crashed trials are uneven.

Implement four functions:

- `pass_hat_k(counts, k)` and `pass_at_k(counts, k)` over a map of task to `(n, c)`: estimated per task from its n trials, then averaged over tasks. Raise `ValueError` for `k` below 1, an empty map, or any task with fewer than `k` trials.
- `summarize(records, k)`: tasks, trials, infra-error rate, pass^k, pass@k, mean cost and mean turns over every trial, and cost per success (`None` when nothing succeeded).
- `compare(a_records, b_records, k=1)`: the difference in pass^k (B minus A) over the tasks both variants ran, a `half_width` for the noise band, and a verdict: `"b_better"`, `"a_better"`, or `"inside_noise"` when the gap is not wider than the band. Raise `ValueError` with fewer than two shared tasks.

Two decisions are yours. First, whether an infra-error trial is dropped from the pass counts or counted as a failure; the hidden tests accept either, and the comment at the top of your file says which and why. Second, how to compute the noise band. The hidden tests run many seeded comparisons of two identical variants and of two variants with a real gain of about eleven points, with three to ten trials per task: a band that calls more than about one identical pair in eight a win, or misses more than one real gain in five, fails.

The visible tests end with 100,000 trials over 5,000 tasks, summarised and compared in under 2 seconds. `compare` must give the same answer every time it is called on the same input.

## Answer

**The estimators.** tau-bench defines pass^k as the chance that k independent trials of a task all succeed, averaged over tasks, and estimates it per task as C(c, k) / C(n, k): the share of k-subsets of the recorded trials that are all successes. pass@k is one minus the share of k-subsets with no success, C(n − c, k) / C(n, k). Both are computed per task and then averaged, never from a pooled success rate, because a pooled rate pretends every task is equally flaky. The reference writes the ratio as a running product, (c / n) × ((c − 1) / (n − 1)) and so on over k factors, which needs no big integers. `math.comb` divided by `math.comb` is also correct in Python, since integer true division rounds correctly; the hidden tests include n = 3,000 and k = 1,500 to catch a version that computes factorials in floating point and overflows.

**One pass over the records.** The reference groups records into a dict of task to `[n, c]` in a single loop, so summarising and comparing are linear in the number of trials. Building the task list first and then filtering all records once per task is 5,000 × 100,000 = 500 million comparisons for the visible test; that version took 49 seconds in CPython 3.12.6 when this problem was checked, against 0.09 seconds for the reference.

**Infra errors are a real decision.** Dropping an infra-error trial measures the agent: the cluster failed, so the trial says nothing about the harness. Counting it as a failure measures what a reader of the benchmark number gets. The two differ by more than the gaps people argue about. Anthropic measured infra-error rates of 5.8% at strict per-task resource limits on Terminal-Bench 2.0; counting those as failures turns a task the agent passes half the time into 0.5 × (1 − 0.058) = 0.471, 2.9 points lower, which is the size of gap Anthropic says deserves scepticism. The reference drops them and reports the rate beside the score. Its cost: when a harness causes its own infra errors (a variant that runs builds in parallel and runs the sandbox out of memory), dropping them flatters exactly the variant that broke things. Counting them as failures is the better choice when infra-error rates differ between variants on the same cluster, since the difference is then the harness's doing.

**The noise band.** Both variants ran the same tasks, so the comparison is paired by task: the reference takes the per-task difference in pass^k estimates, and the half-width is 1.96 times the sample standard deviation of those differences over the square root of the number of shared tasks. Pairing removes task difficulty from the noise: a variant that gains 20 points on every task has a half-width of zero, while an unpaired comparison charges it the full spread between easy and hard tasks. An unpaired binomial band on pooled trials also passes the hidden tests: it is conservative, so it finds fewer real gains, but with 34 flaky tasks out of 89 it still finds the eleven-point gain. A bootstrap over tasks passes if its seed is fixed; one with an unseeded generator fails the determinism test.

**How the reference fails.** The band covers trial noise on this task set and nothing else. If the two variants ran on different days or on different clusters, the time-of-day and resource effects Anthropic describes move one arm and not the other, and no statistic on the records can see it; the runner has to interleave the arms and record the configuration, which the lab for this module builds. With a dozen tasks, 1.96 understates the interval: the t quantile for 11 degrees of freedom is 2.20. And a gap outside the band is real on these tasks, not on the tasks your users bring.

## Follow-ups

- *What changes to run this against a real harness instead of a list of records?* Trials run in containers, concurrently, and each record gains the model snapshot, the harness commit, the resource guarantee and limit, the timeout and the wall-clock start, so two runs can be checked for comparability before their scores are. Infra errors need a classifier with its own tests, because an out-of-memory kill, a pod eviction and an agent that killed its own process can share an exit code. Transcripts are stored, because a score that moved is read trial by trial.
- *Pushback: the band says a 4-point gain is inside noise, the release is on Friday, and doubling trials doubles the eval bill. Which do you cut, and what do you put in writing?* Spend the extra trials only on the tasks whose outcomes varied in the first run, since tasks that always pass or always fail add nothing to the band; write down that a regression on a task that looked stable could be missed, and recheck those tasks after release.
- *Reversal: what would you need to see to switch from dropping infra errors to counting them as failures?* An infra-error rate that differs between the variants on the same cluster and configuration, or infra errors concentrated on the tasks where the new variant does more work at once. Either says the errors belong to the harness.
- *A product manager wants pass@k on the dashboard because it is higher. What do you say?* pass@k answers whether an agent can solve a task given k tries and a way to pick the good one; pass^k answers whether a user gets a good result every time. Show the one that matches how the product is used, and label k.

## Common mistakes

- Computing pass^k as a pooled success rate raised to the power k.
- Filtering every record once per task, which is quadratic in practice.
- Comparing two variants with separate intervals and reading overlap as a tie.
- Neither reporting the infra-error rate nor saying whether infra errors were dropped.
- Seeding a bootstrap from the clock, so the same runs give a different verdict on each call.
