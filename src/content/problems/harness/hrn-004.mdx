## Question

<Callout kind="interview" label="The prompt">
"Nothing under `infra/prod/` may be edited by the agent, in any session, on any laptop. The team runs Claude Code in auto mode. Which of these still holds on a turn where the model has decided the edit is justified?"
</Callout>

Pick one.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each option, ask whether a transcript could exist in which that control was configured correctly and the edit still happened.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what happens to each control if the organisation changes auto mode's settings or turns it off.</p></details>

## Answer

The command hook. Claude Code's best-practices page splits every control into two kinds: instructions the model reads and decides about, and configuration the harness executes every time. Hooks, deny rules, the sandbox in strict mode and managed settings are the second kind. A `PreToolUse` hook that exits 2 blocks the tool call, its stderr goes back to Claude as the reason, and the hooks reference says even a `permissionDecision` of `allow` printed alongside cannot override the block.

Why the others are tempting:

- **`CLAUDE.md`** is loaded into every request, which feels like a system-level rule. It is still text the model weighs against the code in front of it. And if the line was added mid-session, it is not loaded at all until `/clear`, `/compact` or a restart.
- **Auto mode's classifier** is a separate model that sits outside the main model's reasoning, so it feels like enforcement. It is a judgement, tunable and switchable; the docs say deny rules and `PreToolUse` hooks apply before the classifier sees anything, and that never-rules belong there.
- **A skill** is the most structured of the advisory options, which makes it look like policy. Whether it loads and whether it is followed are both the model's call.
- **The prompt hook** fires at exactly the right point in the loop, which is why it fools people. The decision inside it is another model's, so it is not deterministic; for enforcement the docs point to `command` or `http` hooks.

The correct answer has holes. A hook on `Edit|Write` does not see `sed -i` in a Bash call or a Python script that writes the file; to hold against those, add the shell to the matcher with a path check, or use the sandbox's filesystem rules, which apply at the OS level. A hook that crashes or times out is a non-blocking error by default, so a policy hook needs its failure set to block. And a hook in the repository's `.claude/settings.json` only starts running on a laptop once that person accepts the workspace trust prompt; a rule the security team owns belongs in managed settings, which no personal settings file can override. A deny rule such as `Edit(./infra/prod/**)` is enforced in the same way and is simpler to maintain than a hook for a pure path rule.

## Follow-ups

- *The hook blocks a legitimate emergency fix at 2 a.m. Who can bypass it, and how is the bypass recorded?*
- *Which of the five would you use for "prefer named exports", and why not a hook?* The best-practices page keeps rules with exceptions in `CLAUDE.md` and warns that every hook will sometimes fire when it should not.
- *How do you test that the hook still blocks after someone edits the settings file?* Run a headless session that attempts the edit and assert the tool call was refused.

## Common mistakes

- Treating anything outside the main model, such as the classifier, as deterministic.
- Treating any hook as enforcement without checking whether it is a command hook or a prompt hook.
- Matching only `Edit` and `Write`, then finding the file changed by a shell command.
- Writing the rule in `CLAUDE.md` with more emphasis after it is ignored.
