## Question

<Callout kind="interview" label="The prompt">
"What matters more in a coding agent, the model or the harness? Don't argue it in general. Here are five failures from one week of our runs. Tell me who fixes each one."
</Callout>

The traces are constructed for this problem. The agent is Claude Code on a TypeScript monorepo, with default settings.

- **A.** `npm run build` printed 41,000 lines of bundler output. Over the next three turns the agent re-ran the build with different flags, then asked the user to restate the task.
- **B.** The agent's last message was "All tests pass." CI failed on the same commit. The transcript shows no test command after the agent's final edit.
- **C.** Asked why the session cache serves stale entries under load, the agent read the eviction code, the failing test, and test output showing two writers racing. It then changed the log line next to the race and declared the bug fixed.
- **D.** After the agent edited `src/gen/client.ts`, an engineer added "Never edit anything under src/gen/" to the project `CLAUDE.md`, mid-session. Forty minutes later the agent edited `src/gen/types.ts`.
- **E.** The agent ran `pytest tests/test_sync.py -x` six times in a row with identical arguments and an identical failure, then hit the turn limit.

For each failure: name the layer that fixes it (model, harness or both), the specific control, and whether that control is enforced or advisory. Exactly one failure needs both layers; say which and why. For A, choose the character budget you would give a single tool result and defend it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For A, ask where in the 41,000 lines the build's actual error was printed.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For C, ask what happens when the same transcript, cut just before the bad edit, is replayed five times against a stronger model or a higher effort level.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For D, ask when Claude Code read that `CLAUDE.md`, and what the agent's own run log says it had loaded.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A, B and D are harness failures: an unbounded tool result, a completion nobody checked, and a rule written as advice and loaded too late. C is the model: the evidence was in context and the reasoning failed, so the levers are which model and how much effort. E needs both. The harness can see the repeat and stop paying for it, but only the model can pick a different action, so a harness-only fix turns a loop into an earlier stop, not into progress. For A, I would budget about 30,000 characters per result, keep the full output in a file the agent can search, and show the head and the tail, because builds print their error last.</p>
</Fragment>
<Fragment slot="long">
<p><strong>A, harness, enforced.</strong> The tool returned more than the model could use and pushed the task out of view. The control is a per-result budget with a file fallback: inline up to the budget, save the rest, return a preview and the path. Claude Code does exactly this for Bash, inlining up to roughly 30,000 characters by default and otherwise returning the saved file's path with a preview of up to 2,000 characters. The trap in copying it is the preview. A build log's error is usually at the end, so a head-only preview hides the one line that matters. Show head and tail, or say in the truncation note that the model should search the saved file for "error".</p>
<p><strong>B, harness, enforced.</strong> "All tests pass" is the model's summary, which Claude Code's own best-practices table files under what Claude decides. The control is a Stop check: a `Stop` hook that runs the tests and exits 2 with the failures on stderr, which sends the agent back to work instead of ending the turn. A `CLAUDE.md` line saying "run the tests before finishing" is advisory and works most of the time, not every time.</p>
<p><strong>C, model.</strong> Nothing was missing from the context: the code, the test and the race were all read. That is a reasoning failure, and the harness's levers are configuration rather than mechanism: a stronger model, a higher effort level, or a review step by a second model. Settle it with the measurement in Hint 2. If the stronger configuration fixes the right function in most replays, it was the model; if it fails the same way, look again for a harness cause, such as a truncated test output that dropped the second writer's stack.</p>
<p><strong>D, harness, enforced, and the edit was never loaded.</strong> Claude Code reads the project-root `CLAUDE.md` once at session start; an edit mid-session does not apply until `/clear`, `/compact` or a restart. Even loaded, a `CLAUDE.md` line is a guideline the model may decide does not apply. A rule with no exceptions belongs in a deny rule such as `Edit(./src/gen/**)` or a `PreToolUse` hook that exits 2. The recommended fix has its own hole: Edit deny rules cover the file tools and the file commands Claude Code recognises, not `node scripts/patch-client.js` writing the same files. If the rule must hold against scripts too, it needs the sandbox's filesystem rules, and then the legitimate `npm run codegen` that regenerates `src/gen/` must run somewhere else, such as CI. That conflict between the rule and the generator is the decision to raise with the team.</p>
<p><strong>E, both.</strong> The harness half: key each call on its tool and canonical arguments, notice that nothing changed between identical runs, and on the second identical failure answer with "this is a repeat; the output is unchanged" instead of running it again, then stop after a small number. That saves the turns and the spend. The model half: after the repeat notice, a capable model reads the failure, opens `test_sync.py`, and changes something. If the model cannot, the harness can only end the run sooner. Treating E as harness-only produces a run that stops cleanly and still fails.</p>
<p>In Böckeler's terms, A, B and D are fixed by computational controls (a truncation rule, a test run, a deny rule), and C is the case no computational control reaches.</p>
</Fragment>

### Choosing the budget for A

The budget is a share of the context window you are willing to spend on one observation, plus the cost of getting it wrong in each direction.

| Choice | When it is reasonable | What it costs |
|---|---|---|
| A few thousand characters, with a saved file | Search and listing tools, where the model narrows the query anyway | Logs get cut before the error; the agent spends turns paging |
| About 30,000 characters, with a saved file (Claude Code's default for Bash) | General shell output in a long-context model | One noisy build can still use a large slice of the window |
| No cap | Never in an unattended run | Failure A |
| A cap with no saved file | Never | The truncated part is gone; the agent re-runs the command to see it |

SWE-agent's ablations point the same way at a different scale: on SWE-bench Lite with GPT-4 Turbo, the paper reports 18.0% resolved with a 100-line file window against 14.3% with 30 lines and 12.7% with the whole file. Too little and too much both cost accuracy, and those numbers come from one model in 2024, so measure on your own traces before copying them.

## Follow-ups

- *Two engineers disagree about C: one wants to switch the default model, the other wants a second-model review on every edit. How do you decide without deciding by rank?* Replay the failing transcripts against each option and compare fix rate and cost per run on the same set.
- *What would make you move E entirely into the model's column?* A model that, given the repeat notice, changes approach in nearly every replay; then the harness's job shrinks to the cap.
- *A teammate says B is solved by adding "always run tests" to `CLAUDE.md` in capitals. What do you tell them?* The best-practices page says emphasis rarely fixes a missed line; a rule that must hold becomes a hook.

## Common mistakes

- Calling every failure a model problem because "a smarter model wouldn't do that". Three of five here are fixed without touching the model, and a fourth is half harness.
- Fixing D by editing `CLAUDE.md` again and expecting it to apply in the running session.
- Choosing a truncation budget without a saved-file fallback, so the agent's only way to see the rest is to run the command again.
- A head-only preview for build and test logs, which hides the error at the end.
- Fixing E with a stop and calling it solved; the run still fails, just sooner.
