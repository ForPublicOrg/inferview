## Question

<Callout kind="interview" label="Interview question">
"Our training dashboard computes MFU for a dense BF16 pre-training run on H100 SXM GPUs, using 6 × parameters × tokens per second as the numerator. Which per-GPU peak belongs in the denominator?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the footnote on the datasheet figure says.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which published MFU numbers the dashboard will be compared with, and what peak those used.</p></details>

## Answer

The dense BF16 peak, 989.5 TFLOP/s. NVIDIA's H100 page lists 1,979 teraFLOPS for BF16 with an asterisk that reads "With sparsity", and NVIDIA's Hopper post says the sparsity feature doubles standard Tensor Core throughput by exploiting fine-grained structured sparsity. A dense pre-training run has no such structure in its weights, so the rate it can approach is half the listed figure. Llama 3's table confirms the convention: 400 TFLOPs per GPU is reported as 41% MFU (400 / 0.41 = 976), and 430 as 43% (1,000).

The sparse figure is tempting because it is the number on the page, and a dashboard built from the datasheet reports every run at half its real MFU. The team then compares 20% against a published 41% and opens a kernel project that the run did not need.

The benchmark ceiling is tempting because it is honest about what the GPU can really do, and it is a useful number for a systems team. It is not MFU. PaLM defined the denominator as the system's published maximum so that runs on different systems can be compared; a measured ceiling makes the result higher, differs between matmul shapes and driver versions, and breaks every comparison the metric exists for.

The FP8 figure is tempting because the GPU can reach it, and because a mixed-precision run may use FP8 for some GEMMs. For a BF16 run it is the wrong precision. For an FP8 run, 1,979 is the right dense FP8 figure, which is why the same number appears as both a wrong and a right answer depending on the precision, and why a report that quotes "1,979" without naming precision and sparsity cannot be checked.

## Follow-ups

- The run uses FP8 for its MLP GEMMs and BF16 for attention. What denominator do you report, and what do you write next to it?
- The systems team wants the dashboard to show utilisation against a measured GEMM ceiling. Is that wrong, and what would you call it?

## Common mistakes

- Reading the datasheet number without its footnote.
- Changing the denominator between runs, so a trend line shows a peak change as an efficiency change.
- Quoting an MFU without the precision of the peak it was computed against.
