## Question

<Callout kind="interview" label="The round">
"Our GRPO run's responses have quadrupled in length over 400 steps and accuracy stopped improving at step 200. What is going on, and what do you change?"
</Callout>

As a scenario: R1-Zero-style GRPO from a 7B base model on maths prompts, G = 8, generation cap 4,096 tokens, no KL term, a binary reward from a boxed-answer checker. The loss and reward, from an internal fork of an open-source trainer:

```python
def advantages(rewards_by_group):
    out = []
    for r in rewards_by_group:                 # r: tensor of shape [G]
        out.append((r - r.mean()) / (r.std() + 1e-4))
    return torch.cat(out)

def policy_loss(logp, old_logp, adv, mask, eps=0.2):
    ratio = torch.exp(logp - old_logp)
    surr = torch.minimum(ratio * adv[:, None], ratio.clamp(1 - eps, 1 + eps) * adv[:, None])
    per_seq = (surr * mask).sum(dim=1) / mask.sum(dim=1)
    return -per_seq.mean()

def reward(text, gold):
    ans = extract_boxed(text)                  # None when the response hit the cap first
    return 1.0 if ans is not None and ans == gold else 0.0
```

## Answer

**The cause is the per-response length normaliser.** `per_seq` divides each response's summed token loss by its own length before averaging over the batch. For a wrong answer the advantage is negative, and the push-down per token is that advantage divided by length. Computed for a group with one correct answer out of eight: `r.std()` in PyTorch uses the n - 1 denominator, so the group std is 0.354 and the wrong samples' advantage is (0 - 0.125) / 0.354 = -0.354. At 400 tokens each token of a wrong answer carries -0.354 / 400 = -0.00088; at 3,000 tokens, -0.00012, 7.5 times less. The policy is pushed away from short wrong answers far harder than from long ones, so the wrong answers that survive are long. Liu et al. name this bias and show it lengthens incorrect responses in particular, which is the signature in the table: correct responses grow by 150 tokens, incorrect ones by 2,680.

**Why the others are tempting, and how they rank.**

1. *The standard-deviation scaling* is a real defect and ranks second. A prompt the policy solves seven times in eight has a group std of 0.354, the same as a prompt solved once in eight, while a prompt solved four times in eight has 0.535; dividing by it gives nearly solved and nearly failed prompts more weight than their information warrants. Liu et al. call this a difficulty bias. It distorts which prompts drive learning but does not single out wrong answers for lengthening.
2. *Truncated responses scored as wrong* compound the main defect. A response cut at 4,096 tokens gets the same 0 as a wrong answer but carries the smallest per-token penalty of any response in the batch, so running to the cap is the cheapest way to be wrong. The truncation rate going from 1% to 31% is that effect.
3. *No KL term* is TRL's current default and DAPO's choice for reasoning RL. It removes an anchor but has no reason to act on wrong answers only.
4. *Reasoning RL lengthens outputs* is true of runs where length grows with accuracy. Here accuracy is flat from step 200 while length keeps growing, and the growth is in the wrong answers.

**What to collect.** Truncated transcripts, to see whether the tail is repetition or genuine work; length by difficulty bucket; and a short A/B of the same run under a fixed normaliser. Without them, change the normaliser anyway: the bias is a property of the code, not a hypothesis.

**The fix: two defensible normalisers, plus a decision on truncation.**

- *A constant denominator (Dr. GRPO).* Divide the summed token loss by a constant such as the generation cap. Every token of every response gets the same weight. Cost: the gradient's scale now depends on the cap, so changing the cap from 4,096 to 8,192 halves the effective learning rate unless you retune it.
- *A token mean over the batch (DAPO, TRL's default on main).* Divide by the total number of tokens in the batch. Every token weighs the same within a batch. Cost: the gradient scale changes with batch composition, so a batch of long responses takes smaller steps per token than a batch of short ones.

For truncation, choose between DAPO's soft overlong penalty and masking truncated samples out of the loss. The quantity to choose is the penalty band. DAPO used a 4,096-token band below a 16,384-token maximum, a quarter of the budget; a band of a quarter to an eighth of the cap is reasonable. A band that starts below the length of typical correct answers (about 760 tokens here) is unreasonable, because it penalises answers the task needs. Masking truncated samples avoids penalising long correct work but throws away the signal that running out of budget is a failure.

The constraint conflict is token cost against accuracy on the hardest prompts: the old normaliser is buying length that costs inference money on every future query, and any fix that shortens responses risks cutting the long reasoning that hard prompts need.

My pick: the token-mean loss with the soft overlong penalty, std scaling turned off or moved to batch level, and per-bucket length tracking.

**Failure mode of the recommendation.** Removing the bias also removes its accidental benefit of letting hard prompts run long. If the hardest bucket's accuracy falls after the change while the easy buckets hold, the overlong penalty is too tight for that bucket, and a single band for all prompts is the wrong shape.

## Common mistakes

- Reading longer responses as more reasoning without splitting by correctness.
- Blaming the missing KL term, which acts on all responses equally.
- Fixing the normaliser and leaving truncated responses indistinguishable from wrong answers.
- Changing the normaliser and the cap at once, then misreading the change in effective learning rate as a change in the method.
