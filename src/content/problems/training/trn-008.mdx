## Question

<Callout kind="interview" label="Interview question">
"You have a kernel and a cycle-accurate simulator. It reports total cycles, IPC, a breakdown of stall reasons, occupancy and memory bandwidth. Design a rigorous plan to profile and optimise the kernel."
</Callout>

Constraints for this version, as a scenario: one simulator run takes 45 seconds; you have one working day; the kernel's input is a batch whose contents change control flow inside the kernel (it branches on data); a second engineer and an automated search tool will propose changes in parallel with you; the kernel ships into a library that other teams call with batch sizes you do not control.

Your plan should say what you measure first, how you decide which change to try next, how you know a change helped, what stops a change that is fast and wrong, when you stop, and what you write down. Choose and defend how many simulator runs you spend per experiment.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask whether the simulator is deterministic for a fixed program and input, and how much cycle counts vary across realistic inputs.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the machine's per-cycle limits on each kind of operation and on memory traffic.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask who can edit the tests and the benchmark inputs, and where the reference implementation lives.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Treat it as an experiment loop. Fix a correct baseline and a benchmark set of inputs that covers the data-dependent paths; compute a lower bound from the machine's per-cycle limits so you know the gap; form one hypothesis from the stall breakdown, change one thing, measure on the whole set, and keep it only if it passes a correctness gate held outside anyone's edit access. Stop at a target fraction of the bound fixed in advance or when gains per hour fall below what the kernel's share of the workload is worth. Log every experiment. What you give up is speed of iteration: one day at 45 seconds a run is about 640 runs, and the plan spends a share of them on gating and measurement rather than on trying changes.</p>
</Fragment>
<Fragment slot="long">
<p><b>Baseline and benchmark set.</b> The simulator is deterministic per program and input, so noise is not the problem; input dependence is. Build a set of inputs that covers the branches: sizes that do and do not divide the vector width, the batch sizes callers use, and data that drives each path. Run the baseline on all of them and record the distribution of cycles. The set size is a budget choice: at 45 seconds a run, one working day of about eight hours is 8 × 3,600 / 45 = 640 runs. Eight inputs per measurement leaves 80 measurements; three leaves about 210. Choose by how much cycles vary across inputs: if the spread is small, three representative inputs per experiment plus the full set at each checkpoint is enough; if it is large, measure every experiment on the full set and accept fewer experiments.</p>
<p><b>Bound.</b> From the machine's per-cycle limits (issue slots per unit, memory bandwidth), compute the minimum cycles for the work the kernel must do. The gap between baseline and bound is the budget, and the binding unit says what kind of change can help. Recompute it after each structural change, because the binding unit moves.</p>
<p><b>Choosing the next change.</b> Use the stall breakdown to form a hypothesis that names a resource: "dependency stalls dominate, so interleaving independent work will raise IPC and cut cycles". Predict the direction of each counter before running. Change one thing. A change that raises IPC without cutting cycles has added instructions, not removed stalls. When two kept changes might interact, measure the four combinations before crediting either.</p>
<p><b>The correctness gate.</b> Every candidate is checked against a reference implementation on the full input set plus inputs the proposers never saw, from a copy of the tests nobody proposing changes can edit. This is the lesson of Anthropic's public take-home: none of its first-day submissions below 1,300 cycles were valid, and in each a language model had modified the tests. With an automated search tool in the loop, the gate runs on every proposal before its cycle count is even looked at.</p>
<p><b>Two defensible ways to run the day.</b> Bound-first: spend the first hour computing the bound and restructuring toward the binding unit, then tune. It finds the large wins early but can sink hours into a restructure that the dependency chains cannot realise. Counter-first: take the top stall reason each round and fix it. It makes steady progress with little upfront cost but can polish a structure that cannot reach the bound. With one day and a large gap, bound-first; with a small gap, counter-first.</p>
<p><b>Stop rule.</b> Fix a target in advance, for example within 15% of the bound on the median input, or stop when three consecutive experiments each gain under 1%. Anthropic's own record shows why the target must be set first: 1,579 cycles after 2 hours, 1,487 after 11.5 hours, a further 6% for nearly six times the time.</p>
<p><b>What you write down.</b> One log entry per experiment: hypothesis, the single change and its diff, inputs, cycles per input, counters that moved against the prediction, bound and binding unit, gate result, keep or revert. At the end, a short memo: final cycles against baseline and bound per input class, the changes that bought them, the inputs the library was not tested on, and the remaining ideas with their estimated gain.</p>
<p><b>Failure mode of this plan.</b> The benchmark set is chosen on day one, and the kernel gets tuned to it. A caller's batch size outside the set can land on a slow path or on a remainder bug the gate never exercised. Mitigate with a second, held-out set the optimisers never see, run only at checkpoints, and say in the memo which batch sizes were covered.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li>The search tool finds a variant 18% faster that passes the gate but whose cycles vary twice as much across inputs. Your library's callers care about the worst case. Do you ship it, and what do you write in the release note?</li>
<li>Halfway through the day the simulator team says its memory model undercounts bank conflicts. Which of your logged results do you still trust, and what would make you throw the day's work away?</li>
<li>Your colleague wants to drop the held-out set to get 30% more experiments into the day. Make the case for or against with the run budget.</li>
</ul>

## Follow-ups

- How would the plan change on real hardware, where the same program and input give different timings run to run?
- The kernel is 3% of an end-to-end workload. How does that change the stop rule?

## Common mistakes

- Optimising against one input, so data-dependent paths and remainders go untested.
- Reading IPC or occupancy as the objective instead of cycles on the benchmark set.
- Changing two things at once and crediting both.
- Letting the optimiser, human or automated, run the tests from a copy it can edit.
- No stop rule, so the day ends when the time does, with no record of what was left.
