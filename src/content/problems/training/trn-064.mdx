## Question

<Callout kind="interview" label="As asked">
"Your platform team runs a self-serve LoRA fine-tuning service on 8B to 30B open models. Today it passes PEFT's defaults through. Most jobs are supervised, 5,000 to 200,000 examples; a few are RL. Teams get one run per request unless they pay for a sweep. Users complain that LoRA 'underperforms'. What defaults do you ship for targets, rank, alpha, learning rate and batch, what evidence backs each, and what do you give up?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what learning rate the users' failed runs used, and whether it came from a full fine-tuning recipe.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the batch sizes of the complaining runs and how the service chooses them.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how many adapters a serving node keeps resident and how much memory each may use.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>All linear layers including MLP and expert layers, because attention-only adapters lose to MLP adapters even at matched parameter count. Alpha fixed at 32 and the rank set by dataset size, because with alpha over r scaling the best learning rate barely moves with rank. Learning rate at ten times the model's published or measured full fine-tuning rate, because that ratio held across 14 Llama and Qwen models. Batch capped at 32 sequences, because the LoRA gap grows with batch and rank does not close it. The cost: larger adapters per job, slower jobs at small batch, and a single-run default that is right on average and wrong for some jobs.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why PEFT's defaults are not recommendations.</strong> r 8, alpha 8 and architecture-chosen targets (query and value, per PEFT's notes) are values that construct a valid config. Three published comparisons say the target choice costs quality: QLoRA's ablation, Biderman et al. on Llama-2-7B, and Thinking Machines' matched-parameter test, where attention-only at rank 256 lost to MLP-only at rank 128. The default rate is whatever the user brings, usually a full fine-tuning rate about ten times too low for LoRA.</p>
<p><strong>The learning-rate default is the decision with two defensible answers.</strong> (a) A fixed rule, 10x the model's full fine-tuning rate (15x for jobs under about 100 steps), one run per job. Cost: the ratio is a fit across models; some jobs land off their optimum, and nothing in the service tells them. (b) A mandatory three-point sweep around that rule. Cost: three times the GPU spend per job, which the service's pricing does not cover. The constraint conflict is GPU budget against quality per job. I would ship (a) as the default and make the sweep a one-flag option with the rule's centre, because the ratio is stable enough that most of the loss is in using the wrong order of magnitude, not in missing the optimum by 2x.</p>
<p><strong>Rank.</strong> Above rank 4 the best rate moves by less than 2x, so rank can be chosen for capacity without re-tuning. LoRA matches full fine-tuning while its parameters exceed the information in the data; typical supervised sets of this size fit at rank 16 to 64 on all linear layers. RL jobs carry far less information per episode, and rank 1 matched full fine-tuning on the published RL tasks, so RL jobs default low. Serving memory pulls the other way: a larger rank makes every resident adapter bigger, so the rank default is a trade between capacity and how many adapters a node holds.</p>
<p><strong>Batch.</strong> Thinking Machines found the LoRA gap grows with batch size independently of rank; at batch 32 it was small and shrinking. Cap the default at 32 sequences and let users raise it with a warning. Cost: lower GPU utilisation per job.</p>
<p><strong>How these defaults fail.</strong> A team doing continued pretraining on billions of tokens will exceed any default rank's capacity, and the service will report a LoRA result that trails full fine-tuning for a reason no hyperparameter fixes. The service should detect large raw-text jobs and say so before running, not after.</p>
</Fragment>

The evidence behind each default is cited above with its conditions: Llama and Qwen models, supervised sets such as Tulu3 and OpenThoughts3, and RL on MATH, GSM8K and DeepMath-103K. A model family or optimizer outside that set is a reason to run the sweep, not to trust the rule.

## Follow-ups

- *The sweep option doubles the cost of jobs on the 30B MoE models. Do you keep it optional for them, and what risk do you write down?*
- *A team wants full fine-tuning instead because "LoRA underperforms". What do you ask before agreeing?*
- *What metric would show, from production jobs alone, that the 10x rule is wrong for a model family?*

## Common mistakes

- Treating library defaults as tuned recommendations.
- Reusing a full fine-tuning learning rate for LoRA and concluding LoRA is weaker.
- Raising rank to fix a gap caused by a large batch, which rank does not close.
- Changing alpha and learning rate independently, when with alpha over r scaling they act as one knob.
- Turning on rank-stabilised scaling without re-sweeping, which changes the effective step by a factor of the square root of the rank.
