## Question

A team lead sends you this plan for review before compute is approved. List every flaw you find and what you would change, then open the checklist.

> **Plan: CodeTutor-SFT v1**
>
> **Goal.** Fine-tune our 7B model to explain and fix Python bugs for the learning product. Ship in four weeks.
>
> **Data.** We will generate 1,000,000 examples with the strongest available API model. Seeds: 12,000 bug-fix problems scraped from public tutorials, Q&A sites and two open benchmark repositories. For each seed, the generator writes 80 to 90 variations (renamed variables, different libraries, different bug types), then for each variation writes the buggy code, an explanation of the bug, the fixed code and three unit tests. Temperature 1.0, one sample per prompt to maximise diversity. We remove exact duplicate strings.
>
> **Quality.** The generator is stronger than any model we could train, so its output is high quality by construction. We will spot-check 100 examples by hand.
>
> **Training.** Standard SFT, 2 epochs over the full set.
>
> **Evaluation.** We hold out 5% of the generated examples as a test set. Success: test loss lower than baseline, plus a gain on two public bug-fixing benchmarks.
>
> **Cost.** About one million generator calls, within the approved API budget.

## Answer

The plan treats generation as the product and has no filter, so its quality is whatever the generator's error rate is, replicated a million times. The changes, roughly in order of how much they matter:

**Add a filter that decides quality, and make it executable.** The domain has the best filter available: run the code. Each example's fixed code must pass its tests, the buggy code must fail at least one, and the tests must be checked against something independent of the generator (a reference solution, or a second generator's tests that must agree), because generator-written tests can be wrong in the same way as the fix. Nemotron-4's pipeline used ground truth or verifiers wherever they existed and a reward model only elsewhere; here the explanation text is the only part without a verifier.

**Use rejection sampling instead of one sample at temperature 1.0.** Several samples per prompt, kept only when they pass, is the cheapest quality lever and turns the API budget into accepted examples instead of raw ones. Then measure yield by seed difficulty. Llama 3 reports that a strict code filter initially hurt benchmarks because it removed the challenging examples; its fix was to revise the hardest responses until they passed. Expect the same skew here and resample by stratum.

**Separate the evaluation from the training distribution.** A 5% split of generated examples shares seeds with the training set, often the same seed with renamed variables, so test loss measures memorisation of the seed set. Hold out whole seeds, and build a small human-written set for the learning product's real failure cases.

**Decontaminate before training.** The seeds include two open benchmark repositories, and the success criterion is a gain on public bug-fixing benchmarks. If those overlap, the gain is contamination. Exact match is the floor, as Llama 3 did for its post-training data; n-gram overlap catches copies; and because the plan's own variations are paraphrases, a semantic nearest-neighbour check against the benchmark items is needed too. Llama 3's pretraining analysis found 85% of HellaSwag examples contaminated with an estimated 14.8-point gain for its 8B model, which is the size of effect this can produce.

**Bound the generator's style.** The student inherits the generator's length and format: DeepSeek-V3 reported R1-generated data suffered from overthinking and excessive length, and distillation doubled its MATH-500 response length. A tutoring product has a length budget; enforce it in the filter.

**Reconsider the volume.** 12,000 seeds and 80 to 90 near-copies each is mostly paraphrase, and exact-string dedup will not remove near-duplicates. Fewer, filtered, deduplicated examples by embedding similarity per seed are likely worth more than a million unfiltered ones; the pilot below decides the number.

**Check the generator's terms.** Whether its terms of use allow training on its outputs is a legal question to settle before the first call, not after a million of them.

**A plan that fits four weeks.** Week one: filter, decontamination and held-out seed split, run on a 20,000-example pilot, with yield by stratum reported. Week two: scale generation with rejection sampling to the volume the pilot suggests. Week three: train and evaluate. Week four: buffer. What is given up: the million-example headline and some explanation diversity, in exchange for a gain that can be trusted.

## Follow-ups

- The pilot's yield is 70% on easy seeds and 9% on hard ones. Do you raise samples per prompt for hard seeds, revise responses, or accept the skew, and what does each cost in API budget?
- The team lead pushes back that a stronger generator makes filtering unnecessary. What single measurement from the pilot settles it?
- What would you need to see on the human-written held-out set to approve a second million-example run?

## Common mistakes

- Accepting "the generator is stronger than our model" as a quality argument.
- Treating a random split of generated data as a held-out test.
- Checking the fix against generator-written tests without checking the tests.
