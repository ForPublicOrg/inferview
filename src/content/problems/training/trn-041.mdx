## Question

## Answer

The cause is the stats helper. `stats` is decorated with `torch.no_grad()`, so `P` comes back as a tensor with no graph, and `aux` is built from two gradient-free vectors. The value is correct, the dashboard shows it, and its gradient with respect to the router is zero. The balance loss works only through `P`: `f` comes from an argmax and never had a gradient, and `P` is the path that pushes probability away from overloaded experts. The refactor kept the number and removed the force. The logs read exactly like that: the aux value climbs tenfold over 3,000 steps and nothing pulls it back, because nothing can.

The change hides the defect well: the new line computing `aux` is mathematically identical to the Switch formula, and the decorator sits on a helper whose name says it only computes statistics, which is also what a reviewer was told it was for.

**Ranking the rest after the fix.**

1. *bf16 router logits.* Real and second. Switch Transformers casts the router input to float32 inside the router specifically for stability, then casts the dispatch and combine tensors back so no float32 crosses the network. With a working balance loss the run may survive bf16 routing, but collapse becomes easier to trigger and harder to reproduce. Restore the cast; it costs almost nothing.
2. *Capacity factor 1.0.* Real and third. It turns any imbalance into dropped tokens, and the 73.8% drop rate is what the skew costs under it. With balance restored and a balanced load near 1.0 times the mean, drops at 1.0 may be acceptable; measure them per layer before deciding to return to 1.25, which costs memory the team wanted back.
3. *Unnormalised top-2 gates.* Not a defect. Normalising over the selected experts, as DeepSeek-V3 does, is one design; using the raw top-k probabilities is another, and this change did not touch it.

**What to collect.** The router weight gradient from the auxiliary term alone on one batch (zero confirms it in a minute), the previous run's aux curve for the same steps, and per-layer drop rates. **What to ship without it.** Moving `P` out of the `no_grad` helper (compute `f` there for logging, `P` in the forward pass) and restoring the float32 cast are safe today, since neither changes anything a correct run depends on.

**Restart or continue.** That is the decision with two defensible answers. Continuing from the latest checkpoint with the fix keeps 3,000 steps of compute, but the router and the two hot experts have trained into a collapsed state, and a balance loss at 0.01 may take a long time to pull it back, or settle into a different local skew. Restarting from the last checkpoint before step 1,000, where max-over-mean was 2.4, throws away 2,000 of the 3,000 steps and starts from a router that was still close to balanced. The choice depends on how much compute the steps represent against how long recovery takes: run both for a few hundred steps if the budget allows and pick by max-over-mean and loss.

**How the fix fails.** A per-batch balance loss with small micro-batches still lets individual sequences collapse onto a few experts; and if someone later moves `P` back into a logging helper, the same bug returns silently. Add an assertion that `aux.requires_grad` is true in the training step, and a test that the router receives gradient from the auxiliary term alone.

## Follow-ups

- *Your restart decision costs a day of cluster time, and the deadline does not move. Which of the three fixes do you ship if you can only restart once, and what risk do you write down?*
- *After the fix, two layers still sit at 4 times the mean load while the rest are balanced. Would you raise alpha globally, per layer, or switch those layers to a bias balancer, and what would make you reverse that?*
- *How would you make this class of bug, a loss that is logged but carries no gradient, fail CI instead of failing a run?*

## Common mistakes

- Picking bf16 because it is the most familiar MoE stability fix, without checking whether the balance loss still has a path to the router.
- Treating the drop rate as the cause; it rises after the skew and is a symptom of it under a tighter capacity.
- Raising alpha, which multiplies a gradient of zero.
- Reading only the newest log line; the slope from step 500 to 1,000, with the aux value already rising, is the evidence that the balancer is absent rather than overwhelmed.
