## Question

<Callout kind="interview" label="Interview question">
"Here are five kernels from one transformer layer's forward pass on an H100 SXM. Which of them is compute-bound?"
</Callout>

The setting, as a scenario: BF16 activations and weights, a micro-batch of 4,096 tokens, hidden size 4,096, MLP width 16,384, each op run as its own kernel with its inputs read from and outputs written to HBM.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask, for each kernel, how many bytes it must move at minimum and how many FLOPs it does on them.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which kernels run on the tensor cores and which on the vector units, and what each unit's peak is.</p></details>

## Answer

**The output projection is compute-bound.** It multiplies 4,096 × 4,096 activations by a 4,096 × 4,096 weight: 2 × 4,096³ ≈ 1.37 × 10<sup>11</sup> FLOPs over 3 × 4,096² × 2 bytes ≈ 101 MB, an intensity of about 1,365 FLOPs per byte. The H100 SXM's dense BF16 rate over its bandwidth is about 295, so the kernel spends longer computing than moving data.

**The LoRA projection is the tempting wrong answer.** It is a matmul and runs on the tensor cores, which is why it is easy to file under compute-bound. With a 4,096 × 16 weight, the intensity BDF / (BD + DF + BF) = 4,096 × 4,096 × 16 / (4,096² + 2 × 4,096 × 16) ≈ 15.9 FLOPs per byte: the kernel reads the whole activation tensor to do 16 output columns of work. Low-rank adapters add little compute and a full extra pass over the activations, which is why fusing the adapter into the base projection matters more than its FLOP count suggests.

**Softmax, GELU and LayerNorm run on the vector units.** Their comparison is against 67 TFLOPS of FP32 over 3.35 TB/s, about 20 FLOPs per byte. A BF16 elementwise kernel moves 4 bytes per element (2 in, 2 out), so it needs about 80 FLOPs per element to become compute-bound. Softmax's exponential feels expensive and GELU's tanh form looks heavy, but both are a small fraction of 80. LayerNorm's two reductions per row make it look like more work than a pointwise op; they add synchronisation within a row, not arithmetic. This is the pattern Horace He measured in BERT, where these ops were 0.2% of FLOPs but ran at hundreds of times fewer FLOPS than the matmuls.

## Follow-ups

- The same layer runs at a micro-batch of 128 tokens during a long-context phase with sequence parallelism. Which answer changes?
- You can fuse one of the four bandwidth-bound kernels into a neighbour. Which saves the most time, computed from its tensor size?

## Common mistakes

- Classifying by op type: "matmuls are compute-bound" misses the LoRA projection and the small-batch case.
- Comparing elementwise kernels with the tensor-core ratio of 295 instead of the vector units' 20.
- Counting a transcendental function as many FLOPs; it changes the constant, not the regime.
