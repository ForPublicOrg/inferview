## Question

A team reports that their QLoRA run on a 33B model "trains in 4-bit" and asks whether moving to a GPU with native 4-bit matmul support will speed it up. Before answering, pin down what QLoRA keeps in which precision. Which description is accurate?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which tensors in the run receive gradients, and which are only read.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask the team for the data type of the inputs to the matmul kernel in a profile of one training step.</p></details>

## Answer

QLoRA separates a storage data type from a computation data type. The frozen base weights are stored in 4-bit NormalFloat in blocks of 64, and the per-block scales are themselves quantised to 8-bit floats (double quantisation). For every forward and backward matmul, a block is dequantised to BF16 and multiplied in BF16. The LoRA adapters, on every linear layer, are the only parameters that receive gradients, and they and their optimizer state stay in higher precision. Activations are BF16 throughout.

So the answer to the team: the run stores in 4-bit and computes in 16-bit. A GPU with native 4-bit matmuls does not speed up QLoRA as published, because QLoRA never issues a 4-bit matmul; it would need a different method that keeps the weights in a hardware 4-bit format for compute, with its own accuracy evaluation.

The wrong options are each a reasonable reading of "4-bit fine-tuning". Quantising the adapters too sounds like more saving, but the adapters are about 1% of the parameters at the paper's settings and updates that small would vanish at 4-bit resolution. 4-bit arithmetic is what "4-bit" means for inference kernels, and QLoRA is not one. Keeping attention in higher precision is a pattern from some inference quantisation recipes, not from QLoRA, whose ablation found that adapters on every linear layer, attention included, are what matched 16-bit fine-tuning.

## Follow-ups

- The team's profile shows a large share of step time in dequantisation kernels. Which knobs change that share, and which of them change memory?
- When the adapter is merged for serving, which base weights do you merge into, the original BF16 or the dequantised NF4, and what differs?

## Common mistakes

- Reading "4-bit" as the arithmetic precision rather than the storage format.
- Assuming the optimizer state is quantised; paged optimizers move it to CPU memory, they do not shrink it.
- Forgetting that activations are BF16 and grow with tokens, so the 4-bit storage does nothing for long sequences.
