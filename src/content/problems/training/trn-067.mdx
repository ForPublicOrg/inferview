## Question

An 8B base model, two LoRA runs from one shared config, each compared against a full fine-tuning run on the same data (scenario):

```text
shared LoRA config: r=16  lora_alpha=32  target_modules=all-linear  lora_dropout=0.05
                    lr=2e-4 (full fine-tuning baseline: 2e-5)  cosine decay  AdamW

run A  instruction set, 60,000 examples (about 30M tokens), 3 epochs, global batch 64 sequences
       held-out instruction eval:  full FT 71.8   LoRA 71.2

run B  maths web text, 6B tokens, 1 epoch, global batch 1,024 sequences x 4,096 tokens
       held-out maths loss (nats/token)
       tokens seen   full FT   LoRA
       0.5B          1.212     1.214
       1B            1.150     1.158
       2B            1.091     1.118
       4B            1.040     1.087
       6B            1.012     1.071
       maths benchmark at 6B:   full FT 41.0   LoRA 33.5
       general benchmark average, change from base:   full FT -2.9   LoRA -0.8
```

No rank or batch ablations were run. Which explains why LoRA matches on run A and falls short on run B? Then rank the other defects in the setup and say what you would measure next.

<details class="hint"><summary>Hint 3</summary><p>Request a short run at a higher rank and one at a smaller batch on the first 2B maths tokens.</p></details>

## Answer

**The cause.** Only the data and the batch differ between the runs; rank, alpha, targets, dropout and the learning-rate ratio are shared, and the shared config matched full fine-tuning on run A. So the explanation has to be something run B's data or batch triggers. The loss gap is 0.002 at 0.5B tokens, 0.008 at 1B, 0.027 at 2B, 0.047 at 4B and 0.059 at 6B: it opens late and widens. That is the shape of a capacity limit. By the bits-per-parameter reasoning in LoRA Without Regret, a rank-16 adapter on an 8B model has tens of millions of parameters, while 6B tokens of a new domain carry far more information than that; run A's 30M tokens do not. Biderman et al. found the same split on Llama-2-7B: LoRA matched full fine-tuning in instruction tuning and trailed by a wide margin in continued pretraining on maths, where full fine-tuning's weight changes had rank 10 to 100 times higher than typical LoRA settings.

**Ranking the rest.**

1. *Batch 1,024 sequences.* A real second defect. The LoRA gap at large batch grows with batch size and does not shrink with rank, so it can add to run B's gap, but its signature is a gap present throughout, not one that opens with tokens. It is secondary here.
2. *The choice of LoRA for continued pretraining at all.* Not a bug in the config; a method choice the evidence argues against, and the one decision that matters most.
3. *Alpha 32 at rank 16* and *dropout 0.05* are shared with the run that worked and are not defects.

**What to measure, and what to do without it.** The cheapest discriminating test is two short runs on the first 2B tokens: rank 128 at batch 1,024, and rank 16 at batch 256. If the higher rank closes most of the 2B-token gap, capacity is confirmed; if the smaller batch does, the batch effect is larger than the curve suggests. Without those runs, the decision for a 6B-token maths corpus is full fine-tuning with replay to control forgetting, or LoRA at a much higher rank if serving many adapters on one base is a hard requirement. The cost of full fine-tuning is visible in the last line of the trace: it forgot more of the general benchmark (-2.9 against -0.8), so replay or a forgetting budget has to come with it.

## Follow-ups

- *The higher-rank pilot closes half the gap. Do you keep raising rank or switch to full fine-tuning, given the team serves twelve adapters on one base?*
- *Product says the general-benchmark drop of 2.9 under full fine-tuning is unacceptable. What do you change in the full fine-tuning run, and how do you know it worked?*

## Common mistakes

- Blaming a setting that is shared with the run that worked.
- Treating the batch effect as the cause without checking whether the gap is constant or growing.
- Reading LoRA's smaller general-benchmark drop as a reason to keep it, without counting what it failed to learn.
- Raising rank without re-checking the learning rate, when the 1/r scaling keeps the best rate roughly stable but not identical at very low ranks.
