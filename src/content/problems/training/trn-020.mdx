  solution: |
    def _bounds(k, n):
        base, extra = divmod(k, n)
        out, lo = [], 0
        for c in range(n):
            hi = lo + base + (1 if c < extra else 0)
            out.append((lo, hi))
            lo = hi
        return out


    def ring_allreduce(buffers, send):
        n = len(buffers)
        if n == 0:
            return []
        k = len(buffers[0])
        if any(len(b) != k for b in buffers):
            raise ValueError("every rank needs a buffer of the same length")
        work = [list(b) for b in buffers]
        if n == 1:
            return work
        bounds = _bounds(k, n)

        # Reduce-scatter. At step t rank r forwards chunk (r - t) mod n to rank r + 1, which adds
        # its own values. Every chunk is summed once, in one fixed order, along one chain of ranks.
        for t in range(n - 1):
            wire = []
            for r in range(n):
                lo, hi = bounds[(r - t) % n]
                vals = work[r][lo:hi]
                if vals:
                    send(r, (r + 1) % n, vals)
                wire.append(((r + 1) % n, lo, vals))
            for dst, lo, vals in wire:
                buf = work[dst]
                buf[lo:lo + len(vals)] = [x + y for x, y in zip(vals, buf[lo:lo + len(vals)])]

        # Rank r now owns the finished chunk (r + 1) mod n. The all-gather copies finished chunks
        # around the ring and never adds, so every rank ends with the same bits.
        for t in range(n - 1):
            wire = []
            for r in range(n):
                lo, hi = bounds[(r + 1 - t) % n]
                vals = work[r][lo:hi]
                if vals:
                    send(r, (r + 1) % n, vals)
                wire.append(((r + 1) % n, lo, vals))
            for dst, lo, vals in wire:
                work[dst][lo:lo + len(vals)] = vals
        return work

## Question

<Callout kind="interview" label="Interview question">
"Write an all-reduce over N ranks that sum their gradient buffers. Each rank can only send to its neighbour. Then tell me how much each rank sends and why that matters more than N."
</Callout>

Write `ring_allreduce(buffers, send)`. There are `N` ranks in a ring, rank `r` holds `buffers[r]`, a list of `K` numbers, and the result is the elementwise sum on every rank. The simulation runs in one process, but treat it as a network: a rank may only send to rank `(r + 1) mod N`, and every message goes through `send(src, dst, values)`, which the tests use as a meter. Return each rank's copy of the sum and leave the inputs alone.

Two budgets apply, and the hidden tests enforce both:

- **Traffic.** No rank sends more than `2 * (N - 1) * ceil(K / N)` values or more than `2 * (N - 1)` messages. For `N = 16` and `K = 40,000` that is 75,000 values per rank. A rank that forwards its whole buffer once around the ring sends 15 x 40,000 = 600,000; gathering at rank 0 and broadcasting makes rank 0 send the same 600,000.
- **Agreement.** With floating-point inputs, every rank must return exactly the same bits, not values that are merely close. Replicas whose gradients differ in the last bit apply different updates and drift apart.

`K` need not divide by `N`, and `K` may be smaller than `N`. How you cut the buffer into chunks, which chunk a rank owns after the first phase, and whether you send empty messages are your choice; only the result and the budgets are checked.

## Answer

The reference splits the buffer into `N` contiguous chunks whose sizes differ by at most one, then runs two phases of `N - 1` steps each.

**Reduce-scatter.** At step `t`, rank `r` sends chunk `(r - t) mod N` to its neighbour, which adds the incoming values to its own copy of that chunk. After `N - 1` steps, chunk `c` has passed through every rank once and sits complete on rank `(c - 1) mod N`. Each rank sent one chunk per step, `(N - 1) * K / N` values.

**All-gather.** Each rank forwards finished chunks for another `N - 1` steps, and receivers overwrite rather than add. That is another `(N - 1) * K / N` values per rank, so the total is `2 * (N - 1) * K / N`. For the visible case, `N = 4` and `K = 8`, that is 2 x 3 x 8 / 4 = 12, the number the test asserts.

**Why the agreement test passes.** Every element of the result is computed exactly once, by one chain of additions in one fixed order, and then copied. The all-gather moves bits; it never recomputes. A design in which each rank sums all `N` buffers itself, starting from its own buffer, produces sums that differ in the last bits from rank to rank. The hidden test uses values spread over 16 orders of magnitude to make that visible.

**Why the per-rank number matters more than `N`.** `2 * (N - 1) / N` approaches 2 as `N` grows, so the time for a large buffer depends on the buffer size and on the slowest link in the ring, not on how many ranks share the work. The gather-and-broadcast design sends `(N - 1) * K` from rank 0 alone, `N / 2` times the ring's per-rank traffic: 8 times at `N = 16`. The price the ring pays instead is `2 * (N - 1)` sequential steps, each paying a link's latency. At `N = 1,024` that is 2,046 hops, and for a small buffer the latency term outweighs the bandwidth term.

**The slowest link.** On H100 nodes the scaling book gives 450 GB/s per direction per GPU over NVLink and 50 GB/s per GPU over InfiniBand. A ring that spans two nodes has at least one hop on the 50 GB/s link, and every step waits for it, so the whole collective runs at the scale-out rate: 9 times slower per byte than the same ring inside one node.

**The decision with two defensible answers: how to cut uneven buffers.** The reference uses near-equal chunks, which meets the budget and leaves the last chunks one element short. The alternative pads `K` to a multiple of `N` so every message has the same size, which is what a kernel that works in fixed-size slices prefers; it costs up to `2 * (N - 1)` padding values per rank, which the `ceil` in the budget allows. Near-equal chunks win when the buffer is small relative to `N`; padding wins when the kernel's efficiency depends on uniform message sizes. Both pass.

**Where the reference fails.** It sums in the input type. In a real job the buffers are bf16 gradients, and accumulating many bf16 partial sums in bf16 loses low-order bits on every hop; the agreement test would still pass, because every rank agrees on the same rounded bits. Accumulating in fp32 and sending fp32 partial sums doubles the bytes on the wire; accumulating in fp32 locally and sending bf16 keeps the traffic and rounds once per hop instead. Which one to ship is a precision-against-bandwidth decision that depends on the gradient magnitudes in the job.

## Common mistakes

- Reporting traffic as `2K` regardless of `N`, which is the limit, not the value; for `N = 2` it is `K`.
- Recomputing the sum on every rank during the all-gather, which passes integer tests and fails the bitwise test with floats.
- Forwarding whole buffers around the ring, which is correct and sends `N - 1` times the buffer per rank.
- Applying a step's messages while the other ranks in the same step are still sending, so a rank forwards a chunk it has already changed in that step.
