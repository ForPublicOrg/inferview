Which defect explains the symptom?

## Answer

**The cause.** `dcp.load` calls `app.state_dict()` first to learn what to read, then reads into it. In the restarted process the optimizer has never stepped, so `self.optimizer.state_dict()` returns its parameter groups and no per-parameter state; AdamW creates its moment tensors on the first step. DCP reads the least data needed to fulfil the requested state dict, so it reads the parameter groups and none of the saved moments. `optimizer.load_state_dict` then receives a state dict with no state, and nothing fails. The checkpoint on disk is probably fine; the restore asked for less than was saved. The save path wrote the moments correctly because, at step 41,000, the optimizer had state.

**Why the log looks like this.** Step 41,001's loss is computed with the restored weights before any update, so it matches the pre-crash trend. Its update is the first AdamW step with fresh moments, and bias correction makes that first step about one learning rate per coordinate in the direction of the gradient's sign, regardless of the gradient's size. Every parameter moves by roughly 2.4 × 10⁻⁴ at once, which is far larger than steady-state updates for most coordinates. Loss and gradient norm spike over the next few steps, the moments rebuild within tens of steps (with β₂ = 0.95 the second-moment average spans roughly 20 steps), and the run settles onto a slightly worse trajectory. Held-out loss moving with training loss says the model got worse, not that the data changed.

**Why each wrong option is tempting.** The loader really is missing from the state dict, so after the restart the run re-reads the start of its data; that is a real defect, but it lowers training loss on repeated data and does not touch held-out loss or produce a spike at step 41,002. The `async_save` future is discarded, so a save can still be uploading when the next one starts or when the job dies; that is a real defect too, but the crash was 200 steps after the save and the restored weights reproduce the pre-crash loss. The scheduler option is the classic restart bug, ruled out here by the logged learning rate.

**What to collect, and what to do without it.** First, `len(optimizer.state)` after load against the parameter count, and the stored keys in the checkpoint metadata: if the metadata holds the moments and the restarted job did not request them, the diagnosis is confirmed. Second, a fork test on a small model: save at step k, restore in a fresh process, and compare the next steps bitwise. Without that evidence, the fix is still clear: build the optimizer state dict with `get_optimizer_state_dict` and restore it with `set_optimizer_state_dict` (canonical keys, with the docs' rule that the set happens before `backward()` or after `step()`), and assert after every load that every parameter has optimizer state.

**Roll back or continue.** Two defensible answers. Roll back to step 41,000 with the fixed restore and redo 3,000 steps on 256 GPUs: the cost is known and the trajectory is the one the run was on. Or continue: the spike recovered within 200 steps, the remaining gap is 0.03 in held-out loss, and an LR schedule with most of its length left often absorbs a gap like that, but nobody can promise it. The conflict is a known compute cost against an unmeasured quality risk that would show up only at the end of the run. I would roll back if the run is in its first half and the redo costs under a day, and continue with a written note and a comparison checkpoint otherwise. Failure mode of rolling back: if the step-41,000 checkpoint is itself incomplete, because nothing waited on its upload, the rollback fails too, so verify it loads with the fixed code before discarding the 44,000 state.

**Ranking the other defects.** Second is the discarded `async_save` future: wait on the previous `upload_completion` before starting the next save and before exit, or the next failure may find no complete checkpoint. Third is the missing loader state: add the loader position to the state dict, or every restart re-reads the start of the data.

## Follow-ups

- *The research lead says 0.03 of held-out loss is within noise and refuses to roll back. What measurement settles it, and how long do you wait for it?*
- *Your fix adds an assertion that fails the job if any parameter lacks optimizer state after load. A frozen embedding table has none by design. What do you change, and who reviews it?*
- *What would make you trust the restore path enough to remove the post-load assertion?* A fork test in CI on every change to the checkpoint code, passing bitwise on the same layout and within tolerance after a reshard.

## Common mistakes

- Concluding the checkpoint file is corrupt without inspecting it, when the evidence points at what the load asked for.
- Blaming the scheduler without checking the logged learning rate.
- Fixing only the optimizer and leaving the discarded `async_save` future, which breaks the next restore instead.
- Treating "loaded with no warnings" as proof of a correct restore.
