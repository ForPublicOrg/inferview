## Question

<Callout kind="interview" label="Debug round">
"Since Tuesday's release, long support conversations fail. Short ones are fine. Here is the request builder and what we logged. What is the cause, and what do you need that we have not given you?"
</Callout>

The assistant runs on `claude-opus-5-5` with adaptive thinking and has run on its own organisation account since the product was split out of its parent company's account in September 2026. Release 4.2 changed three things in the request builder: it replaced the old compaction, which summarised the whole session into one user message, with a version that keeps the last six turns verbatim, because users said the bot forgot what they had just told it; it added the current date to the system prompt; and it moved the threshold to 60,000 input tokens.

```python
SUMMARISE_AT = 60_000
KEEP_TURNS = 6

def build_request(session):
    system = SYSTEM.format(company=session.company, today=date.today().isoformat())
    history = session.messages
    if session.last_input_tokens > SUMMARISE_AT:
        head, tail = split_turns(history, KEEP_TURNS)
        summary = summarise(head)
        history = [{"role": "user", "content": "Earlier in this conversation:\n" + summary}] + tail
    return dict(model=MODEL, max_tokens=4096, system=system, tools=TOOLS,
                messages=history, thinking={"type": "adaptive"})

def split_turns(messages, keep):
    starts = [i for i, m in enumerate(messages)
              if m["role"] == "user" and not is_tool_result(m)]
    cut = starts[-keep] if len(starts) >= keep else 0
    return messages[:cut], messages[cut:]

def record(session, response):
    session.messages.append({"role": "assistant", "content": response.content})
    session.last_input_tokens = response.usage.input_tokens
```

What the team logged over two days (scenario figures):

| | sessions | requests that got a 400 |
|---|---|---|
| never past 60,000 input tokens | 41,200 | 0 |
| past 60,000 input tokens | 1,870 | every request after the first summary, in all of them |

The logger keeps the status and the error type (`400 invalid_request_error`) and drops the message body. Failing sessions include some that never called a tool. The client's own token count puts failing requests between 18,000 and 31,000 tokens. Failures are spread evenly across the day.

## Answer

The keep-tail summary is the cause. On newer Claude models, a `thinking` block sent back in the history is checked against its prefix: the top-level `system`, the `tools` and every message before it. The release puts a freshly generated summary in position 0 on every request past the threshold, so each kept turn's thinking now sits on a history it was not produced against. The preserved-thinking docs list "summarise or drop old turns on the client and keep recent turns" as invalid, and for accounts created on or after 31 August 2026 the API enforces the check by default and returns a 400 `invalid_request_error`. This account was created in September 2026. The old compaction replayed nothing earlier than the summary, which is why it never failed.

The evidence fits and also leaves gaps. Sessions under the threshold never summarise, so they never fail; sessions past it fail on every request, because the summary is regenerated each time; tool-free sessions fail because the check applies to any replayed thinking, not to tool pairs. What is missing is the message body, which names the first failing block (for example `messages.1.content.0`) and usually what changed, and the `request_id` for support. Collect both by logging the body for 400s. Then replay one failing request with the `thinking-binding-controls-2026-08-01` beta header and `prefix_mismatch_behavior: "drop_block"`, and read `input_transformations`: `prefix_binding_mismatch` entries confirm the diagnosis.

Without that evidence, ship the change that is right under either reading. Freeze the summary: generate it once when the threshold is crossed and store it in the session, strip the thinking blocks from the kept turns at that moment (removing blocks is valid; the model loses that reasoning), and append from then on. That keeps the six verbatim turns users asked for. The alternative is to go back to whole-session compaction, which replays nothing and is the smallest change, but brings back the complaint that caused the release. `drop_block` stops the errors today, at the price of regenerating the dropped reasoning as output tokens on every request; the docs call it a stopgap, and it hides the edit instead of removing it.

Why the wrong picks are tempting, ranked by what they will cost later:

- **The date in the system prompt** is a real defect and the next incident. The `system` prompt is part of every block's prefix, so a session that crosses midnight fails on its first request after it, short or long, and the prompt cache misses on the first request after it. Move the date into the newest user turn.
- **Regenerating the summary on every request** is also a cost defect: one extra model call per request for the rest of the session. The frozen summary fixes it.
- **The orphaned tool result** is the defect this function would have if it cut by message or by token count. `split_turns` cuts only at user turns that are not tool results, so it cannot strand one; and tool-free sessions fail too.
- **Two user messages in a row** looks wrong to anyone used to strict alternation, but the Messages API combines consecutive same-role turns into one.

## Follow-ups

- *Suppose the account had been created in July 2026. Would this release have failed?* Not with a 400. Older accounts run the check only when a request sets `prefix_mismatch_behavior`; otherwise the stale blocks pass, so the edit would sit in the code until a migration to a new account or an opt-in surfaced it. Run CI with `"error"` so it surfaces there.
- *The frozen summary is written once and the session runs another two hours. When do you summarise again, and what happens to the thinking blocks produced since the last summary?*
- *How do you test this before the next release?* Record real sessions past the threshold, replay them through `build_request`, and assert that from one request to the next the `messages` array only grows at the end and `system` and `tools` stay byte-identical.

## Common mistakes

- Reading "400" as "the request is too big" and lowering the threshold; the failing requests are 18,000 to 31,000 tokens, and every one of them fails, which a size limit would not do.
- Turning on `drop_block` in production and closing the incident.
- Fixing the summary and leaving the date in the system prompt.
- Diagnosing without asking for the error body that the logger dropped.
