## Question

<Callout kind="interview" label="The format Sierra published in April 2026; the 30-minute plan is this problem's">
Plan: you define a product in your own domain while the interviewers ask questions. Build: two hours alone, with any AI tools and frameworks you like; you may change scope. Review: you demo it, then the panel reviews the code (data model, abstractions, extensibility), the path to production and how you used AI.
</Callout>

Run it. Give yourself 30 minutes to plan, with the plan written down, then two hours to build in your own environment with whatever AI tools you use at work. If no product in your own domain comes to mind, use this one: an on-call engineer pastes an incident's timeline and log excerpts, and gets a draft postmortem in which every factual sentence cites the line it came from.

Before the build, set one number and keep it: how many of the 120 minutes you reserve for checking the build and preparing the demo. After the build, answer these review questions out loud or in writing, then open the checklist.

1. Walk through the data model. Which entity changes first when a second team, with its own data, uses this?
2. Which abstraction did you introduce, and which one did you decide not to introduce?
3. What stands between this and production? Give the first three items in order.
4. Show something an AI tool produced that you rejected or rewrote, and say why.
5. What did you cut during the build, and when did you decide?

## Answer

A worked answer for the fallback brief. Your own product will differ; the decisions should not.

<Depth>
<Fragment slot="short">
<p>I planned one flow: paste a timeline, get a draft whose factual sentences each cite a log line, and see the sentences that could not be cited. I kept real persistence for incidents and drafts, stubbed auth, and reserved 30 minutes for five checked-in cases and a rehearsal. The production gaps, in order, are a citation check against real incidents, tenancy and retention for log data, and a cost and latency budget per draft.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The plan's decision: depth or breadth.</strong> Two plans are defensible. A vertical slice builds one flow with real storage and the model call at its centre: the review has a real data model and real failure handling to inspect, and the cost is a demo with one flow. A broad demo mocks storage and fixes the model's outputs to show four flows (paste, edit, share, export): the demo looks like a product, and the cost is that the code review finds scaffolding where the data model and abstractions should be, which is the part the panel said it reviews. I took the slice, because the review questions are about code, not screens.</p>
<p><strong>Data model.</strong> <code>Incident</code> (id, title, created_at), <code>Evidence</code> (incident_id, line number, source, text: the pasted lines, immutable), <code>Draft</code> (incident_id, version, model, prompt hash, created_at) and <code>Claim</code> (draft_id, sentence, evidence_ids). Claims are rows rather than markup inside the draft so the check in the next section can run over them. For a second team, <code>Incident</code> gets a tenant id first, and every query starts filtering by it; Evidence holds log text, so it also needs a retention rule.</p>
<p><strong>Abstractions.</strong> One interface around the model: <code>draft(evidence) -&gt; list[Claim]</code>, with structured output and three handled failures (malformed output retried once, a refusal shown as such, a timeout that keeps the user's paste). I did not introduce a provider abstraction for switching models: one provider is in use, and a second would be designed when it exists.</p>
<p><strong>Checking the build.</strong> I reserved 30 of the 120 minutes, set before the build. Five checked-in incidents with known causes run in one command, and each run reports the share of sentences with a citation and whether every cited line exists in the evidence. That is not an eval; it is the minimum that lets me say the demo is not one lucky run. Under ten minutes is the reservation I would call unreasonable: it leaves no time to start the build once from a clean state, so the first clean start is the demo itself.</p>
<p><strong>Path to production, in order.</strong> First, a citation check against real incidents, labelled by the people who wrote those postmortems, because a draft that cites lines that do not say what the sentence claims is worse than no draft. Second, tenancy, retention and access to log data. Third, a cost and latency budget per draft. The first one blocks launch.</p>
<p><strong>AI use.</strong> I delegated the web form, the storage layer and the test runner, and wrote the prompt and the claim schema myself. I rejected an agent's version of the citation check that matched sentences to lines by string overlap, because it passed any sentence that repeated a log line's words without checking what the sentence asserted.</p>
<p><strong>The failure mode of this answer.</strong> The vertical slice puts all its weight on one flow. If the model call misbehaves during the demo, there is nothing else to show; the five cases and their recorded results are the fallback, so they are part of the demo, not a footnote.</p>
</Fragment>

<li><em>You kept 30 of 120 minutes for checking and the demo shows one flow. Another candidate showed four flows. Which part of your checking would you cut to show a second flow, and what risk do you accept out loud?</em></li>
<li><em>Halfway through the build, what would make you switch from the slice to the broad demo?</em> The model call not producing usable claims by the one-hour mark: then the slice has nothing at its centre, and showing the product shape with fixed outputs, labelled as fixed, is the better use of the second hour.</li>
<li><em>The panel points at a function the agent wrote and asks you to change its contract while they watch. What do you do first?</em></li>

The same idea runs in other loops at other lengths, which changes the plan. One candidate's report of a Cursor onsite describes eight to nine hours on an add-on to an existing service, ending in a 30-minute presentation where every choice was questioned; a day allows an existing codebase and a real integration. Cognition's CEO describes a build of a few hours aimed at what the candidate thinks is worth building. Two hours, as at Sierra, leaves room for one flow done properly or several done as a facade, and the plan is where that choice is made.

## Follow-ups

- *Your data model has four tables. Which would you drop if the build had been one hour?*
- *Two panelists disagree about your path-to-production order: one says tenancy blocks launch, not the citation check. How do you settle it without deferring to rank?* Ask which failure costs more to undo: a leaked log line across tenants is a disclosure, a wrong citation is a correctable draft.
- *What would the five checked-in cases have to show for you to call the feature ready for a pilot with one team?*

## Common mistakes

- A plan that lists features instead of naming the one flow the demo will show.
- Spending the build on auth, settings and screens the brief said could be skipped.
- An AI-use answer of "I used it for boilerplate" with no example of a rejected suggestion.
- Calling the five checked-in cases an eval.
- A path to production that lists everything and orders nothing.
