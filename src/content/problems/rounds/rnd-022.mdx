    import heapq, math, random

    # Ties at the k-th logit: keep exactly k, the lowest token ids first. The support size is then what the request asked
    # for, which keeps the cost of the sampling step bounded; the price is a bias toward low ids among exact ties.
    SORT_ABOVE = 0.1   # above k = 10% of the vocabulary a full sort beat heap selection when this was measured


    def _top_ids(logits, k):
        V = len(logits)
        if k >= V:
            return range(V)
        if k <= SORT_ABOVE * V:
            # heapq.nlargest(n, it, key) is documented as sorted(it, key=key, reverse=True)[:n], so ties keep low ids.
            return heapq.nlargest(k, range(V), key=logits.__getitem__)
        return sorted(range(V), key=logits.__getitem__, reverse=True)[:k]


    def top_k_sample(logits, k, temperature, rng):
        if k is not None and k < 1:
            raise ValueError("k must be at least 1, or None for no truncation")
        if temperature < 0:
            raise ValueError("temperature must be 0 or more")
        V = len(logits)
        if temperature == 0:
            return max(range(V), key=logits.__getitem__)          # the first id among equal maxima
        ids = _top_ids(logits, V if k is None else k)
        m = max(logits[i] for i in ids)
        # Subtract the max before exp: a logit of 1e4 at temperature 0.01 would otherwise overflow.
        weights = [math.exp((logits[i] - m) / temperature) for i in ids]
        target = rng.random() * sum(weights)
        acc, last = 0.0, None
        for i, w in zip(ids, weights):
            if w > 0:
                acc, last = acc + w, i
                if target < acc:
                    return i
        return last          # target fell on the rounding edge of the running sum


    def sample_batch(rows, ks, temperatures, rngs):
        # Each row draws only from its own request's generator, so batch composition cannot change its token.
        return [top_k_sample(r, k, t, g) for r, k, t, g in zip(rows, ks, temperatures, rngs)]

## Question

<Callout kind="interview" label="Coding round">
"Decode with top-k sampling, no PyTorch, no NumPy. Then the serving version: a batch of requests, each with its own k and its own temperature."
</Callout>

Write two functions:

- `top_k_sample(logits, k, temperature, rng)`: one token id, sampled from softmax(logits / temperature) over the k largest logits. `k` of `None`, or at least the vocabulary size, means no truncation. Temperature 0 is greedy and deterministic. Raise `ValueError` for k below 1 or a negative temperature. `rng` is a `random.Random` that belongs to the request.
- `sample_batch(rows, ks, temperatures, rngs)`: one token id per row. A row's token must not depend on which other rows share the batch or in what order, and the logits must not be modified.

The hidden tests are statistical: thousands of seeded draws per case, compared with the exact distribution over the kept tokens with a tolerance of five standard errors, including logits of 1e4 at temperature 0.01. They also replay a batch of six requests over twenty steps, then a subset of three in a different order with the same seeds, and compare tokens row by row.

One decision is yours: ties at the k-th logit. Keep exactly k tokens, or keep every token tied with the k-th. Both are accepted; the comment at the top says which and why.

The visible tests end with 32 rows over a 128,000-token vocabulary, k from 1 to 64 and two rows with no truncation, sampled within 1.5 seconds.

## Answer

**Select, then normalise only what you kept.** Dividing by a positive temperature preserves order, so the k largest logits are the same before and after it; the reference selects first and exponentiates only the kept k. It subtracts the largest kept logit before `exp`, which is what keeps a logit of 1e4 at temperature 0.01 (an exponent of 1e6) finite. Sampling is one uniform draw against the running sum of the k weights, O(k); a Gumbel-max sampler that draws k times is equally correct and the statistical tests accept it.

**Selection is where the time goes.** On one 128,000-logit row, measured in CPython 3.12.6 when this problem was checked: `heapq.nlargest(50, range(V), key=row.__getitem__)` took 4.4 ms, a full `sorted` on the same key took 28.7 ms, and sorting (value, index) tuples took 96 ms. The heap's advantage shrinks as k grows: at k = 8,000 it took 16.0 ms against 30.1 ms for the sort, and at k = 32,000 it took 59.3 ms against 27.6 ms. The crossover is a quantity you choose; the reference switches to a full sort above k = 10% of the vocabulary, which sits between those two measurements, and the heapq docs give the same direction without a number. Over the visible test's batch the reference took 0.18 s, a full key sort for every row 0.74 s, and the tuple sort 2.8 s.

**Batch invariance is a reproducibility contract.** A shared generator advanced row by row gives each request a random stream that depends on how many requests sit above it in the batch. In a server that rebuilds the batch every step, a seeded request then returns different tokens on every replay, and a bug report with a seed cannot be reproduced. The reference draws each row from the generator its request owns; the hidden tests replay a subset of rows in a different order and require identical tokens.

**The tie decision.** Keeping exactly k makes the support size what the request asked for and bounds the cost of the step; `heapq.nlargest` is documented as equivalent to a stable sort, so the reference keeps the lowest token ids among exact ties, a bias towards low ids where ties occur. Keeping every tied token is unbiased among them but makes k a soft limit: a row whose logits are all equal keeps the whole vocabulary. Exact ties are rare in float logits and common after an earlier transform writes the same value into many positions, which is the question hint 3 asks. The reference keeps exactly k.

**The constraint conflict, and where the reference fails.** Per-row selection respects each row's k but does a separate selection per row. A tensor library prefers one selection at the batch's largest k followed by a per-row mask: one batched operation instead of B, wasted work for rows with small k, and a single row with no truncation pushes the whole batch to a full sort. The reference's own weak spot is the no-truncation row: it exponentiates the whole vocabulary every step, about 9 ms per 128,000-logit row in the same measurement, so a batch where most requests disable top-k is dominated by those rows.

## Follow-ups

- *What changes to run this inside an inference engine?* Logits stay on the GPU; selection runs as a batched top-k kernel and sampling as a kernel with per-request generator state; the logits are cast to float32 before the softmax so small probabilities do not underflow in bf16; and the order of logit processors (penalties, temperature, top-k, top-p) is fixed and documented, because the last two do not commute.
- *Pushback: per-request generators stop you from using one batched random-number kernel, and your profile shows the sampling step slower with them. Product wants reproducible seeds. What do you give up, and what do you write down?* Keep per-request streams for requests that send a seed and use the batched kernel for the rest; write down that unseeded requests are not reproducible and that the two paths need their own distribution tests.
- *Reversal: what evidence would make you switch the tie policy to keeping every tied token?* Production traces where the k-th position is tied often, typically after quantised logits or a processor that writes a constant into many entries, together with a measurable skew towards low token ids in what gets sampled.
- *Two staff engineers disagree: one wants top-p computed over the top-k renormalised distribution, the other over the full distribution. How do you decide without deciding by rank?* Write both, sample each on the same seeded prompts, and compare the kept-set sizes and the eval scores; then document the order in the API, since users tune p against whichever one ships.

## Common mistakes

- Exponentiating logits / temperature without subtracting the maximum.
- Sampling every row from one shared generator.
- Sorting the whole vocabulary of (value, index) tuples for every row.
- Treating temperature 0 as a division by zero instead of greedy decoding.
- Renormalising over the full vocabulary after masking, so dropped tokens still take probability mass.
