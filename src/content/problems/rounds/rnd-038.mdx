    import time
    from collections import deque


    class StoreUnavailable(Exception):
        """The shared store did not answer in time."""


    class MemoryStore:
        """Stands in for the store every server shares (Redis, in the round).

        read and write are separate round trips. atomic(key, fn) is one round trip that runs
        fn(value) -> (new_value, result) on the store with nothing else in between, the way a
        Lua script runs in Redis; it stores new_value and returns result. While down is True,
        every call raises StoreUnavailable. calls counts round trips.
        """

        def __init__(self):
            self.data, self.calls, self.down = {}, 0, False

        def _trip(self):
            if self.down:
                raise StoreUnavailable("store timed out")
            self.calls += 1

        def read(self, key):
            self._trip()
            return self.data.get(key)

        def write(self, key, value):
            self._trip()
            self.data[key] = value

        def atomic(self, key, fn):
            self._trip()
            value, result = fn(self.data.get(key))
            self.data[key] = value
            return result


    class AssistantDraft:
        """The assistant's answer to "a sliding-window rate limiter shared by every server, with an injectable clock".
        Kept as it was written: the visible tests run your suite against it."""

        def __init__(self, store, limit, window, clock=time.time):
            self.store, self.limit, self.window, self.clock = store, limit, window, clock

        def allow(self, key):
            now = self.clock()
            log = self.store.read(key) or []
            log = [t for t in log if t > time.time() - self.window]
            if len(log) < self.limit:
                log.append(now)
                self.store.write(key, log)
                return True
            return False


    class SlidingWindowLimiter:
        """Exact sliding-window log. The whole check-and-record runs inside one atomic call, so servers sharing the
        store cannot interleave between the count and the append. When the store is down it denies: the downstream
        falls over above its limit, and no server can see what the others admitted."""

        def __init__(self, store, limit, window, clock=time.time):
            self.store, self.limit, self.window, self.clock = store, limit, window, clock

        def _decide(self, log, now):
            # A request admitted at t counts for requests in [t, t + window), so drop t once t + window <= now.
            if log is None:
                log = deque()
            while log and log[0] + self.window <= now:
                log.popleft()
            if len(log) < self.limit:
                log.append(now)
                return log, True
            return log, False

        def allow(self, key):
            now = self.clock()
            try:
                return self.store.atomic(key, lambda log: self._decide(log, now))
            except StoreUnavailable:
                return False


    def boundary_suite(make):
        def at(limit, window):
            now = [0.0]
            return make(limit, window, lambda: now[0]), now

        # The limit is exact: limit admitted, the next one denied, at one instant.
        lim, now = at(3, 10)
        assert [lim.allow("a") for _ in range(4)] == [True, True, True, False], "limit, then deny"

        # Keys are independent.
        assert lim.allow("b"), "another key has its own window"

        # The edge: a request admitted at t stops counting at exactly t + window, not after.
        lim, now = at(1, 10)
        assert lim.allow("a")
        now[0] = 9.5
        assert not lim.allow("a"), "still inside the window"
        now[0] = 10.0
        assert lim.allow("a"), "the request from t=0 stops counting at t=10"

        # Denied requests do not count: a client retrying while limited is admitted once the window moves.
        lim, now = at(2, 10)
        assert lim.allow("a") and lim.allow("a")
        for t in (1, 2, 3, 4, 5, 6, 7, 8, 9):
            now[0] = float(t)
            assert not lim.allow("a")
        now[0] = 10.0
        assert lim.allow("a"), "denied retries must not extend the window"

        # The window slides; it does not reset at fixed boundaries.
        lim, now = at(2, 10)
        assert lim.allow("a")
        now[0] = 9.0
        assert lim.allow("a")
        now[0] = 10.0
        assert lim.allow("a"), "t=0 has left the window"
        now[0] = 10.5
        assert not lim.allow("a"), "t=9 and t=10 are both inside [0.5, 10.5]"

## Question

<Callout kind="interview" label="The round, as a candidate report describes it">
A candidate report on PracHub describes a Snowflake onsite round for a machine learning engineer: design a rate limiter, have an AI assistant write it while you direct, review its output for races and time-handling errors, show how you test it, then defend how it works across servers and what it does when its store is down. This version starts after the assistant has answered.
</Callout>

You asked for "a sliding-window rate limiter shared by every server, with an injectable clock". The assistant produced `AssistantDraft` (in the editor, with the store it talks to) and these two tests, which pass:

```python
def test_limits_burst():
    lim = AssistantDraft(MemoryStore(), limit=5, window=1.0)
    assert [lim.allow("u") for _ in range(6)] == [True] * 5 + [False]

def test_window_slides():
    lim = AssistantDraft(MemoryStore(), limit=1, window=0.05)
    assert lim.allow("u") and not lim.allow("u")
    time.sleep(0.06)
    assert lim.allow("u")
```

The limiter protects a downstream service that falls over when it receives more than its limit. The store stands in for Redis: `read` and `write` are separate round trips, and `atomic(key, fn)` is one round trip that runs `fn` on the store with nothing in between, the way a Lua script runs.

**The rules.** A request admitted at time t counts against requests at times in `[t, t + window)`. A request is admitted when fewer than `limit` admitted requests count against it. Denied requests are not recorded. Keys are independent. Every server holds its own `SlidingWindowLimiter` on the same store, and together they never admit more than `limit` in any window for one key; in this problem the servers' clocks agree.

**Write two things.**

1. `boundary_suite(make)`. `make(limit, window, clock)` returns a limiter on a fresh, healthy store. The suite raises `AssertionError` when the limiter breaks the rules and returns `None` when it keeps them. It is run against the assistant's draft, against correct limiters whose internals differ from yours, and against several limiters that are wrong in ways an assistant plausibly writes.
2. `SlidingWindowLimiter`, the fix, with the draft's constructor and `allow(key)`.

**Operating constraints.** While the store is healthy, a request costs one round trip. When the store raises `StoreUnavailable`, `allow` returns a boolean and never raises, and no single server admits more than `limit` for one key in any window; what it does inside that bound is your decision. One hot key can carry a limit of 50,000 per window, and the hidden tests time 200,000 requests against it.

<p>The draft has three defects, and its tests can see none of them. It prunes with `time.time()` while recording `self.clock()`, so with any injected clock other than wall time it prunes everything and never limits. It reads the log, decides, then writes it back in a second round trip, so two servers can both read four entries against a limit of five and both admit. And it rebuilds the whole log on every request, which is linear in the limit. The fix runs the prune, the count and the append inside one atomic call over a deque. When the store is down I would deny for this downstream, because it falls over above its limit; a per-server local log is the defensible alternative when rejecting everyone costs more than a bounded overload.</p>

<p><strong>Atomicity.</strong> A separate read and write leave a gap in which another server's request runs. In Redis this is one `EVALSHA` of a script that trims a sorted set by score, counts it and adds the new member; Redis runs the script with all other server activity blocked, which is also its cost on a hot key.</p>

### The suite

The suite is graded the way a reviewer grades a test: it must pass every correct limiter and fail every wrong one. The cases that kill the plausible mutants are boundary cases on a clock you control:

- the limit is exact: `limit` admitted at one instant, the next denied;
- the edge: a request admitted at t still counts at `t + window - 0.5` and stops counting at exactly `t + window`. This kills a prune written with `>=` where the rules need `>`;
- a client that keeps retrying while limited is admitted once the window moves. This kills a limiter that records denied requests, which locks a retrying client out for as long as it retries;
- two requests at 0 and 9 with a limit of 2 and a window of 10: at 10 one is admitted, at 10.5 one is denied. This kills a fixed window that resets at 10 and admits twice the limit across the boundary;
- a second key has its own window.

Use clock values whose arithmetic is exact in binary floating point, such as halves and whole seconds. A suite that probes `t + 0.1 + 0.2` against `t + 0.3` tests the floating point, not the limiter, and fails correct implementations that compute the edge in a different order.

### The fix

`SlidingWindowLimiter` keeps one `deque` of admitted timestamps per key. `_decide` pops from the left while `log[0] + window <= now`, admits and appends if fewer than `limit` remain, and returns the log and the decision; `allow` passes `_decide` to `store.atomic`. Each timestamp is appended once and popped once, so the cost per request is amortised constant. On the laptop that checked this problem, CPython 3.12 ran the hidden test's 200,000 requests in about 0.1 s; a version that rebuilds the list on every request had processed 36,608 requests after 30 s.

The quantity left to you is what a server admits during an outage. The reference denies. The other reasonable choices are a local log per key at `limit / N` for a fleet of N servers the limiter knows about, which keeps the fleet near the global limit if the load balancer spreads each key's traffic evenly, or at the full limit, which the tests allow but which lets the fleet admit N times the limit. The full limit per server is reasonable only when N is small and the downstream tolerates N times its limit for the length of an outage.

The constraint conflict is protection against availability. Denying keeps the downstream inside its limit and makes a store outage a full outage of the limited endpoint. Local decisions keep traffic flowing and spend the downstream's headroom to do it.

**What the reference gets wrong.** It denies only after the store call fails, and a store that hangs fails only at the client's timeout, so during an outage every request waits out that timeout before it is denied. Put a circuit breaker in front of the store call, so that after a few consecutive failures requests are denied at once and the store is probed occasionally. If you choose local logs instead, bound them with an LRU cap: an outage under traffic keyed by client IP otherwise grows one log per IP, and an evicted key comes back with an empty log. Either way, the exact log costs memory proportional to the limit for every active key: 50,000 timestamps for the hot key here. Cloudflare's two-counter estimate costs two integers per key; Cloudflare measured it wrongly allowing or limiting 0.003% of 400 million requests from 270,000 sources, a vendor's own number from 2017. If the downstream's limit is a capacity cliff rather than a fairness target, that error is the cost of the cheaper structure.

## Follow-ups

- *What do denied clients receive?* A 429 with `Retry-After` set to when the oldest counted request leaves the window, which RFC 6585 permits but does not require, plus jitter so the clients denied together do not return together.
- *The limit changes per tier without a deploy.* Read the limit inside the script from a config key, and decide whether a lowered limit applies to requests already counted.
- *A client sends from several API keys.* Which key you limit on is a product decision the code cannot make; state it.
- *Run it on Redis.* One Lua script per request: `ZREMRANGEBYSCORE key -inf now-window`, `ZCARD`, then `ZADD` and `PEXPIRE` if admitted, with the key passed in `KEYS` so it routes in a cluster. Read the time with `TIME` inside the script, so a server whose clock is ahead cannot prune entries the others still count. Make sorted-set members unique (timestamp plus a request id), or two requests in the same millisecond collapse into one entry.

## Common mistakes

- Trusting the assistant's tests because they pass. Both use the default clock, which hides the clock bug, and neither runs two servers.
- Wrapping `allow` in a `threading.Lock`. That serialises one process; the race is between servers.
- Fixing the race with a lock key in the store (set if absent, read, write, delete): four round trips per request and a lock that outlives a crashed server.
- Failing open during an outage for a downstream that falls over above its limit.
- Writing boundary tests with `time.sleep` and the wall clock, which are slow and flaky and cannot hit the edge exactly.
