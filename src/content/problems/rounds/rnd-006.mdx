    import codecs
    import json
    import re

    # Largest event (one line plus the data already buffered for its event) the parser will hold, in characters.
    # Big enough for any event this client expects with headroom; small enough that a server that never sends
    # a newline costs a bounded amount of memory before the stream is refused.
    MAX_EVENT_CHARS = 16_000_000

    _EOL = re.compile(r"\r\n|\r|\n")


    class StreamParser:
        def __init__(self, max_event_chars=MAX_EVENT_CHARS):
            self.max_event_chars = max_event_chars
            self._decoder = codecs.getincrementaldecoder("utf-8-sig")()   # holds split characters; drops one leading BOM
            self._parts = []          # pieces of the current, unterminated line
            self._line_chars = 0
            self._skip_lf = False     # the last chunk ended in \r; a \n that starts the next one belongs to it
            self._event = ""
            self._data = []
            self._data_chars = 0

        def feed(self, chunk):
            text = self._decoder.decode(chunk)
            if self._skip_lf and text:
                if text[0] == "\n":
                    text = text[1:]
                self._skip_lf = False
            events, pos = [], 0
            for m in _EOL.finditer(text):           # only the new text is scanned: linear in the stream length
                self._parts.append(text[pos:m.start()])
                line = "".join(self._parts)
                self._parts, self._line_chars = [], 0
                self._line(line, events)
                pos = m.end()
            if text.endswith("\r"):
                self._skip_lf = True
            rest = text[pos:]
            if rest:
                self._parts.append(rest)
                self._line_chars += len(rest)
            if self._line_chars + self._data_chars > self.max_event_chars:
                raise ValueError(f"event larger than {self.max_event_chars} characters")
            return events

        def _line(self, line, events):
            if line == "":
                if self._data:
                    events.append((self._event or "message", "\n".join(self._data)))
                self._event, self._data, self._data_chars = "", [], 0
                return
            if line.startswith(":"):
                return
            field, _, value = line.partition(":")
            if value.startswith(" "):
                value = value[1:]
            if field == "event":
                self._event = value
            elif field == "data":
                self._data.append(value)
                self._data_chars += len(value) + 1


    def assemble(events):
        """Fold parsed events into the response: text, complete tool calls, stop reason, output tokens and any error."""
        text, partial, tools = {}, {}, {}
        out = {"text": "", "tool_calls": [], "stop_reason": None, "output_tokens": 0, "error": None}
        for _, data in events:
            msg = json.loads(data)
            kind = msg.get("type")
            if kind == "error":
                out["error"] = {"type": msg["error"].get("type"), "message": msg["error"].get("message")}
                break                                   # nothing after an error event belongs to this response
            if kind == "content_block_start":
                block, i = msg["content_block"], msg["index"]
                if block.get("type") == "text":
                    text[i] = [block.get("text", "")]
                elif block.get("type") == "tool_use":
                    tools[i] = {"id": block["id"], "name": block["name"]}
                    partial[i] = []
            elif kind == "content_block_delta":
                delta, i = msg["delta"], msg["index"]
                if delta.get("type") == "text_delta" and i in text:
                    text[i].append(delta["text"])
                elif delta.get("type") == "input_json_delta" and i in partial:
                    partial[i].append(delta["partial_json"])
            elif kind == "content_block_stop":
                i = msg["index"]
                if i in partial:
                    raw = "".join(partial.pop(i))
                    tools[i]["input"] = json.loads(raw) if raw else {}
            elif kind == "message_delta":
                if msg.get("delta", {}).get("stop_reason"):
                    out["stop_reason"] = msg["delta"]["stop_reason"]
                if "usage" in msg:
                    out["output_tokens"] = msg["usage"]["output_tokens"]   # cumulative: the last value wins
        out["text"] = "".join("".join(text[i]) for i in sorted(text))
        out["tool_calls"] = [tools[i] for i in sorted(tools) if "input" in tools[i]]   # unfinished calls are never returned
        return out

## Question

<Callout kind="interview" label="The prompt">
"Write the client-side parser for a model's streaming response. The network hands you bytes in whatever chunks it likes. Give me the text, the tool calls and any error."
</Callout>

The stream follows the Claude Messages streaming format over server-sent events. It opens with `message_start`. Each content block then sends a `content_block_start`, one or more `content_block_delta` events and a `content_block_stop`, and the stream ends with `message_delta` and `message_stop`. `ping` events can appear anywhere, an `error` event can arrive after the HTTP 200, and new event types may be added at any time.

Write two things:

1. **`StreamParser.feed(chunk)`.** It takes raw bytes and returns every event this chunk completes, as `(event_name, data)`. Apply the event-stream rules:
   - Lines end in CRLF, LF or a lone CR, and a blank line dispatches the event.
   - A line starting with a colon is a comment.
   - One space after the field's colon is removed, `data` lines join with a newline, and the default event name is `message`.
   - An event with no data is not dispatched, and one leading UTF-8 byte order mark is dropped.

   Chunks can split anywhere, including inside a multi-byte character and between a `\r` and its `\n`.
2. **`assemble(events)`.** It returns `text` (the text blocks only, in block order), `tool_calls` (the `id`, `name` and parsed `input` of each tool-use block that reached its `content_block_stop`), `stop_reason`, `output_tokens` and `error` (the first error event's `type` and `message`; nothing after it counts). When an error cuts the response short, keeping or dropping the text received so far is your call. The hidden tests check only that what you return is a prefix of the full text. A tool call that never reached its stop event is never returned.

Choose `MAX_EVENT_CHARS`, the most characters one event may hold before `feed` raises `ValueError`, and say why. The visible tests feed one 2 MB event in 64-byte chunks with a 3-second budget.

## Answer

The reference parser has three layers.

- **Decoding.** An incremental `utf-8-sig` decoder from `codecs` turns bytes into text. With `final=False` it holds back a partial multi-byte sequence until the next chunk completes it, and the `-sig` variant drops one leading byte order mark even when the mark itself is split.
- **Line splitting.** Each decoded chunk is split with a regular expression for `\r\n`, `\r` or `\n`, and only the new text is scanned. The unterminated tail goes into a list of parts that are joined only when its line ends. A chunk that ends in `\r` is treated as a line end at once, and a flag swallows the `\n` if the next chunk starts with one. The parser never waits, and never sees CRLF as two lines.
- **Fields.** A line becomes an `event` or `data` field, a comment is skipped, and a blank line dispatches.

The scan-only-new-text rule is what the 2 MB test measures. A parser that appends each chunk to one string and searches it from the start copies and rescans the growing buffer on every one of the roughly 31,000 chunks. In this harness's local CPython 3.12.6, that design took 7.0 seconds on the test's event, and the reference took 0.06 seconds.

`assemble` dispatches on the types it knows and ignores the rest. The rest includes `ping`, `thinking_delta` and `signature_delta`, plus the `future_event` the tests add as a stand-in for an event type the API adds later. It accumulates `partial_json` strings per block and parses them once, at `content_block_stop`. The docs give this sequence; the fragments are not valid JSON on their own. It takes the last `message_delta` usage value, because the docs state the counts there are cumulative. It stops at the first `error` event.

The limit is a decision with two kinds of cost:

- **Too low.** A valid response becomes an error the user sees.
- **Too high, or absent.** A server or proxy that never sends a newline holds as much memory as it likes.

Tool input arrives as many small `input_json_delta` events, so tool calls do not set the bound. The large single events are the ones that carry whole objects, such as `message_start` or a block's start. Set the limit from the largest event in your own logs with headroom. The reference uses 16,000,000 characters. Values from a few MB to a few tens of MB are reasonable. `None`, and anything in kilobytes, are not.

The latency-against-correctness conflict sits in `assemble`. Text can be shown as each delta arrives, because a prefix of text is still correct text. Tool input cannot be acted on until the block stops, because a prefix of JSON arguments can parse to the wrong call.

**How the recommended answer fails.** The limit counts characters, not bytes. A stream of four-byte characters can hold four times as many bytes as the limit suggests, so cap bytes instead if memory is the reason for the limit. When the limit trips, the whole stream is abandoned, including any complete text already received. A client that wants to keep that text has to catch the error and assemble the events it already has.

## Follow-ups

- *What changes to run this in a real client?* Read the response body with an async byte iterator and feed each chunk. Put an idle timeout on reads, separate from the total timeout, so a stalled stream is noticed. In most code, the SDK's stream helpers and final-message accumulation do this for you; the hand-written parser earns its place when you proxy or log raw events.
- *The connection drops in the middle of a text block. How do you resume?* For Claude 4.6 and later, the streaming docs describe sending the partial response back in a user message with an instruction to continue, because assistant prefill returns a 400 on those models. The docs also say tool-use and thinking blocks cannot be partially recovered, so a cut-off tool call is requested again, never completed by guesswork.
- *Pushback: the product wants tool arguments shown as they stream. Do you parse partial JSON?* Show it through a tolerant partial parser for display only, and still parse strictly at `content_block_stop` before anything executes. Write that rule next to the code that executes tools.
- *An `overloaded_error` arrives after 600 tokens of text. Do you retry?* It is the streaming form of a 529. Retry the request with backoff, keep the partial text visible but marked incomplete, and do not count the failed attempt's tokens as the answer.

## Common mistakes

- Decoding each chunk with `bytes.decode()`, which fails or corrupts a character split across chunks.
- Treating a trailing `\r` as a line end and then counting the next chunk's `\n` as a second, empty line.
- Rescanning the whole buffer on every chunk.
- Concatenating thinking deltas into the answer text.
- Parsing each `partial_json` fragment on its own.
- Summing `output_tokens` across `message_delta` events.
- Returning a tool call whose block never stopped.
- Raising on an unknown event type.
