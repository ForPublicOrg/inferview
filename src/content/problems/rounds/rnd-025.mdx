    import json


    class KV:
        def __init__(self):
            self.data = {}      # the visible state, including writes of open transactions
            self.counts = {}    # value -> number of keys holding it in the visible state
            self.undo = []      # one dict per open transaction: key -> (existed, old value) before its first write

        def _apply(self, key, exists, value):
            if key in self.data:
                old = self.data[key]
                self.counts[old] -= 1
                if not self.counts[old]:
                    del self.counts[old]
                del self.data[key]
            if exists:
                self.data[key] = value
                self.counts[value] = self.counts.get(value, 0) + 1

        def _remember(self, key):
            if self.undo and key not in self.undo[-1]:
                self.undo[-1][key] = (key in self.data, self.data.get(key))

        def set(self, key, value):
            self._remember(key)
            self._apply(key, True, value)

        def get(self, key):
            return self.data[key]              # KeyError when missing; None is a value

        def delete(self, key):
            if key not in self.data:
                return False
            self._remember(key)
            self._apply(key, False, None)
            return True

        def keys(self):
            return sorted(self.data)

        def begin(self):
            self.undo.append({})

        def commit(self):
            if not self.undo:
                raise RuntimeError("no open transaction")
            log = self.undo.pop()
            if self.undo:                       # an inner commit folds into its parent
                parent = self.undo[-1]
                for key, before in log.items():
                    parent.setdefault(key, before)

        def rollback(self):
            if not self.undo:
                raise RuntimeError("no open transaction")
            for key, (existed, old) in self.undo.pop().items():
                self._apply(key, existed, old)

        def count(self, value):
            return self.counts.get(value, 0)

        def _committed(self):
            state = dict(self.data)
            for log in reversed(self.undo):     # innermost first; outer logs hold older values and win
                for key, (existed, old) in log.items():
                    if existed:
                        state[key] = old
                    else:
                        state.pop(key, None)
            return state

        def dump(self):
            return json.dumps({"format": "kv/1", "items": list(self._committed().items())})

        @classmethod
        def load(cls, text):
            doc = json.loads(text)              # a truncated dump is not valid JSON: ValueError
            if not isinstance(doc, dict) or doc.get("format") != "kv/1" or not isinstance(doc.get("items"), list):
                raise ValueError("not a kv/1 dump")
            store = cls()
            for pair in doc["items"]:
                if not (isinstance(pair, list) and len(pair) == 2 and isinstance(pair[0], str)):
                    raise ValueError("bad item in dump")
                if pair[0] in store.data:
                    raise ValueError("duplicate key in dump")
                store._apply(pair[0], True, pair[1])
            return store

## Question

<Callout kind="interview" label="Coding round">
"Write a key-value store with transactions. Requirements will come in stages."
</Callout>

Three stages grow one `KV` class. Each stage runs its visible tests and then hidden tests against your whole program, and the next brief appears only after the current stage passes. Plan for about 50 minutes.

Two choices are yours:

- How a transaction remembers what it changed. One option is an undo log of old values, applied on rollback. The other is a write set per level, layered over the committed data and merged on commit.
- The dump format, provided it round-trips every key and value and refuses a truncated dump.

One number is also yours. Measure how long your `dump()` takes for 100,000 keys, then state the largest store you would dump synchronously on a request path whose latency budget is 50 ms (a scenario budget), and what you would do above it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask how deep transactions nest in practice, and how many keys a typical transaction touches.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask who reads a dump, and whether it should ever contain uncommitted writes.</p></details>

## Answer

The reference solution uses an undo log.

- **Data.** `data` holds the visible state, including the writes of open transactions. `counts` maps each value to the number of keys holding it.
- **The undo stack.** `undo` is a stack with one dict per open transaction. Each dict maps a key to `(existed, old_value)` and is filled on the first write to that key at that level.
- **`rollback`.** It pops the top dict and writes each old value back through the same helper that maintains `counts`, so `count` stays correct with no extra work.
- **`commit`.** It folds the top dict into its parent with `setdefault`. Where both levels touched a key, the parent's entry is the older value, so it wins.
- **`dump`.** It copies `data`, applies the undo dicts from the innermost outward to recover the committed state, and writes JSON: a format tag plus a list of `[key, value]` pairs. JSON keeps the difference between `1`, `"1"` and `None`, escapes every character a key can hold, and fails to parse when any byte is cut from the end of an object, so a truncated dump raises `ValueError` on load instead of yielding a partial store.

Stage 2's test fails the obvious designs:

- **A snapshot on `begin`.** Copying 100,000 keys 5,000 times is 500 million key copies.
- **A `count` that scans.** Twenty thousand scans of 100,000 keys is 2 billion comparisons.

The undo log makes rollback cost what the transaction touched, and `counts` makes `count` a dict lookup.

Stage 3 is where the two transaction designs separate, and both are defensible:

- **Undo log (the reference).** Reads and `count` are `O(1)`. A dump inside open transactions must copy the store and reverse the logs, which costs `O(n + changes)` time and a second copy of the data in memory.
- **Write set per level.** The committed data is never touched before the outermost commit, so a dump serialises it directly. In exchange, every read walks the levels from the top, `O(depth)`, and `count` needs a per-level delta that has to be merged on commit and dropped on rollback.

Choose by the read-to-dump ratio and the nesting depth you measured, not by taste.

The dump budget is where speed and safety conflict. In this harness's local CPython 3.12.6, the reference dumped 100,000 keys in 0.041 seconds (2.6 MB of JSON) and loaded them in 0.107 seconds. At that rate, a 50 ms budget allows a synchronous dump of roughly 50 ÷ 41 × 100,000, about 120,000 keys. Any answer near that figure, with a stated margin for Pyodide or a slower host, is reasonable. Dumping millions of keys on the request path is unreasonable. Above the limit, take the dump off the request path: copy the committed state under the lock (or freeze it with copy-on-write), release the lock, then serialise.

**How the recommended answer fails.** A long transaction that rewrites every key holds a full second copy of the store in its undo dict, and a dump taken inside it then makes a third. Memory peaks at the moment an operator is most likely to ask for a dump. A JSON dump is also only as durable as the file write. If you write it in place and the process dies, the result is a truncated file that load refuses. That is better than loading half the data, but it is still a lost dump, unless the dump goes to a temporary file that is renamed over the old one once it is complete.

## Follow-ups

- *What changes to make this durable and multi-client?* Make the dump a checkpoint and log every committed write between checkpoints, so recovery loads the checkpoint and replays the log. Each client session gets its own transaction stack, and two sessions writing the same key need isolation rules, such as locks held to commit or optimistic version checks.
- *Pushback: your dump doubles memory while transactions are open, and the box has no headroom. Which do you give up: dumps during open transactions, or `O(1)` reads?* If dumps are rare and reads are hot, refuse a dump while a transaction is open, or queue it until the outermost commit, and write that limit into the API contract. If dumps are frequent, move to write sets and accept the `O(depth)` reads.
- *Reversal: two senior engineers disagree, one for undo logs and one for write sets. How do you decide without deciding by rank?* Instrument the read rate, the dump rate, the typical nesting depth and the keys touched per transaction on real traffic, then run both designs on a replay of that trace and compare latency and peak memory.

## Common mistakes

- Snapshotting the whole store on `begin`.
- On an inner commit, discarding the inner undo entries instead of folding them into the parent.
- Letting a parent's older undo entry be overwritten by the child's newer one during that fold.
- A `count` that scans every key.
- A line-based dump format (`key=value` lines) that breaks on keys containing `=` or a newline.
- Loading whatever parses from a truncated dump.
- Dumping uncommitted writes.
