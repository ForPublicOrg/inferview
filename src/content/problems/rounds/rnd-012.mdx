## Question

<Callout kind="interview" label="AI-assisted round">
You asked the built-in assistant for "an LRU cache with a per-entry TTL, O(1) operations, injectable clock". It produced the class and two tests below, and the tests pass. Before you move on, the interviewer asks whether you would ship it.
</Callout>

```python
from collections import OrderedDict

class TTLCache:
    def __init__(self, capacity, ttl, clock):
        self.capacity, self.ttl, self.clock = capacity, ttl, clock
        self.data = OrderedDict()              # key -> (value, expires_at)

    def get(self, key):
        item = self.data.get(key)
        if item is None:
            return None
        value, expires_at = item
        if self.clock() >= expires_at:
            del self.data[key]
            return None
        return value

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = (value, self.clock() + self.ttl)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)

def test_evicts_oldest():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); c.put("b", 2); c.put("c", 3)
    assert c.get("a") is None and c.get("c") == 3

def test_expires():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); t[0] = 60
    assert c.get("a") is None
```

The interviewer adds what happened when a version of this ran in front of a configuration service: capacity 10,000, TTL 300 seconds. `config:global` is written once at startup and read on every request, and at peak the logs show it fetched from the service several times a minute. The logs do not say whether each miss found the key absent or expired.

Which defect explains the refetching?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the misses on `config:global` over one peak hour, split into "key absent" and "key present but expired".</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how many distinct keys the cache sees at peak between two writes of `config:global`, and compare that with the capacity.</p></details>

## Answer

`get` never marks a hit as used. Recency changes only on `put`, so the cache evicts in write order, not in use order. `config:global` was written once at startup, every later write lands behind it, and once 10,000 other keys have been written it reaches the front of the `OrderedDict` and is the entry `popitem(last=False)` removes. It is refetched, written again, and starts the same walk to the front. The fix is one line in `get`, after the expiry check: `self.data.move_to_end(key)`.

The evidence is incomplete, and the answer depends on what is missing. A miss that found the key absent means eviction; a miss that found it expired means the TTL. Several fetches a minute against a 300-second TTL already rules out expiry as the main cause, but the split from Hint 1 settles it. Without the split, I would still ship the fix, because a read that does not count as a use breaks the specification whatever the logs say, and I would add the miss reason as a label on the cache's miss counter so the next question takes one query.

The assistant's tests passed because they encode the same assumption as the code: both write, then read. A test written from the specification, that a key just read is not the next to go, fails at once:

```python
def test_read_refreshes_recency():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); c.put("b", 2)
    c.get("a")                 # a is now the most recently used
    c.put("c", 3)              # so b is evicted, not a
    assert c.get("a") == 1 and c.get("b") is None
```

**Ranking the rest.** Expired entries that linger until read are the second defect and a real one: they hold memory and capacity, so the cache evicts live entries earlier than its size suggests. Fix it by popping expired entries before evicting a live one, which needs a structure ordered by expiry, because this one is ordered by recency. The `popitem(last=False)` direction is correct and a common misreading. The `>=` comparison is a boundary decision: state that an entry is gone at exactly its expiry and test it at that instant.

## Follow-ups

- *Fix the lingering expired entries without making `put` scan the cache.* A heap of expiry times with lazy deletion, or a sweep from the front that is exact only when every entry has the same TTL.
- *Make it thread-safe.* One lock around `get` and `put`. After the fix `get` mutates the order, so it needs the lock too, which the original code made easy to forget.
- *The service team asks for `config:global` to be pinned so it is never evicted.* What does pinning cost when the next pinned key is added by someone else, and what would you do instead?

## Common mistakes

- Treating the assistant's passing tests as evidence. Tests written in the same pass as the code share its assumptions.
- Rewriting the class instead of finding the one missing line, which costs time and adds new risk.
- Adding `move_to_end` calls to `put`, where recency already updates, instead of to `get`.
- Picking the lingering-entries defect because it is real, without checking whether it can produce the specific symptom.
