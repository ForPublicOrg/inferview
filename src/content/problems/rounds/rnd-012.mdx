    correct: true
    why: Recency only changes on put. The hot key was written once, long ago, so it sits at the front of the OrderedDict and is the first thing popitem(last=False) removes.
  - text: "`popitem(last=False)` removes the newest entry instead of the oldest"
    correct: false
    why: With last=False, popitem removes from the front, the least recently moved end. That is the right end for LRU; the bug is that reads never move anything.
  - text: Expired entries are never removed unless they are read, so they fill the cache
    correct: false

    correct: false

## Question

<Callout kind="interview" label="AI-assisted round">
You asked the built-in assistant for "an LRU cache with a per-entry TTL, O(1) operations, injectable clock". It produced the code and two tests below. The tests pass. Before you move on, the interviewer asks: "Would you ship this?"
</Callout>

```python
from collections import OrderedDict

class TTLCache:
    def __init__(self, capacity, ttl, clock):
        self.capacity, self.ttl, self.clock = capacity, ttl, clock
        self.data = OrderedDict()              # key -> (value, expires_at)

    def get(self, key):
        item = self.data.get(key)
        if item is None:
            return None
        value, expires_at = item
        if self.clock() >= expires_at:
            del self.data[key]
            return None
        return value

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = (value, self.clock() + self.ttl)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)

def test_evicts_oldest():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); c.put("b", 2); c.put("c", 3)
    assert c.get("a") is None and c.get("c") == 3

def test_expires():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); t[0] = 60
    assert c.get("a") is None
```

In production this cache sits in front of a configuration service. The key `config:global` is read on every request and written once at startup, yet the logs show it being refetched over and over. Pick the root cause.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Both tests only ever write and then read. Neither reads a key and then writes others.</p></details>
<details class="hint"><summary>Hint 2</summary><p>In an LRU cache, what operations count as a use?</p></details>

## Answer

`get` never marks the key as used. Recency in this class changes only on `put`, so the cache is first-in, first-out by write time, not least recently used. `config:global` was written once at startup, so it drifts to the front of the `OrderedDict` and is the first entry `popitem(last=False)` removes once newer keys arrive. The fix is one line in `get`, after the expiry check: `self.data.move_to_end(key)`.

The more useful lesson is why the assistant's tests passed. Both tests encode the same assumption as the code: they write, then read. A test written from the specification ("a key that is read is not the next to go") fails at once:

```python
def test_read_refreshes_recency():
    t = [0]
    c = TTLCache(2, ttl=60, clock=lambda: t[0])
    c.put("a", 1); c.put("b", 2)
    c.get("a")                 # a is now the most recently used
    c.put("c", 3)              # so b should be evicted, not a
    assert c.get("a") == 1 and c.get("b") is None
```

In the room, say the habit out loud: you write or at least read one test from the spec before trusting generated code, and you treat tests the assistant wrote alongside its code as the assistant's opinion, not as evidence. Canva's published list of what its AI-assisted interviewers look for includes whether you can find and fix issues in AI-generated code; this is that skill.

Why the other picks are tempting. `popitem(last=False)` reads backwards to many people, but it pops from the front, which is correct. Expired entries lingering until read is a real weakness (memory and capacity held by dead entries) and makes a good follow-up, but it cannot explain a live, hot key disappearing. The `>=` boundary is a choice to state, not a bug.

## Follow-ups

- *Fix the lingering expired entries.* On `put`, pop expired entries from the front before evicting a live one, or run a periodic sweep. Note that entries are ordered by recency, not expiry, so a sweep from the front is a heuristic unless every entry has the same TTL.
- *Is `get` still O(1)?* Yes; `move_to_end` is O(1) on an `OrderedDict`.
- *Make it thread-safe.* Wrap `get` and `put` in one lock. `get` now mutates order, so it needs the lock too, which is easy to forget.
- *How would you prompt the assistant differently?* Give it the failing test first and ask for the smallest change that makes it pass, then read the diff.

## Common mistakes

- Accepting the assistant's tests as proof because they pass.
- Rewriting the whole class instead of finding the one-line defect, which costs time and adds new risk in a timed round.
- Fixing `put` (adding more `move_to_end` calls) instead of `get`.
- Not saying what you are checking while you read, so the interviewer sees silence instead of verification.
