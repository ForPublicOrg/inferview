## Question

<Callout kind="interview" label="Behavioural">
"Tell me about a task you took away from an agent and gave back to ordinary code."
</Callout>

Answer from a system you shipped. If you need a case, use this one (scenario). Your team built an agent that reconciles supplier invoices for accounts payable: it reads the invoice, finds the purchase order and the goods receipt, decides whether they match, posts an adjustment or routes an exception to a clerk, and emails the supplier. Each run takes about eight tool decisions. On a replay of 500 past invoices, 79 percent came out right end to end. In production it posted the same adjustment twice on four invoices after a timeout, and accepted a 2 percent price difference on some invoices while rejecting it on others. Month-end close is five working days away, the auditors want every posting decision explained, and the accounts payable team is four clerks.

Say what you took away from the agent, what you left with the model, the number that decided it, what it cost, and what went wrong with the code version.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Request the replay results per decision, not only end to end: which of the eight steps fail, and how often.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask the finance lead which of the agent's decisions already have a written policy.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the clerks how many exceptions a day they can work before close slips.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>On the scenario: I moved the decisions that finance already had a written rule for (the three-way match with its price tolerance, the posting, and the routing) into code, and left the model two jobs: reading fields from messy invoices, checked against the purchase order totals, and writing the explanation a clerk reads on an exception. The arithmetic decided it: eight steps at about 97 percent each compound to 0.97⁸ ≈ 78 percent, which is what the replay showed; three model steps at the same rate give 0.97³ ≈ 91 percent, and the code steps are checked by tests. Duplicate postings ended with an idempotency key on the posting. The cost was two engineers for three weeks and an exception queue that grew until we wrote rules for the new cases.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What the replay said.</strong> End to end, 79 percent of 500. Per step, the failures were not spread evenly: matching and the tolerance decision failed most, and those were the steps with a written policy. The model was making a judgement call where finance had already made it. Multiplying per-step rates assumes independent failures, which is rough, but 0.97 to the eighth power is 0.78 and the replay said 0.79, so the model of compounding error was close enough to argue from.</p>
<p><strong>The threshold I chose.</strong> A step stays with the model if it needs reading or writing language, its replay accuracy is at least 95 percent, and its errors are caught by a check downstream before money moves. A step goes to code if a written rule exists for it, whatever the model's accuracy. A different threshold, 90 or 99 percent, is defensible if it comes with the downstream check; a threshold with no check is a hope. METR's measurements track the length of task agents complete at 50 percent success, and that length has doubled about every seven months; at the success rate a ledger needs, the horizon is shorter, and a trend in that number is no reason to leave a posting decision with the model today.</p>
<p><strong>The two defensible answers.</strong> Keep the agent and add a verifier model that checks each posting before it lands. It handles new suppliers and odd invoices without engineering work, at the cost of an extra model call per posting, more latency, and a posting decision the auditors cannot trace to a rule. Or move the policy into code. It is deterministic and explainable to the auditors, at the cost of three engineer-weeks before close and a rule set that does not know about a supplier format it has not seen. The engineer who built the agent argued for the first, and was right that the code version would be brittle; the audit requirement decided it, because "the model judged the 2 percent difference acceptable this time" is not an explanation an auditor accepts.</p>
<p><strong>Where the code version failed.</strong> Anything the rules did not cover went to the clerks as an exception. In the first close the exception queue roughly doubled, and four clerks could not clear it in five days. The fix was to group exceptions by cause each week, write rules for the largest groups, and let the model draft a proposed rule for a group that a finance lead approves. The failure mode remains: a new kind of invoice lands in the queue until someone writes its rule, and the queue is the measure to watch.</p>
<p><strong>Written down.</strong> The step-by-step split with the threshold and the replay numbers, the audit requirement as the deciding constraint, the exception-queue limit that triggers a rules review, and what the model is still allowed to decide.</p>
</Fragment>

## Follow-ups

- *Pushback: the code version took three engineer-weeks and doubled the clerks' queue for a month. The verifier model would have taken three days. Which cost would you accept in writing now?* The verifier for a fixed period, if close cannot slip, with a written note that postings in that period are not explainable by rule and a date by which the code version replaces it.
- *Reversal: what would you need to see to give the matching decision back to a model?* The matching policy changing faster than engineers can encode it, with a model that matches the written policy on a replay of real invoices at the rate the auditors accept and logs which rule it applied for each decision.
- *Two staff engineers disagree: one wants everything deterministic, the other wants an agent with stronger checks. How do you decide without deciding by rank?* Run both on the same replay of a month's invoices, measure correct postings, exceptions per day and engineer-days, and let the clerks' capacity and the audit requirement pick.
- *Next quarter you add a second ERP system with different purchase order formats. Where does the model come back in?* In mapping the new formats to the existing schema, behind the same validation against totals, while matching and posting stay in code.

## Common mistakes

- A story where the agent was replaced because it was "unreliable", with no per-step numbers.
- Moving everything to code, including the steps that need reading language.
- Leaving out what the code version broke and who absorbed it.
- No deciding constraint: the audit, the deadline or the team's capacity.
- Describing a replacement someone else decided on.
