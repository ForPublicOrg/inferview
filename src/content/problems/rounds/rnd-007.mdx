            raise NotImplementedError

            """Spend `cost` and return True if it fits now; otherwise spend nothing and return False."""
            raise NotImplementedError

  solution: |
    class TokenBucket:
        def __init__(self, capacity, per_second, now=0.0):
            self.capacity = capacity
            self.per_second = per_second
            self.tokens = capacity
            self.last = now

        def _refill(self, now):
            if now > self.last:
                self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.per_second)
                self.last = now

        def wait_time(self, cost, now):
            if cost > self.capacity:
                raise ValueError("cost exceeds bucket capacity")
            self._refill(now)
            if self.tokens >= cost:
                return 0.0
            return (cost - self.tokens) / self.per_second

        def take(self, cost, now):
            if self.wait_time(cost, now) == 0.0:
                self.tokens -= cost
                return True
            return False

    def itpm_cost(usage):
        return usage.get("input_tokens", 0) + usage.get("cache_creation_input_tokens", 0)

    class Limiter:
        def __init__(self, rpm, itpm, now=0.0):
            self.requests = TokenBucket(rpm, rpm / 60, now)
            self.input = TokenBucket(itpm, itpm / 60, now)

        def try_admit(self, usage, now):
            cost = itpm_cost(usage)
            wait = max(self.requests.wait_time(1, now), self.input.wait_time(cost, now))
            if wait == 0.0:
                self.requests.take(1, now)     # both checks passed, so both spends succeed
                self.input.take(cost, now)
            return wait

## Question

<Callout kind="interview" label="The prompt">
"Write a rate limiter for calls to an LLM API. Requests are not equal: one costs 200 tokens, the next costs 50,000. Then tell me how you'd make it work across many workers."
</Callout>

Model it on how the Claude API documents its own limits. Capacity refills continuously rather than resetting at the top of each minute, there are separate limits for requests per minute (RPM) and input tokens per minute (ITPM), and on most models tokens read from the prompt cache do not count toward ITPM.

Write a `TokenBucket`, the function that says which input tokens count, and a `Limiter` that admits a request only when both buckets can pay. Time is passed in as a number of seconds so the tests can use a fake clock; no `time.sleep` anywhere.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Refill lazily: when you are asked anything, add (now minus last) times the rate, capped at capacity.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Check both buckets before spending from either. Spending from one and then failing on the other leaks capacity.</p></details>
<details class="hint"><summary>Hint 3</summary><p>The usage dict has three input fields. Only one of them is excluded from the count.</p></details>

## Answer

The bucket stores a balance and the time it last refilled. Every call first refills: the balance grows by elapsed seconds times the rate, up to capacity. `wait_time` is then simple arithmetic: zero if the balance covers the cost, otherwise the shortfall divided by the rate. With capacity 10 at 2 per second, after spending 8 the balance is 2, and a request for 5 waits (5 − 2) / 2 = 1.5 seconds.

`itpm_cost` follows the Claude docs: `input_tokens` plus `cache_creation_input_tokens` count toward ITPM, and `cache_read_input_tokens` do not, on most models. The docs' own example shows why that matters: with a 2,000,000 ITPM limit and an 80 percent cache hit rate, you can push 10,000,000 total input tokens a minute, because only the uncached fifth is charged.

The `Limiter` holds two buckets, each with capacity equal to its per-minute limit and a refill rate of limit / 60 per second. `try_admit` asks both for their wait and takes the larger. Only when both are zero does it spend from both. The test that checks `requests.tokens == 59` after a refused request is there because the natural first draft calls `take` on the request bucket, then discovers the token bucket is short, and has already spent a request slot.

## Follow-ups

- *What about output tokens?* You do not know them until the response ends. Charge an estimate at admission and settle the difference afterwards, or keep a separate output bucket you charge as tokens stream. The Claude docs note that `max_tokens` does not count toward the output limit, so charging `max_tokens` up front is more conservative than the server.
- *Your limiter allows 60 RPM but you still get 429s.* The docs say a 60 RPM limit may be enforced as 1 request per second, so a burst of 60 at once can be rejected. Size the client bucket's capacity well below the per-minute number.
- *Make it distributed.* Keep the balance and last-refill time in Redis and do the refill-and-spend in one Lua script so it is atomic, or give each of N workers a bucket with 1/N of the limit and accept some waste. Either way, still honour the server's `retry-after`, because the server is the source of truth.
- *Per-tenant limits?* One bucket pair per tenant, plus the global pair, and admit only when all four can pay.

## Common mistakes

- A fixed window that resets every minute, which lets a full minute's quota through just before the boundary and another just after it, twice the limit in a few seconds.
- Charging one unit per request, so a single 50,000-token request slips through a limiter that thinks it is idle.
- Counting cache reads against ITPM, which throttles exactly the cheap, cached traffic you want more of.
- Calling `time.time()` and `time.sleep()` inside the limiter, which makes it untestable without real waiting.
