    from collections import deque
    from urllib.parse import urldefrag, urljoin

    RETRY_STATUS = {429, 500, 502, 503, 504}


    def _resolve(base, link):
        return urldefrag(urljoin(base, link))[0]


    def _fetch(service, url, grants, sleep, max_attempts, base_delay, max_delay):
        """The response, or None after max_attempts transient failures. Never sleeps after the last attempt."""
        for attempt in range(max_attempts):
            try:
                resp = service.get(url, dict(grants))
            except (TimeoutError, ConnectionError):
                resp = None
            if resp is not None and resp.status not in RETRY_STATUS:
                return resp
            if attempt == max_attempts - 1:
                return None
            delay = min(max_delay, base_delay * 2 ** attempt)
            if resp is not None and resp.status == 429:
                try:
                    delay = float(resp.headers["retry-after"])
                except (KeyError, ValueError):
                    pass
            sleep(delay)
        return None


    def escape(service, start, sleep=lambda seconds: None, max_attempts=4, base_delay=0.5, max_delay=8.0):
        """Return the list of URLs from start to the exit, or None when no exit is reachable."""
        start = _resolve(start, start)
        host = urlsplit(start).netloc
        parent = {start: None}            # doubles as the visited set
        queue = deque([start])            # breadth first: no recursion, and the path found is shortest
        grants = {}                       # header name -> value, collected while crawling
        blocked = {}                      # grant name -> rooms that answered 401 for it
        while queue:
            url = queue.popleft()
            resp = _fetch(service, url, grants, sleep, max_attempts, base_delay, max_delay)
            if resp is None:
                continue
            grant = resp.headers.get("x-grant", "")
            name, sep, value = grant.partition("=")
            if sep and name not in grants:
                grants[name] = value
                queue.extend(blocked.pop(name, []))    # each locked room is retried once per new grant
            if resp.status == 401:
                try:
                    need = json.loads(resp.body)["requires"]
                except (ValueError, KeyError, TypeError):
                    continue
                if need not in grants:
                    blocked.setdefault(need, []).append(url)
                continue
            if resp.status != 200:
                continue
            try:
                doc = json.loads(resp.body)
            except ValueError:
                continue
            if not isinstance(doc, dict):
                continue
            if doc.get("exit") is True:
                path = []
                while url is not None:
                    path.append(url)
                    url = parent[url]
                return path[::-1]
            for link in doc.get("links", []):
                if not isinstance(link, str):
                    continue
                nxt = _resolve(url, link)
                if urlsplit(nxt).netloc != host or nxt in parent:
                    continue
                parent[nxt] = url
                queue.append(nxt)
        return None

## Question

<Callout kind="interview" label="Coding round">
"There's a maze behind an HTTP service. Start at this URL and keep requesting until you reach the exit. Then we'll make it harder."
</Callout>

Three stages grow one `escape` function against `MazeService`, a deterministic stand-in for the network that sits at the top of the starter. Read its docstring the way you would read an unfamiliar API's reference. Each stage runs its visible tests and then hidden tests, which build their own mazes, and the next brief appears only after the current stage passes. Plan for about an hour.

Three choices are yours:

- The traversal order.
- The backoff schedule, within a cap of 8 seconds per wait.
- Which collected keys you send with which request.

One number is also yours: your base delay. From it, work out the longest your crawler can spend waiting on a single room that never recovers.

## Answer

The reference is a breadth-first crawl with a queue.

- **Visited set.** `parent` maps each discovered URL to the URL it was found from. It is the visited set and the path record at once.
- **Links.** Each link is resolved with `urljoin` against the current URL, and its fragment is dropped with `urldefrag`. A resolved URL on another host is never queued.
- **Fetching.** `_fetch` makes up to `max_attempts` requests for one room. It treats a 429, 500, 502, 503, 504, `TimeoutError` or `ConnectionError` as transient, sleeps `retry-after` when a 429 carries it and `min(8, 0.5 × 2^attempt)` otherwise, and never sleeps after the last attempt. Anything else goes back to the crawl loop. There a 404, a body that is not JSON, or a room that never recovered is a dead end, and the crawl goes on.
- **Keys.** An `x-grant` header adds a key to `grants`, which is sent on every later request to the maze's host. A 401 parks the room under the key it names, and the room goes back on the queue once, when that key arrives.

The stages expose the usual shortcuts:

- **Stage 1: recursion and a list.** A recursive depth-first crawl dies in the 5,000-room corridor, because CPython 3.12.6 reports a recursion limit of 1000 in this harness. A visited list instead of a set turns the 50,000-room maze into up to 50,000 × 50,000 / 2 = 1.25 billion comparisons.
- **Stage 2: retrying the unretryable.** A crawler that retries every failure sends four requests for a 404 or a malformed body that will never change.
- **Stage 3: a permanent visited mark.** A crawler that marks a 401 room as visited for good never gets past the first locked door. One that re-polls locked rooms in a loop never stops.

Two decisions have more than one defensible answer:

- **Traversal order.** Breadth-first returns the shortest walk and keeps memory proportional to the frontier. Depth-first with an explicit stack can reach a deep exit with fewer requests, and its path comes from the stack, but the walk it returns can be long. The tests accept either, because they check that the walk follows real links.
- **Which keys to send.** Sending every collected key on every request saves a 401 round trip per locked room, but it hands every key to every room. Sending a key only with the retry of the room that asked for it costs one extra request per locked room and follows least privilege. The reference sends all of them to keep the code short. A service where rooms belong to different owners should send only the named key.

The waiting budget is where finishing fast conflicts with the service's load. With a base of 0.5 seconds, doubling and four attempts, a room that never recovers costs 0.5 + 1 + 2 = 3.5 seconds of sleep. A base of 0.1 to 1 second is reasonable for a service you share with others. A base of zero hammers a service that is already failing. Each 429's `retry-after` overrides the formula, because the server knows its own load.

**How the recommended answer fails.**

- **Visited-set memory.** The visited set grows with every URL discovered. At 50,000 rooms that is nothing, but on the open web it dominates memory, and swapping in a probabilistic filter means occasionally skipping a page that was never fetched.
- **URL identity.** Deduplication is only as good as normalisation. `/r/1` and `/r/1?ref=nav` can be one room on a real server, but they are two strings to this code, so both would be fetched. A link to `HTTPS://MAZE.TEST/r/1` would be refused as another host, because the host comparison is case-sensitive.
- **Host changes.** The Python docs warn that `urljoin` is not safe with an attacker-controlled URL, because an absolute or scheme-relative link replaces the host. That is why the host check runs on the resolved URL, after the join; the hidden tests include a `//evil.test/...` link.

## Follow-ups

- *What changes to run this against a real service?* Concurrency first. A candidate report of an Anthropic phone screen describes the interviewer accepting a thread pool as the direction for a crawler, after a single-threaded version passed. Bound in-flight requests per host, set separate connect and read timeouts, and decide whether to follow redirects. A redirect to another host is a second way for keys to leave the maze, so check whether your HTTP client forwards custom headers when a redirect crosses hosts.
- *Pushback: security says one leaked key opens every door, and sending all keys everywhere doubles the blast radius. Product says the extra 401s double latency on locked paths. Which do you ship, and what goes in the risk note?* Send only the named key, accept the extra request per locked room, and write down the measured latency cost. If the latency is unacceptable, scope each key to the rooms the grant names, and get the service owner to publish that mapping instead of guessing.
- *Reversal: what would make you switch from breadth-first to depth-first?* Measurements showing exits that are reliably deep, with frontier memory, not request count, as the limit. Breadth-first's shortest-path property is then worth less than depth-first's memory, which grows with depth instead of width.

## Common mistakes

- Recursing through rooms.
- Keeping visited URLs in a list.
- Deduplicating before resolving relative links and dropping fragments.
- Checking the host before `urljoin` instead of after it.
- Retrying 404s and malformed bodies.
- Sleeping after the final attempt.
- Marking a locked room as permanently visited, or polling it in a loop.
