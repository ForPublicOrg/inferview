## Question

<Callout kind="interview" label="The prompt">
"You serve Llama 3 70B in bf16. After weights and activations you have 40 GiB of GPU memory left for the KV cache. How many requests can you hold at the full 8,192-token context? Show the arithmetic."
</Callout>

The published configuration, from Table 3 of the Llama 3 paper: 80 layers, model dimension 8,192, 64 attention heads, 8 key/value heads. bf16 is 2 bytes per number. Assume every request uses the whole 8,192 tokens and the cache is allocated per token with no fragmentation.

Give the number of concurrent sequences.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Head dimension is model dimension divided by attention heads.</p></details>
<details class="hint"><summary>Hint 2</summary><p>The cache stores keys and values, so there is a factor of 2, and only the key/value heads count.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Work out bytes per token first, then per sequence, then divide the budget.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>About 16. Each token costs 2 (K and V) × 80 layers × 8 KV heads × 128 dims × 2 bytes = 327,680 bytes, which is 320 KiB. A full 8,192-token sequence is 2.5 GiB, and 40 GiB holds 16 of them. If I had used all 64 heads instead of the 8 KV heads it would be 2, which is why grouped-query attention matters for serving.</p>
</Fragment>
<Fragment slot="long">
<p>Head dimension: 8,192 / 64 = 128. The cache holds one key vector and one value vector per layer, per KV head, per token. Llama 3 70B uses grouped-query attention with 8 KV heads shared by 64 query heads, so the per-token cost is 2 × 80 × 8 × 128 = 163,840 numbers, times 2 bytes = 327,680 bytes.</p>
<p>Per sequence: 327,680 × 8,192 = 2,684,354,560 bytes, exactly 2.5 GiB. Budget: 40 GiB / 2.5 GiB = 16 sequences. If the budget were 40 GB (decimal) instead of GiB, the answer is 14.9, so 14; the accepted band covers both readings.</p>
<p>What this means operationally. Concurrency at full context is 16, but most requests do not use 8,192 tokens. A server that reserves the maximum per request wastes most of that memory; paged allocation hands out cache in blocks as tokens arrive, so the real concurrency depends on the length distribution, not the maximum. Quantising the cache to 8 bits doubles the count to 32, at some quality risk you would measure.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What if this were full multi-head attention?</em> 64 KV heads instead of 8: 8 times more memory per token, 2 sequences.</li>
<li><em>How does tensor parallelism across 4 GPUs change it?</em> The KV heads split across GPUs, so each GPU holds a quarter of each sequence's cache; the per-GPU budget is what you divide.</li>
<li><em>How big can this get?</em> Pope et al. report a 3 TB KV cache for PaLM 540B at batch 512 and context 2,048, three times the size of the model's parameters.</li>
</ul>
</Fragment>
</Depth>

The formula to remember:

```text
bytes = 2 × layers × kv_heads × head_dim × bytes_per_value × tokens × sequences
      = 2 × 80 × 8 × 128 × 2 × 8,192 × 16
      = 42,949,672,960 bytes = 40 GiB
```

## Follow-ups

- *Your p50 request is 1,500 tokens and p99 is 8,192. How many can you serve?* Compute with the distribution, not the maximum, and keep headroom for the long tail; this is the argument for paged KV allocation.
- *The context window grows to 128K tokens. What breaks first?* One full-length sequence is 327,680 × 131,072 bytes = 40 GiB, the whole budget. Long context trades concurrency directly.
- *Where else does memory go?* Weights (70B parameters at 2 bytes is about 140 GB before any cache), activations, and the framework's own reserve. The 40 GiB in the question is what was left after those.

## Common mistakes

- Forgetting the factor of 2 for keys and values, which doubles the answer to 32.
- Using the 64 query heads instead of the 8 KV heads, which gives 2.
- Mixing GB and GiB without saying which; the difference here is 16 against 14.9.
- Computing per-token memory and forgetting to multiply by sequence length, so the answer comes out in the thousands.
