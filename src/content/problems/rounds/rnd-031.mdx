## Question

<Callout kind="interview" label="The shape of a take-home one candidate reported at Sierra, via aced.io (about two years before the report); the features and time box are this problem's">
"Build a customer service agent for a fake outdoors company. Pick two of the five features. If this were running in production, what metrics would you track and what dashboards would you want?"
</Callout>

The company sells tents, sleeping bags and climbing gear online. The five features:

1. Order status and shipment tracking.
2. Returns and exchanges under the company's policy: 30 days from delivery, unused items only, final-sale items excluded (scenario policy).
3. Gear recommendations for a described trip.
4. Warranty claims with a photo of the damage.
5. Handoff to a human agent with a summary of the conversation.

You have four hours. The reviewers will run your code before the discussion. Choose two features, build them against a mock order store, and write the production section: the metrics, the dashboards, and the alerts. Then open the checklist.

One quantity is yours to set and defend: the window after which a conversation with no further contact from the customer counts as resolved.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask whether the reviewers will try to break the agent, and if so, with what kinds of requests.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which of the five features produces the most contacts today, and which costs the most when it goes wrong.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how a customer reaches the company again after a conversation ends, and whether that contact can be linked to the first.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Returns and handoff. Returns is the feature where the agent changes something, so it needs a policy check in code and produces the metric that matters most, wrong writes; handoff is the agent's way out, and its rate and quality are half of the production story. Resolution is counted only after a seven-day window with no re-contact, the reliability number is pass^k on scripted conversations, and every alert names who acts on it.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The choice.</strong> Two pairs are defensible. Order status with recommendations demos well and is safe to build in four hours, since nothing is written; its cost is that the production section has little to measure beyond lookups, and recommendations bring their own risk, advice about gear for conditions the agent cannot see. Returns with handoff is harder: a write action that has to respect a policy, and a path out when it should not decide. Its cost is a plainer demo. I take returns and handoff, because the question about production is a question about what can go wrong, and only a feature that writes can go wrong in a way that costs money. Warranty claims would add image handling and the same write risk at twice the build time.</p>
<p><strong>The build.</strong> Tools: <code>get_order(order_id)</code>, <code>check_return(order_id, item_id)</code> and <code>create_return(order_id, item_id, reason)</code> against a mock store the reviewer can reset, plus <code>handoff(summary, facts)</code>. <code>create_return</code> calls the same policy function as <code>check_return</code> and refuses anything outside it, whatever the conversation said, so a customer who argues the agent into agreeing still gets a refusal from the code and a handoff offer. A scripted set of conversations, including customers pushing for an out-of-policy return, runs five trials each and reports pass^1 and pass^5 from the final state of the mock store.</p>
<p><strong>Why pass^k.</strong> A support agent is used by many customers on the same kind of request, so what matters is whether it gets the request right every time. tau-bench proposed pass^k for this and reports gpt-4o below 25% on pass^8 in its retail domain. The arithmetic shows why: a task the agent passes half the time, with independent trials, passes all eight with probability 0.5<sup>8</sup>, about 0.4%.</p>
<p><strong>Metrics and dashboards.</strong> Outcome: resolution rate, where resolved means no further contact within seven days; re-contact rate; handoff rate, and the share of handoffs where the human did not have to ask again for facts the agent had collected; satisfaction from a sampled survey. Correctness: returns created per day, returns blocked by the policy check (counts, with examples), and a weekly human review of a sample of created returns. Health: tool error rate per tool, latency per turn at p50 and p95, cost per conversation. Alerts: blocked returns in an hour above three times the median hour of the past week (my threshold, to be tuned on the first month) pages the on-call engineer, since it means either an attack or a prompt change that makes the agent try more; created returns that fail the weekly review go to the support lead.</p>
<p><strong>The window.</strong> Seven days is my choice: long enough for a return label to be used and a refund to arrive, so a customer whose return went wrong has had time to come back. A window of a few hours is the unreasonable choice; it counts as resolved every conversation that fails after the customer hangs up. A window of thirty days makes the metric so slow that a bad release is visible only weeks later. What it costs: the headline number lags a release by a week, so the release dashboard watches re-contact within one day as an early signal.</p>
<p><strong>The metric I leave off.</strong> Containment, the share of conversations without a handoff, on its own. It rises when the agent refuses to hand off, which is the failure the handoff feature exists to prevent.</p>
<p><strong>Where this fails.</strong> The policy check makes wrong returns rare, so the dashboard shows few problems on the write path. The cost moves into handoffs: customers with legitimate edge cases (a gift, a delayed delivery) are handed off rather than served, and the handoff rate is where that shows up. If it climbs after launch, the policy in code is stricter than the policy the support team applies, and the fix is a policy change agreed with them, not a looser prompt.</p>
</Fragment>
<Fragment slot="followups">

<li><em>What would you need to see in the first month to add order status as the third feature?</em> A handoff rate whose summaries show order-status questions as a large share of what the humans handle.</li>
<li><em>The support lead wants containment as the headline metric because that is how the contract is priced. How do you agree on the dashboard without deciding by who owns the contract?</em></li>
</ul>

## Follow-ups

- *A customer pastes text that reads like an instruction to approve the return. Where in your build does that get stopped, and how would the dashboard show attempts?*
- *The company opens a store in Germany with a different return policy. What changes in the code, the scripted conversations and the dashboard?*
- *Your pass^5 on the out-of-policy scripts is 1.0 and pass^1 on legitimate returns is 0.7. Which do you fix first?*

## Common mistakes

- Choosing the two features that demo best and then having nothing to put on a production dashboard.
- Putting the return policy only in the prompt.
- Counting a conversation as resolved when it ends.
- Reporting one run of each scripted conversation as the agent's reliability.
- A dashboard of averages with no alert that says who acts and what they do.
