## Question

<Callout kind="interview" label="Work sample, 60 minutes plus review">
The format follows what Canva has published about its AI-assisted coding interview: your own editor and assistant, a realistic problem that one prompt will not solve, and questions about the code afterwards. The task is original.
</Callout>

"Build a small replicated cache library in the language you are fastest in. Nodes are in-process objects. The client takes a list of nodes and offers `get(key)`, `put(key, value, ttl=None)` and `delete(key)`. Keys are placed on nodes by consistent hashing, every key lives on two distinct nodes, and the cache keeps answering when one node is killed. Use your assistant however you like. You have 60 minutes. At the end I will run my own test against it, and then we will talk about it."

The clock runs like this:

1. **Minutes 0 to 10, planning.** Write, in a file or a comment, how you will split the work, which pieces you will hand to the assistant, and how you will know each piece is right. Nothing is built yet.
2. **Minutes 10 to 50, build.** At minute 35 the interviewer adds: "One client must always read its own writes, even right after a node comes back."
3. **Minutes 50 to 60, finish and hand over.** The interviewer's test runs here.
4. **Review, 15 minutes.** Questions on the data model, the abstractions, the path to production and how you used the assistant.

Do the planning step now, on paper: the decomposition, the delegation split, the verification plan and your virtual-node count. Then, if you can spare an hour, build it in your own environment with your own assistant, keeping to the clock. Then open the checklist.

<p>I would plan four pieces: the ring, the node store with TTL, the client with replication and failover, and the tests. I write the ring's replica selection and the tests myself, because those encode the decisions the interviewer will probe, and I delegate the node store, the TTL plumbing and the test scaffolding, then read every line. The verification plan is a model-based test against a plain dict for single-node semantics and a fault test that kills each node in turn and checks every key is readable. The mid-round requirement I meet with writes to both replicas and reads from the first live one, and I write down that a node returning after missing writes serves stale data until it is repaired.</p>

<Fragment slot="long">
<p><strong>Delegation.</strong> Two splits are defensible. Writing the core by hand and delegating the periphery costs time to first green, but the replica selection, the part most likely to be subtly wrong, is code you wrote and can defend line by line. Delegating a full skeleton in one prompt and then reviewing it reaches a running system sooner, but the review is the bottleneck: a skeleton that arrives at once has to be read at once, and skipping that read is the Hands-Off pattern Canva's interviewers describe. The second split is acceptable when you stated the design before the prompt, the skeleton is small enough to read in the time it saves, and the tests were written or audited before you trusted it.</p>
<p><strong>Review targets.</strong> The plausible first draft of replica selection walks the ring and takes the next two points. With virtual nodes, the next two points can belong to one physical node, so both replicas sit on one machine and killing it loses the key. Skip points until the second replica is on a different node. Check the wraparound past the last point. Check that `delete` reaches both replicas, and what a node that missed the delete returns when it comes back.</p>

### The virtual-node count is yours to choose

Choose it from a measurement. This script places 100,000 keys on 5 nodes using MD5 for both keys and ring points:

```python
import hashlib, bisect
def h(s): return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")
keys = [h(f"key-{i}") for i in range(100_000)]
for v in (1, 10, 100, 200):
    ring = sorted((h(f"node-{n}#{i}"), n) for n in range(5) for i in range(v))
    points, load = [p for p, _ in ring], [0] * 5
    for k in keys:
        load[ring[bisect.bisect(points, k) % len(ring)][1]] += 1
    print(v, max(load) / (len(keys) / 5))
```

On the laptop that checked this problem it printed a busiest node at 2.04 times the mean with 1 point per node, 1.37 with 10, 1.07 with 100 and 1.09 with 200. That is one hash function and one set of node names, so the exact figures move with both, but the shape holds: one point per node is unreasonable, because the busiest node carries about twice its share. Anything from about 100 to a few hundred points per node is reasonable here, and the cost of more points is a larger ring to sort and search, which is negligible at 5 nodes and matters only with many nodes and frequent membership changes.

### The constraint conflict

The deadline pulls against verification, and the minute-35 requirement pulls against availability. Reading your own writes after a node returns needs either writes that wait for both replicas (a put fails or blocks while a replica is down) or a version per key so the client can tell a stale replica's answer from a fresh one. In 15 remaining minutes, the defensible move is writes to both live replicas plus a per-key version checked on read, with the repair of a returning node left as a written gap.

### What you give up, written down

The work sample ends with a short risk note handed to the interviewer, for example:

```text
Not handled: a node that returns after missing writes or deletes serves stale data until rewritten;
deletes leave no tombstone, so a deleted key can come back from a returning node.
First to break in production: membership. Nodes are a fixed list; adding one moves about 1/N of keys
with no migration, so those keys miss until rewritten.
Given up: availability of writes during a replica outage, for read-your-writes.
Assistant use: node store, TTL and test scaffolding generated and read line by line;
replica selection and the fault test written by hand.
```

**The failure mode of this plan.** The model-based test compares the cluster with a dict, which has no notion of a node being down, so it proves single-node semantics and nothing about failure. The fault test kills one node at a time and checks reads, which misses the case the interviewer's own test is most likely to try: kill a node, write, bring it back, read. If there is time for one more test, it is that sequence.

## Follow-ups

- *Path to production.* Nodes become processes, so every call can time out; membership needs a source of truth; a returning node needs hinted handoff or read repair; and TTL needs one clock or an expiry stored as an absolute time.
- *The interviewer's test fails on a key that hashes exactly onto a ring point.* Which side of the point owns it in your code, and in the assistant's?
- *How did you decide what to ask the assistant for?* Name a prompt you rewrote and why.

## Common mistakes

- Starting to prompt in minute one, before the decisions that the review will ask about are written down.
- Treating the assistant's "all tests pass" as the verification step instead of reading the test output.
- Spending the build chasing every requirement, including the minute-35 one, without saying what was cut.
- A replica selection that can place both copies on one physical node.
- No written note at the end, so the review starts with the interviewer discovering the gaps.
