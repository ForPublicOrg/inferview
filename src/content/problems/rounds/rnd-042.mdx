## Question

<Callout kind="interview" label="Critique, 30 minutes">
You are calibrating interviewers for an AI-assisted coding round. Below is a candidate's transcript, constructed for this problem, with the code excerpts the interviewer saved. The interviewer who ran it wrote "strong hire: fast, fluent with the tool, finished everything". List every problem with the candidate's process and code, then say what the first 15 minutes should have looked like.
</Callout>

**The brief given to the candidate.** "Build a seat-hold service for a venue. `hold(seat, user)` reserves a seat for 10 minutes; `confirm(seat, user)` books it if the user holds it; `release(seat, user)` gives it back. A seat is never booked twice. In production the service runs on two app servers behind a load balancer and shares a Postgres database; for the round, use whatever storage you like but say how it maps. 60 minutes."

```text
00:02  Candidate pastes the brief into the assistant: "Write the complete implementation and a full test suite."
00:06  Assistant returns about 180 lines: SeatService with an in-memory dict and a threading.Lock, plus 12 tests.
00:07  Candidate runs pytest: "12 passed". "Great, that's the core done."
00:09  Candidate narrates the class structure from the assistant's explanation.
00:14  Interviewer: "What happens if two users hold the same seat at the same moment?"
       Candidate types the question into the assistant, then reads its answer aloud:
       "The lock serialises access, so only one hold succeeds."
00:19  Candidate adds a test for expiry. It fails: at exactly 600 seconds, a second user's hold is refused.
00:22  Candidate asks the assistant to fix the failing test. It changes `now = 600` to `now = 601`.
       Candidate accepts the change. "Passing now."
00:26  Manual try: release a seat twice. KeyError. Candidate pastes the trace; the assistant wraps
       release in try/except. Accepted.
00:30  Candidate: "Is this code correct and thread-safe?" Assistant: "Yes. All mutations happen under
       the lock and the tests cover the main paths." Candidate: "Good."
00:33  Candidate asks for a waitlist. Then email notifications (stubbed). Then an admin endpoint to
       list holds. Each accepted after one read-through of the explanation.
00:52  Candidate runs pytest: "19 passed".
00:55  Candidate: "It's fully tested and production-ready."
```

Saved excerpts:

```python
class SeatService:
    def __init__(self, seats, clock=time.monotonic, hold_seconds=600):
        self.seats = set(seats)
        self.clock, self.hold_seconds = clock, hold_seconds
        self.holds = {}      # seat -> (user, expires_at)
        self.booked = {}     # seat -> user
        self.lock = threading.Lock()

    def available(self):
        now = self.clock()
        return [s for s in self.seats
                if s not in self.booked and (s not in self.holds or self.holds[s][1] <= now)]

    def release(self, seat, user):
        with self.lock:
            try:
                del self.holds[seat]
            except Exception:
                pass

def test_all_available_seats_can_be_held(service):        # fixture: SeatService(seats=[])
    for seat in service.available():
        assert service.hold(seat, "u1")
```

<p>The two flaws a reviewer misses on first read are in the excerpts, not the transcript. The test over `service.available()` loops zero times on the fixture's empty venue, so it passes for any implementation, including one where `hold` always fails. And the expiry edit at 00:22 looks like a test fix, but the test was right: the brief says 10 minutes, so a seat held at 0 should be free at 600, as `available` already agrees while `hold` does not. ### The flaws, in order of cost

1. **The silenced crash.** `release` deletes the hold whoever asks, so any user can release another user's hold. The `KeyError` on a double release was the only signal that release had no ownership check, and `except Exception: pass` removed it. The fix checks `self.holds.get(seat, (None,))[0] == user` and returns a result rather than swallowing errors.
2. **Two servers, one lock per process.** Above.
3. **The edited test.** Above. The rule decides the boundary; code that disagrees is the thing to change.
4. **The vacuous test.** A loop over an empty collection asserts nothing. Twelve passing tests included at least one that could not fail, and the candidate never looked.
5. **Tests accepted on a count.** MIT's agentic-coding notes say to audit tests before asking for the implementation; here they arrived with it and were never read. Claude Code's guidance asks for the command and its output as evidence, because "tests pass" says little on its own.
6. **The assistant answered the interviewer.** Canva's guide asks candidates to answer with their own thinking before seeking AI help. Here the answer was relayed, and it was wrong.
7. **Self-review.** Asking the model that wrote the code whether it is correct gets the author's opinion. A useful second look comes from a reviewer that did not write it, or from a test aimed at the claim: two services on one store, two holds, one success.
8. **Scope.** Waitlist, notifications and an admin endpoint while the core was unverified is the Feature Marathon pattern in Canva's guide.
9. **The closing claim.** "Production-ready" with in-process state, a known edited test and no ownership check is a claim without evidence.

### A judgement call

Asking for a skeleton at minute 2 is not itself the flaw. It is acceptable if the candidate has first stated the data model and the invariant (a seat has at most one booking, and a hold is valid only before its expiry), the generated code is read, and at least one test comes from the brief rather than from the assistant. The flaw at minute 2 is that the assistant made all three decisions.

### The first 15 minutes, rewritten

- **00:00 to 00:04.** Questions: is a hold extended by a second `hold` from the same user; can a user hold several seats; may `confirm` succeed after the hold expired if nobody else took the seat. State the invariant and the storage mapping: a holds table with a primary key on seat and an `expires_at` column, a bookings table with a unique constraint on seat.
- **00:04 to 00:08.** Write two tests by hand from the brief: two users hold one seat and exactly one succeeds; a seat held at 0 is free at 600.
- **00:08 to 00:15.** Ask the assistant for an implementation that passes those tests, with storage behind an interface so the in-memory version can be swapped for the Postgres one. Read the diff, run the tests, read the output.

Two openings are defensible. The one above is plan-first: decisions and tests before code. Its cost is that nothing runs for the first several minutes, and if the plan is wrong the correction comes late. The alternative is a fast skeleton followed by an immediate read and a hand-written test against it. It gets running code sooner, and it costs reading code that may encode decisions you would not have made, then undoing them. The conflict is the deadline against verification. Plan-first fits a brief with a hard invariant, as here; skeleton-first fits an open-ended product task where the interesting decisions only appear once something runs.

**The rewrite's failure mode.** A candidate who spends 15 minutes planning and then hits an unfamiliar framework can reach minute 50 with a correct core and nothing the interviewer's test can call. The plan needs a running end-to-end path by about minute 20, even if thin.

## Common mistakes

- Critiquing the candidate's prompting style instead of what was verified and what was not.
- Missing the two code excerpts, which hold the flaws the transcript does not show.
- Calling all early delegation wrong, which fails strong candidates who state the design first and delegate the typing.
- Treating finished features as evidence of quality without asking which of them were checked.
