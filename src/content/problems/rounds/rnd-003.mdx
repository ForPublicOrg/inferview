  solution: |
    import math

    # NaN policy: raise. A NaN score means the scorer failed on that item, and dropping it silently changes which
    # items the number describes; the caller can filter and report how many it dropped.


    def auc(scores, labels):
        if len(scores) != len(labels):
            raise ValueError("scores and labels differ in length")
        if any(isinstance(s, float) and math.isnan(s) for s in scores):
            raise ValueError("NaN score")
        n_pos = sum(1 for y in labels if y == 1)
        n_neg = len(labels) - n_pos
        if n_pos == 0 or n_neg == 0:
            raise ValueError("AUC needs at least one positive and one negative")
        order = sorted(range(len(scores)), key=scores.__getitem__)
        rank_sum = 0.0
        i = 0
        while i < len(order):
            j = i
            while j + 1 < len(order) and scores[order[j + 1]] == scores[order[i]]:
                j += 1
            avg = (i + j) / 2 + 1          # tied scores share the mean of the 1-based ranks they span
            rank_sum += avg * sum(1 for k in range(i, j + 1) if labels[order[k]] == 1)
            i = j + 1
        return (rank_sum - n_pos * (n_pos + 1) / 2) / (n_pos * n_neg)

## Question

<Callout kind="interview" label="Coding round">
"Write ROC AUC for a binary scorer, no scikit-learn. We will run it over a judge's scores on the full eval set."
</Callout>

Given parallel lists `scores` and `labels` (1 positive, 0 negative), return the probability that a randomly chosen positive scores higher than a randomly chosen negative, with a tie counted as one half. Raise `ValueError` when either class is missing.

Two constraints come with it. The visible tests time 20,000 items and allow 1 second. And one decision is yours: what the function does with a NaN score. Raise `ValueError`, or leave those items out and score the rest; the hidden tests accept either, and the docstring says which and why.

## Answer

The definition is pairwise: over every (positive, negative) pair, a win when the positive scores higher, half a win on a tie, divided by the number of pairs. Written that way it is O(P · N), and for 20,000 items split evenly that is 10,000 × 10,000 = 100 million comparisons. When this problem was checked in CPython 3.12.6 the pairwise version took 3.8 s on the visible test's input; the rank version below took 0.014 s.

The rank form is the Mann-Whitney U statistic. Sort once. Give each item its 1-based rank, and give a run of tied scores the mean of the ranks it spans. Sum the positives' ranks into R, subtract the smallest sum P positives could have, P(P + 1) / 2, and divide by P · N. Mean ranks are what make a tie count one half: a tied positive and negative share a rank, so the pair adds 0.5 to R − P(P + 1) / 2.

Worked on scores 0.9, 0.8, 0.8, 0.3, 0.1 with labels 1, 0, 1, 0, 0: ascending ranks are 1, 2, 3.5, 3.5 and 5. The positives hold 5 and 3.5, so R = 8.5; subtract 2 · 3 / 2 = 3 for 5.5, and divide by 2 · 3 = 6 pairs. Pairwise: the 0.9 beats three negatives, the positive 0.8 beats two and ties one, 5.5 wins.

Ties are the case that matters for LLM work. A judge that grades 1 to 5 puts thousands of items on five values, and a version that breaks ties by input order returns a different AUC when the same rows arrive shuffled; the hidden tests shuffle the input, apply a monotone transform to the scores and flip the labels (AUC becomes 1 − AUC), and compare with the pairwise count on inputs made almost entirely of ties.

**The NaN decision.** Raising treats a NaN as a scorer failure that must be seen: the cost is that one bad row stops the eval run. Dropping keeps the run going: the cost is that the number now describes a subset the scorer chose, and if the scorer fails more often on hard items the AUC rises for the wrong reason. The reference raises and leaves it to the caller to filter and report how many rows it dropped. Python's `sorted` does not raise on NaN; it silently produces an order that depends on where the NaN sits, so a version with no policy returns a number that changes when the input is shuffled.

**Where the reference falls short.** It holds every score in memory and sorts, O(n log n). For a stream of scores larger than memory, bucket the scores into a fixed histogram per class and compute the rank sum from the bucket counts; that is exact for a judge with five grades and approximate for continuous scores, with an error bounded by the pairs that share a bucket. The bucket count is the quantity to choose and defend: a judge with five grades needs five buckets and loses nothing, and for continuous scores more buckets shrink the share of pairs counted as ties at the cost of memory per shard.

## Follow-ups

- *What changes to run this inside an eval pipeline rather than a function call?* Scores arrive in shards, so compute per-class histograms per shard and merge them; report P, N and the count of excluded rows next to the AUC, because an AUC over 40 positives and one over 4,000 are not the same claim.
- *The positives are 1% of the data. Is AUC the number to report?* It averages over every threshold, including ones you will never ship; precision at the operating threshold, or the precision-recall curve, says more about the alerting cost.
- *Two judge prompts differ by 0.01 AUC on the same items. Is that a difference?* The comparison is paired, since both scored the same items; resample items with their labels and both scores together and read the interval of the difference.

## Common mistakes

- Breaking ties by position, so the same scores in a different order give a different AUC.
- Using 0-based ranks in the rank-sum formula, which lowers every answer by 1 / N.
- Returning 0.5 or 0 when a class is missing instead of raising.
- Letting NaN through to `sorted`, which neither raises nor sorts it consistently.
