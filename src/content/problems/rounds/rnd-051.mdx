## Question

<Callout kind="interview" label="Reported format, 2021">
A 2021 candidate report from a DeepMind research engineer loop describes an ML screen where the interviewer added a constraint to each proposed solution, and where "L1 gives sparse features" was not accepted without the intuition in terms of gradients. The chain below is constructed for this problem.
</Callout>

Answer each step before reading the next.

1. You predict whether a user clicks a suggested query. The model is logistic regression over hashed n-gram and cross features, about one billion distinct feature ids in a month of logs (scenario). Training is one online pass over a stream. What goes wrong first, and what do you do about it?
2. The serving fleet gives the weight table 2 GB per replica (scenario). How many weights can you keep, and how do you choose which?
3. You propose L1. Why does L1 put weights at exactly zero when L2 with the same strength does not? Use the gradient, not the picture of a diamond.
4. A colleague added the L1 subgradient to the SGD update. After a day of training, almost no weight is exactly zero. Why?
5. Two features are near-duplicates (the query lowercased and the query as typed). What does L1 do with them, and do you care?

## Answer

<Depth>
<Fragment slot="short">
<p>At w = 0 the L2 penalty's gradient is zero, so nothing holds a weight at zero; L1's subgradient at zero is any value in [-λ, λ], so a weight whose loss gradient is smaller than λ in magnitude has zero as its optimum and stays there. Plain SGD with the L1 subgradient steps across zero instead of landing on it, which is why the colleague got no zeros; a proximal step (soft-thresholding) or FTRL-Proximal sets them exactly. For the memory budget I would use FTRL-Proximal with L1 and tune λ to the budget, and the price is that training still tracks the features serving drops.</p>
</Fragment>
<Fragment slot="long">
<p><b>Step 1.</b> The weight table, not compute, is the constraint: a dense table over a billion ids has a billion weights, and most ids are rare. In the ad-click system McMahan et al. describe, half the unique features in some models occur once in billions of examples.</p>
<p><b>Step 2.</b> The count, computed. If the serving format stores an 8-byte key and a 4-byte weight per non-zero (an assumption to confirm with hint 1), 12 bytes each, then 2,000,000,000 / 12 is about 167 million non-zeros. The reader chooses how to get there; two answers are defensible.</p>
<p>L1 with a sparsity-producing optimizer keeps the weights the data supports and tunes λ until the non-zero count fits. Cost: model size depends on the data, so a traffic shift can grow it past the budget, and the training job still stores state for every feature it has seen.</p>
<p>Feature hashing into a fixed table gives a fixed memory bound regardless of traffic, and a hashed table needs no key: 2,000,000,000 / 4 is 500 million 4-byte buckets. Cost: collisions and lost interpretability. Weinberger et al. bound the interference, and McMahan et al. note that the hashed personalised spam model in that work fit in 2<sup>24</sup> features, but they report that on their ads data they could not hash below several billion features without observable loss.</p>
<p>The constraint conflict is memory against accuracy. Choose λ by sweeping it on held-out data and taking the largest value whose loss increase stays within the budget the team sets with hint 3; a λ chosen to hit the memory number without looking at the loss is not defensible.</p>
<p><b>Step 3.</b> One coordinate, loss ½(w - a)², shown with numbers. With an L2 penalty λw², the optimum solves (w - a) + 2λw = 0, so w = a / (1 + 2λ). With a = 0.3 and λ = 0.5 that is 0.15: shrunk, never zero for any non-zero a. With an L1 penalty λ|w|, the optimum is sign(a) · max(|a| - λ, 0). With the same numbers, |a| = 0.3 is below λ = 0.5, so w = 0 exactly. The gradient reading: L2 pulls with force 2λw, which vanishes as w approaches zero; L1 pulls with constant force λ until zero, and at zero any pull between -λ and λ balances the loss gradient, so the weight stays.</p>
<p><b>Step 4.</b> The subgradient update w ← w - η((w - a) + λ · sign(w)) with η = 0.1, starting at w = 0.01, goes -0.011, 0.070, 0.043, 0.019, -0.003, 0.077: it oscillates across zero and never lands on it, because a fixed step almost never ends exactly at 0. McMahan et al. say the same: adding the L1 subgradient to online gradient descent essentially never produces exact zeros. The fix is a proximal step: take the loss step u = w - η(w - a), then w = sign(u) · max(|u| - ηλ, 0). From w = 0.01, u = 0.039, which is below ηλ = 0.05, so w = 0, and the next step gives u = 0.03, still 0. FOBOS, truncated gradient, RDA and FTRL-Proximal are all versions of this. In McMahan et al.'s comparison (their own data, 2013), RDA kept 3 percent more non-zeros than FTRL-Proximal at a 0.6 percent AucLoss detriment, FOBOS 38 percent more, and a count threshold with no L1 216 percent more.</p>
<p><b>Step 5.</b> L1 tends to keep one of two highly correlated features and drop the other, and which one can change between runs (Zou and Hastie). For memory that is fine. It matters if anyone reads the weights as feature importance, or if the kept feature disappears upstream and the model loses the signal its twin carried. Adding an L2 term (elastic net) keeps both with shared weight, at the cost of more non-zeros.</p>
</Fragment>

### Where the recommended answer fails

L1 saves memory at prediction time, not in training: McMahan et al. describe tracking more features in training and sparsifying for serving, because dropping state for zero-weight features during training cost them unacceptable accuracy. If the training job is also memory-bound, the answer needs probabilistic feature inclusion on top; their Bloom-filter variant admitting a feature after two occurrences saved 66 percent of training RAM for a 0.008 percent AucLoss detriment on their data. The second failure is drift in size: λ tuned on last month's traffic says nothing about next month's non-zero count, so the serving path needs a hard cap and an alert, not only a tuned λ.

### What changes in a real system

The toy uses one coordinate and a squared loss. Logistic loss has no closed-form optimum, so the soft-threshold appears inside the optimizer's update, per coordinate, with per-coordinate learning rates in FTRL-Proximal. The serving format then stores only non-zero weights, keyed by feature id, which is why step 2 counts a key next to every weight and the hashed table does not.

## Follow-ups

- *You recommended FTRL-Proximal. A colleague says a count threshold is simpler and the accuracy loss was zero in the paper's table. Why is that not the whole story, and when would you take the simpler option?*
- *What evidence from production would make you reverse the L1 decision and move to a fixed hashed table?*
- *The same question for a neural ranker with embedding tables instead of logistic weights: does L1 still give you memory savings, and what replaces it if not?*

## Common mistakes

- Drawing the L1 diamond and stopping, without saying why the gradient holds a weight at zero.
- Claiming SGD with an L1 term produces a sparse model, when exact zeros need a proximal or thresholded update.
- Choosing λ to hit the memory number without measuring the loss it costs.
- Treating L1-selected features as importance rankings when correlated features are present.
- Forgetting that serving sparsity does not shrink the training job's state.
