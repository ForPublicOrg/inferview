## Question

<Callout kind="interview" label="Reported in a candidate report, not confirmed by the company">
A candidate's report of an Anthropic final round gives the question as how to design the implementation for a customer in a regulated industry that wants to use Claude APIs, with follow-ups on the hosting model, API management, what changes in a government contractor environment, and compliance, security and trust. The case below is original material.
</Callout>

What the interviewer tells you when asked (scenario):

- A US health insurer wants Claude to draft a first-pass summary of each appeal file for the nurse reviewer: member letter, clinical notes and claim history, sent as PDFs averaging 60 pages. About 3,000 appeals a week; files arrive through the day, and a backlog of 9,000 builds up each quarter.
- The decision on each appeal is made by a licensed clinician. The insurer's policy forbids any automated denial.
- Everything the insurer runs is in its own AWS account. Its security team requires a BAA with every processor of PHI and approves a new vendor in about eight weeks.
- Two of the insurer's engineers and you, for ten weeks.

Part 1: design the implementation: hosting, data handling, API management, the review loop and the logs. Part 2: the insurer wins a subcontract on a federal health programme whose terms require FedRAMP High authorized cloud services (scenario). What changes? And what changes if the contractor is a defence contractor instead?

Write the decision memo you would leave with the customer, including what you give up.

## Answer

<Depth>
<Fragment slot="short">
<p>Part 1: Claude on Amazon Bedrock inside the insurer's AWS account for v1, behind a thin model client so the provider can change, because it reuses a processor and network controls they have already approved and it is the route that extends to GovCloud. The alternative, the first-party API with HIPAA readiness, gets current models and features sooner but adds an eight-week vendor review and blocks the Batch API. Every summary sentence cites its page; nurses see the summary beside the file; a sample is audited for omissions, which are the failure a nurse cannot see. Part 2: the Claude API is not FedRAMP authorized, so the route is Bedrock in AWS GovCloud, with every other component inside the same boundary and the eval rerun on whichever Claude model GovCloud offers. For defence work, the March 2026 supply chain risk designation can rule Claude out of the contract entirely, so the design has to run on a second model.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Hosting: two defensible answers.</strong></p>
<p>The first-party Claude API with HIPAA readiness. Anthropic is the processor; the standard BAA can be executed from the Console; current models arrive there first, and <code>inference_geo: "us"</code> pins inference to the US at 1.1 times the standard price on Claude 4.6 and later models. The costs: a new vendor through an eight-week security review in a ten-week project; a HIPAA-enabled organization is permanent and returns 400 for non-eligible features, which here means no Batch API for the quarterly backlog, no Files API (PDFs go inline, which is eligible), and a second organization for any non-PHI work. Claude Platform on AWS does not help: HIPAA readiness is not available there.</p>
<p>Claude on Bedrock in the insurer's AWS account. The cloud provider is the processor under the insurer's existing agreements, IAM and logging are the ones its security team already audits, and the region is set by the endpoint. The costs: model and feature availability follow the provider, which can lag the first-party API, and Anthropic's own controls such as <code>inference_geo</code> do not apply.</p>
<p>I choose Bedrock for v1. The vendor review alone would consume most of the project, and Part 2 lands on Bedrock anyway. I would reverse that if the evaluation on the insurer's files showed the model available on Bedrock missing clinical facts that the first-party model catches, by a margin the clinical lead calls material.</p>
<p><strong>The request path.</strong> A gateway service in the insurer's account holds the only model credentials, so no team calls the model with its own key; it records per-request metadata (appeal id, model id, token counts, latency) and never content. Files are split into documents, each sent with its page numbers; the prompt asks for a summary in a fixed structure where each claim carries a page reference, and a post-check drops any claim whose cited page does not contain its key terms. Structured output schemas hold field names only; PHI never goes into a schema, since the first-party docs note that schemas are cached outside the PHI protections, and the same habit costs nothing on Bedrock.</p>
<p><strong>A quantity I choose: tokens per file.</strong> At an assumed 600 tokens per page (scanned clinical notes vary; measure on 50 real files before committing), a 60-page file is 36,000 input tokens, and 3,000 appeals a week is 108 million input tokens a week, about 324 million for the 9,000-appeal backlog. That size makes the backlog a throughput question: it has to fit inside the account's rate limits alongside daily traffic, so the backlog runs off-peak at a capped concurrency, and the daily queue always has priority.</p>
<p><strong>The review loop and the audit.</strong> The nurse sees the summary beside the original file with every citation clickable. The failure the nurse cannot detect is an omission: a contraindication on page 41 that the summary never mentions reads exactly like a file without one. So a second nurse audits a random 5 percent of summaries against the full file, about 150 a week, recording omissions of decision-relevant facts. If the true omission rate is 2 percent, a month of audits (600) measures it within about 1.96 × √(0.02 × 0.98 / 600) ≈ ±1.1 points. Any audit rate from 3 to 10 percent is defensible; at 1 percent, 120 audits a month give about ±2.5 points, too wide to tell 2 percent from 4. The rollback trigger, agreed with the clinical lead before launch: an omission rate above an agreed threshold in any month, or any omission tied to an appeal decision later overturned, switches the unit back to unassisted review while the cause is found.</p>
<p><strong>The constraint conflict.</strong> Compliance boundary against model capability and the deadline: the approved route is fast to ship but decides which models the insurer can use, and the backlog that would be cheapest as a batch job cannot run on the batch path under first-party HIPAA readiness.</p>
<p><strong>Failure modes of this design.</strong> Citations prove a claim came from the file; they do not prove the summary is complete, so the audit is the only control on omissions and it measures them a month late. The post-check that drops unsupported claims can also drop true ones with paraphrased wording, producing shorter summaries that look cleaner and say less. And the gateway is a single point of failure for the unit; when it is down, nurses fall back to the unassisted process, which is acceptable only because the decision never depended on the summary.</p>
<p><strong>Part 2, FedRAMP High.</strong> The government page states the Claude API and Claude Enterprise are not FedRAMP authorized. The FedRAMP High routes it names are Bedrock in AWS GovCloud (US), Vertex AI with Assured Workloads, and Claude for Government, which runs in the desktop app for chat and Claude Code and is not an API for this pipeline. What changes: the whole pipeline (gateway, document store, logs, audit tool) moves inside the GovCloud boundary, because the authorization covers services, not the model; data for the federal programme is separated from commercial appeals by account; and the evaluation is rerun on whichever Claude model GovCloud offers. The May 2025 GovCloud approval named Claude 3.5 Sonnet v1 and Claude 3 Haiku, so the model inside the boundary may be older than the one the commercial evaluation passed, and the memo has to say what quality the federal workload will get. If the programme's data were ITAR controlled, the same page points to Bedrock in GovCloud rather than the other routes.</p>
<p><strong>Part 2, a defence contractor.</strong> The same page reports a March 2026 Department of War supply chain risk designation covering Claude's use as a direct part of DoW contracts and subcontracts, with litigation ongoing. Before any design, legal confirms whether the work falls under it. If it does, the model client has to run a second model, evaluated on the same audit set, and the memo says which parts of the design survive the switch: the gateway, the citations and the audit do; the prompt and the pass bar have to be re-established.</p>
<p><strong>What you give up.</strong> The newest models and first-party features in v1, the batch discount for the backlog on the first-party path, full-content traces for debugging, and, for the federal programme, parity with the commercial pipeline's model.</p>
<p><strong>The memo.</strong> Scope: first-pass summaries for nurse reviewers; no automated decision. Hosting: Bedrock in the insurer's account, model client portable. Data: PHI only in message content, never in schemas or logs; content stays in the account. Controls: page citations with a post-check, nurse review of every appeal, 5 percent omission audit. Accepted risks: omissions found a month late (owner: clinical lead); model lag on Bedrock (owner: engineering). Rollback triggers: the omission threshold, or one omission tied to an overturned decision. Federal variant: GovCloud boundary, eval rerun, separate account. Defence variant: legal review of the designation first; second model required.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not redact PHI before the model call and skip the BAA question?</em> Appeals turn on clinical detail tied to the member; redaction strong enough to remove identifiers removes the dates and conditions the nurse needs, and re-identification from clinical context is a risk the insurer would still own.</li>
<li><em>How do you keep the backlog run from starving the daily queue?</em> Both draw on the same account quota, so the backlog's concurrency cap is set from the measured daily peak plus headroom, not from the account limit, and the cap is lowered automatically when daily latency rises.</li>
</ul>

## Follow-ups

- *Pushback: the federal programme starts in sixty days, and on GovCloud's model your audit set shows twice the commercial omission rate. Do you ship degraded, and who signs?* Ship only if the clinical lead accepts the measured rate in writing for that programme, with a higher audit rate there until a newer model is approved inside the boundary; otherwise the federal work runs unassisted.
- *Reversal: what would you need to see to move the commercial pipeline from Bedrock to the first-party API?* An evaluation on the insurer's own files showing a first-party model reduces omissions by a margin the clinical lead calls material, and a completed vendor review; until both, the switch adds risk for an unmeasured gain.
- *Two senior engineers disagree: one wants the summary generated per document, the other once over the whole file. How do you decide without deciding by rank?* Run both on the same 100 audited files and count omitted facts that span documents, such as a medication in one note and a contraindication in another; per-document is cheaper and misses exactly those.
- *The security team asks for prompts and outputs to be logged for audit. What do you log, where, and for how long?* Content in a store inside the account under the same access controls as the claims system, with a retention set by the insurer's records policy; the gateway's metadata log stays content-free.

## Common mistakes

- Answering "regulated" with encryption and a VPC, without naming who the processor is and what agreement covers it.
- Assuming every API feature is available once a BAA is signed, and designing the backlog around the Batch API.
- Treating FedRAMP as a property of the model rather than of every service the data passes through.
- Assuming the model inside a government boundary is the same one the commercial evaluation passed.
- Measuring summary quality only on what the summary says, never on what it left out.
- Writing PHI into structured output schemas, log lines or prompt templates.
