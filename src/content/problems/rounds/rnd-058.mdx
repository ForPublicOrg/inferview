## Question

<Callout kind="interview" label="Behavioural">
"What could your last agent write to, and who approved that list?"
</Callout>

Answer for an agent you shipped, from memory first, then check it against what you can reconstruct. If you need a case, use this one (scenario). Your platform team of six runs an on-call agent. It reads logs and dashboards, updates incident tickets, opens pull requests in service repositories, re-runs CI pipelines, restarts deployments in staging and production, and runs SQL through a service account that was created for a reporting job. It makes about 400 write calls a day. Security wants every write approved by a person. The agent is the team's plan for cutting on-call pages this quarter.

List what it could write to, directly and indirectly, who approved each item, what you changed, and how you settled the disagreement with security.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Request the service account's actual grants from the database, not the job description it was created for.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what happens on merge in each repository the agent can open a pull request against.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask security which of the 400 daily writes they believe can be undone, and how.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>On the scenario, my first answer would have been wrong. Directly it wrote tickets, pull requests, CI runs and deployment restarts; through the reporting service account it could also write to every table in the production database, because the account had been granted read-write when the reporting job was set up. Indirectly, a pull request to a repository that deploys on merge is a write to production if anyone approves it quickly, and the agent could open one against the repository holding its own tool configuration. Nobody had approved the list as a list: each tool was added in a separate change. I gave the agent its own credentials scoped per system, signed by each system's owner, enforced in those systems, and put approval on the writes that cannot be undone rather than all 400.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The inventory.</strong> Every tool, the credential it uses, what that credential can actually do (read from the grants, not from the tool's description), and what each write triggers downstream. That last column changed the answer: a pull request is harmless until a repository's CI deploys on merge, and the agent's own configuration lived in a repository it could open pull requests against, so it could propose widening its own permissions. OWASP calls this excessive agency and splits it into too many tools, too many permissions per tool and too much autonomy on high-impact actions; the inventory had all three.</p>
<p><strong>Who approves.</strong> The owner of each downstream system signs for the agent's scope on that system: the database owner for the SQL grants, each service owner for their repository and deployment, not the platform team that builds the agent. The list is reviewed when a tool, a credential or a tool's description changes, since a changed description changes what the model will try to do with the same permission, and it expires each quarter.</p>
<p><strong>The disagreement, and the number I chose.</strong> Security wanted approval on every write. At an assumed 20 seconds for a person to read and approve a write, 400 writes are 8,000 seconds, about 2.2 hours of on-call time a day, which removes the reason for the agent and trains people to approve without reading. I classified each write by whether it can be undone with a known procedure in minutes: ticket updates, pull requests, CI re-runs and staging restarts can; production restarts, merges to deploying branches and any database write cannot, or not safely. That put about 30 of the 400 behind approval, 600 seconds or 10 minutes a day. The classification is the quantity to defend: putting production restarts on the reversible side is defensible for a stateless service with fast rollback and not for one holding connections or caches that take an hour to warm.</p>
<p><strong>The two defensible positions.</strong> Approval on every write: simple to audit and easy to explain to an auditor, at the cost of hours a day and approval fatigue that makes the approvals meaningless. Restriction by construction (separate credentials per agent with only the grants it needs, production database access removed, the agent's configuration repository out of its write scope, enforced by the database and the code host rather than by the prompt) with approval only on irreversible writes: costs a week of platform work and a less capable agent. OWASP's complete-mediation advice is the reason the controls live in the downstream systems. Replit's response after its agent deleted a database during a code freeze was of the same kind: separating development and production databases, adding backups with one-click restore and a planning-only mode, rather than adding instructions to the prompt.</p>
<p><strong>Where this answer fails.</strong> The 30 approvals a day still arrive at 3 a.m. and get clicked. And the inventory is correct on the day it is made: the next tool, credential or description change reopens it, so the review on change is the control, not the list. Two writes that are each reversible can combine into one that is not, such as a CI configuration change followed by a re-run that deploys it; the review has to look at what the agent can do in sequence, not only per tool.</p>
</Fragment>

## Follow-ups

- *Pushback: security still wants every write approved and will block the launch without it. Which half of your design do you give up, and what risk do you accept in writing?* Accept approval on every write for the first two weeks while measuring approval time and rejection rate, then use the rejection rate on reversible writes as the evidence to remove them from approval; the written risk is the on-call time spent in those two weeks.
- *Reversal: what would you need to see to let the agent restart production deployments without approval?* A month of approved production restarts with no rejections, a tested rollback for each service that completes within the service's error budget, and the agent's restart rate limited in the deployment system, not in the prompt.
- *Two staff engineers disagree: one says the agent should act as the on-call engineer with their permissions, the other says it should have its own narrower identity. How do you decide without deciding by rank?* List the writes the on-call engineer's identity allows that the agent's tasks never need; if the list is not empty, acting as the engineer grants them, and the audit log cannot tell the agent's writes from the engineer's.
- *A new MCP server for the incident tool updates its tool descriptions in a minor version. What happens to your approved list?* The change goes through the same review as a new tool: pinned version, diff of descriptions and parameters, the incident tool's owner signs.

## Common mistakes

- Listing the tools and not the credentials behind them.
- Missing indirect writes: merges that deploy, configuration the agent can change, automations triggered by a ticket.
- "The agent was told not to" as a control.
- Approval on everything, with no account of what it costs or whether anyone reads the prompts.
- A list nobody signed, or one signed once and never reviewed.
