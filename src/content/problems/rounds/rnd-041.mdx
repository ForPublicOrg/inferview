## Question

<Callout kind="interview" label="AI-assisted round, minute 25 of 60">
"You've used the assistant a lot so far. Tell me what you are deliberately not handing to it in this round, and why. Then tell me what changes now: you have 25 minutes left, the optimisation phase hasn't started, and the retry logic you just accepted has no test."
</Callout>

The round is a multi-file job scheduler you did not write: jobs with priorities, retries with backoff, and a worker pool. The assistant can read every file. Answer both parts: the standing rule for what you keep, and the decision for the next 25 minutes.

Type your answer before opening the hints.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the interviewer how the remaining phases are scored: is an unfinished optimisation worse than an unverified one?</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each piece of code so far, ask yourself what you would run to know it is right, and whether you or the assistant chose that check.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether the interviewer's own tests will be run against your code at the end, and on which phases.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>I keep three things: the definition of correct, the decisions with trade-offs, and the judgement that a step is done. Concretely, I write or audit the test that defines each behaviour before I accept code for it; I decide retry policy, ordering and failure handling myself and use the assistant to implement them; and I run and read every change before the next prompt. I delegate what is cheap to check: skeleton code, unfamiliar library calls, mechanical refactors, and expanding test cases from an oracle I wrote. For the next 25 minutes, I spend the first few writing one test for the retry logic, because unverified code under the interviewer's tests is the larger risk, then start the optimisation with a stated scope.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The definition of correct.</strong> A test written in the same pass as the code shares the code's assumptions, so it confirms what the code does, not what it should do. If the assistant writes the tests, I read them before the implementation, as MIT's agentic-coding notes recommend, and I add the case it did not think of, usually a boundary or an interleaving.</p>
<p><strong>The decisions.</strong> Retry policy (which errors, how many attempts, whether a retried job keeps its priority), ordering under ties, and what happens to a job whose worker dies are product decisions with costs. The assistant will pick one if asked to implement; I pick, say why, then delegate the code.</p>
<p><strong>The judgement of done.</strong> Meta's AI-enabled round, as Hello Interview reports it, scores verification as one of four criteria, and the AI there answers only in chat, so every line in the editor went through my hands anyway. Done means I ran it and read the output, not that the assistant said tests pass.</p>
</Fragment>

### Two defensible splits

**Tests by hand, implementation delegated.** You write the failing test, the assistant writes the code until it passes. This gives the assistant a check to run, which Claude Code's best-practices page names as the difference between work that is done and work that looks done. Cost: tests written under a deadline are thin, and code written to pass them fits them exactly, so every gap in the tests ships as a bug.

**Critical code by hand, tests delegated and audited.** You write the retry and scheduling core; the assistant writes scaffolding and tests, which you audit. MIT's notes suggest writing critical code by hand because verifying generated code can be harder than writing it. Cost: the core takes longer, and generated tests are written from your prompt's description of the behaviour, so a misunderstanding in the prompt reaches the tests too.

I would choose the first split in a round scored on verification, and the second when the core is small, subtle and on the critical path, such as the concurrency in the worker pool, where reading a generated version costs more than writing it.

### The quantity you choose: the verification reserve

Hello Interview's report of Meta's format gives a 60-minute session with about 5 to 6 minutes of orientation and three phases. That leaves about 54 minutes, or 18 per phase if they are even. Choose what share of each phase goes to running and reading. A third gives 6 minutes per phase, enough to run the tests, read one diff and fix one failure. Zero is the Hands-Off pattern Canva's guide describes. More than half leaves too little time to build the phase at all. Anything from about a quarter to a half is defensible if you say what it buys.

### The constraint conflict and the decision now

The deadline pulls against verification. With 25 minutes left and an untested retry path, I would write one test for the riskiest retry behaviour, a job that fails twice and succeeds on the third attempt keeping its priority, run it, and fix what it shows. Then I would start the optimisation with a stated scope ("I'll do the indexed lookup, not the batching"). What I give up is part of the optimisation phase, and I state the cut and what it leaves undone.

**The failure mode of this answer.** Keeping the tests means my blind spots are in the tests. The assistant may know a failure mode I do not, and by writing every test myself I never hear about it. The fix is cheap: after writing my test, ask the assistant what cases it would add, and read the list rather than the code. Claude Code's best-practices page goes further and reviews a diff in a fresh subagent that never saw the conversation, which is the same idea with less shared context.

### When the rules say no AI

Anthropic's published guidance says live interviews and take-homes are without AI unless the interviewer says otherwise. Delegation is a question only once you know the round allows it. Anthropic's own account of a take-home that did allow AI describes leaving out debugging tools on purpose, because deciding what tooling to build, by hand or with a model, was part of what was assessed.

## Follow-ups

- *The assistant proposes a retry policy you had not considered and it is better than yours. Do you take it? How do you show the interviewer the decision is still yours?*
- *Two engineers on your team disagree: one wants agents to write all tests, the other forbids it. What data from your own repository would settle it?*
- *What would make you reverse your split mid-round?* A test you wrote that turns out to encode the wrong behaviour, found by the assistant's code failing it for a good reason.

## Common mistakes

- Answering with a list of tool features or prompting techniques instead of what you keep and why.
- "I review everything," with no check named. Reading a diff without running it leaves its behaviour unchecked.
- Keeping everything, which turns a 60-minute round into a 60-minute hand-coding round with an idle assistant.
- Asking the assistant to answer the interviewer's design question before giving your own view.
