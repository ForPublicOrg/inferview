    from bisect import bisect_right

    _GONE = object()     # tombstone


    class VersionedKV:
        def __init__(self):
            self.times = {}      # key -> sorted list of write timestamps
            self.values = {}     # key -> values aligned with times; _GONE marks a delete
            self.last = None     # timestamp of the most recent write
            self.horizon = None  # history before this timestamp has been compacted away

        def _write(self, key, value, ts):
            if self.last is not None and ts <= self.last:
                raise ValueError("timestamps must increase")
            self.last = ts
            self.times.setdefault(key, []).append(ts)
            self.values.setdefault(key, []).append(value)

        def _at(self, key, ts):
            if self.horizon is not None and ts < self.horizon:
                raise ValueError("history before the compaction horizon is gone")
            times = self.times.get(key)
            if not times:
                return _GONE
            i = bisect_right(times, ts)
            return _GONE if i == 0 else self.values[key][i - 1]

        def _latest(self):
            if self.horizon is not None and (self.last is None or self.last < self.horizon):
                return self.horizon
            return self.last

        @staticmethod
        def _same(a, b):
            if a is _GONE or b is _GONE:
                return a is b
            return type(a) is type(b) and a == b

        def set(self, key, value, ts):
            if value is None:
                raise ValueError("None is not a storable value")
            self._write(key, value, ts)

        def delete(self, key, ts):
            self._write(key, _GONE, ts)

        def get(self, key, ts=None):
            at = self._latest() if ts is None else ts
            value = _GONE if at is None else self._at(key, at)
            return None if value is _GONE else value

        def keys(self, ts=None):
            at = self._latest() if ts is None else ts
            if at is None:
                return []
            return sorted(k for k in self.times if self._at(k, at) is not _GONE)

        def restore(self, ts, now):
            if self.last is not None and now <= self.last:
                raise ValueError("now must be later than every write")
            if ts >= now:
                raise ValueError("restore to a time before now")
            changes = []
            for key in list(self.times):
                then = self._at(key, ts)                    # ValueError before the horizon
                if not self._same(then, self._at(key, self._latest())):
                    changes.append((key, then))
            for key, then in changes:                       # history is kept: restore writes new versions at now
                self.times[key].append(now)
                self.values[key].append(then)
            self.last = now

        def compact(self, horizon):
            if self.horizon is not None and horizon <= self.horizon:
                return
            for key in list(self.times):
                times, values = self.times[key], self.values[key]
                i = bisect_right(times, horizon)
                keep_from = i - 1 if i and values[i - 1] is not _GONE else i
                if keep_from > 0:
                    del times[:keep_from]
                    del values[:keep_from]
                if not times:
                    del self.times[key], self.values[key]
            self.horizon = horizon

        def version_count(self):
            return sum(len(t) for t in self.times.values())

## Question

<Callout kind="interview" label="Coding round">
"Design an in-memory key-value store where every write has a timestamp. We'll add point-in-time features in stages."
</Callout>

Three stages grow one `VersionedKV` class. Each stage runs its visible tests and then hidden tests against your whole program, and the next brief appears only after the current stage passes. Plan for about 50 minutes.

Two choices are yours:

- How versions are laid out per key.
- Which keys a restore writes: every key, or only those whose value differs.

Before stage 3, choose a horizon policy for this scenario: a service that promises point-in-time restore for the last 24 hours and takes 1,000 writes per second. Say how far behind the newest write the horizon sits, and how many versions that keeps.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask how many versions the hottest key accumulates and how often old timestamps are read.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask whether a restore must keep the history it replaces, and who reads that history afterwards.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what a reader should get when the time it asks about has been compacted away.</p></details>

## Answer

The reference keeps, for each key, two parallel lists: write timestamps and values, with a sentinel object standing for a delete. Because timestamps increase across all writes, every write is an append, and `get(key, ts)` is a `bisect_right` on the key's timestamps. That costs `O(log v)` for a key with v versions.

A linear scan per read is the design stage 1 rules out. The visible test makes 200,000 reads against a key with 200,000 versions, so a scan touches up to 4 × 10^10 entries. The reference answered all 200,000 reads in 0.20 seconds in this harness's local CPython 3.12.6.

**Restore.** `restore(ts, now)` compares, for each key, the value at `ts` with the current value, and appends a version at `now` (a value or a delete) wherever they differ. History is never rewritten, so a reader holding an earlier timestamp keeps getting the same answer. That is also why the hidden tests check every saved snapshot again after each restore.

**Compaction.** `compact(horizon)` cuts each key's lists down to the floor version at the horizon plus everything after it. The floor version is dropped too when it is a delete. A key left with no versions is removed. A read or restore below the horizon raises `ValueError`. Returning the oldest kept value instead would be a wrong answer that looks right.

The restore design has two defensible answers:

- **Restore as new writes (the spec here).** The audit trail is kept and readers of past timestamps are undisturbed. Storage grows by one version for each changed key on every restore.
- **Restore as truncation.** Every version after `ts` is deleted. This is cheaper in storage and simpler to compact, but it destroys the history a postmortem needs and changes the answers for anyone who read at a later timestamp.

Writing only the changed keys costs a comparison per key, `O(K log v)` in total. Writing every key costs the same lookups plus a version for each unchanged key, so compare first.

The horizon is where history depth conflicts with memory. With 24 hours of restore promised at 1,000 writes per second, the horizon sits at least 86,400 seconds behind the newest write. That keeps about 86,400 × 1,000 = 86.4 million versions, plus one floor version per key. Add a margin for a restore that starts just before the boundary, and for clock skew between writers. Two horizons are unreasonable: "compact to now", which breaks the restore promise, and "never compact", which grows without bound.

**How the recommended answer fails.**

- **Global timestamps.** The rule that timestamps increase across all writes assumes one writer or one timestamp source. Two writers with their own clocks need a hybrid logical clock or a sequencer, and this class rejects their interleaved writes.
- **Compaction cost.** `del times[:k]` shifts the list's remaining entries, so compaction costs `O(versions kept)` per key every time it runs. For hot keys compacted often, keep a start offset and trim the list occasionally, or use a ring buffer.

## Follow-ups

- *What changes to run this as a storage engine?* Versions become `(key, timestamp)` records in a sorted structure on disk, compaction becomes a background merge that drops versions below the horizon, and the horizon is persisted, so a crash never resurrects compacted history. Restore becomes a metadata write when the engine can route reads through it.
- *Pushback: a restore across 50 million keys writes up to 50 million versions and takes minutes, and readers see a half-restored state while it runs. What do you change, and what do readers see?* Make the restore atomic for readers: write the new versions at `now` but publish `now` as readable only when the last one lands, so reads at the newest timestamp see either all of it or none. Accept in writing that the restore itself is slow, and measure how long it takes.
- *Reversal: what would make you change reads below the horizon from raising to returning the oldest kept value?* Evidence that every caller treats the answer as best-effort, such as dashboards, not billing, together with a field in the response that marks it as approximate. Without that field, keep the error.
- *Operating: a customer asks you to restore to a time 30 hours ago, six hours past your horizon. What do you tell them, and what do you change?* That those versions are gone. Then record the request and decide whether the 24-hour promise or the memory budget changes next, with the arithmetic above as the cost of each extra hour: 3.6 million versions at this write rate.

## Common mistakes

- Scanning a key's versions linearly on every read.
- Treating a delete as "remove the key's history" rather than as a version.
- Implementing restore by truncating history.
- Compacting away the floor version, so reads at the horizon return `None`.
- Returning a value for a time before the horizon.
- Accepting a write whose timestamp equals the last one.
