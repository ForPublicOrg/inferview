## Question

<Callout kind="interview" label="The brief, as a 2026 interview guide quotes it; the time limit is this scenario's">
"Here are 50 markdown docs. Build a Q&A system, an eval set of 20 questions, and report recall@5 and faithfulness." You have three hours and a repository to submit.
</Callout>

Plan the submission. Say what you build in which order, what you deliberately leave out, how you build and use the eval set, and what the README says. Assume the instructions are silent on AI tools; say what you do about that too.

## Hints

<details class="hint"><summary>Hint 1</summary><p>The eval is the deliverable the brief names twice. Build it before you tune anything.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Recall@5 is about retrieval and faithfulness is about generation. Your design should let you measure them separately.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Twenty questions is a small sample. Decide what size of difference you can honestly claim.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>I would ship a simple, working pipeline with a real eval rather than a clever one with none. First the eval set: 20 questions written from the docs, each labelled with the chunk or chunks that answer it. Then the simplest retrieval that could work (heading-aware chunks, BM25 plus embeddings), a generator that must cite chunk ids, a script that prints recall@5 and a faithfulness score, and one improvement chosen by reading the failures. The README reports the numbers with the sample size, lists what I cut and why, and says what I would do with another day.</p>
</Fragment>
<Fragment slot="long">
<p>Before anything else, read the brief and the AI-tool policy. Anthropic's published guidance says take-homes are done without Claude unless the instructions say otherwise, and OpenAI says expectations vary by format, so if the brief is silent I ask the recruiter, and I write the answer into the README either way.</p>
<p>Eval set first, because everything else is judged by it. I write 20 questions by reading the docs, not by asking a model to generate them from the chunks, and I mix the kinds: single-fact lookups, questions whose answer spans two documents, questions phrased with different words from the docs, and two or three questions the corpus cannot answer. Each has gold evidence (document and section) and a short reference answer.</p>
<p>Baseline next. Chunk by markdown heading so chunks keep their titles; index with BM25 and with an embedding model; merge the two ranked lists with reciprocal rank fusion. The generator gets the top five chunks and must answer with chunk ids or say it does not know. This is enough to produce both metrics end to end within the first part of the time box.</p>
<p>Metrics. Recall@5 is the share of questions whose gold evidence appears in the top five retrieved chunks. Faithfulness is whether every claim in the answer is supported by the retrieved chunks; I score it with an LLM judge given the answer and the chunks, and I hand-check the judge on all 20 because 20 is small enough to read. Unanswerable questions are scored on whether the system declines.</p>
<p>One improvement, chosen from evidence. I read every failure and sort it into retrieval misses, ranking misses (evidence at rank 6 to 20), and generation errors. I fix the largest bucket only, rerun, and report before and after.</p>
<p>What I cut, and say so: no UI beyond a CLI, no vector database server (an in-memory index is fine for 50 docs), no agentic multi-hop, no fine-tuning, no caching layer. Each line in the README gets one sentence on why it is out of scope at this size.</p>
<p>The README is a short report: how to run it in one command, the numbers in a table with n = 20 next to them, the failure buckets with an example of each, what changed between baseline and final, what I would do next, and how I used AI tools if allowed.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your recall@5 went from 16/20 to 18/20. Is that an improvement?</em> It is two questions. With 20 items I would call it a direction, show the two questions, and say I would need a larger set to claim more.</li>
<li><em>How do you know the judge is right?</em> I read all 20 judged answers and report how often I agreed with it. On a bigger set I would hand-label a sample and report agreement.</li>
<li><em>What would you do with another day?</em> Grow the eval set from real user questions if any exist, add a reranker if ranking misses dominate, and add a regression test that runs the eval in CI.</li>
</ul>

What reviewers can check. OpenAI's interview guide lists take-home projects among its assessment formats and states what it looks for in engineering interviews: well-designed solutions, high-quality code, optimal performance and good test coverage. None of those is "most features". Anthropic's engineering post on redesigning its take-home lists principles such as representative work and many chances to show skill, which a short, measured submission gives a reviewer.

A plan for the three hours that fits this answer, offered as my allocation rather than a rule: read and set up first, then the eval set, then the baseline running end to end, then one improvement, and keep the last stretch for the README and a clean run from a fresh clone. If the baseline is not producing numbers by the halfway point, cut the improvement and report the baseline honestly.

## Follow-ups

- *The reviewer runs your repo and it fails on their machine.* Pin dependencies, put the one command in the README, and run it from a fresh clone before submitting. This is the cheapest point in the whole exercise.
- *How would this change if the corpus were 50,000 documents?* Ingestion becomes a pipeline with incremental updates, the index moves to a vector store, and the eval set needs stratifying by document type.
- *Would you use an LLM to generate the eval questions?* To draft candidates, perhaps, then filter and rewrite by hand. A question generated from a chunk can reuse its wording, which flatters lexical retrieval; check for that before trusting the set.

## Common mistakes

- Spending most of the time on a UI or on framework setup and submitting with no numbers.
- Generating the 20 questions from the same chunks the retriever indexes, then reporting a high recall@5 that measures string overlap.
- Reporting one faithfulness number from an unchecked judge.
- Claiming an improvement from 17/20 to 18/20 as if it were significant.
- A README that describes the architecture at length and never says what was cut or what the numbers mean.
