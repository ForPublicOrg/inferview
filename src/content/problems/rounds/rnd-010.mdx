## Question

<Callout kind="interview" label="The brief as a July 2026 interview guide quotes it; the time box and the rest are this scenario's">
"Here are 50 markdown docs. Build a Q&A system, an eval set of 20 questions, and report recall@5 and faithfulness."
</Callout>

You have three hours. The reviewer will clone the repository and run it on a laptop with an API key of their own, and the brief says nothing about AI tools. Plan the submission: the order of work, what you leave out, how the eval set is built and used, what the README claims, and what you do about the AI-tool question.

Two quantities are yours to set and defend: the smallest change in recall@5 on these 20 questions that you would report as an improvement, and the point in the three hours after which you stop building and only measure and write.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the recruiter whether AI tools are allowed, and whether you may draft eval questions with a model.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the reviewer runs first: the app, the eval script or the README.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Once a baseline runs, count how many of the 20 failures are retrieval misses and how many are wrong answers over the right chunks.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A baseline that runs end to end in one command, an eval set I wrote and labelled by hand, both numbers with n = 20 next to them, and at most one improvement, reported as which questions changed and in which direction. On 20 questions I would not call any change of five questions or fewer an improvement. I stop building at about two hours and fifteen minutes. The README says what I cut, what the numbers can and cannot support, and how I used AI tools after asking.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The AI-tool question first.</strong> Policies differ even inside one company: Anthropic's candidate guidance says take-homes are done without Claude unless it says otherwise, while its own performance take-home explicitly permits AI. So I email the recruiter in the first five minutes, work without AI tools until I have an answer, and write the answer and how I used the tools into the README.</p>
<p><strong>The eval set before any retrieval code.</strong> Twenty questions written by reading the docs, each labelled with the document and section that answer it and a one-line reference answer. The mix matters more than the count: single-fact lookups, questions whose answer spans two documents, questions worded differently from the docs, and two or three the corpus cannot answer. Writing them before the retriever exists keeps me from writing questions my retriever already handles.</p>
<p><strong>The baseline.</strong> Chunk by markdown heading so each chunk keeps its title path; BM25 and one embedding model, merged by reciprocal rank fusion; a generator that must cite chunk ids or decline. Fifty documents fit in memory, so there is no vector database to install on the reviewer's laptop.</p>
<p><strong>The two numbers.</strong> Recall@5 per question: does any gold section appear in the top five chunks. Faithfulness per answer: is every claim supported by the retrieved chunks, scored by a judge model and checked by me on all 20, with the agreement count in the README. The unanswerable questions are scored on whether the system declines, and reported separately so they do not inflate either number.</p>
<p><strong>The decision.</strong> With the baseline in, there are two defensible uses of the next hour. One improvement, chosen from the largest failure bucket and reported before and after, shows that I can move a number; its cost is that 20 questions cannot separate most changes from noise, and the change is tuned on the same questions it is scored on. Or no improvement, and the hour goes into the measurement: a second set of questions drafted with a model if allowed, filtered by hand, used to pick the improvement so the original 20 stay a test set. Its cost is a submission with no gain on the numbers the brief names. I take the improvement if the baseline numbers exist by the 90-minute mark, and the measurement otherwise.</p>
<p><strong>The threshold, computed.</strong> Compare two configurations on the same 20 questions by the questions that changed: b went from miss to hit, c from hit to miss. The two-sided sign test on the b + c changed questions gives, with c = 0, p = 2 × 0.5<sup>b</sup>. That is 0.0625 for b = 5 and 0.03125 for b = 6. So the smallest change this eval can call an improvement at the usual 0.05 is six questions with no regressions, 30 points of recall@5. A threshold of six is the honest one; reporting smaller moves as "direction, not evidence" is also reasonable. Calling 16/20 to 18/20 an improvement is not.</p>
<p><strong>What I give up, in writing.</strong> No UI beyond a CLI, no vector database, no reranker unless the failure buckets ask for it, no multi-hop agent, no caching. The README has a "what I cut and why" table with one line each, the numbers with n and the judge agreement, the failure buckets with one example each, the decision about the improvement and its tuning-on-test caveat, a one-command run tested from a fresh clone, and the AI-tool note.</p>
<p><strong>Where this plan fails.</strong> A hand-written set of 20 reflects what I think users ask. If my questions are easier than the real ones, every number in the README is high, and nothing in the submission can show it. The README says so, and names the first thing I would do with real traffic: replace half the set with logged questions.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your eval work takes half the time box, and the retrieval is BM25 plus one embedding model. The rubric weights the product. Which half of the eval work do you cut, and what does the README say about the risk you took?</em></li>
<li><em>What would you need to see in the baseline to skip the improvement entirely?</em> Retrieval misses as a small share of the failures (my line is a quarter): then the next hour goes to the generator's citations, which recall@5 does not measure.</li>
<li><em>The reviewer reruns your eval and gets 15/20 where your README says 17/20. What in the submission lets them find out why in five minutes?</em> Pinned versions, a seed, the judge model and prompt recorded, and per-question results written to a file next to the summary.</li>
</ul>

The time plan behind the answer, as my allocation and not a rule: the first 15 minutes reading the docs and emailing the recruiter; until about 0:45 the eval set; until 1:30 the baseline producing both numbers; until 2:15 the improvement or the measurement work; the rest for the README and a run from a fresh clone. The cut-off at 2:15 is the quantity to defend. Forty-five minutes is enough to write the README and debug one broken install; fifteen is not, and a repository that does not run on the reviewer's machine leaves them nothing to grade.

A second failure mode of the recommended plan: reciprocal rank fusion over BM25 and embeddings is a sensible default on prose docs, but if the docs are mostly API reference with exact identifiers, BM25 alone may beat it, and the baseline then needs one line in the README saying the fused variant was checked and lost.

## Follow-ups

- *Would you let a model write the 20 questions?* Drafting, perhaps, from documents it is not shown chunked; then rewrite by hand. A question generated from a chunk reuses its wording, which flatters BM25. Check overlap before trusting the set.
- *The corpus is 50,000 documents instead of 50. What in your submission changes, and what in the README stays the same?*
- *Two reviewers disagree: one wants the improvement, the other the measurement. How do you decide without deciding by seniority?* Ask which claim the team needs to make next; if it is "this beats what we have", the measurement comes first.

## Common mistakes

- Submitting with no numbers because the UI or a framework ate the time.
- Generating questions from the indexed chunks and reporting a recall@5 that measures string overlap.
- One faithfulness number from a judge nobody checked.
- Picking the improvement and scoring it on the same 20 questions without saying so.
- A README that describes the architecture at length and never says what was cut or what the numbers can support.
