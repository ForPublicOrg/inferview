## Question

<Callout kind="interview" label="The format, as the company describes it">
A medium-sized codebase and a draft PR from a colleague that adds a cross-cutting feature. Pull the code, check what it does, review it and improve it, working with coding agents. Sierra describes piloting this round; the PR below is original.
</Callout>

The codebase is a customer-service agent platform: an async web service that runs a model with tools (`find_order(email)`, `refund(order_id, amount)`), logs through Python's `logging` under module loggers such as `platform.agent` and `platform.tools`, exports OpenTelemetry spans, and stores every conversation's transcript, which is also loaded back when a conversation resumes after a handoff. Tools run in a thread pool through `loop.run_in_executor`. A customer's data processing agreement requires that email addresses, phone numbers and card numbers do not reach logs, traces or stored transcripts, and their security review is in three weeks.

Draft PR #482, "Redact PII from logs, traces and transcripts", constructed for this problem:

```python
# platform/redaction.py (new)
import logging
import re
from contextvars import ContextVar

current_policy = ContextVar("current_policy", default="standard")

PATTERNS = {
    "email": re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"),
    "phone": re.compile(r"\+?\d[\d ()-]{8,}\d"),
    "card": re.compile(r"\b(?:\d[ -]?){13,16}\b"),
}
STRICT_ONLY = {"phone"}


def redact(text):
    for name, pattern in PATTERNS.items():
        if name in STRICT_ONLY and current_policy.get() != "strict":
            continue
        text = pattern.sub(f"[{name}]", text)
    return text


class RedactingFilter(logging.Filter):
    def filter(self, record):
        record.msg = redact(str(record.msg))
        return True
```

## Answer

The PR redacts the paths its author looked at and none of the paths the data actually takes. Every sink below leaks with the tests green, because the tests check `redact()` on strings and one message on the root logger.

**Logs, twice over.** The filter is added to the root logger. Python consults a logger's filters only for events logged on that logger; records from `platform.tools` and `platform.agent` propagate to the root's handler without passing through the root's filter. Every module logger in the codebase bypasses it. And where the filter does run, it rewrites `record.msg` only: `log.info("lookup %s", email)` keeps the address in `record.args`, which the formatter interpolates after the filter. The fix attaches redaction where every record passes once, fully formatted: a filter on each handler that formats the message, redacts it and clears `args`, or a log record factory. The test that catches both: log through a child logger with the address as an argument.

**Traces.** `llm.prompt` is redacted; `tool.args` is the raw JSON of what the model passed to `find_order` and `refund`, which is the customer's email and sometimes a card number. That is the most PII-dense attribute in the system. Redact every string attribute in a span processor before export instead of at each `set_attribute` call, so a new attribute added next month is covered without anyone remembering.

**Streams.** `stream_reply` redacts each chunk on its own. An address split across two chunks, `jane.doe@exa` and `mple.com`, matches neither. Redact a buffer that holds back a tail as long as the longest possible match, or log the reply once when the stream ends.

**Tenant policy in tool threads.** `current_policy` is a contextvar. `asyncio.to_thread` documents that it carries the current context into the thread; `run_in_executor` does not, and a `ThreadPoolExecutor` worker reads the variable's default. Every tool call, including any logging inside tools, runs under `"standard"`, so strict tenants lose phone redaction exactly where phone numbers are handled. Use `asyncio.to_thread` with a bounded pool, or wrap the call in `contextvars.copy_context().run`.

**Over-redaction.** The card pattern matches any 13 to 16 digit run, which includes order and tracking numbers. Support analytics loses the ids it joins on, and debugging a refund from its trace becomes guesswork. A Luhn check removes most of these. You were asked for a rate you would accept: anything from zero to a few percent of order ids is defensible if it is measured by running the pattern over a day of real order ids and the support team agrees to it; "we'll see" is not.

**Transcripts are a decision, not a bug.** Redacting before save means a conversation resumed after a handoff reloads `[email]`, and the agent can no longer call `find_order`. It is acceptable if the transcript store is analytics-only and live conversation state is kept separately with a short retention. If the same table serves both, the PR breaks resumption.

**Not in the PR.** Months of logs, traces and transcripts already hold raw PII; the customer's agreement covers those too, so retention and a scrub job belong in the plan. There is no flag, so the change reaches every tenant at once, including the over-redaction.

### The decision: redact at the sinks, or tokenise at ingress

- **Redact at each sink**, as the PR does but completed: handler-level log redaction, a span processor, a stream buffer, a transcript policy. Cost: every new sink (an analytics event, a new exporter, a debug dump) is a new leak until someone adds redaction to it, and the model and tools still see raw PII, which the agreement may or may not allow.
- **Tokenise at ingress.** Replace PII in user messages with reversible tokens (`<email_1>`) held in a per-conversation vault; tools detokenise at the edge when they call the order system. Cost: a vault with its own access control and retention, tools that must all go through the detokenising layer, and a model that sometimes has to reason about a token instead of an address. Sinks are clean by construction, including ones nobody has written yet.

With three weeks to the security review, I would finish the sink approach now, because tokenising touches every tool, and put tokenisation in the design for next quarter. What I give up, written in the PR: the model provider still receives raw PII, and the next sink someone adds leaks until the canary test below catches it. The way this answer fails is the canary itself: it only finds the sinks it searches, so a sink missing from its list (a crash dump, a third-party error tracker) leaks with the test green.

### Working with the coding agent

Give the agent the inventory and the mechanical fixes: find every `logging.getLogger` call, every `set_attribute`, every write to `db.*` and every outbound analytics call, then move the filter to the handlers and add the span processor. Do not give it the policy: what counts as PII here, whether transcripts keep raw data, and the false-positive rate are decisions with a customer contract behind them. The check on the agent's work is an end-to-end canary test written by hand: run a scripted conversation through the real service in which the customer gives a synthetic email, phone and card number, capture logs at the handler, spans with an in-memory exporter and the transcript rows, and assert none of the three strings appears anywhere. It fails on this PR at the child loggers and at `tool.args`, and it fails again whenever someone adds a sink without redaction.

## Follow-ups

- *The canary, the span processor, the handler fix, the stream buffer and the transcript split are five changes and you have three weeks. Which three ship before the review, and what do you tell the customer in writing about the other two?*
- *What would you need to see to move from sink redaction to tokenisation sooner?* A second leak through a sink nobody listed, or a customer contract that forbids sending PII to the model provider.
- *The PR's author says the root-logger filter works because their test passes. How do you settle it without deciding by rank?* Run the test through `logging.getLogger("platform.tools")` with the address as an argument, in front of them.
- *Security asks for redaction of names as well. What changes?* Names need a model or a dictionary, not a regex, so the latency budget per log line and the false-positive rate on product names become the constraints.

## Common mistakes

- Reading `redaction.py` closely and never asking which loggers the rest of the code uses.
- Fixing the filter's position and missing `record.args`, or the reverse.
- Treating the transcript change as a fix rather than a product decision about resumed conversations.
- Asking the agent to "make sure no PII is logged" and accepting its summary instead of a test that searches every sink.
- Proposing tokenisation as the only answer without the vault, the tool changes and the timeline it needs.
