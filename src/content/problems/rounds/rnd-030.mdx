## Question

<Callout kind="interview" label="The prompt">
"This take-home came in yesterday for a senior applied-AI role. The brief was the 50-docs RAG task. You have half an hour before the debrief: what is wrong with it, how much does it matter, and do we bring this person onsite?"

The submission below is constructed for this problem. Read it as you would read a real one, list the flaws, rank them, and write the recommendation with the questions you want asked next. Then open the checklist.

### README.md

> **DocQA.** Run `pip install -r requirements.txt && python eval.py`.
>
> **Approach.** Documents are split into 300-token chunks with 50-token overlap and embedded with a hosted embedding model. BM25 and vector results are fused with weight `alpha`. The generator answers from the top five chunks and cites chunk ids.
>
> **Eval set.** 20 questions. To avoid my own bias I generated them: for each of 20 randomly chosen chunks, a model wrote one question answerable from that chunk, and that chunk is the gold label.
>
> **Results.**
>
> | configuration | recall@5 | faithfulness |
> |---|---|---|
> | dense only | 0.75 | 0.91 |
> | hybrid, alpha 0.3, 300-token chunks | 0.90 | 0.95 |
>
> Hybrid search improves recall@5 by 20% and faithfulness by 4%. I swept alpha over 0.1 to 0.9 in steps of 0.1 and chunk size over 200, 300 and 500 tokens and report the best configuration. Faithfulness is judged by the same chat model as the generator (temperature 0.7 for both): 1 if the answer is supported by the context, else 0.
>
> **Tests.** `pytest`: 14 tests, all passing, 92% line coverage.
>
> **Limitations.** The eval set is small; with more time I would add questions.

### eval.py (excerpt)

```python
def main():
    index = Index.load_or_create("./index")
    index.add(chunk_all(DOCS, size=CHUNK, overlap=50))
    results = {q.id: index.search(q.text, k=5, alpha=ALPHA) for q in QUESTIONS}
    print("recall@5", recall_at_5(results), "faithfulness", faithfulness(results))
    index.save("./index")

def recall_at_5(results):
    hits = 0
    for q in QUESTIONS:
        docs = {c.doc_id for c in results[q.id][:5]}
        hits += q.gold_doc in docs
    return hits / len(QUESTIONS)
```

## Answer

Ranked by how much each flaw changes what the submission can claim.

**1. The headline number is a tuned number.** The sweep is 9 values of alpha times 3 chunk sizes, 27 configurations, scored on the same 20 questions, and the best is reported. With 20 questions, the best of 27 will beat the baseline on noise alone often enough that 0.90 says little about the next 20 questions. The fix is cheap and the README should have used it: choose on some questions, report on others.

**2. The improvement is three questions at most.** 0.75 and 0.90 are 15/20 and 18/20. If three questions went from miss to hit and none the other way, the two-sided sign test gives 2 × 0.5³ = 0.25; if any went the other way it is weaker still, and the per-question file is not in the submission. "20%" is the relative change of 0.15 over 0.75, which makes three questions sound like a result.

**3. The table contains an impossible number.** A binary judge on 20 answers gives a multiple of 0.05. 0.91 is not one, so something else was averaged: several runs, per-sentence scores, or a bug. At temperature 0.7 with one run reported, either answer means the faithfulness column cannot be compared across rows. It is also the easiest flaw here to read past.

**4. Recall is measured at the wrong grain.** The README says the gold label is a chunk; `recall_at_5` checks the gold document. With 50 documents, five chunks often span several documents, so a hit needs only some chunk from the right document. It also explains how the chunk-size sweep was possible at all: chunk ids change with chunk size, document ids do not.

**5. The eval set flatters lexical retrieval and never asks a question the docs cannot answer.** Questions written by a model from one chunk reuse that chunk's wording, which is what BM25 rewards, so part of the hybrid gain may be the question-writing method. With no unanswerable questions, what the system does when the docs do not hold the answer, decline or invent, is never measured.

**6. The eval is not repeatable.** `main` loads a persisted index, adds every chunk again and saves it. The second run has two copies of every chunk, the top five fills with duplicates, and the reviewer who reruns it gets different numbers from the README's.

**7. Coverage without the risky code.** The tests check that an answer is a string, that chunks fit a size, and that the prompt contains an id. None covers `recall_at_5` on a known case, a citation to a chunk id that was not in the context, re-ingestion, or a query that retrieves nothing. 92% line coverage measures that lines ran.

**Judgement calls.** Generating questions with a model is acceptable if they were filtered and rewritten by hand and checked for overlap with the gold chunk; nothing here says they were. One run is acceptable if generation and judging run at temperature 0, or if the spread over a few runs is reported. A file-backed index instead of a vector database is fine at 50 documents.

## Follow-ups

- *Rewrite the Results section as you would want it submitted, with the same data.*
- *The brief said 20 questions. Is splitting them into 10 for choosing and 10 for reporting worse than tuning on all 20?* On ten questions the smallest change the sign test supports at 0.05 is still six questions with none going the other way, 60 points, so the better move is a second, model-drafted and hand-filtered set for choosing, with the 20 kept for the report.

## Common mistakes

- Accepting the table and reviewing only the code.
- Reading "improves recall@5 by 20%" as 20 points.
- Treating 92% coverage as evidence that the evaluation code is right.
- Flagging model-generated questions as wrong in every case instead of asking how they were filtered.
- Returning a list of flaws with no recommendation and no questions for the next round.
