    def raises(fn):

    probs = [0.5, 0.3, 0.15, 0.05]
    assert sorted(top_p_filter(probs, 0.8)) == [0, 1], "the token that crosses p is kept, and the set stops there"
    assert sorted(top_p_filter(probs, 0.81)) == [0, 1, 2], "0.8 is not enough for p = 0.81"
    assert sorted(top_p_filter(probs, 1.0)) == [0, 1, 2, 3], "p = 1.0 keeps everything"
    assert sorted(top_p_filter([0.1, 0.6, 0.3], 0.5)) == [1], "sort by probability, not by index"
    assert abs(top_p_filter(probs, 0.8)[0] - 0.625) < 1e-9, "renormalise over the kept set: 0.5 / 0.8"
    assert sorted(min_p_filter(probs, 0.2)) == [0, 1, 2], "threshold is 0.2 * 0.5 = 0.1"
    assert sorted(min_p_filter([0.9, 0.05, 0.05], 0.1)) == [0], "the threshold is relative to the top token, 0.09 here"
    assert abs(sum(min_p_filter(probs, 0.2).values()) - 1) < 1e-9, "min-p output sums to 1"
    p = softmax([1000.0, 1001.0, 1002.0])
    assert abs(sum(p) - 1) < 1e-9 and p[2] > p[1] > p[0], "subtract the max before exp, or this overflows"
    assert softmax([2.0, 1.0], 0.5)[0] > softmax([2.0, 1.0], 2.0)[0], "lower temperature sharpens the distribution"
    assert raises(lambda: softmax([1.0, 2.0], 0)), "temperature 0 means greedy decoding: use argmax, not a division by zero"
    assert sample({0: 0.625, 1: 0.375}, 0.6) == 0 and sample({0: 0.625, 1: 0.375}, 0.7) == 1
    assert sample({1: 0.375, 0: 0.625}, 0.6) == 0, "walk indices in ascending order, whatever the dict order"
  solution: |
    import math

    def softmax(logits, temperature=1.0):
        if temperature <= 0:
            raise ValueError("use argmax for greedy decoding")
        z = [x / temperature for x in logits]
        m = max(z)                      # shift so the largest exponent is exp(0)
        e = [math.exp(x - m) for x in z]
        s = sum(e)
        return [x / s for x in e]

    def _renormalise(probs, keep):
        total = sum(probs[i] for i in keep)
        return {i: probs[i] / total for i in keep}

    def top_p_filter(probs, p):
        order = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)
        keep, cum = [], 0.0
        for i in order:
            keep.append(i)
            cum += probs[i]
            if cum >= p:
                break
        return _renormalise(probs, keep)

    def min_p_filter(probs, p_base):
        threshold = p_base * max(probs)
        return _renormalise(probs, [i for i, q in enumerate(probs) if q >= threshold])

    def sample(dist, u):
        cum = 0.0
        last = None
        for i in sorted(dist):
            cum += dist[i]
            last = i
            if u < cum:
                return i
        return last                     # float round-off can leave cum just under 1

## Question

<Callout kind="interview" label="The prompt">
"Here is a list of logits. Write temperature, top-p and min-p sampling in plain Python, then show me how you'd test it." You have 25 minutes and no NumPy.
</Callout>

Fill in the four functions. `sample` takes the random number as an argument instead of calling `random` itself, so the tests are deterministic. Keep that design in the interview too: an injected source of randomness is the difference between a sampler you can test and one you can only eyeball.

The order of operations is temperature first (inside `softmax`), then one filter, then `sample`. Libraries do not all apply temperature, top-k and top-p in the same order, so say which order you chose.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Top-p sorts by probability, descending, and stops at the first token that makes the running total reach p. That token is kept.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Min-p does not need sorting: compute one threshold from the largest probability and keep everything at or above it.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Both filters must renormalise, otherwise `sample` walks a distribution that sums to less than 1 and the last token absorbs the gap.</p></details>

## Answer

The reference solution sorts once for top-p, accumulates until the running total reaches p, and keeps the crossing token. Holtzman et al. define the nucleus as the smallest set whose probability mass is at least p, so with probabilities 0.5, 0.3, 0.15 and 0.05 and p = 0.8 the set is the first two tokens: 0.5 + 0.3 reaches 0.8 exactly. Renormalised, the top token gets 0.5 / 0.8 = 0.625.

Min-p, from Nguyen et al., scales the cut-off by the model's confidence: the threshold is p_base times the top probability. With p_base = 0.2 and a top probability of 0.5 the threshold is 0.1, so three tokens survive. When the model is confident the cut rises with it: with probabilities 0.9, 0.05 and 0.05 and p_base = 0.1 the threshold is 0.09, and only the top token survives. That adaptivity is the reason the paper gives for preferring it at high temperature.

`softmax` subtracts the maximum before exponentiating. Mathematically the result is the same; numerically `exp(1002)` overflows a float and `exp(0)` does not. Temperature 0 raises, because greedy decoding is an argmax, not a limit you can compute by dividing.

`sample` walks indices in ascending order so the result does not depend on dict insertion order. The final `return last` covers float round-off, where the running total ends at 0.9999999 and u is larger.

## Follow-ups

- *Add top-k.* Sort, keep the first k, renormalise. Ask whether top-k and top-p together should intersect (the usual answer) or apply in sequence, and test the case where they disagree.
- *What happens at p exactly on a cumulative boundary?* Summation order changes the last bits, so a reference implementation that sums in a different order can keep one more or one fewer token. Tests should avoid exact boundaries unless both sides sum the same way. The test here relies on 0.5 + 0.3 comparing greater than or equal to 0.8 in Python floats, which it does; check a case like that rather than assume it.
- *Make it batched.* The same code over a list of rows, then the vectorised version: sort per row, cumulative sum, a mask, and a scatter back to the original order.
- *Why not always use greedy?* For open-ended text, Holtzman et al. found likelihood-maximising decoding produces bland, repetitive output. For input-grounded tasks such as summarisation, greedy or beam search is often fine.

## Common mistakes

- Keeping tokens whose individual probability is above p. That is a different (and wrong) filter.
- Stopping before the crossing token, which can leave an empty set when the top token alone is below p.
- Forgetting to renormalise, so sampling silently favours the last kept token.
- Sorting the probabilities and losing the original indices, so the sampler returns a rank instead of a token id.
- Treating min-p as an absolute floor rather than a fraction of the top probability.
