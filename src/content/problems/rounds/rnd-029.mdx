## Question

<Callout kind="interview" label="The shape one candidate reported for an OpenAI forward deployed engineer loop, via a vendor guide (July 2026); the customer is this problem's">
Roughly five hours on OpenAI's APIs: build a retrieval feature, a small agent or an eval harness, and record a walkthrough. The walkthrough opens the technical deep dive that follows.
</Callout>

Treat the build as a pilot for a customer: a regional insurer's claims team whose adjusters search a few hundred policy documents and internal guidelines to answer "is this covered, and under which clause?" Choose one of the three options, build it in five hours, and record the walkthrough. Then open the checklist.

Set two numbers before you start and hold yourself to them: the length of the recording, and the hour at which you stop adding features.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the recruiter who watches the recording, and whether they watch it before or during the next interview.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask whether there is a usage cap on the API key, and whether the reviewers will run the code or only watch it.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Write down the question an adjuster would ask in the first minute of a pilot, and check which of the three options can answer it on camera.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The retrieval feature, because the adjuster's question is a retrieval question and the eval comes with it. I build on the hosted file search tool to save the build time, request the search results so retrieval can be measured, and spend the time saved on a 25-question evaluation, citations to clauses, and a visible "not in these documents" path. The recording is eight minutes and shows a failure as well as a success.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The choice among three.</strong> Each option is defensible for a different reviewer. A small agent (look up the policy, check the claim against it, draft a response) makes the strongest demo and is the hardest to make reliable in five hours; its cost is that the recording can show success on the cases it was tuned on and little else. An eval harness is the most production-shaped artefact and the least like something a claims team would use; its cost is that "customer-demo quality" has to be argued rather than shown. The retrieval feature answers the adjuster's actual question and carries its own measurement. I build the retrieval feature and say in the recording what the agent would have added.</p>
<p><strong>Build or use the hosted tool.</strong> The Responses API's <code>file_search</code> tool searches vector stores I upload the documents to. It saves the ingestion and index code, which is most of an hour. Its costs: fewer knobs (the guide exposes <code>max_num_results</code> and metadata filters), and the search results are not returned unless the request includes <code>file_search_call.results</code>, so an eval written without that measures answers only. Writing my own chunking and hybrid search gives control over clause boundaries, which matter in policy documents, and costs the hour. I use the hosted tool, include the results, and put the clause-boundary risk in the README as the first thing I would test with real documents.</p>
<p><strong>What production-shaped means here.</strong> Configuration for keys, model names and the vector store id; one command from a clean clone; logs per request with latency, tokens and model; handled paths for no answer in the documents, a timeout and a rate-limit error, each shown in the UI rather than as a stack trace; and pinned SDK versions with the date of the docs I built against. Fine-tuning is not on the list: OpenAI closed self-serve fine-tuning to organisations that had not used it on 7 May 2026, so it is not an option a new customer pilot can count on.</p>
<p><strong>The evaluation.</strong> Twenty-five questions an adjuster would ask, written from the documents, each labelled with the clause that answers it, including five whose answer is not in the documents. I report retrieval recall at the configured number of results, answer correctness checked by hand, and the decline rate on the five. With 25 questions this is a smoke test with a direction, and the README says so.</p>
<p><strong>The recording.</strong> Eight minutes, my choice: one minute on the customer and the question, three on the demo including one question it should decline, two on the architecture and the hosted-tool decision, one on the eval and its limits, one on what changes for a real deployment. I treat ten minutes as the ceiling because the recording opens an interview, not because any published rule says so; under five leaves no room for the failure path.</p>
<p><strong>Where this fails.</strong> Hosted retrieval with few knobs is fast to build and slow to fix. If recall on clause-level questions is poor, the levers left are document preparation and metadata filters, and the honest next step is the own-retrieval version I chose not to build. The recording says this before the deep dive asks it.</p>
</Fragment>

<li><em>Your evaluation and logging took ninety minutes of a five-hour build, and the UI is a single page. The customer's lead says it looks like a prototype. Which part of that ninety minutes would you give back, and what risk would you accept in the pilot agreement?</em></li>
<li><em>What would you need to see in the first week of the pilot to replace the hosted search with your own?</em> Clause-level recall below what the adjusters accept on their own questions, with the misses traced to chunk boundaries rather than to wording.</li>
<li><em>The customer's security team asks where the policy documents are stored and for how long. What do you answer from your build, and what do you have to find out?</em></li>

The stop-adding-features hour is the other number to defend. I stop at hour three and a half: an hour for the evaluation, the README and a clean-clone run, and thirty minutes to record, so a second take is possible if the first runs long. Stopping at hour four and a half leaves one take and no clean-clone check, which is a choice I would not make for a recording that opens the next interview.

## Follow-ups

- *The reviewer says a retrieval feature is the safe choice. Defend it in one minute, or argue for the agent instead.*
- *The customer's documents include scanned PDFs. What in your build breaks first, and how would the evaluation show it?*
- *You have a week instead of five hours. Which of the three options do you build then, and why does the answer change?*

## Common mistakes

- Choosing the agent because it demos best, then recording only the cases it was tuned on.
- An evaluation that scores answers without requesting the search results, so retrieval misses and generation errors look the same.
- A recording that walks through the code file by file instead of showing what the customer would see, including a failure.
- Planning on fine-tuning for a customer pilot without checking whether the account can create fine-tuning jobs.
- No numbers for latency or cost per request, which a customer's engineer needs before agreeing to a pilot.
