  solution: |
    def recall_at_k(ranked, relevant, k):
        if not relevant:
            raise ValueError("recall needs at least one labelled relevant document")
        gold = set(relevant)
        return len(gold.intersection(ranked[:k])) / len(gold)


    def faithfulness(claims, context_ids):
        if not claims:
            return None
        context = set(context_ids)
        return sum(1 for _, support in claims if context.intersection(support)) / len(claims)


    def evaluate(cases, k=5):
        recalls, faiths, triage = [], [], {}
        for case in cases:
            r = recall_at_k(case["ranked"], case["relevant"], k)
            f = faithfulness(case["claims"], case["ranked"][:k])
            recalls.append(r)
            if f is not None:
                faiths.append(f)
            if r < 1.0:
                triage[case["id"]] = "retrieval"
            elif f is None or f < 1.0:
                # Policy: a refusal with every gold document in context failed to use the evidence (Not Extracted).
                triage[case["id"]] = "generation"
            else:
                triage[case["id"]] = "ok"
        return {
            "recall@k": sum(recalls) / len(recalls) if recalls else 0.0,
            "faithfulness": sum(faiths) / len(faiths) if faiths else None,
            "triage": triage,
        }


    def recall_curve(cases, max_k):
        # One pass per case: the first rank of each gold document, then a running sum over k.
        gained = [0.0] * (max_k + 1)
        for case in cases:
            gold = set(case["relevant"])
            if not gold:
                raise ValueError("recall needs at least one labelled relevant document")
            seen = set()
            for rank, doc in enumerate(case["ranked"][:max_k], start=1):
                if doc in gold and doc not in seen:
                    seen.add(doc)
                    gained[rank] += 1 / len(gold)
        curve, total = [], 0.0
        for k in range(1, max_k + 1):
            total += gained[k]
            curve.append(total / len(cases) if cases else 0.0)
        return curve

## Question

<Callout kind="interview" label="The take-home, as a public interview guide reports it">
"Here are 50 markdown docs. Build a Q&A system, an eval set of 20 questions, and report recall@5 and faithfulness."
</Callout>

This is the scoring half of that take-home, with no model calls so it runs in the browser. Your pipeline has run on 8 labelled questions over 12 documents (`d01` to `d12`). For each question you have the gold document ids, the ranked list your retriever returned, and the answer split into claims, with the documents a reviewer found to support each claim (an empty list means none does). The model saw the top `k` documents as context.

Write four functions:

- `recall_at_k`: the fraction of gold documents in the top `k`.
- `faithfulness`: the fraction of claims supported by a document that was in the context.
- `evaluate`: the means over the set, and a triage label per question that blames the first broken stage. One case is yours to decide: a refusal (no claims) when every gold document was in the context. State the label you give it and why.
- `recall_curve`: mean recall@k for every `k` from 1 to `max_k`. The hidden tests run it on 2,000 questions with 1,000-document rankings and `max_k` of 1,000, in under 2 seconds.

Then choose the `k` you would ship for the submission and defend it from the curve. The prompt has room for 4,000 tokens of context and the chunks average 350 tokens (a scenario figure), so `k` can go as high as 11.

## Answer

The reference is four short functions; the judgement is in the definitions and in one data layout.

**recall@5 is 0.6875.** Per question: q1 1, q2 0.5 (`d03` is at rank 6), q3 1, q4 0 (`d06` at rank 6), q5 1, q6 1, q7 1, q8 0. That is 5.5 / 8. Hit rate@5 on the same data is 6 / 8 = 0.75, which is why Hint 1 matters: the two numbers differ on every question with more than one gold document.

**Faithfulness is 0.667.** Seven answers make claims: q1 1, q2 0.5 (the receipts claim needs `d03`, which the model never saw), q3 0.5 (the WireGuard claim has no support anywhere), q5 1, q6 2/3 (the laptop purchase claim is in `d12`, outside the context), q7 1, q8 0. The sum is 14/3 and the mean 14/21. q6's unsupported claim may well be true, since it is in the corpus; faithfulness flags it because the model asserted something it was not shown.

**Triage and the refusal policy.** q2, q4 and q8 are retrieval failures: a gold document never reached the context, so their faithfulness is a consequence, not a cause. q3 and q6 had all their evidence and made unsupported claims, so they are generation failures. The case the tests leave to you is a refusal with full recall. The reference labels it `generation`: the labels promise the gold document contains the answer (Hint 2), so a refusal with it in context is the Not Extracted failure in Barnett et al.'s list. Labelling it `ok` is defensible only if the gold labels mean "related", in which case the refusal may be correct; its cost is that a model which refuses whenever it is unsure scores perfectly on generation. Faithfulness stays undefined for refusals either way and is left out of the mean; counting a refusal as 1 rewards refusing, and as 0 punishes an honest "I don't know" after a retrieval miss.

**The curve and its constraint.** The obvious `recall_curve` calls `recall_at_k` once per `k` per question, which rebuilds a set from a slice of up to 1,000 ids a million times per 1,000 questions. On the laptop that checked this problem (CPython 3.12.6) that took 1.9 s for 200 questions, so about 19 s for the hidden test's 2,000. The reference reads each ranked list once, records the rank at which each gold document first appears, adds `1 / len(gold)` at that rank, and turns the gains into a running sum: 0.07 s for the same 2,000 questions. The curve at every `k` agrees with `recall_at_k`, which the hidden tests check, including on rankings that repeat an id.

**Choosing k.** The curve on the 8 cases is 0.5, 0.5625, 0.6875, 0.6875, 0.6875, 0.875 for `k` from 1 to 6. Two answers are defensible.

- *Ship k = 5, as the brief asks.* Cost: two questions whose gold document sits at rank 6 stay unanswerable, and the write-up has to say so. It keeps the context at about 1,750 tokens and the number of distractors low.
- *Ship k = 6 or more.* Recall rises to 0.875, at 350 tokens per extra chunk, and every extra chunk that is not gold is a distractor the model can draw an unsupported claim from. It also changes the metric the reviewer asked for, so the report has to give recall@5 anyway.

The constraint conflict is recall against context cost and distraction, decided on a sample too small to separate them: with 8 questions one question moves recall by 0.125, and with the brief's 20 by 0.05. The jump from 0.6875 to 0.875 is 1.5 questions. I would ship k = 5, report the curve to `k` = 11 beside it, and name rank 6 as the next experiment, because the gain is two questions and the faithfulness cost of more context is not measured on this set. Choosing a `k` past the point where the curve flattens on a larger set is the unreasonable choice: it buys tokens and distractors and no recall.

**The failure mode of this scorer.** Every number rests on the reviewer's claim labels. In the real take-home an LLM extracts and verifies claims, as Ragas does, and the extractor decides how many claims an answer has: the same answer split into 2 or 3 claims scores differently. A faithfulness change between two pipeline versions scored by two extractor versions measures the extractor. Pin the judge, keep its verdicts per claim, and hand-check a sample before reporting a difference.

**What the write-up says next.** Fix retrieval first, since three of the five failures never had the evidence; for q3 and q6, add a citation check and a prompt that cites only the documents given; report recall, hit rate, faithfulness and correctness separately, with the curve.

## Follow-ups

- *What changes to run this on the real pipeline?* Rankings come back as chunk ids, so recall needs a chunk-to-document map or chunk-level gold labels, and the two give different numbers. Claims come from a pinned extractor whose verdicts are stored with its version. The curve runs on logged rankings, not live calls, so changing `k` does not cost a rerun.
- *The reviewer says 20 questions cannot tell recall@5 from recall@8 and your choice of k is noise. You have three hours in total. Which part of the build do you cut to label 30 more questions, and what risk do you write down?*
- *What would you need to see to ship k = 8 instead of 5?* On a set large enough that a step is more than one question, recall rising between 5 and 8 and correctness rising with it, with faithfulness flat.
- *A colleague labels refusals with the evidence present as `ok` and you label them `generation`. How do you settle it without deciding by rank?* Read the refused questions' gold documents together: if most contain the answer verbatim, the labels mean "contains" and the refusal is a failure.

## Common mistakes

- Computing hit rate and calling it recall@5.
- Treating a claim as faithful because it is true somewhere in the corpus.
- Counting refusals as faithfulness 0 or 1.
- Blaming generation for questions whose evidence never reached the prompt.
- Recomputing recall from scratch for every `k` on the curve.
- Choosing `k` from a difference of one question.
