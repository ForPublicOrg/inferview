## Question

<Callout kind="interview" label="The prompt">
"Compare flat, IVF and HNSW indexes. How do you pick one, and what does recall@k cost you in latency?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Map each index to a database structure you already know: a full scan, a hash with fuzzy buckets, a skip list.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each, name the build-time knob and the query-time knob.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Recall of an approximate index is measured against exact search on the same queries.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Flat is exact search, a full scan with perfect recall and linear cost, right for small corpora and as ground truth. IVF clusters vectors and scans only the nearest `probes` clusters: fast to build, light on memory, recall set by probes. HNSW is a layered graph searched greedily: the best speed-recall trade-off, but slower to build and heavier on memory, with `ef_search` as the per-query recall knob. I pick by corpus size, memory budget and update rate, and I measure recall against flat search at the setting I ship.</p>
</Fragment>
<Fragment slot="long">
<p>Flat. Compare the query with every vector. pgvector does this by default, and its README says it "provides perfect recall". Cost grows linearly with rows, so it is fine up to the point where latency breaks your budget, and it stays useful forever as the reference for measuring the others.</p>
<p>IVF. Run k-means to make `lists` centroids, store each vector in its nearest centroid's list, and at query time scan the `probes` nearest lists. pgvector's guidance is lists = rows / 1000 up to a million rows and the square root of rows above that, with probes starting at the square root of lists. More probes means more recall and more latency. Building needs data to train the centroids, so an IVF index built on an early sample degrades as the distribution shifts.</p>
<p>HNSW. A multi-layer proximity graph: sparse upper layers for long jumps, a dense bottom layer for the final search. `m` (links per node) and `ef_construction` (build-time candidate list) are fixed at build; `ef_search` (query-time candidate list) trades recall for latency per query. pgvector defaults are 16, 64 and 40, and the README describes HNSW as having the better speed-recall trade-off with slower builds and more memory. It supports inserts without retraining, which suits changing corpora.</p>
<p>Compression is a separate axis. Product quantization or binary quantization shrinks vectors (Qdrant documents up to 64x for PQ) and is combined with IVF or HNSW when memory is the constraint, usually with rescoring of an oversampled shortlist using full-precision vectors.</p>
<p>The recall and latency cost. There is no universal curve; it depends on data, dimension and engine. Measure it: take a few hundred real queries, compute exact top-k, then sweep `ef_search` or `probes` and plot recall@k against p95 latency. Ship the cheapest setting that clears your recall target, and re-run the sweep when the corpus grows.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your HNSW recall is fine in tests but poor in production. Why?</em> Filters. pgvector applies the WHERE clause after the scan, so a selective filter leaves too few candidates; iterative scans or partitioning fix it.</li>
<li><em>What about LSH?</em> Locality-sensitive hashing buckets vectors with random hyperplanes. It is simple to shard and comes with probabilistic guarantees; whether it matches graph or cluster indexes on your data is something to measure on the same recall-versus-latency sweep, not assume.</li>
<li><em>When is a dedicated vector database worth it over pgvector?</em> When you need built-in quantization, multi-vector search, fusion inside one query or sharding at a scale your Postgres operators do not want to own.</li>
</ul>
</Fragment>
</Depth>

The core of a strong answer is the database analogy plus the two knobs. Flat is the sequential scan. IVF is a hash index whose buckets are learned clusters, so its query knob is how many buckets you open. HNSW is a skip list over a neighbour graph, so its query knob is how wide a frontier you keep at the bottom layer. Each approximate index is judged by one number, recall@k against flat search, at the latency you can afford.

## Follow-ups

- *How do you choose `ef_search` for a top-10 query?* It must be at least 10; sweep upwards and stop when recall@10 against exact search reaches the target.
- *What happens to HNSW with heavy deletes?* Graph quality degrades and deleted nodes still cost traversal until the index is vacuumed or rebuilt; pgvector 0.8.3 fixed a vacuum corruption bug, so run 0.8.3 or later.
- *Why is IVF build faster?* It is k-means plus a bucket assignment; HNSW inserts each vector by searching the graph it is building.

## Common mistakes

- Quoting pgvector's defaults as properties of HNSW in general.
- Claiming a recall number without saying what it was measured against.
- Forgetting that exact search exists and is often fast enough for small corpora.
- Ignoring filters, which change effective recall more than any index parameter.
