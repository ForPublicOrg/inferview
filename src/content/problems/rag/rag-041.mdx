## Question

<Callout kind="interview" label="The prompt">
"Offline recall is good, but online search quality is bad. What do you check, in what order?"
</Callout>

The interviewer gives you the case. Two weeks ago an internal search product moved from BM25 to dense retrieval with `intfloat/e5-base-v2` in pgvector. One table, 20 million chunks, shared by tenants. The nightly offline eval said the new system was better; users say it is worse.

```text
Offline eval, nightly (eval/harness.py, exact search, no tenant filter)
  golden set: 300 questions generated by an LLM from sampled chunks, one source chunk each
  recall@10 0.91   MRR 0.74
ANN check, Northwind rows only, ef_search 40 against exact: recall@10 0.97

Online, 14 days after the switch
  thumbs-down rate                4.1% before, 11.8% after
  results returned per query      mean 9.7 of 10
    tenants over 5% of rows       10.0
    tenants under 1% of rows      1.4
  query length                    median 7 words, p99 31 words
  tickets                         41, of which 37 from Northwind (62% of rows)

Replay: 50 queries quoted in Northwind tickets as failing,
run through eval/harness.py with "AND tenant_id = 'northwind'" added
  source document in top 10: 44 of 50
```

```python
# search/encoder.py
class Encoder:
    def __init__(self, name="intfloat/e5-base-v2", prefix="passage: "):
        self.model = SentenceTransformer(name)
        self.prefix = prefix

    def encode(self, texts, batch_size=64):
        texts = [self.prefix + t for t in texts]
        return self.model.encode(texts, batch_size=batch_size, normalize_embeddings=True)


# search/service.py
ENCODER = Encoder()

def search(query: str, tenant_id: str, k: int = 10):
    q = " ".join(query.split())[:512]
    vec = ENCODER.encode([q])[0]
    with pool.connection() as conn:
        conn.execute("SET hnsw.ef_search = 40")
        return conn.execute(
            "SELECT doc_id, chunk_id, embedding <=> %s AS dist FROM chunks "
            "WHERE tenant_id = %s ORDER BY embedding <=> %s LIMIT %s",
            (vec, tenant_id, vec, k),
        ).fetchall()


# ingest/job.py
ENCODER = Encoder()

def embed_chunks(chunks):
    return ENCODER.encode([c.text for c in chunks])


# eval/harness.py
model = SentenceTransformer("intfloat/e5-base-v2")

def embed_query(text):
    return model.encode(["query: " + text], normalize_embeddings=True)[0]

def run(golden, k=10):
    hits = 0
    for item in golden:
        rows = exact_search(embed_query(item.question), k)
        hits += item.chunk_id in {r.chunk_id for r in rows}
    return hits / len(golden)
```

Which defect explains Northwind's complaints? Rank the others, and say what you would collect before changing anything.

## Answer

The replay is the decisive evidence. The same 50 queries, against the same rows, with the same tenant restriction, find their source document 44 times through the harness. Online they are the queries users filed tickets about. So the index, the data and the model are not the difference; the query path is. ANN against exact on Northwind's rows is 0.97 at `ef_search` 40, which rules out the approximate index for this tenant. What is left on the query path is how the query becomes a vector: the harness prepends `query: `, the service goes through `Encoder`, whose default prefix is `passage: `, because the class was written for ingestion and then reused. The E5 card says inputs must carry the prefix the model was trained with or performance degrades. A query encoded as a passage tends to match passages that look like it (other tickets restating a question, FAQ titles) rather than the passages that answer it. The defect is a constructor default, not a changed line in `search()`, which is why review missed it.

**What the evidence does not show, and what to collect.** The 44 of 50 comes from the harness; nobody has the online top 10 for those queries. Collect, for the 50 replayed queries: the vector `search()` produces and the one `embed_query()` produces (their cosine is below 1 if the prefixes differ; equal vectors would clear this cause at once), and the online top 10. Then confirm the ingestion side: the build that wrote the 20 million rows must have used `passage: `. If it did, the fix is query-side only and nothing is re-embedded. If it used something else, the fix is a full re-embed, and the decision becomes how to run two vector columns side by side. Without that information, change nothing in the table; a query-side fix behind a flag, gated on the replay, is safe either way.

**The fix.** `Encoder` gets `encode_query` and `encode_passage` and no default prefix, so nothing can call it without choosing. The harness imports the same `encode_query`. The replay set of 50 becomes a permanent check in the nightly run.

**The other defects, ranked.**

- *Post-filtering for small tenants* (second). Tenants under 1% of rows get 1.4 results per query. pgvector filters after the index scan; the README's arithmetic is that a condition matching 10% of rows leaves about 4 of the 40 candidates. Below 1% the expectation is under 0.4, and the observed 1.4 is higher only because a tenant's queries are about its own content, whose vectors sit near the query. These tenants did not file the tickets, probably because they get few results rather than wrong ones. It needs fixing this week too.
- *Golden set generated from chunks* (third). Questions written by a model from a chunk share its vocabulary and have exactly one target. That is why 0.91 looked safe, and it would have hidden the prefix bug even if the harness used the service path, because a passage-encoded question still lands near the chunk it was copied from. Replace it with real queries and pooled judgments as the pilot logs grow.
- *Exact identifiers* (fourth). Dense retrieval can lose to BM25 on error codes and part numbers, and the old system was BM25. Check the replay's 6 misses for this pattern before deciding on hybrid retrieval; it does not explain the 37 tickets.
- *Character truncation* is not a defect at these query lengths.

### Two decisions with a cost each

**Should the harness call the production query path?** Yes for the encoder, because path drift is what happened here. The cost: a bug shared by both paths becomes invisible offline. So keep one differential check that does not share code: a pinned reference script embeds 50 fixed queries with the prefix written out literally, and the nightly run compares its vectors with the service's. An alarm at a cosine below 0.999 is reasonable for the same model and precision; 0.99 is too loose to catch a prefix change on short queries reliably, and you should measure where a deliberate prefix change lands before fixing the threshold.

**What to do for small tenants.** Iterative scans (pgvector 0.8.0 and later, `relaxed_order`, up to 20,000 tuples by default) keep one index and cost latency on exactly the queries that need them. Routing small tenants to exact search through a B-tree on `tenant_id` gives them recall 1.0 and costs a scan that grows with the tenant: at 768 dimensions and 4 bytes, 20,000 chunks are 61 MB of vectors per query, and 200,000 are 614 MB. You choose the cut-over point from a measured p95 of exact search at a few tenant sizes; a threshold of 1% of the table is unreasonable, because it sends 600 MB scans to the exact path. I would use exact search below the measured cut-over and iterative scans above it, and accept that the cut-over has to be revisited as tenants grow.

**Where this fails.** The fix makes the harness and the service agree, which says nothing about whether either matches users. The golden set is still synthetic, Northwind's replay is 50 queries chosen because they failed, and a thumbs-down rate is a noisy proxy. Until real judged queries exist, "offline recall is good" will keep being a weaker statement than it sounds.

## Follow-ups

- *Pushback: the search lead wants to roll back to BM25 tonight and debug offline for two weeks. Rolling forward with the query-side fix is a one-line change behind a flag. Which do you do, and what do you write down about the risk of the one you pick?*
- *Reversal: what would you need to see in the replay after the prefix fix to conclude the move to dense retrieval was wrong for this product, rather than badly deployed?*
- *Ingestion turns out to have written half the rows with no prefix at all during the first week. How do you find them, and do you re-embed now or at the next model change?*

## Common mistakes

- Trusting offline recall that runs through a different query path from production.
- Raising `ef_search` for everyone to fix a symptom that only small tenants have.
- Re-embedding the corpus before checking which prefix the stored vectors used.
- Treating a golden set generated from the indexed chunks as evidence about real queries.
- Concluding "dense retrieval is worse" from a deployment defect.
