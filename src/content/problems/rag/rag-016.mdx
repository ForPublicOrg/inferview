## Question

<Callout kind="interview" label="The prompt, as candidates report it">
"Design a retrieval-augmented generation system that answers employee questions from our internal wiki and documents. Cover ingestion, indexing, retrieval and generation, and tell me how you would know it works."
</Callout>

Clarify scope before drawing anything. Assume, as a scenario: 2 million pages across a wiki, a document store and a ticket system; 20,000 employees; permissions per space and per document; pages edited throughout the day; answers must cite their sources.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Spend the first minutes on requirements: who asks, how fresh, who may see what, how answers are judged.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Draw two paths, the ingestion path and the query path, and put access control on both.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Close with evaluation: what you measure offline, online, and per stage.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Two paths. Ingestion: connectors with change feeds, layout-aware parsing, structure-aware chunking with heading paths and ACL labels on every chunk, hybrid indexing (BM25 and vectors), deletes as tombstones and a nightly reconciliation. Query: rewrite the question with chat history, hybrid retrieval filtered by the user's groups, rank fusion, a cross-encoder rerank of a budgeted candidate set, a live permission check on the final chunks, and generation with citations that are validated against what was sent. Evaluation: a labelled question set with gold chunks, per-stage metrics (recall@k, gold in prompt, faithfulness, correctness), run in CI and fed by production feedback.</p>
</Fragment>
<Fragment slot="long">
<p>Requirements. Users: employees asking lookup and how-to questions, some multi-document. Freshness: an edit or delete should be reflected within minutes for policies. Access: no answer may use a document the asker cannot open. Quality: answers cite sources; "I could not find this" beats a guess. Latency target and cost per query set with the product owner.</p>
<p>Ingestion. Connectors subscribe to change events per source and fall back to polling with content hashes. Parsing keeps headings, lists and tables. Chunks follow structure, carry the heading path, document id and version, timestamps and ACL labels, and optionally a short model-written context (contextual retrieval reduced Anthropic's top-20 failure rate from 5.7% to 1.9% in combination with BM25 and reranking). Each chunk is indexed for BM25 and as a vector. Deletes and permission changes flow through the same pipeline; a reconciliation job diffs source ids against the index nightly.</p>
<p>Index. A search engine or Postgres with pgvector, depending on scale and team. Selective permission filters are the hard part: filters applied after an approximate scan return too few rows, so use filtered traversal, iterative scans or partitioning by space.</p>
<p>Query path. A router decides whether to retrieve at all, or to call a structured API ("who owns service X?"). The question is rewritten as a standalone query. Hybrid retrieval runs with the user's resolved groups as a filter; results are fused with RRF with an explicit window; a cross-encoder reranks a candidate count set by the latency and cost budget; the final chunks get a live permission check; the context is assembled best-first within a token budget, with documents before the question.</p>
<p>Generation. Chunks are passed with ids and titles (Claude's search_result blocks do this natively); the model must cite; a post-check rejects citations to anything not sent. When nothing relevant is found, the answer says so.</p>
<p>Evaluation. A labelled set of a few hundred questions written from real queries, with gold chunks and reference answers, including identifier queries, multi-document and unanswerable questions, and questions over restricted documents. Per-stage metrics: recall@k after fusion, gold in final prompt, faithfulness, correctness, refusal accuracy, and permission-leak tests that must be zero. Failures are triaged by first failing stage using the Barnett et al. failure points. Online: thumbs down, rephrased follow-ups and escalations feed new eval cases.</p>
<p>Operations. Trace every request with retrieved ids, scores and the prompt; alert on freshness lag, empty-result rate per permission group, and latency per stage.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Where is the bottleneck at 10 times the traffic?</em> The reranker and generation scale with queries, the index with corpus size and filter selectivity; load-test to see which saturates first.</li>
<li><em>How do you roll out a new embedding model?</em> Build a parallel index, backfill, compare recall on the eval set, switch reads, then delete the old index.</li>
<li><em>What would you cut for a first version?</em> Query routing and contextual chunk enrichment; never the permission filter or the eval set.</li>
</ul>
</Fragment>
</Depth>

The diagram is the part of this answer most likely to look like anyone else's. What carries it is the requirements discussion at the start, access control enforced before the model sees text, deletes treated as first-class events, and an evaluation plan that measures each stage separately so failures can be attributed.

## Follow-ups

- *A VP says the bot "makes things up". How do you respond in week one?* Pull the examples, triage each to a stage, and show the per-stage numbers before changing anything.
- *How do you handle questions that span many pages, like "what changed in our travel policy this year"?* Retrieve by metadata (document, date range) and summarise the versions, or precompute change summaries at ingestion.
- *How do you keep costs predictable?* Cap candidates and context tokens per request, cache the static system prompt, and route small talk away from retrieval.

## Common mistakes

- Jumping to "chunk, embed, vector DB, LLM" without asking about permissions or freshness.
- Enforcing access control in the prompt or after generation.
- An evaluation plan that is only "use an LLM judge".
- Ignoring deletes and permission changes in the ingestion design.
