## Question

<Callout kind="interview" label="The prompt">
"We want to move from text-embedding-3-small to text-embedding-3-large. We have 80 million chunks indexed. What does the switch cost, how long do we run both, and what has to be true before we cut over?"
</Callout>

The interviewer narrows it to one number: **the peak memory the vector tier needs during the switch, in GB, for the configuration you would ship.** Work out the re-embedding bill on the way.

Published inputs (OpenAI's embeddings and Batch API guides, checked 2026-10-28):

- text-embedding-3-small returns 1,536 dimensions; text-embedding-3-large returns 3,072 and accepts a `dimensions` parameter that shortens the output.
- Embedding prices are given as pages per dollar at about 800 tokens per page: 62,500 for 3-small, 9,615 for 3-large.
- The Batch API is 50% cheaper than synchronous calls, completes within 24 hours, and takes at most 50,000 embedding inputs per batch.

Scenario inputs:

- 80 million chunks. The chunker caps chunks at 512 tokens, and a sample of 10,000 put the mean somewhere between 350 and 450 tokens; pick a value.
- The index is a RAM-resident HNSW graph with M 16 and float32 vectors. The fleet has 1.2 TB of RAM for vectors; adding nodes takes a quarter.
- 300,000 new chunks arrive per day and must be searchable under whichever model is serving.
- Use Faiss's sizing rule for HNSW: d x 4 + M x 2 x 4 bytes per vector.

## Answer

<Depth>
<Fragment slot="short">
<p>About 880 GB, for the configuration I would ship: text-embedding-3-large shortened to 1,024 dimensions, float32, HNSW M 16, both indexes resident for a 14-day window. The old index is 80 million x (1,536 x 4 + 128) bytes = 502 GB; the new one is 80 million x (1,024 x 4 + 128) = 338 GB; 14 days of dual-written arrivals add 4.2 million chunks to each, about 44 GB. Re-embedding is the small number: at a mean of 400 tokens, 32 billion tokens at $0.13 per million is about $4,160, or about $2,080 through the Batch API. The dominant term is the second index in RAM, not the API bill. Full 3,072 dimensions at float32 would need about 1.5 TB at the peak, which does not fit.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The price, derived.</strong> 9,615 pages per dollar x 800 tokens per page = 7.69 million tokens per dollar, so 3-large costs about $0.13 per million tokens. (3-small: 62,500 x 800 = 50 million per dollar, $0.02 per million.)</p>
<p><strong>The re-embedding bill.</strong> 80 million chunks x 400 tokens = 32 billion tokens. Synchronous: 32,000 x $0.13 = $4,160. Batch: $2,080. Across the sampled range of 350 to 450 tokens the batch bill is $1,820 to $2,340. It takes 80,000,000 / 50,000 = 1,600 batches; the creation limit of 2,000 per hour is not what binds, the organisation's enqueued-token limit is, and that number is on the limits page, so ask for it. The dual-written arrivals add 300,000 x 400 = 120 million tokens a day, about $16 a day synchronously.</p>
<p><strong>The memory, per configuration.</strong> Links at M 16 are 16 x 2 x 4 = 128 bytes per vector. The old index stays as it is: 1,536 x 4 + 128 = 6,272 bytes, x 80 million = 502 GB.</p>
<ul>
<li><strong>3,072 dimensions, float32:</strong> 12,416 bytes, 993 GB. Peak 1,495 GB before arrivals. Over the 1.2 TB budget: unreasonable unless the old index leaves RAM or nodes are bought.</li>
<li><strong>1,536 dimensions, float32:</strong> 502 GB. Peak 1,004 GB, plus about 53 GB of arrivals over 14 days: 1,057 GB. Fits, with 12% headroom.</li>
<li><strong>1,024 dimensions, float32:</strong> 4,224 bytes, 338 GB. Peak 840 GB, plus 4.2 million x (6,272 + 4,224) bytes = 44 GB: about 884 GB.</li>
<li><strong>3,072 dimensions, int8 in the graph, float32 on SSD for a rescore:</strong> 3,200 bytes, 256 GB. Peak 758 GB, plus 40 GB of arrivals: about 798 GB.</li>
</ul>
<p><strong>Which choices are reasonable.</strong> The last three, depending on what the comparison shows; that is why the accepted band runs from 700 to 1,100 GB. Unreasonable: full 3,072-dimension float32 (does not fit), and cutting over without running both indexes, which gives a peak of a single index but no rollback and no side-by-side comparison. I would ship 1,024 dimensions if the labelled comparison shows it within noise of 1,536, because it leaves 300 GB of headroom for the window to run long.</p>
<p><strong>The dominant term and the assumption that flips it.</strong> The second index in RAM dominates. The API bill is about $2,000 and can be paid again if a run fails; the memory peak is the term that can stop the switch outright. The assumption that flips the conclusion is the dimension and format of the new index: at full 3,072 float32 the switch cannot happen without hardware, and at int8 it fits with room for a month-long window.</p>
<p><strong>What has to be true before cut-over.</strong> Two different checks. First, the new model must retrieve at least as well as the old on labelled queries: recall@k of the relevant chunks, both models, the same queries, compared per query and per segment, not only in aggregate. OpenAI's own MTEB figures (62.3% against 64.6%) say nothing about this corpus. Second, the new index must find what the new embeddings say is nearest: recall of the HNSW search against exact search on the new vectors, at the production efSearch. A query is embedded with the model of the index it is sent to, and every cache key carries the model version, so no query ever mixes the two spaces.</p>
<p><strong>The failure mode.</strong> The window runs long. Re-embedding finishes, but the comparison finds a segment where the new model loses, and fixing it takes weeks. Every day adds 300,000 chunks to both indexes, 3.8 GB a day at 1,536 dimensions, so the 143 GB of headroom left at day 14 lasts about another 38 days. Set the window and a written rollback trigger before starting: if the comparison is not settled by day 21, drop the new index and stop dual-writing.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Can the old index move to SSD for the window?</em> If the serving path tolerates its latency for the rollback case only, yes, and the peak falls to the new index plus the cache you keep.</li>
<li><em>Why shorten to 1,024 instead of keeping 3,072 at int8?</em> Either can be right; the labelled comparison decides, and int8 adds a rescore read per query.</li>
</ul>

### The calculation

| Item | Arithmetic | Result |
|---|---|---|
| 3-large price | 1 / (9,615 x 800) per token | $0.13 per million tokens |
| Re-embedding, batch | 80M x 400 x $0.13 / 1M x 0.5 | $2,080 |
| Old index | 80M x (1,536 x 4 + 128) | 502 GB |
| New index, 1,024 dims | 80M x (1,024 x 4 + 128) | 338 GB |
| 14 days of arrivals, both | 4.2M x (6,272 + 4,224) | 44 GB |
| Peak | 502 + 338 + 44 | about 884 GB |

## Follow-ups

- *Pushback: finance asks why the switch needs 880 GB when the bill for the model is $2,080. Which half do you cut: the window, the dimension or the rollback path, and what risk do you accept in writing?*
- *Reversal: what result in the labelled comparison would make you stop the migration after paying for the re-embedding?*
- *Two engineers disagree: one wants 1,024 dimensions at float32, the other 3,072 at int8 with a rescore. How do you decide without deciding by rank?* Run both on the same labelled queries and price each in RAM and in p95.
- *The model you are moving from is announced for retirement in 60 days. What do you drop from this plan?*

## Common mistakes

- Pricing the re-embedding and calling that the cost of the switch.
- Mixing query embeddings from one model with documents from the other during the window.
- Comparing the models on a public leaderboard instead of labelled queries from this corpus.
- Sizing the new index from vectors alone and leaving out links and arrivals.
- Starting the window without a date and a rollback trigger.
