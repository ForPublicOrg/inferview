    import math

    # Exact ties go to the lower document id, so a tie resolves the same way in every run of the eval.


    def rrf(rankings, k=60, weights=None, window=None):
        if weights is None:
            weights = [1.0] * len(rankings)
        if len(weights) != len(rankings):
            raise ValueError("one weight per ranking")
        if any(w < 0 for w in weights):
            raise ValueError("weights must be 0 or more")
        if k < 0:
            raise ValueError("k must be 0 or more")
        if window is not None and window < 1:
            raise ValueError("window must be at least 1")
        terms = {}
        for w, ranking in zip(weights, rankings):
            if w == 0:
                continue
            cut = ranking if window is None else ranking[:window]
            seen = set()
            for rank, doc in enumerate(cut, start=1):
                if doc in seen:
                    continue
                seen.add(doc)
                terms.setdefault(doc, []).append(w / (k + rank))
        # fsum rounds once, so the score does not depend on the order the rankings came in.
        scored = [(doc, math.fsum(ts)) for doc, ts in terms.items()]
        scored.sort(key=lambda pair: (-pair[1], pair[0]))
        return scored


    def fused_ids(rankings, k=60, weights=None, window=None, top=None):
        ids = [doc for doc, _ in rrf(rankings, k, weights, window)]
        return ids if top is None else ids[:top]

## Question

<Callout kind="interview" label="Coding, 30 minutes">
"We fuse BM25 and dense results with reciprocal rank fusion, and we want to tune k, the per-retriever weights and the window offline before we touch the engine config. Write the fusion function the tuning loop calls. It runs once per query per grid point, so it has to be fast, and two runs of the eval on the same inputs have to give the same numbers."
</Callout>

The docstring in the starter is the contract. Two parts of it are not in the visible tests: what happens when a ranking repeats an id, and that the result must not depend on the order the rankings are passed in. Ties are yours to order; write the rule in the comment at the top and say why you picked it.

The tuning loop (scenario): 300 eval queries, three retrievers (BM25, a dense model on chunk text and a dense model on titles), 500 candidates each, about 40 grid points per run. One grid point must fuse all 300 queries in under 2 seconds.

## Answer

The reference solution collects each document's terms `w / (k + rank)`, sums each document's list with `math.fsum`, and sorts by `(-score, id)`. Four details carry the problem.

**Cost.** One grid point is 300 queries × 3 rankings × 500 entries = 450,000 contributions. A dict keyed by id makes each one constant time. The version that loops over the union of documents and calls `ranking.index(doc)` per ranking scans up to 500 entries per lookup; on the stated grid point in CPython it took 6.9 seconds against 0.17 seconds for the dict version, and Pyodide is slower than CPython for both.

**Order independence.** RRF is a sum, so it looks order-free, but floating-point addition is not associative. In the hidden test, document X sits at ranks 1, 2 and 7 in the three lists, Y at 2, 7 and 1, and Z at 7, 1 and 2, so their exact scores are equal. Summing left to right in list order gives `(1/61 + 1/62) + 1/67` for X and `(1/67 + 1/61) + 1/62` for Z, and those differ in the last bit. It is not a rare case: of the 9,139 sets of three distinct ranks below 40, 2,121 give different floats depending on the order of addition at k = 60. A one-ulp difference bypasses the tie rule, so the order between X and Z depends on which retriever's list came first. In an eval that order decides precision at a cutoff, and the run stops being repeatable. `math.fsum` rounds the exact sum once, so the same terms give the same float in any order. Exact `Fraction` arithmetic also passes, at about eight times the CPython time of the fsum version on the grid point, which leaves little margin under the 2-second budget in Pyodide.

**The tie rule, two defensible choices.** Ordering ties by id is cheap and reproducible; its cost is a systematic preference, because if ids follow ingestion order, older documents win every tie. Ordering ties by best single rank, then id, prefers a document one retriever was sure about over one that was middling everywhere; its cost is a second key per document and a rule no engine config reproduces. Both pass the tests. No rule at all fails them, because dict insertion order then leaks into the ranking.

**Windows, repeats and missing documents.** The 2009 paper defines each ranking as a permutation of all documents, so every document has a rank in every list. Engines fuse truncated lists, so a document outside a ranking's window gets nothing from it: rank 11 of a 10-wide window counts the same as never retrieved, a penalty the paper's formula did not have. A repeated id, which appears when a retriever returns several chunks of one document, counts once at its first position, and later positions keep their numbers so the other documents' ranks match what the retriever returned.

The visible tests' numbers: d1 (second and first) scores 1/62 + 1/61 = 0.03252 and d3 (first and third) 1/61 + 1/63 = 0.03227. With the BM25 weight at 3, d3 scores 3/61 + 1/63 = 0.06505 and overtakes d1 at 3/62 + 1/61 = 0.06478. At k = 60, y (fourth in both lists) scores 2/64 = 0.03125 against 1/61 = 0.01639 for x, first in one; at k = 1, x scores 1/2 against 2/5 for y.

**Where this solution fails.** It makes permuted ties exact, not every mathematical tie: two documents whose different terms sum to the same rational number can still differ in the last bit. And the k and weights it tunes mean something only in an engine that defines them the same way.

## Follow-ups

- *You tuned weights [3, 1] at k = 60 with this function. What changes when the config is copied into Qdrant?* Qdrant puts the weight inside the rank term, 1 / (k + (r + 1) / w - 1) with zero-based r and a default k of 2, so [3, 1] there makes third place in the first list equal first place in the second. In Elasticsearch, as here, the weight multiplies the score. The same pair of numbers is a different fusion; retune per engine, or put the engine's formula in the loop.
- *Elasticsearch's rank_window_size defaults to 10, and the loop fused 500 per retriever. What does the gap cost?* Every document past rank 10 of a retriever contributes nothing in production. Rerun the grid with the window the engine will use, and keep rank_window_size at least size plus the page offset for paginated results.
- *In a real engine the retrievers run on shards. Where does fusion happen, and what has to be true of each list?* At the coordinating node, after each retriever's per-shard results are merged into one global top window; fusing per shard and merging afterwards gives a different answer.
- *The eval set grows to 3,000 queries and the grid stays at 40 points. Do you keep this code?* At the measured rate that is about 1.7 seconds per grid point and 70 seconds per run in CPython. Store each retriever's ranked list once per query and precompute the rank-to-id arrays, since only k, the weights and the window change between grid points.

## Common mistakes

- Starting ranks at 0, which at small k lets a first place dominate far more than the formula intends.
- Summing raw BM25 and cosine scores instead of ranks.
- Leaving ties to dict order or to whichever retriever answered first, so the eval moves between identical runs.
- Pairing weights with rankings through `zip` without a length check, which silently drops a retriever.
- Tuning k and weights offline with one engine's formula and shipping them to another.
