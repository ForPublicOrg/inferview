  solution: |
    def rrf(rankings, k=60, weights=None):
        if weights is None:
            weights = [1.0] * len(rankings)
        if len(weights) != len(rankings):
            raise ValueError("one weight per ranking")
        scores = {}
        for w, ranking in zip(weights, rankings):
            for rank, doc in enumerate(ranking, start=1):
                scores[doc] = scores.get(doc, 0.0) + w / (k + rank)
        return sorted(scores.items(), key=lambda item: (-item[1], item[0]))

    def fused_ids(rankings, k=60, weights=None, top=None):
        ids = [doc for doc, _ in rrf(rankings, k, weights)]
        return ids if top is None else ids[:top]

## Question

<Callout kind="interview" label="The prompt">
"You have results from BM25 and from a vector search. Merge them into one ranked list. The scores are on different scales, so do not use them. Then let me weight one retriever more than the other."
</Callout>

Implement reciprocal rank fusion. Each document's score is the sum, over the rankings it appears in, of `w / (k + rank)`, where `rank` starts at 1 and `w` is that ranking's weight. A document missing from a ranking gets nothing from it. Sort by score, highest first, and break exact ties by document id so the output is deterministic.

## Hints

<details class="hint"><summary>Hint 1</summary><p>`enumerate(ranking, start=1)` gives you 1-based ranks.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Accumulate into a dict keyed by document id, then sort the items by the pair (negative score, id).</p></details>
<details class="hint"><summary>Hint 3</summary><p>Validate the weights before the loop, so a mismatch fails loudly instead of being silently truncated by `zip`.</p></details>

## Answer

The solution accumulates `w / (k + rank)` per document across rankings, then sorts by `(-score, id)`. Three details are what interviewers check.

**Ranks start at 1.** With 0-based ranks the first document scores `1 / k`, and at small k a first place dominates far more than the formula intends. The test that a lone first place scores 1/61 at k = 60 catches it.

**k controls how much agreement matters.** In the test, "y" is fourth in both lists and "x" and "z" are each first in one. At k = 60, "y" scores 2/64 = 0.03125 against 1/61 = 0.0164 for "x", so agreement wins. At k = 1, "x" scores 1/2 = 0.5 against 2/5 = 0.4 for "y", so being first anywhere wins. The 2009 paper fixed k = 60 after a pilot and found it "not critical"; Elasticsearch defaults to 60 and Qdrant to 2, so the same code gives different fusions depending on where it runs.

**Weights and validation.** `zip` silently stops at the shorter list, so a missing weight would drop a whole retriever without an error. Checking lengths first turns a silent quality bug into an exception.

With the default lists, "d1" (second and first) scores 1/62 + 1/61 = 0.03252 and "d3" (first and third) scores 1/61 + 1/63 = 0.03227, so "d1" edges ahead. With BM25 weighted 3, "d3" scores 3/61 + 1/63 = 0.06505 and overtakes "d1" at 3/62 + 1/61 = 0.06478.

## Follow-ups

- *How many results from each retriever do you fuse?* Set it explicitly. Elasticsearch's `rank_window_size` defaults to 10, so a fusion of "top 100 from each" needs the window raised.
- *When would you use score fusion instead?* When scores are calibrated or you have training data to learn a combination. Min-max normalisation is fragile when one list's scores are bunched together.
- *What comes after fusion?* A reranker over the fused top N, with N set by the latency and cost budget.

## Common mistakes

- 0-based ranks.
- Fusing raw scores ("just add BM25 and cosine").
- Non-deterministic tie-breaking, which makes eval results flicker between runs.
- Forgetting that a document absent from one list contributes 0 from it, not a penalty.
