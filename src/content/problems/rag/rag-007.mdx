## Question

<Callout kind="interview" label="The prompt">
"The model just cited a policy we deleted last week. Why did that happen, and how do you stop it?"
</Callout>

HR deleted the 2024 remote-work policy at 14:05 UTC on 20 October and published a new one. On 27 October an employee asks how many remote days are allowed and gets the old answer, with a citation. The index is a pgvector table. You have the sync job, the store, two nights of job logs and one request trace.

```python
def sync(state):
    since = state.last_run
    for change in source.changes(since=since):
        if change.kind == "deleted":
            store.delete([change.doc_id])
            stats["deleted"] += 1
            continue
        doc = source.get(change.doc_id)
        for i, text in enumerate(chunk(doc.text)):
            store.upsert(
                id=f"{doc.id}:{i}",
                vector=embed(text),
                text=text,
                meta={"doc": doc.id, "version": doc.version},
            )
        stats["upserted"] += 1
    state.last_run = datetime.now(timezone.utc)
    log.info("sync since=%s %s ok", since, stats)


class ChunkStore:
    def delete(self, ids):
        with self.conn.cursor() as cur:
            cur.execute("DELETE FROM chunks WHERE id = ANY(%s)", (ids,))

    def upsert(self, id, vector, text, meta):
        with self.conn.cursor() as cur:
            cur.execute(
                "INSERT INTO chunks (id, embedding, text, meta) VALUES (%s, %s, %s, %s) "
                "ON CONFLICT (id) DO UPDATE SET embedding = EXCLUDED.embedding, "
                "text = EXCLUDED.text, meta = EXCLUDED.meta",
                (id, vector, text, Json(meta)),
            )
```

## Answer

The delete path exists and runs, and deletes nothing. Chunk rows are written as `hr-remote-2024:0`, `hr-remote-2024:1` and so on; the delete is issued with the bare document id, `WHERE id = ANY(['hr-remote-2024'])` matches zero rows, Postgres does not treat that as an error, and the job increments `deleted` for the call, not for rows. The log for the 21 October run says `deleted: 1 ok`, which is what makes this survive review: every signal anyone looks at says deletes work. The old and new policies are about the same topic, the old one scores slightly higher on this question, and the model does what it was told with the top chunk.

**What the evidence does not show, and what to collect.** The log does not say which document the one delete was for. Before fixing, pull the change feed between 02:11:37 on 20 October and 02:12:05 on 21 October and confirm it holds `hr-remote-2024` as `deleted`; if it does not, the source never reported the deletion and the defect is upstream. Then count the orphans: rows whose `meta->>'doc'` is not among the source's current ids. If you cannot get the feed (retention ran out), the fix below is safe either way, because it deletes by document and adds a reconciliation that does not depend on the feed.

**The fix.**

1. Delete by document: `DELETE FROM chunks WHERE meta->>'doc' = %s`, with an index on that expression, and log the rows deleted, not the calls. A delete that removes zero rows for a document the index has seen is a warning.
2. Make an edit replace the document's chunks in one transaction: delete every row for the document, insert the new chunks, commit. That also fixes the second defect below. pgvector lives in Postgres, so this is one transaction; with a vector store that has none, write the new version under versioned ids and delete the old version after.
3. Reconcile nightly: list source ids, list `meta->>'doc'` values, delete the difference. Change feeds lose events, and this would have caught the bug on its first night.
4. Add eval questions about recently deleted and edited documents, and assert the old answers do not come back.

**The other defects, ranked.**

- *Positional ids on edits* (second). When a document shrinks from 12 chunks to 9, rows `:9` to `:11` keep the old text forever. Same symptom class, different document: any edited document can be cited from its old tail. It will happen to the next policy that is shortened.
- *Cursor saved at job end* (third). `state.last_run` is taken after the loop, so a change that lands between the feed read and the end of the run is never seen. The 20 October run ended at 02:11:37 and the deletion was at 14:05, so not this time. Fix by saving the feed's own position, or the time the read started minus a margin, and relying on idempotent upserts for the overlap.
- *Semantic cache and HNSW* are not defects here. The trace shows `cache: miss`. In pgvector a deleted row leaves dead tuples that can reduce the number of results until vacuum, but they are not returned; the problem here is that the row was never deleted.

## Follow-ups

- *Legal says a deleted policy must be unsearchable within 24 hours. Which of your fixes meets that on its own, and what do you alert on?*
- *The reconciliation would delete 30 percent of the index tonight because the source listing API timed out halfway. What stops it?*
- *The same store holds access-control labels in `meta`. What does this bug do to a document whose permissions were revoked rather than deleted?*

## Common mistakes

- Concluding deletes work because the job logs a delete count; it counts calls.
- Adding "prefer the newest document" to the prompt, which leaves the deleted text retrievable.
- Fixing the delete id and leaving the positional tails of edited documents.
- Treating a nightly full re-index as the fix; it hides the broken delete path and grows with the corpus.
