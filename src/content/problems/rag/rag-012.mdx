## Question

<Callout kind="interview" label="The prompt">
"We have three assistants to build on the same model. For each one, do we put the documents in the window, cache them as a prefix, or build retrieval? Give me a cost per query for each option you consider."
</Callout>

The workloads (scenario):

1. **HR handbook.** 150,000 tokens, edited about once a week, readable by every employee. 20,000 questions a day, all between 08:00 and 18:00.
2. **Contract review.** A lawyer uploads one 60-page contract and asks about six questions over 25 minutes, sometimes with gaps over five minutes while reading. Typical questions: "which clauses conflict with the indemnity cap?" and "where does the termination notice period differ from the master agreement?"
3. **Support knowledge base.** 40,000 articles, 30 million tokens, updated hourly. Customers see the articles for their plan, one of three. 200,000 questions a day.

The model is Claude Sonnet 5.5 for all three: $2 per million input tokens, $0.10 per million for cache reads, $2.50 per million for 5-minute cache writes, $4 per million for 1-hour cache writes, a 1M-token window billed at the standard rate (prices checked 2026-10-28). Output is the same for every option, so price the input side.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each workload, ask how many requests arrive in a five-minute window at the quietest hour you still serve.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which users may read which documents, and whether that ever changes inside one session.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request an accuracy measurement on your own questions at the full prompt length, not a needle score.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Handbook: a cached prefix or retrieval are both defensible; the cached prefix costs $0.015 of input per question against about $0.008 for retrieval, $132 a day more, and saves running a retrieval stack, so I choose by accuracy at 150,000 tokens on our own questions. Contracts: the whole contract in the window, cached for the session, because the questions span clauses and one document is small; about $0.018 per question against $0.072 uncached. Knowledge base: retrieval with a plan filter, because 30 million tokens do not fit, the corpus changes hourly and visibility differs by plan.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Handbook.</strong> Uncached, every question sends 150,000 × $2 / 1M = $0.30. As a cached prefix it reads 150,000 × $0.10 / 1M = $0.015. At 20,000 questions over ten hours, about 33 a minute, the 5-minute cache never goes cold during the day; it is written each morning and after each weekly edit at 150,000 × $2.50 / 1M = $0.375, which is noise. Retrieval of six 700-token chunks is 4,200 tokens, $0.0084, plus the embedding pipeline and index. The gap is ($0.015 − $0.0084) × 20,000 = $132 a day. That buys not having a chunker, an index, retrieval evals and a re-embedding job, and it buys whole-handbook context for questions such as "what changes for me if I move to part-time", which touch several sections.</p>
<p>What it does not buy is accuracy for free. Chroma's Context Rot report found performance falling with input length across 18 models, and on LongMemEval every model scored significantly higher with a focused prompt of about 300 tokens than with the full prompt of about 113,000. HELMET found needle tests do not predict downstream performance. So the deciding measurement is our own question set run both ways at the real prompt length. If the cached prefix is within noise of retrieval, I ship the prefix. If it is not, retrieval, and the $132 a day goes the other way.</p>
<p><strong>Contracts.</strong> The quantity to choose is tokens per page. Anything from 500 to 800 is defensible for dense legal text; at 600, the contract is 36,000 tokens. Uncached, 36,000 × $2 / 1M = $0.072 per question, $0.43 a session. Cached for 5 minutes: one write at $0.09 and five reads at $0.0036, $0.108 a session, $0.018 a question. Each gap over five minutes turns a $0.0036 read into a $0.09 rewrite, $0.0864 more. The 1-hour cache writes at $0.144, $0.054 more up front, so it pays when sessions average more than 0.054 / 0.0864 = 0.625 long gaps; read the gap distribution from the session logs and pick. Retrieval is the wrong tool here: the questions are about relations between clauses, the document fits many times over, and chunking a contract per upload adds indexing latency before the first question.</p>
<p><strong>Knowledge base.</strong> 30 million tokens is 30 times the window, so stuffing is out before cost. Retrieval of eight 600-token chunks is 4,800 tokens, $0.0096 a question, with the system prompt and instructions as a small cached prefix. The plan filter goes into the retrieval query. Hourly updates re-embed only the changed articles.</p>
<p><strong>The conflict.</strong> Cost against quality, with freshness and access control as hard limits. Caching moved the cost line: a long prefix that is read thousands of times an hour costs about twice retrieval, not 36 times. It did not move the quality line or the access line.</p>
<p><strong>Where the recommendations fail.</strong> The handbook prefix assumes everyone reads everything. The day HR adds a managers-only section, the options are one cached prefix per permission group (two writes a morning instead of one, and a second prompt to keep in sync) or retrieval with a filter, and the cost argument for the prefix weakens with every group. The contract plan assumes 60 pages. A 400-page master agreement with schedules is about 240,000 tokens at the same density: $0.024 a cached read, still affordable, but it is the length at which the measured accuracy, not the price, has to be rechecked.</p>
</Fragment>

## Follow-ups

- *Pushback: the handbook eval shows the cached prefix two points below retrieval on accuracy, within the confidence interval of a 200-question set. Finance prefers the cheaper option and product prefers the simpler one. What do you ship, and what do you write down?*
- *Reversal: what would you need to see in production to move the contract assistant from long context to retrieval?* Sessions where documents routinely run past the length at which your eval accuracy drops, or questions that cite clauses in other contracts the user did not upload.
- *Legal asks whether caching the handbook means one employee's request can see another's. What do you answer?* The cached prefix is the handbook, identical for everyone, and caches are isolated by organization and workspace; personal fields placed after the prefix are never shared. The answer changes the day personal data enters the prefix.

## Common mistakes

- Comparing uncached long context, $0.30 a question, with retrieval and calling retrieval 36 times cheaper.
- Putting per-user or per-request text (date, user name, locale) before the long document and getting no cache hits.
- Treating a needle-in-a-haystack score at 1M tokens as evidence the model will answer handbook questions at 150,000.
- Proposing one shared cached prompt for a corpus with per-plan or per-role visibility.
- Building a retrieval pipeline per uploaded contract when the questions are about how clauses relate.
