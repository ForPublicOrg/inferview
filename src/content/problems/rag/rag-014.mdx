## Question

<Callout kind="interview" label="The prompt">
"Our RAG system returns the correct documents but the LLM still gets the answers wrong. Diagnose and fix."
</Callout>

You have a 40-question eval set with gold chunk ids. The numbers below are from your own runs (scenario):

```text
recall@5 of the reranked list           36 / 40  (0.90)
gold chunk present in the final prompt  14 / 40  (0.35)
answer correct, pipeline as deployed    15 / 40
answer correct, oracle context          34 / 40   (gold chunks placed directly in the prompt)
```

The context builder:

```python
def build_context(question, budget_tokens=1500):
    hits = hybrid_search(question, top_k=20)
    reranked = rerank(question, hits)                  # list of (chunk, score); higher score is better
    ordered = sorted(reranked, key=lambda pair: pair[1])
    context, used = [], 0
    for chunk, score in ordered:
        if used + chunk.tokens > budget_tokens:
            break
        context.append(chunk.text)
        used += chunk.tokens
    return "\n\n".join(context)
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>Two of the four numbers disagree with each other in a way that points at one function.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which way does Python's `sorted` order by default?</p></details>

## Answer

`sorted(reranked, key=lambda pair: pair[1])` sorts ascending, so the chunks the reranker liked least come first and the token budget fills with them. The best chunks are cut. That explains every number: the reranked list contains the gold chunk for 36 questions (recall@5 is measured before this function), but only 14 prompts contain it; the deployed pipeline gets 15 right; and with the gold chunks placed in the prompt, 34 are right. In Barnett et al.'s taxonomy this is FP3, Not in Context: retrieved, then lost during consolidation.

The fix is `sorted(reranked, key=lambda pair: pair[1], reverse=True)`, plus a test that asserts the highest-scored chunk is the first one in the built context, plus a metric for "gold in prompt" next to recall@k in the eval report, so retrieval and context assembly are measured separately from now on.

After the fix, the ceiling is the oracle run: 34 of 40. The remaining 6 fail with perfect evidence and are generation problems to triage separately.

Why the wrong picks are tempting. "Answer only from the context" is the reflex for anything called hallucination, and it changes nothing when the evidence is not in the prompt. Chunk size is a common cause of incomplete answers, but the oracle run uses the same chunks. Lost in the middle is a real effect on some models, but there is nothing in the middle to lose when the gold chunk was cut.

## Follow-ups

- *Which metric would have caught this on day one?* "Gold chunk in final prompt" per question. recall@k on the retriever output cannot see anything that happens after retrieval.
- *The budget is 1,500 tokens. Is that the next problem?* Possibly; once sorting is fixed, check how often the gold chunk is at reranked position 4 or 5 and still cut by the budget.
- *How do you verify faithfulness after the fix?* Score claims in the answers against the context actually sent, and report it beside correctness, because a faithful answer to a stale chunk is still wrong.

## Common mistakes

- Trusting recall@k as the measure of what the model saw.
- Tuning the prompt before running oracle context.
- Fixing the sort without adding a test or a "gold in prompt" metric, so the next refactor breaks it again.
