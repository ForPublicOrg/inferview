## Question

<Callout kind="interview" label="The prompt">
"Our RAG system returns the correct documents but the model still gets the answers wrong. Diagnose and fix."
</Callout>

The system, the release and the numbers are a scenario. Release 2.14 went out on Tuesday with three changes: the rerank client moved from v1 to v2, whose changelog says `rerank()` now returns `(chunk, relevance_score)` pairs in the order the candidates were passed in; the context builder was adjusted for that; and the chunker was retuned. Answers got worse the same day. The release also carries the v2 client because v1 stops being served on Friday.

You have a 40-question eval set with gold chunk ids, remapped to the new chunks by span overlap. Your own runs:

```text
                                                before 2.14    after 2.14
recall@5 of the reranked list                   35 / 40        36 / 40
gold chunk present in the final prompt          33 / 40        14 / 40
answer correct, pipeline as deployed            30 / 40        15 / 40
answer correct, oracle context                  35 / 40        31 / 40   (gold chunks placed directly in the prompt)
```

The diff:

```diff
--- a/rag/chunking.py
+++ b/rag/chunking.py
-CHUNK_TOKENS, OVERLAP_TOKENS = 400, 80
+CHUNK_TOKENS, OVERLAP_TOKENS = 250, 0

--- a/rag/context.py
+++ b/rag/context.py
 from operator import itemgetter
-from rerank_client.v1 import rerank
+from rerank_client.v2 import rerank

 def build_context(question, budget_tokens=1500):
-    hits = hybrid_search(question, top_k=20)
+    hits = hybrid_search(question, top_k=30)
     reranked = rerank(question, hits)
+    ordered = sorted(reranked, key=itemgetter(1))
     context, used = [], 0
-    for chunk, score in reranked:
+    for chunk, score in ordered:
         if used + chunk.tokens > budget_tokens:
             break
         context.append(chunk.text)
         used += chunk.tokens
     return "\n\n".join(context)
```

Which defect explains the drop from 30 to 15? Then rank the other changes, say what you would collect before Friday, and choose the regression threshold you would put on "gold in prompt" in CI.

## Answer

`sorted(reranked, key=itemgetter(1))` sorts ascending. v1 returned pairs best first, so the old loop needed no sort; v2 returns them in input order, the sort was added to restore best first, and it restored worst first. The budget of 1,500 tokens holds six 250-token chunks, and they are the six weakest of 30 candidates. The `top_k` change from 20 to 30 makes this worse, not better: there are more weak candidates to fill the budget with.

The numbers say the same thing without reading the code. recall@5 is measured on the reranked list and held at 36 of 40, so the reranker still puts the gold chunk near the top. Gold in the prompt fell from 33 to 14, so something between the reranker and the prompt lost it. Correctness fell from 30 to 15, tracking the prompt rather than the reranker. In Barnett et al.'s list this is FP3, Not in Context: retrieved, then lost during consolidation.

**Ranking the rest.** The chunker change is a real defect and second. Its cost shows in the oracle row: with perfect evidence the ceiling fell from 35 to 31, so 4 questions now need two 250-token chunks where one 400-token chunk with overlap used to hold the answer, which surfaces as Incomplete answers once the sort is fixed. The `top_k` change is neutral with a correct sort and harmful with this one. The v2 client is not a defect; its contract changed and the builder read it wrong.

**What the evidence does not show.** The table cannot say how many of the 26 missing gold chunks were cut by the sort and how many by the budget, since 250-token chunks leave room for six. Collect the reranker position of each chunk in the prompt (Hint 2): with the sort fixed, a gold chunk at position 7 or lower is the budget's doing. Collect the oracle run with the old chunks on the new release (Hint 3) to confirm the 4-question cost belongs to the chunker and not to the label remapping.

**What to ship before Friday, without that evidence.** Rolling back 2.14 puts the system on a client that stops on Friday, so fix forward: `sorted(reranked, key=itemgetter(1), reverse=True)`, a unit test that the highest relevance score is the first chunk in the built context, and the chunker reverted to 400 and 80 in the same release, because its cost is measured and its benefit is not. The failure mode of this fix: the test pins today's reading of v2's contract. If a later client returns a distance instead of a relevance score, `reverse=True` is wrong again and the unit test, written against a stub, still passes. The guard against that is the CI metric, not the unit test.

**The CI threshold is yours to choose.** On 40 questions one question is 2.5 points. Failing the build when "gold in prompt" drops by 3 or more questions against the last release is reasonable, and so is 2 if retrieval is deterministic; failing on any drop of 1 blocks releases on label noise and remapping, and a threshold of 5 or more would have let a smaller version of this bug through. Gate it as a fraction of recall@5, so a retrieval change does not trip the context check.

## Follow-ups

- *With the sort fixed, gold in prompt comes back to 30 of 40 and recall@5 is 36. Is the remaining gap the budget, and what do you measure before raising it?* The reranker position of each gold chunk that missed: if they sit at positions 7 to 10, the budget cut them; then measure correctness at budgets of 1,500 and 2,500 tokens, since more context also adds distractors.
- *The product manager wants the smaller chunks kept because citations look tidier in the UI. What would you need to see to keep them?* An oracle ceiling back at 35 with 250-token chunks, for example with overlap restored or neighbouring chunks expanded at assembly time.
- *Why did recall@5 not catch this, and should you drop it?* It measures the reranker's output, which was correct. Keep it, and report gold in prompt beside it so the stage between them is measured.

## Common mistakes

- Trusting recall@k as the measure of what the model saw.
- Tuning the prompt before running oracle context.
- Reverting the whole release when the client it carries stops being served on Friday.
- Fixing the sort and leaving the chunker change, whose cost is already in the oracle row.
- Adding a unit test and no "gold in prompt" metric, so the next contract change breaks it again.
