## Question

<Callout kind="interview" label="The prompt">
"What do M, efConstruction and efSearch control in HNSW? Pick values for our service, and tell me where HNSW becomes hard to operate."
</Callout>

The service is a scenario: 20 million chunks, 768-dimension float32 embeddings, one RAM-resident HNSW index per replica on nodes with 96 GB of RAM. The target is recall@10 of 0.95 against exact search, inside a 30 ms p95 for the search call. About 200,000 chunks are added and 150,000 deleted each day, and a customer can ask for their data to be removed.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the bytes per node, vector and links separately, and compare the total with the RAM on a replica.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request a recall-against-latency curve on logged queries, and ask which of the three knobs that curve can be redrawn for without a rebuild.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what happens to a deleted chunk in this index, and how long until its memory comes back.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>M is the number of links per node: it sets memory and how navigable the graph is, and changing it means a rebuild. efConstruction is the candidate list used while inserting: it buys graph quality with build time, and also needs a rebuild. efSearch is the candidate list at query time: it trades latency for recall per query and can change at any time, so it is the knob you tune against a recall curve. For this service I would build with M 16 and an efConstruction between 64 and 100 (pgvector's and Qdrant's defaults), then sweep efSearch upward from 40 on logged queries until recall@10 reaches 0.95, and take the first value inside 30 ms. HNSW gets hard to operate at deletes, rebuilds and memory: the graph has to stay in RAM, deletes leave dead nodes until a vacuum or rebuild, and any change to M, efConstruction or the embedding model means building 20 million nodes again.</p>
</Fragment>
<Fragment slot="long">
<p><strong>What each knob costs, computed.</strong> Faiss gives HNSW memory as d x 4 + M x 2 x 4 bytes per vector. At 768 dimensions the vector is 3,072 bytes. M 16 adds 128 bytes of links, 3,200 bytes in all, and 20 million nodes take 64 GB; M 32 takes 66.6 GB; M 64 takes 71.7 GB. At this dimension the links are 4 to 14 percent of the index, so M is not a memory decision here. It becomes one when vectors are compressed: a 768-bit binary code is 96 bytes, and M 16's 128 bytes of links are then bigger than the vector.</p>
<p><strong>The choice I would defend.</strong> 64 GB on a 96 GB node leaves room for the process, the OS and a second index during a rebuild only if the rebuild happens on another node, which decides how rebuilds work before they are needed. Start at M 16. Take efConstruction at 64 to 100; higher builds a better graph more slowly, and the only way to know whether it helps this data is to build twice and compare recall at equal efSearch. Then sweep efSearch at 40, 64, 100, 160 and 256 against exact top-10 on a few hundred logged queries, and pick the smallest value that reaches 0.95 inside 30 ms. If none does, the order of moves is: check the embedding and the queries first, then raise M with a rebuild, then compress the vectors and rescore. A value of efSearch picked without the sweep, or a default quoted as if it were a property of HNSW, is not an answer.</p>
<p><strong>Where it becomes hard to operate.</strong></p>
<ul>
<li><strong>Deletes.</strong> Removing a node from a navigable graph means repairing the links of everything that pointed to it. Faiss's HNSW does not support direct removal; pgvector marks rows dead and repairs the graph in vacuum, which its README says can be slow enough to reindex first. At 150,000 deletes a day, dead nodes accumulate between vacuums, take memory, and take slots in the candidate list. A customer removal request has to be answered from the results layer the same day, and from the index on the vacuum schedule.</li>
<li><strong>Rebuilds.</strong> M, efConstruction and the embedding model are fixed at build time. A rebuild of 20 million nodes needs a second copy of the index in memory somewhere, and pgvector's README says builds are faster when the graph fits in <code>maintenance_work_mem</code>, so a 64 GB graph is a memory plan, not a command.</li>
<li><strong>Filters.</strong> The graph knows nothing about metadata. A selective filter applied after the scan leaves too few results, which turns a tuning problem into a design problem.</li>
<li><strong>Recall is an average.</strong> 0.95 over a query sample can hide queries with recall near zero, often in sparse regions or between tight clusters, the data on which the paper says its neighbour-selection heuristic matters.</li>
</ul>
<p><strong>The constraint conflict</strong> is memory and build time against recall. Every move that raises recall without touching efSearch costs a rebuild, and every rebuild needs headroom this node does not have.</p>
<p><strong>The failure mode of this answer.</strong> efSearch is tuned once, on the data and queries of the day it was tuned. Six months of inserts in new regions, deletes waiting for vacuum, and a shift in what users ask move the curve, and recall at the chosen efSearch falls with no alert. Run the sweep as a scheduled job against exact search on a fresh sample, and alert when recall at the production efSearch drops below the target.</p>
</Fragment>

## Follow-ups

- *Why does efConstruction help recall if search never uses it?* It decides which links exist; a link that was never made cannot be followed at any efSearch.
- *Your sweep says efSearch 100 meets the target on English queries and misses it on German ones. One setting or two?* efSearch is per query, so the router can set it per language; measure the cost before adding a second code path.
- *You switch to binary codes with a full-precision rescore. Does M 16 still make sense?* The links now outweigh the codes, so test M 8 and M 12 at the recall target before keeping 16.

## Common mistakes

- Treating M as the first recall knob when efSearch needs no rebuild.
- Sizing the index from the vectors alone and finding the links only after compression.
- Quoting one library's defaults as if they were the algorithm's.
- Measuring recall once at launch and never again.
- Treating a delete as instant because the row disappeared from the results.
