  solution: |
    from array import array
    from heapq import nsmallest
    from operator import mul

    # Storage: one flat float32 array for every token vector and a (start, count) span per document, so a vector costs
    # 4 bytes per dimension instead of a list of Python floats. Scores from the index carry float32 rounding.
    # Ties: equal scores come back in the order the documents were first added.
    # Re-adding an id replaces its document; the old vectors stay in the array until compact() rebuilds it.


    def _check(vectors, dim, what):
        if not vectors:
            raise ValueError(f"empty {what}")
        for v in vectors:
            if len(v) != dim:
                raise ValueError(f"{what} vector has {len(v)} dimensions, expected {dim}")


    def maxsim(query, doc):
        if not query or not doc:
            raise ValueError("query and doc need at least one vector each")
        dim = len(query[0])
        _check(query, dim, "query")
        _check(doc, dim, "doc")
        return sum(max(sum(map(mul, q, d)) for d in doc) for q in query)


    class LateIndex:
        def __init__(self, dim):
            if dim <= 0:
                raise ValueError("dim must be positive")
            self.dim = dim
            self._data = array("f")
            self._spans = {}       # doc_id: (first vector, vector count), in first-insertion order
            self._live = 0

        def add(self, doc_id, vectors):
            _check(vectors, self.dim, "doc")
            start = len(self._data) // self.dim
            for v in vectors:
                self._data.extend(v)
            if doc_id in self._spans:
                self._live -= self._spans[doc_id][1]
            self._spans[doc_id] = (start, len(vectors))
            self._live += len(vectors)
            if len(self._data) // self.dim > 2 * self._live:
                self.compact()

        def compact(self):
            data, spans = array("f"), {}
            for doc_id, (start, n) in self._spans.items():
                spans[doc_id] = (len(data) // self.dim, n)
                data.extend(self._data[start * self.dim:(start + n) * self.dim])
            self._data, self._spans = data, spans

        def _score(self, query, start, n):
            dim, data = self.dim, self._data
            rows = [data[(start + i) * dim:(start + i + 1) * dim] for i in range(n)]
            return sum(max(sum(map(mul, q, row)) for row in rows) for q in query)

        def search(self, query, k):
            _check(query, self.dim, "query")
            if k <= 0:
                return []
            scored = ((-self._score(query, s, n), pos, doc_id)
                      for pos, (doc_id, (s, n)) in enumerate(self._spans.items()))
            return [(doc_id, -neg) for neg, _, doc_id in nsmallest(k, scored)]


    def footprint(n_vectors, dim, bits=None):
        if n_vectors < 0 or dim <= 0:
            raise ValueError("n_vectors must be 0 or more and dim positive")
        if bits is None:
            return n_vectors * dim * 2
        if bits not in range(1, 9):
            raise ValueError("bits must be 1 to 8")
        return n_vectors * (4 + -(-dim * bits // 8))

## Question

<Callout kind="interview" label="Coding round">
"Our dense retriever misses on part-number and error-code queries. Someone proposes ColBERT. Write the scoring and a small index we can run experiments on, then tell me what the production index would weigh."
</Callout>

Write three things.

- `maxsim(query, doc)`: the late-interaction score. Each query token vector takes its largest dot product with any document token vector, and the score is the sum of those maxima.
- `LateIndex(dim)` with `add(doc_id, vectors)` and `search(query, k)`, returning up to k `(doc_id, score)` pairs, best first.
- `footprint(n_vectors, dim, bits=None)`: bytes for the token vectors, either 16-bit floats per dimension or the ColBERTv2 encoding of a 4-byte centroid id plus a residual of `bits` bits per dimension.

The constraint: the visible tests add 2,500 documents of 8 token vectors each at 32 dimensions, every vector a fresh list of Python floats, and the index may retain at most 4,000,000 bytes as measured by `tracemalloc`. That is 200 bytes per vector.

Three decisions are yours, and the docstring states them: how the index stores vectors (and so how much precision its scores keep), how `search` orders equal scores, and what `add` does with an id that is already present. The hidden tests accept any precision whose scores land within 0.01 of the exact MaxSim, any tie order that is the same on every call, and either replacing a re-added document or raising `ValueError`.

Then the arithmetic, for the production corpus (scenario): 12 million passages averaging 70 tokens, 128-dimension token vectors, one node with 64 GB of RAM for the index. What does the index weigh at 16 bits, at 2 bits and at 1 bit, and which would you ship?

## Answer

`maxsim` is a direct transcription: for each query vector, the maximum over document vectors of the dot product, summed. The validation matters more than it looks. A query vector of the wrong length would otherwise be silently zipped against shorter document vectors by `map`, and the score would be wrong with no error.

The index is where the memory budget bites. A list of 32 Python floats is a list object plus 32 separate float objects; in CPython 3.12.6 on a 64-bit machine the straightforward index that keeps the lists it was given retained 22,044,896 bytes for the 20,000 test vectors, about 1,100 bytes per vector, five times the budget. Converting each vector to a tuple keeps the float objects and retained 21,726,168. One `array('d')` per vector retained 7,167,808 and one `array('f')` per vector 4,607,808, both still over, because every array object carries its own header. The reference keeps one flat `array('f')` for the whole corpus, 4 bytes per dimension, and a `(start, count)` span per document id; it retained 3,042,872 bytes. Pyodide is a 32-bit build, so object headers are smaller there, and the list-of-floats version still fails.

The cost of float32 is precision: scores from the index differ from the exact float64 MaxSim by rounding, which is why the tests compare within a tolerance and why the hidden top-k check accepts any document whose exact score is within 0.01 of the k-th best. Storing 16-bit floats (via `struct` with format `e`) halves the memory again at a larger rounding error, still inside the tolerance at these dimensions.

The reference's policies: equal scores come back in first-insertion order, by carrying the insertion position into the heap key, so `nsmallest` never compares two document ids of different types; re-adding an id replaces the document, and the stale vectors stay in the array until more than half of it is dead, when `compact()` rewrites it. Raising instead is equally valid and simpler; it pushes updates onto the caller as delete-and-add.

Search is exhaustive: every document is scored, and `heapq.nsmallest` keeps the top k in O(n log k). That is fine for experiments on thousands of documents and hopeless for millions, which is what PLAID and MUVERA exist for.

**The production arithmetic.** 12,000,000 × 70 = 840,000,000 token vectors.

- 16-bit floats, 256 bytes per vector: 840M × 256 = 215.0 GB.
- 2-bit residuals, 4 + 32 = 36 bytes: 840M × 36 = 30.2 GB.
- 1-bit residuals, 4 + 16 = 20 bytes: 840M × 20 = 16.8 GB.
- For comparison, one 768-dimension float32 vector per passage: 12M × 3,072 = 36.9 GB.

These are the vectors alone. ColBERTv2's MS MARCO figures (154 GiB uncompressed, 16 or 25 GiB compressed at 1 or 2 bits) include 4.5 GiB of inverted list from centroid to vectors, so budget a few more GB for ours, plus the centroid table.

**The decision.** Two answers are defensible on a 64 GB node.

- 2-bit residuals: about 30 GB plus the inverted list fits with headroom for the process and growth. The ColBERTv2 paper reports that this encoding largely preserves quality. The cost is the engine: compressed late interaction needs PLAID-style candidate generation and decompression, which few managed vector stores offer, so the team runs its own index.
- Stay single-vector and add a cross-encoder reranker over the top 100. About the same storage as 2-bit late interaction, an index any vector store serves, and a reranker that sees the query and passage together. The cost is reranker latency on every query and a candidate set that still comes from the dense retriever, which is the stage that missed the part numbers.

1-bit residuals are reasonable when memory is the binding constraint and a quality drop on your own eval set is measured and accepted. 16 bits is not reasonable on this node: 215 GB does not fit, and memory-mapping it from disk moves the cost to random reads at query time.

The conflict is memory against recall: the 2-bit index costs nearly twice the 1-bit one for quality you can only price with your own eval set. I would build the 2-bit index on a 10 percent sample, compare recall at 10 against the dense retriever plus reranker on the part-number and error-code queries that started this, and choose on that.

**Where the recommendation fails.** Residual compression assumes the centroids describe the corpus. ColBERTv2 picks them from the embeddings at indexing time, a number proportional to the square root of the embedding count. Passages added later from a new domain, a product line with its own vocabulary, land far from every centroid, their residuals saturate the one or two bits, and their scores degrade without any error. Track recall on new-domain queries and re-cluster when it drifts, which is a full re-index.

## Follow-ups

- *What changes to run this in a real engine?* Vectors live in one memory-mapped array per shard; scoring is a matrix product of the query matrix against candidate documents' token matrices on a GPU or with SIMD, not Python loops; candidates come from the inverted list (centroid to passages) rather than a scan, with PLAID's centroid pruning before any residual is decompressed; updates go to a small uncompressed delta index merged on a schedule.
- *Your 2-bit index costs as much RAM as the single-vector index plus reranker, and the reranker is a library call. Which do you build first, and what result makes you build the other?*
- *What would you need to see on the eval set to drop late interaction and ship BM25 plus dense with a reranker instead?* A recall gap on the part-number and error-code queries smaller than the run-to-run noise of the eval, once BM25 is in the hybrid, since exact-token queries are what BM25 already matches.
- *Two senior engineers disagree: one wants MUVERA so the index fits a standard vector store, the other wants PLAID for its reported latency. How do you decide without deciding by rank?* Both papers report against different baselines and corpora; run both on the same shard and query log, and compare recall at 10, p95 latency and the operational work each adds.

## Common mistakes

- Averaging the per-token maxima instead of summing them; the ranking is the same for one query, but scores then cannot be compared across queries of different lengths in logs.
- Taking the best document vector once per document instead of once per query vector.
- Counting passages instead of tokens when sizing the index, which underestimates it by the average passage length.
- Keeping the caller's lists of floats in the index and meeting the memory budget only on small tests.
- Quoting the 6 to 10 times compression ratio without the inverted list that the paper's own figures include.
