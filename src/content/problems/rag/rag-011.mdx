## Question

<Callout kind="interview" label="The prompt">
"Design a RAG system for a customer support chatbot: 5 million documents, 300 QPS, p95 latency under 1.2 seconds, budget under $0.002 per query." The interviewer narrows it: "How many retrieved candidates can you afford to rerank?"
</Callout>

Use these inputs. The ones marked scenario are numbers you would get from your own load tests and invoices; they are not published figures.

- Retrieval (query embedding plus hybrid search) at p95: 150 ms (scenario).
- Generation at p95: 800 ms (scenario).
- Reranker p95 latency: 50 ms plus 4 ms per candidate, measured under load (scenario).
- Generation cost: $0.0012 per query on average (scenario).
- Reranker: Cohere Rerank 5 Pro at $0.05 per million tokens, with query and document tokens both billed. Each candidate is a 40-token query plus a 400-token chunk.

Estimate the largest number of candidates you can rerank per query.

## Hints

<details class="hint"><summary>Hint 1</summary><p>There are two budgets, latency and money. Compute the candidate limit from each and take the smaller.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For latency, subtract everything that is not the reranker from 1,200 ms first.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For cost, one candidate is 440 tokens at $0.05 per million.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>About 36. Latency leaves 1,200 - 150 - 800 = 250 ms for reranking, and 50 + 4N under 250 gives N up to 50. Money leaves $0.002 - $0.0012 = $0.0008 per query, and each candidate costs 440 tokens x $0.05 per million = $0.000022, so N up to 36. Cost binds, so I rerank the top 36 of the fused list, and I would check recall@36 of the first stage to make sure the answer is usually in that window.</p>
</Fragment>
<Fragment slot="long">
<p>Latency budget. Adding the stages' p95s is a simplification, since their slow tails do not always land on the same request; it is fine for an estimate and must be confirmed with an end-to-end load test. 1,200 - 950 = 250 ms. The reranker model is 50 + 4N, so N = (250 - 50) / 4 = 50.</p>
<p>Cost budget. Generation already uses $0.0012 of the $0.002. Each candidate bills 40 + 400 = 440 tokens; at $0.05 per million that is 440 x 0.05 / 1,000,000 = $0.000022. So N = 0.0008 / 0.000022 = 36.4, rounded down to 36.</p>
<p>What 36 means at scale. 300 QPS x 36 candidates is 10,800 query-document pairs per second, or 300 x 36 x 440 = 4.75 million tokens per second sent to the reranker. Check the vendor's rate limits before you check its accuracy. The monthly reranking bill at 30 days is 300 x 86,400 x 30 = 777.6 million queries x 36 x $0.000022 = about $616,000.</p>
<p>Is 36 enough? Only if the first stage puts the answer in its top 36. Measure recall@36 of the fused list on the eval set; if it is low, spend on better first-stage retrieval, not on reranking more.</p>
<p>Levers if the answer is too small. Shorter chunks cut tokens per candidate linearly. A cheaper tier (Cohere lists Rerank 5 Fast at $0.02 per million) or a self-hosted cross-encoder changes the cost line. Caching generation for repeated questions frees money for reranking.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you measure the reranker's latency model?</em> Load-test at the target QPS with batch sizes from 10 to 100 and fit p95 against candidate count; the intercept is network and overhead, the slope is per-candidate compute.</li>
<li><em>What changes with an older per-search billing model?</em> Cohere's search unit is one query with up to 100 documents, so cost is flat up to 100 short candidates and the cost constraint disappears; documents over 500 tokens count as several.</li>
<li><em>Could you skip reranking for some queries?</em> Yes: if the first-stage top result has a large margin, or for exact identifier queries where BM25 is decisive.</li>
</ul>

The binding constraint is cost, at 36 candidates. The accepted band is 30 to 40.

## Follow-ups

- *The product team wants p95 under 800 ms. What now?* The reranker budget becomes negative with these generation numbers; stream the answer and measure time to first token instead, or move to a smaller, faster generation model.
- *Where does the rest of the $0.002 go?* Embedding the query and running the vector search also cost money; with them included the reranker's share shrinks further.
- *Why not rerank all 5 million documents?* A cross-encoder scores pairs one by one and nothing is precomputed; that is exactly why retrieval comes first.

## Common mistakes

- Using only the latency budget and answering 50.
- Billing only the document tokens and forgetting the query is sent with every candidate.
- Treating the reranker's latency as constant regardless of candidate count.
- Quoting a reranker latency from memory instead of labelling it as a measured input.
