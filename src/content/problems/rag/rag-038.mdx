## Question

<Callout kind="interview" label="The round">
"Our assistant's semantic search is too slow and misses things. You own it for a quarter. What do you change, in what order, and what do you not do?"
</Callout>

The question is reported from a Microsoft machine-learning engineer onsite (candidate report via PracHub). The system and the numbers are a scenario:

- An assistant for 8,000 customer organisations, 120 million chunks, 768-dimension embeddings from an off-the-shelf model. One shared HNSW index, filtered by organisation after the scan.
- Retrieval p95 is 380 ms against a budget of 250 ms. On 600 labelled queries, recall@20 of the relevant chunks is 0.68. Support tickets say part numbers and error codes "never work".
- An edited document takes about six hours to show up, because re-embedding runs as a batch job.
- Five engineers, one quarter. The product manager wants a fine-tuned embedding model. The platform lead will fund one full re-embedding of the corpus this quarter, not two.
- A load test of a hosted cross-encoder reranker measured 20 ms plus 2.5 ms per candidate at p95 (scenario).

## Answer

<Depth>
<Fragment slot="short">
<p>Measure before choosing: run exact search on the 600 labelled queries to split the 0.68 into what the index loses and what the embedding model loses, by query type. Then the order: route by organisation so a query searches only its organisation's partition, which fixes most of the latency and the filtered-recall loss together; add BM25 beside the dense index with rank fusion and rerank about 50 candidates, which fixes part numbers and error codes without spending the re-embedding; move updates to an event-driven path with a small exact-searched delta so edits appear in minutes. Fine-tuning waits: it spends the quarter's only re-embedding on a gain nobody has measured. The written artefact is a decision memo with the measurements, the order and the rollback triggers.</p>
</Fragment>
<Fragment slot="long">
<p><strong>First, find where the 0.68 goes.</strong> Exact search over the same 600 queries, with the same organisation filter, is the ceiling the index can reach with this model. If exact recall@20 is near 0.68, the model is the problem and index tuning is wasted. If it is well above, the index and the filter are losing it: an organisation that owns 0.1% of a shared index is filtered after the scan, and a post-filtered graph search returns few of its rows. Split by query type as well: part numbers and error codes are tokens an embedding model was never trained to match exactly, and they need a lexical path whatever the model.</p>
<p><strong>Latency: stop searching other organisations' data.</strong> Partition by organisation: dedicated partitions for the largest few hundred, hashed groups for the rest, and route each query to its partition. The guide on vector-database interviews names the trade: shard by tenant and fan-out drops; shard by anything else and every query waits for its slowest shard. Pinecone's pricing shows the same cost shape from the other side: a filtered query over a 100 GB shared namespace is billed as 100 GB of scan, a tenant namespace of 1 GB as 1. Cost: a migration of 120 million rows, per-partition indexes to build, and small organisations in shared groups still filter, though over a far smaller graph.</p>
<p><strong>Quality: two defensible answers.</strong></p>
<ul>
<li><strong>Hybrid plus rerank, no re-embedding.</strong> A BM25 index per partition, fused with dense results by reciprocal rank, then a cross-encoder over the top candidates. Fixes identifier queries outright and usually lifts the rest. Cost: a second index to keep fresh, analyser choices per language, and the reranker's latency on every query.</li>
<li><strong>Fine-tune the embedding model.</strong> Train on pairs from click and feedback logs, then re-embed. Can lift natural-language recall where the off-the-shelf model is weak on this domain. Cost: the quarter's one re-embedding, a dual-index window with two copies in memory, a training pipeline and a model to own, and feedback pairs skewed to the largest organisations. It does nothing for exact part numbers.</li>
</ul>
<p>I would ship hybrid plus rerank this quarter and keep the re-embedding for a measured model change. Fine-tuning becomes the right call if exact search shows the model is the ceiling on natural-language queries after the lexical path is in.</p>
<p><strong>The rerank depth is a number you choose.</strong> With partition-local retrieval, suppose the stages measure 15 ms for the query embedding and 40 ms for dense and BM25 in parallel. Keep 25 ms of the 250 ms for network and merge: 250 - 25 - 15 - 40 = 170 ms for the reranker, so 20 + 2.5N ≤ 170 and N ≤ 60. Anything from about 30 to 60 is defensible; pick it from the first stage's recall@N on the labelled set, the smallest N where it stops rising. A depth chosen from the latency budget alone, or 100 because it is round, is not.</p>
<p><strong>Caching.</strong> Cache query embeddings by normalised query text and model version: safe, because the embedding of a string does not depend on who asks. Cache result lists only with a key of organisation, the user's permission set, index version and query, and invalidate on any document or permission change in the partition. No semantic cache across organisations, ever.</p>
<p><strong>Freshness.</strong> Embed on the edit event, write to a per-partition delta that every query searches exactly, and fold the delta into the index in the background, the pattern turbopuffer documents for its write-ahead log. Six hours becomes the event lag plus one embedding call.</p>
<p><strong>The constraint conflict</strong> is latency against recall: every quality lever on this list adds a stage to a path that is already 130 ms over budget, so partitioning has to land first to make room.</p>
<p><strong>The failure mode of this plan.</strong> The reranker becomes the p95. Its 2.5 ms per candidate was measured on one load test; at peak, a hosted reranker queues, and 50 candidates at a slower rate eat the whole budget. Put a deadline on the rerank call and fall back to the fused order when it fires, log how often it fires, and treat that rate as the signal to cut N or self-host. The second failure is the result cache after a permission change: a stale entry is a disclosure, so invalidation is tested before the cache ships.</p>
<p><strong>What you give up.</strong> No fine-tuned model this quarter, and the product manager hears that in week one with the exact-search numbers behind it. A second index to keep fresh. Reranker cost on every query.</p>
<p><strong>Written down.</strong> A decision memo: the exact-search split, the order (partition, hybrid and rerank, freshness, then the model decision), N and its measurement, and per-step rollback triggers: roll back partitioning if any organisation's recall@20 drops on the labelled set, roll back the reranker if p95 exceeds 250 ms for an hour or the fallback fires on more than a set share of queries.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why reciprocal rank fusion and not a weighted score?</em> BM25 and cosine scores are on different scales that shift per partition; ranks are not. Tune weights only once there is a labelled set per segment.</li>
<li><em>What do you shard the 200 largest organisations by if one of them alone is too big for a node?</em> By document within the organisation, and accept fan-out for that organisation only.</li>
</ul>
</Fragment>

## Follow-ups

- *Pushback: partitioning takes six of your twelve weeks. The product manager says customers want fine-tuning, not a migration. Which do you cut, and what do you write down about the risk?*
- *Reversal: what result from exact search on the labelled set would make you spend the re-embedding on a fine-tuned model in week two?*
- *Two staff engineers disagree: one wants to self-host the reranker to control its p95, the other wants to keep the hosted one and cut N. How do you decide without deciding by rank?*
- *A large customer asks for their data to be excluded from any model training, including your fine-tuning. What does that do to the pairs you can train on, and to the other customers' results?*

## Common mistakes

- Fine-tuning before measuring how much of the loss is the index.
- Expecting an embedding model to match part numbers and error codes exactly.
- Raising efSearch on the shared index to fix latency and recall at once, which makes latency worse.
- A result cache keyed by query text alone, which serves one organisation's results to another.
- Choosing the rerank depth without the first stage's recall at that depth.
