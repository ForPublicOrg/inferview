## Question

<Callout kind="interview" label="The prompt">
"We are building an assistant over our internal documents: wiki, drive, tickets. Different employees can see different documents, and permissions change daily. Design the retrieval so nobody ever gets an answer built from a document they cannot open. Where do you enforce access control?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Filtering after generation is too late; the model has already read the text.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Filtering after retrieval loses recall. Filtering inside retrieval needs the permissions in the index.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Permissions change. What is the window in which the index is wrong?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Enforce access before the model sees anything. Every chunk carries the access-control labels of its source document (users and groups allowed), ingested and updated with the document. At query time the user's identity resolves to their groups, the search applies that as a filter inside the retrieval call, and a final check against the source system's live permissions runs on the few chunks that will go into the prompt. The index filter gives recall; the live check closes the staleness window.</p>
</Fragment>
<Fragment slot="long">
<p>Options. (1) Filter after generation: wrong, the model already read the text and can leak it in the answer. (2) Retrieve top k, then drop what the user cannot see: simple, but a user who can see 2% of documents gets almost nothing back, and the result count reveals that hidden documents matched. (3) Filter inside retrieval with ACL labels in the index: right default. (4) Separate index per tenant or permission group: strongest isolation, and expensive when groups overlap.</p>
<p>Data model. Per chunk: document id, `allowed_users`, `allowed_groups`, and a permission version. Group membership is resolved at query time from the identity provider and cached briefly, so adding someone to a group does not require re-indexing their documents.</p>
<p>The filtered search problem. Approximate indexes filter after the scan by default. In pgvector a filter matching 10% of rows with ef_search 40 leaves about 4 candidates. For selective permissions use iterative scans, partitions by tenant or department, or engines that apply filters during graph traversal, and test with the user who can see the least.</p>
<p>Freshness. Permission changes flow through the same change pipeline as content, with a tighter target, because a stale grant is a leak. As a backstop, check the final context chunks against the source system's permission API before generation; it costs one batched call per request for a handful of documents.</p>
<p>Other leak paths. Caches keyed only on the question serve one user's answer to another: key them by permission set or do not cache. Logs and traces contain retrieved text: protect them like the source. Prompt injection inside a document can instruct the model to reveal other context, which is one more reason to never put a document the user cannot see into the prompt. OWASP's LLM Top 10 lists sensitive information disclosure and vector and embedding weaknesses as named risks.</p>
<p>Verification. A test suite of users with known permissions and questions whose answers sit in restricted documents; assert refusals. Run it in CI and after every connector change.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not one index per user?</em> Documents shared with thousands of people would be stored thousands of times, and every share would rewrite many indexes.</li>
<li><em>How do you handle "anyone with the link" documents?</em> Treat them as visible only to users who have opened the link, or exclude them; indexing them as public turns an obscure link into a searchable document.</li>
<li><em>What does the model say when the answer exists but is restricted?</em> The same as when it does not exist. Saying "there is a document you cannot see" leaks its existence.</li>
</ul>
</Fragment>
</Depth>

The design hinges on one sentence: no chunk enters the prompt unless the requesting user can open its source right now. Everything else (labels in the index for recall, live checks for freshness, partitioning for selective filters, cache keys by permission set) is how you make that sentence true at acceptable latency.

## Follow-ups

- *Permissions are nested groups with thousands of members. Where do you expand them?* At query time, from the identity provider, into the user's flat group list; index documents by group, not by expanded user list.
- *A user loses access mid-conversation. What happens to context already in the chat?* Re-check permissions on every turn for the chunks being reused, or drop retrieved context from history after each answer.
- *How do you audit this?* Log, per answer, the document ids used and the permission decision for each, so a disclosure report can be produced.

## Common mistakes

- Filtering after generation, or relying on a prompt instruction ("do not reveal confidential documents").
- Post-filtering top-k and calling it done, then discovering low-permission users get empty results.
- Sharing a response cache across users.
- Forgetting that permission changes need the same freshness pipeline as content changes.
