## Question

<Callout kind="interview" label="The prompt">
"Tenants of our RAG product say answers cite too few sources. Here is what we have. Which explanation fits the symptom, what else is wrong, and what do you change first?"
</Callout>

One pgvector table holds about 30 million chunks for every tenant. pgvector is 0.8.7 and every setting not shown is the default. Two weeks ago migration 0042 shipped:

```sql
DROP INDEX IF EXISTS chunks_embedding_ivfflat;
CREATE INDEX chunks_embedding_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);
SET hnsw.iterative_scan = relaxed_order;
CREATE INDEX chunks_tenant_idx ON chunks (tenant_id);  -- for the admin page's per-tenant counts
```

The retrieval query, issued by the application through its connection pool:

```sql
SELECT id, title, embedding <=> $1 AS distance
FROM chunks
WHERE tenant_id = $2 AND deleted_at IS NULL
ORDER BY embedding <=> $1
LIMIT 10;
```

Rows returned per query over one hour, with each tenant's share of the table:

| Tenant | Share of rows | Mean rows returned |
|---|---|---|
| 7 | 41% | 10.0 |
| 42 | 8% | 3.1 |
| 311 | 1.2% | 0.4 |
| 980 | 0.05% | 0.0 |

About 6% of all rows have `deleted_at` set; soft-deleted chunks are kept for 30 days before a nightly job removes them. A plain `EXPLAIN` of the query for tenant 42, run by the on-call engineer from psql, shows an index scan on `chunks_embedding_hnsw` with the tenant and `deleted_at` conditions as a filter. Nobody has run `EXPLAIN ANALYZE` from the application's role yet.

## Answer

**The cause.** `SET` changes a setting for the session that runs it. The migration's session turned on iterative scans for itself and then ended; the application's pooled connections never ran the statement, so their HNSW scans still return `hnsw.ef_search` candidates, 40 by default, and the `WHERE` clause thins those. The table is the check: 40 x 0.08 x 0.94 = 3.0 expected rows for tenant 42, 40 x 0.012 x 0.94 = 0.45 for tenant 311, and 15.4 for tenant 7, which `LIMIT 10` caps at 10. Mean rows returned scale with the tenant's share, which is what a fixed candidate list predicts and what no index-quality problem would produce.

**Why the other options are tempting.** Soft-deleted rows are a real defect: they are live tuples in the graph, they match nothing, and the README warns that dead tuples and filter conditions both shrink results. At 6% they cost about one row in ten for a tenant that otherwise fills its limit. The `max_scan_tuples` cap is real too, but it only applies once iterative scans run; a scan of 20,000 tuples at 8% x 0.94 would pass about 1,500 qualifying rows. It will matter for tenant 980 after the fix: 20,000 x 0.0005 x 0.94 is about 9 rows, so the smallest tenants can still come back short. Building HNSW before a bulk load is a reflex carried over from IVFFlat, whose lists are trained on the data present at build time; an HNSW graph adds each row as it arrives.

**The evidence that is missing, and what to do without it.** Run `SHOW hnsw.iterative_scan` and `EXPLAIN (ANALYZE, BUFFERS)` through the application's pool and role, because psql sessions and pooled sessions can see different settings. Count soft-deleted rows per tenant, since a tenant that recently re-imported its corpus may have far more than 6%. Without those, the arithmetic is strong enough to act on, and the first change is reversible: set the parameter where the application's sessions pick it up, with `ALTER ROLE app_user SET hnsw.iterative_scan = strict_order`, and watch rows returned per tenant.

**The decision: which ordering, and what else.** Two defensible answers.

- *Iterative scans for everyone, with `strict_order`.* One setting, results stay in distance order, nothing else in the query changes. Cost: the README says relaxed ordering gives better recall, so strict ordering leaves some on the table, and every selective query now reads more of the graph, so p95 rises most for the smallest tenants, which read up to 20,000 tuples and may still return short.
- *`relaxed_order` plus an exact path for small tenants.* Small tenants get `WHERE tenant_id = $2` through the B-tree index and exact distances, which is correct and cheap when the tenant has few rows; large tenants use the HNSW scan with relaxed ordering, re-sorted in a materialized CTE with `ORDER BY distance + 0` on Postgres 17 and later. Cost: two query shapes and a threshold to maintain, and the re-sort is easy to drop in a later refactor, after which citations arrive slightly out of order.

The threshold is a number you choose: the tenant row count below which exact search's measured p95 is inside the latency budget. Measure the exact scan for tenants of 10,000, 100,000 and 1 million rows on production hardware before picking it; a threshold chosen from the table's size alone is unreasonable.

**The constraint conflict** is latency against result count. Every fix that returns ten rows to tenant 980 reads more data per query, and the cheapest one, a higher `ef_search`, raises latency for every tenant to help a few.

**The failure mode of the recommended fix.** Role-level settings apply when a session starts. A pooler that keeps server connections open for hours serves the old setting until those connections recycle, so the fix looks partial for a while, and a later role or database change can silently override it. Assert the setting in the retrieval path's health check, and alert on rows returned divided by the requested limit, per tenant, so the next regression is caught by a ratio rather than by a complaint.

## Follow-ups

- *The iterative scan doubles p95 for the smallest 200 tenants and they are on a latency SLA. Do you ship it to them, move them to the exact path this week, or accept short results in writing until next quarter?*
- *The nightly purge of soft-deleted rows makes every HNSW vacuum take hours. What do you change: the retention window, the purge schedule, or a reindex before vacuum as the README suggests, and what does each cost?*
- *What would you need to see in production to reverse the decision to keep all tenants in one table, and move the largest ones to their own partitions?*
- *Two senior engineers disagree: one wants `strict_order` everywhere, the other `relaxed_order` with the re-sort. How do you decide without deciding by rank?* Replay a day of queries under both and compare rows returned per tenant and how often the top three citations change order.

## Common mistakes

- Raising `LIMIT`, which changes nothing while the scan returns 40 candidates.
- Rebuilding the index with a larger `m` or `ef_construction` for what is a candidate-count problem.
- Testing the fix in psql, where a `SET` in the same session makes it look solved.
- Turning on `relaxed_order` without the re-sort when the order of citations matters.
- Ignoring soft-deleted rows because they are a small fraction of the table, when they can be a large fraction of one tenant.
