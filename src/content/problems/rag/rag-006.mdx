## Question

<Callout kind="interview" label="The prompt">
"You have a 200-page PDF with headings, two-column pages and a lot of tables, and a user asks a question about it. Walk me through what happens between pressing enter and the answer, and tell me how you would chunk it."
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Split the answer into index time and query time; most of the quality is decided at index time.</p></details>
<details class="hint"><summary>Hint 2</summary><p>What does a table row mean once it is separated from its header?</p></details>
<details class="hint"><summary>Hint 3</summary><p>The unit you match on and the unit you show the model do not have to be the same.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>At index time: parse with a layout-aware parser that keeps headings and tables, chunk along that structure, write each table row out with its header, attach the heading path and page as metadata, then embed and index for both BM25 and vectors. At query time: rewrite the question, run hybrid retrieval, rerank, and pass the top chunks, or their parent sections, to the model with an instruction to cite pages. Chunk size is chosen by measuring recall on questions written from this document, not by a default.</p>
</Fragment>
<Fragment slot="long">
<p>Parsing. A PDF stores positioned glyphs, so a naive extractor reads across two columns and turns tables into a stream of cells. Use a parser that detects reading order, headings and tables, strip running headers and footers, and OCR any scanned pages. For pages that are mostly charts or forms, page-image retrieval (ColPali-style) avoids depending on extraction at all.</p>
<p>Chunking. Split on the heading hierarchy first, then pack paragraphs within a section up to a size limit measured in tokens (LangChain's default length function counts characters). For tables, emit one chunk per row or small group of rows that repeats the column headers and the table caption, and keep the full table as a parent. Prepend the heading path ("4 Pricing > 4.2 Discounts") to every chunk, or go further with contextual retrieval and have a model write a short context for each chunk.</p>
<p>Parent-child retrieval. Match on small chunks for precision, return the enclosing section for reading. This separates "what finds the answer" from "what explains the answer".</p>
<p>Overlap. Not a default. In Chroma's comparison, 400-token chunks with 200 overlap had lower recall than the same size with none, and half-size overlap roughly doubles storage. Use it only if your eval shows it helps.</p>
<p>Query time. Rewrite the question if it is conversational, retrieve with BM25 and vectors (tables are full of exact terms), fuse, rerank, assemble context within a token budget with the best chunks first, and require page citations.</p>
<p>Measurement. Write 20 to 30 questions from the document, including several whose answers live in tables, label the gold pages, and compare chunkers by recall@k before tuning anything else.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The document is only 200 pages. Why retrieve at all?</em> It may fit in a long context: about 200,000 tokens is Anthropic's rough threshold for putting a whole knowledge base in the prompt. Retrieval still wins on cost per query and on latency if the same document serves many questions without caching.</li>
<li><em>How do you test the parser?</em> Snapshot tests on a few hard pages: a two-column page, a table spanning a page break, a scanned page. Compare extracted text with a hand-made expected output.</li>
<li><em>A table spans two pages. Now what?</em> Detect the continuation (same column headers, no new caption) and merge before chunking; otherwise the second half loses its headers.</li>
</ul>
</Fragment>
</Depth>

The answer interviewers want has three properties: it puts parsing before chunking, it treats a table row and its header as one unit of meaning, and it ends with a measurement rather than a magic number. Any specific size you name should come with "and then I would check it on labelled questions".

## Follow-ups

- *What metadata do you store per chunk?* Document id and version, page numbers, heading path, chunk position, a content hash, and access-control labels.
- *How would you handle footnotes and cross-references?* Attach footnotes to the paragraph that cites them; for "see section 2.1", store the reference so the context builder can pull the target section in.
- *Which chunking strategy would you start with?* Structure-aware with token-based size limits, because it is cheap and keeps tables whole; semantic chunking only if the eval shows a gain worth its extra embedding calls.

## Common mistakes

- Starting with chunk size and overlap before looking at what the parser produced.
- Splitting tables mid-row or separating rows from headers.
- Measuring chunk size in characters while talking about tokens.
- Claiming a universal best chunk size; no source supports one.
