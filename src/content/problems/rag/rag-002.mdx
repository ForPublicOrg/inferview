  solution: |
    import heapq
    import math
    from collections import Counter


    def tokenize(text):
        return text.lower().split()


    class BM25:
        def __init__(self, docs, k1=1.2, b=0.75):
            self.k1, self.b = k1, b
            self.n = len(docs)
            self.tf = [Counter(tokenize(d)) for d in docs]
            lengths = [sum(c.values()) for c in self.tf]
            avgdl = sum(lengths) / self.n if self.n else 0.0
            # The length part of the denominator depends only on the document, so it is computed once.
            self.norm = [k1 * (1 - b + b * n / avgdl) if avgdl else k1 for n in lengths]
            self.postings = {}
            for i, counts in enumerate(self.tf):
                for term, c in counts.items():
                    self.postings.setdefault(term, []).append((i, c))
            self.idf = {t: math.log(1 + (self.n - len(p) + 0.5) / (len(p) + 0.5)) for t, p in self.postings.items()}

        def _terms(self, query):
            # Policy: a query term counts once however often the query repeats it.
            return [t for t in dict.fromkeys(tokenize(query)) if t in self.postings]

        def _part(self, term, tf, i):
            return self.idf[term] * tf * (self.k1 + 1) / (tf + self.norm[i])

        def score(self, query, i):
            counts = self.tf[i]
            return sum(self._part(t, counts[t], i) for t in self._terms(query) if t in counts)

        def top_k(self, query, k):
            acc = {}
            for t in self._terms(query):
                for i, tf in self.postings[t]:
                    acc[i] = acc.get(i, 0.0) + self._part(t, tf, i)
            best = heapq.nsmallest(k, acc.items(), key=lambda kv: (-kv[1], kv[0]))
            return [(i, s) for i, s in best if s > 0]

## Question

<Callout kind="interview" label="The prompt">
"Write a BM25 index in Python, standard library only. It is built once over the corpus and then serves a few thousand queries. Lowercase and split on whitespace; I care about the scoring and the data layout, not the tokenizer."
</Callout>

Implement `BM25(docs, k1=1.2, b=0.75)` with `score(query, i)` and `top_k(query, k)`. For every query term that appears in document `i`, the score adds

`idf(q) * tf * (k1 + 1) / (tf + k1 * (1 - b + b * len(doc) / avg_len))`

with `tf` the term's count in the document and Lucene's IDF, `log(1 + (N - df + 0.5) / (df + 0.5))`, over `N` documents of which `df` contain the term. `top_k` returns up to `k` pairs of `(index, score)`, best first, and never a document that scores 0.

Two policies are yours to choose and state: whether a query that repeats a word counts it once or once per occurrence, and the order of documents with equal scores. The tests accept either choice for both.

The scale is part of the question. The hidden tests build the index over 40,000 documents and time 2,000 `top_k` calls against a budget of 3 seconds in total. Then say which `k1` and `b` you would start from for a corpus of one-line ticket titles, and how you would decide whether to move them.

## Answer

The reference builds everything that does not depend on the query in the constructor: one `Counter` per document, a postings list from each term to `(document, tf)` pairs, the IDF per term, and the length part of the denominator per document, `k1 * (1 - b + b * len / avg_len)`. A query reads only the postings of its own terms, accumulates partial scores in a dict, and takes the `k` best with `heapq.nsmallest` on `(-score, index)`. `score(query, i)` uses the same per-term function, so the two methods cannot disagree.

**The worked example in the visible tests.** In four documents, `E1234` appears in one and `timeout` in two, so their IDFs are log(1 + 3.5 / 1.5) = 1.204 and log(1 + 2.5 / 2.5) = 0.693. The first document has 6 tokens against an average of 23 / 4 = 5.75, so its denominator is 1 + 1.2 x (0.25 + 0.75 x 6 / 5.75) = 2.239 and it scores 1.204 x 2.2 / 2.239 = 1.183. The rare identifier carries the ranking. That is the query class where a dense bi-encoder is weakest and the reason BM25 stays in hybrid stacks; BEIR reports BM25 as a robust zero-shot baseline across its datasets.

**What the hidden tests check.** Properties of the formula, not one ranking. A term in fewer documents outweighs a term in more. A term in every document still scores above zero, which is what the `1 +` inside Lucene's logarithm buys over the classic Robertson form. Scores rise with `tf` by shrinking steps, and the ratio of `tf = 8` to `tf = 1` stays below `k1 + 1`. With `k1 = 0` a term counts once whatever its frequency. With `b = 0` length does not matter, a larger `b` widens the gap between a short and a long document, and a document of exactly average length scores the same for every `b`. `top_k` agrees with `score` and returns the largest positive scores in descending order. Then the timing.

**The performance constraint.** Scoring every document per query, through `score` in a loop, took about 30 ms per query on the 40,000-document corpus under CPython 3.12.6 on the laptop that checked this problem, so 2,000 queries take about a minute. The postings version read about 16 documents per query and ran all 2,000 in under 0.1 s on the same machine. The difference is the inverted index: work proportional to the postings of the query's terms instead of to the corpus.

**The two policies.** Counting a repeated query word once makes the score a function of the set of query terms, which is what most callers of a search box expect. Counting each occurrence lets a caller weight a term by repeating it, at the cost that a pasted error message with a repeated word skews the ranking. Ties by lower index are deterministic and testable. Any tie order is acceptable if it is stable between calls, because paginated results that reshuffle on refresh read as a bug.

**`k1` and `b` for ticket titles.** Start from Lucene's defaults, 1.2 and 0.75. One-line titles have nearly uniform length, so the length factor carries little information and a lower `b` is a reasonable direction, as is a lower `k1` because titles rarely repeat a word. Moving either without labelled queries to measure against is the unreasonable choice: the change is invisible in spot checks and shows up only as a shift in which tickets reach the top.

**The constraint conflict** is memory against query latency. The reference stores every `(document, tf)` pair twice, in the postings and in the per-document counters, so that `score(query, i)` is a dictionary lookup. Dropping the counters halves that memory and turns `score` into a postings scan. Precomputing IDF and the length norms buys query speed by freezing the corpus statistics at build time.

**The failure mode of the reference.** It reads every posting of every query term. A query containing a word that appears in most documents, such as "error" in a ticket corpus, reads most of the corpus, so latency depends on the query's most common word rather than on `k`. Production engines skip postings that cannot reach the current top `k`; the reference has no such bound. And because the statistics are frozen, adding documents means a rebuild: an index that appends without recomputing IDF and the average length scores new documents against an old corpus.

## Follow-ups

- *What changes to run this behind a real search service?* Postings stored compressed on disk, document lengths in a separate array, immutable segments merged in the background so that adds and deletes do not rewrite the index, a tokenizer with stemming and a stop list chosen per language, and a skip structure so common query terms do not force a full postings scan.
- *Postgres is already in the stack. Is `ts_rank` BM25?* No. The PostgreSQL 18 documentation says its ranking functions use no global information, so there is no IDF, and length normalisation is off unless you set the bit mask. On an identifier query it can put documents that repeat a common word above the one that contains the rare code.
- *The product team wants to drop BM25 for dense retrieval to save one index, since a cross-encoder reranks anyway. What would you need to see on your own queries to agree, and which query class do you check first?*
- *Two engineers disagree on counting repeated query words. How do you settle it without deciding by rank?* Replay a sample of logged queries that repeat a word through both policies and have someone judge only the results that changed.

## Common mistakes

- Recomputing document frequencies or the average length inside the query path.
- Counting document frequency per occurrence instead of per document.
- Using the IDF without the `1 +`, which makes a term found in most documents lower the score of the documents that contain it.
- Returning zero-score documents to fill `k`.
- Computing the average length over the matching documents instead of the corpus.
