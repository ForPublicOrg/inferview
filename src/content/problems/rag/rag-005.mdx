## Question

<Callout kind="interview" label="The prompt">
"The corpus is 50 million chunks, embedded with text-embedding-3-small. Does your index still fit in memory, and what happens when it doesn't?"
</Callout>

Estimate the memory for the raw float32 vectors alone, in gigabytes. Then say what you would do about it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>text-embedding-3-small returns 1,536 dimensions, and float32 is 4 bytes per dimension.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Work out one vector's size first, then multiply by 50 million.</p></details>
<details class="hint"><summary>Hint 3</summary><p>The graph links, metadata and chunk text come on top of the raw vectors.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>One vector is 1,536 x 4 = 6,144 bytes, so 50 million is about 307 GB of raw float32, before the HNSW graph, metadata and text. Unless the node has that much RAM to spare, it does not fit, and I would shrink it: halfvec halves it to about 154 GB, binary quantization cuts it to 9.6 GB for the search pass with full-precision rescoring of an oversampled shortlist, and shortening dimensions or sharding are the other levers.</p>
</Fragment>
<Fragment slot="long">
<p>The arithmetic. 1,536 dimensions x 4 bytes = 6,144 bytes per vector. 50,000,000 x 6,144 = 307,200,000,000 bytes, which is 307.2 GB, or 286 GiB if your tool reports binary units.</p>
<p>What else lives in memory. An HNSW index stores neighbour links per node on every layer it appears in, plus the vectors themselves if the engine keeps them in the index. Metadata for filtering and the chunk text add more. No source used here gives a per-node overhead figure, so measure it: build the index on a 1 million chunk sample and scale.</p>
<p>What happens when it does not fit. HNSW search is a sequence of dependent random reads, one neighbour list after another. In RAM each hop is cheap; once the working set spills to disk, every hop can become a disk read and p95 latency climbs sharply, with no change in recall. That is why "does it fit?" is the first capacity question.</p>
<p>The levers. halfvec (2 bytes per dimension) gives 153.6 GB. Binary quantization (1 bit per dimension) gives 50,000,000 x 1,536 / 8 = 9.6 GB for the search pass; keep float vectors on disk and rescore an oversampled shortlist with them. Hugging Face measured that binary kept 92.53% of retrieval performance without rescoring and 96.45% with it on one model; Qdrant reports 0.9847 for text-embedding-3-small with 3x oversampling and rescoring. The OpenAI `dimensions` parameter shortens v3 embeddings, which cuts memory linearly at some quality cost you must measure. Sharding spreads the index across nodes and adds a fan-out and merge step.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Which lever first?</em> Binary or scalar quantization with rescoring, measured against exact search on your queries; it is usually a configuration change rather than a re-architecture.</li>
<li><em>What does quantization cost?</em> Recall, unless you rescore; and the rescoring step reads full vectors from disk for the shortlist, so oversampling too much brings disk reads back.</li>
<li><em>What would change the estimate?</em> A 3,072-dimension model doubles it; 800-token chunks with 400 overlap roughly double the chunk count for the same corpus.</li>
</ul>
</Fragment>

The accepted band is 280 to 320 GB, wide enough to cover 307.2 GB and the 286 GiB you get if you divide by 2^30.

## Follow-ups

- *Would you use text-embedding-3-large instead?* Its 3,072 dimensions double every row of the table, and in pgvector a `vector` index stops at 2,000 dimensions, so you would need `halfvec` or a shorter `dimensions` setting anyway.
- *How do you budget the graph overhead without a source?* Build on a sample, read the index size from the database, divide by row count, and multiply out.
- *Is 50 million chunks the right number?* Ask how it was derived: chunk overlap, duplicate documents and boilerplate pages often inflate it.

## Common mistakes

- Forgetting the 4 bytes per float and answering 77 GB.
- Mixing GB and GiB and then arguing about a 7% difference.
- Stopping at the raw vectors and calling it the index size.
- Proposing binary quantization without rescoring or a recall measurement.
