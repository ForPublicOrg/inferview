## Question

<Callout kind="interview" label="Estimate, 20 minutes">
"We want to run MIPROv2 on the support assistant before the next release. Split the labelled data, pick the run size, and tell me what the run costs in task-model calls and dollars, including the check afterwards."
</Callout>

The program is a scenario: three DSPy predictors in sequence (classify the ticket, write a search query, draft the reply), one task-model call each. You have 700 labelled tickets. Without demonstrations a call averages 1,200 input and 250 output tokens; each demonstration in a predictor's prompt adds about 400 input tokens. Scenario prices for the task model: $0.40 per million input tokens and $1.60 per million output tokens. Instruction proposals go to a separate prompt model.

From DSPy's source as of 28 October 2026 (inputs, not answers):

```text
auto        candidates n    validation batch
light       6               100
medium      12              300
heavy       18              1000

num_trials       = int(max(2 * num_vars * log2(n), 1.5 * n))     num_vars = predictors, x2 when demos are optimised
minibatch_size   = 35, a full evaluation on the validation set every 5 trials
program runs     ~ 35 * num_trials + len(valset) * (num_trials // 5 + 1)
max_bootstrapped_demos = 4, max_labeled_demos = 4 per predictor
```

Give the split, the mode, the number of task-model calls and the cost, and name the term that dominates.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the result has to show afterwards, and how many held-out tickets it takes to see a lift of that size.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how many demonstrations the winning program carries per predictor on average; the run tries many candidates, not only the winner.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether minibatching stays on for this run.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Split 700 as about 100 for bootstrapping, 300 for MIPROv2's validation set and 300 held out. Run <code>auto="medium"</code>: 43 trials, about 4,200 program runs, about 12,600 task-model calls. At an average of four demonstrations per predictor that is about $19, plus about $2 for the held-out check and about $1 for bootstrapping: call it $22. The full evaluations on the validation set are two thirds of the runs, and turning minibatching off triples the bill.</p>
</Fragment>
<Fragment slot="long">
<p><b>The split, chosen.</b> The held-out set decides the release, so size it first. With accuracy near 50% and two independent samples, the 95% half-width on a difference is 1.96 × sqrt(0.5 / n): ±9.8 points at n = 200 and ±8.0 at n = 300. A paired comparison on the same tickets is narrower, but plan on the unpaired figure. Hold out 300. That leaves 400; DSPy's guidance of 200 or more examples for MIPROv2 is met by giving it 300 for validation and 100 to bootstrap demonstrations from. Reasonable alternatives: 200 held out and 400 for the optimiser if you expect a lift above 10 points. Unreasonable: a held-out set under 100 (±14 points or more, so nothing short of a large lift is distinguishable from noise), or using the validation set as the held-out set, because the search selected on it.</p>
<p><b>The mode.</b> Medium's validation batch of 300 matches the split. Heavy wants 1,000, more than the whole pool. Light (100) would leave 200 labelled tickets doing nothing.</p>
<p><b>Trials.</b> Three predictors, demos optimised, so num_vars = 6 and n = 12: 2 × 6 × log2 12 = 43.0, against 1.5 × 12 = 18. 43 trials.</p>
<p><b>Program runs.</b> Minibatches: 35 × 43 = 1,505. Full evaluations: 43 // 5 + 1 = 9, each on 300 tickets, so 2,700. Total 4,205 runs, each three calls: 12,615 task-model calls.</p>
<p><b>Cost per call, with your assumption.</b> At four demonstrations per predictor on average, input is 1,200 + 4 × 400 = 2,800 tokens: 2,800 × $0.40 / 10⁶ + 250 × $1.60 / 10⁶ = $0.00112 + $0.00040 = $0.00152. 12,615 × $0.00152 = $19.17. With no demos the call costs $0.00088 and the run $11.10; with all eight, $0.00216 and $27.25. Bootstrapping is small next to this: 12 candidate demo sets, each a few dozen program runs at the shorter prompt length, about a dollar. The prompt model's calls are tens, not thousands.</p>
<p><b>The check afterwards.</b> 300 held-out tickets × 3 calls × 2 programs: 900 calls for the baseline at $0.00088 ($0.79) and 900 for the winner at $0.00152 ($1.37). About $2.20 at 300, $1.40 at 200.</p>
<p><b>The total.</b> About $22 for medium with four demos on average. Light with 100 for validation: 31 trials (2 × 6 × log2 6 = 31.0), 35 × 31 + 100 × 7 = 1,785 runs, 5,355 calls, about $8 at the same prompt length. The accepted band, $4 to $35, covers light to medium and zero to eight demos.</p>
<p><b>The dominant term.</b> Full evaluations are 2,700 of 4,205 runs, 64%. The assumption that flips the conclusion is minibatching: with it off, every trial scores the whole validation set, 300 × 43 = 12,900 runs and 38,700 calls, about $59 at four demos. The second is prompt length: the demos multiply every call's input, so a program whose demonstrations are long tickets can double the bill without a single extra call.</p>
<p><b>Where this estimate is wrong.</b> DSPy's docs put a typical simple run at about $2 and ten minutes; this one is ten times that because it has three predictors, a 300-ticket validation set and long prompts. The run-count formula comes from the estimator in the source, and the source can change between releases: pin the DSPy version you price against, and check the bill of a light run before a medium one.</p>
</Fragment>

## Follow-ups

- *Pushback: a colleague says 300 held-out tickets is wasted data and the optimiser should get all 700. What do you say, and what number do you show?*
- *Reversal: what result would make you rerun with heavy, and where would the extra labelled tickets come from?*
- *Operating: the run hits the provider's rate limit at 12,600 calls in ten minutes. What changes in the plan, and does the cost change?*

## Common mistakes

- Counting only the winner's prompt length, when every trial runs a candidate with its own demonstrations.
- Forgetting that each program run is three model calls.
- Holding out nothing because the optimiser already has a validation set.
- Taking the docs' typical $2 as this run's price without checking the program's size.
