## Question

<Callout kind="interview" label="Debug, 25 minutes">
"Our AI feature is costing about ten times more per user than projected. Here is what we have. What is driving it, and what do you do?"
</Callout>

The feature: an assistant inside a document app. Users ask questions about their workspace documents; when a document is opened, the app shows a summary at the top. Answers run on Claude Sonnet 4.6; titles for saved answers run on Claude Haiku 4.5 (list prices: Sonnet 4.6 $3 per million input, $0.30 per million cache hits, $15 per million output; Haiku 4.5 $1 input, $5 output).

The launch document projected $0.17 per active user-day. Finance reports $1.72 for the last week, across 4,000 active users. The gateway tags every call with a purpose; this is the bill of materials, mean per active user-day for the week, beside the launch projection:

| Purpose | Model | Calls (projected) | Calls (actual) | Cache-hit tokens per call | Uncached input per call | Output per call |
|---|---|---|---|---|---|---|
| answer | Sonnet 4.6 | 10.0 | 10.4 | 6,000 | 4,000 (projected 2,000) | 300 |
| answer, retried after 429 | Sonnet 4.6 | 0 | 1.2 | 6,000 | 4,000 | 300 |
| title | Haiku 4.5 | 0 | 10.4 | 0 | 1,200 | 20 |
| summary | Sonnet 4.6 | 0.4 | 11.6 | 0 | 40,000 | 600 |

Product analytics, same week: 0.4 documents uploaded and 11.6 documents opened per active user-day.

The change merged three weeks ago, which the team suspects:

```diff
 RETRIEVAL = RetrievalConfig(
-    top_k=4,
+    top_k=8,
     min_score=0.35,
 )
 ...
 async def answer(session, question):
     ctx = await retrieve(question, RETRIEVAL)
     resp = await llm(model="sonnet-4.6", system=SYSTEM, context=ctx, question=question)
+    title = await llm(model="haiku-4.5", prompt=title_prompt(resp.text))
+    await save_answer(session, resp.text, title.text)
     return resp
```

And the document-open handler, unchanged since launch:

```python
async def on_document_open(session, doc):
    key = f"summary:{session.id}:{doc.id}"
    summary = await kv.get(key)
    if summary is None:
        summary = await llm(model="sonnet-4.6", prompt=summary_prompt(doc.text))
        await kv.set(key, summary, ttl=timedelta(days=30))
    return summary
```

You do not have per-user distributions, and you do not know whether the 4,000 users are typical of the user base the projection assumed. Which of these explains the cost gap? Then rank the other three, and say what you would collect and what you would ship before you have it.

## Answer

Price the rows first. An answer call costs 6,000 × $0.30 + 4,000 × $3 + 300 × $15, per million, which is $0.0018 + $0.0120 + $0.0045 = $0.0183. A summary call costs 40,000 × $3 + 600 × $15 per million, $0.120 + $0.009 = $0.129. A title costs $0.0012 + $0.0001 = $0.0013.

| Purpose | Calls | Cost per call | Per user-day | Share |
|---|---|---|---|---|
| answer | 10.4 | $0.0183 | $0.190 | 11% |
| retry | 1.2 | $0.0183 | $0.022 | 1% |
| title | 10.4 | $0.0013 | $0.014 | 1% |
| summary | 11.6 | $0.129 | $1.496 | 87% |
| **Total** | | | **$1.722** | |

The projection was 10 answers at $0.0123 (with 2,000 retrieved tokens) plus 0.4 summaries at $0.129, $0.175. The actual is 9.9 times that, and the summary row alone is 8.6 times the whole projection.

**The cause.** The summary cache key includes the session id. The projection assumed one summary per upload; the code produces one per document per session, so every time a user opens a document in a new session it is summarised again. 11.6 summaries against 0.4 uploads is the signature. The provider's prompt cache does not rescue it: the summary prompt carries no cache breakpoint, and repeat opens of the same document are spread over hours, beyond a 5-minute cache lifetime.

**Why the others are tempting, and how they rank.**

1. *top_k 4 to 8* is in the diff everyone is looking at, and it is real: 2,000 more uncached tokens on every answer is $0.006 a call, $0.062 per user-day. It is the largest of the secondary costs, and it deserves its own eval: if answer quality did not move, revert it.
2. *Retries without backoff* add $0.022 a day now, but they are a load-dependent defect: during an incident the same loop multiplies traffic exactly when the provider is shedding it. Fix for reliability, not for cost.
3. *The title call* doubles the request count, which is why it dominates a dashboard of calls, and costs $0.014 per user-day on the small model.

**What to collect.** Summary calls grouped by (doc id, content hash): the count per pair is the waste multiplier directly. The per-user distribution of summary calls, because a few users who open the same large documents all day can drive a mean that the median user never sees, and the fix differs if that is the case. Whether summaries differ across sessions for the same document version, in case someone intended per-session summaries (for example, personalised to the user's question history).

**What to ship before you have it.** Key the summary by document id and content hash, so it is computed once per version and shared across sessions. It is safe because the summary does not depend on the session; if product meant it to, that is a design conversation, not a cache key. Expected effect, if every document view in the week was a repeat of an uploaded version: summary cost falls to the upload rate, 0.4 × $0.129 = $0.052, and the total to about $0.28 per user-day.

**How the fix fails.** Shared summaries need the same access control as the documents: a summary keyed only by document id is served to anyone who can open the key, so the lookup has to check the reader's access to the document, not only the key. And large documents that change often (a shared notes file edited all day) still regenerate on every edit; for those, summarise on a debounce or only when the summary is shown.

**The quantity you choose.** Whether to summarise on upload (eager, predictable cost, wasted on documents nobody opens) or on first open (lazy, no waste, latency on the first open). With 0.4 uploads and 11.6 opens a day, most opens are repeats, so either works; on a product where most uploaded documents are never opened, lazy is cheaper.

## Follow-ups

- *Finance asks why the projection missed it. What would you change in how the next feature is projected?* Price the bill of materials per purpose from a staging trace, with the trigger for each call (per upload, per open, per answer) written next to its count.
- *Product says per-session summaries were intentional because they include the user's recent questions. What do you propose, and what does it cost?*
- *What would you need to see to decide that top_k 8 stays?* An eval on answer quality at 4 and 8 on the same question set, with the difference worth more than $0.062 per user-day.

## Common mistakes

- Starting from the diff, because the last change is the obvious suspect, and never pricing the table.
- Counting calls instead of dollars: the title call doubles calls and costs almost nothing.
- Reverting top_k and declaring victory when the bill drops by 4%.
- Fixing the key without an access check, which turns a cost bug into a data leak.
