## Question

Twelve LLM features run in production at an invented company, across four groups: two chat assistants, three search features (query rewriting, answer synthesis, result summaries), four extraction pipelines (documents, invoices, contracts, support tickets), and three agents that call internal tools. Each team calls two hosted vendors with its own keys, its own retry code and its own logs. Finance cannot attribute last month's model spend to features. Security found two vendor keys in a repository last quarter.

Design the shared inference platform. You have two platform engineers for the next quarter, the existing service mesh cannot be replaced, and nothing may move that breaks a feature's latency budget. One number to work with: answer synthesis has a 400 ms budget for its model call at the 95th percentile, and its measured vendor latency at that percentile is 340 ms (scenario inputs).

Produce the design, the order in which features move onto it, and a written migration plan with rollback triggers.

<p>A gateway in the existing mesh that holds every vendor key, issues each feature a scoped key with a budget and rate limits, writes one trace per call with team, feature, model version and prompt version, and owns retry and fallback so clients stop retrying. Batch extraction moves first (most spend, no tight latency), then chat and agents, and answer synthesis last, behind a measured check that the gateway adds less than its 60 ms of headroom at p95. What I give up: a shared cache and a router this quarter, and a single path for every feature on day one.</p>

<Fragment slot="long">
<p><b>The decision with two answers.</b> Mandate the gateway for all twelve features this quarter, or mandate it for keys and traces only and let latency-critical features keep direct calls with platform-issued keys. Full mandate: one path, complete cost attribution, one retry policy; it costs the risk of breaking answer synthesis's budget and puts two engineers on twelve migrations. Keys-and-traces mandate: closes the security finding and gives finance its numbers for most spend; it costs a second path the platform has to monitor, and the exception becomes the precedent the next team cites. With two engineers and one quarter I would take the second, with an expiry on each exception.</p>
<p><b>The quantity to choose.</b> The latency the gateway may add. For answer synthesis it is computed: 400 − 340 = 60 ms of headroom at p95, and the gateway cannot take all of it, because vendor latency varies week to week. I would allow the gateway half the headroom, 30 ms at p95 for that feature, and require the measurement before it moves. Reasonable choices sit between a third and two-thirds of the headroom; taking all of it leaves no margin for a slower vendor week, and setting a single company-wide number ignores that extraction can absorb seconds.</p>
<p><b>The constraint conflict.</b> Central control against latency and against two engineers' time. The gateway hop costs every call some latency and makes the gateway every feature's dependency.</p>

### The design

**Gateway.** A service in the existing mesh with one API across the two vendors. Its jobs, as Huyen lists them for a model gateway: a unified interface, access control, cost management and fallback when a vendor rate-limits or fails. It holds the vendor keys; teams never see them. Each feature gets its own key scoped to the models it may call, with a budget and rate limits. In LiteLLM's proxy that is a virtual key with `models`, `max_budget`, `budget_duration`, `tpm_limit`, `rpm_limit` and `team_id`, with spend per key and per team; building on it means running its PostgreSQL database. Building in-house is defensible if the mesh already has an auth and rate-limit layer to reuse.

**Retry and fallback, owned once.** Huyen notes that one retry doubles the API calls. If the client retries three times and the gateway retries three times, one user request can become up to 16 vendor calls (4 × 4). The gateway owns retries and fallback; client retries on gateway errors are removed as each feature migrates, and that removal is a migration checklist item, not a recommendation.

**Fallback per feature, not global.** Extraction can fall back to the second vendor's model if its eval passed on that model. Chat may fall back only to a model its eval covered. Agents do not fall back mid-run: a tool-calling run that switches models between steps sees a different tool-call format and behaviour, so an agent run that loses its vendor fails and is retried from the start or from its last checkpoint.

**Trace per call.** Team, feature, key, vendor, model and version, prompt name and version, input and output tokens, latency, status, retry count, fallback used. Written asynchronously, so a slow log store does not add latency.

**Model catalogue.** Approved models with their retirement dates and which features use them. A vendor notice such as OpenAI's end of new fine-tuning jobs on 6 January 2027 becomes a list of affected features on the day it is read.

**Not this quarter.** A router, a semantic cache (Huyen calls its value more dubious than prompt or exact caching), and an eval service. Each is a request from a second team away.

### Migration order and the written plan

1. Extraction pipelines (batch, no tight latency, likely most spend): shadow both paths for a week, compare outputs and cost, cut over.
2. Chat assistants: canary a share of traffic through the gateway; rollback trigger on p95 latency increase beyond the agreed budget or error rate above the direct path's.
3. Agents: migrate with fallback disabled; rollback trigger on run failure rate.
4. Search, then answer synthesis last: measure the gateway's added p95 under synthesis's traffic shape; move only if it is within 30 ms. Otherwise a direct call with a platform-issued key and client-side traces in the gateway's schema, with an expiry date.

Each step's rollback is a configuration flag in the client that restores the direct path, kept for two weeks after cut-over.

### The failure mode of this design

The gateway is now a shared dependency, and its outage is twelve features' outage. It needs its own on-call, an error budget, and a documented emergency bypass (direct vendor access with keys held in the secrets store, used only during a gateway incident and logged). The second failure mode is the exceptions: a direct-call exception without an expiry is permanent, so each one is listed on the platform's quarterly review with a decision to renew or close.

## Follow-ups

- *A vendor raises prices and finance asks you to route a third of chat traffic to the cheaper vendor next week. What evidence do you require before the router change, and who signs it?*
- *One extraction team hits its budget mid-month and its pipeline stops. Whose call is it to raise the limit at 3 a.m., and what does the gateway do while nobody answers?*
- *Two agents share a tool that charges per call. Do per-feature keys stop one agent from exhausting the other's budget, and if not, what does?*

## Common mistakes

- Designing the gateway and forgetting client-side retries, so the gateway multiplies vendor calls during the incidents it was built for.
- Global fallback to a second vendor for every feature, including features never evaluated on that vendor's model.
- A single latency allowance for the gateway across batch extraction and synchronous search.
- Migrating all twelve features at once with no per-feature rollback path.
- Treating "no team holds vendor keys" as done while a direct-call exception has no expiry.
