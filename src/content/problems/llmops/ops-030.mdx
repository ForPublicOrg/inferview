## Question

<Callout kind="interview" label="Concept, 20 minutes">
"How do you evaluate a generative model after fine-tuning?" The model is an 8B open-weight instruct model, LoRA-tuned to draft replies for a support team. Besides drafting, the product uses the same model to call two tools and to refuse requests outside policy. Say what you measure, against what, and how you would know it got worse at something you did not train.
</Callout>

<p class="tiny">The product setup is a scenario.</p>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the model would be replaced by if the fine-tune were dropped tomorrow.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the list of everything the product sends to this model that is not a draft reply.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which checkpoint the training job saved last and which one would be deployed.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Three evaluations, all paired on the same cases. The task: held-out conversations split by customer or time, scored against the prompted base model the team would otherwise ship. The regressions: a suite for every other job the model does (tool-call validity, refusals, schema compliance) plus facts the base already answered correctly, run on base and tuned models. The checkpoint: pick it at the peak of a dev-set task metric, not the last one. Only then an online test, because offline cases miss what users do.</p>
</Fragment>
<Fragment slot="long">
<p><b>The task eval.</b> Hold out cases before any processing, split by customer or by time so near-duplicate conversations do not sit on both sides, with the same diversity of inputs as training. Score the tuned model and the baseline on every case. The baseline is the best prompted configuration of the same base, and the current production model if there is one; beating the untuned base with no system prompt proves only that training did something. Draft quality needs a rubric scored by people or by a judge whose agreement with people you have measured on these drafts.</p>
<p><b>The regression suite.</b> A fine-tune changes behaviour it was not trained on. Biderman et al. measured it with three public benchmarks: after code instruction tuning, the mean of HellaSwag, ARC-Challenge and WinoGrande fell to 0.414 under full fine-tuning against about 0.51 for a rank-64 LoRA. Public benchmarks are a smoke test; the product's regressions are specific. Build a slice for each other job: tool calls scored for valid arguments and correct tool choice, a refusal set with both should-refuse and should-answer cases, the output schema, long multi-turn conversations. Add a slice of factual questions the base model answers correctly, because Gekhman et al. showed fitting unknown facts lowers accuracy on facts outside the training data.</p>
<p><b>How big each slice is.</b> The reader chooses the regression that matters. To see a refusal-accuracy drop from 90% to 85% between two models scored on different cases takes about 7.84 × (0.90 × 0.10 + 0.85 × 0.15) / 0.05² ≈ 682 cases per model at 95% confidence and 80% power. Scoring both models on the same cases needs fewer, because only disagreements carry information. A 50-case refusal set can only catch collapses.</p>
<p><b>The checkpoint.</b> Training loss keeps falling after the task metric peaks. Gekhman et al.'s 50% unknown-facts run scored 43.0 at the dev-set peak and 38.8 at convergence. Evaluate saved checkpoints on a dev set and deploy the peak.</p>
<p><b>Where this fails.</b> Every offline set is built from the past. The tuned model may write drafts agents edit more heavily without scoring lower on the rubric, so the release still needs an online comparison on edit distance or acceptance rate, with the regression slices as guardrails.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li>The tuned model wins the task eval by six points and loses three points of tool-call validity. Who decides, and with what number?</li>
<li>Your judge was calibrated on the base model's drafts. Why might its agreement with people change on the tuned model's drafts?</li>
</ul>

## Follow-ups

- The base model's provider ships a new version next month. Which parts of this evaluation do you rerun, and which can you reuse?
- How do you keep the held-out set from leaking into the next training round when both come from the same production logs?
- The team proposes MMLU as the general-capability check. What does it tell you about this product, and what does it miss?

## Common mistakes

- Comparing against the untuned base without a prompt instead of the configuration that would ship.
- Splitting train and test by row, so paraphrases and repeated tickets sit on both sides.
- Using training or eval loss as the decision metric.
- Checking only the trained task and missing tool-call, refusal and schema regressions.
- Deploying the last checkpoint by default.
