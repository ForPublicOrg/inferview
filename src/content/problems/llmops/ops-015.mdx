## Question

<Callout kind="interview" label="Debug, 30 minutes">
"A provider updated the model behind an alias. How would you detect it, and how would you separate it from a change in traffic mix?" Here is the week it may have happened. Pick the explanation, then say how you would have known on the first day.
</Callout>

The service, as a scenario. Customers upload invoices, receipts and purchase orders; the service sends each document to a hosted model and asks for JSON matching a fixed schema. The request names the provider's family alias, which the provider documents as pointing to the newest dated snapshot of that model. The reply goes through `json.loads` and schema validation; a failure is retried once with the same prompt, and a second failure sends the document to the human-review queue.

What the service logs per request: customer, document type, the alias it requested, input and output tokens, finish reason, HTTP status, latency and the parse result. It does not log the model field from the response body.

Since Tuesday the review queue has taken 6.3% of documents, against 2.1% the week before. On the same Tuesday a large new customer went live; its traffic is almost all multi-page purchase orders and is now 30% of volume. Nobody on the team changed the prompt, schema or client that week.

| Cohort | Share of requests, before / after | Review-queue rate, before / after | Median output tokens, before / after | Finish reason "length", before / after |
|---|---|---|---|---|
| Existing customers, invoices | 55% / 39% | 1.8% / 4.9% | 410 / 395 | 0.1% / 0.1% |
| Existing customers, receipts | 45% / 31% | 2.4% / 5.6% | 180 / 172 | 0% / 0% |
| New customer, purchase orders | none / 30% | none / 8.9% | none / 1,240 | none / 3.1% |
| HTTP 429 and 5xx, all traffic | 0.4% | 0.4% | | |

## Answer

**Why the alias.** A traffic-mix change moves the aggregate by changing the weights; it cannot change the rate inside a cohort whose own traffic did not change. The two existing cohorts did not change customers, documents or prompt, and their review rates went from 1.8% to 4.9% and from 2.4% to 5.6%. Something between the request and the parser changed for everyone. The output lengths in those cohorts moved by 4% (410 to 395, 180 to 172), and the invoice reply in the queue starts with a Markdown code fence that `json.loads` rejects. That is the shape Chen, Zaharia and Zou saw between two GPT-4 snapshots: the paper reports directly executable code falling from 52.0% to 10.0%, partly because the June snapshot wrapped its code in extra quotes. Nobody on the team shipped anything, so the provider side is the remaining suspect, and the alias is the part of the request that is allowed to move.

**Separating the two changes, in numbers.** The aggregate before was 0.55 × 1.8% + 0.45 × 2.4% = 2.1%; after, 0.39 × 4.9% + 0.31 × 5.6% + 0.30 × 8.9% = 6.3%. If the existing cohorts had held their old rates, the aggregate would be 0.39 × 1.8% + 0.31 × 2.4% + 0.30 × 8.9% = 4.1%, so at least 2.2 of the 4.2 points come from inside the existing cohorts. Of the new customer's 8.9%, the 3.1% that ended on the token cap is truncation, 0.30 × 3.1% = 0.9 points of the aggregate; the other 5.8% is close to what the existing cohorts now fail at, so it reads as the same new formatting on new documents. The mix shift is real but not the main cause; the existing-cohort rows are the control.

**The ranking.**

1. *The model behind the alias changed and its formatting broke the strict parser.* Everything except the truncation, about 3.3 of the 4.2 points, of which at least 2.2 are measured inside cohorts whose traffic did not change; the rest is the new customer's non-truncation failures, which also include whatever its documents would have failed at under the old model.
2. *The output token cap is too low for long purchase orders.* About 0.9 points, confined to the new customer, and it will grow with its volume. Raise the cap from measured output lengths of its documents, or split long documents by page.
3. *The retry repeats the identical request.* When the failure is a formatting habit of the model, the same prompt usually fails the same way twice, so the retry costs a call and rescues little. It did not cause the rise, but it hides nothing either; a retry that feeds back the parse error, or a repair step, would.
4. *The service does not log the response model.* Not a cause, but the reason this took a week. The OpenTelemetry GenAI conventions separate `gen_ai.request.model` (the alias) from `gen_ai.response.model` (what answered), and the conventions' OpenAI attributes add `openai.response.system_fingerprint` for changes in the serving environment.

**What the evidence does not show, and what to collect.** Nothing here proves the snapshot changed; the fence is suggestive, and a serving change behind the same model ID can do the same thing (Anthropic's documentation says infrastructure updates on a fixed ID occasionally change observable behaviour, and its 2025 postmortem describes a misconfiguration that produced unexpected characters). Collect: any stored raw response bodies, with their model field, from before and after Tuesday; the hourly review rate on Tuesday against the new customer's first request; and a replay of 300 documents from the existing customers' previous week, sent once to the alias and once to the previous dated snapshot if the provider still serves it. If the replay through the old snapshot parses at the old rate and the alias does not, the question is closed. Without any of it, ship the parser fix tonight anyway: it is safe whatever the cause.

**Tonight, and the decision after.** Tonight: strip a leading and trailing code fence before parsing, count every repair as a metric, and send repaired documents through schema validation as usual. LinkedIn reported the same class of fix: schema-invalid output about 10% of the time, cut to about 0.01% with a defensive parser.

Then two defensible structures:

- *Pin the dated snapshot.* The request names a fixed snapshot, and upgrades become the team's own release with a gate. Cost: improvements arrive only when the team migrates, every snapshot has a retirement date that forces a migration on the provider's schedule, and a pinned ID still changes at the serving layer, so pinning does not remove the need for detection.
- *Stay on the alias with detection and a fallback.* Log the response model and fingerprint, run a frozen replay set daily, and fall back to the pinned previous snapshot when it alarms. Cost: users eat up to a day of the new behaviour before the alarm, and the fallback works only while the old snapshot is served.

I would pin. For a parser-facing extraction service, a format change is an outage, and the cost of pinning is a migration the team schedules. Use the provider's structured-output mode if it constrains decoding to the schema, which removes the fence class of failure entirely.

**The detection you choose.** A frozen replay set of documents from existing customers, run daily against the production model ID with fixed parameters. The size is the choice. At a 2% baseline, with an alarm at a count no more than 1% likely by chance, the binomial gives:

| Replay set | Alarm at | Chance of catching a move to 5% on day one |
|---|---|---|
| 100 documents | 7 failures | 23% |
| 300 documents | 13 failures | 74% |
| 400 documents | 16 failures | 85% |

At 300, two consecutive days catch it about 93% of the time (1 − 0.26²). Anything from 300 to 1,000 documents is defensible depending on what a replay costs; 100 mostly misses a move this size. The replay holds the inputs fixed, so it answers the alias question regardless of traffic; the per-cohort rates on production answer the mix question. Log the response model next to both.

**Where the recommendation fails.** The repair hides the signal. The fence-stripping parser would have kept this week's queue near 2% while the model changed underneath; if nobody watches the repair count, the next behaviour change that the repair also absorbs goes unnoticed. And the replay set ages: it holds last month's documents, so a regression that only affects the new customer's purchase orders never reaches it until those documents are added.

## Follow-ups

- *Pushback: finance says the daily replay costs more than the review queue it protects. You can afford one of the two: the replay or logging and alarming on the response model. Which do you keep, and what change does the one you drop leave undetected?*
- *Reversal: what would you need to see to move back from the pinned snapshot to the alias?* A quarter of alias changes that the replay set caught within a day with no customer-visible failure, plus a provider changelog that announces snapshot moves before they happen.
- *Operating: the pinned snapshot retires in sixty days, and its successor fails 4% of the replay set where the current one fails 2%. Do you migrate early, wait, or keep the repair layer and ship, and who signs off?*

## Common mistakes

- Reading only the aggregate, which blends a mix shift with a within-cohort change.
- Blaming the new customer because it arrived the same day, without checking the cohorts that did not change.
- Treating a pinned model ID as a guarantee that output will never change, when the serving layer can still change it.
- Adding a tolerant parser and no counter on the repairs it makes.
- Logging the requested model and not the one that answered.
