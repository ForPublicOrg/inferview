## Question

<Callout kind="interview" label="Concept, staff, 30 minutes">
"How do you detect drift in your evaluator, separately from drift in the system it evaluates? And our judge model is retired in 60 days: what happens to the quality trend we report to the board?"
</Callout>

The setup, as a scenario. A hosted model judges 6,000 production answers a day against a pass or fail rubric, and the weekly pass rate goes into a quarterly report. A frozen replay set of 500 inputs runs through the production path every night. The human budget is 300 graded items a week. Last week the judged pass rate fell from 88% to 84.5% with no deploy on your side, and the provider has announced that the judge's model ID retires in 60 days.

Explain how you would attribute a change in the judged pass rate to the system, the traffic or the judge; how you would spend the 300 human labels; and what you do about the trend at the migration.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which items in your pipeline have both a fixed output and a stored human label.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how many verdicts change when today's judge scores the same fixed outputs twice.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask whether the outputs, retrieved context and rubric version behind last year's scores are stored, and what it costs to score them again.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Hold one side still at a time. A judge-control set of fixed outputs with human labels, scored on a schedule and on every judge change, measures the judge alone: the outputs cannot change, so any change in verdicts is the judge. The replay set, regenerated nightly and scored by a pinned judge, measures the system without traffic. Production measures everything. In the scenario, if the control set shows the judge net 3.5 points stricter while the replay set holds, the 88 to 84.5 drop is the judge. For the migration, either rescore stored history under the new judge or run both judges in parallel for an overlap window and report the break with a measured offset; which one depends on whether the history is stored and on the rescoring bill.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The attribution table.</strong> Three instruments, each holding something fixed:</p>
<table>
<thead><tr><th>Instrument</th><th>Fixed</th><th>Free</th><th>A change means</th></tr></thead>
<tbody>
<tr><td>Judge-control set: stored outputs with human labels, including known ties, verbosity bait and order-swapped pairs</td><td>Inputs, outputs, labels</td><td>Judge</td><td>The judge moved</td></tr>
<tr><td>Replay set: frozen inputs regenerated nightly, scored by the pinned judge</td><td>Inputs, judge</td><td>System</td><td>The system moved, or the judge did; read it next to the control set</td></tr>
<tr><td>Production sample</td><td>Nothing</td><td>Traffic, system, judge</td><td>Any of them; split by slice and version before reading</td></tr>
</tbody>
</table>
<p>The control set runs on every change to the judge's model ID, prompt, rubric or output schema, and also on a schedule with no change, because a pinned ID is not a pinned behaviour: Anthropic's documentation says serving infrastructure can change observable behaviour on an unchanged ID, and older aliases move to new snapshots. Track per run the verdict flips against the baseline run, their direction, agreement with the human labels by slice, invalid-output rate and order consistency on the swapped pairs.</p>
<p><strong>Sizing the alarm.</strong> Suppose the control set is 400 items. Score it twice with the same judge on the same day to measure its own noise; say 2% of verdicts flip, 8 expected. The standard deviation of that count is √(400 × 0.02 × 0.98) ≈ 2.8, so 15 or more flips is about 2.5 standard deviations above the noise and worth an alarm. If last week's run shows 20 flips, 17 of them pass to fail and 3 fail to pass, the judge is net (17 − 3) / 400 = 3.5 points stricter on fixed outputs. With the replay set flat under the same judge, that accounts for the whole 88 to 84.5 drop, and the right report is that quality did not change.</p>
<p><strong>The 300 human labels.</strong> They cannot be the sensitive instrument: 50 judge-fail items a week measure the judge's precision on fails, around 0.8, to only about ±11 points (1.96 × √(0.8 × 0.2 / 50)). The control set, paired against itself, is far more sensitive. Spend the humans where the control set is blind. One reasonable split: 100 a week on a fresh production audit stratified by judge verdict and slice, which catches the judge drifting on outputs that do not look like the control set; 100 to refresh the control set with recent outputs, versioned so old and new runs stay comparable; 100 a quarter re-labelling old control items blind, which measures criteria drift in the humans, the effect Shankar and colleagues named when grading changes the graders' criteria. Zheng and colleagues put strong judges at about the level of agreement humans have with each other, so a disagreement between judge and graders is evidence to inspect, not a verdict against the judge.</p>
<p><strong>The migration: the decision.</strong> Two answers are defensible.</p>
<p>Rescore history: re-run the new judge on every stored output and context and publish one continuous series. At 6,000 a day, a quarter of history is about 6,000 × 91 ≈ 546,000 judge calls, and it only works if the outputs, retrieved context and rubric version were stored. It gives a series where every point was scored the same way.</p>
<p>Overlap and splice: run old and new judges on the same items for a window, say two weeks, measure the offset and the agreement between them per slice, and report a marked break with the offset. It costs two judge bills for the window and no backfill, and the offset is only as good as its stability across slices.</p>
<p>The constraint conflict is the 60-day deadline and the judge budget against comparability of the board's series. If history is stored and the backfill fits the budget, rescore; if not, overlap. Either way, before the switch the new judge has to pass the control set and the human audit on its own, or there is no migration to make.</p>
<p><strong>Failure mode of this design.</strong> The control set ages. It holds outputs from last quarter's system, and when the product starts producing longer, tool-heavy answers, the judge can be stable on the control set and drift on what it now sees. The fresh audit and the refresh exist for that, and they are the first thing a tight budget cuts. A second failure: if the human graders' criteria drift in the same direction as the judge, the audit agrees with the judge and both are wrong; the blind re-label of old items is the only check on that.</p>

## Follow-ups

- *Pushback: two engineers own the judge and they want to replace the control set with a weekly human audit only, because it "measures what matters". What specific drift does that miss, and at what size?*
- *Reversal: what would you need to see before trusting judge scores across a judge change without any overlap or rescoring?* A control set that showed flips within the noise and no net direction, on a refreshed set, across several previous judge changes.
- *Operating: the provider's retirement date moves up to 21 days. Which part of the migration plan do you drop, and who signs off on the gap in the series?*

## Common mistakes

- Using the replay set to detect judge drift, when the replay regenerates outputs and so mixes system and judge.
- Treating a pinned model ID as a pinned judge and only running the control set when the ID changes.
- Spending the human budget on a weekly pass-rate estimate that is too noisy to see a few points of judge drift.
- Splicing the trend across a judge change without measuring the offset on the same items.
- Assuming the human labels are fixed ground truth and never measuring their own drift.
