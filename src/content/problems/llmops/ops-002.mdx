## Question

<Callout kind="interview" label="Concept, 25 minutes">
"We pointed MIPROv2 at the ReAct agent behind internal search. The run log says exact match went from 24% to 51%. The PM wants it in Thursday's release. What do you check before it ships, and what do you ship if the checks are not done by Thursday?"
</Callout>

The run mirrors the informal one in DSPy's optimizer documentation: `auto="light"`, `gpt-4o-mini`, 500 HotPotQA question-answer pairs, `answer_exact_match`. Your team's production traffic is employees asking about internal documents, not HotPotQA. The log shows two numbers and does not say which examples the 51% was scored on. Today is Monday.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which examples produced the 51%, and for the per-example scores of both programs on them.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the input tokens and tool calls per query before and after, at the same percentile.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask for twenty of the baseline's exact-match failures, read side by side with the gold answers.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A 27-point lift from an optimiser is a claim about the set it selected on, scored by a metric it optimised against, on data that is not production's. Before it ships I need three things: a held-out score the search never saw, compared pair by pair with the baseline; a reading of what the metric rewarded, because exact match on HotPotQA rewards answer format as much as retrieval; and the cost and latency per query, because the program now carries demonstrations into every step of the ReAct loop. If those are not done by Thursday, nothing optimised ships; at most the instruction text, without demos, behind a canary on a label of its own.</p>
</Fragment>
<Fragment slot="long">
<p><b>Which examples produced the 51%.</b> MIPROv2 chooses among candidates by scoring them on its validation set, so the best score on that set is biased upward by the selection itself. Size it: with <code>auto="light"</code> the current source draws a validation batch of 100 examples, and at 24% the standard error of one candidate's score is sqrt(0.24 × 0.76 / 100) = 4.3 points. If 20 candidates had the same true accuracy, the expected best observed score would sit about 1.87 standard errors above it, about 8 points (1.87 is the mean of the largest of 20 standard normal draws). That does not explain 27 points, and it does say the 51% overstates the lift. The number to ship on comes from a held-out set the optimiser never touched, scored on the same questions for both programs, so the comparison is paired and the losses are visible.</p>
<p><b>What the metric rewarded.</b> Exact match on short-answer QA fails correct answers phrased differently. A baseline at 24% exact match can be a better retriever than it looks, and an optimiser that teaches the agent to answer in HotPotQA's span style lifts exact match without finding more answers. Read 20 baseline failures beside their gold answers: if half are right and phrased differently, most of the lift is format. That matters because production users read prose answers about internal documents, where HotPotQA's span style is neither expected nor checked.</p>
<p><b>What the program now costs.</b> With the defaults, each predictor can carry up to 4 bootstrapped and 4 labelled demonstrations, and a ReAct agent calls its predictor once per step. Compare input tokens and tool calls per query at the median and p95, and the rate of runs that hit the step limit. An optimised ReAct program that answers better with longer prompts can still miss the latency budget.</p>
<p><b>Per-input regressions.</b> OpenAI's optimizer guide says an optimised prompt can do worse than the original on specific inputs. Count the flips on the held-out set: questions the baseline answered and the candidate lost. A 10-point net gain made of 20 wins and 10 losses is a different release from 10 wins and none.</p>
<p><b>Distribution.</b> The run optimised on HotPotQA. The demos it bootstrapped are HotPotQA questions with Wikipedia-style evidence, now placed in front of every internal-search query. The held-out set that decides the release has to be drawn from production queries with labels, and building it is the item most likely to miss Thursday.</p>
<p><b>Two defensible answers.</b> Ship the full optimised program (instructions and demos) once a held-out set of production queries confirms a paired gain: the cost is the labelling, and probably the Thursday date. Or ship only the optimised instruction text, without demos, to a canary label: the cost is most of the gain, if the gain came from the demos, in exchange for no extra prompt tokens and no foreign examples in the context. I would hold the full program for the held-out result and offer the instruction-only canary for Thursday, because it is the change I can roll back and measure without the labelled set.</p>
<p><b>The constraint conflict.</b> The deadline is Thursday and the measurement that justifies shipping does not exist yet. Shipping without it trades a release date for an unmeasured regression risk on employee queries. That trade belongs in writing, with the PM's name next to it if they take it.</p>
<p><b>How the recommendation fails.</b> A canary on production queries has no exact-match labels, so it measures proxies: thumbs-down rate, reformulated queries, time to a click. An instruction change that makes answers terser can move those proxies up while making answers less complete. Put the canary's success criteria, and the size of change that would count as a regression, in the release note before the canary starts, not after the first dashboard.</p>
</Fragment>

## Follow-ups

- *Pushback: the optimiser's own validation split is 100 examples the training never saw. Why is that not a held-out set?* Because the search chose the winner by its score on those 100; a held-out set is one no choice depended on.
- *Reversal: you rerun the optimiser with three seeds and get 49%, 50% and 51% on the held-out set, with different demos each time. What does that change in your recommendation?*
- *Two staff engineers disagree: one wants the optimiser in CI on every prompt change, the other wants it run by hand twice a year. How do you decide without deciding by rank?* Compare what each costs per run and how often the held-out set would have to be refreshed to stay unseen.
- *Operating: what changes to run this optimisation against the production model client instead of a notebook?* Rate limits during the search, the client's request cache returning the same completion for identical prompts, and recording the model, optimiser version and seed in the registry next to the prompt.

## Common mistakes

- Reading the optimiser's best validation score as the expected production lift.
- Treating exact match as accuracy without reading the failures it counts.
- Comparing the two programs on different samples, so the interval on the difference is wider than it needs to be and the losses never show.
- Shipping instructions and demos tied to one model as if they were model-independent.
