## Question

<Callout kind="interview" label="Concept, 25 minutes">
"We're testing a new model in our in-product assistant. Do we randomise by user, by conversation or by request? Decide, and show me what your choice does to the error bars."
</Callout>

The setup, all of it scenario:

- An assistant inside a project-management product. Conversations average 6 turns. Over 14 days an active user has 3.0 conversations on average, with a standard deviation of 3.0.
- 30% of users have turned on memory: the assistant saves facts from one conversation and reads them in later ones.
- Candidate metrics: task completed per conversation (55% today, from an explicit "done" action), thumbs-down per turn, and 14-day return rate per user.
- The experiment can have about 80,000 active users over 14 days, split 50/50.
- From last month's logs: the correlation of the completion flag between two conversations of the same user is 0.25; the correlation of thumbs-down between two turns of the same user is 0.5.
- Product wants a readout in two weeks.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the model in turn 4 reads that the model in turn 3 wrote.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what memory stores, who can read it, and whether a memory written in one arm is read in the other.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask for the distribution of conversations per user, not only the mean.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Not by request: the model in each turn reads the other model's earlier turns, so a per-request coin flip measures a mixed policy nobody would ship. Between user and conversation, memory decides it: with 30% of users carrying facts written by one arm into the other arm's conversations, conversation assignment leaks treatment into control. I randomise by user and pay for it in the error bar. With 120,000 conversations per arm and a completion rate of 55%, the naive 95% half-width on the difference is 0.40 points; with a user's conversations correlated at 0.25 and uneven conversation counts, the design effect is 1 + (6 − 1) × 0.25 = 2.25, so the standard error grows by 1.5 times and the half-width is 0.60 points. The minimum detectable effect at 80% power moves from 0.57 to 0.85 points. A per-turn metric is worse: 18 turns per user at a correlation of 0.5 gives a design effect of 9.5, three times the naive standard error.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Request is out for this product.</strong> A conversation is one stateful process: turn 4's input contains turns 1 to 3. Assigning per request means a conversation alternates models, each one continuing the other's work, and the measured difference is between two mixtures. Request-level assignment is right for stateless calls (a classifier, autocomplete, a single-shot summary), and nowhere here.</p>
<p><strong>Conversation against user, the real decision.</strong> Conversation-level assignment gives more independent units and needs no design effect for a per-conversation metric. Its costs: a user meets both models within a week, so expectations set by one carry into the other; the 14-day return rate cannot be attributed to either arm; and memory breaks independence outright, because a fact saved in a treatment conversation is read in the user's next control conversation. User-level assignment keeps each user's experience consistent and makes user-level metrics attributable, and costs precision, because a user's conversations are correlated.</p>
<p><strong>The error calculation.</strong> Per arm: 40,000 users × 3.0 = 120,000 conversations. Naive standard error of the difference in completion: √(2 × 0.55 × 0.45 / 120,000) = 0.00203, a 95% half-width of 1.96 × 0.00203 = 0.40 points. Miller's clustered error adds the within-user cross terms of the residuals; with clusters of size m and correlation ρ the variance multiplies by 1 + (m − 1)ρ. With every user at exactly 3 conversations that is 1 + 2 × 0.25 = 1.5. Users are not equal: with a mean of 3 and a standard deviation of 3, the size that matters is E[m²] / E[m] = (9 + 9) / 3 = 6, so the factor is 1 + 5 × 0.25 = 2.25 and the standard error is √2.25 = 1.5 times naive.</p>

<p>The MDE column is 2.802 × SE, from z<sub>0.975</sub> + z<sub>0.80</sub>. The last row is how Anthropic's "over three times" happens in practice: large clusters with strongly correlated items. In production I would not plug in the formula; I would compute the clustered error directly from the per-user residual sums, one pass over the rows, which also handles a power user or a test account with hundreds of conversations that the mean hides.</p>
<p><strong>The estimand is also a choice.</strong> Pooled completion (all completed conversations over all conversations) weights heavy users by their volume; the mean of per-user completion rates weights every user equally. Both are valid under user assignment and they answer different questions: the pooled ratio is the share of work the assistant finishes, the per-user mean is the typical user's experience. Pick one as primary before launch; the pooled ratio needs the clustered error above, the per-user mean has users as independent rows already.</p>
<p><strong>Where user assignment fails.</strong> The unit is really whatever shares state. If the product also has workspace-level memory or shared prompt templates that the assistant writes, treatment users change what control users in the same workspace read, and the unit becomes the workspace: perhaps a few thousand clusters with heavy correlation, and an interval wide enough that two weeks will not resolve a 1-point effect. The other leak is identity: people with two accounts, or logged-out traffic keyed by device, land in both arms.</p>
<p><strong>When conversation assignment is the better answer.</strong> If memory is off for everyone, the metric is per conversation, and the readout date cannot move, conversation assignment is defensible and buys back the factor of 2.25 in sample size. Restricting it to the 70% of users without memory is a weaker version: the result then speaks for a population that chose not to use a feature, and does not generalise to the 30% who did.</p>

## Follow-ups

- *Pushback: product says 0.85 points is too coarse and the readout cannot move; they want conversation assignment and a 0.57-point MDE. What do you accept in writing about memory leakage, and how would you estimate its size from the data you will have?*
- *Reversal: what would you need to see in a pilot to switch from user to workspace assignment, given that it widens the interval several times over?*
- *Operating: the control model gets a retirement notice with Anthropic's 60-day minimum, and the user-level test needs 14 days plus analysis. Which assignment do you use for the migration test, and what changes if memory content was written by the retiring model?*

## Common mistakes

- Randomising by request because it maximises the number of units, for a product where each turn reads the previous ones.
- Assigning by user and then computing the standard error as if conversations were independent.
- Using the mean conversations per user in the design effect when the counts are skewed.
- Ignoring memory and other shared state that carries one arm's output into the other arm.
- Leaving the choice between a pooled ratio and a per-user mean to whoever writes the dashboard.
