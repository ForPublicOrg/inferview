    import hashlib
    import hmac
    import re
    from datetime import datetime, timezone

    EMAIL = re.compile(r"[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,}")
    CATEGORIES = {"billing": "billing", "payments": "billing", "login": "account", "account": "account",
                  "bug": "technical", "technical": "technical"}


    def to_epoch(value):
        if isinstance(value, (int, float)):
            return float(value)
        return datetime.fromisoformat(value.replace("Z", "+00:00")).astimezone(timezone.utc).timestamp()


    def clean(text):
        return re.sub(r"\s+", " ", EMAIL.sub("<EMAIL>", text or "")).strip()


    def build_dataset(users, tickets, messages, key):
        eligible = {u[0] for u in users
                    if not u[2] and u[3] and u[4] is None and not u[1].lower().endswith("@demo.test")}
        by_ticket = {}
        for m in messages:
            by_ticket.setdefault(m[1], []).append(m)
        out, seen = [], set()
        for ticket_id, user_id, status, category, _created in sorted(tickets, key=lambda t: t[0]):
            if user_id not in eligible or status != "resolved":
                continue
            thread = sorted(by_ticket.get(ticket_id, []), key=lambda m: (to_epoch(m[4]), m[0]))
            first = next((m for m in thread if m[2] == "customer" and clean(m[3])), None)
            if first is None:
                continue
            start = to_epoch(first[4])
            reply = next((m for m in thread if m[2] == "agent" and clean(m[3]) and to_epoch(m[4]) > start), None)
            if reply is None:
                continue
            prompt, response = clean(first[3]), clean(reply[3])
            signature = (prompt.casefold(), response.casefold())
            if signature in seen:
                continue
            seen.add(signature)
            out.append({
                "ticket_id": ticket_id,
                "user_key": hmac.new(key.encode(), str(user_id).encode(), hashlib.sha256).hexdigest()[:16],
                "category": CATEGORIES.get((category or "").strip().lower(), "other"),
                "prompt": prompt,
                "response": response,
            })
        return out

## Question

<Callout kind="interview" label="Code, 35 minutes">
Here is a demo copy of our support database. Get a usable fine-tuning set out of it, using SQL for the extract and Python for the rest.
</Callout>

The database has three tables. The demo copy was built from production with test accounts added, and a migration two years ago changed how message times are stored.

```sql
users    (user_id INTEGER, email TEXT, is_internal BOOLEAN, consent_training BOOLEAN, deleted_at TEXT NULL)
tickets  (ticket_id INTEGER, user_id INTEGER, status TEXT, category TEXT, created_at TEXT)
messages (message_id INTEGER, ticket_id INTEGER, sender TEXT,    -- customer | agent | bot
          body TEXT, sent_at)                                    -- ISO 8601 text, or epoch seconds before the migration
```

Two parts.

1. Write the SQL that pulls candidate rows out of the database. State which filters belong in SQL and which in Python, and why.
2. Implement `build_dataset(users, tickets, messages, key)` over the rows of the three tables, returning one example per usable ticket with a pseudonymous `user_key`, a normalised `category`, a `prompt` and a `response`.

Usable means: the user is not internal, not on the demo domain `@demo.test`, has consented to training use and is not deleted; the ticket is resolved; the prompt is the first non-empty customer message and the response is a human agent's reply that comes after it. Email addresses must not survive. The same prompt and response must not appear twice. One user maps to one pseudonym, which changes with the key and cannot be computed from the user id alone. The output must not depend on the order of the input rows. Categories arrive as free text typed by agents; reduce them to at most five values of your choosing. The full table has about 60,000 messages and the build has five seconds.

Which agent reply becomes the response is your decision; say what it costs.

## Answer

**The extract.** Every filter that excludes people runs in SQL, so rows from internal, demo, deleted and non-consenting users never leave the database:

```sql
WITH eligible AS (
  SELECT user_id FROM users
  WHERE NOT is_internal
    AND consent_training
    AND deleted_at IS NULL
    AND lower(email) NOT LIKE '%@demo.test'
)
SELECT m.message_id, m.ticket_id, t.user_id, t.category, m.sender, m.body, m.sent_at
FROM tickets t
JOIN eligible e ON e.user_id = t.user_id
JOIN messages m ON m.ticket_id = t.ticket_id
WHERE t.status = 'resolved'
  AND m.sender IN ('customer', 'agent');
```

There is no ORDER BY on `sent_at`, deliberately. In SQLite a column holding both integers and text sorts every integer before every string, with no conversion before the sort, so ordering by `sent_at` puts every pre-migration message ahead of every later one regardless of time. The thread order is computed in Python after parsing both forms. On a database with stricter typing, the fix belongs in the migration; in the extract, parse and sort in one place.

Python does what SQL does badly or what must be tested: parsing two time formats, redaction, choosing the reply, deduplication and the pseudonym.

**The reference solution, step by step.** It groups messages by ticket once, which is what keeps it inside five seconds: looping over tickets and scanning all messages for each one is 12,000 × 60,000 = 720 million comparisons. Each thread is sorted by parsed time, with the message id as the tie-break, so the result does not depend on row order. The prompt is the first customer message that is non-empty after cleaning. The response is the first agent reply after the prompt.

That choice is the decision the question leaves open. The first reply is usually the one that addresses the customer's message as written, and it is cheap to identify. The last agent message before resolution is often the one that solved the problem, but it answers a conversation, not the first message, so pairing it with the opening prompt teaches the model to answer things the customer has not yet said. A third option is to keep the whole thread as a multi-turn example, which is the most faithful and the most expensive to review. The first-reply rule fails on tickets where the first reply is "Looking into it": a filter for short holding replies, or the support lead's review of a sample, catches those.

Redaction runs before deduplication, so two tickets that differ only in the customer's email collapse into one. The pseudonym is an HMAC of the user id under the key: a plain hash of a small integer id is reversed by hashing every id, and the key also lets the deletion path find a user's rows later. Unknown or free-text categories map to `other`, which keeps the category set bounded and makes the long tail visible instead of inventing a mapping for it.

The hidden tests check properties, not one output: no row from an excluded user or unresolved ticket, no email address, prompt and response taken from the right senders in the right order, no duplicate pairs, one pseudonym per user and a different one under another key, the same tickets regardless of input order, at most five categories, and most eligible tickets present.

## Follow-ups

- *The same job now runs against the production replica, with 400 million messages. What changes?* The extract streams with a server-side cursor in ticket order, sorted by a parsed timestamp column added for the job, and the consent and deletion filters are evaluated at a recorded snapshot time, so a rerun can show which consent state it used.
- *Consent was added as a column last year and is NULL for older users. Is NULL consent or refusal?* Refusal, unless legal says the earlier terms covered training; the NULL rows are counted and reported, not silently dropped.
- *A user is deleted after the dataset is built. How does the deletion reach it?* The keyed pseudonym is computed for the deleted id, every dataset version containing it is rebuilt without those rows, and the next fine-tune uses the rebuilt version.
- *The regex misses names and street addresses. What do you put in its place for the production run, and how do you know its miss rate?*

## Common mistakes

- Pulling every user's messages into Python and filtering consent there, which copies non-consented data out of the boundary the filter exists to protect.
- Ordering by a column of mixed integers and strings and trusting the order.
- One query per ticket, which is the 720-million-comparison loop moved into the database.
- Using the bot's automatic acknowledgement as the response because it is the first non-customer message.
- Deduplicating before redaction, so templated tickets that differ only in an email address all survive.
- Hashing the user id without a key.
