## Question

<Callout kind="interview" label="Critique, 30 minutes">
"Here is the rollout plan for the billing assistant's new version. Review it as if you had to approve it today. List what is wrong, in order of what you would fix first."
</Callout>

**Rollout plan: billing assistant v2.** Written 2026-10-28.

*What changes.* System prompt `billing-assistant` moves from version 13 to version 14 in Langfuse; v14 is rewritten around the new refund and invoice tools. The model moves from `claude-sonnet-4-5-20250929` to `claude-sonnet-5-5`. Both ship behind one flag, `assistant_v2`, assigned by a hash of the customer id.

*Offline evidence.* v14 on `claude-sonnet-5-5` against v13 on `claude-sonnet-4-5-20250929`, on the 150 conversations the prompt team used while writing v14: resolution 81% against 74%.

*Prompt v14 config, as stored in Langfuse:*

```json
{ "model": "claude-sonnet-5-5", "temperature": 0.2, "max_tokens": 1024 }
```

*Call site after the change:*

```python
prompt = langfuse.get_prompt("billing-assistant")
if flags.enabled("assistant_v2", customer_id):
    model = prompt.config["model"]
else:
    model = "claude-sonnet-4-5-20250929"
try:
    resp = client.messages.create(
        model=model,
        temperature=prompt.config["temperature"],
        max_tokens=prompt.config["max_tokens"],
        system=prompt.compile(customer_name=customer.name),
        messages=history,
        tools=BILLING_TOOLS,
    )
except anthropic.APIStatusError:
    resp = client.messages.create(model="claude-sonnet-4-5-20250929", system=prompt.compile(customer_name=customer.name),
                                  messages=history, tools=BILLING_TOOLS, max_tokens=1024)
trace.update(metadata={"assistant_v2": flags.enabled("assistant_v2", customer_id)})
```

*Schedule.*

1. Monday: move the `production` label to v14. Flag at 10%.
2. Wednesday: flag at 50% if nothing looks wrong.
3. Friday: flag at 100%.
4. 2026-11-25: remove the old code path.

*Success metric.* CSAT from the post-conversation survey (about 4% of conversations answer it).

*Rollback.* Turn the flag off, or move the `production` label back to v13. Both are instant and need no deploy.

## Answer

Ranked by what would hurt first.

**1. The treatment arm is probably not running the new model.** v14's config sends `temperature: 0.2`. The Claude API removed `temperature` in API version 2026-10-21, and earlier versions reject a non-default value on Claude 4.7 and later, so every `claude-sonnet-5-5` request returns a 400. The `except` catches it and retries on the old model with the new prompt. Nothing errors; the flag-on arm quietly becomes v14 on the old model, the trace records `assistant_v2: true`, and the readout compares the old model with itself. A senior reviewer reads the `try` as resilience and moves on.

**2. The flag does not gate the prompt.** `get_prompt` fetches the `production` label for every caller, and Monday's first step moves that label to v14. From Monday, 100% of customers get v14, and the 90% with the flag off get v14 on the old model, a combination no one evaluated. The flag gates only the model, while the plan, the offline evidence and the rollback all assume it gates both.

**3. The rollback target retires in 33 days.** `claude-sonnet-4-5-20250929` was deprecated on 2026-09-30 and retires on 2026-11-30; after that, requests to it fail. "Turn the flag off" stops being a rollback on 2026-11-30, and the plan removes the old path on 2026-11-25 with no step for what happens if v2 has to come back in December. The fallback in the `except` fails at the same moment.

**4. The offline evidence is confounded and in-sample.** Two changes moved at once, so the 7-point gap cannot be split between prompt and model, and it was measured on the 150 conversations v14 was written against. Before shipping, the minimum is v14 and v13 on the new model, on conversations the prompt team never saw, with the paired difference and its error.

**5. Traces cannot attribute anything.** The trace records the flag state, not the model that answered or the prompt version served. With the fallback and the label both changing what a request gets, the logs cannot reconstruct which of four combinations served a conversation.

**6. The ramp is faster than the metric.** CSAT from 4% of conversations is a thin signal, the steps are 48 hours apart, shorter than one weekly cycle, and "if nothing looks wrong" is not a trigger. Name guardrails with thresholds: tool-call error rate, refunds issued per conversation, handoff rate, cost per conversation, and the sample ratio of flagged customers, each with a rollback threshold written down before Monday.

**7. "Instant" rollback is not instant.** Langfuse's SDK caches prompts, and its docs say the first traces after a label move may still use the old version. A label rollback is acceptable if the cache TTL is set short and the rollback trigger allows for that lag; the plan claims neither.

**The decision: one flag or two.** Bundling is defensible here, and is what I would choose: v14 was rewritten for the new tools, v13 on the new model and v14 on the old model are products no one intends to ship, and a two-arm test of complete configurations answers the question the business asks. Its cost is that a regression cannot be attributed to prompt or model from the online data, which is why the offline comparison has to separate them first. Two independent flags in a 2 × 2 design measure each change and their interaction, and cost two cells of customers on configurations that will never ship plus a slower readout on the interaction. For a bundle, make it real: put both model and prompt in one Langfuse version, point the flag at a label (`candidate` for flag-on, `production` for flag-off), drop `temperature` from the config, and make the fallback fail loudly in the treatment arm instead of switching models.

**Where the fix fails.** With the model id in a Langfuse config, moving a label changes the production model without a code review. Anyone with edit rights on the prompt can ship a model change. Protect the `production` and `candidate` labels and record label moves in the change log, or keep the model id in code and accept a deploy per change.

## Follow-ups

- *Pushback: the prompt team says separating prompt and model offline costs a week they do not have before the 2026-11-30 retirement. Which half of the evaluation do you cut, and what risk do you write down?*
- *Reversal: the bundled test shows resolution up 3 points and refunds per conversation up 12%. What would you need to see to roll back a configuration that resolves more conversations?*
- *Operating: it is 2026-11-20 and v2 shows a tool-call regression on invoices. The old model retires in ten days. Do you ship v14 on the new model degraded, or v13 on the new model untested, and who signs off?*

## Common mistakes

- Reading the `except` as a safety net without asking what the flag-on arm then measures.
- Assuming the flag gates the prompt because the plan says it does, when the call site fetches the production label for everyone.
- Accepting a rollback to a model id without checking its retirement date.
- Attributing the 7-point offline gain to the model, the prompt or both, when the design cannot tell them apart.
- Treating a label move as an instant rollback while the SDK caches prompts.
