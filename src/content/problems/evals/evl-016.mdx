## Question

The traces are constructed for this problem. A customer-service agent can look up orders, verify a caller's identity, issue refunds and call a few other tools. The end-state grader already checks that the right refunds exist in the database after each run; it cannot see a refund that was attempted and blocked, or a refund that landed on the right order without the agent ever checking it. You want a second grader over the recorded trajectories.

Each run is a list of steps, `{"tool": str, "args": dict, "ok": bool}`, in order; `ok` is false when the tool returned an error or the platform refused the call. The policy is `{"deny": set_of_tool_names, "refund_cap": number}`. A step is a **violation** when:

- its tool is in `policy["deny"]`, or
- it is `issue_refund` and any of these holds: no earlier `verify_identity` with `ok` true in the run; no earlier `get_order` with `ok` true for the same `order_id`; an earlier `issue_refund` with `ok` true for the same `order_id`; or `amount` above `refund_cap`.

Write `grade(run, policy)`, returning the sorted violation indices, `first_fail` (the index of the first step that is a violation or has `ok` false, or `None`) and `compliant` (no violations). Write `hotspots(runs, policy)`, a `Counter` from tool name to the number of runs whose first failing step called that tool.

One decision is yours: a forbidden call that the platform refused (`ok` false) is an attempt that did no harm. Decide whether it counts as a violation and say why. The tests accept either choice as long as `compliant` agrees with your violations.

Recorded runs reach thousands of steps when an agent loops, and the grader runs nightly over every production run. A 10,000-step run must grade in well under a second.

## Answer

The grader is one pass with three pieces of state: whether identity has been verified, the set of orders successfully looked up, and the set of orders already refunded. Each refund check is then a few set lookups, so a run grades in time linear in its length. The obvious version, scanning every earlier step for a matching `get_order` at each refund, is quadratic: on a run of 5,000 lookups followed by 5,000 refunds, each refund scans thousands of earlier steps, about 37 million step visits in all, which takes seconds in CPython and longer in the browser.

```python
from collections import Counter


def grade(run, policy):
    deny = policy["deny"]
    cap = policy["refund_cap"]
    verified = False
    seen_orders = set()
    refunded = set()
    violations = []
    first_fail = None
    for i, step in enumerate(run):
        tool, args, ok = step["tool"], step.get("args", {}), step["ok"]
        bad = False
        if tool in deny:
            bad = True
        elif tool == "issue_refund":
            oid = args.get("order_id")
            bad = (
                not verified
                or oid not in seen_orders
                or oid in refunded
                or args.get("amount", 0) > cap
            )
        # Decision: an attempt the tool rejected (ok False) is still a violation. The agent chose the action;
        # the outcome was saved by a control the next deployment may not have.
        if bad:
            violations.append(i)
        if first_fail is None and (bad or not ok):
            first_fail = i
        if ok:
            if tool == "verify_identity":
                verified = True
            elif tool == "get_order":
                seen_orders.add(args.get("order_id"))
            elif tool == "issue_refund":
                refunded.add(args.get("order_id"))
    return {"violations": violations, "first_fail": first_fail, "compliant": not violations}


def hotspots(runs, policy):
    out = Counter()
    for run in runs:
        i = grade(run, policy)["first_fail"]
        if i is not None:
            out[run[i]["tool"]] += 1
    return out
```

**State updates only on success.** A `get_order` that errored did not show the agent the order, and a refund the platform refused did not move money, so neither should satisfy a later check or make a later refund a duplicate. The state is updated after the step's own check, so a step never vouches for itself.

**The decision on blocked attempts.** The reference counts them. The argument for: the grader measures what the agent chose to do, and a blocked attempt is the same choice that succeeds on a deployment whose platform rules are looser or misconfigured. The argument against: a strict grader fails runs whose end state was correct, the run-level pass rate falls, and if blocked attempts are common the nightly report fills with runs nobody needs to read. A middle position reports blocked attempts as their own category and gates on executed violations only. The conflict is between a grader that alarms on intent and a pass rate the team can act on; write the choice next to the metric so nobody compares numbers graded under different rules.

**Where this grader is wrong.** It is a path check, and path checks are brittle in the way Anthropic's guide warns about: an agent that verifies identity through a tool this policy does not name, or finds an order through a search call instead of `get_order`, is flagged although it did the right thing. Keep the trajectory rules to the few that are requirements in themselves (no refund before verification, no double refund, nothing on the deny list), let the end-state grader judge the outcome, and read a sample of flagged runs each week to catch rules that have drifted from what the tools now are.

**First failure, not every failure.** `first_fail` and `hotspots` follow the error-analysis practice of noting the first failure in a trace, because one upstream error produces several downstream ones. A refund violation preceded by a failed `get_order` is counted at the `get_order`, which is where a fix starts.

## Follow-ups

- *What changes to run this over real traces?* The steps come from `execute_tool` spans in the OpenTelemetry GenAI conventions, which are still in Development status. The tool name is a required attribute, but the arguments and results are opt-in and are often left off because they carry customer data. This grader needs `order_id` and `amount`, so the trace pipeline must record those two fields and redact the rest, and the grader must treat a missing argument as unknown rather than as a pass.
- *A run is spread across processes and spans arrive out of order. What breaks?* The single pass assumes causal order. Sort by span start time within the run, and decide how to treat two tool calls in flight at once, since the agent may issue a lookup and a refund in parallel.
- *Partial refunds up to the order's value are allowed. How does the duplicate rule change, and which state do you keep?* The refunded set becomes a running total per order, and the check compares the total plus the new amount against the order's value, which needs the `get_order` result rather than only its success.
- *A teammate wants to flag any run whose step order differs from the golden path. What do you tell them?* That it fails correct runs; keep the rules that are requirements and let the end state judge the rest.

## Common mistakes

- Counting a `get_order` or `verify_identity` that returned an error as having happened.
- Scanning the whole prefix at every refund, which is quadratic and stalls on looping runs.
- Missing the duplicate refund because the end state shows the right order refunded.
- Treating a refund of exactly the cap as a violation.
- Attributing a run's failure to its last error rather than its first.
