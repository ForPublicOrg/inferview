## Question

<Callout kind="interview" label="As a public interview guide phrases it">
"How do you trace a multi-step run so you can see which tool call went sideways?"
</Callout>

One answer is a transition failure matrix. A text-to-SQL agent runs through named states: `ParseRequest`, `DecideTool`, `GenSQL`, `ExecSQL`, `Answer`. Each trace is a list of `"State:ok"` or `"State:fail"` strings in order. For every failed trace, record the last state that succeeded and the state where the first failure happened, then count the pairs. The most common pair is where to spend your next week.

Write three functions:

- `first_failure(trace)` returns `(last_ok, failed_at)`, using `"START"` when the very first step fails, or `None` if nothing failed. Only the first failure counts; later failures are usually consequences. State names may themselves contain a colon, so split on the last one.
- `failure_matrix(traces)` returns a `collections.Counter` from `(last_ok, failed_at)` pairs to counts, skipping traces with no failure.
- `worst_transition(traces)` returns the most common pair, breaking ties by the pair's normal sort order, or `None` if no trace failed.

Standard library only.

## Hints

<details class="hint"><summary>Hint 1</summary><p>`"Fetch:http:ok".rsplit(":", 1)` gives `["Fetch:http", "ok"]`.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Walk the trace once, remembering the last state that was ok; return on the first fail.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For the tie-break, sort by negative count and then by the pair itself.</p></details>

## Answer

The whole technique is one loop. Walk the steps, remember the last state that succeeded, and return the pair at the first failure. Splitting on the last colon keeps state names like `Fetch:http` intact.

```python
from collections import Counter


def first_failure(trace):
    last_ok = "START"
    for step in trace:
        state, status = step.rsplit(":", 1)
        if status == "fail":
            return (last_ok, state)
        last_ok = state
    return None


def failure_matrix(traces):
    return Counter(t for t in map(first_failure, traces) if t is not None)


def worst_transition(traces):
    m = failure_matrix(traces)
    if not m:
        return None
    return min(m.items(), key=lambda kv: (-kv[1], kv[0]))[0]
```

On the six test traces, five fail, and the matrix has `("GenSQL", "ExecSQL")` twice and every other pair once, so the agent's weak point is executing the SQL it generated. In the FAQ's version of this example, the same pair had 12 failures against 2 for the DecideTool to PlanCal transition, which is the kind of gap that tells you where to look.

Why first failure and not every failure: once SQL generation goes wrong, execution and the answer usually fail too. Counting all of them adds noise and points at downstream symptoms. The `min` with a key of `(-count, pair)` gives a deterministic answer on ties, which matters when the result feeds a report or a test; `Counter.most_common` keeps insertion order on ties, which depends on trace order.

## Follow-ups

- *How would you turn this into a dashboard?* Rows as the last successful state, columns as the failed state, cells as counts, filtered by prompt version and model version so a release that shifts failures between states is visible.
- *The agent can loop back to an earlier state. Does this still work?* Yes, because it records the last ok state before the first failure, whatever the path. For loops you may also want a per-state retry count.
- *Where do the state labels come from in a real system?* From span names in your traces, such as OpenTelemetry `execute_tool` spans with the tool name, plus a check per span that decides ok or fail.

## Common mistakes

- Counting every failure in a trace, which over-weights downstream symptoms.
- Splitting on the first colon and mangling state names.
- Returning `most_common(1)` and getting a different answer when the traces arrive in a different order.
- Building the matrix from all traces, including successes, then dividing by the wrong total when reporting rates.
