## Question

<Callout kind="interview" label="As public interview guides phrase it">
"When do you trust GPT-4-as-judge vs a human?" and "What does LLM-as-a-judge do, and what are its failure modes?"
</Callout>

Your team wants to replace weekly human review of a summarisation feature with an LLM judge. How do you decide whether the judge can be trusted, what do you measure, and what would make you keep humans in the loop?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Treat the judge as a classifier. What does a classifier need before it ships?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which class is "positive" when the judge's job is to find failures?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Each known bias has a cheap experiment that tests for it.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>I trust a judge after I have measured it against human labels it was not tuned on. One binary judge per failure mode, labels from a domain expert split into train, dev and test, and on the test set I report TPR (the share of real failures it catches) and TNR (the share of good outputs it passes), not raw agreement. I run bias checks for position, length and self-preference. Humans stay for creating and refreshing those labels, for high-stakes slices, and whenever the judge's model or prompt changes.</p>
</Fragment>
<Fragment slot="long">
<p>What the judge does. It reads an output, and usually the input and some context, and returns a verdict on a criterion. It is a classifier written in English, so it needs a specification, labelled data and a test set like any classifier.</p>
<p>Build. Start from error analysis so each judge targets one real failure mode with a binary verdict. Have one principal expert label outputs with pass or fail and a short critique; the critiques become few-shot examples. Ask for reasoning before the verdict.</p>
<p>Validate. Split labels roughly 10 to 20% train, 40 to 45% dev, 40 to 45% test, with 30 to 50 examples of each label in dev and test. Iterate on dev, measure once on test. Use failure as the positive class: TPR is failures caught, TNR is passes passed. Raw agreement hides a judge that always says pass when failures are rare.</p>
<p>Bias tests. Position: run pairwise comparisons in both orders and count only consistent wins; in MT-Bench GPT-4 was consistent 65.0% of the time with its default prompt (77.5% with a few-shot prompt), and a later study found inconsistency is worst when answers are close in quality. Length: pad answers without changing content and see whether verdicts move. Self-preference: judge with a different model family, or check whether swapping judges changes the ranking.</p>
<p>Use. Correct the production pass rate for measured TPR and TNR, report it with an interval, and re-validate when the judge model or prompt changes. Keep humans for labels, for audits of a sample of judge verdicts, and for low-volume, high-stakes slices.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What agreement number is good enough?</em> There is no universal threshold. It depends on the cost of each error type; I set targets for TPR and TNR separately, from what a miss and a false alarm cost the product.</li>
<li><em>The MT-Bench paper says GPT-4 agrees with humans over 80% of the time. Is that enough?</em> That was on pairwise preferences in that dataset, equal to human-human agreement there. It says nothing about my judge on my failure modes.</li>
<li><em>How do you detect judge drift?</em> Keep labelling a small fresh sample each cycle and recompute TPR and TNR; alert when they move.</li>
</ul>
</Fragment>
</Depth>

### When a judge is the wrong tool

Code beats a judge whenever the property is mechanical: a schema, a date that must match a record, an identifier that must appear in the source. A judge without the reference or the source documents cannot verify facts; it grades plausibility. And a human beats a judge when there is no labelled data yet, because the judge needs those labels to be validated at all.

## Follow-ups

- *How many labels do you need?* Enough failures in the test set that one misclassified case does not swing TPR wildly; the FAQ's 30 to 50 per label in dev and test is a reasonable floor.
- *Two experts disagree with each other. What then?* Measure their agreement on a shared sample. It sets a ceiling for the judge, and the disagreements usually expose a vague criterion to tighten.
- *Would you fine-tune a judge model?* Only with a large labelled set and a stable criterion; a prompted judge with good examples is cheaper to change while the criterion is still moving.

## Common mistakes

- Reporting raw agreement on imbalanced data.
- Validating on the same examples used as few-shot examples in the judge prompt.
- One judge with a 1 to 10 "quality" score instead of binary judges per failure mode.
- Assuming a newer, larger judge model needs no validation.
