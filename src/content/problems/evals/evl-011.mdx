## Question

The setup is a scenario. A team evaluates its coding agent nightly on 80 tasks in four families, five trials each. Last week two pull requests merged on the same day: the agent's system prompt moved from v14 to v15, and the eval runner moved from a hosted sandbox service to the team's own Kubernetes cluster. The next run:

```text
family           tasks x trials   last week (v14, hosted)   this week (v15, k8s)
git-ops              20 x 5                71                       69
http-services        20 x 5                64                       62
data-pipelines       20 x 5                58                        0
compile-c            20 x 5                40                       37
```

The product manager asks whether v15 broke data work and wants to revert it today.

The runner change, as merged:

```diff
 task_defaults:
-  runner: hosted-sandbox
+  runner: k8s
-  timeout_s: 1800
+  timeout_s: 1200        # p90 task duration on the old runner was about 1,100 s
   cpus: 2
   memory: 4Gi
+  k8s:
+    requests: {cpu: "{cpus}", memory: "{memory}"}
+    limits: {cpu: "{cpus}", memory: "{memory}"}
+  pip_index: https://pypi-mirror.internal/simple   # internal mirror; the public index is blocked from the cluster
```

How the runner records a trial (unchanged in either PR):

```python
def record(trial):
    reward = grade(trial) if trial.finished else 0.0
    return {"task": trial.task, "reward": reward,
            "status": "passed" if reward == 1.0 else "failed"}
```

Three data-pipeline trials from this week, abridged. Last week the same tasks ran with a median duration of 410 seconds.

```text
trial dp-07/3   steps 3   duration 41 s   status failed   reward 0.0
  1 bash  "ls data/ && head -5 data/events.csv"          -> 6 lines
  2 bash  "cat requirements.txt"                          -> pandas, scikit-learn, pyarrow
  3 bash  "pip install -r requirements.txt"               -> (no tool result)

trial dp-12/1   steps 4   duration 67 s   status failed   reward 0.0
  ...
  4 bash  "pip install pandas pyarrow"                    -> (no tool result)

trial dp-15/5   steps 5   duration 88 s   status failed   reward 0.0
  ...
  4 bash  "pip install scikit-learn"                      -> Successfully installed scikit-learn-1.5.2 ...
  5 bash  "python fit.py"                                 -> (no tool result)
```

Pick the hypothesis that explains the collapse of data-pipelines. Then rank the other real defects in the diff and the recorder, say what you would collect before answering the product manager, and what you tell them today without it.

## Answer

The memory limit is the cause. The diff sets the Kubernetes limit equal to the request, so 4Gi is both the floor and the kill ceiling, with no room for a transient spike. Installing pandas, scikit-learn and pyarrow, or fitting a model with them, can briefly exceed that; the kernel kills the container, the harness gets no tool result, and the trial ends with `finished` false. Every piece of evidence fits: the runs stop within 41 to 88 seconds when the same tasks took a median of 410 seconds last week, the last step is always a heavy install or a fit, nothing after it was recorded, and the families that do not install the scientific stack barely moved. Anthropic hit the same configuration on Terminal-Bench 2.0 and describes the enforcement exactly this way, and names installing the Python data science stack on `bn-fit-modify` as a task that can exhaust memory before any solution code is written.

Why the others are tempting. A missing wheel on the mirror is the first thing anyone who has run an internal mirror suspects, and the mirror did change in the same diff; but pip reports a missing distribution as an error the agent sees and reacts to, and here there is no result at all, and dp-15 shows an install from the mirror succeeding. The prompt change is what the product manager suspects and is not ruled out for the other families; it cannot produce runs that stop after three steps with no output. The timeout cut is a real regression, and the comment shows it was set below the old p90, so it will clip some long compile-c trials; it cannot touch runs that end in under two minutes.

The ranking of the real defects:

1. **Limits equal to requests.** Explains the zero. Fix by giving each task a guaranteed allocation and a separate, higher kill threshold.
2. **The recorder turns unfinished trials into failures.** Not the cause, but the reason a crash reached the dashboard as a capability number and a product manager is about to revert a prompt. Record `infra_error` as its own status, exclude it from pass rates, and alarm on its rate.
3. **The timeout below the old p90.** Small and real: some compile-c trials now time out that used to finish. Either restore 1,800 seconds or record timeouts as their own status and decide per family.
4. **Two changes merged on the same day.** Every family's delta mixes the prompt and the runner. The small drops in the other three families cannot be attributed to v15 until v14 runs on the new runner.

<p><b>Choosing the ceiling.</b> Anthropic's sweep on Terminal-Bench 2.0 is the published reference: with the spec as both floor and ceiling, infra errors were 5.8%; at a 3x ceiling they fell to 2.1% while the success rate stayed within noise (p = 0.40); uncapped, infra errors fell to 0.5% and success rose almost 4 more points. Their recommendation is a guaranteed allocation plus a separate kill threshold, calibrated so the floor and ceiling scores sit within noise of each other, with the multiplier reported. I would start at 3x for this suite and keep the multiplier in the run metadata.</p>
<p><b>The failure mode of the fix.</b> Raising the ceiling changes what the eval measures. Anthropic found that past 3x the extra headroom let agents succeed with heavier approaches, large dependency installs and memory-hungry test suites, so scores rose for reasons that have nothing to do with the prompt. If production runs this agent in 4Gi sandboxes, an eval at uncapped memory will overstate it, and a model that prefers a lean standard-library approach will be undersold relative to one that installs everything. The ceiling should match where the agent will run, and when it cannot, the eval report says which it matches.</p>

## Follow-ups

- *The hosted sandbox provider will not tell you how it enforces memory. How do you make old and new runs comparable?* Measure it: run a fixed set of tasks with known memory profiles on both and compare infra-error rates and scores per family.
- *Two engineers disagree: one wants to rerun only data-pipelines, the other the whole suite. How do you decide?* The runner changed for every family, so a partial rerun leaves three families mixing two changes; the cost is one night of compute.
- *What would make you accept a revert of v15 before the paired rerun finishes?* Finished transcripts on the other families showing wrong answers that trace to the new tool guidance.

## Common mistakes

- Reading a family at 0 of 100 as a capability result before opening a transcript.
- Blaming the mirror because it changed in the same diff, without checking what a failed install returns.
- Fixing the limit and leaving the recorder, so the next infrastructure fault reaches the dashboard as a model regression again.
- Raising memory to unlimited and comparing the new scores with last week's as if only the prompt had changed.
- Treating two changes merged on the same day as one experiment.
