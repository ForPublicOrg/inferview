## Question

The vendor and its numbers are a scenario. A coding-agent vendor's release notes say its new harness raises SWE-bench Verified from 71.2% to 74.2% with the same model, "a three-point gain from harness improvements alone". The new harness also uses about 1.6 times the tokens per task, by the vendor's own figure. Your team's coding agent uses this vendor, and the engineering manager wants to switch everyone to the new harness this sprint.

What does the three points tell you, and what do you ask the vendor for before switching? Choose the evidence that would make you switch and say why that bar and not a lower one.

<Callout kind="interview" label="The pushback">
"It's the same model on the same benchmark. Isn't that the cleanest comparison you'll ever be handed?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the per-task results of both harnesses, not the two totals.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how many runs each total is, on which dates, and with what resource limits and time limits per task.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what your own agent's last month of failures were, and whether any of them are the kind a harness change fixes.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>On its own, very little. Three points on 500 tasks is 15 tasks net. If those are two single runs, each has a binomial standard error of about 2 points, and their difference about 2.8, so the gain is about one standard error. Anthropic measured 6 points of swing from resource limits alone on Terminal-Bench 2.0 and advises skepticism below about 3 points until configurations are matched. On top of that, OpenAI found flawed tests in 59.4% of the hard Verified problems it audited and has stopped reporting the benchmark. I would ask for per-task results from at least three runs of each harness under the same limits, the paired count of tasks each solves that the other does not, cost per resolved task, and the same comparison on SWE-bench Pro. I would switch on a paired result that holds across runs and survives the token cost, and I would check it on our own tasks first.</p>
</Fragment>
<Fragment slot="long">
<p><b>The arithmetic.</b> At about 72% on 500 tasks, one run's standard error is √(0.72 × 0.28 / 500) = 2.0 points, and the difference between two independent runs has √2 times that, 2.8 points. A three-point gain is about one standard error, not a result. The same model and benchmark help, because the comparison can be paired: the useful number is how many tasks only the new harness solves against how many only the old one solves. Fifteen net tasks is significant or not depending on that split. If 40 tasks flip to solved and 25 flip to failed, a sign test on the 65 discordant tasks gives a two-sided p of about 0.08; if 30 flip one way and 15 the other, p is about 0.04. The vendor has that table and quoting the totals throws it away.</p>
<p><b>What else moves three points.</b> Resource and time limits: Anthropic measured a 6-point spread on Terminal-Bench 2.0 between the tightest and the uncapped configuration with the same model and harness. Its SWE-bench check moved only 1.54 points from 1x to 5x memory, because those tasks need less, but a harness that runs the test suite more often or installs more tooling is exactly the kind of change that interacts with limits. Run-to-run variance, and Anthropic's unmeasured observation that pass rates varied by time of day. And the benchmark itself: with narrow tests that reject correct fixes on 35.5% of audited problems and wide tests on 18.8%, a gain on those tasks can come from matching the reference patch's choices rather than from fixing more bugs, and only the per-task table shows which tasks moved. OpenAI also found that models that had seen a problem in training were more likely to pass its underspecified tests, and a harness that elicits recall gains the same way.</p>
<p><b>The bar I would set.</b> A paired comparison over at least three runs of each harness, same model version, same resource and time limits, with the discordant split significant on the pooled tasks and the gain present in each run, plus the same direction on SWE-bench Pro's public set. A lower bar, one run each with matched settings, is defensible for a change that costs nothing; this one costs 1.6 times the tokens. That cost sets the second condition: cost per resolved task must not rise. At 71.2% and 1.0 cost units per task, cost per resolved task is 1.0 / 0.712 = 1.40 units; at 74.2% and 1.6 units it is 1.6 / 0.742 = 2.16 units, 54% more. Three points does not pay for the tokens unless the extra solved tasks are the expensive ones for us.</p>
<p><b>The failure mode of this answer.</b> Demanding paired, repeated, matched runs can become a reason never to adopt anything; vendors will not always rerun for one customer, and a sprint is not long enough to run it ourselves on 500 tasks. The cheaper test that actually decides is our own: a few dozen tasks from our repositories, both harnesses, three trials each, in our sandbox. It will not resolve a three-point gap either, but it will show a large one, the token bill, and the failures the new harness introduces, which is what the switch is about.</p>

### The request to the vendor

| Ask for | What it settles |
|---|---|
| Per-task pass or fail for both harnesses, every run | The paired split, which decides significance; whether the gain repeats across runs |
| Model version, run dates, number of runs | Whether the two totals are the same model, and how much of the gap is run-to-run variance |
| Resource limits, how they are enforced, time limit per task | Whether the harness gain is a configuration gain |
| Tokens, tool calls and wall-clock per task | Cost per resolved task, and where the 1.6 times goes |
| SWE-bench Pro public-set results for both harnesses | Whether the gain holds on a set OpenAI still recommends |
| The tasks the new harness newly fails | What the switch breaks, which the total hides |

## Follow-ups

- *The vendor answers that the gain comes from running the tests after every edit. Does that make you more or less confident it transfers to your repositories?* More, if your repositories have fast, reliable tests; less if your suite takes twenty minutes, because the mechanism then costs wall-clock time the benchmark did not charge.
- *Two of your engineers disagree: one wants to switch now and measure in production, the other wants the vendor's paired data first. How do you decide without deciding by rank?* Switch one team for two weeks and compare merged changes and token spend against a team that stays; the cost of being wrong for two weeks on one team is small.
- *What would make you switch back?* Cost per merged change rising with no rise in merged changes per engineer, or new failure categories in transcripts that the old harness did not have.

## Common mistakes

- Comparing two totals when per-task results for the same tasks are available.
- Treating "same model, same benchmark" as "same conditions" without asking about limits, dates and runs.
- Ignoring the token cost because the pass rate went up.
- Citing SWE-bench Verified as current without saying that OpenAI stopped reporting it in February 2026.
