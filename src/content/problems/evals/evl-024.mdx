checklist:
  - Tags every case with the features and policies its reference depends on, so a release can find the cases it makes stale
  - Quarantines touched cases automatically from the release's change manifest, excludes them from the gate and reports how many were excluded
  - Runs error analysis on fresh production traces every month and adds failures as capability cases, graduating them to regression after a stated number of passing releases
  - Writes retirement rules with reason codes, never retires a case for being hard or failing, and moves saturated cases to a cheaper, less frequent tier instead of deleting them
  - Makes set versions immutable and records set, judge, prompt and model versions on every score
  - Keys eval runs on those versions so a retried run reuses results, bounds judge retries, and marks unjudged cases as ungraded rather than passed or failed
  - Works out monthly labelling hours from the re-label and intake volumes at a chosen pace and shows they fit the expert's time
  - Audits a random sample of active cases each month to catch references that went stale without a manifest entry
  - Chooses between a frozen anchor and a chain-linked index for the trend line, with the cost of each
  - Stores every output so a judge change can be re-graded without calling a retired model
  - Requires a second sign-off for reference changes that flip a recent verdict and for retiring more than a stated share of the set in a month
  - Writes the versioning policy, the changelog format and the note that goes under the board chart, with rollback triggers for the rollout

## Question

<Callout kind="interview" label="Workflow, 45 minutes">
"Our golden set was accurate in January. The product ships every month, and by now nobody trusts it: some cases fail because the product changed, not because the assistant got worse. Design how the set stays current, what gets retired and when, and how we report a quality trend that still means something across a year."
</Callout>

The setting (scenario):

- A B2B support assistant. The set has 600 cases. The product ships a release on the first Monday of each month, with a change manifest listing the features and policies it touched.
- Last quarter, each release made the reference of about 41 cases wrong on average; one release removed a feature that 12 cases depended on.
- Monthly error analysis surfaces about 60 new failure cases worth keeping.
- The eval team is two engineers. The domain expert has 6 hours a week for labelling.
- The model vendor retires a model version about every six months; a retired version cannot be called.
- The VP of Product wants one line on the quarterly board chart: assistant quality over the last four quarters.

Design the workflow: the states a case moves through, what triggers each move, who approves what, the run keys and retries, the budget, and how the trend is computed. Choose the labelling pace and the size of anything you freeze.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask how often the change manifest missed a change that turned out to affect answers.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the per-case pass history for the last six releases, to see how many cases have never failed.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask the VP what decision the board line is used for, and whether a break in the series with a note would be accepted.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Make staleness a tracked state, not a surprise. Every case carries the feature and policy ids its reference depends on; each release's manifest quarantines the touched cases before the release eval, the gate runs without them and reports how many it lost, and the expert re-labels them into a new reference version. Monthly error analysis feeds new capability cases, which graduate to regression after passing three releases; saturated cases move to a cheaper tier; retirement needs a reason code. Set versions are immutable and every score records set, judge, prompt and model versions. For the board, freeze an anchor of 150 cases on behaviour that rarely changes and plot that, with a bridge run each time the anchor is renewed. The labelling load is about 10 hours a month against 26 available. What I give up: one number over the whole set across the year.</p>
</Fragment>
<Fragment slot="long">
<p><strong>1. Case states.</strong> candidate (from error analysis, not yet labelled), capability (labelled, currently failing or new), regression (passed three consecutive releases), quarantined (reference suspected stale), saturated (passed by every version for six months), retired. Moves are recorded in the changelog with a reason code and the person who made them.</p>
<p><strong>2. Triggers.</strong> Each case is tagged with the feature and policy ids its reference depends on; engineers propose tags with a model's help and the expert confirms them, once, for the 600. A release's manifest lists touched ids, and a job moves every tagged case to quarantined before the release eval. The gate runs on the rest and its report says "41 cases quarantined", so a gate on a shrinking set is visible. A removed feature retires its cases with reason code feature-removed.</p>
<p><strong>3. Intake and graduation.</strong> Error analysis on about 100 fresh traces a month, Husain's 2 to 4 week cadence at its slow end, yields the 60 cases, which enter as capability cases. A case passing on three consecutive releases graduates to regression; that number is a choice that trades suite churn against how long a case must prove itself.</p>
<p><strong>4. Retirement and saturation.</strong> Retire for: feature removed, policy withdrawn, duplicate of a newer case. Never retire a case because it is hard or keeps failing. A regression case passed by every version for six months moves to the saturated tier and runs weekly instead of on every change; it is still in the set and still versioned. Retiring more than 5 percent of the set in a month needs the eval lead and the product owner to sign.</p>
<p><strong>5. Versions, run keys and retries.</strong> A set version is immutable; any re-label, addition or retirement produces a new version with a changelog entry. An eval run is keyed on hash(set version, model version, prompt version, judge version), so a retried pipeline reuses the stored result instead of re-spending or double-recording. A judge call gets three attempts with backoff; after that the case is ungraded, not passed and not failed, and a run with more than 2 percent ungraded is invalid. Every output is stored, so a judge change re-grades old outputs without calling a model the vendor has retired.</p>
<p><strong>6. Approvals.</strong> The expert's re-label becomes the new reference. If it flips the verdict of the latest production run, an engineer reviews it, because that is where a convenient reference change can hide a regression.</p>
<p><strong>7. The budget, at a chosen pace.</strong> I choose 5 minutes per re-label and 6 per new case. Monthly: 41 × 5 + 60 × 6 = 205 + 360 = 565 minutes, about 9.4 hours. The expert has 6 × 52 / 12 = 26 hours a month. The slack goes to a random audit of 50 active cases a month at 5 minutes each, about 4 hours, which catches references that went stale without a manifest entry. At double my pace the total is about 27 hours and does not fit; then the audit shrinks first.</p>
<p><strong>8. The trend line: the decision with two defensible answers.</strong></p>
<ul>
<li><strong>A frozen anchor.</strong> 150 cases chosen from those whose tags were never touched in the last year, frozen for twelve months, run on every release. The board line is the anchor pass rate. Cheap and comparable by construction. Its cost: it describes the stable part of the product, the part least likely to regress, and a score that is watched gets tuned against.</li>
<li><strong>A chain-linked index over the full set.</strong> Each time the set version changes, run the production model on both versions in the same week and link the series by the ratio. It covers the whole product. Its cost: two runs per version change, error that accumulates link by link, and a link that cannot be made when the vendor has retired the model version used for the previous run, unless that run's outputs are stored and only the grading changed.</li>
</ul>
<p>The constraint conflict is comparability against freshness, with the VP on one side and the product's release calendar on the other. I take the anchor for the board line and keep the anchor's per-release scores out of the dashboards prompt authors use, so it is not tuned against. The full set gates releases and is reported per version, never as a trend. Each year the anchor is renewed with one quarter in which old and new anchors both run, which gives the bridge.</p>
<p><strong>9. Written down.</strong> A one-page versioning policy (states, triggers, reason codes, sign-offs); a changelog per set version (added, re-labelled, retired, counts per reason); and the note under the board chart: what the anchor covers, what it does not, and where the series breaks. Rollout: month 1 tags and quarantine, month 2 run keys and stored outputs, month 3 anchor and the first board line. Rollback trigger: if a release quarantines more than 15 percent of the gate set, that release is gated on the previous set version and the release owner signs for the gap.</p>
<p><strong>What I give up.</strong> A single number over the full set across the year, gate coverage of quarantined cases in the days before re-labelling, and about 4 hours a month of the expert's time on audits instead of new cases.</p>
<p><strong>Where this design fails.</strong> The manifest is the trigger, and manifests miss changes: a copy change in a help article or a pricing change made in a billing system outside the release. Those cases go stale silently until the random audit finds them, and 50 a month covers the 600 once a year. The anchor drifts from the product as the product grows; after a year its line can be flat while users meet regressions in features the anchor never covered. And tags are only as good as the first tagging pass; a case tagged to the wrong feature is never quarantined.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not let the release owner re-label the cases their release touched?</em> Because the person shipping the change is the one with a reason to make the reference agree with it; the expert re-labels and an engineer reviews flips.</li>
<li><em>What does Husain's advice to use product metrics for long-term tracking add?</em> A second line that does not depend on the set at all; when the anchor is flat and the product metric falls, the anchor is the suspect.</li>
</ul>

## Follow-ups

- *Pushback: the VP rejects a chart with a break in it and wants the full-set score as the line. What do you put on the slide, and what do you write in the note underneath?*
- *Reversal: after a year the random audit has never found a stale case the manifest missed. Would you stop it, shrink it, or keep it, and what would you need to see first?*
- *The vendor retires the production model in sixty days and the replacement fails 12 of 40 cases in one feature area. Which ships degraded, how does the set record it, and who signs?*
- *Two senior engineers disagree: one wants failing capability cases in the gate, the other wants only regression cases there. How do you decide without deciding by rank?*

## Common mistakes

- Editing references in place, so last month's scores silently change meaning.
- Retiring cases because they keep failing, which removes exactly the evidence the set exists for.
- Plotting the full-set score across versions as if the set had not changed.
- Letting the gate shrink through quarantine without reporting how much of it is gone.
- Treating the set as a project with an end date instead of a system with an owner and a budget.
