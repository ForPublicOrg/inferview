## Question

<Callout kind="interview" label="As a public question bank phrases it">
"What are OpenTelemetry's GenAI semantic conventions, and why should you care?"
</Callout>

You are adding OpenTelemetry tracing to an LLM service so that traces work with whichever observability backend the company picks. A teammate makes four claims about the GenAI semantic conventions as they stand in October 2026. Which one is true?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Think about what a default instrumentation should do with text that might contain a customer's medical history.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Check the status line on the convention documents before trusting any name to stay fixed.</p></details>

## Answer

Content capture is opt-in. Prompts and completions can carry personal data, so the conventions define `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions` and `gen_ai.tool.definitions` as opt-in attributes, with `_ref` variants that point to external storage. A default instrumentation records the operation, model, token counts and timings, which is enough for cost and latency dashboards and not enough for error analysis. Turning content on is a decision with privacy review attached.

Why the others are tempting. `gen_ai.system` appeared in older instrumentations and blog posts, so it looks familiar; it was deprecated in v1.37.0 in favour of `gen_ai.provider.name`. "Stable" is a reasonable guess for something with a version number, but every GenAI document is marked Development, and the main repository's GenAI pages read "Moved" from v1.42.0 on 12 June 2026. The cached-token claim is tempting because some provider APIs report cached tokens in a separate field from the total; OTel's `input_tokens` should include them, so adding the cache-read count again double counts.

Why you should care, which is the second half of the interview question: a shared vocabulary means the same span names (`chat some-model`, `invoke_agent`, `execute_tool`) and attributes work across tracing backends, so you can switch vendors without re-instrumenting, and agent runs become span trees you can walk to find the failing tool call.

## Follow-ups

- *What would you log beyond the conventions?* The prompt version (`gen_ai.prompt.version` exists for this), a cost estimate as an application attribute, and the eval scores attached to the trace.
- *How do you do error analysis if content capture is off?* Turn it on for a sampled, redacted slice, or store content behind the `_ref` URIs with access controls and retention limits.
- *Which attribute catches a provider moving an alias to a new model?* `gen_ai.response.model`, compared with `gen_ai.request.model`.

## Common mistakes

- Hard-coding attribute names from a 2025 blog post without checking the current documents.
- Assuming traces contain prompts by default and building an error-analysis workflow on data that is not there.
- Double counting cached tokens when computing cost from both OTel attributes and a provider's usage field.
