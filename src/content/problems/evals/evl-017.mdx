## Question

<Callout kind="interview" label="Question">
"What is the difference between a guardrail and an evaluator?" Answer it by placing a check.
</Callout>

A payments-support assistant answers customers and can call internal tools. The team wants four new checks. The constraint from the platform team: no additional model call may be added to the request path, because the latency budget is already spent. Which one of these four should run inline, as a guardrail that can block or rewrite a reply before the customer sees it? The other three will run elsewhere.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which of the four needs no model call at all?</p></details>
<details class="hint"><summary>Hint 2</summary><p>A guardrail is worth its cost when one miss is expensive and the failure is clear-cut.</p></details>

## Answer

The deterministic block on card numbers and malformed tool payloads. A guardrail sits in the request path, so it must be fast and deterministic, and it should target clear, high-impact failures: leaking a card number to the wrong place or sending a broken payload to a payments tool are failures where blocking is cheaper than any after-the-fact analysis. A regex with a checksum and a schema validator run in the time budget of ordinary code and never time out on a model provider.

The other three are evaluators. The tone judge and the faithfulness judge each need a model call and measure nuanced quality, which is what evaluators do: run after the reply, asynchronously, on a sample of traffic, with results feeding dashboards and the offline suite. The weekly human review is the slowest and most trustworthy of all, and it is where judges get their labels; it cannot stop a reply because it happens days later.

The tempting mistake is to promote the faithfulness judge to a guardrail because hallucinations are expensive. Without the latency constraint, that can be a reasonable design for a narrow high-stakes slice, but then it is a production dependency: it needs its own timeout, a fallback when the judge provider is down, and a validated false-positive rate, because every false positive blocks a correct answer for a real customer.

## Follow-ups

- *The judge finds that 3% of sampled replies contain an unsupported claim about fees. What now?* Read those traces, add the cases to the offline suite, and consider a deterministic guardrail for the specific pattern, such as fee amounts that must match a pricing table.
- *How do you monitor the guardrail itself?* Count blocks by rule, sample blocked replies for false positives, and alert on sudden changes in block rate.
- *Where does a refusal classifier fit?* If it is a small fast model within the latency budget, it can be a guardrail; validate its false-positive rate like any judge.

## Common mistakes

- Calling an asynchronous LLM judge a guardrail. If it runs after the user has the reply, it guards nothing.
- Putting every check inline "to be safe", and turning each one into a latency and availability risk.
- Building guardrails without measuring how often they block correct replies.
