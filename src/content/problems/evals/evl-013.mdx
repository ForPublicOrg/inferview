## Question

<Callout kind="interview" label="The prompt">
"Design the pipeline that decides whether a prompt, retrieval or model change can merge and ship, and that keeps checking after it ships. Then: the gate you designed blocks the release the CEO promised a customer for Monday. Defend it."
</Callout>

The operating constraints are a scenario, given by the interviewer:

- A support assistant for a B2B product. Prompts, retrieval settings and the model snapshot change through pull requests: about 40 merges and 160 pushes a month.
- Four engineers own the assistant; nobody is a full-time eval owner.
- An intent classifier already labels every conversation (billing, refunds, access, how-to) for analytics.
- Model calls for evals are capped at $3,000 a month, judges included.
- The CI tooling today is a shell script that runs a 50-case smoke test. The team was about to adopt OpenAI's Evals platform.

Thursday afternoon, the release candidate fails the gate. Two must-pass cases fail: in both, the assistant tells an admin a refund will be issued outside the contract's terms. On the 400-case judged regression suite, 9 cases regressed and 2 improved. The CEO asks you to switch the gate off for this release.

Write the pipeline design, choose the numbers it needs, and write the note you send the CEO on Thursday.

## Answer

<Depth>
<Fragment slot="short">
<p>Three tiers in CI and two after merge. Must-pass cases (contract terms, refunds, data access, past incidents) are hard gates with no statistics: one failure blocks. Judged regression metrics gate on an exact one-sided sign test over the cases that flipped between baseline and candidate on the same set, at a pre-agreed alpha. Everything else (capability suites, cost, latency, tool calls) is reported on the pull request, not gated. After merge, a canary with rollback triggers and online judges on a sampled share of traffic, with production failures fed back as cases. On Thursday the gate holds, but the release does not have to: the refund behaviour is the failure, so I would offer to ship everything else with refund questions routed to the current prompt, or ship nothing until the two cases pass. Switching the gate off is not one of the options, because an override with no owner and no record is how the next gate gets deleted.</p>
</Fragment>
<Fragment slot="long">
<p><b>Data.</b> A versioned suite built from error analysis of real traces: about 1,000 cheap deterministic cases, a 400-case judged regression suite expected to pass near 100%, a capability suite that is allowed to fail, and a must-pass list of a few dozen cases, each with a named owner and a reason. Every result records the suite version, prompt hash, resolved model snapshot, retrieval config and judge version, so a dataset change never reads as a model regression.</p>
<p><b>Per push.</b> Schema, citation-present, banned-content and length assertions on the 1,000 deterministic cases. Outputs are cached by case, prompt hash, snapshot and parameters, and the job runs only when prompts, retrieval config or the model pin change, the same path filter promptfoo's GitHub example uses. These block.</p>
<p><b>Per merge candidate.</b> The judged regression suite on the candidate; baseline outputs come from the cache. The gate counts regressions and fixes and runs the exact sign test, because flip counts on a 400-case suite are small (11 on Thursday) and the chi-squared shortcut is traditionally avoided below 25 discordant pairs. Alpha 0.05 one-sided, because the question is "did this make things worse"; I would accept 0.10 from a team that prefers fewer escaped regressions to fewer false blocks, if it is written down before the first run. Must-pass cases run here too, three times each, and any failure blocks.</p>
<p><b>The pull-request comment.</b> One comment, updated per run, with pass rates per failure mode and their sample sizes, the flipped cases with links to both transcripts, and cost and latency deltas. Reviewers read the flips. Promptfoo's <code>--fail-on-error</code> and a results.json check, or Braintrust's eval-action, can carry this; the design does not depend on either. Do not start on OpenAI's Evals platform: it is read-only from 31 October 2026 and shuts down on 30 November 2026, and OpenAI's migration guide points to Promptfoo, which OpenAI announced it would acquire on 9 March 2026.</p>
<p><b>After merge.</b> A canary on a share of tenants with rollback on escalation rate, refund-promise rate and cost per conversation. Online judges on a sampled share of production traces, asynchronously, with a spend cap per evaluator; inline guardrails stay deterministic and fast. Every production failure that error analysis finds becomes a case, and must-pass candidates go to their owner.</p>
<p><b>Keeping the pipeline honest.</b> Judges are checked against human labels when their model or prompt changes. The baseline runs against itself weekly to measure the flip noise. Regression cases that have passed for months move to a slower schedule; capability cases that pass reliably graduate into the regression suite.</p>
</Fragment>

### The cost line, computed

Scenario prices: $0.002 per deterministic case, $0.002 per generation plus $0.004 per judge call with four judges, so $0.018 per judged case.

| Tier | Runs a month | Cost per run | Month |
|---|---|---|---|
| Deterministic, per push | 160 | 1,000 × $0.002 = $2.00 | $320.00 |
| Judged regression, per merge candidate (baseline cached) | 40 | 400 × $0.018 = $7.20 | $288.00 |
| Baseline against itself, weekly | 4 | $7.20 | $28.80 |
| Capability and multi-turn suite, per release | 4 | $150.00 | $600.00 |
| Online judges, 5% of 20,000 conversations a day, two judges | 30 days | 1,000 × 2 × $0.004 = $8.00 | $240.00 |
| Total | | | $1,476.80 |

That leaves about half the $3,000 for reruns of borderline flips, judge re-validation and growth. Running the judged suite on every push instead of every merge candidate would cost 160 × $7.20 = $1,152 a month for that line alone, four times the plan, for feedback the author mostly does not need until the pull request is ready.

### Thursday: the gate result

The statistical gate on its own: 9 regressions of 11 flips, P(X ≥ 9 | n = 11, p = 0.5) = (55 + 11 + 1) / 2,048 = 3.3%, below 0.05. It blocks. It does not matter much here, because the two must-pass failures block on their own, and they are the part the customer's admin would see.

### Two defensible answers, and their costs

- **Hold the release until both must-pass cases pass.** Cost: the Monday promise slips, probably by days, and the CEO carries that conversation. Risk accepted: none on refunds.
- **Ship Monday with refund and billing intents routed to the current prompt.** The analytics intent classifier becomes the router. Cost: two prompts in production for at least a sprint, a routing classifier that now sits on the safety path, and its misroutes, so the refund must-pass cases have to run through the router as well, and the canary watches the refund-promise rate on the new prompt.

I would offer the second, with the CEO choosing between the two and the product owner signing the risk note.

### The note to the CEO

> The release is blocked by two cases in which the assistant promises refunds the contract does not allow. That is a legal exposure, not a quality score. Two options: ship Monday with refund and billing questions answered by the current version (risk: misrouted refund questions reach the new version; we watch refund promises hourly and roll back on the first one), or ship when the two cases pass, likely mid-week. Switching the gate off would ship the refund behaviour to every tenant. If you choose to override anyway, the override needs your name and the product owner's on this note, and it expires with this release.

### What you give up

A per-merge gate means an author learns about judged regressions at review time, not at every push. The must-pass list will grow, because every incident adds to it, and a list nobody prunes eventually blocks every release; it needs a quarterly review with owners. The written override path means overrides will happen, and they are visible.

### The failure mode of this design

The gate measures what the suite contains. It passed changes that broke behaviours nobody wrote a case for, and it gives a confident p-value on judges that drift. The weekly self-run catches noise, not drift; judge re-validation on human labels is the only control for the second, and with no full-time eval owner it is the first thing to slip. Track escaped regressions, the production incidents the gate passed, as the pipeline's own metric, and assign the judge re-validation to a named engineer per quarter.

## Follow-ups

- *The CEO overrides with a signed note and nothing goes wrong. Next month the same request comes for a smaller reason. What changes in the override process?*
- *Two senior engineers disagree: one wants alpha 0.10 to catch more regressions, the other wants 0.01 to stop false blocks. How do you decide without deciding by rank?* Replay the last quarter's merge candidates through both thresholds and count escaped regressions against blocked-and-later-fine releases.
- *Must-pass cases run three times each. A must-pass case passes twice and fails once. Block or not, and where is that rule written?*
- *The router misclassifies 2% of refund questions in the canary. Roll back, or accept and fix forward?*

## Common mistakes

- One blended score as the gate, which hides the failure mode that moved.
- Running statistics on must-pass cases, so a refund promise can be averaged away by improvements elsewhere.
- Comparing two pass rates as independent samples when baseline and candidate ran on the same cases.
- A gate with no override path, so the first urgent release removes the gate instead of overriding it on the record.
- Treating CI as the whole pipeline and skipping canary, sampled online judges and the loop from production failures back into cases.
- Running an LLM judge inline as a guardrail and paying its latency and failures on every request.
