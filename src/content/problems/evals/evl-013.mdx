## Question

<Callout kind="interview" label="As public interview guides phrase it">
"Design an evaluation pipeline." Variants: "Build a regression test set for a feature that ships weekly" and "How do you catch regressions when you change a prompt or swap a model?"
</Callout>

A team ships a retrieval-backed assistant. Prompts, retrieval settings and the model version all change through pull requests, several a week. Design the pipeline that decides whether a change can merge and ship, and that keeps checking after it has shipped. Cover what runs when, what blocks, how you handle noisy LLM outputs, what it costs, and how the pipeline itself stays trustworthy.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Not every check deserves to block a merge. Sort them by how deterministic they are.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Baseline and candidate run on the same cases. How do you use that?</p></details>
<details class="hint"><summary>Hint 3</summary><p>The merge is not the end. What changes after it that CI cannot see?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Three tiers in CI. Hard gates that always block: assertions and must-pass cases. Statistical gates for judged metrics: run baseline and candidate on the same versioned set and test the cases that flipped, with a measured noise floor. Report-only diffs posted on the pull request: capability-suite scores, cost, latency, tool calls and links to every flipped case. After merge: shadow traffic, a canary with automatic rollback on guardrail metrics, online judges on sampled traces, and a loop that turns new production failures into cases. Judges are validated against human labels and re-validated when they change.</p>
</Fragment>
<Fragment slot="long">
<p><b>Data.</b> A versioned golden set built from error analysis, split into a regression suite (expected near 100%), a capability suite (tracking progress), must-pass cases (safety, compliance, known incidents) and a held-out slice. Every result records the set version, prompt version, resolved model version and retrieval config.</p>
<p><b>On every pull request.</b> Level 1 assertions on all cases: schema, citations that exist in the retrieved context, banned content, length limits. These block. Outputs are cached by input and config hash, so unchanged cases are not regenerated.</p>
<p><b>On merge candidates.</b> Binary LLM judges per failure mode on the regression and capability suites, baseline and candidate on identical cases. The statistical gate counts cases that broke and cases that got fixed and runs an exact sign test on the flips; it blocks at a pre-agreed alpha. The noise floor comes from running the baseline against itself; nondeterministic cases run several times with a majority vote. Must-pass failures block regardless of statistics.</p>
<p><b>The pull-request comment.</b> Pass rates per failure mode with sample sizes, the list of flipped cases with links to both transcripts, cost and latency deltas, and tool-call counts. Reviewers read the flipped cases, not the averages. Tools exist for this (promptfoo with `--fail-on-error`, Braintrust's eval-action, Langfuse's GitHub Action); the design matters more than the vendor, and nothing new should start on OpenAI's Evals platform, which shuts down on 30 November 2026.</p>
<p><b>After merge.</b> Shadow the candidate on copied traffic with reference-free checks; canary to a small share of users with automatic rollback on errors, escalations and cost; online judges on sampled traces with filters and spend caps; dashboards annotated with prompt and model version changes. Inline guardrails stay separate from all of this: fast, deterministic, blocking.</p>
<p><b>Keeping the pipeline honest.</b> Judges have test sets with TPR and TNR and are re-validated when their model or prompt changes. Each error-analysis cycle adds new failures to the suites. Saturated evals move to a slower schedule. Graders get known-good and known-bad fixtures, so a broken grader fails its own tests before it fails a pull request.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A change improves the average but breaks two must-pass cases. Ship?</em> No. Must-pass cases are hard gates by definition; fix or explicitly re-classify them with an owner's sign-off.</li>
<li><em>The gate blocks too often on noise. What do you change?</em> Measure the noise floor, run flaky cases several times, and gate on fewer, better-validated judges rather than many.</li>
<li><em>How do you handle a model upgrade forced by the provider?</em> Same pipeline: the new model version is the candidate, and the flipped cases go to the owners before the switch date.</li>
</ul>
</Fragment>
</Depth>

### The cost line

Make the cost visible in the design. An illustrative sizing: 300 regression cases and 100 capability cases, four binary judges each, is 400 generations plus 1,600 judge calls per full run. If that runs only on merge candidates, about 10 times a week, it is 20,000 calls a week; running it on every push instead would multiply that by the push count. That is why assertions run on every push and judges run on merge candidates, with caching so only changed outputs are re-judged.

## Follow-ups

- *Why a sign test on flips rather than comparing two confidence intervals?* The runs are paired on identical cases. Overlapping intervals from independent samples can hide a regression that the flips make obvious.
- *How do you decide which judged metrics are gates and which are report-only?* Gate on the few with validated judges and clear product cost; report the rest.
- *What would you monitor to know the pipeline is working?* Escaped regressions, meaning production incidents that the gate passed, and how often the gate blocks changes that humans then override.

## Common mistakes

- One blended quality score as the gate, which hides which failure mode moved.
- Gating on unvalidated judges, so the pipeline confidently blocks good changes and passes bad ones.
- No baseline re-run on the same set version, so a dataset change looks like a model regression.
- Treating CI as the whole story and skipping shadow, canary and online evaluation.
- Putting an LLM judge inline as a guardrail and adding its latency and failures to every request.
