## Question

<Callout kind="interview" label="As public question banks phrase it">
"How would you evaluate an autonomous coding agent? Why can SWE-bench pass rates be misleading?"
</Callout>

Your company wants to roll out a coding agent to its engineers and is choosing between two vendors, plus its own harness built on a frontier model. One vendor quotes a high SWE-bench score. Design the evaluation you would run, and explain what the public score does and does not tell you.

## Hints

<details class="hint"><summary>Hint 1</summary><p>A SWE-bench result is a model plus a harness plus a grader, on public Python repositories. Which of those match your situation?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Look at how SWE-bench decides a fix is correct, and what happens when its tests are wrong.</p></details>
<details class="hint"><summary>Hint 3</summary><p>What does an engineer care about that "the tests pass" does not capture?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The public score is a model, a harness and a grader on public Python repositories that may be in the training data, graded by tests that can be wrong. OpenAI stopped reporting SWE-bench Verified in February 2026 for those reasons. I would build a private suite of real tasks from our own repositories, in sandboxes, graded by hidden tests that must start passing plus existing tests that must keep passing, with static analysis and a rubric for code quality, several trials per task for pass^k, and cost and time per task. Then a pilot with engineers, measured by accepted changes and review effort.</p>
</Fragment>
<Fragment slot="long">
<p><b>Why the public score misleads.</b> Contamination: the issues and fixes are public, so they can be in training data. Grader quality: SWE-bench counts a task as solved when FAIL_TO_PASS tests pass and PASS_TO_PASS tests keep passing; when those tests are wrong, correct fixes fail and lucky ones pass, and OpenAI cited flawed tests when it dropped Verified. Saturation: Anthropic's post puts the starting point for Verified at 30% in one place and 40% in another, with scores now over 80%, so differences at the top say little. Harness: the vendor's score comes from their scaffold, tools and retries, not the setup you will run. Distribution: popular open-source Python projects, not your languages, monorepo, build system or conventions. Even the recommended replacement, SWE-bench Pro, has published criticism of its tests.</p>
<p><b>The private suite.</b> Take 50 to 100 merged changes from your own repositories, written after the models' training cutoffs, across languages and task types: bug fixes, small features, refactors, test writing, dependency upgrades. For each, snapshot the repository before the change, write the task as an engineer would file it, and keep the real tests that came with the change hidden from the agent. Run in a sandbox with your build and test tooling; Inspect or a similar harness can run external agents.</p>
<p><b>Graders.</b> Outcome first: hidden tests that must pass and the existing suite that must keep passing. Then static analysis and linting, a diff-size check, and a rubric judged by a calibrated model or a reviewer for readability and fit with conventions. Separate checks for forbidden actions: touching files outside scope, deleting tests, disabling checks.</p>
<p><b>Metrics.</b> Several trials per task, reporting pass@1 and pass^k; cost, wall-clock time and tool calls per task; and the failure categories from reading transcripts. Compare the three options on the same tasks and harness conditions where possible.</p>
<p><b>Then the real test.</b> A pilot with engineers: share of agent changes merged, review time per change, revert rate, and what engineers stop using it for. The offline suite picks candidates; the pilot decides.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How do you stop your private suite from leaking?</em> Keep it out of any repository that trains or fine-tunes models, refresh it with newer changes, and keep a held-out slice.</li>
<li><em>The agent passes the hidden tests by special-casing them. How do you catch that?</em> Additional held-out tests per task, code review on a sample, and a rubric criterion for test-specific hacks.</li>
<li><em>Which public benchmarks would you still look at?</em> SWE-bench Pro and Terminal-Bench 2.0 as broad sanity checks, read with their dates, harnesses and criticisms, never as a purchase decision.</li>
</ul>
</Fragment>

### Two numbers worth knowing

SWE-bench Verified is 500 tasks, and each is graded by two lists of tests: FAIL_TO_PASS, which the fix must make pass, and PASS_TO_PASS, which must keep passing. Forgetting the second list misses the regression half of the grader. SWE-bench Pro, which OpenAI recommended in its place, has 1,865 problems from 41 repositories split into public, held-out and commercial subsets, a structure designed to resist contamination.

## Follow-ups

- *How many tasks do you need to tell two agents apart?* Compare them on the same tasks and count the tasks where one succeeds and the other fails; a sign test on those flips tells you whether the difference is noise. Expect to need dozens of discordant tasks, not a handful.
- *How do you evaluate the agent on long-running tasks such as a migration?* Break the task into checkpoints with their own tests, and grade the final state in the sandbox.
- *What would make you stop the rollout?* Forbidden-action failures, rising revert rates, or review time per change growing faster than the time saved.

## Common mistakes

- Treating a leaderboard score as a property of the model rather than of the model, harness and grader together.
- Grading only "the new test passes" and missing regressions elsewhere in the suite.
- Building the private suite from tasks old enough to be in public training data.
- Scoring a single trial per task and reporting it as reliability.
