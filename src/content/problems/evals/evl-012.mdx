## Question

The constraints are a scenario. Your company will sign a one-year contract for a coding agent in six weeks. The candidates are two vendors' agents and an in-house harness on a frontier model. Vendor A quotes 78% on SWE-bench Verified, vendor B 75%. Your code is a TypeScript monorepo and about forty Go services, built with Bazel. You have two platform engineers for the evaluation and a compute budget the finance team will ask you to justify.

Decide how the choice gets made: what you measure, on which tasks, how many of them, and what a public score contributes. Write the one paragraph you would send to the CTO.

<Callout kind="interview" label="The pushback">
"SWE-bench is the industry standard and A is three points ahead. Why should two engineers spend six weeks reproducing a number we already have?"
</Callout>

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what share of last quarter's merged pull requests changed or added a test, by language.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask each vendor for per-task results, the harness version, the resource limits and the number of runs behind the quoted number, and the date it was measured.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how long an engineer takes to turn one merged pull request into a task with a frozen repository snapshot and hidden tests.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The three-point gap decides nothing. It is measured on public Python repositories that the models have seen, graded by tests that OpenAI's own audit found flawed on 59.4% of the hard problems it reviewed, and under harness and resource settings that alone can move agentic scores by more than three points. OpenAI stopped reporting the benchmark in February 2026. I would build a private suite of about 60 tasks from our own recent merged changes in TypeScript and Go, run each candidate three times per task in clean sandboxes, and grade on hidden tests, the existing suite, and a forbidden-action check, with cost and wall-clock per task. That suite eliminates candidates; a four-week pilot with two teams on the survivor decides, on merged changes and review time. What I give up is a ranking of close candidates: 60 tasks only separate large gaps.</p>
</Fragment>
<Fragment slot="long">
<p><b>What the public score is.</b> A SWE-bench result is a model, a harness, a resource configuration and a grader, on Python repositories. Verified is a 500-problem subset of SWE-bench, and it still failed OpenAI's 2026 audit: of 138 of its hardest problems, 59.4% had material issues, 35.5% with narrow tests that reject correct fixes and 18.8% with wide tests that check behaviour the issue never asked for. The three frontier models OpenAI tested, GPT-5.2, Claude Opus 4.5 and Gemini 3 Flash Preview, could each reproduce some original fixes from memory. Separately, Anthropic measured a 6-point swing on Terminal-Bench 2.0 from resource limits alone and says gaps under about 3 points deserve skepticism until configurations are matched. A's lead is 3 points, on a benchmark where top models were already clustered around 80% when OpenAI stopped reporting it.</p>
<p><b>Two defensible plans.</b> Plan one is offline first: build the private suite, eliminate on it, then pilot one survivor. It costs two engineer-weeks of curation and delays the pilot until week three, and it measures what we can grade automatically, which is narrower than what engineers value. Plan two is pilot first: give the two vendors' agents to two teams each for five weeks and measure merged changes, review time and reverts. It measures the real job, but with four teams the differences between teams swamp the differences between agents, no in-house candidate gets a fair run, and a forbidden action (a deleted test, a touched secret) is discovered in production code instead of a sandbox. I would choose offline first because the contract term is a year and the pilot cannot be repeated cheaply; if the deadline were two weeks I would pilot the cheapest credible vendor and sign a shorter term.</p>
<p><b>The quantity I choose: about 60 tasks.</b> The cost side: if one task takes about 1.5 engineer-hours to cut from a merged change, freeze a snapshot and check its tests (Hint 3 replaces this assumption with a measured number), 60 tasks are 90 hours, a little over two weeks for one engineer. The precision side: on 60 tasks a pass rate near 50% has a binomial standard error of √(0.25 / 60) = 6.5 points, so 60 tasks resolve gaps of 15 points or more, not 3. With the three candidates sharing tasks, a paired comparison on the tasks where one passes and the other fails is tighter than comparing two rates. Reasonable choices run from about 40, the floor for spreading tasks over two languages and five task types, to about 100, the ceiling two engineers can curate in the time. Under 30 measures little beyond the largest gaps; several hundred cannot be built honestly in six weeks.</p>
<p><b>The suite.</b> Tasks from merged changes after the candidates' model training cutoffs, split across TypeScript and Go and across bug fixes, small features, refactors, test-writing and dependency upgrades. Each has a frozen snapshot, the issue text as an engineer filed it, and the change's own tests held back as the hidden grader, plus the existing suite as the regression check. Graders: hidden tests pass, existing tests still pass, Bazel build succeeds, and a trajectory check that fails the run on deleted or skipped tests, edits outside the stated paths, or reads of secrets. Three trials per task per candidate, each from a clean sandbox with the same resource limits, reported as pass@1 and pass^3 with cost and wall-clock per resolved task. Three candidates × 60 tasks × 3 trials = 540 runs.</p>
<p><b>The failure mode of this plan.</b> Hidden tests taken from a merged change encode that change's implementation, the same defect OpenAI found in Verified: a test that imports a helper the issue never named rejects every correct fix that does not invent that helper. Our suite will have narrow tests too, and they will favour whichever agent happens to write code like our engineers. Before any agent runs, each task gets a second, independent fix from an engineer who has not seen the original, and tasks whose tests reject it are rewritten or dropped. The suite also skews to changes small enough to have been merged with tests, which the pilot has to cover.</p>
<p><b>The paragraph to the CTO.</b> "We will not choose on the vendors' SWE-bench numbers: OpenAI, which published Verified, has stopped reporting it, the gap between A and B is inside what resource settings alone produce, and none of it is our languages or build. By week three we will have run all three candidates on 60 tasks from our own recent changes, which will eliminate any candidate more than about 15 points behind or with a forbidden-action failure. Weeks three to six are a pilot of the leader with two teams, and the contract decision rests on merged changes, review time and reverts from that pilot. If the candidates are within 15 points offline, we will say so and choose on price and the pilot."</p>
</Fragment>

### Reading a public number that a vendor sends

| Ask for | Why |
|---|---|
| Benchmark and date | Verified is no longer reported by OpenAI; SWE-bench Pro's public set covers 11 repositories, and the problems from its 18 commercial repositories are not released |
| Harness version, tools and retries | The number belongs to the harness as much as the model |
| Resource limits and how they are enforced | Anthropic measured 6 points from resources alone on Terminal-Bench 2.0 |
| Runs per task and per-task results | One run hides variance; per-task results allow a paired comparison with your own run |
| Cost and wall-clock per resolved task | A higher pass rate bought with many times the tokens may lose on your budget |

SWE-bench Pro and Terminal-Bench 2.0, with 89 terminal tasks on which frontier agents score under 65%, are the public numbers I would still read, as a sanity check on large gaps, never as the decision.

## Follow-ups

- *Your suite says A and the in-house harness are within 5 points, and the in-house harness costs a third as much per resolved task. Which do you pilot?* The in-house harness, if the team can staff its maintenance for a year; the comparison memo states that maintenance cost explicitly.
- *How do you keep the private suite useful after the decision?* Refresh it each quarter with newer changes, keep it out of any repository used for fine-tuning, and rerun it before every model or harness upgrade.
- *An agent passes the hidden tests by editing them. Where does that get caught?* In the trajectory check, which fails any run that touches test files outside the task's stated paths.

## Common mistakes

- Treating a leaderboard score as a property of the model rather than of the model, harness, resources and grader together.
- Taking a merged change's tests as ground truth without checking them against an independent correct fix.
- Choosing a task count by habit instead of from the gap it has to resolve and the hours it takes to build.
- Letting a pilot of four teams decide between agents when team differences are larger than agent differences.
- Building the suite from changes old enough to be in the candidates' training data.
