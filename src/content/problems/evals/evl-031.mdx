## Question

<Callout kind="interview" label="Debug round">
Release 42 of the support assistant improved the offline suite and production quality fell. Which defect explains the production drop? Rank the others and give the first measurement you would take for each.
</Callout>

The evidence, constructed for this problem.

**What release 42 changed.** `prompts/support.txt` gained tone guidance and six worked examples: 1,400 tokens before, 3,300 after, counted with the model's tokenizer. The model pin moved from one snapshot to its successor. In the same week, and in a separate change, the online judge moved to a newer judge model.

**Offline.** The golden set has 400 single-turn cases, each stored with the chunks that retrieval returned when the case was written in May. Judge pass rate: 81% on release 41, 86% on release 42. The judge was validated against human labels on release 39's answers.

**Production, week before and week after release 42.**

| | Before | After |
|---|---|---|
| Weekly human audit, 150 random conversations, answer correct | 111 (74%) | 97 (65%) |
| Re-contact within 72 hours, about 40,000 conversations a week | 11.2% | 13.9% |
| Online judge, groundedness against the chunks in the prompt, 5% sample | 91% | 90% |
| Billing questions, share of conversations (flat for eight weeks) | 18% | 18% |

**The production path.** Unchanged in this release:

```python
# assistant/context.py
MAX_PROMPT_TOKENS = 8_000

def assemble(system, history, chunks, question, count):
    budget = MAX_PROMPT_TOKENS - count(system) - count(question)
    kept_history = trim_oldest(history, budget // 2, count)
    budget -= sum(count(m) for m in kept_history)
    kept = []
    for ch in chunks:                     # 8 chunks, best first, about 500 tokens each
        if count(ch.text) > budget:
            break
        kept.append(ch)
        budget -= count(ch.text)
    return render(system, kept_history, kept, question)
```

**The offline path.**

```python
# eval/runner.py
def run_case(case, system_prompt, client):
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": render_context(case.chunks) + "\n\n" + case.question},
    ]
    return client.generate(messages, model=case.model or PINNED_MODEL)
```

What you do not have: the assembler logs kept-chunk counts at DEBUG level, which is off in production. The audit sheet does not record how many turns each conversation had.

## Answer

The defect sits in code nobody touched. The assembler pays for the system prompt first, then gives history up to half of what is left, then fills chunks in rank order until the budget runs out. With a question of about 100 tokens:

| | Release 41 | Release 42 |
|---|---|---|
| Budget after system prompt and question | 8,000 − 1,400 − 100 = 6,500 | 8,000 − 3,300 − 100 = 4,600 |
| First turn, no history: chunks kept | 8 (4,000 tokens fit) | 8 (4,000 tokens fit) |
| Later turn, 3,000 tokens of history: history kept | 3,000 (cap 3,250) | at most 2,300 (cap), oldest turns dropped |
| Later turn: chunks kept | 3,500 / 500 = 7 | 2,300 / 500 = 4 at most |

First turns are untouched; later turns lose about half of their retrieved context and part of the conversation. The offline runner calls neither `assemble` nor `trim_oldest`: it puts the stored chunks straight into one user message, and every golden case is a first turn. So the release made the single-turn answers better, which the offline suite measured, and the multi-turn answers worse, which it cannot see. The online judge stayed flat for the same reason: it scores groundedness against the chunks in the prompt, and an answer built from four chunks can be fully grounded in those four while missing the one that held the answer.

**The ranking.**

| Candidate | Explains the drop? | First measurement |
|---|---|---|
| Chunk budget squeezed by the longer prompt | Yes, on mechanism and timing | Replay 100 multi-turn production conversations from traces through `assemble` with each release's prompt and record kept chunks and kept turns; or turn on the kept-chunk metric at INFO for one hour |
| Golden set has no billing cases | No: billing share is flat, the drop starts on release day | Pass rate of 50 newly written billing cases on both releases |
| Offline judge validated on release 39's answers | No: it can only overstate the offline gain | Agreement with human labels on 100 release 42 answers |
| Online judge changed the same week | No: the audit and re-contacts are not judge outputs | Score 500 stored conversations with both judge versions |

The model pin moved too, and nothing in this evidence separates its effect on later turns from the assembler's. The audit split by turn (Hint 1) is the cheapest way to tell: if the drop sits on turns 2 and later and first turns hold at 74%, the assembler is the lead; a drop on first turns as well points at the snapshot. The audit itself is weak evidence on its own: 111 of 150 against 97 of 150 is a one-sided p of about 0.04 on two independent samples. The re-contact rise, 2.7 points on about 40,000 conversations a week, is the stronger signal.

Without the split or the replay, I would still act: the token arithmetic is deterministic, and it holds whatever the snapshot does.

**The fix, two defensible answers.**

- **Roll back the prompt, keep the new snapshot.** Restores the chunk budget today and isolates the snapshot's effect for a week. Cost: the single-turn gains go, and the tone work waits.
- **Keep the prompt and change the budget.** Raise `MAX_PROMPT_TOKENS` to 10,000 or reserve a floor of six chunks before history. Cost: the raise adds up to 2,000 input tokens to every later-turn request, paid on every multi-turn conversation; the floor takes tokens from history, so long conversations forget what the customer said earlier.

I would roll back the prompt now and ship the second option behind a canary, with the six worked examples moved out of the system prompt into retrieval of examples by intent. I would set the chunk floor at six; anything from five to eight is defensible if the replay supports it, and four or fewer reproduces what release 42 shipped. The failure mode of the floor: a customer who explained their account setup on turn one and asks a question on turn six can lose that turn to make room for chunks, and the answer is grounded in documents and wrong for this customer. The replay set has to include conversations where the answer depends on an early turn.

**What changes in the suite.** Golden cases that start from recorded multi-turn conversations and run through the production `assemble`, not a copy of it. A test that fails when the system prompt grows past a stated share of `MAX_PROMPT_TOKENS`. And the kept-chunk count per request becomes a production metric, not a DEBUG line.

## Follow-ups

- *Rolling back the prompt loses a 5-point offline gain the product manager has already announced. Which half of the gain do you keep, and what risk do you accept in writing?*
- *The replay shows the assembler explains only half the drop. What would you need to see to roll back the snapshot as well?* The audit split by turn showing first-turn answers worse on the new snapshot, with the prompt rolled back.
- *Privacy rules allow the audit team to read conversations only where the customer left feedback. How does that bias the split by turn, and what do you measure instead?*
- *The tracing pipeline keeps prompts but drops kept-chunk counts to save storage. What is the smallest change that makes this class of regression visible next time?*

## Common mistakes

- Trusting the offline gain because it was measured on 400 cases, without asking whether the offline path builds the same request as production.
- Blaming the online judge change because it happened the same week, when the drop is measured by people and by re-contacts.
- Fixing the golden set's billing coverage first. It is a real gap and not this regression.
- Raising the token limit without pricing it on every later-turn request.
- Concluding from the flat online groundedness score that answers are fine; groundedness against the prompt cannot see context that never reached it.
