## Question

<Callout kind="interview" label="Concept, 20 minutes">
"Here are four failures from last month on our HR policy assistant. For each one, which of faithfulness, response relevancy, context precision and context recall would have flagged it, and which would have reported it as fine? Then tell me what you would run online with the judge budget we have."
</Callout>

The assistant and the numbers are a scenario. It answers employee questions from the handbook through retrieval of eight chunks per question. About 20,000 answers a day; the judge budget covers 5 percent of them; one reviewer clears about 30 flagged answers a day. The policy team requires every factual claim in an answer to come from the handbook.

1. **Parental leave.** The handbook page was updated in January 2026 but the ingestion job failed on it, so the index still holds the 2024 page. The answer quotes the 2024 entitlement accurately from that chunk.
2. **Carry-over.** "Can I carry unused leave into next year?" The chunk with the rule is retrieved at rank 8 of 8, behind seven chunks about leave requests. The answer says the handbook does not cover carry-over.
3. **Statutory minimum.** A UK employee asks about annual leave. The answer gives the handbook's figures and adds a sentence about the statutory minimum that is true and appears in no retrieved chunk.
4. **Adoption leave.** The question is about adoption leave. Retrieval returns the birth-parent leave section and the answer describes it accurately.

Use the RAGAS definitions. Say what each metric needs as input, whether it can run without a reference answer, and choose the flagging rule for whatever you run online.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which metrics take a reference answer as input, and who keeps those references current.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the number of claims in a typical answer and the judge's measured rate of wrongly marking a supported claim unsupported.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the ingestion pipeline records when a page fails, and whether anything compares the index with the source system.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Faithfulness compares the answer with the retrieved context, so it passes failure 1 (a faithful copy of a stale chunk) and catches failure 3 (a true claim with no support). Response relevancy compares questions generated from the answer with the user's question, so it is the only metric aimed at failure 4, and it can miss it, because questions about adoption leave and birth-parent leave embed close together. Context precision catches the ranking in failure 2 (0.125); context recall, against a current reference, catches failures 1 and 4 and passes failure 2. Only faithfulness and relevancy need no reference, so only they run online, and neither sees the stale index: that needs an ingestion freshness check, which is not a metric. Online I would run faithfulness on a 1 percent sample and flag any unsupported claim, sized to the reviewer.</p>
</Fragment>

<p><strong>Inputs.</strong> Faithfulness takes the question, the response and the retrieved contexts. Response relevancy takes the question and the response, plus a generator model and an embedding model; RAGAS says it does not assess factual accuracy. Context precision in its reference form and LLM-based context recall both need a reference answer, so they run offline on a labelled set. ContextUtilization, the precision variant judged against the response instead of a reference, runs online but inherits the response's errors: in failure 1 it reports the stale chunk as useful.</p>
<p><strong>What the matrix says.</strong> Failure 1 is the worst of the four, because the answer is confidently wrong about an entitlement, and the two metrics that can run online both pass it. The offline metrics catch it only if the reference was written after January 2026; a reference written in 2025 agrees with the stale index and both score it as perfect. So the control for failure 1 is in ingestion: record a version or hash per source page, alert when the index's version differs from the source system's, and fail loudly when a page fails to ingest.</p>
<p><strong>The online rule, with a chosen threshold.</strong> The budget covers 5 percent of 20,000, or 1,000 judged answers a day. Assume four claims per answer and a judge that wrongly marks a supported claim unsupported 3 percent of the time, independently per claim; both are assumptions to replace with a measured sample. Flagging any unsupported claim, the rule failure 3 needs, flags a good answer with probability 1 − 0.97<sup>4</sup> = 11.5 percent: about 115 false flags a day before a single real one, against a reviewer who clears 30. Flagging only at two or more unsupported claims (score below 0.75) cuts false flags to about 5 a day and lets every single-claim addition like failure 3 through.</p>
<p>The two defensible answers. Keep the strict rule and judge 1 percent of traffic: 200 answers, about 23 false flags a day, which fits the reviewer with room for real ones; the cost is that 99 of every 100 answers go unchecked instead of 95. Or judge the full 5 percent at the looser threshold: five times the coverage for multi-claim fabrication, at the cost of the policy team's one-claim rule. I would take the strict rule at 1 percent, because the policy team's rule is the requirement and the looser threshold silently drops it, and spend part of the remaining budget on measuring the judge's false-unsupported rate against 100 hand-labelled claims, since every number above depends on it.</p>
<p><strong>Where this fails.</strong> Faithfulness trusts the retrieved context: if retrieval is stale or wrong, a perfect faithfulness score is evidence of nothing. And the verifier is itself a model: swapping the LLM for the HHEM classifier variant cuts cost but changes its error profile, so the 3 percent has to be re-measured after any change to the verifier, not carried over.</p>

<li><em>Would recall@k do instead of context recall?</em> It needs labelled relevant chunk ids per question rather than a reference answer; cheaper to compute, and it breaks when re-chunking changes the ids.</li>

## Follow-ups

- *The policy team says the statutory sentence in failure 3 is helpful and wants it allowed. How do you change the metric and the prompt, and what new failure do you accept?*
- *The RAGAS version you pinned is deprecating the API your pipeline uses. How do you upgrade without breaking the trend of last quarter's scores?*
- *Your reviewer leaves and the replacement clears 15 flags a day. What changes in the online rule?*

## Common mistakes

- Reading high faithfulness as correctness, when it measures agreement with whatever was retrieved.
- Expecting response relevancy to catch a wrong but on-topic answer.
- Setting a "flag anything below 1.0" rule without multiplying the judge's per-claim error rate by the claims per answer and the daily volume.
- Writing references once and forgetting that a stale reference turns every offline metric into a check against old policy.
