## Question

<Callout kind="interview" label="As a public question bank phrases it">
"How do you evaluate a RAG system? Explain faithfulness, relevance, and context precision/recall."
</Callout>

Define each metric precisely enough that you could compute it by hand, say what it needs as input (a reference answer or not), and give one way each can look good while the system is failing.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Two of the four grade the retrieved context; two grade the answer.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Faithfulness compares the answer with the context, not with the truth.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Split retrieval from generation. Context precision asks whether the relevant chunks are ranked near the top; context recall asks whether the retrieved context contains what a reference answer needs. Faithfulness is the share of the answer's claims supported by the retrieved context; response relevancy is whether the answer addresses the question. Faithfulness can be perfect while the answer is false, because it trusts the context, and relevancy can be perfect while every fact is wrong, because it only checks the topic.</p>
</Fragment>
<Fragment slot="long">
<p><b>Context precision</b> (retrieval ranking). In RAGAS, Context Precision@K is the sum over positions k of precision@k times v_k, where v_k is 1 if the item at k is relevant, divided by the number of relevant items in the top K. Ranked d7, d2, d9, d4, d1 with d2 and d4 relevant: precision@2 = 0.5 and precision@4 = 0.5, so the score is (0.5 + 0.5) / 2 = 0.5. It needs relevance labels, from a reference or from a judge. Looks good while failing: two relevant chunks at the top, but the one that holds the answer was never retrieved.</p>
<p><b>Context recall</b> (retrieval coverage). The LLM variant splits a reference answer into claims and computes the share the retrieved context supports. It needs a reference answer, so it is offline only. Looks good while failing: the reference answer itself is outdated.</p>
<p><b>Faithfulness</b> (grounding). Split the response into claims, check each against the retrieved context, divide supported by total. Two claims with one unsupported scores 0.5. No reference needed, so it runs online. Looks good while failing: the context is wrong or stale, and the answer repeats it faithfully.</p>
<p><b>Response relevancy</b> (on topic). A model generates questions from the answer, three by default, and the score is their mean cosine similarity to the user's question. No reference needed. Looks good while failing: a fluent, on-topic answer with the wrong number in it.</p>
<p>How I use them. Retrieval metrics on a labelled set to tune chunking and ranking; faithfulness as an online signal for ungrounded claims; a task-specific correctness check against references where I have them. And I validate the judge behind each LLM-based metric against human labels, because each one is an LLM judge with a formula around it.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Which can run in production?</em> Faithfulness and response relevancy, because they need no reference. Context recall and reference-based correctness need labelled data, so they run offline.</li>
<li><em>Faithfulness is 0.95 and users say answers are wrong. Where do you look?</em> Retrieval: the answers are grounded in the wrong documents. Check context recall and the freshness of the index.</li>
<li><em>Would you use BLEU or ROUGE?</em> Not as quality metrics for generated answers; at most as cheap signals to find traces to read.</li>
</ul>
</Fragment>
</Depth>

### The trap in one example

Context: "Refunds are processed within 5 business days." The policy changed last month to 10 days, and the index was not updated. The answer says: "Your refund will arrive within 5 business days." Faithfulness is 1.0, every claim supported by the context. Response relevancy is high, the answer is on topic. The answer is wrong. Only a reference-based check or a freshness check on the index would catch it.

## Follow-ups

- *How would you build the labelled set for the retrieval metrics?* From real queries, with the expert marking relevant chunks, plus cases where no chunk is relevant so you can test that the system says so.
- *The RAGAS library changed its API. How do you protect your numbers?* Pin the version, keep the formulas in your own test code, and re-run a fixed sample when upgrading.
- *What is the relationship with recall@k?* Recall@k counts relevant documents retrieved in the top k against all relevant documents; context recall measures the same idea at the level of claims from a reference answer.

## Common mistakes

- Calling faithfulness "accuracy". It measures agreement with the context.
- Using a single blended "RAG score", which hides whether retrieval or generation failed.
- Reporting LLM-computed metrics without ever checking the underlying judge against human labels.
- Forgetting that context recall needs a reference, then wondering why it cannot run in production.
