## Question

<Callout kind="interview" label="Critique, 30 minutes">
"This proposal is on the agenda for Thursday. It gives the docs assistant a release gate this sprint without a labelling budget. Review it: list what is wrong, in order of how much it matters, and say what you would approve instead."
</Callout>

The proposal, as written by the assistant team (scenario):

```text
Golden set v1 for the docs assistant
Owner: assistant team. Goal: a release gate this sprint, no labelling budget.

Generation
  For each of the 412 pages in the public docs, prompt asst-prod (the production
  model, with the production RAG pipeline) with:
    "Write 2 questions a customer might ask that this page answers,
     and the ideal answer to each."
  -> 824 question and reference pairs.

Quality filter
  Run the production pipeline on each question. Keep the pair if the judge
  rates the pipeline's answer 4 or 5 against the reference.
  -> 571 pairs.

Deduplication
  Drop a pair if its question has cosine similarity above 0.95 with a kept one.
  -> 500 pairs.

Grading
  Judge: asst-prod. Prompt: "Score 1 to 5 how well the answer matches the
  reference." Pass = 4 or 5.

Gate
  Release if the pass rate is at least 92%. Prompt changes are tuned
  against the same 500.

Result on the current release: 486 / 500 = 97.2%.

Maintenance
  Regenerate the set each quarter with the then-current production model,
  so it keeps up with the docs.
```

The assistant answers questions about a public product. About a third of its traffic, the team says, is about billing and account limits, which the docs cover on six pages.

List the flaws before opening the checklist.

## Answer

<Depth>
<Fragment slot="short">
<p>The quality filter decides everything else: it keeps a pair only when the production pipeline already answers it to the judge's satisfaction, so the set is a list of things the current release gets right, and its 97.2 percent is close to guaranteed. The 253 dropped pairs are the most useful data in the proposal. Around that, the questions and references are the model's own, written one page at a time, so the set inherits its misreadings and misses the questions users actually ask; the judge is the same model, which is acceptable only after it is checked against human labels; and the gate threshold, the tuning against the same set and the quarterly regeneration each remove what signal is left. I would approve the pipeline as a smoke test after removing the filter, and build the gate from production questions plus the 253, read by a person.</p>
</Fragment>
<Fragment slot="long">
<p><strong>1. The filter selects for passing.</strong> A pair survives only if the production pipeline's answer is rated 4 or 5. The next release is tested on questions the current one passes, which makes the gate a regression suite at best, and one with no cases the current release fails. Anthropic separates capability evals, which start at a low pass rate, from regression evals near 100 percent; this set can only be the second, and the proposal calls it a quality gate. The 253 dropped pairs are either generation errors or real failures, and nobody has looked to find out which.</p>
<p><strong>2. The references come from the model under test.</strong> When asst-prod misreads a page, its misreading is the "ideal answer", and a later model that reads the page correctly is marked wrong. This is the flaw a reviewer misses on first read, because the references look authoritative in a table.</p>
<p><strong>3. The questions come from the model under test, one page at a time.</strong> Each question is answerable from the page it was written from, in the model's own phrasing. Nothing spans two pages, carries a wrong premise, asks about something the docs do not cover, or asks about the user's own account. Hamel Husain's guidance is to start synthetic generation from failure hypotheses and dimensions, with hand-written examples before scaling, because synthetic data cannot show how often a failure happens in production.</p>
<p><strong>4. The allocation ignores traffic.</strong> Two questions per page gives the six billing and limits pages 12 of 824 generated pairs, about 1.5 percent, against about a third of traffic.</p>
<p><strong>5. Retrieval may never be tested.</strong> The docs are public, so the model may answer many questions from pretraining. A closed-book run on the 500 says how many need retrieval at all; if most pass without it, the gate cannot see a retrieval regression. This is the second flaw a reviewer misses, because the pipeline in the proposal does include retrieval.</p>
<p><strong>6. The judge is the model under test.</strong> Self-preference is measured: Panickssery et al. find evaluators score their own outputs above others' that humans rate as equal, rising with how well the model recognises its own text. Here the judge compares its own answer with its own reference. The judgement call: a same-model judge is acceptable if its true positive and true negative rates against human labels hold on a held-out sample, which is the test Husain recommends; without that measurement it is not acceptable, and with it, it may be fine.</p>
<p><strong>7. The scale and the threshold.</strong> A 1 to 5 score with pass at 4 hides what failed. Binary checks per criterion (correct figure, cites the right page, declines when the docs do not say) make disagreement visible and thresholds meaningful.</p>
<p><strong>8. The gate cannot block.</strong> At 97.2 percent on a set selected to pass, a release has to lose 27 of 500 cases to fall below 92 percent. A case-by-case comparison against the current version is the gate; the absolute threshold is not.</p>
<p><strong>9. Tuning on the gate set.</strong> Prompt changes tuned against the same 500 will pass them; nothing is held out.</p>
<p><strong>10. Regeneration.</strong> A new set each quarter, from the next model, filtered by the next model's competence, gives scores that cannot be compared across quarters and drops every case the old model failed and the new one cannot write.</p>
<p><strong>What I would approve instead, this sprint.</strong> The decision has two defensible answers. Approve the synthetic pipeline with the filter removed, as a fast smoke test: no labelling budget, ready this week, and it will catch an answer that stops matching the docs. Its cost is that it still cannot represent traffic or questions the docs do not answer. Or build the gate from production: 150 sampled questions with the billing and limits pages weighted to their traffic, plus the 253 dropped pairs, about 400 cases, read and labelled pass or fail by an engineer who knows the product. I choose a budget of 3 minutes a case, so the 400 take 20 hours, half a week of one engineer: that is the cost of having a gate at all, and the constraint conflict is the sprint deadline against a gate that can fail. I would do both, the smoke test now and the production set within two sprints, with the judge validated on 100 of the labelled cases before it grades anything.</p>
<p><strong>Where my answer fails.</strong> The 253 dropped pairs are themselves synthetic and page-bound, so mixing them in raises the failure rate without fixing coverage. And an engineer labelling at 3 minutes a case has the same blind spots as the team that wrote the docs; a support agent would catch different errors, at a cost the team has not budgeted.</p>
</Fragment>

<li><em>Is synthetic generation ever right for a golden set?</em> For thin strata and for behaviours that are rare in logs, generated from stated dimensions and reviewed by a person, never as the whole set.</li>
</ul>

## Follow-ups

- *Pushback: the team lead says a filtered set is fine because it is "only a regression suite". What does it still miss as a regression suite, and what would you accept in writing to let it ship this sprint?*
- *Reversal: what would the judge validation have to show for you to keep asst-prod as its own judge for the next year?*
- *Two senior engineers disagree: one wants the gate on synthetic cases because production questions contain customer data, the other refuses synthetic cases entirely. How do you decide without deciding by rank?*

## Common mistakes

- Spotting the same-model judge and stopping, when the filter does more damage.
- Treating a 97 percent pass rate as reassurance instead of as a symptom of how the set was built.
- Fixing the judge but keeping references written by the model under test.
- Asking for "more cases" without saying where they come from or who labels them.
