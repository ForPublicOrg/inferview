        """Build one tree per trace from span events that arrive in any order.

        events: dicts with trace_id, span_id, parent_id (None for a root), name, start and end. The exporter retries, so

            {"span_id", "name", "start", "end", "missing": bool, "children": [nodes sorted by (start, span_id)]}
        where missing is True only for a placeholder you create for a parent that never arrived.

        Your policy, with the reason: where does a span whose parent never arrived go?
        """

    # Orphans go under one placeholder per missing parent, so siblings stay together and the gap shows in the tree.
    # A parent cycle is cut at its member with the smallest (start, span_id), so arrival order cannot change the output.


    def assemble(events):
        inf = float("inf")
        spans = {}
        for e in events:
            key = (e["trace_id"], e["span_id"])
            old = spans.get(key)
            if old is None or (old["end"] is None and e["end"] is not None):
                spans[key] = e

        parent = {}
        for key, e in spans.items():
            p = e.get("parent_id")
            parent[key] = None if p is None or p == key[1] else (key[0], p)

        def order(key):
            s = spans[key]["start"]
            return (inf if s is None else s, key[1])

        state = {}
        for first in spans:
            if first in state:
                continue
            path, cur = [], first
            while cur is not None and cur in spans and cur not in state:
                state[cur] = 1
                path.append(cur)
                cur = parent[cur]
            if cur is not None and state.get(cur) == 1:
                cycle = path[path.index(cur):]
                parent[min(cycle, key=order)] = None
            for k in path:
                state[k] = 2

        nodes = {
            key: {"span_id": key[1], "name": e["name"], "start": e["start"], "end": e["end"], "missing": False, "children": []}
            for key, e in spans.items()
        }
        roots, holders = {}, {}
        for key, node in nodes.items():
            p = parent[key]
            if p is None:
                roots.setdefault(key[0], []).append(node)
            elif p in nodes:
                nodes[p]["children"].append(node)
            else:
                holder = holders.get(p)
                if holder is None:
                    holder = {"span_id": p[1], "name": None, "start": None, "end": None, "missing": True, "children": []}
                    holders[p] = holder
                    roots.setdefault(p[0], []).append(holder)
                holder["children"].append(node)

        def node_key(n):
            if n["missing"]:
                return (min(c["start"] for c in n["children"]), n["span_id"])
            return (inf if n["start"] is None else n["start"], n["span_id"])

        for node in list(nodes.values()) + list(holders.values()):
            node["children"].sort(key=node_key)
        for trace in roots.values():
            trace.sort(key=node_key)
        return roots

## Question

<Callout kind="interview" label="Coding round, 40 minutes">
Our trace viewer receives span events from a collector, in whatever order they were exported. Write the function that turns them into one tree per trace, so error analysis can start from a readable trace.
</Callout>

Each event is a dict with `trace_id`, `span_id`, `parent_id` (None for a root), `name`, `start` and `end`. Return `{trace_id: [root nodes]}`; a node holds the span's fields, a `missing` flag and its `children`, sorted by `(start, span_id)`. The starter's docstring gives the exact shape.

The stream is what an exporter with retries produces:

- Children often arrive before their parents.
- A span can arrive more than once. A copy sent before the span finished has `end` set to None, and a copy with an end time wins over one without.
- Some parents never arrive: the process that owned them crashed or sampled them out.
- Instrumentation bugs happen. If parent links form a cycle, the function still terminates and returns every span exactly once.

Two constraints. The visible tests time 100,000 spans in 50 traces of 2,000 spans each and allow 5 seconds. Some agent traces are thousands of spans deep, so a tree that is one long chain has to work too.

One decision is yours: where a span whose parent never arrived goes. Put it at the root level, or under a placeholder node for the missing parent with `missing: True`. The hidden tests accept either, and the comment above your function says which and why.

## Answer

The reference does four passes, none of them recursive.

**Deduplicate by (trace_id, span_id).** The key has to include the trace: span ids are only meaningful inside their trace, and a test fixture or a buggy SDK that reuses `"1"` in two traces otherwise grafts one trace's spans onto the other. One dict lookup per event, keeping the first copy unless a later copy has an end time and the kept one does not.

**Resolve parents and cut cycles.** Each span's parent key is `(trace_id, parent_id)`. A self-parent is treated as no parent. To find cycles, walk each span's parent chain with a colour per span (on the current path, or finished); reaching a span that is on the current path means the chain closed on itself. The reference cuts the cycle at its member with the smallest `(start, span_id)`, a choice that depends only on the spans, so shuffling the input cannot change which link is cut. Each span is walked once, so this pass is linear.

**Attach.** A span whose parent key exists becomes that node's child. A span with no parent is a root. A span whose parent never arrived goes under a placeholder, one per missing parent, created on first use.

**Sort siblings** by `(start, span_id)`. The span id as the tie-break makes the order deterministic when two tool calls start in the same millisecond, which happens with parallel tool calls.

Building the tree takes O(n log n) for the sorts and O(n) for everything else. When this problem was checked in CPython 3.12.6, the reference built the visible test's 100,000 spans in 0.75 s. A version that scans the event list for each span's parent took 3.75 s for 4,000 spans, and it grows with the square of the span count. Recursion is the other trap: a recursive build or sort is fine on the random trees, whose depth grows roughly with the logarithm of their size, and fails on the hidden 20,000-deep chain, since CPython's default recursion limit, which `sys.getrecursionlimit()` reports as 1000, is far below that.

**The orphan decision.** Both answers are defensible.

- *Placeholder per missing parent.* Siblings that lost the same parent stay together, the gap is visible where it happened, and a reviewer reading the trace sees "four tool calls under an agent span we never received". The cost: every consumer has to handle nodes with no name and no timing, and a dashboard that counts root spans counts placeholders unless it filters them.
- *Promote to root.* Every node is a real span and consumers need no special case. The cost: the trace now shows several unrelated-looking roots, the fact that a parent is missing is lost unless you keep `parent_id` on the node, and siblings are scattered among real roots.

The reference uses placeholders because the viewer feeds error analysis, where the question is what happened inside the agent step, and the shape answers that better than a flat list.

**Where the reference fails.** It assumes the whole trace is present when it runs. In a streaming collector, a parent that arrives two seconds after the tree was built is a placeholder in the stored tree, and a trace viewed before its root span ends shows a partial root. The fix is a completeness rule: hold a trace until its root has ended and no span has arrived for a quiet period, rebuild when a late span arrives, and mark the trace incomplete in the viewer when that period passes with placeholders still in it. That trades latency for correctness. A short wait shows traces sooner with more placeholders; a long wait holds every trace in memory until it settles. The cycle cut has the same limit: it returns a tree, but which link was wrong is a guess, so the viewer should flag a trace that needed a cut instead of rendering it as normal.

## Follow-ups

- *What changes to run this inside a collector that never sees the whole list at once?* Partition events by trace id so one worker sees all of a trace; keep per-trace state with a quiet-period timer and a cap on spans and bytes per trace; write the tree when the timer fires and accept late spans as a re-assembly. Memory is bounded by the number of open traces times their size, so the cap and the timer are the capacity plan.
- *Your quiet period is 30 seconds and the product team wants traces visible within 2. Which do you give up, and what do you write down?* Show partial traces immediately with an "assembling" state and placeholders, rebuild on arrival, and record that any eval or alert reading traces younger than the quiet period sees incomplete trees.
- *What would you need to see in production to switch from placeholders to promoting orphans?* Evidence that consumers mishandle placeholders, such as root counts or latency charts that include them, and that orphans are rare enough that their scattered position does not slow reading. The orphan rate per service is the measurement.
- *The tool spans carry `gen_ai.tool.call.arguments`, which the conventions mark opt-in. Two senior engineers disagree on turning it on for the traces error analysis reads. How do you decide without deciding by rank?* Read twenty traces with and without arguments and count how many failures can be diagnosed without them; turn capture on only where the difference is real, with redaction and a retention limit agreed with whoever owns the personal data.

## Common mistakes

- Keying spans by `span_id` alone, which merges traces that reuse an id.
- Keeping whichever duplicate arrived first, so a span shows no end time even though a complete copy arrived.
- Recursing to build or flatten the tree, which works on every test trace until the first deep agent run.
- Following parent pointers without cycle detection, which loops forever on one malformed span.
- Searching the whole event list for each parent, which passes on twenty spans and times out on a real trace store.
- Dropping orphans silently. A trace that quietly loses spans is worse than one that shows where they went.
