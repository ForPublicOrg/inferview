    from collections import OrderedDict


    class PrefixCache:
        def __init__(self, ttl=300, min_tokens=512, lookback=20, max_entries=10_000):
            self.ttl = ttl
            self.min_tokens = min_tokens
            self.lookback = lookback
            self.max_entries = max_entries
            self._live = OrderedDict()   # prefix key -> last_used, least recently used first

        def entries(self):
            return len(self._live)

        def request(self, t, blocks):
            bps = [i for i, b in enumerate(blocks) if b[2]]
            if len(bps) > 4:
                raise ValueError("at most 4 breakpoints")
            last = bps[-1] if bps else -1
            keys, cum = [], []
            h, total = 0, 0
            for i, (content, tokens, _) in enumerate(blocks):
                total += tokens
                if i <= last:
                    h = hash((h, content))
                    keys.append(h)
                    cum.append(total)
            eligible = [i for i in bps if cum[i] >= self.min_tokens]
            hit = -1
            for bp in eligible:
                for j in range(bp, max(-1, bp - self.lookback), -1):
                    if j <= hit:
                        break
                    used = self._live.get(keys[j])
                    if used is not None and t - used < self.ttl:
                        hit = j
                        break
            read = cum[hit] if hit >= 0 else 0
            write = cum[eligible[-1]] - read if eligible else 0
            stamp = [hit] if hit >= 0 else []
            for j in stamp + eligible:
                self._live[keys[j]] = t
                self._live.move_to_end(keys[j])
            while len(self._live) > self.max_entries:
                self._live.popitem(last=False)
            return {"read": read, "write": write, "uncached": total - read - write}

## Question

<Callout kind="interview" label="The prompt">
Our cost model assumes a 90 percent cache hit rate for the new agent. Before finance signs off, build a simulator of the provider's prefix cache from its documentation and run our request traces through it.
</Callout>

Implement `PrefixCache` from the rules the Claude prompt-caching page documents. A request is a list of blocks `(content, tokens, breakpoint)` in serialisation order (tools, system, messages already flattened), sent at time `t` in seconds.

- The prefix at position *i* is blocks 0 to *i* by content. Two prefixes match only if every block is equal and in the same order.
- A request may carry at most four breakpoints; more is a `ValueError`. A breakpoint whose prefix holds fewer than `min_tokens` tokens neither reads nor writes.
- Entries are written only at breakpoints. For each breakpoint, look for a live entry at the breakpoint and up to `lookback − 1` positions before it, nearest first; the search for that breakpoint stops after `lookback` positions. The highest position found over all breakpoints is the read point, and `read` is the prefix's tokens up to it.
- An entry is live while `t − last_used < ttl`. A hit refreshes it to `t`. After the request, every eligible breakpoint's prefix is live with `last_used = t`.
- `write` is the tokens up to the last eligible breakpoint minus `read`. `uncached` is everything else.
- The cache never holds more than `max_entries` entries. Which entry to evict is your decision; say why.

Then answer: to replay one day of traffic for 400 tenants, each with a few hundred conversations, what `max_entries` would you choose, and what does a too-small value do to the predicted hit rate?

## Answer

<Depth>
<Fragment slot="short">
<p>Compute one key per position as a chain, h<sub>i</sub> = hash(h<sub>i−1</sub>, content<sub>i</sub>), so all prefix keys of a request cost one pass. Look up only the lookback window behind each eligible breakpoint, take the highest live hit, charge reads to it and writes from it to the last eligible breakpoint, then stamp the hit and every eligible breakpoint. An ordered dict with move-to-end gives LRU eviction in constant time.</p>
</Fragment>
<Fragment slot="long">
<p>The cost of the naive version is in the keys. Building <code>tuple(content for block in blocks[:j + 1])</code> for each window position is O(n) per key, and hashing a tuple is O(n) again, so a 7,500-block request with four breakpoints costs up to 80 such keys. The chain makes every key O(1) after one pass over the request, which is what the performance test checks: 300 growing requests of up to 7,500 blocks in under 1.5 seconds.</p>
<p>The lookback rule is the behaviour most worth simulating, because it produces misses that a "longest shared prefix" model never predicts. With one automatic breakpoint at the end, a turn that adds 25 positions leaves the previous entry outside the 20-position window, and the request reads nothing. The hidden tests include that case and its 19-position twin, which hits.</p>
<p>Key representation is a decision with two defensible answers. A hash chain stores one integer per entry and is fast, but two different prefixes can collide and produce a phantom hit, and Python's string hashing is salted per process, so keys cannot be persisted or compared across workers. Exact keys (a trie of block contents, or interned tuples) are collision-free but cost memory proportional to every prefix stored. For a cost simulator, a collision probability near 2<sup>−64</sup> per comparison is far below the other errors in the model; for anything that serves content, use a cryptographic hash of the bytes.</p>
<p>Eviction is the second decision. LRU keeps hot tenants and evicts idle ones, which matches how the provider behaves only if the provider's capacity is the binding constraint; evicting the entry closest to expiry keeps the simulation closest to "the TTL is the only limit". The visible behaviour that both must preserve is that a request repeated at once writes nothing, which the hidden tests check with a capacity of 8.</p>
<p>Capacity for the 400-tenant replay is a quantity to choose: the number of entries that can be live at once is roughly concurrent conversations within one lifetime times breakpoints per request. A few hundred conversations per tenant spread over a working day, at most four breakpoints each, is tens of thousands of entries at peak; a cap of 100,000 leaves headroom. A cap below the live set makes the simulator evict entries the provider would still hold and predicts a hit rate that is too low, which is the safe direction for a budget but makes the cache look worse than it is.</p>
<p>Failure mode of the recommended simulator: it predicts what the documented algorithm would do, not what the service does. Provider caches are best effort, and the trace's own hit rate from <code>cache_read_input_tokens</code> is the ground truth to compare against. A simulator that disagrees with measured reads by more than a few points is mis-modelling the request layout, usually the position count (consecutive tool_use or tool_result blocks count as one position on the Claude API).</p>
</Fragment>

## Follow-ups

- *Add the 1-hour lifetime.* Entries carry their own TTL, 1-hour breakpoints must precede 5-minute ones, and writes split into a 1-hour segment and a 5-minute segment priced separately.
- *Two senior engineers disagree on LRU against earliest-expiry eviction. How do you decide without deciding by rank?* Replay the same trace under both and compare each to measured reads; the policy that tracks reality is the one to keep.
- *The agent fires parallel tool calls. What changes in your position count?* Consecutive tool_use blocks, and consecutive tool_result blocks, each count as one position on the Claude API, so the trace has to be flattened the same way before simulation.

## Common mistakes

- Treating the cache as longest-common-prefix with any earlier request, which ignores that entries exist only at breakpoints.
- Searching the whole request backwards instead of stopping after the lookback window.
- Refreshing the lifetime only on writes.
- Building a full tuple per prefix, which passes small tests and fails the timing test.
- Evicting an entry the current request just wrote or read.
