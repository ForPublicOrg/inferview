  solution: |
    def count_tokens(text):
        # Stand-in for a real tokenizer: one token per 4 characters, at least 1.
        return max(1, len(text) // 4)


    def allocate(budget, reserve_output, system, history, docs, pinned=frozenset()):
        pinned = set(pinned)
        remaining = budget - reserve_output - count_tokens(system)
        remaining -= sum(count_tokens(text) for tid, text in history if tid in pinned)
        if remaining < 0:
            raise ValueError("system prompt, pinned turns and output reserve exceed the budget")
        keep = set(pinned)
        for tid, text in reversed(history):
            if tid in pinned:
                continue
            cost = count_tokens(text)
            if cost > remaining:
                break
            keep.add(tid)
            remaining -= cost
        kept_history = [tid for tid, _ in history if tid in keep]
        kept_docs = []
        for doc_id, score, text in sorted(docs, key=lambda d: (-d[1], d[0])):
            cost = count_tokens(text)
            if cost <= remaining:
                kept_docs.append(doc_id)
                remaining -= cost
        return {"history": kept_history, "docs": kept_docs, "left": remaining}

## Question

<Callout kind="interview" label="As a vendor blog describes a phone-screen task">
"Designing a token-budget allocator" for the system prompt, conversation history and retrieved documents.
</Callout>

Write `allocate(budget, reserve_output, system, history, docs, pinned)` for a chat product that retrieves documents on every turn.

- `system` is always sent. Turns whose ids are in `pinned` (the turn where the user set their constraints, say) are always sent. If the system prompt, the pinned turns and `reserve_output` do not fit in `budget`, raise `ValueError`.
- Unpinned history is kept as a contiguous run of the newest turns: walk back from the newest and stop at the first unpinned turn that does not fit. Pinned turns older than that run stay in. Return turn ids oldest first.
- Documents go in by descending score, skipping any that do not fit and trying the next. Ties are yours to break, but the result must not depend on the order documents arrive in.
- Return `{"history", "docs", "left"}`, where `left` is the unused budget after the reserve.

Use the given `count_tokens`. The hidden tests check properties (budget arithmetic, order, contiguity, that no skipped document would still fit, order independence) on random inputs, and a 150,000-turn history must be allocated in under 1.5 seconds.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the interviewer which is worse for this product: a missing old turn or a missing high-scoring document.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for the longest session in the production logs, in turns.</p></details>

## Answer

The reference solution subtracts the system prompt, the reserve and the pinned turns first and raises if the remainder is negative. It walks the history newest first, skipping pinned turns (already paid for) and stopping at the first unpinned turn that does not fit. Kept ids go into a set, and one final pass over the history emits them in order. Documents are sorted by `(-score, doc_id)` and added greedily.

The decisions carry the question more than the loop does.

**Contiguity for unpinned turns.** A history with turn 7 kept and turn 6 dropped shows the model answers to questions it cannot see. Pinned turns are the controlled exception: they are facts the product decided must survive, and the model sees them out of sequence by design.

**Greedy documents.** Skipping a 500-token document to fit two 50-token ones is the greedy answer to a knapsack problem. It is not optimal by total score, and an exact knapsack is pseudo-polynomial in the budget, too slow per request at real budgets; greedy by score is the standard trade.

**History before documents.** That priority suits chat. A retrieval-heavy product may give documents a guaranteed share of the remainder first, and the right answer depends on which loss hurts more, which is why the first hint is a question for the interviewer.

**Tie-break.** Sorting by `(-score, doc_id)` makes the output a function of the input set. Without it, two replicas given the same documents in different orders build different prompts, which also defeats prompt caching.

**Performance.** `kept.insert(0, turn)` is O(n) per call, and `turn_id in pinned` against a list is O(p); both are quadratic on a long history. A set for membership and one ordered pass at the end keep the whole allocation O(n + d log d), which is what the 150,000-turn test checks.

Failure mode of this design: pinned turns are unbounded. A user who pins forty turns makes the mandatory part exceed the budget and every call fails with `ValueError`. The product needs a cap on pinned tokens, or a summarised form of pinned content, before this ships.

## Follow-ups

- *The four-characters heuristic is wrong for your users. What do you use?* The provider's token-counting endpoint for the assembled request, with a margin, because counts depend on the model's tokenizer and on formatting. If server-side context editing is on, the counting endpoint reports input after the edits, so the allocator and the server agree.
- *Pinned turns grow without bound. What is your policy?* A token cap on pinned content, enforced when a turn is pinned, with older pins folded into a structured notes block the user can see.
- *How does the allocator interact with prompt caching?* Its output order is the prompt order. Keeping system, pinned turns and the older history first, and documents last, preserves a cacheable prefix; dropping the oldest unpinned turn rewrites the cache from that point, so drop in chunks.
- *What changes in a real client?* Count tokens on the serialised request including tool definitions and message framing, keep the reserve large enough for thinking tokens on reasoning models, and log what was dropped per call so recall failures can be traced.

## Common mistakes

- Forgetting the output reserve, so the reply is cut off at `max_tokens`.
- Dropping a turn from the middle of the history to fit one more.
- Stopping at the first document that does not fit.
- Sorting documents by score alone, so the output depends on input order.
- Quadratic list operations that pass small tests and time out on long sessions.
