  solution: |
    def count_tokens(text):
        # Stand-in for a real tokenizer: one token per 4 characters, at least 1.
        return max(1, len(text) // 4)


    def allocate(budget, system, history, docs, reserve_output):
        remaining = budget - reserve_output - count_tokens(system)
        if remaining < 0:
            raise ValueError("system prompt plus output reserve exceed the budget")
        kept_history = []
        for turn in reversed(history):
            cost = count_tokens(turn)
            if cost > remaining:
                break
            kept_history.insert(0, turn)
            remaining -= cost
        kept_docs = []
        for score, doc in sorted(docs, key=lambda d: -d[0]):
            cost = count_tokens(doc)
            if cost <= remaining:
                kept_docs.append(doc)
                remaining -= cost
        return {"system": system, "history": kept_history, "docs": kept_docs, "left": remaining}

## Question

<Callout kind="interview" label="As a third-party guide describes the phone screen">
"Designing a token-budget allocator" for the system prompt, conversation history and retrieved documents.
</Callout>

Write `allocate(budget, system, history, docs, reserve_output)`:

- `budget` is the context size in tokens. `system` is a mandatory string. `history` is a list of turns, oldest first. `docs` is a list of `(score, text)` pairs. `reserve_output` is kept free for the reply.
- Raise `ValueError` if the system prompt plus the output reserve already exceed the budget.
- Keep the most recent history turns that fit, walking from the newest backwards and stopping at the first turn that does not fit, so the kept history is contiguous. Return them oldest first.
- Then add documents in descending score order. A document that does not fit is skipped and the next one is tried.
- Return `{"system", "history", "docs", "left"}`, where `left` is the number of unused tokens.

Use the given `count_tokens`, a stand-in of one token per four characters. The tests use strings of repeated letters so the arithmetic is easy to follow.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Subtract the fixed costs first: what is left after the system prompt and the reserve is the only budget you hand out.</p></details>
<details class="hint"><summary>Hint 2</summary><p>`for turn in reversed(history)` with `break` gives a contiguous tail; `insert(0, turn)` keeps chronological order.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For documents, `continue` rather than `break`: a big document should not block smaller ones behind it.</p></details>

## Answer

The reference solution computes `remaining = budget - reserve_output - count_tokens(system)` and raises if it is negative. It walks history newest first, stops at the first turn that does not fit, and inserts kept turns at the front so they come out in order. Then it sorts documents by score and greedily adds any that fit. `left` is whatever remains.

The design choices are the interview, more than the loop:

- **Why history is contiguous.** Keeping turn 5 and turn 3 but not turn 4 shows the model a conversation that never happened: answers to questions it cannot see. Cutting from the old end is safe; cutting from the middle is not.
- **Why documents are not.** Documents are independent. Skipping a 500-token document to fit two 50-token ones loses one source rather than corrupting a sequence. It is the greedy answer to a knapsack problem, and good enough when scores already rank relevance.
- **Why history before documents.** That is one policy, suited to chat. A retrieval-heavy feature may give documents priority or fixed shares (say, a set fraction of the remaining budget each), and the honest answer names the policy and why.
- **Why a reserve.** Without one, a full prompt leaves no room for the answer, and the response ends at `max_tokens`. On reasoning models the reserve must also cover thinking tokens.

## Follow-ups

- *The heuristic of four characters per token is wrong for your users. What do you use?* The provider's token-counting endpoint or the model's tokenizer, and a safety margin, because the two can disagree on special tokens and formatting.
- *Old turns hold facts you still need.* Summarise the dropped turns into a short note that is always kept, or extract facts into a structured memory injected each turn.
- *Retrieved documents are near-duplicates.* Deduplicate before allocating, or the budget fills with the same paragraph five times.
- *How does this interact with prompt caching?* Put the stable parts (system, then older history) first and the per-request documents last, so the allocator's output keeps a cacheable prefix.

## Common mistakes

- Forgetting the output reserve.
- Dropping turns from the middle of the history to squeeze in one more.
- Stopping at the first document that does not fit.
- Returning history newest first.
