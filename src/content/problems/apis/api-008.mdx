    import json

    def run(call_model, user_msg, tools, mutating=frozenset(), max_steps=8):
        messages = [{"role": "user", "content": user_msg}]
        done = {}
        for _ in range(max_steps):
            reply = call_model(messages)
            messages.append({"role": "assistant", "content": reply["content"]})
            calls = [b for b in reply["content"] if b.get("type") == "tool_use"]
            if not calls:
                text = "".join(b["text"] for b in reply["content"] if b.get("type") == "text")
                return text, messages
            results = []
            for call in calls:
                out, is_error = run_one(tools, mutating, done, call.get("name"), call.get("input"))
                results.append({"type": "tool_result", "tool_use_id": call["id"],
                                "content": out, "is_error": is_error})
            messages.append({"role": "user", "content": results})
        raise RuntimeError(f"no final answer after {max_steps} model calls")

    def run_one(tools, mutating, done, name, args):
        fn = tools.get(name)
        if fn is None:
            return f"unknown tool: {name}; available: {', '.join(sorted(tools))}", True
        if not isinstance(args, dict):
            return f"{name}: input must be an object, got {type(args).__name__}", True
        key = None
        if name in mutating:
            key = name + "\x00" + json.dumps(args, sort_keys=True)
            if key in done:
                return f"{name} already ran with these arguments in this conversation; it was not run again. Earlier result: {done[key]}", True
        try:
            out = json.dumps(fn(**args))
        except Exception as e:
            return f"{name} failed: {type(e).__name__}: {e}", True
        if key is not None:
            done[key] = out
        return out, False

## Question

<Callout kind="interview" label="The prompt">
"Write the function-calling handler for our support agent. It runs inside a nightly batch as well as in chat, and last month it emailed one customer the same apology four times."
</Callout>

Write `run(call_model, user_msg, tools, mutating=frozenset(), max_steps=8)` against Claude's block format.

- `call_model(messages)` returns `{"content": [blocks]}`. A block is `{"type": "text", "text": ...}` or `{"type": "tool_use", "id": ..., "name": ..., "input": {...}}`.
- Append each assistant reply to `messages` as `{"role": "assistant", "content": blocks}`. If it contains `tool_use` blocks, answer every one with a `{"type": "tool_result", "tool_use_id": ..., "content": str, "is_error": bool}` in a single user message, in call order. A successful result is `json.dumps` of the return value.
- A reply with no `tool_use` blocks ends the loop: return the joined text and `messages`. After `max_steps` model calls without such a reply, raise `RuntimeError`.
- Nothing the model sends may crash the loop. Anything that stops a tool from running or returning becomes an error result the model can read.
- Tools named in `mutating` have side effects. Once a mutating call has succeeded, a later call to the same tool with the same arguments in the same run must not execute again. What its result says is your decision.
- The batch job runs conversations with up to 20,000 tool calls. Per-call overhead must not grow with the length of the conversation.

The visible tests cover a single call, a tool that raises, a repeated email and a model that never stops. The hidden tests inject other failures and check invariants over random conversations.

## Answer

The reference solution keeps the loop and the executor apart. The loop calls the model, appends the assistant turn before anything else, collects the `tool_use` blocks, and either returns or appends exactly one result per call. `run_one` is the executor: it is the only place a model proposal turns into an effect, so every check sits there.

The executor rejects four kinds of proposal before or around execution: an unknown tool name, an `input` that is not an object, arguments the function does not accept (the `TypeError` from `fn(**args)`), and a return value `json.dumps` cannot serialise. Each comes back as an error result naming the problem. The order matters for the last one: serialisation happens inside the `try`, so a tool that ran but returned a `set` is reported as a failure rather than crashing the turn. That is a real trade-off, because the side effect already happened; the error text should say so, and a production executor records the effect before formatting it.

Duplicate protection is a dictionary keyed by tool name plus `json.dumps(args, sort_keys=True)`. Sorting keys makes `{"card": "c1", "amount_cents": 500}` and `{"amount_cents": 500, "card": "c1"}` one key, at every nesting level. Lookup is constant time, which is the performance constraint: an implementation that scans earlier assistant turns for a matching call does work proportional to the history on every call, and 20,000 calls that each scan an average of 10,000 earlier ones make 200 million comparisons. Only successful calls enter the dictionary, so a send that raised can be retried.

The policy choice is what the duplicate's result says. The reference returns `is_error: true` with the earlier result inside the message, which tells the model the action happened and stops it from trying a third time. Returning the cached result as a success is also defensible: it is what an HTTP idempotency key does, and it keeps the model's plan intact. The cost is that the model never learns it repeated itself, so a loop that keeps re-proposing the same send is invisible in the transcript. The hidden tests accept either.

This guard has a failure mode it cannot see. It protects one `run`. If the batch job retries a whole conversation after a crash, the dictionary is empty and the email goes again, and so does any send the model re-proposes with one changed word. The durable fix is an idempotency key the email service enforces, derived from the business action (ticket id plus template), not from the model's argument string.

The invariants the hidden tests check: every `tool_use` id appears once in the next user message, in order, with string content and a boolean `is_error`; distinct mutating calls run at most once; tools outside `mutating` run every time, because a read after a write should see the write.

## Follow-ups

- *The send times out after the provider accepted it. Your dictionary says it failed, so the model retries and the customer gets two emails. What do you change, and in which system?*
- *The model's turn includes thinking blocks. Your loop rebuilds the assistant content from text and tool blocks only. What happens on the next request, and what does that tell you about who owns the message history?*
- *You move this loop from a single process to a queue of workers, one turn per job. Where does the duplicate table live, how long does it live, and what happens when it is unavailable?*

## Common mistakes

- Sending tool results without first appending the assistant turn that requested them.
- One user message per result instead of one per assistant turn.
- Keying duplicates on `tool_use_id`, which is new for every proposal and so never matches a repeat.
- Deduplicating reads, which hides the effect of a write the model made in between.
- Treating an exception as proof that nothing happened.
