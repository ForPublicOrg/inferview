## Question

<Callout kind="interview" label="The prompt">
"Your application depends on one LLM provider. How do you switch providers without downtime?" And the variant: "How do you handle model updates and deprecations from providers?"
</Callout>

A customer-support product sends all traffic to one provider's model: a classifier, a tool-using assistant with four tools, and a structured-output extraction job. Leadership wants a second provider, both as a failover during outages and as a migration path when the current model is deprecated. Design it. The constraint the interviewer adds: users must not notice which provider answered.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Swapping the HTTP endpoint is the easy part. What else is provider-specific in a request?</p></details>
<details class="hint"><summary>Hint 2</summary><p>"Users must not notice" is a measurable claim. Against what?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Failover and migration have different triggers and different time scales.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Put one internal interface in front of both providers, with per-provider adapters for messages, tools, structured output and errors, and keep prompts versioned per (feature, model). Qualify the second provider with the same golden sets before it takes any traffic. Use it in two modes: automatic failover on overload or sustained errors, behind a circuit breaker, and planned migration through shadow traffic and a canary. "Users don't notice" means the task metrics on the eval sets stay within an agreed margin.</p>
</Fragment>
<Fragment slot="long">
<p>The interface. A small internal API: send messages and tools, get text, tool calls, a stop reason and normalised usage. Adapters translate each provider's shapes: Claude's tool_use and tool_result blocks against OpenAI's function_call and function_call_output items, different strict-schema subsets (OpenAI wants every field required and allows recursion; Claude rejects recursive schemas and numeric constraints), different stop reasons and error codes, and different auth headers. A gateway such as LiteLLM can do much of this, but you still own the behaviour behind it.</p>
<p>Prompts per model. The same prompt does not behave the same on two models. Keep a prompt version per (feature, model) pair, tuned against that feature's golden set. Schemas should stay inside the intersection both providers support, or have a variant per provider and shared local validation.</p>
<p>Qualification. Run each feature's golden set on the second provider and compare task metrics, format failures, refusals, latency and cost per resolved request. Agree on a margin up front. A provider that fails qualification for one feature can still serve the others.</p>
<p>Failover. Trigger on signals that mean the primary cannot serve: 529 overloads, a run of 5xx errors, or latency far past target. A circuit breaker opens after repeated failures, routes to the secondary for a cooldown, then probes the primary. Do not fail over on a 400 or a spend-cap 429, which point to your own bug or account. Fail over whole conversations, not single turns, because a tool-using conversation's history is in one provider's format and style.</p>
<p>Migration. For a deprecation, the path is slower: shadow traffic to the new model, compare outputs offline, canary a small share behind a flag, widen with automatic rollback. The same machinery serves a model upgrade within one provider.</p>
<p>Costs you accept. Prompt caches are per provider, so failover traffic pays full input price. Two sets of prompts, evals and quotas to maintain. Rate limits on the secondary must be provisioned for failover volume, or the failover itself returns 429s.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The secondary is cheaper. Why not route a share of traffic there all the time?</em> You can, per feature, if it passes qualification, and it keeps the failover path warm. The price is two behaviours in production at once, so slice metrics by provider.</li>
<li><em>A conversation fails over mid-way. What does the secondary see?</em> The history converted by the adapter, including tool calls and results. Test that conversion on recorded conversations, because format mismatches there are silent.</li>
<li><em>How do you know failover works before an outage?</em> Game days that force the breaker open in production for a small share of traffic.</li>
</ul>
</Fragment>
</Depth>

Interviewers grading this question listen for three things. First, that you know the hard part is behavioural, not network plumbing: prompts, schemas, tool formats and refusals all differ between models. Second, that "without users noticing" becomes an eval with a margin, not a hope. Third, that failover and migration are separated: one is an automatic reaction in seconds, the other a reviewed rollout over weeks.

## Follow-ups

- *Which errors trigger failover, and which do not?* Overload and sustained server errors do. Client errors, auth errors and spend caps do not; failing over would hide your own bug.
- *What breaks quietly after a dependency bump?* Transport details. Anthropic's SDK 2.x sends the key as `Authorization: Bearer` rather than `X-Api-Key`, so a gateway that reads only the old header fails.
- *How do you handle a provider that rejects a parameter you rely on?* Feature flags in the adapter, such as no sampling parameters or no forced tool choice for newer Claude models, tested in CI against each provider.

## Common mistakes

- Treating providers as interchangeable endpoints with one prompt.
- Failing over on every error, including your own 400s.
- Never sending traffic to the secondary until the outage, then discovering its rate limits.
- Switching providers mid-conversation without converting the history.
