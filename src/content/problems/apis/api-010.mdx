## Question

<Callout kind="interview" label="The prompt">
"Our scheduling assistant picks the right tool but books meetings at the wrong time for some users. Here are two traces from the same user. Which defect explains the complaint, and what do you fix first?"
</Callout>

The assistant has three tools: `find_free_slots`, `create_event` and `cancel_event`. The definition in question:

```json
{
  "name": "create_event",
  "description": "Create a calendar event for the current user.",
  "input_schema": {
    "type": "object",
    "properties": {
      "title":    {"type": "string"},
      "start":    {"type": "string", "format": "date-time", "description": "Start time in ISO 8601."},
      "duration": {"type": "integer", "description": "Duration of the event."}
    },
    "required": ["title", "start", "duration"],
    "additionalProperties": false
  },
  "strict": true
}
```

The handler parses `start` with `datetime.fromisoformat`, treats a value without an offset as UTC, and stores `duration` as minutes.

**Trace 1, web client, 28 October 2026.** System prompt: "Today is 2026-10-28. You are a scheduling assistant." User: "Book a 30 minute sync with Priya tomorrow at 3pm." Call:

```json
{"title": "Sync with Priya", "start": "2026-10-29T15:00:00Z", "duration": 30}
```

The event appears at 20:30 for the user, who is in Pune (UTC plus 5 hours 30 minutes).

**Trace 2, mobile client, same user, same day.** System prompt: "Today is 2026-10-28. User time zone: Asia/Kolkata (UTC+05:30). You are a scheduling assistant." Same request. Call:

```json
{"title": "Sync with Priya", "start": "2026-10-29T15:00:00+05:30", "duration": 30}
```

The event is correct. Support has eleven complaints and has not recorded which client each came from.

## Answer

The difference between the traces is one line of context. With the zone in the system prompt, the model wrote `+05:30`; without it, the model had no way to know the user's offset and wrote `Z`. The tool definition, the schema and the strict flag are the same in both requests, so none of them can explain why one is right and one is wrong. That makes the web client's prompt assembly the cause.

The evidence is incomplete. Two traces from one user show the mechanism, not its reach. Before shipping a fix I would ask for the client on each complaint and pull a sample of `create_event` calls from web sessions, counting how many have a `Z` or no offset. Without that data I would still ship the context fix, because it is cheap and the traces show it works, and I would add the handler check below, because it turns the next silent guess into a visible error.

The secondary defects, ranked:

1. **The handler accepts a guess.** A `Z` from a user whose profile says Asia/Kolkata is almost certainly wrong. The handler knows the user's zone; it should reject a UTC or offset-free start when the profile zone differs, with an error the model can act on: "start must use the user's offset, +05:30; ask the user if unsure". Strict mode cannot do this, because `date-time` constrains the shape of the string, not which instant it names.
2. **The description does not say where the offset comes from.** "Start time in ISO 8601" is satisfied by a UTC value. "Local start time with the user's UTC offset from the system prompt, for example 2026-10-29T15:00:00+05:30" tells the model what to do and what to ask when the zone is missing.
3. **The duration has no unit.** Both sides read minutes today. The next handler change, or a model that reads "duration" as ISO 8601 `PT30M`, breaks it. Rename it `duration_minutes`.

Why the wrong picks are tempting. The description option names a real weakness, and tightening it is the textbook answer to "wrong arguments", but it cannot explain a difference between two requests that share it. The format option assumes the grammar is the weak point, but the grammar did its job: both strings are valid date-times. The duration option is a genuine defect that has not fired yet.

## Follow-ups

- *The web team says adding the zone to the prompt changes the cached prefix for every web request. Where in the request does the zone go so the cache survives?*
- *Should the model or the handler convert between zones?*
- *How would you turn these two traces into an eval case that would have caught the regression?*

## Common mistakes

- Rewriting the tool description and declaring the bug fixed, without checking what differs between a good and a bad trace.
- Reaching for strict mode or a tighter format, which constrain shape, not meaning.
- Fixing the prompt and leaving a handler that accepts any offset.
- Unit-free parameter names such as `duration`, `amount` or `size`.
