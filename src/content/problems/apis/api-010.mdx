## Question

<Callout kind="interview" label="The prompt">
"Your LLM selects the right tool but extracts the wrong parameters. How do you fix parameter extraction?" Here is the trace.
</Callout>

A scheduling assistant has three tools: `find_free_slots`, `create_event` and `cancel_event`. The system prompt says the user is in Pune and today is 28 October 2026. The definition of the tool in question:

```json
{
  "name": "create_event",
  "description": "Create a calendar event.",
  "input_schema": {
    "type": "object",
    "properties": {
      "title":    {"type": "string"},
      "start":    {"type": "string", "description": "Start time"},
      "duration": {"type": "integer", "description": "Duration"}
    },
    "required": ["title", "start", "duration"]
  }
}
```

The user writes "Book a 30 minute sync with Priya tomorrow at 3pm". The model calls:

```json
{"title": "Sync with Priya", "start": "2026-10-29T15:00:00Z", "duration": 30}
```

The handler stores `start` as given and reads `duration` in hours, the unit its database uses. The event appears at 20:30 in Pune (UTC plus 5 hours 30 minutes) and runs for 30 hours. Pick the root cause.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Is the call valid against the schema? Then the schema is not strict enough to be the whole contract.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Read the two descriptions as if you were the model. What would you assume?</p></details>

## Answer

The tool definition is the bug. To the model, the name, the description and each parameter's description are the only specification it has. "Start time" does not say ISO 8601, does not say which time zone, and does not say an offset is required; "Duration" does not say minutes or hours. The model produced a reasonable, schema-valid reading. The handler had a different one.

The fix is to make the contract explicit in the definition and enforce it in the handler:

- `start`: "Local start time in ISO 8601 with the user's UTC offset, for example 2026-10-29T15:00:00+05:30". Reject values without an offset in the handler and return an error that says what to send.
- Rename `duration` to `duration_minutes`, and say "integer minutes, 5 to 480" in the description. Enforce the range in code, since not every provider's grammar enforces numeric limits.
- Return the created event in the user's local time in the tool result, so the model can confirm "3:00 to 3:30 pm tomorrow" and a mismatch is visible to the user before anyone joins an empty call.
- Add this exchange to the tool-call eval set, scoring argument values, not only the tool name.

Why the wrong picks are tempting. Tool overload is a real cause of wrong tool choice, but the choice was right. Strict mode is the reflex fix for argument problems, yet it only guarantees shape. A missing date is a common bug, but the date here is correct.

## Follow-ups

- *Should the model or the code convert time zones?* The code. Let the model pass what the user said plus the zone it was told, and convert in the handler, where it can be tested.
- *How do you catch this class of bug before users do?* An eval of tool calls that checks argument values against expected ones for a set of phrasings and zones.
- *What if the user's zone is unknown?* The tool should require it, and the model should ask rather than guess.

## Common mistakes

- Turning on strict mode and declaring the problem fixed.
- Fixing the prompt ("always use the user's time zone") while the tool definition stays ambiguous.
- Unit-free parameter names such as `duration`, `amount` or `size`.
- Handlers that accept any string and fail far from the cause.
