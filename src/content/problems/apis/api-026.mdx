## Question

<Callout kind="interview" label="The prompt">
A legal-operations tool reviews inbound vendor contracts against a 25-item playbook (liability cap, indemnity, data processing terms, auto-renewal and so on) and shows the findings to a reviewer who waits for them. Decide between one large prompt and a chain of prompts, and specify exactly what is checked between steps.
</Callout>

Constraints (scenario):

- Contracts run 8,000 to 30,000 tokens. The contract store returns text with section numbers and cannot be changed this year.
- The product budget is a p95 of 60 seconds from upload to findings on screen.
- The legal lead requires every finding to quote the contract clause verbatim, because reviewers have been burned by paraphrases that changed meaning.
- Three engineers own the tool. Model: Claude Sonnet 5.5.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for measured output tokens per second and time to first token on your account at the effort level you would use, including thinking.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which of the legal lead's requirements can a program check without a model?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask how often a playbook item depends on two clauses in different sections, such as a cap defined in one place and carved out in another.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A two-stage chain with a programmatic gate, with the second stage run in parallel. Stage one maps every playbook item to the sections and verbatim quotes that bear on it, as structured output. The gate checks every quote is an exact substring of the contract, every section number exists, and every item is either mapped or marked absent with the sections searched. Stage two assesses each item in a parallel call that sees only its quotes and its playbook rule. The summary is rendered from the structured findings, not written by a third call. Serial output stays close to the single prompt's, and the verbatim requirement becomes a check instead of a hope.</p>
</Fragment>
<Fragment slot="long">
<p><b>The two defensible answers.</b> One large prompt is the simplest thing that could work, which Anthropic's guidance says to try first: one call, one context with every clause visible, one end-to-end eval. Its cost is that extraction and judgment fail together, so a wrong quote or a missed item is only visible end to end, and the verbatim rule is an instruction rather than a check. A chain makes each call an easier task and puts a gate between steps; its cost is more calls, more code for three engineers to own, rate-limit pressure (26 calls per contract), and lost context for items whose meaning spans sections.</p>
<p><b>Latency, with your measurements.</b> Let F be time to first token and r the decode rate you measured, thinking included. Suppose the single prompt writes about 200 tokens per item, 5,000 for 25 items (scenario sizes), plus thinking: latency is about F + (5,000 + thinking) / r. The chain's stage one writes item ids, section numbers and quotes, about 3,000 tokens; stage two's 25 calls run in parallel, each about 300 tokens. Its critical path is about 2F + (3,000 + 300 + thinking in both stages) / r. The chain is not automatically slower: the serial path is output tokens, and parallel sectioning removes most of them. Check both against 60 seconds at p95 with your measured F and r, at the largest contract size, before deciding.</p>
<p><b>The gate.</b> (1) Every quote, after whitespace normalisation, is a substring of the contract text. (2) Every cited section number exists in the store's section index. (3) Every one of the 25 items appears exactly once, mapped or marked absent with the sections searched. (4) The output parses against the schema. On failure, retry stage one once with the gate's error list appended; on a second failure, run the single-prompt path and mark the result unverified in the UI.</p>
<p><b>What you give up.</b> Cross-section reasoning in stage two, since each item sees only its quotes; mitigate by letting stage one map several sections to one item. And simplicity: the team now owns a gate, a retry and a fallback path.</p>
<p><b>Written artefact.</b> A decision memo with rollback triggers: if the gate's second-failure rate or p95 latency stays above the thresholds you set for a full day of traffic, switch the default to the single-prompt path behind a flag while you investigate.</p>
</Fragment>

### Failure mode of the recommended design

The gate checks precision, not recall. A quote that exists in the contract passes; a clause stage one never found produces "absent", and the gate accepts it because "absent with sections searched" is a valid answer. An indemnity cap hidden in an exhibit becomes a confident "no cap found". Measure stage one's recall on a labelled set of contracts, per item, and for items where "absent" is the expensive answer (liability cap, indemnity), run a cheap keyword search over the full text and send disagreements to the reviewer as "check this".

### The quantity you choose

The thresholds in the rollback triggers and the size of the labelled recall set are yours to defend. A recall set has to contain enough contracts where each high-risk item is present in an unusual place; twenty contracts drawn at random will contain few exhibits with caps in them, so stratify by where the clause appears.

## Follow-ups

- *One prompt plus the gate, no chain: is that a valid answer?* Yes. It keeps one call and still enforces the quotes. It loses per-item evals and parallel latency, and a gate failure means rerunning the whole review. Choose it if the measured latency fits and the team cannot own more code.
- *What would fold the chain back?* Stage one and the single prompt showing the same recall per item on the labelled set, with the chain's gate rarely firing; at that point the chain is cost without benefit.
- *The contract is 120,000 tokens. What changes?* Stage one may need to run per section group in parallel, and the gate's item-coverage check becomes a merge step; check the latency arithmetic again with the new output size.

## Common mistakes

- Assuming a chain is always slower, without counting output tokens on the serial path.
- A gate that checks only that the JSON parses.
- Letting a model write the summary, which reintroduces paraphrase after the verbatim gate.
- Ignoring thinking tokens in the latency estimate.
- No defined behaviour when the gate fails twice.
