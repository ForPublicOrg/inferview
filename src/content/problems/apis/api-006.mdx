## Question

<Callout kind="interview" label="The prompt">
"How do you implement structured output from LLMs reliably in production?"
</Callout>

The interviewer adds: "Say we extract invoice fields into a typed table every night, and a malformed row breaks the load. What do you build, and what can still go wrong after you build it?"

## Hints

<details class="hint"><summary>Hint 1</summary><p>There are three levels of enforcement: asking, guaranteed syntax, and guaranteed schema. Which does each provider offer?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Schema-valid is not the same as successful. Think about how a response can end.</p></details>
<details class="hint"><summary>Hint 3</summary><p>A schema type of string says nothing about whether the string is right.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Use schema-constrained decoding where the provider supports it (OpenAI Structured Outputs with <code>strict: true</code>, Claude's <code>output_config.format</code>), because the grammar makes invalid syntax impossible. Then check the stop reason before parsing, since refusals and truncation still happen, validate business rules the schema cannot express, and keep a validate-and-repair loop with an attempt cap for models without constrained decoding. Route anything that fails all of that to a dead-letter queue, not into the table.</p>
</Fragment>
<Fragment slot="long">
<p>Levels. Prompting for JSON guarantees nothing. JSON mode guarantees parseable JSON but not your shape, and on OpenAI it errors unless the word "JSON" is in the context and can emit endless whitespace without an instruction. Constrained decoding compiles the schema into a grammar and masks tokens that would break it, so the output matches the schema.</p>
<p>Schema design. Each provider supports a subset. OpenAI strict mode wants <code>additionalProperties: false</code> and every field in <code>required</code>, with optional fields as a union with null, and a root that is an object rather than <code>anyOf</code>. Claude does not support recursive schemas or numeric and string-length constraints, so <code>minimum</code> and <code>maxLength</code> move to local validation.</p>
<p>What still fails. A refusal comes back with HTTP 200 and may not match the schema. A <code>max_tokens</code> stop truncates the object. An enum can differ only by case. A field can be well-typed and wrong. So the order in code is: check the stop reason or status, parse, validate types, validate business rules, then write.</p>
<p>Fallback. For providers or schemas without constrained decoding: parse, validate, send the errors back as a user turn, retry up to a small cap. Each repair is a full extra call, so the cap is also a cost cap.</p>
<p>Trade-offs. Constrained decoding adds latency on the first request with a new schema while the grammar compiles. Whether forcing a format hurts reasoning is contested: one 2024 paper reported a decline and a re-run by dottxt found structured output matched or beat unstructured. Measure on your task, and give the schema a reasoning field before the answer field if you need one.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The feature also needs citations. Anything to watch?</em> On Claude, citations and <code>output_config.format</code> in one request return a 400. Use two calls or pick one.</li>
<li><em>How do you monitor it?</em> Count refusals, truncations, repair attempts and business-rule failures per thousand calls; alert on changes after a model or schema change.</li>
<li><em>Structured output or tool calling?</em> Structured output when you always want the data back; a tool when the model decides whether to act and your code must run something.</li>
</ul>
</Fragment>
</Depth>

The answer interviewers want has two halves. The first is the mechanism: syntax and schema are solved by constrained decoding, not by prompt wording or retries. The second, which separates senior answers, is the list of failures that survive it (refusal, truncation, case mismatches, valid but wrong values) and the code order that catches them.

## Follow-ups

- *Your schema has 300 enum values and the first request takes much longer. Why?* The provider compiles a grammar per new schema; Claude caches it for 24 hours from last use, and OpenAI documents extra latency on the first request with a new schema.
- *How would you evolve the schema without breaking old consumers?* Additive changes only, a version field, and parallel schemas during migration.
- *Can you stream structured output to the UI?* Yes, with a partial JSON parser that drops incomplete items; never act on a partial object.

## Common mistakes

- Saying "JSON mode" when the requirement is a schema.
- Parsing before checking the stop reason.
- Assuming a schema constraint such as `minimum` is enforced by every provider.
- Unbounded repair loops that double the bill on a bad night.
