## Question

<Callout kind="interview" label="The prompt">
"We extract invoice fields into a typed ledger table every night. The primary model is on a provider with strict schema decoding. The failover is an open-weight model behind our gateway that only offers JSON mode. A malformed row breaks the load. What do you build so both paths write valid rows, and what can still go wrong after you build it?"
</Callout>

The schema has `invoice_id` (pattern `^INV-[0-9]{8}$`), `currency` (enum of 12 codes), `total` (number, not negative), `due_date` (date), `line_items` (array of objects) and `notes` (optional string).

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which keywords in this schema each provider's grammar enforces, and get the answer from the docs, not from the SDK's behaviour.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask how many invoices fail over on a bad night and what a repair call costs relative to the first call.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the load does today with a row that parses, matches the schema and is wrong.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>One contract, two enforcement paths, one validator. The JSON Schema is the source of truth. On the primary, strict decoding makes the shape impossible to get wrong, so the remaining work is the stop reason and business rules. On the failover, JSON mode guarantees only that it parses, so every response goes through the same local validator, and failures get a bounded repair loop of one or two attempts with the validator's errors as a user turn. Both paths end in the same validator and a dead-letter table, never the ledger. What still fails on both: refusals, truncation, values that are valid and wrong, and on the failover a repair that converges on a different wrong answer.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The contract.</strong> Keep one schema and generate both the wire schema and the local validator from it. Strict mode on OpenAI needs every field in <code>required</code>, so <code>notes</code> becomes a union with null, and <code>additionalProperties: false</code> on each object including the line items. If the primary is Claude instead, <code>minimum: 0</code> on <code>total</code> is not enforced by the grammar; the SDK helpers move it into the description and validate locally, which is the same thing the failover path needs anyway.</p>
<p><strong>The order in code.</strong> Stop reason first: a refusal comes back with a 200 on Claude and as a <code>refusal</code> item on OpenAI, and a truncated reply (<code>max_tokens</code>, or <code>status: "incomplete"</code>) can be cut mid object. Then parse. Then validate against the full schema from the JSON text, not from a converted object: Pydantic in strict mode accepts <code>"1987-01-28"</code> for a date when validating JSON, because JSON has no date type, and rejects the same string passed as a Python object. Validate every keyword, including the ones the grammar did not enforce. Then business rules the schema cannot express: line items sum to the total within a rounding tolerance, the due date is after the invoice date, the vendor exists. Then write.</p>
<p><strong>The failover path.</strong> JSON mode guarantees syntax only. OpenAI's version errors unless "JSON" appears in the context and, without an instruction, can produce whitespace until the token limit; the gateway's implementation needs the same check, so the prompt carries the schema and an explicit instruction either way. Validation failures go back as a user turn listing the errors, a form every chat API accepts. The cap is a number to choose: I would pick two repair attempts, because each attempt re-sends the invoice and the conversation, and the second attempt sees the same invoice with only one more error list. A reasonable range is one to three; zero makes every recoverable miss a dead letter, and an uncapped loop turns a bad model night into a bill.</p>
<p><strong>What still goes wrong.</strong> Values that pass every check and are wrong: a currency of USD on a euro invoice, a total read from the subtotal line. Enum casing on Claude, which can capitalise a value differently with no error, so compare case-insensitively. A repair that satisfies the validator by inventing a value, such as a due date the invoice does not contain. And a quieter one: the two paths have different error profiles, so a night spent on the failover produces a ledger with a different mix of wrong values. Tag every row with the path and model that produced it.</p>
</Fragment>

<ul>
<li><em>The failover needs three repair attempts on a third of invoices. Do you raise the cap, switch the failover to a provider with strict decoding, or let the load run late?</em></li>
<li><em>Finance wants the notes field to carry the model's reasoning. What does that do on each provider?</em></li>
<li><em>How do you test that the two paths produce the same rows for the same invoice?</em></li>
</ul>
</Fragment>

The constraint conflict is the load deadline against correctness: every repair attempt is latency on a night when the primary is already down, and every row sent to the dead-letter table is a person's work in the morning.

The recommended design fails in one specific way: the shared validator is only as strong as the schema, and a schema with a free-text `vendor_name` will pass a vendor that does not exist. The fix is not in the model path; it is a lookup in the business-rule step.

## Follow-ups

- *Your schema has 300 enum values for the vendor and the first request each morning is slow. Why, and does it matter for a nightly job?*
- *How would you add a field without breaking rows written by the old schema?*
- *Can the failover use a grammar instead of JSON mode? What do you need from the serving stack to find out?*

## Common mistakes

- Saying "JSON mode" when the requirement is a schema.
- Parsing before checking the stop reason.
- Assuming `minimum` or `maxLength` is enforced because the request accepted the schema.
- One validator per provider, which drift apart.
- A repair loop without a cap, or with a cap and no dead-letter path.
