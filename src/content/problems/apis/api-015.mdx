## Question

<Callout kind="interview" label="The prompt">
One runaway agent session must not cost more than $2. What step limit enforces that, with and without a warm prompt cache?
</Callout>

Scenario numbers. An agent runs on Claude Opus 5.5. Every step is one model call that re-sends the whole context. The first call sends 8,000 tokens (system prompt, tools, task). Each step then adds 3,000 tokens to the context (the model's output plus the tool result). Each call generates 400 output tokens. Prices per million tokens from Anthropic's pricing page on 28 October 2026: $4.00 base input, $5.00 for a 5-minute cache write, $8.00 for a 1-hour cache write, $0.20 for a cache read, $20.00 output.

First work out the step limit with no caching. Then **estimate the largest number of steps that stays at or under $2.00 with automatic prompt caching on**, choosing the cache lifetime (some tools in this agent run for several minutes) and stating your assumption about hits.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Write the input of call k as a function of k before pricing anything.</p></details>
<details class="hint"><summary>Hint 2</summary><p>With caching on, which tokens of call k are read, which are written, and at what price each?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask for the distribution of tool durations: how many exceed five minutes?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Without caching, 15 steps: input grows linearly per call, so total cost grows with the square of the steps, and 16 steps cost $2.08. With a warm 5-minute cache, about 50 steps; with 1-hour writes, 43. The write of each step's new 3,000 tokens, not the reads, is the dominant per-step cost once caching is on.</p>
</Fragment>
<Fragment slot="long">
<p>No cache. Call k (from 0) sends 8,000 + 3,000k tokens. Per call, output costs 400 × $20 / 1,000,000 = $0.008 and input costs $0.032 + $0.012k. Over n calls, cost(n) = 0.04n + 0.006n(n − 1). cost(15) = 0.60 + 1.26 = $1.86; cost(16) = 0.64 + 1.44 = $2.08. The limit is 15.</p>
<p>5-minute cache, every call within the lifetime. Call 0 writes 8,000 tokens at $5 per million: $0.04, plus $0.008 output. Call k ≥ 1 reads the previous call's context, 8,000 + 3,000(k − 1) tokens at $0.20 per million, and writes its 3,000 new tokens at $5 per million ($0.015), plus output. Per call that is $0.0246 + $0.0006(k − 1). With m = n − 1 later calls, cost = 0.048 + 0.0246m + 0.0003m(m − 1). At m = 49: 0.048 + 1.2054 + 0.7056 = $1.959. At m = 50: 0.048 + 1.23 + 0.735 = $2.013. So 50 steps.</p>
<p>1-hour cache, for tools that outlast five minutes. Writes cost $8 per million: call 0 is $0.064 + $0.008, and each later call writes 3,000 tokens for $0.024. Cost = 0.072 + 0.0336m + 0.0003m(m − 1). At m = 42: 0.072 + 1.4112 + 0.5166 = $1.9998. So 43 steps.</p>
<p>The accepted band, 40 to 52, covers either lifetime and a few misses. A miss turns one call's reads into writes: at step 30 that is about 95,000 tokens at $5 per million instead of $0.20, roughly $0.46, which removes several steps from the budget. An answer near 15 forgot the cache; an answer above 60 priced the new tokens as reads instead of writes.</p>
<p>The dominant term changes with caching. Uncached, the growing re-sent context dominates; cached, the flat per-step write of new tokens ($0.015 or $0.024) and the output ($0.008) dominate, and the read term only reaches the 5-minute write term at about step 23. The assumption that flips the answer is the hit rate on slow steps: if a third of the tool calls exceed five minutes on a 5-minute cache, those calls rewrite the whole context and the limit falls toward the uncached figure.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Which limit do you enforce: steps, tokens or dollars?</em> Dollars, computed from the usage fields after every call, with a step cap as a backstop; a step cap alone is wrong as soon as the hit rate changes.</li>
<li><em>The cap fires on 4 percent of sessions and users complain. Do you raise it?</em> Only after sampling those sessions: if most are loops (the same tool call repeated), raising the cap pays for more looping.</li>
<li><em>Which lifetime do you pick?</em> The 1-hour write costs 43 steps instead of 50 when every call hits, but it protects against slow tools; the tool-duration distribution decides it.</li>
</ul>
</Fragment>

## Follow-ups

- *Where does a fifty-dollar session come from?* A loop. Uncached, cost(89) = 3.56 + 0.006 × 89 × 88 = $50.55, so the same agent passes $50 at step 89; cached, it takes far longer, which delays detection rather than preventing the loop.
- *How do you detect a runaway before the cap?* Count identical tool calls per session and alert on spend per session at a high percentile, not the mean.
- *What changes for a reasoning model?* Thinking tokens are billed as output, so the flat output term grows and varies with effort, and changing effort mid-session invalidates the cached messages.

## Common mistakes

- Pricing every step at the first step's input size, a linear model of a quadratic cost.
- Pricing each step's new tokens as cache reads rather than writes.
- Assuming every call hits when some tools outlast the cache lifetime.
- Enforcing the cap in the prompt ("stop after 15 tool calls") instead of in the loop.
