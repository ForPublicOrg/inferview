## Question

<Callout kind="interview" label="The prompt">
"How do you version and manage prompts in production?"
</Callout>

Answer as you would for a team of eight engineers shipping three LLM features on two providers. Cover where prompts live, how a change is tested and released, and how you would know which prompt produced a given output six weeks later.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what you already do for configuration that can break production, and which parts carry over.</p></details>
<details class="hint"><summary>Hint 2</summary><p>A prompt's behaviour depends on the model it runs on. What does that mean for the version you log?</p></details>
<details class="hint"><summary>Hint 3</summary><p>What is the prompt equivalent of a unit test, and of a canary?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Prompts live in the repository as templates with an explicit version, go through code review, and render through one function. Every request logs the prompt version, a hash of the rendered prompt, the model ID and the parameters. A golden set of real cases runs in CI on every prompt or model change, and changes ship behind a flag: shadow traffic, then a canary, then full rollout with rollback on the task metric.</p>
</Fragment>
<Fragment slot="long">
<p>Storage. Templates in the repository, next to the code that calls them, not in a database that anyone can edit without review. A prompt registry or management tool is reasonable once non-engineers edit prompts, but it needs the same properties: immutable versions, review, and an audit trail.</p>
<p>Identity. A version is the pair (prompt version, model ID). The same template on a new model is a new version in practice, because the behaviour changes. Log both with every request, plus a hash of the fully rendered prompt so you can tell a template change from a data change.</p>
<p>Tests. A golden set built from production failures, run in CI: exact-match checks for classification and extraction, graded checks with a calibrated judge for free text. A fast smoke subset on every commit, the full set on model changes.</p>
<p>Release. Shadow mode on copied traffic first, then a percentage canary behind a flag, with automatic rollback on the task metric and on cost per resolved request. Keep the previous version deployable until the new one has run for a full traffic cycle.</p>
<p>Model upgrades. Expect API breakage as well as quality change: on current Claude models, prefill, forced tool choice and sampling parameters can return 400 errors that older prompts or client code relied on.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Product managers want to edit prompts without a deploy. How?</em> A registry with versioned, reviewed entries that the service reads by version, and the same CI eval gate before a version can be promoted.</li>
<li><em>How do you handle per-customer prompt variants?</em> Composition over copies: one base template plus small, versioned fragments, so a fix to the base reaches every variant and each variant is still testable.</li>
<li><em>What does prompt versioning cost you?</em> Review overhead and slower iteration. Keep a playground for exploration; only promoted versions reach production.</li>
</ul>
</Fragment>
</Depth>

What interviewers listen for is the shift from "prompt as text" to "prompt as a deployable artifact with tests". Specific signals: you log the model ID with the prompt version, you test against real failures rather than invented examples, you treat a model upgrade as a release, and you know that a small edit can have side effects beyond output quality. One example is cost: a timestamp or a reordered section near the top of a prompt changes the cached prefix, so a harmless-looking edit can raise the input bill.

## Follow-ups

- *A prompt change improved the eval but users complain. What happened?* The golden set does not represent current traffic. Sample production failures into it and slice metrics by segment.
- *How long do you keep old versions?* As long as you need to explain old outputs, which usually means as long as you keep the logs that reference them.
- *Where do few-shot examples live?* In the same versioned template, or in a versioned example set referenced by id, never sampled at random per request.

## Common mistakes

- Logging the prompt version but not the model ID.
- Copy-pasting prompts across services, so a fix lands in one copy.
- Evaluating on hand-written happy-path examples instead of production failures.
- Treating a model upgrade as a configuration change rather than a release.
