## Question

<Callout kind="interview" label="The prompt">
Eight engineers ship three LLM features on two providers. Product managers edit prompt wording several times a day in a shared dashboard and the edits go live immediately. Last month an edit to the refund prompt raised wrong refund approvals for a week before anyone connected the two. Design how prompts are stored, reviewed, tested and released, and say how you keep product's iteration speed.
</Callout>

The full eval set for the refund prompt is 1,200 cases of about 2,000 input and 300 output tokens each, run on Sonnet 5.5 (scenario sizes, list prices).

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what the request log recorded for the bad week. Could anyone have answered "which prompt produced this approval"?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Price one full eval run and time it; then ask how many edits a day product makes.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which outputs of the refund prompt are expensive when wrong, and how many cases in the eval cover them.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Prompts become versioned artefacts: immutable versions in a registry or the repository, each request logging the prompt version, a hash of the rendered prompt, the model ID and the API version. Product keeps a playground and a draft state; promotion to production requires a passing eval gate. The gate has two tiers: a smoke set on high-cost outputs that runs on every promotion in minutes, and the full set before release to all traffic. Rollout goes through a percentage canary with rollback triggers on the expensive error, here wrong refund approvals.</p>
</Fragment>
<Fragment slot="long">
<p><b>Identity.</b> A deployed prompt is the pair of prompt version and model ID, plus the API version that shapes the request. The same template on a new model behaves differently, so log all three plus a hash of the rendered prompt, which separates template changes from changes in the data inserted into it.</p>
<p><b>Storage and review.</b> Where the prompt lives matters less than three properties: versions are immutable, every promotion has a reviewer, and there is an audit trail. A registry the service reads by version lets product edit without a code deploy and keeps those properties; a repository gives them through code review. Either way, few-shot examples are part of the version, never sampled at request time.</p>
<p><b>The gate.</b> One full eval run costs 1,200 × (2,000 × $2 + 300 × $10) / 1,000,000 = $8.40 at list price, or $4.20 through the Batch API, which suits a release gate but not an edit loop. Cost is not the bottleneck; latency of the loop is. The conflict is fast iteration against a regression gate, and the resolution is tiering: choose a smoke set built from the expensive failure (wrong approvals) and recent production failures, small enough to finish in minutes, and require it for every promotion; run the full set before a version reaches more than the canary share.</p>
<p><b>Rollout.</b> Canary by stable hash on the customer, with rollback triggers on the approval rate and on a sampled audit of approvals, not only on aggregate pass rate. Keep the previous version deployable by flag, which is not possible for a model past its retirement date, so model changes need a different fallback.</p>
<p><b>A side effect to review for.</b> Prompt caching matches an exact prefix in the order tools, system, messages. An edit near the top of the system prompt resets the cache for the whole prompt, so a wording tweak can raise input cost; reviewers should see where in the prompt an edit lands.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How large should the smoke set be?</em> Large enough that a regression on the expensive output is distinguishable from rerun noise. On 200 cases at a 95% pass rate the standard error is about 1.5 points, so a 5-point drop on paired cases is visible; on 30 cases it is not.</li>
<li><em>Product says even a five-minute gate kills their flow.</em> The playground stays instant; only promotion waits. If promotions are many per day, batch them into scheduled promotions with one gate run each.</li>
<li><em>What if the eval passes at 100%?</em> The set is no longer finding anything; add recent production failures until it fails sometimes, or it is a gate in name only.</li>
</ul>
</Fragment>
</Depth>

The quantity the answer must choose is the smoke set's size and composition. Reasonable choices run from about a hundred to a few hundred cases weighted toward the expensive failure; a smoke set drawn uniformly from all traffic contains few refund approvals and will not catch the incident that started this. Thirty hand-written happy-path cases is not a gate.

The failure mode of this design is drift between the smoke set and production: the smoke set is built from last month's failures, product's next edit breaks a slice it never contained, and the gate passes. The control is to feed every confirmed production failure back into the smoke set and to review its composition when traffic changes.

What you give up: product loses instant production edits, and the team takes on owning a registry and an eval set. Both are cheaper than a week of wrong refunds, but the trade has to be written down where product agreed to it.

## Follow-ups

- *The two providers need different wording for the same feature. One version or two?* One version id with provider-scoped sections, evaluated per provider, so a policy change is reviewed once and tested twice.
- *How long do you keep old versions?* As long as you keep logs that reference them, since explaining an old output needs the exact prompt.
- *Who approves a promotion when product and engineering disagree on a regression?* The owner of the expensive outcome, here whoever owns refund losses, with the measured flip counts in front of them.

## Common mistakes

- Logging the prompt version without the model ID or the rendered prompt hash.
- One gate for every edit at full-set cost and latency, which product routes around within a week.
- A smoke set sampled uniformly from traffic, so the rare expensive output is barely in it.
- Rollback plans that assume the previous model will still exist.
