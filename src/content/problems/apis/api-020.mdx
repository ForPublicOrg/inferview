## Question

<Callout kind="interview" label="Design, 45 minutes">
Scenario: thirty product teams call model providers today, each with its own wrapper around the provider SDKs. All traffic already goes through a LiteLLM gateway that the infrastructure group runs and will not rewrite this year. You lead a platform team of three with one quarter to ship a shared client library. Design its defaults for timeouts, retries, failover, idempotency and telemetry, say which ones a team may override and how, and write the one-page decision record you would circulate.
</Callout>

What you have: the gateway's settings for fallbacks, retries, cooldowns and timeouts; the provider SDKs; per-team API keys mapped to workspaces. What you do not have: any agreement among the thirty teams about which of them owns a retry.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the infrastructure group what the gateway retries today and whether that can be set per route.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask three teams for one incident each where their wrapper made things worse, and what it did.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the distribution of time to first token and total time per route for the last month.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The library is thin and opinionated: it owns error classification, deadlines, idempotency keys and telemetry; the gateway owns retries and failover. The library sets SDK <code>max_retries=0</code>, propagates a deadline and an idempotency key to the gateway, never retries spend caps or 4xx, and records stop reasons and refusals as first-class metrics. Teams may override timeouts and the route's failover eligibility through reviewed config, never the retry layer.</p>
</Fragment>
<Fragment slot="long">
<p>The first decision is where the single retry layer lives, and both answers are defensible. Gateway retries: one place sees all thirty teams' traffic, can hold a global retry budget and a breaker, and is already deployed; the cost is that the gateway does not know deadlines or side effects unless the library sends them. Library retries: the code that knows the deadline and the side effects decides; the cost is a per-process budget, and thirty teams on thirty library versions during an incident. With a fixed gateway and three engineers, I put retries in the gateway and make the library send what the gateway lacks.</p>
<p>Defaults, each with its override rule:</p>
<ul>
<li><b>Timeouts.</b> First-byte timeout per route from that route's time-to-first-token distribution, at an acceptable false-timeout rate written in config; a total timeout per route from its output-length distribution. Overridable per route in reviewed config, because the library cannot know a route's answer length.</li>
<li><b>Retries.</b> SDK <code>max_retries=0</code>, always. The gateway retries rate-limit 429s with <code>retry-after</code>, 529s and 5xx within a budget. Not overridable per team; a team that needs a different budget asks for a route class.</li>
<li><b>Never retried.</b> Spend-cap 429s (no <code>retry-after</code>, <code>enforced_spend_limit_reached</code>), 400s, auth errors, 504s. Not overridable.</li>
<li><b>Failover.</b> Off by default. A route becomes eligible when its owner registers an eval result for the fallback; the gateway's fallback list is generated from that registry. Overridable only by passing the gate.</li>
<li><b>Idempotency.</b> The library derives a key from the conversation and the tool-use id and passes it to tools; tools with side effects must check it. A tool registered without a key handler cannot be retried by anything.</li>
<li><b>Telemetry.</b> Per call: route, model that served it, stop reason, time to first token, total time, counted input, cache reads, output, retries spent, request id. Refusals and <code>max_tokens</code> stops as counters, because they are HTTP 200s and invisible to error-rate dashboards. Not overridable; teams may add fields.</li>
</ul>
<p>What you give up: teams lose the ability to tune retries for their own path, and a few with genuinely different needs, such as a batch team that would rather wait minutes, will route around the library unless the route classes cover them. Global budgets also mean one team's misclassification can spend another's retries; the gateway accounts budgets per team to contain that.</p>
<p>Failure mode of this design: everything depends on the deadline and idempotency headers reaching the gateway intact. A team on an old library version, or a proxy that strips unknown headers, silently falls back to retries without deadlines. The gateway must treat a missing deadline header as "do not retry beyond one attempt", which makes the failure loud instead of silent.</p>
</Fragment>

<ul>
<li>The infrastructure group says per-route retry config in the gateway is not possible this quarter. What ships instead, and what do you accept in writing?</li>
<li>Two senior engineers disagree: one wants retries in the library for deadline awareness, one wants them in the gateway for a global budget. How do you decide without deciding by rank?</li>
<li>What adoption number after one quarter would make you stop and rethink the design rather than push harder?</li>
</ul>
</Fragment>
</Depth>

The decision record, as circulated:

> **Decision.** One retry layer, in the gateway. The shared library sets provider SDK retries to zero and sends a deadline and an idempotency key with every call.
> **Context.** Thirty teams' wrappers retry independently; the gateway also retries; incidents multiply load. The gateway cannot be rewritten this year.
> **Defaults and overrides.** As listed above: timeouts per route by reviewed config; retries and never-retry classes fixed; failover off until a route's eval passes; telemetry fields fixed, extensible.
> **What we give up.** Per-team retry tuning. Teams whose needs the route classes miss may bypass the library; we track bypass by API key.
> **Risks.** Header loss between library and gateway; mitigated by treating a missing deadline as a single attempt. Shared budget abuse; mitigated by per-team accounting.
> **Rollout.** Three pilot teams with the most incident history first; then teams by traffic. Rollback trigger: a pilot route's error rate or p99 total time worse than its pre-migration baseline for a full day.
> **Revisit when.** Per-route gateway config becomes available, or library adoption stalls below the share of traffic we set as the quarter's goal.

## Follow-ups

- *Pushback:* the largest team refuses `max_retries=0` because their wrapper's retries "work". What evidence do you bring, and what do you concede?
- *Reversal:* what would you need to see in six months of gateway retry and breaker data to move retries into the library?
- *Operating:* a provider retires the model behind a third of your routes in sixty days, and the replacement fails four routes' evals. Which ship degraded, which stay on the old model until retirement, and who signs each?

## Common mistakes

- A library that retries, under a gateway that retries, over an SDK that retries.
- One timeout for every route.
- Failover on by default, with no eval gate.
- Telemetry that counts HTTP errors and misses refusals and truncations.
- Overrides by environment variable, which nobody reviews.
