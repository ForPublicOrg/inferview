## Question

<Callout kind="interview" label="The prompt">
"Three products want a calendar agent: the email client schedules from threads, the CRM books customer meetings, and the HR tool schedules interviews. Design the tool interface they share, and tell me how you change a tool next quarter without breaking anyone's cached prompts or open conversations."
</Callout>

The operating constraints, all scenario:

- A platform team of four owns the calendar backend and would own the tools. The CRM launches in six weeks and is the first customer.
- The email client runs on one provider's API and the CRM and HR tool on another's; both sides use prompt caching and strict tool schemas.
- The HR lead wants the interview agent to see free/busy for anyone in the company. Security wants each agent limited to calendars its user can already see.
- Conversations in the email client last up to a day; CRM and HR sessions last minutes.

Produce the tool list with signatures, the versioning rule, and a decision memo with a rollout plan.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask each product for its top five scheduling requests from logs or user research, and which of them chain more than two backend calls.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for each product's request rate per prompt prefix, and how often traffic on a prefix pauses for more than five minutes.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Five tools in one namespace, consolidated around tasks rather than endpoints: find slots, schedule, reschedule, cancel, and get event, with identity, permissions and product policy taken from the session in the executor, never from arguments. Tool definitions vary by product and version, never by user or tenant, because the definitions sit at the front of the cached prefix and per-user variants fragment it. Tools are versioned as a set; a conversation is pinned to the toolset version it started on, and the executor supports the current and previous version for the longest conversation lifetime plus a margin. The cost is a backend that speaks two dialects at once and a deprecation process the four of us must run.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The tools.</strong> <code>calendar_find_slots(attendee_ids, duration_minutes, window_start, window_end, time_zone)</code>, <code>calendar_schedule(title, attendee_ids, start, duration_minutes, time_zone, idempotency_hint)</code>, <code>calendar_reschedule(event_id, start, duration_minutes)</code>, <code>calendar_cancel(event_id, notify)</code>, <code>calendar_get_event(event_id, response_format)</code>. Schedule does the availability check itself, following Anthropic's advice to consolidate the list-then-create chain into one tool, so the model makes one call where it would make three. Times carry an explicit offset and a zone name; durations carry their unit in the name. Results return attendee names alongside ids and support a concise format, because a calendar listing is where tool output grows.</p>
<p><strong>Policy from the session.</strong> The executor knows the product, the user and their permissions. Free/busy is filtered to calendars the user can already see; the HR tool's request for company-wide visibility becomes a product decision about the HR user's permissions in the calendar system, not a tool parameter the model can set. Interview scheduling in HR may need an extra rule (no event titles visible to candidates); that also lives in the executor keyed on product.</p>
<p><strong>Cache-safe definitions.</strong> The cached prefix is tools, then system, then messages. Changing a tool definition invalidates all three levels; changing <code>tool_choice</code> invalidates only the messages. Per-product definitions cost nothing extra, because each product already has its own system prompt and therefore its own prefix. Per-user definitions (a description that names the user's time zone or calendars) create a prefix per user, and a prefix that sees one request every few minutes never gets a read. User facts go into the conversation after the last breakpoint.</p>
<p><strong>Versioning.</strong> A toolset version is a frozen set of definitions. New conversations get the current version; an open conversation keeps its version to the end, because a definition change mid-conversation rewrites the whole cached history. On Claude Opus 5.5 a cached read is 0.05 times the base input price and a 5-minute write 1.25 times, so the request after a mid-conversation change pays 1.25 / 0.05 = 25 times the input cost for the cached part. Changes inside a version are forbidden; between versions, a parameter's meaning never changes under the same name, and a new behaviour gets a new parameter or a new tool. The executor maps the previous version's calls onto the current backend.</p>
<p><strong>Provider differences.</strong> On the OpenAI side, <code>allowed_tools</code> restricts a product or a conversation phase to a subset while the tool list stays constant, which keeps the prefix. On the Claude side, forced tool choice returns a 400 on the current models, and a subset means a different tool list, so subsets are per product (free) and never per turn. Strict schemas on Claude cap optional and union-typed parameters per request (24 and 16 across strict schemas), which pushes towards required fields with explicit nulls and few tools marked strict.</p>
</Fragment>

### The two defensible answers

**Shared toolset, versioned together.** One contract, one eval set, one executor dialect per version. A change one product needs ships to all three, which is a regression risk for the two that did not ask for it, and every release needs three sign-offs. This wins while the products' needs overlap and the platform team is small.

**Per-product definitions over a shared backend.** Each product writes its own descriptions and ships on its own cadence. The descriptions drift, three evals must be kept, and the executor accepts three dialects, but no product waits on another. This wins when the products' scheduling tasks differ enough that one description serves none of them well, which the hint 1 data would show.

I would start with the shared toolset because the team is four people and the first customer launches in six weeks, and I would write down the condition for splitting: when one product's eval regresses on a change another product needs.

### The numbers you choose

**Support window.** The executor must accept the previous version for at least the longest conversation lifetime, which is a day in the email client. I would choose seven days, which covers the day plus a deploy freeze over a weekend; anything from two days to two weeks is reasonable, and less than the conversation lifetime is not, because it breaks open conversations.

**Cache lifetime.** Reads refresh either lifetime at no cost, so the difference is what a pause costs. A pause longer than five minutes and shorter than an hour makes the 5-minute cache rewrite the prefix at 1.25 times base input and costs the 1-hour cache nothing. The 1-hour cache instead pays 2 - 1.25 = 0.75 times base input more on each write. One such pause per write already costs the 5-minute cache 1.25 against 0.75, so the 1-hour cache wins for any prefix that pauses for five to sixty minutes at least once between full expiries. The per-prefix traffic from hint 2 decides it per product; a CRM prefix that never pauses for five minutes gains nothing from the longer lifetime.

### What you give up

A shared toolset means no product gets a tool shaped exactly for its task, and versioning means the platform team carries two versions of every handler for a week after each release. The CRM gets fewer features at launch than it asked for, because every feature becomes a contract.

### Failure mode of this design

Version pinning keeps a day-long email conversation on an old toolset after a bug fix in the new one. If the fix is in a description (the model was misled), the pinned conversation keeps making the mistake until it ends. The mitigation is an executor-side guard for the bug that applies to both versions, and the rule that urgent fixes go into the executor, not the definitions.

### Decision memo and rollout plan

- **Decision.** Shared `calendar_*` toolset, versioned as a set, conversations pinned to their starting version, executor supports current and previous version for seven days. Identity and visibility from the session.
- **Rejected.** Per-product definitions (revisit when the split condition fires); per-user definitions (fragment the cache).
- **Rollout of each version.** Ship to the CRM's internal users, compare the held-out eval's tool-call error rate and argument accuracy against the previous version, then the other products in turn.
- **Rollback triggers.** The new version's tool-error rate or argument-mismatch rate on the eval set is worse than the previous version's beyond the eval's noise; cache read share on any product drops after the release; any call reads a calendar the user cannot see.
- **Owner.** The platform team owns the toolset and the executor; each product owns its system prompt and its eval cases.

The constraint conflict is speed for the CRM against safety for everyone: every capability the CRM gets in six weeks becomes a contract the email client and HR tool inherit.

## Common mistakes

- One tool per backend endpoint, so the model chains list, check and create, and fails between them.
- Passing user id or permissions as arguments the model fills in.
- Putting user-specific facts in tool descriptions, which gives every user a separate cache prefix.
- Editing a definition in place and calling it a patch release.
- Versioning each tool separately, so a conversation can see an inconsistent mix.
