## Question

<Callout kind="interview" label="The prompt">
Five pull requests touch the prompt builder of a support assistant. Which one leaves the next turn of an existing conversation reading its earlier prefix from cache?
</Callout>

The assistant runs on Claude Opus 5.5 with automatic caching. Each request sends 12 tool definitions, a 4,000-token system prompt, a tenant handbook and the conversation so far. Turns in a conversation arrive about a minute apart.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each pull request, render two consecutive requests and ask where the first differing byte is.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask whether the builder runs in one process or many.</p></details>

## Answer

Appending to the end is the only change that keeps the earlier sequence identical. With automatic caching, the breakpoint sits on the last block and moves forward each turn; the new request's lookback from that breakpoint reaches the entry the previous request wrote, because the previous request is an exact prefix of this one. On Opus 5.5 those tokens are billed at $0.20 per million instead of $4.00.

Each wrong option is a change that has shipped in real codebases because the answers do not change and only the bill does:

- A timestamp at the top of the system prompt caps the cacheable prefix at the end of the tool definitions. It is tempting because the model needs the date; the date belongs at day granularity, or in the newest message.
- A set's iteration order is not guaranteed across processes, so one fleet sends several orderings of the same tools. It is tempting because the tools are "the same", and on a single development machine the order is usually stable, so the miss never shows up locally.
- An effort change looks like a request parameter rather than prompt content, and on Claude it invalidates the messages level. Escalating effort for hard questions is reasonable; doing it mid-conversation costs a rewrite of the whole history.
- Moving the 1-hour handbook after the 5-minute conversation looks like a harmless reordering for a product that wants the newest context near the top. Claude requires longer-lifetime entries before shorter ones, so the layout cannot keep the handbook cached as intended, and every new turn now lands before the handbook.

Claude's `input_tokens` field alone will not show any of these regressions; total input is `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and the read share of that total is the metric to alert on.

## Follow-ups

- *The model really does need the time of day. Where does it go, and what does it cost?* In the newest user message, where it changes nothing before it; at day granularity in the system prompt it costs one rewrite a day per tenant.
- *How do you catch a regression like the set-ordered tools before production?* A CI test that renders the same request in two processes with different hash seeds and compares bytes up to the last breakpoint.
- *What else invalidates the messages level on Claude?* Changing `tool_choice`, and adding or removing an image anywhere in the prompt.

## Common mistakes

- Thinking the cache is keyed on meaning rather than exact bytes.
- Testing cache behaviour in one process and shipping to many.
- Treating request parameters such as effort as outside the cache key.
- Measuring cache health with `input_tokens` alone.
