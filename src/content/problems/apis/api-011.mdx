## Question

<Callout kind="interview" label="The prompt">
"How does prompt caching work?" Show it by predicting which change preserves the cache.
</Callout>

A support assistant runs on Claude Opus 5.5 with prompt caching. Each request sends 12 tool definitions, a 4,000-token system prompt and the conversation so far, with a cache breakpoint on the last message. Traffic is steady, so the cache never expires between turns.

Four pull requests are open. Which one leaves the cached prefix intact on the next turn of an existing conversation?

## Hints

<details class="hint"><summary>Hint 1</summary><p>The cache matches an exact prefix assembled as tools, then system, then messages.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For each change, find the first token that differs from the previous request.</p></details>

## Answer

Appending to the end is the only change that keeps the earlier sequence identical. The prompt cache reuses the longest exact prefix it has seen; on Claude that prefix is the tools, then the system prompt, then the messages in order. A conversation that grows at its end shares everything up to the new turn with the previous request.

The other three each change something early:

- A timestamp at the top of the system prompt differs on every request, so the match ends right after the tools. On Opus 5.5 everything after that point costs $4.00 per million tokens instead of $0.20, twenty times more.
- Tool definitions are the very start of the prefix, and a set has no guaranteed iteration order across processes. Two servers can send the same tools in different orders and never share a cache.
- Effort and thinking settings are part of what the cached messages depend on; Claude's docs list a change to them as invalidating the messages cache.

Each of these is easy to ship by accident because the model's answers do not change. The bill does, and Claude's `input_tokens` field alone will not show it: total input is the sum of `cache_read_input_tokens`, `cache_creation_input_tokens` and `input_tokens`.

## Follow-ups

- *The model really does need the date. Where does it go?* At the end, next to the new user message, or at day granularity in the system prompt so it changes once a day.
- *How do you catch a cache regression in CI?* Render the prompt for two consecutive requests and assert the prefix up to the last breakpoint is byte-identical.
- *What else invalidates the cache on Claude?* Toggling web search or citations, changing `tool_choice`, adding images, and changing the structured-output format.

## Common mistakes

- Thinking the cache is keyed on meaning rather than exact tokens.
- Serialising tools or JSON with non-deterministic key or list order.
- Measuring cache health with `input_tokens` alone.
