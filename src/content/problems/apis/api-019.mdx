## Question

<Callout kind="interview" label="Estimate, 25 minutes">
Two kinds of tenant share one organisation's Claude Sonnet 5.5 limits. Estimate the request rate the organisation can admit at the planned mix, size a per-tenant input and output bucket, and say which change in the tenant mix breaks the plan first.
</Callout>

Published inputs (Claude rate-limits page, checked 2026-10-28): Build tier, Claude Sonnet 5.5, 5,000 requests per minute, 5,000,000 input tokens per minute (ITPM), 1,000,000 output tokens per minute (OTPM). On this model, uncached input and cache writes count toward ITPM; cache reads do not. OTPM counts tokens actually generated.

Scenario inputs, measured by your team last month:

| Tenant class | Share of requests | Input tokens per request | Measured share of input read from cache | Output tokens per request |
|---|---|---|---|---|
| Chat (shared system prompt and tools) | 80 percent | 12,000 | 75 percent | 400 |
| Document Q&A (customer uploads) | 20 percent | 60,000 | 30 percent | 800 |

You choose the headroom to keep below the provider's limits, and defend it. Give the sustainable requests per minute for the whole organisation.

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each tenant class, ask how many of its input tokens the provider actually counts.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Compute the ceiling from each of the three limits separately before choosing one.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what happened to the cache hit rate the last time the chat system prompt changed.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Counted input per average request is 10,800 tokens, so ITPM allows about 463 requests per minute; OTPM allows about 2,083 and RPM 5,000. Input binds, and document Q&A is 78 percent of it. With 10 to 30 percent headroom, admit roughly 320 to 420 requests per minute. A chat prompt change that empties the cache cuts the ceiling to about 278.</p>
</Fragment>
<Fragment slot="long">
<p>Counted input. Chat reads 75 percent of 12,000 from cache, so 3,000 tokens count. Document Q&A reads 30 percent of 60,000, so 42,000 count. At the 80/20 mix: 0.8 × 3,000 + 0.2 × 42,000 = 2,400 + 8,400 = 10,800 counted input tokens per average request.</p>
<p>Ceilings. ITPM: 5,000,000 / 10,800 ≈ 463 requests per minute. OTPM: average output 0.8 × 400 + 0.2 × 800 = 480, so 1,000,000 / 480 ≈ 2,083. RPM: 5,000. Input binds by a factor of more than four; the dominant term is document Q&A's uncached input, 8,400 of the 10,800.</p>
<p>Headroom. The docs say limits can be enforced over intervals shorter than a minute, so bursts within the minute are rejected before the minute's average is reached, and retries consume the same bucket. Keeping 10 to 30 percent below the ceiling gives 463 × 0.9 ≈ 417 down to 463 × 0.7 ≈ 324 requests per minute. The accepted band is 300 to 440.</p>
<p>Per-tenant buckets at 20 percent headroom, 4,000,000 usable ITPM: chat's share of counted input is 2,400 / 10,800, about 22 percent, so roughly 890,000 ITPM; document Q&A gets roughly 3,110,000. Output buckets split the same way are far from binding: chat 0.8 × 400 = 320 of 480 average output tokens, two thirds of the usable OTPM.</p>
</Fragment>
</Depth>

**What breaks the plan.** Two changes, each computed:

- *The chat cache empties.* A system-prompt or tool-list change invalidates the cached prefix; until it warms, all 12,000 chat tokens count. 0.8 × 12,000 + 8,400 = 18,000 counted tokens, a ceiling of about 278 requests per minute, 40 percent below plan, with no change in traffic. This is the assumption that flips the conclusion, and it happens on every prompt deploy.
- *Document Q&A grows.* At a 60/40 mix: 0.6 × 3,000 + 0.4 × 42,000 = 18,600, about 269 requests per minute.

Output binds only for a tenant whose output exceeds a fifth of its counted input, the ratio of OTPM to ITPM. Chat at 400 output against 3,000 counted input is under that; a chat tenant with a cold cache is further under it.

**Unreasonable choices.** Counting cache reads toward ITPM, as on Claude Haiku 3.5 or under a combined TPM model, gives 0.8 × 12,000 + 0.2 × 60,000 = 21,600 tokens and about 231 requests per minute: wrong for this model by a factor of two. Zero headroom ignores sub-minute enforcement and retries. Sizing from output tokens alone, the instinct from providers that reserve `max_tokens`, gives 2,083 and overcommits more than fourfold.

**The decision: static buckets or a shared pool.** Static per-tenant buckets, enforced as workspace limits or in your gateway, isolate tenants: a document upload spike cannot starve chat. The cost is stranded capacity whenever one class is quiet. A shared pool with weighted fair queuing and borrowing uses the whole limit; the cost is that a noisy tenant can push others into latency, and fairness logic you now own. The constraint conflict is isolation against utilisation, and the measured cache hit rate is the input both depend on.

Failure mode of static buckets sized this way: they are sized on last month's hit rate. When a chat prompt deploy empties the cache, chat's counted input quadruples (3,000 to 12,000 tokens per request) inside a bucket sized for 3,000, and chat, the latency-sensitive tenant, is the one rejected. Size chat's bucket for the cold-cache case or exempt the first minutes after a prompt deploy, and write down which.

## Follow-ups

- *Pushback:* sizing chat for a cold cache strands about three quarters of its bucket on every warm day. Which do you give up, utilisation on warm days or chat availability after deploys, and who signs?
- *Reversal:* what would a month of per-tenant counted-input data need to show for you to replace static buckets with a shared pool?
- *Operating:* the provider moves Sonnet 5.5 to a combined bucket with another model your batch jobs use. What changes in this plan, and what do you measure first?

## Common mistakes

- Counting total input tokens instead of counted input.
- Taking one cache hit rate for the whole organisation instead of per tenant class.
- Treating the per-minute limit as a per-minute average that bursts may borrow against.
- Forgetting that a prompt deploy changes the cache hit rate.
