## Question

<Callout kind="interview" label="Multiple choice">
Your service calls the Claude Messages API and gets this response. What should the client do?
</Callout>

```text
HTTP/1.1 429 Too Many Requests
content-type: application/json
request-id: req_018EeWyXxfu5pfWkrYcMdjWG

{
  "type": "error",
  "error": {
    "type": "rate_limit_error",
    "message": "You have reached your API usage limits: your organization has crossed its monthly API usage threshold, set based on your organization's API tier. You will regain access on 2026-11-01 at 00:00 UTC.",
    "details": { "error_code": "enforced_spend_limit_reached" }
  },
  "request_id": "req_018EeWyXxfu5pfWkrYcMdjWG"
}
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which response headers would you expect on a 429 that clears by waiting, and which are here?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask whether this limit is scoped to a model or to the organisation.</p></details>

## Answer

The error type is the same `rate_limit_error` a rate limit returns, which is the trap. The response has no `retry-after` header, and `error.details.error_code` is `enforced_spend_limit_reached`: the organisation has reached its tier's monthly spend cap. Claude's docs say usage pauses until 00:00 UTC on the first day of the next month unless the organisation moves to a higher tier, and that retrying, including the SDK's automatic retries, fails until access resumes. The client's job is to stop generating load, tell a person who can raise the tier or approve other spend, and keep the product honest in the meantime.

Why the wrong options are tempting. Backoff with jitter when the header is missing is OpenAI's documented advice for transient errors, and engineers who wrote clients against that guide carry it over; the same guide also says not to retry quota or billing errors. Failing over to another model works for rate limits, which Claude enforces per model class, but the spend cap belongs to the organisation. A one-minute retry assumes the continuous refill of the rate-limit token buckets, which has nothing to do with a monthly cap.

A neighbouring case: a spend limit your organisation set below the tier cap returns 400 `invalid_request_error`, not 429, with a message starting "You have reached your specified API usage limits". A classifier that pages the API owners for every 400 sends that one to the wrong team.

## Follow-ups

- The SDK retries rate-limit errors by default. How do you keep it from retrying this one without turning its retries off for real rate limits?
- Which metric tells you three days before the cap is reached, and who gets that alert?
- Finance wants a second provider as the fallback for a spend cap. What has to be true about that provider's evals and budget first?

## Common mistakes

- Branching on the status code or error type alone.
- Letting SDK retries and a wrapper loop both retry a response that cannot succeed.
- Failing over to a sibling model in the same organisation.
- Alerting the API owners instead of the person who owns the budget.
