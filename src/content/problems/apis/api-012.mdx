## Question

<Callout kind="interview" label="The prompt">
"How do you estimate the cost of running an AI-powered feature in production?" Then do it, with and without caching.
</Callout>

Scenario numbers. A contract-review feature on Claude Opus 5.5 handles 20,000 requests a day, spread evenly through the day. Every request sends the same 50,000-token prefix (instructions plus a policy handbook), then 500 tokens unique to the request, and gets back 300 output tokens.

Prices per million tokens, from Anthropic's pricing page on 28 October 2026: $4.00 base input, $5.00 for a 5-minute cache write, $0.20 for a cache read, $20.00 output.

**Estimate the daily bill with prompt caching on the 50,000-token prefix**, assuming steady traffic keeps the cache warm all day. Then compare it with the bill without caching.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Split each request into three parts priced differently: the shared prefix, the unique tail, the output.</p></details>
<details class="hint"><summary>Hint 2</summary><p>20,000 requests a day is about 14 a minute. How often does the 5-minute cache need rewriting if every read refreshes it?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Caching changes only the price of the prefix. The tail and the output cost the same either way.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>About $360 a day with caching against $4,160 without, roughly an eleventh of the cost. The prefix drops from $4.00 to $0.20 per million tokens; the tail and output do not change, and with traffic every few seconds the cache is written once and then only read.</p>
</Fragment>
<Fragment slot="long">
<p>Without caching. Input: 20,000 × 50,500 = 1,010,000,000 tokens × $4.00 per million = $4,040. Output: 20,000 × 300 = 6,000,000 tokens × $20.00 per million = $120. Total $4,160 a day.</p>
<p>With caching. Prefix reads: 20,000 × 50,000 = 1,000,000,000 tokens × $0.20 per million = $200. One cache write at the start of the day: 50,000 × $5.00 per million = $0.25. Tail: 20,000 × 500 = 10,000,000 tokens × $4.00 per million = $40. Output unchanged at $120. Total $360.25 a day.</p>
<p>So input falls from $4,040 to $240.25, and output becomes a third of the bill. Over 30 days that is about $10,800 against $124,800.</p>
<p>Check the assumptions. 20,000 requests over 1,440 minutes is about 14 a minute, so a 5-minute lifetime refreshed on every read never lapses; at 20 requests a day it would lapse between almost every pair, and each request would pay the write price instead. The 50,000-token prefix is well above Opus 5.5's 512-token minimum. Cache hits are not guaranteed, so a realistic plan assumes a hit rate below 100% and measures it.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What is the next lever after caching?</em> Output, now a third of the bill: cap answer length, or route easy contracts to a cheaper model.</li>
<li><em>Could the batch API help?</em> For reviews that can wait, the Claude Batch API charges 50% of standard prices and the discounts stack with caching, though cache hits inside batches are best effort.</li>
<li><em>What breaks this estimate?</em> A prompt change that moves anything request-specific above the handbook, which turns every read into a full-price input.</li>
</ul>
</Fragment>
</Depth>

The accepted band is $320 to $400 a day. Answers near $4,160 forgot the cache; answers near $240 forgot the output tokens, which caching does not touch.

## Follow-ups

- *Traffic is 2,000 requests a day, all within an eight-hour working day. Does caching still pay?* That is 250 an hour, so roughly 4 a minute: the 5-minute cache stays warm while people work. Overnight it lapses, and the first morning request pays one write.
- *How would you present this to finance?* Cost per completed review, with the cache-read share as the metric that explains changes.
- *What happens if the handbook changes every hour?* One extra write per change: 24 writes a day at $0.25 each, which is noise next to $360.

## Common mistakes

- Applying the cache discount to the whole request, tail and output included.
- Ignoring the write premium entirely, or charging it on every request.
- Forgetting that a cache lifetime only matters relative to the gap between requests.
- Quoting "caching saves 90%" without naming the model: Opus 5.5 reads at 0.05x base input, not 0.1x.
