## Question

<Callout kind="interview" label="The prompt">
Estimate what prompt caching saves per day on this feature, and say how you would cache the tenants who barely use it.
</Callout>

Scenario numbers. A contract-review assistant on Claude Opus 5.5 serves 400 tenants. Every request sends a 30,000-token tenant prefix (instructions plus that tenant's policy handbook), then 1,000 tokens unique to the request, and gets 400 output tokens back.

- 40 busy tenants send 600 requests each per day, spread evenly over a 10-hour working day.
- 360 idle tenants send 6 requests each per day. When those requests arrive is not known; nobody has looked.

Prices per million tokens from Anthropic's pricing page, read on 28 October 2026: $4.00 base input, $5.00 for a 5-minute cache write, $8.00 for a 1-hour cache write, $0.20 for a cache read, $20.00 output.

**Estimate the daily saving on input cost from caching the tenant prefix, against sending everything uncached.** Choose a policy for the idle tenants (5-minute cache, 1-hour cache, or no cache) and an assumption about when their requests arrive, and state both.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which parts of each request does caching change the price of, and which does it leave alone?</p></details>
<details class="hint"><summary>Hint 2</summary><p>For a busy tenant, how long is the gap between consecutive requests, compared with the cache lifetime?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask for the timestamps of a week of idle-tenant requests before choosing their policy.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>About $2,470 to $2,890 a day, depending on the idle-tenant policy. Almost all of it comes from the busy tenants, whose prefix reads save $2,730 a day. For idle tenants caching can cost more than it saves: with a 5-minute lifetime and gaps longer than five minutes, every request pays the write price, 1.25 times an uncached send.</p>
</Fragment>
<Fragment slot="long">
<p>Only the 30,000-token prefix changes price. The 1,000-token tail and the 400 output tokens cost the same either way, so they drop out of the saving (they matter for the percentage, below).</p>
<p>Uncached prefix. Busy: 40 × 600 × 30,000 = 720,000,000 tokens × $4 per million = $2,880. Idle: 360 × 6 × 30,000 = 64,800,000 tokens × $4 per million = $259.20. Total $3,139.20 a day.</p>
<p>Busy tenants, cached. 600 requests over 600 minutes is one a minute, far inside a 5-minute lifetime refreshed on each read, so each tenant writes once a day and reads 599 times. Per tenant: 30,000 × $5 per million = $0.15, plus 599 × 30,000 × $0.20 per million = $3.594, total $3.744. For 40 tenants, $149.76.</p>
<p>Idle tenants, four reasonable choices:</p>
<ul>
<li>No cache: $259.20, the same as uncached. Total cached cost $408.96, saving $2,730.24.</li>
<li>5-minute cache with requests more than five minutes apart: every request writes. 64,800,000 × $5 per million = $324. Total $473.76, saving $2,665.44. Caching the idle tenants loses $64.80 a day.</li>
<li>1-hour cache with each tenant's six requests inside one hour: one write at $8 per million ($0.24) and five reads ($0.03), $0.27 per tenant, $97.20 in all. Total $246.96, saving $2,892.24.</li>
<li>1-hour cache with requests more than an hour apart: six writes at $0.24, $1.44 per tenant, $518.40. Total $668.16, saving $2,471.04. The worst of the four.</li>
</ul>
<p>The accepted band, $2,400 to $2,950, covers all four. The dominant term is the busy tenants' prefix: $2,880 uncached against $149.76 cached. The assumption that flips the conclusion for the idle tenants is the arrival pattern, which nobody has measured; with no data, not caching them is the choice whose worst case is zero loss.</p>
<p>For the percentage: tail input is 26,160 requests × 1,000 tokens × $4 per million = $104.64 and output is 26,160 × 400 × $20 per million = $209.28. With no idle caching, the whole bill falls from $3,453.12 to $722.88, a 79 percent cut. The largest remaining line is then the idle tenants' uncached prefix at $259.20, ahead of output at $209.28.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Finance asks for one number to put in the plan. Which do you give, and with what caveat?</em> $2,730 a day, the no-idle-caching case, with the caveat that it assumes busy-tenant traffic stays at about one request a minute through the working day.</li>
<li><em>What measurement would move you to the 1-hour cache for idle tenants?</em> A week of timestamps showing their requests cluster within an hour; the break-even is three requests per hour-long window at a 2-times write and 0.05-times reads.</li>
<li><em>What breaks the busy-tenant estimate?</em> Anything per-request placed above the handbook, or a busy tenant whose traffic thins to one request every ten minutes, which turns each read into a write.</li>
</ul>
</Fragment>
</Depth>

Unreasonable choices: applying the cache discount to the tail or the output, which overstates the saving; or charging the write premium on every busy-tenant request, which understates it by about $2,700 and gives an answer near zero.

## Follow-ups

- *The handbook changes every hour for every busy tenant. What does that cost?* One extra write per tenant per change: 40 × 10 × $0.15 = $60 a day, small against the $2,730 saving.
- *Could the Batch API help?* For reviews that can wait, Anthropic's pricing page says the caching multipliers stack with the Batch API discount, so both the prefix and the output lines halve; the estimate then needs the batch hit rate measured, not assumed.
- *Two tenants share an identical handbook. Can they share a cache entry?* Only within one workspace and organisation, and only if the prefix is byte-identical up to the breakpoint; most multi-tenant designs keep them separate for isolation and accept the extra write.

## Common mistakes

- Applying the discount to the whole request rather than the cached prefix.
- Ignoring the write premium, or charging it on every request regardless of traffic.
- Caching every tenant the same way when traffic per tenant differs by two orders of magnitude.
- Quoting "caching saves 90 percent" without naming the model: Opus 5.5 reads cost 0.05 times base input, not 0.1.
