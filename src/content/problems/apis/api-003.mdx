## Question

<Callout kind="interview" label="The prompt">
"Your application is hitting LLM provider rate limits during peak hours. How do you handle it?" Here it comes with logs: find the cause before you propose a fix.
</Callout>

A nightly-report service summarises documents with Claude. At 09:00 a scheduler releases the morning queue to a pool of 64 worker threads. From 09:00 to about 09:20 most calls fail with 429, the service sends far more requests per minute than it does at 08:59, and reports go out late. The queue drains by 09:20 and the errors stop. The synthetic log below is typical.

```python
client = anthropic.Anthropic()                 # SDK defaults

def summarize(doc):
    for attempt in range(3):
        try:
            return client.messages.create(
                model="claude-sonnet-5-5", max_tokens=8192,
                messages=[{"role": "user", "content": doc}])
        except anthropic.RateLimitError:
            time.sleep(1)
    raise RuntimeError("gave up")
```

Pick the root cause.

## Answer

The requests bucket is empty while both token buckets have room, every response carries `retry-after`, and each burst of retries lands within about 10 ms. That is a client-made retry storm on a request-per-minute limit.

Two things produce it. The first multiplies requests: the SDK retries 2 times by default, so each `messages.create` can send 3 requests, and the loop calls it 3 times, up to 9 requests per document. The second keeps them in step. The SDK honours `retry-after`, but when the header is present it waits exactly that long and adds no jitter (jitter applies only on its exponential path, when the header is absent), so workers that failed together come back together 2 seconds later. Once the SDK gives up, the loop's fixed `time.sleep(1)` ignores `retry-after` altogether and sends every worker back at the same instant again. That is the 2 s, 2 s, 1 s rhythm in the log.

Why the other picks are tempting. A spend cap is also a 429, but it has no `retry-after`, carries `enforced_spend_limit_reached`, and would not clear when the queue drains. Counting `max_tokens` against the limit is exactly how OpenAI's TPM works, so engineers who know OpenAI reach for it, but Claude's OTPM counts generated tokens only. Overload would be a 529, a different error with a different response.

<Fragment slot="short">
<p>Retry in one place: set the SDK's <code>max_retries=0</code> or remove the loop. Back off with full jitter and treat <code>retry-after</code> as a minimum, adding random delay on top so workers that failed together do not return together. Then remove the cause of the burst: release the queue at a steady rate with a client-side token bucket sized from the <code>*-remaining</code> headers, and cap concurrency below the RPM limit. Move work that can wait to the batch API at half price.</p>
</Fragment>
<Fragment slot="long">
<p>Immediate fix: one retry layer with jitter and a cap on total retry time, so a failing document fails fast instead of holding a worker.</p>
<p>Structural fix: the scheduler releases 64 requests in the same millisecond against a continuously refilled token bucket. Pace the queue instead, at a rate below the limit, using the rate-limit headers as feedback. A semaphore per model bounds concurrency.</p>
<p>Cheaper fix: a morning report is not interactive. The Message Batches API costs 50% of standard prices and is built for this; results arrive in any order and are matched on <code>custom_id</code>.</p>
<p>Capacity: if paced traffic still exceeds the limit, the answer is a higher tier, prompt caching (cache reads do not count toward input tokens per minute on most Claude models), or a second model, not more retries.</p>
</Fragment>

## Follow-ups

- *What would the logs look like if it were a spend cap?* 429 with no `retry-after`, `error.details.error_code` set to `enforced_spend_limit_reached`, and failures that continue until someone raises the cap.
- *Would raising the rate-limit tier fix it?* It would hide it until the queue grows. The retry multiplier and the burst release remain.
- *Where else do retries stack?* A gateway that retries, a service that retries, and an SDK that retries can turn one call into 27 requests at three attempts per layer.

## Common mistakes

- Increasing the retry count or the sleep without adding jitter.
- Treating every 429 the same way, which keeps hammering a spend cap.
- Reading the problem as "the provider is slow at 9 a.m." without looking at which bucket is empty.
- Applying OpenAI's rule that `max_tokens` counts toward the limit to a Claude client.
