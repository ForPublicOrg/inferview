## Question

<Callout kind="interview" label="Debug, 20 minutes">
Pick the cause that explains the symptom, rank the other defects you can see, and propose the smallest change that ends the 09:00 failures.
</Callout>

A report service summarises documents with Claude Sonnet 5.5. The organisation is on the Start tier. At 09:00 a scheduler releases the morning queue to a pool of 64 worker threads at once. From 09:00 to about 09:20 most calls fail with 429 and reports go out late; the provider's request count for the organisation is several times its 08:59 rate. The queue drains by 09:20 and the errors stop.

```python
client = anthropic.Anthropic()

def summarize(doc):
    for attempt in range(3):
        try:
            resp = client.messages.create(
                model="claude-sonnet-5-5", max_tokens=8192,
                system=REPORT_INSTRUCTIONS,
                messages=[{"role": "user", "content": doc}])
            return resp.content[0].text
        except anthropic.RateLimitError:
            time.sleep(1)
    raise RuntimeError("gave up")

pool = ThreadPoolExecutor(max_workers=64)
results = list(pool.map(summarize, queue.drain()))
```

## Answer

The request bucket is empty while the input and output buckets have room, every 429 carries `retry-after`, and each wave of retries lands within about 10 ms. That is a client-made storm against the request-rate limit.

The arithmetic: Start-tier Sonnet 5.5 allows 1,000 RPM, and the docs say a per-minute limit may be enforced over shorter intervals, as in 60 RPM enforced as 1 per second. 1,000 / 60 is about 16.7 requests per second. The scheduler releases 64 requests in the same millisecond, so most are rejected before any token is generated. Then two layers multiply and align the retries: the SDK retries twice by default, so each `messages.create` can send 3 requests, and the loop calls it 3 times, up to 9 requests per document. Whatever delay the SDK adds on top of `retry-after`, the 2-second waves in the log land within 10 ms of each other, so it is not spreading them. When the SDK gives up, the loop's fixed `time.sleep(1)` sends every worker back in the same instant: the 2 s, 2 s, 1 s rhythm.

Ranking what else is wrong:

1. **The spend-cap blind spot** is a real defect that did not cause this. `RateLimitError` covers both 429s, so on the day the organisation hits its cap, this loop and the SDK retry a response that cannot clear until access resumes.
2. **Acceleration limits** are a real 429 source that fits a jump from idle to 64 workers. The headers favour the request bucket, but without the response body the evidence is incomplete. Collect one body; it names the limit.
3. **The 529 at 09:00:06** is the provider's overload, not your limit. One instance during a storm you are causing is noise; a run of them is a different incident.
4. **`resp.content[0].text`** assumes the first block is text and ignores `stop_reason`. A truncated or refused summary is stored as a finished report. Unrelated to the 429s, and worth a ticket.

The smallest change that ends it: stop releasing 64 requests at once. Start workers at a paced rate below about 16 per second, or put a client-side token bucket in front of the pool sized from the `requests-remaining` header. Then make one layer own retries: `max_retries=0` on the client and jitter on top of `retry-after` in the loop, or delete the loop and keep the SDK's retries.

## Follow-ups

- *What would the logs look like if it were the spend cap?* 429s with no `retry-after`, `enforced_spend_limit_reached` in the body, and no recovery when the queue drains.
- *Would a higher tier fix it?* Build tier's 5,000 RPM is about 83 per second, so this burst would mostly pass, until the queue or the pool grows. The multiplier and the aligned retries remain.
- *Why did it clear at 09:20?* The demand came from the queue; once drained, the rate fell under the limit.

## Common mistakes

- Raising the retry count or the sleep without pacing the release.
- Reading "1,000 RPM" as permission to send 64 requests at once.
- Treating every 429 the same, which hammers a spend cap.
- Applying OpenAI's `max_tokens` accounting to a Claude client.
