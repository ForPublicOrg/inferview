## Question

<Callout kind="interview" label="The prompt">
"Your chatbot loses context after 10 turns in a conversation. How do you maintain a long conversation context?"
</Callout>

The product is a travel-planning assistant. Conversations often run 40 turns over several days. Users mention constraints early ("I can't fly overnight", "budget is fixed", "my partner is vegetarian") and expect them to hold at turn 35. The current code keeps the last 10 turns. Design what replaces it, and say how you would know it works.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Not every turn is worth the same. Which information must survive forever, and which can fade?</p></details>
<details class="hint"><summary>Hint 2</summary><p>A bigger window is one answer. What does it cost in money, latency and quality?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Whatever you build changes the start of the prompt. What does that do to the prompt cache?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Split the conversation into three layers. A structured fact sheet of durable constraints and decisions, extracted as they appear and always sent. A running summary of older turns, refreshed in the background. The recent turns verbatim. Order them for caching: system prompt, fact sheet, summary, recent turns, new message. Measure with an eval of long scripted conversations that check whether early constraints are honoured late.</p>
</Fragment>
<Fragment slot="long">
<p>Why the window alone fails. A sliding window drops facts by age, not by importance; "can't fly overnight" from turn 3 is gone by turn 13. Sending everything forever costs more each turn, and long inputs degrade quality too: Chroma's 2025 study found reliability falls as input grows even on simple tasks.</p>
<p>Fact sheet. After each user turn, a cheap model call (or the main call, via a tool) updates a small structured record: constraints, preferences, decisions, open questions, each with the turn it came from. It is always injected, so the constraint from turn 3 is present at turn 35 regardless of the window. This is what Anthropic's context-engineering post calls structured note-taking. Validate updates: a user saying "actually, overnight is fine now" must replace the old entry, not add a contradictory one.</p>
<p>Summary. Turns that fall out of the verbatim window are folded into a running summary, refreshed every few turns off the request path so it adds no latency. Providers now offer this server-side: Claude has compaction in beta and context editing that clears old tool results once input passes a trigger.</p>
<p>Recent turns. The last several turns verbatim, because tone and immediate references ("the second hotel") live there.</p>
<p>Ordering and caching. Put stable parts first. The fact sheet and summary change only when updated, so between updates the prefix stays cached; each update costs one cache write. Do not rewrite early messages on every turn, or nothing is ever cached.</p>
<p>Retrieval for the long tail. If users ask about details from long ago ("what was that restaurant on day two?"), store all turns and retrieve relevant ones on demand rather than carrying them.</p>
<p>Evaluation. Scripted conversations of 40 turns with constraints planted early and probes late, scored on whether answers respect them; plus a contradiction test where a constraint changes mid-conversation. Track cost per turn and latency against the old design.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The summary invents a constraint the user never stated. How do you stop it?</em> Keep source turn ids on every fact, show the fact sheet to the user for confirmation on important items, and test summarisation against a labelled set. A wrong fact that persists is context poisoning.</li>
<li><em>The conversation spans devices and days. Where does state live?</em> Server-side, keyed by conversation, with the fact sheet as a durable record and the raw turns in storage for retrieval.</li>
<li><em>Users ask you to forget something. What happens?</em> Delete it from the fact sheet, the summary and the stored turns, and re-summarise; a deletion that only edits one layer leaks back.</li>
</ul>
</Fragment>
</Depth>

The strongest answers make two moves that weaker ones miss. They separate durable facts from conversational flow instead of treating all history the same, and they connect the design to cost: where each layer sits in the prompt decides whether the cache survives, and an eval with planted constraints, not a feeling, decides whether memory works.

## Follow-ups

- *Why not just use a model with a 1M-token window?* It postpones the problem and charges for it every turn: cost and latency grow with each turn's input, and long-context reliability is not uniform.
- *How often should the summary be refreshed?* Often enough that nothing important lives only in the dropped turns, and rarely enough that each refresh, which rewrites part of the prompt, does not cancel the caching benefit. Measure both.
- *Where do tool results go?* Clear old ones once they have been used, keeping the call visible, as Claude's context editing does. Clearing changes the prefix, so batch it.

## Common mistakes

- Answering "increase the window" and stopping there.
- Summaries with no provenance, so errors cannot be traced or corrected.
- Rewriting the start of the prompt every turn and losing the cache.
- No evaluation beyond trying a few conversations by hand.
