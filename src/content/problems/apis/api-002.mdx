    class RateLimited(Exception):
        """HTTP 429 rate_limit_error with a retry-after header (seconds), or None when absent."""
        def __init__(self, retry_after=None):
            super().__init__("rate limited")
            self.retry_after = retry_after

        """HTTP 529 overloaded_error."""


    class SpendCapReached(Exception):
        """HTTP 429 rate_limit_error, no retry-after, error_code enforced_spend_limit_reached."""


    class BadRequest(Exception):
        """HTTP 400 invalid_request_error."""


    class Retrier:
        """One retry layer shared by every model call in the process.

        call(fn) calls fn() and returns its result.

        Rules:
        - RateLimited and Overloaded may be retried. Every other exception
          propagates on the attempt that raised it.
        - At most max_attempts calls of fn per call(fn); no sleep after the last.
        - The wait before retry k (k = 0 for the first retry) comes from your jitter
          policy, drawn with rng() (a float in [0, 1)), between 0 and
          min(cap, base * 2 ** k). When the error has a retry_after, the wait is
          never shorter than it.
        - The sleeps inside one call(fn) never add up to more than deadline:
          if the next wait would cross it, re-raise instead of sleeping.
        - Shared budget: when fn has just failed, a retry is allowed only if
          (retries already made in (now - window, now]) + 1
              <= min_retries + ratio * (first attempts made in (now - window, now]),
          where now = clock() and every attempt is timed by clock() when fn is called.
          Otherwise re-raise.
        - clock() returns seconds; sleep(seconds) waits. Both are injected.
        - 20,000 calls inside one window must take well under a second of CPU.
        """

            self.t, self.waits = 0.0, []

            return self.t

            assert s >= 0, "negative sleep"
            self.waits.append(s)
            self.t += s

    import collections


    class RateLimited(Exception):
        """HTTP 429 rate_limit_error with a retry-after header (seconds), or None when absent."""
        def __init__(self, retry_after=None):
            super().__init__("rate limited")
            self.retry_after = retry_after


    class Overloaded(Exception):
        """HTTP 529 overloaded_error."""


    class SpendCapReached(Exception):
        """HTTP 429 rate_limit_error, no retry-after, error_code enforced_spend_limit_reached."""


    class BadRequest(Exception):
        """HTTP 400 invalid_request_error."""


    class Retrier:
        def __init__(self, *, clock, sleep, rng, max_attempts=4, base=0.5, cap=8.0,
                     deadline=30.0, ratio=0.1, min_retries=10, window=60.0):
            self.clock, self.sleep, self.rng = clock, sleep, rng
            self.max_attempts, self.base, self.cap, self.deadline = max_attempts, base, cap, deadline
            self.ratio, self.min_retries, self.window = ratio, min_retries, window
            self.firsts = collections.deque()    # call times, oldest on the left
            self.retries = collections.deque()

        def _budget_allows(self):
            now = self.clock()
            edge = now - self.window
            for q in (self.firsts, self.retries):
                while q and q[0] <= edge:
                    q.popleft()
            return len(self.retries) + 1 <= self.min_retries + self.ratio * len(self.firsts)

        def call(self, fn):
            slept = 0.0
            for attempt in range(self.max_attempts):
                (self.retries if attempt else self.firsts).append(self.clock())
                try:
                    return fn()
                except (RateLimited, Overloaded) as e:
                    if attempt == self.max_attempts - 1 or not self._budget_allows():
                        raise
                    wait = self.rng() * min(self.cap, self.base * 2 ** attempt)   # full jitter
                    retry_after = getattr(e, "retry_after", None)
                    if retry_after is not None:
                        wait = max(wait, retry_after)
                    if slept + wait > self.deadline:
                        raise
                    self.sleep(wait)
                    slept += wait

## Question

<Callout kind="interview" label="As a candidate report describes it">
Add "an async exponential retry mechanism with timeouts and backoff" to a client that calls an LLM API. A candidate report collected by aced.io attributes a version of this task to Sierra. This version is synchronous so it runs in the browser, and it adds the part that matters when many workers share one provider: a retry budget.
</Callout>

Implement `Retrier`. One instance is shared by every model call in a process, and `call(fn)` returns `fn()`'s result. The docstring in the starter is the contract:

- `RateLimited` (a 429 with an optional `retry_after`) and `Overloaded` (a 529) may be retried. `SpendCapReached`, `BadRequest` and anything else propagate on the attempt that raised them.
- At most `max_attempts` calls per `call(fn)`, and no sleep after the last.
- The jitter policy is yours, drawn from the injected `rng()`, within `[0, min(cap, base * 2 ** k)]` for retry `k`, and never shorter than `retry_after`.
- The sleeps inside one `call(fn)` stay within `deadline`.
- The retry budget is shared across calls: a retry is allowed only while the retries in the last `window` seconds stay within `min_retries + ratio × first attempts` in the same window.
- 20,000 calls inside one window must stay fast.

`clock`, `sleep` and `rng` are injected so the tests run in milliseconds and see every wait. The visible tests show the shape; hidden tests check invariants over random error scripts, a spend cap arriving after a rate limit, an overload storm against the budget, and the speed of the bookkeeping.

## Answer

The reference solution keeps two deques of call times, first attempts and retries, oldest on the left. Before each retry it drops entries older than the window from the left of both, which is amortised constant time because each timestamp is appended once and removed once. A naive version that filters the whole history on every retry does the same arithmetic in time proportional to the window's contents, and 20,000 one-retry calls inside one window make that quadratic: the hidden speed test fails it.

On a retryable error the order of checks is: last attempt, then budget, then the jittered wait raised to `retry_after`, then the deadline. Checking the budget before computing the wait means an exhausted budget fails immediately rather than after a sleep. Non-retryable errors are never caught, so a spend cap after a rate limit leaves on the second call.

Why each rule exists:

- **The spend cap is not a rate limit.** Claude returns `rate_limit_error` for both, but the spend cap has no `retry-after`, carries `enforced_spend_limit_reached`, and the docs say retries fail until access resumes, at 00:00 UTC on the first of the next month or when the tier is raised. A client keyed on status code retries it at every layer.
- **`retry-after` is a floor.** OpenAI's guide says the same for its header: wait at least that long and add a small random delay.
- **Jitter is a policy, so the tests check bounds.** Full jitter (`rng() * ceiling`) is the reference. Equal jitter (`ceiling / 2 + rng() * ceiling / 2`) passes as well. Pure exponential backoff fails the hidden test that first-retry waits are not all equal, because clients that failed together would retry together.
- **The budget is what stops a storm.** Attempts and deadline bound one call. They do not bound what 400 workers do together during a provider incident: each still sends up to `max_attempts` requests. A budget tied to recent first attempts caps the extra load at a ratio you choose; Brooker describes the same mechanism as a local token bucket for retries and gives no ratio. The floor (`min_retries`) lets a quiet process still retry.

The choice that stays open is the ratio. At `ratio=0.1`, a provider returning 529 to everything gets at most about 10 percent more requests than the first attempts, plus the floor; most callers fail fast. At `ratio=1.0`, each call keeps its own retries and a full outage doubles the load. A user-facing path with a short deadline and an idempotent call can justify a higher ratio than a batch path that can re-queue.

Failure mode of the reference: the budget is per process. Fifty processes each holding a 10 percent budget still add 10 percent in total, but a process that starts during an incident, with an empty history, gets its full floor of retries at once. A fleet that restarts during the incident spends `min_retries` per process at the worst moment.

## Follow-ups

- *Running it for real:* the SDK raises typed exceptions, so the classification maps `anthropic.RateLimitError` to `RateLimited` or `SpendCapReached` by reading `error.details.error_code` and the `retry-after` header from the response, and the SDK's `max_retries` goes to 0 so this is the only layer.

## Common mistakes

- Catching `Exception`, so spend caps and 400s are retried.
- Sleeping after the final attempt.
- Recomputing the budget by filtering a growing list on every retry.
- Drawing a wait shorter than `retry-after`.
- Pure exponential backoff with no jitter.
- Leaving the SDK's own retries on under this layer.
