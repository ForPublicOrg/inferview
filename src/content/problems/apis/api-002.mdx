    class RateLimited(Exception):
        """HTTP 429 with a retry-after header (seconds), or None if the header was absent."""
        def __init__(self, retry_after=None):
            super().__init__("rate limited")
            self.retry_after = retry_after

    class Overloaded(Exception):
        """HTTP 529: the provider is short of capacity."""

    class SpendCapReached(Exception):
        """HTTP 429 with error_code enforced_spend_limit_reached and no retry-after."""

    class BadRequest(Exception):
        """HTTP 400: the request itself is wrong."""


    def call_with_retry(fn, *, sleep, rng, max_attempts=5, base=0.5, cap=8.0, budget=30.0):
        """Call fn() and return its result, retrying RateLimited and Overloaded.

        Before retry number k (k = 0 for the first retry) wait
        rng() * min(cap, base * 2 ** k) seconds, but never less than the
        error's retry_after when it has one. Make at most max_attempts calls
        and re-raise the last error. Never wait so that the total time slept
        would exceed budget: re-raise instead. Any other exception propagates
        at once. Use sleep(seconds) to wait and rng() for a number in [0, 1).
        """
        raise NotImplementedError
  tests: |
    def script(*outcomes):
        """Build fn() that raises or returns the given outcomes in order, and counts calls."""
        state = {"calls": 0}
        def fn():
            out = outcomes[state["calls"]]
            state["calls"] += 1
            if isinstance(out, Exception):
                raise out
            return out
        return fn, state

    waits = []
    fn, st = script(RateLimited(), RateLimited(), "ok")
    assert call_with_retry(fn, sleep=waits.append, rng=lambda: 0.5) == "ok"
    assert waits == [0.25, 0.5], "full jitter: rng() * min(cap, base * 2 ** attempt)"
    assert st["calls"] == 3

    waits = []
    fn, st = script(RateLimited(retry_after=3.0), "ok")
    call_with_retry(fn, sleep=waits.append, rng=lambda: 0.5)
    assert waits == [3.0], "retry-after is a floor"

    waits = []
    fn, st = script(RateLimited(), RateLimited(), RateLimited(), RateLimited(), RateLimited(), RateLimited(), "ok")
    call_with_retry(fn, sleep=waits.append, rng=lambda: 1.0, max_attempts=7, budget=100)
    assert waits == [0.5, 1.0, 2.0, 4.0, 8.0, 8.0], "the backoff ceiling stops at cap"

    waits = []
    fn, st = script(Overloaded(), "ok")
    assert call_with_retry(fn, sleep=waits.append, rng=lambda: 0.5) == "ok", "529 is retryable"

    waits = []
    fn, st = script(SpendCapReached(), "ok")

    assert st["calls"] == 1 and waits == [], "spend cap: one call, no sleep"

    fn, st = script(BadRequest(), "ok")

        call_with_retry(fn, sleep=waits.append, rng=lambda: 0.5)

  solution: |
    class RateLimited(Exception):
        """HTTP 429 with a retry-after header (seconds), or None if the header was absent."""
        def __init__(self, retry_after=None):
            super().__init__("rate limited")
            self.retry_after = retry_after

    class Overloaded(Exception):
        """HTTP 529: the provider is short of capacity."""

    class SpendCapReached(Exception):
        """HTTP 429 with error_code enforced_spend_limit_reached and no retry-after."""

    class BadRequest(Exception):
        """HTTP 400: the request itself is wrong."""


    def call_with_retry(fn, *, sleep, rng, max_attempts=5, base=0.5, cap=8.0, budget=30.0):
        slept = 0.0
        for attempt in range(max_attempts):
            try:
                return fn()
            except (RateLimited, Overloaded) as e:
                if attempt == max_attempts - 1:
                    raise
                delay = rng() * min(cap, base * 2 ** attempt)
                retry_after = getattr(e, "retry_after", None)
                if retry_after is not None:
                    delay = max(delay, retry_after)
                if slept + delay > budget:
                    raise
                sleep(delay)
                slept += delay

## Question

<Callout kind="interview" label="As public interview guides report it">
Add "an async exponential retry mechanism with timeouts and backoff" to a client that calls an LLM API. Public guides report variants of this task in Sierra and Decagon loops. This version is synchronous so it runs in the browser.
</Callout>

Write `call_with_retry(fn, *, sleep, rng, max_attempts=5, base=0.5, cap=8.0, budget=30.0)`. It calls `fn()` and returns its result. The exception classes are in the starter:

- `RateLimited` (HTTP 429 with an optional `retry_after` in seconds) and `Overloaded` (HTTP 529) are retryable.
- `SpendCapReached` (a 429 with no `retry-after` whose error code says the spend limit is reached) and `BadRequest` (HTTP 400) are not. Let them propagate on the first occurrence.

The wait before retry number *k*, where *k* is 0 for the first retry:

1. Full jitter: `rng() * min(cap, base * 2 ** k)`.
2. If the error has a `retry_after`, wait at least that long.
3. Make at most `max_attempts` calls, then re-raise the last error. Do not sleep after the last attempt.
4. Never let the total time slept exceed `budget`. If the next wait would cross it, re-raise instead.

`sleep` and `rng` are injected so the tests run instantly and deterministically.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Catch only the two retryable classes; anything else should leave the function untouched.</p></details>
<details class="hint"><summary>Hint 2</summary><p>`getattr(e, "retry_after", None)` works for both retryable classes, because `Overloaded` has no such attribute.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Check "is this the last attempt" before computing a delay, and check the budget before calling `sleep`.</p></details>

## Answer

The reference solution keeps a running total of time slept. On a retryable error it re-raises if this was the last attempt, otherwise computes the jittered delay, raises it to `retry_after` when present, re-raises if the delay would cross the budget, and sleeps. Non-retryable exceptions are never caught, so they leave on the first call.

Why each rule exists:

- **Full jitter** spreads clients that failed at the same moment across the whole window. Exponential backoff without jitter keeps them in lockstep; the retry simulator in the API anatomy lesson shows the same number of attempts arriving in the same waves, only spaced further apart.
- **`retry-after` as a floor.** The server knows when capacity returns. A random draw shorter than that asks for another 429.
- **No retry on a spend cap or a 400.** The spend-cap 429 looks like a rate limit but does not clear by waiting; Claude's docs say retries, including the SDK's own, keep failing until access resumes. A 400 fails identically every time.
- **A budget as well as a count.** Five attempts against a server asking for 20 seconds each is 80 seconds of spinner. A time budget turns that into a fast, explainable failure.

<p>Retry code fails in two ways: retrying the wrong things and retrying in too many places. The first wastes time on errors that cannot succeed, such as a spend cap or a malformed request. The second multiplies load: both official Python SDKs already retry twice, so a three-attempt loop around them sends up to nine requests per call, and each layer above multiplies again.</p>
<p>Jitter fixes synchronisation, not capacity. If the provider is short of capacity for minutes, fail over to another model or degrade the feature instead of retrying harder. A retry budget, which limits retries to a share of recent traffic, stops one client from amplifying an outage.</p>
<p>For calls with side effects, a retry is only safe with an idempotency key, because a timeout does not tell you whether the server did the work.</p>

## Follow-ups

- *The SDK you use already retries. What do you do?* Pick one layer. If the application owns the policy, set `max_retries=0` on the client.
- *Which jitter variant would you pick?* Marc Brooker's AWS post compares Full, Equal and Decorrelated Jitter and finds Equal Jitter the weakest; full jitter is the simple default.
- *How would you share one rate limit across 50 workers?* A client-side token bucket in shared storage, sized from the remaining and reset headers, so workers slow down before the server says no.

## Common mistakes

- Retrying every exception, including 400s and spend caps.
- Sleeping after the final attempt, which only delays the error.
- Ignoring `retry-after` and drawing a wait shorter than the server asked for.
- A fixed sleep with no jitter, so every worker returns at the same instant.
- Wrapping an SDK that already retries in another retry loop.
