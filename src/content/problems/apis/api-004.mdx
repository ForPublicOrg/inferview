## Question

<Callout kind="interview" label="The prompt">
"Your few-shot prompting gives inconsistent results across similar inputs. How do you stabilize it?" Here you get the code and three runs. Find the cause first.
</Callout>

A support team classifies tickets as `billing`, `bug` or `account` with a few-shot prompt of about 900 tokens. The pool holds 12 labelled examples, 4 per label. Re-running the same ticket gives different answers.

```python
def build_prompt(ticket):
    shots = random.sample(EXAMPLE_POOL, 4)          # fresh draw on every request
    examples = "\n".join(
        f"<example><ticket>{e.text}</ticket><label>{e.label}</label></example>"
        for e in shots)
    return (f"<instructions>Label the ticket as billing, bug or account. "
            f"Reply with the label only.</instructions>\n"
            f"<examples>\n{examples}\n</examples>\n<ticket>{ticket}</ticket>")
```

The same ticket, "I was charged twice for October and my login still works", three times (synthetic log):

| Run | Labels of the 4 examples drawn, in order | Model output |
|---|---|---|
| 1 | bug, account, billing, billing | billing |
| 2 | billing, bug, billing, account | account |
| 3 | account, billing, account, bug | bug |

Pick the root cause.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Compare each output with the examples drawn for that run. Which position matches?</p></details>
<details class="hint"><summary>Hint 2</summary><p>What is different between runs? Only one line of the code changes the prompt.</p></details>

## Answer

The prompt changes on every request. `random.sample` draws a different set of examples in a different order each time, and in all three runs the output equals the label of the last example. The ticket is ambiguous (a billing problem that mentions login), so the model's guess is easy to tip, and the most recent example tips it. Zhao and colleagues documented this family of effects in 2021: few-shot accuracy moves with the choice and the order of examples, partly through a bias toward answers near the end of the prompt.

The fix is to make the prompt a deterministic function of the input:

- Use a fixed, reviewed example set, balanced across labels, in a fixed order. Include the hard cases on purpose, such as a billing ticket that mentions login.
- If examples must be selected per input, select by similarity to the ticket with a deterministic tie-break, and sort them deterministically.
- Put the prompt version and the example ids in the log for every request, so a changed answer can be traced to a changed prompt.
- Measure on a labelled set, including a check that the same input gives the same label across repeated runs.

Why the wrong picks are tempting. Temperature is the reflex answer for "inconsistent", but sampling noise would not line up with the last example three times out of three, and the Claude API version dated 2026-10-21 rejects the parameter. Lost-in-the-middle needs a much longer context than 900 tokens. Injection needs an instruction in the ticket, and this ticket has none.

## Follow-ups

- *You fixed the examples and it is still inconsistent on some tickets. Now what?* Those tickets are genuinely ambiguous. Add a label or a rule for the overlap (billing beats account when money moved), or route low-confidence cases to a human.
- *How would you choose the fixed examples?* From production errors: the confusable pairs your eval shows, not the easiest cases.
- *Would self-consistency help?* Voting over several samples steadies the answer at several times the output cost. Fix the prompt first; vote only if the eval shows a gain worth the price.

## Common mistakes

- Reaching for temperature before reading the code.
- Fixing the example set but keeping a random order.
- Testing the prompt once per ticket, which cannot reveal run-to-run instability.
- Adding more examples of the label you want, which moves the bias rather than removing it.
