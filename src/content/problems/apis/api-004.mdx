## Question

<Callout kind="interview" label="The prompt">
A support classifier gives the same ticket different labels. The team says it is sampling noise and wants to add voting. Here is the code, last week's change and a replay. Which defect explains the symptom?
</Callout>

The service runs as several long-lived worker processes. Labels are `billing`, `bug` and `account`; the system prompt defines billing as charges, refunds and invoices, and account as login, access, and locked or closed accounts. The example file holds 12 labelled tickets.

```python
@dataclass(frozen=True)
class Example:
    id: str
    text: str
    label: str

POOL = frozenset(load_examples("examples/v7.jsonl"))

def words(s):
    return set(s.lower().split())

def pick_shots(ticket, k=4):
    ranked = sorted(POOL, key=lambda e: -len(words(e.text) & words(ticket)))
    return ranked[:k]

def build_prompt(ticket):
    shots = pick_shots(ticket)
    examples = "\n".join(
        f"<example><ticket>{e.text}</ticket><label>{e.label}</label></example>" for e in shots)
    safe = ticket.replace("<", "&lt;").replace(">", "&gt;")
    return SYSTEM, f"<examples>\n{examples}\n</examples>\n<ticket>{safe}</ticket>"
```

Last week's change touched three lines: `POOL` went from `list(...)` to `frozenset(...)` to drop duplicate rows from the v7 import, `k` went from 3 to 4, and the ticket escaping was added.

Replay of one ticket, "I was charged twice after my account was locked", 20 times per process (synthetic log). Traces store the ticket, the label and the worker's process id; rendered prompts are not logged.

| Process | Replays | Labels returned |
|---|---|---|
| Worker A, pid 4127, up since Monday | 20 | billing 20 |
| Worker B, pid 4188, up since Monday | 20 | account 18, billing 2 |
| Worker A after a restart, pid 5310 | 20 | account 17, billing 3 |

The CI eval, which runs in one process, passes 94% of cases, the same as before the change.

## Hints

<details class="hint"><summary>Hint 1</summary><p>What is the same within a process and different between processes, including across a restart of the same worker?</p></details>
<details class="hint"><summary>Hint 2</summary><p>For this ticket, how many examples share the same number of words with it? Ask for the rendered prompt from each worker.</p></details>

## Answer

The prompt differs by process. `pick_shots` sorts by word overlap, which is a small integer, so several examples tie; Python's sort is stable, so ties keep the order of the input, and the input is a `frozenset` whose iteration order depends on the hashes of its string fields. Python salts `str` hashes with a random value per process, constant within the process and different on the next start. Each worker therefore renders its own fixed set and order of examples, and for a ticket that sits between two labels, which example comes last is enough to tip it. Worker A agreeing with itself 20 times, then switching after a restart, is the signature of per-process state. The defect is the pair of lines together: the `frozenset` change was a reasonable dedupe, and the sort was fine while the pool was a list.

The fix is a deterministic prompt: dedupe into a list ordered by example id, and break ties explicitly, for example `key=lambda e: (-overlap, e.id)`. Then log a hash of the rendered prompt with every request, so the next disagreement can be split into "different prompt" and "same prompt, different output" from the trace alone.

### The secondary defects, ranked

1. **Label overlap.** The definitions really do collide for a charge on a locked account, and that is why this ticket is fragile. After the fix, every worker will give the same answer, but whether it is the right one depends on a tie-break rule the prompt does not state. Add one (money moved means billing, if the business agrees) and an eval case for it.
2. **No rendered prompt in the trace.** It cost the team the most direct evidence. Without it, the diagnosis rests on a restart pattern from one ticket.
3. **Sampling and server-side nondeterminism.** Both exist: worker B returned billing twice. They explain the 2-of-20 minority, not the split between workers.

### What to collect, and what to do without it

Collect the rendered prompt from each worker for this ticket, the list of example ids each one selected, and a replay of a few more borderline tickets across processes. Without that, ship the deterministic tie-break anyway: it is a one-line change, it cannot make the classifier less consistent, and the eval in CI will show whether accuracy moved.

### Why the wrong picks are tempting

Temperature is the reflex for "inconsistent", but worker A's 20 identical answers rule out sampling as the main cause, and the parameter cannot be sent under API version 2026-10-21. Batch-dependent numerics are documented and do flip near-tie outputs, but they would not line up with process identity. The ambiguous definitions are a real defect and the reason this ticket is the one that shows the bug, which makes them the most persuasive wrong answer.

## Follow-ups

- *Why did CI not catch it?* CI runs one process, so it sees one fixed order. A test that builds the prompt under two different hash seeds and compares would have.
- *Voting is still on the table. What would it fix?* It would hide the per-worker difference behind a majority, at several times the output cost, and leave the prompt nondeterministic. Fix the prompt first; measure whether voting adds accuracy afterwards.
- *Similarity-based example selection: keep it or replace it with a fixed set?* Keep it if the eval shows it beats a fixed, reviewed set; otherwise a fixed set is cheaper to cache and easier to review.

## Common mistakes

- Treating every disagreement as sampling noise without checking whether the prompt was identical.
- Blaming the most recent commit's headline change (`k` from 3 to 4) because it is the one that touches the examples visibly.
- Setting `PYTHONHASHSEED` as the fix, which makes every process agree on an order nobody chose.
- Fixing determinism and closing the ticket without deciding which label the ambiguous ticket should get.
