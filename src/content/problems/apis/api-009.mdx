  tests: |
    def start(i, kind, **kw):
        return {"type": "content_block_start", "index": i, "content_block": {"type": kind, **kw}}
    def text_d(i, t):
        return {"type": "content_block_delta", "index": i, "delta": {"type": "text_delta", "text": t}}
    def json_d(i, s):
        return {"type": "content_block_delta", "index": i, "delta": {"type": "input_json_delta", "partial_json": s}}
    def stop(i):
        return {"type": "content_block_stop", "index": i}
    def mdelta(reason, out):
        return {"type": "message_delta", "delta": {"stop_reason": reason}, "usage": {"output_tokens": out}}
    PING = {"type": "ping"}
    MSG_START = {"type": "message_start", "message": {"usage": {"input_tokens": 50, "output_tokens": 1}}}
    MSG_STOP = {"type": "message_stop"}

    simple = [MSG_START, start(0, "text", text=""), text_d(0, "Hello"), PING, text_d(0, ", world"), stop(0),
              mdelta("end_turn", 6), MSG_STOP]
    r = collect(simple)
    assert r["text"] == "Hello, world" and r["tool_calls"] == [] and r["stop_reason"] == "end_turn"

    two_tools = [MSG_START,
        start(0, "text", text=""), text_d(0, "Checking."), stop(0),
        start(1, "tool_use", id="t1", name="get_weather", input={}),
        json_d(1, '{"city": "Pu'), PING, json_d(1, 'ne"}'),
        stop(1),
        start(2, "tool_use", id="t2", name="get_time", input={}),
        json_d(2, '{"tz": "Asia/'), json_d(2, 'Kolkata"}'), stop(2),
        mdelta("tool_use", 40), mdelta("tool_use", 41), MSG_STOP]
    r = collect(two_tools)
    assert r["tool_calls"] == [{"id": "t1", "name": "get_weather", "input": {"city": "Pune"}},

    assert r["text"] == "Checking."
    assert r["output_tokens"] == 41, "message_delta usage is cumulative: take the last value, do not sum"
    assert r["stop_reason"] == "tool_use"

    no_args = [MSG_START, start(0, "tool_use", id="t9", name="list_orders", input={}), stop(0), mdelta("tool_use", 5), MSG_STOP]

  solution: |
    import json

    class StreamError(Exception):
        pass

    def collect(events):
        blocks = {}
        stop_reason, output_tokens = None, 0
        for ev in events:
            kind = ev["type"]
            if kind == "ping":
                continue
            if kind == "error":
                raise StreamError(ev["error"]["type"])
            if kind == "content_block_start":
                b = ev["content_block"]
                blocks[ev["index"]] = {"type": b["type"], "id": b.get("id"), "name": b.get("name"), "buf": ""}
            elif kind == "content_block_delta":
                d = ev["delta"]
                if d["type"] == "text_delta":
                    blocks[ev["index"]]["buf"] += d["text"]
                elif d["type"] == "input_json_delta":
                    blocks[ev["index"]]["buf"] += d["partial_json"]
            elif kind == "content_block_stop":
                b = blocks[ev["index"]]
                if b["type"] == "tool_use":
                    b["input"] = json.loads(b["buf"]) if b["buf"] else {}
            elif kind == "message_delta":
                stop_reason = ev["delta"].get("stop_reason", stop_reason)
                output_tokens = ev["usage"]["output_tokens"]
        order = sorted(blocks)
        text = "".join(blocks[i]["buf"] for i in order if blocks[i]["type"] == "text")
        calls = [{"id": blocks[i]["id"], "name": blocks[i]["name"], "input": blocks[i]["input"]}
                 for i in order if blocks[i]["type"] == "tool_use" and "input" in blocks[i]]
        return {"text": text, "tool_calls": calls, "stop_reason": stop_reason, "output_tokens": output_tokens}

## Question

<Callout kind="interview" label="The prompt">
"Implement streaming responses for an LLM API." Here the network part is done: you get the parsed server-sent events as a list and must turn them into a usable result.
</Callout>

Write `collect(events)`, which folds Claude-style stream events into:

```python
{"text": str, "tool_calls": [{"id", "name", "input"}], "stop_reason": str, "output_tokens": int}
```

The events follow the documented order: `message_start`; for each content block a `content_block_start`, `content_block_delta` events and a `content_block_stop`; then `message_delta` events and `message_stop`. Rules:

- Text comes from `text_delta` deltas. Tool input arrives as `input_json_delta` fragments that are not valid JSON on their own. Parse a tool's input once, at its `content_block_stop`. A tool block with no argument deltas has input `{}`.
- Blocks are identified by `index`, and the result lists them in index order.
- `ping` events carry nothing; ignore them.
- Usage in `message_delta` is cumulative. Report the last value.
- An `error` event can arrive after the HTTP 200 that started the stream. Raise `StreamError` with the error type in the message.
- Never return a tool call whose block did not reach `content_block_stop`.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Keep a dict from block index to a small record with the block type, id, name and a string buffer.</p></details>
<details class="hint"><summary>Hint 2</summary><p>`json.loads` only at the stop event. Mark the block as finished there, so a block cut off mid-stream is easy to leave out.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Two `message_delta` events with 40 and then 41 output tokens mean 41 in total, not 81.</p></details>

## Answer

The reference solution keeps one record per block index with a string buffer. Text deltas and JSON fragments both append to the buffer; the stop event parses the buffer for tool blocks and stores `input`, which doubles as the "finished" marker. `message_delta` overwrites the stop reason and the output token count rather than adding to them. Pings are skipped, and an `error` event raises immediately. The final result sorts blocks by index, joins text blocks, and keeps only tool blocks that have an `input`.

Each rule maps to a documented trap. Parsing fragments as they arrive fails, because `{"city": "Pu` is not JSON. Summing cumulative usage double counts, which shows up as an inflated bill in your own dashboards. Treating the HTTP status as the outcome misses an `overloaded_error` that arrives mid-stream. And acting on a half-received tool call can run a tool with truncated arguments.

OpenAI's Responses stream has the same shape under different names: `response.output_item.added`, then `response.function_call_arguments.delta` events aggregated by `output_index`, then `response.function_call_arguments.done`.

## Follow-ups

- *The UI wants to show the tool arguments as they arrive. How?* A partial JSON parser, such as Pydantic's `from_json(..., allow_partial=True)`, for display only. Execution still waits for the stop event.
- *The stream errors after 400 tokens of text. What does the user see?* Decide per feature: keep the partial text with a retry button, or discard it. On Claude 4.6 and later the documented recovery is a new request with a user turn asking the model to continue.
- *How would you test this against the real API?* Record real streams to fixtures, including an error mid-stream, and replay them in CI.

## Common mistakes

- `json.loads` on each fragment.
- Adding up `output_tokens` from every `message_delta`.
- Assuming a block's deltas are contiguous, when a ping or another block can come between them.
- Returning tool calls from a stream that broke before their stop event.
