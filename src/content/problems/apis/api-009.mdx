    import json

    class StreamError(Exception):
        def __init__(self, kind, partial):
            super().__init__(kind)
            self.partial = partial

    def collect(events):
        blocks = {}
        stop_reason, output_tokens = None, 0
        for ev in events:
            kind = ev.get("type")
            if kind == "message_start":
                output_tokens = ev["message"].get("usage", {}).get("output_tokens", 0)
            elif kind == "content_block_start":
                b = ev["content_block"]
                blocks[ev["index"]] = {"type": b["type"], "id": b.get("id"), "name": b.get("name"),
                                       "parts": [], "done": False}
            elif kind == "content_block_delta":
                d, b = ev["delta"], blocks.get(ev["index"])
                if b is None:
                    continue
                if d["type"] == "text_delta" and b["type"] == "text":
                    b["parts"].append(d["text"])
                elif d["type"] == "input_json_delta" and b["type"] == "tool_use":
                    b["parts"].append(d["partial_json"])
            elif kind == "content_block_stop":
                b = blocks.get(ev["index"])
                if b is not None and b["type"] == "tool_use":
                    raw = "".join(b["parts"])
                    b["input"] = json.loads(raw) if raw else {}
                if b is not None:
                    b["done"] = True
            elif kind == "message_delta":
                stop_reason = ev.get("delta", {}).get("stop_reason") or stop_reason
                output_tokens = ev.get("usage", {}).get("output_tokens", output_tokens)
            elif kind == "error":
                raise StreamError(ev["error"]["type"], _result(blocks, stop_reason, output_tokens))
        return _result(blocks, stop_reason, output_tokens)

    def _result(blocks, stop_reason, output_tokens):
        order = sorted(blocks)
        text = "".join("".join(blocks[i]["parts"]) for i in order if blocks[i]["type"] == "text")
        calls = [{"id": blocks[i]["id"], "name": blocks[i]["name"], "input": blocks[i]["input"]}
                 for i in order if blocks[i]["type"] == "tool_use" and blocks[i]["done"]]
        return {"text": text, "tool_calls": calls, "stop_reason": stop_reason, "output_tokens": output_tokens}

## Question

<Callout kind="interview" label="The prompt">
"Our chat client streams from the Claude Messages API. The transport is done: you get the parsed server-sent events as a list. Turn them into the reply our agent loop consumes, and decide what the loop gets when the stream dies halfway."
</Callout>

Write `collect(events)`, returning:

```python
{"text": str, "tool_calls": [{"id", "name", "input"}], "stop_reason": str | None, "output_tokens": int}
```

Work from the documented event stream for the Messages API, not from the three visible tests: the hidden tests replay streams with every event the documentation says can appear, and some it says may be added later. Two requirements are not in the documentation:

- On a mid-stream failure, raise `StreamError(kind, partial)`, where `partial` is a result dict built from what arrived. What `partial` may contain is part of your design; the hidden tests hold it to the rule that the agent loop must never execute anything from it that the model did not finish.
- Replies with long tool inputs (a bulk upsert of 75,000 rows arrives as tens of thousands of fragments) must assemble in time linear in the reply's length.

## Answer

<Depth>
<Fragment slot="short">
<p>Keep one record per block index with a list of fragments. Text deltas append to text blocks, <code>input_json_delta</code> fragments append to tool blocks, and the stop event joins and parses the tool input once and marks the block finished. Skip pings, thinking blocks and unknown event or delta types. Treat <code>message_delta</code> usage as a running total. On an error event, raise with a partial result that keeps received text and finished tool calls only. On failure I would discard and re-request by default, and continue from the partial text only for long text-only replies, because a continuation is cheaper but can duplicate or drop words at the seam.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Parsing.</strong> The documented flow is <code>message_start</code>, then per block a <code>content_block_start</code>, deltas and a <code>content_block_stop</code>, then <code>message_delta</code> events and <code>message_stop</code>, with any number of <code>ping</code> events anywhere. A tool's input arrives as <code>input_json_delta</code> fragments; the documented example starts with an empty fragment, and a fragment such as <code>&#123;"city": "Pu</code> is not JSON, so parsing waits for the block's stop event. A tool block with no fragments has input <code>&#123;&#125;</code>. Thinking blocks stream <code>thinking_delta</code> and <code>signature_delta</code>; they are not reply text. The output token count in <code>message_delta</code> is cumulative, so 40 then 41 means 41; before any <code>message_delta</code>, the count from <code>message_start</code> is the best available.</p>
<p><strong>Linear time.</strong> The fragments go into a list and are joined once. Appending to a string held in a dict entry copies the whole string each time, because the dict holds a second reference and CPython cannot resize it in place, so a 3 MB reply in 150,000 fragments copies about 225 GB in total (150,000 appends times an average of 1.5 MB). The reference assembles that stream in a fraction of a second.</p>
<p><strong>Forward compatibility.</strong> The streaming docs say new event types may be added and code should handle unknown ones gracefully. An unknown event or delta type is ignored, not raised, because a client that crashes on a new event type breaks on the provider's schedule, not yours.</p>
<p><strong>The partial result.</strong> Text received before the failure is kept, finished tool calls are kept, and a tool block that did not reach its stop event is dropped, since its input is truncated JSON. The streaming docs say tool use and thinking blocks cannot be partially recovered, which matches.</p>
<p><strong>The decision: discard or continue.</strong> Discarding and re-requesting is simple and gives a reply the model produced in one pass. Its cost is the full output billed twice and the user's wait doubled for a long reply. Continuing sends a new request with a user message containing the partial text and an instruction to continue, which is the documented recovery on Claude 4.6 and later; it bills only the remaining output plus the re-sent input, but the seam is a place where the model repeats a clause or changes its plan. I would discard by default and continue only for text replies past a length threshold I would set from our own p95 reply length and the measured seam defect rate on recorded failures.</p>
<p><strong>Failure mode of that choice.</strong> If the stream fails after a finished tool call that the loop has already executed, discarding and re-requesting can make the model propose the same call again. The re-request must carry the executed call and its result, or the executor's duplicate guard must catch it.</p>
</Fragment>

The constraint conflict is latency and cost against correctness: every option that reuses partial output saves tokens and time and adds a way for the final reply to differ from what the model would have written in one pass.

For a real client, the event list becomes an iterator over an HTTP response, so `collect` turns into a generator that yields display updates and returns the final result, and the error path also has to handle a connection that closes without an error event or a `message_stop`. Treat that as a failure, not a reply.

## Common mistakes

- Calling `json.loads` on each fragment.
- Adding up the output tokens from every `message_delta`.
- Concatenating into a string stored in a dict, which is quadratic on long replies.
- Treating the HTTP 200 that opened the stream as the outcome.
- Raising on an event type the code does not recognise.
- Returning a tool call whose block never stopped.
