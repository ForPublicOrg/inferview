  tests: |
    STATUSES = ["paid", "refunded", "pending"]
    DATA = [{"id": i, "amount": i * 10, "status": STATUSES[i % 3]} for i in range(23)]
    calls = []
    def api(cursor=None, limit=5):
        calls.append(cursor)
        start = int(cursor or 0)
        nxt = start + limit
        return {"items": DATA[start:nxt], "next_cursor": str(nxt) if nxt < len(DATA) else None}
    items = fetch_all(api)
    assert [i["id"] for i in items] == list(range(23)), "every item, in order"
    assert calls == [None, "5", "10", "15", "20"], "first call has no cursor; one call per page"
    assert total_by_status(items) == {"paid": 840, "refunded": 920, "pending": 770}
    assert fetch_all(lambda c: {"items": [], "next_cursor": ""}) == [], "an empty string cursor ends the loop"
    assert fetch_all(lambda c: {"items": [{"id": 1}]}) == [{"id": 1}], "a missing next_cursor ends the loop"
    pages = {None: {"items": [], "next_cursor": "a"}, "a": {"items": [{"id": 7}], "next_cursor": None}}
    assert fetch_all(lambda c: pages[c]) == [{"id": 7}], "an empty page with a cursor is not the end"
    try:
        fetch_all(lambda c: {"items": [], "next_cursor": "same"}, max_pages=50)
        raise AssertionError("a cursor that never ends must raise")
    except RuntimeError:
        pass
    assert total_by_status([]) == {}
  solution: |
    def fetch_all(get_page, max_pages=1000):
        items, cursor = [], None
        for _ in range(max_pages):
            page = get_page(cursor)
            items.extend(page.get("items", []))
            cursor = page.get("next_cursor")
            if not cursor:
                return items
        raise RuntimeError(f"pagination did not finish within {max_pages} pages")


    def total_by_status(items):
        totals = {}
        for item in items:
            totals[item["status"]] = totals.get(item["status"], 0) + item["amount"]
        return totals

## Question

<Callout kind="interview" label="As one candidate reported it">
"Implement pagination for an API to retrieve all results. Then do some computation with the JSON response." In this version it is the warm-up of an LLM-application loop: the plumbing you write before any model is involved.
</Callout>

An internal API returns payments a page at a time. `get_page(cursor)` returns a dict with `items` and `next_cursor`. Pass `None` for the first page. A missing, `None` or empty `next_cursor` means you have everything.

Write `fetch_all(get_page, max_pages=1000)`, which returns every item in order and raises `RuntimeError` if the API is still handing out cursors after `max_pages` calls. Then write `total_by_status(items)`, which sums `amount` per `status`.

The tests use a fake API with 23 payments and a page size of 5. They also check three edge cases a real API produces: an empty string as the last cursor, a page with no items that still has a cursor, and a cursor that never ends.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Loop on the cursor, not on whether the page had items: an empty page can still have a next cursor.</p></details>
<details class="hint"><summary>Hint 2</summary><p>`if not cursor` treats `None`, a missing key read with `.get` and the empty string the same way.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Bound the loop with `for _ in range(max_pages)` so a server bug cannot keep you calling forever.</p></details>

## Answer

The loop asks for a page, appends its items, reads the next cursor, and stops when the cursor is falsy. A `for` over `range(max_pages)` replaces `while True`, so a cursor that never ends becomes an error instead of a hung worker. `page.get("items", [])` tolerates a page without the key.

`total_by_status` is a fold into a dict. `collections.Counter` or `defaultdict(int)` work equally well; a plain dict is easy to compare and serialise.

What separates answers in the room is what you say next. Put the per-page call behind the same retry wrapper as every other call, so a 429 on page 40 does not restart the export from page 1. Treat the cursor as opaque: never parse or increment it. And keep memory bounded on large exports by processing or writing each page as it arrives instead of collecting everything first.

## Follow-ups

- *The API has 10,000 pages and each takes 300 ms. How do you speed it up?* Cursor pagination is sequential by design, because each cursor comes from the previous page, so 10,000 pages at 300 ms is 3,000 seconds, 50 minutes. Ask whether the API supports filters you can split on (date or id ranges) and fetch those ranges concurrently under a semaphore.
- *A request fails on page 40. What happens?* Retry that page with backoff, and checkpoint the last good cursor so a crash resumes from page 40, not page 1.
- *Does the order of results matter?* For a cursor API it is the server's order. Batch-style APIs such as the Claude Message Batches API return results in any order, matched on an id like `custom_id`, never on position.

## Common mistakes

- `while page["items"]:` as the loop condition. It stops early on an empty page that still has a cursor.
- No upper bound on the loop, so a server bug becomes an infinite loop.
- Incrementing a numeric cursor yourself instead of using the one the server returned.
- Holding every page in memory for an export that should stream to disk.
