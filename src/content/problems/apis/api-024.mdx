## Question

<Callout kind="interview" label="The prompt">
This prompt and request code ran on Claude Sonnet 4.5 for a year with good reviews. The team is moving it to Sonnet 5.5 before the 2026-11-30 retirement and asked you to review the pull request, which changes only the model string. List every problem you would raise, rank them, and say what you would change and in what order. Then open the checklist.
</Callout>

```python
SYSTEM = f"""Today is {today}. You are helping {customer.first_name} ({customer.tier} tier).

You are Max, the support assistant for Parcelly, a parcel delivery service.
Be warm, concise and use the customer's first name.

CRITICAL: You MUST ALWAYS call lookup_order before replying. NEVER answer without it.

<policy>
{REFUND_POLICY}
</policy>

<context>
Latest customer email:
{email.body}
</context>

Before answering, think step by step inside <reasoning> tags about the policy,
then write the reply.

<examples>
<example>
Customer: My parcel says delivered but it is not here.
Reply: {{"reply": "I'm sorry, Dana. I've opened a trace with the courier...", "action": "escalate"}}
</example>
<example>
Customer: It's been 20 days and my parcel never came. I want a refund.
Reply: {{"reply": "I understand, Sam. Our refund window is 14 days, so...", "action": "refuse"}}
</example>
<example>
Customer: The courier left my parcel in the rain and it's ruined.
Reply: {{"reply": "That's not acceptable, Lee. I'm passing this to our claims team...", "action": "escalate"}}
</example>
</examples>
"""

response = client.messages.create(
    model="claude-sonnet-5-5",          # was claude-sonnet-4-5-20250929
    max_tokens=800,
    temperature=0,
    system=SYSTEM,
    tools=[LOOKUP_ORDER, ISSUE_REFUND],
    messages=[
        {"role": "user", "content": "Please reply to the customer's latest email."},
        {"role": "assistant", "content": '{"reply": "'},
    ],
)
```

`REFUND_POLICY` is about 1,800 tokens; its section 2 grants refunds for lost parcels within 30 days of the delivery date. The rendered system prompt is about 3,000 tokens. The service handles every inbound email, most of which are status questions with an order number.

<Fragment slot="short">
<p>Two lines fail outright on Sonnet 5.5: the assistant prefill and <code>temperature=0</code>, both 400s. Two workarounds for the older model now cost money or quality: the shouted lookup_order rule and the step-by-step reasoning instruction. Two structural defects predate the migration: per-request values at the top of the system prompt defeat caching, and an untrusted email sits in the system prompt. Two specification defects are the ones most reviewers miss: an example contradicts the 30-day policy, and every example ends in an exception action, the last one escalate.</p>
</Fragment>
<Fragment slot="long">
<p><b>Hard failures.</b> Prefill on the last assistant turn returns 400 from Claude 4.6 models onward; the JSON shape belongs in structured outputs or a reply tool. Sampling parameters return 400 under API version 2026-10-21, and on older API versions a non-default value returns 400 on Claude 4.7 and later, so <code>temperature=0</code> fails either way.</p>
<p><b>Workarounds.</b> "CRITICAL: You MUST ALWAYS" was written for a model that under-called tools. Anthropic reports newer models respond more strongly to the system prompt and may overtrigger on such wording; here it forces a lookup on emails with no order number, adding a call and latency to every message. State when the tool applies instead. The reasoning instruction duplicates thinking that is on by default on Sonnet 5.5, may be declined there, and if it runs, the reasoning text lands in a field the code may send to a customer.</p>
<p><b>Structure.</b> The first line holds the date, the customer's name and tier, so the 3,000-token prefix differs on every request and the prompt never caches. The customer's email is third-party text inside the system prompt, with no escaping; it belongs in the user turn, escaped and tagged as third-party content.</p>
<p><b>Specification.</b> Example two refuses a refund at 20 days citing a 14-day window, while the policy grants 30; the model has two specifications and will follow each some of the time. All three examples end in escalate or refuse, and the last is escalate, which biases a borderline email toward escalation. Add a routine resolution and a granted refund, and order them so the last is not the exception.</p>

### The decision: remove the workarounds together or one at a time

The prefill and the temperature must go in this PR; they fail. The two quality workarounds are a choice. Removing both together costs one eval cycle and fits the deadline, and the cost is attribution: if the eval moves, you cannot say which removal moved it, and the next model change starts from folklore again. Removing them one at a time costs a second eval cycle and gives each line a recorded result. With the retirement date fixed, the defensible compromise is one PR, two eval runs on the same cases (with and without each line), which costs eval money rather than calendar time.

### Ranking

1. The two 400s, because nothing else can be measured until they are gone.
2. The policy contradiction in example two, because it produces wrong refusals of money owed, the most expensive error this bot can make.
3. The untrusted email in the system prompt.
4. The overtriggering tool rule and the reasoning instruction.
5. The example ordering bias.
6. The cache-busting first line, which is cost, not correctness.

The failure mode of this ranking: fixing the contradiction by editing example two can shift refusals in other cases, since the bot learned partly from the wrong example. Rerun the refund slice of the eval specifically, not only the aggregate.

## Follow-ups

- *The policy changes monthly. Does it stay in the prompt?* Inline is acceptable if each policy change ships as a prompt version through the same eval; if legal edits it outside that process, serve it through a tool so the prompt version stays meaningful.
- *Where does consistency come from without temperature 0?* From a fixed prompt, a schema-constrained output, unambiguous rules and repeated-run checks in the eval; sampling is no longer a knob on this API.
- *How would an attacker use the email placement?* An email that imitates the policy tags or the instruction style sits in the highest-trust position; the fix is placement and marking, and the refund tool's own authorisation checks are the real control.

## Common mistakes

- Approving the PR because the only diff is the model string.
- Treating the two 400s as the whole migration and skipping the eval.
- Reading the examples for tone and missing that one contradicts the policy.
- Moving the email out of the system prompt but leaving the date and name at the top, so caching is still lost.
