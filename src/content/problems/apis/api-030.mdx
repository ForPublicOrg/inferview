## Question

<Callout kind="interview" label="The incident">
The cache read share of the support assistant dropped from above 0.9 to zero after the 14:05 release and has stayed there for five hours. Traffic is flat. Which change explains the symptom, how do you rank the others, and what do you ship in the next hour?
</Callout>

## Answer

The trace id explains the symptom. `template_vars` now passes the request id, and the template renders it on the first line of the system prompt, before the breakpoint. The prefix up to the breakpoint is therefore different on every request. The usage rows show the signature: the same 40,180 tokens written on two requests 40 seconds apart, with nothing read, which is what a prefix of constant length and changing content produces.

Ranking the rest:

1. **The tool sort** is a real defect in the narrow sense: tools are the start of the prefix, so changing their order invalidated every cached entry at deploy. But the sort is deterministic per tenant, so each tenant's first request after the deploy wrote the new prefix and the next one read it. That explains a dip at 14:00, not five hours at zero.
2. **The cost panel** is a real defect that explains why nobody acted for five hours. It prices `input_tokens` only, which excludes both cache fields, so it moved from 362 to 375 while the real input bill multiplied. The hit-rate query also omits writes; it still showed the collapse.
3. **max_tokens** is not in the cache key and changes nothing here.

What the drop costs, computed from the panel's traffic and Opus 5.5 prices: before, each request read 40,180 tokens at $0.20 per million, $0.008; now it writes them at $5 per million, $0.201. At about 18,000 requests an hour that is roughly (0.201 − 0.008) × 18,000 ≈ $3,470 an hour.

What to collect, in order: two rendered requests from one conversation, byte-diffed up to the breakpoint (the first difference should be on the trace line); the count of distinct system-prompt hashes per tenant per hour (about one before the release, about one per request after); and the invoice line for the period, to confirm the panel's error. Without that evidence, the trace line is still the only change that injects a per-request value before the breakpoint, which is enough to act on.

<p>Two defensible responses, each with a cost.</p>
<ul>
<li><strong>Roll back the whole release.</strong> Fastest path to a known-good state, with no new code to review. It also reverts the tool registry and the max_tokens change that other teams wanted, and reverting the sort invalidates every tenant's entry once more, one write per tenant.</li>
<li><strong>Forward fix.</strong> Delete the trace line from the template and the trace_id from template_vars, keeping the registry and sort. Smaller blast radius for the features, but it is new code under incident pressure, and the cost accrues while it is reviewed and deployed.</li>
</ul>
<p>Choose by deploy latency: if a reviewed one-line fix ships in under an hour, the forward fix; if not, roll back and reapply the release without the trace line. The constraint conflict is support's need for a trace id in transcripts against the cost; it resolves by moving the id out of the prompt, since the model has no use for it. Join transcripts to traces on the conversation and request ids in your own logs.</p>
<p>Failure mode of the forward fix: someone moves the trace id to the end of the newest user message instead of removing it. That keeps the cache (the history is append-only) but sends an identifier the model may repeat in answers, and the next template change can move it back above the breakpoint. A CI test that renders two requests and asserts byte equality up to the last breakpoint prevents the whole class.</p>

## Follow-ups

- *The rendered diff shows the trace line, and also that two tenants' tool lists differ in a description field between pods. Does that change the ranking?* It adds a second, smaller cause for those tenants; a non-deterministic description is a per-pod prefix and caps their read share after the trace fix.
- *How do you prove the fix worked within ten minutes?* cache_read_input_tokens on consecutive requests of one conversation returns to roughly the prefix size, and cache_creation drops to the new tokens per turn.
- *What else in this diff would you flag in review?* `load_tools(ctx.tenant)` makes the tool list tenant-dependent, so tenants no longer share a cached tool prefix; harmless here because tenants are isolated by their system prompts anyway, but worth stating.

## Common mistakes

- Picking the tool sort because it is the change closest to the start of the prefix, without checking whether it would recover.
- Trusting the cost panel because it did not move.
- Rolling back without stating what the rollback reverts besides the cause.
- Moving the trace id later in the prompt instead of out of it.
