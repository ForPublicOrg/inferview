## Question

<Callout kind="interview" label="The prompt">
"We want to stop running our own agent loop. Should we move to a hosted agent platform, an agent SDK, or keep building?"
</Callout>

A health insurer runs a hand-written agent loop, maintained by three engineers, for two workloads. **Appeals**: an agent reads a member's claim history and clinical notes, drafts an appeal decision, and files it after a nurse reviewer approves; about 1,200 sessions a day, each running around 10 minutes plus a wait for review. **IT runbooks**: an agent diagnoses internal infrastructure alerts with shell access to a jump host and read-only cloud APIs; about 400 sessions a day, no member data. The insurer's model agreement includes a HIPAA Business Associate Agreement. The CISO requires that credentials for internal systems never enter an environment where model-written code runs, and audit wants every tool call for a member retrievable for six years. The CTO wants the loop off the team's plate within two quarters.

Make the build-versus-rent call and write the memo.

## Answer

<Depth>
<Fragment slot="short">
<p>Split by data class. Appeals stay in the insurer's environment on an agent SDK, because the hosted platform that fits best stores session history server-side and is not eligible for HIPAA BAA coverage as of 28 October 2026. The IT runbook agent moves to the hosted platform with a self-hosted sandbox, which removes most of the loop work for that workload and keeps execution on the insurer's hosts. The audit log is the insurer's store under both, and credentials sit behind a proxy under both.</p>
</Fragment>
<Fragment slot="long">
<p><b>Two defensible answers.</b> Option 1, the split: rent for runbooks, SDK for appeals. Cost: two runtimes, two sets of on-call knowledge, two upgrade tracks. Option 2, one SDK for both workloads inside the insurer's network. Cost: the team keeps sandboxes, session storage and credential plumbing for runbooks too, and the CTO's goal is only half met. Option 2 wins if the team cannot staff two runtimes; Option 1 wins if the goal is to free engineers, since runbooks have no member data and are the workload a hosted harness fits.</p>
<p><b>Controls tested per option.</b> Session log: the hosted platform keeps it server-side (deletable through the API); the Claude Agent SDK writes JSONL to local disk unless a <code>SessionStore</code> adapter mirrors it; the OpenAI Agents SDK uses whatever session class you pick. Audit therefore needs the insurer's own event store fed from every runtime, plus a daily reconciliation of event counts per session against the runtime's history. Credentials: the hosted platform's vault-and-proxy pattern keeps tokens out of the sandbox; the SDK path needs the same pattern built in front of claims and clinical systems. Tracing: if an OpenAI-based SDK is chosen, default tracing exports inputs and outputs to OpenAI and must be replaced with the insurer's processor.</p>
<p><b>Cost, computed.</b> Runbooks on the hosted platform: say 400 sessions a day at 15 running minutes is 100 session-hours a day, $8 a day at $0.08 per session-hour, about $240 a month. Tokens cost the same rented or built. The comparison is $240 a month against the share of three engineers' time the runbook loop takes today.</p>
<p><b>Approvals.</b> The nurse's approval must be authenticated server-side and bound to the pending item; the SDK docs say restoring run state does not authenticate the snapshot or the reviewer. Filing the appeal carries an idempotency key, because approval permits a call and does not make it exactly-once.</p>
<p><b>Failure mode.</b> The adapters around the SDK (session mirroring, trace processor, credential proxy, approval service) become a private harness that one engineer understands. Give them an owner, tests and a runbook, or the insurer has rebuilt the loop it wanted to stop maintaining.</p>

### The memo

**Decision.** IT runbooks move to the hosted agent platform with a self-hosted sandbox on the jump-host network. Appeals move from the hand-written loop to an agent SDK inside the insurer's environment.

**Controls kept.** Every tool call and model turn is mirrored to the insurer's event store, reconciled daily against the runtime's history. Credentials for internal systems are injected by a proxy at egress and never present in a sandbox. Approvals are authenticated by the insurer's approval service and bound to server-held pending items; side-effecting tools carry idempotency keys.

**What we give up.** A single runtime; vendor-maintained sandboxes and session storage for appeals; two quarters of one engineer building the appeals adapters.

**Risks.** Event mirroring drops records during an incident (mitigated by reconciliation and an alert on mismatch). A vendor harness change alters runbook behaviour without notice (mitigated by a nightly eval on recorded alerts).

**Reversal condition.** Appeals move to the hosted platform when its documentation lists eligibility under the insurer's BAA and the contract covers session storage. Runbooks move back in-house if reconciliation mismatches persist past a set threshold for a month.

### Checklist

- Classifies the workloads by data before choosing a runtime, and lets the classification decide per workload
- Rules out a hosted platform for regulated data only on a documented eligibility fact, dated, not on a general distrust of vendors
- Names who holds the session log, the sandbox, the credentials and the upgrade schedule under each option
- Chooses between one runtime for every workload and a split by data class, with the cost of each stated
- Puts the audit record in the company's own store under every option, with a completeness check against the source
- Keeps credentials for internal systems out of the sandbox with a proxy or vault pattern, whichever runtime is chosen
- Treats approvals as needing server-side authentication and idempotency keys on side-effecting tools, not as a property of the SDK
- Computes the hosted runtime cost from session-hours and compares it with the engineering time it replaces
- Writes a decision memo with the reversal condition (what eligibility or contract change would move the regulated workload)
- States a failure mode of the recommendation, such as the adapters becoming an undocumented private harness

## Follow-ups

- *Audit says a sampled record is acceptable for runbooks but not appeals. Does that change the design?* It removes reconciliation cost for runbooks only; appeals keep full mirroring.
- *The SDK you chose for appeals ships a breaking change in a minor version. What is your upgrade policy?* Pin, upgrade on a schedule as a reviewed change, run the appeals golden set before rollout.

## Common mistakes

- One answer for both workloads without classifying their data.
- Ruling out the hosted platform on vendor distrust rather than on a dated eligibility fact, or ignoring that fact.
- Leaving the audit record in the vendor's retention policy.
- Assuming the SDK's approval feature authenticates the reviewer.
- Counting token cost as a difference between renting and building.
