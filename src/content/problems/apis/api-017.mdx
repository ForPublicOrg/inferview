## Question

<Callout kind="interview" label="The prompt">
"When should you use LangChain vs build from scratch?" Then the follow-up from the same family: "What is LangGraph and when would you use it over LangChain?"
</Callout>

Make it concrete. Service A summarises support tickets: one model call with a fixed prompt, structured output, 50,000 calls a day. Service B is an approval workflow: an agent drafts a refund, waits up to two days for a manager's approval, then executes it, and must survive deploys and crashes while it waits. Would you use a framework for either?

## Hints

<details class="hint"><summary>Hint 1</summary><p>What would you have to build yourself for each service if you used no framework at all?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which of the two has a problem that is mostly about state, not about calling a model?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Service A: no framework. It is one call with a prompt and a schema; the provider SDK plus your own retry and validation code is a few dozen lines, and you can read the exact request. Service B: yes, for the state, not the model calls. A graph runtime with durable checkpoints and human-in-the-loop interrupts, such as LangGraph, solves the hard part (pause for days, resume after a crash) that you would otherwise build on a workflow engine yourself.</p>
</Fragment>
<Fragment slot="long">
<p>What a framework buys: provider abstraction, a standard message format, tool-calling loops, tracing hooks, and for LangGraph a checkpointed state machine with interrupts. What it costs: prompts and calls you did not write, defaults that change between versions, and a lag before new provider features are exposed.</p>
<p>Service A has none of the problems a framework solves. Its risk is cost and correctness at 50,000 calls a day, which you control best by owning the prompt, the cache-friendly layout and the validation. A framework's structured-output helper that silently re-prompts on validation errors is exactly the hidden extra call you do not want at that volume.</p>
<p>Service B's hard problem is durable waiting. LangGraph saves state per thread at each step through a checkpointer and pauses with <code>interrupt()</code>; a manager's decision resumes it with <code>Command(resume=...)</code>. The detail to get right: on resume the interrupted node runs again from its start, so the refund call must sit after the interrupt or be idempotent. Alternatives are a workflow engine (Temporal, a queue plus a state table); choose by what the team already runs.</p>
<p>Either answer is defensible if you name the trade-off. The answer that fails is "always" or "never".</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>You chose no framework for A. A year later there are twelve such services. Still no framework?</em> Probably a thin internal library, not a framework: shared retry, logging, prompt rendering and provider adapters, owned by the team.</li>
<li><em>How do you avoid lock-in for B?</em> Keep business logic in plain functions the graph calls, and keep prompts in your repository, so moving to another runtime rewrites the wiring, not the logic.</li>
<li><em>LangChain or LangGraph?</em> LangChain 1.x's <code>create_agent</code> runs on LangGraph and suits a standard tool-calling agent with middleware; LangGraph directly suits custom control flow and explicit state.</li>
</ul>
</Fragment>
</Depth>

Two facts make the answer concrete. LangChain 1.0 (22 October 2025) narrowed the library to `create_agent` built on LangGraph, moved older chains to `langchain-classic`, and promised no breaking changes until 2.0, which answers the "it changes too often" objection for code written against 1.x. And job descriptions do ask for it: in one 2026 analysis of 889 postings, 18.8% named LangChain and 8.0% LangGraph. Knowing it well is useful; reaching for it by default is a different decision.

## Follow-ups

- *What would make you remove a framework you adopted?* When most incidents trace to the gap between what it sent and what you thought it sent, and the features you use are a few calls.
- *How do you evaluate a framework before adopting it?* Build the hardest path of your service on it in a spike, read every request it sends, and check how it exposes the provider features you need.
- *DSPy?* A different bet: prompts optimised against a metric. Worth it only with an eval metric you trust.

## Common mistakes

- Answering about frameworks in general without looking at the two services.
- Choosing a framework for the model calls when the real problem is durable state.
- Ignoring that a resumed LangGraph node re-runs its code before the interrupt.
- Citing old APIs (`create_react_agent`, legacy chains) as current.
