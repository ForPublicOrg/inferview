## Question

<Callout kind="interview" label="The prompt">
"When should you use LangChain versus build from scratch?" Asked about a specific service, in a design review, by a reviewer who spent last quarter on call for a LangChain service.
</Callout>

The service triages inbound support email for a SaaS company: classify the email, look up the account with one of three internal tools, draft a reply, and either send it or queue it for an agent. About 40,000 emails a day. Drafts above a refund amount wait for a support lead, usually within an hour, sometimes overnight. The team is four Python engineers; one has run LangGraph in production, none has run LangChain 1.x. The reviewer's position: "No LangChain. Last time it made calls we never wrote and nobody could tell us why a run stopped."

Do you use LangChain 1.x `create_agent`, LangGraph directly, or plain code over the provider SDK? Answer the reviewer.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask the reviewer which of their incidents came from the framework's behaviour and which from the team not knowing it.</p></details>
<details class="hint"><summary>Hint 2</summary><p>What has to survive a deploy while a draft waits overnight, and what would you write to make that true without a framework?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>LangGraph directly for the overnight wait, plain provider calls inside the nodes. The wait needs checkpointed state and an interrupt that survives deploys, which is the part worth renting. The model calls are a fixed classify-lookup-draft sequence with one short tool loop, which gains little from <code>create_agent</code> and would add a loop with its own defaults. The reviewer's two complaints become requirements: log every rendered request at the HTTP layer, and set and alert on every step cap.</p>
</Fragment>
<Fragment slot="long">
<p>The reviewer is describing two failure classes, and both are addressable without banning the library. "Calls we never wrote" means the team did not log what reached the provider; a wrapper on the HTTP client that records each request and a counter of model calls per email make extra calls visible within a day. "Nobody could tell why a run stopped" means stop reasons were not recorded. <code>create_agent</code> binds a recursion limit of 9,999 super-steps, so a looping run is stopped by your own budget or not at all; the fix is an explicit limit and a metric on the stop reason.</p>
<p>The overnight wait is what plain code makes expensive: a state table, a resume path, deploy-safe workers and idempotent sends. LangGraph's checkpointer and <code>interrupt()</code> provide it, and one engineer has run it. The cost is that a resumed node runs again from its start, so the send must sit in its own node after the approval and carry an idempotency key, or a deploy during the wait sends the reply twice.</p>
<p>The quantity to choose is the step cap. The happy path is a handful of super-steps; set a cap with headroom above the longest run in the golden set, alert at a fraction of it, and route runs that hit it to the human queue. A cap of 9,999 is not a cap at 40,000 emails a day.</p>
<p>When the reviewer wins: if the team cannot staff a LangGraph owner on call, a queue plus a pending-drafts table keeps everything in code the team already debugs. That is a defensible answer; its cost is owning the resume path forever.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The reviewer accepts LangGraph but asks for <code>create_agent</code> to be banned too. Do you agree?</em> Yes for this service; its middleware solves problems this pipeline does not have.</li>
<li><em>How would you know in a month whether the decision was right?</em> Time to root cause per incident, and model calls per email against the calls the code makes on purpose.</li>
</ul>
</Fragment>
</Depth>

The answer turns on separating the two things a framework offers. LangChain 1.0 (22 October 2025) narrowed the library to `create_agent` on the LangGraph runtime, with middleware and a promise of no breaking changes until 2.0. That answers "it changes too often" for code written against 1.x, but not "it does things we did not ask for": that is answered by logging and explicit limits, whatever the runtime.

## Follow-ups

- *A second team wants `create_agent` for a research agent with an open-ended tool loop. Same answer?* No. An open-ended loop with summarisation and approval middleware is the shape it was built for; the logging and cap requirements still apply.
- *The team later needs a second provider. Does LangGraph make that harder?* Not if model calls go through the team's own client inside nodes; it would if prompts lived in framework templates.

## Common mistakes

- Answering about frameworks in general instead of this service's wait and volume.
- Treating the reviewer's incidents as proof against the library rather than as missing logging and limits.
- Putting the send in the same node as the interrupt, so a resume sends twice.
- Leaving the bound 9,999 limit in place and calling it a cap.
- Citing `create_react_agent` from `langgraph.prebuilt` as the current API.
