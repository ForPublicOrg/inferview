## Question

<Callout kind="interview" label="Interview question">
"Our support product runs 14 prompts on <code>claude-sonnet-4-5-20250929</code>. It retires on 30 November. Today is 28 October. On the replacement, 12 prompts pass their evals and 2 regress. Walk me through the next 33 days."
</Callout>

Two of the 14 prompts run inside an agent loop with tools that write to the ticketing system. The regressions are on the ticket-summary prompt (a structured-output prompt that used assistant prefill) and the escalation classifier (which sets `temperature: 0`).

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask to see the raw API responses for the failing eval cases, not only their scores.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask for token counts per request on both models from the eval run, not only pass rates.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask which API version header the production client sends.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>First check whether the two regressions are request-shape failures, because both prompts use features the new generation rejects: Claude 4.6 and later return 400 on a prefilled assistant message, and API version 2026-10-21 removes <code>temperature</code>, so the summary prompt moves to structured outputs and the classifier drops the parameter. Re-run evals with repeats, re-measure tokens (the newer tokenizer produces about 30 percent more for the same text), then shadow traffic for the read-only prompts, ramp users by stable hash, and let in-flight agent sessions finish on the old model. There is no option to keep the old model past 30 November, so any prompt still regressing on day 25 ships degraded with a written sign-off or falls back to a non-model path.</p>
</Fragment>
<Fragment slot="long">
<p><b>Week 1: make the requests valid.</b> Pin model ID and API version per prompt. Fix request shape: replace prefill with structured outputs; drop sampling parameters; map any <code>thinking</code> settings to what the replacement accepts. Re-run the full eval suite with several trials per case and diff per prompt. If the two "regressions" were 400s, they disappear here and the real comparison starts.</p>
<p><b>Week 1 to 2: cost and context.</b> Compare tokens per request. About 30 percent more tokens for the same text raises cost and moves prompts closer to context limits; the cheaper cache-read multiplier on Sonnet 5.5 offsets part of it for cached prefixes. Update budgets and alerts before traffic moves.</p>
<p><b>Week 2 to 3: shadow and ramp.</b> Shadow the read-only prompts and compare outputs offline. The two agent prompts are not shadowed with write tools; they are evaluated on recorded sessions with tools stubbed. Ramp users by a stable hash of user ID and experiment name (1, 5, 20, 50, 100 percent), comparing resolution rate and escalation rate at each step.</p>
<p><b>Week 4: the deadline.</b> Anything still regressing gets a decision memo: ship degraded with the measured cost, or route that prompt's job to a non-model fallback. A prompt left on the old model fails on 30 November, so "wait" is not an option.</p>
<p><b>Failure mode of this plan.</b> Ramping by user keeps experiences consistent, but agent sessions that started on the old model and resume after a ramp step switch models mid-session. Pin the model per session at session start.</p>
</Fragment>

<ul>
<li><em>The escalation classifier still regresses on day 25. Ship degraded or switch it to rules, and who signs off?</em></li>
<li><em>How long does each ramp step run?</em></li>
<li><em>What do you monitor for the first week after 100 percent?</em></li>

The ramp rule, as code. Users already in treatment stay there as the percentage grows, because the threshold only rises:

```python
import hashlib

def arm(user_id, experiment, treatment_pct):
    h = int(hashlib.sha256(f"{experiment}:{user_id}".encode()).hexdigest()[:8], 16)
    return "treatment" if (h % 10_000) < treatment_pct * 100 else "control"

users = [f"u{i}" for i in range(20_000)]
share = sum(arm(u, "sonnet-5-5-migration", 5) == "treatment" for u in users) / len(users)
moved_out = sum(arm(u, "sonnet-5-5-migration", 5) == "treatment"
                and arm(u, "sonnet-5-5-migration", 20) == "control" for u in users)
print(f"treatment share at 5%: {share:.3f}")
print("users who left treatment when ramping to 20%:", moved_out)
```

```text
treatment share at 5%: 0.052
users who left treatment when ramping to 20%: 0
```

## Follow-ups

- *Why hash by user and not by request?* Per-request assignment shows one user both models in one conversation, which contaminates satisfaction metrics and makes answers inconsistent.
- *The provider changes behaviour under the same model ID.* Pinned snapshots reduce this; a daily run of a small eval set against production configuration catches the rest.
- *Next year the same migration happens again.* The pipeline above should be routine: eval suites per prompt, request-shape tests per API version, and a ramp switch, maintained between migrations rather than rebuilt for each.

## Common mistakes

- Reading eval failures as quality regressions when they are 400 responses.
- Comparing average pass rate across all prompts and missing the two that regress.
- Ignoring the token-count change, so budgets and context limits break after the switch.
- Shadowing an agent with write tools enabled.
- Starting the migration with less time than the ramp needs.
