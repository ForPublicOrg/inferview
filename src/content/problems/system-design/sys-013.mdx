## Question

<Callout kind="interview" label="Interview question">
"How do you roll out a new model version without breaking existing prompts? How would you A/B test it?"
</Callout>

Assume a product with dozens of prompts in production, some of them inside agent loops, on a hosted model that the provider has just announced it will retire.

## Hints

<details class="hint"><summary>Hint 1</summary><p>A model swap can change the request shape and the token count, not just the answers.</p></details>
<details class="hint"><summary>Hint 2</summary><p>What has to run before any user sees the new model, and what only real traffic can tell you?</p></details>
<details class="hint"><summary>Hint 3</summary><p>How do you make sure the same user stays on the same model for the whole experiment?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Pin the model ID and API version per prompt so nothing changes by accident. For a candidate model, first fix the request shape (newer models and API versions reject some parameters), then run every prompt's eval suite with repeats and compare, then shadow real traffic without showing results, then ship to a small slice of users chosen by a stable hash, compare outcome and guardrail metrics against control, and widen in steps. Long-running sessions finish on the old version. Start early: the provider's notice period is the deadline.</p>
</Fragment>
<Fragment slot="long">
<p>Pinning. Every prompt has a config with model ID, API version, prompt version and parameters. Nothing uses an alias that silently moves. That turns "the model changed" into a deploy you can see and revert.</p>
<p>Request shape. A new model can reject what the old one accepted. Anthropic's API version 2026-10-21 rejects temperature, top_p and top_k, Claude 4.6 and later reject assistant-message prefill, and Claude 4.7 and later reject the old thinking parameter. Tokenization moves too: Claude 4.7 and later produce about 30 percent more tokens for the same text, which shifts cost and context limits. So the first migration step is making the requests valid and re-measuring tokens.</p>
<p>Offline. Run each prompt's eval suite on both models, several trials per case, and diff per prompt: pass rates, judge scores, latency, tokens, cost. Prompts that regress get prompt changes and a re-run before moving on.</p>
<p>Shadow. Send a copy of real requests to the candidate and log both outputs without showing the new one. This catches input shapes the eval set never had. It doubles model cost for the shadowed share and must not trigger side effects, so agents with tools are shadowed only with read-only tools.</p>
<p>A/B. Assign users, not requests, by hashing the user ID with the experiment name, so a user sees one model throughout and a new experiment reshuffles assignments. Ramp 1, 5, 20, 50, 100 percent, comparing the product's outcome metric and its guardrails at each step. A hash rule of the form "hash mod 10,000 below the percentage" keeps everyone already in treatment there as the percentage grows.</p>
<p>Sessions in flight. Agents and long conversations finish on the version they started on, with old and new versions running side by side until the old sessions drain, the rainbow deployment Anthropic describes for its agents.</p>
<p>Deadline. Anthropic gives at least 60 days before retirement, after which requests fail; for example, a Sonnet 4.5 snapshot deprecated on 30 September 2026 retires on 30 November 2026. The pipeline above has to fit in that window, so it should be routine, not a project.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The new model is better on average and worse on one prompt.</em> Migrate the others; keep that prompt on the old model until fixed, if the deadline allows, and treat the regression as a prompt bug to fix on the new model.</li>
<li><em>How long does each ramp step run?</em> Long enough to reach the sample size decided before the test for the main metric, and at least one weekly cycle.</li>
<li><em>What do you monitor after 100 percent?</em> The same outcome and guardrail metrics, cost per request, and the token counts, which change with the tokenizer.</li>
</ul>
</Fragment>
</Depth>

The bucketing rule from the long answer, as code:

```python
import hashlib

def arm(user_id, experiment, treatment_pct):
    h = int(hashlib.sha256(f"{experiment}:{user_id}".encode()).hexdigest()[:8], 16)
    return "treatment" if (h % 10_000) < treatment_pct * 100 else "control"

users = [f"u{i}" for i in range(20_000)]
share = sum(arm(u, "model-2026-11", 5) == "treatment" for u in users) / len(users)
moved_out = sum(arm(u, "model-2026-11", 5) == "treatment" and arm(u, "model-2026-11", 20) == "control"
                for u in users)
print(f"treatment share at 5%: {share:.3f}")
print("users who left treatment when ramping to 20%:", moved_out)
```

```text
treatment share at 5%: 0.049
users who left treatment when ramping to 20%: 0
```

## Follow-ups

- *Why hash by user and not by request?* Per-request assignment shows one user both models, which contaminates satisfaction metrics and makes conversations inconsistent.
- *Can you A/B test a prompt the same way?* Yes, with the prompt version as the arm; the eval gate still runs first.
- *The provider changes behaviour under the same model ID.* Pinned snapshots reduce this; a daily canary run of a small eval set on production config catches the rest.

## Common mistakes

- Swapping the model ID and fixing errors as they appear in production.
- Comparing averages across all prompts and missing a regression in one.
- Randomising per request.
- Starting the migration in the last two weeks of the deprecation window.
