## Question

<Callout kind="interview" label="The prompt, as a prep site lists it">
"How would you define success metrics for an AI-oriented feature or product?"
</Callout>

Answer for a concrete feature so the metrics are not abstract: an AI answer box at the top of a search results page, which writes a cited answer to the query. The prep site that reports this question attributes it to Perplexity's loop; the feature here is our example, not theirs.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Separate what the user gets (outcome) from what the model does (quality) from what it costs.</p></details>
<details class="hint"><summary>Hint 2</summary><p>For every metric you want to raise, name the metric that would show you raised it the wrong way.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Offline scores tell you a change is safe to ship; online metrics tell you it helped. You need both.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Four layers. An outcome metric that says users got what they came for (for the answer box: sessions that end satisfied without reformulating the query). Guardrail metrics that catch gaming it (citation accuracy, answers that users contradict by clicking elsewhere, complaint rate). Offline quality metrics on a fixed set run before every change (groundedness, correctness, consistency over repeated runs). And operating metrics (latency to first token, cost per answered query). Ship on offline gates, judge success online against a holdout.</p>
</Fragment>
<Fragment slot="long">
<p>I start from the user's job. Someone typing a query wants an answer they can trust, quickly. So the outcome metric is about task completion: share of sessions where the user does not reformulate or bounce to another result within a short window after reading the answer. Clicks on citations are ambiguous (they can mean trust or doubt), so I would read them alongside reformulation, not alone.</p>
<p>Guardrails come next, one per way the outcome could be gamed. Shorter, more confident answers can reduce reformulation while being wrong, so I track citation accuracy (does the cited passage support the sentence) and a sampled correctness score from a judge that has been checked against human labels. I also track the complaint or report rate and answers on sensitive topics routed to a stricter path.</p>
<p>Offline metrics gate releases. A fixed set of real queries with reference answers, run on every prompt, retrieval or model change: retrieval recall, groundedness, correctness, and consistency across repeated runs (pass^k), because the same query should not flip between right and wrong. Anthropic's research team started such a set with about twenty real queries; size matters less than realism at first.</p>
<p>Operating metrics close the loop: time to first token at P50 and P95, cost per answered query, and the share of queries where the box declines to answer. A box that answers everything is not a success.</p>
<p>Finally, causality. Ship behind an experiment with a holdout that sees the page without the box, and compare the outcome and guardrails between the two groups.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Which one metric would you put on a dashboard for the CEO?</em> The outcome metric, with its main guardrail next to it. One number alone invites gaming.</li>
<li><em>Your judge says quality went up, users say it went down. Who is right?</em> The users, until the judge is re-checked on the new answers against fresh human labels. Judges drift when the answer style changes.</li>
<li><em>How do you measure the cost of a wrong answer?</em> Sample answers flagged by users or by the judge, label severity, and track the rate of high-severity errors separately from average quality.</li>
</ul>
</Fragment>
</Depth>

The answer above is organised the way a grader listens for it: outcome, guardrail, offline gate, operations, causality. The specific metrics change with the feature. For a coding assistant the outcome might be accepted suggestions that survive review; for a support bot, resolution without a human with re-contact as the guardrail. The structure does not change.

## Follow-ups

- *How long do you run the experiment?* Long enough to cover weekly patterns and novelty effects, and with a minimum sample decided before launch, not when the numbers look good.
- *The model provider ships a new version. Which metrics do you rerun?* All offline gates, then a small online slice compared with the current model before switching everyone.
- *What is a leading indicator you can see on day one?* Reformulation and decline rates; retention and complaint trends lag.

## Common mistakes

- Naming only model metrics (accuracy, BLEU) and no user outcome.
- Naming only engagement (clicks, time on page), which a worse answer can raise.
- No guardrail, so the metric can be improved by being confidently wrong.
- No comparison group, so seasonal traffic changes are read as product impact.
