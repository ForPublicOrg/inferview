## Question

<Callout kind="interview" label="Interview question">
"We're self-hosting a 70B model for this assistant. Convert the expected traffic into a number of GPU nodes."
</Callout>

What you get when you ask:

- Model: Llama 3.1 70B, weights and KV cache in BF16 (2 bytes per value). From its config: 80 layers, 8 key-value heads, head dimension 128 (hidden size 8,192 divided by 64 attention heads).
- Hardware: nodes of 8 GPUs with 80 GB each. Keep 10 percent of memory back for activations and fragmentation.
- Size every sequence at the worst case of 8,192 tokens (prompt plus output).
- Traffic: 1,000,000 requests a day; assume peak is 3 times the average.
- Latency per request, measured: 0.5 s to first token, then 300 output tokens at 40 ms each.
- Plan each node at 70 percent of the concurrency its KV memory allows.

How many nodes do you need at peak?

## Hints

<details class="hint"><summary>Hint 1</summary><p>KV cache per token is 2 (keys and values) × layers × KV heads × head dimension × bytes per value.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Memory left for KV on a node is total memory minus the reserve minus the weights. Divide by the bytes one 8,192-token sequence needs.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Little's law: requests in flight = arrival rate × time each request spends in the system.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p><b>4 nodes.</b> KV cache is 320 KiB per token, 2.5 GiB per 8,192-token sequence. A node has 436 GB left after the reserve and the 140 GB of weights, so it holds 162 sequences, 113 at 70 percent. Peak traffic is 34.7 requests a second and each spends 12.5 s in the system, so 434 are in flight: 434 / 113 = 3.8, round up to 4.</p>
</Fragment>
<Fragment slot="long">
<p>KV per token: 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes. Per sequence: 327,680 × 8,192 = 2,684,354,560 bytes, 2.5 GiB.</p>
<p>Memory per node: 8 × 80 GB = 640 GB; keep 10 percent back, 576 GB; subtract weights, 70 billion parameters × 2 bytes = 140 GB; 436 GB for KV. 436 GB / 2.68 GB = 162 sequences. At 70 percent, 113.</p>
<p>Demand: 1,000,000 / 86,400 = 11.6 requests per second on average, 34.7 at peak. Time in system: 0.5 + 300 × 0.04 = 12.5 s. In flight at peak: 34.7 × 12.5 = 434.</p>
<p>Nodes: 434 / 113.4 = 3.83, so 4. I'd say out loud that this is memory-bound sizing at worst-case length, and that the 40 ms per token was measured at some batch size; if the node gets slower as concurrency rises, the latency term grows and so does the answer. Then I'd add one node for failure tolerance, which is a separate decision from peak capacity.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Average sequences are 3,800 tokens, not 8,192. Does that change it?</em> With an allocator that does not reserve the worst case, a node holds about 350 such sequences and two nodes cover the peak on memory alone. Decode speed at that concurrency then becomes the limit to check.</li>
<li><em>What if you used 64 heads instead of 8 KV heads?</em> The KV estimate is eight times too big and you buy eight times too many nodes.</li>
<li><em>Why not size by FLOPS?</em> Decode reads all the weights and the KV cache for every token, so memory bandwidth (3.35 TB/s on an H100 SXM) limits it before peak FLOPS does.</li>
</ul>
</Fragment>
</Depth>

The band of 3 to 6 nodes accepts the answer without the 70 percent headroom (434 / 162 = 2.7, so 3) and answers that add a spare node or round the reserve differently. Answers in the tens usually used 64 KV heads or forgot that one node has eight GPUs.

## Follow-ups

- *How would you check the plan before buying?* Load-test one node at increasing concurrency, record time to first token and per-token latency at each level, and find the concurrency where P95 latency breaks the target. That number replaces the memory-derived 113.
- *Traffic doubles next quarter. What scales?* In-flight requests double, so nodes roughly double, unless shorter outputs or a smaller model cut the 12.5 s.
- *When does the API beat self-hosting?* When traffic is spiky or small enough that the nodes sit idle most of the day. Bring the GPU-hour price as an input from your provider.

## Common mistakes

- Using attention heads instead of KV heads in the cache formula.
- Forgetting the weights take 140 GB of the node before any request arrives.
- Sizing from average traffic instead of peak.
- Treating Little's law output as GPUs instead of concurrent requests.
