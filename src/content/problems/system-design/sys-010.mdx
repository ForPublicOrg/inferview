## Question

<Callout kind="interview" label="Interview question">
"Design a real-time voice assistant. The first audio of each reply should start in under a second."
</Callout>

The assistant answers account and order questions for an online retailer, in the browser and over the phone, and can look up orders through an internal API. Sessions are typically a few minutes. The target in the prompt is the interviewer's; treat it as a P50 and ask about P95.

## Hints

<details class="hint"><summary>Hint 1</summary><p>List every stage between the user stopping talking and the first audio of the reply, with a time for each.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Which stages must finish before the next can start, and which can overlap?</p></details>
<details class="hint"><summary>Hint 3</summary><p>If the whole conversation is re-sent every turn, what happens to cost per minute as the call gets longer?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Budget the critical path, not the components: endpointing, transcript, network, model time to first token, TTS first audio, buffering. With streaming between every stage a published example adds to about 680 ms at P50 and 1,560 ms at P95; waiting for the full text before speaking pushes it past two seconds. Choose speech-to-speech for the lowest latency and a chained pipeline when you must check text before it is spoken; keep a transcript either way. Handle barge-in, connect browsers over WebRTC with ephemeral secrets, and cap or summarize long sessions because each turn re-bills the history.</p>
</Fragment>
<Fragment slot="long">
<p>Scope. Channels (browser and phone), languages, actions (order lookup only, or changes too), and both latency targets. I'd write down P50 under 1 s and ask for a P95, because the slow turns are the ones people notice.</p>
<p>Budget. From ElevenLabs' example, P50 / P95 in ms: capture and endpointing 120 / 280, speech-to-text 60 / 150, network 60 / 160, model time to first token 250 / 600, TTS first audio 110 / 220, buffering 80 / 150. That sums to about 680 / 1,560 only if TTS starts on the first clause. If TTS waits for a 60-token reply at 25 ms a token, the P50 becomes 2,180 ms. So the design is mostly about overlap.</p>
<p>Architecture. Browser clients get an ephemeral secret from our server and connect over WebRTC; phone calls come in through SIP to a media server. Two options for the model: a speech-to-speech session (fewest hops, handles interruptions natively) or STT, a text agent and TTS (each stage replaceable, text checkable before speech). For an order assistant with low-risk actions I'd start speech-to-speech, with the transcript stream feeding logging and a moderation check.</p>
<p>Turn-taking. Semantic VAD instead of a fixed silence threshold, so people are not cut off mid-thought. On barge-in: stop playback at once, truncate the model's record of its last reply to what was played, continue. Human conversation runs on very short gaps (a mode of 0 ms across ten languages in one study), which is why a one-second pause already feels long.</p>
<p>Tools. The order API sits on the critical path when called. Prefetch the account's recent orders at session start, and say a short line from a fixed set if a lookup takes long.</p>
<p>Cost. OpenAI's Realtime API counts user audio at 1 token per 100 ms and assistant audio at 1 per 50 ms, and re-sends the whole conversation each turn. At $32 in and $64 out per million audio tokens, a 10-turn call with 5 s of user and 10 s of assistant audio per turn costs $0.50; 20 turns cost $1.81. Caching the history and summarising old turns cut that; a session cap bounds it.</p>
<p>Reliability. Provider sessions and connections have limits (Gemini Live recycles connections about every 10 minutes and warns before it does), so reconnection with session resumption is part of the design. If the model is unavailable, fall back to a recorded message and a callback or a human.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>P95 is 2.4 s. What do you do first?</em> Break it down per stage on the slow turns; most often it is model time to first token under load or endpointing on noisy lines.</li>
<li><em>How do you evaluate it?</em> Recorded calls replayed through the system, scoring time to first audio percentiles, interruption handling, task success and transcript accuracy.</li>
<li><em>Can you moderate speech-to-speech output?</em> On the transcript stream, stopping playback on a hit; if no unchecked word may ever be spoken, use the chained pipeline.</li>
</ul>
</Fragment>
</Depth>

### Rubric check

**Problem navigation:** asked for P95 and channels before choosing a model shape. **Solution design:** critical path with overlap, transport with ephemeral credentials, barge-in, a fallback. **Technical excellence:** the stage budget with numbers, VAD choice, audio token accounting and how history makes long calls cost more per minute. **Communication:** said what speech-to-speech gives up, not just what it gains.

## Follow-ups

- *Users are in three languages.* Check that STT, the model and TTS support each, measure latency per language, and add each to the eval calls.
- *Can you cut cost per minute without hurting latency?* Cache the history, summarise turns older than a few minutes into text, and keep the system prompt stable so it caches.
- *The business wants every call recorded.* Store audio and transcript with consent, a retention period and access controls; that is also your eval data.

## Common mistakes

- Summing stage averages and calling it the latency, with no P95.
- Waiting for the model's full reply before starting speech.
- Putting the API key in the browser.
- Ignoring that each turn re-sends the history, so long calls cost much more per minute.
