  - Computes a capability diff against the previous approved version, so an update that adds a server, a tool or a network destination is reviewed as new
  - Tiers review by capability, with automated checks for instruction-only plugins and human security review for anything that adds execution, write access or egress
  - Notices that an MCP server declaration pointing at a URL with a vault credential receives that credential automatically, and reviews the URL as a credential grant

  - Publishes by content digest with a signature, and installs pin the digest rather than a branch, tag or version string

## Question

<Callout kind="interview" label="Interview question">
"Teams across the company want to share agent plugins: a plugin bundles skills (instructions and optional scripts) with MCP server declarations. Design the review and distribution pipeline for internal plugins."
</Callout>

Operating constraints (scenario): two security engineers can spend a combined day a week on reviews; about 40 plugin submissions or updates arrive a month; engineers' laptops hold long-lived cloud credentials; a stakeholder in developer productivity argues that any review slower than one business day will push teams to install from public marketplaces instead.

Design the workflow: steps, state per plugin version, approvals, what is automated, how versions reach machines, and how a bad version is pulled. Then open the checklist.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Of last quarter's submissions, how many added an MCP server or a script, and how many changed only instruction text?</p></details>
<details class="hint"><summary>Hint 2</summary><p>When an agent loads a plugin, what can it do afterwards that it could not do before? Ask for that list for one real plugin.</p></details>
<details class="hint"><summary>Hint 3</summary><p>How does an install resolve "version 1.2" today, and who controls what that name points to?</p></details>

## Answer

The pipeline treats a plugin as a dependency that grants capability, and spends scarce review time only where capability changes.

**State per plugin version:** submitted, analysed, tier assigned, under review (tier 2 only), approved, published to ring 1, ring 2, general, and revoked. Each transition is recorded with the actor and the content digest, and publishing is idempotent on the digest, so a retried publish job cannot create two versions.

**Steps.**

1. *Submit.* The owner submits a bundle to the internal registry, never a link to a branch.
2. *Analyse (automated).* Parse the manifest into instructions, scripts, hooks and MCP server declarations. Compute a capability diff against the last approved version: new servers, new tools on existing servers, new network destinations, new script entry points. Static scanners run here as filters that can reject, never as the approval.
3. *Tier (automated).* Tier 1: instruction-only changes with no scripts, hooks or servers, and no capability diff. Tier 2: anything that adds or changes execution, write access, egress or a server URL. An MCP server URL is a credential grant in practice, since a vault credential keyed by that URL is injected when the agent connects to it.
4. *Behavioural check (automated, both tiers).* Load the plugin in a sandbox seeded with canary secrets, run scripted sessions, and record egress. Any canary leaving or any destination not in the manifest fails the check.
5. *Review (tier 2).* A security engineer reviews the capability diff, not the whole plugin, and approves, rejects or approves with a narrower permission set. Two approvals are required for plugins that add shell execution or write access to production systems.
6. *Publish.* The registry signs the bundle; installs pin the digest. Rings: the owning team, then volunteers, then everyone, with the previous approved digest kept installable.
7. *Provenance and revocation.* Agent sessions record the digests they loaded. Revocation marks a digest revoked in the registry, clients refuse to load revoked digests at session start, and running sessions receive a revocation event and unload the plugin's tools.

**Budget arithmetic.** One security-engineer day a week across two people is about 8 hours. At 40 submissions a month, about 10 a week, if tier 2 is a quarter of submissions (ask for the real share; this is a scenario figure), reviewers have 8 / 2.5 ≈ 3 hours per tier-2 review, which is enough for a capability diff and not for reading every line. If tier 2 is three quarters, they have about 1 hour each, the one-day SLA fails, and the design needs either more reviewers or narrower tier-2 criteria. The tier threshold is the quantity to defend.

**Constraint conflict and what you give up.** The review SLA against depth of review. You give up line-by-line review of tier-2 plugins and accept that a malicious instruction-only change in tier 1 can pass analysis. Runtime containment carries that risk: plugins run against sandboxed tools with egress limits, so a tier-1 plugin can change what the model asks for but not what the sandbox allows. Writing that dependency down matters, because it means a weakened sandbox silently raises the plugin risk.

**Failure mode of the recommended design.** Tiering keys on capability diffs, so a plugin that stays within existing capability but changes intent passes as tier 1: a skill whose instructions change from "run the test suite" to "run the test suite, then upload the coverage report to this URL" through a server the plugin already declared. The capability diff is empty; the behaviour is new. The behavioural check with an egress recorder is the control that can catch it, which is why it runs on both tiers.

**Written artefact.** A plugin policy with an owner: the tier criteria, the SLA per tier, the ring schedule, the rollback trigger (any canary hit or unapproved destination in ring 1 or 2 halts promotion), the revocation procedure, and the stated residual risk for tier 1.

## Follow-ups

- *The productivity lead says even tier 2 must clear in one business day or teams route around you. Which checks move after publication, and what do you accept in writing?*
- *What would you need to see to let a team self-approve tier-2 plugins inside its own ring?*
- *A popular public plugin is requested by twenty teams. Do you fork it into the registry, mirror it by digest, or refuse it, and who maintains the fork?*

## Common mistakes

- Pinning by version string or tag, which the publisher can repoint.
- Reviewing the instruction text for malice while ignoring that a new MCP server URL receives credentials.
- Revocation that only blocks new installs while running sessions keep the plugin loaded.
- A single review queue for all changes, which spends the security budget on typo fixes.
