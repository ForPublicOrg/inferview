## Question

<Callout kind="interview" label="The prompt, as a prep site lists it">
"Design an agentic AI system to power customer support for Spotify."
</Callout>

Treat the company as a large consumer subscription service with several plan types, family accounts, payments through app stores and cards, and a support team. The prep site that reports the prompt lists it under Sierra's loop. Nothing here describes either company's real systems.

## Hints

<details class="hint"><summary>Hint 1</summary><p>List the actions support takes today (refund, change plan, fix playback, merge accounts) and which ones the agent may take on its own.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Where does the refund policy live: in the prompt or in a tool?</p></details>
<details class="hint"><summary>Hint 3</summary><p>An approval can take hours. What runs again when the agent resumes?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>One agent loop per conversation with a small set of typed tools over account, billing and playback systems, each tool enforcing policy in code. Low-risk actions run directly; money and account changes above a threshold pause for approval using a checkpointed graph, and side effects carry idempotency keys because resuming re-runs the step. Guardrails block before tools run, the agent acts with the user's identity, and releases are gated on repeated runs of real conversations (pass^k), including simulated users who act on their own accounts mid-conversation.</p>
</Fragment>
<Fragment slot="long">
<p>Scope. Channels (in-app chat first, voice later), languages, the action list and its risk tiers, and the cost of errors. I'd tier actions: informational (explain a charge), reversible (send a password reset, re-sync downloads), money or irreversible (refund, cancel, merge accounts).</p>
<p>Agent and tools. One loop with tools like `get_account`, `get_invoices`, `get_refund_eligibility`, `issue_refund`, `change_plan`, `diagnose_playback`, `handoff`. Eligibility is computed by code from billing rules and returns the refundable amount and the rule that applied; `issue_refund` refuses anything else with a typed error. The prompt explains policy so the agent asks good questions, but tools enforce it. If the business confirms that app-store payments can only be refunded by the store, those get a tool that explains where to ask, instead of a refund tool.</p>
<p>State and approvals. Conversation and tool state live in a checkpoint store keyed by thread. A refund above the auto-approve limit triggers an interrupt; a supervisor approves in a console; the graph resumes. In LangGraph, resuming re-runs the whole node from the start, so the refund lives in a node after the approval, keyed by thread and invoice, and a repeated call returns the first result.</p>
<p>Safety. Input guardrails run in blocking mode for this agent, since in the OpenAI Agents SDK they run in parallel by default and the agent might already have called a tool when one trips. Tool outputs (ticket text, emails) are data, not instructions. The agent authenticates as the user's session, so the backend enforces account ownership.</p>
<p>Evals. Real past conversations turned into tasks with checkable end states (refund row, plan state, ticket status), each run several times and reported as pass^k; tau-bench found agents far less consistent across repeats than single-run scores suggest. A dual-control set where the simulated user changes their plan or payment method mid-conversation, which tau2-bench showed is harder. Online: resolution without a human, refund reversal rate, re-contact rate, and handoff quality rated by agents.</p>
<p>Operations. Deploys keep old versions running until their conversations finish (rainbow deploys), cost per resolved conversation is tracked per intent, and the handoff carries a summary so the human does not re-ask.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A user claims they were charged twice and wants both refunded.</em> The billing tool shows the charges; eligibility decides; a disagreement goes to a human with the evidence attached. The agent cannot override the tool.</li>
<li><em>How do you handle a family plan where the requester is not the owner?</em> Account tools return the requester's role, and the action tools check it; the agent explains what the owner can do.</li>
<li><em>What do you build first?</em> Read-only diagnosis and explanation for the top intents, with handoff, then one action tier at a time behind the eval gate.</li>
</ul>
</Fragment>
</Depth>

### Rubric check

**Problem navigation:** action tiers and app-store payments came up before tools were drawn. **Solution design:** policy in tools, approvals as durable interrupts, a handoff with a summary. **Technical excellence:** node re-run semantics and idempotency keys, blocking guardrails, pass^k. **Communication:** each risky action had its control named next to it.

## Follow-ups

- *How do you roll out a prompt change?* Run the task set with repeats, ship to a small, stable slice of conversations by user hash, compare reversal and re-contact rates, then widen.
- *The billing system is down.* The eligibility tool returns a typed "unavailable" error; the agent tells the user the refund will be handled and creates a ticket; no retries loop.
- *Cost per conversation is too high.* Route intent classification and simple explanations to a smaller model, cache the static prompt and tool definitions, and cap steps per conversation.

## Common mistakes

- Writing refund policy into the prompt and trusting the model to follow it.
- Running the refund before the approval interrupt in the same node.
- Reporting one success rate from one run per task.
- Giving the agent a service account with access to every user's billing.
