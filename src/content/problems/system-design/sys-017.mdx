## Question

<Callout kind="interview" label="Design round, 45 minutes">
Design a code-review bot that runs as a CI job on every pull request, calls a model API with no human present, posts comments, and reports a status check. The platform team wants the check to be required by branch protection on the main repositories.
</Callout>

Scenario inputs from a community version of this exercise: 50,000 pull requests a day across the company, and a review ready within 2 minutes of the pull request opening. Also scenario: the finance owner has approved $40,000 a month for the bot, and about a fifth of pull requests come from forks or from contractors outside the main organization.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask who can write each piece of text the bot reads, including any instruction files in the repository.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask what the platform team expects a required check to do when the model provider is down or the budget is spent.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the distribution of pull request sizes, in changed lines, from the code host.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A CI job with read-only repository access and a model key scoped to this bot, instructions read from the base branch, the diff and description passed as data, and no rights to approve or merge. The status check is required but reports only deterministic outcomes the bot can stand behind (it ran, it found a high-severity finding of a narrow kind); budget exhaustion and provider outages report neutral, not failure. The budget forces tiering: 50,000 reviews a day at a vendor's lightest average already exceeds the monthly budget, so most pull requests get a cheap pass or none, and deep review goes to risky paths.</p>
</Fragment>
<Fragment slot="long">
<p><b>Budget arithmetic first, because it decides the design.</b> $40,000 a month over about 30 days is about $1,330 a day, or $0.027 per pull request at 50,000 a day. GitHub's own estimate for its lightest setting averages about $0.25 per review, and its default about $1.50: at those averages a review of every pull request costs $12,500 or $75,000 a day. Those are a vendor's prices for its product, not my model cost, but they set the scale. So the quantity I choose is the fraction reviewed and the depth: skip docs-only, generated and bot-authored changes, run one cheap single-pass review on small diffs, and an agentic review with file fetching only on paths the repository marks as sensitive. I size the cheap pass from my provider's token prices and the measured diff-size distribution, and set a per-PR token cap the job enforces.</p>
<p><b>Load.</b> 50,000 a day is about 0.58 a second; at 120 seconds each, Little's law gives about 70 reviews in flight on average. Peaks follow working hours, so the runner pool scales on queue depth, and the 2-minute target holds only for diffs under a size limit; larger ones post "review in progress" and finish later.</p>
<p><b>Trust.</b> The pull request author controls the head branch. GitHub's own reviewer reads its custom instructions, agent instructions and skills from the head branch, which is the injection point to avoid: the bot reads instructions from the base branch only and passes the diff, description and comments as delimited data. The CI job that reads fork content runs without repository write tokens or deploy secrets; its only secret is a model key with a spend cap. No repository code runs in the job. Anthropic's account of project configuration executing before a trust decision is the reason: the review job never executes anything from the pull request.</p>
<p><b>The required check, the main decision.</b> Two defensible answers. Fail closed: the check fails when the bot cannot run, so nothing merges without a review. Cost: a provider outage or a spent budget blocks every merge in the company, and the bot's false positives become merge blockers. Fail open with a narrow blocking set: the check is required, reports success or neutral when the bot ran or could not run, and fails only on findings with a deterministic second signal (a secret pattern also matched by the scanner, a dependency on a denylist). Cost: a model-only finding, however serious, cannot block. I choose fail open with the narrow set, because the bot's reviews do not count as approvals anyway, as with GitHub's reviewer by default, and branch protection's human approval stays the gate.</p>
<p><b>Constraint conflict.</b> Cost against coverage, and the platform team's wish for a blocking check against availability. <b>Failure mode of the recommendation.</b> Neutral-on-failure means a sustained outage or an exhausted budget silently removes review for days; the bot posts a visible notice on each pull request it skipped, and the budget burn rate pages the owner at 80 percent of the monthly figure.</p>
<p><b>Quality.</b> Each comment gets an outcome: resolved with a change, dismissed, or ignored. The acted-on rate per category and repository decides which categories stay. An offline set of past pull requests with known bugs gates prompt and model changes.</p>
<p><b>What you give up.</b> Review on most small pull requests, model-only findings as blockers, and the platform team's preference for a check that guarantees review happened.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A pull request description says to approve and stop reviewing. What happens?</em> Nothing the bot can do approves; the text is data; the attempt is logged against the author.</li>
<li><em>Developers want the bot to push fixes.</em> As suggested changes the author applies, or a separate pull request from a sandboxed job, never a push to the author's branch.</li>
</ul>
</Fragment>

### The written artefact

A decision memo for the platform team: the check's states and what each means, the blocking set, the review-depth tiers with their per-PR token caps, and the monthly budget. Rollout: advisory on ten repositories for two weeks, measuring acted-on rate and cost per review; then required with fail-open on the main repositories. Roll back to advisory if the check blocks a merge on a model-only finding, or if cost per reviewed pull request exceeds the tier's cap for three days running.

### Check your answer

- The budget arithmetic is done, and it changes what gets reviewed.
- Instructions come from the base branch; pull request text is data.
- The job that reads untrusted content has no write tokens and runs no repository code.
- The required check's behaviour on outage and budget exhaustion is decided and written down.
- Only findings with a deterministic second signal can block.
- Comment quality is measured by what authors act on.

## Follow-ups

- *Pushback: the security team says fail-open makes the check meaningless. Which repositories, if any, get fail-closed, and who carries the outage risk for them?*
- *Reversal: what acted-on rate and false-positive rate would you need to see before letting a model-only finding block a merge?*
- *Operating: the provider raises prices 40 percent mid-quarter and the budget does not move. Which tier do you cut first, and what do you tell the repositories that lose review?*

## Common mistakes

- Reading the bot's instructions from the pull request branch.
- Running fork pull requests in a job with write tokens or deploy secrets.
- Making the bot's check fail closed without deciding who owns an outage.
- Reviewing every pull request at full depth without doing the budget arithmetic.
- Measuring success by comment count.
