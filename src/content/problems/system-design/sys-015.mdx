## Question

<Callout kind="interview" label="Interview question">
"We hit the provider's rate limits every evening at peak, even though our traffic is under the limit. Find out why."
</Callout>

The organization's limit is 2,000 requests a minute. The team turned off the SDK's built-in retries last month and wrote its own:

```python
client = Anthropic(max_retries=0)

def call(body):
    for attempt in range(5):
        try:
            return client.messages.create(**body)
        except RateLimitError:
            continue
    raise Overloaded("try again later")
```

## Answer

The provider enforces its limits as token buckets over short intervals, so 2,000 a minute behaves like about 33 a second, and the evening peak has seconds that go over even though the minute does not. The first few 429s are normal. The custom loop then retries each one immediately, five times, ignoring the retry-after header, so every rejected request becomes up to five more requests in the same second. At 18:00 the service sends 4,100 requests a minute to serve 1,400 users, and 38 percent of them fail. The loop turned a small overflow into a retry storm.

Why the wrong picks are tempting. A spend limit also returns 429, but it carries no retry-after and does not recover at night. Provider overload is a reasonable first guess at peak, but it has its own status code, 529. And `max_tokens` feels like a reservation, but this provider does not count it toward the output-token limit, and the dashboard shows that limit far from full.

### The fix

```diff
-client = Anthropic(max_retries=0)
+client = Anthropic(max_retries=2)          # SDK backoff honours retry-after
+bucket = TokenBucket(capacity=30, refill_per_s=30)   # stay under the per-second rate
+breaker = Breaker(fail_limit=5, cooldown_s=30)

 def call(body):
-    for attempt in range(5):
-        try:
-            return client.messages.create(**body)
-        except RateLimitError:
-            continue
-    raise Overloaded("try again later")
+    if not bucket.try_take(1):
+        return queue_or_degrade(body)       # wait in a queue, or serve a labelled fallback
+    if not breaker.allow(now()):
+        return queue_or_degrade(body)
+    try:
+        r = client.messages.create(**body)
+        breaker.record(True, now())
+        return r
+    except RateLimitError as e:
+        breaker.record(False, now())
+        code = (e.body or {}).get("error", {}).get("details", {}).get("error_code")
+        if code == "enforced_spend_limit_reached" or e.response.headers.get("retry-after") is None:
+            raise SpendLimitReached() from e   # will not recover by retrying; page someone
+        return queue_or_degrade(body)
```

Pace requests on the client to the provider's real rate, let the SDK back off with jitter and honour retry-after, and stop retrying entirely when the 429 is the kind that does not recover. Then decide what the user gets while the system is saturated: a queue with a visible wait for chat, a smaller fallback model with the response marked as degraded, or a clear "try again" for batch jobs.

## Follow-ups

- *Should we just add a second provider?* It helps with outages and limits, but a fallback that only runs during incidents tends to fail when needed. Send a small share of real traffic through it all the time, evaluate its answers, and cap fallbacks so a failing secondary does not double the load.
- *How do routers handle this?* LiteLLM's router, for one, puts a deployment in cooldown after a few failures (3 by default, for 5 seconds) and caps fallbacks at 5 by default; the shape is the same breaker.
- *How do you find the real peak-second rate?* Histogram requests per second, not per minute; the minute average hides the bursts that trip the limit.

## Common mistakes

- Raising the retry count, which makes the storm worse.
- Asking for a higher tier before measuring how many provider requests are retries.
- Treating every 429 the same, including the spend-limit one that never recovers.
- Turning off the SDK's retries without replacing what they did.
