## Question

<Callout kind="interview" label="The prompt, as candidate reports describe it">
"System design for a multi-tenant Claude deployment." Candidates report that the follow-ups concentrate on the evaluation harness rather than on retrieval.
</Callout>

Make it concrete: you run a platform on which hundreds of business customers each configure their own assistant (system prompt, tools, documents). All of them run on one hosted model provider through your organization's API account. Design the platform, and spend at least half the time on how you evaluate changes to the model, the platform prompt and each tenant's configuration. The company attribution comes from a vendor blog collecting unverified candidate reports.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Rate limits are per organization. What happens to tenant B when tenant A runs a bulk job?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Three things change independently: the model, your platform prompt and tools, and each tenant's config. Each needs its own eval trigger.</p></details>
<details class="hint"><summary>Hint 3</summary><p>The provider retires the model your tenants are on with 60 days' notice. What does the harness have to answer in that window?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A gateway in front of the provider that authenticates tenants, applies per-tenant token buckets carved out of the organization's limits, pins each tenant to a versioned config (model, prompt, tools, documents) and logs every call. Isolation covers data, retrieval indexes, caches and logs. The eval harness runs three suites: a platform suite on every platform or model change, each tenant's own suite on that tenant's config changes, and a migration run of every tenant's suite against a candidate model, with repeated trials, calibrated judges and a report per tenant before anyone is moved.</p>
</Fragment>
<Fragment slot="long">
<p>Platform. Tenant config is a versioned document: model ID, API version, system prompt, tool set, retrieval index, budget. A gateway resolves the config, enforces quotas and writes a trace per call with the config version. Retrieval indexes are per tenant (namespaces), conversation stores are partitioned by tenant, and any response cache is keyed by tenant and config version.</p>
<p>Quotas. The provider's limits apply to the organization: on Anthropic's Start tier for Opus 5.5 that is 1,000 requests, 2,000,000 uncached input tokens and 400,000 output tokens a minute. The gateway splits them with per-tenant token buckets (reserved share plus burst from a shared pool), sends bulk work to the Batch API, and rejects or queues before the provider does, so one tenant's spike is a 429 for that tenant only. Keeping prompts cache-friendly raises everyone's headroom, because cached input does not count toward the input limit on most models.</p>
<p>Eval harness, the deep dive. Three suites. The platform suite covers behaviour every tenant relies on: tool-call formatting, refusal policy, citation format, prompt-injection cases. Each tenant suite starts with about twenty real conversations from that tenant, the way Anthropic started its own agent evals, and grows from flagged production failures. Cases have checkable outcomes where possible (tool called with these arguments, answer cites this document) and judge rubrics where not, with each judge checked against human labels before it gates anything. Every case runs several times, and gates use pass^k so flaky behaviour fails.</p>
<p>Triggers. A tenant config change runs that tenant's suite and blocks on regression. A platform change runs the platform suite plus a sample of tenant suites. A model change runs everything and produces a per-tenant diff.</p>
<p>Migrations. Anthropic gives at least 60 days' notice before retiring a model, and newer API versions also change request shape (API version 2026-10-21 rejects temperature, top_p and top_k; newer models reject assistant prefill). So a migration is a harness job: run every tenant suite on the candidate with the new request shape, auto-migrate tenants with no regressions, and give the rest a report and a deadline.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A tenant says quality dropped yesterday. How do you check?</em> Find the config and model versions in yesterday's traces, rerun their suite on both, and look at sampled production traces scored by the same judges.</li>
<li><em>Tenants want to bring their own eval cases. Risks?</em> Cases can contain sensitive data and prompt injections aimed at the judge; store them in the tenant's partition and run judges with the same input handling as production.</li>
<li><em>How do you keep tenant data out of shared improvements?</em> Platform prompts and suites are built only from consented or synthetic data; tenant suites never feed the platform suite without permission.</li>
</ul>
</Fragment>
</Depth>

### Rubric check

**Problem navigation:** noticed that rate limits are organization-wide and that three things change independently. **Solution design:** versioned tenant configs behind a gateway, isolation listed layer by layer. **Technical excellence:** token buckets carved from provider limits, judge calibration, pass^k gates, a migration flow tied to the deprecation window and API version changes. **Communication:** spent the second half on evals, as asked.

## Follow-ups

- *How many trials per case?* Enough that a flaky case shows up: run a pilot with many trials on a sample, see how pass^k falls with k, and pick the k that matches how often users retry.
- *Judges disagree with humans on one tenant's domain (legal, medical).* Give that tenant a domain rubric and their own labelled calibration set, or keep humans in that loop.
- *The harness is too slow to run on every change.* Tier it: a fast smoke subset on every change, the full suite before release, everything on model changes.

## Common mistakes

- One shared eval set for all tenants.
- Treating rate limits as per tenant when the provider applies them per organization.
- Migrating models by changing an ID, without testing the new request shape.
- Trusting an LLM judge that was never compared with human labels.
