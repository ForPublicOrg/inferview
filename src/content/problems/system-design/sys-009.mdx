## Question

<Callout kind="interview" label="Design round, 45 minutes">
"System design for a multi-tenant Claude deployment." Spend at least half the time on how you evaluate changes.
</Callout>

Scenario, not any company's real platform: you run an assistant platform for 300 business tenants, each with its own system prompt, tools and documents. All traffic goes through one Anthropic organization on the Build tier. 120 tenants are pinned to `claude-sonnet-4-5-20250929`, which retires on 30 November 2026, 33 days from today. Some of those tenants set `temperature` in their configuration. The ten largest tenants produce most of the traffic, and their contracts promise that one tenant's load never degrades another's. Two engineers own the platform.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask at what level the provider enforces rate limits, and what happens to everyone else when one tenant runs a bulk job.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which parts of a tenant's configuration change independently, and who is allowed to change each.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Request the token volume of one full run of every affected tenant's eval suite, and compare it with the organization's limits.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A gateway resolves each request to a versioned tenant configuration, enforces per-tenant budgets carved from the organization's limits (reserved shares for the large tenants, a shared burst pool for the rest), and logs every call with the configuration version. The harness keeps a platform suite and one suite per tenant, gated on pass^k with calibrated graders. The retirement is a harness job: every affected tenant's suite runs on the replacement through the Batch API, which has its own limits, with the new request shape; tenants that hold move automatically and the rest get a report and a date.</p>
</Fragment>
<Fragment slot="long">
<p><b>Isolation, the first decision.</b> Anthropic enforces limits per organization and lets you set lower limits per workspace, but organization-wide limits always apply, even if workspace limits add up to more. Two defensible answers. A workspace per tenant: the provider enforces each cap, and per-workspace spend limits come free. Cost: a cap only stops a tenant from exceeding it; it reserves nothing, so ten capped tenants can still exhaust the organization together, and I have to ask how many workspaces the account supports. A gateway with token buckets: I can reserve as well as cap, and reject before the provider does. Cost: one more service on the request path that my two engineers run. I choose the gateway, with workspaces as a second fence for the ten largest tenants.</p>
<p><b>The quantity I choose.</b> On Build tier, Claude Sonnet 5.5, the replacement model, allows 5,000,000 uncached input tokens a minute. I reserve 60 percent for the ten large tenants in proportion to their contracts and leave 40 percent as a shared pool for the other 290, each with a burst cap. A 50/50 split is also reasonable; turning the shared pool into fixed shares is not: 2,000,000 / 290 is about 7,000 tokens a minute per small tenant, too small for one long-context request. Cached input does not count toward the limit on most models, so stable prompt prefixes raise every tenant's effective share.</p>
<p><b>The harness.</b> Three suites. A platform suite for behaviour every tenant relies on (tool-call format, refusals, citation format, injection cases). A suite per tenant, started from 20 to 50 real conversations, as Anthropic's eval guidance suggests, with outcome checks where possible and model graders only after they are compared with human labels on that tenant's domain. Each task runs several times, reported as pass^k. Triggers: a tenant's config change runs its suite; a platform change runs the platform suite and a sample of tenant suites; a model change runs everything.</p>
<p><b>The retirement.</b> Scenario arithmetic: 120 tenants × 40 tasks × 5 trials = 24,000 runs per candidate model. At 20,000 input tokens a run that is 480 million input tokens, about 96 minutes of the whole organization's input budget if sent live, competing with production. Sent through the Message Batches API, it uses separate limits (300,000 queued requests on Build tier), so 24,000 fit. The request shape changes too: API version 2026-10-21 rejects <code>temperature</code>, <code>top_p</code> and <code>top_k</code> with a 400, so the migration strips them and the suite measures the result, because a tenant who set temperature low for consistency may see its pass^k fall.</p>
<p><b>Decision on moving tenants.</b> Auto-migrate tenants whose pass^k holds within a tolerance, and report the rest with a date. The alternative, asking every tenant to approve, is defensible for contracts that require it, and costs the deadline: 120 sign-offs in 33 days with two engineers. I auto-migrate where contracts allow, and the platform pins no one past retirement, because requests to a retired model fail.</p>
<p><b>Failure mode and conflict.</b> Cost against coverage: 24,000 runs per candidate means one candidate, not three. Deadline against measured regressions: some tenants will regress and move anyway. The plan's weak point is the tenant suites: a tenant with 20 tasks and a judge calibrated on another domain can pass a migration that breaks it, so the first week after each migration samples production traces for that tenant and scores them with the same graders.</p>
<p><b>What you give up.</b> Tenant-level choice of migration timing, the sampling parameters some tenants relied on, and engineering time on a gateway instead of features.</p>
</Fragment>

<ul>
<li><em>A tenant says quality dropped yesterday. Which traces do you pull, and what do you rerun?</em> The configuration and model versions logged on yesterday's calls; that tenant's suite on both versions; production samples scored by the same graders.</li>
<li><em>Tenants want to upload their own eval cases. What do you check first?</em> Sensitive data and injection text aimed at the judge; the cases live in the tenant's partition and the judge treats them as untrusted input.</li>

### The written artefact

A migration plan: the list of 120 tenants with suite results on the replacement, a date per tenant, and the sampling-parameter change called out for tenants that set them. Rollback trigger per tenant: pass^k on the nightly suite or the sampled production score below that tenant's pre-migration level, while the old model is still available, which ends on 30 November. A risk note lists the tenants that will move with a known regression and who accepted it.

### Check your answer

- Rate limits are placed at the organization level, and the design reserves, not only caps.
- The reserved share is a number you chose and defended.
- Each tenant has its own suite, and judges are calibrated per domain.
- Gates use repeated trials, not one run per task.
- The migration's token volume is computed and kept away from production limits.
- The API version change is part of the migration test.
- The plan meets 30 November and says what happens to tenants that regress.

## Follow-ups

- *Pushback: the per-tenant suites cost more to maintain than the gateway. Which tenants lose their own suite, and what risk do you accept in writing?*
- *Reversal: what would you need to see to drop the gateway and rely on workspace limits alone?*
- *Operating: a large tenant's contract requires their approval for any model change, and they have not replied with 10 days left. What do you do on day 33?*

## Common mistakes

- Treating provider rate limits as per tenant.
- One shared eval set for every tenant.
- Running the migration suite through the live API at production priority.
- Changing the model ID without testing the new request shape.
- Trusting an LLM judge never compared with human labels on that domain.
