## Question

<Callout kind="interview" label="Critique, 30 minutes">
"This design document is up for approval this week. Finance wants the saving. List what you would block, what you would accept with conditions, and what you would ask for instead."
</Callout>

Scenario: the enterprise search assistant serves one company of 50,000 employees and costs about $205,000 a month in model calls, most of it on Claude Sonnet 5.5. Retrieval filters on the user's groups inside the vector query. The design below adds an answer cache in front of the whole pipeline.

> **Answer cache for Ask (design, v3)**
>
> **Motivation.** 41% of last month's queries were near-duplicates of an earlier query in the same tenant (cosine ≥ 0.95 on query embeddings). Serving those from cache saves 0.41 × $205,000 ≈ $84,000 a month.
>
> **Key.** `sha256(tenant_id + normalize(query))` for exact hits. On a miss, a semantic lookup over cached query embeddings for the tenant returns the closest entry if cosine ≥ 0.95.
>
> **Value.** The rendered answer, its citations (title, path, URL) and the model version.
>
> **TTL.** 24 hours.
>
> **Invalidation.** The content connectors already emit `document.updated`; on that event we purge every entry citing the document.
>
> **Warm-up.** A nightly job replays the 500 most frequent queries of the previous week through the pipeline, as the `search-indexer` service account, so the morning peak hits a warm cache.
>
> **Feedback.** A thumbs-down purges the entry.
>
> **Metrics.** Hit rate, model spend per day, p95 latency.
>
> **Rollout.** All tenants on day one behind a flag; the flag is the rollback.

## Answer

The cache is placed after the permission boundary in the design's own diagram and before it in the code path: it stores the output of a permission-scoped pipeline and serves it without the scope. Most of the flaws follow from that, and the saving shrinks once it is fixed.

**Block: the key ignores who is asking.** Two employees in the same tenant asking the same question get the same key, though retrieval for each was filtered on different groups. The first asker's answer, built from documents only they can read, is served to the second. Microsoft states the requirement plainly for Copilot: it surfaces only data the individual user has at least view permission for. An answer is derived data and inherits the strictest permission of its sources.

**Block: the warm-up runs as the indexer.** The `search-indexer` account can read every document, because it builds the index. Its replayed answers draw on everything, and the morning peak is served from them. This is the flaw most reviewers miss on a first read, because the warm-up looks like an operational detail. Even with a permission-aware key, a warm-up has no real user's access to run as; it either runs per access pattern or not at all.

**Block: invalidation covers edits only.** A user removed from a group, a document whose ACL is tightened, and a deleted document all keep being served for up to 24 hours. The connectors emit edits; the permission pipeline is separate and the cache never hears from it. Deletion also matters for retention: an answer quoting a document under a deletion request outlives it.

**Fix: the semantic match.** Cosine ≥ 0.95 on query embeddings treats "what is my manager's travel budget" and "what is my travel budget" as near-duplicates, and personal queries resolve "my" from the asking user's context, which the key does not contain. Personal and entity-bearing queries should be excluded from semantic matching, and the threshold should be set on a labelled set of query pairs, not chosen.

**Fix: citations as a side channel.** Even if the answer text were withheld, a cached citation shows a document's title and path to someone who cannot open it. Titles like a reorganisation plan's are themselves the leak.

**The saving, recomputed.** The 41% counts duplicates across all users in a tenant. A permission-safe cache can share an entry only between users whose access to the cited documents is identical, or must check access at serve time. The hit rate that survives is the number the document should report, and it may not justify the work. The metrics also have nothing on quality: a wrong answer cached at 8:00 is served until someone presses thumbs-down.

**Acceptable with conditions.**

- *Shared answers with a serve-time check.* Store the cited chunk IDs with the answer; at serve time, fetch those chunks' ACLs and check them against the user's current groups; any miss regenerates. A fetch costs 1 RU per 10 records, so the check is cheap; what it costs is a dependency on the same ACL copy the index uses, so it is only as fresh as that copy.
- *A per-user cache with a short TTL.* Safe by construction, and its hit rate is likely far below 41%. Acceptable if a week of logs shows repeats by the same user are frequent enough to pay for it.
- *Caching something other than answers.* The fixed part of the prompt (instructions, tool definitions) can be cached by the provider with no permission question at all; retrieval results can be cached per group-set fingerprint. Each saves less than answer caching and leaks nothing.

**The decision.** Two defensible paths: shared answers with a serve-time access check, or no answer cache and provider-side prompt caching plus fewer chunks per prompt. The first saves more and adds a check that fails in the same way the index does; the second saves less and has no new leak path. I would ask the authors for the permission-safe hit rate from last month's logs before choosing, and approve the prompt-side savings now.

**Where the recommended fix fails.** The serve-time check reads the index's copy of ACLs, so a revocation that has not yet reached the index passes the check. The cache adds no new lag, but it extends every existing lag by serving the answer instead of re-retrieving, and the revocation prober has to cover cached paths too.

## Follow-ups

- *Finance says the saving is the point and the serve-time check halves it. Which half do you keep, and what risk goes in the approval in writing?*
- *What would you need to see in a month of production to allow semantic matching for non-personal queries?*
- *The security team and the platform team disagree on whether a cache flag is an adequate rollback for a leak. How do you settle it without deciding by rank?*
- *A legal hold requires keeping every answer shown to a set of users. Does that change where the cache lives?*

## Common mistakes

- Approving the key because it includes the tenant, without asking about users inside the tenant.
- Reading the warm-up as an operations detail rather than a principal with full access.
- Purging on edits and forgetting revocations and deletions.
- Accepting the hit rate measured before the permission constraint is applied.
- Fixing the answer text and leaving citations that name restricted documents.
