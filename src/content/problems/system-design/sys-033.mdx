## Question

<Callout kind="interview" label="Interview question">
"Design the file uploader for our AI chat app. People attach large files of any kind and then ask questions about them."
</Callout>

Scenario: mostly mobile users, many on unreliable networks. Files up to 1 GB, including screen recordings and voice memos. The chat model is a Claude model on the high-resolution image tier with a 200k-token context window. The privacy team requires that when a user deletes a file, every derived copy (extracted text, page images, embeddings, cached prompts that contain it) is gone within 24 hours, and they will audit it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask for the distribution of file types and sizes from the current upload logs, and what share of uploads are followed by more than one question.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask the privacy team whether provider-side copies (uploaded files, cached prompts) count as derived copies, and what evidence of deletion they accept.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the product shows today while a large file is being processed, and how often people re-upload.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Resumable, chunked uploads straight to object storage from the phone, deduplicated by content hash; a worker that identifies files by content and routes them: images resized on the device to the model tier's limits, text PDFs extracted and attached when they fit the token budget, scans and long documents indexed for page-level retrieval, audio and video transcribed, office files converted. Every derived artefact is registered against the source file ID in a lineage table, so deletion is a walk of that table. The central choice is attach versus retrieve per file, made from a token estimate. What I give up is whole-document reasoning on large files, which retrieval cannot do.</p>
</Fragment>
<Fragment slot="long">
<p><b>Upload.</b> Parts uploaded in parallel with a short-lived signed URL per part, retried individually, assembled by storage on completion. A content hash computed on the device lets the server skip files it already has for that user, which matters most on the networks where uploads fail.</p>
<p><b>Route and budget.</b> Text PDFs cost 1,500 to 3,000 text tokens a page on Claude plus the page images; a 40-page document is 60,000 to 120,000 tokens of text alone, so with a 200k window and room left for the conversation, documents above roughly 30 pages go to retrieval. A 2,000 × 1,500 photo costs ⌈2000/28⌉ × ⌈1500/28⌉ = 72 × 54 = 3,888 tokens on the high tier, every turn it stays in uncached history. Voice memos become transcripts; a screen recording becomes a transcript plus keyframes chosen at scene changes, because sending video frames at a fixed rate costs tokens for frames nobody asked about.</p>
<p><b>Attach or retrieve.</b> Attaching is the better answer for documents that fit and are asked about several times: the model reads all of it, and prompt caching makes follow-ups cheap. Retrieval is the better answer for long documents and collections: per-turn cost stays flat, at the price of missing answers that need the whole document (totals across sections, contradictions between pages). For layout-heavy scans, retrieval over page images (ColPali's approach) avoids OCR errors at the cost of a larger multi-vector index.</p>
<p><b>Deletion.</b> Every artefact (parts, extracted text, page images, chunks, embeddings, provider file IDs) is written with the source file ID. Deleting a file deletes down the lineage, removes provider-side uploads through their delete API, and marks conversations that contained the file so their next request is rebuilt without it, which also stops the cached prefix that contains it from being read again.</p>
<p><b>Failure mode of this design.</b> The lineage table is only as complete as the code that writes to it. A new artefact type added by another team without a lineage write survives deletion and fails the audit. I would make the storage layer refuse writes without a source file ID, and run a weekly job that samples deleted file IDs and searches every store for them.</p>
</Fragment>

### The numbers you choose

The attach threshold in tokens (the answer uses about 30 text pages against a 200k window; a lower threshold is defensible if most files are asked about once), the image resize target (the model tier's long edge, or lower if the questions do not need detail), and the keyframe policy for video. A threshold stated in megabytes rather than tokens is not defensible, because a 2 MB scan and a 2 MB text PDF cost very different amounts.

### Constraint conflict

Answer quality wants whole documents in context; per-turn cost and the 200k window want retrieval; the 24-hour deletion rule wants as few derived copies as possible, and every extra artefact type (page images, embeddings, keyframes) is one more store to purge and audit.

### What you give up

Whole-document questions on large files, under retrieval. Fidelity on layout-heavy pages, if extraction is used where page images would have been right. Some upload speed, because the device does hashing and resizing before sending.

### Rollout plan

Ship images and text PDFs first, with the attach-or-retrieve threshold behind a flag; add audio, then video. Rollback triggers: deletion audit finds any surviving artefact (stop new artefact types until fixed); re-upload rate above its current level for a week (progress reporting is not working); per-conversation cost above the finance cap on more than a set share of conversations (lower the attach threshold).

## Follow-ups

- *A user uploads a 600-page PDF and asks for a summary of the whole thing. What do they get, and what does the product say about it?*
- *The model is replaced by one on the standard image tier. Which numbers change?*
- *How would you evaluate the router itself, separately from the model's answers?*

## Common mistakes

- Proxying file bytes through the application server.
- Choosing attach or retrieve by file size in bytes instead of an estimated token count.
- Quoting an image-token figure without naming the model family and tier.
- Sending base64 images in every turn of a long conversation.
- Treating deletion as deleting the original file, with derived copies left in the index and the provider.
