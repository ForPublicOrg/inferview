## Question

<Callout kind="interview" label="The topic, as an interview guide lists it">
Design a multi-tenant chat backend: conversation state, a content moderation pipeline, and billing for token-based pricing.
</Callout>

Business customers embed your chat product for their users. Each tenant picks a model, pays per token at your prices (a margin over the provider's), and sees usage on an invoice. Messages must be moderated. The guide that lists this topic places it in OpenAI's Applied track; it lists focus areas, not a verbatim prompt.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Where is the source of truth for a conversation: your database or the provider's?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Read the provider's usage object field by field. Which ones does your bill need?</p></details>
<details class="hint"><summary>Hint 3</summary><p>A usage event is sent twice after a retry. What stops the customer being billed twice?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Conversations live in our own store, partitioned by tenant, and we build each prompt from it with a stable, cacheable prefix. Moderation checks input before the model call and output before display, with tenant-level policy settings. Every model call writes a usage record from all of the provider's usage fields, with the request ID as an idempotency key, into a ledger; an aggregator rolls it up per tenant and sends meter events to the billing system, reconciling before anything is sent because corrections are only possible for a short window.</p>
</Fragment>
<Fragment slot="long">
<p>Conversation state. A conversations table and a messages table keyed by tenant and conversation, with model ID and prompt version per message. Provider-side state is a convenience, not a record: with OpenAI's `previous_response_id`, every earlier input in the chain is billed again anyway, and stored responses expire after 30 days by default. Long conversations get a summary of older turns so the prompt stays bounded.</p>
<p>Request path. Auth, tenant config, load recent messages and summary, input moderation, build the prompt (tenant system prompt first and unchanged, so it caches), call the model with streaming, output moderation on the stream, persist, write usage.</p>
<p>Moderation. A fast classifier on input and output with per-category thresholds; tenants can tighten but not loosen the platform minimum. Flagged messages are stored with the scores and model version, for appeals.</p>
<p>Metering, the deep dive. On Anthropic, total input is cache reads plus cache writes plus `input_tokens`, and `input_tokens` alone counts only what comes after the last cache breakpoint. Each category has its own price. Example on Claude Sonnet 5: 5,000 cache-read tokens, 800 uncached input tokens and 400 output tokens cost 5,000 × $0.20 + 800 × $2 + 400 × $10 = $0.0066 per call at list price. Billing only `input_tokens` and output gives $0.0056, an under-charge; billing all 5,800 input tokens at the full input price gives $0.0156, an over-charge more than twice the real cost.</p>
<p>The ledger. One usage row per provider call, keyed by our request ID, written in the same transaction as the assistant message. Retries reuse the request ID, so a duplicate is a no-op. An hourly job aggregates per tenant, price category and model, and sends meter events. Stripe processes meter events asynchronously, aggregates by sum, count or last, and allows cancellations only within 24 hours, so the job reconciles the ledger against provider usage before sending, not after.</p>
<p>Tenancy. Per-tenant quotas carved from the organization's provider limits, per-tenant spend caps with alerts, and cache keys and logs scoped by tenant.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A stream fails halfway. Do you bill?</em> Bill what the provider billed, from its usage on the failure if it reports one, and mark the message as incomplete; the customer-facing policy (charge or credit) is a product decision, applied in the ledger.</li>
<li><em>A tenant disputes last month's invoice.</em> Rebuild it from the ledger rows, each tied to a message, model and price version.</li>
<li><em>Prices change mid-month.</em> Price versions with effective dates; each ledger row stores the version used.</li>
</ul>
</Fragment>
</Depth>

### Rubric check

**Problem navigation:** asked who owns conversation history and what the invoice must show. **Solution design:** own store, moderation on both sides, a ledger between usage and billing. **Technical excellence:** usage-field arithmetic with the cache categories, idempotency by request ID, the 24-hour correction window. **Communication:** showed both billing bugs with numbers.

## Follow-ups

- *Should billing call the billing provider on every request?* No. Write to your own ledger synchronously and send aggregates; the billing provider is downstream and asynchronous.
- *A tenant wants to bring their own provider key.* Then the provider bills them for tokens and you bill a platform fee; the ledger still records usage for quotas and support.
- *Which system would you pick for new usage billing?* Stripe's own docs now point new usage-based integrations to Metronome; evaluate both against the ledger design rather than building the invoice logic into either.

## Common mistakes

- Treating the provider's stored responses as the conversation record.
- Billing from `input_tokens` alone and losing cached traffic.
- Sending usage events straight from the request path with no idempotency key.
- Moderating input only, so a model output that breaks policy is shown and billed.
