## Question

<Callout kind="interview" label="Interview question">
"Our cache hit rate is near zero. Here is how we build the request. Which single change fixes it?"
</Callout>

The service runs on Claude Sonnet 5 with a 5-minute cache breakpoint at the end of the system prompt. Requests are built in this order:

```text
tools:    12 tool definitions                          (about 1,800 tokens, same for everyone)
system:   "Now: 2026-10-28T14:03:11Z. User: Priya.      (changes on every request)
           Experiment: answer-style-B."
          + support policy and examples                 (about 3,000 tokens, same for everyone)
          [cache breakpoint]
messages: retrieved chunks + the user's question         (different every time)
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>A prompt cache is keyed on the exact bytes from the start of the request up to the breakpoint.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Find the first byte that differs between two requests.</p></details>

## Answer

The cache key is the exact prefix in the order tools, system, messages. The first thing in the system block is a timestamp, so the prefix differs on every request from that point on, and with the breakpoint at the end of the system block every request writes a fresh entry and none reads one. Moving the volatile lines below the breakpoint makes about 4,800 tokens (1,800 of tools plus 3,000 of policy) identical across requests, and those become cache reads at a tenth of the input price.

Why the others are tempting. A longer cache lifetime sounds like more hits, but entries that are never re-read gain nothing from living longer, and the 1-hour write costs more. Tenant IDs in the tools sound like good hygiene, but the tools sit first in the cache order, so any change there invalidates the rest, and organizations already do not share caches. A semantic response cache is a different layer with its own correctness risk; Redis's own docs say it gives up the guarantee that a hit is correct, and suggest starting thresholds of 0.8 to 0.9, not 0.6. Trimming below the minimum prefix size switches caching off entirely.

## Follow-ups

- *How do you keep this from regressing?* A test that builds two requests for different users at different times and asserts the bytes before the breakpoint are equal, plus an alert on the cache-read share of input tokens.
- *The experiment flag changes the policy text itself. Now what?* Give each arm its own stable prefix; two arms mean two cache entries, which is fine.
- *Where would a semantic cache be appropriate?* For FAQ-like questions whose answers are not personal, keyed by tenant and model version, starting with a strict threshold and spot checks.

## Common mistakes

- Treating the cache as fuzzy: one changed character at the top invalidates everything after it.
- Reaching for a longer TTL before checking whether prefixes repeat at all.
- Mixing up prompt caching (reuses input processing) with response caching (reuses answers).
