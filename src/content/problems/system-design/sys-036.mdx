## Question

<Callout kind="interview" label="Interview question">
"Design a system that uses a coding agent as a CI component: when the main branch goes red, the agent investigates the failure and proposes a fix."
</Callout>

Operating constraints (scenario): the company's CI system cannot be replaced; its runners hold deploy credentials for staging; about 60 main-branch failures a week, of which the build team estimates a third are flaky tests. The engineering director wants the agent live in six weeks and the security team has a veto.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which secrets are present on a CI runner during a normal job, and which of them would the agent's process inherit?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Of the past quarter's main-branch failures, how many were fixed by a change to product code, how many by a test change, and how many by a re-run?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Who reviews the agent's pull request today, and how long do they spend on a typical fix?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The CI system triggers, but the agent does not run on a CI runner. A failure event goes to a queue; a dispatcher filters out failures that a re-run fixes, then starts an agent session in a sandbox with no deploy credentials, a clone made with a token the sandbox never sees, and egress limited to the package mirror and the code host. The agent opens a pull request and never merges. Diff checks reject edits to test assertions, CI config and lock files unless a human asks for them. The budget per failure is capped and the metric is merged fixes per dollar and per reviewer hour.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Where the agent runs: the decision.</strong> (a) On the existing CI runner: zero new infrastructure and the exact build environment, but the agent's process inherits staging deploy credentials, and a committed hook or test fixture can instruct it to use them. Anthropic's own record includes a committed hook that ran before the user had trusted the project. (b) In a separate sandbox built from the same image: no inherited secrets, at the cost of maintaining a second copy of the build environment and some failures that reproduce only on the runner. I would take (b) and accept the reproduction gap, logging "could not reproduce" as an outcome rather than letting the agent guess.</p>
<p><strong>What qualifies.</strong> Re-run first. A failure that passes on re-run is a flake: it goes to a flake tracker, not to the agent, because an agent asked to fix a flaky test tends to weaken or skip it. That leaves the failures that reproduce. Of 60 a week with a third flaky (scenario), about 40 reach the agent.</p>
<p><strong>Guarding the diff.</strong> Duolingo's eval graders show the shape: assertions on the diff for forbidden changes, a maximum number of changed files and path restrictions, plus a check that the reported outcome matches the repository state. In CI the same checks run on every agent pull request: no edits to test assertions, skip markers, CI configuration or lock files unless the failure is in those files; a cap on changed files; and the fix must turn the failing job green in the sandbox before the pull request opens.</p>
<p><strong>Budget (the reader chooses).</strong> Cap each failure at a number of attempts and a token budget. Two attempts at a budget you can state in dollars is defensible; unlimited retries are not, because a failure the agent cannot fix burns the most money. Set the cap so the weekly spend at 40 failures fits the budget the director signs, and report merged fixes per dollar and reviewer minutes per merged fix.</p>
<p><strong>Constraint conflict and what I give up.</strong> Autonomy against safety under a six-week deadline. I give up auto-merge, and I give up fixes for failures that need staging access to reproduce. The agent can still comment its diagnosis on those.</p>
<p><strong>Failure mode of the recommended answer.</strong> Reviewer fatigue. If the agent opens a pull request for every reproducible failure, reviewers approve green diffs quickly. Anthropic reports that users approved roughly 93 percent of permission prompts in its own products, and a pull request from a bot that turns CI green invites the same habit. A plausible fix that passes CI but changes behaviour (catching and ignoring an exception, loosening a type) gets merged. Mitigation: the pull request description must state the root cause and the evidence, and a weekly sample of merged agent fixes is re-reviewed by a second engineer.</p>
<p><strong>Written artefact: rollout plan.</strong> Weeks 1 and 2: diagnosis comments only, no pull requests. Weeks 3 and 4: pull requests for one repository with a named reviewer rota. Weeks 5 and 6: more repositories if the merged-without-changes rate and the re-review findings meet thresholds agreed with the build team. Rollback trigger: any agent fix reverted for a behaviour regression, which pauses pull requests pending review.</p>
</Fragment>

### Rubric

- Refuses to run the agent with the CI runner's inherited credentials, or states exactly how they are removed
- Separates flaky failures from reproducible ones before the agent is called
- Guards the diff with forbidden paths, a changed-file cap and a green-in-sandbox requirement
- Chooses an attempt and token budget per failure and ties it to a weekly spend
- Names reviewer fatigue as the failure mode of the design and mitigates it
- States what is given up (auto-merge, staging-only failures)
- Writes a staged rollout with a rollback trigger

## Follow-ups

- *The agent's fix is correct but touches code owned by another team.* The pull request follows code-owner rules like any other; the agent does not get an exemption.
- *A failure is caused by an upstream dependency release.* The agent may propose a pin; pinning is a decision with security consequences, so those pull requests go to the dependency owners.

## Common mistakes

- Running the agent as a CI step with the job's environment, secrets included.
- Sending flaky failures to the agent and measuring success by green builds.
- Counting pull requests opened instead of fixes merged and kept.
