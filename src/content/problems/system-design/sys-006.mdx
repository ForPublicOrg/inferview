## Question

<Callout kind="interview" label="Interview question">
"Design an enterprise RAG assistant over 10 million documents with per-user permissions."
</Callout>

Constraints, from a community whiteboard exercise built on this prompt: 50,000 employees, P95 latency under 3 seconds to a complete answer, documents and questions in English, Spanish and Mandarin, and 35 minutes for the design. The documents live in a wiki, a shared drive and a ticketing system, each with its own permission model.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Decide where the permission check runs relative to retrieval before you choose a vector store.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Users change groups. How fast must search forget what someone lost access to?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Size the index: documents × chunks × dimensions × bytes, and the one-off embedding bill.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Connectors ingest content and ACLs together into a hybrid index (BM25 plus multilingual vectors) where every chunk carries the groups allowed to read it. The query expands the user to their groups and filters inside the search, never after it. Rerank, answer with citations to versioned chunks, and check that every citation was retrieved. A separate, faster ACL sync path makes revoked access disappear quickly. At 8 chunks a document it is 80 million vectors, about 0.49 TB in float32 and $640 to embed once.</p>
</Fragment>
<Fragment slot="long">
<p>Scope. Read-only answers with citations; three sources; three languages; P95 under 3 s end to end. I'd ask how fast a permission change must take effect and whether answers may combine documents from different sources.</p>
<p>Permissions. The reference behaviour, as Microsoft describes it for Copilot, is that the system only grounds on content the user can at least view. Every chunk stores the IDs of the groups that can read it, copied from the source at ingestion. At query time the user is expanded to their groups (cached briefly) and the vector and keyword queries both filter on them. I filter on groups rather than user IDs because filter lists are capped (10,000 values in Pinecone's `$in`) and user lists are an anti-pattern there. Post-filtering is out: a missed code path leaks, and users with narrow access get empty results.</p>
<p>Ingestion. One connector per source emits content changes and ACL changes as separate event streams. ACL changes take the faster path and are measured as their own lag metric, because a stale grant is a security issue and a stale paragraph is not. Chunks keep a document version, so citations are reproducible.</p>
<p>Retrieval. Multilingual embedding model, BM25 per language with the right analyzers (Mandarin needs word segmentation), reciprocal rank fusion, then a cross-encoder reranker on the top candidates. Contextual chunking (a short document-level prefix on each chunk) is worth testing; Anthropic measured large drops in retrieval failure from it on its own sets.</p>
<p>Latency. Within 3 s at P95, generating the answer is the largest share, so group expansion runs while the query is rewritten, the two searches run in parallel, and the reranker sees a short candidate list. If the full answer does not fit, stream it and set the budget on time to first token instead, after agreeing that with the interviewer.</p>
<p>Sizing. 10 million documents × 8 chunks = 80 million vectors; × 1,536 dims × 4 bytes = 491.5 GB before index overhead; 400 tokens a chunk × 80 million = 32 billion tokens, $640 at $0.02 per million. Re-embedding on a model change is cheap; storage is the line to optimise.</p>
<p>Evals. A query set per source and language with expected documents; a permission suite where synthetic users ask questions answerable only from documents they cannot see, failing the build if any such chunk is retrieved; online, no-answer rate and citation clicks by language.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>A group has 200,000 members and changes every hour.</em> Keep group membership out of the chunks (chunks reference groups, not users) so membership changes never touch the index.</li>
<li><em>A Spanish question whose answer only exists in an English document?</em> Cross-lingual retrieval through the multilingual embeddings, an answer in the user's language, and a citation that says the source is English.</li>
<li><em>The source system's ACLs can't be copied (shared links, external guests).</em> For those sources, check access against the source at query time on the final few chunks, and accept the latency.</li>
</ul>
</Fragment>
</Depth>

### Rubric check

**Problem navigation:** asked about permission-change latency and cross-source answers. **Solution design:** the permission filter sits inside retrieval, with a separate ACL sync path. **Technical excellence:** group-based filtering with its size limit, BM25 analyzers per language, versioned citations, the index arithmetic. **Communication:** said why post-filtering fails, not only that it is worse.

## Follow-ups

- *How do you prove the permission model works?* The permission eval above, run in CI and as a canary in production with synthetic users.
- *Tenants are separate companies, not departments.* Separate namespaces or indexes per tenant on top of the group filter; on serverless stores that is also cheaper per query.
- *Search is slow for one large department.* Measure filtered-query latency per group; if one group is the outlier, give it its own partition and compare.

## Common mistakes

- Filtering by permission after retrieval.
- Treating ACL sync as part of content sync, with the same lag.
- Picking a vector database before sizing the index.
- Testing only in English.
