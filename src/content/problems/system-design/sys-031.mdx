## Question

<Callout kind="interview" label="Design round, 45 minutes, backend only">
Design the backend for a chat product used by fintech customers. Users send a message and get a streamed answer. Behind it, an orchestration layer runs agents for planning, retrieval, calculation, compliance checks and final response generation, with tool calls to internal services and external APIs. Cover the data model, request flow, scaling and failure handling, and the handling of sensitive financial data.
</Callout>

Scenario details the interviewer gives when asked: customers are wealth-management firms; their analysts ask questions such as "what was this client's realised gain this year, and can we say it is tax-efficient?" The compliance team's rule is that no answer reaching the user may contain a forward-looking performance claim or a recommendation the firm is not licensed to make. Product wants the first token on screen in under 2 seconds.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which of the five agents need a model at all, and which are deterministic services with a model-shaped interface.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask compliance whether a sentence that was shown and then retracted counts as having been said.</p></details>
<details class="hint"><summary>Hint 3</summary><p>For each external API, ask for its timeout behaviour and whether its calls can be retried safely.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>One orchestrator per turn running a planned graph, not five free-running agents: the planner is a model call producing a typed plan; retrieval and calculation are services (the calculation runs code over retrieved numbers, never model arithmetic); compliance is a deterministic rule set plus a classifier on the final text; the response model writes from verified facts. The conflict is streaming against compliance: I stream progress and verified facts early, and stream the prose through a sentence-level hold-back that compliance clears, so the 2-second target is met by the first status line, not the first sentence of advice.</p>
</Fragment>
<Fragment slot="long">
<p><b>How many agents.</b> OpenAI's guide recommends getting the most out of a single agent before splitting, because more agents add complexity and overhead. The prompt names five, and the honest design keeps the names but not the autonomy: a planner model call that outputs a typed plan (which accounts, which date range, which calculations), a retrieval service over the firm's documents and positions with the user's permissions, a calculation service that runs fixed functions (realised gain, time-weighted return) on retrieved numbers, a compliance stage, and a response model. Only two of these need a model. The other defensible answer is an agent loop with all five as tools, which handles odd questions better and costs predictability, test coverage and latency on every turn.</p>
<p><b>Data model.</b> Conversation (tenant, user, created), turn (conversation, input, plan, status, version), step (turn, kind, input hash, output, status, attempt, cost), artefact (retrieved passages and calculation results with source IDs). Every number in the final answer links to an artefact; that link is what compliance and audit read. Financial data is encrypted per tenant, logs store artefact IDs not values, and the model provider is configured for zero retention where the contract requires it.</p>
<p><b>Request flow and streaming.</b> The turn is accepted and its ID returned; a stream opens. The first event, within the 2-second target, is the plan in plain words ("Looking up 2026 disposals for account ending 4471"). Calculation results stream as structured cards once computed, because they are facts with sources. The prose answer is generated, split at sentence boundaries, and each sentence passes the compliance rules (patterns for forward-looking claims and recommendation language) and a classifier before it is sent. Compliance's answer to hint 2 decides whether this hold-back is required; if a retracted sentence counts as said, streaming raw tokens is not an option at all.</p>
<p><b>The quantity I choose: the hold-back unit.</b> A sentence. A token-level stream is fastest and cannot be checked; a whole-answer hold-back is safest and makes the user wait for the full generation. One sentence of delay keeps the reading pace while each unit is checked in isolation, at the cost of missing claims split across sentences, which the classifier on the full answer catches after the fact and flags for review.</p>
<p><b>Failure handling, step by step.</b> Each step has a timeout and a recovery class. Retrieval and calculation are read-only and retried with backoff. External APIs that mutate nothing are retried; any that write (none should in this product, and I would ask) get idempotency keys. If calculation fails, the answer says which number it could not compute rather than letting the response model estimate it. If compliance is unavailable, nothing is sent: the stream shows the facts already cleared and a "could not complete" message. Provider 429s are absorbed by a per-tenant queue in front of the model calls so one firm's batch does not starve another.</p>
<p><b>Constraint conflict and failure mode.</b> Latency against compliance. The recommended design's weak point is the rule set: compliance patterns written in English miss paraphrases, and the classifier is a model with its own error rate. Every flagged and every sampled answer goes to a compliance review queue, and the rule set grows from what it finds.</p>
<p><b>What you give up.</b> Open-ended questions the planner's typed plan cannot express, raw token streaming, and answers when compliance is down.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Why not let the response model do the arithmetic?</em> A wrong realised gain in a client conversation is the expensive failure; a function over retrieved numbers is testable and traceable to sources.</li>
<li><em>A user asks a question the plan schema cannot express.</em> The planner returns "unsupported" with the nearest supported question, and the miss is logged to decide the next plan type.</li>
</ul>
</Fragment>

### The written artefact

A risk note for compliance: what is streamed before it is checked (status lines and calculation cards only), what the sentence check covers and misses, the review sampling rate, and the behaviour when compliance is down. Rollback trigger: any confirmed non-compliant sentence delivered to a user moves the tenant to whole-answer hold-back until the rule set is updated.

### Check your answer

- Each named agent is either justified as a model call or replaced by a service.
- Numbers come from code over retrieved data, with sources attached.
- Streaming and compliance are reconciled with a stated hold-back unit.
- Every step has a timeout and a recovery class, including compliance being down.
- Tenant data handling covers logs and the model provider, not only storage.
- One tenant's load cannot exhaust shared model limits.

## Follow-ups

- *Pushback: the sentence hold-back doubles perceived latency on long answers, and product says users leave. What do you cut, and what does compliance sign?*
- *Reversal: what would you need to see to turn the planned graph into a free agent loop with the five agents as tools?*
- *Operating: a regulator asks for every answer given to one client last quarter and the facts behind each number. Which tables answer that, and in how long?*

## Common mistakes

- Five autonomous agents passing messages, with no owner of the turn's state.
- Letting a model compute financial figures.
- Streaming tokens to the user and running compliance afterwards.
- No defined behaviour when the compliance step fails.
- Logging prompts and answers containing client financial data in plain text.
