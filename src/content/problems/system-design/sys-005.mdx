## Answer

The trace id appended to the system text makes the cached block different on every request. A provider cache matches the prefix byte for byte, so each request writes 6,650 tokens and reads none. Uncached input per request went from 40 + 1,060 = 1,100 tokens to 6,650 + 2,080 = 8,730. Of that growth of 7,630 tokens, 6,610 come from the lost cache; that is the prefill the model now does on every request, and it is why time to first token doubled at P50 and P99 together.

The 429s are the same change seen by the limiter. Writes count toward the input-token limit and reads do not: 1,500 × 1,100 = 1.65M tokens a minute before, 1,500 × 8,730 = 13.1M after, under the 20M limit on average and over it in bursty minutes.

**Ranking the other two real defects.** The tokenizer change is real: Claude 4.7 and later produce about 30 percent more tokens for the same text, which is why the prefix is 6,650 instead of 5,140 and output is 395 instead of 310. The TOP_K change is real too: three more chunks, about 700 tokens of uncached tail. Together they are about 1,000 of the 7,630-token growth. They will leave time to first token somewhat above the old baseline after the fix, and the output growth lengthens end-to-end time, which the P99 of time to first token does not show.

**What is missing.** Nothing here measures the new model's own speed on an identical prompt. Before blaming or clearing the model, run the old and new model ids on the same fixed, cached prompt and compare time to first token. Without that measurement: ship the one-line fix first, because it is safe and explains most of the regression, and keep the model and TOP_K changes, then compare the post-fix baseline with the old one.

Overload is the tempting wrong pick because the 429s arrived at the same time. It would show up as 529, and it cannot change the cache fields in your own usage logs.

### The fix

```diff
         "system": [{
             "type": "text",
-            "text": SYSTEM_PROMPT + f"\n\n[request {trace_id}]",
+            "text": SYSTEM_PROMPT,
             "cache_control": {"type": "ephemeral"},
         }],
```

Carry the trace id in your own request metadata or logs, never in prompt bytes before a breakpoint. Then add a CI test that builds two requests with different users and trace ids and asserts the bytes before the last breakpoint are identical, and an alert on the cache-read share of input.

## Follow-ups

- *Would rolling back the whole deploy have been right during the incident?* Yes, as the first move; the cache layout test is what stops the next template change from repeating it.
- *After the fix, TTFT P50 is 0.8 s against 0.6 s before. Do you roll back the model?* Only if the identical-prompt comparison shows the model is slower; otherwise the tokenizer and TOP_K tokens account for it, and TOP_K came from a recall eval.
- *What else silently breaks a prefix cache?* Tool definitions that change order or content, per-request experiment flags, and unordered serialization of JSON in the prompt.

## Common mistakes

- Reading only `input_tokens`, which counts the tail after the last breakpoint and hides the move from cached to uncached.
- Raising the rate limit to make the 429s go away, which pays for the bug.
- Attributing the regression to the model change because it is the change everyone noticed.
- Stopping at the first defect without ranking the other two, which still need a decision.
