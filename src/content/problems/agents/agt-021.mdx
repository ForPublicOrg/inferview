## Question

<Callout kind="interview" label="Design round, 40 minutes">
"Our operations assistant is connected to seven MCP servers with two hundred tools, and it keeps calling the wrong ones. Fix tool selection, and show me how you will know it worked."
</Callout>

The situation, as a scenario:

- An internal assistant used by support and on-call engineers. Seven MCP servers, owned by seven teams, expose 200 tools. You own the agent and the gateway in front of the servers; you cannot change the servers' tools this quarter.
- Tool definitions measure 140,000 tokens with the provider's counter, and every request carries all of them.
- In 300 sampled sessions from last month, 27 had at least one call to the wrong tool. The common confusions: three servers each expose a tool called `search`; `create_ticket` against `create_incident`; and two different `notify` tools.
- The on-call team will reject any change that adds more than one model turn to a typical request.
- The agent runs on one provider today, and leadership wants to keep the option of moving it to another.

## Answer

<Depth>
<Fragment slot="short">
<p>Rename at the gateway so every tool carries its server as a prefix, which removes the three identical names. Defer every tool except the handful the traces show are used most, and let the model find the rest through tool search, so a request carries a few thousand tokens of definitions instead of 140,000. Then measure on a labelled set of real tasks: wrong-tool rate, whether search surfaced the right tool, task success, turns and tokens, before and after, on the same tasks.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Names first.</strong> Three tools called <code>search</code> cannot be told apart by any selection method, deferred or not. The gateway rewrites names to <code>&lt;server&gt;_&lt;tool&gt;</code> and maps calls back. Both providers' docs push the same way: Anthropic's tool search docs say to prefix by service so one search matches the group, and OpenAI's say to keep each namespace under 10 functions, so a server with 40 tools becomes several namespaces. Anthropic's tool-writing guidance adds that prefix against suffix changed its own results and the effect varies by model, so the naming scheme is something the eval decides, not taste.</p>
<p><strong>Then defer.</strong> At 140,000 / 200 = 700 tokens per definition on average, loading the five most-used tools upfront costs about 3,500 tokens, and each search that returns the default 5 tools adds about another 3,500. A request that needs one search carries roughly 7,000 tokens of definitions against 140,000 today. Which tools stay upfront is a number you choose from call counts: the docs suggest 3 to 5, and anything called in most sessions belongs there because it saves the search turn.</p>
<p><strong>Then measure.</strong> Build 400 tasks from real sessions, each labelled with the tool or tools that should be called. At a 9% wrong-tool rate (27 of 300), the standard error on 400 tasks is √(0.09 × 0.91 / 400) ≈ 0.014, so a 95% interval is about ±2.8 points: a fall to 5% is visible, a fall to 8% is not. Run both configurations on the same tasks and compare per task. Report search recall separately (was the right tool among those returned), because it is the failure deferral introduces.</p>

### Two defensible designs

**Provider-hosted tool search.** Mark tools `defer_loading: true`, keep a few upfront, and let the provider's search load the rest: regex or BM25 on Anthropic's API, hosted search over namespaces on OpenAI's. The vendor reports large accuracy gains on its own large-library evaluations (Opus 4 from 49% to 74%, Opus 4.5 from 79.5% to 88.1%). Cost: one extra model turn whenever the needed tool is deferred; matching only on names, descriptions and argument text you do not control this quarter; and two providers with different shapes (Anthropic's deferred tools cannot carry a cache breakpoint; OpenAI injects loaded tools at the end of the context), which works against keeping the provider option open.

**Your own router.** A client-executed search: your code ranks tools against the request using descriptions, call history and the caller's role, and returns the tool references or loads the namespace. OpenAI's docs recommend client-executed search when discovery depends on tenant or project, which matches the support and on-call split. Cost: you own an index, a ranking function and its eval, and in OpenAI's client mode a changing loaded set breaks the prompt cache from that point. It is provider-neutral, because the router is yours.

I would ship hosted search this quarter behind the gateway's renaming, because it fits the one-extra-turn limit and needs no change to the servers, and keep the router as the reversal if the eval shows search recall is the bottleneck or if the provider switch happens. A third option, splitting into one sub-agent per server, puts an agent boundary and a handoff on requests that span two servers, which many on-call requests do (find the incident, then notify), so I would not start there.

**The constraint conflict.** Latency against accuracy: every deferred tool the request needs costs a search turn, and the on-call team allows one. The upfront set is how you buy that turn back for common requests, and every tool you add to it costs about 700 tokens per request and some of the confusion you are removing.

### The rollout, written down

1. Gateway renaming with a reverse map, shipped alone and evaluated alone, because it may fix most of the 27.
2. Deferral with the five most-called tools upfront, on 10% of sessions.
3. Rollback triggers: search recall below 95% on the eval set; wrong-tool rate on live sessions not below the baseline after two weeks; median model turns per request up by more than one.
4. Each server team gets a report of its tools that search missed, with the query that missed them, because descriptions are now retrieval text and only they can fix it next quarter.

**What you give up:** the guarantee that every tool is visible on every turn, a turn of latency on requests that need an uncommon tool, and descriptions written for people; they become search text.

### Where this fails

A search miss is silent. If the right tool does not come back, the model does not know it exists: it uses a near neighbour, falls back to a generic tool, or tells the user it cannot help, and none of those look like a selection error in the trace. That is why search recall is its own metric, measured on the labelled set where the right answer is known, and why a session that ends with "I can't do that" on a task the eval says is possible counts as a failure, not a refusal.

## Follow-ups

- *Your evaluation shows wrong-tool calls fell from 9% to 4%, but median turns rose by 0.8 and on-call says the assistant feels slower. Which half of the change do you keep, and what accuracy do you accept in writing?*
- *What would you need to see in the eval to replace hosted search with your own router?*
- *Two senior engineers disagree: one wants to consolidate the ticket tools at the gateway into one tool with a type argument, the other wants to leave the servers' tools alone. How do you decide without deciding by rank?*
- *Leadership moves the assistant to the other provider in six months. Which parts of your design move unchanged, and which you rebuild?*

## Common mistakes

- Deferring tools without fixing the duplicate names, so search returns three tools called `search`.
- Measuring only wrong-tool calls and missing the tasks where the right tool was never found.
- Comparing before and after on different weeks of live traffic instead of on the same labelled tasks.
- Treating hiding a tool from search as access control.
