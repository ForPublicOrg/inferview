## Question

<Callout kind="interview" label="Interview question">
"Before we launch this coding agent, what does one run cost, and what stops a run that goes wrong from costing ten times that?"
</Callout>

The run, as a scenario: 30 model calls on Claude Opus 5.5, each re-sending the whole conversation. The system prompt and tool definitions are 8,000 tokens. Each turn adds 3,000 tokens to the history (the tool result plus the model's previous reply). Each call writes 400 output tokens. Seven of the calls (calls 6, 10, 14, 18, 22, 26 and 30) come straight after a `run_tests` tool call, and the test suite takes between 4 and 9 minutes.

Published prices for Opus 5.5, per million tokens, checked 2026-10-28: $4 input, $5 for a five-minute cache write, $8 for a one-hour cache write, $0.20 for a cache hit, $20 output. The default cache lifetime is five minutes, refreshed at no cost on every hit and measured from the start of the request.

1. Estimate one run with no caching.
2. Choose a cache lifetime and estimate one run with caching. **Enter this second figure.**
3. Finance sets a ceiling of $3 for any single run (scenario). Choose `max_turns` and `max_budget_usd` for the Claude Agent SDK, and say at which call a runaway stops when the cache holds and when it does not.

## Answer

<Depth>
<Fragment slot="short">
<p>No cache: $6.42, and the re-sent history is most of it. With a one-hour cache that every call hits: $1.29. The five-minute default looks cheaper at $1.01, but test runs longer than five minutes expire the cache, and each call after one rewrites its whole input; with all seven expiring the run costs $2.89. Pick the one-hour lifetime. For the ceiling, a turn cap cannot express dollars, because the same 45 turns cost $2.12 with a warm cache and $13.68 without one; set <code>max_budget_usd</code> to about $2.70 so the one response that can overshoot it still lands under $3, and keep <code>max_turns</code> at about 45 as a backstop that counts the final turn.</p>
</Fragment>
<Fragment slot="long">
<p><b>No cache.</b> Call <i>k</i> sends 8,000 + 3,000 × (<i>k</i> − 1) tokens. Over 30 calls: 30 × 8,000 = 240,000 for the repeated prefix, plus 3,000 × (0 + 1 + … + 29) = 3,000 × 435 = 1,305,000 for the history, so 1,545,000 input tokens, $6.18. Output: 30 × 400 = 12,000 tokens, $0.24. Total $6.42. The history term is 84% of the input (1,305,000 of 1,545,000), and it grows with the square of the number of calls.</p>
<p><b>Cache that holds on every call.</b> From call 2 on, call <i>k</i> reads what call <i>k</i> − 1 sent and writes the 3,000 new tokens. Reads: 1,450,000 tokens at $0.20 per million, $0.29. Writes: the 8,000-token prefix once plus 29 × 3,000, so 95,000 tokens. At the five-minute rate that is $0.475 and the run costs $1.01; at the one-hour rate $0.76 and the run costs $1.29. Output stays $0.24.</p>
<p><b>Which lifetime.</b> A call that comes more than five minutes after the previous one starts finds the cache gone and writes its whole input. A miss at call 30 writes 95,000 tokens at $5 per million instead of reading 92,000 at $0.20, which adds $0.44 to the run. With all seven slow test runs expiring the five-minute cache, the run costs $2.89. The one-hour lifetime costs 95,000 × $3 per million = $0.285 more per run in writes, which a single miss at call 22 or later already exceeds (a miss at call 6 adds only $0.10). Any answer from $1.10 to $1.50 counts: the one-hour figure, or a five-minute figure that assumes only some test runs expire it.</p>
<p><b>The dominant term moves.</b> Uncached, the re-sent history dominates. With the one-hour cache, writes are $0.76 of $1.29, so the next saving is in what each turn adds (smaller tool results), not in the history.</p>
<p><b>The ceiling.</b> With the one-hour cache holding, a runaway that keeps adding 3,000 tokens a turn crosses $3 at call 59. Without the cache, it crosses $3 at call 20 ($2.81 after 19 calls, $3.08 after 20). The SDK compares spend with <code>max_budget_usd</code> after each response arrives, so the response that crosses the cap is paid in full. Near the uncached crossing a single call costs about $0.26, so leave roughly that much headroom: a cap of $2.70 stops an uncached runaway after call 19 at $2.81 and a cached one after call 55 at $2.75, both under $3. <code>max_turns</code> should come from the turn counts of successful runs, plus one for the final text-only turn; 45 here is a backstop, not the cost control.</p>
<p><b>Failure mode of this budget.</b> A normal 30-call run without the cache costs $6.42, so whenever the cache breaks, the $2.70 cap also stops healthy runs at call 19 with <code>error_max_budget_usd</code>. Changing a tool definition invalidates the whole cache, so a tool edit can turn the spend cap into an outage. Alert on the cache-read share per run, so a broken cache is seen as a cache problem rather than as a wave of budget stops.</p>

### Which answers are unreasonable

- $1.01: the five-minute cache with every call hitting, which ignores that the test suite runs longer than the lifetime.
- $0.53: cache reads plus output with no writes. The new 3,000 tokens each turn are written to the cache before they can be read.
- $0.62: the last call's 95,000 input tokens plus the run's output, which prices the input of one call instead of thirty.
- $6.42 for the second figure: correct for the first, but it is the uncached run.

The assumption that flips the lifetime decision is the gap between calls. If every tool returned within seconds, the five-minute lifetime would cost $1.01 against $1.29 and win.

## Follow-ups

- *A teammate proposes a turn cap of 30 because a normal run is 30 calls. What breaks?* The cap counts the final text-only turn, so a run that needed all 30 calls for tools ends with `error_max_turns` and no answer.
- *The agent moves to Claude Sonnet 5.5. Recompute the cached run and say whether the lifetime decision changes.*
- *The full test log makes up most of what those seven turns add (scenario). What does the test tool return instead, and what does the agent lose?*

## Common mistakes

- Pricing the final context instead of the sum over all calls.
- Assuming the five-minute cache survives tool calls that take longer than five minutes.
- Leaving out cache writes, which are the largest cached cost here.
- Setting only a turn cap and calling it a budget.
- Setting the spend cap exactly at the ceiling, which the response that crosses it overshoots.
