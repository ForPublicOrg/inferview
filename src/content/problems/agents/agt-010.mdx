## Question

<Callout kind="interview" label="Design round, 40 minutes">
"Our ticketing MCP server is stateful and sits behind sticky sessions. The 2026-07-28 revision removed the handshake, sessions and server-initiated requests. Plan the migration, and write down what you would retire and when."
</Callout>

The situation, as a scenario:

- One MCP server for the ticketing system, on revision 2025-11-25: six instances behind a load balancer with affinity on `Mcp-Session-Id`.
- In instance memory per session: the user's selected project, a cursor for paginated searches, and `create_ticket` calls paused on an `elicitation/create` request the server sent down the SSE stream, waiting for the client's answer.
- `summarize_thread` asks the client's model to summarise a ticket thread through sampling.
- About forty client applications. You do not control when they upgrade; usage is concentrated, but you have not measured how much.
- Two constraints you cannot move. On 2027-03-31 the platform team replaces the load balancer with the shared MCP gateway, which has no session affinity. And ticket text may only be sent to the company's approved model provider.
- Your team is three engineers this quarter.

## Answer

<Depth>
<Fragment slot="short">
<p>Build a stateless 2026-07-28 front end over the same tool library, and split traffic at the edge by protocol version: modern requests to a stateless pool that moves behind the gateway on schedule, legacy sessions to a frozen, shrinking sticky pool kept outside it. Move each piece of state out of memory: the project becomes a tool argument, the cursor a random handle bound to the user, the paused elicitation an input_required result with integrity-protected requestState, and create_ticket gets an idempotency key enforced in the database. Replace sampling with a direct call to the approved provider. Retire the legacy pool when its traffic falls below a threshold you publish now.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Measure first.</strong> Count calls and distinct clients per revision, and list the ten biggest clients with owners and release cadence. The plan below assumes the long tail is small; if legacy traffic is mostly one team that will not move before the gateway date, the decision changes (see the second design).</p>
<p><strong>State inventory.</strong> The selected project belongs to the user: make it a tool argument, with a per-user default in your database. The search cursor spans requests: return a random, expiring handle and key the stored cursor as user and handle, because the spec says possession of a handle is not authentication. The paused <code>create_ticket</code> becomes a multi round-trip request: return <code>resultType: "input_required"</code> with the elicitation in <code>inputRequests</code> and the partial arguments in <code>requestState</code>, sealed with AEAD and carrying the principal, an expiry and a digest of the original arguments. The client retries with a new request id, and any instance can finish it.</p>
<p><strong>Single use.</strong> The spec is explicit that principal, TTL and digest bound replay but do not make requestState single-use. Two retries of the same answered elicitation, or a retry after a dropped stream (streams are no longer resumable), create two tickets unless <code>create_ticket</code> takes an idempotency key and the database enforces it. The state moves from instance memory to a unique index, which the gateway can live with.</p>
<p><strong>Sampling.</strong> Sampling still works through <code>inputRequests</code> and is not eligible for removal before the first revision released on or after 2027-07-28. Keeping it costs nothing to build but sends ticket text to whatever model each client uses, which breaks the provider constraint for any client not on the approved provider. Calling the approved provider from the server fixes that and moves the model bill and the credential to your team.</p>
<p><strong>Edge routing.</strong> Requests carrying <code>MCP-Protocol-Version: 2026-07-28</code> go to the stateless pool; <code>initialize</code> and anything older go to the legacy pool. Both pools import one tool library, so behaviour cannot drift by more than the protocol layer. The legacy pool keeps affinity because a 2025-11-25 client answers a server-sent elicitation by POSTing to the endpoint, and that POST has to reach the instance holding the paused call.</p>
<p><strong>The rest of the new revision.</strong> Implement <code>server/discover</code>, return <code>tools/list</code> in a fixed order with <code>ttlMs</code> and <code>cacheScope</code>, let the gateway rate-limit and log per tool from the <code>Mcp-Method</code> and <code>Mcp-Name</code> headers, and move any log notifications to OpenTelemetry, since Logging is deprecated.</p>

### Two defensible designs

**Split pools at the edge (recommended).** A stateless pool for modern clients and a frozen sticky pool for legacy sessions, both on one tool library. Cost: two deployments and two protocol layers to keep honest; the legacy pool still drops paused elicitations on every redeploy, so it is frozen except for security fixes; and the gateway date is met only for modern traffic, with the sticky pool surviving as a written, owned exception outside the gateway until it drains.

**One dual-era pool with a relay.** The spec lets one server answer both eras on one endpoint. Legacy sessions move to a shared store, and a pub/sub relay delivers each legacy elicitation answer to the instance holding the paused call, so affinity goes away for everyone before 2027-03-31. Cost: you build and test a relay and a session store for a protocol revision you are retiring, with three engineers, and a relay bug loses tickets for exactly the clients you cannot upgrade. This wins if measurement shows a large legacy share that cannot move before the gateway date and the platform team will not accept an exception.

The conflict is the gateway deadline against clients you do not control. Split pools spend your three engineers on the destination and accept a temporary exception; the relay spends them on the past and meets the date for everyone.

### Choose the numbers

- **requestState TTL.** Long enough for a person to find a project name, short enough to bound replay: 10 to 30 minutes is defensible. Under a minute fails people who switch windows; a day turns a leaked blob into a day-long replay window, bounded only by the idempotency key.
- **Retirement threshold for the legacy pool.** Something like under 1% of calls and no named critical client for 14 consecutive days, published with an end date. A threshold of zero never arrives, because one forgotten script keeps calling.
- **Idempotency key retention.** At least the requestState TTL plus the longest client retry window, so a late retry still finds its key.

### The migration plan, written down

1. Weeks 1 to 2: measure revision mix and client owners; publish the threshold and the legacy end date.
2. Weeks 3 to 8: tool library extracted; stateless front end with MRTR, handles, idempotency keys, direct model calls; contract tests from a 2025-11-25 client and a 2026-07-28 client against both pools.
3. Weeks 9 to 12: edge routing by header; modern pool behind the gateway with a 5% canary, then all modern traffic.
4. From then: migrate clients by call volume, top ten first, with their owners.
5. Rollback triggers: duplicate ticket ids above zero in the canary; any modern request answered with a non-modern error body (it pins dual-era clients to legacy); input_required completion rate on the modern pool below the legacy elicitation completion rate over a week.

**What you give up:** one fleet and one code path until the legacy pool drains, the sampling path's zero model cost, and the claim that everything runs behind the gateway on 2027-03-31.

### Where this fails

Dual-era clients try a modern request first and fall back to `initialize` when the error body is not a recognised modern error, and the spec lets them cache that era per origin and persist it across restarts. A gateway or proxy that answers a modern request with a bare 400 during rollout teaches those clients the server is legacy, and they stay on the sticky pool long after the stateless one works. The legacy share stops falling for a reason that has nothing to do with client owners. Watch the share of clients that send a modern request and then `initialize` from the same origin.

## Follow-ups

- *The gateway date cannot move, the platform team refuses an exception, and twelve legacy clients belong to a team that will not release before July. Do you build the relay or break them, and who signs off in writing?*
- *What would you need to see in the first month of measurements to switch from split pools to the relay?*
- *Two senior engineers disagree: one wants to keep sampling until 2027 to avoid a model bill, the other wants direct calls now. How do you decide without deciding by rank?*
- *A client reports two identical tickets after a network blip. Walk through which of your controls should have stopped it and what you check first.*

## Common mistakes

- Moving the legacy session store to a shared cache and removing affinity, without noticing that a paused legacy elicitation is a live call on one instance.
- Treating the twelve-month deprecation window as the deadline for legacy clients. The window covers deprecated features such as sampling; supporting 2025-11-25 clients is your own policy, with your own end date.
- Signing requestState and assuming that makes it single-use.
- Keeping sampling because it still works, and sending ticket text to models the company has not approved.
