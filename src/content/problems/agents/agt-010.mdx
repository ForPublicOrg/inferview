## Question

<Callout kind="interview" label="Interview question">
"MCP 2026-07-28 removed the initialize handshake, session IDs and server-initiated requests. You run stateful MCP servers behind sticky sessions. Plan the migration."
</Callout>

Scenario: your company runs an internal MCP server for the ticketing system, on revision 2025-11-25, six instances behind a load balancer with session affinity on `Mcp-Session-Id`. It keeps per-session state in memory: the user's selected project, a cursor for paginated searches, and half-finished `create_ticket` calls waiting for an elicitation answer. One tool uses sampling to ask the client's model to summarize a ticket thread. About forty client applications use it, and you do not control when they upgrade.

Design the migration.

## Hints

<details class="hint"><summary>Hint 1</summary><p>List every piece of state the server holds between requests, and decide for each where it goes when there is no session.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Clients upgrade on their own schedule. How does one server tell an old client from a new one?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Sampling is deprecated. Who calls the model now?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Inventory the session state and move each piece out of memory: selected project becomes a tool argument, pagination becomes an opaque cursor or server-minted handle passed back by the client, and pending elicitations become input_required results that the client answers by re-sending the request. Replace sampling with a direct call to a model API. Serve both revisions during the deprecation window, telling them apart by whether a request carries the version in _meta, and drop session affinity once old clients are gone.</p>
</Fragment>
<Fragment slot="long">
<p>State inventory. The selected project is user context: make it an explicit tool argument, or store it per user (not per session) in your own database. The search cursor becomes an opaque, signed token the server returns and the client passes back, so any instance can continue the search. The changelog's own term is a server-minted handle passed as a tool argument.</p>
<p>Mid-call input. A create_ticket that needs the project now returns resultType input_required with an elicitation in inputRequests, holding nothing in memory. The client re-sends the same tools/call with inputResponses. Because the call can arrive at any instance and may be retried, create_ticket needs an idempotency key so a retry after a lost response does not create two tickets. That matters more now that SSE resumability is gone: a broken stream loses the request and the client re-issues it.</p>
<p>Sampling. It is deprecated. The summarizing tool calls a model API directly with the server's own credentials and cost centre, which also makes the cost visible to the team that owns it.</p>
<p>Two revisions at once. Old clients start with initialize; new ones send io.modelcontextprotocol/protocolVersion in _meta on every request. Route both to the same tool implementations through a thin adapter: for old clients keep a session store, but move it from instance memory to a shared store such as Redis so affinity is no longer needed even before the cut-over. Deprecated features keep working for at least 12 months, which bounds the dual-stack period.</p>
<p>Gateway and ops. New requests carry Mcp-Method and Mcp-Name headers, so the gateway can rate-limit and log per tool without parsing bodies. Return tools/list in a deterministic order so clients' prompt caches survive. Implement server/discover. Replace any Dynamic Client Registration with Client ID Metadata Documents in the auth setup.</p>
<p>Rollout. Ship the stateless path behind a flag, run contract tests from both revisions against every instance, migrate clients by usage, watch the share of traffic still on 2025-11-25, then remove affinity and the session store.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What breaks if you skip the idempotency key?</em> Retries after a dropped stream or a re-sent input_required request create duplicate tickets.</li>
<li><em>How do you test statelessness?</em> Send each request of a multi-step flow to a different instance in CI, and kill instances mid-flow.</li>
<li><em>Subscriptions?</em> Resource subscriptions move to subscriptions/listen, so anything that pushed updates over the old GET stream needs reworking.</li>
</ul>
</Fragment>
</Depth>

The core of a strong answer is the inventory. Every piece of in-memory session state is a design decision: does it belong to the user (store it per user), to the request (make it an argument), or to a multi-step flow (encode it in a handle or in the re-sent request)? Candidates who start with "remove sticky sessions" without the inventory usually lose the half-finished elicitations, which are exactly the state the new revision was designed to eliminate.

The second thing interviewers listen for is a plan for the forty clients. The protocol change is a breaking change, and you do not control their upgrade schedule. A dual-stack server with a shared session store for old clients, retired when traffic on the old revision reaches zero, is the standard answer, and the 12-month minimum deprecation window gives you the timeline.

## Follow-ups

- *Why did MCP make this change at all?* So remote servers scale horizontally behind ordinary load balancers without shared session storage, according to the spec's page on multi round-trip requests.
- *What about local stdio servers?* There is one client per process, so affinity was never a problem, but they still move to the new message shapes.
- *How do you sign the cursor handle?* An HMAC over the cursor state, the user and an expiry, so a client cannot forge or reuse another user's cursor.

## Common mistakes

- Removing affinity before moving pending elicitations out of memory, which drops every in-flight call on a redeploy.
- Keeping sampling because it still works, and discovering the removal later.
- Making cursors plain offsets that a client can tamper with to read past its permissions.
- Treating the migration as a server change only, with no plan for clients that upgrade late.
