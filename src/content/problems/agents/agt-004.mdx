## Question

<Callout kind="interview" label="Interview question">
"Discuss the trade-offs of ReAct versus function calling versus LangGraph-style explicit state machines." Then, for each of three systems your team owns, pick one and say what it costs.
</Callout>

The team is two engineers with six weeks. All numbers are scenario.

1. **Invoices.** About 40,000 supplier invoices a day arrive as PDFs. Line items go into the ledger, and totals must reconcile with the invoice total. A wrong posting costs a manual reversal by finance.
2. **Codebase questions.** About 300 engineers ask questions about a large monorepo ("where is the retry policy for the billing client set?"). Answers should arrive within a minute. Some questions need one search, some need a dozen reads.
3. **Refunds.** Gather the order, check it against the refund policy, get a human approval above a threshold, then pay out. Approvals can take two days. Finance wants an audit trail. Workers restart on every daily deploy.

For each system, say which shape you would build, what it costs, and the one number the design depends on that you would choose.

## Answer

<Depth>
<Fragment slot="short">
<p>The three differ in who owns control flow, not in which library runs it. ReAct and native function calling are the same model-directed loop with two encodings of the action; an explicit state graph fixes the transitions in code and puts model calls inside some nodes. Invoices: a fixed workflow, extract then validate in code then post, with failures going to a human queue. Codebase questions: a model-directed loop with function calling, read-only tools, a turn budget and a spend cap. Refunds: a durable state machine with a model call in the policy step and a pause before payout, with the payout after the pause and keyed for idempotency. Whether that state machine is LangGraph or a table in the database you already run is the decision six weeks forces.</p>
</Fragment>
<Fragment slot="long">
<p><b>ReAct versus function calling.</b> ReAct had the model write a thought and an action as text, which the harness parsed; the paper's abstract reports absolute success gains of 34 and 10 points on ALFWorld and WebShop over imitation and reinforcement-learning baselines, measured in 2022. Native function calling returns the action as structured JSON against a schema. The loop is the same; text parsing adds a failure class (malformed actions) that structured calls remove. LangGraph's own prebuilt ReAct agent, <code>create_react_agent</code>, is deprecated in v1 in favour of LangChain's <code>create_agent</code>.</p>
<p><b>Invoices: a workflow.</b> The steps are known: extract, check that line items sum to the total and that the supplier exists, post. Anthropic's definitions put this on the workflow side (predefined code paths), and its prompt-chaining pattern with a programmatic gate fits. Cost per invoice is a fixed number of model calls, every step can be tested with fixtures, and the reconciliation check is code, not a model. The number to choose is the validation-failure rate the human queue can absorb: at 40,000 invoices a day, each percentage point of failures is 400 invoices for reviewers. Ask the reviewers' capacity; if failures exceed it, add a second extraction pass or a narrow model-directed fallback for those invoices only, not for all of them.</p>
<p><b>Codebase questions: a model-directed loop.</b> The number of searches depends on what the first search returns, so no fixed path fits. Function-calling loop, read-only tools (search, read with line ranges, list), and two budgets: a turn cap and a spend cap, because the same number of turns costs different amounts as the history grows. The number to choose is the turn cap: take the turn counts of successful runs from traces, set the cap above the high tail, and add one for the final text-only answer so a capped run still returns something. The minute-long latency target bounds it too: if one call takes a few seconds, a minute holds a limited number of sequential calls.</p>
<p><b>Refunds: a durable state machine, and two defensible ways to build it.</b> The shape is known (gather, check, approve, pay) but a run lives for days, crosses deploys and moves money. Each step has to persist its state, the approval pause has to survive restarts, and every transition has to be recorded.</p>
<ul>
<li><b>LangGraph with a durable checkpointer.</b> Interrupts, checkpoints per step and resumption by thread id come with it. Cost: a new dependency to learn and operate within six weeks, and a checkpointer store to run.</li>
<li><b>A state column in the existing database and the existing job queue.</b> No new dependency, and the audit trail is rows you already back up. Cost: the team writes the pause, resume and retry logic itself, and gets no help from a framework when the flow grows.</li>
</ul>
<p>With two engineers and six weeks, the second is the cheaper start if the team already runs a queue it trusts; the first wins if more flows like this are coming. In both, the model sits inside the policy step only, and the payout is a separate step after the approval.</p>
<p><b>How the refund design fails.</b> LangGraph restarts an interrupted node from its beginning on resume, so a payout placed before the <code>interrupt()</code> in the same node runs again on every resume. Durable execution is at-least-once per step in either build, so the payout needs an idempotency key (the refund id) at the payment provider. The OpenAI Agents SDK documentation says the same of its own approvals: approval permits a call, it does not make it exactly-once, and resuming from an older approved snapshot can run the tool again. And a refund waiting two days for approval resumes under whatever graph or code was deployed since; a deploy that renames a step or changes the state shape breaks every waiting refund unless state is versioned.</p>
</Fragment>

## Follow-ups

- *Which of Anthropic's workflow patterns would you add to the invoice system first, and where?* Routing by supplier format before extraction, or an evaluator-optimizer pass on invoices that fail reconciliation, with a fixed cap on iterations.
- *The refund graph changes shape while 200 refunds are waiting for approval. What do you deploy, in what order?*
- *How do you test each system?* Workflows step by step with fixtures; the model-directed loop with outcome checks over repeated trials and trace review; the state machine by replaying recorded state transitions, including a resume after a restart.

## Common mistakes

- Treating ReAct and function calling as two architectures rather than two encodings of one loop.
- Choosing a model-directed loop because the task involves a model, when the steps are fixed.
- Holding a two-day approval in an in-process loop, which the next deploy discards.
- Putting the payout before the pause, or in the same node as the interrupt, so a resume pays twice.
- Naming a framework as the answer to "how much control does the model have?"
