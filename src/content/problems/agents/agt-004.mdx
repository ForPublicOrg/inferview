## Question

<Callout kind="interview" label="Interview question">
"Compare a ReAct-style agent, native function calling, and an explicit state machine like a LangGraph graph. When would you pick each?"
</Callout>

Make it concrete. For each of these three systems, say which shape you would build and why:

1. Extract line items from uploaded invoices, validate totals, and write them to the ledger.
2. Answer open-ended questions about a codebase by searching, reading files and running commands.
3. Approve refunds: gather the order, check policy, ask a human above a threshold, then pay out.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask whether you could draw the sequence of steps before the request arrives.</p></details>
<details class="hint"><summary>Hint 2</summary><p>ReAct and native function calling are the same loop; what differs is how the action is encoded.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Think about which system has to pause for days and resume.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>They differ in who owns control flow. A workflow or explicit state machine fixes the steps in code; a ReAct loop lets the model choose the next step each turn, and native function calling is just the modern encoding of that choice. Invoices: a fixed workflow. Codebase questions: an open loop with tools. Refunds: a state machine with a model inside some nodes, because it needs checkpoints, a human pause and auditable transitions.</p>
</Fragment>
<Fragment slot="long">
<p>ReAct versus function calling. ReAct had the model write its reasoning and an action as text, which the harness parsed. Native function calling returns the action as structured JSON validated against a schema. The loop is identical; function calling removes the parsing failures. With native tool calling available, there is little reason to parse "Action:" lines yourself.</p>
<p>Open loop versus graph. Anthropic's definitions separate workflows, where code paths are predefined, from agents, where the model directs its own process. A state machine is a workflow with explicit states and transitions, and some nodes can contain a model call or even a small agent loop.</p>
<p>The three systems. Invoices have a known sequence, so a pipeline (prompt chaining with validation gates) is cheaper, testable step by step, and has a fixed cost. Codebase questions have unknown depth: the number of searches depends on what the first search returns, so an open loop with search, read and run tools, plus budgets. Refunds have a known shape but need durable state, a human approval that can take days, and an audit trail, so a graph with a checkpointer and an interrupt before payout; the policy check can be a model call inside one node.</p>
<p>Trade-off. The more control flow you give the model, the more capable and the less predictable the system gets. Start with the most constrained shape that works and open it up where the steps really vary.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What does LangGraph give you over a while loop?</em> Explicit state, checkpoints at every step, interrupts for human input and replay. In LangGraph 1.x the prebuilt agent moved to LangChain's create_agent, which is itself a graph.</li>
<li><em>When does the workflow break?</em> When inputs stop fitting the fixed path, for example invoices in a format the extractor never saw. Add a routing step that sends odd cases to a more open path or a human.</li>
<li><em>How do you test each?</em> Workflows step by step with fixtures; open loops with trajectory checks and outcome evals over repeated trials.</li>
</ul>
</Fragment>
</Depth>

A useful way to say it in the room: control flow is a dial, not a type. Each step you move from fixed code to model choice buys flexibility and costs predictability, cost control and testability. The three examples sit at three positions on that dial: fully fixed, fully open, and fixed with model judgement at chosen nodes.

The refund system is where candidates lose points by picking a pure agent. Money moves, a human must approve above a threshold, and the process may wait days. That needs persisted state keyed by the request, a pause that survives restarts, and side effects that are safe to retry. A graph with a checkpointer gives you all three; an open loop gives you none of them for free.

## Follow-ups

- *Which of Anthropic's workflow patterns fits the invoice system?* Prompt chaining with a programmatic gate between steps (totals must add up before the write).
- *Where would you put an evaluator-optimizer loop?* Around a generation step whose quality can be checked, such as a summary checked against a rubric, with a fixed cap on iterations.
- *Your codebase agent starts taking 40 steps. Do you switch to a workflow?* Not necessarily. Look at the traces first; usually one tool returns too much or too little.

## Common mistakes

- Treating ReAct and function calling as different architectures rather than two encodings of one loop.
- Choosing an agent because the task involves a model, when the steps are fixed.
- Forgetting durability: a human approval step in an in-memory loop is lost on the next deploy.
- Naming a framework instead of a shape. "LangGraph" is not an answer to "how much control does the model have?"
