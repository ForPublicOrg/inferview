## Question

<Callout kind="interview" label="Interview question">
"When do you use A2A and when MCP? Can they work together?"
</Callout>

You are building a travel-booking agent. It needs two integrations:

1. Your company's fare database, which answers price queries in under a second.
2. A partner company's visa-check agent. It runs its own multi-step process that can take days, sometimes stops to ask the traveller for a passport scan, and the partner will not expose how it works inside.

Which design fits best?

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which of the two is a function you call, and which is a party you work with?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Look at the A2A task states. Which ones would the visa agent need?</p></details>

## Answer

MCP is for an agent using tools and data; A2A is for independent agents working with each other. The A2A spec says this itself in its appendix on MCP, and adds that an agent serving A2A requests may use MCP internally. So the first design is right: the fare database is a tool behind an MCP server, and the visa service is a peer agent you reach over A2A.

The visa case is where A2A earns its place. You find the partner through its Agent Card at `/.well-known/agent-card.json`, send it a task, and the task moves through states: submitted, working, then completed, failed, canceled or rejected, with two interrupted states, input required and auth required, for exactly the "send me a passport scan" pause. Updates can stream over SSE or arrive as push notifications to your webhook, so nothing blocks for days.

Why the wrong picks are tempting. Wrapping the partner as one blocking MCP tool is how many teams start, and it holds until the first task that pauses for input or outlives the HTTP timeout. Making everything an agent sounds uniform but puts a model where a query belongs. And transport speed is beside the point: the choice is about what is on the other side, a function or a peer.

## Follow-ups

- *How does your agent trust the partner's agent?* Authenticate per the security schemes in its Agent Card; A2A v1.0 also supports signed Agent Cards.
- *What version header does a client send?* `A2A-Version`; an empty value is treated as 0.3.
- *What if the partner later exposes an MCP server instead?* Then for short, synchronous operations you could call it as a tool, but you would lose the task lifecycle for the long ones.

## Common mistakes

- Framing A2A and MCP as competitors rather than layers.
- Wrapping a long-running remote agent as a synchronous tool and discovering the timeout in production.
- Calling A2A a Google protocol. Google started it, and it is now a Linux Foundation project.
