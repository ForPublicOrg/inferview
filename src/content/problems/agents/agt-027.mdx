## Question

<Callout kind="interview" label="Design, 45 minutes. The prompt, as a candidate report gives it, translated">
"If several agents modify the same file at the same time, how do you avoid conflicts?"
</Callout>

The report gives only that sentence. The interviewer adds a scenario:

Your platform team runs a feature that splits a ticket into tasks and runs up to 8 coding agents at once on a Python monorepo. Two incidents last week:

```text
INC-1  Agents 3 and 6 both edited api/routes.py in the shared checkout. Agent 6 wrote
       the file from its own in-memory copy; agent 3's new route was gone. Both agents
       reported success.
INC-2  Agent 2 renamed users.get_user to users.fetch_user and updated every caller it
       found. Agent 5, on another branch, added billing/invoice.py calling get_user.
       Both branches merged without a textual conflict. main failed to import.
```

Constraints, also scenario: CI takes 25 minutes and belongs to another team, so you cannot change it. An agent finishes a task about every 45 minutes. Two reviewers must approve every merge and can approve about 30 agent pull requests a day between them. In a week of single-agent runs, 40% of tasks touched `api/routes.py`. You have six weeks.

Design prevention and resolution, choose how many agents run at once, and end with a rollout plan with rollback triggers and what you give up.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask which files the last hundred tasks touched, and how often two tasks running at the same time shared one.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request the merge rate the CI and the two reviewers can sustain, per hour and per day.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the test suite would have caught in INC-2 if it had run on the two branches combined.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>The two incidents are different problems. INC-1 is a lost update from shared mutable state, and giving every agent its own git worktree and branch removes it. INC-2 is a semantic conflict that no file lock would have prevented, because the agents touched different files; only tests run on the combined result catch it, so merges go through a queue that tests each branch on top of the ones ahead of it. Prevention is mostly decomposition: plan tasks so that concurrent ones do not share files, and split the hot file that 40% of tasks touch. The binding constraint is not conflicts but review: 8 agents produce about 85 pull requests a day against 30 reviews, so I would run 3.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Isolation.</strong> One worktree and branch per agent. Claude Code documents worktrees for exactly this, and its agent-teams page says two teammates editing the same file leads to overwrites. Isolation turns INC-1 from a silent loss into a merge conflict someone has to resolve, which is the point: conflicts become visible.</p>
<p><strong>Decomposition before locking.</strong> The orchestrator's plan declares the paths each task expects to change. Tasks whose paths overlap get a dependency and run one after the other; tasks whose paths are disjoint run in parallel. Carlini's 16-agent compiler build shows both halves: agents claimed tasks by writing a lock file to <code>current_tasks/</code>, and when every agent chased the same kernel bug they overwrote each other's fixes until the harness changed the decomposition so each agent had different failing files. More agents did not help; a better split did.</p>
<p><strong>The hot file.</strong> If 40% of tasks touch <code>api/routes.py</code> and tasks start independently, the chance that at least two of k concurrent tasks touch it is 1 − 0.6^k − k × 0.4 × 0.6^(k−1): 0.89 at k = 8, 0.35 at k = 3. At 8 agents, routes.py is in conflict almost all the time. Split it into one route module per package with a registry that imports them, so most tasks add a file instead of editing a shared one. That refactor is one engineer-week of the six and removes the largest source of conflicts.</p>
<p><strong>Resolution.</strong> Merges go through a merge train: each branch's pipeline runs against main plus every branch ahead of it, so INC-2 fails in the train instead of on main. A textual conflict goes back to the agent whose branch is behind: it rebases, resolves, and runs its own tests plus the tests added by the branch it conflicted with. A resolution that deletes the other side's lines is rejected by a check that every hunk of the already-merged change is still present, unless a person approves the removal.</p>
</Fragment>

### Two defensible answers

| | Pessimistic: path leases | Optimistic: worktrees and a merge train |
|---|---|---|
| How it works | An agent leases the paths in its plan before editing; a second agent waits or gets another task | Every agent edits freely in its own worktree; conflicts surface at rebase and in the train |
| What it costs | Hot files serialise everything; a crashed agent holds its lease until the expiry; plans that miss a file give no protection | Wasted work when two branches collide; rebases and train restarts; an agent's resolution can drop the other change |
| What it misses | INC-2 entirely: the agents leased different files | Nothing that the tests cover; everything they do not |

I would build the optimistic design, with leases only on files named as hot (routes.py until the split lands, the dependency lockfile, the migrations directory), because leases on every path would serialise the 40% of tasks that touch routes.py, and the train is the only part that addresses INC-2. The lease expiry is a quantity to choose: long enough that a healthy agent never loses its lease mid-task, short enough that a crash does not block the hot file for an afternoon. Twice the 95th-percentile task duration is defensible; one fixed hour is defensible if task durations are not yet measured.

### Choosing the concurrency

Arrivals: 8 agents at one task per 45 minutes is 8 × 60 / 45 = 10.7 pull requests an hour, about 85 in an 8-hour day. A serial merge queue with 25-minute CI merges 60 / 25 = 2.4 an hour. A merge train runs pipelines in parallel (GitLab's default allows 20), so CI throughput can keep up as long as few branches fail. The reviewers cannot: 30 approvals a day sustain 30 × 0.75 / 8 = 2.8 agents. So run 3 agents; at 3, the routes.py collision chance is 0.35 before the split. Two or four is a defensible answer if the reviewer number is soft; eight is not, because the queue of unreviewed branches grows by about 55 a day and every one of them goes stale against main.

### Rollout and rollback

- Weeks 1 and 2: worktree per agent, declared paths in the plan, the hunk-preservation check, leases on the hot files. Concurrency 2.
- Weeks 3 and 4: split routes.py; turn on the merge train. Concurrency 3.
- Weeks 5 and 6: measure collisions per task and train restarts per day; raise concurrency only if review capacity has grown.

Rollback triggers: any merged change found to have removed another agent's merged lines without approval returns to one agent at a time until the check is fixed. Train restarts above a third of merges in a day lower concurrency by one. A lease held past expiry by a live agent more than once a week means the expiry is too short.

**What you give up.** Five of the eight agents the feature advertises, and one week of the six on a refactor that ships no feature. Optimistic merging gives up the guarantee that two agents never work on the same file; it replaces it with detection.

**The failure mode of this design.** The train catches semantic conflicts only as far as the tests reach. INC-2 failed at import, which any test catches. A rename that leaves a caller in a code path no test exercises, or an agent's conflict resolution that keeps both sides and changes behaviour, merges green. Carlini's agents resolved frequent conflicts on their own; the hunk check covers deleted lines, not changed meaning. Coverage of the files agents touch most is therefore part of this design's budget, not a separate project.

## Follow-ups

- *The VP points out the licence covers 8 agents and asks why you run 3. Which constraint do you relax first, the reviewers or the review rule, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants leases on every path, the other wants no leases at all. How do you decide without deciding by rank?* Replay last week's tasks through both policies on the recorded file sets and compare waiting time, collisions and wasted agent-hours.
- *Agents start resolving each other's conflicts by rewriting both changes into a third version that passes the tests. Do you allow it, and who reviews it?*

## Common mistakes

- Answering with a file lock, which stops INC-1 and misses INC-2.
- Letting agents share one checkout and relying on them to re-read files before writing.
- Sizing concurrency by CPU or licence rather than by merge and review throughput.
- Telling the agent with the conflict to keep its own version.
- Adding agents when they collide, which Carlini's kernel stage shows makes it worse.
