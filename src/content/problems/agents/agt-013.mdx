## Question

<Callout kind="interview" label="Interview question">
"Your agent does well on short tasks but degrades past about 30 minutes of autonomous work. Diagnose it."
</Callout>

A coding agent works through a list of eight tasks in a repository. Runs under half an hour go well. In longer runs, it starts re-implementing tasks it already finished, and once it reported "all tasks complete" with three still failing tests. Here is the harness config and an excerpt from a long run (synthetic, written for this problem).

```text
harness config
  compaction       when input tokens exceed 120,000
  compaction step  "Summarize the conversation so far in about 300 words."
  after compaction context = system prompt + summary + last 2 turns
  task list        given once, in the first user message
  progress notes   none

minute 34, first compaction, summary as stored
  "The agent has been improving the payments module. It refactored the
   currency helpers, fixed several failing tests, and discussed the
   approach for retries with the user. Work is progressing well."

minute 35
  assistant  I'll continue with the payments work. Let me look at the
             currency helpers to see what could be improved.
             calls read_file("src/payments/currency.py")
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>When exactly does the behaviour change, and what happens to the context at that moment?</p></details>
<details class="hint"><summary>Hint 2</summary><p>After compaction, where in the context is the list of eight tasks?</p></details>

## Answer

Compaction is erasing the agent's plan. The task list existed only in the first user message, and the compaction prompt asked for a 300-word prose summary, which kept the mood ("work is progressing well") and lost the facts: which of the eight tasks are done, which tests still fail, what was agreed about retries. After minute 34 the agent's context holds the system prompt, a vague summary and two recent turns, so it does the natural thing with a vague summary: it picks something plausible and starts again.

The fix is to put state that must survive outside the context and make compaction preserve facts. Anthropic's long-running harness keeps a feature list where each item starts as failing and flips only after an end-to-end test, plus a progress file the agent updates as it works, and each fresh context starts by reading them. The compaction prompt should demand specific content (open tasks, finished tasks with evidence, decisions, files touched, failing tests) rather than a word count. And "all tasks complete" should be checked by the harness against the task list and the test run, not taken from the model.

Why the wrong picks are tempting. Silent truncation does happen in some homemade harnesses, but here the system prompt is visibly intact and compaction runs well below the limit. Temperature is the reflex answer to "the model wanders", but it cannot explain a change at a specific minute. The prompt cache cannot return stale answers; it only skips recomputing an identical prefix.

## Follow-ups

- *How would you detect this in production?* Log every compaction with before and after token counts, and alert when a run's tool calls after a compaction repeat files or tasks from before it.
- *What should never be compacted?* The goal, the acceptance criteria and the list of open items. Keep them in a pinned block or a file, not in the conversation.
- *Compaction versus tool-result clearing?* Clearing old tool outputs is lighter and keeps the conversation; it is often enough to delay compaction a long way.

## Common mistakes

- Blaming the model's long-context ability without looking at what the harness put in the context.
- Writing compaction prompts with a length target and no required content.
- Letting the model declare completion with no check against the task list and tests.
- Keeping the plan only in the first message of the conversation.
