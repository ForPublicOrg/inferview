## Question

<Callout kind="interview" label="Debug, 30 minutes">
"A long-running coding agent rebuilt two features it had already finished, after a context reset. The progress file and the run checkpoint disagree about what is done. Which defect explains the rebuild, what else is wrong, and what would you change?"
</Callout>

The harness follows the shape of Anthropic's long-running harness: a feature list, a progress file the agent appends to, a commit per feature, and a fresh session when the context gets too long. The team added a run checkpoint so the orchestrator can resume a run after a crash. The code and the evidence below are constructed for this problem.

```python
START_PROMPT = """Features already completed (authoritative): {done}
Do not rework completed features. progress.md has notes from earlier sessions.
Implement the lowest-numbered feature that is not completed, commit it, then call mark_done."""

def run_session(run_id, budget_tokens=150_000):   # 200k window; leave room for the reply
    state = store.load(run_id)                     # {"done": [...], "session": n}
    prompt = START_PROMPT.format(done=", ".join(state["done"]) or "none")
    convo = Conversation(system=SYSTEM, first=prompt)
    finished = []
    while True:
        reply = model.step(convo)
        for call in reply.tool_calls:
            result = tools.run(call)               # bash, edit, git, run_tests, mark_done
            convo.add_result(call, result)
            if call.name == "mark_done":
                finished.append(call.args["feature"])
                progress.append(f"{call.args['feature']}: done")
        if convo.input_tokens > budget_tokens:
            return start_fresh(run_id)
        if reply.stop_reason == "end_turn":
            break
    state["done"] += finished
    state["session"] += 1
    store.save(run_id, state)
    return state
```

## Answer

The reset branch returns before the save. `run_session` collects finished features in a local list and writes them to the store only after the loop breaks on `end_turn`. When the context passes the budget, `return start_fresh(run_id)` leaves the function from inside the loop, so everything session 3 finished is lost from the checkpoint. The counter confirms it: three sessions have run and the loaded state says `"session": 2`. Session 4 then got a prompt that called the stale list authoritative and told it not to rework what was on it, so it did what it was told and started at F5. This is LangGraph's `"exit"` durability mode rebuilt by hand: state persisted only when the run ends cleanly, lost on any other exit, and a context reset is just another exit.

The evidence is incomplete, and two things are worth collecting before changing anything. The store's write log would show whether session 3 ever wrote, which separates "the save never ran" from "the save ran and was overwritten". The transcript tail of session 3 would show whether F7's `mark_done` came before or after a failing test run. Without either, the fix does not depend on them: at session start, derive what is done from evidence instead of trusting any one record.

The secondary defects, ranked:

1. **`mark_done` is unverified.** It writes `F7: done` to `progress.md` on the model's word, and CI says F7 fails. This is the failure Anthropic's harness article names, marking features complete without end-to-end testing, and it will cause the opposite symptom later: a session that skips F7 because the notes say it is done. Make `mark_done` run the feature's test, commit, and only then record the feature, in that order.
2. **Three records, no reconciliation.** The checkpoint, `progress.md` and git each say something different, and the prompt picks the one the harness writes least reliably. Git commits are evidence that code exists, not that it works; the feature tests are the only record that says "done" in the sense that matters.
3. **The prompt asserts authority it cannot check.** "Authoritative" plus "do not rework" turns a stale list into an instruction. A session should start, as Anthropic's does, by reading the git log and the notes and running a basic end-to-end test before new work.

Why the wrong picks are tempting. Overflow is the reflex answer to "the agent forgot", but the harness reset with headroom and the new session started small. Concurrent sessions do produce exactly this kind of duplicate work in harnesses that spawn without waiting; here session 3 does nothing after the reset branch and the log shows one session at a time.

### The decision: what is the source of truth for "done"

Two answers are defensible.

- **Derive "done" from the tests at every session start.** The checkpoint becomes a cache. Cost: test time on every session. As a scenario, if the end-to-end suite takes 6 minutes and sessions run about 39 minutes between resets, as session 3 did from 10:02 to 10:41, re-verification adds 6 / 45, about 13 percent, to wall-clock time.
- **Keep the checkpoint authoritative and make its writes correct.** Save on every exit path (in a `finally`, or better, at each verified `mark_done`, with `sync`-style durability), so the checkpoint is at most one feature behind. Cost: it is still a record the harness can get wrong in a new way, and a crash between the commit and the save means one feature is redone.

I would write the checkpoint at each verified `mark_done` and add a narrow reconciliation at session start: compare the feature commits in git since the last checkpointed feature with the checkpoint, and run only those features' tests. That bounds re-verification to the features in dispute, usually zero or one, instead of the whole suite. The quantity I chose is that scope; running the full suite every session is reasonable when it takes a minute, and unreasonable at 6 minutes with sessions resetting every 40.

The failure mode of this fix is the tests themselves. A flaky end-to-end test flips a finished feature to "not done" and the next session rebuilds it, which is the original symptom with a new cause. And the agent can edit a failing test until it passes; Anthropic's harness tells the agent that removing or editing tests is unacceptable, which is an instruction, not a control. Make the feature tests read-only to the agent's sandbox, and quarantine a test that has flipped twice in a run instead of letting it drive rework.

## Follow-ups

- *Re-verifying disputed features adds a sandbox start and a test run to some sessions, and the team pays for sandbox hours. Which features do you stop re-checking, and what risk do you write down?*
- *What would you need to see in run logs to drop the checkpoint entirely and derive "done" from git and the tests alone?*
- *Two senior engineers disagree: one wants `progress.md` to be the only record because the model reads it anyway, the other wants a database row the harness owns. How do you decide without deciding by rank?*
- *How would you detect this class of bug in production before a person notices duplicate commits?* Alert when a session's commits touch the files of a feature whose test already passes at the session's starting commit, and when the session counter skips.

## Common mistakes

- Blaming the model's memory when the harness handed it a stale list and told it to trust it.
- Fixing the save path and leaving `mark_done` unverified, which trades rebuilt features for skipped ones.
- Treating a commit message that names a feature as proof the feature works.
- Running the whole end-to-end suite at every session start without computing what it costs per session.
