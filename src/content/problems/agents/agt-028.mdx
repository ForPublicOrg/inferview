## Question

<Callout kind="interview" label="Critique, 30 minutes">
The platform team plans to make ReviewBot v2 a required check on all 40 service repositories next Monday. You are the last reviewer on the design. List what is wrong with it, then say what you would require before Monday and what you would let ship as it is.
</Callout>

The design summary, constructed for this problem:

```text
REVIEWBOT v2: design summary (approved at architecture review)

Agents     security, performance, correctness, style, tests
           All Sonnet 5.5, temperature 0, one shared system prompt plus a role section.
Input      The PR's unified diff (3 lines of context) and REVIEW.md from the PR head branch.
Output     Each agent returns [{file, line, severity: low|med|high, message}].

Aggregation
           Post a finding when at least 3 of the 5 agents report a finding on the
           same (file, line). Severity = the highest of the agreeing agents.
           Rationale: majority voting removes single-agent hallucinations without
           an extra model call.

Posting    Findings become review comments. Any high-severity finding fails the
           required "ReviewBot" check, which blocks merge.
Triggers   Every push to an open PR, including drafts.

Pilot      3 weeks, 1 repository.
           Precision 91%: share of posted findings whose comment thread was resolved.
           Recall 38 of 40: bugs injected by a model into single functions.
           Cost $0.21 per review on average.
```

## Answer

The flaws, roughly in the order a reviewer finds them; the later ones are the ones a first read misses.

**The vote runs across specialists.** Voting reduces noise when voters answer the same question; the Debate or Vote paper finds majority voting carries most of the gains of multi-agent debate on benchmarks where every agent answers one question. Here five agents answer five different questions. A SQL injection that only the security agent is asked to look for gets one vote and is never posted, so the design removes exactly the findings the specialist split was meant to add. What survives a 3-of-5 vote is the kind of issue any generalist would see.

**Agreement is keyed on (file, line).** If style flags a long line 42, performance flags a loop on line 42 and correctness flags an off-by-one on line 42, that is three votes, posted at the highest severity, for three unrelated claims. One real bug reported by three agents on lines 41, 42 and 44 gets no agreement at all.

**The voters are not independent.** One model, one shared prefix, temperature 0. Three agents agreeing is closer to one agent asked three times with slightly different instructions; a plausible misreading of the diff is shared, and passes the vote it was meant to fail.

**Nothing checks a finding against the code.** The agents see a diff with 3 lines of context, so a finding about a caller, a lock or a type defined elsewhere is a guess. The vote filters on agreement, not on truth. MAST's verification category (FM-3.2 and FM-3.3) is this system's default state. Anthropic's Code Review, a vendor product doing the same job, documents the opposite choices: agents read the surrounding code, and a verification step checks candidate findings against it before anything is posted.

**REVIEW.md comes from the PR head.** The author of the change, or anyone whose change edits that file, controls the reviewer's instructions: one line telling the reviewer to ignore the payments directory and the check passes. Read it from the base branch only, as Code Review's documentation says it does.

**An unverified finding blocks merge.** With no verification step, a false positive at high severity stops a deploy until someone overrides the check; once overriding is routine, real findings are overridden too.

**The precision number.** A resolved thread includes "won't fix", "not a bug" and threads closed to unblock a merge. 91% is the share of findings that people closed, not the share that were correct.

**The recall number.** Forty bugs injected by a model into single functions are the bugs a diff with 3 lines of context and a majority of generalists find best. The design's blind spots, single-specialist findings and bugs that span files, are absent from the test, so 38 of 40 measures the vote's strengths.

**Cost per review is not cost per PR.** Every push to every open PR, drafts included, is a full five-agent review. A PR pushed fifteen times while in draft costs fifteen reviews, before anyone asked for one.

**Two judgement calls.** A majority vote is acceptable if it aggregates repeated samples of one reviewer answering the same question, with findings matched by meaning (a verifier or a canonical bug key), not by line. The style agent is acceptable if its findings are non-blocking and excluded from any vote and from severity.

**What to require before Monday: two defensible fixes.** Both replace the vote with the union of all agents' findings.

- *Union plus a verifier.* Each candidate finding goes to a verifier that reads the full files around it and either confirms it with a cited line or drops it; only confirmed findings post, and nothing blocks merge in the first month. The cost: one verifier call per candidate finding, so cost and latency scale with how many candidates the five agents produce before any filtering, a number the pilot never reported.
- *Union with non-blocking comments.* Post every finding at its agent's severity, never block, and measure how often authors act on each agent's findings for a month. The cost: noise on every PR, and the authors who stop reading comments in the first week stay stopped.

The conflict is Monday's deadline against a check that can block merges on unverified claims. I would ship union plus a verifier, as a non-blocking check on the pilot repository plus three volunteers, with REVIEW.md from the base branch and drafts excluded, and move the 40-repository rollout until a month of verified findings exists. The vote and the head-branch REVIEW.md do not ship in any version.

**Where the verifier fails.** It is the same model family reading the same code, so it confirms plausible false findings that it would itself have made, and it drops true findings it cannot confirm by reading, such as race conditions that need a schedule to show. A verifier that only drops findings can make recall worse than the union while the precision number improves, so the month of measurement has to include a recall test with cross-file and concurrency bugs, and a sample of dropped findings read by a person.

## Follow-ups

- *The verifier triples the cost per review. Finance asks you to cut it. Which agents' findings skip verification, and what risk do you accept in writing?*
- *Two senior engineers disagree: one wants the security agent's findings to block merge on their own, the other wants nothing to block. How do you decide without deciding by rank?* Measure the security agent's verified precision on the pilot; blocking is defensible only for a finding class whose verified precision is high enough that an override is rare, and that number comes from the month of data.
- *What would you need to see in production to make the check required again?* A month in which verified high-severity findings were acted on far more often than overridden, and a recall test with cross-file bugs that the union plus verifier passes.

## Common mistakes

- Proposing a higher or lower vote threshold, which keeps every problem with voting across specialists.
- Reading 91% as precision.
- Adding a sixth "critic" agent to the vote instead of a verifier that reads the code.
- Missing the head-branch REVIEW.md, which turns a quality problem into a security one.
- Accepting the deadline and the blocking check together because the pilot numbers look good.
