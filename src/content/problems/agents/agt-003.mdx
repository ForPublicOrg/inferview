    import inspect
    import json
    from collections import Counter


    class ToolError(Exception):
        """Raised by a tool. retryable=True means the same call may succeed later."""

        def __init__(self, message, retryable=False):
            super().__init__(message)
            self.retryable = retryable


    def run_agent(model, tools, user_msg, max_turns=8, max_repeat=2):
        messages = [{"role": "user", "content": user_msg}]
        seen = Counter()
        failed = set()
        signatures = {}
        turns = 0

        def stop(reason, answer=None):
            return {"status": "stopped", "reason": reason, "answer": answer, "turns": turns}

        def tool_message(reply, payload, is_error):
            messages.append({"role": "assistant", "tool_call": reply})
            messages.append({"role": "tool", "id": reply["id"], "is_error": is_error, "content": json.dumps(payload)})

        while turns < max_turns:
            last = turns + 1 == max_turns
            reply = model(messages, not last)
            turns += 1
            if reply["type"] == "final":
                if last:
                    return stop("max_turns", reply["text"])
                return {"status": "done", "reason": None, "answer": reply["text"], "turns": turns}
            if last:
                return stop("max_turns")
            name, args = reply["name"], reply["args"]
            key = (name, json.dumps(args, sort_keys=True))
            if key in failed:
                return stop("tool failed")
            seen[key] += 1
            if seen[key] > max_repeat:
                return stop("repeated call")
            fn = tools.get(name)
            if fn is None:
                tool_message(reply, {"error": f"unknown tool {name}", "retryable": False}, True)
                continue
            if name not in signatures:
                signatures[name] = inspect.signature(fn)
            try:
                signatures[name].bind(**args)
            except TypeError as exc:
                tool_message(reply, {"error": f"bad arguments for {name}: {exc}", "retryable": False}, True)
                continue
            try:
                result = fn(**args)
            except ToolError as exc:
                if not exc.retryable:
                    failed.add(key)
                tool_message(reply, {"error": str(exc), "retryable": exc.retryable}, True)
                continue
            except Exception as exc:
                failed.add(key)
                tool_message(reply, {"error": f"{type(exc).__name__}: {exc}", "retryable": False}, True)
                continue
            tool_message(reply, result, False)
        return stop("max_turns")

## Question

<Callout kind="interview" label="The task, as a commercial blog relays it">
A guide published by Perspective AI on 2026-05-29 lists "implementing a tool-use orchestrator" as an example of the Python problem in Anthropic's 60-minute phone screen. It attributes its stage descriptions to candidate reports, and Anthropic has not confirmed the question. The version below is written for this site.
</Callout>

Write `run_agent(model, tools, user_msg, max_turns=8, max_repeat=2)`. The model is a function standing in for the API: `model(messages, tools_enabled)` returns either `{"type": "final", "text": ...}` or `{"type": "tool", "id": ..., "name": ..., "args": {...}}`. `tools` maps a name to a Python function called with `**args`. The loop returns `{"status": "done" | "stopped", "reason": ..., "answer": ..., "turns": n}`, where `turns` counts model calls and `reason` is `None` on a normal finish.

1. Call the model with the whole message list each turn. A final answer ends the run with status `"done"`.
2. Make at most `max_turns` calls. The last allowed call is the final turn: it is made with `tools_enabled=False`, and its text becomes the answer of a run that stops with reason `"max_turns"`. A tool call returned on the final turn is not run, and the answer is `None`.
3. After a tool call, append `{"role": "assistant", "tool_call": reply}` and `{"role": "tool", "id": reply["id"], "is_error": bool, "content": json.dumps(payload)}`. An error payload is `{"error": message, "retryable": bool}`.
4. An unknown tool name, or arguments that do not fit the tool's signature, go back to the model as errors, and the tool is not called.
5. A `ToolError` with `retryable=True` goes back to the model. A `ToolError` with `retryable=False`, or any other exception raised inside a tool, is a failure of that call, and the same call never runs again in this run. Whether the run then ends at once with reason `"tool failed"` or first hands the error to the model is your decision.
6. Stop with reason `"repeated call"` instead of running a call that has already been requested `max_repeat` times. Calls are the same when the tool and the arguments match, whatever the key order, nested values included.
7. The loop's own work per turn must not grow with the length of the history. A hidden test drives a 20,000-turn run against a stand-in model that answers instantly and allows four seconds.

The visible tests cover a normal run, the message shape, an unknown tool, the final turn and a repeated call. Hidden tests inject tool errors and check properties of the run rather than one exact transcript.

## Answer

The reference is a `while turns < max_turns` loop. What matters is the order of the checks inside it and where each piece of state lives.

**The final turn.** Whether a call is the last one is known before the call, so the flag goes to the model with it. The Claude Agent SDK states the same rule from the other side: `max_turns` counts every tool-calling turn plus one for the text-only answer, and a run without that extra turn ends with `error_max_turns` and no response for the user. The OpenAI Agents SDK raises `MaxTurnsExceeded` unless an `error_handlers` entry keyed `max_turns` supplies a fallback output. A tool call returned on the final turn is dropped, not run, because nothing would read its result.

**Bad arguments versus broken tools.** The reference binds the arguments with `inspect.signature(fn).bind(**args)` before calling, and caches the signature per tool. Catching `TypeError` around the call looks equivalent and is not: a `TypeError` raised inside the tool is a bug in the tool, and reporting it as "fix your arguments" sends the model into retries that cannot work. Anthropic's documentation says Claude retries an invalid call 2 to 3 times with corrections before apologising, so a misclassified error costs real turns.

**The failed-call set and the repeat counter.** Both are keyed by `(name, json.dumps(args, sort_keys=True))`, which handles key order at every nesting level, and each costs one dictionary lookup per turn. The tempting version counts repeats by scanning the message history; on the hidden 20,000-turn run that is about 20,000 × 20,000 / 2 = 200 million comparisons, and it misses the four-second limit.

**Your policy decision: what a non-retryable failure does.** Two answers are defensible.

- End the run at once with reason `"tool failed"`. Cost: the user gets a message built from the stop reason rather than from the model, and the model never gets the chance to route around the failure (a refund rejected for exceeding the refundable balance could have been retried with the right amount).
- Hand the error to the model with `"retryable": false`, and refuse the same call if it comes back. The reference does this. Cost: one more model call per failure, which re-sends the whole history, and a model that may route around the failure in a way nobody reviewed.

The second fits tools whose errors say what would work; the first fits tools whose errors are opaque or whose side effects are risky.

**The quantity you choose: `max_repeat`.** It sits on the conflict between stopping stuck runs and allowing honest retries. With `max_repeat=2`, a tool that needs three attempts to get past a transient upstream timeout is stopped as a repeated call. Either raise it, which lets a stuck model spend more turns on each stuck key, or move transient retries into the tool wrapper so the model only sees `"retryable": true` after the wrapper's own retries are spent. The second keeps `max_repeat` at 2 or 3. `max_turns` should come from the turn counts of successful runs in your own traces, plus one for the final turn, not from a library default.

**How the reference fails.** The repeat key is exact. A model that varies its arguments on every retry (`"UPS"`, `"ups"`, `"UPS Ground"`) never trips it, and only `max_turns` stops the run. The final turn has a quieter failure: with tools disabled, the model writes an answer from partial evidence that can read as complete, so the caller has to show the user that the run stopped on `"max_turns"` rather than presenting the text as a finished answer.

## Follow-ups

- *Run this against the Claude Messages API.* Tool results become `tool_result` blocks, first in a user message, with `is_error: true` for errors. The final turn maps to `tool_choice: {"type": "none"}`, but changing `tool_choice` invalidates the cached message blocks, so that one call reprocesses the whole history at the uncached price. Do you pay that, or keep tools enabled and add a user instruction to answer now, and what do you do when the model calls a tool anyway?
- *The model returns three tool calls in one response.* Which of them may run concurrently, how do the results go back, and does a non-retryable failure in the first cancel the other two?
- *The run resumes on another worker after a crash.* The failed-call set and the repeat counter were in memory. Where do they live now, and what happens to a side-effecting call that ran just before the crash?
- *Add a spend budget.* The cost of the next call depends on the history it re-sends. What do you check before the call, and how much headroom do you leave for the call that crosses the line?

## Common mistakes

- Catching `TypeError` around the tool call to detect bad arguments, which reports tool bugs as model mistakes.
- Counting repeats by scanning the history, which is quadratic over the run.
- Raising an exception at the turn limit, so the user receives nothing.
- Keying repeats on `str(args)`, which depends on key order.
- Running the tool call returned on the final turn.
- Treating every tool error as retryable, which turns a permanent failure into a loop that only the turn limit ends.
