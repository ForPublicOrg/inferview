## Question

<Callout kind="interview" label="Critique, 35 minutes">
"Which MCP servers would you refuse to install, and why? Here is the pull request. List what you would block, what you would accept with conditions, and what you would put in place instead."
</Callout>

A platform team opens this pull request against the company monorepo so that every engineer's Claude Code session gets the same tools. Forty new engineers start on Monday and the team wants it merged before then. Host and package names other than the official reference servers and Sentry's are invented for this scenario.

The description:

> Adds a shared MCP setup. Every server is widely used, with thousands of weekly downloads. No secrets are committed: credentials come from each developer's environment. `enableAllProjectMcpServers` saves everyone from approving seven servers one by one. The CI review bot picks up the same configuration automatically, so it can query staging and read Sentry while it reviews.

`.mcp.json`:

```json
{
  "mcpServers": {
    "github":  { "type": "http", "url": "https://mcp.gitbridge-tools.dev/github",
                 "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" } },
    "db":      { "command": "npx", "args": ["-y", "pgquery-mcp@latest", "--dsn", "${DATABASE_URL}"] },
    "files":   { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "${HOME}"] },
    "fetch":   { "command": "uvx", "args": ["mcp-server-fetch"] },
    "mail":    { "command": "npx", "args": ["-y", "mailgrid-mcp"],
                 "env": { "MAILGRID_API_KEY": "${MAILGRID_API_KEY}" } },
    "sentry":  { "type": "http", "url": "https://mcp.sentry.dev/mcp" },
    "metrics": { "type": "http", "url": "http://localhost:9464/mcp" }
  }
}
```

`.claude/settings.json`:

```json
{
  "enableAllProjectMcpServers": true,
  "permissions": {
    "allow": ["mcp__db__*", "mcp__files__*", "mcp__fetch__*", "mcp__mail__send_email", "mcp__sentry__*"]
  }
}
```

From the `Makefile` and the CI workflow:

```text
metrics-mcp:
	metrics-mcp --host 0.0.0.0 --port 9464

# .github/workflows/review.yml, on: pull_request
- run: claude -p "Review this pull request and comment on risky changes"
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }}
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

## Hints

<details class="hint"><summary>Hint 1</summary><p>For each server, ask who published it, which version runs tomorrow morning, and which credential it receives.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Ask which servers can bring text an outsider wrote into the session, which can read private data, and which can send anything out, and whether one session gets all three.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what happens when a pull request edits <code>.mcp.json</code>: on a developer's laptop next week, and in this CI job today.</p></details>

## Answer

The question is not which server is dangerous on its own. It is which credential each one receives, which code runs on every start, and what one session can do with all of them together. Taken that way, two entries are refusals, three are acceptable with conditions, and the two settings around them are the larger problem.

**Refuse: the github entry.** `mcp.gitbridge-tools.dev` is not GitHub. The configuration sends every developer's `GITHUB_TOKEN` to a third party in a header, and that host now holds a credential for every repository the token reaches. The MCP authorization model exists so that a server receives a token issued for it and nothing else; this design hands a third party the upstream credential directly. Use GitHub's own server with each developer signing in through OAuth, or nothing.

**Refuse until pinned and attributed: db and mail.** `npx -y pgquery-mcp@latest` downloads and runs the newest release on every start, and `mailgrid-mcp` with no version does the same. Nobody in the description checked who publishes either. The postmark-mcp package is the worked example: not published by Postmark, 15 clean versions, then 1.0.16 added one line that BCC'd every outgoing email to an outside address, at about 1,500 downloads a week by Koi Security's count. "Thousands of weekly downloads" describes that package too. Invariant Labs' rug-pull case is the same risk one layer up: a server can change a tool's description after you approved it. Pin exact versions, install from a mirror that records hashes, and review updates after a soak period you choose; a week or two lets public reports surface without leaving the team months behind on fixes.

**Accept with conditions.** The filesystem server is the official reference server, pointed at the wrong place: `${HOME}` reaches `~/.ssh`, cloud credential files and every other checkout. Claude Code already reads the working directory, so the server only adds reach outside the repository; scope it to the repository or remove it. The database server is acceptable with a read-only role on a replica, and never with whatever `DATABASE_URL` a developer's shell holds, which on some laptops is production. Sentry with per-developer OAuth and read-only tools is reasonable, but its error messages contain text users and attackers wrote, so it counts as untrusted content.

**The combination.** `fetch` brings in any web page, `db` and `files` read private data, and `mail` sends email, and the allow rules pre-approve all of them. That is Simon Willison's lethal trifecta in one session with no prompt in the path: a fetched page or a Sentry event carrying instructions can query a table and mail the result. Split them: a research profile with `fetch` and no private data or send tools, and a work profile with data tools and no `fetch` or `mail`. If one session needs all three, sending requires a person.

**The metrics server.** `--host 0.0.0.0` with no token makes it reachable by anything on the office or VPN network. The MCP transport spec says local servers should bind to 127.0.0.1, and the security guidance says local HTTP servers should require a token or use stdio.

**The settings that outlive this review.** `enableAllProjectMcpServers: true` approves every server in `.mcp.json`, including those a pull request adds next month, for every developer who has trusted the repository. Whatever you approve today, this line approves the next one without asking.

**The CI job, the worst item.** In `claude -p`, Claude Code connects servers from `.mcp.json` without asking, approved or not. The job runs on the pull request's checkout, so any pull request that edits `.mcp.json` to add a stdio server runs that command on the runner, with the GitHub token, the staging database URL and the API key in its environment, before the model does anything. Permission rules do not help: the process starts when the server connects. Run the review with `--strict-mcp-config` and an explicit configuration from the base branch, or with no MCP at all.

**The decision, with two defensible answers.**

- **An organisation-wide approved catalog.** Managed settings with `allowedMcpServers` and `allowManagedMcpServersOnly: true`, entries by exact `serverCommand` (with the pinned version) and `serverUrl`. Cost: every new server or version waits on the platform team, the forty new engineers start with fewer tools, and the docs warn that `serverName` entries are not a control, so the catalog has to be written in commands and URLs.
- **Per-repository review.** `.mcp.json` under CODEOWNERS with security as an owner, `enableAllProjectMcpServers` removed, CI on a fixed configuration. Cost: each repository reviews the same servers again, and a developer's user-scope servers are invisible to it.

The conflict is the Monday deadline against a configuration that would give forty laptops and a CI runner an unreviewed path from private data to the outside. I would merge a reduced set before Monday (the filesystem server scoped to the repository, Sentry with OAuth, the database on a read-only replica role, pinned), fix CI the same day, and put the catalog in managed settings over the following weeks for everything else.

**Where this fails.** An allowlist that matches exact command arrays makes every version bump a policy change. If that takes a week, teams add servers at user scope instead, where the repository review never sees them, and the catalog covers less than it appears to. Measure it: export which servers sessions actually connect to, through Claude Code's OpenTelemetry tool events, and compare against the catalog each month.

## Follow-ups

- *Security wants the catalog in place before Monday; the platform team says it cannot write and test forty command entries by then. Which half ships, and what risk do you accept in writing for the week between?*
- *What would you need to see in a quarter of session telemetry to move from per-repository review to the central catalog, or back?*
- *A team says their research agent genuinely needs to fetch web pages and email summaries to customers. Design the narrowest version that does both.*
- *The pinned mail server publishes a security fix. Walk through how it reaches forty laptops, and how long that takes under your policy.*

## Common mistakes

- Judging each server alone and approving a set whose combination exfiltrates.
- Reading "no secrets committed" as safe, when `${VAR}` expansion sends each developer's real token to whatever host the file names.
- Treating download counts or a familiar vendor name as provenance.
- Reviewing `.mcp.json` and missing the CI job that executes whatever the next pull request puts in it.
