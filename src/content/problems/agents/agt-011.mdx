## Question

<Callout kind="interview" label="Interview question">
"Explain the MCP authorization model, then tell me what is wrong with this server."
</Callout>

Two remote MCP servers sit behind the company's identity provider: a wiki server and a billing server. A security review finds that an access token a user obtained for the wiki server also works against the billing server, and calls through it return real invoices. Here is the billing server's request path:

```python
IDP_KEYS = load_jwks("https://login.example.com/.well-known/jwks.json")

def authenticate(request):
    token = request.headers.get("Authorization", "").removeprefix("Bearer ")
    claims = verify_jwt(token, IDP_KEYS)   # checks signature and expiry only
    if claims is None:
        raise Unauthorized()
    return claims

async def call_tool(request, name, args):
    claims = authenticate(request)
    if name == "list_invoices":
        return await billing_api.get(
            "/v2/invoices",
            params={"customer": args["customer_id"]},
            headers={"Authorization": request.headers["Authorization"]},
        )
```

Pick the root cause.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Both servers trust the same identity provider. What claim in a token says which server it was issued for?</p></details>
<details class="hint"><summary>Hint 2</summary><p>Look at which credential the billing server uses to call the billing API.</p></details>

## Answer

Two rules from the MCP authorization spec are broken. First, a server must validate that a token was issued for it: the audience. `verify_jwt` checks that the identity provider signed the token and that it has not expired, so any token from that provider passes, including one minted for the wiki server. Second, a server must not pass the client's token through to upstream APIs. Forwarding `Authorization` turns the MCP server into a confused deputy: the billing API sees the user's token and may accept it on its own terms.

The fix: verify the `aud` claim (or the equivalent resource binding) equals this server's own identifier, reject everything else, and call the billing API with the server's own credential, obtained separately and scoped to what the tool needs. On the client side, the spec requires the `resource` parameter (RFC 8707) when requesting tokens, so the identity provider can bind each token to one server in the first place. The tool also lets the caller pick any `customer_id`; authorization should check that the user in `claims` may see that customer.

Why the wrong picks are tempting. Origin validation and binding to 127.0.0.1 are real MCP transport requirements, so they come to mind first, but they defend against browser-based DNS rebinding on local servers, not against a valid token for the wrong service. PKCE is required too, but it protects how the token was obtained, not where it is accepted. The algorithm choice is a red herring: the signature was valid.

## Follow-ups

- *How does the client know which audience to request?* The server publishes Protected Resource Metadata (RFC 9728) naming its identifier and authorization server, and the client sends that identifier as `resource`.
- *What scopes should `list_invoices` need?* A narrow read scope. Use the `scope` value from the server's 401 `WWW-Authenticate` challenge to request more only when a tool needs it.
- *How would you catch this in CI?* A test that presents a token minted for another audience and asserts a 401.

## Common mistakes

- Treating "valid signature" as "valid for me". Signature checks prove who issued the token, not who it was for.
- Forwarding user tokens upstream because it is convenient and keeps per-user permissions.
- Trusting tool arguments such as `customer_id` without checking them against the authenticated user.
