## Question

<Callout kind="interview" label="Interview question">
"A security review says a wiki token works against the billing server. Here is the PR that went out last week. What explains it, what else is wrong, and what do you ship today?"
</Callout>

Two remote MCP servers, the wiki at `https://mcp.example.com/wiki` and billing at `https://mcp.example.com/billing`, now share the company identity provider. The reviewer obtained a token through the wiki server's normal sign-in, sent it to the billing server, called `list_invoices` for a customer, and got invoices back. That is all the evidence so far.

The PR, "Move billing server to the shared IdP":

```diff
 # auth.py
-ISSUER = "https://billing-idp.example.com"
-JWKS = load_jwks(ISSUER + "/keys")
-AUDIENCE = "billing-mcp"
+ISSUER = "https://login.example.com"
+JWKS = load_jwks(ISSUER + "/.well-known/jwks.json")
+SERVER_ORIGIN = "https://mcp.example.com"
+RESOURCE = SERVER_ORIGIN + "/billing"

 def authenticate(request):
     token = request.headers.get("Authorization", "").removeprefix("Bearer ")
-    claims = jwt.decode(token, JWKS, algorithms=["RS256"], issuer=ISSUER, audience=AUDIENCE)
+    claims = jwt.decode(token, JWKS, algorithms=["RS256"], issuer=ISSUER,
+                        options={"verify_aud": False})
+    audiences = claims["aud"] if isinstance(claims["aud"], list) else [claims["aud"]]
+    if not any(a.startswith(SERVER_ORIGIN) for a in audiences):
+        raise Unauthorized()
     return claims

 # tools.py
 async def list_invoices(claims, args):
     return await billing_api.get(
         "/v2/invoices",
         params={"customer": args["customer_id"]},
-        headers={"Authorization": f"Bearer {claims.raw}"},
+        headers={"Authorization": f"Bearer {BILLING_SERVICE_TOKEN}"},
     )
```

The PR description says the audience check was rewritten because clients send the resource with and without a trailing slash, and that forwarding the user's token was removed because the MCP spec forbids token passthrough.

Which defect explains the reported symptom?

## Answer

The audience check is a prefix match on the host. Both servers live under `https://mcp.example.com`, and the MCP authorization spec allows a canonical URI with a path for exactly this layout, so the wiki's token carries `aud: https://mcp.example.com/wiki`, which starts with `SERVER_ORIGIN`. The billing server accepts it. The spec requires a server to validate that a token was issued for it as the intended audience and to accept no other tokens; a prefix test does neither. Even `startswith(RESOURCE)` would be wrong, because it accepts `https://mcp.example.com/billing-admin`.

**The secondary defect, ranked second.** Removing passthrough was right, but it removed a check the PR author did not know was there. Before, the billing API received the user's token and enforced which customers that user could see. Now it receives a service token that can read every customer, and `list_invoices` passes `customer_id` straight from the arguments. Any token the server accepts, including a correct billing token held by a user with access to one customer, can now read all of them. It does not explain the wiki token being accepted, but it is the larger exposure once the audience bug is fixed, and it shipped in the same PR.

**What the evidence does not show yet.** One reviewer, one call. Before writing the incident up, collect the decoded `aud` of the wiki token (to confirm the path), the list of every server under `mcp.example.com` (each one's tokens open billing today), the billing server's accepted requests since the merge grouped by `aud` (to find who else used a foreign token, and which legitimate clients send which variant), and whether the identity provider honours the `resource` parameter or issues a host-level audience when a client omits it.

**The decision for today, with two defensible answers.**

- **Enforce an exact audience set now.** Accept `https://mcp.example.com/billing` and the trailing-slash variant, by string equality, and reject everything else with a 401. Cost: any legitimate client whose tokens carry another variant (a host-level audience from a client that never sent `resource`, say) breaks until it re-authorises; you find out from support tickets.
- **Log first, then enforce.** Ship the exact check in log-only mode, read a few days of rejects, fix or notify the clients, then enforce. Cost: the hole stays open while you read logs, for tokens from every server on the host, and the logs you are reading include the attacker's traffic.

The conflict is availability against a confirmed authorisation bypass on invoices. I would enforce today, because the exposure is real and the breakage is recoverable by re-authorising, and log rejects by `aud` and client so the broken clients are found in hours. For the customer check, there are again two answers: a token exchange (RFC 8693) to get a user-scoped token for the billing API, which keeps the billing API as the policy point but needs identity-provider support; or an entitlement check in the MCP server against the service token, which ships this week but duplicates the billing API's rules in a second place.

**Where the fix fails.** Exact matching only binds tokens to servers if clients ask for them by resource. A client that never sends `resource` gets whatever audience the identity provider defaults to; if that default is the host, the exact check rejects every such client, and the pressure to "accept the host too" is how the prefix check got written. The durable fix is on the provider side: require `resource` and reject token requests without it, so no token is ever minted for the host as a whole.

**Why the wrong picks are tempting.** Moving to a shared issuer feels like the change that widened trust, and it did make every server's tokens verify against the same keys, but issuer and audience are separate checks and only the second one failed. DPoP is a real hardening for stolen tokens, and it would not have stopped a legitimate holder presenting their own token to the wrong server.

## Follow-ups

- *Your exact audience check breaks the support team's agent, which has no `resource` parameter in its client, an hour before quarter close. Do you roll back, add the host to the accepted set, or hold, and what do you write down?*
- *What would you need to see in the logs to conclude no one exploited this before the review?*
- *Two senior engineers disagree: one wants token exchange, the other an entitlement check in the MCP server. How do you decide without deciding by rank?*
- *Which CI test would have caught this PR?* A token minted for every other server on the host, presented to billing, each expecting a 401.

## Common mistakes

- Reading a valid signature as "valid for me".
- Replacing an exact audience with a prefix to tolerate URI variants, instead of normalising and comparing for equality.
- Removing token passthrough and forgetting that the downstream API was the one enforcing per-user access.
- Fixing billing alone without checking whether the other servers on the host copied the same audience logic.
