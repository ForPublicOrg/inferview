## Question

<Callout kind="interview" label="The prompt, paraphrased from a public question bank">
An agent needs 47 model calls for a task that should take 5. How do you debug it?
</Callout>

The task given to a coding agent: "The invoice total is off by one cent for discounted orders. Fix it." A run that goes well searches once, reads the three source files involved, edits one, runs the tests and answers. This run succeeded after 47 model calls. Everything below is synthetic, written for this problem.

```text
harness config
  model_step_cap         60
  parallel_tool_calls    false
  context_editing        clear_tool_uses(trigger=12,000 input tokens, keep=2 tool uses)
  system prompt + tools  about 3,200 tokens
  read_file(path)        returns the whole file

file sizes in tokens
  src/billing.py 4,100   src/discounts.py 2,600   src/money.py 1,900   tests/test_billing.py 3,300

tool calls in the run (46 tool calls + 1 final answer = 47 model calls)
  read_file   29   distinct paths: 4
                   billing.py 9, discounts.py 8, money.py 7, test_billing.py 5
  search       6
  run_tests    7
  edit_file    4

input tokens billed per call, calls 8 to 16
  11,900  11,700  9,100  11,000  11,800  8,900  10,800  11,600  9,000

trace viewer, calls 11 to 14 (each tool result is shown as the tool returned it)
  [11] assistant  Opening money.py for the rounding helper.
                  calls read_file("src/money.py")
  [11] tool       (1,900 tokens of src/money.py)
  [12] assistant  Checking how billing.py applies the helper to discounted lines.
                  calls read_file("src/billing.py")
  [12] tool       (4,100 tokens of src/billing.py)
  [13] assistant  Confirming the discount calculation.
                  calls read_file("src/discounts.py")
  [13] tool       (2,600 tokens of src/discounts.py)
  [14] assistant  Looking at the rounding helper again before editing.
                  calls read_file("src/money.py")
```

You do not have the request bodies the harness sent, only what the trace viewer stored. Pick the defect that explains the repeated reads, rank the other three by what fixing each would save, and say what you would ask for next.

## Answer

The clearing policy is smaller than the agent's working set. The system prompt and the three source files come to 3,200 + 4,100 + 2,600 + 1,900 = 11,800 tokens before a single reply, so the 12,000-token trigger fires as soon as the third file arrives, and `keep=2` replaces every older result with a placeholder. A one-cent rounding bug in discounted lines needs the helper, the caller and the discount code in view together; the agent can only ever see two of them, so it rotates. The sawtooth in billed input tokens (11,800 down to 8,900, 11,600 down to 9,000) is the clearing firing; 29 reads of 4 paths is 25 rereads. The trace viewer hides it because it stores tool results as returned, while the model saw placeholders.

**The ranking of the rest.**

1. *Whole-file reads* rank first among the rest. Ranged reads would shrink the working set to the functions involved instead of three whole files, which keeps it under a sensible trigger. Anthropic's tool-writing guidance recommends range selection, pagination or truncation with sensible defaults for exactly this kind of tool, and notes that redundant calls can point at those parameters.
2. *Serial tool calls* rank second. With parallel calls the first three reads share one turn, which saves calls in each round of reading, but every batched result is cleared the same way.
3. *A larger model* is not a fix. In the calls shown the prompt stays under 12,000 tokens, so nothing is lost to context length; the text was removed by the harness.

**What to ask for next.** The request body of a call that reread a file, to confirm the placeholder, and the `applied_edits` field of each response, which reports `cleared_tool_uses` and `cleared_input_tokens` per call. Without them, the input-token sawtooth plus the file sizes is enough to change the configuration in a test run and count reads again.

**The fix, and the numbers you choose.** Claude's built-in strategy defaults to a 100,000-token trigger and keeping 3 tool uses; this harness set both far lower, presumably to cut input cost. Raise the trigger well above the working set of a typical task (here 11,800 tokens for the prompt and the three files, plus the replies), keep at least as many results as the task needs open at once, set `clear_at_least` so each clearing removes enough to be worth the cache miss it causes, and add `start_line` and `end_line` to `read_file`. A note-taking tool lets cleared facts survive as a short summary.

**The conflict, and how the fix fails.** Clearing exists to bound input cost and context rot; a higher trigger pays more input tokens on every call of long sessions. Clearing also invalidates the cached prefix every time it fires, and here it fires on most calls, so the current policy may not even be saving money: measure tokens and cost per resolved task before and after, not per call. The tempting shortcut, `exclude_tools=["read_file"]`, keeps every read forever. It fixes this run and introduces a quieter failure: after `edit_file`, the pre-edit contents of `billing.py` stay in the prompt next to the new ones, and the agent can reason from the stale copy.

## Follow-ups

- *Which metric finds this without reading traces?* Reads per distinct path per run, and the share of calls with a non-empty `applied_edits`; both are cheap to emit and alert on.
- *Your trigger change raises median input tokens per call. Finance asks you to revert it. What do you show them?*
- *What would make you turn clearing off for this agent entirely?* Runs whose working set is most of the task and whose sessions stay short enough that the full history fits with headroom.

## Common mistakes

- Reading the trace viewer as the prompt; it shows what tools returned, not what the model received.
- Switching to a larger model for a problem that is text the harness deleted.
- Lowering the step cap, which turns a slow success into a failure.
- Telling the agent in its prompt not to reread files; it rereads because it needs the contents.
- Excluding the read tool from clearing without handling stale reads after edits.
