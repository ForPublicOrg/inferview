## Question

<Callout kind="interview" label="Design, 45 minutes">
"Design the persistence for a refund agent that pauses for human approval and resumes days later. No refund is ever paid twice."
</Callout>

The agent reads the order, checks the refund against policy with a model call, and pays through the company's payments service. Refunds over $200 need a human to approve them in an internal tool, and approvers sometimes take two days. Workers are redeployed several times a day.

Operating constraints, a scenario given by the interviewer:

- Three engineers, six weeks to production.
- The payments service cannot be changed this quarter. It wraps Stripe API v1 refunds, passes an `Idempotency-Key` header and a metadata map through, and exposes `list_refunds(order_id)`, which returns each refund with its metadata.
- Finance needs, for every refund, who approved which amount and when, kept for seven years.
- Up to 2,000 refund requests a day, about 15 percent of them over $200.

Write the state, the pause, the resume, the payout and the failure handling. End with a decision memo on where the payout runs, a rollout plan with rollback triggers, and what you give up.

## Answer

<Depth>
<Fragment slot="short">
<p>The run is a graph whose state a Postgres checkpointer saves at every step, keyed by a thread id equal to the refund request id. An approval node pauses with <code>interrupt()</code> and does nothing before it. The approval tool resumes the thread with <code>Command(resume=decision)</code> only after it wins a compare-and-set on the approval row. The payout is its own node: it re-reads the order, calls the payments service with an idempotency key derived from the request id, and before any retry it reconciles against <code>list_refunds</code>, because Stripe v1 may forget a key once it is 24 hours old and a failed attempt can sit longer than that before anyone retries it. Runs use sync durability; audit rows are written by the application, not read out of checkpoints.</p>
</Fragment>
<Fragment slot="long">
<p><strong>State and keys.</strong> State holds the order id, an order snapshot, the policy verdict and its reasons, the requested amount, the approval decision and approver, and a schema version. The thread id is the refund request id, so a retried request finds the same run. The checkpointer is Postgres; an in-memory saver loses every checkpoint on the next redeploy.</p>
<p><strong>The pause.</strong> The approval node returns early for amounts at or under $200. Otherwise it calls <code>interrupt()</code> with the order, the amount and the policy reasons, and nothing else: the node restarts from its first line on resume, so a notification sent before the interrupt is sent again on every resume. The same node also writes no approval row; the row is written by the code that observes the paused run, keyed by thread id, so a re-run cannot create a second one. One interrupt per node, never conditional, because resume values are matched by position.</p>
<p><strong>The resume.</strong> The approval tool runs <code>UPDATE approvals SET status = 'approved', approver = $1, amount = $2 WHERE thread_id = $3 AND status = 'pending'</code> and resumes the thread only if one row changed. Two approvers clicking at once produce one resume, which is the property the Agents SDK docs ask for: no concurrent or replayed submission resumes the same snapshot twice.</p>
<p><strong>The payout.</strong> A separate node after approval. It re-reads the order first, because the snapshot is two days old and a chargeback or a manual refund may have happened since. It calls the payments service with <code>Idempotency-Key</code> of <code>refund:</code> followed by the request id. The key does not include the amount: if an approver changes the amount after a failed attempt, Stripe sees the same key with different parameters and returns an error, which goes to a human instead of becoming a second refund. Before any retry of the payout node, it calls <code>list_refunds(order_id)</code> and treats an existing refund carrying this request id in its metadata as success.</p>
<p><strong>Durability and versions.</strong> Sync durability: each checkpoint is written before the next step starts. The schema version in state lets a run paused under version 3 be migrated or routed to version 3 code on resume; a deploy that changes state shape migrates paused threads before it ships.</p>
<p><strong>Audit.</strong> The application writes an append-only audit row at the approval compare-and-set and after the payout, with the provider's refund id. Checkpoints are an execution record that the platform will prune; the seven-year record cannot depend on them.</p>

### Why approval is not exactly-once

Durable execution is at-least-once per step. A checkpoint records a step's result after the step finishes, so a crash after the payments service accepted the refund and before the checkpoint was written re-runs the payout node. The OpenAI Agents SDK docs say it directly: approval permits a tool call to execute and does not guarantee exactly-once execution. LangGraph's replay documentation says the same about re-executing API calls after a checkpoint. The idempotency key is what turns the re-run into one refund.

### The numbers you choose

**Checkpoint load.** A linear graph of load order, check policy, approval, payout and notify writes a checkpoint for the empty start, the input and each of the five nodes: seven per run, by the docs' count of four for START, A, B, END. At 2,000 requests a day that is 14,000 writes, about 0.16 a second on average. Sync durability costs nothing that matters at this volume; the model call dominates each run's latency. The durability decision is easy here, and it would deserve a measurement at a hundred times the volume.

**The key window against the wait.** Stripe v1 may prune a key once it is at least 24 hours old, and a reused key after pruning is a new request. The approval wait does not matter by itself, because the key is first used when the payout runs, after approval. What matters is the gap between the first payout attempt and a retry. A first attempt that times out on Friday evening, with the run marked failed and retried by an operator on Monday, falls outside the window, and the key no longer protects it. Reconciling before every retry closes that gap. Reconciling only when a retry comes more than 12 hours after the first attempt is a reasonable cheaper rule if the rate limit forces it, provided the attempt time is written before the call; when that write was lost in the same crash, the attempt time is unknown and the retry reconciles.

**The approval deadline.** I pick 5 days, after which a sweeper resumes the thread with a reject decision and the customer is told the request expired. Reasonable choices run from 3 to 10 days depending on approver staffing; unreasonable is no deadline, which leaves paused threads pinned to old graph versions indefinitely and lets the order snapshot drift for weeks.

**Approval volume.** 15 percent of 2,000 is 300 paused runs a day; at a two-day wait, about 600 are paused at any moment. That is the number of threads a state-shape migration must handle.

### Where the payout runs: two defensible answers

| | Payout as a node in the graph | Graph ends at "proposed"; a plain worker pays from the approved row |
|---|---|---|
| What it buys | One run, one history; post-approval steps (the customer message drafted from the approver's note) stay in the same state | The money path has no model, no interrupt semantics and no paused graph versions; it is ordinary outbox code |
| What it costs | Paused threads pin graph code for days while workers redeploy several times a day; every state change needs a migration plan | Two systems to run and monitor; a second graph run for anything model-driven after approval; the agent's state and the payout state can disagree |

**Decision memo.** Keep the payout in the graph for launch, because the customer message after approval needs the model and the approver's note, and one execution history is easier for three engineers to debug in six weeks. Guard it with the idempotency key, reconciliation before retries, the compare-and-set resume and versioned state. Revisit after the first two state-shape migrations: if either needs a manual fix to paused threads, move the payout to the worker.

**What you give up.** Some latency and a provider read on retries; freedom to change state shape without a migration while runs are paused; and the ability to let an approver edit an amount after a failed payout attempt without a human resolving the key conflict.

**Rollout and rollback triggers.** Weeks 1 to 3: the graph runs in shadow, proposing refunds that people pay by hand, and every proposal is compared with what the person did. Weeks 4 to 6: automatic payouts at or under $200, then the approval path for one support team. A nightly job counts provider refunds per request id. Any count above one moves every payout back to manual until the cause is known. A resume error rate above 1 percent after a deploy rolls the deploy back. Paused threads past the deadline that the sweeper did not close page the on-call.

**The failure mode of this design.** Reconciliation reads `list_refunds`, which sees refunds made through the provider. A refund the support team issues by bank transfer, outside the provider, is invisible to it, and the agent pays again. The re-read of the order in the payout node only helps if the order system records those refunds, so the design depends on one place that records every refund regardless of channel; if that does not exist, the launch plan has to say so and keep large refunds manual.

## Follow-ups

- *Why not poll a database flag in a loop instead of interrupting?* A waiting worker holds a slot for two days and still loses its place on the next redeploy; the checkpoint and interrupt free the worker and survive restarts.
- *Two senior engineers disagree about keeping the payout in the graph. How do you decide without deciding by rank?* Agree in advance on the evidence that settles it: the count of manual fixes to paused threads after migrations, and the count of duplicate-refund alarms, over the first month.
- *Finance wants the approver to be able to change the amount at any time. What changes in your key and your reconciliation?* An edited amount is a new payment intent with its own key, recorded with the approver; reconciliation sums refunds per order and refuses a payout that would exceed the captured amount.
- *Your sweeper rejects expired approvals. An approver approves one second after the sweeper's reject.* The compare-and-set makes one of them win; the loser sees a stale-status error in the tool, and the audit row records both attempts.

## Common mistakes

- An in-memory checkpointer in a system that redeploys several times a day.
- Notifications or row writes before `interrupt()` in the same node, which repeat on every resume.
- A random idempotency key per attempt, or one that includes the amount, which makes an edited amount look like a new refund.
- Trusting the idempotency key across a gap longer than the provider keeps keys.
- Paying from a two-day-old order snapshot without re-reading the order.
- Treating checkpoint history as the seven-year audit record.
