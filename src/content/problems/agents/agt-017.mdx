## Question

<Callout kind="interview" label="Concept, 20 minutes">
Your team runs a multi-agent system for internal engineering tasks: an orchestrator, a researcher, a coder, a tester and a verifier, with a billing assistant built on handoffs elsewhere in the company. Last week 212 of its runs failed. You read six failed traces before a planning meeting. For each excerpt, give the MAST failure mode, say whether the failure needs more than one agent to happen, and name the evidence that would change your label. Then say which fix you would fund first, and how you would label enough traces to defend that choice.
</Callout>

The excerpts, constructed for this problem:

```text
T1  researcher notes file:   "Payments API v1 is sunset on 2026-03-31; v2 required."
    researcher -> orchestrator: "v1 supports refunds, partial captures and webhooks."
    writer final report:     "Recommend integrating Payments API v1."

T2  planner -> coder: "Implement the spec. Ask if anything is unclear."
    coder -> planner: "Keep the old /v1/orders endpoint?"   planner: "Follow the spec."
    coder -> planner: "The spec does not mention /v1/orders. Keep it?"   planner: "Follow the spec."
    ... 9 exchanges ...   harness: max_turns=20 reached

T3  tester role prompt: "Write tests under tests/. Do not modify src/."
    tester: edit src/pricing.py (rounding changed)   tester: "All 14 new tests pass."

T4  coder -> verifier: "Done, all tests pass."
    verifier: runs `python -m py_compile` on the changed files -> OK -> "Approved."
    CI, 20 minutes later: 3 failing tests in test_pricing.py

T5  triage -> billing handoff, input_filter=remove_all_tools
    billing -> user: "Could you give me your order number?"
    (the order number was in triage's lookup_order tool result)

T6  orchestrator reasoning: "Wait for the security worker's result before merging."
    orchestrator: tool_call merge_pull_request(1184)
    security worker, 40 s later: "Found a hard-coded token in config.py."
```

## Answer

<Depth>
<Fragment slot="short">
<p>T1 is information withholding (FM-2.4), T2 step repetition with no termination rule (FM-1.3, FM-1.5), T3 disobeying a role specification (FM-1.2), T4 incorrect verification (FM-3.3), T5 loss of conversation history at the handoff (FM-1.4), T6 a reasoning-action mismatch (FM-2.6). T1, T3 and T5 need more than one agent, and T2 in this form; T4 and T6 happen to a single agent too, and their fixes are the single-agent ones. I would fund the verifier fix first, because it catches failures from every class before a user sees them, and then label at least 100 failed traces with the first upstream failure to see whether the multi-agent classes are large enough to justify the boundary fixes.</p>
</Fragment>
<Fragment slot="long">
<p><strong>T1, FM-2.4.</strong> The researcher knew about the sunset and did not pass it on. The label depends on the boundary: if the sunset had been in the researcher's message and the writer dropped it, the label is FM-2.5, ignored other agent's input, and the fix moves from the researcher's output contract to the writer's prompt. Needs two agents by definition. Fix: a return schema with a required field for blocking facts, or the researcher writes its notes to a store and returns a reference, which Anthropic's research system does so that outputs do not pass through a chain of summaries.</p>
<p><strong>T2, FM-1.3 and FM-1.5.</strong> Two agents ping-pong because neither has the authority to decide. The model is not confused; the design never said who decides questions the spec does not answer. The harness cap stopped it at 20 turns, which bounded the cost but produced no answer. Needs two agents in this form. Fix: decision rights in the role specs (the planner answers or escalates to a person), and a stop rule that returns the open question rather than exhausting the turn budget.</p>
<p><strong>T3, FM-1.2.</strong> The tester changed production code to make its own tests pass. A single agent has no role boundary to cross, so the class needs roles. The fix is not a stronger prompt: give the tester write access to <code>tests/</code> only, enforced by the harness.</p>
<p><strong>T4, FM-3.3.</strong> A verifier ran a compile check and approved, the kind of final-stage, low-level check the MAST paper calls inadequate. A single agent that checks its own work the same way fails identically. Fix: the verifier runs the tests itself and never accepts the coder's report as evidence.</p>
<p><strong>T5, FM-1.4.</strong> The handoff filter removed tool items, and the order number lived only in a tool result. The class exists because of the handoff. Fix: pass the fields the next agent needs in a structured handoff payload rather than relying on what survives the filter.</p>
<p><strong>T6, FM-2.6.</strong> The orchestrator said it would wait and then acted. The second agent makes the failure expensive but is not its cause; one agent can reason one way and act another. Fix: make the merge tool refuse until the security check has a recorded result, so the order is enforced by code.</p>
</Fragment>

### What to fund first, and the label budget

Two answers are defensible.

- *Fix verification first.* A verifier that runs tests and checks citations or claims against sources catches T4 directly and, at the join, the downstream effects of T1, T3 and T6 before they ship. The cost: one more model call or test run on every task, and it does nothing for T2's wasted turns or T5's repeated question.
- *Fix the boundaries first.* Output contracts, decision rights, harness-enforced role permissions and structured handoff payloads remove T1, T2, T3 and T5 at the source. The cost: four changes across four agents, each needing its own eval, before anyone knows which class is largest.

Six traces cannot rank these. The quantity you choose is the number of traces to label: MAST's authors started from 150 traces before building the taxonomy and report an inter-annotator kappa of 0.88 for it. With one engineer-day, labelling 100 of the 212 failures with one first upstream failure each, against written rules for the six modes seen so far, is a defensible budget; label until new traces stop adding modes, and record how many you read before the last new one appeared.

I would ship the verifier change this week, since it is one change and it protects users while the labelling runs, and fund boundary fixes in the order the counts give.

**Where this fails.** A verifier at the join can only check what reaches it. In T1 the report recommending v1 is internally consistent and well cited; a verifier that checks claims against the documents the writer used passes it, because the sunset notice never reached the writer. The verifier lowers the visible failure rate while the withholding class grows, so the labelling has to read the worker notes and the handoff payloads, not only the final outputs.

## Follow-ups

- *The 212 failures are the runs that users flagged. What can you say about rates from them, and what can you not?* They show which modes exist and how they rank among flagged runs; a rate for production needs a random sample of all runs.
- *Your verifier costs as much per task as the coder does. Finance asks you to cut it to a sample of tasks. Which tasks keep it, and what do you accept in writing?*
- *What would you need to see in the labelled counts to drop the verifier-first plan?* Boundary classes such as FM-2.4 and FM-1.2 dominating the first upstream labels, with the verifier already catching few of them.

## Common mistakes

- Listing failures a single agent has (hallucination, injection) as multi-agent failures.
- Labelling T1 without looking at what crossed the boundary, so FM-2.4 and FM-2.5 are confused and the fix lands on the wrong agent.
- Fixing T3 with a firmer prompt instead of the tester's write permissions.
- Treating the turn cap in T2 as the fix.
- Ranking fixes from six traces.
