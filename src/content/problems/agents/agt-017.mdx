## Question

<Callout kind="interview" label="Interview question">
"What failure modes show up only once you have more than one agent? How would you find them in traces?"
</Callout>

Name the failure classes, give a concrete example of each, and say what you would change in the design or the harness to prevent it.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Think about what crosses the boundary between two agents, and what does not.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Who checks the combined result, and when does the system decide it is finished?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>MAST groups them into three classes: system design issues (vague role or task specs, ignoring termination conditions), inter-agent misalignment (withholding information, ignoring another agent's input, drifting off task, conflicting implicit decisions), and task verification (stopping early, checking incompletely or not at all). The fixes are explicit contracts at handoffs, shared context where decisions matter, a verifier at the join, and a harness-owned stop condition.</p>
</Fragment>
<Fragment slot="long">
<p>Design issues. A worker gets a brief that underspecifies the task, or a role prompt that conflicts with another agent's, or the system has no clear termination rule, so agents keep handing work back and forth. Fix: structured handoff payloads (goal, constraints, decisions made so far, expected output schema) and a stop condition the harness enforces.</p>
<p>Misalignment between agents. A researcher finds a key fact and the writer never sees it; two coders make incompatible choices because each saw only its own brief, which is Cognition's argument that actions carry implicit decisions. Fix: share the full trace or a decision log for coupled work, and keep coupled work in one agent.</p>
<p>Verification. The orchestrator accepts sub-agent outputs without checking them, or declares success when every worker says "done". Fix: a verifier at the join that runs real checks (tests, schema validation, citation checks), and success defined by those checks.</p>
<p>Finding them. MAST's authors built the taxonomy from annotated traces and reached a kappa of 0.88 between annotators, so it works as a labelling scheme. Tag failed traces by class, count, and fix the biggest class first.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Which class is cheapest to fix?</em> Usually verification: a check at the join catches failures from both other classes before a user sees them.</li>
<li><em>How do you test coordination?</em> Seed tasks where information found by one agent is essential to another, and assert it reaches the final output.</li>
<li><em>When would you merge two agents back into one?</em> When most failures are misalignment between them, and the combined context still fits.</li>
</ul>
</Fragment>
</Depth>

A strong answer ties each class to something you can observe. Design issues show up as agents asking each other clarifying questions in circles or as runs that never terminate. Misalignment shows up as a final output that contradicts something an earlier agent found, or parts that do not fit together, as in Cognition's example of sub-agents building mismatched pieces of a Flappy Bird clone. Verification failures show up as confident final answers with failing tests or unsupported claims.

It also helps to say what multi-agent costs before it fails. Anthropic's research system used about 15 times the tokens of chat. That is fine when parallel exploration is the point, and wasteful when the work is sequential and coupled.

## Follow-ups

- *How would you design a supervisor for code review?* Workers review separate files and return findings in a fixed schema; the supervisor deduplicates and ranks; a verifier runs tests or reproduces each finding before it is reported.
- *What goes in a handoff payload?* The goal, constraints, decisions already made, what has been tried, and the output schema expected back.
- *How do you evaluate the system?* End-to-end task success over repeated trials, plus per-class failure counts from tagged traces.

## Common mistakes

- Listing generic LLM failures (hallucination, prompt injection) that a single agent has too.
- Proposing more agents (a "critic agent") without saying what it checks or with what tool.
- Ignoring termination: who decides the system is done, and on what evidence.
