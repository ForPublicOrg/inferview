## Question

<Callout kind="interview" label="The round, as a public interview guide lists it">
"This agent loops forever on some inputs. Find out why and fix it." In this version you have 25 minutes, the loop's code, the last change to it, and one recorded trace.
</Callout>

A support agent has three tools: `search_orders(customer_id)`, `get_order(order_id)` and `issue_refund(order_id, amount)`. Since a change merged on Monday, some refund conversations end with `RuntimeError("max steps")`; other conversation types look normal. You have no logs from the refund service and no traces from before the merge. This is Monday's change:

```diff
-async def run(messages, tools, max_steps=10):
+async def run(messages, tools, max_steps=20):
     for step in range(max_steps):
-        resp = await llm(messages, tools=tools, model="support-v3")
+        resp = await llm(messages, tools=tools, model="support-v4")
         if resp.tool_calls is None:
             return resp.text
         for call in resp.tool_calls:
             try:
                 result = await tools[call.name](**call.args)
-            except RetryableError as e:
+            except Exception as e:
                 result = {"error": str(e)}
             messages.append(tool_result(call.id, result))
     raise RuntimeError("max steps")
```

Each step re-sends the context, so if a step adds about 60 tokens, call *k* re-sends about 60 × *k*, and *n* calls bill about 30 × *n* × (*n* + 1) tokens: 180 for two calls, 12,600 for twenty. Doubling `max_steps` roughly quadruples what a stuck run bills.

Pick the cause of the loop, then rank the other three by how much each would matter after the cause is fixed, and say what you would collect before shipping a fix and what you would ship without it.

## Answer

The cause is the broadened `except`. `issue_refund` rejects the amount with a permanent validation error (`refund rejected (code 422)`), and the new clause turns it into an ordinary tool result with nothing that marks it as final and nothing that says why. The model reads an error it cannot interpret as a reason to retry, and from step 7 the trace is the identical call `issue_refund(order_id="A-1042", amount=49.0)` with the identical rejection until the step limit. The transient-500 injection shows the same clause behaving well when retrying is the right move, which is why the clause looked safe in review.

**Why the others are tempting, and how they rank.**

1. *The missing final turn* matters most once the loop is fixed. Any run that does hit the limit, for any reason, still ends on an error page. The Claude Agent SDK makes the same point from the other side: `max_turns` needs one extra turn for the text-only answer, or the run ends with `error_max_turns` and no response. The OpenAI Agents SDK lets an `error_handlers` entry keyed `max_turns` return a fallback output instead of raising `MaxTurnsExceeded`.
2. *The model switch* is real and secondary. The search result showed `"refunded": 36.50`, so the right amount was $12.50, and the model asked for $49. That started the failure, but with an error that said "refundable balance is 12.50", a model can correct itself; with an opaque 422 it cannot. Compare `support-v3` and `support-v4` on refund conversations before blaming either.
3. *The higher cap* doubles the steps and roughly quadruples the tokens a stuck run bills, so it raises the cost of the bug without causing it.

**What to collect, and what to ship without it.** The refund service's response bodies for the rejected calls (is the reason always the balance?), the count of distinct (tool, arguments) pairs per failing run across all of them, not just run 8831, and whether any non-refund tool shows repeated identical calls since Monday. Without any of that, the repeat guard and the error contract below are safe to ship today, because they change nothing for runs that do not repeat themselves. The model rollback waits for the comparison.

**The fix, at the error contract rather than the prompt.**

```diff
 async def run(messages, tools, max_steps=20, max_repeat=2):
+    seen = Counter()
     for step in range(max_steps):
-        resp = await llm(messages, tools=tools, model="support-v4")
+        last = step == max_steps - 1
+        resp = await llm(messages, tools=tools, model="support-v4", tool_choice="none" if last else "auto")
         if resp.tool_calls is None:
             return resp.text
         for call in resp.tool_calls:
+            key = (call.name, json.dumps(call.args, sort_keys=True))
+            seen[key] += 1
+            if seen[key] > max_repeat:
+                return await final_answer(messages, f"{call.name} could not complete")
             try:
                 result = await tools[call.name](**call.args)
-            except Exception as e:
-                result = {"error": str(e)}
+            except RetryableError as e:
+                result = {"error": str(e), "retryable": True}
+            except ToolError as e:
+                result = {"error": e.user_message, "retryable": False}
+            except Exception:
+                log.exception("tool %s crashed", call.name)
+                return await final_answer(messages, "internal error")
-            messages.append(tool_result(call.id, result))
+            messages.append(tool_result(call.id, result, is_error="error" in result))
-    raise RuntimeError("max steps")
```

`issue_refund` raises `ToolError` with a message that names the refundable balance, which is the change that lets the model repair the amount. `final_answer` makes one tool-less call so the user gets a sentence, not a stack trace.

**The quantity you choose.** `max_repeat` is a trade between stuck runs and honest retries: at 2, a tool that needs a third attempt after two transient timeouts is cut off. Either set it per tool or move transient retries into the tool wrapper, so the model only sees errors the wrapper has given up on.

**How this fix fails.** The repeat key is exact. A model that varies the amount on every attempt (49.0, 48.99, 45.0) never trips it, and with a clearer error it now has a reason to try amounts. The step limit still bounds that, but a refund tool that accepts any amount below the balance will accept a wrong one. The refund amount needs a check outside the model, for example that it equals the balance the tool itself reports.

## Follow-ups

- *How do you catch the next one before a user reports it?* Emit the count of identical (tool, arguments) calls per run and alert on its tail, not its mean; the median run here looks healthy.
- *`issue_refund` times out after the payment provider accepted the refund. What does your retry do now?* It refunds twice unless the call carries an idempotency key derived from the conversation and order, and the tool returns the earlier result for a repeated key.
- *Product wants the agent to keep trying different amounts because it "usually gets there". What do you accept in writing?*

## Common mistakes

- Reverting the `except` to `RetryableError`, which brings back the crash on the first permanent error.
- Raising `max_steps`, which makes each stuck run more expensive and changes nothing about why it is stuck.
- Fixing the prompt ("never retry a refund") instead of the error contract, so the next tool with an opaque permanent error loops the same way.
- Blaming the model switch because it is the most visible line in the diff.
- Reading only the last steps of the trace; the wrong amount is chosen at step 7 from a search result returned at step 4.
