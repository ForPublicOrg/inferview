## Question

<Callout kind="interview" label="The round, as a public interview guide describes it">
You are handed a running agent and a trace: "This agent loops forever on some inputs. Find out why and fix it." In this version you have 25 minutes, you may read any code, and you talk through what you see.
</Callout>

A support agent has three tools: `search_orders(customer_id)`, `get_order(order_id)` and `issue_refund(order_id, amount)`. The loop is the usual one: send messages, execute any tool call the model returns, append the result, repeat until the model returns plain text or `max_steps` is hit.

```python
async def run(messages, tools, max_steps=20):
    for step in range(max_steps):
        resp = await llm(messages, tools=tools)
        if resp.tool_calls is None:
            return resp.text
        for call in resp.tool_calls:
            try:
                result = await tools[call.name](**call.args)
            except Exception as e:
                result = {"error": str(e)}
            messages.append(tool_result(call.id, result))
    raise RuntimeError("max steps")
```

## Answer

The refund tool rejects the amount with a permanent validation error. The loop catches every exception the same way, appends the error as a tool result, and the model reads "error" as "retry". Nothing distinguishes a retryable failure from a terminal one, and nothing caps repeated identical calls.

Why the wrong picks are tempting. Results appended as user messages also loop, but on `search_orders`, with the model saying it got nothing back. A 20-step cap with no per-tool budget is a real weakness, but it is the backstop that eventually fired, not the cause; a long legitimate task would show different calls, not one call repeated. A prompt-induced verify cycle would put a `get_order` between refunds, and the recorded trace has none.

The final `except Exception` stays: a hallucinated tool name raises `KeyError` and bad arguments raise `TypeError`, and neither should escape the loop or go back to the model.

## Follow-ups

- *How would you catch this in production before a user reports it?* Emit the count of identical (tool, args) calls per run as a metric and alert on its tail, not its mean.
- *The refund tool is not idempotent. What changes?* A retry after a timeout can refund twice. Pass an idempotency key derived from the conversation and order, and make the tool return the earlier result for a repeated key.
- *How do the agent frameworks express the step budget?* The OpenAI Agents SDK takes `max_turns` and raises `MaxTurnsExceeded`; LangGraph raises `GraphRecursionError` past its `recursion_limit`, whose default the docs and the source code disagree on, so set it explicitly; the Claude Agent SDK takes `max_turns` and a `max_budget_usd` cap. None of them tells a permanent tool error from a transient one for you.

## Common mistakes

- Raising `max_steps`. It makes the loop more expensive and changes nothing about why it loops.
- Removing the `try/except` entirely. A hallucinated tool name then crashes the request instead of ending it cleanly.
- Fixing the prompt ("never retry a refund") instead of the error contract. The next tool with an opaque permanent error loops the same way.
- Reading only the last step of the trace. The cause is visible in the search result at step 4, long before the loop starts.
