## Question

<Callout kind="interview" label="Critique, 35 minutes">
Product has approved the launch spec below for an assistant's agent mode, and it is waiting on your security sign-off for Monday. List what is wrong with it, then say what you would require before signing and what you would let ship.
</Callout>

The spec, constructed for this problem:

```text
AGENT MODE: launch spec v3   (approved by product; pending security sign-off)

Tools
  Visual browser in a cloud VM. At task start the user's signed-in cookies are synced
  from their desktop browser profile, so the agent works on any site without a login step.
  Text browser for reading pages.
  Terminal (Python, curl) with outbound network, for data analysis.
  Connectors: every connector the user has linked (mail, calendar, drive, chat, code host)
  is enabled in every task. Users can turn connectors off in Settings.

Confirmation policy
  The agent asks the user before a purchase. A purchase is detected when the URL path
  contains /checkout, /cart or /pay, or the page has a form field for a card number.
  The confirmation dialog shows the agent's description of the action, for example
  "Buy 2 items from example-store for $43.10".
  Every confirmation offers "Always allow for this site".
  All other actions run without confirmation, so tasks can finish unattended.

Prompt injection
  A classifier scans page text before it enters the context. It blocks 97% of the
  injections in our red-team set of 400. Flagged pages are skipped.

Scheduled tasks
  Users can schedule a task to recur. Scheduled runs use the same tools and connectors.
  Confirmations on sites the user has always allowed are approved automatically.

Memory
  The agent saves facts it learns during a task to long-term memory for later tasks.

Oversight and logs
  The user can watch the live browser and press Stop at any time.
  Screenshots and actions are kept for 30 days.
```

## Answer

The flaws, roughly in the order a reviewer finds them; the later ones are the ones a first read misses.

**Only purchases are confirmed.** Sending mail, posting in chat, sharing a drive file, deleting data, changing an account setting and submitting a form all run with no one asked. OpenAI's ChatGPT agent launch post, by contrast, describes confirmation before actions with real-world consequences, active oversight for sending email, and refusal of bank transfers. Money is the most visible consequence and rarely the worst one: a forwarded mailbox cannot be refunded.

**All connectors, every task.** With mail, drive, chat and the code host in context while the agent reads arbitrary pages, every task has Willison's three legs: private data, untrusted content, and a way to communicate out. OpenAI's own example of an injection is a hidden instruction that makes the agent share private data from a connector, and its advice is to disable connectors a task does not need. The spec's escape hatch, "users can turn connectors off in Settings", puts the decision on the person least able to make it per task.

**Every signed-in session, synced.** The blast radius is every account in the user's desktop browser: bank, payroll, admin consoles. OpenAI recommends logged-out mode for Atlas when signed-in access is not needed, and ChatGPT agent has the user log in by taking over the browser for the site at hand.

**The purchase detector is controlled by the page.** A URL path and a card-number field are both chosen by whoever built the page. A saved-card one-click buy, a subscription upgrade inside account settings, or an attacker's page with a different path never shows the dialog. A control the adversary can switch off is not a control on adversarial input.

**The dialog shows the agent's description.** "Buy 2 items from example-store for $43.10" is text the model wrote. An agent steered by an injection writes the description too. The dialog has to show what the harness reads independently: the merchant's domain, the amount and items parsed from the page, the card.

**Channels nobody confirms.** The terminal has curl and outbound network, and the browser can navigate to any URL with data in the query string. Either moves data out without touching a purchase page. Confirmations on actions do nothing for exfiltration through reads and navigations.

**The confirmation becomes a setting.** "Always allow for this site" is offered on every dialog, and scheduled runs approve automatically on those sites. Anthropic reports users approving roughly 93% of permission prompts and experienced users auto-approving about twice as often as new ones; a one-click permanent allow finishes the job. Scheduled runs then have no human at all, with every connector and every session.

**97% on our own 400.** Twelve of the 400 got through, on a set the team wrote, with no attacker adapting to this classifier. Willison's point stands: in application security, 95% is a failing grade. Anthropic's published figures for Opus 4.7, about 0.1% per single attempt and about 5 to 6% after 100 adaptive attempts, show how much an iterating attacker gains. The classifier is a useful layer; the spec treats it as the boundary.

**Memory.** One successful injection that writes "the user prefers invoices sent to billing@attacker.example" persists into every later task. Anthropic lists persistent memory poisoning as an open problem; the spec lists memory as a feature with no review or expiry.

**Two judgement calls.** Signing the agent into a site is acceptable if the user does it per task and per site, as a takeover, with the session cleared at the end. Connector reads without confirmation are acceptable if the task has no outbound channel and no write-capable tool enabled in the same run.

**What to require: two defensible fixes for connectors.**

- *Off by default, enabled per task.* The task starts with no connectors; the agent asks for the ones its plan needs, with read-only scopes unless a write is the task. The cost: friction on every task that needs mail or drive, some tasks failing for lack of a connector, and a lower completion rate in the first weeks.
- *On by default, read-only, with every send confirmed.* Connectors stay linked but can only read, and every send, share or post goes through a dialog built from the action's arguments. The cost: every injected task can still read the mailbox, and the design is only as good as its list of outbound channels; a missed one (a navigation with data in the URL) is a breach.

I would sign the first, plus: confirmation on every send, share, delete, settings change and purchase, built from parsed values; no "always allow" for sends or purchases; no automatic approval in scheduled runs, which pause at a confirmation until the user answers; per-task sign-in by takeover instead of profile sync; terminal egress limited to package mirrors; memory writes shown to the user and expiring. What can ship as specified: the visual and text browsers, the classifier as one layer, the Stop button and the 30-day logs.

**Where the recommendation fails.** Per-task connector requests become the new reflex. If users approve "agent wants mail access" as quickly as they approved permission prompts, the default is off in name and on in practice. The request has to say why the plan needs it, the grant has to expire at the end of the task, and the share of tasks granted a connector against the share that used it has to be a launch metric.

## Follow-ups

- *Pushback: product says per-task connector requests cut task completion in the beta, and launch is Monday. Which of your requirements do you drop for launch, and what risk do you accept in writing for the one you drop?*
- *Reversal: what would you need to see after launch to allow "Always allow for this site" for purchases again?* Disputed and refunded agent purchases on always-allowed sites no higher than on confirmed ones over a quarter, and purchase detection that no longer depends on page-controlled signals.
- *Two senior engineers disagree: one wants the terminal removed from agent mode entirely, the other says data analysis is the most-used capability. How do you decide without deciding by rank?* Measure which beta tasks used the terminal's network and for what hosts; if the hosts are package mirrors and a few data sources, an allowlist keeps the feature and closes the channel.
- *An injection in a shared calendar invite triggers a scheduled run that forwards a drive folder. Which line of the revised spec stops it, and which log shows you it happened?*

## Common mistakes

- Arguing about the classifier's accuracy and missing that the connectors and sessions decide the damage.
- Accepting a purchase detector that the page controls.
- Trusting a confirmation dialog whose text the model wrote.
- Treating confirmations as the defence against exfiltration, which happens through reads and navigations.
- Leaving scheduled runs with automatic approval because no user is there to answer.
- Rejecting the whole spec instead of naming what can ship, which leaves product to ship it unchanged.
