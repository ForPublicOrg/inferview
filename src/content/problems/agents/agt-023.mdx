## Question

<Callout kind="interview" label="Design, 50 minutes">
"Design long-term memory for a personal assistant that people keep using for months. It reads their email and browses the web for them."
</Callout>

The assistant has tools to read email, draft replies, read the calendar and browse. Product wants it to remember what is useful so users stop repeating themselves.

Operating constraints, a scenario given by the interviewer:

- Four engineers, ten weeks to launch, users in the EU among them. Privacy counsel requires that an erasure request reach every copy of the user's data without undue delay, and that the product say what it keeps.
- Conversation transcripts live in an existing store with a 90-day retention that cannot change this quarter.
- Security review lists persistent injection through memory, of the SpAIware kind, as a launch blocker.
- The product manager wants everything remembered and injected into every conversation.

Design the memory kinds and their records, the write policy (who writes what, when, from which sources), the read path and its budget, consolidation, forgetting and deletion. End with a decision memo on when memory is written, a risk note, a rollout with rollback triggers, and what you give up.

## Answer

<Depth>
<Fragment slot="short">
<p>Three stores with different write rules. Semantic memory is a small profile of typed fields plus a collection of facts; episodic memory is a record per completed task; procedural memory is standing instructions the user has confirmed. Every entry records its source (a user turn, a tool result or an inference), the source id, who wrote it and when it was last confirmed. Only text the user wrote can create semantic or procedural entries. Email and web content can appear in episodic records as quoted data with a link back, never as instructions. Facts are extracted by a background job after a conversation ends; the hot path writes only on an explicit "remember this". The read budget is 1,500 tokens per session, loaded once at session start after the cached prefix. Deletion follows provenance: deleting a conversation deletes what was learned from it.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Records.</strong> Every entry has <code>user_id</code>, <code>kind</code> (profile field, fact, episode, rule), <code>text</code> or a typed value, <code>source_kind</code> (user_turn, tool_result, inference), <code>source_ids</code>, <code>author</code> (user or model), <code>created_at</code>, <code>confirmed_at</code>, <code>last_read_at</code> and <code>derived_from</code> for consolidated entries. The profile holds a few typed fields that are always loaded (name, time zone, working hours, language). Facts are a collection, because a profile that absorbs everything becomes the error-prone single document the LangChain docs warn about.</p>
<p><strong>Write policy.</strong> A fact or rule needs a <code>user_turn</code> source. A model inference ("prefers morning meetings") is stored as an inference with lower read priority until the user confirms it. A tool result can only produce an episode: "drafted a reply to the landlord's email of 3 March", with the message id, and the email's text quoted, never paraphrased into the assistant's voice. Procedural rules need explicit confirmation in the UI, because CoALA rates writes to procedural memory as the riskiest kind and a poisoned rule changes every later action. Sensitive categories such as health are not extracted unless the user asks, which is also the default OpenAI describes for ChatGPT.</p>
<p><strong>Read path.</strong> At session start: the profile fields, then facts and rules ranked by relevance to the opening message and by confirmation recency, up to the budget. Memory goes after the stable system prompt, as the first block of the conversation, and stays fixed for the session. The prompt cache invalidates a level and everything after it when that level changes, so re-retrieving memory into the system prompt on every turn turns each turn's cached prefix from a read at 0.1 times the input price into a write at 1.25 times. Within a session, the assistant looks up older episodes and email by tool, as data.</p>
<p><strong>Consolidation and forgetting.</strong> A weekly job merges duplicate facts, flags contradictions for the user to resolve, and records <code>derived_from</code> on every merged entry. Episodes expire after 90 days, matching the transcripts they point to. Facts not read or confirmed in 180 days are dropped, following the memory tool docs' advice to delete what has not been accessed in a long time.</p>
<p><strong>Deletion.</strong> ChatGPT's documented behaviour is that deleting a chat does not delete memories created from it. Here the default control is "delete this conversation and what was learned from it": provenance finds every entry whose sources include the conversation, and a merged entry with surviving sources is recomputed from them. Erasure of the account removes the stores, the embeddings, the caches and the eval samples drawn from them, and the privacy notice states how long deletion logs are kept; OpenAI's help centre names up to 30 days for its own.</p>
</Fragment>

### The numbers you choose

**The read budget.** I choose 1,500 tokens per session. At an assumed 25 tokens for a one-sentence fact, which the tokenizer should confirm on dogfood data, that is room for about 60 facts after the profile. If dogfood shows 3 durable facts a day per user, a scenario number that the third hint's count replaces, six months of use produces 3 x 180 = 540 facts, nine times the budget. Injecting everything, as the PM asks, does not scale past the first few weeks; selection and consolidation are required by month two. A budget between 1,000 and 3,000 tokens is reasonable; a budget that grows with the store is not, because the cost and the noise grow with every month a user stays.

**Expiry.** 90 days for episodes, because their sources leave the transcript store then and an episode that points at nothing cannot be checked. 180 days without a read or a confirmation for facts. Shorter is defensible for a product used weekly; longer needs a re-confirmation prompt, or stale facts ("works at" a former employer) outlive their truth.

### When memory is written: two defensible answers

| | Hot path: the agent calls a memory tool mid-conversation | Background: a job extracts after the conversation ends |
|---|---|---|
| What it buys | Immediate use in the same and the next conversation; the user sees each write as it happens | No latency in the conversation; extraction runs with a fixed prompt over user turns only, where it can be reviewed and evaluated |
| What it costs | The agent writes while untrusted email and pages are in its context, the path SpAIware used; extra latency and a tool call per write | Lag: a fact stated this morning is missing from another conversation until the job runs; extraction quality needs its own evals |

**Decision memo.** Background extraction for facts, from user-authored turns only, run when a conversation has been idle for ten minutes. The hot path writes only when the user says to remember something, and every write, from either path, shows in the conversation as a visible "memory updated" line with an undo. Revisit if dogfood shows users repeating the same fact within a day in a measurable share of conversations.

**Risk note.** Residual risks at launch: an injected instruction the user pastes in their own message is user-authored and passes the source rule; inferences can encode sensitive traits the classifier misses; a merged fact can outlive a deleted source when its other sources have expired. Mitigations: procedural rules need confirmation, inferences need confirmation before they rank high, and a merged entry that cannot be recomputed after a deletion is dropped.

**Rollout and rollback triggers.** Weeks 1 to 4: dogfood with memory writes shown and reviewable, red-team prompts that try to plant rules through email and pages. Weeks 5 to 8: 5 percent of users, memory off by default for existing users until they opt in. Weeks 9 to 10: general availability. Writes stop for everyone if any semantic or procedural entry is found with a tool-result source, which the policy makes impossible and a nightly invariant check verifies. An erasure request not completed across every store within the window counsel sets pauses the rollout.

**What you give up.** Facts that appear only in email or pages are not remembered; the assistant looks them up each time, paying a tool call and some latency, and occasionally misses one. Users get a lag before background facts appear. And a smaller, curated memory means the product cannot claim it remembers everything.

**The failure mode of this design.** Provenance is only as good as the boundary between user text and other text. A user who forwards an email into the chat, or pastes a page, turns third-party text into a user turn, and the source rule admits it. The extractor needs a second check for imperative content in user turns ("always send invoices to...") that would become a rule, and such rules go to explicit confirmation like every other procedural entry.

## Follow-ups

- *Two senior engineers disagree: one wants a single profile document per user, the other a collection of facts. How do you decide without deciding by rank?* Run both extractors on the same dogfood month and compare fact recall on a labelled set, the rate of wrong overwrites, and the cost of deleting by source in each.
- *Your eval set for extraction needs real conversations. Where do those samples come from, and what happens to them on an erasure request?*
- *A regulator asks you to show every fact the assistant holds about a user and where each came from. How long does that take with your design, and what is missing?*

## Common mistakes

- Choosing a vector store before deciding who is allowed to write what.
- Letting tool results, email or pages write facts or rules in the assistant's voice.
- Re-retrieving memory into the system prompt on every turn and paying a cache write each time.
- Deleting a conversation and leaving everything learned from it, or deleting merged entries without recomputing from surviving sources.
- An expiry policy for memory and none for the embeddings, caches and eval samples derived from it.
