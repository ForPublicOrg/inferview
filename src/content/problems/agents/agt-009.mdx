## Question

<Callout kind="interview" label="Interview question">
"What are Agent Skills, and how do they differ from MCP tools and from fine-tuning?"
</Callout>

Your platform team supports thirty internal agents. Three requests arrive in the same week:

1. Every agent that touches a release must follow the company's twelve-step release checklist.
2. Changelogs must come out in the house format, which a short Python script can validate.
3. Agents need to read and update the deploy system, which sits behind SSO.

For each, would you build a skill, an MCP server, or a fine-tune? Explain the mechanism, not just the label.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask what each one changes: what the agent knows how to do, what it can reach, or the model's weights.</p></details>
<details class="hint"><summary>Hint 2</summary><p>How much context does a skill cost before the agent decides to use it?</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>A skill is a folder with a SKILL.md (a name, a description of when to use it, and instructions) plus optional scripts and reference files, loaded on demand. An MCP server gives the agent new capabilities across a process boundary, with its own auth. Fine-tuning changes the weights. Checklist and changelog format: skills. Deploy system: an MCP server. Fine-tuning: none of the three.</p>
</Fragment>
<Fragment slot="long">
<p>Skills are procedural knowledge. At startup the agent sees only each skill's name and description, about 100 tokens per skill in the spec's guidance. When a task matches, it reads SKILL.md (the spec recommends under 5,000 tokens and under 500 lines), and opens referenced files or runs bundled scripts only if needed. A script's output enters the context, not its source. Thirty skills cost a few thousand tokens of descriptions, not thirty manuals.</p>
<p>The checklist is a skill: instructions an agent should follow when the task is a release. The changelog format is a skill with a validator script in scripts/, so the agent writes, runs the check, and fixes. Skills need an agent with a filesystem and code execution; on the Claude API that means the code execution tool, with no network access in the container.</p>
<p>The deploy system is an MCP server. It is a remote capability with authentication (OAuth to an MCP server acting as a resource server, tokens scoped to that server), audit logs and rate limits owned by the deploy team. A skill can tell the agent how to use those tools well, so the two compose.</p>
<p>Fine-tuning fits when behaviour must be cheap and consistent at very high volume and the knowledge is stable, or when you need a smaller model to match a larger one on a narrow task. It is slow to change: a new checklist step means a new training run and new evals, where a skill is a file edit.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How do you govern thirty agents' skills?</em> A reviewed repository of skills with owners, versioned like code, because installing a skill is installing software that runs in your agents.</li>
<li><em>What makes a skill trigger reliably?</em> The description: it must say what the skill does and when to use it, in the words a task would use.</li>
<li><em>Why not put the checklist in the system prompt?</em> It would cost tokens in every call of every agent, relevant or not, and thirty such documents crowd each other out.</li>
</ul>
</Fragment>
</Depth>

The useful framing is three different things to change: what the agent knows how to do (skills), what the agent can reach (tools over MCP), and what the model is (fine-tuning). They are not alternatives competing for the same job.

A valid SKILL.md for the changelog case looks like this. The name must be lowercase letters, digits and single hyphens, at most 64 characters, and must match the folder name; the description can be up to 1,024 characters.

```markdown
---
name: changelog-format
description: Writes and validates changelog entries in the house format. Use when preparing a release, editing CHANGELOG.md, or when asked for release notes.
---
# Changelog format

1. Group entries under Added, Changed, Fixed, Removed.
2. Run `python scripts/check_changelog.py CHANGELOG.md` and fix every error it prints.
```

On the Claude API a skill name also cannot contain the reserved words `anthropic` or `claude`, and custom skills do not sync between claude.ai, the API and Claude Code, so a fleet needs one source of truth that deploys to each surface.

## Follow-ups

- *How do skills and MCP compose?* A skill can contain the instructions for using a set of MCP tools well, and the MCP project has a working group on serving skills over MCP.
- *What is the security risk of skills?* Scripts run with the agent's permissions. A malicious or careless skill is a supply-chain problem, so review and pin them.
- *How would you know a skill helped?* Run the same tasks with and without it and compare outcomes and tokens, not just whether it triggered.

## Common mistakes

- Treating skills as "MCP tools in a folder". A skill changes the agent's instructions; it does not add a capability across a process boundary.
- Reaching for fine-tuning to teach a procedure that changes every quarter.
- Writing a description that says what the skill is but not when to use it, so it never triggers.
- Putting every procedure in the system prompt, which pays for all of them on every call.
