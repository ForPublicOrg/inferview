## Question

<Callout kind="interview" label="Interview question">
"Your platform team supports thirty internal agents. Decide where each of these procedures lives: a skill, an MCP server, the system prompt, or the weights. Price each choice in context tokens."
</Callout>

The scenario. The team's procedure library has 25 documents averaging 2,000 tokens each, measured with the provider's token counter. Agents run on the Claude API and in Claude Code. This week's five requests:

1. The twelve-step release checklist, about 2,400 tokens, needed only when an agent is preparing a release.
2. Changelog entries in the house format, which a 60-line Python script can validate.
3. Reading deploy status and starting deploys in the deploy system, which sits behind company SSO.
4. The hotfix procedure, whose last step deploys to production.
5. Labelling about 200,000 support tickets a month into 40 labels that have not changed in a year.

## Answer

<Depth>
<Fragment slot="short">
<p>Release checklist and changelog format: skills, the changelog one with its validator in scripts/. Deploy system: an MCP server, because it is a capability behind SSO with its own owner and audit. Hotfix: a skill the model cannot invoke on its own, with the production deploy still gated by the deploy server's own authorisation. Ticket labels: a prompt on a small model first, and fine-tuning only if an eval says the prompt misses, on a provider that still offers it. Loading the whole library as skills costs about 2,500 tokens per session against 50,000 for putting it in the system prompt.</p>
</Fragment>
<Fragment slot="long">
<p><strong>The arithmetic.</strong> All 25 documents in the system prompt: 25 × 2,000 = 50,000 tokens in every session of every agent, needed or not. As skills: about 100 tokens of name and description each at startup, 25 × 100 = 2,500 tokens, plus the body of whichever skill a session activates; a release session pays 2,500 + 2,400 = 4,900. A script's source never enters context, only its output, so the changelog validator costs a few lines of error text.</p>
<p><strong>When the system prompt wins.</strong> A procedure needed in a share f of sessions costs about 100 + f × 2,000 tokens as a skill and 2,000 always loaded. Always loaded is cheaper only when f is above (2,000 − 100) / 2,000, which is 95%. Below that, the skill wins on tokens, and it also keeps unrelated procedures out of the model's attention. Pick your own threshold below 95% if a missed trigger is expensive: a procedure needed in most sessions, where forgetting it causes an incident, is a reasonable system-prompt line even at a token loss.</p>
<p><strong>Deploy system.</strong> This is reach, not knowledge. It needs credentials the agent should never hold, an owner who audits calls and rate-limits them, and the same interface for thirty agents. That is an MCP server with OAuth, and a skill can sit on top of it to say how to use its tools well.</p>
<p><strong>Hotfix.</strong> A side-effecting procedure should not start because the model matched a description. In Claude Code, <code>disable-model-invocation: true</code> keeps the skill's description out of context and lets only a person start it. That field is a Claude Code extension that other surfaces reject, so on the API the same procedure needs the gate somewhere the model cannot skip: the deploy tool's own approval or scope check.</p>
<p><strong>Ticket labels.</strong> This is the one case that looks like weights: high volume, stable labels, a narrow task. Start with a prompt and examples on a small model and measure per-label accuracy. Fine-tune only if that misses the target, and check availability first: OpenAI closed self-serve fine-tuning to new organisations on 7 May 2026 and stops new jobs for existing customers on 6 January 2027.</p>

### The three things that can change

A skill changes what the agent knows how to do, and costs about 100 tokens until it is used. An MCP server changes what the agent can reach, across a process and credential boundary someone else owns. Fine-tuning changes the model, costs nothing per call in context, and costs a training run and a new eval for every edit. The system prompt is the fourth place, and the only one paid in every session.

### Where the recommendation fails

Progressive disclosure depends on the model choosing to load the right skill. The trigger is the description alone, and Claude Code truncates description plus `when_to_use` at 1,536 characters in the listing, so a skill whose description says what it is but not when to use it never activates and nothing reports the miss. Log activations per skill against the sessions that needed them; a release session with no checklist activation is the signal.

Skills also need a filesystem and code execution. On the Claude API that is the code execution tool's container, with no network access and no package installation at run time, so a validator that calls an internal service works in Claude Code and fails on the API. Custom skills do not sync between claude.ai, the API and Claude Code, so a fleet needs one repository that deploys to each surface.

## Follow-ups

- *The release checklist changes every two weeks. Which of the four homes handles that best, and which worst?*
- *A team asks for its 9,000-token runbook as one skill. What do you split into references/, and why does the spec suggest keeping SKILL.md under 500 lines?*
- *How would you show the skills saved anything?* Run the same tasks with and without them and compare success, tokens and turns per task, not whether the skill triggered.

## Common mistakes

- Treating skills as "MCP tools in a folder". A skill adds instructions and scripts in the agent's own environment; it adds no capability behind someone else's credentials.
- Putting every procedure in the system prompt, which pays 50,000 tokens per session in this scenario.
- Letting a side-effecting skill trigger from its description and relying on the model to stop before the deploy.
- Reaching for fine-tuning to teach a procedure that changes every quarter.
