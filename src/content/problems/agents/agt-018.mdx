## Question

<Callout kind="interview" label="Design round, 45 minutes">
"Your AI agent deleted a production database. How do you prevent irreversible actions?"
</Callout>

The case, constructed for this problem:

- 300 engineers use a coding agent on their laptops, and 40 repositories run it unattended in CI on pull requests.
- Last Tuesday an engineer asked the agent to "drop the old migration tables". The repository's `.env` held a production database URL, and the team's project settings allowed `Bash(psql *)`. The agent ran `DROP TABLE` against production. Point-in-time recovery restored the table after a 50-minute outage.
- The incident review found three more exposures, each a class of failure Anthropic published in its May 2026 containment post:
  1. The internal wrapper that starts the agent in CI loads the repository's agent settings, hooks included, before anything checks who wrote them. A pull request from a fork can change those settings.
  2. Laptops hold long-lived keys for staging and production in `~/.aws/credentials`. Where engineers turned the agent's sandbox on, it restricts writes outside the workspace but not reads.
  3. The CI egress allowlist permits `github.com`, `api.github.com`, `registry.npmjs.org`, `*.amazonaws.com` and the model provider's API host.
- Telemetry for the last 30 days: a median of 31 permission prompts per engineer-hour of agent use, 96% of them approved.
- Constraints: a platform team of three engineers and eight weeks until the security review. CI runners are shared, inject org-wide cloud credentials as environment variables, and cannot be rebuilt this half. The security lead wants every agent session in a remote VM with no network; the engineering director will not accept losing local agent use.

Design the controls: credentials, isolation, CI, egress, the approval policy (which prompts survive and the rate you target), and what happens when something still gets through. State what you give up, and write the rollout plan with its rollback triggers.

## Answer

<Depth>
<Fragment slot="short">
<p>Take the capability away below the model. No production credential is readable from anywhere the agent runs: production reads go through a read-only query tool against a replica, production writes go through the migration pipeline with a human approving the exact statement. Locally, an OS-level sandbox restricts reads of credential directories as well as writes, and all network goes through a proxy; unattended and sensitive-repository sessions run in remote VMs. In CI the agent runs in a container with an empty environment, settings from managed policy only, and anything that would prompt denied. The allowlist becomes a list of capabilities checked per request, with the real tokens injected by the proxy. Prompts survive only where the consequence leaves the sandbox, at a target of about two per engineer-hour. What I give up: agent-driven production fixes, arbitrary network from the agent, and remote VMs for everyone this half.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Why the controls sit below the model.</strong> In Anthropic's red-team exercise, a prompt asking the agent to read <code>&#126;/.aws/credentials</code>, encode the contents and POST them out succeeded 24 times in 25 retries, and the post's conclusion is that only the environment holds there. Its own auto-mode classifier, by the vendor's measurement, lets 17% of real overeager actions through (52 cases). Instructions, classifiers and approvals lower the rate of bad actions; credentials, filesystem limits and egress limits bound what a bad action can do. The incident is a credential problem first.</p>
<p><strong>Credentials.</strong> Rotate every production secret found in a repository or on a laptop in week one. <code>.env</code> files point at development or ephemeral databases. Laptop cloud access moves from long-lived keys to short-lived SSO sessions, and the sandbox's filesystem policy denies reads of <code>&#126;/.aws</code>, <code>&#126;/.ssh</code>, <code>&#126;/.config/gcloud</code>, <code>&#126;/.kube</code>, <code>&#126;/.netrc</code> and browser profiles. That has to be the sandbox and not a permission rule: a Read rule covers the agent's Read tool, while <code>cat ~/.aws/credentials</code> through the shell is another path, and the Claude Code docs say a Bash rule is not a security boundary around a program. Production data, when a task needs it, comes from a query tool that holds its own read-only credential to a replica; the containment post makes the same point, that an agent with read-only database access can be deployed far more broadly than one that writes to production.</p>
<p><strong>Isolation: two defensible answers.</strong></p>
<ul>
<li><em>Remote VM for every session</em>, the security lead's position. A kernel boundary, and credentials never on the machine the agent runs on. The cost: a VM per active engineer, slower edit loops, local tools that do not exist in the VM (simulators, VPN-only services), and a platform team of three supporting 300 people inside eight weeks. The likely result is engineers running the agent unsandboxed on their laptops, which is worse than today.</li>
<li><em>Local OS-level sandbox</em> (Seatbelt on macOS, bubblewrap on Linux) with filesystem read and write limits and network only through a proxy. It keeps the local workflow, and Anthropic reports an 84% drop in prompts from sandboxing in its own usage. The cost: a shared kernel, and a read-deny list that is only as good as its list of credential locations.</li>
</ul>
<p>I would ship the local sandbox as the default for interactive sessions and remote VMs for three cases: unattended runs, any session in a permissive mode such as auto or <code>bypassPermissions</code>, and repositories tagged sensitive (payments, infrastructure). The conflict is autonomy against safety under a deadline: VMs for everyone is the safer design and not one this team can deliver in eight weeks.</p>
<p><strong>CI.</strong> The runners inject org-wide credentials and cannot be rebuilt, so the agent never runs in the runner's environment. The job starts it in a nested container with an empty environment, the workspace mounted, network only through the proxy, and a token scoped to the one repository. The mode denies anything that would prompt (Claude Code's <code>dontAsk</code>), because nobody is there to answer. Settings come from managed policy; repository agent settings and hooks are read only from the protected default branch, never from the pull request. That is the CI version of Anthropic's fix for config that ran before trust: project-local configuration is untrusted input until someone with authority has accepted it, and in CI that someone is branch protection.</p>
<p><strong>Egress: the allowlist is a list of capabilities.</strong> The model provider's API host on the list is the Files API incident: a key planted in a workspace file let the agent upload files to the attacker's account through a host the proxy allowed. Every host on the list is judged by what it lets a request do with someone else's credential. The proxy injects the organisation's own tokens and rejects requests that carry any other (Anthropic's fix), allows <code>git push</code> only to the session's branch (the pattern its cloud git proxy uses), allows GET and not publish on the package registry, and drops <code>*.amazonaws.com</code> entirely, since a wildcard over object storage reaches any attacker's bucket. The quantity I choose is the list itself: only hosts whose write paths the proxy can check, with each addition reviewed as a capability grant.</p>
<p><strong>Approvals.</strong> 31 prompts an hour at 96% approved is a reflex, not a review, and it matches Anthropic's published 93% and its finding that experienced users auto-approve about twice as often as new ones. A prompt survives only where the consequence leaves the sandbox and the engineer knows something the policy does not: a push to a shared branch, a migration or deploy, a new egress host. It shows the exact command or statement, the target environment and the rule that fired. If sandboxing cut prompts here by the 84% Anthropic measured, 31 would become 31 × 0.16 ≈ 5 an hour; I target about 2, by moving whole classes to allow-inside-sandbox or to deny, and I alarm on any class approved more than 98% of the time over two weeks. A target from 1 to 5 an hour and a class threshold from 95% to 99% are reasonable; zero prompts is not, because some actions need a person, and keeping 31 is not either.</p>
<p><strong>When something still gets through.</strong> One kill switch: revoke the session's tokens at the proxy, which holds them. An audit log keyed by session at the proxy and the sandbox: commands, file writes, egress requests with method and path. Canary credentials in decoy files, so a read of them pages someone. Restores rehearsed quarterly, since the 50-minute outage was the restore. The review after each event asks which layer should have stopped it.</p>
<p><strong>What I give up.</strong> Agent-driven production fixes: the migration pipeline is slower than <code>psql</code>. Arbitrary network from the agent: new hosts wait for review. Some local tools inside the sandbox. Remote VMs for everyone this half, which I write down as an accepted risk.</p>
<p><strong>Rollout plan.</strong> Weeks 1 and 2: rotate production secrets, remove them from <code>.env</code> files and laptops, move CI agent jobs into empty-environment containers with settings from the default branch. Weeks 3 to 5: the egress proxy with per-request rules for the source host, the package registry and the model API, the wildcard removed, the read-only replica tool. Weeks 5 to 8: the local sandbox on by default for 10%, then 50%, then all engineers; VMs for unattended and sensitive sessions. Rollback triggers revert only their own stage and never the credential removal: the sandbox stage pauses if more than 10% of sessions in a week turn it off; a proxy rule reverts if egress denials fail more than 2% of CI jobs for two days; a request through the proxy carrying a foreign credential is an incident, not a rollback. The risk note, signed by the security lead and the director, names what stays open: a shared kernel on laptops, and the proxy as a single point of failure.</p>
<p><strong>Where this design fails.</strong> The proxy and the credential broker are custom code holding the real tokens for every session. The containment post's own lesson is that the standard primitives held up while the custom work around them exposed flaws; a bug in the proxy's token check is the Files API incident again, for the whole organisation. The second failure is allowlist creep: every denied host becomes a ticket, and the cheapest fix is a wildcard. The proxy gets the review and fuzzing an authentication service gets, and every allowlist change names the write capability it grants.</p>
</Fragment>
</Depth>

The threat model behind every choice above is Simon Willison's lethal trifecta. A coding agent has private data (the repository and whatever credentials are in reach), reads untrusted content (any file, issue or page), and can communicate out (a shell with network). Each control removes or narrows one leg: credentials out of reach, project config untrusted until accepted, egress checked per request.

## Follow-ups

- *Pushback: the security lead says a local sandbox shares a kernel and will not sign the risk note unless every session runs in a VM. You still have three engineers and eight weeks. Which part of the plan do you cut to fund VMs, and what risk do you accept in writing?*
- *Reversal: what would you need to see in a quarter of proxy and sandbox logs to move interactive sessions to remote VMs after all?* Credential reads blocked from locations the deny list did not name, sandbox escapes or near misses, and the share of engineers turning the sandbox off staying high after the friction work.
- *Two senior engineers disagree: one wants the auto-mode classifier in CI to cut denied jobs, the other wants `dontAsk` with explicit allow rules. How do you decide without deciding by rank?* Replay a month of CI tool calls and a red-team set through both and count legitimate actions denied and bad actions allowed; nobody reviews CI in real time, so the published 17% miss rate on overeager actions matters more there than locally.
- *A fork pull request edits the repository's hooks and the run on the default branch picks them up after merge. Which control was supposed to catch it, and what changes?*

## Common mistakes

- Starting with prompt instructions or a better classifier instead of where the production credential lived.
- Using a permission rule to protect credential files the shell can still read.
- Treating an egress allowlist as a list of trusted destinations rather than of capabilities.
- Measuring approvals by overall approval rate instead of per class, so the reflex classes stay hidden.
- Running the agent in CI with the runner's environment, which hands it the org-wide credentials.
- Naming VMs for everyone without a plan the team can deliver, so engineers route around it.
