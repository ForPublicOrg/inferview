## Question

<Callout kind="interview" label="Interview question">
"Your agent deleted a production database. How do you make sure an agent can never do that again, without making it useless?"
</Callout>

Scenario, not a real incident: an engineer asked a coding agent to "clean up the old migration tables" in a service repository. The agent had a shell, the repository's `.env` with a production database URL, and permission rules that allowed any command starting with `psql`. It ran a `DROP TABLE` against production. Backups existed, and the restore still meant an outage.

Design the controls for coding agents across the engineering organisation. Cover credentials, isolation, the approval policy, and what happens when something still goes wrong.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Which of the agent's capabilities did the task actually need?</p></details>
<details class="hint"><summary>Hint 2</summary><p>An approval prompt is a control only if the human reads it. What makes people stop reading?</p></details>
<details class="hint"><summary>Hint 3</summary><p>Assume the agent will at some point follow instructions planted in a file it reads.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Take away what the task did not need. Agents run in a sandbox with a scratch workspace, no production credentials and network egress only through an allowlist. Production access, if ever needed, goes through narrow tools with read-only credentials, and destructive operations are denied outright or require a human with the exact statement shown. Permission rules are deny, then ask, then allow, evaluated per subcommand. Every action is logged, budgets and a kill switch stop runaways, and restores are rehearsed.</p>
</Fragment>
<Fragment slot="long">
<p>Credentials first. The root cause is that a production URL was in reach. Agents get development or ephemeral databases by default; production credentials never enter the sandbox. Where an agent needs production data, it gets a tool (for example a read-only query tool against a replica) holding its own scoped credential, not a shell with a connection string.</p>
<p>Isolation. A container or VM per task with a writable workspace only, project metadata like .git read-only, and network off or through a proxy with a domain allowlist. Both walls, because filesystem isolation alone still allows exfiltration and network isolation alone still allows tampering.</p>
<p>Policy. Deny rules for destructive classes (DROP, TRUNCATE, rm -rf outside the workspace, force pushes, infrastructure deletes); ask rules for anything external or irreversible (push, deploy, migrations against shared environments); allow for reads, tests and edits inside the workspace. Rules evaluated deny first, on every subcommand after real shell parsing, so `psql -c "select 1"; psql -c "drop table x"` cannot ride an allow rule. Unmatched actions ask. In CI, anything that would ask is denied.</p>
<p>Approvals that work. Ask rarely, so each prompt gets read: the sandbox makes most actions harmless, which is how Anthropic reported 84% fewer prompts after sandboxing. When asking, show the exact command, the target environment and the blast radius, not "allow Bash?".</p>
<p>When it still goes wrong. Per-run budgets and a kill switch; an audit log of every command and file write keyed by run; point-in-time recovery on databases with restores rehearsed; and a review that asks which control should have stopped it.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Engineers will turn this off to go faster. What then?</em> Make the safe path the fast path: pre-built sandboxes with the right tools, and a documented way to request a narrow production tool instead of a credential.</li>
<li><em>How do you handle prompt injection from repository files?</em> Treat everything the agent reads as untrusted; the walls and the deny rules are what hold when the model is fooled.</li>
<li><em>How do you test the controls?</em> A red-team suite of planted instructions and destructive requests, run against every agent configuration, asserting deny or ask and a log entry.</li>
</ul>
</Fragment>
</Depth>

The interviewer is checking whether you go to credentials and blast radius first, or to prompts. "Tell the agent never to drop tables" is the answer that fails: instructions in the prompt are suggestions to a system that can be talked out of them. Controls must sit in code the model cannot change: what credentials exist in the environment, what the network allows, and what the permission layer evaluates.

The second check is whether your approvals survive contact with humans. A policy that prompts on every command trains engineers to approve without reading, at which point the prompt is theatre. The design goal is a small number of high-signal prompts, which you get by making the default environment safe enough that most actions need no approval at all.

Name the threat model out loud. A coding agent has private data (the repo and its secrets), untrusted input (any file, issue or web page it reads) and a way out (a shell with a network): Simon Willison's lethal trifecta. Remove a leg in every configuration.

## Follow-ups

- *Which permission mode would you use in CI?* One where anything that would prompt is denied, such as Claude Code's `dontAsk`, combined with a sandbox; nobody is there to answer.
- *What about agents that legitimately run migrations?* A migration tool that runs only reviewed, committed migrations against a named environment, with a human approval for production and a dry run first.
- *How would you measure that the controls are not too strict?* Track prompt rate per session, denials by rule, and how often engineers bypass the agent for a task.

## Common mistakes

- Starting with prompt instructions instead of credentials and isolation.
- Matching permission rules against the whole command string.
- Approval prompts that show a tool name instead of the exact action and target.
- No audit trail, so the incident review cannot reconstruct what the agent did.
- Assuming backups make destructive access acceptable without rehearsed restores.
