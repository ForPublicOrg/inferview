        # Final-only resolution, plus flags under which a stricter policy may refuse.
        pending = raw.split("/")[::-1]
        stack, hops = [], 0
        climbed = escaped = entered = False
        while pending:
            seg = pending.pop()
            if seg in ("", "."):
                continue
            if seg == "..":
                if stack:
                    stack.pop()
                else:
                    climbed = True
            else:
                key = "/" + "/".join(stack + [seg])

  solution: |
    from urllib.parse import unquote

    ROOT = "/memories"
    MAX_HOPS = 40   # the per-lookup symlink limit Linux uses; any limit of 8 or more passes


    def _trie(links):
        root = {}
        for key, target in links.items():
            node = root
            for seg in key.split("/"):
                if seg:
                    node = node.setdefault(seg, {})
            node[None] = target   # None never collides with a segment name
        return root


    def safe_memory_path(raw, links=None):
        """Resolve raw the way the store will (decode once, follow links, then . and ..)
        and return it if it is /memories or below; raise PermissionError otherwise.
        Policy: only the final path is checked, as realpath does, and .. at / stays at /."""
        path = unquote(raw)
        if chr(92) in path or chr(0) in path:
            raise PermissionError("backslash or NUL in path")
        trie = _trie(links or {})
        pending = path.split("/")[::-1]   # segments still to walk; the next one is last
        stack, nodes = [], [trie]          # resolved segments, and the trie node of each prefix
        hops = 0
        while pending:
            seg = pending.pop()
            if seg in ("", "."):
                continue
            if seg == "..":
                if stack:
                    stack.pop()
                    nodes.pop()
                continue
            node = nodes[-1].get(seg) if nodes[-1] is not None else None
            if node is not None and None in node:
                hops += 1
                if hops > MAX_HOPS:
                    raise PermissionError("too many links")
                target = node[None]
                if target.startswith("/"):
                    stack, nodes = [], [trie]
                pending.extend(target.split("/")[::-1])
                continue
            stack.append(seg)
            nodes.append(node)
        if not stack or stack[0] != "memories":
            raise PermissionError(f"outside {ROOT}: {raw[:80]!r}")
        return "/" + "/".join(stack)

## Question

<Callout kind="interview" label="Interview question">
"Your agent has a file-based memory tool, the model chooses the paths, and the store has links in it. Write the guard."
</Callout>

Claude's memory tool (`memory_20250818`) is client-side: the model sends `view`, `create`, `str_replace`, `insert`, `delete` and `rename` with paths under `/memories`, and your handler maps that prefix onto storage you control. The paths are untrusted input, because the model may be following text injected into a page or a file it read.

In this scenario the store is a per-user directory, and a migration tool has left symbolic links in it that map old folder names to new ones. For the exercise the links arrive as a dict from an absolute logical path to its target.

Write `safe_memory_path(raw, links=None)`. It returns the path the store would actually open, when that path is `/memories` or below, and raises `PermissionError` otherwise.

1. Decode percent-encoding exactly once.
2. Refuse any path containing a backslash or a NUL character.
3. Treat a relative path as starting from `/`.
4. Resolve the way the kernel does: walk the segments left to right; a segment that names a link is replaced by the link's target (an absolute target restarts from `/`, a relative one continues from the link's directory); a `..` after a link applies to where the link led; `/..` is `/`.
5. Accept `/memories` and anything below it; refuse everything else, including `/memoriesX`.

Two decisions are yours, and the docstring should state them: how many links one lookup may follow (a chain of eight must resolve and a cycle must be refused), and whether a walk that leaves `/memories` and comes back is accepted, as `realpath` would, or refused, as `openat2` with `RESOLVE_BENEATH` would.

One constraint the tests enforce: the path is as long as the attacker wants. A path of a million characters must be answered, either way, in under three seconds, and so must a deep path against a store with tens of thousands of links.

## Answer

The reference decodes once, refuses the two characters, then walks with two stacks: `pending` holds segments still to visit, with the next one on top, and `stack` holds the resolved path. A normal segment moves from one to the other. `..` pops `stack`, and at `/` it does nothing, which is what the kernel does. A segment that names a link is not pushed: its target's segments go onto `pending`, after clearing `stack` if the target is absolute. That ordering is what makes `/memories/l/../x.md` land in `/memories/a/x.md` when `l` points at `a/b`. Normalizing the string first with `posixpath.normpath` would give `/memories/x.md`, a path the store never opens. The check then passes or fails on the wrong file.

The link lookup is where the time goes. Building the prefix string at each segment to look it up in `links` costs time proportional to the depth, so a path 500,000 segments deep does about 500,000 x 250,000 = 1.25 x 10^11 segment copies. Scanning every link key at each segment costs 500,000 x 20,000 = 10^10 comparisons with 20,000 links. `ROOT in PurePosixPath(p).parents` has the same quadratic shape, because it builds every ancestor. The reference builds a trie from the link keys once and keeps a trie node for every entry on `stack`, so each segment is one dict lookup, each `..` is one pop, and the whole walk is linear in the segments visited plus the link targets expanded.

Each expansion counts as a hop. The reference stops at 40, the number Linux follows for a whole pathname according to `path_resolution(7)`; the tests accept any limit of eight or more. A visited set would also stop cycles, but a hop limit bounds the work for a long acyclic chain too.

The second decision is the policy for a walk that leaves the root. The reference checks only the final path, which is `realpath` semantics: it keeps absolute links such as `/memories/old` pointing at `/memories/new` working, and it refuses anything that ends outside. The strict policy refuses the moment the walk is outside `/memories`, and refuses absolute links, as `RESOLVE_BENEATH` does. It costs those absolute migration links, which the tool would have to rewrite as relative ones, and it matches what a real filesystem lookup does, where a final-only check has already let the walk read directories outside the root before it decides. Both pass the hidden tests. They compare your function against a reference resolver on random paths and random link graphs: when you return a path it must be the realpath-style result, have no empty, `.` or `..` segments, and resolve to itself; when you refuse, the path must end outside the root, leave it during the walk, climb above `/`, or need more than eight links. A length cap is also a legitimate choice, and the cheapest defence against the long-path case; the timing tests accept a refusal.

The failure mode of this function is that it checks a model of the store, not the store. Between the check and the open, anything that can write in the memory directory can replace a directory with a link, and the open follows it. In production the check has to be the open: hold a directory descriptor for the user's memory root and open every path relative to it with `openat2` and `RESOLVE_IN_ROOT` or `RESOLVE_BENEATH` (Linux 5.6 or later), which fails with `EXDEV` on an escape and with `EAGAIN` when the kernel could not rule out a `..` race, in which case retry. Keep this function as the first filter, because it gives the model a readable refusal before any I/O.

## Follow-ups

- *What changes to run this against a real filesystem instead of a dict of links?* Open relative to a descriptor for the user's root with `openat2` and `RESOLVE_IN_ROOT`, retry on `EAGAIN`, and stop resolving the path in Python at all, because the check and the open are then one system call.
- *The store moves to Postgres, keyed by path, with no links. Which half of this function survives?* Decoding, the character checks and the lexical walk, plus a tenant prefix in every key. The links and the hop limit go away; the length cap stays.
- *Which commands need which checks?* `rename` has two paths and both go through the guard, and the docs say to refuse `delete` and `rename` of `/memories` itself, which the guard accepts as a valid path, so the handler needs a rule per command on top of it.
- *Security asks you to refuse every path that contains a link, which breaks the migration tool's links. What do you trade?* Refusing links (`RESOLVE_NO_SYMLINKS`) is simpler to reason about and costs a one-time rewrite of the migrated folders; keeping them costs the resolver above and a test suite for it.

## Common mistakes

- Normalizing the string before following links, so the function approves a different file from the one the store opens.
- Checking `raw.startswith("/memories")`, which accepts both `/memories/../../etc/passwd` and `/memoriesX`.
- Decoding twice, or validating the decoded string and passing the raw one to the store.
- Rebuilding the prefix string or scanning every link at each segment, which is quadratic in an input the attacker sizes.
- Calling `os.path.realpath` on the model's string before validating it, which touches the real filesystem with an attacker-chosen path and still leaves the gap between check and open.
