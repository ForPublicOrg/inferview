## Answer

MCP and function calling solve different problems. Function calling is a model API feature: you describe tools in the request, the model returns a structured call, and your code runs it. MCP is a protocol between the host application and tool providers: a host runs one client per server, and servers expose tools, resources and prompts over JSON-RPC 2.0, via stdio or Streamable HTTP. The host converts the MCP tools it discovers into function definitions for the model. So the second statement is the accurate one.

Why the others are tempting. "MCP replaces function calling" is the most common confusion, because demos show a model "using MCP" without showing the host in between. The handshake and server-initiated elicitation statements were correct until the 2025-11-25 revision, and most tutorials still describe them; the 2026-07-28 revision removed sessions so that any server instance can answer any request. The annotations statement mistakes a UI hint for a security control: a malicious server can label a destructive tool read-only.

## Follow-ups

- *Why did MCP go stateless?* So remote servers can scale horizontally behind an ordinary load balancer without shared session storage.
- *When is plain function calling enough?* A single application with a few tools it owns, in its own process.
- *What does MCP cost you?* Tool definitions from every connected server sit in the context on every call, and a server you do not control can change its tool list and break your prompt cache.

## Common mistakes

- Describing MCP as a model capability rather than a protocol the host speaks.
- Teaching the `initialize` handshake and session IDs as the current design.
- Trusting tool annotations from third-party servers to decide what runs without approval.
