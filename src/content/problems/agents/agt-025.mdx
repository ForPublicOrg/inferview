## Question

<Callout kind="interview" label="Concept, 25 minutes">
"Your agent runs a three-hour task and the context fills long before it finishes. How do you keep the goal without keeping everything, and what would you test before you trust it?"
</Callout>

The task, a scenario: migrate 40 tables to a new schema. For each table the agent reads the schema, writes a migration script, runs it on a copy, and compares row counts and checksums. Query results and logs are large. Two rules were agreed with the user at the start: never drop a column whose name starts with `legacy_`, and stop and ask before any table over 50 million rows. By table 12 the input passes 150,000 tokens, the agent re-checks tables it already verified, and on table 14 it proposes dropping `legacy_region`.

You have server-side compaction with a custom prompt, tool-result clearing, a file the agent and harness can read and write, and sub-agents. Say what goes where, choose the thresholds, and say what you would test.

## Hints

<details class="hint"><summary>Hint 1</summary><p>Ask where the two agreed rules physically live in the context at turn 300, and what would have to happen for them to be summarized away.</p></details>
<details class="hint"><summary>Hint 2</summary><p>Request a token breakdown of the context at table 12 by source: instructions, the agent's own turns, and tool results.</p></details>
<details class="hint"><summary>Hint 3</summary><p>Ask what the prompt cache hit rate is on this run, and what it becomes after the first clearing.</p></details>

## Answer

<Depth>
<Fragment slot="short">
<p>Sort the state by how it must survive. The goal, the two rules and the acceptance criteria are pinned outside the conversation, in the system prompt or a file the harness re-injects after every compaction, so no summary can drop them. Progress is a structured file, one row per table with its status and the verification evidence, written by the harness after a check passes. Bulky tool results are cleared first, because they are the bulk of the tokens and the safest thing to drop. Per-table work can go to a sub-agent that returns a short summary. Compaction comes last, with a prompt tuned for recall, and the run is tested by forcing compactions at random points and measuring rework and rule violations.</p>
</Fragment>
<Fragment slot="long">
<p><strong>Pinned.</strong> The rules belong in the system prompt, and the harness enforces them as well: a guard on the SQL tool refuses <code>DROP COLUMN legacy_</code> and any statement on a table over the row limit without an approval. A rule that exists only as an early user message is one compaction away from a paraphrase, and the proposed drop on table 14 is what that paraphrase looks like.</p>
<p><strong>Progress outside the window.</strong> A <code>progress.json</code> row per table: status, script path, row counts, checksum, verified time. The harness writes the row after its own check passes, not when the model says it is done. After a compaction, the next turn starts by reading the file. This is the structured note-taking pattern; Anthropic's long-running harness work says compaction alone isn't sufficient for exactly this reason.</p>
<p><strong>Clearing before compaction.</strong> Tool results from finished tables are the bulk of the context and are not needed again: the file holds their outcome. Clear them with a <code>clear_at_least</code> large enough that the cache rewrite pays for itself (computed below), keep the last few tool uses, and exclude the tool that reads <code>progress.json</code>.</p>
<p><strong>Sub-agents per table.</strong> A sub-agent with a clean context does one table and returns a summary of a thousand or two thousand tokens, which keeps the lead agent's context growing by a summary per table instead of by every query result.</p>
<p><strong>Compaction last.</strong> With a custom prompt that lists what must survive (open tables, decisions made with the user, errors not yet resolved, files touched) and points at <code>progress.json</code> instead of restating it. A custom prompt replaces the default, so it owns recall: tune it for recall first and precision second, as Anthropic advises.</p>

### The quantity to choose: how much to clear at once

Clearing old tool results changes the conversation at the first cleared point, so everything after it that was a cache read becomes a cache write on the next request. Let C be the tokens that remain after the first cleared result, R the tokens cleared, and T the turns left before the next clearing. With 5-minute cache writes at 1.25 times the base input price and reads at 0.1 times:

- One-time extra cost of the rewrite: (1.25 - 0.1) x C = 1.15 C base-price tokens.
- Saving per later turn: R tokens no longer read from cache, 0.1 R. Over T turns, 0.1 R T.
- Clearing pays for itself on cost alone when 0.1 R T is at least 1.15 C, that is R x T at least 11.5 C.

With 100,000 tokens in context and 60,000 of them cleared, C is at most 40,000, so R x T must reach 460,000: 60,000 x T at least 460,000 gives T at least 7.7 turns. With only 5,000 tokens cleared, C is about 95,000 and T must reach 1.09 million / 5,000, about 219 turns. On Claude Opus 5.5 and Sonnet 5.5, where reads cost 0.05 times, the condition becomes R x T at least 24 C and the 60,000-token clearing pays back after 16 turns.

So `clear_at_least` should be a large share of what is clearable, tens of thousands of tokens on this workload, not a few thousand. A clearing that takes small bites every few turns pays the rewrite repeatedly and saves almost nothing. The cost argument is the floor; the reason to clear at all is that recall from a long context degrades, which is what the re-checking at table 12 looks like.

### What to test before trusting it

Replay recorded runs of the task against copies of the database, forcing compaction and clearing at random points, several per run. Measure three things per run: rework (tool calls on a table whose row in `progress.json` is verified), rule violations (attempts the SQL guard refused, which should be zero and are counted even though they were blocked), and false completion (a claim that all tables are done when the file disagrees). Compare compaction prompts on the same recorded runs rather than on fresh ones, so the difference is the prompt and not the run.

The failure mode of this design is the file itself. If the model can write `progress.json`, it can mark a table verified that the harness never checked, and every later session trusts it; the row has to be written by the harness after its own comparison. And a pinned block that grows with every new agreement becomes the next context problem: keep it to rules and criteria, and move anything else into the file.

## Follow-ups

- *Why not just use a model with a larger context window?* It moves the threshold, not the problem: recall still degrades as the context grows, and the cost of every turn grows with it.
- *The guard refuses the drop, and the agent keeps retrying with rephrased SQL. What do you change?*
- *Which of these techniques breaks prompt caching, and which preserves it?* Clearing and compaction both rewrite the prefix from the point they change; sub-agents and the file do not touch the lead agent's prefix.

## Common mistakes

- Treating compaction as the whole answer and leaving the rules and the progress in the conversation.
- Asking the summary for a length instead of a list of what must survive.
- Letting the model write the record of what is verified.
- Clearing a few thousand tokens at a time and paying a cache rewrite for each.
- Testing with fresh runs, so a change in the run is read as a change in the technique.
