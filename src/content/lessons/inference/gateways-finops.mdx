## The invoice nobody could explain

Scenario, not a real company: the monthly model bill doubles. Six teams call three providers with keys copied into their own services. Finance asks which feature caused it. Nobody can answer, because the only record is the provider's invoice, which knows API keys and models but not features or customers. Someone also notices that prompt caching was turned on months ago "to save money", and nobody checked whether it hits.

This lesson is about the layer that would have answered finance's question in five minutes: a **model gateway**. If you have run an API gateway or a service mesh, you know most of it already. It authenticates callers, applies quotas, routes to backends, retries and fails over, caches, and logs. The difference is the unit. HTTP gateways count requests; a model gateway has to count **tokens**, because a request can cost a tenth of a cent or several dollars depending on its size and the model it reaches.

## What a gateway does

Requests from every internal service go through one endpoint. In order, the gateway:

1. Authenticates the caller and attaches **attribution tags**: team, feature, customer, environment.
2. Checks **budgets and rate limits** in tokens, reserving the worst case before the call.
3. **Routes**: picks a model and provider by policy, cost, latency or health, with fallbacks.
4. Optionally answers from a **response cache**, and shapes the prompt so the provider's **prompt cache** hits.
5. Calls the provider, streams the result back, and records usage: input, cached input, output, latency, cost.
6. Settles the budget with the real token counts.

Open-source and hosted options exist for each piece. LiteLLM's proxy offers per-key, user, team and customer budgets and a router with several strategies. Portkey's gateway offers fallbacks, load balancing, conditional routing, retries, timeouts and caching. OpenRouter is a hosted router across many providers. The design questions are the same whichever you pick.

Three things in that table matter more than any single price. Output costs five or six times input across these rows, so an answer that rambles costs more than a long prompt. Cached input is 5% to 10% of base input, but only if the cache hits, and writing it costs extra (below). Haiku 5.5 is also priced by prompt length: a request whose prompt is over 100,000 tokens pays $0.50 input, $0.05 cached and $2.50 output, five times the short-prompt rates. Gemini also charges $4.50 per million cached tokens per hour of storage on the Pro model. And the Gemini page already lists a price for the same Flash model from 2027-01-01 at double the current rate, so a cost model without dates is a cost model that silently goes stale.

Price per token is also not comparable across vendors, because tokenizers differ. Anthropic's pricing page states that Claude 4.7 and later use a tokenizer that "produces approximately 30% more tokens for the same text". Compare cost per completed task on your own traffic, not list price per million.

**Batch APIs** are the easiest discount on the page. OpenAI, Anthropic and Gemini all price batch work at half the standard rate. OpenAI's guide says each batch completes within 24 hours and accepts up to 50,000 requests and 200 MB per input file. Anything that does not have a user waiting, such as nightly evals, backfills, document enrichment or classification of yesterday's tickets, belongs there.

## Prompt caching: a write premium you have to earn back

Provider prompt caching reuses the provider's KV cache for a repeated prefix, the same mechanism as the previous lesson's prefix caching, sold back to you as a discount. The catch is the write. On Anthropic a 5-minute cache write costs 1.25 times base input and a 1-hour write costs 2 times. On OpenAI's GPT-5.6 and later, a 30-minute write costs 1.25 times and a 12-hour write 2.5 times; the 12-hour option is Responses API only. Reads cost 0.1 times on most Claude models, 0.05 times on Opus 5.5 and Sonnet 5.5, and 0.05 times on gpt-6.1-sol.

If every miss writes the cache, the prefix costs `hit_rate x read + (1 - hit_rate) x write` relative to not caching. Setting that equal to 1 gives the break-even hit rate: `(write - 1) / (write - read)`.

A worked month makes it concrete. Take Claude Haiku 5.5 at its prompts-up-to-100k prices (input $0.10, 5-minute write $0.125, hit $0.01, output $0.50), one million requests, each with a 6,000-token shared prefix, 500 fresh input tokens and 300 output tokens. Without caching: 6,500 x $0.10 + 300 x $0.50 = $800 per million requests. With caching at a 0% hit rate every request pays the write: 6,000 x 0.125 + 500 x 0.10 + 150 = $950. At 50% it is $605, and at 90% it is $329. Caching that never hits is a 19% price increase.

Hit rate depends on prompt layout more than on anything else. Both providers cache exact prefixes. Anthropic builds the prefix in the order tools, system, messages, and a change at one level invalidates that level and everything after it. A timestamp in the system prompt, tool definitions in a different order, or per-user text before the shared document all turn hits into writes. Both providers also have a minimum: OpenAI's guide gives 1,024 tokens for GPT-5.6 and later, and Anthropic's minimum varies by model, with shorter prompts processed without caching "and no error is returned". That silence is why the scenario team never noticed. Log cached-input tokens per request and alert on the hit rate.

## Routing and fallbacks

Routing decides which model and which provider serve a request. Three patterns cover most designs.

**Rules and classifiers** send a request by feature, tenant tier or a cheap classifier's guess at difficulty. **Cascades** try a small model and escalate when a checker rejects the answer. If the small model costs 0.10 of the large one and the checker 0.02, a cascade costs 0.12 + escalation_rate, so it saves money while fewer than 88% of requests escalate, and escalated requests pay the latency of both calls. FrugalGPT showed large savings on its benchmarks with this pattern; your escalation rate is something you measure, not assume. **Provider routing** picks among hosts of the same model: OpenRouter by default prefers providers without recent outages and weights them by the inverse square of price, so a $1 provider is about 9 times as likely to be tried first as a $3 one.

Fallbacks need the same care as in any distributed system. LiteLLM's router puts a deployment in cooldown after `allowed_fails` failures (default 3 per minute) for `cooldown_time` (default 5 seconds). Retries should be limited and jittered, and a fallback to a different model changes the output, so it needs the same evaluation as any model change.

## Budgets, rate limits and attribution

A request-count rate limit is wrong for models: one request can be a hundred times bigger than another. Limit tokens per minute per tenant with a token bucket, and because output length is unknown up front, **reserve** the worst case (prompt tokens plus `max_tokens`) before the call and **settle** with the real count afterwards.

```python
class TenantBudget:
    def __init__(self, tokens_per_minute, clock):
        self.rate, self.capacity = tokens_per_minute / 60.0, tokens_per_minute
        self.level, self.clock, self.last = float(tokens_per_minute), clock, clock()

    def _refill(self):
        now = self.clock()
        self.level = min(self.capacity, self.level + (now - self.last) * self.rate)
        self.last = now

    def try_reserve(self, prompt_tokens, max_tokens):
        self._refill()
        need = prompt_tokens + max_tokens
        if need > self.level:
            return None                     # caller returns 429 with Retry-After
        self.level -= need
        return need

    def settle(self, reserved, prompt_tokens, output_tokens):
        refund = reserved - (prompt_tokens + output_tokens)
        self.level = min(self.capacity, self.level + refund)
```

Spend budgets work the same way in dollars over a longer window. Know how your gateway fails: LiteLLM's docs say budgets need a Postgres database and that the global `max_budget` "fails open" without one. A budget that silently stops enforcing during an outage is not a budget.

**Attribution** is a logging discipline. Every call carries team, feature and customer tags, and the gateway records input, cached input and output tokens with the price in effect that day. Then cost per resolved ticket, per document processed or per active user is a query, and the doubling in the scenario is a five-minute investigation: group by feature, compare weeks.

## Napkin math for self-hosting

Self-hosting turns a per-token price into a fixed hourly cost. The comparison needs three inputs that only you have: the quoted price per GPU-hour, the throughput you measured at your latency objective, and your utilisation. The arithmetic: monthly fixed cost = GPUs x price per GPU-hour x hours, and the break-even volume is that cost divided by the API cost per request. The interview follow-ups are where the real answer lives: peak versus average traffic (you pay for peak capacity), engineering and on-call time, the quality gap between the open model and the API model, and how much prompt caching and batch pricing already lower the API side. ## When this is wrong

The caching break-even assumes every miss writes the cache. Providers route by prefix hash, so a miss on one machine may coincide with a warm copy elsewhere, and real behaviour can be better or worse than the formula. Measure cached-token counts in the usage records rather than trusting the model.

List prices are a ceiling for many buyers. Committed-use contracts, regional processing uplifts (OpenAI lists 10% for some newer models, Anthropic 1.1 times for US-only inference on Claude 4.6 and later), speed tiers and long-context surcharges all move the real number. Use the provider's billing export, not the pricing page, for anything finance will see.

A gateway is also a new single point of failure and a new hop of latency. Run it like any other critical proxy: replicated, with health checks, and with a tested path for what callers do when it is down.
