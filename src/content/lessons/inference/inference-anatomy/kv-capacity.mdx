## Capacity is cached tokens, not requests

A replica's concurrency limit is a token count: the memory left after weights and runtime overhead, divided by KV bytes per token. Requests only enter when you divide that token count by how many tokens a request holds while it is resident, and that divisor is where most sizing errors come from. This lesson computes bytes per token from published configs, turns memory into a token budget, and then sizes a deployment from a traffic mix.

## Bytes per token from the config

For standard attention, every layer caches one key and one value vector per KV head for every token:

`bytes per token = 2 × layers × kv_heads × head_dim × bytes_per_element`

The DeepSeek-V2 paper tabulates the element counts by attention type: 2·n_h·d_h·l for multi-head, 2·n_g·d_h·l for grouped-query with n_g KV groups, 2·d_h·l for multi-query, and (d_c + d_h^R)·l for multi-head latent attention, which caches one compressed latent of width d_c plus one positional key of width d_h^R per layer. Read each term from `config.json`, because three of the models below break a naive reading of it.

**Qwen3-32B** sets `head_dim: 128` explicitly. Dividing `hidden_size` 5120 by 64 heads would suggest 80, and a calculator that derives head_dim gets 2 × 64 × 8 × 80 × 2 = 163,840 bytes instead of 262,144, under-sizing the cache by 37.5%.

**gpt-oss-120b** has 36 layers that alternate sliding-window attention with a 128-token window and full attention, 8 KV heads and head_dim 64. Counting every layer as full gives 2 × 36 × 8 × 64 × 2 = 73,728 bytes per token. Only the 18 full layers grow with context, 36,864 bytes per token, while the 18 sliding layers hold at most 128 tokens each. At 131,072 tokens that is 36,864 × (131,072 + 128) = 4.84 GB per sequence in BF16, half of the 9.66 GB the naive formula gives. You get the half only if the engine allocates sliding layers by window; check that for your engine version before counting on it.

**DeepSeek-V3** lists `num_key_value_heads: 128`, and plugging it in with its head dimensions gives 61 × 128 × (192 + 128) × 2 = 4,997,120 bytes per token for decompressed keys and values. An MLA-aware engine caches the latent instead: `kv_lora_rank` 512 plus `qk_rope_head_dim` 64 per layer, 61 × 576 × 2 = 70,272 bytes in BF16. The config-driven number is 71 times too large.

For scale, the vLLM paper computes 800 KB per token for OPT-13B, 2 × 5,120 × 40 × 2 bytes with full multi-head attention, so one 2,048-token request held up to 1.6 GB. Llama 3 70B, five times larger, holds 40% of that per token because 64 query heads share 8 KV heads.

## From memory to a token budget

The budget per replica is GPU memory times the fraction the engine may use, minus weights, minus activations, CUDA graphs and other runtime overhead. vLLM's `--gpu-memory-utilization` defaults to 0.92 in the current docs, and the engine profiles a forward pass at startup and logs the KV size it allocated; `--kv-cache-memory-bytes` fixes the size directly. The overhead depends on the engine, the batch limits and the model, so read it from the startup log rather than estimating it.

Before overhead, Llama 3 70B with FP8 weights (about 70 GB) on two H100s at tensor parallel 2 has 2 × 80 × 0.92 − 70 = 77.2 GB, which is 77.2e9 / 327,680 = 235,596 tokens. On four H100s it has 224.4 GB, 684,814 tokens; on eight, 518.8 GB. Every replica pays for its own copy of the weights, so two TP2 replicas hold 154.4 GB of cache where one TP4 replica on the same four GPUs holds 224.4 GB.

Tensor parallelism splits KV heads across GPUs, which is why the per-replica budget is the right unit. It stops working when the tensor-parallel degree exceeds the KV head count: with 8 KV heads at tensor parallel 16, each GPU still needs at least one head, so heads are duplicated and cache per token grows.

## Sizing from a traffic mix

Requests do not all sit at full context, and the ones that stay longest are the long ones. A request occupies cache from admission until its last token, a period roughly proportional to its output length at a given inter-token latency, and during decode its resident size grows from its prompt length P to P + output o, averaging P + o/2. The mix of requests resident at any moment is therefore weighted by output length, not by arrival share.

Take a scenario mix: 60% of requests with a 2,000-token prompt and 500 output tokens, 30% at 8,000 and 1,000, 10% at 32,000 and 2,000.

<p>Weights p × o: 0.6 × 500 = 300, 0.3 × 1,000 = 300, 0.1 × 2,000 = 200, total 800. Sizes P + o/2: 2,250, 8,500 and 33,000. (300 × 2,250 + 300 × 8,500 + 200 × 33,000) / 800 = 9,825,000 / 800 = <b>12,281 tokens</b>. Averaging by arrival share instead gives 0.6 × 2,250 + 0.3 × 8,500 + 0.1 × 33,000 = 7,200, which under-sizes the cache by 41%.</p>
</Predict>

Add arrival rate and latency. At 2 requests per second and 30 ms per output token (scenario values), the number resident is 2 × 0.03 × 800 = 48 sequences, holding 48 × 12,281 = 589,500 tokens. In BF16 that is 589,500 × 327,680 = 193.2 GB of cache; in FP8, 96.6 GB.

With BF16 cache, one TP4 replica's 224.4 GB holds it at 86% before overhead, while TP2 replicas need 193.2 / 77.2 = 2.5 of them, so three, on six GPUs. With FP8 cache two TP2 replicas suffice, 96.6 / 154.4 = 63%. The sum covers mean load; the 32,000-token class alone puts a 34,000-token, 11.1 GB sequence on one replica at its peak, and bursts add sequences, so size for the arrival rate at your busiest interval and keep headroom for the largest request class.

Paging makes these sums close to real. Before PagedAttention, serving systems reserved contiguous space for each request's maximum length, and the vLLM paper measured only 20.4% to 38.2% of KV memory holding token states. With 16-token blocks, the default in the paper, a sequence wastes at most 15 tokens, 4.9 MB for Llama 3 70B in BF16.

When the cache does fill, the engine does not fail the request. The paper's scheduler serves first-come first-served, preempts the latest arrivals first, evicts a sequence's blocks all or nothing, and restores them by swapping or recomputation. Under-sizing therefore shows up as `vllm:kv_cache_usage_perc` near 1, a rising `vllm:num_requests_waiting` and recomputed prefills, which look like latency regressions rather than capacity errors.

## The sizing in code

```python
def kv_per_token(layers, kv_heads, head_dim, elem_bytes=2):
    return 2 * layers * kv_heads * head_dim * elem_bytes

def resident_tokens(mix, rate, itl_s):
    """mix: (share, prompt, output) per class; returns (sequences, tokens) resident."""
    seqs = rate * itl_s * sum(p * o for p, P, o in mix)
    toks = rate * itl_s * sum(p * o * (P + o / 2) for p, P, o in mix)
    return seqs, toks

def replica_budget(gpus, gpu_bytes, weight_bytes, util=0.92, overhead=0.0):
    return gpus * gpu_bytes * util - weight_bytes - overhead

mix = [(0.6, 2_000, 500), (0.3, 8_000, 1_000), (0.1, 32_000, 2_000)]
seqs, toks = resident_tokens(mix, rate=2.0, itl_s=0.030)
need = toks * kv_per_token(80, 8, 128)                    # Llama 3 70B, BF16 cache
print(seqs, toks, need / 1e9)                             # 48.0 589500.0 193.16736
print(replica_budget(4, 80e9, 70e9) / 1e9)                # 224.4, before measured overhead
```

## When this is wrong

The resident-size model assumes requests stream out at a steady inter-token latency and ignores time spent queued and in prefill, when a request already holds its prompt's cache. Long prompts make that time significant, so measure resident tokens from `vllm:kv_cache_usage_perc` against arrival rate once there is traffic, and use the model only to size the first deployment.

Shared prefixes change the arithmetic. With prefix caching, a system prompt or a document that many requests share is stored once and referenced by each; a 6,000-token shared prefix across 48 resident requests is 6,000 tokens of cache, not 288,000. `vllm:prefix_cache_hits` over `vllm:prefix_cache_queries` gives the hit rate to discount by.

The formula covers dense attention, MLA and sliding windows, and engines implement each differently. FP8 KV cache formats carry scales, MLA latents have their own FP8 variant (`fp8_ds_mla` in vLLM's options), and hybrid models with linear-attention or state-space layers keep a fixed-size state per sequence that does not grow with tokens. Take bytes per token from the engine's startup log for the exact model and version, and use the formula to check that number rather than replace it.
