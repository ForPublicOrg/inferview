## The autoscaler that arrived late

Scenario, not a real company: a product launch sends traffic to a self-hosted model at three times the usual rate within a minute. The Kubernetes autoscaler, watching GPU utilisation, sees nothing unusual at first, because a decode-bound GPU reports busy whether it is serving 4 users or 40. When it finally scales, each new node has to be provisioned, pull a container image, load tens of gigabytes of weights and warm up, and that takes minutes. For those minutes the queue grows, time to first token climbs past 30 seconds, and clients start retrying, which makes the queue longer.

Nothing in that story is specific to language models except the numbers: slow capacity, a misleading utilisation metric, and retries amplifying load. This lesson maps the standard operating toolkit onto LLM serving and points out where the usual defaults mislead.

## Service levels in tokens

An SLO needs an SLI, and the Google SRE workbook defines an SLI as good events divided by total events. For a streaming LLM endpoint the useful "good event" definitions are:

- **TTFT** under a threshold, per request. This is what users perceive as "it started answering". It includes queueing, so it is the first number to break under load.
- **Inter-token latency** under a threshold, per request (p99 of the request's gaps, or its mean ITL). This is what users perceive as "it is typing slowly or stuttering".
- **Success**: the request completed without an error or a truncation the client did not ask for.

Keep them separate. A deploy that changes the chunked-prefill budget can trade TTFT for ITL, and a combined "latency" SLO will hide which one moved. NVIDIA's NIM docs point out that benchmark tools disagree on whether the first token counts toward ITL, so write the definition into the SLO document.

The workbook's other rule is the useful one: "the error budget is 100% minus the SLO". At 99.9% of requests meeting the TTFT target over 30 days, the budget is 0.1%, which is 43.2 minutes of total failure (30 x 24 x 60 x 0.001) or, more realistically, a longer period of partial degradation. An error budget policy decides in advance what happens when it is spent, for example freezing model and engine upgrades until the burn stops.

## Autoscaling on the right signal

Google's GKE guidance for LLM inference recommends autoscaling on **queue size** when you want maximum throughput within a latency target, and on **batch size** for lower latency targets. On GPU utilisation it says the metric "does not measure how much work is being done while the GPU is active". That matches the anatomy lesson: decode is bandwidth bound, so a GPU looks equally busy at very different loads.

vLLM exposes the signals directly: `vllm:num_requests_waiting` is the queue, `vllm:num_requests_running` is the batch, `vllm:kv_cache_usage_perc` tells you how close memory is to forcing preemptions, and `vllm:num_preemptions` tells you it already is. A scale-up rule on sustained waiting requests, with KV usage as a second trigger, reacts to the thing users feel.

## How many replicas: Little's law

Little's law says the average number of requests in a system equals the arrival rate times the average time each spends inside. For LLM serving, "time inside" is end-to-end latency, and "capacity" is the number of concurrent sequences a replica can hold while still meeting the ITL objective, which you find with a load test, not a spec sheet.

<p>In flight: 50 x 8 = 400 requests. Usable concurrency per replica: 64 x 0.7 = 44.8. 400 / 44.8 = 8.9, so <b>9 replicas</b> at peak. The 70% headroom is a choice, not a law: it buys room for bursts and for long requests that hold more KV cache than average.</p>

Cold starts are what make LLM autoscaling different from scaling a stateless web tier. A replica is not ready until its node exists, the image is pulled, tens of gigabytes of weights are loaded into GPU memory, and the engine has warmed up. There is no general number for how long that takes; it depends on the cloud, the node pool, image size and where the weights are stored, so measure it in your environment. Whatever it is, any spike that arrives faster than that time has to be absorbed by capacity you already have. So the plan has two parts: scale on queue depth for slow growth, and keep **spare replicas** sized for the largest spike you must absorb within one cold-start time. The usual mitigations shorten the cold start: keep a warm node pool, cache images on nodes, load weights from local or nearby fast storage, and keep a small number of standby replicas.

```python
import math

def replicas_needed(peak_rps, mean_e2e_s, max_concurrency, headroom=0.7):
    in_flight = peak_rps * mean_e2e_s                  # Little's law
    return math.ceil(in_flight / (max_concurrency * headroom))

def spare_for_spike(spike_rps, mean_e2e_s, max_concurrency, cold_start_s, spike_ramp_s):
    if cold_start_s <= spike_ramp_s:
        return 0                                       # autoscaling keeps up
    return math.ceil(spike_rps * mean_e2e_s / max_concurrency)

print(replicas_needed(50, 8.0, 64))                    # 9
print(spare_for_spike(20, 8.0, 64, cold_start_s=300, spike_ramp_s=60))   # 3
```

The inputs above are illustrative. The second function is a simplification for a design conversation, not a policy: it holds enough spare capacity for a 20 requests per second jump whenever the spike arrives faster than a replica can start.

## Rolling out a model change

A new model version, a new quantization, a new engine release and a changed system prompt are all deploys, and all can change behaviour without raising an error. A rollout plan for model changes adds three checks to the usual canary:

- **Quality**: run the evaluation set against the candidate before any traffic, then compare online signals (thumbs-down rate, escalations, task success) between canary and control.
- **Tokens**: compare input and output tokens per request. A model that answers 40% longer costs 40% more output and holds KV cache 40% longer, which lowers capacity. A tokenizer change moves the same numbers: Anthropic states that Claude 4.7 and later produce about 30% more tokens for the same text, which changes cost, context headroom and rate-limit consumption at once.
- **Latency by percentile**, split into TTFT and ITL.

**Shadow** traffic (send a copy of real requests to the candidate and discard its answers) tests load and latency safely, but costs a full second set of tokens and cannot measure user reactions. A **canary** at a small share of real traffic measures reactions, with a fast rollback that is just a routing change. Keep the previous model loaded until the new one has burned no error budget for an agreed period; reloading weights during an incident is a cold start you chose.

## Load testing an LLM endpoint

Most LLM load tests flatter the system. A credible one does the following.

- Replays realistic **length distributions** for prompts and outputs. A test where every prompt is 100 tokens and every answer 100 tokens misses the long prefills that cause tail latency.
- Gets **prefix sharing** right. Sending the same prompt repeatedly gives a near-perfect prefix cache hit rate and unrealistically low TTFT. Vary prompts the way production does.
- Ramps concurrency and records TTFT and ITL percentiles at each level, so the result is a curve with a knee, not one number.
- Measures goodput, the request rate at which both latency objectives still hold, and reports it next to raw throughput.
- Watches the engine's own metrics during the run: waiting requests, KV usage and preemptions explain where the knee comes from.

## Multi-region and failure drills

A second region is only a failover target if it has the headroom to absorb the first region's traffic, which for GPUs means paying for idle capacity or accepting degraded service during failover. Decide which: full capacity in both, or a smaller model, shorter context limits or a hosted API as the degraded mode. Then drill it. Kill a replica during a load test and watch the queue. Make the primary provider return 429s and confirm the gateway's fallback works and does not retry-storm. Write the postmortem in the usual blameless form, with the timeline in TTFT, ITL, queue depth and preemptions, because those are the numbers that show what the users saw.

The design prompt from techinterview.org is a good rehearsal: 10 million calls a day, about 1,000 requests per second at peak, TTFT under 500 ms and at least 30 tokens per second. Those are interview assumptions, not industry facts, but notice what they imply: 10 million a day averages 116 requests per second (10,000,000 / 86,400), so the stated peak is about 8.6 times the average, and that ratio decides how much of your fleet idles at night.

## When this is wrong

Little's law holds for averages over a stable period. Bursty arrivals and heavy-tailed output lengths mean the instantaneous load can sit well above the average, which is why the headroom factor exists and why its value is a judgement you should revisit with production data.

Per-replica concurrency is not a constant. It depends on context lengths, prefix cache hit rate, engine version and settings such as the batched-token budget. Re-run the load test whenever one of them changes, and treat the replica count as an output of measurement rather than a number in a config file.

If you call a hosted API instead of running GPUs, most of this lesson moves to the provider, but not all of it. Your SLOs still need TTFT and ITL from the client side, rate limits replace capacity as the constraint, and the gateway lesson's fallbacks become your multi-region plan.
