## A cache key that encodes position and history

Engine prefix caching keeps the KV blocks of finished requests and hands them to new requests whose prompts start with the same tokens. The cache key is what makes it different from a response cache. The keys and values for a token depend on every token before it, through attention in every layer, so the same 16 tokens after two different preambles have different KV. A block can be reused only if the whole prefix before it matches.

vLLM encodes that directly. Each full block's hash is computed from three inputs: the hash of the block before it, the token ids in the block, and extra hashes that make it unique beyond its tokens, such as a LoRA adapter id, the hash of an image whose placeholder tokens sit in the block, and a cache salt. Chaining through the parent hash means a lookup walks the request's blocks in order and stops at the first miss: the hit is always a prefix, and one hash per block decides it. The structure is a Merkle chain over KV pages, with the paged allocator from PagedAttention underneath so a cached block can be referenced by many running requests at once.

Only full blocks are cached. A prompt whose shared part ends mid-block reuses everything up to the last full block and recomputes the rest. The hash function is a configuration choice with consequences: since v0.11 the default is SHA-256 over a pickle serialisation, which is not reproducible across Python or vLLM versions; `sha256_cbor` is the deterministic option for caches shared across processes or languages; and the xxHash options are faster but non-cryptographic, which the docs warn raises the collision risk, with collisions able to cause undefined behaviour or leak private information between tenants.

```python
import hashlib

BLOCK = 16

def block_hashes(tokens, salt=""):
    """vLLM-style chain: each full block hashes its parent's hash, its tokens and extra keys."""
    hashes, parent = [], salt
    for i in range(0, len(tokens) - BLOCK + 1, BLOCK):
        h = hashlib.sha256(repr((parent, tuple(tokens[i:i + BLOCK]))).encode()).hexdigest()
        hashes.append(h)
        parent = h
    return hashes

def cached_tokens(tokens, cache, salt=""):
    hit = 0
    for h in block_hashes(tokens, salt):
        if h not in cache:
            break
        hit += BLOCK
    return hit

system = list(range(1000, 4000))              # 3,000-token shared system prompt
cache = set(block_hashes(system + [7] * 500))  # first request fills the cache

req = system + [9] * 500                       # same system prompt, different user turn
print("hit tokens, same prefix:      ", cached_tokens(req, cache))
stamped = [42] + system[1:] + [9] * 500        # one token changed at position 0
print("hit tokens, first token edited:", cached_tokens(stamped, cache))
print("hit tokens, other tenant salt: ", cached_tokens(req, cache, salt="tenant-b"))
# hit tokens, same prefix:       2992
# hit tokens, first token edited: 0
# hit tokens, other tenant salt:  0
```

The second line is the production failure: a timestamp, request id or user name at the top of the system prompt changes the first block, every later hash changes with it, and the hit rate is zero while the cache metrics show the cache working. Stable content goes first and variable content last; that ordering is a contract between the prompt owners and the serving team, and it belongs in the prompt review checklist.

## Eviction

Blocks no request references go on a free queue, a doubly linked list threaded through the block table so every move is constant time. A cached block stays findable by hash while it sits there and is evicted only when the allocator needs it, least recently used first. Two details shape what survives. When a request finishes, its blocks join the queue in reverse order, so the tail of the request, which hashes the most tokens and is least likely to be shared, is evicted before the system prompt at its head. And blocks that a new request hits are pulled off the queue before its new blocks are allocated, so an allocation cannot evict the prefix it is about to use.

The V1 release post reports less than 1% throughput loss at a 0% hit rate, which is why prefix caching is on by default in vLLM V1. SGLang reaches the same reuse with RadixAttention, which keeps cached prefixes in a radix tree; NVIDIA's Dynamo router also tracks cache locations in a radix tree. The data structure differs; the contract (longest cached prefix, LRU eviction of unreferenced pages) is the same.

## What a hit saves

A hit skips the prefill of the cached tokens: their FLOPs, and the time to first token they would have cost. It does not shorten decode. Every decode step still reads the full KV of the sequence, cached prefix included; the saving on the decode side is memory, because many running requests can reference one copy of the shared blocks.

Take Llama 3 8B serving 20 requests per second, each a 3,000-token system prompt followed by a 500-token user turn, with 16-token blocks. The system prompt fills 187 full blocks, 2,992 tokens, and the last 8 tokens share a block with the user turn.

That figure assumes the prefix stays resident. On one replica at 20 requests per second it will: the head blocks are touched constantly and sit at the young end of the LRU queue. The estimate breaks in two places. Under memory pressure, a burst of long requests can push even hot blocks out. And across replicas, each one has its own cache, so the question becomes which replica a request lands on.

## Routing decides whether the hit happens

With one shared system prompt, cache-blind routing costs little: every replica sees the prefix often and keeps its own copy. With many distinct prefixes (one per tenant, per document, per long conversation), a cache-blind balancer spreads requests for the same prefix across replicas, each replica computes and stores its own copy, and the copies compete for memory until they evict each other.

llm-d's benchmark (the project's own, September 2025) shows the size of the effect: 8 vLLM pods on 2 H100 each serving Qwen3-32B, 150 customers each with a 6,000-token shared context and 5 users sending 1,200-token queries, at 3 to 60 queries per second, with all active prefixes needing about 73% of the cluster's KV capacity. Random scheduling produced 4,428.7 output tokens per second and a p90 time to first token of 92.551 seconds; approximate prefix-aware scheduling, which predicts cache location from past routing, 6,944.4 and 31.083; precise scheduling, which indexes the KV events each pod publishes and scores pods by how much of the request's prefix they hold, 8,730.0 and 0.542.

Approximate routing, whether it predicts location from its own routing history or hashes a prefix key consistently to a replica, fails where the router's belief and the pod's cache disagree: after an eviction under pressure, a restart, or a scale event. The precise method needs the engine to publish block-level events and a component to index them. Both have to be combined with a load signal, because perfect affinity sends every request for a hot prefix to one replica; llm-d and Dynamo both score cache overlap and load together. The policy question is how much queueing you accept on a warm replica before a cold one becomes cheaper, and it is answered by comparing the queue wait against the prefill time of the prefix.

## Shared caches leak

A cache shared across tenants is a side channel. If tenant B's request returns faster, or reports more cached tokens, when it starts with text tenant A sent, B can test guesses about A's prompts. vLLM's `cache_salt` closes it: the salt is injected into the first block's hash, so blocks are reusable only by requests carrying the same salt, and the docs give timing attacks as the reason.

The advisory GHSA-935w-9g4m-p28p (published 2026-09-28, CVE-2026-105752, low severity) shows where such controls break. On vLLM's `/v1/responses` path for GPT-OSS models, a request that used a built-in or MCP tool ran as a loop, and the continuation turn after the tool call was resubmitted without the caller's salt. That prefix was cached in the unsalted namespace, and an attacker able to reconstruct the post-tool history could read exact cached-token counts from the usage field of the response. Versions below 0.30.0 were affected; the fix passes the salt into the continuation call. Two lessons generalise: the salt has to follow every internal resubmission path, not only the request handler, and usage fields that report cached tokens are an oracle as direct as timing.

Salting has a cost the security review does not see. A salt per tenant makes the chain per tenant from the first block, so a system prompt that every tenant shares is stored once per tenant per replica. With Llama 3 8B, one token of BF16 cache is 2 × 32 layers × 8 KV heads × 128 × 2 bytes = 131,072 bytes; the 2,992 cached tokens are 0.39 GB for one copy and 59 GB for 150 tenants on the same replica, if all stay resident. In practice they do not, so salting shows up as a lower hit rate rather than as an out-of-memory error. The middle option is a salt per isolation group, tenants who accept sharing with each other, which the salt mechanism supports because reuse follows whoever holds the same salt.

## When this is wrong

The savings estimate counts linear-layer FLOPs for the cached tokens and ignores attention, which makes it an underestimate for long prefixes, and it assumes the prefix is resident, which makes it an overestimate under memory pressure. The measured hit rate per replica, in tokens rather than requests, is the number to plan with; a request that hits 10 tokens of a 3,000-token prompt counts as a hit in some dashboards.

Prefix caching assumes the prefix is byte-identical in tokens. Two prompts that differ in whitespace, in the order of tool definitions, or in a tokenizer version produce different tokens and share nothing. Multimodal inputs add another failure: the image hash is part of the block key, so the same image re-encoded or resized misses.

Engine-level caching is also not the same thing as the prompt caching a model API sells. Provider caches have their own lifetimes, minimum lengths and prices, and they cache on the provider's fleet; the mechanism here is what runs inside the engine you operate.
