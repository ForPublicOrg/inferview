## Four ways to use more than one GPU

A serving deployment uses several GPUs for one of two reasons: the model does not fit on one, or one replica is too slow per token. Data parallelism, more replicas, addresses neither; it adds throughput. The other three split a single replica, and each one moves a different cost.

Tensor parallelism (TP) splits every weight matrix across the GPUs of a group, so each GPU holds and reads a slice of every layer and the group combines partial results with collectives inside every layer. Pipeline parallelism (PP) assigns contiguous layers to different GPUs, so only the activations at stage boundaries cross between them. Expert parallelism (EP) places whole experts of a mixture-of-experts model on different GPUs and routes each token to the GPUs holding its experts. vLLM's guidance follows the same lines: TP is "the most common strategy for large model inference within a single node", PP is for when efficient TP is maxed out or across nodes, EP is for MoE models, and DP replicates the model to scale throughput.

## Tensor parallelism: latency for synchronisation

TP is the only one of the three that lowers the latency floor of a decode step. A step reads every weight once; with TP the read is split, so each GPU reads 1/N of the bytes in parallel.

The price is synchronisation. Megatron-LM's layout splits the first GEMM of each block by columns and the second by rows, so a transformer layer needs two all-reduces in the forward pass, one after attention and one after the MLP. Serving runs only the forward pass, so Llama 3 70B at any TP degree performs 2 × 80 = 160 all-reduces per decode step. Each carries the hidden state of every token in the step: 8,192 × 2 bytes = 16 KiB per token in BF16, so 1 MiB for a batch of 64. With a ring all-reduce each GPU sends about 2(N − 1)/N times the payload, which at TP8 and batch 64 is about 1.8 MiB per all-reduce and 294 MB per step.

Two properties of that traffic decide where TP works. Volume grows with the batch, and at NVIDIA's listed 900 GB/s NVLink against 128 GB/s PCIe Gen5 per H100, the same bytes take about seven times longer over PCIe. And the count is fixed: 160 synchronisation points per token, each a barrier on the critical path, so any per-collective latency is paid 160 times per step. Across nodes, over a network instead of NVLink, both costs grow, which is why TP stays inside one NVLink domain and vLLM warns that raising it "may cause excessive synchronization overhead".

TP also has a structural limit. Llama 3 70B and 405B both have 8 KV heads. At TP8 each GPU holds one KV head; beyond 8, the KV heads cannot be split further and must be replicated, so the extra GPUs add synchronisation without reducing KV bytes per GPU.

## Pipeline parallelism: fit across nodes

PP sends only activations between stages: one hidden state per token per boundary, rather than two collectives per layer. That tolerates slower links, which is why it is the standard way to span nodes; Megatron-LM's training work composes TP inside a node with PP across nodes for the same reason, to avoid expensive cross-node communication.

For serving, PP buys capacity, not latency. A single sequence's decode step still traverses every stage in order, so its time per token is at least the sum of the stages plus the hops; vLLM lists latency penalties as the cost. To keep all stages busy, the scheduler needs at least as many micro-batches in flight as there are stages, so each stage processes a different batch at any moment. Under-filled pipelines leave stages idle, the bubble problem, which is why uneven batches hurt PP more than TP; Sarathi-Serve's uniform chunked batches were partly a fix for that. PP also composes less freely with other features: vLLM's docs state that PP and speculative decoding were not composable in vLLM 0.15.0 and earlier.

The decision PP usually settles is a format question in disguise. Llama 3 405B in BF16 is 810 GB, more than one node of eight 80 GB H100s (640 GB), so BF16 needs two nodes, TP8 within each and PP2 across them. In FP8 it is 405 GB and fits one node. One token of its BF16 KV is 2 × 126 layers × 8 KV heads × 128 × 2 bytes = 516,096 bytes. With 5 GB per GPU reserved, the FP8 single node leaves 640 − 405 − 40 = 195 GB, about 378,000 tokens; the BF16 two-node pipeline leaves 1,280 − 810 − 80 = 390 GB, about 756,000 tokens, at twice the GPUs and with a cross-node hop in every step. If FP8 passes the quality floor, the single node wins on latency and cost per token; if it does not, PP is what makes BF16 possible at all.

## Expert parallelism: keep experts whole

An MoE layer has many small expert MLPs and routes each token to a few of them. TP would slice every expert N ways, turning already small per-expert GEMMs into tiny ones. EP instead places whole experts on different GPUs: each token's hidden state is sent to the GPUs holding its experts and the results are sent back, an all-to-all dispatch and combine in every MoE layer. DeepSeek's stated reason for wide EP is to give each expert a large enough batch.

DeepSeek-V3's published deployment shows the shape at scale. The model has 671B parameters with 37B active per token, and each MoE layer has 1 shared and 256 routed experts with 8 routed experts active per token. The prefill unit is 4 nodes and 32 GPUs: attention at TP4 with sequence parallelism and DP8, MoE at EP32, plus 32 redundant copies of high-load experts, re-chosen periodically. The decode unit is 40 nodes and 320 GPUs with EP320, one expert per GPU. Tokens cross nodes over InfiniBand at 50 GB/s and are forwarded inside a node over NVLink at 160 GB/s in that cluster. Prefill and decode use different layouts because they have different bottlenecks, which is the disaggregation lesson applied to parallelism.

In vLLM, EP is enabled with `enable_expert_parallel` and its size is TP × DP; with TP 1, attention is replicated across the data-parallel ranks while experts are sharded across all of them. The all-to-all backend follows the phase: `deepep_high_throughput` for prefill-heavy multi-node work, `deepep_low_latency` for decode, `allgather_reducescatter` as the default. Routing is skewed in practice, so some experts receive far more tokens than others and the GPUs holding them set the step time; vLLM's EPLB redistributes experts across ranks and can hold redundant copies, at a memory cost that comes out of KV capacity.

## Picking a layout for a stated model and node

The procedure: choose a format, then the smallest TP that fits the weights with enough KV room for the batch you need; raise TP inside the NVLink domain only if the latency floor misses the target; use PP only to cross nodes; use EP for MoE experts; spend remaining GPUs on replicas. KV tokens per replica are (N × 80 − 70 − N × 5) GB over 327,680 bytes. TP1 is ruled out by KV room: 15,259 tokens is a handful of chat sequences. Each step up in TP stores the weights once more per node instead of once per replica, which frees memory for KV, and halves the weight-read floor. Against that, it halves the number of independent replicas, so a replica failure or a slow request affects a larger share of traffic, and it adds synchronisation the floor column does not show. TP2 or TP4 is the usual answer for this model and node; the choice between them is the latency target. A 15 ms per-token target with KV reads on top rules out TP2's 10.4 ms floor in practice; a 50 ms target does not, and four replicas then give more scheduling freedom than two.

## When this is wrong

The table counts only weight reads. Communication, KV reads and kernel efficiency all change with the TP degree: small per-GPU GEMMs at high TP run further from peak, and the all-reduce cost depends on message sizes that change with the batch. Measure step time against batch size for each candidate layout before choosing; the table only says which layouts are worth measuring.

The MoE picture depends on routing statistics that differ between models and traffic. A workload that sends most tokens to a few experts makes EP behave like a slow TP with one hot GPU, and expert load balancers trade memory for that imbalance. DeepSeek's layout is the published design of one operator at one scale, with its own network; copy the reasoning, not the degrees.

And the hardware boundary moves. Systems with NVLink domains larger than eight GPUs, such as rack-scale designs, move the edge where TP stops paying, and the "TP inside a node" rule is really "TP inside the fast interconnect domain". Check the domain size of the hardware you have before applying it.
