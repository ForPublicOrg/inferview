## The decision

Once more than one team calls a model API, someone decides where keys, quotas, routing, caching and usage records live: in a library each service imports, in a proxy every call passes through, or in a hosted router that also holds your provider relationships. All three are an API gateway with a token meter. Three things make the model case different from an HTTP gateway in front of stateless services.

The unit of cost varies by more than an order of magnitude between requests to the same endpoint, and it is not known until the response finishes, because the model decides the output length. Price is also not one number per token. A Claude request is billed separately for fresh input, 5-minute cache writes, 1-hour cache writes, cache hits and output, and Haiku 5.5 raises every one of those rates fivefold when the prompt crosses 100,000 tokens (Anthropic pricing page, checked 2026-10-28).

Backends are not interchangeable. Two HTTP replicas return the same body; two models, or one open-weight model from two providers running different quantisations, return different answers. A fallback is therefore a behaviour change, not only an availability event.

The usage record is the only source of truth for attribution. The provider's invoice knows keys and models; it does not know tenants or features.

The rule that follows: the gateway owns whatever must be uniform across teams or needs the whole picture of spend, and the product owns whatever depends on a feature's semantics.

## What the gateway owns, in request order

**Identity and tags.** The gateway issues its own keys to services and holds the provider keys, so a leaked service key is revoked without rotating a provider key shared by every team. Each call carries tenant, feature and environment tags. In production an untagged call is rejected, because it becomes spend nobody can attribute.

**Token quotas with reserve and settle.** A requests-per-minute limit treats a 200-token classification and a 150,000-token document review as equal. The limit has to be in tokens, and since output length is unknown at admission, the gateway reserves prompt tokens plus `max_tokens`, then settles to the actual count when the response ends. LiteLLM's proxy does this for dollar budgets: its docs describe a reservation that holds the estimated maximum cost before the call and replaces it with the actual cost afterwards, on by default.

**Routing and fallback.** The gateway chooses a deployment for the requested model (provider routing) and, by policy, a different model when the first fails (model fallback). Provider routing among identical deployments is the gateway's job. Deciding which model is acceptable for a feature is not; the product declares an ordered allowlist per feature, and the gateway enforces it. Routing by difficulty is the next lesson.

**Caching.** An exact-match response cache is safe at the gateway for deterministic, tenant-scoped calls, with tenant, model and every sampling parameter in the key. Provider prompt caching is different: a hit needs a byte-identical prefix, so the hit rate depends on how the product assembles the prompt. The gateway can measure the hit rate per feature; only the product can fix it.

**The usage record.** One row per attempt, with requested model, served model, every token category, latency, the tags, and the cost computed from a dated price table. The served model matters because each of the products compared below can serve a model other than the one requested.

## What stays in the product

The prompt, its layout and its cache breakpoints. Output validation, and what happens when validation fails. Safety of the user-visible operation under retries: a gateway retry of a call whose first attempt already triggered a tool call is the product's problem. Evals, because "model B is an acceptable fallback for feature X" can only be decided against feature X's eval set. Streaming behaviour toward the end user. A gateway that rewrites prompts, for example trimming context to fit a cheaper model's window, has made a product decision without the product's evals.

All three do fallbacks, retries and load balancing. They differ in where they run, how budgets are enforced, and what fails when a dependency is down.

Four behaviours under those rows decide production outcomes.

**What happens when the budget store is down.** LiteLLM's docs state that budgets are enforced against spend read from Postgres, and that the global `max_budget` fails open without a database rather than erroring. A runaway agent loop during a database incident is exactly when a budget is needed. Either alert on the fail-open path or check budgets against a store whose outage blocks traffic, and decide which per feature in writing, because it is a choice between an outage and an uncapped bill.

**Where the counters live.** LiteLLM's `max_parallel_requests` returns an immediate 429 with no queue, and the docs state the limit is per process, not shared across workers: ten workers with a cap of 20 admit 200. Usage-based routing that shares counters goes through Redis, which the same docs say is not recommended for production because of the latency it adds. A token limit exact across replicas costs a round trip to a shared store per request; an approximate one splits the rate across replicas and accepts unfairness between them.

**What the budget can see.** Portkey's budget page says requests showing 0 cents in its cost column do not count toward the budget, and limits apply to models it has pricing for. A self-hosted model, or a new model the price table does not know yet, is invisible to the cap. LiteLLM's cost-based routing has the mirror problem: a deployment missing from its cost map is assigned $1. Either way the price table is production configuration and needs an owner and a test that every routable model has a price.

**How a fallback shows up.** OpenRouter returns the model actually used in the response's `model` attribute and bills at that model's price. LiteLLM sets `x-litellm-model-id` and records `attempted_fallbacks` and `original_model_group` in its spend logs. Portkey shows every attempt under the request's trace ID. None of them stop a product from treating a fallback answer as a primary answer. Unless the served model is written into the usage record and compared with the requested one, a context-length fallback can move a feature to a different model for weeks without anyone deciding it.

OpenRouter's provider routing is not round robin, and the split is worth computing. Among providers with no significant outage in the last 30 seconds, it weights the cheapest by the inverse square of price. With three stable providers at $1, $2 and $3, the weights are 1, 1/4 and 1/9, which sum to 1.361, so the $1 provider is tried first 73% of the time, the $2 provider 18% and the $3 provider 8%. If those providers run different quantisations of the same open-weight model, about three quarters of your traffic goes to the cheapest quantisation unless you pin `quantizations` or `order`.

## The usage record, priced at the date of the call

Cost is a function of the full token breakdown, not of total tokens, and the function has thresholds. The record below keeps requested and served models apart and prices from a table that carries its check date.

```python
from dataclasses import dataclass

# USD per million tokens, from platform.claude.com/docs/en/about-claude/pricing, checked 2026-10-28.
PRICES = {
    ("claude-haiku-5.5", "short"): dict(inp=0.10, w5m=0.125, w1h=0.20, hit=0.01, out=0.50),
    ("claude-haiku-5.5", "long"): dict(inp=0.50, w5m=0.625, w1h=1.00, hit=0.05, out=2.50),
    ("claude-sonnet-5.5", "short"): dict(inp=2.00, w5m=2.50, w1h=4.00, hit=0.10, out=10.00),
}

@dataclass
class Usage:
    tenant: str
    feature: str
    requested_model: str
    served_model: str          # differs from requested_model after a fallback
    fresh_in: int
    write_5m: int
    write_1h: int
    cache_hit: int
    out: int
    us_only: bool = False      # inference_geo "us": 1.1x on every token category

def cost_usd(u: Usage) -> float:
    prompt = u.fresh_in + u.write_5m + u.write_1h + u.cache_hit
    tier = "long" if u.served_model == "claude-haiku-5.5" and prompt > 100_000 else "short"
    p = PRICES[(u.served_model, tier)]
    usd = (u.fresh_in * p["inp"] + u.write_5m * p["w5m"] + u.write_1h * p["w1h"]
           + u.cache_hit * p["hit"] + u.out * p["out"]) / 1e6
    return usd * (1.1 if u.us_only else 1.0)

a = Usage("acme", "contract-qa", "claude-haiku-5.5", "claude-haiku-5.5", 4_000, 0, 0, 95_000, 800)
b = Usage("acme", "contract-qa", "claude-haiku-5.5", "claude-haiku-5.5", 6_000, 0, 0, 95_000, 800)
print(f"{cost_usd(a):.5f} {cost_usd(b):.5f} {cost_usd(b) / cost_usd(a):.1f}x")  # 0.00175 0.00975 5.6x
```

The two requests differ by 2,000 fresh input tokens. The second crosses 100,000 prompt tokens, and Anthropic's page says prompt length counts cache reads and writes, so every token in it, including the 95,000 cached ones, moves to the higher rates: $0.00975 against $0.00175, 5.6 times the cost. A gateway that estimates cost as total tokens times an average price misses this, and a feature whose retrieved context grows by a few chunks can multiply its bill by five with no change in traffic.

Attribution queries run on these rows: cost per tenant per feature per week, reserved against settled tokens, cache-hit tokens as a share of prompt tokens, and the share of attempts where the served model differs from the requested one. The last two explain most unexplained bills, and neither is visible on a provider invoice.

## When this is wrong

With one team and one provider, a gateway is a hop and a service to operate in exchange for what the provider console already shows. The case for it starts when attribution across teams, tenants or providers is a requirement, or when keys must be revocable per service.

Cost computed from list prices is an estimate. Committed-use discounts, batch pricing, regional multipliers such as Anthropic's 1.1 times for US-only inference on Claude 4.6 and later, and credit fees such as OpenRouter's 5.5% on purchases all sit between the usage record and the invoice. Reconcile monthly against the provider's billing export and treat a persistent gap as a price-table bug.

The comparison is dated 2026-10-28. These products ship often, and a documented default is what a fresh install does, not what yours does after a year of configuration. Read the running configuration before trusting any comparison table, this one included.
