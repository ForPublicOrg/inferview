## Two ways to serve a fine-tune

A LoRA adapter replaces a weight matrix W with W + (α/r)·B·A, where A and B have rank r. A serving platform can apply that sum once, before serving, or on every forward pass. The choice decides the unit of deployment.

Merged, the adapter disappears: the server holds W' and runs the base model's kernels at the base model's speed. Fireworks, whose docs describe both modes, says a live-merged deployment performs identically to a natively trained model with no inference overhead, and allows one adapter per deployment. The cost is that every tenant is a full model copy.

Unmerged, one copy of W serves every adapter, and each request carries an adapter id; the server computes x·W + (α/r)·(x·A)·B for that request's adapter, batching requests for different adapters together. Fireworks calls this multi-LoRA, puts its overhead at a TTFT often 10 to 30% above the base (the vendor's estimate), and says the number of adapters on a deployment has little effect on per-request performance. The cost moves from memory into operations: slot limits, rank caps, cache sharing and routing.

## The arithmetic of one adapter

An adapter on a matrix of shape d_in × d_out stores r·(d_in + d_out) parameters. Mistral-7B's config gives the shapes: hidden size 4096, MLP width 14336, 32 layers, and 8 KV heads of 128, so the key and value projections are 4096 × 1024.

Against that, the base is 7.24 billion parameters by the same config (32 layers of 218 million plus 262 million for the untied embeddings and output head), 14.48 GB in BF16. A merged tenant costs 14.48 GB; an unmerged rank-16 tenant on all linear layers costs 83.9 MB, 173 times less. LoRA Land served 25 fine-tuned Mistral-7B models from one 80 GB A100 with LoRAX; at the all-linear rank-16 size, 25 adapters are 2.1 GB, while 25 merged copies would be 362 GB. The memory argument for unmerged serving is settled at this scale; the remaining questions are about compute and operations.

```python
MISTRAL_7B = {"hidden_size": 4096, "intermediate_size": 14336, "num_hidden_layers": 32,
              "num_attention_heads": 32, "num_key_value_heads": 8, "vocab_size": 32000}

def shapes(cfg):
    h, f = cfg["hidden_size"], cfg["intermediate_size"]
    kv = cfg["num_key_value_heads"] * h // cfg["num_attention_heads"]
    return {"q_proj": (h, h), "k_proj": (h, kv), "v_proj": (h, kv), "o_proj": (h, h),
            "gate_proj": (h, f), "up_proj": (h, f), "down_proj": (f, h)}

def lora_bytes(cfg, rank, targets, elem=2):
    s = shapes(cfg)
    return sum(rank * (s[t][0] + s[t][1]) for t in targets) * cfg["num_hidden_layers"] * elem

def base_params(cfg):
    layer = sum(i * o for i, o in shapes(cfg).values())
    return layer * cfg["num_hidden_layers"] + 2 * cfg["vocab_size"] * cfg["hidden_size"]

ATTN = ["q_proj", "k_proj", "v_proj", "o_proj"]
ALL = ATTN + ["gate_proj", "up_proj", "down_proj"]
print(lora_bytes(MISTRAL_7B, 16, ATTN))     # 27262976
print(lora_bytes(MISTRAL_7B, 64, ALL))      # 335544320
print(base_params(MISTRAL_7B))              # 7241465856, norms excluded
```

## What the S-LoRA paper changed

The S-LoRA paper's main baseline, which it calls vLLM-packed, merges each adapter into its own copy of the base and runs the copies as separate vLLM processes on one GPU. It measured that baseline at 2.04 requests per second with 5 adapters on one A100 80GB, out of memory at 100. S-LoRA keeps every adapter in host memory, copies to the GPU only those the running batch uses, and allocates adapter weights and KV blocks from one paged pool so that adapters of different ranks and sequences of different lengths fragment the same memory. With Llama-7B rank-8 adapters it served 5 adapters at 8.05 requests per second and 2,000 at 7.61. The paper reports up to 4 times the throughput of vLLM-packed and 30 times that of HuggingFace PEFT. Its ablation is the decision rule for merging: merging wins with one adapter and loses beyond two, because each adapter switch leaves the GPU underused.

Host memory is the reason it scales. At Mistral-7B shapes, 2,000 rank-8 attention-only adapters are 2,000 × 13.6 MB = 27.3 GB, more than a third of an 80 GB GPU; in host memory they cost little, and only the working set competes with the KV cache. The paper names the I/O of loading adapters as a remaining concern and mitigates it by prefetching adapters for requests already in the waiting queue.

Multi-LoRA batching has since moved into the mainstream engines. The rest of this lesson uses vLLM's current interface, because its limits are where the operating decisions sit.

## The knobs that become incidents

vLLM's LoRA configuration has four limits that matter, with defaults from the current docs:

- `--max-loras`, default 1: the most adapters in one batch. With the default, requests for a second adapter wait for the first adapter's requests to clear, which looks like a latency problem on a lightly loaded replica.
- `--max-cpu-loras`, at least `max_loras`: adapters cached in host memory, the S-LoRA tier.
- `--max-lora-rank`, default 16, from a fixed set of choices (1, 8, 16, 32, 64, 128, 256, 320, 512): the docs say to set it to the highest rank among the adapters and warn that a value much higher than needed wastes memory.
- `--fully-sharded-loras`, default off: with tensor parallelism, only half of the LoRA computation is sharded unless this is enabled.

The rank cap is checked against the adapter, and it is checked strictly. vLLM's `peft_helper.py` takes the largest rank across the adapter's base `r` and every per-module `rank_pattern` entry, and rejects the adapter if that exceeds `max_lora_rank`. An adapter declared at rank 16 with one module at rank 64 fails on a server capped at 32. The same validation rejects DoRA, LoRA bias terms and adapter bias, so a training configuration can produce adapters that load in PEFT and fail at serving time.

The memory cost of a high cap is a budget question. A slot sized for rank 64 on all linear layers of Mistral-7B is 335.5 MB, so eight such slots hold 2.68 GB. Mistral-7B caches 2 × 32 × 8 × 128 × 2 = 131,072 bytes per token in BF16, so those slots equal the KV cache of 20,480 tokens. Raising the cap to fit one tenant's large adapter takes capacity from every tenant on the replica; lowering it to recover capacity breaks the tenants whose adapters exceed the new cap, at load time, with an error naming the rank.

## Prefix sharing stops at the adapter

In vLLM the prefix-cache block hash includes the LoRA ID. Two tenants with different adapters and the same 2,000-token system prompt each cache their own copy, because the adapter changes every layer's keys and values. On one replica serving 25 such tenants, that prompt holds 25 × 2,000 × 131,072 bytes = 6.55 GB instead of 262 MB. Shared prompts across tenants are a reason to keep common traffic on the base model and send only the tenant-specific part of a workflow to the adapter.

## Routing sticks to the adapter

An unmerged adapter is cheap to hold and expensive to fetch for the first time, so routing has to prefer replicas that already hold it, the same bounded affinity the fleet-routing lesson applied to prefixes, with the adapter id as the key. A popular adapter needs a larger replica set than a rare one, so the router maps each adapter to a set of replicas sized by its traffic and spreads load inside the set; a rare adapter maps to one or two replicas and accepts a cold load when they are busy. The cost is that adapter popularity becomes a placement input the platform has to measure and update, and a tenant whose traffic jumps lands on too few replicas until the mapping catches up.

Loading is a control-plane path, not a request path. vLLM supports loading adapters at runtime through `/v1/load_lora_adapter` when `VLLM_ALLOW_RUNTIME_LORA_UPDATING` is set, and its docs warn that this carries security risks and should not be used in production outside an isolated, fully trusted environment; resolver plugins that download adapters on demand from remote sources are described as insecure and not intended for production. A tenant-facing platform therefore validates each adapter once at upload (rank against the fleet's cap, supported features, target modules, an evaluation gate), stores it in a store the platform controls, and pushes it to replicas, which load it from local disk. An adapter is a release: it changes answers for one tenant, and it goes through the same probe-and-rollback discipline as a model version.

## When this is wrong

The memory arithmetic assumes adapters are small next to the base. Adapters on embeddings and the output head, or at high rank on a model with a wide MLP, can reach a sizeable share of the base, and at that point a merged copy and an unmerged slot are closer in cost than the 173 times above.

The overhead figures are conditional. Fireworks' 10 to 30% is the vendor's estimate for its own stack, S-LoRA's numbers are for 2023-era kernels and baselines, and the ratio between merged and unmerged speed depends on batch composition: a batch of many distinct adapters does more small matrix products than a batch where most requests share one. Benchmark the engine version you deploy with the adapter mix you expect.

Quantization changes the merge decision. Merging an adapter into a quantized base means requantizing the merged weights, and unmerged serving may require a higher-precision base: Fireworks' multi-LoRA requires BF16 deployment shapes and does not support addons on FP8 or FP4 shapes, as of the check date. A fleet that runs its base in FP8 for capacity may find that adapters cost it that capacity back.
