## Balance is a query, not a column

A token-credit system that stores one balance per customer and decrements it fails on the first requirement that is not a decrement: a grant that expires, a request whose cost is unknown when it starts, a refund for a failed request, an event that arrives after a later one. Each of those is an entry in a ledger, and the balance is derived from the entries. Stripe's billing credits are built this way; its docs describe each credit grant as backed by an immutable, append-only ledger, and they distinguish a ledger balance from an available balance, the second net of expired credits and unrecorded transactions.

Getting it wrong costs in both directions. Debits that never post, or usage reported too late to invoice, are lost revenue. Holds that are too large, or expirations applied in the wrong order, reject requests from customers who have paid. The exercise is common enough in interviews to have several candidate reports: Hello Interview's OpenAI L5 guide lists a credit-tracking service for token balances, and PracHub lists a CreditTracker with expirations tagged Perplexity (August 2025) and an expiring GPU-credit tracker with out-of-order events tagged OpenAI (March 2026). Those are candidate reports, not company statements.

The ledger has five entry types: grants (amount, effective time, expiry, priority, category), debits, holds and their captures or releases, refunds, and expirations. The decisions are the consumption order, how big a hold is, what happens when a grant expires under an in-flight request, and when usage must reach the billing system.

## Consumption order: soonest expiring first

When several grants are live, the order in which a debit draws from them decides how many credits expire unused. Drawing from the grant that expires soonest is the order that minimises waste for a fixed usage pattern: any debit taken from a later-expiring grant while an earlier one has credit can be swapped onto the earlier grant without making anything worse.

Expiry is not the only key. Stripe applies grants by priority first (a lower number wins), then earliest expiry, then promotional before paid, then earliest effective date, then earliest creation. Priority exists because a business may want paid credits, which are deferred revenue, or contract-specific credits used in a fixed order regardless of expiry. The tie-breakers matter for one reason: two replays of the same events must produce the same allocation, or reconciliation cannot compare them. Write the full sort key down and never let it depend on storage order.

## Out-of-order events and replay

Usage events arrive late and out of order. A gateway retries a report; a region's queue drains after a partition; a debit stamped 23:59 arrives after a grant that started at 00:00. If the ledger applies events in arrival order, the allocation depends on network timing. The robust model stores events and computes balances by replaying them in event-time order; the PracHub variant with out-of-order events tests exactly this.

```python
import heapq

class CreditLedger:
    def __init__(self):
        self.grants, self.debits = [], []

    def grant(self, gid, amount, start, expires):        # usable on [start, expires)
        self.grants.append((start, expires, amount, gid))

    def debit(self, amount, at):                          # events may arrive out of order
        self.debits.append((at, amount, len(self.debits)))

    def replay(self, until):
        """Replays every event up to `until`, soonest-expiring grant first.
        Returns (remaining, expired, short): short is usage no grant covered."""
        events = [(s, 0, gid, amt, exp) for s, exp, amt, gid in self.grants]
        events += [(t, 1, seq, amt, None) for t, amt, seq in self.debits]
        events.sort(key=lambda e: e[:3])                  # grants before debits at equal times
        live, left, expired, short = [], {}, 0, 0

        def expire(now):
            nonlocal expired
            while live and live[0][0] <= now:
                _, gid = heapq.heappop(live)
                expired += left.pop(gid)

        for t, kind, key, amt, exp in events:
            if t > until:
                break
            expire(t)
            if kind == 0:
                left[key] = amt
                heapq.heappush(live, (exp, key))
                continue
            while amt and live:
                gid = live[0][1]
                take = min(amt, left[gid])
                left[gid] -= take
                amt -= take
                if left[gid] == 0:
                    heapq.heappop(live)
                    left.pop(gid)
            short += amt
        expire(until)
        return sum(left.values()), expired, short

book = CreditLedger()
book.grant("G1", 100, start=0, expires=10)
book.grant("G2", 50, start=2, expires=5)
book.grant("G3", 100, start=15, expires=30)
for at, amount in [(20, 100), (3, 60), (8, 70)]:         # arrives out of order
    book.debit(amount, at)
print(book.replay(until=25))                              # (0, 20, 0)
```

Replaying from the first event costs O(n log n) per query, so the total over a customer's lifetime grows with the square of its event count. Production ledgers checkpoint: they materialise per-grant balances at a watermark and replay only events after it. An event older than the watermark forces a replay from its timestamp, which is why the watermark trails real time by the lateness the system accepts, and why events later than that are handled as adjustments rather than rewrites.

## Holds for requests whose cost is unknown

A model request's cost is known only when it finishes, because output length is decided by the model. Admitting it against the balance needs a hold: an entry that reduces the available balance now and is captured at the actual cost, or released, when the request ends. The size of the hold is the policy decision.

Take scenario prices of 1 credit per input token and 5 per output token, a customer with 100,000 credits, and requests of 2,000 input tokens with `max_tokens` 8,000 whose outputs average 600 tokens. A hold at the maximum cost is 2,000 + 5 × 8,000 = 42,000 credits, so the customer can have two requests in flight. Their actual cost is 2,000 + 5 × 600 = 5,000, so the balance would cover twenty. Three policies, each with a cost:

- **Hold the maximum.** The ledger never goes negative, and customers near their limit are throttled to a fraction of what they paid for. Reasoning models with large output budgets make the gap wider.
- **Hold an estimate** such as the customer's 95th-percentile cost for that model, and allow the capture to exceed the hold. Concurrency matches real usage; the ledger can go negative by up to the in-flight overshoot, which the business either writes off or recovers from the next grant.
- **No holds, post-paid with a credit limit.** The simplest path; exposure is the credit limit plus everything in flight when it is reached.

Whichever policy wins, holds need a lifetime. A gateway that crashes between hold and capture leaves credit reserved; a hold expires after a TTL longer than the longest legitimate request, and a capture that arrives after its hold expired still posts as a debit. Captures are keyed by request id so a retried capture posts once.

Expiry under a hold needs a rule too. A request that starts at 23:59 against a grant expiring at midnight can either be allocated to that grant at hold time and honoured past expiry, or allocated at capture time against whatever is live then. The first is kinder to the customer and makes the allocation depend on start time; the second is simpler and can turn a covered request into an overage. Pick one, write it into the terms, and make replay implement the same rule.

## Refunds

A refund reverses a debit, so it must know which grants the debit drew from; store the allocation with each debit rather than recomputing it. Returning credits to a grant that has since expired is a policy choice with a precedent: when a Stripe invoice that used credits is voided, the credits go back to their grant and, if it is past its expiry, expire immediately. Stripe also notes that issuing a credit note does not restore grants; restoring them takes a new grant. A refund that silently extends an expired grant is a revenue leak that reconciliation will find months later.

## Reporting usage to billing inside its window

The ledger decides what a customer may use; the billing system decides what the customer pays for usage beyond their credits. Usage reaches billing as events, and every billing system has a correction window. Stripe's, as of the check date: a meter event's timestamp must be within the past 35 days and no more than 5 minutes in the future; acceptance does not guarantee invoicing; invoices finalise one hour after creation by default, configurable to at most 72 hours; usage reported after finalisation can appear in meter summaries but is added neither to the finalised invoice nor to the next one. Late usage is not rejected; it is unbilled, and nothing errors. Validation failures arrive asynchronously as `v1.billing.meter.error_report_triggered` events, so a pipeline that only checks the HTTP response misses them. Stripe's docs now recommend Metronome over Billing Meters for most new integrations; the constraints below are Billing Meters'.

Throughput bounds the event design. Live-mode meter event calls are limited to 1,000 per second per account and one concurrent call per customer per meter, with API v2 streams accepting 10,000 events per second. A fleet completing a scenario 3,000 requests per second cannot report one event per request on v1. Aggregating per customer per minute turns 20,000 active customers into 20,000 / 60 = 333 events per second, each with an identifier derived from customer, meter and minute, so a retried report deduplicates.

The ledger therefore closes a billing period on a schedule: at period end it stops attributing usage to the period, flushes aggregates, and must have them accepted before finalisation, which with the default grace leaves an hour minus the pipeline's own lag.

## Reconciliation

Three records describe the same usage: serving logs (tokens per request id), the ledger (debits per request id) and the billing system's meter summaries. A daily job compares them per customer and hour, and each mismatch has a known cause: a completed request with no debit is an expired hold whose capture was lost; two debits for one request id is a deduplication failure; billed usage below ledger overage is a late or rejected meter event. The job's output is adjustments, entered as new ledger entries, never edits to old ones, and an alert when an unexplained difference exceeds a stated share of revenue.

## When this is wrong

The ledger described here is per customer and assumes one writer per customer at a time. Organisations with shared pools across many API keys and regions need either a single owner per pool, which adds a cross-region hop to every admission, or per-region allotments that are rebalanced periodically, which strands credit in idle regions. Rate limits are the same problem at a shorter time scale and usually live in a separate, approximate system for that reason.

Soonest-expiring-first minimises waste for the customer, which is not always what the contract says. Some contracts require committed spend to be drawn before promotional credit, or forbid using one product's credits on another; the sort key encodes the contract, and the minimal-waste order is a default, not a rule.

Replay assumes events carry trustworthy timestamps. Clock skew across regions can reorder a debit before the grant it depends on; ledgers either stamp events at one authority or accept the skew and reconcile.
