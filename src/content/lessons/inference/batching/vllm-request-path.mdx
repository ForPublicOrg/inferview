## What it is and who runs it

vLLM is an Apache-2.0 serving engine for transformer models, developed in the open at `github.com/vllm-project/vllm`. It began as the system around the PagedAttention paper (SOSP 2023) and has been rebuilt since on the V1 architecture announced in January 2025. Anyone serving open-weight models can run it, behind an OpenAI-compatible HTTP server or as an offline Python library. This teardown describes the engine, not any operator's deployment: how a provider configures it, routes to it or patches it is not public.

Unlike most teardowns, almost everything here can be read in source. The difficulty is the rate of change: v0.30.0, v0.31.0 and v0.32.0 shipped on 22 September, 5 October and 18 October 2026. Every file reference below is to v0.32.0 at commit `5df63a7`, the latest release on 2026-10-28. Line-level behaviour can differ at any later commit.

**API server process.** The OpenAI-compatible frontend accepts the request, applies the chat template, tokenizes, preprocesses images or audio, and later detokenizes and streams tokens back. The V1 release post moved this CPU-heavy work out of the process that drives the GPU so it overlaps with the engine loop instead of stretching every step. The frontend talks to the engine core over ZeroMQ sockets.

**Scheduler.** It lives in the engine core process, whose busy loop in `vllm/v1/engine/core.py` repeats three calls: `scheduler.schedule()`, `model_executor.execute_model()`, `scheduler.update_from_output()`. `schedule()` produces a map from request id to tokens to compute this step, bounded by `max_num_batched_tokens` and `max_num_seqs`. It serves running requests first, then admits waiting ones if nothing was preempted, under a first-come-first-served or priority policy. Prompts and outputs are the same kind of token to it; a prefill is a request whose computed count lags far behind its known count.

**KV block manager.** At startup the engine reserves a share of GPU memory for the KV cache, set by `gpu_memory_utilization` (0.92 by default in v0.32.0), and carves it into a preallocated pool of blocks of 16 tokens by default. Each `KVCacheBlock` carries an id, a hash once full, a reference count and pointers into a doubly linked free queue, so moving a block to the tail of the queue is constant time. `allocate_slots()` gives a request the blocks for the tokens scheduled this step, or fails, which is when the scheduler preempts. Since `scheduler_reserve_full_isl` defaults to on, admission also checks that the request's whole input fits, not just its first chunk.

**Prefix cache.** Full blocks are indexed by a hash of the parent block's hash, the block's token ids and extra keys (LoRA id, multimodal hashes, `cache_salt`). A new request walks its prompt block by block until the first miss and takes a reference on every hit, removing unreferenced hits from the free queue. Freed blocks keep their hashes in the free queue until allocation reaches them at the head, which makes the cache an LRU over idle blocks with no separate memory budget. The design doc's name for this is automatic prefix caching; it has been on by default since V1.

**Model runner.** It turns the scheduler's output into one forward pass. V1 keeps the input tensors as a persistent batch and applies only the diff each step (requests added, removed, tokens appended), captures piecewise CUDA graphs, and compiles the model with `torch.compile`. With tensor parallelism, workers cache request state and receive only per-step diffs. Async scheduling, which overlaps the next step's scheduling with the current step's execution, is enabled by default in `vllm/config/vllm.py` unless the configuration rules it out.

**Metrics.** The engine core records timestamps for queued, scheduled, preempted and new-token events and ships them with each step's outputs; the API server computes intervals and exports Prometheus metrics. Doing the arithmetic in the frontend keeps it off the engine loop, at the cost of a rule the design doc spells out: intervals must use timestamps from one process, because monotonic clocks differ between processes.

## Context strategy

For a serving engine, context is KV cache, and vLLM manages three scopes of it. Within a request, the KV grows a block at a time and is discarded on finish or preemption; recomputation, not swapping, is the only recovery path in V1. Across requests, the prefix cache shares full blocks by hash, so a stable system prompt or a long multi-turn history is computed once while it stays resident. Across steps, chunked prefill spreads a long prompt over several steps under the token budget, and the full-input admission check stops the engine from starting prompts it cannot finish.

Nothing is persisted beyond GPU memory in the default configuration. KV connectors that offload to CPU, disk or other nodes exist but are outside this teardown. Caching decisions are exact: a one-token difference early in the prompt changes every later block hash.

## Tools and permission model

vLLM has no tools in the agent sense; its permission model is about who may call what. The security docs are blunt about the limits. `--api-key` protects only routes under `/v1`, `/v2`, `/inference` and `/cohere`. With a key set, `/invocations` still serves the same inference without authentication, operational routes such as `/pause`, `/abort_requests` and `/update_weights` stay open, and so do `/metrics`, `/tokenize` and `/health`. The docs say not to rely on the key alone.

Within one process vLLM does not isolate tenants, and the prefix cache is a timing side channel: a fast first token reveals that someone sent the same prefix. `cache_salt` limits sharing to requests with the same salt, and the docs recommend a secret random salt per user or per organisation. Traffic between nodes in a multi-node deployment (PyTorch distributed, KV transfer) is unauthenticated and unencrypted by default, and dynamic LoRA loading is not a secure operation. The intended posture is an isolated network with only the API port reachable, behind a gateway that does authentication and per-tenant limits.

## Cost and latency

Three costs dominate a step: the forward pass, CPU work around it, and waiting for it. The V1 rewrite's reported gain of up to 1.7 times over V0 came from cutting CPU overhead with nearly identical kernels, which says how much of a small model's step time used to be Python. The token budget sets the step's worst-case length, and its default depends on the GPU the engine finds: the OpenAI-compatible server uses 2,048 on A100s and smaller GPUs, 8,192 on 70 GiB and larger non-A100 GPUs, and 16,384 at 160 GiB and above. Prefix caching costs under 1% of throughput at a zero hit rate by the V1 post's measurement and saves whole prefills when it hits.

Preemption is the cost that hides. In the trace, one eviction after 400 output tokens forces 3,400 tokens of recomputation, the 3,000 uncached prompt tokens again plus the 400 it had generated. With about 100 decodes taking their share of a 2,048 budget, that is two steps of prefill (1,948 + 1,452 tokens) before token 401, delivered as a stall in the middle of a stream that had been running at one token per step.

## Failure modes

- **Preemption churn.** Admission outruns KV capacity, and requests evict and recompute each other. Signs: `vllm:kv_cache_usage_perc` near 1, `vllm:num_preemptions` rising, ITL spikes on preempted requests. Remedies in the docs: more memory for the cache, fewer concurrent sequences or a smaller budget, more parallelism; the `watermark` setting keeps headroom at admission.
- **Budget drift across hardware.** An unpinned `max_num_batched_tokens` follows the detected GPU, so the same configuration on A100s and H100s runs different latency trade-offs.
- **Silent prefix misses.** A timestamp or request id near the start of the system prompt changes every block hash after it. Hit rate falls to zero with no error; `vllm:prefix_cache_queries` and `vllm:prefix_cache_hits` are the only signal.
- **Exposed control routes.** Treating `--api-key` as the access control leaves `/invocations` and operational routes open to anyone who reaches the port.
- **Misread metrics.** A comment in `loggers.py` warns that `vllm:iteration_tokens_total` may be wrong when several API server processes share Prometheus multiprocess mode.

## What is not public

Little about the engine itself, since the source is open; the gaps are in how it behaves in anyone's production. The defaults, their reasons and their benchmarks are spread across pull requests and release notes that this teardown did not read (the A100 budget exception cites PR 17885), and the V1 post does not fully specify its benchmark configuration. No source here reports prefix-cache hit rates, preemption rates or budget settings from a real deployment. And any excerpt is only true at its commit: scheduler settings such as `scheduler_reserve_full_isl` and `long_prefill_token_threshold_adaptive` are recent, and the next release may rename or change them.

<Fragment slot="short">
<p>TTFT is queue time plus the prefill steps, and the metrics split them. If queue time grew, admission changed: <code>max_num_seqs</code>, the full-input admission check or a watermark. If prefill time grew, the budget or the prefix cache changed: a different default budget for the GPU, or a hash change that dropped the hit rate. Diff the effective configuration the two versions log at startup before reading any code.</p>
</Fragment>
<Fragment slot="long">
<p>I would start from the request path. A request queues in the waiting queue, gets a prefix lookup on admission, runs its uncached prompt in chunks under the budget alongside decodes, then samples its first token. Each part has its own metric: <code>vllm:request_queue_time_seconds</code>, <code>vllm:request_prefill_time_seconds</code>, prefix-cache queries and hits, and tokens per step.</p>
<p>If queue time doubled at flat throughput, the engine is admitting differently. A full-input admission check that the old version lacked, a lower <code>max_num_seqs</code> default, or a watermark would all hold requests in the queue that used to start and then preempt. That trade may be intended: fewer preemptions, better ITL, worse TTFT.</p>
<p>If prefill time doubled, look at the budget first, since its default follows the GPU and can change between versions, and at the hit rate, since a hash or template change makes every system prompt a miss and multiplies prefill work at unchanged throughput. Then check preemptions during prefill, which the metrics assign to TTFT.</p>
<p>The fix is to pin the settings that encode our latency policy, not to roll back by reflex, and to add a startup check that fails the deploy when the effective budget, sequence cap or prefix-caching state differs from the pinned values.</p>
