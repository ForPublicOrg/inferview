## The allocation problem continuous batching created

Once requests join and leave every step, the KV cache becomes a heap with thousands of allocations whose final size is unknown at allocation time. Before vLLM, serving systems stored each request's KV cache in one contiguous region sized for the longest output it might produce. The PagedAttention paper (SOSP 2023) breaks the resulting waste into three parts: slots reserved for tokens not generated yet, internal fragmentation from over-provisioning for the maximum length, and external fragmentation from the allocator between regions. Profiling Orca-style allocation, it found that only 20.4% to 38.2% of KV memory held actual token states. vLLM's paged layout reached 96.3% in the same experiment.

The sizes make the waste expensive. The paper computes OPT-13B's KV cache at 2 (key and value) × 5,120 (hidden size) × 40 (layers) × 2 bytes = 819,200 bytes, about 800 KB, per token. Models with grouped-query attention store far less: Llama 3 70B has 80 layers and 8 KV heads of dimension 128 (8,192 / 64), so one token costs 2 × 80 × 8 × 128 × 2 = 327,680 bytes in BF16, and Llama 3 8B costs 2 × 32 × 8 × 128 × 2 = 131,072. Either way, the batch size of a decode-bound server is set by how many tokens of KV fit, and every wasted slot is a request that could not be admitted.

## Blocks and block tables

PagedAttention applies the page table idea. The KV cache is divided into fixed-size blocks, each holding the keys and values of a fixed number of tokens (16 by default in vLLM). Each sequence has a block table that maps its logical blocks, filled left to right, to physical blocks anywhere in GPU memory, with a count of filled slots per entry. A new physical block is allocated only when the last one is full, so a sequence wastes at most one partially filled block, and a finished sequence returns whole blocks that any other sequence can use. External fragmentation disappears because every allocation is the same size.

The difference from an operating system's pages is who reads them. The attention kernel itself walks the block table, so the indirection sits inside the hottest kernel in the model. The paper measures 20% to 26% higher attention kernel latency than FasterTransformer's contiguous kernel, and wins end to end anyway because the batch grows: on OPT-13B it holds 2.2 times as many requests concurrently as Orca (Oracle), a baseline that is told each request's true output length in advance.

<p>1,300 tokens / 16 = 81.25, so the request holds <b>82 blocks</b> (1,312 slots) and wastes 12 slots in its last block. A contiguous scheme that reserved the 2,048-token maximum up front would hold 748 slots that no token has used, and would have held them since the request was admitted.</p>

The headline result is 2 to 4 times the throughput of FasterTransformer and Orca at the same latency. On the ShareGPT trace the paper reports 1.7 to 2.7 times the request rate of Orca (Oracle), 2.7 to 8 times that of Orca (Max), which reserves the full 2,048 tokens, and up to 22 times that of FasterTransformer. The gains are larger for longer sequences, because that is where reservation and fragmentation waste the most.

## Block size

Block size trades kernel efficiency against fragmentation and sharing. Small blocks give the kernel less contiguous data per read and leave GPU parallelism unused; large blocks waste more slots in each sequence's last block and match fewer shared prefixes, because sharing works in whole blocks. The paper's ablation found block sizes from 16 to 128 best on ShareGPT, while on Alpaca's shorter sequences only 16 and 32 did well and larger blocks degraded throughput. vLLM chose 16, and `vllm/config/cache.py` still defaults to 16 when no size is given in v0.32.0. The same file carries separate fields for the attention block size, the hash block size and a Mamba block size, so on hybrid models or some attention backends the effective size can differ; read the value the engine logs at startup.

## Sharing by reference count

Because the table is an indirection, two sequences can point at the same physical block. The paper uses this for parallel sampling and beam search. All samples of one prompt map their prompt blocks to the same physical blocks, each block carries a reference count, and a write to a block whose count is above one triggers copy-on-write of that block only. Beam search shares more, because candidates share whole histories and the sharing pattern changes as beams are pruned; blocks whose count reaches zero are freed. The paper measures memory savings of 6.1% to 9.8% for parallel sampling and 37.6% to 55.2% for beam search on Alpaca, and 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT, where prompts are longer.

<Predict id="inf-paged-cow" question="Block size 16. Four parallel samples share a 1,000-token prompt. After each sample writes its first generated token, how many physical blocks are in use?" answer={66} tolerance={0} unit="blocks">
<p>1,000 = 62 × 16 + 8, so the prompt fills 62 blocks and 8 slots of a 63rd. The 62 full blocks stay shared. Each sample's first token lands in the shared partial block: the first three writers each copy it to a new block, and the fourth finds the reference count back at 1 and writes in place. That is 62 + 4 = <b>66 blocks</b>, against 4 × 63 = 252 without sharing.</p>
</Predict>

The allocator behind both predictions is short. This is the part the paged design makes simple; the policy questions (who gets preempted, when to admit) live in the scheduler.

```python
BLOCK = 16

class PagedKV:
    def __init__(self, num_blocks):
        self.free = list(range(num_blocks))
        self.refs = [0] * num_blocks
        self.table = {}    # seq id -> physical block ids, in logical order
        self.length = {}   # seq id -> tokens written

    def _take(self):
        if not self.free:
            raise MemoryError("out of KV blocks: preempt a sequence")
        b = self.free.pop()
        self.refs[b] = 1
        return b

    def append(self, seq, copy=lambda src, dst: None):
        n = self.length.get(seq, 0)
        blocks = self.table.setdefault(seq, [])
        if n % BLOCK == 0:                    # last block full, or first token
            blocks.append(self._take())
        elif self.refs[blocks[-1]] > 1:       # shared partial block: copy on write
            new = self._take()
            copy(blocks[-1], new)
            self.refs[blocks[-1]] -= 1
            blocks[-1] = new
        self.length[seq] = n + 1

    def fork(self, parent, child):            # parallel sampling: share every block
        self.table[child] = list(self.table[parent])
        self.length[child] = self.length[parent]
        for b in self.table[child]:
            self.refs[b] += 1

    def release(self, seq):                    # finish or preempt: all or nothing
        for b in self.table.pop(seq):
            self.refs[b] -= 1
            if self.refs[b] == 0:
                self.free.append(b)
        del self.length[seq]

kv = PagedKV(num_blocks=300)
for _ in range(1000):                          # a 1,000-token prompt
    kv.append("s0")
for i in range(1, 4):
    kv.fork("s0", f"s{i}")                     # four samples of one prompt
for i in range(4):
    kv.append(f"s{i}")                         # each sample writes its first token
print("blocks in use:", 300 - len(kv.free))    # 66, against 4 x 63 = 252 unshared
```

A real engine writes a whole step's tokens per sequence at once and allocates before the forward pass, not per token; [problem inf-006](/problems/inf-006) asks for that version with invariant tests.

## Prefix caching: sharing across requests by hash

Sharing inside one request needs no lookup, because the fork knows its parent. Sharing across requests needs a way to find a block that already holds the same prefix. vLLM's automatic prefix caching gives every full block a hash of its parent block's hash, its own token ids, and extra keys that change the KV contents or must isolate it: the LoRA adapter id, multimodal input hashes, and an optional per-request `cache_salt`. Chaining the parent hash makes a block's hash identify the entire prefix up to and including that block, so a lookup walks the new prompt's blocks in order until the first miss.

The design doc spells out the rules that decide hit rates in practice:

- Only full blocks are cached. In the doc's example with block size 4, a second request whose first 10 tokens match the first request hits only 8 of them, because the third block matches in 2 positions out of 4.
- A finished request's blocks are not erased. Blocks whose reference count reaches zero go to the tail of a free queue with their hashes intact, in reverse order so a sequence's last block (the least likely to be reused) is evicted first. Allocation takes from the head, which makes eviction least recently used.
- A full hit still computes something. `kv_cache_manager.py` caps the hit at the prompt length minus one so the model produces logits for the last token, and because allocation is block-aligned, that can mean recomputing a whole block.
- The default hash is SHA-256 over pickled data, which the doc says may not be reproducible across Python or vLLM versions; `sha256_cbor` exists for reproducible hashes. The `cache_salt` exists because a shared cache leaks timing: a fast first token reveals that someone else sent the same prefix.

V1 turned prefix caching on by default, and its release post reports less than 1% throughput loss at a 0% hit rate. The faster-cheaper module covers when prefix caching pays and how to shape prompts for it.

## When blocks run out: preemption

Paging makes running out of memory a scheduling event instead of an out-of-memory error. When a running sequence needs a block and none is free, the engine evicts a whole sequence. The paper argues for all-or-nothing eviction because every block of a sequence is read at every step, so evicting part of one only guarantees it stalls; sequences in one request, like beams, are gang-scheduled for the same reason. The paper's policy is first come, first served, preempting the latest arrivals first.

An evicted sequence can come back two ways. Swapping copies its blocks to CPU memory and back. Recomputation drops them and, on readmission, runs the prompt and the tokens generated so far as one new prompt, which a single prefill handles efficiently. The paper measured that swapping suffers at small block sizes, where many small PCIe transfers waste bandwidth, while recomputation's cost does not depend on block size; recomputation was never more than 20% slower than swapping, and the two were comparable end to end for block sizes 16 to 64.

vLLM V1 recomputes by default, and the optimization docs give the reason as lower overhead in the V1 architecture. The `--swap-space` flag is gone and the swap metrics no longer apply. In v0.32.0, `_preempt_request` frees the victim's blocks, sets its computed-token count to zero and puts it at the front of the waiting queue. With prefix caching on, the victim's full blocks sit in the free queue with their hashes until something evicts them, so a request readmitted soon after preemption can find part of its own prefix still cached.

<Callout kind="gotcha">
Preemption is invisible in request errors and very visible in latency. A sequence preempted during decode recomputes its whole context before it emits another token, and the metrics design doc assigns that time to inter-token latency, not TTFT. A rising `vllm:num_preemptions` next to a rising p99 ITL usually means admission is outrunning memory.
</Callout>

## When this is wrong

The paper's multiples are 2023 numbers against Orca-style contiguous allocation, which no production engine uses any more. Today every serious engine pages its KV cache, so the comparison that matters is between paged engines with different block sizes, kernels and eviction policies, and the paper's numbers do not answer it.

Sharing is exact and block-granular. Prefix caching hits only on identical token ids in whole blocks with identical extra keys; a timestamp in the system prompt, a different LoRA adapter or a different tokenizer version produces zero hits with no error. The block size also caps how much of a short shared prefix can ever be reused.

The one-table-per-sequence picture is a simplification for hybrid models. Models that mix full attention with sliding-window attention or state-space layers keep different kinds of state per layer group, which is why v0.32.0 carries a hybrid KV cache manager and a separate Mamba block size. The byte counts above assume BF16 KV with no compression; quantized or compressed KV changes every capacity number in this lesson.
