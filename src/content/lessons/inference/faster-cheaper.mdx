## Six levers and one budget

Scenario, not a real company: you have been asked to halve the serving cost of a 70B model without users noticing. Someone sends a list: quantize to 4 bits, turn on speculative decoding, enable prefix caching, split prefill and decode, add more GPUs with tensor parallelism, route easy requests to a small model. Every item is real. Several of them make things worse in the wrong conditions, and the interview question is always which one, and why.

The previous two lessons give a cost model for one decode step: bytes read (weights plus KV cache) divided by bandwidth, shared across the batch. Each lever attacks one term.

- Quantization shrinks the bytes per weight and per cached token.
- Speculative decoding produces more than one token per expensive pass.
- Prefix caching skips prefill work that was already done.
- Disaggregation stops prefill and decode from interfering.
- Parallelism adds bandwidth and memory, and adds communication.
- Routing and distillation send work to a smaller model.

## Quantization: fewer bytes per weight

Decode reads every weight each step, so halving the bytes per weight roughly halves the bandwidth floor. For a 70B-class model the weight memory by format is a multiplication:

The fractional numbers are the scales. Q8_0 stores one 16-bit scale per 32 int8 weights, so 8 + 16 / 32 = 8.5 bits. A "4-bit" model is never exactly 4 bits once you count its metadata.

The methods differ in how they choose the rounded values. **GPTQ** quantizes weights one shot after training using approximate second-order information, to 3 or 4 bits; it quantized a 175B model in about four GPU hours and reports about 3.25 times faster inference on an A100 than FP16. **AWQ** observes that a small fraction of weights matter far more than the rest: protecting 1% of salient weights, chosen from activation statistics rather than weight magnitudes, greatly reduces the error. **FP8** keeps a floating-point format with two encodings, E4M3 (more precision) and E5M2 (more range), and Hopper-class GPUs run FP8 matrix multiplies natively, so prefill gets faster too, not just decode. **GGUF** is a file format from the llama.cpp project that carries tensors and metadata; Q4_K and friends are the quantization types stored in it, not the format itself.

Four-bit floating point is now a shipping format rather than a research one. **MXFP4** (microscaling FP4, listed in the Hugging Face GGUF type table as "4-bit Microscaling Block Floating Point") stores 32 four-bit values with one shared 8-bit power-of-two scale, so 4 + 8 / 32 = 4.25 bits per weight in llama.cpp's block definition. gpt-oss-120b ships in it: its config.json sets `quant_method` to `mxfp4` and leaves attention, the router, embeddings and the LM head unconverted. **NVFP4** uses smaller blocks, one 8-bit unsigned E4M3 (UE4M3) scale per 16 four-bit E2M1 values, which is 4.5 bits per weight in llama.cpp's layout; the finer scales track outliers more closely. Blackwell runs FP4 on its tensor cores: NVIDIA's DGX B200 page lists FP4 throughput at twice the FP8 figure. vLLM v0.32.0 (18 Oct) extends its NVFP4 KV cache to more GPU generations, so the cache, not only the weights, can drop to 4 bits.

The KV cache can be quantized separately. vLLM supports `fp8_e4m3` and `fp8_e5m2` KV caches, which halve cache bytes against BF16 and so roughly double the tokens that fit. Its docs warn that scales default to 1.0 without calibration and that sliding-window layers are more sensitive to KV quantization.

<Callout kind="gotcha">
No general "INT4 costs N points of accuracy" number survives contact with a specific model and task. Quantization error concentrates in outliers, long reasoning chains and some languages. Measure on your own evaluation set, including the slices you care about most, before and after.
</Callout>

## Speculative decoding: more tokens per expensive pass

A decode step at small batch leaves the arithmetic units mostly idle. Speculative decoding spends that idle compute. A cheap **draft** proposes several tokens; the large **target** model checks all of them in a single forward pass, which costs about the same as generating one token because the pass is bandwidth bound anyway. Accepted tokens are kept; at the first rejection the target supplies a corrected token and the rest are thrown away.

The correctness argument is what interviewers probe. For a draft token x proposed with draft probability q(x), the target accepts it with probability min(1, p(x) / q(x)). On rejection it samples from the normalised residual max(0, p - q). Leviathan et al. and Chen et al. show that the output then follows the target distribution exactly, up to hardware numerics. You trade compute for latency without changing what the model says. Medusa's "typical acceptance" and other lossy schemes relax this on purpose, so check which verification your engine uses.

The widget uses the paper's Theorem 3.8: speedup = expected tokens / (gamma x c + 1), where c is the cost of one draft step relative to one target pass. Drag gamma to 12 at alpha 0.8 and c 0.1: you pay for 12 draft steps and gain little, because the 9th draft token is accepted only if the first 8 were. The best draft length is short when acceptance is low or drafts are expensive.

Where the draft comes from has changed quickly. A separate small model is the original design. **EAGLE** predicts at the feature level from the target's own hidden states, and **EAGLE-3** (2025) predicts tokens directly from fused features of several layers, reporting up to 6.5 times speedup. Some models ship **multi-token prediction** heads that serve as a built-in draft. **N-gram** and suffix methods need no model at all and work well when the output repeats the input, as in code edits. SGLang's docs report LLaMA-Instruct 3.1 8B on one H100 going from 158.34 tokens per second to 244.10 with EAGLE-2 and 373.25 with EAGLE-3 on MT-Bench, which is 1.54 and 2.36 times.

The trap is batch size. Verification costs gamma + 1 tokens of compute per sequence. At small batch that compute was idle. At large batch with short contexts the step is already near compute bound, and rejected draft tokens become real wasted work, so throughput can fall. MagicDec complicates the easy answer: at moderate to long contexts the KV reads keep even large batches bandwidth bound, and it reports gains up to 2.51 times for Llama3.1-8B at batch 32 to 256. The honest answer is conditional on where the step sits on the roofline.

```python
import random

def speculative_sample(p, q, rng):
    """Draft one token from q, verify against target p. Output is distributed as p."""
    vocab = range(len(p))
    x = rng.choices(vocab, weights=q)[0]
    if rng.random() < min(1.0, p[x] / q[x]):
        return x                                          # accept the draft
    residual = [max(0.0, pi - qi) for pi, qi in zip(p, q)]
    return rng.choices(vocab, weights=residual)[0]        # resample from norm(max(0, p - q))

rng = random.Random(42)
p, q = [0.5, 0.3, 0.2, 0.0], [0.25, 0.25, 0.25, 0.25]
draws = [speculative_sample(p, q, rng) for _ in range(200_000)]
print([round(draws.count(i) / len(draws), 3) for i in range(4)])   # about [0.5, 0.3, 0.2, 0.0]
```

Here the acceptance rate is the overlap of the two distributions, the sum of min(p, q) = 0.25 + 0.25 + 0.2 = 0.7. A draft that agrees with the target more often gets accepted more often; that is the whole design space.

## Prefix caching: skip work you already did

Many requests share a prefix: the system prompt, tool definitions, a long document, the earlier turns of the same conversation. With paged KV blocks, a server can keep the blocks for a prefix after the request ends and reuse them when the next request starts with the same tokens.

vLLM's automatic prefix caching hashes each **full** block from its parent block's hash plus its own tokens (plus extra keys such as a LoRA id). Because the parent hash is part of the key, a block matches only if every token before it matched too. A trailing partial block is not cached. Unused blocks are evicted least recently used first. SGLang's **RadixAttention** keeps prompts and outputs in a radix tree, which makes "longest shared prefix" a tree lookup and lets the scheduler order requests to maximise hits. The V1 release blog reports prefix caching costs under 1% of throughput even at a 0% hit rate, which is why it is on by default.

The practical rule: put stable content first and variable content last. A timestamp, a request id or the user's name at the top of the system prompt changes the first block, so every later block hashes differently and nothing is reused. Layers such as LMCache extend the idea by offloading KV blocks to CPU memory and storage and sharing them across engine instances.

## Disaggregation: separate the two workloads

Prefill wants compute; decode wants bandwidth and steady latency. Running both on the same GPUs means a burst of prefills makes every streaming user stutter. **Disaggregated serving** runs them on separate pools and ships the KV cache from the prefill pool to the decode pool over a fast interconnect.

DistServe reports serving 7.4 times more requests, or meeting a 12.6 times tighter objective, while keeping latency within target for over 90% of requests. Splitwise reports 1.4 times the throughput at 20% lower cost, or 2.35 times at the same cost and power. vLLM's docs are blunt in the other direction: "Disaggregated prefill DOES NOT improve throughput"; the reasons to use it are tuning TTFT and ITL separately and controlling tail ITL. Both are true: the papers measure goodput under latency targets, and vLLM is talking about raw throughput. Production stacks built around the idea include NVIDIA Dynamo (with a KV-aware router and the NIXL transfer library) and llm-d on Kubernetes. The price is a KV transfer per request and two pools to size.

## Parallelism: more memory and bandwidth, more communication

When the model does not fit on one GPU, split it. **Tensor parallelism** (TP), from Megatron-LM, splits each layer's matrices across GPUs and combines results with collective operations on every layer, so it needs the fast links inside one server. Each GPU reads only its share of the weights per step, which is why TP also lowers per-token latency. **Pipeline parallelism** (PP) puts different layers on different GPUs; communication happens only between stages, so it tolerates slower links across nodes, at the cost of pipeline bubbles and added latency. vLLM's guidance: use TP when the model is too large for one GPU, and PP when TP is maxed out or across nodes. **Expert parallelism** places different experts of a mixture-of-experts model on different GPUs and routes tokens to them.

## Routing and distillation: a smaller model when it is enough

The cheapest token is one a small model produces. A **cascade** tries a small model first and escalates when a checker rejects its answer; FrugalGPT reports matching the best single model with up to 98% cost reduction on its benchmarks. **Learned routers** predict up front which model a request needs; RouteLLM reports more than 2 times cost reduction in some cases without quality loss. **Distillation** trains a small model on a large one's outputs for a narrow task. All three need an evaluation set to prove quality held, which is a theme of the evals track.

<p>Mechanics: a draft proposes gamma tokens; the target scores all of them in one forward pass. For each position in order, accept with probability min(1, p(x)/q(x)). At the first rejection, sample a replacement from max(0, p - q) renormalised and discard the rest. If all are accepted, sample one bonus token from the target. <p>Speed: expected tokens per pass is (1 - alpha^(gamma+1)) / (1 - alpha), capped at 1/(1 - alpha), while draft cost grows linearly in gamma. At alpha 0.8 and a draft costing 5% of the target, the paper's formula gives about 2.8 times at gamma 4.</p>
<p>When it hurts: the target pass is cheap only while it is bandwidth bound. ## When this is wrong

The step model in this lesson treats each lever in isolation. They interact. Quantizing weights to 4 bits leaves less idle compute for speculation to use, because the bandwidth floor dropped. Prefix caching shrinks prefill, which reduces the interference that disaggregation fixes. Tensor parallelism lowers per-GPU bytes but adds a collective per layer that the bandwidth model ignores. Change one lever at a time and measure goodput, not throughput alone.

Most speedups quoted here are from the authors of the method, on their hardware and their workloads. They tell you the mechanism works; they do not tell you what you will get. A 2 to 3 times gain on a single A100 demo can be zero on a busy H100 at batch 128.

And the cheapest optimization is often not on this list: shorter prompts, fewer output tokens, and not calling the model at all when a cache or a rule answers the question. The next lesson covers the gateway layer where those decisions live.
