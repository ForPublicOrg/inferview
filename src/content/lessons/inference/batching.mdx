## The batch that waited for one essay

Scenario, not a real company: an internal summarisation service collects requests into groups of 16, runs each group on the GPU, and returns the results together. Most summaries are a few dozen tokens. Now and then someone asks for a 400-token report. Whenever that happens, 15 slots finish early and sit idle until the long one is done, and the 16 requests waiting in the queue cannot start because the batch is still "running".

The previous lesson showed why batching matters: every decode step reads all the weights, so sharing that read across more sequences is the cheapest throughput you will ever buy. This lesson is about doing it without the convoy.

## Static versus continuous batching

Static batching works like a barrier in a parallel program. A batch starts together and ends together, so its run time is the run time of its slowest member. In text generation the members differ wildly, because nobody knows the output length in advance.

Continuous batching, which the Orca paper (OSDI 2022) called **iteration-level scheduling**, moves the scheduling decision from the request to the decode step. After every step the scheduler removes finished sequences and admits waiting ones into the freed slots. If you have written a worker pool that pulls the next job the moment a worker is free, you already know the idea. The engineering problem is that the "workers" share one GPU kernel launch per step, so the batch changes shape on every iteration.

Anyscale reports up to 23 times when continuous batching is combined with vLLM's memory management, and credits about 8 times to continuous batching alone over naive batching. Both depend on the workload and the baseline, so quote them with their conditions or not at all.

## PagedAttention: virtual memory for the KV cache

Continuous batching creates a memory problem. Before vLLM, servers typically reserved a contiguous KV buffer per request sized for the maximum possible output, because the final length is unknown. A request that stops after 40 tokens still held space for 2,048. The vLLM paper measured that in existing systems "only 20.4% - 38.2% of the KV cache memory is used to store the actual token states". The rest was reserved-but-unused space and fragmentation.

PagedAttention borrows the operating system's answer. The KV cache is cut into fixed-size **blocks** (16 tokens by default in vLLM). Each request has a **block table** mapping its logical blocks to physical blocks anywhere in GPU memory, exactly like a page table maps virtual pages to physical frames. A request takes a new block only when its last one fills, so the only waste is the unfilled tail of the final block. The vLLM launch blog puts that under 4%.

Two consequences matter in interviews:

- **More sequences fit**, so the batch grows, so throughput rises. That is where vLLM's headline gains come from: the paper reports 2 to 4 times the throughput of FasterTransformer and Orca at the same latency. The blog's "up to 24x" is against Hugging Face Transformers, a different baseline.
- **Blocks can be shared.** Parallel samples from one prompt can point at the same prompt blocks, with copy-on-write when one of them diverges. The blog reports up to 55% less memory for parallel sampling and beam search. The same mechanism makes prefix caching possible, covered in the next lesson.

PagedAttention is a memory layout and an allocator, not a faster attention formula. The attention kernel now reads keys and values from non-contiguous blocks through the table, which is extra indirection the kernel authors had to make cheap.

```python
BLOCK = 16   # tokens per block, vLLM's default

class BlockAllocator:
    def __init__(self, num_blocks):
        self.free = list(range(num_blocks))
        self.tables = {}      # request id -> physical block ids
        self.lengths = {}

    def append_token(self, rid):
        n = self.lengths.get(rid, 0)
        if n % BLOCK == 0:                     # first token, or the last block is full
            if not self.free:
                raise MemoryError("no free KV blocks: preempt or queue")
            self.tables.setdefault(rid, []).append(self.free.pop())
        self.lengths[rid] = n + 1

    def release(self, rid):
        self.free.extend(self.tables.pop(rid))
        del self.lengths[rid]

def paged_waste(token_counts):
    slots = sum(-(-t // BLOCK) * BLOCK for t in token_counts)   # round each up to whole blocks
    return 1 - sum(token_counts) / slots

print(f"{paged_waste([37, 410, 1203, 95, 2000]):.1%}")   # 0.8% for these five lengths
```

Reserving 2,048 slots for each of those same five requests would waste 63% of the space, which is how the old approach lost most of its memory.

## Chunked prefill and head-of-line blocking

Continuous batching mixes prefill and decode in the same step. That creates a new failure. A 30,000-token prompt arrives; its prefill takes far longer than a decode step; and every user currently streaming a reply sees their next token stall until that prefill finishes. It is head-of-line blocking, the same thing that happens when one large message blocks a TCP connection carrying small ones.

**Chunked prefill** splits a long prefill into pieces and runs one piece per step alongside the ongoing decodes. Sarathi-Serve calls this stall-free scheduling: decodes never wait for a whole prefill. It reports 2.6 times the serving capacity of vLLM at the time for Mistral-7B on one A100, and up to 3.7 times for Yi-34B on two A100s, under its latency targets.

The knob is the token budget per step. In vLLM it is `max_num_batched_tokens`. The optimization docs say a smaller budget (they give 2048 as an example) gives better inter-token latency because fewer prefill tokens interfere with decodes, a larger one gives better TTFT, and more than 8192 is suggested for throughput. Chunked prefill is on by default in current vLLM "whenever possible".

<Callout kind="gotcha">
Chunking does not make the prefill cheaper. The long prompt still needs all its FLOPs; they are spread across more steps, so its own TTFT gets slightly worse while everyone else's ITL gets better. That is the trade you are choosing when you lower the budget.
</Callout>

## Scheduling, preemption and fairness

vLLM V1 (alpha announced January 2025) folds all of this into one scheduler. Each step is expressed as a mapping from request id to the number of tokens to process for it: a whole prompt, a chunk of a prompt, one decode token, or several when speculative decoding proposes extra tokens. There is no separate prefill phase and decode phase in the scheduler any more. The release blog reports 1.7 times the throughput of the V0 engine.

When the cache runs out of blocks mid-flight, something has to give. The scheduler **preempts** a running request, frees its blocks, and puts it back in the queue. Older vLLM could swap the blocks to CPU memory; the V1 guide says V1 "no longer requires KV cache swapping", and the optimization docs say the default preemption mode is `RECOMPUTE`: the request's cache is rebuilt by re-running its prefill when it is readmitted. Preemptions show up as `vllm:num_preemptions`, and a rising count is a sign that you admitted more concurrency than memory can hold.

Fairness is a policy choice layered on top. First come, first served is the default and is easy to reason about. Priority classes let paid or interactive traffic jump the queue, at the cost of starving batch traffic unless you add aging. Preempting the newest request first wastes the least recompute. Shortest-job-first would minimise average latency, but output length is unknown in advance, so it only works with a length predictor you trust.

## When this is wrong

The simulator charges every step the same cost and gives every running request one token per step. On real hardware a step with 64 sequences takes longer than one with 4, as the previous lesson showed, so slot utilisation overstates the throughput gain. Treat it as a picture of idle slots, not a benchmark.

Continuous batching helps in proportion to how much output lengths vary. For an embedding or classification workload where every request is one forward pass, there is no decode loop and static batches of similar-length inputs are fine.

Finally, the specific defaults in this lesson (block size, budget, preemption mode) belong to vLLM as of the release checked, v0.32.0. SGLang, TensorRT-LLM and Hugging Face TGI make different choices, and vLLM itself changed the preemption default between V0 and V1. Read the docs of the engine and version you run.
