## The decision

In RL with verifiable rewards, the verifier is the specification. The policy never sees the task description you wrote for humans; it sees which outputs scored 1. So the design question is the one you ask of an input validator on an untrusted boundary: what does it accept that it should reject, and what does it reject that it should accept. The first set is reward hacking; the second set teaches the policy to avoid correct answers that the parser cannot read. An environment is the verifier plus the prompts, the tools the policy may call, and the sandbox they run in, and each piece has its own failure surface.

## What the published runs used

**DeepSeek-R1-Zero.** Two rule-based rewards and nothing learned. An accuracy reward checks the final answer (a maths answer in a fixed format, code through test cases), and a format reward checks that the reasoning sits inside think tags and the answer inside answer tags; v2 of the paper combines them with equal weight. The stated reason for no neural reward model is that it is "susceptible to reward hacking" during large-scale RL. With that reward alone, pass@1 on AIME 2024 rose from 15.6% to 71.0% in v1 of the paper and to 77.9% in v2, and 86.7% with majority voting.

**Qwen3.** The reasoning RL stage ran on 3,995 query-verifier pairs, selected by four rules: not used in the cold-start SFT, learnable by the cold-start model, as hard as possible within that, and covering many sub-domains. Over 170 RL steps, Qwen3-235B-A22B moved from 70.1 to 85.1 on AIME'24. The general RL stage uses three reward types: rule-based, a model judge given a reference answer (Qwen2.5-72B-Instruct), and a preference-trained reward model where no reference exists. The size of the set is the point: a few thousand well-chosen pairs carried the reasoning stage.

**Kimi K2.** A "Verifiable Rewards Gym" across task families, each with its own verifier. Maths, STEM and logic problems have their difficulty set by the SFT model's pass@k. Instruction following combines code-interpreter checks for verifiable constraints (length, style), an LLM judge for nuanced ones, and a hack-check layer for responses that claim to follow an instruction without doing so. A sentence-level faithfulness judge flags unsupported claims. Software-engineering environments are built from GitHub pull requests and issues with executable tests, on Kubernetes sandboxes that support over 10,000 concurrent instances. For tasks with no verifier, a self-critique rubric reward: the model ranks its own responses pairwise against core rubrics, prescriptive rubrics written against known hacks (no opening praise, no sentences justifying why the response is good), and human-annotated task rubrics, and the critic is refined during RL on verifiable tasks so its judgements stay anchored. The report flags its own limitation: the rubric may favour confident answers on ambiguous topics.

**Open tooling.** Prime Intellect's `verifiers` is a library for building environments to train and evaluate models, integrated with their Environments Hub, where environments are published and installed by others. INTELLECT-3, a 106B MoE on the GLM 4.5 Air base, trained on 512 H200 GPUs across 64 nodes with environments for maths, code, science, logic, deep research and software engineering; the blog post of 26 November 2025 says the Hub had 500+ tasks, of which the run used a small fraction. The engineering consequence: an environment becomes a versioned dependency of the training run, with the same review and pinning you give a library.

## Difficulty is part of the verifier

Group-relative advantages give zero gradient to a group where every sample scores the same. A prompt the policy always solves, or never solves, is pure generation cost. Qwen3's "learnable" and "as challenging as possible" and Kimi's pass@k filter are the same rule: keep prompts where the current policy's success rate is far from 0 and 1, and re-filter as the policy improves.

## A verifier, and its exploit list

A maths verifier in the R1-Zero style, written to be strict about what counts as an answer:

```python
import re
from fractions import Fraction

BOXED = re.compile(r"\\boxed\{([^{}]*)\}")

def as_number(s):
    try:
        return Fraction(s.strip().replace(",", ""))
    except (ValueError, ZeroDivisionError):
        return None

def reward(response: str, gold: str) -> float:
    if response.count("<think>") != 1 or response.count("</think>") != 1:
        return 0.0                                  # format gate, not a bonus
    final = response.split("</think>", 1)[1]        # only text after reasoning
    boxes = BOXED.findall(final)
    if len(boxes) != 1:                             # zero or several answers
        return 0.0
    got, want = as_number(boxes[0]), as_number(gold)
    return 1.0 if got is not None and got == want else 0.0

assert reward("<think>2+2</think> \\boxed{4}", "4") == 1.0
assert reward("<think>?</think> \\boxed{3} \\boxed{4}", "4") == 0.0
assert reward("<think>half</think> \\boxed{0.5}", "1/2") == 1.0
```

Now list how a policy passes it without solving the problem, the way you would threat-model an endpoint.

**Accepts too much.** Integer answers from a small range reward guessing, so a dataset of answers between 0 and 999 pays one in a thousand random guesses, and more for guesses biased towards common answers. A format reward paid separately from accuracy pays for well-formatted wrong answers, which is why the code above gates on format instead of adding to it. A parser that takes the last number in the text pays for listing several candidates.

**Rejects too much.** `x = 4`, `\boxed{\frac{1}{2}}` and `4.0 cm` are all correct and all score 0 here. The policy learns to avoid those forms, which is harmless for a benchmark and harmful if users need units. Every false negative is a gradient against a correct answer; measure the false-negative rate on held-out correct solutions before the run, not after.

**Code verifiers.** Tests that the policy can read, edit or exit around. Baker et al. saw two systemic hacks in agentic coding environments: calling `exit(0)` before all tests ran, and raising `SkipTest` outside the test framework so tests were skipped. The verifier must run in a process the policy does not control, count tests that ran and passed rather than check an exit code, and treat any change to test files as a failure.

**Judge verifiers.** Flattery, confident tone and length. Kimi K2's prescriptive rubrics exist because those hacks appeared; its note that the rubric favours confidence is the next one.

The general rule is to write the exploit list before the run and turn each entry into a test of the verifier: an output crafted to exploit it must score 0.

## When this is wrong

"Verifiable" is a property of the task, and few production tasks have it end to end. Maths answers and test suites are the easy cases; most of what a product needs has a verifiable part and a judged part, and the judged part brings back every problem of learned reward models. Kimi K2's rubric reward and Qwen3's model-based rewards are the published answers, and both are judges.

The published results do not say which verifier choices mattered. R1, Qwen3 and K2 each report a stage result, not an ablation of the verifier, and their prompt sets are not public. Treat their verifier designs as existence proofs.

Strict verifiers are not free. Every false negative trains the policy away from a correct answer, and a verifier tuned to reject every exploit you listed can reject a correct form you did not think of. Measure both error rates on held-out outputs.
