## Redundancy is the cost of plain data parallelism

Plain data parallelism replicates everything: N GPUs hold N identical copies of 16 bytes per parameter, and each step ends with an all-reduce of the gradients. The bandwidth bill is 2 Psi bytes per GPU per step in the ring model (Psi is the parameter count, and BF16 gradients make Psi elements 2Psi bytes; this lesson follows the ZeRO paper and counts in elements). The memory bill is what makes it stop working: a model whose 16 bytes per parameter exceed one GPU cannot use it at all.

ZeRO removes the redundancy in three cumulative stages, each defined by what one data-parallel rank stops holding in full.

## Three stages, and what each one sends

**ZeRO-1 shards the optimizer states.** Each rank keeps the FP32 master weights and Adam moments for 1/N of the parameters. The step becomes: reduce-scatter the gradients so each rank holds the summed gradient for its slice, update its slice, then all-gather the updated BF16 parameters. Reduce-scatter plus all-gather is exactly an all-reduce's traffic, so ZeRO-1 costs nothing extra in bytes.

**ZeRO-2 also shards the gradients.** Since each rank only updates its own slice, it never needs the rest of the summed gradient; it can free gradient buckets as soon as they are reduce-scattered. Same traffic again.

**ZeRO-3 also shards the parameters.** Now no rank holds a full layer at rest. Before each layer's forward pass, the ranks all-gather its parameters, compute, and free them; before its backward pass they all-gather again; after it they reduce-scatter its gradients. That is Psi for the forward all-gather, Psi for the backward all-gather and Psi for the reduce-scatter: 3Psi against 2Psi, the 1.5 times the ZeRO paper reports.

The Playbook's per-GPU memory, with k = 12 and N_d data-parallel ranks:

```
ZeRO-1:  2Psi + 2Psi + 12Psi / N_d
ZeRO-2:  2Psi + (2Psi + 12Psi) / N_d
ZeRO-3:  (2Psi + 2Psi + 12Psi) / N_d
```

The ZeRO paper's worked example is a 7.5B model on 64 ranks: 120 GB per device with plain data parallelism, 31.4 GB with ZeRO-1, 16.6 GB with ZeRO-2 and 1.88 GB with ZeRO-3. Each is the formula above with Psi = 7.5B; 31.4 is 30 + 90/64.

## When ZeRO-3's traffic hides

ZeRO-3 trades memory for 2 x num_layers - 1 extra all-gathers per step, by the Playbook's count, and they sit in front of every layer. Whether they cost step time depends on whether each all-gather finishes while the previous layer computes. The ratio is derivable.

For one layer with P_l parameters and T tokens per GPU in the micro-batch, the forward pass costs 2 x P_l x T FLOPs and the all-gather moves about 2 x P_l bytes (BF16) per GPU. With achieved throughput F in FLOP/s and per-GPU bandwidth B in bytes per second:

```
compute time = 2 * P_l * T / F
gather time  = 2 * P_l / B
hidden if T >= F / B
```

P_l cancels. The condition is on tokens per GPU per micro-batch, which is why the Playbook says ZeRO-3 prefers large micro-batch and sequence length. The backward pass does twice the FLOPs and moves an all-gather plus a reduce-scatter, so it lands on the same condition.

Inside one node at NVLink speed (NVIDIA quotes 600 GB/s for the A100, an aggregate figure), the threshold falls to about 208 tokens, which is why ZeRO-3 confined to a node, or sharded inside the node and replicated across nodes, is so much easier to hide.</p>

Two further limits come from outside the formula. The all-gathers are latency-bound for small layers, so a model with many thin layers misses the threshold even when T is large. And the Playbook gives a rule of thumb that prefetching only keeps up while data parallelism stays at or below 512 ranks; past that, per-layer collectives over that many ranks stop overlapping.

## FSDP2: the PyTorch implementation

FSDP2's `fully_shard` is ZeRO-3 with a different unit of sharding from FSDP1. FSDP1 flattened a module's parameters into one FlatParameter and sharded that; FSDP2 makes each parameter a DTensor sharded on dimension 0, using `torch.chunk` across the data-parallel mesh. TorchTitan's paper reports about 7% lower per-GPU memory and a 1.5% average throughput gain over FSDP1 on Llama 2 7B, and per-parameter sharding is what lets FSDP2 compose with tensor parallelism and Float8 on the same DTensor.

The communication unit is the module `fully_shard` is applied to, not the parameter. Every call creates one group whose parameters are all-gathered together. The documentation is blunt about the degenerate case: apply it only to the root and all communication happens as two large blocking operations with no overlap with compute. The working pattern applies it to each transformer block and then to the root.

```python
import torch
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.layers:
    fully_shard(block, mp_policy=mp)            # one all-gather group per block
fully_shard(model, mp_policy=mp)                # root: embeddings, final norm, output head
```

This needs an initialised process group and GPUs, so it does not run in the browser; the arguments are what matter.

**`reshard_after_forward`.** True frees the gathered parameters after forward and gathers again in backward, which is full ZeRO-3. False keeps them gathered until backward, saving one all-gather per layer at the memory of the unsharded parameters, which is ZeRO-2's memory for those modules. The default is True for non-root modules and False for the root, whose parameters are needed first in backward anyway. An integer reshards to a smaller group after forward, for example the 8 GPUs of a node, so the backward all-gather runs over NVLink only. Llama 3's report describes its FSDP as sharding optimizer states and gradients while not resharding parameters after forward, which is the False setting chosen for the same reason.

**`MixedPrecisionPolicy`.** `param_dtype` sets the dtype of the all-gather and of compute; `reduce_dtype` sets the dtype of the gradient reduce-scatter. TorchTitan's default is BF16 gathers and compute with FP32 reductions, so the reduce-scatter carries twice the bytes of the all-gathers.

**Prefetching.** By default each block's forward all-gather is issued as the previous block starts. `set_modules_to_forward_prefetch` and `set_modules_to_backward_prefetch` let a block prefetch two or more blocks ahead, which the documentation describes as more overlap at the cost of more reserved memory. This is the knob to turn when the all-gather is exposed but memory has headroom.

**Gradient accumulation.** `set_requires_gradient_sync(False)` skips the reduce-scatter on micro-batches that do not end a step, the FSDP2 counterpart of FSDP1's `no_sync`. The unsharded gradients then accumulate locally, which costs their full memory until the last micro-batch.

## HSDP: shard inside, replicate across

A 2D mesh with a shard dimension inside the node and a replicate dimension across nodes gives hybrid sharding: parameter all-gathers and gradient reduce-scatters stay on NVLink, and only a gradient all-reduce of each rank's shard crosses nodes, once per step. Memory is ZeRO-3 over 8 ranks instead of over the whole cluster. It is the same hierarchical move as the hierarchical all-reduce in the collectives lesson, applied to the ZeRO-3 schedule.

## When this is wrong

The 3Psi count assumes reshard after forward everywhere. Keeping the root, or every module, gathered after forward moves ZeRO-3 back toward 2Psi at the memory of the unsharded parameters, so real traffic sits between the two figures.

The hiding condition assumes about 2 FLOPs per parameter per token. An embedding table is a lookup: many parameters, almost no FLOPs, so the root group that holds it is gathered with nothing to hide behind. Profiling shows this as a gap at the start of forward, which is one reason the root defaults to staying gathered.

ZeRO does not shard activations. A model whose activations alone exceed the card needs recomputation, tensor and sequence parallelism, context parallelism or pipeline parallelism; adding data-parallel ranks does not help.

Finally, the Playbook's rule of thumb of 512 data-parallel ranks is a measurement on its cluster, not a law. A faster fabric moves it; a cluster with stragglers moves it down.
