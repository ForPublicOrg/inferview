## The decision

Given a model, a cluster and a global batch, choose the degree of each parallel dimension (data with a ZeRO stage, tensor with sequence, pipeline with a schedule, context, expert) and the mesh order that maps each onto the hardware. The product of the degrees is the GPU count; everything else is a trade between memory, communication on each fabric, and the pipeline bubble.

The Playbook's procedure is the right skeleton because it orders the constraints by how hard they are:

1. **Fit one replica.** Find the smallest set of model-parallel degrees and recomputation that makes one training step fit in GPU memory. Memory is a wall, not a cost.
2. **Reach the global batch.** Fill the rest of the GPUs with data parallelism and gradient accumulation (or context parallelism for long sequences) until micro-batch x accumulation x DP equals the batch optimization asked for.
3. **Maximise throughput.** Only now trade dimensions against each other: raise TP toward the node size, raise DP with ZeRO-3, move to PP when DP communication becomes the bottleneck, tune the micro-batch.

## The inputs that change it

**Parameter count, and for MoE, active against total.** Model states at 16 bytes per parameter decide step 1. For MoE, total parameters set memory and active parameters set compute, so the two can point in different directions.

**Sequence length.** Activations grow with it; past about 128K tokens, context parallelism is the only lever that divides one sequence's activations.

**Scale-up domain size.** The number of GPUs on the fast fabric, 8 per node in every published configuration in this lesson, caps TP and decides whether EP can stay on NVLink.

**Per-GPU scale-out bandwidth.** Sets whether ZeRO-3's per-layer gathers and cross-node EP all-to-all hide. Read the spec carefully: a figure per node and a figure per GPU differ by the node size.

**Global batch.** Fixed by the optimization team. It bounds data parallelism times micro-batches, so it sets the pipeline bubble and how far DP can scale.

**Team and stack.** DualPipe, zero-bubble schedules and ring attention exist in some stacks and not others. A schedule nobody on the team has debugged is a risk with a cost.

## The options and when each wins

**ZeRO-3 / FSDP alone.** Wins below about 10B parameters, and up to more when micro-batches are large enough to hide per-layer gathers. Zero model code changes. The Playbook reports that at 512 GPUs and above, pure DP/ZeRO-3 becomes inefficient.

**TP 8 inside the node plus FSDP across.** The 10B to 100B default for dense models. TorchTitan's 70B run on 256 GPUs was FSDP 32 with TP 8. Loses when the per-node shard of model states plus activations still does not fit.

**TP 8, PP across nodes, ZeRO-1 or ZeRO-2 DP.** The large dense default, and the Playbook's suggestion at 1,024 GPUs and above. Llama 3's 405B used TP 8, PP 16 and DP 64 to 128 at 41 to 43% MFU. Korthikanti's 530B configuration used TP 8 and PP 35. Pays the bubble, so needs a large global batch.

**PP with ZeRO-3.** The Playbook says the combination is possible but rarely used, because it needs a much larger global batch to amortise both PP's bubble and ZeRO-3's weight traffic. Choose it only when neither alone fits.

**PP and EP with ZeRO-1, no TP.** DeepSeek-V3's choice for a 671B-total MoE on 2,048 H800s: PP 16, EP 64 over 8 nodes, ZeRO-1. It avoided TP by aggressive memory work and paid for cross-node EP with node-limited routing, custom kernels and DualPipe.

**Add CP.** Only when one sequence's activations do not fit at TP 8. Llama 3 added CP 16 for its 131,072-token stage and took it out of DP, which fell from 128 to 8.

The two big published layouts are worth reading side by side. Llama 3 is a dense model with TP on NVLink and everything else across nodes. DeepSeek-V3 is an MoE with no TP at all and its expert all-to-all on InfiniBand. Both are correct for their models; a layout copied from one to the other's model would not be.

## Worked decision: the reported Meta prompt

The reported prompt: design an MoE pretraining pipeline for a bilingual model on about 1T tokens with 256 A100-80GB GPUs, 32 nodes of 8 with NVLink, 200 to 400 Gbps between nodes, then scale to 1,024 GPUs. Everything below except those facts is a scenario choice, stated as such.

**Model, chosen to fit the budget.** Take 60B total parameters, 10B active, of which 4B are dense (attention, embeddings, shared parts) and 56B are experts. Training compute is 6 x 10e9 x 1e12 = 6e22 FLOPs. At an assumed 35% MFU on 312 TFLOP/s A100s, the cluster delivers 256 x 312e12 x 0.35 = 2.8e16 FLOP/s, so the run takes 2.15e6 seconds, 24.8 days. That number is the sanity check every other choice must respect: a layout that costs 20% throughput adds five days.

**Read the network.** The prompt gives 200 to 400 Gbps without saying per GPU or per node. Per GPU at 400 Gbps is 50 GB/s; per node at 200 Gbps is 25 GB/s shared by 8 GPUs, 3.1 GB/s each. That is a 16 times range, and the plan must work at the bottom of it or the interviewer's first question breaks it.

**Step 1, fit a replica. Layout A: EP 8 inside each node, DP 32 across nodes.** Each GPU holds the full 4B dense part and one eighth of the experts, 7B expert parameters. Parameters and gradients in BF16: 4B x 4 bytes = 16 GB dense plus 7B x 4 = 28 GB expert. Optimizer states sharded ZeRO-1 style, the dense part over all 256 GPUs (12 x 4B / 256 = 0.19 GB) and each expert shard over its 32 replicas (12 x 7B / 32 = 2.6 GB). Total 46.8 GB, leaving about 33 GB for activations and buffers. With 4,096-token micro-batches, h = 4096 and 24 layers (scenario), Korthikanti's sbh x 34 under selective recomputation gives 13.7 GB as a dense approximation; MoE layers differ, so measure one layer.

**Communication of layout A.** The all-to-all, on the critical path of every MoE layer, stays on NVLink. Cross-node traffic is gradient synchronisation once per step: the dense part, reduced hierarchically, puts 2 x 31/32 x 8 GB / 8 = 1.9 GB per GPU on the network; each expert shard is all-reduced across its 32 replicas, 2 x 31/32 x 14 GB = 27.1 GB per GPU. With an assumed 4M-token global batch, a step is 6 x 10e9 x 4e6 = 2.4e17 FLOPs, 8.6 seconds on the cluster. At 50 GB/s per GPU, 27.1 GB is 0.54 s and overlaps with backward. At 3.1 GB/s per GPU it is 8.7 s, longer than the step.

**Layout B: EP 32 across 4 nodes, DP 8.** Each GPU holds 1.75B expert parameters: 25.8 GB of model states, expert gradient sync 6.1 GB per GPU. But the all-to-all now crosses nodes in every MoE layer. With top-2 routing and 24 MoE layers (scenario), each token sends 2 x 4096 x 2 bytes for dispatch and the same for combine, doubled for backward: 1.57 MB per token per step, 25.8 GB per GPU at 16,384 tokens per GPU, three quarters of it crossing nodes under uniform routing. That is 19 GB on the critical path instead of 27 GB off it.

**Decision.** Layout A, if the network is 50 GB/s per GPU: the critical-path exchange stays on NVLink and the cross-node traffic overlaps. If the network turns out to be the per-node reading, neither layout works as stated, and the fix is not a parallelism change: it is ZeRO-2 for the experts (reduce-scatter instead of all-reduce, halving the 27.1 GB), a larger global batch to lengthen the step, or both. What A gives up: 46.8 GB of model states leaves less room for longer sequences, and every expert's weights are replicated 32 times, which makes checkpoints larger.

**Scale to 1,024 GPUs.** Layout A becomes EP 8, DP 128. Per-GPU expert gradient traffic barely moves, 2 x 127/128 x 14 GB = 27.8 GB, because a ring's per-GPU bytes do not grow with ring size. But at a fixed 4M-token batch, each GPU processes a quarter of the tokens and the step falls to 2.1 s, so the same 27.8 GB is now a quarter of the step at 50 GB/s and no longer hides as easily. The levers, in order: ask optimization for a larger batch; move experts to ZeRO-2; then EP 16 across two nodes to halve the replicated expert state. Llama 3's report gives the reliability term at this scale: 466 interruptions in 54 days on its 16K-GPU cluster, 419 of them unexpected. Checkpoint interval and restart time belong in the plan at 1,024 GPUs, not as an afterthought.

## What to measure after deciding

Measure tokens per second per GPU and MFU against the 35% assumption, because the 24.8-day schedule rests on it. Measure exposed communication per step, split by collective, from a profile, not inferred from MFU. Track all-to-all imbalance as the most-loaded expert's token count over the mean, per layer, because the exchange finishes at the slowest receiver. Record peak memory per GPU at the worst stage or rank, with the headroom left. Log time to checkpoint and time to restart, and loss spikes with the step and data shard that produced them. Set a written trigger for each: for example, exposed communication above a stated fraction of the step for a day triggers the ZeRO-2 change.

## When this is wrong

The procedure assumes memory is the binding constraint first. On some clusters it is the network, and a layout that fits easily but saturates the scale-out links loses to one that barely fits.

The worked case uses an assumed MFU, uniform routing and a dense activation formula for MoE layers. Each is a place the real numbers will differ. Uniform routing in particular understates the all-to-all, because the exchange finishes when the most loaded GPU finishes.

Published layouts are evidence about their clusters, not rules. Llama 3 and DeepSeek-V3 were trained on 8-GPU nodes; larger scale-up domains move the boundary where TP and EP leave the fast fabric, and the right composition moves with it.
