## What it is and who runs it

TorchTitan is a pre-training codebase from the PyTorch team, described in a paper first posted in October 2024 and revised in June 2025. Its claim is that the pieces earlier lessons treated separately, FSDP2, tensor and sequence parallelism, pipeline schedules, context parallelism, Float8 and distributed checkpointing, compose in plain PyTorch on one abstraction, the DTensor on a device mesh, without a separate framework on top. It is the closest public answer to "what does a production training loop look like in PyTorch today", with measurements on Llama 3.1 at 8B, 70B and 405B on H100s.

Studying it answers a question the published model reports do not: what each layer of the stack is worth, measured one at a time on the same code.

**FSDP2.** The data-parallel dimension. Each parameter becomes a DTensor sharded on dimension 0 across the data-parallel ranks, replacing FSDP1's flattened FlatParameter. The paper reports about 7% lower per-GPU memory and a 1.5% average throughput gain over FSDP1 on Llama 2 7B. Per-parameter sharding is what lets the same parameter also carry a tensor-parallel placement and a Float8 representation. By default parameters are all-gathered and computed in BF16 and gradients are reduce-scattered in FP32. A 2D mesh with a replicate dimension gives HSDP.

**Tensor and pipeline parallelism.** TP and SP are applied by annotating modules with DTensor ColwiseParallel and RowwiseParallel plans and are bundled under one TP degree, the column-then-row pairing from the tensor-parallelism lesson. The paper places TP inside nodes and FSDP across them. AsyncTP overlaps TP communication with the matmuls using SymmetricMemory and requires H100-class GPUs with NVSwitch. Pipeline parallelism splits the model into stages and offers six schedules: GPipe, 1F1B, Interleaved 1F1B, Looped-BFS, Flexible-Interleaved-1F1B and ZeroBubble. Context parallelism is applied in the next mesh dimension out from TP.

**Float8 training.** Linear layers run in Float8 through torchao, with dynamic, delayed or static per-tensor scaling. This is coarser than DeepSeek-V3's 1x128 and 128x128 tiles: one scale per tensor is simpler and composes with FSDP's all-gather, at more exposure to outliers.

**Distributed checkpointing.** Checkpoints use PyTorch's DCP. Each rank writes only its own shards of each DTensor, in parallel, plus a global metadata file; on load, each rank reads the least data it needs and the checkpoint can be loaded into a different topology. Asynchronous saving copies the state to CPU memory and writes it from a separate thread or process, so training resumes after the copy rather than after the write. The paper reports asynchronous checkpointing cutting checkpoint overhead 5 to 15 times against synchronous DCP on Llama 3.1 8B.

**Elastic scaling.** The abstract lists elastic scaling among the features. The mechanism that makes it possible is DCP's load-time resharding: a checkpoint written with one mesh can be loaded with another, so a job that loses nodes can restart on fewer GPUs, or grow, without converting the checkpoint offline.

Two more pieces matter operationally. Regional torch.compile compiles each TransformerBlock separately, and because the blocks are identical, compiles once and reuses it, which keeps compile time bounded. Flight Recorder logs the start, end and enqueue times of every collective and point-to-point operation, which is what an engineer needs when a 512-GPU job hangs and every rank reports a timeout.

## Measured gains, one layer at a time

The paper's results are cumulative, each row adding one technique on the same model and GPU count.

**Llama 3.1 8B, 128 GPUs, FSDP only.** 5,645 tokens per second per GPU at 67.0 GiB. Adding torch.compile: 6,482, 14.82% faster, at 62.1 GiB. Adding Float8: 9,319, 65.08% over the FSDP baseline, at 61.8 GiB. Float8 contributes most of the gain at this scale.

**Llama 3.1 70B, 256 GPUs, FSDP 32 and TP 8 with Float8 and compile.** 897 tokens per second per GPU; with AsyncTP, 1,010, 12.59% more, with memory falling from 70.3 to 67.7 GiB.

**Llama 3.1 405B, 512 GPUs, FSDP 4, TP 8, PP 16.** 100 tokens per second per GPU with 1F1B; 130 with Interleaved 1F1B, 30% more, at 80.3 GiB against 78.0. That is the bubble arithmetic from the pipeline lesson in a measurement: with FSDP 4, each pipeline gets a quarter of the global batch, which bounds m, and interleaving's division of the bubble by v pays.

**Long context.** On Llama 3.1 8B with 8 GPUs, context parallelism reached 262,144 tokens; throughput fell from 3,890 tokens per second at 32,768 tokens to 548 at 262,144 while memory stayed near 84 GiB. The 405B model with 4D parallelism ran at 262,144 tokens at 16 tokens per second per GPU and 84.9 GiB.

To compare against the Llama 3 report's 405B MFU, convert with the same formula on both sides; the TorchTitan paper reports tokens per second, and a conversion needs FLOPs per token for the exact configuration, which is easy to get wrong for attention at long context.

## Checkpointing in detail

The checkpoint path is the part most training stacks get wrong, and the documentation is specific about its contract.

A DCP checkpoint is a directory with at least one file per rank, not one file. Loading is in place: the model and optimizer are constructed and sharded first, on the target mesh, and DCP fills their existing storage, reading only the shards each rank needs. That is what makes resharding cheap: a checkpoint from FSDP 32 and TP 8 can be loaded into FSDP 16 and TP 8 by reading different byte ranges.

The `get_state_dict` and `set_state_dict` helpers translate between parallelism-specific keys and canonical fully qualified names, so the same checkpoint loads into FSDP, DDP or an unsharded model. The documentation labels these helpers experimental, and states that saved state dicts carry no backward-compatibility guarantee across PyTorch versions. For a run that lasts months, the PyTorch version is effectively pinned for the run, or the checkpoint format is converted and verified before an upgrade.

Asynchronous save moves the cost from the write to the copy. The state is staged into CPU memory first, and the documentation gives separate completion signals for staging and for the upload; parameters must not change until staging completes, and the write proceeds in the background. Two limits follow: host memory must hold a copy of the rank's shards, and a new checkpoint should wait on the previous one's upload.

## Failure modes

A hang in a collective is the characteristic failure of composed parallelism: one rank enters a different collective than its peers, or never enters, and every other rank waits until a timeout. Flight Recorder's per-operation timestamps are the instrument for finding which rank and which operation diverged.

Composition makes ordering bugs possible that single-dimension parallelism does not: a parameter wrapped by TP after FSDP instead of before, or a pipeline stage whose FSDP group does not match its peers', produces wrong shapes or silent mis-sharding. A stack that fixes the order in which the parallelisms are applied removes this class of bug for its users, which is part of what a stack provides beyond the primitives.

Asynchronous checkpointing has a gap: between staging and the completion of the write, the latest checkpoint exists only in host memory. A node failure in that window loses it, and recovery falls back to the previous checkpoint. The checkpoint interval has to account for that.

## What is not public

Production cluster failure data is not public. The paper describes the features for recovery, checkpointing, resharding on load and Flight Recorder, and reports throughput and memory, but it does not publish how often jobs on its clusters failed, how long restarts took, or how much training time was lost to failures. Questions about TorchTitan's effective training time at scale cannot be answered from the paper; Llama 3's report, from a different stack, is the public reference for that number at 16K GPUs.

<p>Switch to DCP async_save, which takes the write off the critical path; the paper measured 5 to 15 times lower checkpoint overhead on 8B. That allows shorter intervals at the same throughput, but not more storage bandwidth, so the interval is set by write bandwidth, not training stalls. <Fragment slot="long">
<p>Expected loss per failure is about half the interval plus the restart time, so at one failure every two days and a two-hour interval, roughly an hour of compute plus restart per failure. Async DCP removes most of the stall: the loop waits only for the copy to host memory. That makes a one-hour interval cheap in step time, and it halves the expected loss per failure.</p>
<p>The storage team's constraint is separate. Halving the interval doubles the average write bandwidth, regardless of async. Options: write the frequent checkpoints to node-local or a nearby fast tier and copy every Nth to the shared filesystem, accepting that a failure of the node holding the recent copy falls back further; or checkpoint only model and optimizer shards that changed, which for a dense model is all of them, so it does not help. I would ship async DCP at a one-hour interval if the storage budget allows it, and a two-tier scheme if not. Failure mode: async leaves a window in which the newest checkpoint is in host memory only; a failure in that window loses it, so the interval should be measured from the last completed write, not from the last save call.</p>
