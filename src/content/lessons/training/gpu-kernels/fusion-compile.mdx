## The ladder, and where to stop on it

The Ultra-Scale Playbook ranks the ways to get a kernel: plain PyTorch (easy, slow), torch.compile (easy, fast, not flexible), Triton (harder, faster, more flexible) and CUDA (hardest, fastest and most flexible if done right). Each rung costs more to write and much more to keep: a hand-written kernel needs its own backward, its own numerical tests and a re-check on every framework and driver upgrade. The decision is how far up to climb for a given op, and the previous lesson already gives the bound on what any rung can win: the bytes a bandwidth-bound op stops moving, or the launches an overhead-bound step stops paying for.

## What fusion saves

An unfused chain of k pointwise ops on a tensor reads and writes the tensor k times. Fused into one kernel, it reads once and writes once. Horace He's example is `x.cos().cos()`: four global reads and writes unfused, two fused, a 2x speedup for an op that is entirely bandwidth-bound. Fusion does nothing for FLOPs; the arithmetic is the same.

The same arithmetic tells you where fusion is not worth the effort. Fusing a residual add with the LayerNorm after it saves one write and one read of a 4,096 × 8,192 BF16 activation, 67 MB, about 0.02 ms. Against the roughly 6.7 ms of forward matmul compute in a layer of the previous lesson's scenario block (2.22 ms for the QKV and output projections together, 4.44 ms for the two MLP matmuls), that is 0.3%. A custom kernel for it is rarely worth writing by hand; a compiler that fuses it for free is.

## torch.compile: modes and their costs

`torch.compile` traces Python into graphs and hands them to a backend, Inductor by default, which fuses pointwise and reduction ops into generated kernels. The PyTorch 2.14 documentation lists four modes:

| Mode | What it adds | Cost |
|---|---|---|
| `default` | fusion and code generation | compile time on first call and on each recompilation |
| `reduce-overhead` | CUDA graphs, described as useful for small batches | more memory, because workspace memory is cached; only applies to CUDA-only graphs that do not mutate inputs |
| `max-autotune` | Triton or template matmuls chosen by benchmarking, with CUDA graphs on by default on GPU | longest compile time, plus the CUDA-graph constraints |
| `max-autotune-no-cudagraphs` | autotuning without CUDA graphs | compile time |

Two parameters decide how often you pay compile time again. A compiled frame is guarded on the properties it was traced with, including input shapes. With `dynamic=False` every new shape is a new specialisation. With the default `dynamic=None` PyTorch detects that a dimension changed and compiles a more dynamic kernel on the recompile. With `dynamic=True` it tries to generate the most dynamic kernel up front. A frame keeps at most `recompile_limit` compiled results, 8 by default, and then falls back to eager; with `fullgraph=True`, hitting the limit raises `FailOnRecompileLimitHit` instead. The caches are per code object, so a function compiled once and called from many places shares one set of results.

`fullgraph=False`, the default, lets the tracer split the function at anything it cannot capture, a graph break, and run that piece in Python. Each break ends a fused region and adds a return to the interpreter, so a model with a print, a data-dependent Python branch or a `.item()` in the middle compiles into several smaller graphs with less fusion between them. `fullgraph=True` turns every break into an error, which is the way to find them.

## CUDA graphs: what capture freezes

A CUDA graph records a sequence of kernel launches once and replays it with one launch from the CPU. It attacks the overhead regime: in Horace He's measurement PyTorch issued about 280 thousand operations per second on tiny tensors, about 3.6 µs each. A scenario step of 2,000 small kernels would spend 2,000 × 3.6 µs = 7.2 ms issuing them; if the GPU work takes 5 ms, the CPU is the bottleneck and a graph replay removes most of that 7.2 ms.

Replay works because nothing about the recorded launches changes, and the CUDA semantics notes list what that forbids. During capture, ops that synchronise the CPU with the GPU, such as `.item()`, are prohibited, as is control flow that depends on CPU or GPU data unless expressed with `torch.cond`. Dynamic shapes are prohibited. CPU work is not captured and is skipped on replay. Every replay reads and writes the same memory addresses, which is why graph inputs must be copied into static buffers and why graphs own a private memory pool that lives until the graph and every tensor it created are gone.

The consequence for training is that a CUDA graph is a specialisation on shape. Feed a `reduce-overhead` model a new sequence length and it needs a new graph, with its own memory, on top of a recompile. Bucketing sequence lengths to a small fixed set of shapes is what makes CUDA graphs usable with variable-length data. Where a whole step cannot be captured, `torch.cuda.make_graphed_callables()` graphs the safe parts and leaves the rest eager.

## The caching allocator, and timing honestly

PyTorch does not return freed GPU memory to the driver; its caching allocator keeps freed blocks for reuse. `torch.cuda.empty_cache()` releases unused cached blocks, but the documentation is explicit that it does not increase the memory available to PyTorch, because tensors in use are not freed. Calling it every step only forces the allocator to request memory from the driver again. Fragmentation from varying allocation sizes, for example varying batch shapes, is what `PYTORCH_ALLOC_CONF=expandable_segments:True` addresses (experimental, off by default in 2.14); `max_split_size_mb` is documented as a last resort for out-of-memory failures.

Kernel launches are asynchronous, so a Python timer around a GPU op measures the launch, not the work. Time with `torch.cuda.synchronize()` before reading the clock or with CUDA events. `CUDA_LAUNCH_BLOCKING=1` makes every launch synchronous; it is for locating the op that raised an error, and timings taken under it measure a different program.

## When a hand-written kernel is worth it

The procedure, applied per op:

1. Compute the ceiling: bytes removed times occurrences per step divided by 3.35 TB/s, or launches removed times launch cost. If the ceiling is under a few percent of step time, stop.
2. Try `torch.compile` with `fullgraph=True` on the region, fix the graph breaks it reports, and measure. Automatic fusion of pointwise and norm chains usually reaches most of the ceiling.
3. Write Triton when the compiler cannot express the fusion: an op that needs a custom tiling, an online reduction across a dimension (the pattern behind FlashAttention), or an epilogue the compiler does not fuse. Triton keeps the kernel in Python and portable across NVIDIA generations.
4. Write CUDA when the kernel needs hardware features the higher rungs do not expose well, such as explicit TMA pipelines or cluster shared memory, and when a team will own it through upgrades.

The Playbook's own numbers show why step 4 is rare: a correct, tiled CUDA matmul reached about 6.6 TFLOPS, 0.67% of the H100's dense BF16 peak. The rung is the fastest only for engineers who already know how to reach the hardware's limits.

## When this is wrong

Compile time is real time. For a short fine-tuning job or an evaluation loop that changes shapes, compilation and autotuning can cost more than they save, and `max-autotune` has the longest compile of the modes. Measure end to end, including the first steps.

Fusion changes the order of floating-point operations, so a fused kernel does not match the eager result bit for bit. Test against tolerances derived from the reference's own variation, not against equality, and expect loss curves to differ in the low digits.

The mode descriptions here are from the PyTorch 2.14 documentation. Defaults such as the recompile limit and which modes enable CUDA graphs are version-specific; check the documentation for the version you run.
