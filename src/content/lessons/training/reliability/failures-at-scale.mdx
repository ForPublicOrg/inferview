A synchronous data-parallel training job commits once per step: every rank contributes to the same all-reduce or reduce-scatter, and one rank that stops answering stalls all of them. In a web fleet a dead host costs one host's capacity; in a 16,384-GPU job a dead GPU costs the whole job until it restarts from the last checkpoint. The design question is not how to prevent failures but what failure rate the run will see, how much work each failure destroys, and which of those costs can be bought down.

Meta's Llama 3 paper is the most detailed public account of that rate at frontier scale. This lesson reads it as an operator would: what failed, how often, what the paper's own table gets wrong, and why effective training time is the number that says whether the run is on schedule.

## The rate, from the paper's own counts

The paper describes a 54-day snapshot of Llama 3 405B pre-training on up to 16K H100 GPUs. In that window the job was interrupted 466 times. 47 were planned (automated maintenance such as firmware upgrades, or operator changes to configuration or datasets). The other 419 were unexpected.

<Predict id="trn-rel-mtbf" question="From 419 unexpected interruptions in 54 days, what is the mean time between unexpected interruptions of the job, in hours?" answer={3.09} tolerance={0.1} unit="hours">
54 days is 1,296 hours, and 1,296 / 419 = 3.09 hours. Counting planned interruptions too, 1,296 / 466 = 2.78 hours. The job restarted eight to nine times a day on average.
</Predict>

Three hours between failures changes what a long-running job is. Any cost that scales with the time since the last checkpoint, and any recovery step that needs a human, is on the critical path several times a day. The paper says significant manual intervention was needed only three times in the 54 days; automation handled the rest. That ratio is the real engineering result of the section. A team that pages a person for each restart at this rate is staffing a restart desk.

The rate scales with job size. If failures are independent and the per-GPU rate is constant, the job-level rate is proportional to the GPU count. The paper gives the GPU count only as "up to 16K", so taking 16,384 GPUs for all 54 days gives the lowest per-GPU rate the numbers allow:

| Job size | Mean time between unexpected interruptions at the same per-GPU rate |
| --- | --- |
| 16,384 GPUs | 3.1 hours |
| 4,096 GPUs | 12.4 hours |
| 2,048 GPUs | 24.7 hours |

These come from one fleet, one hardware generation and one 54-day window. They are a planning prior for H100-class clusters, not a property of GPUs.

## What failed

Table 5 of the paper breaks the 419 unexpected interruptions into root causes. The largest rows, with the paper's counts and percentages and the count divided by 419:

| Component | Category | Count | Paper's % | Count / 419 |
| --- | --- | --- | --- | --- |
| Faulty GPU | GPU | 148 | 30.1% | 35.3% |
| GPU HBM3 memory | GPU | 72 | 17.2% | 17.2% |
| Software bug | Dependency | 54 | 12.9% | 12.9% |
| Network switch or cable | Network | 35 | 8.4% | 8.4% |
| Unplanned host maintenance | Unplanned maintenance | 32 | 7.6% | 7.6% |
| GPU SRAM memory | GPU | 19 | 4.5% | 4.5% |
| GPU system processor | GPU | 17 | 4.1% | 4.1% |
| NIC | Host | 7 | 1.7% | 1.7% |
| NCCL watchdog timeouts | Unknown | 7 | 1.7% | 1.7% |
| Silent data corruption | GPU | 6 | 1.4% | 1.4% |
| GPU thermal interface and sensor | GPU | 6 | 1.4% | 1.4% |

Seven smaller rows (SSD, power supply, server chassis, IO expansion board, dependency, CPU and system memory) account for the remaining 18 interruptions.

### The row that does not add up

Every row's percentage equals its count divided by 419 except the first. 148 / 419 is 35.3%, not 30.1%; 30.1% of 419 would be 126. The counts sum to 419 and the printed percentages sum to 94.9%. Either the 148 or the 30.1% is wrong, and since the counts close to 419, the percentage is the likelier error. The paper does not say which.

The error propagates. The text's "GPU issues are the largest category, accounting for 58.7% of all unexpected issues" is exactly the sum of the printed percentages of the six GPU rows (30.1 + 17.2 + 4.5 + 4.1 + 1.4 + 1.4). From the counts, the same rows are 268 of 419, which is 64.0%. The "about 78%" hardware figure cannot be reproduced from the table either: leaving out software bugs, dependencies and the unknown NCCL timeouts gives 79.8% from the printed percentages and 85.0% from the counts, and the paper does not list which rows it counted.

None of this changes the engineering conclusion that GPUs and their memory dominate. It matters for anyone who writes "30% of failures are faulty GPUs" into a capacity plan or a postmortem: the share that matches the paper's own counts is 35%, and a share of interruptions is not a failure rate anyway. Problem trn-032 is a postmortem built on that mistake.

### Categories that cost more than their count

Interruption counts treat every failure as equal. Three categories cost more than their count.

**Silent data corruption.** Six interruptions. A corrupted value that does not crash anything can be averaged into the weights by the next gradient reduction. The cost is not the restart but not knowing how far back the last clean checkpoint is.

**NCCL watchdog timeouts with no root cause.** Seven, filed under "Unknown". A watchdog timeout says a collective did not finish; it does not say which rank stopped. The paper describes the tooling Meta built for this: PyTorch's NCCL flight recorder keeps collective metadata and stack traces in a ring buffer and dumps them on a watchdog or heartbeat timeout, and Meta's NCCLX snapshots the failing collective's finished and pending transfers between ranks. NVLink failures appear as CUDA kernels stalled on loads and stores with no error code, so detection depends on timeouts.

**Stragglers.** Absent from the table, because a slow GPU does not interrupt the job. The paper notes that one straggler can slow thousands of GPUs and looks like slow communication rather than an error. Its cost lands in throughput.

## MFU and effective training time have different denominators

The paper reports BF16 model FLOPs utilization of 38% to 43% across the three pre-training configurations: 43% on 8,192 GPUs, 41% on 16,384 GPUs, and 38% with 16-way context parallelism at 131,072-token sequences. MFU is model FLOPs per second divided by peak, measured while steps are running.

Effective training time is the paper's other headline, defined as "the time spent on useful training over the elapsed time", and above 90% for Llama 3. Its denominator is wall-clock time, including restarts, work lost since the last checkpoint, checkpoint stalls and job startup.

They multiply. Useful model FLOPs per reserved GPU-hour, as a fraction of peak, are MFU times effective training time: at 41% and 90%, 0.41 × 0.90 = 0.369. A failure storm barely moves MFU, because MFU is measured over steps that ran; it moves effective training time. A straggler does the opposite: no interruption, so effective training time is unchanged, but every step is slower, so MFU drops. A dashboard with only one of the two hides one class of failure.

## Designing for the rate

Read Table 5 as requirements. With an interruption every three hours:

**Restart is automatic end to end.** Detection, isolating the bad host, rescheduling, loading the checkpoint and resuming the data loader all run without a person. Meta needed one three times in 466 interruptions.

**Lost work per interruption is a design parameter.** It is, on average, half a checkpoint interval plus the restart time. The [checkpointing lesson](/learn/training/reliability/checkpointing) derives the interval from the failure rate and the save stall, and shows why restart time usually dominates once saves are asynchronous.

**Planned maintenance is part of the rate.** The paper says automated maintenance such as firmware and kernel upgrades caused at least one interruption a day. Draining one host at a time without killing a synchronous job is a scheduler feature, and it would remove that row.

**Diagnosis works after the fact.** The failing rank is usually gone by the time anyone looks, hence ring-buffer traces dumped on timeout, and configuration that turns on heavier tracing in a live job without a code release or restart, which the paper also describes.

The paper adds two sources of loss that no per-component table captures. Throughput varied 1% to 2% with time of day, which the paper attributes to mid-day temperatures affecting GPU dynamic voltage and frequency scaling. And when tens of thousands of GPUs stall together, for a checkpoint or a collective, data-centre power swings by tens of megawatts, which the paper calls an ongoing challenge for the power grid. A checkpoint that pauses every GPU at the same instant is also a power event.

```python
# Expected unexpected interruptions per day for a job of N GPUs, from the Llama 3 snapshot.
# Assumes independent failures and 16,384 GPUs in the job for the whole 54 days.
PER_GPU_DAY = 419 / (16_384 * 54)

for n in (2_048, 4_096, 16_384):
    per_day = PER_GPU_DAY * n
    print(n, round(per_day, 2), "per day,", round(24 / per_day, 1), "hours apart")

# Table 5 check: the counts sum to 419, the printed percentages do not.
counts = [148, 72, 54, 35, 32, 19, 17, 7, 7, 6, 6, 3, 3, 2, 2, 2, 2, 2]
printed = [30.1, 17.2, 12.9, 8.4, 7.6, 4.5, 4.1, 1.7, 1.7, 1.4, 1.4, 0.7, 0.7, 0.5, 0.5, 0.5, 0.5, 0.5]
print(sum(counts), round(sum(printed), 1), round(100 * 148 / 419, 1))  # 419 94.9 35.3
```

## When this is wrong

The constant per-GPU rate assumes independent failures. Real failures cluster: a bad batch of memory, a switch that takes out a rack, a firmware rollout, a cooling fault in one row. Correlated failures break the scaling table above and break any spare pool sized from the average rate.

The rate is one fleet in one window. The 54-day snapshot is not the whole run, the GPU count over the window is given only as "up to 16K", and failure rates change as hardware ages: a new cluster and a cluster in its second year are different populations. Use the paper as a prior and replace it with your own interruption log as soon as there are a few weeks of it.

Effective training time is Meta's metric with Meta's definition. Other reports use goodput or useful-time fractions with different denominators, for example whether planned maintenance, queueing before start or evaluation time count. Compare definitions before comparing percentages.

Interruption counts are not failure counts. One unhealthy host can cause several interruptions if the scheduler puts it back into the job, and one interruption can have more than one cause. A table built from interruptions overweights components that are hard to diagnose and get retried.
