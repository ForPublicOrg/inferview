## The decision

Every RL stage optimises a number, and the number is never the thing you want. The choice of reward source decides which gap the policy will find: a rule rewards whatever passes the rule, a learned reward model rewards whatever it scores highly, and a step-level reward rewards whatever looks like a good step. The question for a task is which of those gaps you can measure and bound, and the answer is usually a rule where one exists, a learned model where it does not, and a held-out measurement that the policy never optimises against.

## Four reward sources

**Rule-based rewards.** DeepSeek-V3 uses rules wherever a question has a deterministic answer: maths answers in a designated format so a parser can check them, LeetCode problems run through a compiler against test cases. DeepSeek-R1-Zero went further and trained only on an accuracy reward and a format reward (thinking between the think tags). The paper's stated reason for not using a neural reward model: it "may suffer from reward hacking in the large-scale reinforcement learning process", and retraining it adds cost and complexity. A rule fails at its edges. A format check accepts a correctly formatted wrong answer if the accuracy check is lenient; test-based rewards reward code that passes weak tests; a parser that takes the last number in the response rewards listing several numbers.

**Pairwise reward models.** A Bradley-Terry model scores each response with a scalar and is trained so that the chosen response outscores the rejected one: the loss is −log σ(r(chosen) − r(rejected)). Only differences enter the loss, so the reward is defined up to a constant per prompt, and comparing raw rewards across prompts means nothing unless you normalise them. Llama 3 trains this objective with the margin term from Llama 2 removed ("diminishing improvements after data scaling"), drops pairs whose responses are similar, uses rankings of edited over chosen over rejected where an annotator improved the chosen response, and packs a prompt with several shuffled responses into one row for efficiency. A pairwise model learns whatever separates chosen from rejected in the training data. If chosen responses are longer on average, it learns length, and a policy optimised against it gets longer.

**Generative reward models.** DeepSeek-V3's model-based reward is trained from DeepSeek-V3 SFT checkpoints, and its preference data includes the chain of thought leading to the reward, which the report says helps mitigate reward hacking. The reasoning is inspectable, so an auditor can read why a response won. It costs a generation per scored response and inherits the judge's own biases.

**Process reward models.** An outcome reward model scores the final answer; a process reward model scores each step. Lightman et al. trained both on MATH and report that process supervision significantly outperforms outcome supervision: their process-supervised model solves 78% of a representative subset of the MATH test set, and they release PRM800K, 800,000 step-level human labels. DeepSeek-R1 then listed a PRM among its unsuccessful attempts, for three reasons the paper gives in order: a fine-grained step is hard to define in general reasoning, judging whether an intermediate step is correct is hard, and a model-based PRM "inevitably leads to reward hacking" and needs retraining. The two results do not contradict each other. Lightman et al. used the PRM to rank sampled solutions (best-of-N) with 800,000 human step labels; R1 needed a reward to optimise against for many RL steps, where every weakness of the PRM gets found.

## How far you can push a proxy

Gao, Schulman and Hilton measured over-optimisation directly. A 6B "gold" reward model stood in for people and labelled 100,000 synthetic comparisons (90,000 used for training). Proxy reward models from 3M to 3B parameters were trained on those labels, and a 1.2B policy was optimised against each proxy with best-of-n sampling or with PPO. Let d be the square root of the KL divergence from the initial policy. The gold reward followed

- best-of-n: R(d) = d(α − βd)
- RL: R(d) = d(α − β log d)

with α and β fitted per proxy, changing smoothly with proxy size. Both curves rise, peak and fall: the proxy keeps rising after the gold score turns. Setting the derivative to zero gives the peak: d = α / 2β for best-of-n, and d = exp(α/β − 1) for RL. Larger proxy reward models had higher peaks further out, which is the paper's support for spending on the reward model.

Best-of-n has a closed-form KL from the initial policy: log n − (n − 1)/n. That makes it a cheap way to probe a reward model before any RL run.

The paper's finding on the KL penalty matters for practice. In their RL setup, varying the KL penalty changed where the run converged but not the gold-reward-versus-KL frontier, so the penalty acted like early stopping. They note the result may be sensitive to hyperparameters. The practical reading: a KL penalty is a stopping mechanism, not a fix for a bad reward model, and you still need a gold-like measurement to choose where to stop.

## Choosing a reward source and naming the exploit

A decision procedure for one task:

1. Can a program check the output (tests, a parser against a known answer, a schema)? Use the rule, and name its weak edges: which wrong outputs pass. Write adversarial cases for those edges before the run.
2. If quality is a judgement (helpfulness, tone, completeness), train a pairwise or generative reward model, and list the features that separate chosen from rejected in your data that are not the quality you want: length, hedging, citations, formatting. Each is a direction the policy will move in.
3. If you think step-level rewards will help, decide whether you are reranking (where Lightman et al.'s result applies) or optimising (where R1's three reasons apply).
4. In every case, keep a held-out signal the policy never trains against (human ratings on a fixed prompt set, or a stronger judge) and plot it against KL from the starting policy. That plot is the stopping rule.

Combined rewards are common: R1's final reasoning reward adds a language-consistency term, the proportion of target-language words in the chain of thought. The paper reports that it slightly lowered benchmark performance and kept it for readability, a stated trade of measured accuracy for a property users see.

```python
import re

def extract_boxed(text):
    return re.findall(r"\\boxed\{([^{}]*)\}", text)

def normalise(ans):
    return ans.replace(" ", "").rstrip(".").lower()

def reward(text, gold, n_tokens, max_tokens=4096):
    """A rule-based reward with two known exploits closed."""
    finals = extract_boxed(text)
    if len(finals) != 1:
        return 0.0          # several boxed answers would let the policy hedge
    if n_tokens > max_tokens:
        return 0.0          # truncated reasoning earns nothing
    return 1.0 if normalise(finals[0]) == normalise(gold) else 0.0

assert reward(r"so \boxed{42}.", "42", 300) == 1.0
assert reward(r"\boxed{41} or \boxed{42}", "42", 300) == 0.0
```

<p><strong>Spend the labels where the model is uncertain.</strong> Sample pairs from the SFT policy (the distribution RL will start from), and spend part of the budget on pairs the current reward model scores as close, which is where its errors are.</p>

## When this is wrong

Gao et al.'s gold reward model is itself a model, not people, and their policy and proxies are from 2022. The functional forms are empirical fits in that setup; use them to reason about shape (a peak exists and moves out with a better proxy), not to predict a step count for your run.

Lightman et al.'s 78% is on a subset of MATH with a 2023 base model, reranking samples rather than training against the PRM. R1's objections are about optimising against a learned step judge for many RL steps; a PRM used only to rerank samples is exposed to the weaknesses that reranking can find, which is a smaller search.

A rule-based reward is only as good as its checks. Tests that miss edge cases, answer extraction that accepts several answers, and format rewards with no accuracy gate have all produced policies that score well and do the task badly. Audit the rule with outputs written to break it, the same way you would review a security control.
