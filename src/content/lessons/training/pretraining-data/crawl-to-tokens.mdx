A web corpus is the output of a pipeline of passes over Common Crawl: extract text from HTML, identify the language, drop documents with heuristic filters, deduplicate, and score what is left with a quality classifier. Each pass deletes tokens. The pipeline resembles a compiler's pass list, and the difference is the test suite: no unit test says whether a filter was right. The accepted test is to train a small model on the corpus with and without the pass and compare benchmark scores. Two open efforts, FineWeb and DataComp-LM (DCLM), published the ablations behind each pass, and their numbers are the best public guide to what each stage is worth.

## The stages, with the numbers behind each

**Extraction.** Common Crawl ships raw HTML (WARC files) and its own pre-extracted text (WET files). Both FineWeb and DCLM re-extracted from HTML. FineWeb found trafilatura on WARC trained clearly better models than WET, which keeps menus and boilerplate; DCLM found resiliparse beat WET by at least 2.5 points on its Core benchmark average. Extraction is the most expensive pass to rerun, because it touches every byte of HTML, so it is the one to settle first.

**Language identification.** FineWeb keeps documents that a fastText language classifier scores at 0.65 or higher for English. After extraction, language ID, a URL blocklist and MassiveText's quality and repetition filters, FineWeb had about 36T GPT-2 tokens across 96 snapshots. The threshold is a precision-recall choice made per language; a single global threshold over-filters languages where the classifier is less confident, which matters again in the lesson on [benchmarks that move for the wrong reason](/learn/training/pretraining-data/benchmarks-wrong-reason).

**Heuristic filters.** These are cheap per-document rules. FineWeb adopted C4's rules except one: the terminal-punctuation rule alone removed about 30% of tokens, and the ablation did not justify that loss. It then built its own. The team computed over 50 statistics on a high-quality and a low-quality snapshot, turned the largest differences into 16 candidate filters, and kept three that won ablations:

| Filter (drop the document if) | Tokens removed |
|---|---|
| fraction of lines ending in punctuation is at most 0.12 | 10.14% |
| fraction of characters in duplicated lines is at least 0.1 | 12.47% |
| fraction of lines shorter than 30 characters is at least 0.67 | 3.73% |

Together the three removed about 22% of tokens and raised the aggregate benchmark score by about one point in 28B-token ablations.

**Deduplication.** The [next lesson](/learn/training/pretraining-data/dedup-levels) covers it in full. The result that shapes the rest of the stack: FineWeb deduplicated each snapshot on its own with MinHash, because deduplicating globally across all 96 snapshots removed up to 90% of the oldest snapshots and the data that survived was worse than the data removed.

**Model-based quality filtering.** This is the stage DCLM found decisive. A classifier scores each document for resemblance to a reference set, and a threshold keeps the top slice. DCLM's winner is a fastText classifier with positives drawn from OpenHermes 2.5 instruction data and high-scoring r/ExplainLikeImFive posts, negatives sampled from a RefinedWeb reproduction, keeping the top 10% of documents. At the 1B-1x scale DCLM compared it with alternatives on the Core average:

| Filter | Core |
|---|---|
| fastText, OpenHermes 2.5 plus ELI5 positives | 30.2 |
| top-k average logits | 29.2 |
| perplexity filtering | 29.0 |
| AskLLM | 28.6 |
| RefinedWeb reproduction (heuristics only) | 27.5 |
| PageRank, top 20% | 26.1 |

At 7B and 280B tokens, the filter choice alone moved MMLU from 35% to 44%. The resulting DCLM-Baseline, about 3.8T tokens from a 240T-token pool, trained a 7B model to 64% 5-shot MMLU on 2.6T tokens (63.7 in the paper's table) when mixed with StarCoder and ProofPile2 data. DCLM also reports that human judgments of document quality were of limited use in picking the classifier: the cheap model trained on instruction-like positives beat filters that looked more principled.

FineWeb-Edu took the other common route, an LLM-labelled classifier. Llama-3-70B-Instruct scored 460,000 pages from 0 to 5 for educational value; a linear regression head on the snowflake-arctic-embed-m embedding model, trained on 410,000 of those labels, reached 82% F1 at a threshold of 3. Classifying all 15T FineWeb tokens took 6,000 H100 hours, about 690,000 tokens per GPU-second (15 × 10<sup>12</sup> / (6,000 × 3,600)). Keeping documents at 3 or above left 1.3T tokens and, at 350B-token ablation scale, raised MMLU from 33% to 37% and ARC from 46% to 57%.

## The stack as code

The heuristic stage is a sequence of predicates, each with a threshold an ablation picked. Keeping each rule separately named makes its marginal removal measurable, which is the number the ablation plan needs.

```python
def lines(doc):
    return [l for l in doc.splitlines() if l.strip()]

def punct_ratio(doc):
    ls = lines(doc)
    return sum(l.rstrip()[-1] in '.!?"' for l in ls) / max(len(ls), 1)

def dup_line_char_ratio(doc):
    ls, seen, dup = lines(doc), set(), 0
    for l in ls:
        if l in seen:
            dup += len(l)
        seen.add(l)
    return dup / max(sum(map(len, ls)), 1)

def short_line_ratio(doc):
    ls = lines(doc)
    return sum(len(l) < 30 for l in ls) / max(len(ls), 1)

RULES = {  # thresholds from FineWeb's ablations, applied in this order
    "punct": lambda d: punct_ratio(d) <= 0.12,
    "dup_lines": lambda d: dup_line_char_ratio(d) >= 0.1,
    "short_lines": lambda d: short_line_ratio(d) >= 0.67,
}

def apply(docs):
    removed = {name: 0 for name in RULES}
    kept = []
    for d in docs:
        hit = next((name for name, rule in RULES.items() if rule(d)), None)
        if hit:
            removed[hit] += len(d.split())  # charged to the first rule that fires
        else:
            kept.append(d)
    return kept, removed

nav = "Home\nAbout\nContact\nLogin\nHome\nAbout"
prose = "The kernel fuses the two matmuls into one launch.\nIt saves a round trip to HBM."
print(apply([nav, prose]))
```

The navigation page fails all three rules and the prose passes. Because removal is charged in stack order, the marginal cost of each rule depends on its position; FineWeb's percentages above are per rule, which is why they sum to more than the combined 22%.

## The ablation plan that picks the thresholds

The pipeline is only as good as the experiment that compares variants. FineWeb's setup is the template: one fixed architecture (a 1.71B-parameter Llama-style model with the GPT-2 tokenizer and sequence length 2,048), 28B training tokens for filter ablations and 350B for deduplication and cumulative runs, two models per variant trained on different random subsets with different seeds, and a fixed set of benchmarks. Over 70 models cost about 80,000 H100 hours.

DCLM made the same idea a benchmark with fixed compute scales, where training tokens are 20 times parameters times a multiplier:

| Scale | Parameters | Tokens | H100 hours |
|---|---|---|---|
| 400M-1x | 412M | 8.2B | 26 |
| 1B-1x | 1.4B | 28.8B | 240 |
| 3B-1x | 2.8B | 55.9B | 740 |
| 7B-1x | 6.9B | 138B | 3,700 |

A filter plan at the 1B-1x scale with six variants and two seeds each costs 12 × 240 = 2,880 H100 hours, under 4% of FineWeb's whole ablation budget. Rerunning the two finalists at 3B-1x with two seeds adds 4 × 740 = 2,960. That split, cheap screening and a confirmation one scale up, is what the published rank correlations support: DCLM reports that method rankings at 400M-1x, 1B-1x and 3B-1x correlate with rankings at 7B-1x with Pearson r of 0.838, 0.956 and 0.982. The [ablations lesson](/learn/training/pretraining-data/ablations) covers how to set the noise floor that a difference must clear.

Three rules come out of both papers. Settle stages in pipeline order, because a change upstream invalidates every downstream threshold. Measure each pass as a marginal change on top of the current stack. And keep the classifier's reference set and the evaluation set apart, or the classifier learns the benchmark.

## When this is wrong

The classifier's reference set is a target, and benchmarks reward resemblance to it. DCLM's positives are instruction data and explanatory forum answers; FineWeb-Edu selects educational text, and its largest gains are on MMLU and ARC, which are knowledge and school-science benchmarks. Both are real gains on those evaluations, and both shift the corpus toward the register those benchmarks test. A model for code review, legal text or casual conversation may want a different reference set, and the published ablations cannot tell you, because they measured the benchmarks they selected for.

Small-scale ablations rank variants but do not size effects. DCLM's correlations are about rankings across methods, and the 400M-1x scale ranks at r of 0.838, weak enough that a close call there is not a decision. A filter worth a point at 1B may be worth less or more at 70B, and the published papers do not report that curve for most passes.

The pipelines are English-first. FineWeb's thresholds, DCLM's classifier and most published ablations are English. Line-length and punctuation rules built on English text behave differently on scripts without spaces or with different punctuation conventions; reusing the thresholds without per-language ablation is a choice, and its cost shows up only in per-language evaluation.

Both corpora were built for pretraining from scratch at fixed token budgets. A team that is short on tokens trades filter strictness against repetition, which is a different optimisation, covered in the [playbook on running short of high-quality tokens](/learn/training/pretraining-data/not-enough-tokens).
