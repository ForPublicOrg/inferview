Web text repeats at every granularity: the same URL crawled in many snapshots, the same article syndicated across sites, the same cookie banner on a million pages, the same licence paragraph inside unrelated code. Deduplication is three different operations, one per granularity, with different costs and different failure modes. Llama 3 runs all three: URL-level (keep the most recent version of each URL), document-level (global MinHash), and line-level (drop lines that appear more than 6 times in each bucket of 30M documents, following ccNet). The design question is never whether to deduplicate. It is at which granularity, against which scope, and how far, and the published evidence says the answer to "how far" is not "as far as possible".

## What duplication costs

Lee et al. measured C4 and found one 61-word English sentence 61,036 times in the training set and 61 times in validation. Their exact-substring pass, which matches any span of 50 BPE tokens or longer using a suffix array, found 7.18% of C4's training tokens inside duplicated spans; their near-duplicate pass flagged 3.04% of training examples. 4.60% of C4's validation examples had a near-duplicate in training, which inflates any validation number computed on them.

The headline effect is on memorisation. They sampled 100,000 unprompted generations from 1.5B-parameter models and counted tokens inside a 50-token span copied from training:

| Training set | 1 epoch | 2 epochs |
|---|---|---|
| C4 as published | 1.926% | 1.571% |
| NearDup | 0.189% | 0.264% |
| ExactSubstr | 0.138% | 0.168% |

The "ten times less" in the abstract is a rounding of ratios that run from 1.571 / 0.264 = 6.0 to 1.926 / 0.138 = 14.0 depending on method and epoch. Perplexity did not get worse and in some evaluations dropped by up to 10%. Memorisation is a privacy and licensing risk before it is a quality problem, and it is the cost a team pays by skipping dedup.

## The three levels

**Exact and URL-level.** Hash the normalised document or the URL and keep one. This is a hash join and costs one pass; it catches re-crawls and mirrors and misses everything with a changed timestamp or ad slot. Llama 3 keeps the most recent version per URL, which also makes the corpus date-ordered in a useful way: older versions of a page are dropped, not the page.

**Near-duplicate documents.** MinHash estimates Jaccard similarity between shingle sets (FineWeb and Lee et al. both shingle into word 5-grams). Each document gets a signature of k minimum hash values; the probability that two documents agree on any one value equals their Jaccard similarity s. Locality-sensitive hashing splits the signature into r bands of b values and treats two documents as candidates if any band matches exactly, so the probability of being flagged is

1 - (1 - s<sup>b</sup>)<sup>r</sup>

This is an S-curve whose midpoint is set by b and r. FineWeb uses 112 hashes as 14 bands of 8, aiming at documents about 75% similar or more. Lee et al. use 9,000 hashes as 450 bands of 20 and then confirm candidates with edit similarity above 0.8. Candidate pairs become edges in a graph, connected components become clusters, and one document per cluster survives.

**Lines and substrings.** Document-level dedup leaves boilerplate inside otherwise unique pages: navigation, cookie notices, licence headers, "related articles" blocks. Line-level dedup counts lines across a bucket of documents and deletes the frequent ones; Llama 3's rule is more than 6 occurrences in a bucket of 30M documents. Lee et al.'s exact-substring pass is the finer version, removing any repeated span of 50 tokens. Both edit documents instead of dropping them, which can leave fragments that no longer read as text; heuristic filters after this pass catch some of that, and OLMo 2 adds a filter that drops documents with 32 or more repeated n-grams of 1 to 13 tokens.

## Near-dup in code

The mechanism fits in a page of standard-library Python. This version unions documents as soon as any band collides, which is the connected-components step done incrementally.

```python
import hashlib
import re

def shingles(text, n=5):
    w = re.findall(r"\w+", text.lower())
    return {" ".join(w[i:i + n]) for i in range(max(len(w) - n + 1, 1))}

def h(s, seed):
    d = hashlib.blake2b(s.encode(), digest_size=8, salt=seed.to_bytes(16, "little"))
    return int.from_bytes(d.digest(), "little")

def minhash(sh, k):
    return [min(h(s, i) for s in sh) for i in range(k)]

def near_dup_clusters(docs, b=14, r=8):  # b bands of r hashes, FineWeb's setting
    parent = {d: d for d in docs}
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x
    buckets = {}
    for doc_id, text in docs.items():
        sig = minhash(shingles(text), b * r)
        for band in range(b):
            key = (band, tuple(sig[band * r:(band + 1) * r]))
            if key in buckets:
                parent[find(doc_id)] = find(buckets[key])
            else:
                buckets[key] = doc_id
    clusters = {}
    for d in docs:
        clusters.setdefault(find(d), []).append(d)
    return sorted(clusters.values())

base = ("the scheduler admits a request only when the kv cache has room for its prompt "
        "and the expected output so a long prompt can wait behind many short ones and the "
        "operator sees queueing delay rise before any error appears in the logs")
docs = {
    "a": base,
    "b": base.replace("in the logs", "in the dashboards"),
    "c": "cookie settings accept all reject all manage preferences privacy policy terms of use",
}
print(near_dup_clusters(docs))  # [['a', 'b'], ['c']]
```

At corpus scale the costs move. Signatures dominate memory: in a scenario with 2 billion documents per snapshot, 112 hashes of 4 bytes each is 2 × 10<sup>9</sup> × 112 × 4 = 896 GB, which is why production jobs shard by band, write band keys to disk, and join them as a distributed group-by. The union-find over candidate edges is the step that does not shard cleanly; transitive clustering also chains documents that are not similar to each other through intermediaries, which a confirmation step (Lee et al.'s edit similarity) limits.

## Scope: per snapshot or global

Global dedup sounds strictly better and was not. FineWeb deduplicated across all 96 snapshots and lost up to 90% of the oldest snapshots, leaving 4T tokens that trained models barely better than no dedup at all and well below RefinedWeb. For the 2013-48 snapshot, the roughly 31B tokens that survived global dedup were worse than the tokens removed. The mechanism is selection: content that recurs across years is disproportionately content people kept publishing, mirroring and quoting, so global dedup preferentially removes it and keeps one-off pages. Per-snapshot dedup left 20T tokens and matched RefinedWeb, and FineWeb shipped it. Lighter global variants (URL-only, line-level, three-line windows) also lost to per-snapshot document dedup in FineWeb's ablations.

OLMo 2's microannealing results point the same way from the other end. In 50/50 mixes of a math source and web data, seeing the math source twice scored 66.0 on GSM\* against 63.5 for once, and four times scored 65.0. A small amount of repetition of high-value data helped. Duplication is a weight in the mix, and dedup is the operation that resets every weight to one; whether that reset helps is an empirical question per source.

## When this is wrong

The memorisation numbers are from 1.5B models on C4 with unprompted sampling. Prompted extraction, which is how licensed text is tested, is a different measurement, and a larger model is a different subject; the ratios in Lee et al.'s table are evidence that dedup helps, not an estimate for your model.

Jaccard on word 5-grams is a lexical measure. It misses translations, paraphrases, and templated pages whose shared structure lives in the markup the extractor removed, and it treats two short documents with a shared sentence as more similar than two long ones. For code, whitespace and identifier renaming defeat word shingles, so a code pipeline needs its own normalisation before hashing.

The quality effects are measured on English web text at small scale. FineWeb's global dedup result concerns one corpus and its filters; on a corpus with very different snapshot composition, or at a token budget where repetition is forced anyway, the ranking can change. OLMo 2's repetition result is for a small, high-value math source in an anneal and says nothing about repeating web text during pretraining.

Deduplication against benchmarks is a different job. Removing near-duplicates of evaluation items from training (decontamination) protects the evaluation, not the model, and its thresholds trade false positives on common phrases against missed paraphrases; the [benchmarks lesson](/learn/training/pretraining-data/benchmarks-wrong-reason) covers it.
