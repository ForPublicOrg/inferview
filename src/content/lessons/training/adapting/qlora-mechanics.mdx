## What QLoRA quantises, and what it does not

QLoRA's headline is a 65B model fine-tuned on one 48 GB GPU. Three changes produce it, and each targets a memory term that does not grow with the number of tokens in a step:

1. The frozen base weights are stored in 4-bit NormalFloat (NF4), quantised in blocks of 64 with one scale per block.
2. The per-block scales are themselves quantised ("double quantisation"): 8-bit floats in blocks of 256, with one 32-bit constant per block of scales.
3. Optimizer state can be paged to CPU memory through NVIDIA unified memory when the GPU runs short, and paged back for the update.

Everything that does compute stays in higher precision. The storage type is NF4, the compute type is BF16: each base weight block is dequantised to BF16 for the forward and backward matmuls, the LoRA adapters live in higher precision and are the only parameters that receive gradients, and activations are BF16. Nothing in QLoRA makes activations smaller. That one sentence predicts where it breaks.

## The storage arithmetic

NF4 is 4 bits per weight. With a 32-bit scale per 64 weights, the scales add 32 / 64 = 0.5 bits per weight. Double quantisation stores those scales as 8-bit floats, 8 / 64 = 0.125 bits per weight, plus one 32-bit constant per 256 scales, 32 / (64 x 256) = 0.002 bits. The total for constants falls from 0.5 to 0.127 bits per weight, a saving of 0.373 bits.

For LLaMA 65B (80 layers, hidden size 8,192, MLP size 22,016, vocabulary 32,000), the linear layers inside the blocks hold 80 x (4 x 8,192^2 + 3 x 8,192 x 22,016) = 64.76B parameters. At 4.127 bits that is 33.4 GB. Double quantisation's 0.373 bits on those parameters is 3.0 GB, the paper's "about 3 GB". Keeping the embedding and output head in BF16 (an assumption here; check what your quantisation config skips) adds 2 x 32,000 x 8,192 x 2 bytes = 1.05 GB. Base model: 34.5 GB, against 130.6 GB for the same 65.28B parameters in BF16.

## The adapter and its optimizer state

QLoRA's Guanaco runs used rank 64 with `alpha` 16 on every linear layer, and the paper's own ablation says adapters on all linear layers are what make 4-bit fine-tuning match 16-bit full fine-tuning; query-and-value-only adapters do not. On LLaMA 65B that adapter is:

- attention, four projections of 8,192 to 8,192: 4 x 64 x 16,384 = 4.19M per layer
- MLP, three projections between 8,192 and 22,016: 3 x 64 x 30,208 = 5.80M per layer
- 80 layers: 0.80B parameters, 1.2% of the model

With BF16 adapter weights and gradients and FP32 Adam moments, that is 2 + 2 + 8 = 12 bytes per parameter, 9.6 GB, of which the Adam moments are 6.4 GB. Keeping an FP32 master copy of the adapter adds 4 bytes per parameter. Either way the adapter's training state is about a quarter the size of the 4-bit base, which is why rank was not the lever for memory and why the paper could put adapters on every layer.

## Activations: the term QLoRA leaves alone

The paper's own measurement for LLaMA 7B on FLAN v2 at batch 1: LoRA input gradients took 567 MB and the LoRA parameters 26 MB, next to a 5,048 MB 4-bit base. With gradient checkpointing the input gradients fell to about 18 MB per sequence. The authors' conclusion is that activation gradients, not adapters, dominate the trainable side of the budget, and their Figure 6 was measured at sequence length 512, batch 1, with checkpointing on. Longer sequences and larger batches are outside that figure.

With checkpointing at every layer boundary, the stored activations are one hidden-state vector per token per layer: 80 x 8,192 x 2 bytes = 1.31 MB per token for 65B. The logits for the loss add vocabulary x 4 bytes in FP32, 0.128 MB per token. Neither depends on how the weights are stored. During the backward pass one layer at a time is recomputed, and its working set (attention and MLP intermediates for every token in the micro-batch) comes on top; it also scales with tokens.

## Paged optimizers: a spike absorber, not free memory

Paged optimizers move optimizer state to CPU RAM when the GPU runs out and fetch it back when the optimizer step needs it, the same mechanism as virtual-memory paging between RAM and disk. The paper reports regular-speed training for 65B on 48 GB GPUs at batch 16 with paging enabled, and names the purpose as handling memory spikes, such as a batch of unusually long sequences under group-by-length batching. If the steady state does not fit, every step pays a round trip of the paged state over the host link; for the 65B adapter above that is 6.4 GB each way per step. A run tuned to rely on paging every step is slower than one sized to fit, and the profile to request before trusting it is the per-step time with and without paging.

## Where QLoRA stops helping

- **Long sequences and big batches.** Checkpointed activations grow linearly with tokens per micro-batch; at 8,192 tokens they are 10.7 GB for 65B, a third of the whole 4-bit base. Gradient accumulation, not a larger micro-batch, is how the paper's 65B runs reached their batch sizes on one GPU.
- **Large vocabularies.** The FP32 logits term is vocabulary x 4 bytes per token. At 32,000 it is small; a model with a vocabulary several times larger multiplies it by the same factor, and chunked loss computation matters more than weight format.
- **Throughput.** Every matmul dequantises its weight block first. QLoRA buys memory with compute; the abstract's claims are about memory and quality, not speed.
- **Merging.** The adapter learned a correction to the dequantised NF4 weights, not to the original BF16 weights. Merging it into the original BF16 checkpoint gives a model the adapter was never trained against, and requantising the merged weights to 4-bit adds fresh quantisation error to the adapter's contribution. Serving the adapter unmerged on top of the same NF4 base reproduces training exactly. PEFT's `loftq` initialisation exists to reduce the quantisation error the adapter starts from.

## When this is wrong

The memory arithmetic counts the terms named here and assumes checkpointing at every layer boundary; real frameworks add allocator fragmentation, temporary dequantised blocks, communication buffers and the CUDA context, which is what the reserve stands in for, and the reserve has to be measured. The 99.3% figure is the paper's own result on its chatbot benchmark, judged as the paper describes, and does not transfer to a different task. NF4's design assumes normally distributed weights; models or layers whose weights are far from that distribution lose more to quantisation, and the only check is a comparison against a 16-bit adapter run on the same data. Newer GPUs with native low-precision formats change the compute side of the trade, not the activation term.
