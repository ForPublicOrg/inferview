export const pairedReport = `import math

def wilson(hits, n, z=1.96):
    p = hits / n
    centre = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return centre - half, centre + half

def flips(before, after):
    """before, after: question id -> True if that run got it right."""
    fixed = sorted(q for q in before if after[q] and not before[q])
    broken = sorted(q for q in before if before[q] and not after[q])
    return fixed, broken

def sign_test(fixed, broken):
    """Exact two-sided p-value on the questions that changed; unchanged ones carry no information."""
    n, k = fixed + broken, min(fixed, broken)
    if n == 0:
        return 1.0
    tail = sum(math.comb(n, i) for i in range(k + 1)) / 2 ** n
    return min(1.0, 2 * tail)

def report(before, after):
    n = len(before)
    for name, run in (("baseline", before), ("change", after)):
        hits = sum(run.values())
        lo, hi = wilson(hits, n)
        print(f"{name}: {hits}/{n} (95% interval {lo:.0%} to {hi:.0%})")
    fixed, broken = flips(before, after)
    print(f"fixed {fixed}, broke {broken}, sign test p = {sign_test(len(fixed), len(broken)):.3f}")
`;

## What a reviewer can see

A take-home reviewer reads the README, runs the one command it gives, skims the tests and opens two or three files. They cannot ask why a component is missing, so every omission is either explained in the repository or counted against you. That is the design problem: the repository has to carry the reasoning a design review would carry, for a reader with less time than you had.

The published criteria are short. OpenAI's interview guide lists take-home projects among the skills assessments that vary by team, and for its engineering final interviews names four things it generally looks for: well-designed solutions, high-quality code, optimal performance and good test coverage. Feature count is not on the list. The same page says expectations for AI tools vary by interview and are stated in the preparation materials. Anthropic's candidate guidance, last updated 10 July 2025, says take-homes are done without Claude unless Anthropic says otherwise. Read the policy in the brief before planning, because it decides whether "how I used AI" is a section of your report or an admission that disqualifies the submission.

## Why take-homes moved toward judgement

Anthropic's January 2026 post on its performance-engineering take-home is the most detailed public account of a take-home being redesigned as models improved, and it shows what reviewers now weigh.

The original, designed in November 2023 and used from early 2024, was a Python simulator of an accelerator with scratchpad memory, VLIW, SIMD and multiple cores, and a tree-traversal kernel to optimise. Over 1,000 candidates took it. The limit went from 4 hours to 2 because scheduling delayed the pipeline. By May 2025, the post says, Claude 3.7 Sonnet was good enough that over half of candidates would have scored better by handing the whole task to Claude Code, and a pre-release Claude Opus 4 then beat almost all humans within 4 hours. Version 2 dropped multicore, cleaned up the starter code and shifted weight from debugging and code volume to optimisation insight. A pre-release Claude Opus 4.5 then matched the best human score within 2 hours. Version 3 is a set of puzzles on a tiny instruction set, shipped with no visualisation or debugging tools and starter code that only checks validity; the post says judgement about how much to invest in tooling is part of the signal.

The detail that matters most for anyone writing a take-home report is in the README of the published challenge. None of the submissions received on the first day below 1,300 cycles were valid; in each case a language model had modified the tests. The README asks submitters to show that `git diff origin/main tests/` is empty. A reviewer who has seen that will check the same thing in your repository, and a report that states how correctness was verified, by which command, against tests you did not edit, answers the check before it is made.

Two consequences hold for any take-home, not only performance ones. When the brief allows AI, working code is weak evidence on its own, so the signal moves to the decisions a model did not make for you: scope, the eval you trusted, the trade-off you wrote down. And the integrity of your verification is now something a reviewer inspects rather than assumes.

## Scoping a three-to-four-hour brief

The brief techinterview.org quotes is typical of applied-AI take-homes: 50 markdown documents, build a Q&A system, write a 20-question eval set, report recall@5 and faithfulness. A second variant it describes gives thirty input and output pairs with human labels and asks for an automated faithfulness and relevance eval calibrated against them. Neither states a time limit. The plan below assumes three to four hours and does not depend on the exact number.

The order of work follows from what the reviewer reads first. Build the eval before the system, because the eval is the deliverable that makes every other claim checkable. Then the simplest pipeline that produces numbers end to end. Then one change chosen by reading the failures, not a list of techniques. Then the report and a run from a clean clone. Set one checkpoint: if the pipeline is not producing numbers by the midpoint, the improvement is cut and the report describes the baseline.

| Component | Build or cut | The line in the README |
|---|---|---|
| Question set with gold evidence ids | build first | how questions were written and why not generated from chunks |
| In-memory index over 50 documents | build | why no database server at this size |
| One retrieval change (reranker, hybrid, chunk size) | build if the failures point at it | which failure bucket it targets |
| Judge for faithfulness | build, with agreement measured | agreement with your own labels |
| Web UI | cut | a command line produces every number in the report |
| Caching, deployment, auth | cut | not exercised by the eval |
| Fine-tuning, multi-agent orchestration | cut | no failure in the eval points at them |

The cut column is evidence of judgement only if each line has a reason tied to the brief or the eval. The same items half-built read the other way: a reviewer who finds a UI that crashes has learned how you spend time.

## The report a reviewer reads first

The README is a short eval report: the command, the numbers with their sample size, the change and what it moved, the failures by type with one real example each, how the judge was checked, how AI tools were used if allowed, what was cut and why, and the next thing you would build.

Sample size is where most reports overclaim. A 20-question set is enough to find failure types and nowhere near enough to rank two systems.

<p>n = 1.96² × 0.75 × 0.25 / 0.05² = 3.8416 × 0.1875 / 0.0025 = 288.1, so 289 questions. At n = 20 the same formula gives about 19 points either side. No take-home produces 289 labelled questions, so the report cannot rank two configurations by their percentages. It can still say which questions changed, and that paired comparison has more power than the two marginal rates.</p>

When a change goes from 15/20 to 16/20, the headline hides what happened. The cell below takes a per-question result for each run, lists the questions that flipped in each direction, and runs an exact sign test on the flips only. Run it and read the three printed lines.

<CodeRunner id="lesson-rounds-thd-paired" title="Paired flips and an honest interval" starter={pairedReport} tests={pairedTests} gradable={false} />

Three fixed and two broken gives p = 1.0: the change moved five questions and the net effect is indistinguishable from noise. The last assertion is the planning number. With no breakages, five clean fixes is still above 0.05 (2 × 0.5⁵ = 0.0625) and six is below it (2 × 0.5⁶ = 0.031). On a 20-question set, a change has to fix six questions and break none before the eval supports a claim, so the README line for this run is "15/20 baseline, 16/20 after the reranker; it fixed q16 to q18 and broke q03 and q09, shown below; the set is too small to call the difference."

The judge needs the same treatment. In the labelled-pairs variant, the human labels are the ground truth and the judge is the system under test.

<Predict id="rounds-thd-judge-base" question="What raw agreement with the human labels does a judge get if it answers faithful every time, in percent?" answer={80} tolerance={0.5} unit="%">
<Fragment slot="prompt">
<p>Of the thirty labelled pairs, the humans marked 24 faithful and 6 unfaithful.</p>
</Fragment>
<p>24 of 30, so 80%. Now take a real judge that agrees on 26 of 30: it calls 23 of the 24 faithful answers faithful and catches 3 of the 6 unfaithful ones. Raw agreement is 87%, seven points above a judge that does nothing. Expected agreement by chance is 0.8 × 26/30 + 0.2 × 4/30 = 0.72, so Cohen's kappa is (0.867 − 0.72) / (1 − 0.72) = 0.52. The sentence the report needs is about the class that matters: the judge catches 3 of the 6 unfaithful answers. That tells a reviewer how much of the faithfulness score to believe.</p>
</Predict>

If AI tools were allowed, the report says where they wrote code and how that code was verified: which tests you wrote by hand, and that the test directory was not edited by the tool. If they were not allowed, the report does not mention them.

The practice for this lesson is [the RAG take-home plan](/problems/rnd-010), which asks you to decide the deliverables without a list.

<Fragment slot="long">
<p>The constraints conflict on the remaining ninety minutes: the reranker is the only evidence I can improve the system, and the report and clean run are the only evidence the numbers are real. A reviewer who cannot reproduce 12/20 learns nothing from a later 15/20, so the report and the run go first.</p>
<p>Then I read the eight misses. If most have the gold chunk at rank six to twenty, the reranker targets them and I can say so with counts, for example "five of eight misses have the gold chunk in the top twenty." If most have it outside the top twenty, a reranker cannot help and the report says the next change is chunking or query rewriting. Either way the report states the upper bound on what the planned change could recover, which is more useful than a rushed run that moves two questions.</p>
<p>The cut list names the reranker, the reason (time, after the run and report), and the measurement I would use to judge it: flips on the existing 20 plus a larger question set, since six clean fixes is the smallest result this set can show.</p>

## When this is wrong

Most companies do not publish take-home rubrics. The OpenAI criteria and the Anthropic post are the official texts found for this lesson; the brief comes from a prep site, and grading beyond that varies by team. When a brief says what it values, the brief wins.

Some take-homes are scored on one number. Anthropic's performance take-home is graded in cycles, and a strong submission there is the fastest correct kernel with untouched tests, not a scoped README. Research take-homes may value one careful experiment over working software. Identify which kind you have before deciding where the hours go.

The sign-test arithmetic assumes questions are independent and equally weighted. Twenty questions written from three documents are not independent, and a reviewer who sees that will discount the eval more than any interval suggests. When the question set is the weak part, the report says so first.

The cut list is a judgement, not data. If the recruiter says the team wants a UI, the UI is in scope, and one question before starting costs less than four hours on the wrong deliverable.
