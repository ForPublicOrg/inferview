## The decision

The decision in a build-and-defend work sample is how to divide the window between product surface, the parts the review will inspect, and verification, and it is made mostly before the window opens.

Sierra's April 2026 post is the clearest official description of the format. Sierra removed its coding and algorithms interviews, replaced the coding phone screen with system design, and runs an onsite in three parts. Plan is a working session where the candidate defines a product, ideally from their own domain, while interviewers ask questions that sharpen it. In Build the interviewer steps out and the candidate builds for over 2 hours with the AI tools and frameworks of their choice, free to pivot or cut scope. Review is a demo, a discussion of product flows, a code review for technical judgement (data model, abstractions, extensibility), the path to production and how AI was used along the way. The post says the criteria are shared in advance, including that cutting scope and skipping boilerplate such as CRUD and auth is fine, and that interviews run in pairs to calibrate.

The review is the half that scores. What the reviewers can assess is whether the data model fits the product, whether one abstraction was chosen for a reason, whether the candidate knows which code they verified and how, and whether the path to production is concrete.

## The inputs that change it

**Window length.** Reported windows range widely. Sierra's is over 2 hours. Cognition's CEO, in an April 2026 press interview, described "a few hours" to build a product surface with as much AI as the candidate wants. One candidate report from a new-grad engineer describes a remote day of 8 to 9 hours at Cursor. A vendor page on OpenAI's forward deployed engineer loop, built mainly from one first-person account, reports a take-home of about five hours. The shorter the window, the larger the share the plan and the reserved end take.

**Greenfield or an existing codebase.** In the Cursor report the candidate was given part of the company's codebase and told to pick something to build and present it. That changes what the review asks: whether the feature belongs in that service, and whether something like it already exists. Greenfield formats ask instead whether your own data model is right.

**Who chooses the product.** Sierra asks for an idea from the candidate's domain. That is an advantage only if the plan narrows it to one user and one flow; a domain you know well tempts you into scope you cannot build.

**The review medium.** A live code review rewards a small codebase whose structure you can explain file by file. The reported OpenAI format grades a recorded walkthrough for customer-demo quality, which moves time toward the demo path, an eval result you can show and a cost note.

**The AI policy.** Sierra and Cognition make AI use part of the evaluation, and the Cursor report describes AI tools in use on the build day. That makes verification a first-class deliverable. The README of Anthropic's published performance take-home reports that none of the first-day submissions below 1,300 cycles were valid, because in each case a language model had modified the tests. A reviewer asking how you used AI is asking which code you checked, and against what.

## The options and when each wins

**A thin vertical slice with one hard part done properly.** One user, one flow, end to end, with the part that makes the product non-trivial (a model call with a schema-checked output and a small labelled check, a matching rule, a state machine) built and tested, and everything else stubbed or fixture-backed. Wins when the review includes code review of the data model and abstractions, as Sierra's does, because every file the reviewer opens is load-bearing.

**A broad surface with stubs.** Many screens or endpoints, most backed by fakes. Wins only when the format grades the product surface itself and the review is a demo, which is closest to the Cognition description. It loses badly in a code review, where the reviewer opens a stub.

**Foundation first.** Data model, interfaces and tests, with a thin UI or a command line. Wins in an existing codebase on a long window, where the review asks whether the change fits the service and the questions in the Cursor report (why this service, is that already in our codebase, what are the trade-offs if it is new) are about integration rather than surface.

**Slice plus demo polish.** The thin slice, with the demo path rehearsed, one eval number on screen and a cost and latency note. Wins when the review is a recorded walkthrough, as in the reported OpenAI format.

## Spending the plan and the build

The plan is where scope is cut, because during the build every cut costs a context switch. Leave the plan with five things written down: the user and the one flow; the data model as entities and the fields that matter; the one hard part; the cut list (auth, CRUD screens, real integrations behind a fixture, deployment); and the order of work, with the point at which you stop adding.

The build has three checkpoints. First, a walking skeleton: the one flow running end to end on fixture data with the hard part stubbed. Second, the hard part replaced with the real implementation and its check passing. Third, the stop point, after which only the README, the clean run and the demo path change. Commit at each checkpoint; the history shows the review how you worked.

With an agent writing much of the code, decide before the build which tests you write by hand and tell the agent not to edit them, as the Anthropic README recommends for its test folder. Keep a short log of what you asked the agent to do and what you checked, because "how did you use AI" is a review topic at Sierra and a one-line answer is weak evidence.

## Worked decision: a carrier-exception desk in Sierra's format

Scenario (constructed for this lesson): a candidate who has worked in logistics proposes a tool for support agents. Carrier status events arrive; the tool classifies each delivery exception, drafts a customer message, and the agent approves, edits or rejects the draft.

The plan narrows it to one flow: a fixture file of carrier events goes in, the agent sees a queue of exceptions with drafts, and approves or edits one. The data model is four entities. A shipment holds the customer and the promised date. A carrier event holds the raw code and text and is keyed by the carrier's event id, so a duplicate delivery of the same event is ignored. An exception holds the shipment, a kind from a fixed enum (delayed, damaged, address problem, lost, other), the ids of the events that support it, and the prompt version that classified it. A draft holds the exception, the text, its status and who changed it. Drafts are separate from exceptions because one exception can produce several drafts as events arrive, and the edits agents make are the labelled data a later version would learn from.

The one hard part is classification: a model call that must return the enum and evidence ids, validated against a schema, with a rules fallback for unknown carrier codes. Its check is a dozen hand-labelled fixture events with the expected kind, run as a test the candidate writes before asking the agent to implement the classifier. The abstraction worth defending is a classifier interface with two implementations, model and rules, because that is the seam the path-to-production answer depends on.

Cut, with reasons in the README: auth (single-user demo, in Sierra's published advice), admin CRUD for shipments (the fixture is the admin), real carrier integrations (a webhook adapter would emit the same event records), sending messages (approved drafts are logged).

The path to production, prepared for the review rather than built: carrier webhooks into the same event table with the event id as idempotency key; prompt version stored on every exception so a regression can be traced; the labelled fixture grown from agent edits and run in CI on every prompt change; customer data handling in drafts.

The order of work: skeleton with a stubbed classifier returning "other"; the labelled check written; the model classifier with schema validation; the approve and edit loop; stop. If the classifier is not passing its check at the second checkpoint, the rules implementation ships and the review discusses why the model version was not ready, with the failing cases on screen.

## What to measure after deciding

Practice runs are the only place to measure this, so time two or three full builds against the clock and record four things. Time to the walking skeleton, which tells you whether your plan was small enough. Minutes spent after the stop point on anything other than the README and demo, which measures scope discipline. The share of review questions you could answer by pointing at a file or a commit, using the reported Cursor questions and Sierra's review topics as the question list. And the agent-written code covered by a test you wrote yourself, which is the honest answer to the AI-use question.

## Self-review rubric

Go through the repository as the reviewer will. [Problem rnd-028](/problems/rnd-028) runs the whole format against this rubric.

| Check | Where the reviewer finds it |
|---|---|
| The one flow runs from a clean clone with one command | README, first line |
| Each entity in the data model exists for a reason you can state | the schema file and its comments |
| One abstraction has two implementations or a stated reason to exist | the interface and its callers |
| The hard part has a check you wrote before the implementation | the test file and the commit order |
| The tests were not edited by the agent after you wrote them | the history of the test file |
| The cut list names each cut and the reason | README |
| The path to production names the first three changes and what they protect | README |
| You can say which files the agent wrote and how each was verified | your log and the commits |

## When this is wrong

The evidence base is thin and uneven. Sierra's post is official and current as of April 2026. The Cognition description is a press report of a CEO's remarks with no stated length beyond "a few hours". The Cursor account is one new-grad candidate's report on a third-party site, about a year old at the check date. The OpenAI format is a vendor's reconstruction from mainly one account. Formats change faster than these pages are updated, and the brief you receive overrides all of them.

The playbook assumes the review inspects code. If a company grades only the demo, the broad-surface option can win, and the thin slice looks unambitious. Sierra publishes its review topics; where a company does not, ask the recruiter what the review covers before the plan.

It also assumes the hard part can be checked in the window. Some products have no checkable core in two hours (a design tool, a visualisation), and the defensible move there is a smaller product, not a check on the wrong part.

Sierra says it amended the format slightly for infrastructure candidates without saying how, so the data-model emphasis here may not carry over to those loops.
