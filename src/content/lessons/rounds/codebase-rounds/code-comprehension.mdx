## The round reads before it writes

Code comprehension is moving from an implicit part of coding rounds to a named one. Entrepreneur reported on 8 May 2026, from a Business Insider story on an internal Google document, that Google is piloting a code comprehension interview for select junior and mid-level software engineering roles on select US teams from the second half of 2026. Candidates use an AI assistant, which a Google spokesperson said is Gemini, to analyse an existing codebase, find bugs, improve performance and refine the code. The document, as reported, says interviewers will evaluate AI fluency, including prompt engineering, output validation and debugging skills.

Meta's AI-enabled round, as Hello Interview describes it from candidate reports, starts the same way: a multi-file codebase with classes, data models and logic the candidate did not write, about five to six minutes of orientation in a 60-minute round, and a first phase that can include explaining the existing unit tests and the code's complexity. The guide quotes internal guidance that candidates should use AI but need to show they understand the code.

The skill is the one used on the first day of any on-call rotation for a service someone else built. The difference in a round is the budget: ten minutes, not an afternoon, and an assistant on screen whose account of the code is fluent whether or not it is right.

## A reading order

Reading top to bottom, file by file, spends the budget on whatever was written first. A fixed order spends it on what determines behaviour.

**Entry points.** Find where control enters: the package `__init__`, the public class, the CLI `main`, the route table, the handler registered with a framework. The entry points are the module's contract; everything else is implementation. A list of three to five entry points with one line each is the skeleton of the explanation.

**One input's path.** Pick one realistic input and follow it from an entry point to its output, noting each transformation and each place state is read or written. One complete path teaches more than a partial reading of every file, because it shows the data model, the layering and the side effects together. Where the path forks on a condition, note the condition and keep to one branch.

**The tests as the specification.** Tests are the only part of the repository that states intended behaviour in executable form. Read them for what is pinned (the behaviours someone cared enough to assert) and, more usefully, for what is not: an untested branch is a branch whose intended behaviour nobody wrote down. Meta's phase one asks for this directly.

**Names and comments last.** A docstring states what the author meant at the time it was written; the code states what happens now. When they disagree, the code wins for behaviour and the disagreement is itself a finding. Reading names first is how a reader, or an assistant, ends up explaining the docstring.

## Ten minutes, allocated

Code Reading Club, which runs group sessions for reading unfamiliar code, publishes its exercises with timings for an hour of group work: a one-minute first glance, ten minutes marking the code's structure (variables, calls and instances, linked to their uses), eight minutes choosing the five most important lines, and five minutes writing a summary, each followed by discussion. Its advanced exercises ask for the decisions made in the code, their consequences and the assumptions behind them.

Compressed for one person and a ten-minute clock, the same sequence becomes a budget. This allocation is a choice, not a measurement: one minute on the file tree and entry points; four minutes following one input; two minutes reading the tests for what they pin and what they leave open; two minutes on the five lines that, if changed, would change behaviour most; one minute writing the explanation. The explanation has a fixed shape: what the module is for in one sentence, its entry points, the path of one input, the invariants and where each is enforced, what the tests leave unpinned, and one risk.

## Practise on two files

The two files below are written for this lesson. Read them in the order above, then answer.

```python
# window.py
def bucket_start(ts, width):
    return ts - ts % width
```

```python
# counter.py
from window import bucket_start


class RecentCounter:
    """Counts events in the last three minutes."""

    def __init__(self, width=60, keep=3):
        self.width, self.keep = width, keep
        self.buckets = {}

    def add(self, ts, n=1):
        b = bucket_start(ts, self.width)
        self.buckets[b] = self.buckets.get(b, 0) + n
        for old in sorted(self.buckets)[:-self.keep]:
            del self.buckets[old]

    def total(self):
        return sum(self.buckets.values())
```

<Fragment slot="prompt">
<p>A fresh <code>RecentCounter()</code> receives <code>add</code> with timestamps 5, 59, 60, 130, 400 and then 10, in that order, one event each. Then <code>total()</code> is called.</p>
</Fragment>
<p>Follow the buckets. After 5, 59, 60 and 130: buckets 0 (two events), 60 and 120. Adding 400 creates bucket 360; there are now four buckets, and the prune keeps the three largest keys, dropping bucket 0. Adding 10 recreates bucket 0 with one event, which is now the smallest key and is pruned at once. The buckets are 60, 120 and 360 with one event each, so <b>total() is 3</b>.</p>
<p>The docstring says "events in the last three minutes". At timestamp 400, the last three minutes contain one event. The code keeps the three most recent buckets that have events, whatever the gap between them, so after a quiet period it reports events from long ago; and it drops a late event silently. Which behaviour is intended is a question for the tests. If no test covers a gap or a late event, neither is pinned, and the explanation says so.</p>
</Predict>

The docstring is the first thing a reader or an assistant sees, and it describes a time window. The code implements a count of non-empty buckets. That gap is the finding, and it only shows to a reader who traced an input instead of reading the names.

## Reading with an assistant

An assistant reads faster than a person and writes a fluent account of any code it is given. The account is a set of claims about the code: this function is called from here, this dictionary holds that, this branch handles that case. Some are right, and a wrong one reads exactly like a right one.

Scenario arithmetic shows why verification has to be selective rather than total. Suppose, as a scenario, an assistant's summary makes 14 checkable claims and each is right with probability 0.95, independently. The chance that every claim is right is 0.95^14 = 0.49, so the summary contains at least one wrong claim about half the time. Checking all 14 costs most of the ten minutes. The working rule is to check the claims the next action depends on: the entry point you are about to edit, the call sites of the function you will change, the condition under which the bug's branch is taken.

Questions that produce checkable answers are worth more than questions that produce prose. "List every call site of `parse_rows` with file and line" can be checked with a search in seconds. "Which tests cover the late-event path?" can be checked by opening them. "Explain what this module does" produces a paragraph whose errors cannot be found without doing the reading it was meant to replace, and in the counter above it would likely repeat the docstring. A one-line probe (call the function with the edge input and print the result) settles a disagreement between the assistant and the code faster than reading either.

The reported Google criteria name output validation explicitly, and the Meta guidance asks candidates to show they understand the code they use.

<Fragment slot="short">
<p>I spend the time on the change, not the module: read the diff, find its entry points and every call site of what it touched, trace one failing reconciliation through the new code, and run it as a probe if I can. On the call I claim only what I checked against lines or a run, say which parts of the assistant's account I did not verify, and recommend rollback if the failing path goes through the change and the change has no data migration that rollback would strand.</p>
</Fragment>
<Fragment slot="long">
<p>Two constraints conflict: 30 minutes is not enough to understand the module, and a rollback decision needs confidence about one specific question, whether the change causes the incident and whether undoing it is safe. So I scope the reading to that question.</p>
<p>Ten minutes on the diff and its blast radius: the functions it changed, their call sites (asked of the assistant as a list with locations, then spot-checked with a search), and whether it changed stored data or only code. Ten minutes on one failing record from the incident, traced through the new path, with a probe run against a copy if the environment allows. Five minutes on the tests the change added or modified, for what they pin. The last five minutes go to writing three lines: what I verified, what I did not, and the recommendation with its condition.</p>
<p>What I give up: I will not understand the module, and if the cause is an interaction with code the change did not touch, I will miss it. I say that on the call. If the change wrote data in a new format, rollback is not free, and I would rather keep it and ship a forward fix than strand records the old code cannot read.</p>

## When this is wrong

The reading order assumes behaviour lives in the code in front of you. In configuration-driven systems, plugin registries, dependency injection and metaprogramming, the entry point is a name in a file the tree view does not highlight, and the path of one input runs through framework code. The first minute then goes to finding the registration, not the function.

Tests as the specification assumes the tests were written to state intent. Tests generated to raise coverage, or written after the fact to match existing output, pin whatever the code did, bugs included; a pinned behaviour is evidence of what someone accepted, not of what was intended.

The 0.95 per claim is a scenario input, not a measured accuracy for any assistant, and claims in a real summary are not independent: an assistant that misreads the data model gets every claim built on it wrong together. That makes the case for checking the claims everything else rests on even stronger, and the arithmetic itself less reliable.

The Google pilot is known from a press report of an internal document, and the Meta format from a prep vendor's account of candidate reports. Neither company has published how comprehension is scored.
