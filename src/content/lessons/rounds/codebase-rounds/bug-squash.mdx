## What the round hands you

A bug-squash round gives you a library you did not write, a behaviour that is wrong, and a clock. The deliverable is the three artefacts an incident review asks for: a reproduction that fails, the smallest change that makes it pass in the module that owns the broken rule, and a test that keeps it fixed. The difference from an incident is what is missing. There are no logs from the failing run, no commit history that introduced the bug, and no owner to ask, and the code is sized so that reading all of it does not fit in the time.

Two reported versions of the round show the range, each labelled by what kind of source it is.

**Stripe, candidate report.** A new-grad candidate's write-up on PracHub, published 17 October 2026, covers an onsite with a separate AI coding round and a combined Integration and Bug Squash round, taken in Python. The candidate's preparation notes list the open-source libraries reported for the bug squash: Mako with three bugs (an AST visitor missing its `visit_arg` method, a template lookup that checked that a path existed but not that it was a file, and a compile failure when an `if`, comment and `endif` block could not trigger a pass), Requests with one (after a 307 redirect the body stream had already been read to the end, so the resent request carried an empty body under a non-zero length header and timed out; the author flags this one as not guaranteed accurate), and Colander with three. The write-up does not state the time limit, whether AI was allowed in that round, or how it was graded.

**Meta, prep vendor describing candidate reports.** Hello Interview's guide to Meta's AI-enabled round, which it dates to a rollout from October 2025, describes a 60-minute round for E5 to E7 and M2 set in one multi-file codebase. Phase one is a bug fix, typically non-algorithmic: a type cast, an off-by-one, a wrong conditional. It can include explaining the existing unit tests and the code's complexity. Whether the assistant may be used in phase one varies by interviewer, and the assistant can read the project files but cannot edit them.

The shared shape is that the bug is reported as a behaviour at the library's public surface and caused somewhere else. Every technique below is about crossing that distance without reading everything in between.

## The loop

**Reproduce at the public boundary.** Write the reported behaviour as a failing test that calls the library the way its user would, before reading any internals. The test is the specification of the bug; until it fails for the reported reason, every hypothesis is untestable. If it passes, the report is incomplete, and the missing condition (an input shape, a platform, a second call) is the first finding.

**Shrink the input.** A reproduction with 4,000 rows or a 600-line template hides the cause in noise. Halve it and keep the half that still fails, as below.

**Localise by following the wrong value backward.** Start where the output is wrong and walk the value back through the call chain, asserting the invariant at each module boundary: type, unit, range, emptiness. The first boundary where the value is already wrong on the way in sits downstream of the defect; the module that produced it owns the bug. A breakpoint or a one-line `print` at each boundary is faster than reading the modules in order.

**Fix in the owning module, minimally.** The fix goes where the invariant is first broken, and changes as little as possible there. A patch where the symptom shows up passes the reported case and leaves every other caller of the broken function still broken.

**Pin it.** Keep the public reproduction as a test, and add one at the boundary where the bug lived, with the smallest input that exercises it. The second test is the one that names the cause for the next reader.

## Bisection when there is no history

With history, the search is over commits. `git bisect run` drives it from a script: exit 0 marks a revision good, any code from 1 to 127 except 125 marks it bad, 125 skips a revision that cannot be tested, and anything else aborts. The search halves the candidate range each step, so a range of N revisions needs about log2 N tests; the documentation's own example prints 675 revisions left as roughly 10 steps, and log2 675 is 9.4.

A bug-squash repository usually has no useful history: the bug was seeded, not committed by someone on a date. The search moves to the input and to the call path. Zeller and Hildebrandt's delta debugging (ddmin) automates the input half. In their Mozilla case study it reduced 896 lines of HTML to the single line that crashed the print path after 57 tests, and the whole study took 139 automated runs. They prove two bounds that set expectations: when one change induces the failure, at most 2 log2 |c| tests for an input of size |c|; in the worst case, when parts of the input only fail together, |c|² + 3|c| tests.

## Three bug classes that cross a file boundary

The reported bugs fall into a few classes that recur in seeded rounds and in real libraries, and each has a characteristic place to look.

**Representation at a parse boundary.** A value enters as text and is converted once, at the edge, into a representation that cannot hold it: binary floats for money, naive datetimes for zoned ones, `int()` on a string with a stray character. Every module downstream is correct and every result is wrong. The symptom shows in the formatter or the total, and the cause is in the parser.

**State consumed by the first attempt.** A request body is a file object or a generator; the first send reads it to the end; a redirect, retry or resend reads it again and gets nothing. Requests handles this explicitly in `resolve_redirects`. Only a 307 or 308 keeps the body; every other redirect drops it along with its length and type headers. When the body is kept and the request recorded a stream position, Requests calls `rewind_body` to seek back, and a body whose position could not be recorded raises `UnrewindableBodyError` rather than hanging the connection. Any retry wrapper around a streamed body needs the same three answers: does this status resend the body, can the stream be rewound, and what happens if it cannot. A Python generator has no rewind, which is why the failure is often an empty body rather than an exception.

**A predicate that accepts more than the author meant.** `os.path.exists` is true for a directory with the template's name; `isinstance(x, int)` is true for `True`; a visitor that dispatches with `getattr(self, "visit_" + kind, self.generic_visit)` silently skips a node type it has no method for. The code reads as correct because the predicate's name matches the intent. The test that finds it uses the input the predicate wrongly admits.

## Practise on original code

The package below is written for this lesson. The reported behaviour: `summarize(["rent,1200.00", "fees,0.29", "fees,0.57"])` displays `1200.84`, and the ledger owner expects `1200.86`. The formatter in `money.py` builds the wrong string and is the first file most readers open; follow the value backward from there. Fix `tally/parse.py`. Hidden tests check other amounts, including signs, whole numbers and one very large amount.

<CodeRunner id="lesson-rounds-bug-squash-tally" title="Fix the ledger" starter={tallyParse} files={tallyFiles} target="tally/parse.py" tests={tallyTests} hidden={tallyHidden} solution={tallySolution} gradable={false} />

The cause is the conversion, not the formatter. `float("0.29") * 100` is `28.999999999999996` and `int` truncates toward zero, giving 28; `0.57` gives `56.99999999999999` and then 56. The two lost cents are the 1200.84.

`int(round(float(text) * 100))` passes the visible tests and fails one hidden test, and the reason is arithmetic rather than taste. A double has a 53-bit significand, so integers above 2^53 = 9,007,199,254,740,992 are not all representable, and amounts above 2^53 / 100, about 90 trillion in major units, cannot all be held to the cent. `float("90071992547409.93") * 100` evaluates to `9007199254740994.0`, one cent high. `Decimal` parses the string exactly and the multiplication by 100 is exact. The reference solution also makes one policy decision the tests leave open: an amount with three decimal places raises instead of rounding. Rounding half-even is equally defensible for some ledgers; either way it is a behaviour change for callers, and belongs in the fix's description.

## Minimal fix or right fix

Three places could absorb this bug: the formatter (it receives cents that are already wrong), the report (every other caller of `parse_amount` stays broken), and the parser. Inside the parser, `round()` is the minimal diff and `Decimal` is the fix for the class. Two inputs decide between them. If the library's callers can send amounts above the float limit or more than two decimals, the minimal diff leaves a known defect, and the class fix changes behaviour for some of those callers. If neither can happen, `round()` is a one-line change a reviewer can verify by reading, and the remaining limit belongs in a comment with the number.

The same procedure applies to the consumed-stream class. Buffering the body in memory before the first send is a minimal fix that works for small bodies and becomes an unbounded allocation for an upload; rewinding a seekable stream and failing loudly on an unseekable one is the Requests choice, and costs a new exception type that callers must handle.

## When this is wrong

The halving arithmetic assumes one deterministic cause. When two rows only fail together, halving separates them and both halves pass; ddmin handles that by testing complements at finer granularity, at a worst case of |c|² + 3|c| runs, which is too slow to do by hand inside a round. When the failure is intermittent (thread timing, set iteration order under a hash seed, a clock), a single run is not evidence, and the reproduction has to pin the seed, the clock or the scheduling before any bisection means anything.

Following the wrong value backward assumes the value is wrong at some boundary. Some bugs are an absence: a missing visitor method, a branch never taken, a resend that should have happened. For those, the tests that pass are as informative as the one that fails, and a coverage run on the reproduction shows which code the failing path never reached.

The round descriptions here are one candidate's notes and one prep vendor's summary. Neither company has published a rubric for its round, so the weight given to the regression test, the narration or the use of an assistant is not known, and a round whose clock is shorter than its codebase's reading time may value a correct minimal fix over the class fix argued above.
