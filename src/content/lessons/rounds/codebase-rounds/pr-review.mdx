## What the round asks

The diff compiles, the tests pass, and the question is what happens when it meets production data. A candidate's report of a Netflix machine learning engineer phone screen in September 2026 describes exactly that: 30 minutes of ML fundamentals and 30 minutes on a PR for a feature pipeline whose tests all passed, with the question of what problems it would cause if it landed. The discussion closed on how to serve the features under different real-time requirements. The candidate found some edge cases, felt they had not answered what the interviewer was after, and was rejected.

Sierra's engineering blog (official, 22 April 2026) describes a piloted round with the same core: a medium-sized codebase, a draft PR from a colleague that adds a cross-cutting feature, and the task of reviewing and improving it while iterating with coding agents. Sierra says the level of AI use is still to be decided, because new models can fix many issues in one shot.

Passing tests narrow the search rather than end it. The defects left are the ones the fixture cannot express: the fixture has five rows, no nulls, a clock passed in by hand, a store that never fails and a process that imports one module. A review against style or naming finds none of them. Bacchelli and Bird's study of review at Microsoft found the same gap in day-to-day practice: finding defects is the main reason developers give for review, reviews turn out to be less about defects than expected, and understanding the change is the hard part. In this round, understanding the change means knowing what the data looks like where it will run.

## Review against failure classes

A feature pipeline has a short list of ways to be correct on a fixture and wrong in production. Each class has one question to put to the diff and one test that would have caught it.

| Class | Question for the diff | Test that catches it |
|---|---|---|
| Time and freshness | Which clock anchors the window, and is it the partition's time or the wall clock? Is the window closed on both ends? | Backfill a past partition with an event after its end; the event must not count. |
| Missing values and coverage | What does a null become, and can anything downstream tell it from a real value? | A fixture with nulls in every column, plus a coverage metric with an alert threshold. |
| Memory and scale | What grows with input size: users, events, distinct keys? | A run on a generated input at production cardinality under a memory cap, or a peak-allocation measurement. |
| Retries and partial failure | If the task dies after half its writes and the scheduler reruns it, what is in the table? | A store that fails once mid-write, a retry, and an exact row count. |
| Cross-cutting effects | What does this change for code that did not import it: shared config, globals, schemas, consumers? | A test that imports a second job after this module and checks its configuration. |
| Training against serving | Does serving compute the same value from the same inputs at the same time? | Log the features used at serving and compare them with the batch values for the same keys. |

The last row comes from Google's Rules of Machine Learning: Rule 29 says the best way to make sure you train like you serve is to save the set of features used at serving time, and Rule 31 warns that a table joined at training and at serving can change in between. Rule 10 gives the shape of the coverage failure, with an example of a feature column populated in 90% of examples suddenly dropping to 60%, and a Play table that had been stale for six months, where refreshing it alone gave a 2% boost in install rate. Neither failure raises an error; both show up as a gradual loss of quality.

## Why each one survived the tests

The PR ships with tests that build features for three users from five events with `now` passed explicitly, write them to a list, and check the counts. Each defect is invisible to that fixture for a specific reason.

Passing `now` in every test is what hides the wall-clock default; the code path that production takes is never executed. The missing upper bound only matters when events exist after `now`, which never happens when `now` is today and always happens in a backfill. Five events cannot show memory growth. A list store never fails halfway. A test process that imports one module cannot see what that import does to another job.

The null default needs arithmetic to show its effect.

## The tests that would have caught them

The code below is the fixed shape of the two functions and three of the tests from the table. It runs as is.

```python
from datetime import datetime, timedelta

WINDOW_DAYS = 30


def build_features(events, users, as_of):
    """Features for the partition ending at as_of: aggregates only, events in [as_of - window, as_of)."""
    start = as_of - timedelta(days=WINDOW_DAYS)
    count, spend = {}, {}
    for e in events:
        if start <= e["ts"] < as_of:
            count[e["user_id"]] = count.get(e["user_id"], 0) + 1
            spend[e["user_id"]] = spend.get(e["user_id"], 0) + e["amount"]
    return [{"user_id": u["id"], "purchases_30d": count.get(u["id"], 0),
             "spend_30d": spend.get(u["id"], 0), "country": u.get("country")} for u in users]


class FlakyStore:
    """Keyed by (partition, user_id); the first write dies after two rows, as a preempted worker would."""
    def __init__(self):
        self.rows, self.failed = {}, False

    def put(self, partition, row):
        if not self.failed and len(self.rows) == 2:
            self.failed = True
            raise ConnectionError("worker preempted")
        self.rows[(partition, row["user_id"])] = row


def write_features(rows, store, partition):
    for r in rows:
        store.put(partition, r)


# Test 1: a retried write leaves exactly one row per user.
users = [{"id": i, "country": None if i % 3 == 0 else "DE"} for i in range(5)]
day = datetime(2026, 10, 1)
events = [{"user_id": 1, "ts": day - timedelta(days=2), "amount": 40},
          {"user_id": 1, "ts": day + timedelta(hours=3), "amount": 99}]  # after the partition: must not count
rows = build_features(events, users, as_of=day)
store = FlakyStore()
for attempt in range(2):
    try:
        write_features(rows, store, "2026-10-01")
        break
    except ConnectionError:
        pass
assert len(store.rows) == len(users), len(store.rows)

# Test 2: a backfill for a past partition ignores events after it.
assert rows[1]["purchases_30d"] == 1 and rows[1]["spend_30d"] == 40

# Test 3: missing country stays missing, so coverage can be measured downstream.
print(sum(r["country"] is None for r in rows) / len(rows))  # 0.4
```

With the PR's `append`, test 1 ends with 7 rows for 5 users: the 2 written before the failure plus 5 on the retry. With the PR's open-ended window, test 2 counts the purchase three hours after the partition. The keyed `put` makes the retry harmless only if the whole partition is rewritten on every run; a run that writes a subset leaves stale rows from the previous run, which is why a staging partition with an atomic swap is the stronger fix when the store supports it.

## Acceptable if

Not every finding blocks the merge, and the review is more useful when it says which ones do. Holding events in memory is acceptable if the input is bounded by contract and the bound is asserted in code: a pipeline over one tenant's day of events at a known ceiling does not need streaming aggregates. A majority-class default is acceptable if the model was trained with the same default and a coverage alert exists, because then the shift is at least visible. A wall-clock default is not acceptable in a function that writes dated partitions, because the failure is silent and lands in training data that outlives the bug.

The cross-cutting mutation is the one a reviewer reading only the diff misses most easily, because the line is correct in isolation. Sierra's pilot frames the whole round around a cross-cutting feature for that reason: the defect is in the interaction with code that is not in the diff.

## When this is wrong

The failure-class list is a prior for batch feature pipelines. A diff to an online service is reviewed against a different list: concurrency and shared state, timeouts and their budgets, authorisation on each new path, and backwards compatibility of the wire format. The method carries over (a question per class, a test per question); the list does not.

Several of the findings depend on facts outside the diff: production cardinality, whether the scheduler retries, whether readers read partial partitions, whether another job imports the shared module. A review that asserts them without asking is guessing. In a round, those are questions to put to the interviewer; at work, they are what the PR description should have stated.

The two round descriptions are one candidate's report and one company's description of a pilot. Neither says how the review was scored, so the weight given to proposing tests, to prioritising findings or to fixing them with an agent is not known.
