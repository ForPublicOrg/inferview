export const evalReport = `import math

def recall_at_k(retrieved, gold, k=5):
    """retrieved: one ranked list of chunk ids per question.
    gold: one set of acceptable chunk ids per question.
    A question counts as a hit if any gold chunk is in its top k."""
    hits = sum(1 for r, g in zip(retrieved, gold) if set(r[:k]) & set(g))
    return hits, len(gold)

def wilson(hits, n, z=1.96):
    """95% Wilson score interval for a proportion; better than p +/- 1.96 se at small n."""
    p = hits / n
    centre = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return centre - half, centre + half

def report(name, hits, n):
    lo, hi = wilson(hits, n)
    return f"{name}: {hits}/{n} = {hits / n:.0%} (95% interval {lo:.0%} to {hi:.0%})"
`;

## Three hours, fifty documents

Scenario: the email arrives on a Friday. "Here are 50 markdown docs. Build a Q&A system, an eval set of 20 questions, and report recall@5 and faithfulness. Please spend no more than three hours." A 2026 guide to applied-AI interviews quotes the first three sentences of this brief almost word for word, along with its live counterpart: "this agent loops forever on some inputs; find out why and fix it." The three-hour limit is this scenario's, chosen because prep guides describe take-homes of about that length.

Both formats grade the same thing from different angles. The take-home shows your judgement when nobody is watching: what you built first, what you cut, and whether your numbers mean what you say they mean. The debug round shows the same judgement under a clock: whether you reproduce before you theorise, and whether you can turn a symptom into a hypothesis you can test in one step.

## A pull request for a sceptical reviewer

The best mental model for a take-home is a pull request to a team that does not know you yet. The reviewer will read the README first, run one command, skim the tests, and open two or three files. They will not read everything, and they cannot ask you questions. So the repository has to answer them.

What reviewers say they look for is published in only a few places. OpenAI's interview guide lists take-home projects among its assessment formats and names its engineering criteria: well-designed solutions, high-quality code, optimal performance and good test coverage. Notice what is missing from that list: feature count. Anthropic's January 2026 post on its performance-engineering take-home lists the principles it designs to, including that the work should be representative of the real job and give candidates many chances to show skill. Neither describes a rubric that rewards breadth.

That same Anthropic post is worth reading for a second reason: it explains why take-homes are changing. The original version was a Python simulator of a fake accelerator, used since early 2024 and completed by more than 1,000 candidates. The time limit went from 4 hours to 2. Then Claude models started matching or beating most applicants within the limit, and the take-home went through further versions; the original is now a public challenge on GitHub. Scores are clock cycles, lower is better:

The practical consequence for you: take-home designers now assume models can produce working code, so the signal they look for is in the parts a model does not decide for you. The scope you chose, the eval you trusted, the trade-off you wrote down. Read the AI policy in the brief before you start. Anthropic's default, per its candidate guidance, is no Claude on take-homes unless the instructions say otherwise, and the performance take-home is an explicit exception. Other companies differ; if the brief is silent, ask.

## Scope first, then build

A plan that fits most three-hour briefs, offered as my allocation rather than a rule: read the brief and set up; build the evaluation; get the simplest pipeline producing numbers end to end; make one improvement chosen by reading failures; and keep the last stretch for the README and a clean run from a fresh clone. If the pipeline is not producing numbers by the halfway point, drop the improvement and report the baseline honestly.

Things to cut, and to list as cut in the README with one reason each: a UI beyond a command line, a database server when an in-memory index holds 50 documents, multi-agent orchestration, fine-tuning, caching, deployment. A reviewer reads a cut list as evidence of scope judgement. The same items half-built read as the opposite.

The README is a short report, not architecture prose. One command to run. A results table. What failed and why, with an example of each failure type. What changed between the baseline and the final version. What you would do with another day. How you used AI tools, if they were allowed.

<p>About 19 points. sqrt(0.75 × 0.25 / 20) = 0.0968, and 1.96 × 0.0968 = 0.190. So "75%" means "somewhere around 56% to 94%" by this approximation, and the Wilson interval in the code cell below gives 53% to 89%. A change from 15/20 to 16/20 is one question. A table of percentages with no sample size, and a claimed improvement smaller than the noise, is an easy way for a good take-home to lose credibility. Put n next to every number. If you made a change, show the questions that flipped in each direction.

## Debug rounds: reproduce, then bisect

The live version gives you code you did not write and a symptom. The habits that score are the ones you use on a real incident, done out loud.

Reproduce first. Run the failing case before reading the whole codebase. Read the trace or log from the start of the failing run, not only the last line; in loop bugs the cause is often several steps before the loop begins.

Form one hypothesis at a time, and make it falsifiable. "If the refund tool is returning a permanent error, then the arguments of the repeated calls are identical." Check that one thing. The interviewer is listening for the shape "if X, then I expect to see Y", and for you to drop a hypothesis when the evidence says no.

Use arithmetic as evidence. If an export is 37 records short and the page size is 100, check whether 37 is the size of the last page. If the bill grows faster than the number of steps, check whether the whole context is being re-sent each step. Numbers that match a hypothesis exactly are the fastest confirmation available.

Fix narrowly, then add the test that would have caught it. In an interview, a one-line fix plus a regression test beats a rewrite.

AI-assisted variants combine both formats. A prep vendor's guide to Meta's AI-enabled round, built from candidate reports, describes one multi-file codebase with a bug-fix phase, an implementation phase and an optimisation phase in about an hour, with the built-in assistant available throughout. Treat the details as reported rather than confirmed; the habits above apply either way, and the next lesson covers working with the assistant.

<p>A table with each metric as a count over n, not only a percentage, for the baseline and the final version. Then the failures sorted into a few types with one example each, the single change I made and which questions it flipped in each direction, and how I checked the faithfulness judge against my own reading. I say plainly what 20 questions can and cannot show, and what I would build next to get a trustworthy number.</p>
</Fragment>
<Fragment slot="long">
<p>Start with what was measured and how. Recall@5 means the gold evidence for a question appears in the top five chunks; I say how I labelled gold evidence and that I wrote the questions from the documents myself rather than generating them from chunks.</p>
<p>Numbers with their sample size: 15/20 baseline, 16/20 final, with a 95% interval if I computed one. On 20 items, a one-question change is not evidence of improvement, and I say so before the reviewer does.</p>
<p>Faithfulness. If an LLM judge scored it, I report how often I agreed with the judge on all 20, because a judge I have not checked is another unknown, not a measurement.</p>
<p>Failure analysis is the most useful part. Retrieval misses, ranking misses where the evidence was just outside the top five, and generation errors, each with a real example from the run. The change I made targeted the biggest bucket, and I show which questions it fixed and which it broke.</p>
<p>Next steps tied to the evidence: grow the eval set, add a reranker if ranking misses dominate, wire the eval into CI so regressions show up.</p>
</Fragment>

## When this is wrong

Most companies do not publish take-home rubrics. The OpenAI criteria and Anthropic principles quoted here are the official texts found for this lesson; everything else about grading comes from candidates and prep vendors, and varies by team. When a brief says what it values, follow the brief over this lesson.

Some take-homes are not RAG or app work at all. Anthropic's performance take-home is scored on a single number, clock cycles, and a strong submission there is the fastest correct kernel, not a well-scoped README. Research-style take-homes may value a careful experiment over working software. Identify the kind before you plan your hours.

The time plan and the cut list are judgement, not data. If a reviewer told you they wanted the UI, build the UI. If you are unsure what they want, one short question to the recruiter before you start is cheaper than three hours spent on the wrong thing.

What I would say in the room: "I build the eval first, ship the simplest thing that produces honest numbers, change one thing because the failures told me to, and write down what I cut."
