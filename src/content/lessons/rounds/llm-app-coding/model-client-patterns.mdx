    """Return ("retry", wait or None), ("stop", None), ("shrink", None) or ("stream", None)."""
    if status == 429:
        details = (body or {}).get("error", {}).get("details", {})
        if details.get("error_code") == "enforced_spend_limit_reached":
            return "stop", None

    if status == 413:

export const poolCode = String.raw`class MicroBatcher:
    """Collect items; flush when max_items are waiting or the oldest has waited max_wait."""
    def __init__(self, flush, max_items, max_wait):
        self.flush, self.max_items, self.max_wait = flush, max_items, max_wait
        self.items, self.first_at = [], None

    def add(self, item, now):
        if not self.items:
            self.first_at = now
        self.items.append(item)
        if len(self.items) >= self.max_items:
            self._send()

    def tick(self, now):
        if self.items and now - self.first_at >= self.max_wait:
            self._send()

    def _send(self):
        batch, self.items = self.items, []
        self.flush(batch)


class Breaker:
    """Opens after threshold consecutive failures; after cooldown lets one probe through."""
    def __init__(self, threshold, cooldown):
        self.threshold, self.cooldown = threshold, cooldown
        self.failures, self.opened_at, self.probing = 0, None, False

    def allow(self, now):
        if self.opened_at is None:
            return True
        if not self.probing and now - self.opened_at >= self.cooldown:
            self.probing = True
            return True
        return False

    def record(self, ok, now):
        if ok:
            self.failures, self.opened_at, self.probing = 0, None, False
            return
        self.failures += 1
        if self.probing or self.failures >= self.threshold:
            self.opened_at, self.probing = now, False


def pick(pool, now):
    """pool: (name, breaker) pairs in preference order."""
    for name, breaker in pool:
        if breaker.allow(now):
            return name
    return None
`;

## Five patterns, each small enough for one round

When a coding round puts a model API in the loop, the model is the least interesting part. What is tested is the client: which failures it retries, how much it sends at once, how it reads a stream, how it groups work, and what it does when a provider is sick. Two candidate reports show the range. Perplexity's technical screen in August 2025, reported on PracHub and filed there as ML system design, asked for the design of a client library that routes across several LLM providers with per-provider rate limits, health checks, circuit breakers with half-open probes, and fallback. Anthropic's screen in September 2025, also via PracHub, was a crawler that ended on "now make it multithreaded".

This lesson writes each pattern once against the Claude API's documented behaviour, checked on 28 October 2026, with the OpenAI Python SDK where it differs. Two of the patterns have full problems in this module: [rnd-006](/problems/rnd-006) parses a stream with awkward chunk boundaries, and [rnd-008](/problems/rnd-008) runs a model call over thousands of documents with a resumable checkpoint.

## Classify before you retry

A retry policy is a function from a failed response to an action, and most bugs are a missing branch. The Claude error reference gives enough to write the function:

Both official Python SDKs already retry. The Anthropic SDK retries connection errors, rate limits and 5xx twice by default, with exponential backoff that honours `retry-after`. The OpenAI SDK retries connection errors, 408, 409, 429 and 5xx twice by default, and does not retry the consumption of a stream, because replaying a request could duplicate output the application already received. A hand-written retry loop around either is therefore a second layer, and its attempts multiply with the SDK's: three attempts around an SDK that makes three is nine requests per call. Pick one layer: set `max_retries=0` and own the policy, or keep the SDK's and add only what it lacks, such as the spend-cap stop.

The cell's `classify` retries everything at 429 and above and ignores `retry-after`, a policy that passes a happy-path test and little else. Fix it so the tests pass; `call_with_retry` takes `sleep` and `rng` as arguments so no test waits.

## Bound concurrency by the token limit, not the thread count

The Claude API rate-limits with a token bucket that refills continuously, along three dimensions per model: requests, input tokens and output tokens per minute. Four documented details change how a client should bound itself:

- On most models only uncached input counts toward ITPM; cache reads do not.
- ITPM is estimated when the request starts and corrected as it runs, so a client-side budget should reserve its estimate up front too.
- `max_tokens` does not count toward OTPM; only generated tokens do.
- Limits may be enforced over shorter intervals: 60 RPM can mean one request per second, so a burst that fits the minute can still draw a 429.

The concurrency a client needs follows from the limit and the latency, not from a guess about threads.

The code is a semaphore around the call plus a reservation against an input-token budget that refills over time; the Anthropic crawler report's "thread pool" is the same bound in a different runtime. The bound does not stay put: when prompt caching lifts the effective input limit, the binding constraint moves to output tokens or requests, and the bound has to be recomputed from whichever dimension now binds.

## Parse the stream as events

A Claude stream is a sequence of server-sent events in a documented order: `message_start`; then for each content block a `content_block_start`, its deltas and a `content_block_stop`; then one or more `message_delta` events; then `message_stop`. `ping` events can appear anywhere. Four rules follow from the docs, and each is a test in rnd-006:

1. Tool arguments arrive as `input_json_delta` fragments in `partial_json`. They are not valid JSON one at a time; accumulate per block index and parse at `content_block_stop`.
2. The usage counts in `message_delta` are cumulative. Summing them over-counts output tokens.
3. An `error` event, such as `overloaded_error`, can arrive after the HTTP status was 200. The status code check has already passed by then, so the stream loop needs its own error path.
4. New event types may be added. Ignore unknown types instead of raising.

Recovery is where the version matters. The streaming docs describe capturing the partial response and continuing; for Claude 4.6 and later the continuation is a new user message that contains the partial text and asks the model to continue, rather than a prefilled assistant turn. Text can be resumed this way. Tool-use and thinking blocks cannot be partially recovered, so a stream that dies inside a tool call is re-requested from the start of that turn.

## Batch inside a window, or hand the batch to the provider

Two different things are called batching. A **micro-batcher** groups items that arrive close together into one call: an embedding request for 64 texts, or one classification prompt over 20 short items. It flushes when it holds `max_items` or when the oldest item has waited `max_wait`, so the latency it adds is bounded by `max_wait`. The bug is a batcher that only flushes on size and holds the last item of a quiet period indefinitely.

A **provider batch** is an asynchronous job. The Message Batches API charges 50 percent of standard prices, takes up to 100,000 requests or 256 MB per batch, finishes most batches within an hour, and expires work not done within 24 hours. Results come back in any order and are matched by `custom_id`, and errored, canceled or expired requests are not billed. It is the right tool when the deadline is hours away, and the wrong one when it is minutes: "most within an hour" is a description, not a promise.

## Keep the provider pool honest

The Perplexity question asks for the design of the whole library. Its core is a circuit breaker per provider: after a threshold of consecutive failures the breaker opens and calls fail fast; after a cooldown exactly one probe goes through; a success closes the breaker, and a failure reopens it for another full cooldown. The pool tries providers in preference order and takes the first whose breaker allows a call. That is passive health checking, driven by real traffic. Active checks, a cheap request on a timer, find a recovered provider when no traffic is going to it, and they cost requests against the same rate limit.

Failover has a cost that is specific to model APIs. On the Claude API, cache reads do not count toward ITPM on most models; the rate-limits page's example has a 2,000,000 ITPM limit admitting 10,000,000 input tokens a minute at an 80 percent cache hit rate. A fallback provider starts with a cold cache, so the same traffic arrives there as uncached input, five times what the primary counted in that example. A fallback sized from the primary's counted tokens will hit its own limit within minutes of a failover. The other cost is behavioural: a different model answers differently, so the prompt and any output parser have to be tested against the fallback before the day it is needed.

The cell runs a micro-batcher, a breaker and the pool's selection with an injected clock in milliseconds. Try one break: remove `self.probing = True` from `allow`, and the half-open test fails because every caller after the cooldown is let through at once.

## When this is wrong

Every number above is the Claude or OpenAI documentation as read on 28 October 2026. Tiers, model names, SDK defaults and the continuation rule for interrupted streams change; the streaming page already documents two continuation rules, one for Claude 4.5 and earlier and one for 4.6 and later. Other providers count limits differently: the rate-limits page notes that many use one combined tokens-per-minute limit, and even on Claude, Haiku 3.5 counts cache reads toward ITPM; the classifier and the token budget have to be rewritten per provider, which is an argument for keeping them behind one interface.

The cells are single-threaded with injected clocks because the browser cannot block. A production client is asynchronous, and the hard parts move: cancellation that releases its semaphore slot and its token reservation, a breaker whose state is shared by every worker, and a micro-batcher whose flush races with its own timer.

Not every model-API round is about the client. Rounds that hand over an agent loop or a retrieval pipeline test other things, and the patterns here are the floor of those rounds rather than their subject. And where an SDK already implements a pattern correctly, the better production choice is often to configure it rather than rewrite it, which a round that asks you to write it from scratch will not show.
