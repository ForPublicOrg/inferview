export const solution = String.raw`class Store:
    def __init__(self):
        self.data = {}        # key -> {field: (value, expires_at or None)}
        self.backups = []     # (taken_at, snapshot) in time order

    def _live(self, ts, key):
        rec = self.data.get(key, {})
        for f in [f for f, (_, exp) in rec.items() if exp is not None and exp <= ts]:
            del rec[f]
        if not rec:
            self.data.pop(key, None)
        return rec

    def set(self, ts, key, field, value, ttl=None):
        rec = self._live(ts, key)
        rec[field] = (value, None if ttl is None else ts + ttl)
        self.data[key] = rec

    def get(self, ts, key, field):
        hit = self._live(ts, key).get(field)
        return None if hit is None else hit[0]

    def delete(self, ts, key, field):
        rec = self._live(ts, key)
        if field not in rec:
            return False
        del rec[field]
        if not rec:
            self.data.pop(key, None)
        return True

    def scan(self, ts, key, prefix=""):
        rec = self._live(ts, key)
        return [f"{f}({v})" for f, (v, _) in sorted(rec.items()) if f.startswith(prefix)]

    def backup(self, ts):
        snap = {}
        for key in list(self.data):
            rec = self._live(ts, key)
            if rec:
                snap[key] = {f: (v, None if exp is None else exp - ts) for f, (v, exp) in rec.items()}
        self.backups.append((ts, snap))
        return len(snap)

    def restore(self, ts, at):
        found = [snap for taken, snap in self.backups if taken <= at]
        if not found:
            return False
        self.data = {key: {f: (v, None if left is None else ts + left) for f, (v, left) in rec.items()}
                     for key, rec in found[-1].items()}
        return True
`;

## The stage-one record shape is a bet on stage four

A progressive round hands over one specification at a time. Stage one is a small CRUD surface; each later stage adds an operation or a rule; the earlier tests keep running; and stage n+1 stays hidden until stage n passes. What gets graded is the program at the end, so the cost of stage three is fixed by choices made in the first ten minutes, before anyone has seen stage three.

Candidates report the format at several AI companies in 2025 and 2026. Everything below is a candidate report or a vendor's summary of reports, and the exercises in this module use original specifications rather than any company's question.

Strip the domain and these specs share four additions on top of CRUD: filtered scans, expiry on an injected clock, snapshots with restore, and a scope that can be undone. Each has a representation that absorbs it in a few lines and one that forces a rewrite. Before reading further, attempt the first two stages of [rnd-023](/problems/rnd-023), an in-memory database specified in four stages; the stage-three and stage-four sections below are about what your stage-one code then costs.

## Scans: keep the record a record

Stage two usually asks for a read over part of a record or of the store: every field of a key that starts with a prefix, sorted; the top n keys by some counter; every file under a directory. A dict of dicts, `data[key][field]`, answers a per-record prefix scan by filtering and sorting at read time, O(f log f) for f fields, with no extra structure. The design that breaks is the flattened one, `data["user1.name"]`, which turns a scan of one record into a scan of the store and is corrupted by the first field name that contains the separator.

Counters are the other stage-two trap. If a later stage might rank keys by how often they changed, the count has to be incremented on every mutating path. A store whose set, delete and restore all go through one write helper adds the counter in one line. A store where each operation mutates the dict directly adds it in every operation, and misses one.

## Expiry: one clock, one read path

Every spec in this family that has TTL passes the time in as an argument, `set(ts, key, field, value, ttl)`, and the store never reads a wall clock. That is what makes the tests deterministic, and it is the same reason production code injects a clock.

Store an absolute expiry per field, `ts + ttl`, and route every read through one function that drops expired entries before answering. Redis does the same on its passive path: a key is expired when a client touches it after its deadline. Redis also runs an active path that periodically samples keys that have an expiry and deletes the expired ones, because keys nobody reads again would otherwise hold memory forever. At interview sizes the passive path is enough. At the 200,000-operation bound on the PracHub page for the Perplexity time-versioned store, a workload whose writes all carry TTLs and whose reads are rare can leave the store holding mostly dead entries.

The bug stage three exposes is a second read path. `get` filters expired fields; `scan`, written in stage two, iterates the dict directly and returns a field that `get` says does not exist. The boundary is the other bug: is a field set at 10 with a ttl of 5 visible at 15? The spec decides. If it is silent, pick one, say which, and pin it with an assert.

## Snapshots: copy the state or keep the log

Stage four asks for backup and restore, or for `get` at a past timestamp. There are two representations, and each is defensible.

A **copy per backup** stores the live state at backup time. Restore is a replacement, O(state). Memory grows with the number of backups times the size of the state, and it cannot answer "what was the value at 37" unless a backup was taken at 37.

A **mutation log** appends every set and delete with its timestamp. A point-in-time `get` is a binary search over that key's history, and a restore pops mutations newer than the target, which is the hint on the PracHub page for the time-versioned store. Memory grows with the number of mutations, and restore costs the mutations undone.

The next stage usually tells you which one you needed. A spec that asks for history queries or range reads wants the log. A spec that asks only to save and load whole states is served by copies, with less code.

TTL interacts with both. When a record is restored, what does its expiry mean? One rule stores the time remaining at backup and re-bases it on restore, so the field lives as long after the restore as it had left at the backup. The other keeps the absolute deadline. Redis takes the second: expiries are stored as absolute Unix timestamps, time keeps flowing while the instance is down, and the Redis documentation warns that an RDB file moved to a machine with a badly skewed clock can have its keys expire at load. Neither rule is wrong. They answer different product questions, and the test pins the one the spec chose.

## Undo and transactions: a journal in the write helper

The Anthropic report's last level restores a record to its state before a lock; KV-store variants add begin, commit and abort, then nesting. Both reduce to saving the prior value of anything a scope touches and replaying those saved values in reverse on abort or undo. With a single write helper, journaling is one line in that helper plus a stack of scopes. Without one, every operation grows its own undo code, and nested scopes are where those copies disagree.

## Tests for every stage, always run

When stage n's text arrives, turn its examples into asserts before writing code, and append them to the same list that holds the earlier stages' asserts. The backward-compatibility rule in the Anthropic report is the failure this catches: a stage-three change that alters stage-one behaviour, such as `get` on a missing field returning an empty string instead of `None` once expiry is involved.

The cell below is a store that already passes stages one to three, written the way this lesson recommends: records as dicts of `(value, expires_at)`, one `_live` read path that every operation goes through, and the clock as an argument. Stage four is yours. `backup(ts)` returns the number of non-empty records it saved; `restore(ts, at)` restores the latest backup taken at or before `at`, re-basing each field's remaining ttl onto `ts`, and returns whether such a backup existed.

## In the room

<Callout kind="interview" label="Interview question">
"Your service keeps feature-flag overrides in an in-process store: per-key fields, overrides with TTLs, prefix scans for the admin UI. After an incident, the on-call team wants to restore the store to any minute in the last 24 hours. It has to ship this sprint, and the process may grow to at most twice today's 50 MB. The store takes about 20 writes a second of about 200 bytes each. What do you build?"
</Callout>

<Depth>
<Fragment slot="short">
<p>Neither in-memory option fits the cap, so history goes to disk: an append-only mutation log plus a periodic checkpoint of the full state. Restoring to minute m loads the newest checkpoint at or before m and replays the log up to m. The process keeps today's memory plus a write buffer. Restored overrides keep their absolute deadlines, because the team wants the flags as they were at 10:42, and an override due to lapse at 11:00 should still lapse at 11:00.</p>
</Fragment>
<Fragment slot="long">
<p>The arithmetic rules out keeping history in memory. A per-minute copy for a day is 1,440 × 50 MB = 72 GB. A log for a day is 20 × 86,400 = 1,728,000 writes, times 200 bytes, about 346 MB. Both exceed the 50 MB of headroom, so history leaves the process.</p>
<p>On disk the choice is between per-minute snapshots, 72 GB written a day with the simplest possible restore, and a log of about 346 MB a day plus hourly checkpoints, 24 × 50 MB = 1.2 GB a day. The log needs a replay path, and replay is the code that has to be right on the worst night. At 20 writes a second an hour of replay is 72,000 mutations, seconds of work. I would ship checkpoints plus log, with a restore that runs the same write helper as live traffic so that counters and any journal stay correct.</p>
<p>What I give up: a corrupt log segment loses every minute after the checkpoint before it, so each segment carries a checksum and the restore refuses to cross a bad one, and says so. The failure mode of the plan is a write that bypasses the helper, an admin bulk import for example, and so never reaches the log. The restore test replays a recorded hour and compares the result with a snapshot taken at the end of that hour, which catches it.</p>
</Fragment>

## When this is wrong

The reports behind this lesson are few and self-selected: mostly one candidate per company, through vendors that sell preparation, with dates read from those pages on 28 October 2026. Stage counts, platforms and pass bars change, and the Ramp report shows that the announced platform and the actual task can differ.

Designing for stage four is the wrong move when it means building stage four early. A dict of dicts with one read path costs nothing extra; a mutation log built speculatively in stage one is code the round may never ask for. The defensible default is the representation that keeps each later addition local, not the one that implements it ahead of time.

Some progressive rounds do not grow state at all. The Perplexity file system's later stage adds `cd` and relative paths, which is path resolution on unchanged state, and a credit ledger may add policy rather than storage. The four pressures above are the common case, not the whole set.

A store that passes every stage on one thread says nothing about concurrent callers. If the follow-up is "two writers at once", the single write helper is again where a lock or a version check goes, which is the last argument for having one.
