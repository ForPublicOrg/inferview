RETRYABLE = {429, 500, 502, 503, 504}

def fetch(get, path, headers, attempts=3):
    for _ in range(attempts):
        status, body = get(path, dict(headers))
        if status not in RETRYABLE:
            break
    return status, body

def crawl(get, start="/start"):
    seen, queue = {start}, deque([start])
    headers, parked = {}, []
    while queue:
        path = queue.popleft()
        status, body = fetch(get, path, headers)
        if status == 401:
            parked.append(path)       # try again only after the header set changes
            continue
        if status != 200:
            continue
        if body.get("exit"):
            return path
        grant = body.get("grant", {})
        if any(headers.get(k) != v for k, v in grant.items()):
            headers.update(grant)
            queue.extend(parked)
            parked = []
        for link in body.get("links", []):
            if link not in seen:
                seen.add(link)
                queue.append(link)
    return None

## One client, grown part by part

An integration round gives you a service you have not seen, a document or an endpoint list, and a task in parts that unlock in order. Each part extends the same client: list everything, then follow links, then authenticate, then write corrections back, then survive failures. It is the progressive format applied to I/O instead of in-memory state, and the same rule carries over: the part-one structure decides what part three costs.

Three recent candidate reports show the shape.

- **Stripe** (new-grad onsite, October 2026, via PracHub). The integration round offered Bikemap in five parts, where the author writes that "completing 3 is generally enough" and nobody had yet reported parts four and five, and Payment Reconciliation in four parts, the fourth explicitly optional. One author, one level, one month: read the pass bar as that, not as a rule.
- **Ramp** (AI engineer, 2026, via aced.io). "Escape the Maze": issue HTTP requests until an exit URL is found, with robust error handling. The second level needs auth headers that are collected while crawling.
- **Anthropic** (technical screen, September 2025, via PracHub). A crawler restricted to one hostname, then how to make it multithreaded. The interviewer told the candidate that most people never reach the multithreading part.

Exercises in this module are original: the maze below, the reconciliation spec and the mock service are written for Inferview. [rnd-027](/problems/rnd-027) is the maze as a staged problem, and the [integration-round lab](/labs/integration-round) runs five parts against a deterministic payments API: cursor pagination, tokens collected from response headers, idempotent reconciliation, retries in one layer with partial failure, and a report.

## Reading an unfamiliar API before writing the client

Five facts determine the client's structure, and each comes from the document or from one probe request whose raw response is printed:

- how a request authenticates, and whether credentials change during the task;
- how a list ends (cursor, `has_more`, a next link, an offset) and whether the list can change while you read it;
- the error body and which statuses the service actually returns;
- whether writes accept an idempotency key, and what identifies a record across calls;
- rate-limit signals and ordering guarantees.

Then write one function that performs every request: `fetch(path, headers)` returning status and parsed body. Part one does not need it. Part two adds headers to it, part three adds an idempotency key, part four adds retries, and each of those is a change in one place instead of in every caller. Build accessors from the probe's actual response, not from the document; in a timed round the probe is ground truth and the document may not be.

## Pagination is where data goes wrong quietly

Offset pagination over a list that changes during the read is the classic part-one bug, and it passes a test against a static fixture.

<Predict id="rounds-integration-offset-drift" question="How many records does the loop read twice?" answer={45}>
<Fragment slot="prompt">
<p>A list endpoint returns 1,000 records newest first, 100 per page, addressed by offset. Your loop computes 10 pages up front and fetches offsets 0, 100, … 900. Between each fetch, 5 new records are inserted at the head of the list.</p>
</Fragment>
<p>Before page k (k from 2 to 10) the list has shifted by 5 × (k − 1) records in total, so page k starts 5 records before where page k − 1 ended: 5 duplicates at each of 9 boundaries, <b>45</b>. Because the loop stopped after 10 pages, it also never reached the 45 oldest records, which slid past offset 999. Deduplicating by id fixes the first problem and not the second; a cursor, or a loop that runs until the service says the list is done, fixes the second. Dedup by id is still needed with a cursor, because a page re-fetched after a timeout can return records already processed.</p>
</Predict>

## Crawling with collected headers: the frontier carries state

The maze format is a graph search where the service is the graph. Part one is a breadth-first crawl with a visited set, bounded retries on 429 and 5xx, and dead ends on 404. Part two, in Ramp's reported version, makes some rooms answer 401 until the crawler presents a header that another room handed out.

The decision part two forces is what to do with a 401. Retrying it immediately loops; dropping it loses the exit. The structure that survives is a parked list: a 401 room waits there, and the parked rooms go back on the queue only when the set of collected headers changes. That bounds the extra requests by the number of parked rooms times the number of new grants, and it terminates when no grant arrives.

The spec also has to answer whether a header collected on one branch applies everywhere. The reported wording, headers "collected as you crawl", reads as global; if the spec says a header belongs to the path that found it, the frontier entry carries its own header set and the visited set becomes keyed by room and header set. The two designs share almost no code.

The starter below is a working part-one crawler. The service is a deterministic mock: `/b` fails once with a 503, `/e` always returns 500, `/gone` does not exist, and `/vault` answers 401 until the request carries the `X-Key` that `/d` grants in its body under `grant`. Extend `crawl` so it reaches the exit without retrying the vault on every pass.

## Reconciliation: idempotent writes and resumable progress

The reconciliation format, reported at Stripe in four parts and at Ramp with receipts, joins two sources and writes corrections. A version for practice: a processor lists charges, the internal ledger lists payments, and for every mismatch the client posts an adjustment. The parts then add amounts that differ, records missing from one side, a service that times out on some writes, and a final report.

Three decisions decide whether the later parts are small:

1. **Key every correction by what it corrects.** The idempotency key for an adjustment is derived from its content, for example `recon:{charge_id}:{kind}`, not generated per attempt. A retry after a timeout, or a rerun of the whole job after a crash, then cannot post the same adjustment twice. If the service accepts no idempotency keys, the client reads existing adjustments for the charge before writing, and the extra read is the price.
2. **Checkpoint per page, not per run.** After each page is reconciled, record the cursor and the set of ids done. A resumed run starts from the checkpoint and skips done ids, which matters because the page boundary may have shifted since.
3. **Isolate per item.** A malformed record or a write that fails after its retries goes to an error list with the reason; the loop continues. The final report is then a fold over results already collected: matched, corrected, failed with reasons, skipped as already done.

Each is a few lines when the client already has one `fetch` and the loop already produces a result per item. Each is a rewrite of the loop when part one returned a bare list.

## Concurrency, when the last part asks

The Anthropic report ends where many crawl rounds do: make it concurrent. In a single process that means a fixed pool of workers pulling from the same frontier, a visited set updated under a lock before a URL is enqueued (so two workers cannot both claim it), and a termination condition that is not "the queue is empty", because a queue can be empty while workers are still fetching pages that will add links. Count in-flight work and stop when the queue is empty and the count is zero. The retry budget and the parked list from part two become shared state too, which is the argument for keeping them in one object from the start.

<Fragment slot="short">
<p>Read with a time bound and dedup: filter the list to records created before the run started, if the endpoint supports it, and run until the partner says the list is done, deduplicating by payout id. Make writes idempotent on our side: a local table of intended adjustments keyed by payout and kind, and a read of the partner's existing adjustments before each write. Automate small, unambiguous corrections; route everything else to a human queue with the evidence. Checkpoint per page so a crash at 04:00 resumes instead of restarting.</p>
</Fragment>
<Fragment slot="long">
<p>The read side: offset pagination over a changing list duplicates and skips records. If the partner supports a created-before filter, the list stops changing for this run and offsets become safe. If not, run until the list reports its end, deduplicate by payout id, and accept that records inserted during the run are picked up tomorrow; the report says how many arrived after the run started.</p>
<p>The write side has no idempotency key, so the risk is a timeout on a write that succeeded, followed by a retry that pays twice. Our table records the intent before the call and the outcome after it; on a retry or a resume, an intent without an outcome triggers a read of the partner's adjustments for that payout before anything is written. That doubles calls on the error path only, which the rate limit can absorb if retries are bounded.</p>
<p>What I refuse to automate: adjustments above a threshold finance sets, and any mismatch where the two sides disagree on the payout's identity rather than its amount. Those go to a queue. What I give up is completeness by 06:00 on bad nights: if the partner is down, the job reports partial coverage and stops, and nobody gets an automatic correction based on a half-read list. The failure mode of this design is the read-before-write itself: if the partner's list of adjustments lags their write endpoint, the check misses a write that just succeeded, so retries of the same payout wait at least as long as the lag the partner documents, or we measure it.</p>
</Fragment>

## When this is wrong

The reports here are three candidates, one of them a new grad, from pages read on 28 October 2026. The Stripe author's "3 of 5" is their impression, not a published bar, and Stripe's own description of the round is not public. Formats rotate: the same author believed one option had already been retired.

The mock in this lesson is synchronous and deterministic, because the browser cell cannot block on real I/O. Real integration code adds timeouts per request, connection reuse, cancellation and, under concurrency, the visited-set and termination problems above; a single-threaded answer that passes every part has not yet met any of them.

And not every part rewards the structure argued for here. A five-part round where parts four and five are never reached rewards finishing part three cleanly over a client designed for part five. The one-function rule costs nothing; anything beyond it should wait for the part that asks.
