from collections import OrderedDict

class ReferenceLRU:
    """Slow and checkable by reading: a list ordered from least to most recently used."""
    def __init__(self, capacity):
        self.capacity, self.items = capacity, []          # [(key, value)]
    def get(self, key):
        for i, (k, v) in enumerate(self.items):
            if k == key:
                self.items.append(self.items.pop(i))      # a read is a use
                return v
        return None
    def put(self, key, value):
        self.items = [(k, v) for k, v in self.items if k != key] + [(key, value)]
        if len(self.items) > self.capacity:
            self.items.pop(0)

class AssistantLRU:
    """The assistant's version. Its own tests passed."""
    def __init__(self, capacity):
        self.capacity, self.data = capacity, OrderedDict()
    def get(self, key):
        return self.data.get(key)
    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)

def random_ops(seed, n=200, keys="abcd"):
    """Few keys and a small capacity, so evictions and re-reads happen within a handful of operations."""
    rng = random.Random(seed)
    return [("get", rng.choice(keys), None) if rng.random() < 0.5
            else ("put", rng.choice(keys), rng.randint(0, 9)) for _ in range(n)]

def first_divergence(make_impl, ops, capacity=2):
    """Index of the first get where the two disagree, or None."""
    ref, impl = ReferenceLRU(capacity), make_impl(capacity)
    for i, (op, key, value) in enumerate(ops):
        if op == "get":
            if ref.get(key) != impl.get(key):
                return i
        else:
            ref.put(key, value)
            impl.put(key, value)
    return None

def shrink(make_impl, ops):
    """Cut after the divergence, then drop one operation at a time while it still diverges."""
    ops = ops[: first_divergence(make_impl, ops) + 1]
    i = 0
    while i < len(ops):
        shorter = ops[:i] + ops[i + 1:]
        if first_divergence(make_impl, shorter) is not None:
            ops = shorter
        else:
            i += 1
    return ops

## What the round scores, by the sources that say

The companies that run assistant-enabled coding rounds describe the score in the vocabulary of an ordinary coding round. Hello Interview's guide to Meta's AI-enabled round, a vendor summary that Meta has not confirmed, lists problem solving, code quality, verification and communication, says the evaluation "isn't about prompt engineering", and reports candidates marked down for leaning on the assistant. Canva's interviewers ask, in the June 2025 post that introduced its round, whether a candidate can identify and fix issues in AI-generated code and bring it to production standard. Canva's October 2025 follow-up names three failure patterns: AI Showcase (demonstrating prompting instead of solving the task), Feature Marathon (accepting output quickly to ship more features) and Hands-Off (delegating without critical review).

Two of the three Canva patterns are verification failures. That is the shift these rounds make: generation costs seconds, so the scarce, observable work is establishing that what was generated is correct, inside a fixed clock. Shopify's head of engineering, interviewed in July 2025, described reviewing generated code with candidates, and a candidate who prompted for a fix that needed one character changed. Prompting for a fix you could type is the same failure in miniature: the assistant was handed the part that needed understanding.

The environment shapes what verification looks like. In the Meta round as the vendor describes it, the assistant answers in a chat panel and cannot edit files, so every line reaches the editor because the candidate pasted or typed it. Each paste is a diff the candidate has accepted. The third phase runs larger, tiered inputs against the phase two solution, which makes complexity part of correctness: code that is right and quadratic fails there.

## Why the assistant's tests prove little

A test written by the same model, in the same context, from the same prompt shares the implementation's reading of the spec. If the model decided that a cache read does not count as a use, its tests write keys and read them back and never read a key between two writes that overflow the capacity. The tests pass and they are not evidence, for the same reason a health check that calls the service's own handler is not evidence the service works: the check and the thing checked fail together.

The defects that survive this are not random. They sit where the request left a decision unstated and the assistant picked a default without saying so. Ask for "a function that retries API calls with exponential backoff" and the request does not say which failures are retryable, whose delay wins when the server sends one, or what the caller sees when retries run out. ## Reading a generated diff

Read the diff against that list, in this order, because the order follows where assistant defects cluster and where a reading is fast.

1. **Unstated decisions.** Boundaries (inclusive or exclusive, empty, duplicates, exactly at capacity), tie-breaks, error policy, what is returned on failure. Each one gets either a test or a sentence of justification.
2. **Edits outside the request.** A renamed parameter, a changed return type, a reformatted block hiding a semantic change, a helper that now swallows an exception it used to raise. These cost the most later because nobody asked for them and nobody re-reads them.
3. **Complexity against the stated input sizes.** A `list.pop(0)` or an `in` test on a list inside a loop is correct and fails a tiered input. The bound takes seconds to read off and is cheaper than discovering it from a timeout.
4. **Library facts.** A keyword argument that does not exist in the installed version, a default that changed between releases. Run it rather than debate it.

Small steps make this possible. One function or one behaviour per request keeps each diff short enough to read completely, and when a check fails there is one recent change to suspect. A large paste moves the bottleneck from generation to review, and review is where the clock is lost.

## Choosing the check

The check has to be independent of the assistant's reading of the task. There are three ways to get that inside a round, and they cost different amounts of it.

A fresh reviewer is a fourth option where the environment allows one. Anthropic's Claude Code documentation recommends reviewing in a context that never saw the conversation, because that reviewer is not swayed by the reasoning that produced the code, and warns that a reviewer asked to find problems always finds something, so the review prompt should be scoped to correctness. In a chat-only round the fresh reviewer is a new conversation holding the spec and the diff and nothing else. Its findings still need a test before they count.

## A differential test that ends in a counterexample

The reference for a stateful structure is a version too slow to ship and simple enough to verify by reading. For an LRU cache it is a list ordered from least to most recently used. The generator matters as much as the reference: keys drawn from a set barely larger than the capacity force evictions and re-reads within a handful of operations, while a realistic key space would almost never evict a key the test later reads.

The assistant's `OrderedDict` version below updates recency on `put` and not on `get`. Before running it, work the shortest case by hand.

Three things in the output carry the lesson. The shrinker turns a divergence at an arbitrary index into a five-operation sequence of the same shape as the Predict, a counterexample a second person can check by hand; the raw 200-operation trace is not. The seed is printed, so the failure replays. And the measured catch rate climbs with sequence length: at 5 operations almost no seed hits the one ordering that exposes the bug, at 50 roughly half do, and the 20-seed sweep at 200 operations still contains a seed that never diverges. A single short random sequence would have reported the assistant's code correct. Run many seeds, keep the key space small, and read "no divergence" as a statement about the generator as much as about the code.

The fix is one line, `self.data.move_to_end(key)` in `get` when the key is present, and the cell checks that the fixed class agrees with the reference on all 20 seeds.

<Fragment slot="short">
<p>Complexity first, because it can be read off the code quickly and the next phase's outcome depends on it: if the bound is wrong at ten times the input, correctness on small inputs does not matter. Then a differential test on eviction with a small key space and a few seeds, cut short if time runs out. What I accept: eviction correctness rests on reading plus the visible tests, and I state which boundary is untested, so the risk is named rather than discovered.</p>
</Fragment>
<Fragment slot="long">
<p>The two checks differ in cost and in what they protect. The complexity bound is read off the code: find the loops, find the operations inside them that are linear in the data size, multiply. If the generated code does a list removal or a membership test on a list per operation, it is quadratic, and a tenfold input is a hundredfold time. That check is short and protects the whole next phase.</p>
<p>The eviction check needs a reference and a driver. If the structure has an obvious slow equivalent, the reference is short, and the driver is a loop over seeded random operations. If time remains after the complexity fix, I write it with keys drawn from a set one or two larger than the capacity, and I shrink any divergence before trying to fix it.</p>
<p>If only one fits, the deciding fact is which failure the next phase will see. A slow algorithm fails the tiered input deterministically. An eviction bug fails only if the hidden inputs read a key between writes that overflow capacity, which is likely but not certain. So performance first, with the eviction risk written as one sentence: the read path's recency update is verified by reading only.</p>
<p>The failure mode of this plan is that the complexity fix introduces the eviction bug, which is common when a list is replaced by an ordered map. So the fix gets one targeted assertion: read a key, overflow by one, check which key left.</p>

## When this is wrong

Differential testing needs a reference simpler than the implementation. For an optimisation problem the reference is the naive algorithm and that works. For a problem whose difficulty is the specification itself, such as a parser for an ambiguous grammar or a scheduler whose rules are the question, the reference is as hard to get right as the code, and agreement only shows that two readings of the spec match. There the check is assertions from the problem statement, and the interviewer's answers to clarifying questions are part of the spec.

Random generators find what they can produce. Bugs that need a large key space, a specific clock reading or interleaved threads do not appear in a four-key, single-threaded sequence; they need an injected clock and hand-written boundary cases, which is the territory of this module's rate-limiter and TTL problems.

The rounds described here put the assistant in a chat panel. When a round allows an agent that edits files and runs commands, the diff per step is larger and the agent can run checks itself; the discipline moves from reading every line to choosing the checks the agent must pass and reviewing its evidence, which is the third lesson in this module. Finally, everything above about scoring comes from Canva's own posts, a vendor's account of Meta's round and one executive interview. None publishes a rubric with weights, so the weight of verification against problem solving in a given loop is not public.
