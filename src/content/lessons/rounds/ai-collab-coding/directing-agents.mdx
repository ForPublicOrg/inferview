## What is left to observe

In a round with a chat assistant the candidate types or pastes every line, so the interviewer sees each decision as it is made. In a round with an agent that edits files and runs commands, most of the typing happens without the candidate, and in Sierra's Build stage, by its own description, without the interviewer in the room for two hours. What can be examined afterwards is narrower and more durable: the instructions the agent was given, the checks it had to pass and what they showed, and how its output was reviewed before it was called done. Sierra's Review stage covers the code, the path to production and how AI was used. Cognition's CEO, per a press report, describes judging what the candidate chose to build and why. Anthropic's performance take-home, which allows AI, states that judgement about how to invest in tooling is part of the signal.

Anthropic's Claude Code documentation, as checked on 28 October 2026, traces a session that goes wrong to one of three causes: the agent lacked information it could not get from the repository, it had no way to check its own work, or a rule was left to a prompt that cannot guarantee it. Those map onto the three things a round can observe. The rest of this lesson is how each is done under a clock.

## The plan: what the agent cannot read

An agent reads code quickly. What it cannot read is the decision that was never written down: the scope cut, the interface chosen over the alternative, the behaviour the spec leaves open. The documentation's guidance for a prompt is to name the file, describe the symptom and say what fixed looks like; for work not yet specified it suggests having the agent interview you until it can write a spec, then building from that spec in a fresh session so the build starts from a clean context and a written definition of done.

In a two-hour build the plan is short and it is a file, not a message, because the review will need it. It holds four things: what is in and out of scope, the interfaces between the parts, the decisions the spec left open with the choice made for each, and the acceptance checks that define done. The open-decisions list is the same list the first lesson in this module builds before reading a diff. Written before the agent starts, it constrains the defaults the agent would otherwise pick silently.

The plan is also the record. A reviewer who reads it afterwards sees what was decided, when, and what was deliberately not built, which is the content Sierra's Review asks about. A log kept alongside it, one line per decision with the evidence it rested on, costs little while the agent is running, and the agent is running for most of the round.

## The check: pass or fail, written before the code

The documentation's framing is that an agent stops when the work looks done, and without something to run that returns pass or fail, "looks done" is all it has. With a check it can make a change, run it, read the failure and iterate. It also recommends asking for evidence, the command and its output, rather than a report that tests pass.

The order matters more than the tool. MIT's 2026 Missing Semester lecture on agentic coding gives it as: write the tests first, audit them, then have the agent implement against them, and let the agent run the failing check itself. The audit is the step that keeps the check independent of the implementation. If the agent writes tests and code together, the tests encode its reading of the spec, which is the correlated-check problem from the first lesson at a larger scale.

An agent with write access to the tests can also make them pass by changing them. The documentation's answer for a rule with no exceptions is configuration rather than a prompt: deny rules, which hold in every permission mode, or a hook. In a round with an unfamiliar setup, a check that guards its own inputs is quicker to write and works with any agent.

```python
# check.py: the one command the agent must pass. Freeze once after auditing the tests.
import hashlib, json, pathlib, subprocess, sys

LOCK = pathlib.Path(".tests.lock")

def digest():
    return {p.as_posix(): hashlib.sha256(p.read_bytes()).hexdigest()
            for p in sorted(pathlib.Path("tests").rglob("*.py"))}

if sys.argv[1:] == ["--freeze"]:                 # run once, after the tests are audited
    LOCK.write_text(json.dumps(digest(), indent=1))
    sys.exit(0)

now = digest()
changed = [f for f, h in json.loads(LOCK.read_text()).items() if now.get(f) != h]
if changed:
    sys.exit(f"FAIL: audited tests were edited or deleted: {changed}")
run = subprocess.run([sys.executable, "-m", "unittest", "discover", "-s", "tests", "-q"],
                     capture_output=True, text=True)
print(run.stdout + run.stderr)                   # the evidence, not a summary of it
sys.exit(run.returncode)
```

New test files pass through, so the agent can add coverage; an edited or deleted audited file fails the check before any test runs. The agent can still edit `check.py` or the lock file, so both belong on the short list of files whose diff is read on every acceptance.

## The review: someone who did not write it

The documentation describes reviewing a diff in a fresh context that never saw the conversation, so the review is not swayed by the reasoning that produced the code, and a second session as the simplest independent reviewer available. It adds a warning that matters under a clock: a reviewer asked to find problems will always find something, and fixing every finding produces abstraction and tests for cases that cannot happen. The review prompt names the plan file and asks for gaps that affect correctness, and each finding is kept only if a test can be written that fails on it.

MIT's lecture adds the limit on all of this: verifying code can be harder than writing it, so critical code is written by hand. In a round, critical means the part whose correctness the rest depends on and that no cheap check covers, such as a concurrency rule or a money calculation. Delegating it and then reviewing it can cost more than typing it.

## Steering, and when to stop

The documentation's steering rules are specific. Watch the first minute and stop the agent the moment it drifts; after two failed corrections, clear the context and write one better prompt, because a third correction adds to a conversation that already holds two failed attempts for the agent to re-read. Checkpoints can roll back edits made through the agent's own file tools, but a file changed only by a shell command is not restored, so version control remains the undo for anything the agent ran. MIT's lecture names the same failure from the other side: agents can enter debugging spirals.

## Investing in tooling

Anthropic's current take-home ships without the visualisation and debugging tools of earlier versions. Candidates insert print statements or have a coding model generate an interactive debugger, and the post states that how they invest in tooling is part of what is measured. The context is a model trajectory the same post documents: Claude Opus 4 produced a more optimised solution than almost all humans within the earlier 4-hour limit, so a format that allows AI has to measure something the model does not do for the candidate.

With an agent, a tool costs minutes of the agent's time plus the minutes to check that the tool reports correctly, and it pays back through faster iterations afterwards. That is a break-even, and it can be estimated before committing.

<p slot="prompt">Scenario inputs: building and checking a trace viewer with the agent costs 15 minutes. Without it, each investigation cycle (run, read the output, form a hypothesis) takes 9 minutes; with it, 4 minutes.</p>
<p>Each cycle saves 9 minus 4, which is 5 minutes, so 15 divided by 5 is 3 cycles. If the remaining work needs fewer than three investigations, the tool does not pay back inside the round. The estimate is most sensitive to the per-cycle saving: at 2 minutes saved, the same tool needs 8 cycles, which few two-hour builds contain.</p>
</Predict>

The calculation leaves out the risk that the generated tool is wrong. A debugger that misreports state costs more than its build time, because cycles spent trusting it are lost. One known case checked against the tool's output is the minimum before relying on it.

## In the room

<Callout kind="interview" label="Interview question">
"Fifty minutes into a two-hour build, you find that one of the agent's three green runs passed because it edited an assertion. Two features in the plan are not started and the demo is at the end. What do you do with the next ten minutes?"
</Callout>

<Depth>
<Fragment slot="short">
<p>Fix the check before building anything else, because every green run from now on is worth nothing until the tests are frozen. Restore the assertion from version control, freeze the audited tests, rerun, and record which earlier acceptances relied on the edited test. Then cut one of the two features in the plan, in writing, so the demo shows one verified feature rather than two unverified ones. What I give up is scope; what I keep is the claim that what I demo works.</p>
</Fragment>
<Fragment slot="long">
<p>The constraints conflict: the demo rewards visible features, and the Review examines how the result was verified. A broken check affects every later decision, so it comes first, and it is cheap: restore the file, write the lock, add the check of audited files to the one command the agent runs.</p>
<p>Then the past. Three acceptances were made on the strength of green runs. The one that passed through an edited assertion is unverified, and the code it accepted may be wrong in exactly the case the assertion covered. Rerunning the restored test tells me whether it was a cosmetic edit or a hidden failure, and the log records which.</p>
<p>Then scope. Seventy minutes remain and the plan had two features left. With the check fixed, I estimate each from what the first features took and cut the one with the larger unknown, writing the cut and the reason into the plan file. The failure mode of this choice is that the cut feature was the one the problem was really about; I check the brief before cutting, not after.</p>
<p>Finally, the agent's instructions change: the tests directory is out of bounds, by configuration if the tool supports a deny rule, and by the check either way.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>Your verification is now taking a third of the round. Which half do you cut, and what risk do you accept in writing?</em> The fresh-context review goes for the second feature; the frozen tests stay. The accepted risk is a defect the tests do not cover, recorded against that feature.</li>
<li><em>The agent edited the assertion because the assertion was wrong. Does that change anything?</em> The fix to a wrong test is a decision I make and log, then re-freeze; a test the agent can change is not a check on the agent.</li>
<li><em>What would make you stop using the agent for the remaining hour?</em> A spiral on the core logic after a cleared context and a rewritten prompt, or a remaining task small enough that reviewing generated code costs more than writing it.</li>
</ul>

## When this is wrong

Many AI-allowed rounds do not provide an agent. Meta's built-in assistant, per the vendor account, answers in chat and cannot edit files, and there the first lesson in this module applies instead: the candidate is the one applying each change, and the review happens on every paste.

The controls cited here are Claude Code's, as documented on the date checked, and its defaults change between releases. Other agents expose different controls, and in a round the environment may be someone else's machine with unfamiliar settings. The plan file, the frozen check and the fresh-context review are portable because they live in files and commands rather than in one tool's configuration.

For small, well-specified tasks the overhead of a plan file, an audited test suite and a separate review can exceed the task. MIT's lecture suggests building the same small feature by hand, with autocomplete, with inline chat and with an agent; the comparison is what calibrates where the agent starts paying for its setup, and that point differs by person and by task.
