export const softmaxCode = `import math

def softmax(xs):
    m = max(xs)                      # subtract the max so exp() cannot overflow
    exps = [math.exp(x - m) for x in xs]
    s = sum(exps)
    return [e / s for e in exps]

def logsumexp(xs):
    m = max(xs)
    return m + math.log(sum(math.exp(x - m) for x in xs))

def cross_entropy(logits, target):
    # log-softmax of the target, negated, without ever forming the softmax
    return logsumexp(logits) - logits[target]

def online_normalizer(xs):
    # one pass: running max m and running sum d, rescaled whenever the max grows
    m, d = float("-inf"), 0.0
    for x in xs:
        m_new = max(m, x)
        d = d * math.exp(m - m_new) + math.exp(x - m_new)
        m = m_new
    return m, d
`;

export const softmaxCodeTests = `import math

## Forty-five minutes, no NumPy

Scenario: the recruiter's email says "ML coding, 45 minutes, shared editor". The interviewer opens with "write top-p sampling", and twenty minutes later asks for causal attention. You have called both a thousand times through a library. You have never had to say where the mask goes or which token top-p keeps at the boundary.

That is the round. Public question banks for AI-engineering interviews list the same small set again and again: scaled dot-product attention with a causal mask, multi-head and grouped-query attention, a KV cache decode step, BPE training and encoding, temperature, top-k and top-p sampling, cosine similarity, softmax and LayerNorm, AUC, and a LoRA layer. None of them is long. Each has one or two invariants that a library hides from you, and the interviewer is listening for whether you know them.

## Write the reference implementation, then the tests

The useful frame comes from compilers. When you write an optimising compiler you keep a slow, obviously correct reference interpreter beside it, and you test the fast path against the reference. A hand-writing round asks you to be the reference interpreter: plain loops, no cleverness, every step something you can say out loud. Then it asks how you would know it is right, which is the test suite.

So the shape of a strong answer is the same for every question in this module. State the shapes or types. Write the plain version. Name the invariant. Write a test that would fail if the invariant broke.

## Predict first

<Predict id="rounds-top-p" question="With top-p = 0.9, how many tokens stay in the draw?" answer={3} unit="tokens">
<Fragment slot="prompt">
<p>After temperature, the next-token probabilities are 0.5, 0.3, 0.15 and 0.05.</p>
</Fragment>
<p>Three. Sorted descending, the running total is 0.5, then 0.8, then 0.95. The nucleus is the smallest set whose total reaches 0.9, so it stops at the token that crosses the line, and that token stays in. A filter that keeps "tokens with probability above 0.9" keeps none, and a filter that stops before crossing keeps two. Both are common first drafts.</p>
</Predict>

The definition is from Holtzman et al.: the nucleus is the smallest set of tokens whose cumulative probability is at least p, and the distribution is rescaled over that set. Min-p, from Nguyen et al. (an ICLR 2025 oral, revised November 2025), is now asked about alongside it. Its threshold is relative: keep tokens with probability at least p_base times the top token's probability. With the same probabilities and p_base = 0.2, the threshold is 0.2 × 0.5 = 0.1 and three tokens survive. When the model is confident the threshold rises with it, which is the paper's argument for using it at high temperatures.

Say the order of operations you chose. Libraries do not all apply temperature, top-k and top-p in the same order, so the interviewer wants to hear that you know an order exists, not a claim that yours is universal. And say that temperature 0 is not a division: greedy decoding is an argmax.

One computed number from that BPE corpus is a good trap to know about. On the first merge, three pairs tie: `e s` appears in newest (6) and widest (3), so 9 times; `s t` likewise 9; `t` followed by the end-of-word marker likewise 9. Which merge comes first depends on your tie-break rule, so a test that asserts a specific first merge must fix the rule. The foundations lesson on tokens has a runnable BPE; this module's problems cover attention, sampling, AUC and the KV cache estimate.

<Callout kind="gotcha">
The KV cache stores keys and values, not queries. The memory formula has a factor of 2 for K and V and multiplies by layers, KV heads, head width, sequence length, batch and bytes per value. Grouped-query attention reduces the number of KV heads, not query heads.
</Callout>

## Softmax, cross-entropy and the one-pass normaliser

<CodeRunner id="lesson-rounds-softmax" title="Stable softmax and cross-entropy" starter={softmaxCode} tests={softmaxCodeTests} gradable={false} />

`online_normalizer` is the trick that lets attention be computed block by block. It keeps a running maximum and a running sum, and whenever a larger value arrives it rescales the sum by `exp(old_max - new_max)`. The result equals the two-pass version, and it never needs the whole row in memory at once. You will not be asked to write a fused kernel in an interview, but "how would you compute the softmax without materialising the full row?" is a natural follow-up to attention, and this is the answer.

Practical notes for the room. Code in Python unless told otherwise, and ask whether NumPy is allowed; when it is, write the loop version first anyway if you are unsure of the broadcasting, then vectorise. Name your shapes in a comment above every matrix operation. Keep a tiny example (three tokens, two dimensions) you can compute by hand, because a hand-checked number is a stronger test than "it ran".

## In the room

<Callout kind="interview" label="Interview question">
"Implement causal self-attention for one head. Then tell me how you would test it."
</Callout>

<Depth>
<Fragment slot="short">
<p>Scores are Q times K-transpose divided by the square root of the key width. Set positions with j greater than i to negative infinity, softmax each row with the max subtracted, and multiply by V. I test invariants: every row of weights sums to 1, the upper triangle is exactly zero, row 0 copies V[0], and one weight I computed by hand pins the scale. Then a decode test: attending with only the newest query and cached K and V must equal the last row of the full computation.</p>
</Fragment>
<Fragment slot="long">
<p>Shapes first. Q and K are T by d_k, V is T by d_v, so the scores are T by T and the output is T by d_v. I say that out loud because transposing the wrong operand is a silent bug in a toy example where every matrix is square.</p>
<p>The scale is sqrt(d_k). The original paper's reason is that dot products grow with the width and push the softmax into a region with tiny gradients; in the base model d_k is 64, so the divisor is 8. Using d_k or the model width instead is a mistake the hand-computed weight test catches.</p>
<p>The mask goes before the softmax, as negative infinity, so masked positions become exactly zero and rows still sum to 1. Zeroing after the softmax breaks the row sums. The comparison is j greater than i; j greater than or equal to i hides each token from itself and leaves row 0 with nothing to attend to.</p>
<p>Edge cases I would mention: a padding mask combined with the causal mask can leave a row with every position masked, which makes the softmax divide zero by zero, so decide what that row returns. Memory is O(T squared) for the weights, which is what blockwise kernels with the online normaliser avoid.</p>
<p>Extensions, if time allows: multi-head by splitting the width into h heads and concatenating; grouped-query by letting several query heads share one K and V head, which shrinks the KV cache.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you verify it against a library?</em> Run the same random inputs through a reference implementation and compare with a tolerance, not equality, because summation order changes the last bits.</li>
<li><em>How does it fail at long context?</em> The T by T weights dominate memory; compute in blocks with a running max and normaliser.</li>
<li><em>What is the alternative to a KV cache?</em> Recomputing K and V for the whole prefix at every step, which is correct and quadratic in work; the cache trades memory for that compute.</li>
</ul>
</Fragment>
</Depth>

## When this is wrong

This lesson treats the round as pure Python with loops, because that is the version the browser runner here can execute and the version that forces you to know each step. Many interviews expect NumPy or PyTorch with batch and head dimensions, and fluency with broadcasting and `einsum` matters there. Practise both; the invariants are the same.

The invariant tables assume the textbook versions. Production code differs: fused kernels compute attention blockwise, samplers apply penalties and filters in library-specific orders, and tokenizers add byte fallbacks and special tokens. If the interviewer asks how a specific library does it, the honest answer is often "I would check the source", followed by the property you would test either way.

Not every loop has this round. Some companies test general data-structure coding, and others give LLM-application problems instead (the next lesson). Ask the recruiter what the coding rounds contain; it is a normal question.

What I would say in the room: "I write the plain version first, I name the invariant it keeps, and I test the invariant, not the output I expect to see."
