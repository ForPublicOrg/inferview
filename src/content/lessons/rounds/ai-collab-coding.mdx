export const lruCheck = `import random
from collections import OrderedDict

class ReferenceLRU:
    """Obviously correct and slow: a list ordered from least to most recently used."""
    def __init__(self, capacity):
        self.capacity, self.items = capacity, []          # [(key, value)]
    def get(self, key):
        for i, (k, v) in enumerate(self.items):
            if k == key:
                self.items.append(self.items.pop(i))      # a read is a use
                return v
        return None
    def put(self, key, value):
        self.items = [(k, v) for k, v in self.items if k != key] + [(key, value)]
        if len(self.items) > self.capacity:
            self.items.pop(0)

class AssistantLRU:
    """What the assistant wrote. Its own tests passed."""
    def __init__(self, capacity):
        self.capacity, self.data = capacity, OrderedDict()
    def get(self, key):
        return self.data.get(key)
    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)

def first_divergence(make_impl, seed, steps=300, capacity=3, keys="abcde"):
    """Run the same random operations on both; return the first step where they disagree, or None."""
    rng = random.Random(seed)
    ref, impl = ReferenceLRU(capacity), make_impl(capacity)
    for step in range(steps):
        k = rng.choice(keys)
        if rng.random() < 0.5:
            if ref.get(k) != impl.get(k):
                return step, "get", k
        else:
            v = rng.randint(0, 9)
            ref.put(k, v); impl.put(k, v)
    return None
`;

## Scenario: an airport in forty-five minutes

Scenario, modelled on an example Canva published: you open a shared editor with an AI assistant in the side panel. The prompt is "build a control system that manages takeoffs and landings at a busy airport". It is too big to finish, deliberately. The interviewer does not tell you how to use the assistant. Forty-five minutes later they have watched you decompose the problem, write or generate pieces, catch what the assistant got wrong, and explain your trade-offs. The code on the screen at the end matters less than how it got there.

Several companies now run a round like this, and the rules differ by company and by round. Know which one you are walking into.

Two habits follow. Ask the recruiter, for each round, whether AI tools are allowed, expected or banned, and which tool; OpenAI and Meta both tell candidates to confirm the details. And practise both ways, because a loop can contain one round of each.

## What the interviewer is scoring

Only Canva has published the questions its interviewers ask themselves in this round. They include whether candidates can identify and fix issues in AI-generated code, and the rest of the post points the same way: understanding the problem, directing the tool, and judging its output. Prep sites publish rubrics of their own. One attributes to Anthropic a round, with any AI tool allowed, scored on prompt clarity, verification, task decomposition, integration and judgement; Anthropic's own guidance (no AI in live interviews unless indicated) does not support that. Another lists problem solving, code quality, verification and communication for Meta. No company has confirmed either list, so treat them as practice checklists.

The analogy that works is pair programming with a fast, confident junior who never gets tired and never learns during the session. You would not let that pair push to main unreviewed. You would give them small, well-specified tasks, ask them to show you the test, and read every line they wrote. The difference from a human junior is that the assistant gives no reliable sign of doubt. Its wrong code reads as fluently as its right code, so fluency tells you nothing; only checks do.

Habits that show up as signal:

- Decompose before prompting. Say the components out loud (a runway scheduler, a queue of requests, a conflict check), and give the assistant one component at a time with its interface.
- Write the spec as a test first, or at least one test, before accepting generated code. A test the assistant wrote alongside its code shares its assumptions.
- Ask for small diffs and read all of them. Narrate while you read: "this handles the empty queue, this does not check two landings on one runway."
- Run the code early and often. A run is cheaper than a debate.
- Reject and redirect. Saying "no, that changes the interface; keep `schedule()` returning a list" is judgement, and interviewers can only score what they see.

Anti-patterns that show up just as clearly: pasting the whole problem into the assistant and waiting, accepting output because it compiles, long silences while the assistant generates, and arguing with the tool for five minutes instead of writing the ten lines yourself.

## Review the assistant's code

The three defects are the ones that matter for LLM clients specifically. Catching every exception retries permanent failures such as a 400 or a bug in your own code. A fixed sleep with no jitter ignores the server's `retry-after` and makes many clients retry in lockstep, and it sleeps after the last attempt for nothing. Returning `None` hides the failure from the caller. If you flagged `delay *= 2` or the loop header, look again: doubling is the backoff, and the loop bound is fine once the final sleep is skipped.

## Verify with a reference, not with the assistant's tests

The strongest verification habit to show in this round is a differential test: compare the generated code against a slow implementation that is obviously correct, on random operations, and report the first disagreement. It takes a few minutes to write and catches bugs no hand-picked test anticipated.

The cell holds a reference LRU cache (a list, linear time, impossible to get wrong), the assistant's `OrderedDict` version, and a driver that runs both on the same random sequence. The assistant's version never marks a key as recently used when it is read, so it is first-in, first-out by write time. Its own write-then-read tests could not see that.

<CodeRunner id="lesson-rounds-lru-diff" title="Differential test against a reference" starter={lruCheck} tests={lruCheckTests} gradable={false} />

Change `AssistantLRU.get` to call `self.data.move_to_end(key)` when the key exists, and the divergence disappears. In an interview you would say: "I trust the reference because I can check it by reading; I trust the fast version because it agrees with the reference on a few thousand random operations."

<Fragment slot="short">
<p>I do not rely on noticing by reading alone. Before I accept generated code I have at least one test written from the spec, not by the assistant, and I run it. For anything stateful I write a slow reference version and compare on random inputs. I keep diffs small so I can read every line, and I read for the edge cases I listed before prompting: empty input, duplicates, the boundary, the failure path. If the assistant's explanation and its code disagree, I trust neither until a test decides.</p>
</Fragment>
<Fragment slot="long">
<p>Plausible code is the normal case, not a warning sign, because the assistant writes everything fluently. So I build checks that do not depend on how the code reads.</p>
<p>Spec tests first. Before generating, I write down two or three behaviours from the problem statement and turn one into an assertion. That is the test the assistant's own tests cannot replace, because they encode the assistant's reading of the task.</p>
<p>Differential testing for stateful code. A cache, a scheduler, a parser: write the dumbest correct version, run both on random operations, report the first divergence. It is a few minutes of work and it finds the bugs nobody thought to test.</p>
<p>Small diffs, read aloud. I ask for one function at a time and read it before running it, naming what each branch handles. Narrating gives the interviewer the verification signal even when I find nothing.</p>
<p>Check where a demo proves least. A happy-path run says nothing about boundaries, error handling, or calls that depend on library versions, so I check those first. If it uses an API I am not sure of, I look it up rather than trusting either of us.</p>
<p>Judgement on time. When a generated piece is wrong twice, I write it myself.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>What would you refuse to delegate?</em> The decomposition, the interfaces between parts, and the tests that define correct; those are where my judgement is being assessed.</li>
<li><em>How do you prompt so the output is easier to verify?</em> Give the interface and a failing test, ask for the smallest change that passes it, and ask for no unrelated edits.</li>

## When this is wrong

Every policy in this lesson is dated because policies move. The Google entry is a press report, the four-dimension rubric is from prep sites, and the Meta details come from a careers page that does not show a date. Confirm each round's rules with the recruiter close to the interview.

The habits here assume the assistant is a chat or inline-completion tool inside an editor. Agentic tools that edit many files and run commands change the rhythm: you review larger diffs and spend more time on instructions and permissions. The verification principle is the same, but a differential test may matter more when the tool can change ten files at once.

And in rounds where AI is banned, none of this applies directly. You are back to writing every line yourself, with decomposition, testing and narration still the skills on show. Practise without the assistant too, so a no-AI round does not feel like a different job.

What I would say in the room: "I decide the structure and the tests; the assistant writes code inside them; nothing gets accepted until a check I trust has run."
