export const toolLoop = `import json

TOOLS = {}

def tool(fn):
    TOOLS[fn.__name__] = fn
    return fn

@tool
def get_weather(city):
    return {"Paris": "18 C"}.get(city, "unknown city")

def run_agent(model_step, user_msg, max_steps=5):
    """model_step(messages) returns an assistant message with a content list."""
    messages = [{"role": "user", "content": user_msg}]
    for _ in range(max_steps):
        reply = model_step(messages)
        messages.append(reply)
        calls = [b for b in reply["content"] if b["type"] == "tool_use"]
        if reply.get("stop_reason") != "tool_use" or not calls:
            return messages
        results = []
        for c in calls:                     # exactly one tool_result per tool_use
            fn = TOOLS.get(c["name"])
            try:
                if fn is None:
                    raise KeyError("no tool named " + c["name"])
                out, err = fn(**c["input"]), False
            except Exception as e:          # report it to the model; do not crash the loop
                out, err = type(e).__name__ + ": " + str(e), True
            results.append({"type": "tool_result", "tool_use_id": c["id"],
                            "content": json.dumps(out), "is_error": err})
        messages.append({"role": "user", "content": results})   # all results in one turn
    raise RuntimeError("step budget exhausted")
`;

## The model is the flaky dependency

Scenario: a seed-stage company's coding round. "We call an LLM for every support ticket. Write the client: it should handle rate limits, not lose tickets when the provider has a bad minute, and stream the answer to the agent's screen." No attention, no sampling, no model internals. Forty-five minutes of what is, underneath, ordinary backend code.

Public question banks list the same family of tasks for this round: an LRU cache with a time-to-live, a token-bucket rate limiter where cost scales with tokens, an async batch processor with retries and jitter, a streaming SSE parser that survives arbitrary chunk boundaries, a minimal agent loop with tool dispatch and a step budget, conversation memory, and retry with exponential backoff. Candidate reports from 2025 and 2026 add the general-purpose versions that AI companies also ask: an in-memory database with SQL-like queries, a key-value store with transactions, and a single-host web crawler that grows a thread pool.

If you have built a payments integration, you have the instincts already. Treat the model API like a remote service you do not control: it is slow, it is rate limited, it fails in several distinct ways, some of its failures arrive after a success code, and every call has a price. The difference from a payments API is the meter. Cost and limits are counted in tokens, input and output separately, and a single request can be a hundred times bigger than the one before it.

## Six patterns the round tests

### Retry only what can succeed on retry

Retry 429, 5xx, the overloaded 529, timeouts and connection errors. Do not retry a 400: a validation error will fail the same way every time. When the server sends `retry-after`, wait exactly that long. Otherwise use exponential backoff with full jitter, a uniform draw between zero and the capped exponential, so clients that failed together do not retry together. One Claude-specific case: a 429 caused by your organisation's spend limit carries no `retry-after` and keeps failing until access resumes, so retrying it just burns attempts.

### Limit in tokens, not requests

The Claude API documents its limiter as a token bucket that refills continuously, with separate limits for requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM). On most models, tokens read from the prompt cache do not count toward ITPM. A client-side limiter that counts requests lets one 50,000-token request through as if it were a 200-token one.

### Parse streams, do not split them

A stream is a sequence of typed events, and chunk boundaries have nothing to do with event boundaries. Buffer until a blank line, follow the WHATWG rules for comments and `data:` lines, tolerate event types you have never seen, and remember that usage in `message_delta` is cumulative. Tool arguments arrive as `partial_json` fragments that are not valid JSON on their own; parse them once, at `content_block_stop`. An `error` event can arrive after the HTTP status was 200.

### Keep the tool protocol intact

Every `tool_use` block gets exactly one `tool_result` with its `tool_use_id`, in the next user turn, before any text. Tool failures go back as results with `is_error: true` so the model can recover; they do not crash the loop. A step budget ends a model that never stops calling tools. One 2026-specific detail worth knowing: Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 return a 400 for `tool_choice` set to `any` or a specific tool, so sample code copied from older docs that forces a tool will break.

### Paginate on the documented signal

Stop when `has_more` is false, after processing that page's data; pass the last id as the next cursor; and guard against a cursor that does not advance. For offline jobs over many inputs, a provider's batch API is usually the better answer than your own loop: both Anthropic and OpenAI price batch requests at half the normal rate, both work within a 24-hour window, and both return results that may be out of order, so you join on `custom_id`.

### Trim memory by turns, not messages

A history trimmer that cuts at an arbitrary message can separate a `tool_use` from its `tool_result` and produce an invalid request. Trim whole turns, start on a plain user message, and decide which layer owns trimming: your code, the framework (LangGraph checkpointers hold a thread's state; stores hold memory across threads), or the API (Claude's context-editing beta clears old tool results past a token trigger).

## A tool loop that keeps the protocol

This is the core of the "minimal agent loop" question in a form you can test without a model: `model_step` is a scripted stand-in. Run the cell, then try two breaks. Append each tool result as its own user message instead of collecting them, and the first test fails. Remove the `try` and the unknown tool `get_forecast` crashes the run instead of becoming an error the model can read.

Two details to say aloud. Tool results go back in one user turn because the model asked for both calls in one turn; splitting them breaks the pairing the API expects. And the step budget raises rather than returning a partial answer, so the caller decides what the user sees.

<Fragment slot="long">
<p>The protocol. Every tool-use block needs exactly one result with its id, in the next user turn, results first. Parallel calls return together. An unknown tool name or bad arguments become an error result, because a hallucinated tool name should not crash a request.</p>
<p>Errors. The model can only recover from errors it can read and act on. A tool should say what is wrong ("refund exceeds the refundable balance of 12.50"), not "error 422". Permanent errors should end the run with a message for the user rather than invite the model to retry forever; transient errors are better retried inside the tool layer, so the model never sees them.</p>
<p>Budgets. A step budget stops infinite loops; a token or cost budget stops expensive ones, because every step re-sends the growing conversation. A repeated-call guard catches the common loop where the model retries the same call with the same arguments.</p>
<p>Where the code lives. In an interview I write the loop by hand. In production I would weigh a framework: the OpenAI Agents SDK has a turn limit, LangGraph a recursion limit with checkpointed state, the Claude Agent SDK turn and budget caps. None of them decides for you which tool errors are permanent.</p>

## When this is wrong

The limits, retry counts and error codes in this lesson are the Claude and OpenAI documentation as checked on 28 October 2026. Tiers, model names and defaults change; read the current page before you quote a number in a design. Other providers use different limit dimensions, and some count requests where these count tokens.

The exercises here are single-threaded with injected clocks, because that is what the browser can run. Real clients are asynchronous: a semaphore caps concurrency, an async limiter sits in front of the call, and cancellation has to clean up. Write the synchronous version first in an interview if it helps you think, then say how it becomes concurrent.

And not every LLM-app round is about the LLM. Candidate reports from AI companies describe in-memory databases, key-value stores with transactions, and crawlers, which are classic backend questions graded on the same habits: clear state, tested edge cases, and a plan for concurrency.

What I would say in the room: "I treat the model as a rate-limited, metered, flaky remote service. I retry at one layer, I limit in tokens, I parse streams as events, and I never let one bad input take down the batch."
