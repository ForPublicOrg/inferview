class Value:
    def __init__(self, data, parents=(), backward=None):
        self.data, self.grad = data, 0.0
        self.parents, self._backward = parents, backward

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other))
        def backward():
            self.grad += out.grad          # += because a node can feed several consumers
            other.grad += out.grad
        out._backward = backward
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other))
        def backward():
            self.grad += other.data * out.grad
            other.grad += self.data * out.grad
        out._backward = backward
        return out

    def relu(self):
        out = Value(max(0.0, self.data), (self,))
        def backward():
            self.grad += (self.data > 0) * out.grad
        out._backward = backward
        return out

    def backward(self):
        # iterative post-order DFS: no recursion limit on deep graphs
        order, seen, stack = [], set(), [(self, False)]
        while stack:
            node, done = stack.pop()
            if done:
                order.append(node)
            elif id(node) not in seen:
                seen.add(id(node))
                stack.append((node, True))
                stack.extend((p, False) for p in node.parents)
        self.grad = 1.0
        for node in reversed(order):
            if node._backward:
                node._backward()

def prefix_product_backward(a, g):
    # dL/da[k] = P[k-1] * S[k], where P is the exclusive prefix product and
    # S[k] = g[k] + a[k+1] * S[k+1]; no division, so zeros in a are fine
    n = len(a)
    S = [0.0] * n
    acc = 0.0
    for k in range(n - 1, -1, -1):
        acc = g[k] + (a[k + 1] * acc if k + 1 < n else 0.0)
        S[k] = acc
    grads, P = [], 1.0
    for k in range(n):
        grads.append(P * S[k])
        P *= a[k]
    return grads

def cross_entropy(logits, target):
    m = max(logits)
    lse = m + math.log(sum(math.exp(x - m) for x in logits))
    return lse - logits[target]

def cross_entropy_grad(logits, target):
    m = max(logits)
    e = [math.exp(x - m) for x in logits]
    s = sum(e)
    return [ei / s - (i == target) for i, ei in enumerate(e)]

## What the reported rounds ask

Three candidate reports on PracHub describe hand-written gradient rounds in 2025 and 2026. They are reports, not official descriptions, and the material below is original; none of it reproduces the reported code.

- Anthropic, Software Engineer onsite (posted 2025-09-06): a one-hidden-layer binary classifier in vectorised NumPy with no autograd, float64 throughout, mean binary cross-entropy in a numerically stable form, every gradient derived by hand, gradient descent, and a central finite-difference check reporting relative error per parameter.
- OpenAI, Machine Learning Engineer onsite (posted 2026-09-20): the backward pass of a prefix product in linear time without dividing by the inputs, because the inputs may contain zeros, checked numerically with one zero and with two; then mean softmax cross-entropy over an N by C batch with its gradient.
- OpenAI, Software Engineer technical screen (posted 2026-09-19): a `Tensor` class with add, multiply, 2-D matmul, ReLU, sum and `backward()`, accumulating gradients for tensors used more than once, with follow-ups on broadcasting, a no-grad mode and graphs with hundreds of thousands of nodes.

The three share one structure: a derivation that holds for every shape, an implementation, and a check that would fail if either were wrong. None states a tolerance for the check, so choosing one and defending it is part of the answer.

## Shapes first: the one-hidden-layer classifier

Write the forward pass with every shape, because the backward pass is the same graph read in reverse and every gradient must have its parameter's shape.

```
X  : N×D      W1 : D×H   b1 : H      W2 : H×1   b2 : 1
z1 = X @ W1 + b1          N×H   (b1 broadcast over N rows)
a1 = f(z1)                N×H
z2 = a1 @ W2 + b2         N×1
loss = mean over N of  max(z2, 0) - y*z2 + log(1 + exp(-|z2|))
```

The loss line is binary cross-entropy written on the logit. Computing `sigmoid` first and then `log(p)` and `log(1 - p)` loses `1 - p` to rounding once `p` is within machine epsilon of 1, and returns infinity. The logit form never forms `p`, and its derivative is the familiar one: `d loss_i / d z2_i = sigmoid(z2_i) - y_i`.

Backward, with the mean's `1/N` entering exactly once:

```
dz2 = (sigmoid(z2) - y) / N     N×1
dW2 = a1.T @ dz2                H×1
db2 = dz2.sum()                 1
da1 = dz2 @ W2.T                N×H
dz1 = da1 * f'(z1)              N×H   (ReLU: 1 where z1 > 0, else 0)
dW1 = X.T @ dz1                 D×H
db1 = dz1.sum(axis=0)           H
```

Two rules generate every line. A matmul `C = A @ B` sends `G @ B.T` to A and `A.T @ G` to B, and the shapes leave no other arrangement. A bias that was broadcast over the batch in the forward pass receives the sum over the batch in the backward pass. That second rule is the whole of "broadcasting in the backward pass" in the autograd report: whatever axes the forward pass expanded, the backward pass sums over.

The shape check is the cheapest invariant and catches transposed operands. It does not catch the `1/N` applied twice or not at all, which leaves every shape right and every gradient off by a factor of N. The finite-difference check catches that.

## The finite-difference check, with its step size derived

The central difference `(L(θ + h) - L(θ - h)) / 2h` has a truncation error that shrinks with `h²` and a rounding error that grows like `ε/h`, where ε is the float's machine epsilon. Too large a step measures the curvature; too small a step measures rounding.

<Predict id="rnd-hw-fd-step" question="Taking the total error as h² + ε/h with ε = 2.2e-16 (float64), what h minimises it, in millionths?" answer={4.8} tolerance={0.4} unit="× 1e-6">
<p>Set the derivative to zero: 2h &minus; ε/h² = 0, so h = (ε/2)^(1/3) = (1.11e-16)^(1/3) = 4.8e-6. At that step the modelled error is about 6.9e-11. At h = 1e-3 the truncation term alone is 1e-6, and at h = 1e-9 the rounding term alone is 2.2e-7, both thousands of times worse. In float32, with machine epsilon 1.19e-7, the same formula gives a step of 3.9e-3 and a modelled error of 4.6e-5, which is why the Anthropic report asks for float64: in float32 a correct gradient and one with a small bug can show the same relative error.</p>
</Predict>

The constants in the error model depend on the third derivative and on the magnitude of L, so treat the result as a scale, not a value. A relative error of `|analytic - numeric| / max(|analytic|, |numeric|, 1)` below about 1e-7 in float64 is a reasonable pass threshold for smooth functions; I would state that number and the reason for it. Two practical traps. ReLU is not differentiable at 0, so if any pre-activation is within h of 0 the numeric gradient straddles the kink and disagrees with a correct analytic one; check where `|z1|` is small and move those points. And the check costs two forward passes per scalar parameter: with D = 3 and H = 4 the network has 3 × 4 + 4 + 4 + 1 = 21 parameters, so 42 forward passes, which is why it runs on tiny shapes and the code under test must not depend on the shapes being tiny.

## Prefix product without division

The forward pass is `y[i] = a[0] × a[1] × ... × a[i]`. The upstream gradient is `g[i] = dL/dy[i]`, and the report asks for `dL/da[k]` for every k in linear time.

Start with the special case where the loss depends only on the total product. Then `dL/da[k]` is the product of every other element. Dividing the total by `a[k]` fails at zeros in two different ways: with one zero at index z, every gradient except `a[z]`'s is 0, and `a[z]`'s is the product of the others, which division computes as 0/0. Two passes fix it: an exclusive prefix product from the left, an exclusive suffix product from the right, and their elementwise product.

The general case expands the chain rule. `y[i]` depends on `a[k]` for every k up to i, so

```
dL/da[k] = sum over i >= k of  g[i] × (product of a[j] for j <= i, j != k)
         = P[k-1] × S[k]
P[k-1]  = a[0] × ... × a[k-1]           (1 when k = 0)
S[k]    = g[k] + a[k+1] × S[k+1]        (S[n-1] = g[n-1])
```

S is a right-to-left recurrence, the reverse-mode analogue of a suffix sum, and P is computed on the way back left to right. Both passes are O(n), neither divides, and zeros flow through the products like any other value.

<Predict id="rnd-hw-prefix" question="For a = [2, 3, 0, 4] and L = y[0] + y[1] + y[2] + y[3], what is dL/da[2]?" answer={30}>
<p>Every g[i] is 1. S[3] = 1, S[2] = g[2] + a[3] × S[3] = 1 + 4 = 5. P[1] = a[0] × a[1] = 6. So dL/da[2] = 6 × 5 = 30. Check it directly: a[2] appears in y[2] = 2·3·a[2] and y[3] = 2·3·a[2]·4, so the derivative is 6 + 24 = 30, even though y[2] and y[3] are both 0 at this point. A division-based backward computes y[3] / a[2] = 0/0 here. The same recurrence gives dL/da[0] = S[0] = 1 + 3 × (1 + 0 × 5) = 4.</p>
</Predict>

The cross-entropy half of the same report is shorter. Mean softmax cross-entropy over an N by C batch has the gradient `(softmax(z) - onehot(y)) / N` with respect to the logits. The forward pass is `logsumexp(z) - z[y]` per row with the row maximum subtracted inside the log-sum-exp, which stays finite for any finite logits. The report's follow-up about why frameworks fuse softmax with cross-entropy has a two-part answer: the fused gradient is that one subtraction, and composing `exp`, `sum` and `log` as separate nodes stores N by C intermediates for the backward pass and overflows `exp` unless each node is stabilised separately.

## A reverse-mode engine

micrograd is the reference most candidates have read: a scalar engine of about 100 lines over a dynamically built graph, tested against PyTorch. The engine in a round is the same idea, and three properties decide whether it is right.

Order: a node may propagate its gradient only after every consumer has added to it. A reverse topological order of the graph guarantees that. Propagating as soon as one consumer is done gives wrong gradients for any node used twice.

Accumulation: each local backward adds into its inputs' gradients. With `b = a * a + a`, the node `a` receives three contributions, and an engine that assigns instead of adding returns the last one. Whether leaf gradients accumulate across separate `backward()` calls is a policy decision; PyTorch accumulates and requires an explicit zeroing, and the round expects you to choose and say which.

Depth: a recursive depth-first search for the topological order recurses once per level of the graph. CPython 3.12 measured here has a recursion limit of 1000, so a graph a few thousand nodes deep, an unrolled sequence for instance, raises `RecursionError`. The report's follow-up about hundreds of thousands of nodes is asking for an iterative traversal, and for releasing each node's saved inputs and closure after its backward runs so peak memory does not hold the whole graph twice. A no-grad mode is the same memory argument at forward time: record no parents and no closures.

The matrix version adds only the two rules from the classifier: matmul transposes, and summing over broadcast axes. ReLU's backward is the upstream gradient masked by `x > 0`; at exactly 0 the gradient is a convention, and a test that hits 0 is testing the convention.

The cell is a scalar engine with an iterative topological sort, the division-free prefix-product backward, and the cross-entropy gradient, each checked by finite differences at the step size derived above, including the one-zero and two-zero inputs.

## When this is wrong

Finite differences check smooth points only. A network whose pre-activations are all positive on the check inputs never exercises the zero branch of the ReLU mask, so a backward that forgot the mask passes. The inputs for the check have to put some pre-activations on each side of every kink, and none within h of it.

A float64 check proves the derivation and nothing about the dtype the code runs in. Gradients that agree in float64 can underflow, overflow or lose the `1 - p` term in bf16, and the classifier's stable loss exists because of that.

A scalar engine allocates one Python object per number and is a teaching device; the matrix engine is the smallest thing that resembles production. Real autograd adds saved-tensor version checks for in-place operations, higher-order gradients and memory planning, and JAX expresses the same mathematics as function transformations rather than a recorded tape. And these are candidate reports with dates: the questions rotate, and a report on a site that sells premium answers is evidence about the topic, not about the grading.
