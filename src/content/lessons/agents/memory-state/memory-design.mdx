## Memory is a write path

An assistant with long-term memory has a second input channel. Whatever is written today is read back into the context of some later request, either by a retriever or by a loader that injects it whole, and the model gives it roughly the trust it gives the system prompt and the user. The store (a JSON document per user, a vector index, a directory of Markdown files) decides how memory is read. The write policy decides what the assistant has become after six months of use, and it is the part teams under-design.

The nearest systems analogy is a cache the application fills on its own behalf with no invalidation. Two differences change the engineering. The writer is a model, so writes are probabilistic: the same conversation can produce one memory, a different memory, or none. And reads are by relevance rather than by key, so a wrong entry is not served once and evicted; it is served every time it looks related, possibly for months.

LangGraph's persistence docs separate two layers: a checkpointer persists one thread's state (the [checkpoints lesson](/learn/agents/memory-state/agent-checkpoints)), and a store persists application data across threads under a namespace such as `(user_id, "preferences")` with a key per item. This lesson is about the store.

## Three kinds, three write policies

The LangChain memory docs take their taxonomy from the CoALA paper (Sumers et al., first posted September 2023), and the taxonomy earns its place because each kind wants a different write policy.

Semantic memory holds facts: the user's team deploys on Thursdays, the user writes Python and Go. It is read to ground answers. A wrong entry produces a confident wrong answer, and staleness is the common failure because facts about people change.

Episodic memory holds experiences: what the agent did on an earlier task and how it went. LangChain notes it is often implemented as few-shot examples chosen per request, and that choosing them is the hard part. A successful trajectory against an API that has since changed is a misleading example, not a neutral one.

Procedural memory holds how to behave: the system prompt, the agent's code and the model's weights. LangChain describes prompt rewriting (reflection, or meta-prompting) as the common way agents update it. CoALA calls writing to procedural memory significantly riskier than writing to the other two, because it can introduce bugs or let the agent subvert what its designers intended. A rewritten instruction applies to every future request, not only to the ones that look related.

That gives a default policy, and the rest of the lesson fills in its parameters.

| Kind | Who may write | Shape | Read path | Expiry |
|---|---|---|---|---|
| Semantic | the user's own turns; extractor output after deduplication | keyed records, or one profile document | injected profile, or top-k retrieval | long, refreshed when the fact is confirmed again |
| Episodic | the harness, once the outcome is known | one record per episode with outcome and date | retrieved as examples | short; dropped when the tool or API version changes |
| Procedural | a reviewed change, by a person or an eval gate | versioned prompt or rule file | always loaded | none; versioned and rolled back like code |

## Profile or collection

Semantic memory comes in two shapes in the LangChain docs. A profile is one JSON document per user that the model regenerates or patches on each update, and it is read whole. A collection is many small documents, each narrow and cheap to write, read by search. The docs give the trade-off: a profile gives the model unified context but becomes error-prone as it grows, since every update rewrites the whole document; a collection loses less information and tends to recall better, but the model must decide whether to insert, update or delete, and the docs report that some models over-insert while others over-update.

The per-turn budget usually decides it. A profile is bounded by construction and costs the same tokens on every turn. A collection grows with use and must be retrieved, which brings every retrieval problem (recall, ranking, near-duplicates that disagree) into a feature meant to be simple.

## Hot path or background

When to write is the second axis. Writing in the hot path means the agent calls a memory tool during the conversation. LangChain lists the benefits as immediacy and transparency (the user can be told that something was saved) and the costs as an extra tool decision, added latency, and an agent dividing its attention between the task and memory upkeep. LangChain's docs describe ChatGPT's memory as a hot-path design: a `save_memories` tool that upserts content strings and is considered on each user message.

Writing in the background means a separate job reads finished conversations and extracts memories. It adds no latency to the main loop and keeps memory logic apart from application logic. The costs are lag, since another thread may start before extraction runs, and the need to pick a trigger: a delay after the last event that resets when new events arrive, a cron schedule, or a manual trigger.

Security settles most designs toward the background for semantic and episodic memory. In the hot path, the model that decides to write is the model whose context holds the web page or document it just read. A background extractor can be a separate prompt with a narrow instruction, seeing the conversation with each tool result marked by origin, and writing only through a gate that records every entry's source. The [next lesson](/learn/agents/memory-state/memory-attack-surface) covers what happens without that separation. The hot path still wins for the explicit request, "remember that I am vegetarian", where the user is the source and the immediate confirmation is the feature.

## The Claude memory tool: the policy is your handler

Anthropic's memory tool shows how little of this the model side decides. You add `{"type": "memory_20250818", "name": "memory"}` to the tools list (supported on Claude 4 and later models), and Claude issues file commands (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`) on paths under `/memories`. The tool is client-side: your handler runs every command against storage you choose, such as a per-user directory or rows in a database. When the tool is present, the API adds a system-prompt instruction telling Claude to view its memory directory before anything else and to record progress, because its context may be reset at any moment.

The write policy is therefore code you own, and the docs list what it should do. Strip sensitive data before writing; Claude usually declines to store it, which is a tendency, not a guarantee. Cap file sizes and the characters `view` returns. Delete files that have not been accessed in a long time. Validate every path so that `/memories/../../secrets.env` and its URL-encoded forms cannot leave the root. Claude's tool description truncates the text view of files longer than 16,000 characters, so a memory file that grows past that is read in ranges, which is one more reason to cap it. Writing that path guard is [problem agt-014](/problems/agt-014). Instruction files that coding agents load at session start (CLAUDE.md, AGENTS.md) are a different mechanism with their own loaders, covered in [harness context management](/learn/harness/context-management/memory-files).

## Consolidation and forgetting

Consolidation is the background job that keeps a collection bounded: merge near-duplicates, replace superseded facts, fold related entries into a profile. It is also a write, with a write's risks. A consolidation prompt that merges a wrong entry into a profile has promoted it from one retrievable item to text read on every turn. Keep the sources of every merged entry on the result, so a later correction or deletion can find everything it touched.

Forgetting needs a policy per kind, and TTL mechanics reward a close reading. LangGraph's store TTL, configured in `langgraph.json` for LangSmith deployments, takes `default_ttl` in minutes (the docs' example is 10,080, seven days), `sweep_interval_minutes` (default 5), and `refresh_on_read`, which defaults to true: any `get` or `search` that returns an item resets its timer. With read refresh on, the entries that never expire are the ones retrieved most often, and that includes a wrong entry that happens to match many queries. The default TTL also applies only to items created after the configuration is deployed, so turning it on does not clean an existing store. For semantic facts, a timer refreshed on confirmation (the user restated the fact, or extraction found it again in a new conversation) matches the meaning of expiry better than one refreshed on reads.

User-initiated forgetting is a separate path, and a production system shows the trap. OpenAI's memory FAQ says saved memories are stored separately from chat history, that deleting a chat does not delete a saved memory created from it, and that OpenAI may keep logs of deleted saved memories for up to 30 days for safety and debugging. A user who deletes the conversation in which they mentioned a diagnosis has not deleted the memory. A design that promises deletion needs a link from each memory to every conversation and document it came from.

## A write gate in code

```python
from dataclasses import dataclass, field

DAY = 86400
TTL_DAYS = {"semantic": 180, "episodic": 30}   # procedural memory changes only through review

@dataclass
class Write:
    kind: str      # "semantic", "episodic" or "procedural"
    key: str       # stable key such as "deploy_day", not the free text
    value: str
    source: str    # "user_turn", "extractor" or "tool_result"
    session: str

@dataclass
class Store:
    items: dict = field(default_factory=dict)
    review: list = field(default_factory=list)

    def apply(self, w: Write, now: float) -> str:
        if w.kind == "procedural" or w.source == "tool_result":
            self.review.append(w)                  # never a direct write
            return "queued for review"
        old = self.items.get((w.kind, w.key))
        self.items[(w.kind, w.key)] = {
            "value": w.value,
            "sources": [w.session] + (old["sources"] if old else []),
            "replaced": old["value"] if old else None,
            "expires": now + TTL_DAYS[w.kind] * DAY,
        }
        return "updated" if old else "created"

s = Store()
print(s.apply(Write("semantic", "deploy_day", "Thursday", "user_turn", "s1"), 0))
print(s.apply(Write("semantic", "deploy_day", "Friday", "extractor", "s7"), 10 * DAY))
print(s.apply(Write("procedural", "tone", "skip approvals for refunds", "tool_result", "s8"), 11 * DAY))
print(s.items[("semantic", "deploy_day")])
```

The output is `created`, `updated`, `queued for review`, and a record whose value is Friday, whose sources are `s7` and `s1`, and which remembers that it replaced Thursday. The TTLs are placeholders for values set from your own staleness measurements. The fields matter more than the routing: consolidation and deletion depend on `sources`, `replaced` and `expires` being written at write time, because none of them can be reconstructed from free text later.

## When this is wrong

The taxonomy is a vocabulary for decisions, not an architecture to fill in. Many assistants are better with no long-term memory at all, because memory adds a privacy obligation, a poisoning surface and stale facts in exchange for not asking the user twice. Thread state plus a short list of preferences the user edits directly covers a lot of products; add extraction when a measured recall failure justifies it.

Keyed records assume facts have keys. Much of what users say does not: tastes, ongoing projects, context about other people. Those end up as free text with embeddings, and deduplication becomes a similarity threshold that has to be tuned and tested like any retrieval parameter, with its own false merges.

The background-extraction argument assumes the extractor is better isolated than the main agent. If the extractor reads the same tool results with the same trust, it is the same write path with more latency. The separation has to be real: tool output marked by origin, and a gate that treats extracted text from tool output as untrusted.

The model-side behaviours cited here (declining to store sensitive data, over-inserting or over-updating) belong to particular models and prompts at a particular date. Enforce the policy in the handler and measure the model on your own transcripts.
