## Persistence turns one injection into every session

A prompt injection without memory lasts as long as the context that holds it. Close the conversation and the attacker's instructions are gone. Long-term memory removes that bound. If injected text can cause a memory write, the instructions are replayed into future contexts, in a position the model treats as trusted background about the user, and they keep running after the page or document that carried them is forgotten.

Three properties make memory a better foothold than the conversation itself. It persists across sessions and devices. It is injected into contexts where the user never saw the original source. And it is mostly invisible: the user sees a short notice at write time, if the product shows one, and nothing at read time unless the product shows sources. For a security review, memory belongs in the same class as a stored cross-site scripting payload: data written once from an untrusted path and executed in later, trusted contexts. The difference is that there is no parser boundary to escape. The model reads memory as language, and instructions are language.

## The spAIware chain

Johann Rehberger's September 2024 write-up against the ChatGPT macOS app is the reference case, and its timeline matters as much as its mechanism.

The chain had two halves. First, the user asks ChatGPT to look at an untrusted website or document. Instructions inside it make ChatGPT call its memory tool and store a memory whose content is itself an instruction: send what the user types, and the replies, to an attacker's server. Second, in every later conversation that memory is loaded, and ChatGPT renders an image from the attacker's server with the conversation data in the URL's query string. The image can be invisible. Because the server sees every request and controls the image responses, the author points out it can also serve updated instructions, which turns the channel into command and control.

The timeline, from the post: image-based exfiltration was reported to OpenAI in April 2023. OpenAI added a `url_safe` check in December 2023, but only in the web app, and the check ran client-side, so mobile and desktop clients that did not call it stayed exposed. The memory-injection half was reported in May 2024 and closed as a model safety issue rather than a security one. An end-to-end exploit across sessions followed in June 2024. ChatGPT macOS 1.2024.247 fixed the exfiltration channel in September 2024, and the author states plainly that injecting memories through prompt injection was not fixed.

The design lesson is in that last sentence. The vendor closed the sink (image rendering to arbitrary hosts) and left the write path open. That is a defensible priority, since a poisoned memory without an exfiltration sink can mislead but cannot leak, but it means every future sink (a new connector, a new renderer, a browsing tool) re-opens the whole chain against memories that are already stored.

## The user's yes is not provenance

A common first defence is to allow memory writes only when the user asked for them. Rehberger's February 2025 post on Gemini shows why "the user asked" is weaker than it sounds. A document's hidden instructions shape the summary Gemini produces and end it with a question; the instructions say that if the user replies yes, sure or no, Gemini should save particular memories. The user answers the question, Gemini treats the reply as a direct instruction, and the memory tool runs. The demo saved false facts (an age of 102, a belief that the earth is flat), and Gemini repeated them later. Google assessed the issue as low likelihood and low impact; the author's recommendations were to require explicit confirmation before persisting memories and to treat sensitive tool calls as needing confirmation once the context holds untrusted data.

The general point: the turn that triggers a write can be the user's, while the content of the write is the attacker's. Provenance has to describe where the text of the memory came from, not who sent the last message. A confirmation that asks "save this?" without showing the exact text to be stored, and the source it came from, is a confirmation the attacker can elicit.

## The read side: memory is a data source

Memory is also something to steal. OpenAI's system card for ChatGPT agent (July 2025) lists, among its prompt-injection mitigations, that memory was disabled at launch for the agent, to mitigate injections that try to exfiltrate data from memory, with a note that this might be revisited. An agent that browses arbitrary pages, has connectors to the user's mail and calendar, and has a summary of everything the user has told the assistant over months has collected the three ingredients of an exfiltration in one context: untrusted instructions, private data, and a way out. Removing one of the three is the cheapest control; the agent team removed memory.

The same reasoning applies to your own design. Decide per tool set whether memory is loaded at all. A session that will read untrusted content and can make outbound requests is the place to load only the memory the task needs, or none.

## Provenance on every entry

Most of the controls depend on fields written at the moment of the write.

Each entry records its sources: the conversation IDs, documents and connector items whose content produced it. Each entry records taint: whether the context that produced it contained untrusted content (a web page, a retrieved document, an email, a tool result from a third-party server) at the time of the write. Consolidation keeps both: an entry merged from a tainted entry and a clean one is tainted, and its sources are the union.

With those fields, the write gate is a policy rather than a hope. Writes from untainted contexts that the user explicitly requested go straight in. Writes from tainted contexts need a confirmation that shows the exact text and its origin, or go to a review queue the user sees later. Procedural memory (anything that changes how the assistant behaves, as opposed to facts about the user) is never written from a tainted context. At read time, memory is rendered into the prompt as quoted data with its origin, separate from the instructions, and tainted entries can be excluded from sessions that have outbound tools.

The cost is friction, and it is worth computing before arguing about it.

<p>10 × 1.5 = 15 proposed writes a week, and 15 × 0.6 = 9 of them come from tainted contexts, so 9 prompts a week. That is enough for prompt fatigue to set in, and a fatigued user is exactly what the delayed-invocation attack relies on. The levers are in the inputs: write less often (batch proposals to the end of the session, which also makes the confirmation a review of a list), narrow taint (a fact the user typed before any tool result arrived is not tainted by a page read later), or route tainted proposals to a review queue that blocks nothing.</p>
</Predict>

TTL settings interact with poisoning. LangGraph's store, for example, refreshes an item's expiry on every `get` or `search` by default. A poisoned entry written to match many queries is retrieved often, so it never expires; expiry refreshed on confirmation, not on reads, removes that advantage.

## Deletion has to reach memory

Memory makes deletion a graph problem. OpenAI's current memory FAQ lists the places remembered information can live for one fact: the memory summary, saved memories, regular and archived chats, files in the Library, and connected apps. Deleting a chat does not necessarily delete a saved memory created from it. "Don't mention this again" reduces future references without deleting the source. Turning off chat-history reference schedules what was remembered from past chats for deletion within 30 days, and OpenAI may keep logs of deleted saved memories for up to 30 days for safety and debugging. In ChatGPT for Healthcare and regulated Enterprise workspaces, improved memory is off by default and not covered by the BAA, and the FAQ says protected health information should not be entered with it on.

Each of those is a reasonable product decision, and together they show what a deletion request has to traverse. The design question is what your system does when the source of a memory is deleted, especially after consolidation has merged it with content from sources that were not deleted.

```python
from collections import defaultdict

class Memory:
    def __init__(self):
        self.entries = {}                     # id -> text, sources, tainted, stale
        self.by_source = defaultdict(set)     # chat or document id -> entry ids

    def write(self, eid, text, sources, tainted):
        self.entries[eid] = {"text": text, "sources": set(sources),
                             "tainted": tainted, "stale": False}
        for s in sources:
            self.by_source[s].add(eid)

    def consolidate(self, eid, parts, text):
        sources = set().union(*(self.entries[p]["sources"] for p in parts))
        tainted = any(self.entries[p]["tainted"] for p in parts)
        for p in parts:
            self.forget(p)
        self.write(eid, text, sources, tainted)   # taint and provenance survive the merge

    def delete_source(self, src):
        gone, rederive = [], []
        for eid in sorted(self.by_source.pop(src, set())):
            e = self.entries[eid]
            e["sources"].discard(src)
            if e["sources"]:
                e["stale"] = True                  # text still mixes in deleted content
                rederive.append(eid)
            else:
                self.forget(eid)
                gone.append(eid)
        return gone, rederive

    def forget(self, eid):
        for s in self.entries.pop(eid)["sources"]:
            self.by_source[s].discard(eid)

    def render(self):
        return "\n".join(
            f'<memory id="{k}" tainted="{str(v["tainted"]).lower()}">{v["text"]}</memory>'
            for k, v in sorted(self.entries.items()) if not v["stale"])

m = Memory()
m.write("m1", "Prefers vegetarian restaurants", ["chat-4"], tainted=False)
m.write("m2", "Has a nut allergy", ["chat-9"], tainted=False)
m.write("m3", "Uses the Lisbon office", ["chat-9", "doc-2"], tainted=True)
m.consolidate("m4", ["m1", "m2"], "Vegetarian; nut allergy")
print(m.delete_source("chat-9"))
print(m.render())
```

Deleting `chat-9` prints `([], ['m3', 'm4'])` and then an empty render. No entry came only from `chat-9`, so nothing is simply deleted, yet both remaining entries still contain text derived from it. The consolidated `m4` mixes the vegetarian preference from `chat-4` with the allergy from `chat-9`, and no string operation can separate them reliably. Both are withheld from prompts until a re-derivation job rebuilds them from their remaining sources. That job is the expensive part of a deletion promise, and it is why consolidation without provenance makes a deletion guarantee impossible to keep.

## When this is wrong

Taint tracking at the context level is coarse. Once a session has read one web page, everything after it is tainted, including facts the user typed themselves. Finer tracking (which span of text a proposed memory was drawn from) is possible with structured extraction and quoting, but it is model-dependent and can be fooled by paraphrase. Context-level taint over-blocks; span-level taint under-blocks. Choose knowingly and measure both rates on real sessions.

Closing sinks does more than gating writes in the short term, which is why the vendors in both cases fixed sinks first. The argument here is not that sink fixes are wrong, only that they leave stored memories waiting for the next sink. If your product has no outbound channels at all (no rendering of remote content, no tools that make requests), memory poisoning degrades answers but cannot leak data, and a lighter write policy is defensible.

The vendor details are dated. ChatGPT's memory controls, OpenAI's retention notes and the agent's memory setting have each changed since launch, and the system card itself says the memory decision may be revisited. Cite them with their dates, and re-check before using any of them as a current fact.

Model refusals are not controls. The Claude memory tool docs say Claude usually refuses to write sensitive information and recommend handler-side validation for stronger guarantees. That pattern holds for every vendor: the model's tendency reduces volume, and the handler enforces the policy.
