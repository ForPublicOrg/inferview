## The run that cost more than the week

Scenario, not a real company: a team ships an internal agent that answers questions about deploys. In testing, a typical question takes four model calls. In the first week of production, the median run is still four calls, but a handful of runs go to sixty, and those few runs account for most of the bill. Nobody wrote a bug in the usual sense. The loop did exactly what it was told: call the model, run the tool it asked for, append the result, call the model again.

That loop is the whole subject of this lesson. If you can draw it, cost it and stop it, you can answer most first-round agent questions, and you can debug the trace in [Agent loops forever](/problems/agt-002).

## An agent is a while loop you own

Strip away the frameworks and an agent is this:

```python
def run_agent(messages, tools):     # model and run_tool are stand-ins
    while True:
        reply = model(messages, tools)
        if reply.is_final:
            return reply.text
        result = run_tool(reply.tool_name, reply.args)
        messages += [reply, result]
```

If you have written an interpreter, you have written this shape. The model is the instruction decoder: it reads the program state (the message list) and emits the next instruction (a tool call) or halts (plain text). Your code is the machine that executes the instruction and writes the result back into state. The difference from an interpreter is that the decoder is stochastic and nobody wrote the program in advance. The model decides the control flow at run time.

The ReAct paper gave this pattern its name: the model interleaves a reasoning trace with actions, and each observation feeds the next step. Its reported gains were large for 2022, +34 and +10 points of absolute success over imitation and reinforcement-learning baselines on two interactive benchmarks. Today native tool calling has replaced the text parsing ReAct used, but the loop is the same.

Anthropic's definitions are the ones interviewers expect. Workflows are "systems where LLMs and tools are orchestrated through predefined code paths". Agents are systems where "LLMs dynamically direct their own processes and tool usage". The same post names five workflow patterns: prompt chaining, routing, parallelization, orchestrator-workers, and evaluator-optimizer. Each is a fixed graph you could draw before the request arrives.

<Callout kind="interview" label="Interview tip">
"Agent or workflow?" is really "how much control flow are you willing to hand to the model?" Pick the least autonomy that solves the task. If you can draw the graph in advance, write the graph. Reach for the open loop when the number and order of steps depends on what the tools return.
</Callout>

## The loop is quadratic

Every model call re-sends the whole conversation, because the model has no memory between calls. If the run starts with an 8,000-token prefix (system prompt plus tool definitions) and every turn adds 3,000 tokens of tool results and replies, call *k* sends 8,000 + 3,000 × (*k* − 1) tokens.

At Claude Opus 5.5's list price of $4 per million input tokens, those 1,545,000 tokens cost $6.18, and 30 replies of 400 output tokens at $20 per million add $0.24, so the run costs $6.42. Prompt caching changes the shape: everything already sent is read from cache at $0.20 per million, and only the new 3,000 tokens per turn are written at $5 per million. The same run then costs about $1.00 (1,450,000 cached tokens read for $0.29, 95,000 tokens written for $0.475, and the same $0.24 of output). Move the sliders and watch which term dominates.

Two things to notice. Doubling the calls nearly quadruples the input tokens, which is why one runaway run can outweigh a hundred normal ones. And the cached number assumes every turn hits the cache. The Codex post lists what breaks that: the prefix must match exactly, the tool list must be identical between requests, and an MCP server announcing a changed tool list mid-conversation causes an expensive miss. Treat the prompt prefix like a build cache key: anything that reorders or edits early content invalidates everything after it.

## Termination: three budgets and a stuck detector

A loop with no exit condition other than "the model says it is done" will eventually meet a model that never says it. Production loops carry three budgets and one detector.

A step budget caps model calls. The OpenAI Agents SDK raises `MaxTurnsExceeded` past `max_turns`, which defaults to 10 in its source. LangGraph raises `GraphRecursionError` past `recursion_limit`; its docs say the default became 1000 in version 1.0.6, while the source code says 10000 at that tag, so set the limit yourself rather than trusting either number. The Claude Agent SDK takes `max_turns`.

A spend budget caps money, which a step cap does not, because steps get more expensive as context grows. The Claude Agent SDK exposes `max_budget_usd`. In your own loop, check the projected cost of the next call before making it.

A wall-clock budget caps latency for anything a user is waiting on.

The stuck detector catches the failure the budgets only bound: the same tool called with the same arguments, getting the same error. Count `(tool name, canonical JSON of the arguments)` per run and stop when a key repeats more than a small number of times. That heuristic misfires on tools that legitimately poll, so make the threshold per tool.

<Callout kind="gotcha">
Raising `max_steps` is the wrong fix for a looping agent. It makes the loop more expensive and changes nothing about why it loops. The usual cause is an error contract: the tool returns an opaque error, the loop hands it back, and the model reads "error" as "try again".
</Callout>

## Planning, reflection and verification

Two refinements of the loop come up often. Plan-then-execute asks the model for a plan first and then runs steps against it, which makes traces easier to read and lets you check the plan before anything irreversible happens. Reflection, which Anthropic's post calls evaluator-optimizer, sends the output to a second prompt that critiques it and loops until the critique passes.

The Claude Agent SDK describes its loop as four stages: gather context, take action, verify work, repeat. The third stage is the one teams skip. A loop that verifies with something deterministic (tests pass, the schema validates, the record now exists in the database) stops for a reason you can trust. A loop that verifies by asking the model whether it is done stops whenever the model feels done.

Tool design matters as much as loop design. Anthropic reports that while building a SWE-bench agent, the model made mistakes with relative file paths once it had moved out of the root directory, and requiring absolute paths fixed it. They call this poka-yoke, the manufacturing term for designing a part so it cannot be fitted the wrong way.

## A loop you would ship

This version adds the budgets, the stuck detector and an error contract. The model and the cost estimator are stand-ins you pass in, so it runs anywhere. `estimate(messages)` predicts the next call's cost from the current context, and `model` returns the reply with what the call actually cost.

```python
import json
from collections import Counter

class ToolError(Exception):        # terminal: the model cannot fix this by retrying
    pass

def run_agent(model, estimate, tools, user_msg, max_steps=8, max_cost=0.50, max_repeat=2):
    messages = [{"role": "user", "content": user_msg}]
    seen, spent = Counter(), 0.0
    for step in range(max_steps):
        if spent + estimate(messages) > max_cost:   # refuse the call, do not regret it
            return {"status": "stopped", "reason": "budget"}
        reply, cost = model(messages)
        spent += cost
        if reply["type"] == "final":
            return {"status": "done", "answer": reply["text"], "steps": step + 1}
        key = (reply["name"], json.dumps(reply["args"], sort_keys=True))
        seen[key] += 1
        if seen[key] > max_repeat:
            return {"status": "stopped", "reason": "repeated call"}
        fn = tools.get(reply["name"])
        try:
            result = fn(**reply["args"]) if fn else {"error": f"unknown tool {reply['name']}"}
        except ToolError as e:
            return {"status": "stopped", "reason": str(e)}
        except Exception as e:      # bad arguments: let the model correct itself
            result = {"error": str(e), "retryable": True}
        messages += [{"role": "assistant", "tool_call": reply},
                     {"role": "tool", "content": json.dumps(result)}]
    return {"status": "stopped", "reason": "max_steps"}
```

Four choices are worth defending out loud. The budget check runs before the model call, so the call that would break the budget is never made. An unknown tool name goes back to the model as an error, because the model can pick a real tool on the next turn. A `ToolError` ends the run, because no retry will make a refund over the order total valid. And every exit returns a status with a reason, so the caller can show a message and your dashboards can count stops by reason. The [code problem for this module](/problems/agt-003) asks you to write it against tests.

## When this is wrong

The quadratic model assumes the client re-sends the full history every call. Server-side conversation state, compaction and context editing all change the curve, and so do providers whose cache pricing, minimum cacheable length or cache lifetime differ from the numbers used here. The $1.00 cached figure also assumes every single turn hits the cache; one miss on a long context costs more than many hits save.

The stuck detector is a heuristic. An agent can loop without repeating exact arguments (searching for "refund policy", then "refunds policy", then "policy on refunds"), so in practice teams also watch for repeated results and for the same tool dominating a run.

And "agent" is a spectrum, not a type. Most production systems that work are mostly workflow with one or two open loops inside them. If you find yourself defending a fully open loop for a task with a fixed shape, the interviewer is waiting for you to say so.
