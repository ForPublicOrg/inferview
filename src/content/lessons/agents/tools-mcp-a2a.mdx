## One hundred and forty tools

Scenario, not a real company: a platform team wraps its internal REST API as an MCP server, one tool per endpoint, 140 tools. The demo works. In production the agent calls `list_orders` when it needed `search_orders`, pulls back 20,000 tokens of JSON to read one field, and when an update fails the error says `400 Bad Request` and nothing else. The model is not the problem. The tools were designed for a client that reads documentation once and then writes code. This client reads the documentation on every call and decides at run time.

## A tool is an API whose client is a model

Everything you know about API design applies, with three changes in emphasis.

Narrow beats general. A tool that does one job with few parameters is easier to choose and harder to misuse. Anthropic's tool-writing guide argues for tools that match how a person would do the task (`schedule_event` that finds a free slot) rather than thin wrappers over every endpoint (`list_users`, `list_events`, `create_event`).

Responses are context, and context is money. Claude Code caps tool responses at 25,000 tokens by default. The same guide shows a `response_format` parameter where the "detailed" response was 206 tokens and the "concise" one 72. Return identifiers the model can pass to the next call, paginate, and filter on the server.

Errors are prompts. The model reads your error message and decides what to do next. "Refund rejected: amount 49.00 exceeds refundable balance 12.50" lets it correct itself; "422" makes it retry. MCP's 2025-11-25 revision clarified that input validation failures should be returned as tool execution errors (`isError: true` in the result) rather than protocol errors, for exactly this reason: the model can see them and fix its arguments.

Descriptions are the documentation the model actually reads. In Anthropic's research system, an agent that rewrote a tool's description cut task completion time by 40% for the agents that used it afterwards.

<Callout kind="gotcha">
Idempotency is a tool property, not a loop property. If a tool can be called twice for one intent (a retry after a timeout, a replay after a crash), it needs an idempotency key or a natural one, or the second call charges the card again.
</Callout>

## MCP: tools across a process boundary

Function calling is the model API feature: you pass tool schemas in the request, the model returns a structured call, your code runs it. The Model Context Protocol is a layer below that: a standard way for an application to discover and call tools, read resources and fetch prompts that live in another process, written by someone else. The roles are hosts (the LLM application), clients (one connector per server, inside the host) and servers. Messages are JSON-RPC 2.0. Servers offer tools, resources and prompts; the client offers elicitation, which lets a server ask the user for input. The host still turns MCP tools into function-calling schemas for the model, so MCP does not replace function calling. It standardizes where the tools come from.

Two transports exist. stdio runs the server as a subprocess and exchanges newline-delimited JSON-RPC over its pipes. Streamable HTTP sends each message as an HTTP POST to one endpoint, and the reply is either a JSON object or an event stream scoped to that request. The older HTTP+SSE transport was replaced in 2025-03-26 and is formally deprecated in 2026-07-28.

## What changed on 2026-07-28

Until this revision, a connection began with an `initialize` request and an `initialized` notification, and over HTTP the server handed back an `Mcp-Session-Id` header that every later request carried. When a tool needed something from the user mid-call, the server sent its own request (an elicitation) back down the open stream and waited. That state lived in memory on one server instance, so a load balancer had to pin every session to the instance that created it.

The current revision removes all of that. Every request carries the protocol version and the client's capabilities in `_meta`, and the HTTP transport mirrors the method and tool name into `Mcp-Method` and `Mcp-Name` headers so a gateway can route without parsing the body. A server that needs more input no longer sends a request. It returns a result with `resultType: "input_required"` and a set of `inputRequests`, and the client sends the original request again with `inputResponses` attached. The same revision deprecates sampling, roots and logging, deprecates OAuth Dynamic Client Registration in favour of Client ID Metadata Documents, moves tasks into an extension, adds a `server/discover` method every server must implement, and asks servers to return `tools/list` in a deterministic order so the tool list does not break prompt caches. Features deprecated in this revision (sampling, roots, logging, Dynamic Client Registration) cannot be removed before 2027-07-28 under the new lifecycle policy, so you will meet servers that use them for a while yet. HTTP+SSE, deprecated since 2025-03-26, has a shorter window: it becomes eligible for removal three months after the lifecycle policy itself is finalized.

<Callout kind="interview" label="Interview tip">
If you describe MCP with `initialize` and session IDs as the current design, a well-read interviewer will notice. Say "until the 2026-07-28 revision" and then explain why it went stateless. That one sentence shows you follow the spec, not a blog post from last year.
</Callout>

## Authorization for remote servers

Over HTTP, an MCP server is an OAuth 2.1 resource server. It publishes Protected Resource Metadata (RFC 9728) so the client can find the authorization server. The client uses PKCE and sends a `resource` parameter (RFC 8707) naming the server it wants a token for, and the server must check that a presented token was issued for it (the audience) and must not pass the token through to anything else. stdio servers skip OAuth and take credentials from the environment.

Two transport rules prevent the browser attacks people forget. Servers must validate the `Origin` header, which blocks DNS rebinding, and local servers should bind to 127.0.0.1 rather than 0.0.0.0.

Tool annotations such as `readOnlyHint` and `destructiveHint` are hints for the client UI. Their defaults assume the worst (not read-only, destructive, open-world), and the schema itself says clients should never make tool-use decisions based on annotations from untrusted servers. A server that lies about being read-only is the threat you are defending against, so annotations cannot be the defence.

## A2A: agents as peers

MCP connects an agent to tools. The Agent2Agent protocol connects agents to other agents that are opaque to each other: different teams, vendors or frameworks. Each agent publishes an Agent Card at `/.well-known/agent-card.json` describing its skills and how to reach it. Messages travel over JSON-RPC, gRPC or HTTP+JSON. Work is a task with a lifecycle: submitted, working, then completed, failed, canceled or rejected, with two interrupted states, input required and auth required, for when the remote agent needs something. Clients must send an `A2A-Version` header.

A2A is a Linux Foundation project; the Linux Foundation's April 2026 release calls v1.0 the first stable specification and counts more than 150 supporting organizations. The spec's own appendix answers the comparison question: MCP standardizes how an agent uses tools and data, A2A standardizes how independent agents communicate, and an A2A agent may use MCP internally.

## Too many tools

Every tool definition sits in the context of every call, and similar tools blur together. Four fixes, in rough order of effort. Namespace and merge tools so the list is short and each name says what it does. Route first: a small classifier or a cheap model picks a toolset, then the agent sees only that set. Load on demand: Agent Skills package instructions and scripts in a folder with a `SKILL.md`, and an agent sees only each skill's name and description (about 100 tokens per skill, per the spec) until it decides to open one.

Write code instead of calls: Anthropic presented MCP servers to an agent as a file tree of code APIs. The agent reads only the tool files it needs for the task, then writes a short program that calls them, so intermediate results stay in the sandbox instead of passing through the context.

## Permissions and tool firewalls

The question "can this agent read email and send money?" is a permission design question. Simon Willison's lethal trifecta is the test: an agent with access to private data, exposure to untrusted content, and a way to communicate externally can be talked into leaking the data. Remove one leg per agent, require confirmation for irreversible actions, and enforce allowlists in your host code, never in the prompt. The [coding agents lesson](/learn/agents/coding-agents) builds the approval gate itself.

## Building a stateless request

```python
PROTOCOL_VERSION = "2026-07-28"

def tools_call(req_id, name, arguments, client_caps=None, input_responses=None):
    params = {
        "name": name,
        "arguments": arguments,
        "_meta": {
            "io.modelcontextprotocol/protocolVersion": PROTOCOL_VERSION,
            "io.modelcontextprotocol/clientCapabilities": client_caps or {},
        },
    }
    if input_responses:                      # retrying after an input_required result
        params["inputResponses"] = input_responses
    return {"jsonrpc": "2.0", "id": req_id, "method": "tools/call", "params": params}

def headers(msg):
    return {
        "Accept": "application/json, text/event-stream",
        "MCP-Protocol-Version": PROTOCOL_VERSION,
        "Mcp-Method": msg["method"],
        "Mcp-Name": msg["params"]["name"],
    }
```

A result with no `resultType` is treated as complete. The client loop is: send, and if the result says `input_required`, collect the answers (from the user, or from policy) and send the same call again. No session to restore, so the retry can land on any instance.

<Fragment slot="short">
<p>Function calling is how a model asks your code to run a tool you described in the request. MCP is a protocol for getting those tools, plus resources and prompts, from servers in other processes or on other machines, written by other people. The host still exposes MCP tools to the model through function calling. As of the 2026-07-28 revision MCP is stateless: no handshake, no sessions, and a server that needs input returns input_required instead of calling the client back.</p>

<Fragment slot="long">
<p>Layering. Function calling is a model API feature. MCP sits beneath the host: hosts run one client per server, servers expose tools, resources and prompts over JSON-RPC 2.0, via stdio for local subprocesses or Streamable HTTP for remote ones.</p>
<p>What MCP buys. One integration per tool provider instead of one per application, discovery at run time, and a shared auth story: remote servers are OAuth 2.1 resource servers, clients send RFC 8707 resource indicators and use PKCE, servers check token audience and never pass tokens through.</p>
<p>The current revision. 2026-07-28 removed the initialize handshake and Mcp-Session-Id. Version and capabilities ride in _meta on every request, and server-initiated requests became multi round-trip requests, so any instance can serve any request. Sampling, roots and logging are deprecated.</p>
<p>Costs. Every tool definition is context on every call, servers you do not control can change their tool list and break your prompt cache, and a third-party server is a supply-chain dependency with code and data access. Annotations are hints, not security.</p>
</Fragment>

## When this is wrong

The protocol facts in this lesson are pinned to the 2026-07-28 MCP revision and A2A 1.0, both checked on the date at the top of the page. MCP published five revisions between November 2024 and July 2026, so check the changelog before an interview, and expect real deployments to lag: many servers and clients still speak 2025-11-25 during the deprecation window.

The tool-design numbers come from one vendor's experience with its own models. A 40% speed-up from a rewritten description is a reason to measure your own descriptions, not a constant.

And "fewer, better tools" has a limit. Some domains really have hundreds of operations. There the answer is routing or code execution, not merging until each tool does five unrelated things.
