## Two posts, one week, opposite advice

On 12 June 2025 Cognition published "Don't Build Multi-Agents". The next day Anthropic published how it built Claude's Research feature as a lead agent that spawns parallel sub-agents, and reported that it beat a single agent by 90.2% on its internal research eval. Both are right, about different tasks. The decision this lesson teaches is which kind of task you have, and what the answer costs.

The test has two inputs. How separable is the work: can a subtask be done well by an agent that sees only its brief and returns a short result? And how much is a better answer worth: enough to pay several times the tokens of doing it in one context? Multi-agent wins when both are yes. When subtasks share decisions, it loses even if money is no object.

## Fan-out with lossy workers

The shape is scatter-gather: a lead splits the work, workers run in parallel, the lead merges. Two things differ from the scatter-gather in a search backend. The workers are not deterministic shards of one query; each reinterprets its brief. And the merge receives prose that is a compression of everything the worker read, so whatever the worker did not write down is gone. Anthropic's post makes compression the point: sub-agents read widely in their own context windows and condense the important tokens for the lead. Cognition's post makes it the problem: every action carries decisions nobody wrote down, and an agent that sees only a brief cannot honour decisions it never saw.

Cognition's example is a Flappy Bird clone split into two sub-tasks, the background with its pipes and the bird. One sub-agent produced a background in the style of Super Mario Bros; the other produced a bird that neither looked nor moved like the game's. Giving both sub-agents the full conversation did not fix it, because they still could not see each other's work. The two outputs were each defensible and jointly wrong, which is the signature of coupled work.

Research questions split the other way. "Find the board members of every IT company in the S&P 500", the example in Anthropic's post, has dozens of subtasks whose answers do not constrain each other. A worker that gets one company wrong does not make another worker's company wrong, and the merge is a union.

## What the published numbers say, and under what conditions

Anthropic's system ran Claude Opus 4 as the lead and Claude Sonnet 4 as sub-agents. On BrowseComp, three factors explained 95% of the variance in performance: token usage alone explained 80%, and the number of tool calls and the model choice the rest. That reframes the 90.2%. Much of what several agents buy is the ability to spend more tokens on a question in parallel, each in a fresh context, than one context window allows. The same post reports that upgrading to Sonnet 4 gained more than doubling the token budget on Sonnet 3.7, so spend is not the only lever.

The spend is large. In Anthropic's data agents used about 4 times the tokens of a chat interaction and multi-agent systems about 15 times. The post states the economic condition plainly: the task has to be valuable enough to pay for the performance. Latency moves the other way. The lead starts 3 to 5 sub-agents in parallel and each sub-agent calls 3 or more tools in parallel, which cut research time by up to 90% for complex queries.

Anthropic also published where it does not fit: domains where all agents need the same context, or with many dependencies between agents, and most coding tasks, which have fewer truly parallelizable parts than research. OpenAI's practical guide to building agents gives the same default from the other side: maximize a single agent first, and split when prompts accumulate branching logic or the agent keeps choosing the wrong tools. Its tool-count observation is about overlap, not size: some systems handle more than 15 distinct tools while others struggle with fewer than 10 overlapping ones.

## Why the token bill is not simply N times one agent

Each turn of an agent re-sends its whole history. One context that makes 45 tool calls pays for a history that grows with every result, so its input tokens grow with the square of its length. Three workers making 15 calls each pay for three short histories. At fixed work, splitting can be cheaper per call; Anthropic's 15 times comes from multi-agent systems doing far more work, not from the split itself. The toy model below makes the difference visible. Its token counts are a stated scenario, not measurements; the prices are the list prices above.

```python
PRICES = {  # USD per million tokens: input, output, cache write (5 min), cache read; checked 2026-10-28
    "opus-5.5": (4.00, 20.00, 5.00, 0.20),
    "sonnet-5.5": (2.00, 10.00, 2.50, 0.10),
}

def run_cost(model, turns, base, per_turn, out_per_turn, final_out, cached=False):
    """One agent context: every turn re-sends the whole history, then appends a tool result and a short output."""
    p_in, p_out, p_write, p_read = PRICES[model]
    total_in = sum(base + i * per_turn for i in range(turns))
    out = turns * out_per_turn + final_out
    if not cached:
        return (total_in * p_in + out * p_out) / 1e6
    new = base + (turns - 1) * per_turn          # tokens written to the cache once
    return ((total_in - new) * p_read + new * p_write + out * p_out) / 1e6

single = run_cost("opus-5.5", 45, 3000, 2200, 200, 2000)
worker = run_cost("sonnet-5.5", 15, 3000, 2200, 200, 1000)
lead = run_cost("opus-5.5", 6, 3000, 1200, 200, 3000)
print(f"single {single:.2f}  multi {lead + 3 * worker:.2f}")    # single 9.47  multi 2.00
single_c = run_cost("opus-5.5", 45, 3000, 2200, 200, 2000, cached=True)
multi_c = run_cost("opus-5.5", 6, 3000, 1200, 200, 3000, True) + 3 * run_cost("sonnet-5.5", 15, 3000, 2200, 200, 1000, True)
print(f"cached: single {single_c:.2f}  multi {multi_c:.2f}")   # cached: single 1.16  multi 0.58
```

The scenario: a 3,000-token system prompt and task, each turn appending a 2,000-token tool result and 200 tokens of model output, so 2,200 tokens per turn. The single agent runs on Opus 5.5 for 45 turns. The multi-agent version runs three Sonnet 5.5 workers for 15 turns each, and an Opus 5.5 lead for 6 turns whose results are 1,000-token summaries.

The toy holds the work fixed at 45 calls. Real multi-agent systems do not: the lead's effort rules in Anthropic's post go from one agent with 3 to 10 tool calls for a fact check, to 2 to 4 sub-agents with 10 to 15 calls each for a comparison, to more than 10 sub-agents for complex research. Each worker also pays its own system prompt, its own planning and duplicated reads. The bill you should expect is the 15 times chat that Anthropic measured, not the toy's saving, and the toy says why the saving from short contexts does not offset it.

## Every boundary is a step that can fail

A multi-agent run adds steps a single agent does not have: the lead writes a brief, the worker interprets it, the worker summarises, the lead merges. If each of those succeeds independently with probability p, the run succeeds with p to the power of the number of steps, and a user who runs the system k times sees pass^k, every run succeeding.

<AgentsCompounding />

At the defaults, 10 steps at 0.95 succeed 59.9% of the time end to end, and pass^4 is 12.9%. Raise the step success rate to 0.99 and the longest chain that still succeeds half the time goes from 13 steps to 68. The arithmetic argues for fewer boundaries and for a check at each join that catches an error before the next step builds on it. The delegation-contract lesson in this module is about writing that check.

## Three tasks, decided

Due-diligence research across 40 vendors, each needing its security pages, pricing and incident history read. Separable: each vendor is independent and returns a short structured record. Worth the spend if the report replaces analyst days. Several agents, one per batch of vendors, with the lead merging records and a citation pass at the end. Cost: plan for something like Anthropic's 15 times a chat interaction, and measure it.

Renaming a field across a service, its 40 call sites, a migration and the tests. Coupled: the migration's shape decides what every call site writes, and a test fix in one file depends on a choice in another. One agent with one context, using sub-agents only to answer bounded questions ("which call sites write this field?") whose answers come back as lists. That is the pattern Cognition described in Claude Code in June 2025: sub-agents answering a question, never writing code in parallel with the main agent.

Security review of a 30-file pull request. Mixed. Per-file checks (an unparameterised query, a secret in a config) separate cleanly; cross-file issues (authorisation checked in a handler, bypassed by a new route in another file) need one view of the whole change. Parallel readers that return findings in a fixed schema, then one agent that reads the full diff with those findings and looks for interactions. Cost: the readers add tokens, and the single synthesiser still has to read everything, so this only pays if the readers find what the synthesiser alone would miss; measure that on past reviews before building it.

## When this is wrong

The 90.2%, the 80% of variance and the 15 times are Anthropic's own measurements, on its internal eval and BrowseComp, with Claude 4 models in 2025. They tell you the conditions under which the pattern worked for one vendor's research product, not a gain to quote for yours. Cognition's argument is likewise a design position from a coding-agent company with one worked example, not a measurement.

The separable-or-coupled test assumes you know the coupling before you start. Many tasks look separable and are not: two research workers that each pick a different definition of "revenue" produce records the merge cannot reconcile, exactly as the Flappy Bird sub-agents did. The contract that fixes this, a shared definition written into every brief, is the next lesson's subject.

The compounding widget assumes independent steps at a fixed success rate. Real errors correlate (one bad brief breaks every worker that got it) and recover (a lead that checks a summary can re-dispatch), so it shows how fast an unchecked chain decays, not a prediction for a checked one.

And the boundary moves. Cognition's post expects multi-agent collaboration to improve as single agents get better at communicating context, and Anthropic names asynchronous sub-agents as future work. Recheck both positions against current posts before quoting them as the state of the art.
