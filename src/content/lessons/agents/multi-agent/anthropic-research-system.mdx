## What it is and who runs it

Research is the Claude feature that searches the web, Google Workspace and connected integrations over several minutes and returns a cited answer. Anthropic launched it in April 2025 as an early beta for Max, Team and Enterprise plans in the United States, Japan and Brazil, and in June 2025 published how it is built: an orchestrator-worker system in which a lead agent plans and delegates to sub-agents that search in parallel. The post is the most detailed public account of a production multi-agent system from a model vendor, and every figure in it is Anthropic's own measurement on its own evaluations.

The design at the time of the post: Claude Opus 4 as the lead, Claude Sonnet 4 as sub-agents. That pairing beat single-agent Claude Opus 4 by 90.2% on Anthropic's internal research eval, on queries such as finding the board members of every IT company in the S&P 500. The lesson on when several agents pay covers why that result depends on breadth; this page covers the system.

Lead agent. Analyses the query, uses extended thinking to plan and to assess which tools fit, spawns sub-agents with specific tasks, synthesises what they return and decides whether more research is needed, in which case it spawns more or changes strategy. It scales effort to the query by rules in its prompt: one agent with 3 to 10 tool calls for a simple fact, 2 to 4 sub-agents with 10 to 15 calls each for a comparison, more than 10 sub-agents with divided responsibilities for complex research.

Memory. The lead writes its plan to memory early, because a context that exceeds 200,000 tokens is truncated and the plan must survive. For long conversations, agents summarise completed phases into external memory and can hand off to fresh sub-agents with clean contexts.

Sub-agents. Each gets an objective, an output format, guidance on tools and sources, and boundaries. Each runs its own search loop in its own context window, with interleaved thinking after tool results to judge quality and choose the next query, and starts with short, broad queries before narrowing. The post calls them filters: they read widely and return the important parts, which is the compression that makes the lead's context last.

Search tools. Research searches the web, Google Workspace and connected integrations; MCP servers bring external tools whose descriptions vary in quality. Anthropic built a tool-testing agent that used flawed MCP tools, rewrote their descriptions, and cut task completion time by 40% for later agents using the new descriptions.

Artefact store. Sub-agents can write their output to external storage and pass a lightweight reference back to the lead, instead of relaying everything through the lead's context, which the post calls the game of telephone. The post names structured outputs such as code, reports and data visualisations as the cases it suits.

Citation agent. When the lead stops researching, a citation agent processes the documents and the draft report to find where each claim should be attributed, and the cited result goes to the user.

Synchronous execution. The lead launches a set of sub-agents and waits for all of them before continuing. The post names this as a bottleneck: the lead cannot steer sub-agents mid-run, sub-agents cannot coordinate, and one slow sub-agent blocks the whole system. Asynchronous execution is named as future work, with its costs: result coordination, state consistency and error propagation across sub-agents.

Checkpoints. Agents run for a long time and carry state across many tool calls, so a restart is expensive and an error compounds. The system resumes from where the agent was when the error occurred, using retry logic and regular checkpoints, and tells the agent when a tool is failing so it can adapt, which the post says works surprisingly well.

Production tracing. Full tracing of agent decisions, monitored as decision patterns and interaction structures, without monitoring the contents of individual conversations.

Rainbow deployment. Agents may be mid-run when code ships, so traffic shifts gradually from old to new versions while both stay live, to avoid disrupting running agents.

## Context strategy

Three mechanisms, each answering a different limit. Parallel sub-agents multiply the total context the system can use, which is how token usage, the factor that explained 80% of BrowseComp variance, scales past one window. Memory and phase summaries keep the lead's plan when its own window fills. Artefacts passed by reference keep large outputs out of the lead's context altogether.

The cost of the first mechanism is that each sub-agent sees only its brief. Anthropic's early lead agents wrote short briefs and got duplicated and misdirected work; the fix was the delegation detail above, and the post's limits section says domains where all agents must share context, or with many dependencies between agents, are not a good fit today.

## Tools and permission model

The post describes tool selection, not permissions. The lead assesses which tools fit the task; tool descriptions are treated as part of the prompt, and bad ones send agents down wrong paths. Permissions appear only in the launch post: Workspace access has to be enabled domain-wide by Team and Enterprise admins before users connect accounts. The post says nothing about how sub-agents are restricted, whether they can call write tools in integrations, or how injected instructions in fetched pages are handled.

## Evaluation

Evaluation is part of the system's design. The team started with about 20 queries drawn from real usage, because early changes had effects large enough to see on a small set. A single LLM judge call scored outputs from 0.0 to 1.0 and gave a pass-fail grade against a rubric: factual accuracy, citation accuracy, completeness, source quality and tool efficiency. Because agents take different valid paths to the same answer, the appendix recommends judging the end state rather than the steps. Human testers caught what the judge did not: early agents preferred SEO-optimised content farms over authoritative but lower-ranked sources.

## Cost and latency

Tokens: agents used about 4 times the tokens of chat and the multi-agent system about 15 times, so the post limits the pattern to tasks valuable enough to pay for it. Latency: running 3 to 5 sub-agents in parallel, each making 3 or more tool calls in parallel, cut research time by up to 90% for complex queries. Both are Anthropic's own figures.

Synchronous waves bound how much of that parallelism you keep.

## Failure modes

From the post's own account of early versions: spawning 50 sub-agents for simple queries; searching endlessly for sources that do not exist; sub-agents distracting each other with excessive updates; duplicated and misdirected work from vague briefs; a preference for SEO content farms; and, reported by users, agents not finding obvious information, which production tracing was added to diagnose.

From the architecture: small changes to the lead agent can change sub-agent behaviour unpredictably, so a prompt edit is a system-wide change. A stateful run that fails midway is expensive to restart, which is why the checkpointing exists. A single slow sub-agent blocks its wave. And the post's broader warning, that the gap between a working prototype and a reliable production system is wider than expected, is its own summary of why the production layer in the diagram is half the boxes.

## What is not public

The prompts as they run today: the post links example prompts from the system, open-sourced in Anthropic's Cookbook, and does not say how closely they track production. The internal research eval: its size, its tasks beyond the example, and how the 90.2% was computed. Per-query distributions of cost, token usage and latency, of which the post gives only ratios to chat and a best case for time saved. How the citation agent decides that a passage supports a claim, beyond attributing claims to sources. How the effort rules are enforced: they are described as prompt guidance, and the post does not say whether the runtime caps sub-agent counts or tool calls. Which models run Research today; the post's pairing is from June 2025. Whether asynchronous sub-agents have shipped since. And the permission model for sub-agents over connected integrations.

<p>Not uniformly in tokens: in Anthropic's data token usage explained 80% of BrowseComp variance, so a flat budget cut is a quality cut. I would route by query type first, sending simple fact queries to one agent with a small tool budget, which is the post's own effort rule, then move sub-agents to a cheaper model and measure, since model choice was one of the three factors and a model upgrade beat doubling tokens. Every change is gated on the eval with the two-point floor.</p>
</Fragment>
<Fragment slot="long">
<p>First, the cost distribution by query type. If a large share of queries are simple and still fan out to several sub-agents, routing them to one agent is the cheapest win and barely touches quality, because the multi-agent gain comes from breadth those queries do not need. The router itself is a small classifier, evaluated on labelled queries; misrouting a complex query to the single agent is the failure to watch.</p>
<p>Second, the sub-agent model. Sub-agents do most of the reading; a cheaper model there cuts most of the bill if source-quality judgement holds up. Measure on the eval's source-quality and citation-accuracy rubric items, not only the overall score.</p>
<p>Third, waste: duplicated searches across sub-agents, which the delegation contract's ownership field reduces, and re-reads, which prompt caching makes cheaper.</p>
<p>What I give up: complex queries may get slightly thinner reports. I write the per-segment results down, and if the two-point floor holds overall but breaks for one high-value segment, I take that to the product lead rather than averaging it away.</p>
