## The problem the paper solves

Multi-agent frameworks such as ChatDev, MetaGPT, AG2 and Magentic-One often gained little over single-agent frameworks or best-of-N sampling, the paper notes, and nobody could say why in shared terms. Each team read its own traces and named its own bugs. Cemri and colleagues measured failure rates of 41% to 86.7% across seven open-source multi-agent systems and set out to build the missing vocabulary: a taxonomy that two engineers reading the same trace apply the same way.

The analogy is an incident classification scheme for postmortems. The difference is the unit of analysis: a postmortem classifies one outage after the fact, while MAST is applied to every trace in an eval run, so the output is a failure profile per system that you compare before and after a change.

## The mechanism

The taxonomy came from data, not from a design. Six experts read 150 traces from five frameworks (HyperAgent, AppWorld, AG2, ChatDev and MetaGPT) on programming and maths tasks, using Grounded Theory: label what you see, compare across traces, merge and split labels, and stop when new traces add no new modes. That took over 20 hours of annotation per expert.

Then they tested whether the labels were usable by someone else. In each of three rounds, three annotators independently labelled five randomly chosen traces, discussed every disagreement, and changed the definitions: adding, removing or merging modes. Resolving disagreements alone took about 10 hours. Agreement in the final rounds averaged a Cohen's kappa of 0.88. The process is the one you would use to make a labelling guide for a golden set, and it is the reason the definitions are short and operational.

Finally they made it cheap. An LLM annotator (OpenAI o1, given the definitions and few-shot examples from the human labels) reached 94% accuracy and a kappa of 0.77 against the experts; zero-shot it reached 89% and 0.58. On systems and benchmarks it had not seen, kappa was 0.79. That annotator labelled MAST-Data: 1,642 traces from seven frameworks, with GPT-4-series, Claude 3.7 Sonnet, Qwen2.5-Coder and CodeLlama models.

The taxonomy, with the prevalence Figure 1 reports for each mode across the 1,642 traces:

| | FM-1.3 Step repetition | 15.7% |
| | FM-1.4 Loss of conversation history | 2.80% |
| | FM-1.5 Unaware of termination conditions | 12.4% |
| FC2 Inter-agent misalignment | FM-2.1 Conversation reset | 2.20% |
| | FM-2.2 Fail to ask for clarification | 6.80% |
| | FM-2.3 Task derailment | 7.40% |
| | FM-2.4 Information withholding | 0.85% |
| | FM-2.5 Ignored other agent's input | 1.90% |
| | FM-2.6 Reasoning-action mismatch | 13.2% |
| FC3 Task verification | FM-3.1 Premature termination | 6.20% |
| | FM-3.2 No or incomplete verification | 8.20% |
| | FM-3.3 Incorrect verification | 9.10% |

The categories map to where a fix lives. FC1 failures happen at run time but trace back to choices made before it: the role prompts, the workflow, the stop condition, what state is kept. FC2 failures are breakdowns in the information flow between agents during the run. FC3 failures are quality control on the output: stopping early, checking too little, or checking the wrong thing.

## The key number: interventions with the model held fixed

The paper's claim is that multi-agent failure is not only a function of the model, and that a better design gains with the same model. Table 5 is the evidence. ChatDev on ProgramDev-v0, a set of 32 program-writing tasks, with GPT-4o succeeded on 25.0% of tasks. Refined role specifications, under which only a superior agent may end a conversation and the verifier's role focuses on task edge cases, raised that to 34.4%. Changing the topology from a DAG to a cycle that ends only when the CTO agent confirms every review is satisfied, with an iteration cap, raised it to 40.6%. On AG2's MathChat with GSM-Plus, an improved prompt with a verification section moved GPT-4 from 84.75% to 89.75%, while the new topology reached only 85.50%, a change the authors report as not significant (Wilcoxon p = 0.4). With GPT-4o both changes helped: 84.25% to 89.00% and 88.83%, each at p = 0.03.

Read both halves. The ChatDev change is large relative to its base: 40.6 / 25.0 is 1.62 times the success rate, from design alone. It is also small in tasks: on 32 tasks, 25.0% to 40.6% is 8 to 13 programs, and ChatDev still fails about 59% of them after the best intervention. The authors call these tactical fixes limited and inconsistent, and conjecture that better base models will not close the full taxonomy either.

The Wordle example in the paper shows why FC1 is not only weak instruction following. Asked for a standard Wordle game with a new five-letter word each day, ChatDev produced code with a fixed word list; told explicitly not to use a fixed word bank, it still produced a fixed list, with new errors. The specification was clear; the system's way of passing it between roles lost it.

## What changed in practice

Three habits follow, and each has a direct engineering form.

Classify before you fix. An aggregate success rate hides trade-offs, which is why the paper breaks each intervention down by failure mode in Appendix H.3: a change that lowers one mode can raise another. Run the annotator over a fixed eval set before and after each change and diff the failure profiles, the way you diff a latency histogram rather than a mean. The authors open-sourced the annotator pipeline and the traces.

Treat verification as more than a final unit test. FC3 is 23.5% of failures, and the paper's third insight is that relying only on final-stage, low-level checks is inadequate: a verifier that confirms the code compiles does not confirm it does what the task asked. Check the objective as well as the artefact.

Count latent defects, not just failed runs. Table 7 compares successful and failed runs for ChatDev and MetaGPT. FM-1.5 (unaware of termination) and FM-2.4 (information withholding) appear almost only in failed runs. Verification failures appear in successful runs too: incorrect verification in 20.0% of ChatDev's successful runs and 25.0% of its failed ones. A passing run with a broken verifier is a failure waiting for a harder input.

## When this is wrong

The prevalence figures describe research frameworks on programming, maths and general-assistant benchmarks, mostly with 2024 and early 2025 models. A production system with typed hand-offs, schema-validated outputs and a turn budget will have a different profile, and the absolute percentages say nothing about yours. Use the taxonomy, not the distribution.

Most of MAST-Data was labelled by the o1 annotator, whose agreement with experts was a kappa of 0.77 with examples. Mode-level percentages carry that labelling error; category-level comparisons are sturdier than claims about a single mode under 2%.

A trace can carry several modes: Table 8 reports category rates above 1.0 per trace for AG2 with GPT-4o on all three benchmarks it compares. So "44% of failures are design failures" does not mean 44% of failed runs had only a design failure.

Only FC2 strictly needs several agents. Step repetition, missed termination, premature termination and weak verification all occur in single-agent loops, and the taxonomy works as a review checklist there too. The claim to resist is the converse: that adding an agent, typically a reviewer or a manager, fixes FC1 failures. Neither ChatDev intervention added an agent: one changed which agents may end a conversation, the other turned the pipeline into a loop that ends on the CTO's confirmation.
