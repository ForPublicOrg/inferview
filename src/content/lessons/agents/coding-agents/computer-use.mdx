## Three ways to act on the same system

An agent can change a system in three ways. It can call an API or a connector, which is typed, fast and fails with a status code. It can drive a browser and read the page's structure, which works on any website but depends on markup it does not control. Or it can drive a whole desktop from screenshots and input events, which works on anything a person can see and is the slowest and least reliable of the three. The comparison is the one between a service call and an end-to-end UI test: the UI path covers the most and breaks the most, and its cost structure is different enough to change the design.

The products now ship all three paths side by side and let the model pick. OpenAI's ChatGPT agent (July 2025) runs a visual browser, a text-based browser, a terminal and direct API access in one virtual computer, plus connectors such as Gmail and GitHub; its launch post gives the intended routing, with calendar data through an API, long text through the text browser, and the visual browser for sites designed for humans. Anthropic splits the same choice into separate client toolsets: `computer_toolset_20260801` for a desktop and `browser_toolset_20260801` for tasks that stay inside web pages, with its web fetch and web search server tools as the lighter option when the agent only needs to read.

The decision this lesson builds toward is when the screen path is worth paying for. That needs three things: what one step costs, where the failures come from, and what the published benchmarks say about long tasks.

## What one step costs

The computer-use loop is the ordinary tool loop with a screenshot as the main tool result. The model returns one or more `tool_use` blocks (`left_click`, `type`, `key`, `scroll`, `zoom`, `screenshot` and the rest of the 17 members), the executor runs them against a virtual display, and returns a screenshot so the model can see what happened. On the current toolset a response can carry several actions. The executor runs them in order, stops at the first failure, and answers every remaining block with the fixed text `Not executed: an earlier computer action in this turn failed.` so the model knows exactly which actions happened.

Two costs recur on every step. The toolset definition adds about 4,500 input tokens to each request (about 4,590 on Claude Sonnet 5 and 4,520 on the other supported models; turning off `zoom` removes about 410). The screenshot is billed as image input. For Claude Opus 4.7 and later, an image costs ceil(width / 28) x ceil(height / 28) visual tokens, up to 2,576 px on the long edge and 4,784 tokens. At the recommended 1280x720 that is 46 x 26 = 1,196 tokens; at 1024x768 it is 37 x 28 = 1,036. The docs put a typical screenshot at roughly 1,000 to 1,800 input tokens. These patch sizes are Claude's; other model families count image tokens differently, so a figure without its family is not comparable.

The browser toolset changes the mix. Its definition is larger, about 6,600 input tokens with the default 27 of 31 members, but `read_page` returns the accessibility tree as text, with each element tagged by a reference such as `[ref_2]` that the model passes back to click or fill. The docs state that a tree read of a typical page often costs fewer tokens than a screenshot, and they cap a single read at 50,000 characters. References replace coordinate guessing wherever the page exposes a usable tree; on canvas interfaces, embedded video, virtualized lists and cross-origin iframes the model falls back to screenshots and coordinates.

The step cost compounds because every earlier screenshot stays in context until something removes it.

Pruning interacts with caching, which is why the docs do not say to drop old screenshots every turn. Removing an image changes the prefix and invalidates everything cached after it, so the guidance is to prune in batches: keep the last three screenshots and prune every 25 turns, with one `cache_control` breakpoint after the system prompt and tools and up to three more on recent tool results. On Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 the docs go further and say to avoid client-side pruning, because it invalidates later thinking blocks, and to use server-side tool result clearing instead. A harness written for an older model that strips screenshots itself is doing the wrong thing on these models.

## Where the flakiness comes from

The API does not resize for you. The toolset rejects a screenshot or zoom image over the model's limits with a validation error, and once a request holds more than 20 images each side is capped at 2000 px. The executor therefore owns two transforms that are easy to get wrong: shrinking the capture to fit, and mapping the model's coordinates (in screenshot pixels, origin top left) back to display pixels. A macOS Retina display doubles the device pixel ratio, which is the usual source of clicks that land at half or twice the intended position.

```python
import math

PATCH, LONG_EDGE_MAX, TOKEN_MAX = 28, 2576, 4784   # Claude, Opus 4.7 and later


def image_tokens(w, h):
    return math.ceil(w / PATCH) * math.ceil(h / PATCH)


def fit(w, h):
    """Largest scale <= 1 that keeps a capture inside both image limits (the API rejects, never downscales)."""
    s = min(1.0, LONG_EDGE_MAX / max(w, h))
    while image_tokens(int(w * s), int(h * s)) > TOKEN_MAX:
        s *= 0.99
    return s


def to_display(x, y, s):
    """The model clicks in screenshot pixels; the executor clicks in display pixels."""
    return round(x / s), round(y / s)


def run_batch(blocks, execute):
    """Run a turn's tool_use blocks in order; after the first failure, answer the rest with the halt text."""
    out, failed = [], False
    for b in blocks:
        if failed:
            ok, content = False, "Not executed: an earlier computer action in this turn failed."
        else:
            ok, content = execute(b)
            failed = not ok
        out.append({"type": "tool_result", "tool_use_id": b["id"], "toolset_name": "computer",
                    "is_error": not ok, "content": content})
    return out


print(image_tokens(1280, 720), image_tokens(1024, 768))   # 1196 1036
s = fit(2880, 1800)                                       # a 2x Retina capture of a 1440x900 screen
print(round(s, 3), int(2880 * s), int(1800 * s))          # 0.834 2401 1500 (86 x 54 = 4,644 tokens)
print(to_display(640, 400, s))                            # (768, 480) in capture pixels
```

The Retina capture fits only after it is scaled to 0.834: at the long-edge limit alone (2576 x 1610) it would be 92 x 58 = 5,336 tokens, over the cap. Sending it at that size is not a degraded request; it is a rejected one. The capture is still in device pixels, so the executor divides by the device pixel ratio as well before it moves the pointer.

Past the plumbing, the documented limitations are the ones a UI test suite has. The model can produce wrong coordinates, and the docs' own executor example rejects clicks outside the display bounds before running them. Scrolling does not always take effect, and keyboard alternatives such as Page Down work better; dropdowns and scrollbars are hard to drive with the mouse; spreadsheet cell selection needs `left_mouse_down` and `left_mouse_up` with modifiers. Resolution is a trade: the docs recommend 1024x768 or 1280x720 for desktop tasks and 1280x800 or 1366x768 for web apps, and say to avoid anything above 1920x1080, because a larger screen costs more tokens or is downscaled until small targets are hard to hit, which is what `zoom` is for. Latency is the last documented limit: the docs say computer use may be too slow for interactive use and point it at background work and automated testing.

## What the benchmarks say about long tasks

OSWorld is the standard desktop benchmark. The 2024 paper reported 369 tasks on real operating systems, humans completing over 72.36% and the best model 12.24%, with failures attributed mainly to GUI grounding and operational knowledge. The maintainers re-released the fixed task set as OSWorld-Verified on 2025-07-28, and the 2024 scores should not be read as current.

OSWorld 2.0 (announced on the project site on 2026-06-26) changes what the benchmark measures. Its 108 tasks are workflows that take a person a median of about 1.6 hours and average 318 tool calls for Claude Opus 4.7 at maximum thinking, against about 30 in the original set. Under binary completion at a 500-step limit, the maintainers report Claude Opus 4.8 at 20.6% (54.8% partial credit, 244K output tokens), Opus 4.7 at 18.2% at 150K tokens, and GPT-5.5 near 14% at about 39K. Their diagnosis is the useful part: the agents no longer mostly fail at clicking or coding; they lose track of constraints, miss information that arrives mid-task, guess instead of asking the user, and skip verification.

The step count explains why. If 318 actions each had to succeed independently, reaching a 50% task success rate would need a per-action success rate of 0.5<sup>1/318</sup> = 0.99782, roughly one error in 460 actions. Real agents notice and repair many errors, so the independence assumption overstates the problem; the direction still holds. A screen agent's reliability is a property of how many steps the task needs, and every step an API call can replace is a step that cannot go wrong.

## When to pay for the screen

The order of preference follows from the costs and failure modes above.

Use an API or connector when one covers the action at the scope you need. It is typed, it returns errors the model can act on, and it removes about a thousand screenshot tokens per step. OpenAI's agent guide describes computer use as the route for legacy systems without APIs, which is the right default framing.

Use a browser agent with element references when the system is a web application without a suitable API, or when the pages build their content with JavaScript. Read the tree, act by reference, and take a screenshot to verify the result or when the tree is missing.

Use full computer use when the task crosses desktop applications, when the application has no usable accessibility tree, or when the interface is itself the thing under test. In the last case the cost is the point: an agent that drives the real UI catches failures that an API-level test cannot.

Mixed designs usually win. An agent can read through the API and write through the UI, then confirm each write by reading it back through the API, which turns the API into the oracle for a flaky actuator. Whatever path writes, put it behind an adapter that a later API can replace, because the screen path is usually a bridge rather than the end state.

Security is the other half of the decision. A screen or browser agent reads attacker-controlled pixels and markup with whatever sessions the environment holds; the docs recommend a dedicated VM or container with minimal privileges, no credentials given to the model, a domain allowlist, and a human confirmation for consequential actions, and Anthropic runs prompt-injection classifiers over screenshots and browser returns. [Autonomy controls](/learn/agents/coding-agents/autonomy-controls) sets those limits, and [prompt injection against acting agents](/learn/agents/coding-agents/acting-agent-injection) sizes the residual risk.

## When this is wrong

The token arithmetic is Claude's, with its 28-pixel patches, limits and toolset sizes as documented on 2026-10-28; another model family prices images and tool definitions differently, and both change with toolset versions. The browser toolset's statement that a tree read often costs less than a screenshot is a documented tendency, not a figure, and a page with a very large accessibility tree can reverse it.

Reading the DOM is not strictly safer than reading pixels. A tree or page-text read includes elements a person never sees, and OpenAI names invisible elements and metadata as places where injected instructions hide; a screenshot shows only what is rendered. Choosing the text path for cost widens what the model reads.

The benchmark figures are maintainers' runs under fixed step limits and effort settings, not your workload. OSWorld 2.0 reports the trade between output tokens and completion, and a team that cannot afford the token budget behind the best score will not see that score. The independent-step calculation bounds intuition; it is not a model of a real agent, which recovers from many of its own errors.
