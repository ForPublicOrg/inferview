## Four dials, set per action class

An agent's autonomy is not one switch. It is four settings that a design document should state separately, the same way a deploy pipeline states its rate limits, approvals and breakers separately.

The first dial is the default: what happens to an action no rule mentions. It can run, ask, or be denied. The second is the budget: per-action caps, rates, and totals, enforced in the tool or the account rather than in the prompt. The third is the confirmation rule: which action classes need which human, and what that human is shown. The fourth is the kill switch: who can stop the run, how fast, and what stopping does to credentials and in-flight actions.

OpenAI's agent-building guide gives the input to all four. It rates each tool low, medium or high from four properties (read-only or write, reversible or not, the account permissions it needs, and its financial impact), and names two triggers for handing control to a person: exceeding a failure threshold, such as repeated attempts that do not progress, and high-risk actions, with cancelling orders, authorising large refunds and making payments as its examples. The ratings decide where each tool sits on the dials; the rest of this lesson is how to set them so they hold.

## How shipped products set the default

Claude Code makes the first dial explicit as permission modes, and the set as documented on 2026-10-28 is a useful reference. `default` (shown as Manual) runs reads and asks for edits, shell commands and network access. `acceptEdits` adds file edits and common filesystem commands inside the working directory. `plan` reads and proposes without editing. `auto` runs everything through a classifier that blocks what escalates beyond the request. `dontAsk` runs only what rules allow and denies anything that would have prompted, which suits CI where no one is there to answer. `bypassPermissions` runs everything and is documented for isolated containers or VMs without internet access only. Two properties make the modes composable with rules: deny rules block in every mode including bypass, and a short list of actions (explicit ask rules, critical-path removals, some interactive tools) is never auto-approved by any mode.

The default itself moved. From Claude Code v2.1.283, auto mode is the built-in starting mode for interactive terminal and VS Code sessions on every plan and provider; before that, the built-in default was Manual except on some plans. A team that wrote its threat model against "the agent asks before running commands" is now describing a configuration it has to set on purpose.

ChatGPT agent sets the third dial in three tiers. It asks for permission before actions with real-world consequences such as a purchase; it requires active supervision (Watch Mode) for critical tasks such as sending email; and it refuses high-risk tasks such as bank transfers. Its takeover mode is a fourth control on a different axis: when a login is needed, the user types into the browser directly and OpenAI says the agent does not collect those inputs, so the model never holds the credential. A refusal tier is the part most in-house designs leave out. Some actions should not be available to the agent at any approval level, because the approval is exactly what an attacker or a confused model will ask for.

## Why approvals decay

Anthropic's auto-mode post gives the number behind approval fatigue: users accepted 93% of Claude Code's manual permission prompts. A prompt that is answered yes 93 times in 100 trains the person answering it to say yes, and the dangerous request arrives in the same queue and the same format as the routine ones. An approval rate that high is a sign the prompt is asking about the wrong things.

The repair has three parts. Move actions that are safe given the environment (reads, edits inside a sandboxed workspace, purchases under a hard cap) out of the prompt and into allow. Move actions that should never happen into deny or refuse, so no approval can unlock them. What remains is rare, so the prompt is read. Then make the prompt specific. Claude Code's docs apply the same rule to approvals given in conversation: an approval has to name the action and the specific thing that makes it dangerous, such as the branch of a force push, and naming the verb alone clears nothing. A confirmation that reads "Approve purchase?" asks the human to check nothing; one that shows the amount, payee, refundability and the idempotency key asks for a check that can fail.

Auto mode replaces most prompts with a classifier, and its published error rates show what that trade buys. On 10,000 real internal actions the two-stage pipeline wrongly blocked 0.4%; on 52 real overeager actions it let 17% through; on 1,000 synthetic exfiltration attempts it let 5.7% through. The fast first stage alone blocked 8.5% of benign actions and missed 6.6% and 1.8% respectively, so the second stage trades misses for fewer false blocks. Anthropic's own reading of the misses is the lesson for any approver, human or model: in most of them the classifier saw the danger and wrongly judged that the user's earlier approval in the session covered the action's full blast radius. The breaker is part of the design: three consecutive or 20 total denials stop the model and hand control back to the human. These are Anthropic's measurements on its own traffic, with a small overeager sample; the [auto mode teardown](/learn/harness/permissions-sandboxing/claude-code-auto-mode) and [classifiers as approvers](/learn/harness/permissions-sandboxing/classifier-approvers) cover the pipeline.

## Budgets hold when approval fails

An approval can be wrong, fatigued, or socially engineered; a cap enforced by the payment tool is none of those. The useful way to set budgets is to compute the worst case they allow before anyone notices, because that number, not the cap on any one action, is the blast radius.

With no daily cap, what is the most it can spend before the human acts?" answer={6000} tolerance={0} unit="currency units">
<p><b>6,000.</b> 300 per purchase x 5 per hour x 4 hours. The per-purchase cap felt small; the rate and the detection latency multiplied it by 20. A daily cap of 1,000 bounds the same window at 1,000, and halving the response time to 2 hours without a daily cap still allows 3,000. The term that dominates is detection latency times rate, which is why the daily cap and the kill switch belong to the same design as the per-action cap.</p>
</Predict>

Three properties make a budget real. It is enforced outside the model, in the tool implementation, the payment account or the API gateway, so a prompt cannot raise it. It is keyed on the principal the agent acts for (per user, per day), not per run, so restarting the run does not reset it. And it fails closed: when the spend service is unreachable, the purchase is refused, not allowed.

Retries are where budgets leak. OpenAI's Agents SDK documentation states that approval does not guarantee a tool runs exactly once: if the process stops after the external action but before the run state is saved, resuming from the older snapshot can repeat it. Its recommendation is a stable idempotency key per logical action reused across retries, and, where the destination cannot deduplicate, reconciling with the destination before retrying and recording the outcome as unknown rather than replaying it. A cap that counts attempts instead of settled charges double-counts; one that counts only confirmed charges can be exceeded by in-flight ones, so the budget check reserves the amount before the call and releases it on a definite failure.

## The kill switch is three actions

Stopping the loop is the easy part. A kill switch that only stops the loop leaves the agent's sessions logged in, its API tokens valid and its queued actions pending. The switch needs to stop new model calls, revoke or suspend the credentials the agent holds (the session cookies, connector tokens and payment instrument), and cancel or quarantine actions that were approved but not executed. ChatGPT agent exposes the user-facing half: pause, take over the browser, or stop and receive partial results, plus a single setting that deletes browsing data and logs out of all sites. The operator-facing half, a global switch per tool or per payment instrument, is the one that matters during an incident.

Durable runs make the pause cheap. In the Agents SDK, a pending approval pauses the run as an interruption and the `RunState` serializes, so a run can wait hours for a human and resume in another process. That is what lets the confirmation tier exist at all without holding a process open; it also means a killed run's state has to be marked as killed, or a later resume will continue it.

## Setting the dials for an agent that spends money

Scenario: a travel agent books trips for employees under a written travel policy. Each action class gets a setting and a reason.

| Action class | Setting | Reason |
|---|---|---|
| Search fares, read the itinerary, read the policy | allow | read-only, no spend |
| Hold a reservation with free cancellation | allow, logged | reversible at no cost |
| Purchase within policy, refundable | allow under caps | reversible; the cap bounds the error |
| Purchase within policy, non-refundable | confirm by the traveller | irreversible; the traveller can check dates and names |
| Purchase above policy | confirm by the traveller's manager | the policy owner, not the requester, approves exceptions |
| Add a payee, change the payment method, transfer money | refuse | no approval should unlock these for this agent |

The budgets sit in the booking tool: a per-purchase cap at the policy limit, a per-traveller daily cap, and a rate limit. The kill switch suspends the corporate card token and the airline sessions. Metrics decide when to move a row: approval rate and time-to-decision per class (a class that is never rejected and approved in seconds is a candidate to become an allow under a cap), rejected confirmations and what they would have bought, cap hits, and breaker trips.

```python
from dataclasses import dataclass, field


@dataclass
class Dials:
    per_action_cap: float          # enforced by the payment tool, not the prompt
    daily_cap: float
    max_per_hour: int
    confirm_above: float
    refuse: frozenset = field(default=frozenset({"bank_transfer", "add_payee", "change_payment_method"}))


def decide(action, amount, spent_today, actions_last_hour, dials, killed=False):
    if killed:
        return "stop"
    if action in dials.refuse or amount > dials.per_action_cap or spent_today + amount > dials.daily_cap:
        return "refuse"
    if actions_last_hour >= dials.max_per_hour:
        return "wait"
    return "confirm" if amount > dials.confirm_above else "allow"


def confirmation(action, amount, payee, refundable, key):
    """What the human sees: the specifics that make the action dangerous, not the verb."""
    return (f"{action}: {amount:.2f} EUR to {payee}, {'refundable' if refundable else 'not refundable'}; "
            f"idempotency key {key}. Approve this payment only.")


d = Dials(per_action_cap=300, daily_cap=1000, max_per_hour=5, confirm_above=150)
print(decide("book_hotel", 120, 0, 0, d))        # allow
print(decide("book_flight", 240, 120, 1, d))     # confirm
print(decide("book_flight", 280, 800, 2, d))     # refuse: daily cap
print(decide("add_payee", 0, 0, 0, d))           # refuse
print(confirmation("book_flight", 240, "Example Air", False, "run-81/step-14"))
```

The order of the checks is the design: the kill switch first, then refusals and caps that no approval overrides, then the rate limit, and only then the question of whether a person is asked. A confirmation that sits above the caps in that order is a confirmation an attacker can talk past.

## When this is wrong

The 93% is Anthropic's measurement of Claude Code users approving coding actions, not a constant. A high approval rate is also what a well-behaved agent produces; the signal of rubber-stamping is the combination of a high rate with a short time-to-decision and approvals of actions that should have been rejected. Teams that need to know can seed occasional known-bad requests into the approval queue and measure how many are caught, with the obvious cost to trust if it is done badly.

Caps bound money; they do not bound sending an email, posting a message, or sharing a document, where one action is the whole harm. For those classes there is no per-action cap, and the controls are refusal, confirmation with the recipient and content shown, or recipient allowlists.

The classifier error rates come from small or synthetic sets (52 real overeager actions, 1,000 synthetic exfiltration attempts) on one vendor's traffic and models. They show the shape of the trade between false blocks and misses; they do not transfer to an approver built for a different action set. Product details in this lesson (mode names, the v2.1.283 default, ChatGPT agent's tiers as launched in July 2025, a launch post now marked outdated) change faster than the dials do.
