## Three causes, three signatures

An agent loop ends in exactly one way: a model response with no tool calls. The OpenAI Agents SDK treats output as final when it is text of the desired type with no tool calls, the Claude Agent SDK ends the loop on the first response without tool calls, and the Codex post calls that assistant message the termination state. A looping agent is one that never produces that response before a budget stops it, and there are three common reasons, each with its own shape in the trace.

The first is a tool error that looks like progress. The tool returns success with nothing in it (an empty result set, a `pending` status, a 200 with a default object) when the real condition is an error the model cannot see: a bad filter, a wrong time zone, a permission that silently scopes the query to nothing. The model reasonably concludes its query was wrong and tries another. The signature is one tool called with new arguments each time and the same result each time. A repeat detector keyed on exact arguments never fires, and the step budget is the only thing that ends the run. ReAct's error analysis saw the same dynamic with search: non-informative results were 23% of its sampled HotpotQA failures, and the paper notes they derail the reasoning that follows.

The second is a turn with no way to end. The model has the answer but the loop will not accept a response without a tool call. Forcing `tool_choice` to a required tool does this, which is why the OpenAI SDK resets it to `auto` after a tool call by default; its docs describe the alternative as tool results going back to a model that calls a tool again "ad infinitum". A final-output schema the model keeps failing, or a system prompt that demands a tool on every turn, has the same effect. The signature is an answer visible in the assistant text while the calls continue, often a write tool repeated with identical arguments.

The third is lost context. A client that trims history to a token window, or a compaction that summarises away a result, removes facts the task still needs, and the model fetches them again. The signature is successful calls repeated with identical arguments and identical results, usually after a large result or a compaction event. The Claude Agent SDK emits a `compact_boundary` message when it compacts, and its docs warn that specific instructions from early in the conversation may not survive the summary.

A fourth shape, the same call returning the same error, belongs to the tool error contract from [the first lesson of this module](/learn/agents/agent-loop/loop-economics): an opaque or misclassified error that the model reads as retryable. Anthropic's tool docs say Claude retries an invalid call 2 to 3 times with corrections, so a tool that rejects valid input produces this shape on every request.

## Reading a recorded trace

The trace below is synthetic: an alert-triage agent that ran to its step cap of 20. The first option is the trace as recorded; the other three inject one fault each into a replay. Step through the recorded trace, read the gauges, then switch faults and find the one that reproduces it.

<p class="tiny">Token counts per step are approximate. The $4 per million input tokens is the Claude Opus 5.5 list price checked 2026-10-28; the widget applies it to input tokens only.</p>

The identical-calls gauge stays at 1 on the recorded trace while every result is empty, which rules out lost context (it repeats successful calls exactly) and a missing termination path (the agent never has an answer to repeat). The time-zone fault reproduces it: `search_logs` reads `since="14:00"` as UTC-7, so every query covers a window seven hours after the alert and returns zero matches as a success. Raising the step cap would only make each run longer. The fix is in the tool: echo the window it actually searched with every result, and return `is_error: true` with an instructive message when the window starts in the future. With that, the model gets one error it can act on instead of six empty successes.

The other two faults are worth stepping through for their own signatures. With `tool_choice` forced, the summary is posted at call 3, the turn cannot end, and `post_summary` repeats with identical arguments, so the gauge climbs to 3; on a real incident channel that is three identical summaries posted. With the trimmed history, `get_deploys` and `search_logs` alternate with identical arguments and identical results, because each 240-token log result pushes the deploy list out of a 300-token window.

## A procedure for the first ten minutes

Start from the stop reason. `error_max_turns` in the Claude Agent SDK, `MaxTurnsExceeded` in the OpenAI SDK, or your own loop's budget status tells you the run hit a cap rather than crashed; `error_during_execution` is a different investigation. Then tabulate the calls: per tool, the number of calls, distinct argument sets and distinct results. Look for boundary events (compaction, truncation, a tool-list change) and note which calls follow them. Find the first call at which the model had what it needed to answer, if any. Finally, form a hypothesis and replay the run with the suspected fault injected; a hypothesis that reproduces the signature is worth fixing, one that does not is a guess.

The tabulation is mechanical enough to run on every capped trace before a human looks at it.

```python
import hashlib
import json

WRITES = {"post_summary"}          # tools with side effects; a repeat is never progress

def digest(x):
    return hashlib.sha256(json.dumps(x, sort_keys=True).encode()).hexdigest()[:12]

def signatures(calls, streak_limit=3):
    """calls: [(tool, args, result, is_error)]. Returns the first call index of each loop signature."""
    found, seen = {}, {}
    streak, prev = 0, None
    for i, (tool, args, result, is_error) in enumerate(calls):
        key = (tool, digest(args))
        if key in seen:
            if tool in WRITES:
                found.setdefault("repeated write: no termination signal", i)
            elif is_error:
                found.setdefault("repeated error: error contract", i)
            elif digest(result) == seen[key]:
                found.setdefault("repeated success: context lost", i)
        seen[key] = digest(result)
        same = prev is not None and prev[0] == tool and prev[1] != key[1] and prev[2] == digest(result)
        streak = streak + 1 if same else 1
        if streak >= streak_limit:
            found.setdefault("same result, new arguments: tool hides an error", i)
        prev = (tool, key[1], digest(result))
    return found

empty = {"results": [], "count": 0}
recorded = [("get_deploys", {"service": "payments"}, [{"id": "d-311"}], False)] + [
    ("search_logs", {"query": q, "since": "14:00"}, empty, False)
    for q in ["timeout", "error", "slow OR latency", "payments", "payments-api", "ledger"]]
required = [("get_deploys", {"service": "payments"}, [{"id": "d-311"}], False),
            ("search_logs", {"query": "timeout", "since": "14:00"}, {"count": 212}, False)] + [
            ("post_summary", {"text": "Likely cause: d-311"}, {"ok": True}, False)] * 3
window = [("get_deploys", {"service": "payments"}, [{"id": "d-311"}], False),
          ("search_logs", {"query": "timeout", "since": "14:00"}, {"count": 212}, False)] * 3

for name, trace in [("recorded", recorded), ("required", required), ("window", window)]:
    print(name, signatures(trace))
# recorded {'same result, new arguments: tool hides an error': 3}
# required {'repeated write: no termination signal': 3}
# window {'repeated success: context lost': 2}
```

Each signature points at a layer, and the layer is where the fix goes.

Only the last row is fixed by changing the budget. The step cap is the backstop that keeps the first four cheap, and the reason to fix them anyway is cost per run: at the 8,000-token prefix and 3,000 tokens per turn used in this module, a run capped at 20 calls sends 20 × 8,000 + 3,000 × 190 = 730,000 input tokens, $2.92 at $4 per million, against 4 × 8,000 + 3,000 × 6 = 50,000 tokens ($0.20) for a four-call run that succeeds. Each looping run costs as much as 14.6 good ones and returns nothing.

## When this is wrong

The signatures assume one cause per run. Real loops combine them: a compaction drops the instruction to post once, and a write tool that reports success without an id then gets called again. The classifier reports the first signature it sees, and the replay with fault injection is what separates a cause from a symptom.

Exact hashes of arguments and results are brittle. Tools that put timestamps or request ids in their results make identical results look different, and models that reorder keys or rephrase queries make identical intent look new. Normalise results before hashing (drop volatile fields) and expect to tune the streak threshold per tool.

Synthetic replays prove that a fault can produce a signature, not that it did. A replay against today's tool may not match the tool's behaviour on the night of the incident, so keep the tool's version and configuration in the trace, and treat a reproduced signature as strong evidence rather than proof.

And some long runs are not loops. A research agent that fans out over many sources produces varied, productive calls until its budget, and the fix there is the budget or the task split, not any of the tool or context changes above.
