## Plans and reflections are model output

A plan, a critique of the last step and a claim that the task is done are all sampled tokens. They have the same failure modes as a tool call with wrong arguments, and nothing about writing them in the imperative mood makes them more reliable. The engineering question for any reasoning step inside a loop is the one you would ask of an unvalidated input: what checks it, and what new information does that check bring in?

The Claude Agent SDK post describes the loop as gather context, take action, verify work, repeat. The third stage is the one that decides whether a loop converges. A loop that verifies with something outside the model (a test run, a schema validator, a read of the database row it just wrote) stops for a reason you can audit. A loop that verifies by asking the model whether it is done stops when the model's estimate of done crosses a threshold, and that estimate is produced by the same process that made the error.

## Three places to put the reasoning

ReAct interleaves a thought, an action and an observation on every step. The paper reports absolute success gains of 34 and 10 points on ALFWorld and WebShop over imitation and reinforcement-learning methods, prompted with one or two examples. Its error analysis is the more useful part for production. On 200 human-labelled HotpotQA trajectories with PaLM-540B, hallucination was 56% of chain-of-thought failures and 0% of ReAct failures, because every fact came from a search observation. ReAct paid for that grounding elsewhere: reasoning errors were 47% of its failures against 16% for chain of thought, including runs stuck repeating the previous step, and uninformative search results were another 23%. Grounding moved the failures from invented facts to bad observations and loops, and the headline score barely moved: 27.4 exact match against 29.4 on HotpotQA, 60.9 against 56.3 accuracy on FEVER. Native tool calling has replaced ReAct's text parsing, but the trade it measured is still the trade.

Plan-then-execute asks for the whole plan first and runs it step by step, re-planning when an observation contradicts it. Like a query planner's output, the plan is an artefact you can inspect before anything runs; unlike one, it has no cost model behind it, so what you can check is its shape rather than its quality. Every step names a tool that exists, no irreversible step runs without an approval checkpoint, and the step count fits the budget. Anthropic's agent guidance calls for exactly these: checkpoints for human feedback and stopping conditions such as a maximum number of iterations. The Claude Agent SDK ships the first half as a mode: with `permission_mode="plan"` the agent explores and plans without editing source files, and a human or a policy check approves the plan before a second run executes it.

Evaluator-optimizer puts a second prompt after the output to critique it, and loops until the critique passes. Anthropic recommends it when there are clear evaluation criteria and iterative refinement provides measurable value. Both conditions matter: without explicit criteria the critic grades the same way the generator wrote, and without measurement you cannot tell refinement from churn.

## Reflection without new information

The cleanest evidence on reflection comes from separating the critique from the signal it uses. Huang et al. ran intrinsic self-correction, where the model reviews its own answer with no external feedback. GPT-3.5 on CommonSenseQA fell from 75.8 with one call to 38.1 after one round of self-correction at three calls, and recovered only to 41.8 after a second round at five calls. GPT-4 on GSM8K fell from 95.5 to 91.5 to 89.0. When the paper instead used the ground-truth label to decide when to stop, the same procedure appeared to help: 89.7 on CommonSenseQA and 97.5 on GSM8K. The improvement came from the label, which kept the model from changing a right answer, and a production loop does not have the label.

Reflexion shows the other side. Its agent reached 91% pass@1 on HumanEval Python against 80% for GPT-4, by reflecting on the results of unit tests it wrote and executed. The executed tests are the new information. The same method scored 77% on MBPP Python against an 80% baseline, and the paper attributes the drop to its own tests: they passed on wrong solutions 16.3% of the time on MBPP against 1.4% on HumanEval. A checker that passes wrong answers ends the loop early with a confident error, and a reflection step costs at least one more model call with the full context each time it runs.

Three cases where reflection only adds cost follow from this. No new information enters between the attempt and the critique. The base success rate is already high, so a critic that changes answers has more right answers to break than wrong ones to fix, as in the GPT-4 GSM8K row. And the critic shares the generator's blind spots, which is the default when both are the same model with the same context. The Agent SDK post is blunt about the model-as-judge version: it is "generally not a very robust method" and has latency costs.

## One deterministic check, placed where it pays

The post's ordering of feedback is the practical one: clearly defined rules first, with a message saying which rule failed and why; then visual checks such as a screenshot of rendered output; then a model as judge. Rules include linters, type checkers (it suggests generating TypeScript over JavaScript for the extra layer of feedback), schema validation and reading back the state the agent just changed. A check is worth its place when it runs after a step whose errors are otherwise silent and before the step that makes them irreversible.

The value of a check compounds over steps, which a toy model makes concrete. Each number below is a scenario input, not a measurement.

<p>A step stays wrong if the error slips past the check, 0.05 × 0.2 = 0.010, or if it is caught and the retry also goes wrong, 0.05 × 0.8 × 0.05 = 0.002. That is 0.012 per step, and 0.988<sup>10</sup> = <b>88.6%</b> of runs come out clean. Without the check it is 0.95<sup>10</sup> = 59.9%. Recall drives the result. At 50% recall the per-step residual is 0.05 × 0.5 + 0.05 × 0.5 × 0.05 = 0.02625 and the clean-run share falls to 0.97375<sup>10</sup> = 76.6%. Precision drives the cost: a check that fires on correct steps adds retries and, if the retry policy is "until it passes", turns into one of the loops the next lesson debugs.

## Measuring what the check catches

The toy model assumed recall and error rate. In production you measure them, and the measurement is cheap if you plan for it. Recall comes from fault injection: feed the check outputs you have broken on purpose (a mutated value, a dropped field, a test edited to fail) and count how many it flags. Precision comes from labelling a sample of the steps it flagged. The error rate per step comes from labelling a sample of steps that passed. Log every check verdict with the step id so the three numbers come from the same traces.

The simulation below reproduces the toy numbers and is the harness to plug measured values into.

```python
import random

def run_plan(rng, steps=10, err=0.05, recall=0.8, check=True):
    """One run of a plan. Returns (succeeded, model_calls, check_runs, caught)."""
    calls = checks = caught = 0
    ok = True
    for _ in range(steps):
        calls += 1
        bad = rng.random() < err
        if check:
            checks += 1
            if bad and rng.random() < recall:   # the check fires: retry the step once
                caught += 1
                calls += 1
                bad = rng.random() < err        # the retry is not re-checked
        ok = ok and not bad
    return ok, calls, checks, caught

rng = random.Random(2026)
for check in (False, True):
    runs = [run_plan(rng, check=check) for _ in range(100_000)]
    n = len(runs)
    print(f"check={check!s:5} success={sum(r[0] for r in runs) / n:.3f} "
          f"calls/run={sum(r[1] for r in runs) / n:.2f} caught/run={sum(r[3] for r in runs) / n:.3f}")
# check=False success=0.601 calls/run=10.00 caught/run=0.000
# check=True  success=0.887 calls/run=10.40 caught/run=0.404
```

The cost side belongs in the same table. Each extra model call re-sends the run's context, so 0.4 extra calls late in a long run cost more than 0.4 calls early in it, and a check that takes minutes (a full test suite) can outlast a five-minute prompt cache and make the next call a miss. [The loop's cost](/learn/agents/agent-loop/loop-economics) prices both. A check that is slow but precise usually belongs at a few points (before a commit, before a send), and a fast one after every step.

## When this is wrong

The toy model treats step errors as independent. In practice they cluster: a misread requirement corrupts every step that depends on it, and a per-step check can pass each step while the plan is wrong as a whole. Plan-level checks (an approval, a dry run against a staging copy) catch what step checks cannot.

The self-correction results are for reasoning tasks without tools, measured on 2023 models. Later models and reasoning modes may reflect better, and a critique that is allowed to call a tool or run code is no longer intrinsic. What carries over is the test: measure the critic against labelled outcomes before trusting it, and keep the ground truth out of its stopping rule when you measure.

Deterministic checks are only as good as the rules behind them. A test suite with gaps is a checker with low recall, and the Reflexion MBPP result shows that a checker with poor precision can make the loop worse than no loop at all. The model-as-judge has a place where no rule exists, such as tone or layout, and there the measurement of its agreement with human labels is the check on the check.
