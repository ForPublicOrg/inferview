## What the revision changed

Revisions up to and including 2025-11-25 open a session: an `initialize` request and an `initialized` notification negotiate version and capabilities once, and over HTTP the server can assign an `Mcp-Session-Id` that every later request then carries. When a tool needed something from the user, the server sent its own request (an elicitation, a sampling call, a roots query) down an open stream and waited, holding the half-finished call in memory. That design behaves like a connection-oriented protocol with server-side session state: the load balancer pins each session to the instance that created it, and a deploy or crash on that instance loses the sessions on it.

The 2026-07-28 revision, the current one as of this lesson's date, removes all of that. The changelog lists the handshake and protocol sessions as removed (SEP-2575, SEP-2567); every request carries its protocol version and client capabilities in `_meta`; server-to-client requests are replaced by multi round-trip requests (SEP-2322); every result carries a required `resultType`; `ping` and `logging/setLevel` are removed, with log level set per request; SSE stream resumption is removed; experimental tasks move into an official extension (SEP-2663); and a new `server/discover` RPC is mandatory for servers. The specification's own summary of the base protocol now reads as stateless, self-contained requests with per-request capability negotiation.

The rest of this lesson follows one request through the new wire format, then covers what a server with session state has to change and how long it has to keep speaking the old protocol.

## The request carries its own context

Each request's `_meta` holds `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`; clients SHOULD add `clientInfo`, and servers SHOULD return `serverInfo` in each result's `_meta`. On Streamable HTTP, every message is its own POST to one endpoint, and the transport mirrors three body fields into headers so a gateway can route without parsing JSON: `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` (the tool name, prompt name or resource URI). A server that processes the body MUST reject a request whose headers and body disagree with HTTP 400 and JSON-RPC error `-32020` (`HeaderMismatch`). The reason given is the split-brain case: a load balancer routing or rate-limiting on the header while the server executes the body.

Servers can also mark a tool parameter with `x-mcp-header`, and conforming clients then send its value as `Mcp-Param-{Name}`, for example a region to route on. The spec says servers SHOULD NOT mark sensitive parameters this way, because intermediaries see headers. It also tells intermediaries that enforce policy on mirrored headers to reject requests whose version predates header validation, since an older client's headers were never checked against its body.

Version negotiation is per request. A server that does not support the requested version answers 400 with `UnsupportedProtocolVersionError` (code `-32022`) listing the versions it does support, and the client retries with one of them. `server/discover` returns the supported versions, capabilities and identity in one call; clients may skip it and handle the error inline.

## Multi round-trip requests

A server that needs input in the middle of `tools/call`, `prompts/get` or `resources/read` (the only three methods allowed to do this) returns a result with `resultType: "input_required"`, an `inputRequests` map of elicitation, sampling or roots requests keyed by server-chosen ids, and optionally a `requestState` string. The client gathers the answers and sends the original request again with a different JSON-RPC id, an `inputResponses` map with the same keys, and the `requestState` echoed byte for byte. The spec states the purpose directly: handle server-to-client requests without shared storage across instances or stateful load balancing. Any instance can take the retry, because the retry carries everything.

The state therefore travels through the client, and the spec treats it as attacker-controlled. If `requestState` influences authorisation, resource access or business logic, the server MUST protect its integrity (HMAC or AEAD) and reject state that fails verification, and SHOULD bind inside the protected payload the authenticated principal, a short expiry, and an identifier of the originating request such as the method and a digest of its parameters. Those bindings stop cross-user and cross-request reuse within the expiry; they do not make the state single-use, and the spec says a server that needs at-most-once consumption MUST enforce it server-side.

Two design consequences follow for tool authors. The server MUST NOT assume the client will retry, so a tool that performs a side effect and then asks a question leaves the side effect done and the call abandoned; ask for input before acting. And a server may answer the retry with another `input_required` if answers are missing, so the interaction is a loop the client bounds, not a single exchange.

## Streams, cancellation and retries

The server answers each POST with a JSON object or with an SSE stream scoped to that request, carrying progress and log notifications for it and then the response. The server MUST NOT send independent requests on any stream. Closing the stream is the cancellation signal on HTTP. Resumption with `Last-Event-ID` is gone: a broken response stream loses the in-flight request, and the client MUST re-issue it as a new request with a new id. For a tool with side effects that is an at-least-once delivery path, and the idempotency design from the [previous lesson](/learn/agents/tools-mcp-a2a/tool-design) is what keeps it from acting twice.

Change notifications that used to arrive on a standalone GET stream now arrive on the response stream of a `subscriptions/listen` POST, which stays open and carries only the notification types the client opted into. A modern-only server that receives a legacy GET or DELETE SHOULD answer 405, and SHOULD ignore an `Mcp-Session-Id` header rather than echo or mint one.

## Lists become cacheable

Because there is no connection state, `tools/list` MUST NOT vary per connection or as a side effect of other requests, though it MAY vary by the authorisation on the request, which is per-request input. List and read results now carry `ttlMs`, a freshness hint, and `cacheScope`, `public` or `private`, which says whether shared intermediaries may cache them (SEP-2549). Servers SHOULD return tools in a deterministic order, and the changelog gives the reason as client-side caching and higher prompt cache hit rates: a host that renders tool definitions into the model prefix gets a different prefix every time the order shuffles.

## The deprecation window

The revision also adopts a feature lifecycle policy (SEP-2596): a deprecated feature stays in the specification for at least twelve months, or ninety days under an expedited-removal exception, before it becomes eligible for removal. The registry as of 2026-10-28:

The sampling row is an organisational change as much as a code change. A server that used sampling borrowed the host's model and the host's bill; after migration it needs its own provider credentials, its own spend limits and its own data-handling review.

## Migrating a stateful server

The spec names three kinds of implementation: modern (2026-07-28 and later, per-request metadata), legacy (2025-11-25 and earlier, `initialize` handshake), and dual-era. Its compatibility matrix decides the migration plan. A dual-era server works with both kinds of client: an `initialize` request selects legacy semantics scoped to that session or stdio process, and a request with modern `_meta` is served statelessly, concurrently on the same endpoint. A modern-only server fails every legacy client, and legacy clients have no fall-forward mechanism; the spec asks such a server to name its supported versions in the error it returns to `initialize`, because that error may be the only diagnostic the user sees. Dual-era clients probe: on HTTP they send a modern request and fall back only if a 400 body is not a recognised modern error; on stdio they send `server/discover` first.

The migration work, in order:

1. Inventory what lives in the session today: per-connection tool lists, open transactions, cursors, cached credentials, pending elicitations.
2. Move cross-call state into explicit handles returned by a creating tool and passed as arguments, authorised against the caller on every call, with the lifetime stated in the tool description.
3. Replace server-initiated requests with `input_required` results, putting whatever the server held in memory into a sealed `requestState`; move every side effect after the last question.
4. Implement `server/discover`, the required headers and header validation, `resultType` on every result, deterministic list order and the cache fields.
5. Serve both eras behind the same endpoint, with sticky routing kept only for requests that carry a legacy session id, and measure the legacy share by client.
6. Remove the legacy path when that share reaches a threshold agreed in advance with the people who own the remaining clients.

The core of a dual-era front door and a sealed `requestState`, in standard-library Python:

```python
import base64, hashlib, hmac, json, time

SUPPORTED = ["2026-07-28", "2025-11-25"]        # modern first; legacy kept for the window
KEY = b"rotate-me"                               # from a secret store in a real server


def era(msg, headers):
    """Pick the era from how the client opens, as a dual-era server must."""
    if msg.get("method") == "initialize":
        return "legacy"
    version = msg.get("params", {}).get("_meta", {}).get("io.modelcontextprotocol/protocolVersion")
    if version is None:
        return "legacy" if "Mcp-Session-Id" in headers else "reject"
    if headers.get("MCP-Protocol-Version") != version:
        return "header_mismatch"                # 400 with JSON-RPC error -32020
    return "modern" if version in SUPPORTED else "unsupported"   # 400 with -32022 and the list


def _digest(method, name, args):
    return hashlib.sha256(json.dumps([method, name, args], sort_keys=True).encode()).hexdigest()


def seal(principal, method, name, args, state, ttl_s=300):
    """requestState bound to the caller, the originating request and an expiry."""
    body = json.dumps({"p": principal, "d": _digest(method, name, args),
                       "exp": int(time.time()) + ttl_s, "s": state}).encode()
    return base64.urlsafe_b64encode(hmac.new(KEY, body, hashlib.sha256).digest() + body).decode()


def unseal(token, principal, method, name, args):
    raw = base64.urlsafe_b64decode(token.encode())
    mac, body = raw[:32], raw[32:]
    if not hmac.compare_digest(mac, hmac.new(KEY, body, hashlib.sha256).digest()):
        raise ValueError("tampered")
    c = json.loads(body)
    if c["p"] != principal or c["d"] != _digest(method, name, args) or c["exp"] < time.time():
        raise ValueError("wrong caller, wrong request or expired")
    return c["s"]


tok = seal("user:42", "tools/call", "create_ticket", {"title": "Disk full"}, {"step": "need_project"})
print(unseal(tok, "user:42", "tools/call", "create_ticket", {"title": "Disk full"}))  # {'step': 'need_project'}
```

HMAC gives integrity, not secrecy: anything in the state is readable by the client, so a server that must hide it uses an AEAD cipher instead, which the standard library does not provide. Key rotation needs two keys accepted during the overlap, or every in-flight retry fails at the switch.

## When this is wrong

This lesson is pinned to the 2026-07-28 revision as read on 2026-10-28. The changelog cited here also lists items that were renumbered during drafting (error codes moved into a reserved range), which is a sign that SDKs and servers will disagree with each other and with the text for a while; test against the SDK versions you ship, not the specification alone.

Most deployed servers and clients were written against 2025-11-25 or earlier, and the ecosystem moves at the pace of its slowest clients, so for a server with external users the dual-era period is the normal state, not a transition. The twelve-month window applies to features of the current revision, not to how long legacy revisions are supported; nothing in the spec obliges a server to keep serving 2025-11-25, and nothing obliges a client to stop.

Statelessness moves state, it does not remove it. Handles live in a store the server runs, sealed request state grows with every round trip, and a design that needed a session for a long-running interaction may be better served by the tasks extension or by a durable workflow behind a single tool, which the [workflows track](/learn/workflows) covers.
