## Four places a procedure can live

A team's procedures (how to cut a release, how to triage a page, how to write an API doc in house style) can reach an agent in four ways, and they differ in when they cost context and who decides they run.

A memory file such as `CLAUDE.md` or `AGENTS.md` is loaded into every session in full; Claude Code's best-practices page says every line takes a little attention on every task, relevant or not, and its memory guide recommends staying under 200 lines. A tool is a definition in context on every call (unless deferred) plus code that runs outside the model. A harness rule (a hook, a deny rule, a managed setting) costs no context and runs every time, because the harness rather than the model executes it. A skill sits between them: its name and description are in context every session, its body loads when the agent decides the task needs it, and its bundled files load only when the body points to them. The effect resembles lazy loading with an index kept in memory: the index is always paid for, the pages only on a hit.

The Claude Code docs draw the line between the first and last groups sharply. A prompt, a `CLAUDE.md` line or a skill the model starts itself is non-deterministic: the model usually follows it and is not obliged to. Hooks, deny rules and skills that only a person can start are enforced by the harness. A rule with zero exceptions belongs in the second group whatever its length.

## The SKILL.md format

The Agent Skills specification (Anthropic published it as an open standard on 2025-12-18) defines a skill as a directory containing `SKILL.md`, with optional `scripts/`, `references/` and `assets/`. The file opens with YAML frontmatter:

<div class="tablewrap">
<table>
<thead><tr><th>Field</th><th>Required</th><th>Constraint</th></tr></thead>
<tbody>
<tr><td><code>name</code></td><td>Yes</td><td>1 to 64 characters; lowercase letters, digits and hyphens; no leading, trailing or consecutive hyphens; must match the directory name</td></tr>
<tr><td><code>description</code></td><td>Yes</td><td>1 to 1,024 characters; what the skill does and when to use it, with the keywords tasks will contain</td></tr>
<tr><td><code>license</code></td><td>No</td><td>A licence name or a bundled licence file</td></tr>
<tr><td><code>compatibility</code></td><td>No</td><td>Up to 500 characters of environment requirements</td></tr>
<tr><td><code>metadata</code></td><td>No</td><td>String-to-string map for client-specific properties</td></tr>
<tr><td><code>allowed-tools</code></td><td>No</td><td>Space-separated pre-approved tools; marked experimental, support varies by agent</td></tr>
</tbody>
</table>
</div>

The body has no required format. The spec recommends keeping `SKILL.md` under 500 lines, moving detail into referenced files one level deep, and validating with the `skills-ref` library. Products add their own fields on top: `disable-model-invocation`, `user-invocable` and `context: fork` are Claude Code extensions, not part of the open specification, so a skill that depends on them for safety is not portable to another agent without checking how that agent treats them.

## Progressive disclosure, priced

The specification gives the budget for each level: about 100 tokens of metadata per skill loaded at startup for every installed skill, fewer than 5,000 tokens recommended for the body loaded on activation, and resources loaded only as required. Anthropic's PDF skill shows the third level: form-filling instructions live in a separate `forms.md` that is read only when a form is being filled, and a bundled Python script extracts form fields without the script or the PDF entering context. Scripts are where skills beat prose for repeatable steps, since code runs the same way each time.

Product behaviour adds detail the spec does not cover. In Claude Code, the listing truncates a skill's description and `when_to_use` text at 1,536 characters combined; once invoked, the rendered body enters the conversation as one message and stays there for later turns rather than being re-read; and after compaction the most recent invocation of each skill is re-attached, keeping the first 5,000 tokens of each within a combined budget of 25,000 tokens, filled from the most recently invoked, so older skills can drop out of a long session. Its caching docs say skills are injected as messages at invocation, so loading one leaves the cached prompt prefix intact. Memory files behave differently: project-root and user `CLAUDE.md` are read once at session start, and a mid-session edit neither breaks the cache nor applies until `/clear`, `/compact` or a restart.

## Who may start a skill

A skill whose description matches a task can be started by the model. For a procedure with side effects (cutting a release, rotating a credential, running a database failover), that is the wrong default. Claude Code's controls:

<div class="tablewrap">
<table>
<thead><tr><th>Frontmatter</th><th>Person can start</th><th>Model can start</th><th>Context loading</th></tr></thead>
<tbody>
<tr><td>(default)</td><td>Yes</td><td>Yes</td><td>Description always in context; body on invocation</td></tr>
<tr><td><code>disable-model-invocation: true</code></td><td>Yes</td><td>No</td><td>Description not in context; body on invocation</td></tr>
<tr><td><code>user-invocable: false</code></td><td>No</td><td>Yes</td><td>Description always in context; body on invocation</td></tr>
</tbody>
</table>
</div>

The best-practices page uses a release skill as its example of a workflow that should carry `disable-model-invocation: true`, so it runs only when someone types `/release`. That setting also removes the description from context, which makes user-only skills free in tokens. `allowed-tools` does the opposite of what its name suggests to many readers: it pre-approves the listed tools for the turn that invokes the skill and does not restrict which tools are available, so it widens permissions rather than narrowing them. The permission design itself belongs in the harness, covered in [Permissions and policy in the harness](/learn/harness/permissions-sandboxing).

## Skills, tools or a memory file

<div class="tablewrap">
<table>
<thead><tr><th>The procedure</th><th>Home</th><th>Why</th></tr></thead>
<tbody>
<tr><td>Applies to nearly every task and is short (build command, test command)</td><td>Memory file</td><td>Paid every session either way; no activation to miss</td></tr>
<tr><td>Needed in some sessions, written as steps and judgment</td><td>Skill the model can start</td><td>Index always present, body only when needed</td></tr>
<tr><td>Has side effects someone must choose to trigger</td><td>Skill only a person can start</td><td>Explicit start, no description cost</td></tr>
<tr><td>Must happen every time without exception</td><td>Hook or deny rule</td><td>The harness runs it whatever the model decides</td></tr>
<tr><td>Is an operation on another system with its own credentials</td><td>Tool, often over MCP</td><td>Typed contract, server-side authorisation, usable by other agents</td></tr>
</tbody>
</table>
</div>

Skills and tools combine more than they compete. A skill tells the agent how the team does something and which tools to call in what order; the tools do the work against systems with their own access control. Anthropic's code execution post describes the reverse direction as well: an agent that writes working code against MCP tools can save it as a function in a skills folder and add a `SKILL.md` to reuse it. The MCP specification lists Skills over MCP among its extensions, a sign that distribution of skills through servers is being standardised, though as of this lesson's date it is an extension rather than core protocol.

A check a team can run in CI over its skill directories, using the spec's rules plus one policy the team chooses (here: anything that can push, deploy or apply infrastructure must be user-started):

```python
import re
from pathlib import PurePosixPath

NAME = re.compile(r"^[a-z0-9]+(-[a-z0-9]+)*$")      # lowercase, digits, single hyphens, no edge hyphens


def frontmatter(text):
    """Flat 'key: value' frontmatter only; a real checker uses a YAML parser or skills-ref."""
    if not text.startswith("---\n"):
        raise ValueError("SKILL.md must open with YAML frontmatter")
    head, _, body = text[4:].partition("\n---\n")
    fields = dict(line.split(":", 1) for line in head.splitlines() if ":" in line)
    return {k.strip(): v.strip() for k, v in fields.items()}, body


def check_skill(path, text, side_effect_tools=("Bash(git push", "Bash(kubectl", "Bash(terraform apply")):
    meta, body = frontmatter(text)
    problems = []
    name, desc = meta.get("name", ""), meta.get("description", "")
    if not (1 <= len(name) <= 64 and NAME.match(name)):
        problems.append("name: 1-64 chars of a-z, 0-9 and single hyphens")
    if name != PurePosixPath(path).parent.name:
        problems.append("name must match the skill directory")
    if not 1 <= len(desc) <= 1024:
        problems.append("description: 1-1024 chars, saying what it does and when to use it")
    if len(meta.get("compatibility", "")) > 500:
        problems.append("compatibility: at most 500 chars")
    if len(body.splitlines()) > 500:
        problems.append("body over 500 lines: move detail into references/")
    # Team policy, not the spec: anything that can push, deploy or apply is user-started only.
    tools = meta.get("allowed-tools", "")
    if any(t in tools for t in side_effect_tools) and meta.get("disable-model-invocation") != "true":
        problems.append("side-effecting skill must set disable-model-invocation: true")
    return problems


release = """---
name: release
description: Cut a release. Bumps the version, writes the changelog entry, tags and pushes.
allowed-tools: Bash(git tag *) Bash(git push *)
---
1. Check the tree is clean on main.
"""
print(check_skill(".claude/skills/release/SKILL.md", release))
# ['side-effecting skill must set disable-model-invocation: true']
```

The policy check keys on `allowed-tools`, which is only a proxy: a skill can instruct the agent to run a deploy command without pre-approving it, and the agent will then ask for permission or be blocked by the harness. The real guarantee is the harness's permission rules; the check catches the common mistake of pre-approving a side effect in a skill the model can start. The Anthropic post's security guidance applies to every skill a team did not write: install only from trusted sources, and audit the rest, including bundled code, dependencies and any instruction to reach external networks.

## When this is wrong

The token figures are the specification's estimates and one product's documented behaviour. Other agents implement skills differently: some may load bodies eagerly, ignore `allowed-tools` or have no equivalent of user-only invocation, and the open specification marks `allowed-tools` as experimental. Check the agent you deploy, and do not rely on a product-specific field for a safety property in a skill meant to be portable.

Activation is a model decision made from a description, which makes it a retrieval problem with a recall rate. A procedure that matters and is missed is worse in a skill than in the memory file, where it was at least present; for those, the memory file or a harness rule is the right home despite the cost. And a skill body that stays in the conversation after invocation keeps costing context until compaction, so a long session that touches many skills drifts back towards the memory-file budget.

Skills also do not replace fine-tuning or tools where those fit. A behaviour needed in every response at low latency may belong in the model, and an operation with its own credentials and audit needs belongs behind a tool with server-side checks, whatever text describes it.
