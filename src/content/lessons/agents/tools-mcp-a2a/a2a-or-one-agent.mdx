## Three shapes, one question

A capability an agent needs can arrive in three shapes. It can be a tool inside the agent's own loop, defined in-process or reached over MCP. It can be another agent that this agent calls like a tool and whose result it reads (OpenAI's guide calls this the manager pattern). Or it can be a peer agent behind a protocol boundary, reached over A2A, which accepts a task, runs its own loop with its own model, tools and budget, and reports a lifecycle back.

The question that decides between them is who owns the other side. A protocol boundary between agents behaves like a service boundary between teams: worth its cost when the two sides deploy independently, sit in different trust domains or belong to different companies, and pure overhead when one team owns both. Most systems inside one team need neither A2A nor a second agent. OpenAI's guide gives the same default from the other direction: maximise a single agent's capabilities first, and split only when instructions with many conditional branches or overlapping tools stop working after the tools themselves have been made clearer.

## What A2A specifies

The specification's latest released version is 1.0.0, after 0.3.0, 0.2.6 and 0.1.0. The Linux Foundation's April 2026 release calls 1.0 the first stable specification, counts more than 150 supporting organisations (up from more than 50 a year earlier) and names integrations in Azure AI Foundry, Copilot Studio and Amazon Bedrock AgentCore Runtime; it claims production deployments without giving a count.

Discovery is an Agent Card, a JSON document at `https://{server_domain}/.well-known/agent-card.json` with a name, description, version, an ordered list of supported interfaces (the first is preferred), capabilities (streaming, push notifications, extensions, and whether an extended card is available through `GetExtendedAgentCard`), security schemes, and a list of skills with ids, descriptions and tags. Cards can be signed with JWS over the RFC 8785 canonical form, and the spec says clients should verify at least one signature before trusting a card. Security schemes cover API keys, HTTP auth, OAuth 2.0, OpenID Connect and mutual TLS.

The same operations run over three bindings: JSON-RPC, gRPC and HTTP+JSON/REST, plus custom bindings. They are `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, create, get, list and delete for push notification configs, and `GetExtendedAgentCard`. Streaming uses server-sent events when the card declares it; push notifications are HTTP POSTs to a webhook the client registers. Clients MUST send an `A2A-Version` header in `Major.Minor` form (an empty value is read as 0.3), and a server that does not support the version returns `VersionNotSupportedError`.

The unit of work is a task with nine states: unspecified, submitted, working, completed, failed, canceled, rejected, and two interrupted states, input required and auth required, in which the remote agent waits for the caller. Cancellation is a request: the spec says the server will attempt it and success is not guaranteed. The design principle that matters most for the decision is opacity: agents collaborate without sharing their internal thoughts, plans or tool implementations. The caller sees messages, artifacts and states; it does not see the remote agent's trace. The spec lists tracing and monitoring among concerns to align with enterprise practice and defines no trace context propagation of its own.

## How MCP and A2A relate, and who governs them

The A2A specification's Appendix B describes the two as complementary: MCP standardises how an agent connects to tools, APIs and data, and A2A standardises how independent agents discover each other and delegate work as peers, with the example of an A2A server agent that uses MCP internally to reach its tools.

Both now sit at the Linux Foundation. A2A is a Linux Foundation project, originally developed by Google. On 2025-12-09 Anthropic donated MCP to the Agentic AI Foundation, a directed fund under the Linux Foundation co-founded by Anthropic, Block and OpenAI, with Block's goose and OpenAI's AGENTS.md as the other founding projects; the announcement says MCP's governance model stays unchanged and gives Anthropic's own counts of more than 10,000 active public MCP servers and more than 97M monthly SDK downloads. Neutral governance lowers the risk of standardising on either protocol; it does not change which one a given boundary needs.

The difference that decides the boundary is the contract. An MCP tool call is a request whose result the caller's model reads and acts on (the tasks extension adds polling for long-running calls, still with the caller in charge). An A2A task is delegated judgment: the remote agent decides how to do the work, may stop to ask for input or credentials, and returns an outcome the caller can accept, reject or cancel, but cannot step through.

## What a boundary costs

Latency adds up first. A tool call costs one execution plus the caller's model turn to read it. A delegated task costs the remote agent's whole loop plus the caller's turn to read the result, and the remote loop length is set by someone else's prompt, model and tools.

Tokens come next. Anthropic reports that its agents use about 4 times the tokens of a chat interaction and its multi-agent research system about 15 times, so in that system adding agents multiplied token use by roughly 15 / 4 = 3.75. The same post reports the multi-agent system beat a single Opus 4 agent by 90.2% on Anthropic's internal research eval, on broad questions that split into independent searches. The trade is real in both directions, and it was measured on a task shaped for parallel fan-out.

Debugging cost is the one teams underestimate. Inside one agent, a wrong answer has a trace: every prompt, tool call and result. Across an A2A boundary the trace stops at the task: the caller gets states, messages and artifacts, and the opacity principle means the remote side owes nothing more. MCP at least documents OpenTelemetry trace context keys in `_meta` (SEP-414), so a tool call can join the caller's trace when the server propagates it; for A2A, any shared tracing is an agreement between the two owners outside the specification.

The middle column is the common case for integrations with other teams: they publish operations as MCP tools, and your agent keeps the judgment and the trace. A2A wins when the other party will not or cannot expose operations (their tools, data and prompts are their product), when the work outlives a request, or when a human on their side may need to step in. Splitting your own agent into several A2A agents is justified by the same test and rarely passes it: inside one team, agents-as-tools in one process give the separation without the protocol.

When you do delegate, the caller owns its own deadline. The remote agent's budget is not yours, and an interrupted state is a decision the caller has to make, not something to answer automatically:

```python
TERMINAL = {"TASK_STATE_COMPLETED", "TASK_STATE_FAILED", "TASK_STATE_CANCELED", "TASK_STATE_REJECTED"}
INTERRUPTED = {"TASK_STATE_INPUT_REQUIRED", "TASK_STATE_AUTH_REQUIRED"}


def await_remote(get_task, cancel_task, task_id, deadline, clock, sleep, poll_s=2.0):
    """Poll a delegated A2A task until it ends, stops for us, or our budget runs out."""
    while True:
        task = get_task(task_id)
        state = task["status"]["state"]
        if state in TERMINAL:
            return state, task
        if state in INTERRUPTED:
            return state, task            # the caller answers, escalates to a person, or cancels
        if clock() + poll_s > deadline:
            cancel_task(task_id)          # best effort: the spec does not guarantee cancellation
            return "DEADLINE", task
        sleep(poll_s)


t = [0.0]
states = iter(["TASK_STATE_WORKING"] * 10)
get = lambda tid: {"id": tid, "status": {"state": next(states)}}
cancelled = []
print(await_remote(get, cancelled.append, "task-8", deadline=5.0, clock=lambda: t[0],
                   sleep=lambda s: t.__setitem__(0, t[0] + s))[0], cancelled)   # DEADLINE ['task-8']
```

In production the polling is replaced by `SubscribeToTask` or a push notification webhook when the card declares them, and a cancelled task can still finish on the remote side, so any side effect it was asked to perform needs the same idempotency treatment as a tool call.

## When this is wrong

The organisational-boundary rule assumes the remote party exposes something either way. Some capabilities exist only as agents (a vendor's support agent, a counterparty's negotiation agent), and there the choice is A2A or no integration. The rule also undercounts the case where the work is long and interruptible inside one company: a job that waits days for a human approval in another department fits a task lifecycle better than a tool call, whoever owns it, although a durable workflow is often the simpler answer there.

The cost figures are scenario arithmetic and one vendor's measurement on one task type. A remote agent with a short loop on a fast model can cost less than your own agent doing the same work with a larger model, and a multi-agent split that runs searches in parallel can lower wall-clock time while raising tokens.

Finally, A2A 1.0 is young as a stable specification, and adoption counts from a foundation press release measure supporting organisations, not traffic. Check the version header your counterpart actually speaks before designing around a feature of the current specification.
