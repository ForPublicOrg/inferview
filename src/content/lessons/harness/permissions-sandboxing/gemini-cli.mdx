## What it is and who runs it

Gemini CLI is Google's open-source terminal agent, Apache 2.0, in the `google-gemini/gemini-cli` repository. It is taught here as the open reference implementation of a terminal agent's permission stack, because its policy engine, sandbox and checkpointing are documented in the repository alongside the code.

Its status changed in 2026. A Google Developers Blog post of 19 May 2026 announced that from 18 June 2026 Gemini CLI and the Gemini Code Assist IDE extensions stop serving Google AI Pro and Ultra subscribers and free individual use, in favour of Antigravity CLI. Enterprise customers with Gemini Code Assist Standard or Enterprise licences and organisations using Code Assist for GitHub through Google Cloud keep access, and Gemini CLI remains usable with paid Gemini API keys. The repository's README, checked 2026-10-28, says the CLI is designed for those enterprise products, is not tuned for Gemini 4 and later models and should not be used for model benchmarks, and points individual users to Antigravity CLI (`agy`). Preview and stable releases still ship weekly on Tuesdays, with nightly builds.

Antigravity CLI is described in the post as built in Go, able to orchestrate multiple agents asynchronously, and sharing a server-side agent harness with the Antigravity 2.0 desktop app. Agent Skills, hooks, subagents and extensions (renamed Antigravity plugins) carry over, without one-to-one feature parity at launch. Nothing else about its internals is documented in the sources read here.

**GEMINI.md context.** Context files load from three places: the global `~/.gemini/GEMINI.md`, the configured workspace directories and their parents, and, just in time, the ancestors of any path a tool touches, up to a trusted root. Their contents are concatenated and sent with every prompt. `/memory show` prints the concatenation and `/memory reload` rescans. Files can import others with `@file.md`, and `context.fileName` can point the CLI at `AGENTS.md` or a list of names.

**Policy engine.** Every tool call passes a rule engine configured in TOML files under `~/.gemini/policies/`. A rule names a tool (or an MCP server, or a subagent), optional argument patterns, and a decision: `allow`, `deny` or `ask_user`. For `run_shell_command` there are two shorthands, `commandPrefix` and `commandRegex`, which cannot be combined in one rule. The engine is priority-ordered rather than deny-first: the highest-priority matching rule wins. Each rule's priority (0 to 999) is added, divided by 1,000, to a tier base, which the page's table gives as default 1, extension 2, workspace 3, user 4 and admin 5 (its worked examples and its supplemental-policy note use bases one lower; the ordering is the same either way). The workspace tier, the one a repository could supply, is currently disabled. A deny without argument patterns removes the tool from the model's view entirely. In non-interactive runs, `ask_user` becomes deny.

**Approval modes.** Four modes sit over the rules: `default`, where most write tools need confirmation; `autoEdit`, where some write tools are auto-approved; `plan`, a strict read-only mode; and `yolo`, where every tool is auto-approved. An "allow for all future sessions" approval applies to the current mode and every more permissive one, and approvals granted in `plan` apply to all modes.

**Built-in tools and MCP.** The CLI ships file-system, shell, web-fetch and search tools, and loads MCP servers configured in `~/.gemini/settings.json`.

**Sandbox.** Sandboxing is enabled with `-s` or `--sandbox`, the `GEMINI_SANDBOX` variable or `tools.sandbox` in settings. On macOS it uses Seatbelt through `sandbox-exec`; elsewhere a Docker or Podman container (by default `ghcr.io/google/gemini-cli:latest`), gVisor's `runsc` on Linux, an experimental LXC/LXD mode, or a Windows native sandbox that sets integrity levels with `icacls`. Tool sandboxing isolates individual tool executions such as `shell_exec` and `write_file` rather than the whole CLI, and can be turned off with `security.toolSandboxing: false`.

The six Seatbelt profiles form a grid. Permissive restricts writes, restrictive restricts more, and strict restricts reads as well as writes; each comes in an `-open` variant with network allowed and a `-proxied` variant that routes network through a proxy. The default, `permissive-open`, denies operations by default, confines writes to the project directory, and allows broad reads and network access. The doc's own guidance is to use the most restrictive profile that allows the work, and it states that sandboxing "reduces but doesn't eliminate all risks". A project can define its own container image in `.gemini/sandbox.Dockerfile`, built when `BUILD_SANDBOX=1` is set (automatic builds only work when running from source).

**Checkpointing.** Off by default, enabled with `general.checkpointing.enabled`. When the user approves a file-modifying tool, the CLI commits the project state to a shadow git repository at `~/.gemini/history/<project_hash>` before the change runs, and saves the conversation and the pending tool call as JSON. `/restore` reverts the files, restores the conversation and re-proposes the original call to run, edit or skip. The `--checkpointing` flag was removed in version 0.11.0.

## Context strategy

Gemini CLI's durable context is GEMINI.md, layered from global to workspace to just-in-time, concatenated in that order and resent with every prompt. The just-in-time layer means a tool call that touches a new subdirectory can add instructions from that directory and its ancestors to every later prompt. The sources read here do not describe how the CLI compresses long conversations, so that is not covered.

## Tools and permission model

The policy engine's semantics differ from the other engines in this module in one way that matters for review. Claude Code and Codex let the most restrictive matching rule win. Gemini CLI lets the highest-priority rule win, and the tier dominates the rule's own priority, because the rule's priority is divided by 1,000. By the table, a user-tier `allow` at priority 0 (final 4.000) outranks a default-tier `deny` at priority 999 (final 1.999), and an admin-tier rule outranks both. That is ordered firewall-rule semantics: correct and predictable, and it means a reviewer cannot read a deny in isolation and conclude the action is blocked.

Two protections against a repository changing the rules are documented. The workspace tier is disabled, so policies a repository ships do not load. The standard admin policy directory is loaded only if it passes ownership checks: root-owned with no group or other write access on Linux and macOS, and inside `C:\ProgramData` with no standard-user write access on Windows; a directory that fails is ignored. Supplemental admin paths, given with `--admin-policy` or `adminPolicyPaths`, get the admin tier without those checks, and are ignored when the standard directory already holds policy files, so a command-line flag cannot override a central policy once one exists.

Three sharp edges come from the same page. `commandRegex` is tested against a JSON string, so `^` and `$` anchors often do not behave as written. Shell redirection prompts even under a matching allow rule unless that rule sets `allowRedirection = true`, the same conservatism Codex shows with its opaque scripts. And an underscore in an MCP server name can make wildcard and security rules fail silently, because the parser splits names on the first underscore after `mcp_`.

## Cost and latency

The cost change in 2026 is access, not price. Individual free use and Google AI Pro and Ultra stopped on 18 June 2026; paid Gemini API keys and enterprise Code Assist licences continue. The sources read here give no per-request cost or latency figures for either CLI. Operationally, weekly stable releases mean a fleet's policy and sandbox behaviour can change weekly, which belongs in the rollout plan.

## Failure modes

**The default sandbox allows the network.** `permissive-open` confines writes to the project directory and allows broad reads and network access, so a sandboxed command can read a credential file the user can read and send it anywhere. Containment of exfiltration needs a `-proxied` or stricter profile, or a container with network policy.

**Priority surprises.** Because tiers dominate, a broad user-tier allow overrides every default-tier deny it matches. A policy review that does not compute final priorities will miss it.

**Regex and naming footguns.** Anchored `commandRegex` patterns and underscored MCP server names fail without errors, the most expensive way for a security rule to fail.

**A repository can define the sandbox image.** `.gemini/sandbox.Dockerfile` in the project root defines the container the tools run in, when `BUILD_SANDBOX=1` is set and the CLI runs from source. A file the agent can write that defines its own sandbox belongs on the list from this module's attack-surface lesson.

**Checkpoints are off by default.** Without them, an approved write has no built-in undo beyond the user's own version control.

**Status drift.** The README says the CLI is not tuned for Gemini 4 and later. A team that stays on it is choosing an older harness for newer models, and evaluation results from one do not transfer to the other.

## What is not public

Antigravity CLI's internals are not documented in the sources read here: its permission model, whether and how it sandboxes tool execution, and what runs on Google's servers in its "server-side harness" as opposed to the user's machine. The post states that features carry over without full parity and links to migration documentation this teardown did not read. Gemini CLI itself is open source, so its behaviour is answerable from the code; this teardown limits itself to the repository's documentation.
