## What it is and who runs it

Copilot cloud agent is GitHub's asynchronous coding agent. GitHub's docs used to call it "coding agent"; the current pages call it Copilot cloud agent. It researches a repository, plans a change, edits files, runs tests and linters, and opens a pull request. Work starts from the agents panel, a chat, an issue or pull request, a security campaign (code scanning alerts assigned to Copilot), an automation on a schedule or repository event, or an integration such as Slack or Microsoft Teams.

It is in this module because its permission model is unlike the local harnesses. Claude Code, Codex and Cursor ask, per action, whether the agent may do something on the developer's machine. Copilot cloud agent asks almost nothing during the run. It moves the controls to the edges: who can start a task, what the throwaway environment can reach, what the agent can do to the repository, and who must approve the result. GitHub runs all of it. Everything below comes from GitHub's documentation, checked 2026-10-28.

**Task trigger.** A task names one repository, and the agent can change only that repository: no cross-repository changes in one run, one branch at a time and one pull request per task. Automations add a trigger with no person behind each run; their pull requests and pushes are attributed to the user who created the automation.

**Input gate.** Only users with write access can trigger the agent, and comments from users without write access are never presented to it. Events from such users are ignored by automations by default, with an opt-in. Before user input reaches the agent, hidden characters are filtered; the documented example is that text inside an HTML comment in an issue or pull request comment is not passed on. This is the only prompt-injection mitigation the risks page describes for the agent itself.

**Ephemeral environment.** Each session runs in a throwaway cloud environment that the firewall page places in "the GitHub Actions appliance environment". A repository customises it with `.github/workflows/copilot-setup-steps.yml`, a single job that must be named `copilot-setup-steps`; only `steps`, `permissions`, `runs-on`, `services`, `snapshot` and `timeout-minutes` are honoured. The file only takes effect from the default branch. The steps run before the agent starts, and their output lands in the session log. A session has a hard 59-minute limit that cannot be extended, and `timeout-minutes` can only shorten it. Runners can be standard or larger GitHub-hosted runners, or self-hosted runners managed by Actions Runner Controller; only Ubuntu x64 and Windows 64-bit are supported.

**Agent loop.** The agent researches, plans, edits and runs commands inside the environment. The model is selectable, with availability depending on plan, policy and how the task was started. Custom instructions, custom agents and agent skills shape its behaviour, and hooks can run commands during its work for validation or logging.

**MCP servers.** MCP servers give the agent tools and data beyond the repository. By default the GitHub MCP server provides context only from the agent's own repository; broader access is a repository setting.

**Bash tool processes and the firewall.** Internet access is restricted by a firewall with an allowlist. GitHub's recommended list covers common OS package repositories, container registries, language package registries, certificate authorities, and the browser downloads the Playwright MCP server needs. Custom entries are domains (which include subdomains) or URLs (scheme, host and path prefix). A blocked request is reported in the pull request body, or as a comment on an existing pull request, with the address and the command that tried it. The firewall applies only to processes the agent starts through its Bash tool.

**Validation.** Before it completes a pull request, the agent runs CodeQL, Copilot code review, dependency checks against the GitHub Advisory Database (malware and High or Critical CVSS vulnerabilities) and secret scanning. These do not require a GitHub Advanced Security, Secret Protection or Code Security licence, and each can be turned off. The session log shows what ran.

**One branch, push only.** The agent writes to a new `copilot/` branch, or to the existing pull request's branch when it was triggered by mentioning `@copilot` on that pull request. It can perform only simple push operations and cannot run `git push` or other git commands directly. Branch protections and required checks still apply. Commits are authored by Copilot with the requesting developer as co-author, signed, and linked to their session log.

**Draft pull request and the reviewer.** The agent cannot mark its pull request ready for review, approve it or merge it. The user who asked for the pull request cannot approve it, so a second person with write access has to. If the agent opens a pull request under its own app identity, one extra approval is required where the repository already requires at least one. Workflows on the branch do not run until someone with write access selects "Approve and run workflows", unless an administrator allows automatic runs.

## Context strategy

The agent's context comes from the repository it was given, the task text after filtering, custom instructions saved at personal, repository and organisation level, and whatever custom agents and skills the task invokes. The GitHub MCP server's default scope keeps cross-repository context out unless a repository grants it. The setup steps' output is in the session log; whether and how it reaches the model's context is not documented. GitHub does not publish the prompt, how the agent compacts or summarises a long session, or how it decides what to read.

## Tools and permission model

The model is "approve the environment and the result, not the actions". Inside the run, nothing asks a person. The agent can run any command its environment allows, so the controls that matter are what the environment holds and reaches:

- **Who can start it**: repository write access, enforced by GitHub.
- **What enters it**: filtered task text, and nothing from users without write access.
- **What it can reach**: the firewall for Bash processes, the MCP configuration for everything MCP servers do.
- **What it can change**: one branch in one repository, through simple pushes.
- **What leaves it**: a draft pull request that needs an approver other than the requester, branch protections, and workflow runs that wait for a click.

The design turns the merge into the permission prompt. That suits an asynchronous agent, where nobody is watching to approve commands, and it uses controls a GitHub organisation already operates. Firewall settings follow the organisation's lead: owners can set the firewall and the recommended allowlist to on, off or "let repositories decide", and can turn off repository custom rules; organisation allowlist entries cannot be deleted at the repository level.

## Cost and latency

Latency is bounded by the 59-minute session cap, which the docs say cannot be extended or bypassed. Setup steps run inside that time, so a slow dependency install is spent from the agent's budget.

On cost, GitHub's legacy request-based billing page, which applies to Copilot Pro and Pro+ subscribers on an existing annual plan after 1 June 2026, says a cloud agent session consumes both GitHub Actions minutes, from the account's shared allowance for hosted runners, and premium requests, one per session under a dedicated SKU, with a session starting when Copilot is prompted or assigned to an issue. This teardown did not check billing for other plans; the about page defers to GitHub's billing documentation. A 59-minute session on a larger runner draws on the same minutes as the repository's CI.

## Failure modes

**The firewall has documented holes.** It does not apply to MCP server processes or to processes started by setup steps, and the page warns that sophisticated attacks may bypass it and that it "should not be considered a comprehensive security solution". It is not compatible with Windows runners and must be disabled for self-hosted runners, so teams on either have no integrated egress control and need their own. An MCP server configured with broad network or data access is outside the one network control the agent has.

**Visible injection is not filtered.** Hidden-character filtering removes text a human reviewer would not see in the issue. Text a reviewer can see, in the issue, in a linked page, in a dependency's files, still reaches the model. The containment for that is the environment and the review, not the filter.

**Setup failure is silent by design.** A failing setup step skips the rest and the agent starts with whatever state exists. An agent that cannot run the test suite may still produce a plausible pull request; the session log records the failure, and only a reviewer who reads it will know.

**The merge gate is a person.** The requester-cannot-approve rule removes self-approval, and "Approve and run workflows" stops CI from running agent code automatically. Both are clicks, and both inherit approval fatigue at volume. A workflow run on the agent's branch executes code the agent wrote, with the permissions the workflow has.

**Validation is advisory.** CodeQL, review, dependency and secret checks run before completion, and each can be disabled. The docs do not say whether a finding blocks the pull request or is only reported.

## What is not public

GitHub's documentation does not describe:

- **Model routing.** Which model a task uses by default, and how selection works when it is not offered, beyond "depends on how you start the task".
- **The prompt.** The system prompt, how custom instructions are merged into it, and how long sessions are managed.
- **The validation step's internals.** Whether the agent sees and acts on CodeQL and review findings before opening the pull request, and whether any finding blocks completion.
- **Token scope.** The risks page says the agent can perform only simple pushes; it does not say how the credential is scoped.
- **The firewall's implementation.** Only its coverage and limits are documented.

The firewall's exclusions are public: MCP servers and setup steps are outside it.

<Fragment slot="short">
<p>Enable it on GitHub-hosted runners with the firewall and recommended allowlist set at organisation level, on repositories whose MCP configuration grants nothing beyond the repository. Hold the dozen with production-database MCP servers until the server is scoped or removed for the agent, because MCP is outside the firewall. Self-hosted runner repositories wait for an egress control on those runners. Write down that visible injection still reaches the model and that the merge review is the final control.</p>
</Fragment>
<Fragment slot="long">
<p>Sort the 200 by the two documented gaps. A repository is ready when it runs on GitHub-hosted Ubuntu runners, where the firewall works, and its MCP configuration gives the agent nothing outside the repository. Lock the firewall on at organisation level and decide whether repositories may add custom allowlist rules.</p>
<p>For the dozen with production-data MCP servers, the firewall is irrelevant: the server process reaches the database and any network the runner allows. Either give the agent a separate MCP configuration without that server, or accept the exposure in writing with the data owner's sign-off.</p>
<p>For self-hosted runners, GitHub requires disabling the integrated firewall, so the runners need network policy of their own before the agent runs there. Ephemeral, single-use runners, which the docs recommend, also limit what one session leaves behind.</p>
<p>Keep the review rules: requester cannot approve, workflow runs need approval. What you give up is time to coverage; maybe a third of repositories wait. Record the reason for each and the condition that releases it.</p>
