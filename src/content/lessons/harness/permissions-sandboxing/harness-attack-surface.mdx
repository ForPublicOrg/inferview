## The agent can write its own configuration

Every harness in this track is configured by files in the repository it works on: permission rules, hooks, MCP server definitions, instruction files, skills. Its write access usually covers that repository. So a harness that does not special-case those paths lets the agent edit its own policy, and an agent steered by injected text edits it on someone else's behalf. The same holds for files that configure the next program to run in the repository: git hooks, editor tasks, pre-commit config, CI workflows. Those run later, often under a person's identity and with their credentials.

This is the CI problem of a job that can rewrite its own workflow file, with a difference that makes it harder: the writer reads untrusted text as part of its job, and its writes are proposals from a model rather than commits from a reviewed branch.

A self-grant needs three things: a path the agent can write, a reader that treats the file as configuration or code, and no consent step between the write and the read. The vendors' defences each remove one of the three.

## Defence one: protected paths

**Claude Code** never auto-approves writes to a fixed list of directories (`.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.claude`, with exceptions such as `.claude/worktrees/` and auto-memory files) and files (`.gitconfig`, `.gitmodules`, shell startup files including `.bashrc`, `.zshrc` and `.envrc`, `.npmrc`, `.yarnrc`, Bazel and wrapper configs, `.pre-commit-config.yaml`, lefthook files, `.devcontainer.json`, `.mcp.json`, `.claude.json`, files passed to `--settings`, `--mcp-config` or `--agents`, and any settings file that is a symlink). In Manual and `acceptEdits` mode such a write prompts; in auto mode it goes to the classifier; in `dontAsk` it is denied; in `bypassPermissions` it is allowed. An allow rule never pre-approves one, so `Edit(.claude/**)` in allow does nothing.

**Codex** in `workspace-write` keeps `.git` read-only recursively (and, when `.git` is a `gitdir:` pointer file, the directory it points to), plus `.codex`, `.agents` and `.aws` when they exist as directories. The enforcement is the OS sandbox (Seatbelt on macOS, bubblewrap and seccomp on Linux), so it holds for any process the agent starts, not only for its edit tool.

**Cursor's** sandbox protects `.git/config`, `.git/hooks`, `.vscode`, `.cursorignore` and sensitive Cursor config, and team policies and hardcoded rules sit above local files so a repository cannot weaken them.

All three cover git, because `.git/hooks` and `core.fsmonitor` in `.git/config` run code on the next git command, whoever runs it. The difference in length has a plausible reading. Claude Code's file permissions are checked per tool call, so each path that executes later has to be named; Codex's sandbox already confines writes to the workspace, so shell startup files in the home directory are out of reach without being listed. A list is only as complete as its author's inventory, which is the argument for running your own.

## Defence two: grants wait, restrictions do not

The second defence is an asymmetry in how configuration takes effect. In Claude Code, `deny` and `ask` rules in a project's `.claude/settings.json` apply immediately, because they only restrict. `permissions.allow` rules and `additionalDirectories` grant capability, so they wait until the user accepts the workspace trust dialog, which lists them. A `.claude/settings.local.json` that is tracked in git, or reached through a symlinked `.claude`, is treated as repository-supplied and held the same way. A project file cannot raise the starting mode: `defaultMode` set to `auto` or `bypassPermissions` in project settings does not take effect. Codex loads project-local rules from `.codex/rules/` only when the project's `.codex/` layer is trusted.

The asymmetry has a precise edge. It governs what a cloned repository can grant. It does not stop an agent with write access from editing `.claude/settings.json` in a folder already trusted; that is defence one's job, which is why `.claude` is on the protected list. The two defences cover different authors: the repository's previous contributors, and the agent itself.

There is one more party that can outrank the rules. A Claude Code mod that handles the `tool.check` event can approve a call a deny rule refuses or a hook blocked, when the machine has no managed settings and the session is not on a Team or Enterprise login. An installed mod is trusted code with authority above the rule file, and an audit has to list them.

## Defence three: nothing runs before the decision

The third defence is ordering. Configuration that can execute must not be read before the user decides whether to trust the folder.

Anthropic's containment post (25 May 2026) reports three vulnerabilities between mid-2025 and January 2026 in which code ran before the user had consented to anything. In the main case, a cloned repository's `.claude/settings.json` defined a hook; Claude Code read project settings at startup, before the "Do you trust this folder?" prompt, and the hook ran. The fix deferred parsing and execution of project-local configuration until the user accepts the prompt.

The fix applies to interactive sessions. A `claude -p` run or an SDK session never shows the trust dialog and treats the folder as trusted. In those sessions the repository's hooks, its `env` block and helper commands such as `apiKeyHelper` are used, and servers in its `.mcp.json` are connected without asking. The repository's allow rules are still not applied. For a CI job that runs the agent on a pull request, the pull request's author is writing configuration that executes on the runner. The documented mitigations: `--setting-sources user` so neither project settings nor `.mcp.json` are read, `--bare` to skip project hooks, skills, plugins and MCP servers (the project's `env` block still applies), `--settings '{"disableAllHooks": true}'` passed on the command line (a user-settings value alone loses to the project's), and `disabledMcpjsonServers` to reject servers by name.

## The failure case: CVE-2025-54135

Cursor before 1.3.9 required approval to edit an existing dotfile and did not require it to create one. The CVE record, published 5 August 2025, describes the chain: indirect prompt injection hijacks the agent, the agent creates `.cursor/mcp.json` where none existed, and because an MCP server entry is a command to launch, the result is remote code execution without approval. It is scored CVSS 3.1 8.6 and classed as CWE-78 (OS command injection) and CWE-829 (inclusion of functionality from an untrusted control sphere). The fix shipped in 1.3.9.

The check keyed on the operation (modify) rather than the path (a file the harness will execute). Any protection written as "ask before changing X" has the same hole if X can be created, deleted and recreated, renamed into place, or reached through a symlink. Claude Code's docs address the last two explicitly: a write whose path is itself a symlink is refused and redirected to the target, and a deny rule applies when either the requested path or the file it resolves to matches.

The injection step is the part teams underweight. A model that refuses injected instructions almost every time is still not a control for a write that grants code execution.

## Auditing a harness for self-grant paths

The audit asks, for each file that some program treats as configuration or code: can the agent write it, who reads it and with what privileges, and is there a consent step between? Build the inventory from four sources.

1. **Harness configuration at every scope**: settings and rule files, hooks, MCP definitions, skills (a skill's `allowed-tools` pre-approves tools, and the permissions page says workspace trust never gates it), instruction files, installed mods.
2. **Toolchain configuration that executes**: `.git/hooks`, `.git/config`, `.husky`, pre-commit and lefthook config, `.vscode` tasks, `.devcontainer`, package-manager configs.
3. **Files that run elsewhere with other credentials**: CI workflows, deploy manifests, infrastructure code.
4. **Persistent instructions**: CLAUDE.md, AGENTS.md, memory files. The containment post notes that content injected into persistent state is reloaded every time an agent starts. Claude Code reads project-root CLAUDE.md at session start, so a planted line there waits for the next session, `/clear` or `/compact`; a nested CLAUDE.md in a subdirectory loads on demand, so one the agent writes before it loads takes effect in the same session.

For each entry, test the write in a scratch repository in every mode you ship, through the edit tool and through Bash, as an edit and as a creation where the file is absent, and through a symlink. Then classify the session's actual writes. The script below does the last step against a transcript's list of written paths; the table is the part you maintain.

```python
import posixpath

# path or prefix -> (who reads it, when it takes effect)
SELF_GRANT = {
    ".claude/settings.json": ("Claude Code rules and hooks", "hooks as soon as the file watcher sees the edit"),
    ".claude/settings.local.json": ("Claude Code rules and hooks", "hooks as soon as the file watcher sees the edit"),
    ".claude/skills/": ("skills, with their hooks and allowed-tools", "when the skill loads"),
    ".mcp.json": ("MCP servers, each a command to launch", "next session"),
    ".cursor/mcp.json": ("Cursor MCP servers", "next session"),
    ".codex/": ("Codex config and rules", "next session, if the layer is trusted"),
    ".git/hooks/": ("git hooks", "next git command, by the agent or a person"),
    ".git/config": ("git config such as core.hooksPath or core.fsmonitor", "next git command"),
    ".husky/": ("git hooks via husky", "next commit"),
    ".pre-commit-config.yaml": ("pre-commit hooks", "next commit"),
    ".vscode/": ("editor tasks and settings", "when a person opens the folder"),
    ".devcontainer/": ("container build and lifecycle commands", "next container build"),
    ".github/workflows/": ("CI jobs, with CI secrets", "next push or pull request"),
    "CLAUDE.md": ("instructions the agent loads", "root: next session, /clear or /compact; nested: when first loaded"),
    "AGENTS.md": ("instructions the agent reloads", "next session"),
}


def audit(written_paths):
    findings = []
    for raw in written_paths:
        path = posixpath.normpath(raw.replace("\\", "/"))
        for prefix, (reader, when) in SELF_GRANT.items():
            hit = path.startswith(prefix) if prefix.endswith("/") else (path == prefix or path.endswith("/" + prefix))
            if hit:
                findings.append((path, reader, when))
    return findings


session_writes = ["src/app.py", "./.mcp.json", "docs/../.git/hooks/pre-commit", "services/api/AGENTS.md", "README.md"]
for path, reader, when in audit(session_writes):
    print(f"{path}: {reader}; takes effect {when}")

assert [f[0] for f in audit(session_writes)] == [".mcp.json", ".git/hooks/pre-commit", "services/api/AGENTS.md"]
```

One easy mistake: stripping a leading `./` with `lstrip("./")` also strips the dot from `.mcp.json`, and the audit reports nothing. Path handling in a security check is where the bypasses live; normalise once, with the library, and test the dotfiles.

## When this is wrong

Protected-path lists are enumerations, and the set of files that execute is open. `package.json` scripts, a `Makefile`, `conftest.py` and the test files themselves run code, and the agent has to edit them to do its job. No list covers them without making the agent useless, so the residual risk moves to the next runner of that code: the reviewer who reads the diff, the CI job that executes it with or without secrets, and the developer who runs `npm test` locally. The lists stop the agent from changing the rules it runs under; they do not make its output safe to execute.

The consent step is a prompt, and prompts are clicked through. The trust dialog lists the allow rules a folder would grant, which helps only if someone reads it, and the 93% acceptance rate Anthropic measured for permission prompts is the reason not to count on that. Managed settings, which no project or user file can override, are the control that does not depend on a click.

Finally, every one of these defences is version-specific. Cursor's fix is a version number, Claude Code's pre-trust fix followed reports made between mid-2025 and January 2026, `onFailure` exists from v2.1.295, and symlinked deny rules gained real-path matching in v2.1.268. An audit that does not record the harness version it tested has tested nothing a fleet can rely on.
