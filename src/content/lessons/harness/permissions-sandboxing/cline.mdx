## What it is and who runs it

Cline is an open-source coding agent, Apache 2.0, published by Cline Bot Inc. Its repository describes it as an autonomous coding agent available as an SDK, an IDE extension (VS Code and the JetBrains family) and a CLI that can run headless. Its default is the most conservative of the tools in this module: every file edit and terminal command needs the user's approval. Two features shape how teams loosen that default: a Plan mode that cannot change anything, and auto-approve settings by category.

The design choice that makes it worth a teardown is where Cline draws the line between a command that can run unattended and one that needs a person. Claude Code draws it with rules and a separate classifier; Codex with rules and an OS sandbox. Cline draws it with a flag the acting model sets on its own command. Cline's source code is public; this teardown reads only its documentation, checked 2026-10-28, and limits its claims to what the docs say.

**Plan mode.** Cline reads the codebase, runs searches and discusses an approach. The docs say it "cannot modify any files or execute commands". `/deep-planning` extends this into a systematic exploration that identifies affected files and dependencies, writes a detailed plan and asks clarifying questions; its prompt is tuned per model family. The docs suggest Act directly for small tasks, Plan then Act for medium ones, and `/deep-planning` for large ones.

**Act mode.** Act keeps the planning conversation and can modify files, run commands and carry out the plan. With "Use different models for Plan and Act" enabled, each mode has its own model, and switching modes switches models. The docs' example pairings are GLM 4.6 for Plan with Grok Code Fast for Act, for cost, or Claude Opus for Plan with Claude Sonnet for Act, for quality.

**Context.** Switching modes keeps the full history, so the Act model inherits the Plan model's exploration. Auto Compact summarises the conversation as it approaches the model's context window limit and replaces the history with the summary; on models without support Cline falls back to rule-based truncation. The Memory Bank is a methodology rather than a feature: six markdown files (`projectbrief.md`, `productContext.md`, `activeContext.md`, `systemPatterns.md`, `techContext.md`, `progress.md`) that custom instructions tell Cline to read at the start of every task.

**The `requires_approval` flag.** For terminal commands, "Cline does not use a fixed allowlist". The model assigns each command a `requires_approval` flag from the command and its arguments. The docs give examples of commands on each side and call them "examples, not guarantees".

**Auto-approve settings.** Categories are toggled independently: read project files, read all files (outside the workspace), edit project files, edit all files, execute safe commands, execute all commands, use the browser, use MCP servers. The "all" variants extend a base toggle and only matter when it is on. "Execute safe commands" runs any command the model flagged as not requiring approval. YOLO mode auto-approves file changes, terminal commands, browser actions, MCP tools and the transition from Plan to Act, with no confirmation dialog. Optional OS notifications fire when approval is needed and when an auto-approved command has been running for 30 seconds.

**Checkpoints.** After each tool use, Cline commits the project state to a shadow git repository kept separate from the project's history, including files git does not track. A checkpoint can restore files and keep the conversation, truncate the conversation and keep files, or both. On very large repositories the docs warn that checkpoints may use significant storage and slow Cline down, and suggest disabling them if performance suffers.

## Context strategy

Cline's context strategy is conversation-first. The planning history carries into Act, Auto Compact replaces history with a summary near the window limit, and durable project knowledge lives in files the user (or Cline) maintains and a rule tells it to read. The Memory Bank docs describe the manual routine: ask Cline to "update memory bank", start a fresh conversation, tell it to follow its custom instructions. `/newtask` is offered for the same purpose.

Two consequences matter for permissions. First, the Act model's approval decisions are made with the Plan model's whole exploration in context, including every file and page it read. Second, the Memory Bank is a set of files the agent writes and is instructed to read at the start of every task. Text that reaches `activeContext.md` once, from the agent summarising something injected, is reloaded into every later task.

## Tools and permission model

The permission model is two-dimensional: categories the user toggles, and for terminal commands, a per-command flag the model sets. The category dimension is deterministic. The flag is not. "Execute safe commands" means "execute commands the model judged safe", and the model making that judgement is the one proposing the command, with tool results, file contents and fetched pages in its context.

Compare the other designs in this module. Claude Code's rules are evaluated by the harness, and its auto-mode classifier is a separate model that never sees tool results. Codex's rules and sandbox are enforced outside the model. Cline's safe-command line has neither separation: if injected text persuades the model a command is routine, the same persuasion sets the flag. The docs' own guidance reflects the risk: enable only "Read project files" by default, and turn on checkpoints before enabling edits.

Plan mode is the strongest documented control, since no edits or commands are possible there. Two settings weaken it. YOLO mode auto-approves the switch from Plan to Act, so the boundary is no longer a human decision. And the documentation states the restriction as behaviour; it does not say whether Plan mode removes the edit and command tools or relies on the model not calling them.

Checkpoints are the recovery control, and they cover files in the project. The docs describe snapshots of project state and do not claim to undo anything else, so a push, a package publish or a database write made by an auto-approved command is outside what a checkpoint restores.

## Cost and latency

Cline's cost levers are the model per mode and the size of context. A cheaper Act model executing an expensive model's plan is the documented cost pairing. Auto Compact's summarisation shows up as a tool call with its own cost, like any other API call. Checkpoints cost disk and time on large repositories, which is the docs' stated reason some users disable them, and disabling them removes the recovery control. The 30-second notification for auto-approved commands is the only latency figure in the pages read.

## Failure modes

**The approval flag is injectable.** A command the model has been talked into treating as safe runs under "Execute safe commands" without a prompt. This is the failure the docs gesture at with "not guarantees", and there is no second check between the flag and the terminal unless the user disabled the category.

**Category toggles are coarse.** "Execute all commands" and the "all files" variants switch off the remaining distinctions. Once enabled for convenience on one task, they stay on for the next.

**Two models, one plan.** The Act model executes a plan it did not write, with a different model's strengths and blind spots. The docs present the pairing as a cost or quality choice, and the risk side is that the cheaper model is the one making approval decisions.

**Persistent instruction files.** The Memory Bank pattern turns any injection that reaches those files into a standing instruction.

**Recovery stops at the workspace.** Checkpoints restore files. Effects outside the project directory are not files in it.

## What is not public

The documentation read for this teardown does not describe:

- **How `requires_approval` is produced**: the prompt that asks the model for it, and whether Cline checks the flag against anything.
- **How Plan mode is enforced**: tool removal or model instruction.
- **What checkpoints exclude**: files outside the workspace and external effects are not discussed.
- **Auto Compact's trigger and model list**: the page gives no threshold and does not name supported models.
- **Memory Bank internals**: there are none in the product; it is a convention built from custom instructions and markdown files.

Cline's source is public, so these are answerable by reading the code; they are not answered by the docs.

**"A team wants to roll out Cline with Edit project files and Execute safe commands auto-approved, to stop prompt fatigue on a monorepo. Developers' laptops have a kubeconfig for staging. The team lead wants it live this sprint and has no budget for container setups. What do you approve?"**
</Callout>

<Depth>
<Fragment slot="short">
<p>Approve auto-approved edits with checkpoints on, and keep commands on manual approval until there is a control outside the model. The safe-command flag is set by the model that may have read injected text, and a staging kubeconfig turns one misjudged command into a change to shared infrastructure. If prompt fatigue on commands is the blocker, move the kubeconfig out of the default environment first, then revisit.</p>
</Fragment>
<Fragment slot="long">
<p>Edits inside the project are reviewable in the diff and recoverable from checkpoints, so auto-approving them trades little. Commands are different: Cline's line between safe and unsafe is a flag the acting model assigns, with no fixed allowlist, and the docs call the examples "not guarantees". An approval decision that the same model makes under the same context is not a second check.</p>
<p>The concrete exposure is the kubeconfig. With "Execute safe commands" on, a `kubectl` command the model judges routine runs against staging. Without container budget, the cheapest change is environmental: keep cluster credentials out of the shell Cline uses by default and require an explicit context switch for cluster work.</p>
<p>Then reduce the prompts that remain by planning more: Plan mode cannot run commands, so longer planning and fewer, batched commands in Act cut approvals without delegating them to the flag.</p>
<p>What you give up: developers keep approving commands this sprint. Write down the condition for revisiting it, such as credentials out of the default environment and a measured approval count per task.</p>
</Fragment>
