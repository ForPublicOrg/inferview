## What it is and who runs it

Devin is Cognition's autonomous software agent. A session runs in a cloud workspace with a shell, a VS Code IDE and a browser, takes a task from the web app, Slack or an API, and usually ends in a pull request. Around that core Cognition has added a CLI and desktop app, self-hosted execution, access to the user's own machine, and two mechanisms for running many sessions at once.

Everything below is from Cognition's public documentation as checked on 2026-10-28 and from two Cognition blog posts. Devin's docs change often and several features named here are mid-migration (Knowledge and Playbooks are both being replaced by Skills), so treat product names as dated.

Cloud VM. Each session runs in a Linux virtual machine (Windows and macOS are configurable) with the organisation's repositories cloned and dependencies installed. The user sees the same machine through three tools: a shell with command history, a VS Code IDE where they can watch edits or stop the session and take over, and the browser Devin uses. The Progress tab logs every command, edit and browser action in one view, and side chats answer questions about the session read-only while it keeps running.

Blueprints and snapshots. A blueprint is YAML in the settings UI, and the docs compare the three pieces to a Dockerfile, `docker build` and an image. `initialize` installs runtimes and system packages and runs only during builds. `maintenance` installs or updates dependencies during builds and is surfaced to the agent at session start but not executed. `knowledge` holds lint, test and build commands, is never executed, and is loaded into context at session start. An organisation-level `post-build` step validates the assembled environment and fails the build on a non-zero exit. Builds run on save and about every 24 hours. Every session boots a fresh copy of the one active snapshot, and nothing a session changes is written back.

Knowledge, Playbooks and Skills. Knowledge entries are organisation-level instructions retrieved by a trigger description or pinned to repositories, and Devin imports them from `.rules`, `.mdc`, `.cursorrules`, `.windsurf`, `CLAUDE.md` and `AGENTS.md`. Playbooks are reusable prompts for repeated tasks. Both are being replaced: Knowledge is deprecated and migrating to Skills in plugins, and new accounts start with Skills and no Playbooks from 2026-10-24. Skills are `SKILL.md` files committed at `.agents/skills/<skill-name>/SKILL.md` under the Agent Skills standard, and Devin proposes new ones as pull requests when it learns something about a repository.

Outpost workers. Outposts run sessions on infrastructure the customer controls. The agent loop, meaning inference and planning, stays in Cognition's cloud; every command, file edit and repository operation runs on the customer's machine. An outpost is a named queue; `devin worker start --outpost=<name>` turns a machine into a worker that opens an outbound HTTPS connection, claims waiting sessions and executes their tool calls. N workers serve N concurrent sessions. An orchestrator, including an open-source Kubernetes operator, can create a fresh VM or container per session and tear it down afterwards.

Local Hands. A cloud session can ask for a second tool set on the user's own computer, for a local checkout with uncommitted changes, a device on the network or a tool behind a VPN. The session keeps its VM; the two machines share nothing except what an approved tool call copies.

Managed Devins. A coordinator session splits a large task, launches child sessions each in its own VM with its own prompt, playbook, tags and ACU limit, messages them, is woken when one finishes or needs input, and compiles results. The docs say the coordinator resolves conflicts; they do not say how.

Dynamic workflows. The orchestration itself as code: Devin writes a Python script using `agent(prompt, schema=...)`, `pipeline()` and `parallel()`, each agent call returns structured output shaped by a JSON Schema, and every call is recorded against a run ID so an interrupted run replays finished calls and reruns only unfinished ones.

## Context strategy

Devin's context comes from four places with different lifetimes. The snapshot is context in the broadest sense: a session that boots with dependencies installed and the right test command in `knowledge` does not spend turns discovering them, which is why the docs call environment configuration the single highest-leverage thing a customer can do. Organisation instructions arrive by trigger or by pinning, and now through Skills. The task prompt and any playbook come next. Everything else the agent finds by searching.

Cognition's own writing explains why search matters. Its October 2025 SWE-grep post reports, as its own measurement, that trajectories in Windsurf and Devin often spent over 60% of their first turn just retrieving context, and introduces models trained with reinforcement learning to issue up to 8 parallel tool calls per turn over at most 4 turns. The post lists Devin as a place the models will be deployed after validation; whether Devin uses them today is not documented.

Cognition's June 2025 post argues for single-threaded agents whose context is continuous, extended on long tasks by a model dedicated to compressing history into key decisions, and says Cognition has fine-tuned smaller models for that. It reads as a statement of design preference. Managed Devins and dynamic workflows split work across sessions anyway, and the workflow docs draw the boundary in the same place the post does: use a plain session when the work is tightly coupled through shared state, and fan out when units are independent.

## Tools and permission model

In the cloud, the VM is the sandbox and the permission model is mostly about what the session can reach: the repositories granted through the Git integration, secrets and environment variables set in the environment configuration, and whatever the network allows.

The local paths are where per-call approval appears. Local Hands requests are single-use and expire after 10 minutes; connecting is the approval for the connection, and each tool call then needs its own approval unless the user turns on bypass. Calls touching credential files and destructive commands always ask. Connecting a machine makes the session private, so nobody else in the organisation can steer a session that can run commands on that computer, and sessions with no user to approve (scheduled sessions, automations, service-user API sessions) cannot request a machine at all.

The Devin CLI has five modes. Normal auto-approves reads and prompts for edits and shell commands; Accept Edits auto-approves edits in the workspace; Smart lets a fast model auto-run actions it judges clearly safe; Bypass approves everything; Autonomous auto-approves shell and network calls because an OS-level sandbox enforces what they can touch, and still prompts for direct file edits, which run outside it. Organisation deny and ask rules hold in every mode. The sandbox fails closed: if it cannot start, the CLI refuses to run, and it is not supported on Windows.

Outposts move execution, not inference. Tool output from a worker's machine still goes to the agent loop in Cognition's cloud. The docs advise granting passwordless `sudo` only when the machine is dedicated to Devin and recycled after each session.

Fan-out has its own approvals. Child sessions launch without asking by default, and so do workflow runs; both have a setting to require approval first.

## Cost and latency

Usage is metered in ACUs for enterprise customers and in plan quota plus credits for self-serve, and accrues from the number and complexity of actions plus VM time, which the docs describe as typically a small fraction. Windows sessions cost about 9% more than Linux; macOS currently costs the same, labelled promotional pricing. A session does not consume usage beyond keeping the VM alive while waiting for the user, waiting for tests, or cloning, and it sleeps after 30 minutes idle (5 minutes for Lite and API-created sessions), costing nothing while asleep. Coordinators can cap each child's ACUs.

Cognition does not publish an exchange rate between ACUs and tokens or wall-clock time, so a cost model for a fan-out has to come from a pilot: run a few child sessions, read their ACU consumption from the coordinator, and multiply.

The docs give start-up speed as one reason snapshots exist: a session boots into a configured environment instead of installing everything first. Cognition publishes no start-up or task-duration figures.

## Failure modes

Snapshot drift. Maintenance commands are surfaced, not run, at session start. A session that pulls a newer branch than the snapshot was built from may run against stale dependencies unless the agent chooses to re-run them, and anything a session installs is gone at the next boot.

Fan-out cost before value. Auto-approved child sessions and workflow runs mean a single prompt can launch many VMs. The docs' guidance (roughly five or more independent units for a workflow; a codemod or linter for purely mechanical changes) is the cost control, and it is advice, not enforcement.

Semantic conflicts between children. Each child works from the same snapshot and its own prompt. Cognition's own Flappy Bird example is the failure: two pieces of work that are each reasonable and do not fit together. The coordinator's conflict resolution is undocumented, so a review step that sees all children's diffs together is the customer's to add.

Data movement on hybrid setups. With Local Hands or an outpost, files move between machines only through tool calls, and tool output reaches the cloud agent loop. A team that adopts outposts for data residency needs to account for the second half of that sentence.

## What is not public

Cognition does not publish which models Devin uses or how it mixes them, the structure of the agent loop (how planning, retrieval and editing are split across calls), or the virtualisation technology behind the cloud VMs and their isolation guarantees. It does not say how a coordinator resolves conflicts between managed Devins, whether SWE-grep or a context-compression model runs inside Devin today, or how an ACU maps to tokens or time. The two blog posts describe design choices and measurements on Cognition's own data; they are not documentation of the product's internals, and nothing here should be read as more than that.
