## The problem the post took on

One agent session does one thing at a time. Nicholas Carlini's February 2026 post on Anthropic's engineering blog describes what happens when you remove that limit and the human operator at the same time: 16 instances of Claude Opus 4.6, each in a loop that starts a new Claude Code session the moment the last one exits, building a C compiler in Rust from scratch with no internet access and no dependencies beyond the Rust standard library. The post presents the project as a capability benchmark the author has run across the Claude 4 series, and the harness as a bare-bones research prototype.

Two reasons are given for running in parallel. Debugging several issues at once is faster than one at a time, and parallelism allows specialisation: while most agents work on the problem itself, others maintain documentation, watch code quality or take specialised sub-tasks. The question for an engineer is what coordinates 16 writers to one codebase when no agent is in charge.

## The mechanism, in engineering terms

The infrastructure is a bare git repository mounted into one Docker container per agent at `/upstream`. Each agent clones to its own `/workspace`, works there, and pushes back. The outer loop is a `while true` shell script that runs `claude --dangerously-skip-permissions -p` with a prompt file and logs each run under the current commit hash; the post's advice is to run it in a container, not on your machine.

Task claiming is a lock file. An agent takes a task by committing a text file under `current_tasks/`, for example `current_tasks/parse_if_statement.txt`. If two agents claim the same task, git's synchronisation forces the second to pick another. When the work is done the agent pulls, merges the others' changes, pushes, and deletes its lock. Merge conflicts are frequent, and the agents resolve them.

The primitive underneath is git's push rule: a push to a branch succeeds only if it fast-forwards the remote ref from what the pusher last fetched. That makes `git push` a compare-and-swap on the branch head, and the lock file is optimistic concurrency built on it: write locally, publish, and find out on publish whether someone else got there first. Two consequences follow from the post's own description. A claim protects anything only from the moment it is pushed, not from the moment it is written. And nothing in the scheme expires a lock, so a lock held by a session that died stays until some agent decides to remove it.

There is no orchestration agent and no other channel between agents. Each picks what the post calls the "next most obvious" problem. Stuck agents often kept a running document of failed approaches and remaining tasks. Specialised roles were assigned by prompt: one agent coalesced duplicate code, one improved the compiler's own performance, one improved the efficiency of the generated code, one critiqued the design from a Rust developer's point of view and restructured it, and one maintained documentation.

Most of the author's effort went into the test harness rather than the loop, because with nobody watching, the verifier is the specification. Test output was designed for a reader with a context window: a few lines printed, details logged to files, failures written as `ERROR` and the reason on one line so `grep` finds them, summary statistics precomputed. Because the model has no sense of elapsed time, the harness prints progress rarely and has a default `--fast` mode that runs a 1% or 10% random sample of tests, deterministic per agent and different across machines, so each agent can identify its own regressions while the fleet still covers every test.

## The key numbers

Over nearly 2,000 Claude Code sessions across two weeks, Opus 4.6 consumed 2 billion input tokens and generated 140 million output tokens, for a total cost just under $20,000. The result is a 100,000-line compiler that builds a bootable Linux 6.9 on x86, ARM and RISC-V, compiles QEMU, FFmpeg, SQLite, Postgres and Redis, and passes 99% of most compiler test suites including the GCC torture tests, by the author's report.

The token split is worth computing: 2,000,000,000 / 140,000,000 is about 14 input tokens per output token. Agents spent most of their tokens reading code, tests and logs, which is why the post's test-output rules exist.

## Where the scheme stopped working

Parallelism was trivial while the test suite had many distinct failures: each agent took a different failing test, and once the suite reached 99%, each took a different small open-source project to compile. It broke on the Linux kernel. Compiling the kernel is one task, so every agent hit the same bug, fixed it, and overwrote the others' changes. Sixteen agents behaved like one agent with fifteen conflicting copies.

The fix was in the verifier, not the coordination. A new harness compiled most of the kernel with GCC, a known-good compiler, and a random subset of files with Claude's compiler. If the kernel worked, the bug was not in that subset; if it broke, recompiling some of those files with GCC narrowed it further. That turned one monolithic signal into many per-file signals, each agent could chase a different file, and delta debugging later found pairs of files that failed together but passed alone.

This is the most transferable result in the post. The lock-file scheme distributes work exactly as well as the verifier decomposes it. When the verifier emits one bit for the whole system, any number of agents collapses to one.

Other limits the post reports: near the end, new features and fixes often broke existing behaviour, and the author added a CI pipeline with stricter enforcement late in the project. The compiler cannot generate 16-bit real-mode x86 within the 32k code limit Linux enforces (its output was over 60kb) and calls GCC for that phase; the demo used GCC's assembler and linker; and the generated code is less efficient than GCC's with all optimisations disabled.

## Three other ways to coordinate

Planned fan-out into isolated checkouts. Claude Code's best-practices page (checked 2026-10-28) gives each piece of parallel work its own git worktree: `claude -w feature-auth` starts a session in a new one, and `/batch` splits one large mechanical change into 5 to 30 units, shows the plan, runs each unit in its own worktree and opens a PR per unit. From a shell the same pattern is a loop over files with `claude --bare -p`, a pre-approved tool list, `--permission-mode dontAsk` and `--max-turns 20`. Here the plan is the coordination: units are made independent up front, and conflicts surface at PR review instead of at push time. A worktree is a fresh checkout, so gitignored files and installed dependencies are missing unless listed in `.worktreeinclude` or installed by the session; at many units, setup time per worktree becomes part of the cost.

A single thread. Cognition's June 2025 post argues against splitting a task across agents at all. Its two principles are to share context as full agent traces, not just messages, and that actions carry implicit decisions, so agents acting on different unstated assumptions produce results that do not fit together. Its example splits a Flappy Bird clone into background and bird for two subagents; one builds a Super Mario style background and the other a bird that matches neither, and sharing the original task with both does not fix it. The recommendation is one linear agent, extended for long tasks with a separate model that compresses history into key decisions. The post also describes Claude Code's subagents as of June 2025 as not running in parallel with the main agent and mostly answering questions; Claude Code's best-practices page (checked 2026-10-28) says the subagents it starts run in the background by default, so date that observation.

An orchestrator with workers. Anthropic's research system uses a lead agent that spawns subagents. On Anthropic's internal research eval, Opus 4 leading Sonnet 4 subagents outperformed single-agent Opus 4 by 90.2%, at a cost: agents use about four times the tokens of chat, and multi-agent systems about fifteen times. The lead waits for each batch of subagents, which the post names as a bottleneck. Devin's dynamic workflows go one step further and make the orchestrator a deterministic Python script rather than an agent: every agent call is recorded, so an interrupted run replays completed results and reruns only unfinished work.

## What changed in practice

The C compiler post and Cognition's post look like opposite positions and are mostly about different conflict types. The compiler's conflicts were mechanical: two agents claiming one task show up as a rejected push, two edits to one function show up as a merge conflict, a broken feature shows up as a failing test. Cognition's conflicts were semantic: two consistent pieces of work that disagree on style or interpretation pass every check and still do not fit. Parallel agents with no orchestrator are safe where every conflict that matters is detected by a mechanism, and unsafe where the decisive conflicts are unstated decisions.

That reading explains what shipped since. Worktrees became the default isolation unit in Claude Code, with one PR per unit, so each unit's conflicts surface in a review queue a human already runs. OpenAI's harness team made its app bootable per worktree, each with its own observability stack, so an agent's verification does not depend on anyone else's. Devin moved orchestration into code that can be read and resumed. Each moves coordination toward mechanisms that fail loudly.

## When this is wrong

A C compiler is an unusually good target for parallel agents: large public test suites, a known-good reference implementation to compare against, and outputs that are either correct or not. Most product work has none of those, and the post's own success came only after the author built verifiers for each new phase. Read the result as a statement about what is possible with an excellent oracle, not about parallel agents in general.

It is also one project, run by one researcher who calls the harness a research prototype and the run very expensive. The quality limits are part of the result: regressions late in the project, generated code slower than GCC without optimisation, and the author's own unease about deploying code no human has verified.

Cognition's post predates most of the tooling discussed here, and both its examples and its recommendation are about agents sharing one deliverable. Independent units of a migration, each verified on its own, are a case it does not address. The 90.2% research-system figure is from Anthropic's internal eval of breadth-first research, where subtasks are naturally independent; it says little about coding, and the same post notes that most coding tasks involve fewer truly parallelizable tasks than research.
