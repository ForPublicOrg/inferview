## What it is and who runs it

This is the harness Anthropic described in November 2025 for getting a coding agent to build a full application across many context windows: in the post's example, a clone of claude.ai, built by Claude Opus 4.5 running in the Claude Agent SDK. It is a research write-up, not a product, and Anthropic published a companion implementation in its `claude-quickstarts` repository under `autonomous-coding`. This teardown covers both, and says which facts come from which. The lesson on the long-running harness in this module covers the design decisions; this page covers the system as published.

The post's footnote frames the architecture precisely. The initializer and the coding agent are called separate agents only because their first user prompts differ; the system prompt, the tools and the harness are the same.

App spec. The input. The post's example is a one-line prompt; the quickstart reads a specification file, `app_spec.txt`, and copies it into the generated project.

Initializer session. The first context window runs with a prompt that asks the model to expand the spec into a complete list of end-to-end features, write a script that starts the development server, start a progress log, and make an initial commit showing the files added. The post cites Anthropic's prompting guide, whose section on work across several context windows recommends a different prompt for the very first window, tests kept in a structured file, and an `init.sh` for starting servers and running checks.

Feature list. For the claude.ai clone, over 200 features; the quickstart defaults to 200 and its README suggests 20 to 50 for a faster demo. Each entry has a category, a description, a list of steps a user would take, and a `passes` flag that starts false. The post's example entry is "New chat button creates a fresh conversation" with five steps. Coding sessions are told to change only `passes`, in deliberately strong wording, and the format is JSON because in Anthropic's experiments the model was less likely to inappropriately change or overwrite JSON than Markdown.

Progress file. `claude-progress.txt`, a plain-text log of what each session did, read at the start of the next.

init.sh. Starts the development server. Its purpose in the post's failure table is to stop every session spending time working out how to run the app.

Git repository. The record of work and the undo mechanism. Each session ends with a commit with a descriptive message, and the post notes this let the model revert bad changes and recover working states.

Session loop. Each coding session starts with a fresh context. In the quickstart the loop continues automatically after a 3-second delay, runs until stopped unless `--max-iterations` is set, and resumes from the project directory when rerun after Ctrl+C.

Coding session. One feature per session. Within a session the Agent SDK's own context management, including compaction, applies; across sessions only the files and git carry over.

End-to-end check. Two uses. At the start, the session starts the server and exercises the basics (for the clone: open a new chat, send a message, get a response) to catch a broken state before adding to it. After implementing, it tests the feature through browser automation as a user would. The post used the Puppeteer MCP server.

Security hook. In the quickstart, not described in the post: Bash commands run in an OS-level sandbox, file operations are limited to the project directory, and a hook blocks any command outside an allowlist (`ls`, `cat`, `head`, `tail`, `wc`, `grep`, `npm`, `node`, `git`, `ps`, `lsof`, `sleep`, and `pkill` restricted to development processes).

## Context strategy

The strategy is to make each session's opening steps reconstruct the project's state from files, rather than to carry state in the context window. The post's diagnosis is that compaction did not always pass perfectly clear instructions to the next agent, so the harness writes those instructions down in a form the next agent reads directly. The orientation sequence is mostly bounded: the feature list has a fixed number of entries and `git log --oneline -20` returns twenty lines. The progress file is the unbounded part, and nothing in the post or the quickstart README describes rotating it.

The post also claims a token saving: because `init.sh` and the end-to-end routine are written once, sessions do not spend tokens working out how to run and test the app.

## Tools and permission model

The post names three tool families: the file and shell tools of the Agent SDK, git, and the Puppeteer MCP server for browser automation. Its permission story lives in the quickstart: an OS-level sandbox around Bash, file operations confined to the project directory, and a hook that rejects commands outside the allowlist, with blocked commands reported as "Command blocked by security hook". Adding a command means editing `ALLOWED_COMMANDS` in `security.py`.

The rules about the feature list are not part of that enforcement. The prompt asks the agent to change only `passes`; no hook checks it.

## Cost and latency

The post reports no token counts, costs, session counts or wall-clock times for the claude.ai clone. The quickstart README gives rough expectations for its own defaults: the initializer takes several minutes and may appear to hang while it writes 200 features; each coding session takes 5 to 15 minutes; a full application of 200 features takes many hours across sessions.

## Failure modes

The post's own table lists four failures and the fix on each side of the harness. The agent declares the project done too early, answered by the feature list and choosing one feature per session. It leaves bugs or undocumented progress, answered by the git repository, the progress file, a smoke test at the start and a commit and update at the end. It marks features done prematurely, answered by self-verification before setting `passes`. It wastes time working out how to run the app, answered by `init.sh`.

Two failures remained. Without explicit prompting, Claude tested with unit tests or `curl` and marked features complete that did not work end to end; prompting it to use browser automation and to test as a human user would fixed much of this. And the tooling cannot see some bugs: browser-native alert modals are invisible through the Puppeteer MCP, and features relying on them were buggier.

A smaller one is visible in the post itself. Its transcript reads the feature list early in the session and later says it will review "the tests.json file". Anthropic's prompting guide, which the post cites, uses `tests.json` as its example name for the same structured test file, so the likeliest explanation is a prompt or example carried over from the guide. Either way it is the drift a harness has to guard against when the same artefact is named in several prompts and documents.

## What is not public

The post does not report a success rate across projects, how many sessions or tokens the claude.ai clone took, its cost, how long it ran, or how many of the 200-plus features ended up passing. It does not say how often coding sessions edited the feature list beyond `passes` despite the instruction, which is the measurement that would show whether the JSON choice and the wording were enough. The quickstart's prompts are published, but neither the post nor the README says whether they are the prompts used for the post's runs, and the quickstart's default model differs from the post's. Finally, the post leaves open whether one general coding agent or specialised testing, QA and clean-up agents would do better, and whether the approach carries over from web apps to other long-running work.

## In the room

<Callout kind="interview" label="Interview question">
**"Scenario: a team ran the quickstart pattern for a week on an internal admin app. The feature list shows 180 of 200 passing; manual QA finds about 40 of those 180 broken. You can make one change to the harness before the next week-long run, and the run's token budget cannot grow by more than a fifth. What do you change?"**
</Callout>

<Depth>
<Fragment slot="short">
<p>Take the `passes` flag away from the coding agent. The harness, not the agent, runs each feature's listed steps through the browser after the session commits, and sets the flag only if they pass. That attacks the measured problem, false passes, directly. One scripted end-to-end run per feature is likely cheaper than a coding session, which is why it may fit the 20% headroom; measure it on ten features before the run.</p>
</Fragment>
<Fragment slot="long">
<p>First classify the 40. If most fail on things the browser tooling cannot see (native dialogs, downloads, timing), a harness-run check will pass them too, and the right change is to the steps or the tooling, not to who sets the flag. If most fail on behaviour the steps do cover, the agent is certifying work it did not test properly, and independent verification fixes it.</p>
<p>Budget it: a harness-run check is a scripted browser pass with no model in the loop if the steps are concrete enough, or a short model-driven session if they are not. Measure the cost on ten features. If it exceeds the 20% allowance, verify only features touched by the session plus a fixed smoke set, and run the full list nightly.</p>
<p>Also re-baseline: reset the 40 to failing, so the next run starts from the truth.</p>
<p>What you give up: features whose steps are ambiguous will now fail the harness check and sit at failing; that list goes to a human, and the risk note says the count is expected to rise before it falls.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li>The harness check costs 35% more, not 20%. Which features do you stop verifying every session, and what risk do you accept in writing?</li>
<li>Half of the 40 failures turn out to be wrong steps written by the initializer. Who is allowed to edit the list now, and through what path?</li>
<li>What result from the next run would make you hand the flag back to the agent?</li>
</ul>
