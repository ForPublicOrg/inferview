## State that outlives the context window

A long-running coding agent is a sequence of sessions, each starting with an empty context window. Whatever the next session needs to know has to be on disk before the current one ends, and whatever is on disk can be rewritten by the same model that is supposed to obey it. The harness design question is therefore a storage question with an unusual threat model: which artefacts persist, in what format, and which writer may change which field.

Anthropic's November 2025 post on long-running harnesses is the clearest public account. With Claude Opus 4.5 running in the Claude Agent SDK across many context windows and a one-line prompt to build a clone of claude.ai, compaction alone did not get to a working application. The post names two failure patterns. Early in a project the agent tried to build everything at once, ran out of context mid-implementation and left the next session a half-built, undocumented feature to reverse-engineer. Later in a project a fresh session looked around, saw a lot of code, and declared the job done.

Both are state failures, not reasoning failures. The first is a missing write-ahead record: work happened that the next reader cannot see. The second is a missing definition of done: the reader has no list to check the code against, so it judges completion from appearances.

## The artefacts and their writers

The fix splits the run into two prompts over the same harness. The first session, the initializer, runs once and lays down the state; every later session, the coding agent, reads that state, does one unit of work and writes it back. The post's footnote is explicit that these are "separate agents" only in the sense of different first user prompts; the system prompt, tools and harness are identical.

| Artefact | Written by | Read by | Mutation rule in the post | How the rule is held |
|---|---|---|---|---|
| Feature list (JSON) | initializer, once | every session | coding agents change only the `passes` field | prompt wording and the JSON format |
| `claude-progress.txt` | every session, at the end | every session, at the start | summarise what was done | prompt |
| `init.sh` | initializer | every session | starts the dev server | prompt |
| git history | every session | `git log --oneline -20` at the start | descriptive commit per unit of work; revert bad changes | prompt |

For the claude.ai clone the feature list held over 200 end-to-end features, all initially marked failing, each with a category, a description, a list of steps a user would take, and a `passes` boolean. The prompt forbids removing or editing tests in strong language, and the team chose JSON after experimenting because the model was less likely to inappropriately change or overwrite a JSON file than a Markdown one.

That last finding shows where the enforcement lives. Every rule in the table above is held by the prompt and by a format the model happens to respect more. None is held by the harness. A database analogy fits up to a point: the feature list is the table of record, `passes` is the only column the application should update, and the protection is a comment in the schema asking callers to behave.

## The session protocol

Each coding session runs the same opening, which the post shows as a transcript: `pwd`, read the progress file, read the feature list, `git log --oneline -20`, start the dev server through `init.sh`, then exercise the basics end to end (for the clone, open a new chat, send a message, see a response) before touching anything new. Only then does it pick the highest-priority failing feature, implement it, test it as a user would through browser automation, commit, and append to the progress file.

Running the basic end-to-end check before new work is recovery, not testing. A previous session may have ended with the app broken; building a feature on top makes the breakage harder to find. The check bounds how far a bad session can propagate.

One feature per session bounds the blast radius of running out of context. If the window fills mid-feature, at most one feature is half-done, and the last commit is a known-good state to revert to. The post calls this incremental approach critical to addressing the tendency to do too much at once.

Verification is where the format alone failed. Without explicit prompting, Claude tested with unit tests or `curl` against the dev server and marked features passing that did not work end to end. Prompting it to use browser automation (the Puppeteer MCP server) and to test as a human user would fixed most of that. It did not fix bugs the tooling cannot observe: browser-native alert modals are invisible through the Puppeteer MCP, and features that relied on them stayed buggier.

## Holding the rules in the harness

The rule "only `passes` may change" is cheap to check mechanically. A pre-commit hook or a harness step between sessions can diff the file against the last commit and reject anything else. The policy choices are yours: the version below allows any number of features to go from passing to failing (an honest regression report) and at most one to go from failing to passing per commit, which also enforces one feature per session.

```python
import json


def allowed_change(old, new):
    """Violations of the feature-list contract; an empty list means the commit may proceed."""
    problems = []
    if len(old) != len(new):
        problems.append(f"feature count changed from {len(old)} to {len(new)}")
    for i, (a, b) in enumerate(zip(old, new)):
        if {k: v for k, v in a.items() if k != "passes"} != {k: v for k, v in b.items() if k != "passes"}:
            problems.append(f"feature {i}: fields other than 'passes' changed")
    flips = sum(1 for a, b in zip(old, new) if not a["passes"] and b["passes"])
    if flips > 1:
        problems.append(f"{flips} features marked passing in one commit; one per session")
    return problems


old = [
    {"category": "functional", "description": "New chat button creates a fresh conversation",
     "steps": ["Click New Chat"], "passes": False},
    {"category": "functional", "description": "Theme toggle persists across reloads",
     "steps": ["Toggle theme", "Reload"], "passes": True},
]
new = json.loads(json.dumps(old))
new[0]["passes"] = True
print(allowed_change(old, new))   # []
new[1]["steps"] = ["Toggle theme"]
print(allowed_change(old, new))   # ["feature 1: fields other than 'passes' changed"]
```

The check moves one rule from the model-decided column to the deterministic column, at the cost of a false block whenever the initializer wrote a wrong step and a later session legitimately needs to fix it. That cost is real: the initializer writes 200 features from a short spec in one sitting, and some will be wrong. The usual answer is a separate, rarer path for spec changes (a human edit, or a dedicated session whose only permission is editing the list) rather than letting every coding session do it.

The harder question is who may write `passes = true`. In the post the coding agent marks its own work after testing. The alternative is for the harness to run each feature's steps itself, through the same browser tooling, and to own the flag. That buys independence from the agent that wrote the code and costs one extra end-to-end run per feature plus a verifier that is good enough to trust. The C compiler project made the same point from the other side: when the agents are unattended, the author found the verifier had to be nearly perfect, "otherwise Claude will solve the wrong problem."

## What grows without bound

Three of the four artefacts are bounded by construction: the feature list has a fixed number of entries, `init.sh` is small, and `git log --oneline -20` reads twenty lines however long the history is. The progress file is the exception. Appended every session and read in full at the start of the next, it grows linearly, and the total read cost grows with the square of the session count.

A bounded read (the last N entries plus a rolling summary rewritten every so often) caps the per-session cost at a constant. OpenAI's harness team ran into the same structure from a different direction. Their report, about a product built almost entirely by Codex, describes single Codex runs working on one task for upwards of six hours. Their persistent state is the repository: execution plans with progress and decision logs, checked in and split into active and completed, a technical-debt tracker, and a roughly 100-line AGENTS.md that serves as a map into a structured `docs/` tree. Freshness is enforced by linters and CI jobs that check the knowledge base is cross-linked and current, and a recurring doc-gardening agent opens fix-up pull requests for stale documents. That is a mechanical answer to the rot problem the progress file has.

The C compiler build, with no human in the loop, asked agents to maintain READMEs and progress files updated frequently with the current status, and observed agents keeping a running document of failed approaches when stuck on a bug. A list of what was tried and failed is worth persisting on purpose: it is the one piece of state a fresh session cannot reconstruct from the code.

## The design, stated as decisions

A long-running harness answers five questions in writing before the first session runs.

What is the definition of done, and who wrote it? A list of end-to-end checks, written once, in a format the model treats as data. Changes to it go through a different path from the work.

What does a session read first, and is each read bounded? Progress tail, recent commits, the list, then a smoke test of the running system.

What is the unit of work? One item from the list, small enough that running out of context mid-item loses at most that item.

Who sets an item to done? The working agent after its own test (cheap, correlated with its own mistakes) or the harness after an independent run (costlier, independent).

Which rules does the harness enforce rather than request? The ones that are cheap to check and expensive to violate: the list's shape, one transition per commit, a commit at the end of every session, the allowed commands. The quickstart that accompanies the post already enforces one of these: a security hook blocks any Bash command outside an allowlist.

<Fragment slot="long">
<p>The Monday constraint (all or nothing per endpoint) is a transaction boundary, so the unit of work is one endpoint and the commit is the commit point. A session that ends without passing tests has its changes reset by the harness, not left for the next session to guess at.</p>
<p>The budget constraint fights verification. Running the full suite after every endpoint is the safe choice; the cheaper one is that endpoint's contract tests plus a fixed smoke subset, with the full suite every twenty endpoints and a bisect on failure. The C compiler's deterministic per-agent sample is the same trade. The risk note records which was chosen and how a regression found late is attributed.</p>
<p>Formats: the list as JSON with a schema the hook validates; progress as an append-only file read by its tail; failed approaches as a separate file per endpoint, because that is the one thing a fresh session cannot recover from the code. Git holds everything else.</p>
<p>What you give up: the list is frozen once the weekend starts, so an endpoint whose contract tests are wrong will be marked failing and left untouched; the risk note says how many such endpoints are acceptable and who triages them on Monday.</p>

## When this is wrong

The evidence is one demo per vendor. Anthropic's post reports what worked on a full-stack web app and what still failed, but no success rate across projects, no session counts and no token totals. The accompanying quickstart defaults to Claude Sonnet 4.5 while the post describes Opus 4.5, so its timings (coding sessions of 5 to 15 minutes, many hours for all 200 features) describe a different model from the one in the text. OpenAI's report says its results depend heavily on that repository's structure and tooling and should not be assumed to generalize without similar investment.

The design assumes the work decomposes into independent, end-to-end-testable items. A web app's features mostly do. A data migration, a performance project or a refactor whose value is visible only when every piece lands does not, and a list of 200 items that each pass can still add up to a system that does not.

Harness choices tied to one model's behaviour go stale. Anthropic's Managed Agents post describes adding context resets because Claude Sonnet 4.5 wrapped up tasks early as it sensed the context limit, then finding on Claude Opus 4.5 that the behaviour was gone and the resets were dead weight. The JSON-over-Markdown finding is the same kind of fact: measured on one model, not a property of formats. Re-measure it when the model changes, and prefer mechanical checks that hold whatever the model does.

Finally, self-verification has blind spots that more prompting does not close. The alert-modal gap is a tooling limit; a feature marked passing through tooling that cannot see the bug is a false positive the harness cannot detect from inside.
