## What it is and who runs it

In February 2026 OpenAI published an engineering account, by Ryan Lopopolo, of a team that built and shipped an internal beta of a software product with no manually written code. Every line, from application logic and tests to CI configuration, documentation, observability, dashboards and internal tools, was written by Codex. The product has internal daily users and external alpha testers.

There is no single harness binary to tear down. The harness is the repository: the files the agent reads first, the checks that reject its mistakes, the environment it can start and observe, and the recurring agents that clean up after it. Every figure below is OpenAI's own and unaudited, and the post says plainly that the behaviour depends heavily on this repository's structure and tooling and should not be assumed to generalise without similar investment.

AGENTS.md as a map. The team tried one large instruction file first and lists why it failed: it crowded out the task and the code, everything marked important stopped guiding anything, it went stale with no way to tell which rules still held, and a single blob could not be checked mechanically for coverage, freshness, ownership or cross-links. The replacement is a file of roughly 100 lines injected into context, used as a table of contents pointing elsewhere.

docs/ as the system of record. A structured tree holds design documents with an index, verification status and a set of core beliefs; execution plans split into active and completed, with progress and decision logs; a technical-debt tracker; product specs; generated references such as a database schema; reference material for third-party tools in `llms.txt` form; and top-level documents for design, frontend, plans, product sense, quality, reliability and security. A quality document grades each product domain and architectural layer over time. Small changes use lightweight ephemeral plans; complex work gets a checked-in execution plan.

Codex run. An engineer describes a task and lets the agent open a pull request. Codex uses `gh`, local scripts and skills embedded in the repository to gather context itself. OpenAI reports regularly seeing single runs work on one task for upwards of six hours, often overnight.

App per worktree. The application boots per git worktree, so each change gets its own running instance that the agent can launch and drive.

Observability per worktree. Each worktree gets an ephemeral local stack of logs, metrics and traces, torn down when the task completes. Agents query logs with LogQL and metrics with PromQL, which makes prompts such as "ensure service startup completes in under 800ms" checkable by the agent itself; that figure is the post's example of a prompt, not a measured result.

Chrome DevTools Protocol. Wired into the agent runtime, with skills for DOM snapshots, screenshots and navigation, so the agent can reproduce a UI bug, validate a fix and record before-and-after videos.

Custom lints and structural tests. Each business domain is split into fixed layers (types, config, repository, service, runtime and UI, in that order) and code may depend only forward through them; cross-cutting concerns such as auth, connectors, telemetry and feature flags enter through one interface called Providers. Linters, themselves written by Codex, and structural tests enforce the dependency directions, plus taste invariants: structured logging, naming conventions for schemas and types, file size limits and platform reliability requirements. Because the lints are custom, their error messages are written to inject remediation instructions into the agent's context.

Agent reviewers. Codex reviews its own change locally, requests further agent reviews locally and in the cloud, responds to human or agent feedback, and iterates until the agent reviewers are satisfied. Humans may review pull requests but are not required to, and the post says almost all review effort has moved to agent-to-agent review.

Main branch. Few blocking merge gates, short-lived pull requests, and test flakes often handled with follow-up runs rather than blocking. Agents often squash and merge their own pull requests.

Doc-gardening and clean-up agents. A recurring doc-gardening agent finds documentation that no longer matches the code and opens fix-up pull requests. Background Codex tasks scan for deviations from "golden principles" (for example, shared utility packages over hand-rolled helpers, and validating data at boundaries instead of guessing shapes), update quality grades and open targeted refactoring pull requests, most reviewable in under a minute and automerged.

## Context strategy

The governing rule in the post is that anything the agent cannot reach in context while running does not exist for it. Knowledge in Google Docs, chat threads or people's heads is invisible, so the team keeps pushing decisions into the repository: an architectural agreement reached in Slack is, to the agent, as unknown as it would be to a hire who joined three months later.

Delivery is progressive disclosure. The agent starts from the small, stable map and is pointed to deeper documents as the task needs them, rather than receiving everything up front. Freshness is held mechanically: linters and CI jobs check that the knowledge base is current, cross-linked and correctly structured, and the doc-gardening agent repairs drift.

The same rule shapes technology choices. The team favours dependencies the agent can fully reason about inside the repository, and describes "boring" technologies as easier for agents to model because of composability, API stability and representation in training data. In one case it had the agent write its own map-with-concurrency helper rather than adopt a generic library, integrated with its OpenTelemetry instrumentation and fully covered by tests.

## Tools and permission model

The agent uses the team's standard tools directly: `gh`, local scripts, repository skills, the browser through the DevTools Protocol, and the observability stack. Its authority is broad by design. It opens, reviews, responds to and merges pull requests, including its own, and escalates to a human only when judgement is required.

The constraint system is architectural, not permission-based: the layer model and taste invariants are enforced by lints and structural tests that every change must pass. The post describes the approach as enforcing invariants without micromanaging implementations; for example it requires data shapes to be parsed at the boundary but does not prescribe how. The post does not describe sandboxing, network policy, credentials or which actions, if any, need human approval.

## Cost and latency

OpenAI reports about a million lines of code and roughly 1,500 merged pull requests in five months from the first commit in late August 2025, driven by three engineers growing to seven, and an average of 3.5 pull requests per engineer per day, with throughput rising as the team grew. It estimates the product took about a tenth of the time hand-writing would have.

No token counts, compute costs or per-run costs are published. The one time cost given for maintenance is the one the team removed: before encoding golden principles, it spent every Friday, 20% of the week, cleaning up what it calls AI slop by hand.

Latency is traded deliberately. With agent throughput above human attention, the post argues that corrections are cheap and waiting is expensive, hence short-lived PRs and flakes handled by reruns; it adds that the same policy would be irresponsible in a low-throughput environment.

## Failure modes

Pattern replication. Codex copies patterns already in the repository, uneven or suboptimal ones included, so drift accumulates. The response is continuous clean-up rather than periodic rewrites, which the post compares to garbage collection.

Instruction files that rot. The one-big-AGENTS.md failure is a failure mode of any harness that grows instructions by accretion; the fix here is structure plus mechanical freshness checks.

Weak merge gates. Reruns for flakes and agent-approved merges move risk from merge time to production. The post presents this as a trade-off it accepts at its throughput, not as a free win.

Human attention as the bottleneck. As code throughput rose, the limit became human QA capacity, which is why the team invested in making the UI, logs and metrics legible to the agent.

Long-term coherence. The post says the team does not yet know how architectural coherence evolves over years in a fully agent-generated system, or how it will change as models improve.

## What is not public

The product is not named and the code is not published. OpenAI gives no defect, incident, rollback or revert rate, no figures on how often agent reviewers approved changes that later broke, and no share of pull requests that merged without a human reading them. Beyond GPT-5 generating the initial scaffold through Codex CLI, the models used over the five months are not stated, nor are token use or cost. The post does not describe the sandbox, network and credential model, or how the layer linters and structural tests are implemented. The one-tenth estimate is OpenAI's own and its method is not given.

<p>Adopt the parts that make agents cheaper to check, not the parts that remove checks: a short AGENTS.md pointing into versioned docs, custom lints whose messages carry the fix, and an app plus logs per worktree so agents verify their own changes. Refuse agent self-merge and flake reruns on paths that touch production this quarter. Let agents merge only low-risk classes (docs, generated references, clean-up refactors that pass structural tests) and measure revert rate per class against human-merged changes before widening.</p>
</Fragment>
<Fragment slot="long">
<p>OpenAI's setup started from an empty repository with mechanical architecture rules from day one. A six-year-old monorepo has neither, and the post says its autonomy depends on that structure. So the quarter's work is building the checks: pick one domain, write its layer rules as lints with remediation messages, and measure how many agent PRs pass them unaided.</p>
<p>The SRE objection is testable. Define change classes, track revert and incident attribution per class for agent-merged and human-merged changes, and agree the thresholds with the SRE lead before the first agent merge. Widen self-merge class by class when its numbers match the human baseline.</p>
<p>The CTO's deadline is met partially: by quarter end agents merge in the classes the data supports, and the rest have a dated plan.</p>
<p>What you give up: speed in the domains without lints yet, where agent PRs still wait for human review; the risk note names those domains and the review load they create.</p>
