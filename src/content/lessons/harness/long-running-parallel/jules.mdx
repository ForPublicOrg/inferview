## What it is and who runs it

Jules is Google's asynchronous coding agent, run by Google Labs and in Public Beta as of the FAQ checked on 2026-10-28. A user connects GitHub, picks a repository and branch, describes a task and leaves. Jules runs the task in a fresh virtual machine, shows a plan before writing code, and ends with a branch the user can turn into a pull request. A task can also start from a GitHub issue labelled `jules`.

The design is narrower than the other tools in this track, and that is its interest. One task, one short-lived VM, one plan gate, one branch. Everything below comes from Google's Jules documentation; there is no engineering post describing the internals.

Task VM. Each task runs in what the docs call a secure, short-lived virtual machine on Ubuntu Linux, with internet access. The environment page lists the preinstalled toolchain as of its environment check: Python 3.12.11 (3.10.18 through pyenv) with pip, poetry, uv, pytest, ruff, mypy and black; Node.js 22.16.0 by default (18 and 20 through nvm) with npm, yarn, pnpm, eslint and prettier; Bun; Go 1.24.3; OpenJDK 21.0.7 with Maven and Gradle; Rust 1.87.0; GCC 13.3.0, Clang 18.1.3 and CMake; Docker 28.2.2 with Compose; git 2.49.0. Running `. /opt/environment_summary.sh` inside a setup script prints the current list.

Setup script. Per-repository commands entered under Configuration, typically installing dependencies and running lint and tests. The FAQ rules out long-running processes such as dev servers or watch scripts in setup scripts; it asks for discrete install and test commands. Simple repositories work without a script, using hints from `AGENTS.md` or the README.

Snapshot. Run and Snapshot executes the setup script, and on success creates a snapshot of the environment that future tasks from that repository start from. The docs recommend it for environments with long setup times. Run to Validate runs the script so its output can be checked, for example tool versions printed with `node -v`.

AGENTS.md. Jules looks for an `AGENTS.md` at the repository root and uses it to produce more relevant plans and code.

Jules agent. The plan table names the models: Gemini 2.5 Pro on the free plan, and the latest model starting with Gemini 3 Pro on the paid plans.

Plan review. After cloning, VM initialisation and dependency installation, Jules presents a plan: a description of the approach, step-by-step breakdowns, and assumptions or setup steps. The user can comment, ask for revisions, or click approve. Google's review page also says that if the user navigates away, Jules eventually auto-approves the plan on a timer.

Branch and PR. At the end Jules shows a summary with files changed, total runtime and lines added, changed and removed. Create branch pushes the work; the user owns the branch, Jules appears as the commit author, and the PR is opened from GitHub. For an issue-triggered task Jules comments on the issue and links the PR when it is done.

## Context strategy

Context is assembled per task and discarded with the VM. The persistent inputs are the repository itself, `AGENTS.md` at its root, and the snapshot, which carries installed dependencies rather than knowledge. The per-task inputs are the prompt, attached images (only at task creation, not in follow-ups), and whatever the user types into the chat while Jules works. The docs publish nothing about compaction, memory across tasks or retrieval inside a task.

The plan is the main context checkpoint. Because it is shown before any edit, it is the point where a misread task is cheapest to correct: a comment there costs one replan, while the same correction after execution costs a rerun of the task.

## Tools and permission model

The permission model is coarse and sits at the edges of the task rather than per call.

Repository access is granted through the Jules GitHub app, either for all repositories or a chosen set, and changed in GitHub's application settings.

Inside the VM, Jules can run what the toolchain allows, with internet access. The FAQ asks users to treat the VM with the precautions due to any shared compute surface: keep secrets out of the repository, avoid vulnerable dependencies, and be careful with third-party packages and shell commands. It also notes that Jules operates on non-code files as well as code, which is where instructions planted in a repository would enter.

The plan gate is the one approval in the loop, and with auto-approval on a timer it is a soft gate: it stops a task only if someone is watching. There is no per-command approval in the docs.

The output gate is git. Jules does not push until the user clicks Create branch, the user owns the branch, and merging is a normal pull request, so the repository's branch protection and required checks apply.

## Cost and latency

Jules is priced by plan, not per task. The limits page (checked 2026-10-28) sets daily tasks over a rolling 24 hours and concurrent tasks per plan:

| Plan | Daily tasks | Concurrent tasks | Model access |
|---|---|---|---|
| Jules | 15 | 3 | Gemini 2.5 Pro |
| Jules in Pro | 100 | 15 | latest model, starting with Gemini 3 Pro |
| Jules in Ultra | 300 | 60 | priority access to the latest model |

Paid plans come through Google AI subscriptions and, per the same page, are available only for individual Google accounts for now. Google says limits may change.

Latency is the asynchronous kind: the docs expect the user to leave and come back, with browser notifications when a plan is ready or a task finishes. Snapshots exist to cut setup time from every task.

## Failure modes

Setup failures. The FAQ names broken setup scripts and vague prompts as the common causes of failed tasks. Jules retries automatically and, if failures continue, marks the task failed and notifies the user. A snapshot built from a script that later stops matching the repository fails every task until someone reruns Run and Snapshot.

No running services in setup. A repository whose tests need a dev server or a watcher cannot start one from the setup script, per the FAQ. Whether the agent can start one during the task is not stated.

Unattended plans. A plan nobody reads is approved on a timer. For issue-triggered tasks at volume that is the normal path, so the plan gate catches nothing and review moves entirely to the pull request.

Untrusted repository content. A VM with internet access, operating on non-code files as well as code, is exposed to instructions planted in the repository or its dependencies; the FAQ's advice puts that responsibility on the user.

## What is not public

Google does not state the auto-approval delay, only that it exists. It does not publish the VM's lifetime beyond "short-lived", its CPU, memory or disk, or its network egress rules beyond having internet access. It does not say whether a snapshot is tied to a branch as well as a repository, when snapshots are invalidated, or how many times a failed task is retried. Nothing is published about the agent loop: how the plan is generated, which model handles which step on a given plan, whether tests are run automatically before the summary, or how context is managed in a long task. That plans auto-approve is stated on Google's own review page; how and when is not.

## In the room

<Callout kind="interview" label="Interview question">
**"Scenario: your team wants to label up to 30 backlog issues `jules` every evening on the Pro plan and review the pull requests in the morning. Nobody will read plans overnight, the integration tests need a Postgres instance, and the release freeze starts in two weeks. What do you set up, and what do you refuse to automate?"**
</Callout>

<Depth>
<Fragment slot="short">
<p>Accept that overnight plans auto-approve, so all control moves to the pull request: required CI, branch protection, and a reviewer per PR. Make the snapshot carry everything the tests need, and run Postgres from the test command (for example a test fixture that starts the container) rather than the setup script, which cannot hold long-running processes. Restrict labelling to issues with acceptance tests, and keep anything touching migrations or auth out of the overnight batch until the freeze ends.</p>
</Fragment>
<Fragment slot="long">
<p>Thirty tasks fit the Pro plan's 100 a day; at 15 concurrent, two waves cover them if tasks take under a few hours. Morning review is the real limit: thirty PRs a morning is a lot for a small team, so cap the batch by reviewer capacity, not by plan limits.</p>
<p>The Postgres question is the environment risk. Test it with Run to Validate before relying on it: Docker is preinstalled, but whether a container started in the task survives the way the tests need is not documented, so the safer design starts the database inside the test run and tears it down after.</p>
<p>Write the issue filter down: issues must name the files or behaviour and carry a test that fails today, because a vague prompt is one of the two failure causes the docs name.</p>
<p>What you give up: with plans unread, a misunderstood issue costs a full task and a review before anyone notices, instead of one comment on a plan.</p>
</Fragment>
