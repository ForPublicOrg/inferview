## The decision

An agent loop with no limits runs until the model decides it is done. The Agent SDK documents that this is the default: `max_turns` and `max_budget_usd` both default to no limit, which the docs call fine for well-scoped tasks and a risk on open-ended ones. The decision is which stops to put around a run, and the trap is assuming one stop covers the others. Each control below stops one kind of runaway and lets the rest through.

**Turn cap** (`max_turns`, `--max-turns`). Stops a loop that keeps calling tools. A turn is one round trip with tool calls, plus one for the final text-only response; a cap that leaves no room for that last turn ends with `error_max_turns` and no answer. It does not bound cost per turn, so twenty turns over a large context can cost more than a hundred over a small one.

**Dollar cap** (`max_budget_usd`, `--max-budget-usd` with `-p`). Stops spend directly. Claude Code checks the estimate after each response arrives, so the response that crosses the cap completes and counts; spend can exceed the cap by one response plus whatever running subagents spend before they stop. Since v2.1.217 the cap covers subagents: once reached, spawning another fails with `Budget limit reached`. With streaming input the budget accumulates across messages in a conversation and `/clear` resets it.

**Denial fallback** (auto mode). After 3 classifier blocks in a row or 20 in total, interactive auto mode pauses and resumes prompting; the thresholds are not configurable. This stops an agent that keeps attempting blocked actions, but only when a person can answer the prompt. In `-p` mode there is nothing to fall back to: the blocked action does not run, Claude keeps working, and Claude Code does not stop the run unless you pass `--permission-prompt-tool`. Headless, the denial thresholds are not a stop at all.

**Stop-hook block cap.** A `Stop` hook that exits with code 2 sends Claude back to work, which is how a harness enforces "tests pass before done". If the hook blocks eight stops in a row with no tool call between them, Claude Code overrides the next block and ends the turn (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap). This stops the loop where the model has given up and keeps trying to stop. It does not stop the loop where the model keeps editing and the check keeps failing, because each edit is a tool call that resets the count. That loop needs a turn or dollar cap.

**Per-task budget with partial submission.** SWE-agent capped each benchmark instance at $4, roughly 30 to 40 turns, and submitted whatever edits existed when the cap hit. The paper reports that 93.0% of resolved instances were submitted before the budget ran out, against 69.0% of all instances: the cap fell mostly on runs that were failing anyway, and the authors expected a larger budget to add little. The design point is what happens at the cap. SWE-agent turned it into a partial result; the Agent SDK's error results carry no `result` field but do carry `session_id`, so the run can be resumed with a higher limit.

## The inputs that change it

**Is anyone watching?** Attended sessions have a human stop: interrupting, `/clear`, and auto mode's fallback to prompting. Headless runs have only what the configuration enforces. Claude Code's best-practices page reduces the unattended checklist to five questions, one of which is "What stops it?", answered with `--max-turns`, `--max-budget-usd` or a spend limit.

**Who pays, and in what unit?** On an API key the runaway is dollars, and a dollar cap is the direct control. On a subscription the runaway is usage-limit drain, and cache misses are the hidden multiplier. Anthropic's April 2026 postmortem is the example: a change meant to clear old thinking once from sessions idle for over an hour instead cleared it on every turn from March 26 until the fix on April 10, causing cache misses that Anthropic believes drove reports of usage limits draining faster than expected. No per-run cap would have caught that; a fleet-level cache-read ratio would.

**What does a stopped run cost to resume?** Resuming an SDK session restores its context, but a resume after the cache TTL re-reads the whole history at the write price, and a run that stopped mid-edit leaves a working tree to inspect. If resuming is cheap and the task is valuable, set caps tight and resume the stragglers by hand. If resuming means re-reading a large context cold, set caps looser and stop fewer runs.

## Effort is a cost lever that costs quality

Effort reduces tokens per turn and latency, which makes it tempting as a default-level cost control. The postmortem records what happened when Anthropic used it that way. On March 4, 2026, Claude Code's default effort for Sonnet 4.6 and Opus 4.6 changed from high to medium, because some users saw thinking times long enough that the UI appeared frozen. On April 7 it was reverted; Anthropic called the change "the wrong tradeoff" after users said they preferred higher intelligence with the option to lower effort themselves. A separate system-prompt instruction limiting text between tool calls to 25 words and final responses to 100 words, shipped April 16, cost 3% on one evaluation for Opus 4.6 and 4.7 in an ablation and was reverted April 20.

The process commitments that followed are the transferable part: per-model evals for every system prompt change, and soak periods, broader evals and gradual rollouts for any change that could trade against intelligence. A cost lever that changes what the model does is a model change and ships like one. Defaults have moved again since: as of October 2026, Claude Code's best-practices page says Opus 5.5, Sonnet 5.5 and Haiku 5.5 default to medium.

## Worked decision

A scenario, with pilot numbers invented to make the arithmetic concrete. A nightly CI job runs `claude -p` over 200 files to migrate them to a new logger API, on an API key with Opus 5.5, following the loop in Claude Code's best-practices page: `--bare`, `--allowedTools` limited to read, edit and the two git commands, `--permission-mode dontAsk`. A pilot on three files cost $0.40, $0.55 and $1.30 and took 9, 11 and 17 turns.

The choices. `--max-turns 20` gives room above the pilot's worst case and matches the docs' example. `--max-budget-usd 2.00` sits above the pilot's worst case. `dontAsk` instead of auto mode, because headless auto mode's denial thresholds do not stop anything, while `dontAsk` refuses everything outside the allow list up front. No Stop hook: the job's acceptance check is the CI run on the resulting branch, outside the agent.

Then the bound. Per-run caps do not bound the night. Suppose the largest single response the job can produce is a cold request with 150,000 input tokens written at Opus 5.5's $5 per million (a cache miss after a slow tool call) plus 8,000 output tokens at $20 per million.

<p>The largest response costs 150,000 × $5 / 1,000,000 + 8,000 × $20 / 1,000,000 = $0.75 + $0.16 = $0.91. Each run can reach $2.00 and overshoot by $0.91, so the bound is 200 × $2.91 = <b>$582</b>.</p>
<p>The pilot's mean of $0.75 predicts about $150 for the night. The gap between $150 and $582 is what the per-run caps allow, and it is the reason for a fleet cap: the loop sums <code>total_cost_usd</code> from each result and stops launching runs past a nightly budget set from the pilot, for example twice the expected $150.</p>

Runs that end with `error_max_turns` or `error_max_budget_usd` are recorded with their `session_id` and file name and reported as failures, not retried in the same night. Retrying capped runs automatically would undo the caps.

What you give up: some files that would have succeeded at turn 25 are reported as failures, and the fleet cap can stop the job with files untouched. Both show up in the morning report, which is the point.

## What to measure after deciding

The dashboard that shows a runaway before the invoice does is per run and per fleet. Per run: `total_cost_usd`, `num_turns`, the result subtype, the ratio of cache reads to cache writes, classifier denials, and Stop-hook blocks. Use `modelUsage` rather than `usage` for cost, because `usage` covers only the main loop and misses subagents. Per fleet: cost per successful run rather than per run, the distribution of run cost (watch the upper tail, not the mean), the share of runs ending in `error_max_turns` or `error_max_budget_usd`, and spend rate against the expected rate for the time of day.

Two alerts earn their noise. A cache-write share that jumps across many sessions at once means a harness or configuration change broke the prefix, which is the postmortem's failure. And a rising share of capped runs means either the task got harder or the agent got worse; both need a person before the next night's run.

## When this is wrong

The controls are Claude Code and Agent SDK mechanisms at the versions cited, and the thresholds (3 and 20 denials, 8 Stop-hook blocks) are documented defaults that change between releases. Another harness has different stops and different gaps; map each runaway to a control before trusting an equivalent.

The SWE-agent evidence that caps mostly cut failing runs is from a 2024 model on SWE-bench, where the task ends with a submission. On open-ended work there is no submission, and a capped run's partial output may be worth nothing.

A dollar cap is an estimate from the usage the API returns. It does not include costs outside the model bill, such as CI minutes triggered by the agent's pushes or a sandbox's runtime, and those can be the larger runaway.
