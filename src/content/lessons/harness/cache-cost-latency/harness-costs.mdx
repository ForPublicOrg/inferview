## Two models of a harness bill

A harness bill has two useful decompositions, and a proposed change usually moves one term of one of them.

The first is **dollars per agent-hour times agent-hours**. It works when the change alters how long agents run: adding a planner, an evaluator loop, a retry policy, a sprint structure or more parallel workers.

The second is **sessions times tokens per session times price**, with input split into cache writes and cache reads. It works when the change alters what each request carries: a model swap, a compaction policy, a bigger tool set, a cache-breaking feature.

Anthropic has published enough long runs in 2025 and 2026 to calibrate both. Every number below is the vendor's own measurement of a single run unless stated, which bounds what they can support.

## Calibrating dollars per agent-hour

The March 2026 harness-design post compares a solo agent with a three-agent harness (planner, generator, evaluator) on one prompt, a 2D retro game maker, on Opus 4.5. The solo run took 20 minutes and cost $9. The full harness took 6 hours and cost $200, which the post calls over 20 times more expensive.

Divide each by its duration. The solo run burned $27 per hour; the full harness, $33 per hour. The cost ratio of 22 is mostly the duration ratio of 18. The harness did not make each hour much more expensive; it made the agents work 18 times longer, and the output was much better for it.

The same post's second harness, on Opus 4.6, built a digital audio workstation in the browser and published a cost per phase:

| Build, round 1 | 2 hr 7 min | $71.08 |

| Build, round 3 | 10.9 min | $5.88 |

The table answers a question that matters when someone proposes an evaluator: what does the evaluator cost? Its own three QA rounds total $10.39, 8.3% of the run. But the first two QA rounds each sent the generator a list of missing or stubbed features, and the build rounds that followed, 2 and 3, cost $42.77, 34% of the run. The evaluator's bill is mostly the rework it orders. That is the intended effect, and it is also the term to estimate: price an evaluator by its expected number of rejected rounds times the length of a fix round, not by its own tokens.

The post also shows harness components becoming dead weight as models improve. Context resets were needed for Sonnet 4.5 and dropped with Opus 4.5; the sprint structure was dropped with Opus 4.6, which ran the build coherently for over two hours; the evaluator moved from grading each sprint to a pass at the end of the run. Each removal shortens the run, and with a steady burn rate that is a proportional cost cut.

## Calibrating dollars per session

The February 2026 C compiler post is the largest published run. Sixteen Opus 4.6 agents, each in its own container pulling from and pushing to a shared bare git repository, ran nearly 2,000 Claude Code sessions across two weeks. They consumed 2 billion input tokens and generated 140 million output tokens, for a total just under $20,000, and produced a 100,000-line Rust compiler that builds Linux 6.9 on x86, ARM and RISC-V.

Per session that is about $10, 1 million input tokens and 70,000 output tokens. Pricing those tokens at Opus 4.6 list prices is instructive because it does not reconcile:

```python
def by_hours(agent_hours, burn_per_hour):
    """Use when the change alters how long agents work. burn: $ per agent-hour from your own runs."""
    return agent_hours * burn_per_hour


def by_tokens(sessions, input_m, output_m, cached_share, price):
    """Use when the change alters what each session carries. Tokens in millions, price in $ per million."""
    written = input_m * (1 - cached_share) * price["write"]
    reread = input_m * cached_share * price["read"]
    return sessions * (written + reread + output_m * price["out"])


OPUS_46 = {"write": 6.25, "read": 0.50, "out": 25.00}   # 5-minute writes, list price
OPUS_55 = {"write": 5.00, "read": 0.20, "out": 20.00}

print(round(by_hours(8, 124.70 / 3.83)))                  # an 8-hour build at the DAW burn rate: 260
for share in (0.0, 0.9):
    print(share, round(by_tokens(2000, 1.0, 0.07, share, OPUS_46)),
          round(by_tokens(2000, 1.0, 0.07, share, OPUS_55)))
# 0.0 16000 12800
# 0.9 5650 4160
```

With no cache reads at all and every input token written at the five-minute rate, 2,000 such sessions come to $16,000, still under the reported total; with 90% of input read from cache, $5,650. Output alone is $3,500 of any of these. The post does not split input into cache reads and writes or state the TTL, so the reported $20,000 cannot be decomposed from its token counts; the residual after output works out to at most $8.25 per million input tokens, between the five-minute and one-hour write prices. The method holds even when the inputs don't: when a published total and its token counts disagree, carry the total as the measured number, and treat the token-level model as the tool for predicting changes, calibrated on your own usage fields.

Two more points from the compiler run are cost-relevant. There was no orchestration agent: each agent claimed a task by writing a lock file and let git conflicts sort out collisions, so the coordination cost was merge work, not tokens. And the harness was built to save context, with test output limited to a few lines, details logged to files, and a `--fast` mode running a deterministic 1% or 10% sample of tests per agent. Each of those is a by-tokens term.

## The multi-agent multiplier

The June 2025 research-system post supplies the multiplier for fan-out: in Anthropic's data, agents use about 4 times the tokens of chat, and multi-agent systems about 15 times. A multi-agent system therefore uses about 15 / 4 = 3.75 times the tokens of a single agent on comparable work. In return, an Opus 4 lead with Sonnet 4 subagents beat a single Opus 4 agent by 90.2% on Anthropic's internal research eval, and token usage alone explained 80% of the variance on BrowseComp, with tool calls and model choice bringing it to 95%.

That last figure is the honest caveat on every cost estimate here: on those tasks, spending more tokens was most of what bought performance. The post says multi-agent systems pay off only when the task's value covers the spend, and that most coding tasks have fewer parallelisable subtasks than research and share more context, which makes them a poor fit.

## Pricing a change before running it

The procedure is to name the term, calibrate it on your own runs, and write down the assumption that would flip the result.

- Adding an evaluator: price by expected rejected rounds times fix-round length, using your build burn rate. The DAW run's evaluator cost 8.3% directly and caused 34% in rework.
- Removing a scaffold the model no longer needs (resets, sprints): price the saved wall time at the burn rate, and measure quality on the same tasks, because the saving is real only if output holds.
- Parallel workers: by-hours, multiplied by worker count, plus the merge and collision cost. With no coordinator, as in the compiler run, that cost lands in git rather than in tokens.
- A model swap: by-tokens, but re-measure tokens per task, because a different model takes a different number of turns. Token for token, Opus 5.5 list prices are 20% below Opus 4.6 on input and output and 60% below on cache reads.

## When this is wrong

Each published figure is one run of one prompt, measured by the vendor on a model that has since been superseded. The steady burn rate is an observation from three Opus runs, not a law: a harness with heavy parallel tool calls, big file reads or a cache-breaking feature will burn at a different rate, and the per-hour model hides that until you measure it.

The dollar figures are API list prices. On a subscription, the constraint is usage limits rather than dollars, and the arithmetic changes shape even if the tokens do not.

The multi-agent multiplier comes from research tasks. Anthropic's own post says coding tasks parallelise less, so 3.75 times a single agent is the number for breadth-first work, not a default for coding fan-out.

Finally, neither model counts human cost: review of a 100,000-line output, or the time to write the tests and harness that made the compiler run possible. The compiler post describes that harness work at length, and it is not in the $20,000.
