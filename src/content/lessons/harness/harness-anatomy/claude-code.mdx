## What it is and who runs it

Claude Code is Anthropic's coding agent. It runs in a terminal, in IDE extensions, a desktop app, the web, Slack and CI, and the docs describe the loop and tools as identical across those surfaces. Execution happens locally by default, in Anthropic-managed or self-hosted cloud environments, or on the user's machine driven from a browser. The Claude Agent SDK, in Python and TypeScript, bundles a native Claude Code binary and runs the same loop inside your application, with the same tools, hooks, permissions, sessions and compaction exposed as options.

Everything below comes from Anthropic's public documentation as checked on 2026-10-28 and from three Anthropic engineering posts dated March to May 2026. Claude Code versions are cited where the docs tie a behaviour to one, because defaults change often: interactive terminal and VS Code sessions start in auto mode from v2.1.283, and the default model on most plans is Opus 5.5 at medium effort.

Agentic loop. The docs describe three phases, gather context, take action and verify results, that blend together; the model chooses each next step from what the last one returned. In SDK terms one turn is a model response with tool calls plus their execution, and the loop ends on a response with no tool calls. Read-only tools in one response can run concurrently; `Edit`, `Write` and `Bash` run one at a time.

Claude model API. Every turn re-sends the full request: system prompt and tool definitions, then project context, then the conversation. Each model has its own cache, so the model and effort are best fixed at the start of a session.

Memory files. CLAUDE.md files from the user, project and ancestor directories load at launch, nested ones on demand. Auto memory is a MEMORY.md the agent writes itself, of which the first 200 lines or 25KB load at session start. If there is no CLAUDE.md, Claude Code can read AGENTS.md instead.

Skills. A skill is a `SKILL.md` under `.claude/skills/<name>/`. Its name and description are in context from session start; the body loads when the skill is used. Setting `disable-model-invocation: true` means only the user can start it, which moves the skill from model-decided to user-decided.

Hooks. 33 events across three cadences (per session, per turn, per tool call) plus standalone events such as `PreCompact` and `FileChanged`. Handlers are `command`, `http`, `mcp_tool`, `prompt` or `agent`; matching hooks run in parallel. Exit code 2 blocks on events that can block, such as `PreToolUse` and `Stop`.

Auto-compaction. Near the context limit the conversation is replaced by a summary and selected content is re-injected. If a single output refills the context right after each summary, Claude Code stops after a few attempts and shows an error instead of looping.

Session store. Every message, tool call and result is written to a plaintext JSONL file under `~/.claude/projects/`. Resume reopens the same session ID and appends; fork copies history into a new ID.

Permission engine. A mode sets the baseline, permission rules are checked deny then ask then allow, `PreToolUse` hooks can block, and in auto mode a classifier reviews what the rules and the built-in allowlist did not settle.

Built-in tools. The SDK lists file operations (`Read`, `Edit`, `Write`), search (`Glob`, `Grep`), execution (`Bash`), web (`WebSearch`, `WebFetch`), discovery (`ToolSearch`) and orchestration (`Agent`, `Skill`, `AskUserQuestion`, task tools).

MCP servers. Tool definitions from MCP servers are deferred by default: only names and server instructions load, and `ToolSearch` loads a schema when needed. Output above 10,000 tokens produces a warning, and the default limit is 25,000 tokens.

Sub-agents. A sub-agent runs in its own context window, fresh unless it is a fork, and returns a summary. Its tool calls stay out of the parent's context, and its tool set can be restricted in its definition, which the harness enforces.

OS sandbox and proxy. Off by default. When on, shell commands and their children run under Seatbelt on macOS or bubblewrap on Linux and WSL2, with writes limited to the working directory, a temp directory and added directories, and no direct network route: traffic goes through a proxy outside the sandbox that checks each hostname against allowed domains, which start empty. It is built on the open-source `@anthropic-ai/sandbox-runtime`.

Checkpoints. Before editing a file with its file tools, Claude Code snapshots it; pressing Esc twice rewinds. Checkpoints are separate from git, do not track files changed only by `Bash`, and cannot undo remote side effects such as database writes or deployments.

## Context strategy

The strategy is a stable prefix plus aggressive deferral. Tool schemas for MCP servers, skill bodies, nested CLAUDE.md files and path-scoped rules all stay out of context until a name, a file read or a skill invocation pulls them in. Plan mode, skill bodies and output-style changes are appended as messages so the cached prefix survives. Sub-agents move large reads into separate windows that return only a summary.

Compaction is where the strategy shows its priorities. The docs list what comes back: the system prompt and output style still apply; project-root CLAUDE.md, unscoped rules and auto memory are re-read from disk; the plan from plan mode is re-injected; nested CLAUDE.md files and path-scoped rules reload on demand; up to five files read or edited in the session are re-read, most recently modified first, with any file over 5,000 tokens returned as a reference; invoked skill bodies are re-injected with caps; `SessionStart` hooks matching the compact source run again. Instructions given only in conversation are summarised with everything else, which is why the docs keep repeating that persistent rules belong in CLAUDE.md.

## Tools and permission model

Six modes set the baseline. `default` (shown as Manual) runs reads only without asking. `acceptEdits` adds file edits and common filesystem commands. `plan` explores and proposes without editing source files. `auto` runs everything, with background checks. `dontAsk` runs pre-approved tools and denies anything that would prompt, for CI. `bypassPermissions` runs everything and is documented for isolated containers and VMs only. Deny rules block in every mode, including `bypassPermissions`, and some actions are never auto-approved: explicit ask rules, critical-path removals such as `rm` on recognised critical paths, and tools that require user interaction.

Auto mode is the part Anthropic has explained in most depth. Its March 2026 post describes two layers. An input-layer probe scans tool results for prompt injection and adds a warning before the agent reads them. An output-layer transcript classifier, running on Sonnet 4.6 at publication, reviews each action that reaches it in two stages: a fast single-token filter tuned to err toward blocking, then chain-of-thought reasoning only on what the filter flags. The classifier sees user messages and tool calls and is deliberately blind to the agent's prose and to tool results, so the agent cannot argue its case and injected content cannot reach it directly. Three tiers decide what it sees: a built-in allowlist and user rules first, in-project file edits second, everything else third. Entering auto mode drops broad allow rules such as `Bash(*)`, wildcarded interpreters and package-manager run commands so those commands reach the classifier. The classifier also runs at both ends of a sub-agent handoff: the outbound check can deny the delegation, and the return check prepends a security warning for the parent instead of discarding the results.

The sandbox is the deterministic layer under all of that, with limits stated plainly in the docs: it is off until enabled, it wraps shell commands only, its default read scope includes credential files such as `~/.ssh` unless `denyRead` or the credentials settings change it, and processes Claude Code starts itself (hooks, local MCP servers, the status line) run with the user's full access. Anthropic reports the sandbox cut permission prompts by 84%.

## Cost and latency

Cost is dominated by how much of each request is a cache read. The docs list what forces a slower, uncached turn: switching models, changing effort on most models, toggling fast mode, connecting or removing an MCP server when tools are loaded up front, enabling some plugins, denying a whole tool without tool search, compacting, dropping old images, and upgrading Claude Code. Editing files, editing CLAUDE.md, changing permission mode, invoking skills and rewinding keep the cache. Cache entries live five minutes by default and one hour for the main conversation on a subscription within plan usage; sub-agents fall in the five-minute bucket unless configured.

Auto mode adds a round trip only for actions that reach the classifier, mainly shell commands and network operations, since reads and in-project edits skip it. Stage 2 uses the same prompt as stage 1 except for the final instruction, so it is almost entirely a cache hit. Budget caps in the SDK are checked after each response arrives, so spend can exceed `maxBudgetUsd` by one response plus whatever running sub-agents spend before they stop.

## Failure modes

The April 2026 postmortem is the clearest public record of harness failures presenting as model failures: a default effort reduction from high to medium (4 March to 7 April), a bug that cleared prior reasoning on every turn after a session had idled for an hour (26 March to 10 April), and a system prompt line limiting response length that cost 3% on one evaluation (16 to 20 April). The thinking bug passed code review, unit and end-to-end tests and dogfooding; Anthropic says it took over a week to find.

Anthropic's containment post adds two security failures. Reported vulnerabilities let a cloned repository's project settings define hooks that ran before the folder-trust dialog, fixed by deferring project configuration until after consent. And in an internal red-team exercise, a phished prompt asked Claude Code to read `~/.aws/credentials` and post it out; it succeeded in 24 of 25 retries, because the instruction came from the user and nothing in the model layer looked anomalous. Only egress and filesystem boundaries stop that case.

Auto mode's own published miss rate is 17% on real overeager actions, and Anthropic says most misses were the classifier treating approval-shaped evidence as consent for a riskier action. A boundary stated in conversation ("don't push until I've reviewed") is read by the classifier but can be lost when the conversation compacts.

## What is not public

Anthropic has not published the full system prompt; the postmortem quotes one line of it. The auto-mode classifier's fixed prompt template is not published, though its three configurable slots and their defaults can be printed with `claude auto-mode defaults`. How the classifier model was tuned, beyond the three evaluation sets in the March post, is not described, and neither is the server-side prompt-injection probe's model or threshold. The per-model auto-compaction thresholds are documented, but not how they were chosen or what evaluation supported them. Statements about any of these are guesses unless they cite a newer Anthropic source.

<Fragment slot="short">
<p>Managed settings carry the controls security owns: sandbox required with a managed domain allowlist only, credential paths in deny and sandbox read-deny, a short list of deny rules for force pushes and production deploys, and the classifier's trusted-environment description. Repositories carry their own hooks, allow rules for their test commands and CLAUDE.md. The residual risk is the classifier's measured miss rate on whatever reaches it and anything a user instructs directly, which the sandbox bounds but does not eliminate.</p>
</Fragment>
<Fragment slot="long">
<p>Start from what each layer can guarantee. Deny rules and managed settings hold in every mode and cannot be overridden by personal or repository files. The sandbox bounds shell commands, but not the file tools, MCP servers or hooks, so credential protection needs both a Read deny and a sandbox read-deny, plus moving credentials out of the default read scope.</p>
<p>Egress: require the sandbox and allow only managed domains, so a new host is denied rather than prompted. That removes most prompts for routine work and makes the phished-prompt case fail at the network. It costs developer friction for every new registry or API, so publish a fast path for adding domains.</p>
<p>Auto mode then handles what remains: shell and network actions inside the allowed boundary. Its 17% miss rate on overeager actions applies to that residue, not to the denied set. Configure the environment slot with your source-control org and buckets so it stops blocking routine pushes to working branches.</p>
<p>Repositories own their CLAUDE.md, test-command allow rules and Stop hooks. Because project hooks run with full user access once the folder is trusted, review them like CI config.</p>
<p>What you give up: some legitimate network access needs a request, and some prompts remain for writes to protected paths.</p>
</Fragment>
