## The layer the vendors now name

A coding agent is two programs. The model samples the next tokens. The harness decides what the model sees, which actions it can take, what happens to each action, when the run stops, and what persists afterwards. The vendors converged on the word in 2026. Claude Code's documentation describes Claude Code as the layer around the model that supplies the tools and manages what the model sees, and calls that layer the agentic harness. OpenAI's January 2026 post on the Codex loop calls its agent the harness and describes the Codex harness as the agent loop and execution logic underneath the CLI, the cloud product and the IDE extension. Birgitta Böckeler's April 2026 article on martinfowler.com uses the short form Agent = Model + Harness, with the harness defined as everything except the model.

The definition matters because it assigns ownership. When a coding agent does something wrong, the fix sits in one of two places: the weights (which you cannot change, only swap) or the harness (which you configure, extend or write). A failure blamed on the wrong layer gets the wrong fix: a model upgrade for a harness bug, or one more instruction for a model that already had the instruction and reasoned past it.

## What the harness owns

Seven responsibilities cover what the Claude Code and Codex documentation describe. A compiler driver is the closest analogy: it owns flags, include paths, linking and the exit code, while the optimiser owns the code it emits. The difference is that the "optimiser" here can request actions from the driver, so the driver also needs an access-control layer.

| Responsibility | What the harness decides | Documented example |
|---|---|---|
| Prompt assembly | Order and content of every request | Claude Code puts system prompt and tools first, project context second, conversation last; Codex sends `instructions`, `tools` and an `input` list |
| Tool set | Which actions exist and their shapes | Read, Edit, Write, Glob, Grep, Bash, WebFetch, Agent in Claude Code; `shell`, `update_plan`, web search and MCP tools in Codex |
| Context management | What stays, what is summarised, what is re-read | Claude Code auto-compaction; Codex calls a `/responses/compact` endpoint past `auto_compact_limit` |
| Permissions and sandbox | Which actions run, ask or are refused, and inside what boundary | Deny, ask, allow rules and an OS sandbox; Codex sandbox modes plus an approval policy |
| Verification | What counts as done | A `Stop` hook that runs the typecheck and refuses to let the turn end |
| Budgets | When the loop stops regardless of the model | `maxTurns`, `maxBudgetUsd`, a spend limit |
| Persistence | What survives the session | Claude Code writes every message and tool result to a JSONL file and snapshots files before editing them |

The model owns one thing on that list outright: given the request, which action to propose next. Everything else is configuration, code or policy that someone on your side can read and change.

Böckeler adds a second axis that is useful when you build the outer harness around a vendor tool. Controls are either guides that steer before the agent acts (feedforward) or sensors that observe afterwards and feed back (feedback), and each is either computational (tests, linters, type checkers, structural tests) or inferential (an LLM reviewer, a judge). Her mapping puts AGENTS.md conventions in the inferential feedforward cell and an ArchUnit test in a pre-commit hook in the computational feedback cell. Her observation that feedback alone produces an agent that repeats mistakes, while feedforward alone produces rules nobody checks, is the reason a working harness has entries in both columns.

## Holding the model fixed

The cleanest evidence that the harness moves results is a change that touches only the harness. SWE-agent (2024) ran the same model, GPT-4 Turbo, on the same 300 SWE-bench Lite tasks under two harnesses: a plain Linux shell, and its own interface with capped search, a 100-line file viewer and a linter-guarded edit command.

The 2026 version of the same evidence is Anthropic's April postmortem on Claude Code quality reports. Three changes, all in the harness, explained weeks of complaints that the model had become worse. On 4 March the default reasoning effort went from high to medium; it was reverted on 7 April. On 26 March a change meant to clear old thinking once from sessions idle for over an hour cleared it on every turn instead, which made the agent forgetful and repetitive and also caused cache misses; it was fixed on 10 April. On 16 April a system prompt line capping text between tool calls at 25 words and final responses at 100 words shipped; a broader ablation found a 3% drop on one evaluation for both Opus 4.6 and 4.7, and the line was reverted on 20 April. Anthropic states the API was not affected. Each change hit a different slice of traffic on a different schedule, so the symptom looked like broad model degradation.

## Assigning failures to layers

Most production failures can be placed by asking one question: if the model proposed the same action again tomorrow, would the outcome change without retraining anything?

| Failure | Layer that fixes it | Why |
|---|---|---|
| The agent occasionally edits `migrations/` despite a CLAUDE.md line forbidding it | Harness | Claude Code's best-practices page says a CLAUDE.md line is the model's call on every turn; a `PreToolUse` hook that exits 2, or a deny rule, makes it the harness's call |
| The agent says it is done while the typecheck fails | Harness | A `Stop` hook that exits 2 sends the agent back with the compiler output; the hooks reference caps this at eight consecutive continuations |
| The agent forgets mid-session why it made earlier edits | Harness first | The April 2026 thinking-clearing bug produced exactly this symptom with an unchanged model |
| A user pastes a phished prompt that reads `~/.aws/credentials` and posts it out | Harness environment | In Anthropic's red-team exercise the prompt succeeded in 24 of 25 retries; a classifier anchored on user intent sees nothing anomalous when the user typed it, so only egress and filesystem boundaries hold |
| Session cost jumps after an MCP server connects mid-session | Harness | Tool definitions sit in the cached prefix; Claude Code now defers MCP tools behind tool search and keeps the first request's tool list, so a late server no longer changes it |
| The agent finds the right files and still writes a wrong fix for a subtle concurrency bug | Model | The request held the right context; the proposal was wrong |
| The same wrong fix, only at the default effort level | Both | Effort is a model capability the harness chooses a default for; the April postmortem's first change sat exactly on this line |

The last row is the one that trips teams up. Effort, thinking budgets and output limits are parameters on the model call, so they look like model properties, but the harness picks their defaults per product and per release.

<Callout kind="gotcha">
Two statements that circulated in 2025 coding-agent material are wrong as of October 2026. Editing a project-root or user CLAUDE.md mid-session does not break Claude Code's prompt cache, and it does not take effect either: those files are read once at session start, and the edit loads on the next `/clear`, `/compact` or restart. Nested CLAUDE.md files and path-scoped rules are different: they load on demand, so an edit made before they load does apply. And Cursor's current search docs say Cursor does not store embeddings of your codebase for search; its Instant Grep builds a local index. Cursor's 12.5% average gain from semantic search (6.5% to 23.5% by model) was published on 6 November 2025 and describes the product at that date.
</Callout>

## A harness in forty lines

Every responsibility in the table above shows up as a few lines in even the smallest loop. The model is any callable that takes the request and returns a message plus its cost.

```python
import subprocess

DENY_PREFIXES = ("rm -rf", "git push --force")
MAX_STEPS, MAX_COST_USD = 30, 3.00


def build_request(system, project_context, history):
    # Stable layers first, so consecutive requests share the longest prefix.
    return [system, project_context, *history]


def allowed(cmd):
    # Enforced by the harness, whatever the model was told. A prefix check is
    # a placeholder; a real gate parses the shell (see the controls lesson).
    return not cmd.strip().startswith(DENY_PREFIXES)


def tests_pass():
    return subprocess.run(["python", "-m", "pytest", "-q"]).returncode == 0


def run(model, task, system, project_context):
    history, cost = [{"role": "user", "content": task}], 0.0
    for _ in range(MAX_STEPS):
        reply, step_cost = model(build_request(system, project_context, history))
        cost += step_cost
        history.append(reply)
        if cost > MAX_COST_USD:
            return "stopped: budget"
        cmd = reply.get("command")
        if cmd is None:
            if tests_pass():
                return "done"
            history.append({"role": "user", "content": "Tests fail. Continue."})
            continue
        if not allowed(cmd):
            history.append({"role": "tool", "content": "Denied by policy."})
            continue
        out = subprocess.run(cmd, shell=True, capture_output=True, text=True, timeout=60)
        history.append({"role": "tool", "content": (out.stdout + out.stderr)[-4000:]})
    return "stopped: step limit"
```

Only one line calls the model. The rest decide what it sees (`build_request`, the 4,000-character tail), what it may do (`allowed`), when it is finished (`tests_pass`), and when it must stop regardless of what it believes (`MAX_STEPS`, `MAX_COST_USD`). The budget check runs after the response arrives, so spend can pass the cap by one response; the Claude Agent SDK documents the same overshoot for `maxBudgetUsd`.

<Fragment slot="long">
<p>One sweep cannot cover a full factorial at useful run counts, so spend it on the two off-diagonal cells (old model with new prompt, new model with old prompt) against the baseline you already have. That isolates each change at the cost of not measuring their interaction, which is the risk to state.</p>
<p>Check harness telemetry before burning eval budget: cache hit rate, tokens per turn, turns per task, compaction count and tool-error rate per session. The April 2026 Claude Code postmortem is the reference case: a thinking-clearing bug showed up as cache misses and repetitive tool calls, and a single prompt line cost 3% on one evaluation that the original suite did not include. Harness regressions often leave traces in those counters; model regressions usually do not.</p>
<p>Roll back by reversibility. The prompt change is yours and reverts in minutes; gate model-specific prompt lines to the model they target so the next upgrade does not inherit them. Keep the new model if the off-diagonal run clears it, and ship the old prompt with it.</p>

## When this is wrong

The line between model and harness moves into the API. Codex's compaction endpoint returns an encrypted item that stands in for the earlier conversation, Claude Code can run its auto-mode classifier server-side, and Anthropic's clearing of old thinking used an API header. Parts of the harness you depend on now run on the vendor's servers, where you can observe their effects but not read them.

Models are tuned for their vendor's harness. Anthropic's postmortem says the team optimises the harness for each model before release, and OpenAI bundles model-specific instructions into the Codex CLI. Running a model in a foreign harness therefore measures the pair, not the model; a "harness-neutral" comparison does not exist.

Böckeler's grid also blurs at the edges. A `prompt` or `agent` hook in Claude Code sits in the harness's control flow but asks another model to decide, so it is a harness mechanism with model-grade reliability. Placing a failure in the harness tells you who can change it, not that the change will be deterministic.
