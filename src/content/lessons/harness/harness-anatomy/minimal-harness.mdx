## The question

SWE-agent showed that harness design moved results for a 2024 model. The follow-up question is the one that matters for anyone deciding what to build in 2026: how much harness does a capable model need, and what do you lose when you delete it? Three designs answer from different directions. mini-swe-agent keeps the agent loop and deletes almost everything around it. CodeAct keeps the loop and changes the action format from tool calls to executable code. Agentless deletes the loop and replaces it with a fixed pipeline.

## mini-swe-agent: the loop and nothing else

mini-swe-agent comes from the team behind SWE-bench and SWE-agent, under an MIT licence, now at version 2. Its README states the design in three choices. The agent has no tool except bash. Its history is completely linear: each step appends to the message list, so the trajectory and the prompt are the same object. And each action runs as an independent subprocess instead of inside a persistent shell session, so moving execution into a container means replacing one call with `docker exec`.

The README describes the agent class as about 100 lines of Python. The file `default.py` measured 190 lines on 2026-10-28, including docstrings, trajectory serialization and saving; the control flow itself is a `while` loop around `step()`, which calls the model and then executes whatever actions came back. Limits are four numbers: a step limit (0, meaning none, by default), a cost limit (3.0 by default), an optional wall-clock limit, and an exit after three consecutive format errors. The task ends when a command's output begins with a fixed sentinel line. In v2 the default model class sends a single `bash` function through the provider's tool-calling API; a text-based variant parses one fenced block per response with a regular expression for models without tool calling.

The README reports a score above 74% on SWE-bench Verified and says the project is used as the harness for a bash-only leaderboard that compares models under identical scaffolding. That second use is the more important one: with a harness this small, differences between runs are mostly differences between models.

## CodeAct: code as the action space

CodeAct (Wang and colleagues, ICML 2024) asks what the action format should be. Tool calling in JSON or text gives the model one call per action and no control flow. CodeAct has the model write Python that runs in an interpreter, so one action can loop over files, call several tools, store intermediate results in variables and handle errors. The paper evaluates 17 LLMs on API-Bank and on M3ToolEval, a new 82-task benchmark that needs several tools over several turns. It reports up to 20% higher absolute success than the best alternative format and up to 30% fewer actions; for `gpt-4-1106-preview` the gain over text actions was 20.7 points with 2.1 fewer turns on average. The authors also released CodeActInstruct, about 7,000 multi-turn interactions for fine-tuning.

mini-swe-agent's bash-only design is a CodeAct-style choice with a different interpreter: the model composes `grep`, `sed`, `python -c` and pipes instead of picking from a menu of narrow tools.

## Agentless: no loop at all

Agentless (Xia and colleagues, 2024) removes the agent's control over what happens next. A fixed three-phase pipeline runs on every issue. Localisation is hierarchical: the model ranks suspicious files from a tree of the repository, an embedding-retrieval pass ranks files by their code, and the files both methods agree on go forward, then names classes and functions from a skeleton of each file's declarations, then names edit locations, sampled four times. Repair samples several candidate patches per location in a simple diff format. Validation generates a reproduction test for the issue and uses it together with the repository's regression tests to pick the final patch.

With GPT-4o (`gpt-4o-2024-05-13`), Agentless resolved 32.00% of SWE-bench Lite, 96 of 300 issues, at an average cost of $0.70 per issue, and the paper reports that as the best result among open-source approaches at the time.

## What each design gives up

The useful comparison is not the scores, which come from different models and different benchmark splits, but which harness responsibilities each design keeps.

| Responsibility | mini-swe-agent | CodeAct | Agentless | Claude Code or Codex |
|---|---|---|---|---|
| Prompt assembly | Two templates (system, task), then append | Multi-turn; interpreter output appended | One prompt per pipeline stage | Layered, cache-ordered |
| Tool set | `bash` | A Python interpreter | None exposed to the model | Built-in file, search, shell, web and orchestration tools, plus MCP |
| Context management | No compaction; each output capped at 10,000 characters by the config template; history grows until a limit stops the run | Not the paper's subject | Each stage starts fresh | Compaction, sub-agents, deferred tools |
| Permissions | None; the environment is the boundary | Not the paper's subject | No free-form actions to permit | Rules, modes, classifier, OS sandbox |
| Verification | The model decides when to submit | The model, from interpreter feedback | Built in: regression and reproduction tests choose the patch | Hooks, tests, CI |
| Budgets | Step, cost, wall-clock limits | Not the paper's subject | Fixed by pipeline shape | Turns, spend caps |

Three conclusions follow. First, the context-management and tool-design work that SWE-agent did by hand can be absorbed by a capable model with a general interpreter, which is the case mini-swe-agent and CodeAct make. Second, verification moved in the opposite direction: Agentless gets its result partly by making verification structural instead of trusting the model to decide when it is done. Third, permissions cannot be absorbed by the model at all. mini-swe-agent's safety is whatever the execution environment provides, which is fine in a disposable benchmark container and unacceptable on a developer laptop with credentials in the environment. Nothing in these papers suggests a capable model makes an access boundary unnecessary; Anthropic's containment post reports capable models finding unexpected paths around restrictions.

<p>Two harnesses, with a shared core and a measured gap. The minimal one stays for rollouts and model comparisons because its simplicity makes trajectories reproducible and attributable to the model. The product harness keeps the controls a model cannot absorb: permissions, sandbox, verification gates. Run the product eval on both harnesses each release and track the gap, so training-serving skew is a number, not a worry.</p>

<Fragment slot="long">
<p>The case for one harness is real: a model trained on rollouts from harness A and served in harness B sees different prompt layouts, tool sets and context policies. Anthropic's 2026 postmortem says its team tunes the product harness per model before release, which is the same skew managed from the other side.</p>
<p>The case for two is that the requirements conflict. Rollouts want linear, replayable trajectories and no hidden state; the product wants compaction (which rewrites history), sub-agents and a permission engine with side effects such as approval prompts. Forcing the product harness into rollouts makes trajectories harder to replay; forcing the minimal harness into the product removes the controls.</p>
<p>The compromise is a shared core: one tool schema for shell and edit, one prompt layout for the stable prefix, one trajectory format. The product harness adds layers around the core; the rollout harness does not. Each release, run the product's task suite in both and report the score and cost gap. If it stays small, the skew is acceptable; if it grows, move more of the product layout into rollouts.</p>
<p>What you give up: two harnesses to maintain, and a standing eval cost to measure the gap.</p>

## When this is wrong

The scores in this lesson cannot be ranked against each other. SWE-agent used GPT-4 Turbo on Lite, Agentless used GPT-4o on Lite, CodeAct used a different benchmark entirely, and mini-swe-agent's figure is self-reported on SWE-bench Verified with a model the README headline does not name. A high score with a minimal harness says the model is strong, not that the harness is good.

"Minimal" also depends on where the work moved. mini-swe-agent has no permission layer because benchmark runs happen in containers; it has no compaction because benchmark tasks fit the step and cost limits. Its design is a statement about the environment it runs in. Agentless works because SWE-bench tasks have a fixed shape (one issue, one patch, tests available); a task that needs exploration, a migration across services or a conversation with the user has no fixed pipeline to run.

And the model changes the answer. The mini-swe-agent README's own argument is that SWE-agent's interface work became unnecessary because models became more capable between 2024 and 2025; by the same argument, the right amount of harness is a property of a model generation, not a constant. Re-run the deletion experiment when the model changes instead of carrying the conclusion forward.
