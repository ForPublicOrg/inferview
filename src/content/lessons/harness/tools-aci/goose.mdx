## What it is and who runs it

goose is an open-source, general-purpose agent with a desktop app and a CLI. Block built it and, on 7 April 2026, donated it to the Agentic AI Foundation (AAIF) at the Linux Foundation, the same foundation that holds MCP and AGENTS.md. The docs now carry an AAIF copyright.

Its distinctive design choice for this module is that it has no private tool interface. Every capability, including the file and shell tools that ship with it, is an extension, and every extension is an MCP server. The tool set a goose session sees is therefore the union of whatever MCP servers are enabled, which makes goose a clean case study for three questions from the earlier lessons: what happens to errors, what happens to context as tools return output, and how one tool layer serves both its own interface and other editors.

Everything below comes from goose's public documentation as of 28 October 2026. Where the docs are silent, the section on what is not public says so.

**Interface.** The desktop app and the CLI take the user's request and display output. The docs treat the interface as a thin layer: a session starts an agent and the agent does the work. goose Desktop talks to the agent over WebSocket by starting `goose serve` locally on a loopback port.

**ACP server mode.** `goose acp` runs goose as an Agent Client Protocol server on stdin and stdout, so an editor such as Zed starts it as a subprocess and drives it for the life of the connection. `goose serve` exposes the same protocol over HTTP and WebSocket, listening on 127.0.0.1:3284 by default with the endpoint at `/acp` and a secret key header; requests without the secret get a 401. The direction also reverses: goose can use an external ACP agent such as Claude Code or Codex as its provider, in which case that agent runs tools itself and goose passes its extensions through as MCP servers.

**Agent.** The agent runs the loop the docs describe in six steps: take the request, send it with the available tools to the provider, execute any tool call the model returns (the model can request a call but cannot run it), return the results, revise the context, and produce the response. It repeats the middle steps until the model stops calling tools.

**Model provider.** The providers table lists 47 providers, plus a CLI provider and ACP providers. The docs state that goose relies on tool calling, that models without it can only chat, and that extensions should be disabled for such models.

**Extensions.** An extension implements a small interface (name, description, instructions, tools, status, and a `call_tool` entry point) and is reached over MCP. Built-ins include Developer (enabled by default), Computer Controller, Memory, Tutorial and Auto Visualiser; platform extensions include Analyze, Extension Manager, Skills and Summon, all enabled by default, and Code Mode, which runs JavaScript for tool discovery and calling when it is included in the build. External extensions run over stdio or Streamable HTTP from `config.yaml`, and goose checks external extensions for known malware before activating them.

**Error results.** This is the path the docs single out. goose separates traditional errors (network failures, an unavailable model), which go to the caller of the agent API, from agent errors, where the system works but the model's output causes the problem: an unknown tool name, incorrect parameters, arguments that are not valid JSON. An agent error in a tool call becomes an error tool result and goes back to the model, and so does a well-formed call that fails inside the tool. The error-handling page says the messages give the model instructions on how to recover.

**Context revision.** Between turns, goose trims what it sends. The architecture page lists the techniques: summarising with smaller, faster models, deleting old or irrelevant content, and keeping tool output small at the source.

Step 4 is the design decision. A harness that raised an exception there would end the session on a formatting slip; one that silently dropped the call would leave the model waiting on a result that never comes. goose treats the malformed call as data for the next turn, which is cheap and usually works, and leaves the bound on repeated failure to the session's turn limit.

## Context strategy

goose combines a documented compaction trigger with source-side reduction.

The trigger is `min(GOOSE_AUTO_COMPACT_THRESHOLD × context window, GOOSE_AUTO_COMPACT_TOKEN_LIMIT)`, with defaults of 80% and 225,000 tokens. With the default context limit of 128,000 tokens that is min(102,400, 225,000) = 102,400 tokens. On a model with a 1,000,000-token window it is min(800,000, 225,000) = 225,000, so on large-window models the absolute limit, not the percentage, decides when compaction runs. Setting the threshold to 0 turns auto-compaction off.

When the limit is still exceeded, the CLI applies a context strategy: summarize, truncate, clear, or prompt. Interactive CLI sessions prompt the user; headless `goose run` summarises automatically; the desktop app only summarises. Separately, older tool-call outputs are summarised in the background while recent calls stay in full, with a cutoff derived from the context limit and the compaction threshold (tunable through `GOOSE_TOOL_CALL_CUTOFF`).

Source-side reduction is in the architecture page: find-and-replace edits instead of rewriting large files, ripgrep to skip system files, and summarising verbose command output. These are the output-budget choices from the earlier lesson, made inside the tools rather than in the loop. The page also says goose includes all relevant content rather than relying on semantic search, a stated choice against embedding-based retrieval for what enters the agent's context.

## Tools and permission model

The tool set is whatever extensions are enabled, and the Extension Manager can enable and disable extensions during a session. Because the loop sends the available tools with each request, every enabled extension adds definitions to the prompt; the many-tools lesson's arithmetic applies directly. Code Mode, where present, is goose's version of tool discovery through code.

Permissions are set by mode:

| Mode | Behaviour |
| :- | :- |
| Completely Autonomous (`auto`) | Edits, extension calls and deletions run without approval. The docs say this mode is applied by default. |
| Manual Approval (`approve`) | Asks before any tool or extension use. |
| Smart Approval (`smart_approve`) | Risk-based: low-risk actions run, others are flagged. Write tools, such as file edits and shell `rm`, `cp` and `mv`, need approval. |
| Chat Only (`chat`) | No extension use and no file changes. |

In Manual and Smart modes, each tool can be set to Always Allow, Ask Before or Never Allow, and the per-tool setting overrides the mode for that tool. The docs describe smart approval's read-or-write classification as best-effort and interpreted by the LLM provider, which means the permission decision for a call depends on a model judgement rather than on a declared property of the tool.

## Cost and latency

goose publishes mechanisms, not measurements. The cost levers it documents are the compaction trigger and strategies, background summarisation of old tool output, smaller models for summarisation, and the source-side reductions. The latency-relevant limits are a per-extension timeout (shown as 300 seconds in the configuration examples) and `GOOSE_MAX_TURNS`, which defaults to 1,000 consecutive turns without user input, after which goose asks whether to continue. The CLI shows context use in bands: green below 50%, yellow from 50% to 85%, red above 85%.

The cost of the error-as-result design is a turn per failed call: the malformed request, the error, the reissue. That is the cheapest possible recovery when the model fixes the call on the next turn, and the most expensive design if it does not, because nothing short of the turn limit is documented to stop it.

## Failure modes

**Autonomous by default.** A new session can edit and delete files without approval. Teams that adopt goose for others choose the mode explicitly; the default is a single-user convenience.

**A model classifying its own risk.** Smart approval asks the provider's model whether an action is a write. Content the model has read, including tool output from an untrusted source, sits in the same context as that judgement. Per-tool Never Allow and Ask Before settings are the deterministic layer beneath it.

**Unbounded recovery loops.** Agent errors go back to the model with no documented retry cap. A model that keeps producing malformed calls for one tool is bounded only by the 1,000-turn default.

**Summaries that drop the detail needed later.** Background summarisation of old tool output trades exact text for space. A stack trace or file excerpt summarised at turn 30 is gone in its exact form at turn 60 unless the tool can be called again.

**Extension sprawl.** Every enabled MCP server adds tools to the request and is code from somewhere. The malware check covers known malware, not a server that is merely careless with its output or its tool descriptions.

**Models without tool calling.** goose depends on native tool calling. With a model that lacks it, the docs' advice is to disable extensions, which turns the agent into a chat client.

## What is not public

- Production usage data: sessions, tool-call volumes, error rates, or how often agent errors recover on the next turn.
- Model routing defaults beyond the docs: which model performs summarisation by default, and how "smaller, faster" models are chosen for context revision.
- The retry policy for agent errors, if any exists beyond the turn limit.
- The exact error texts returned to the model and the full list of agent error types.
- How smart approval prompts the provider to classify an action, and on which model.
- The token cost of the default extension set's tool definitions per request.
- How the "algorithms to delete old or irrelevant content" decide what is irrelevant.

<Fragment slot="long">
<p>Security and speed conflict first. Autonomous mode is the default and the fastest, and it is not reviewable. Smart approval is faster than manual but delegates the read-or-write call to the model, so I would not let it be the only control: per-tool settings are the reviewable artefact, and security signs those, not the mode.</p>
<p>The extension list is the second artefact. Internal servers are reviewed like any service; public ones are pinned to versions, and their tool descriptions are read as untrusted input because they shape what the model calls.</p>
<p>Spend is bounded through the loop's own limits. The 1,000-turn default is far above any interactive task, so a lower `GOOSE_MAX_TURNS` is the session cap, and an explicit `GOOSE_AUTO_COMPACT_TOKEN_LIMIT` bounds per-request size on large-window models.</p>
<p>In the first two weeks I measure, per session: approval prompts (if engineers approve without reading, the rules are too noisy), agent errors and the share fixed on the next turn, sessions ending at the turn limit, and tokens per session against the cap. What I give up is speed, and I write down that a lower turn limit will cut off some long tasks, with the limit and the reason.</p>
