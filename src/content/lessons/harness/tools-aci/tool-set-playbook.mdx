## The decision

A coding agent's tool set is its action space: the only verbs the model has. Four shapes are in production or in published scaffolds as of October 2026.

- **Bash only.** mini-swe-agent gives the model one tool, a shell, and does not use the vendor's tool-calling interface at all: the model writes a command in text, the harness runs it with `subprocess.run`, and each action is independent of the last (no persistent shell session). The README claims over 74% on SWE-bench Verified with an agent class of about 100 lines.
- **Bash plus a string-replace editor.** Anthropic's Claude 4 announcement (May 2025) reports 72.5% for Opus 4 and 72.7% for Sonnet 4 on all 500 SWE-bench Verified problems with a scaffold of exactly two tools: bash and a file editor that edits by string replacement. It dropped the planning tool its Claude 3.7 Sonnet scaffold had used.
- **A broad built-in set.** Claude Code ships Read, Edit, Write, Glob, Grep, Bash, WebFetch, WebSearch, Agent, Skill, ToolSearch, LSP and more, each with its own limits, permission default and a name that permission rules and hooks match on.
- **Code as the action space.** The model writes a program that calls tools as functions. CodeAct reported up to 20% higher success than text or JSON actions across 17 models; Anthropic's programmatic tool calling and its code-execution-with-MCP pattern are the 2025 production versions.

The scores above come from different models, years and run settings, and none is a controlled comparison. The choice turns on four inputs that differ between teams.

## The inputs that change it

**Model strength.** The SWE-agent paper (2024) is the strongest evidence that interface design once mattered a great deal. With GPT-4 Turbo on SWE-bench Lite, its purpose-built interface resolved 18.00% against 11.00% for a shell-only agent, which the paper reports as a 64% relative increase. Its ablations moved the score by several points per design choice: a 100-line file viewer scored 18.0% against 12.7% for showing the whole file, and search that summarised results scored 18.0% against 12.0% for iterative search. A year later, a bash-only agent claims over 74% on Verified with newer models. Different benchmark split, different models, no shared configuration: read it as a direction, not a delta. Claude Code shows the same direction from the vendor side. Its docs say newer models get no task-tracking tools by default because they keep track of multi-step work without a written checklist, and the tools' definitions and reminders take up context. A tool that helped a weaker model can cost a stronger one.

**Portability across vendors.** Bash-only needs nothing from the vendor's API beyond text in and text out, so the same harness runs against any chat endpoint and the trajectory format never changes. Every specialised tool is a schema translated into each vendor's tool-calling format, and the model's skill with a given editor depends on what it was trained and evaluated with. Anthropic publishes its SWE-bench numbers with a string-replace editor; that tells you what its models were measured with, not what another vendor's models handle best.

**Permission checks a security team can audit.** A permission rule keyed on a tool name and a structured argument is simple to write and review: Claude Code's tool names are the exact strings used in permission rules, subagent tool lists and hook matchers. A bash-only agent turns every action into a shell string, and the policy engine has to parse shell to decide. Claude Code itself lives with this: on macOS, Linux and WSL its Glob and Grep tools are absent by default, search runs as `find` and `grep` through Bash, and those searches reach hooks and permission rules as Bash calls. Bash also carries a built-in list of read-only commands that run without a prompt, which is a shell parser inside the permission system.

**Observability and invariants.** A structured edit call carries the path, the old string and the new string, and the harness can enforce preconditions on it. Claude Code's Edit refuses an `old_string` that is not an exact, unique match and, on older models, refuses to edit a file the conversation has not read. A `sed -i` through bash has no such checks, and reconstructing what it changed means diffing the filesystem. The bash-only camp argues the other side of observability: mini-swe-agent's history is linear, every step appends to the messages, so the trajectory and the model input are the same object, which the README calls good for debugging and fine-tuning.

## The options and when each wins

**Bash only wins** when the agent must run on several vendors' models or on open-weight models served without reliable tool calling, when the trajectories feed fine-tuning or RL (no scaffold-specific verbs to overfit to), and when the sandbox, not the tool layer, is the security boundary. It loses when a policy must distinguish actions by kind, because every kind is a string.

**Bash plus an editor wins** for most single-vendor coding agents. The editor carries the invariants that matter most (exact match, uniqueness, staleness) and gives a clean edit log; bash covers everything else. It is the smallest set a vendor has published SWE-bench numbers for. It loses on audit if the model routes writes through bash anyway, which nothing in the tool layer prevents.

**A broad built-in set wins** for an interactive product where each verb needs its own limit, permission default and prompt wording: Claude Code's Read returns at most 25,000 tokens per call and Glob caps at 100 files with a truncation flag. The cost is a larger prefix on every request, more choices the model can get wrong, and a tool set that moves with model generations, as Claude Code's own Glob, Grep and task-tool changes show.

**Code as the action space wins** when work chains three or more dependent calls or aggregates data the model does not need to read. Anthropic reports programmatic tool calling cut average tokens from 43,588 to 27,297 on its complex research tasks, and its code-execution post works an example from 150,000 tokens down to 2,000. Both numbers are the vendor's own. It loses when the model must reason over every intermediate result, and it needs a sandbox with resource limits and monitoring before it runs anything.

Tool definitions are the cost people quote against a broad set. With caching, the dollars are small.

## A worked decision

The case, all scenario: a platform team builds an agent that fixes failing unit tests on pull requests in a Python and TypeScript monorepo. It runs in CI in an ephemeral container with no network. Today it uses one vendor's models; a second vendor's model is under evaluation for next quarter. The security team requires a record of every file the agent changed, with before and after content, and no write outside the checkout.

Bash only would make the second vendor trivial and would satisfy the no-write-outside-checkout rule through the container (read-only root, writable checkout), which has to exist anyway. It fails the audit requirement only if the audit is taken from the tool log. Take it from the filesystem instead: snapshot `git diff` and untracked files after every tool call. That record is complete whichever tool wrote the file, which no tool-level log can claim.

Once the audit lives at the filesystem layer, the editor's job is reliability, not compliance. That is the deciding argument. The SWE-agent paper found 51.7% of its trajectories had at least one failed edit, and an edit's chance of eventually succeeding fell from 90.5% overall to 57.2% after one failure. Exact-match and uniqueness checks turn a silent wrong edit into an error the model can act on.

The decision: bash plus a string-replace editor, the container as the security boundary, the audit from per-step filesystem diffs, and a bash-only configuration kept runnable for the second vendor's evaluation, so the comparison is between each vendor's best scaffold rather than one scaffold on two models. What the team gives up: per-verb permission prompts (there is no human in CI to answer them) and the search caps a broad set would provide, so the bash tool needs its own output budget.

## What to measure after choosing

- Resolve rate on a fixed set of past CI failures, paired per task across scaffolds.
- Failed edits per task, and the share followed by a successful edit within two turns.
- Bash-write share: files changed by bash commands rather than the editor, from the per-step diffs. A high share means the model is not using the editor and its invariants protect nothing.
- Tokens and turns per resolved task, with the cache hit rate beside them.
- Audit gaps: any change seen in a diff that no tool call explains. The expected count is zero; anything else is a harness bug.

Rerun the comparison at each model upgrade. Claude Code's tool changes and the path from SWE-agent to mini-swe-agent both say the best tool set moves with the model.

## When this is wrong

The published numbers in this playbook come from SWE-bench variants: Python repositories with test suites, scored by vendors or tool authors on their own runs. Your repository mix, languages and definition of "fixed" differ, and the only number that decides your tool set is a paired run on your tasks.

The model-strength argument assumes models keep getting better at generic tools. A cheaper model chosen for cost can move you back toward the SWE-agent regime, where interface details were worth several points each.

The evidence for code as the action space comes mostly from tool-orchestration tasks (research, data movement), not from editing repositories. Treat it as the answer for the agent's integrations, not yet for its edits.

The platform changes the answer inside one product: Claude Code keeps Glob and Grep as default tools on Windows and removes them on macOS, Linux and WSL. A tool set is a per-environment decision, not a property of the agent.
