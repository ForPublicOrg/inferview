## Definitions are a prefix tax

Every tool the model can call is described in the request: name, description, input schema. Those descriptions sit at the front of the prompt, are sent on every call, and are part of what the model attends over when it picks an action. Anthropic's November 2025 post measured what that costs with real MCP servers. Five servers (GitHub, Slack, Sentry, Grafana, Splunk) expose 58 tools and take about 55K tokens before the conversation starts. GitHub alone is 35 tools and about 26K tokens; Slack's 11 tools take about 21K; adding Jira is about 17K more. Anthropic reports seeing 134K tokens of tool definitions internally before optimising.

With caching, the dollar cost of a static block is modest. On Claude Sonnet 5.5, writing 55K tokens to the cache once costs 55,000 × $2.50/M = $0.14, and each later call reads it for 55,000 × $0.10/M = $0.0055, so a 50-call session pays about $0.14 + 49 × $0.0055 = $0.41 for its tool definitions. The larger costs are elsewhere: the window space (55K of a 200K window is more than a quarter before any code is read), and selection accuracy, which is the number Anthropic's post leads with.

## Deferred loading and tool search

The fix is the one a dynamic linker uses: resolve symbols on first use instead of loading every library at start. The model sees a small set of tools plus a search tool; definitions marked `defer_loading: true` stay out of the prompt until a search returns them, and then they are appended. The difference from a linker is that the resolver is the model itself. If it does not think to search, or the search does not surface the right tool, the tool does not exist for that turn, and nothing fails loudly.

Anthropic's numbers for its tool search tool (beta header `advanced-tool-use-2025-11-20`, vendor's own measurements):

- A setup that cost about 77K tokens before work began cost about 8.7K with tool search, an 85% reduction.
- On its MCP evaluations, Opus 4 went from 49% to 74% and Opus 4.5 from 79.5% to 88.1% with tool search enabled.
- The guidance is to keep the three to five most-used tools always loaded and defer the rest, and to use search when definitions exceed about 10K tokens, when there are 10 or more tools, or when several MCP servers are connected. It is less useful with fewer than 10 tools or when every tool is used in every session.

The accuracy gain is the counter-intuitive part: removing tools from view made the model pick correctly more often. Fewer candidates means fewer near-duplicates competing for the same intent, which Anthropic's context-engineering post describes as bloated tool sets with ambiguous decision points.

## What Claude Code does with it

Claude Code and the Agent SDK load core built-in tools such as Bash, Read and Edit on every request and defer MCP tools and the other built-ins by default on supported models. The prompt-caching docs describe a second benefit that matters more for an interactive harness than the token count. Tool definitions sit in the system-prompt layer, the first thing in the cached prefix. With tool search on, Claude Code keeps the tool list from the conversation's first request for the whole conversation, so an MCP server that finishes connecting mid-session supplies its tools as deferred definitions and nothing already cached is disturbed. With tools loaded upfront, a server connecting adds definitions and invalidates the cache.

The size of that invalidation is easy to compute. At a 150,000-token context on Sonnet 5.5, the next call rewrites the whole prefix: 150,000 × $2.50/M = $0.375 instead of 150,000 × $0.10/M = $0.015 for a cached read, plus the latency of processing 150,000 uncached tokens. The same docs note that denying a whole tool keeps the cache when tool search is active, because the definitions in the request do not change; the deny is enforced at call time.

## When the calls chain: code instead of turns

Deferred loading fixes the cost of definitions. It does nothing about the cost of results flowing through the model. If an agent needs 20 calls whose results it only aggregates, each call is a model turn and each result is re-sent on every turn after it.

<p>There are 21 model calls. Call k (counting from 0) sends 10,000 + 2,500 × k tokens. The total is 21 × 10,000 + 2,500 × (0 + 1 + ... + 20) = 210,000 + 2,500 × 210 = <b>735,000 input tokens</b>. If the model instead writes one program that makes the 20 calls, sums the items and returns a 300-token table, there are two model calls: about 10,000 tokens, then about 10,000 plus the program (say 400 tokens) plus the 300-token result, roughly 20,700 in total. Caching narrows the dollar gap, since most of the 735,000 tokens would be cache reads, but not the 19 extra model round trips.</p>
</Predict>

That is the case for code as the orchestration layer. Anthropic's programmatic tool calling lets the model write code in a sandbox that calls tools marked as callable from code; intermediate results stay in the sandbox. The vendor reports average tokens on complex research tasks falling from 43,588 to 27,297, accuracy on internal knowledge retrieval rising from 25.6% to 28.5% and on GIA from 46.5% to 51.2%, and 19 or more inference passes removed when 20 or more calls run in one code block.

The code-execution-with-MCP pattern goes one step further: MCP tools are presented as files in a directory tree, one module per tool, and the agent lists the folders and reads only the definitions it needs. A `search_tools` function with a detail level does the same job as tool search. Anthropic's worked example drops from 150,000 tokens to 2,000, and it notes that moving a 2-hour meeting transcript from one system to another through the model could add 50,000 tokens on its own, because the text passes through the context twice. In the code version the transcript never enters the context.

## Choosing among them

| Situation | Approach | Why it wins | What it costs |
| :- | :- | :- | :- |
| Under 10 tools, all used most sessions | Load everything | No search step, no miss risk | Prefix tokens, which caching makes cheap |
| Many tools, a few used per session | Tool search, top 3 to 5 always loaded | Smaller prefix, better selection in the vendor's evals, cache survives server changes in Claude Code | A search turn before first use; silent misses |
| Chains of 3 or more dependent calls, aggregates | Programmatic calling or code execution | Results stay out of context, fewer model turns | A sandbox with limits and monitoring; the model cannot reason over what it does not see |
| Bulk data movement between systems | Code execution | Data never passes through the model, and sensitive fields can be tokenized in the harness | Same sandbox cost; harder to debug from the transcript |

Search quality now depends on descriptions and names, the way a search index depends on its documents. Anthropic's tool-writing guidance recommends namespacing tools under common prefixes and reports that prefix and suffix namespacing had non-trivial effects in its evaluations. Treat tool descriptions as indexed content: test that the obvious queries for each task return the right tool.

The measurements that tell you whether the choice holds: definition tokens per request (from the token-counting endpoint), the share of sessions where a needed tool was never loaded (from traces, by checking tasks that failed for a tool that existed), the selection error rate on a fixed task set with and without deferral, and the cache-creation tokens per turn after an MCP server connects.

## When this is wrong

Every figure here from Anthropic is the vendor's own evaluation on its own tasks and models. The direction (fewer visible tools, better selection) is plausible and consistent across its reports; the size on your tool set is unknown until measured.

Tool search depends on the model and the platform. Claude Code's caching docs list configurations where tool search is off or unavailable and every definition loads upfront, including some cloud-hosted model versions. A harness that must run on several vendors may need a client-side search of its own, with the same miss risk and none of the vendor's tuning.

Code execution hides intermediate results from the model by design. The advanced-tool-use post says it is less useful when the model must reason over every result, and debugging gets harder: the transcript shows a program and a final value, not the 20 responses that produced it.

Deferral is also a security boundary in disguise. A tool that is never loaded cannot be called by an injected instruction unless the model searches for it, but a search tool over every server's descriptions is a way for one server's description to shape which other tools get loaded. Server descriptions are untrusted input to that search.
