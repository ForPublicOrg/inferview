## The problem the post takes on

The post is Anthropic's account, published 2026-03-24, of a harness for building whole applications over hours. It starts from a failure its author calls self-evaluation: agents "reliably skew positive when grading their own work", praising output a human would call mediocre. The problem is sharpest for design, where no test returns pass or fail, but the post says it shows up on verifiable tasks too.

The earlier long-running harness (2025-11-26) had dealt with coherence across context windows and closed by asking whether specialised testing or QA agents would do better than one general agent. This post is the experiment. Its claim is not that a second model is unbiased. The evaluator "is still an LLM that is inclined to be generous towards LLM-generated outputs". The claim is that tuning a separate evaluator to be skeptical is far more tractable than making a generator critical of its own work.

That is the code-review argument, separation of author and reviewer, with a twist that matters for the design: both roles are the same model family with the same priors, so the separation buys a different prompt and a different context, not a different mind. Everything else in the post is about making that difference large enough to matter.

## The mechanism, in engineering terms

**Criteria that turn taste into a rubric.** For frontend work the author wrote four criteria given to both generator and evaluator: design quality, originality, craft and functionality. Craft and functionality were the ones Claude already passed by default, so the post weighted design quality and originality more heavily to push the generator toward risk. The post gives no numeric weights.

**Calibration by example.** The evaluator was calibrated with few-shot examples carrying detailed score breakdowns, which the author says aligned its judgment with his and reduced score drift across iterations. This is the judge-calibration step from the evals track applied inside a loop: the score means something only relative to labelled examples.

**An evaluator that uses the product.** The evaluator had the Playwright MCP and exercised the live page, screenshotting and navigating before it scored, instead of grading a static screenshot or reading code. In the full-stack version it clicked through the running app and tested UI features, API endpoints and database state.

**Hard thresholds per criterion.** In the full-stack harness each criterion (product depth, functionality, visual design, code quality) had a hard threshold, and one criterion below it failed the sprint, with detailed feedback to the generator. A weighted average lets a strong visual score hide a broken feature; a per-criterion floor does not. The post does not publish the thresholds.

**Sprint contracts negotiated in files.** Before each sprint the generator proposed what it would build and how success would be checked, and the evaluator reviewed the proposal until both agreed. They communicated by writing files the other read and answered. The contracts were granular: the post says Sprint 3 alone had 27 criteria for the level editor. This is the acceptance-criteria step of a ticket, written by the two agents before code exists, so the evaluator grades against something it agreed to rather than something it invents after seeing the output.

**A planner in front.** A planner turned a one-to-four-sentence prompt into a product spec, deliberately high level, because a wrong technical detail in the spec would cascade into the build.

The evaluator's findings in the post read like a QA engineer's bug reports: a rectangle fill tool that only placed tiles at the drag endpoints, a delete handler gated on the wrong pair of state variables, and a FastAPI route for `/frames/reorder` declared after `/{frame_id}`, so "reorder" was parsed as an integer id and returned 422. Each of those passes a code read and fails a click.

Getting there took tuning. In early runs the evaluator found real issues and then would "talk itself into deciding they weren't a big deal", approving the work anyway, and it tested superficially. The loop the author describes is reading the evaluator's logs, finding where its judgment diverged from his, and editing the QA prompt, over several rounds.

## The numbers

All figures are Anthropic's own, from single runs described in the post.

The first comparison used Claude Opus 4.5 on one prompt, a 2D retro game maker. A solo agent ran 20 minutes for $9. The full harness ran 6 hours for $200, over 20 times the cost, after the planner expanded the prompt into 16 features over ten sprints. The solo build's game mode did not work: entities rendered and nothing responded to input. The harness build was playable, with rough physics.

## What changed when the model changed

The post's second half is an ablation done by hand. The author states the principle: every component in a harness encodes an assumption about what the model cannot do alone, and those assumptions go stale as models improve. A first attempt to simplify radically failed and made it hard to tell which parts were load-bearing, so he removed one component at a time.

Claude Opus 4.6 shipped during that work. The sprint construct went first: the builder ran coherently for over two hours without decomposition. The evaluator moved from grading every sprint to one pass at the end. The planner stayed, because without it the generator under-scoped. Context resets had already gone between Sonnet 4.5 and Opus 4.5, replaced by the Agent SDK's automatic compaction.

The evaluator's value became conditional. On Opus 4.5 the builds sat at the edge of what the generator did well solo, and the evaluator caught meaningful issues throughout. On Opus 4.6 much of the work fell inside that edge, and there the evaluator was overhead. The post's rule is that the evaluator "is worth the cost when the task sits beyond what the current model does reliably solo". In the DAW run it still caught clips that could not be dragged, missing instrument panels and stub-only recording.

## How you would know your evaluator is stricter than your generator

The post judged the evaluator by reading its logs against the author's own judgment. That works for one person and one app. For a team it needs a labelled set and a paired comparison.

Build a set of outputs with known defects: take finished builds, seed one defect each of the kinds you care about (a broken handler, an unreachable route, a stubbed feature), and keep some clean builds. Run the generator's own final self-check and the evaluator on the same builds. Two numbers matter: how often each catches a seeded defect, and how often the evaluator fails a clean build, because an evaluator that fails everything is strict and useless.

```python
from math import comb


def sign_test(b, c):
    """Two-sided exact test on the discordant pairs: b where only the evaluator failed the build, c where only the generator did."""
    n, low = b + c, min(b, c)
    return min(1.0, 2 * sum(comb(n, i) for i in range(low + 1)) / 2 ** n)


def compare(defective, clean):
    """Each list holds (generator_failed_it, evaluator_failed_it) per build, from the same runs."""
    gen_catch = sum(g for g, _ in defective) / len(defective)
    ev_catch = sum(e for _, e in defective) / len(defective)
    b = sum(1 for g, e in defective if e and not g)
    c = sum(1 for g, e in defective if g and not e)
    ev_false_fail = sum(e for _, e in clean) / len(clean)
    return gen_catch, ev_catch, b, c, sign_test(b, c), ev_false_fail


# scenario: 40 builds with one seeded defect each, 20 clean builds
defective = [(1, 1)] * 10 + [(0, 1)] * 17 + [(1, 0)] * 2 + [(0, 0)] * 11
clean = [(0, 1)] * 3 + [(0, 0)] * 17
g, e, b, c, p, ff = compare(defective, clean)
print(f"generator catches {g:.1%}, evaluator {e:.1%}; discordant {b} vs {c}, p = {p:.4f}; evaluator fails {ff:.0%} of clean builds")
```

On the scenario data it prints `generator catches 30.0%, evaluator 67.5%; discordant 17 vs 2, p = 0.0007; evaluator fails 15% of clean builds`. The pairing is what makes 40 builds enough: only the 19 builds where the two disagree carry information about which is stricter. The 11 defects neither caught are the evaluator's blind spots and the next round of prompt tuning. The 15% false-fail rate is the cost: three clean builds in twenty would buy another build round.

Rerun the comparison when the model changes, because the post's own result is that the gap moves with the model.

## When this is wrong

The evidence is two applications, each run once per configuration, judged by the author. There is no variance across runs, no ablation table with numbers, and no published rubric thresholds, so the post shows the mechanism works on these builds and says nothing about how often. The costs are Anthropic's own and depend on its pricing and models at the time.

The criteria are themselves a prompt to the generator. The post reports that a phrase like "the best designs are museum quality" pushed designs toward a particular visual convergence, and that the first iteration was already better than an unprompted baseline before any evaluator feedback. Part of the effect it attributes to the loop may come from the rubric text alone, which is cheaper to test first.

An evaluator from the same model family can share the generator's blind spots. The post's own limit is concrete: Claude cannot hear, so the QA loop was weak on musical taste, and its testing missed deeply nested features. Seeded defects only measure the defect classes you thought to seed.

Separation also costs coherence. Contracts written in files are only as good as the generator's proposal and the evaluator's review of it, and the post's later harness dropped per-sprint contracts with the sprints. For tasks that sit inside what the current model does reliably solo, the post's own conclusion is that the evaluator is unnecessary overhead.
