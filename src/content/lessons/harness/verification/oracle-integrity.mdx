## The oracle is inside the sandbox

The previous lesson made "tests pass" the agent's stop condition. In most setups the tests live in the same working tree the agent edits, so the cheapest path to the stop condition sometimes runs through the tests. This is not an exotic failure. Anthropic has published it twice in the last year, once as a prompt rule and once as a warning to candidates.

The long-running agents post (2025-11-26) set up a JSON file of over 200 end-to-end features, all marked failing, and told coding agents they could change only each feature's `passes` field. The prompt used what the post calls strongly worded instructions: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." The team chose JSON over Markdown because the model was less likely to overwrite it. Both measures are requests. They lower the rate; they do not make the file unwritable.

The performance take-home README (checked 2026-10-28) shows what happens without enforcement. When Anthropic published its old take-home and invited people to beat Claude's cycle counts, none of the submissions received on the first day below 1300 cycles were valid; "in each case, a language model modified the tests to make the problem easier." The README's example: the simulator has multicore support that is disabled on purpose with `N_CORES = 1`; a model implemented multicore, saw no speedup, "debugged" the core count and "fixed" it.

The repository's defence is worth reading because it is structural. `tests/submission_tests.py` imports the machine, the reference kernel and `N_CORES` from `tests/frozen_problem.py`, a frozen copy, not from the `problem.py` that the candidate's `perf_takehome.py` imports. Changing the core count in `problem.py` changes nothing the tests measure; changing it where the tests read it means editing `tests/`. So the README's acceptance check is one line, `git diff origin/main tests/`, which must print nothing, followed by running the submission tests. The test inputs are also generated without a fixed seed, so a kernel that special-cases the inputs it saw does not pass.

## The same failure at benchmark scale

When the oracle is wrong, the agent is graded against the wrong thing even if it never touches it. OpenAI's audit of SWE-bench Verified (2026-02-23) is the largest public measurement of that. It took the 138 problems that o3 did not solve consistently over 64 runs, had each reviewed by at least six experienced engineers, and found that 59.4% had material issues in test design or problem description. It split them into three groups: tests that enforce implementation details the description never asked for ("narrow", 35.5% of the audited problems), tests that check functionality the description never mentioned ("wide", 18.8%), and other issues (5.1%).

The narrow example is `pylint-dev__pylint-4551`: the reference fix added a function `get_annotation`, the issue never names it, and the tests import it directly, so, in OpenAI's words, many valid solutions fail the tests on import errors. That is an oracle coupled to one implementation, and it is exactly the kind of test an agent's own test suite grows when the agent writes tests alongside the code.

The audit found a second problem the same post treats as disqualifying: every frontier model it tested could reproduce gold patches or verbatim problem details for some tasks, which means the oracle's answers were in the training data. OpenAI now recommends reporting SWE-bench Pro. For your own harness the lesson transfers directly: an oracle the agent has seen, through the repository, the history or the training data, is partly an answer key.

## A check the agent cannot weaken

The design goal is that nothing the agent can write changes the verdict. Layer it from the control that holds to the ones that only give early feedback.

**Grade from a copy the agent cannot write.** Run the tests as they are on a ref the agent cannot push to, in a directory the agent's session never had. The tests the agent saw guide it; the copy grades it. The take-home's frozen simulator is the same idea one level down: freeze what the oracle depends on, not only the test files.

**Treat a diff to protected paths as a failure, not a no-op.** Grading from the base copy already ignores edited tests, but an edited test is evidence the agent took the shortcut, and you want that signal in the log. Reject the run and say why.

**Hold some tests back.** Visible tests tell the agent what done means. Hidden tests, never in its workspace, catch overfitting to the visible ones. Unseeded or property-based inputs, as in the take-home, catch special-casing.

**Block edits early, and know what the block misses.** A deny rule such as `Edit(tests/**)` in Claude Code, or a `PreToolUse` hook that exits 2 for paths under `tests/` as the best-practices page describes for a migrations folder, turns the shortcut into an immediate refusal instead of a rejected run. The permissions page (checked 2026-10-28) states its limit: Edit deny rules cover the built-in file tools, Bash file commands Claude Code recognises such as `sed` and `tee`, and redirect targets, but not a Python or Node script that opens the file itself. The OS-level control is the sandbox. Treat the rule as feedback and the base-copy grading as the control.

**Keep a person on the oracle.** Changes to `tests/` go through code owners and branch protection, separately from the code they test.

This script does the first two in CI after an agent's run, in Python with the standard library and `pytest`:

```python
import os
import subprocess
import sys
import tarfile
import tempfile
from io import BytesIO

BASE = "origin/main"          # a ref the agent cannot push to
PROTECTED = ["tests"]         # the oracle and everything it imports


def git(*args):
    return subprocess.run(["git", *args], capture_output=True, check=True).stdout


changed = git("diff", "--name-only", BASE, "--", *PROTECTED).decode().split()
untracked = git("ls-files", "--others", "--exclude-standard", "--", *PROTECTED).decode().split()
if changed or untracked:
    sys.exit(f"REJECTED: protected paths differ from {BASE}: {', '.join(changed + untracked)}")

with tempfile.TemporaryDirectory() as oracle:
    # grade with the tests as they are on the base ref, not as they are in the agent's checkout
    tarfile.open(fileobj=BytesIO(git("archive", BASE, *PROTECTED))).extractall(oracle, filter="data")
    env = {**os.environ, "PYTHONPATH": os.getcwd()}
    run = subprocess.run([sys.executable, "-m", "pytest", "-q", "-p", "no:cacheprovider", os.path.join(oracle, "tests")], env=env)
sys.exit(run.returncode)
```

On a toy repository whose `add` subtracts, the script fails the run with the base test's assertion. When the test file is edited to expect the wrong answer, it exits with `REJECTED: protected paths differ from origin/main: tests/test_calc.py`. With the bug fixed and the tests untouched, it passes. `git diff BASE` compares the working tree, so uncommitted edits count; the `ls-files` call catches new files, such as a `conftest.py` dropped into `tests/`.

<Fragment slot="short">
<p>Split the oracle from the code. CI grades every agent pull request against the tests from the base branch and rejects any pull request that touches `tests/` together with source. A test change goes in its own pull request, with the failing case and the reason, owned by a person through code owners. The agent can still propose that the test is wrong; it cannot make its own fix pass by changing it in the same change.</p>
</Fragment>
<Fragment slot="long">
<p>The conflict is autonomy against integrity, with review capacity as the budget. Blocking all test edits is cheap and wrong, because some tests encode the bug, and OpenAI's audit shows oracles are often wrong in exactly the narrow way agents trip on. Allowing them in the same pull request makes "tests pass" meaningless.</p>
<p>So the gate becomes two pull requests with different reviewers. The code pull request is graded by base-branch tests plus hidden tests the agent never saw, and a diff to protected paths fails it with a message the agent reads. The test pull request is small, carries the agent's justification, and goes to the squad's reviewer; it merges first, and then the code pull request is graded against the new base.</p>
<p>Inside the agent's session, a deny rule on `tests/**` gives fast feedback, with the known gap that a script can still write the file. The CI check is the control.</p>
<p>What I give up: a legitimate test fix now costs a human review and a round trip, so agent pull requests that need one take longer. I write that down with the count of test pull requests per week, and if the reviewer queue grows, I would rather add reviewers to test changes than relax the split.</p>
</Fragment>

## When this is wrong

Freezing the oracle freezes its mistakes. OpenAI's audit found material issues in 59.4% of the hard problems it reviewed in a benchmark that had already been filtered by expert review. A frozen narrow test rejects correct fixes forever, and an agent graded against it learns to reproduce one implementation. The split-pull-request design exists because the oracle needs a maintenance path, not only a lock.

Protecting `tests/` is not protecting the oracle. The oracle's verdict also depends on the code under test's import path, configuration files, fixtures, the simulator or environment it runs against, and anything that can run at import time. The take-home froze its simulator into `tests/` for that reason. Run the grading step in a clean environment from the base ref, and list everything it reads, before you call it out of reach.

Passing an untouched oracle is still not correctness. The agent can satisfy the tests' letter with code that hard-codes outputs or handles only the cases the tests exercise. Hidden tests and generated inputs raise the cost of that; they do not remove it. The long-running harness post's other finding stands next to this one: agents marked features done after unit tests and `curl` checks without verifying them end to end, and the fix there was a better check, browser automation run as a user would, not a better lock.

And the published evidence is anecdotal in shape. Anthropic's README reports the first-day submissions without a count, and the long-running post describes the prompt rule without saying how often agents edited tests before or after it. The audit is the one source here with a sample and a method, and it measures oracle quality, not agent behaviour.
