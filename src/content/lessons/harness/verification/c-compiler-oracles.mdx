## What it is and who ran it

Nicholas Carlini, a researcher on Anthropic's Safeguards team, published the account on 2026-02-05. He set 16 Claude agents to write a C compiler in Rust from scratch, with no internet access and only the Rust standard library, aiming at compiling the Linux kernel. Over nearly 2,000 Claude Code sessions across two weeks, using Claude Opus 4.6, the agents consumed 2 billion input tokens and produced 140 million output tokens for a total just under $20,000. The result is a 100,000-line compiler that builds a bootable Linux 6.9 on x86, ARM and RISC-V, compiles QEMU, FFmpeg, SQLite, Postgres and Redis, and passes 99% of most compiler test suites the post names, including GCC's torture tests.

The post presents the project as a capability benchmark the author has run across the Claude 4 series, and states that earlier Opus 4 models were barely able to produce a working compiler. Its harness is deliberately bare: no orchestration agent, no message passing between agents, only a shared git repository. The author says most of his effort went into the tests, the environment and the feedback, which is why it belongs in a module on verification. Everything below comes from the post; the source is public on GitHub.

**Restart loop.** Each agent is a shell `while true` loop that runs `claude -p` with the contents of `AGENT_PROMPT.md` and logs to a file named after the current commit. When a session ends, the next starts. The prompt asks the agent to break the problem into small pieces, track what it is working on and keep going until it is perfect. The post's warning beside the script is to run it in a container, not on your own machine.

**Claude Code session in a container.** Each agent runs in its own Docker container with the bare repository mounted at `/upstream`; it clones to `/workspace`, works locally and pushes back. Every session starts with no memory, so orientation comes from the repository: the prompt tells agents to keep extensive READMEs and progress files current, and stuck agents keep a running document of failed approaches.

**Lock files.** To stop two agents working on the same thing, an agent claims a task by writing a text file into `current_tasks/`, such as `parse_if_statement.txt`. If two agents try to claim the same task, git's synchronisation forces the second to pick a different one. The lock is released by removing the file after merging. It is an advisory lock kept in the same repository as the code, so claiming work and publishing work go through one channel; the post does not describe the mechanics beyond that.

**Sampled fast tests.** The test runner has a default `--fast` option that runs a random 1% or 10% sample. The sample is deterministic per agent and random across machines, so each agent sees the same subset every run and can tell a regression from noise, while the 16 agents together cover the whole suite. This is the answer to what the post calls time blindness: left alone, an agent will spend hours running tests.

**Output written for agents.** The harness prints a few lines and logs the rest to files, puts `ERROR` and the reason on the same line so `grep` finds it, and pre-computes summary statistics so the agent does not. Progress is printed rarely to keep the context clean.

**GCC as a known-good oracle.** Independent failing tests parallelise naturally, one per agent, and after the suite reached a 99% pass rate each agent took a different open-source project to compile. The Linux kernel did not parallelise: it is one build, every agent hit the same bug, fixed it and overwrote the others' fixes. The fix was a new harness that compiled most of the kernel with GCC and a random subset of files with Claude's compiler. If the kernel worked, the bug was not in that subset; if it broke, recompiling some of the subset with GCC narrowed it. One failing build became many independent per-file tasks again.

**Delta debugging.** Once per-file narrowing worked, some failures remained that appeared only when two files were compiled by Claude's compiler together and not when either was alone. The post says delta debugging techniques found those pairs.

**CI, added late.** Near the end, new features frequently broke existing functionality. The response was a continuous integration pipeline with stricter enforcement so that new commits could not break existing code. It arrived after the regressions did.

## Context strategy

No session inherits anything except the repository. That choice makes the repository the memory: READMEs, progress files, the list of claimed tasks and the failed-approaches document carry state between sessions and between agents. It also explains the test output rules. Each session's context is spent first on orientation and then on test output, so the harness keeps the second small, logs everything to files the agent can search, and computes aggregates for it. The post frames this as writing the harness for Claude rather than for the author.

## Tools and permission model

Each session runs with `--dangerously-skip-permissions`, so there is no permission prompt and no rule engine inside the session. The containment is the container: one per agent, no internet access at any point, and a git remote as the only shared resource. The post records one case of the agent damaging its own environment: it ran `pkill -9 bash`, killed its own loop and ended that agent's run. There is no orchestration agent. Specialisation was by prompt: one agent removed duplicate code, one improved the compiler's own performance, one improved the generated code, one critiqued the design as a Rust developer would, and one maintained documentation.

## Cost and latency

The post's totals are nearly 2,000 sessions, 2 billion input tokens, 140 million output tokens and just under $20,000 over two weeks. Per session that is about $20,000 / 2,000 = $10, about 1 million input tokens and about 70,000 output tokens, with input outnumbering output by 2,000 / 140, roughly 14 to 1. Across 16 agents, 2,000 sessions is 125 per agent, about 9 per agent per day over 14 days; if all 16 ran continuously, the average session lasted about 14 × 24 / 125 = 2.7 hours. That last figure assumes no idle time, which the post does not state. The author calls the project extremely expensive next to even the most expensive Claude Max plan, and a fraction of what it would have cost him to write the compiler himself.

## Failure modes

**One task, sixteen agents.** Parallel agents only parallelise when there are independent failures to divide. The kernel build was one task, and all agents converged on the same bug and overwrote each other. The oracle was the fix; without a known-good reference the project would have been serial at the hardest point.

**Regressions late in the project.** As the compiler grew, new features broke old ones. The sampled tests were per agent and partial by design, and the full guard came from CI added near the end. The post's description of the limits says new features and bug fixes still frequently broke existing functionality.

**Cheating the hard part.** The compiler can emit correct 16-bit x86 for real mode, but the output is over 60kb against the 32k code limit Linux enforces, so for that phase it calls out to GCC. The post describes this plainly as Claude cheating. It also lacks its own reliable assembler and linker; the demo used GCC's.

**Passing tests, weak output.** Even with all optimisations on, the compiler's output is less efficient than GCC's with optimisations off, and the Rust is reasonable but not expert. The tests checked correctness, so correctness is what the agents delivered. The author's own closing warning is that with autonomous agents it is easy to see tests pass and assume the job is done.

## What is not public

The post does not publish per-task failure data: how many tasks were attempted, how many sessions ended without a merged change, or how many attempts a typical fix took. It does not say how often lock contention occurred, meaning how often two agents claimed the same task and one had to back off, or how much work was lost to the frequent merge conflicts. It gives no breakdown of the $20,000 between the main work and the specialist roles, no date for when CI was added, and no measure of how many regressions it caught. Nothing here estimates those numbers.

## Interview questions about it

<Callout kind="interview" label="Interview question">
**"You are asked to use parallel agents to port a large internal service from one web framework to another in a quarter. There is no GCC for your service: no second implementation to compare against. Agent budget is fixed, and the service owners will not accept a freeze longer than two weeks. What is your oracle, and how do you split the work so sixteen agents do not all fix the same bug?"**
</Callout>

<Depth>
<Fragment slot="short">
<p>The old service is the oracle. I record production requests and responses, replay them against the ported service, and diff the responses, which makes every endpoint, and every recorded request class within it, an independent failing test an agent can claim. Where an endpoint cannot be compared (side effects, time-dependent output), I write contract tests by hand first. Tasks are claimed through lock files or an issue queue, each agent runs a fixed sample of the replay set, and the full replay runs in CI before merge from day one, not at the end.</p>
</Fragment>
<Fragment slot="long">
<p>The compiler project's lesson is that parallel agents need many independent failures, and the oracle is what creates them. GCC let the author route most files through a known-good path and a few through the new one. The equivalent here is routing: a proxy that sends most traffic to the old service and shadows a slice to the new one, comparing responses per route. A diff on route X is a task with an owner.</p>
<p>Normalisation is the work nobody budgets for: timestamps, ordering, ids and headers differ legitimately, and an oracle that flags them sends agents chasing noise. That normaliser is written by a person, reviewed, and treated like protected test code.</p>
<p>Partition the replay set so each agent has a fixed sample for fast feedback, and run the full replay in CI on every merge from the start, because the compiler post's late CI is the part I would not copy.</p>
<p>What I give up: recorded traffic covers what users do, not what they could do, so rarely used paths have weak coverage, and I write down the routes below a traffic threshold that need hand-written tests or a person's sign-off.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li>Replaying traffic means storing production payloads with customer data. Security says no. What is your oracle now, and what risk do you accept in writing?</li>
<li>Half the diffs turn out to be the old service's bugs. Who decides whether the port reproduces a bug, and how do agents learn the decision?</li>
<li>Two weeks in, merge conflicts eat more agent time than fixes. Do you reduce the number of agents, change how work is split, or add an orchestrator, and what would make you reverse it?</li>
</ul>
