## Where "done" gets decided

A coding agent ends its turn when the transcript looks finished to the model. Nothing in the loop checks that claim unless the harness puts something there. Claude Code's best-practices page (checked 2026-10-28) states the consequence directly: without a check, "looks done" is all the agent has, and the user becomes the test suite.

The fix the page recommends is narrow: give the agent something it can run that comes back pass or fail, and put the command in `CLAUDE.md`. The page calls that command the single most useful line in the file. Its example `CLAUDE.md` holds three commands (install, run one test file, typecheck), two conventions and one gotcha, and nothing about architecture: the file is for what the agent cannot work out from the code, and which command the team trusts as proof is one of those things.

The decision in this lesson is who enforces the check. The same page sorts every control into model-decided and harness-enforced, and for "when it's done" the two columns are a request for evidence, `/goal` or `/code-review` on one side, and tests, typecheck, a `Stop` hook or CI on the other. A line in `CLAUDE.md` saying "always typecheck before you finish" is model-decided: the page says it works most of the time, not every time.

## Four strictness levels

The Claude Code page orders the options from the model deciding to the harness enforcing.

**In the prompt.** "Run the auth tests after, and keep going until they pass." The model decides when it is satisfied. No setup, no guarantee.

**As a goal.** `/goal all tests in tests/auth pass and lint is clean` sets a condition that a separate model checks against the conversation after every turn. The hooks reference describes `/goal` as a built-in shortcut for a session-scoped, prompt-based Stop hook. The check is still a model reading the transcript, so it can be satisfied by a transcript that claims the tests pass.

**As a Stop hook.** A command hook on the `Stop` event runs whenever the agent tries to end its turn. Exit code 2 blocks the stop, and whatever the script printed to stderr goes back to the agent as the reason. The page's whole example is one line in `.claude/settings.json`:

```json
{ "hooks": { "Stop": [ { "hooks": [ { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" } ] } ] } }
```

The redirect to stderr is the important part: the compiler's error list becomes the agent's next instruction. This is a pre-commit hook in shape, with one difference that drives the rest of this lesson: the output is not read by a person who knows the codebase, it is read by the agent that just wrote the code, and it is the entire content of the next turn.

**By someone who did not write the code.** `/code-review` reviews the diff in a fresh subagent that never saw the conversation. The page's caution about reviewers applies to any model check: a reviewer asked to find problems always finds something, so the review prompt it recommends ends with "report gaps that affect correctness and skip style".

Whichever level you use, the page asks for evidence: the command the agent ran and its output. "All tests pass" in a final message is a claim; the output is the evidence, and for a run nobody watched it is the only evidence.

The Agent SDK post (2025-09-29) gives the same ordering by robustness. Rules-based feedback, meaning lint and types, is "the best form of feedback". Visual feedback through screenshots, automated with Playwright, comes next for UI work. An LLM judge comes last: "generally not a very robust method", with heavy latency tradeoffs, worth it only where the gain pays for that.

## What the Stop event gives you, and what stops it

The hooks reference (checked 2026-10-28) fixes the mechanics a production hook depends on.

The input carries `stop_hook_active`, true when the agent is already continuing because a stop hook blocked it, plus `last_assistant_message`, `background_tasks` and `session_crons`. The reference tells you to check `stop_hook_active` or the transcript so you do not block forever on a condition that will never resolve.

Claude Code also enforces its own bound: after stop hooks have continued the turn eight times in a row, it overrides the next block and ends the turn. The count resets every time the agent calls a tool. So a hook that keeps failing while the agent keeps editing never trips the cap; the cap only catches the case where the agent answers a block with text and no tool call, which is what an agent does when it has decided it cannot fix the failure. `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap.

Two more details change designs. The default timeout for a command hook is 600 seconds, so a check that takes longer is killed rather than awaited. And `Stop` has no matcher: it fires at the end of every turn, including a turn the agent ends to ask you a question. A strict hook in an interactive session therefore sends back clarifying questions along with unfinished work.

There is also a softer path. Returning `hookSpecificOutput.additionalContext` instead of a block keeps the conversation going under the same loop protections, but the transcript labels it "Stop hook feedback" rather than a hook error. That fits guidance ("run the test suite before finishing"); a block fits a rule.

## A hook you can measure

A check is a control with a false-positive rate and a cost, so it needs a log. This hook runs the repo's check, logs one line per stop attempt, and returns the tail of the failure output. Python, standard library only:

```python
import json
import subprocess
import sys
import time
from pathlib import Path

CHECK = ["pnpm", "-s", "check"]     # the command CLAUDE.md names: typecheck, lint, affected tests
TAIL = 40                           # lines of failing output the agent gets back

event = json.load(sys.stdin)
log = Path(event["cwd"]) / ".claude" / "stop-checks.jsonl"
started = time.monotonic()
proc = subprocess.run(CHECK, cwd=event["cwd"], capture_output=True, text=True)
record = {
    "session": event["session_id"],
    "continuing": event.get("stop_hook_active", False),
    "passed": proc.returncode == 0,
    "seconds": round(time.monotonic() - started, 1),
}
log.parent.mkdir(exist_ok=True)
with log.open("a") as f:
    f.write(json.dumps(record) + "\n")

if proc.returncode != 0:
    tail = (proc.stdout + proc.stderr).splitlines()[-TAIL:]
    print(f"{' '.join(CHECK)} exited {proc.returncode}. Fix this before finishing:", file=sys.stderr)
    print("\n".join(tail), file=sys.stderr)
    sys.exit(2)
```

The tail limit is deliberate. The C compiler post's harness printed at most a few lines and logged the rest to a file, with `ERROR` and the reason on one line so `grep` finds it, because a check that prints thousands of lines spends the agent's context on noise. The same post's test runner had a `--fast` mode that ran a 1% or 10% sample, deterministic per agent, so a check inside the loop stayed short while the full suite still ran elsewhere.

The report reads the log per session:

```python
import json
import sys
from collections import defaultdict

sessions = defaultdict(list)
with open(sys.argv[1]) as f:
    for line in f:
        r = json.loads(line)
        sessions[r["session"]].append(r)

events = [r for rs in sessions.values() for r in rs]
bounced = sum(1 for rs in sessions.values() if not all(r["passed"] for r in rs))
ended_red = sum(1 for rs in sessions.values() if not rs[-1]["passed"])
print(f"{len(sessions)} sessions, {len(events)} stop events, {sum(not r['passed'] for r in events)} blocked")
print(f"sent back at least once: {bounced / len(sessions):.1%}; ended on a failing check: {ended_red}")
print(f"check time per session: {sum(r['seconds'] for r in events) / len(sessions):.0f} s")
```

"Ended on a failing check" counts sessions whose last stop attempt failed: the cap fired, the hook timed out, or the user interrupted. That number should be near zero, and when it is not, the hook is blocking on something the agent cannot fix.

## Running it headless

In CI the same check works with `claude -p`. The best-practices page lists the flags a scripted run needs: `--allowedTools` with `--permission-mode dontAsk` to refuse anything not pre-approved, and `--max-turns` or `--max-budget-usd` to bound it. It also recommends `--bare` so a run does the same thing on every machine, and `--bare` skips hooks along with skills, plugins, MCP servers and `CLAUDE.md`. A headless run that relies on a Stop hook for its definition of done has to pass the hook back in through `--settings`, which the headless docs list as the way to load settings in bare mode, or leave `--bare` off, and you should confirm it fired by reading the hook log rather than assuming it.

The page's checklist for unattended runs has five questions; two of them are this lesson. Does it know what done looks like, and can it check its own work? The other three (what it may touch, what stops it, who signs off) are why the hook alone is not the merge gate: CI and branch protection still run after it.

## When this is wrong

A passing check is evidence that the check passes. If the tests do not cover the change, the hook turns a confident wrong answer into a confident wrong answer with a green log. The next lesson covers the worse case, where the agent can edit the tests that stand between it and done.

The hook fires on every turn end. In interactive use that includes turns where the agent stops to ask a question, and a strict hook will send the question back. For interactive sessions the softer `additionalContext` path, or a hook that only blocks when files changed since the last passing run, is often the better default; the hard block fits unattended runs.

A flaky check is worse than no check inside this loop. A person learns which test is flaky; an agent handed a failing test reads it as a defect and changes code until it passes, or until the cap ends the turn. Quarantine known flaky tests out of the Stop check and keep them in CI where a person reads the result.

Rules beat judges for code because code has rules. For work where the defect is taste, layout or whether a feature is complete end to end, there may be no command that returns pass or fail, and the check becomes a screenshot comparison or a separate evaluator, both slower and less reliable. The Agent SDK post's ordering is a ranking of robustness, not a menu you can always pick the top item from.

Finally, every line here is version-sensitive. The cap of eight, the 600-second default timeout, the `/goal` command and the `--bare` behaviour are from the Claude Code documentation as checked on 2026-10-28; other harnesses expose the same idea under different names, and some do not let a hook block a stop at all.
