## The decision

A harness change reaches every session through some set of gates: code review and tests, dogfooding, an eval suite, ablations, a soak period, a gradual rollout, a deployment scheme for sessions already running. Each gate costs calendar time and compute. The decision is which gates a given change gets, and the useful evidence is a postmortem in which three changes each passed the gates they were given and still shipped regressions.

Anthropic's April 2026 postmortem traced weeks of reports that Claude Code had got worse to three harness changes. The API and inference layer were unaffected.

Each change hit a different slice of traffic on a different schedule, so together they looked like broad, inconsistent degradation, and neither internal usage nor evals reproduced it at first. That is the attribution problem from [the first lesson of this module](/learn/harness/evaluating-harnesses/attribution), created by the release process itself.

## The inputs that change it

**What the change touches.** Four classes behave differently. Prompt text and tool descriptions change model behaviour on every request and show up on an eval, if the eval is broad enough. Defaults (effort, turn limits, compaction thresholds) trade quality against latency or cost, and the eval can measure the quality side but not whether users accept the trade. Request-construction code (what context management sends to the API) fails as a bug, often only in particular session states. Model-specific tuning helps one model and can hurt the others.

**Whether a fresh-session eval can see the failure.** The thinking-clearing bug needed a session that had been idle for over an hour and then continued. An eval harness that starts each task in a new session never enters that state, however many tasks it runs. Any change whose behaviour depends on session age, idle time, resumption or accumulated context needs a gate that runs in wall-clock time.

**How many models the change spans.** The verbosity line was added for Opus 4.7, which Anthropic describes as more verbose than its predecessor; it shipped to three models and cost Opus 4.6 the same 3% on the eval that caught it.

**How small an effect you must detect.** Anthropic's multi-agent team started evaluating with about 20 queries, which was enough because early prompt changes moved success from 30% to 80%. At 20 tasks and 50% success, a single run's 95% half-width is 1.96 × √(0.25 / 20) = ±21.9 points: fine for a 50-point effect, useless for 3. For a paired eval where the two versions disagree on a fraction d of tasks, the half-width of the difference is about 1.96 × √(d / n). With d = 0.1, getting it down to 3 points needs n = 0.1 × (1.96 / 0.03)² ≈ 427 tasks, per model.

**How long sessions live.** The multi-agent post describes agents as stateful webs of prompts, tools and execution logic running almost continuously; a deploy lands on sessions mid-task. A harness change that alters persisted state or prompt layout needs a plan for those sessions.

**What delay costs.** A soak period is calendar time with the old behaviour. For a security fix that is the wrong trade; for a verbosity tweak it is cheap.

## The options and when each wins

**Code review, tests and dogfooding alone** win for changes that never reach a model request: rendering, logging, local tooling. They lose for request construction, as the postmortem shows: the bug passed all of them. Anthropic's back-test is the one cheap improvement on this gate: Code Review with Opus 4.7 found the bug when given the repositories needed for full context, and Opus 4.6 did not.

**Request invariants in production** are this playbook's addition, not a postmortem commitment. Assert properties of what the harness sends, per session, and emit a metric when they fail: the history is append-only between turns except at a logged compaction or clearing event; a clearing event fires at most once per idle period; the system prompt hash matches the registry entry for the model. The thinking-clearing bug would have failed the second assertion on its second turn. Cache hits are the free version of the same signal: the bug also caused cache misses, so a drop in cache-read share among sessions older than an hour was visible in telemetry the harness already had.

**A broad per-model eval suite** wins for prompt text, tool descriptions and defaults, and Anthropic now commits to one for every Claude Code system prompt change. Its cost scales with models × suite size × trials, and the sample-size arithmetic above says a suite small enough to run on every change cannot see 3-point effects.

**Line-by-line ablations** win when several prompt edits ship together. Removing one line at a time attributes the effect to a line, which is how the 3% was found. The cost is lines × models × suite, so run them on bundles before release and on the whole prompt periodically, not on every one-line edit.

**A soak period** wins for state-dependent failures: staff using the exact public build for days, not the feature-testing build, which is the first commitment in the postmortem. It loses when the failure needs traffic shapes staff do not produce.

**A gradual rollout** by stable hash, with rollback triggers written before it starts, wins for trade-offs users judge, such as the effort default, and for regressions that only show on the real task distribution. It needs metrics per cohort, and it creates the overlapping-slices problem unless every cohort is tagged with the exact set of changes it carries.

**A rainbow deployment** wins when sessions outlive deploys: the old and new versions run together, new sessions go to the new version, and in-flight sessions finish on the version they started on. The multi-agent post uses it for exactly that reason. The costs are two versions in production, version-tagged telemetry and persisted state both versions can read.

**Model gating** wins whenever a change is motivated by one model's behaviour: apply it only to that model, by configuration, so other models keep their tested prompt. Anthropic added guidance to its own CLAUDE.md to enforce this.

## A worked decision

The case, all scenario: a platform team runs an internal coding agent on three models (call them A, B and C), interactive and in CI, with CI sessions running up to six hours. This week's release carries three changes: a lower compaction threshold in the context manager; two system-prompt lines to curb model C's verbosity; and a default turn limit lowered from 200 to 120 to cut cost. Releases are weekly and the team has eval compute for about 2,000 task runs a week.

**Compaction threshold** (request-construction code, state-dependent). Gates: request invariants shipped first, in the release before, so the baseline exists; a seven-day soak on internal users of the exact build; then a rainbow deployment so six-hour CI sessions finish on the old context manager. Rollback trigger: cache-read share among sessions past their first compaction more than 5 points below the old cohort's for two consecutive hours, or any invariant failure rate above zero that the old version does not show.

**Model C prompt lines** (prompt text, one model). Gates: gated to model C by configuration; a two-line ablation on C (both lines, each alone, neither) on a 400-task paired suite, close to the 427 tasks the arithmetic above asks for. That is 1,600 of the week's 2,000 runs, so A and B get no eval for this change, which is acceptable only because the gate guarantees their prompt is byte-identical.

**Turn limit** (a default that trades quality for cost). Gates: a per-model run on the remaining budget measuring how many currently resolved tasks need more than 120 turns, which is a count from existing trajectories rather than a new eval; then a rollout at 5%, 25% and 100% over two weeks with the limit shown to users. Rollback trigger: resolved-task rate in the cohort below the control by more than the interval of the paired comparison, or a rise in users raising the limit by hand, which is the effort-default lesson: users who keep a default are not consenting to it.

What the team gives up: a week of calendar time on the compaction change, any evidence about the prompt lines on models A and B, and a faster cost saving from the turn limit. The release ledger records which cohort carries which of the three, so a complaint can be mapped to a change.

## What to measure in the first week

Measure by version cohort, never by calendar date, because overlapping rollouts make date-based comparisons attribute one change's effect to another.

- Cache-read share of input tokens per request, split by session age and by whether the session has crossed an idle or compaction event.
- Invariant failures per thousand requests, by version.
- Tokens, turns and output tokens per turn per task, by model.
- The paired replay eval per model, nightly, on a fixed task set.
- Settings drift: the share of sessions on each default and the share that changed it.
- Explicit feedback rate and interrupt rate per cohort.
- For rainbow deployments: in-flight sessions still on the old version, which should fall to zero within the longest session length, and resume errors at the version boundary.

## When this is wrong

The evidence is one vendor's postmortem about one product, written by the team that owns both the harness and the model. A team that consumes a model through an API has less visibility into model-side changes and more need for its own invariants and replay evals, because it cannot ask the model team what changed.

Every gate here costs time, and for some changes the cost is wrong: a fix for an actively exploited permission bypass ships through review and tests, without soak or gradual rollout, with the risk written down.

Rainbow deployments assume both versions can read persisted state. If the change alters the session format, the old version must at least refuse a new-format session cleanly, or in-flight sessions will fail at resume, which is a worse outcome than the regression being guarded against.

Per-model gating assumes the model list is short. A harness that routes across many models, including a customer's choice of endpoint, cannot run a broad suite per model per change; it needs a small canary suite per model and a larger one on the models carrying most traffic, with the gap stated.
