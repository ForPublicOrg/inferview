## Each benchmark fixes something different

A coding-agent benchmark is four things: a task set, a harness, a grader and a date. The benchmarks in common use differ in which of those they hold constant, and that decides the claim each can support. The database analogy is TPC-C against TPC-H: both are "database benchmarks", and quoting one to answer a question about the other is a category error. The difference here is that two of the four parts decay. Public tasks leak into training data, and graders built from one human patch reject correct alternatives, so a benchmark's meaning changes with its age and with how close the field is to its ceiling.

The [previous lesson](/learn/harness/evaluating-harnesses/attribution) covers holding model, harness and infrastructure fixed. This one covers which instrument to point at which question.

## SWE-bench Verified: saturated and contaminated

Verified is 500 problems that OpenAI and expert reviewers kept in 2024 from 1,699 SWE-bench problems, each reviewed by three engineers. The original SWE-bench drew issues from 12 Python repositories; the agent sees the issue and the repository before the fix, and passes only if hidden tests that the reference fix made pass now pass and regression tests still pass.

On 2026-02-23 OpenAI stopped reporting it and recommended others do the same. Its reasons are the two failure modes of any public benchmark:

- **The grader rejects correct work.** OpenAI audited the 138 problems that o3 did not solve consistently over 64 runs, 27.6% of the set, with at least six engineers per problem. It found material issues in 59.4% of them: 35.5% had narrow tests that require implementation details the issue never states (in one example, the tests import a helper function by a name the issue never mentions), 18.8% had wide tests that check functionality the issue never asked for, and 5.1% had other problems.
- **Models have seen the answers.** OpenAI's red-teaming found every frontier model it probed could reproduce the gold patch or verbatim problem details for some tasks, and its own GPT-5.2 solved 31 tasks the audit had judged almost impossible.

<p>59.4% of 138 is 82 problems, so the ceiling is (500 − 82) / 500 = <b>83.6%</b>. OpenAI reported the state of the art rising from 74.9% to 80.9% in the six months before the post, which put the field within 2.7 points of that bound. Once the sound tasks are mostly solved, further points have to come from the flawed ones, where passing a narrow test means producing the implementation the reference patch chose. OpenAI found that models which had seen the problems in training were more likely to pass them, which is why gains at the top stop meaning capability.</p>
</Predict>

**What Verified can still support:** a regression check of your own harness across versions with the model fixed, where both arms suffer the same flawed tasks, and comparisons among older or smaller models far from the ceiling. **What it cannot:** ranking frontier models, any gap of a few points above about 75%, and anything about languages other than Python.

## SWE-bench Pro: bigger patches, private splits

SWE-bench Pro (September 2025) is OpenAI's recommended replacement. It has 1,865 problems from 41 repositories in three splits: 731 public problems from 11 repositories under strong copyleft licences such as the GPL, 858 held-out problems from 12 repositories kept private to detect overfitting later, and 276 commercial problems from 18 startup codebases the authors bought, kept private with results published. The 731 + 858 + 276 add to the total. Reference solutions average 107.4 lines across 4.1 files, and no task changes fewer than 10 lines.

The paper scores every model with the SWE-Agent scaffold, the same prompt and a 50-turn limit. On the public set Claude Sonnet 4.5 reached 43.6% and GPT-5 (high) 41.8%; on the commercial set the best, Claude Opus 4.1, reached 17.8%. Two design choices bound what it measures. Problem statements are augmented with requirements and an interface specification, so Pro measures implementing a specified change, not resolving an ambiguous issue. The paper measures the size of that choice: under a $2 per-task cap, GPT-5 (high) resolved 25.9% with the augmentations and 8.4% with the problem statement alone. And the copyleft argument (that licences deter inclusion in commercial training sets) is a deterrent, not a guarantee: OpenAI's post says its contamination pipeline found cases on Pro, rarer and less severe than on Verified, with no verbatim gold patch.

**What Pro supports:** model comparisons under one stated scaffold, multi-file work, and the public-to-commercial gap as a measure of how much a score depends on familiar code. **What it cannot:** the value of a different harness (one scaffold), or a score from another scaffold or budget compared to the paper's. The same paper reports GPT-5 (high) at 41.8% in its main table and 25.9% once each task is also capped at $2.

## Terminal-Bench 2.0: beyond repository patches

Terminal-Bench 2.0 is 89 tasks chosen from 229 submitted by 93 contributors, each with a Docker image, an instruction, a reference solution and tests that check the final container state rather than the commands used. Reviewers spent about three hours per task. The tasks are not mostly patches: they range from training a model to building Linux from source, reverse engineering binaries and fixing the OCaml garbage collector. Task authors estimated under one hour of expert time for 36 tasks, 48.6% of the 74 the paper's time table covers. Agents may reach the internet. The best published result is Codex CLI with GPT-5.2 at 62.9%, and the authors write that the benchmark may saturate within the next year.

Its distinguishing feature for harness work is the Harbor framework, which runs Claude Code, Codex CLI, OpenHands, Mini-SWE-Agent and the neutral Terminus 2 on the same tasks. **What it supports:** harness comparisons with the model fixed, and long-horizon terminal work outside Python repositories. **What it cannot:** small gaps, because 89 tasks give a single-run 95% interval of about ±10 points at 60%, and comparisons across resource configurations, where Anthropic measured a 6-point swing from enforcement alone.

## tau-bench: policy and consistency, not code

tau-bench is not a coding benchmark, and it belongs on the map because it measures the property coding benchmarks hide: whether the agent does the same correct thing every time under a written policy. Its 115 retail and 50 airline tasks pair an agent with an LLM-simulated user (gpt-4-0613 in the paper) and domain tools; a trial scores 1 only if the final database matches the one outcome the policy allows and the replies contain the required facts. The paper introduced pass^k, the chance that all k trials of a task succeed: gpt-4o with function calling reached 61.2% pass^1 in retail and 35.2% in airline, and pass^8 in retail fell below 25%.

The cost line matters for harness design: the gpt-4o agent cost $0.38 per retail task, and 95.9% of that was input tokens, mostly the policy document and tool definitions resent on every turn. That is a harness property (prompt layout and caching), not a model property.

**What it supports:** consistency claims under policy, and the effect of harness changes to prompts and tool definitions on pass^k. **What it cannot:** anything about editing code, and anything finer than its simulator: a user played by a model bounds how realistic the conversation is.

## The bash-only leaderboard: one harness, many models

The SWE-bench site can filter Verified to runs in the mini-SWE-agent environment; its own description is that these scores compare models rather than harnesses. mini-swe-agent is an agent class of about 100 lines of Python with bash as its only tool, no use of the vendor's tool-calling interface, and each command run as an independent subprocess, so the harness has almost nothing model-specific in it.

The leaderboard also records dollars, which turns it into a price-performance table. Three runs from 2026-02-17 with mini-SWE-agent 2.0.0, dividing each run's total cost by 500 tasks and then by the resolve rate:

## "Our harness scores X"

The questions that turn the sentence into a claim:

- Which benchmark, version and split, and which tasks were excluded?
- Which model snapshot and reasoning effort, and are they the same as the comparison row's?
- Which harness version, turn limit and cost cap?
- One attempt or best of several, and was a verifier or test run used to choose?
- How many trials per task, and what is the interval?
- What resource allocation and kill limit, and what share of trials ended in infrastructure errors?
- When was it run, relative to the model's training cutoff and the benchmark's publication?
- What did it cost per task and per resolved task?
- How do the benchmark's languages and task types compare with our repositories?

For an internal decision the last question usually ends the discussion: a paired run on 50 to 100 of your own past tasks answers it more directly than any public score.

## When this is wrong

The map treats each benchmark's limits as fixed. They move: Verified was a reasonable frontier benchmark in 2024, Pro's public split will contaminate the same way over time, and the held-out split exists precisely to measure that. Re-read a benchmark's status before quoting it, not the lesson's.

The half-widths assume one trial per task and tasks as a sample. Leaderboards that run several trials and treat the task set as fixed report much narrower intervals, which are correct for "on these tasks" and wrong for "on our work".

All of these grade end states with tests or database comparisons. None measures whether a reviewer would accept the patch, how readable the diff is, or how often the agent should have stopped and asked. If your agent's failures in production are of that kind, every number on this page is beside the point, and the instrument you need is human review of sampled sessions.
