## A score has three authors

A coding-agent benchmark result is the output of one end-to-end system test: a model snapshot at a reasoning setting, a harness at a version with its prompts, tools, turn limit and budget, and an execution environment with CPU, memory, kill policy, network and an API whose latency moves with traffic. Change any one and the number moves. "Harness B is better than harness A" is a claim about one of the three with the other two held fixed, and most published comparisons do not hold them fixed.

The closest systems analogy is a performance regression that appeared in the same release as a compiler upgrade and a move to new hardware. The difference is that the agent is interactive: the environment is not a passive host for the program but part of the problem, because the agent's strategy depends on what the environment lets it do. A tight memory limit does not just slow a run, it kills the strategies that install heavy dependencies and rewards the ones that do not.

The [agent-evals module](/learn/evals/agent-evals) covers grading, trials and pass^k. This lesson covers the step before grading: designing a run whose difference can be attributed to the harness.

## Infrastructure alone moves the score by more than a leaderboard gap

Anthropic's February 2026 post on infrastructure noise is the measurement to know. Running Terminal-Bench 2.0 on Google Kubernetes Engine, the team found its scores off the public leaderboard's and up to 6% of tasks failing on pod errors. The cause was enforcement. Container runtimes take two numbers, a guaranteed allocation and a hard kill limit; Anthropic's setup set both to the task's specified resources, so any transient spike was an out-of-memory kill. The leaderboard's sandbox provider allows temporary overallocation.

They then ran six resource configurations with the same Claude model, harness and tasks, from strict (1x, allocation equal to the kill limit) to uncapped:

The shape matters more than the endpoints. Up to 3x, extra headroom removes spurious kills, and most of the tasks that crashed at 1x would have failed anyway: the eval becomes more stable without becoming easier. Above 3x, infra errors fall only 1.6 more points while success rises almost 4, because generous limits let the agent pursue strategies that only work with room: installing pandas, networkx and scikit-learn for a Bayesian-network task, running memory-heavy test suites. Past that point the resource limit is changing what the benchmark measures. A SWE-bench crossover on 227 problems with 10 samples each found the same direction at smaller size: 1.54 points higher at 5x RAM than at 1x.

So a harness that prefers heavyweight strategies and one that prefers lean ones can swap ranks as the ceiling moves, and a harness comparison is valid only at a stated ceiling. The post also reports, unquantified, that pass rates moved with time of day, probably through API latency: run A on Monday and B on Thursday and the calendar is a fourth author.

## Harness effects: from inside the noise to seventeen points

Terminal-Bench 2.0 is the best public dataset for the harness term, because its Harbor framework runs several agents against the same 89 tasks, and the paper ran every supported model and agent pair at least five times (32,155 trials in total). Holding the model fixed and reading across Table 2:

**The harness effect is conditional on the model.** For Sonnet 4.5 the four harnesses sit inside each other's intervals; for Haiku 4.5 OpenHands is 16.5 points below the best. "Harness B is better" without "for model M at effort E" is not a claim the data supports, and a fleet that routes to several models needs the comparison per model.

**A vendor's own harness is not reliably its model's best.** Claude Code was below Terminus 2 for Opus 4.5, and Gemini CLI was below Terminus 2 and Mini-SWE-Agent for Gemini 2.5 Pro. Codex CLI was the best GPT-5.2 harness by 8.9 points. (Gemini CLI's individual tiers stopped serving on 2026-06-18 in favour of Antigravity CLI; the row predates that.)

**Vendor harnesses cannot be crossed.** The paper ran Claude Code, Codex CLI and Gemini CLI only with their own vendor's models. A neutral harness, here Terminus 2 with one tool (a tmux terminal), makes model comparison possible, but it has biases of its own, just not a vendor's.

**The model term is usually larger.** Codex CLI with GPT-5.2 scored 62.9% against 49.6% with GPT-5, a 13.3-point move from the model with the harness fixed. The paper's own conclusion is that model selection usually matters more than the scaffold. The Haiku and Gemini 2.5 Pro rows are the exceptions, and both are among the weaker models in the table: the harness term grows where the model leaves more to the scaffold.

Public leaderboards rarely give you rows this clean. On the SWE-bench Verified leaderboard, the same snapshot (Claude Opus 4.5, 20251101, medium effort) appears at 74.4% under mini-SWE-agent 1.16.0 and at 79.2% under live-SWE-agent, an entry its authors submitted that the maintainers have not marked as checked. The bash-only view exists precisely to hold the harness fixed, and even there Opus 4.5 at high effort with mini-SWE-agent 2.0.0 scores 76.8%: harness version and effort moved together, so the 2.4 points over 74.4% cannot be split between them.

Run budget is a harness parameter too. The SWE-bench Pro paper reports GPT-5 (high) at 41.8% on its 731-task public set with a 50-turn limit, and 25.9% in an appendix table that also caps each task at $2. The paper does not present the two as a controlled pair, but a cap that coincides with a 38% lower score belongs in every comparison's configuration record.

## How much noise one run carries

<Predict id="eh-attr-single-run" question="What is the half-width of a 95% interval on that score, in percentage points?" answer={10.2} tolerance={1} unit="points">
<Fragment slot="prompt">
<p>One run of a harness on Terminal-Bench 2.0's 89 tasks, one trial per task, resolves 60%. Treat the 89 tasks as a sample from the work you care about and use the normal approximation.</p>
</Fragment>
<p>Standard error is the square root of 0.6 × 0.4 / 89, which is 0.0519; 1.96 × 0.0519 = 0.102, so <b>about ±10.2 points</b>. Two such independent runs have a difference whose standard error is 0.0519 × √2 = 0.0734, a 95% half-width of about ±14.4 points. A 3-point leaderboard gap is invisible at this sample size unless the comparison is paired and repeated.</p>
</Predict>

Pairing is what makes small benchmarks usable. Run both harnesses on the same tasks and only the tasks where they disagree carry information. Suppose A and B each resolve about 60% of the 89 tasks, B alone solves 12 and A alone solves 8. The difference is 4 / 89 = 4.5 points, and its standard error is the square root of (12 + 8 − (12 − 8)² / 89) divided by 89: √19.82 / 89 = 0.050, a half-width of 9.8 points. Pairing cut the interval from ±14.4 to ±9.8 and B's 4.5-point lead is still inside it.

Repeated trials per task shrink the trial-to-trial part of the variance, not the task-sampling part. That forces a decision about the question. If the question is "is B better on these 89 tasks", the tasks are fixed and enough trials can make the interval as narrow as Terminal-Bench's ±2.5 to ±3 points (the paper does not say in its text how those intervals were computed). If the question is "is B better on our work", the 89 tasks are a sample and no number of trials on them narrows the interval below what 89 tasks allow. Anthropic's remark that naive binomial intervals already span 1 to 2 points fits the first question; with the 89 tasks treated as a sample, the interval is several times wider. Most procurement decisions are the second question.

## The run that isolates the harness

An unrecorded variable cannot be held fixed, so the configuration record comes first:

- **Model:** snapshot identifier, reasoning effort or thinking budget, sampling settings, provider endpoint and region. Terminal-Bench ran every model at the provider's default effort; your vendor's harness may set a different default than your own.
- **Harness:** version or commit, system prompt hash, tool set, turn limit, cost limit, context-management settings (compaction threshold, output truncation).
- **Infrastructure:** sandbox provider, resource allocation and kill limit per task, concurrency, network policy, the time window of each run.
- **Tasks and grader:** benchmark version, task list, grader version.

The run:

1. Vary one thing. A harness change that also moves the effort default is two variables, and the result belongs to the bundle.
2. Pair by task and interleave. Schedule A and B trials for the same task in the same time window on the same pool, so time-of-day and cluster health hit both arms.
3. Set the resource ceiling deliberately: a guaranteed allocation and a separate, higher kill limit, calibrated (Anthropic's suggestion) so that scores at the floor and the ceiling fall within noise of each other. Record the multiplier.
4. Classify every trial's exit as pass, fail or infra (pod killed, sandbox error, API error after retries) from logs, not from the grader, and report the infra rate per arm.
5. Report the paired difference twice: infra counted as failure, and infra trials excluded. If the two readings disagree, the infrastructure is the result and the harness question is not yet answered.
6. Report tokens, turns and dollars per trial beside the resolve rate: a harness that wins by spending more is a budget decision.

The data below is synthetic: harness B is given a 3-point per-trial lift, but its trials ran on a pool with a 6% infra failure rate against A's 0.5%.

```python
import random
from statistics import mean

def rate(runs, infra_as_fail):
    if not infra_as_fail:
        runs = [r for r in runs if r != "infra"]
    return sum(r == "pass" for r in runs) / len(runs) if runs else None

def paired_report(a, b, infra_as_fail, n_boot=4000, seed=0):
    """a, b map task id to a list of trial outcomes: 'pass', 'fail' or 'infra'."""
    diffs = []
    for t in sorted(set(a) & set(b)):
        ra, rb = rate(a[t], infra_as_fail), rate(b[t], infra_as_fail)
        if ra is not None and rb is not None:
            diffs.append(rb - ra)
    rng = random.Random(seed)
    boots = sorted(mean(rng.choices(diffs, k=len(diffs))) for _ in range(n_boot))
    lo, hi = boots[int(0.025 * n_boot)], boots[int(0.975 * n_boot)]
    return round(100 * mean(diffs), 1), (round(100 * lo, 1), round(100 * hi, 1))

# Synthetic data: 89 tasks, 5 trials per harness per task. Harness B is 3 points
# better per trial, but its runs went to a cluster with a 6% infra failure rate.
rng = random.Random(42)
p = {f"task-{i:02d}": rng.betavariate(0.6, 0.6) for i in range(89)}
def trials(task, lift, infra):
    out = []
    for _ in range(5):
        if rng.random() < infra:
            out.append("infra")
        else:
            out.append("pass" if rng.random() < min(1.0, p[task] + lift) else "fail")
    return out
A = {t: trials(t, 0.00, 0.005) for t in p}
B = {t: trials(t, 0.03, 0.06) for t in p}
print("infra counted as fail:", paired_report(A, B, infra_as_fail=True))
print("infra runs excluded:  ", paired_report(A, B, infra_as_fail=False))
# infra counted as fail: (2.9, (-2.2, 8.3))
# infra runs excluded:   (5.5, (0.3, 10.7))
```

Counted as failures, B's lift sits inside an interval that covers zero; with infra trials dropped, the interval just clears zero and the point estimate is nearly double the true lift, because random noise in 89 tasks is that large. Neither line is the harness effect. The action is to rerun B on A's pool. The bootstrap resamples tasks, so it answers the "our work" question; to answer the "these 89 tasks" question, resample trials within each task instead.

## When this is wrong

The three-author model treats the terms as separable. They are not: harness effects depend on the model, and resource effects depend on the agent's strategy. A harness effect measured at one model and one ceiling is a point on an interaction surface, valid for that configuration until either moves.

Holding infrastructure fixed is not always the goal. If production runs on tight sandboxes, an uncapped benchmark run measures a system you do not operate; for product decisions, measure at your production ceiling.

Some benchmarks drift underneath you. Terminal-Bench lets agents reach the internet, and the paper notes that even stable external resources change, so a rerun months later may not be the same test.

Selecting the best configuration inflates the winner. Terminal-Bench's headline figure reports each model with the harness that scored best for it; with several harnesses per model, the maximum of noisy scores is biased upwards. When you pick the best of several harness variants on one run, confirm the winner on a fresh run before reporting its margin.
