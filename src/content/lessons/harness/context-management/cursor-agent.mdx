## What it is and who runs it

Cursor's agent is the component of the Cursor editor that plans, searches, edits and runs commands; Cursor builds and operates it. Cursor also runs agents in the cloud; this teardown covers the local agent, because that is what the cited documentation describes in detail. Everything here comes from Cursor's documentation as checked on 28 October 2026 and two Cursor engineering posts. Cursor's harness is closed source, so where the docs are silent, this page says so rather than filling the gap.

Two design choices set Cursor apart from terminal-first harnesses. Context comes from a local search index and editor-native rules rather than a single memory file. And command execution is decided by a layered policy (an allowlist, an OS sandbox and a model classifier) that the user selects as a run mode.

**Rules.** Project rules are `.mdc` files under `.cursor/rules`, each typed by frontmatter: `alwaysApply: true` for every chat, `globs` to attach the rule when a matching file is in context, `description` alone for the agent to pull in when it judges the rule relevant, and neither for rules applied only when @-mentioned. A plain `.md` file in that folder is ignored. Team rules come from the dashboard on Team and Enterprise plans and can be enforced so users cannot disable them; user rules apply across projects. When guidance conflicts, team rules win over project rules and project rules over user rules. AGENTS.md is supported in the root and in subdirectories, with the more specific file winning. Files a rule references are read on demand rather than inlined.

**Instant Grep.** Cursor's own search engine, which the docs say outperforms ripgrep on large codebases without giving a figure. Its index is built and queried on the user's machine. The docs state that Cursor does not store embeddings of the codebase for search and does not upload file paths or code to build an index; file content the agent opens can still be sent to the model.

**Explore sub-agent.** Broad searches run in a sub-agent with its own context window on what the docs call a faster model, unnamed. The main agent starts it automatically or on request.

**Run mode.** One of three policies for tool calls. In Auto-review, which shipped as the recommended default in version 3.6, allowlisted calls run immediately, other shell commands run in the sandbox where possible, and calls that do not go through the sandbox go to a classifier. Allowlist mode runs listed actions without approval and has no classifier. Run Everything runs every call with neither sandbox nor classifier.

**Auto-review classifier.** A model call on Cursor's backend, covering shell, MCP and Fetch tool calls. The docs name the current models (Gemini 3.5 Flash Lite, with Claude 4.5 Haiku as fallback) and say the classifier may make read-only ReadFile, Grep, Glob and ListDir calls on the machine, for example to read a script a command would run. When it blocks a call, the agent can try another approach; if it still wants the action, the user gets an approval prompt. The docs state that it is not a security boundary and that it can allow a call the user would have blocked, or block one the user would have allowed.

**permissions.json and sandbox.json.** `permissions.json` holds plain-English `allow_instructions` and `block_instructions` for the classifier, in `~/.cursor` and in the project's `.cursor`, merged; a team configuration overrides both. `sandbox.json` holds the network allowlist, combined with built-in defaults for common package managers in the default network mode.

**OS sandbox.** Shell commands run with read and write access to the workspace, `/tmp` writable, `.git/config`, `.git/hooks` and `.vscode` protected, and files in `.cursorignore` hidden. On macOS it is Seatbelt, with a profile generated at runtime from workspace and admin settings; on Linux, seccomp blocks unsafe syscalls and Landlock restricts the filesystem, with ignored files replaced by unreadable copies in an overlay. Linux needs kernel 6.2 or later with Landlock v3 and unprivileged user namespaces; without them Cursor falls back to approval prompts. On Windows, Cursor runs its Linux sandbox inside WSL2.

**Network.** Blocked by default inside the sandbox and opened by the network mode and `sandbox.json`. Outside the sandbox, the security page says that with default settings the agent's own tools reach only GitHub, direct link retrieval and web search providers.

## Context strategy

Cursor's context is assembled from three sources with different timing. Rules and AGENTS.md arrive at the start or when a matching file enters context. Code arrives by search, through a local lexical index and a sub-agent that keeps exploration out of the main context. Referenced files arrive only when read.

The most consequential fact is a change. In November 2025 Cursor published a post reporting that semantic search raised average accuracy by 12.5% in its own offline evaluation (6.5% to 23.5% by model) and code retention by 2.6% on codebases of 1,000 or more files, and concluded that grep and semantic search together worked best. Its current search docs describe a local index with no stored embeddings. The direction matches what Anthropic recommended in 2025 and what Cognition built with SWE-grep: fast lexical search, kept out of the main context by a sub-agent.

## Tools and permission model

The permission model has four layers, and each is documented as having a different strength:

1. **Allowlist.** Deterministic, by match. Runs listed calls without asking.
2. **OS sandbox.** The only layer enforced by the kernel. Bounds filesystem and network for shell commands, not for MCP or Fetch calls.
3. **Classifier.** A model judging a call, with plain-English instructions as its policy. Documented as fallible and as not a boundary.
4. **Approval prompt.** The user, as the last resort when the classifier blocks and the agent persists, or when the sandbox cannot be used.

MCP is handled separately: every connection and, by default, every tool call needs approval unless an MCP allowlist pre-approves the tool. In Auto-review, MCP calls go to the classifier, and allowlisted MCP calls run outside the sandbox.

Administrators can override available run modes, sandbox network rules and the read-access policy from the dashboard, and team settings take precedence over user and project files.

## Cost and latency

Cursor publishes two operational numbers. In its February 2026 sandboxing post, sandboxed agents stopped 40% less often than unsandboxed ones, mostly asking only when they needed the internet, and a third of requests on supported platforms ran with the sandbox. Both are Cursor's own measurements.

The rest is structural. The classifier adds a model call on Cursor's backend for each shell, MCP or Fetch call it reviews, which is why it runs on small models; sandboxed and allowlisted calls skip it. Instant Grep moves search cost to a local index build, which avoids a network round trip per search. The Explore sub-agent runs on a faster model, trading the main model's quality for speed on a task where precision of the returned list matters more than reasoning depth. Cursor does not publish latency figures for any of these.

## Failure modes

- **Silent fallback to prompts on Linux.** Below kernel 6.2, or without Landlock v3 and unprivileged user namespaces, there is no sandbox and every unlisted command asks. In a fleet of older dev boxes this turns Auto-review back into approval fatigue.
- **Classifier as the boundary.** A team that treats Auto-review as the security control has a model deciding, with plain-English instructions as policy. The docs say it is not a boundary, and a sandbox-blocked command can be rerun outside the sandbox on the classifier's say-so.
- **Rule precedence surprises.** Team rules win over project rules in Cursor, while Codex and Claude Code concatenate from the root down so the most specific file comes last, and Codex documents that later files override earlier guidance. A repository that relies on its own rule overriding an organisation default behaves differently across tools.
- **Glob rules arrive late.** A rule scoped by glob is absent until a matching file is in context, so a first plan made before any file is opened is made without it.
- **Retry loops on sandbox failures.** Cursor's own post reports agents retrying the same command when the sandbox blocked it, fixed by naming the constraint in the tool result. A custom tool or MCP server that hides its own failure reason recreates the problem.

## What is not public

- **The system prompt.** Cursor does not publish the agent's system prompt or how rules are placed in the request.
- **The classifier's accuracy.** The docs say it can make mistakes in both directions and give no false-allow or false-block rates, no evaluation set and no per-model comparison.
- **When and why semantic search was removed.** The November 2025 post reports gains; the current docs say no embeddings are stored for search. Neither says when the change happened or why, so treat the 2025 numbers as describing an earlier product.
- **How Instant Grep's index is built and refreshed.** The docs say it is local and faster than ripgrep on large codebases, without a figure or a description of updates.
- **The Explore sub-agent's model.** The docs say "a faster model" and do not name it.

## When this is wrong

Cursor ships frequently, and version numbers run through every source above: Auto-review became the recommended default in 3.6, the read-access setting arrived in 3.23, and the search docs changed between November 2025 and now. Re-check each claim against the current docs before acting on it.

The architecture is assembled from documentation, not observed. The diagram shows components and the flows the docs describe; the order in which context is assembled and where each rule sits in the request are not public.
