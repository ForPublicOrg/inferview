## A request that rewrites history

Compaction replaces the conversation the model sees with a shorter one the harness believes is equivalent. Log compaction in a storage engine is the nearest analogy, and the difference is the whole lesson: a storage engine's compaction is lossless by construction, while an agent's is a model request whose output is a judgement about what mattered. Three things follow. What survives is a policy the harness owner sets, partly by mechanism and partly by prompt. Compaction has a price, set by the cache state at the moment it runs. And the failures it causes are silent, because the model does not know what it no longer knows.

## What survives, by harness

**Claude Code** separates content by how it entered the context. Its context-window documentation (checked October 2026) lists the outcome per mechanism:

| Content | After compaction |
|---|---|
| System prompt, output style | Still apply |
| Project-root CLAUDE.md, unscoped rules, auto memory | Re-injected from disk |
| The plan written in plan mode | Re-injected from disk |
| Files Claude read or edited | Up to five re-read, most recently modified first; a file over 5,000 tokens returns as a path reference only |
| Invoked skill bodies | Re-injected, capped at 5,000 tokens per skill and 25,000 in total, oldest dropped, truncation keeps the start |
| Path-scoped rules, nested CLAUDE.md | Summarised away; reloaded when a matching file is next touched |
| Context hooks added earlier | Summarised with the conversation |
| SessionStart hooks matching `compact` | Run again, output added |
| Everything said in conversation | Whatever the summary keeps |

The pattern is that anything with a file on disk can be restored exactly and anything that lives only in the message history becomes summary text. A correction typed in turn 12 ("use the v2 client, not v1") is conversation. So is a sentence such as "don't push until I've reviewed", which Claude Code's auto-mode classifier treats as a block signal; the best-practices page warns that it can be lost when the conversation compacts. The summary prompt can be steered with a "Compact Instructions" section in CLAUDE.md or a focus argument (`/compact focus on the API changes`), and since v2.1.198 the summarisation request inherits the session's thinking setting.

**Codex** compacts through the Responses API. Michael Bolin's January 2026 post on the Codex loop describes the history: the first `/compact` asked the model for a summary and used that assistant message as the new input; the current version calls a `/responses/compact` endpoint, automatically once `auto_compact_limit` is exceeded, and receives a list of items that includes a `type=compaction` item carrying opaque `encrypted_content`, which the post says preserves the model's latent understanding of the conversation. The operational consequence is that the harness owner cannot read what survived. Testing compaction in Codex means testing behaviour after it, not inspecting the summary.

**OpenHands** makes compaction an event. The SDK's default `LLMSummarizingCondenser` triggers when the view exceeds `max_size` events (default 120), keeps the first `keep_first` events (default 4, usually the system prompt and task), keeps the most recent `max_size // 2 - keep_first - 1` events, which is 55, and summarises the middle into one event, for a view of 60. It writes a `Condensation` event to the log with the forgotten event ids and the summary, so the full history stays on disk and every condensation can be audited and replayed. The SDK paper cites up to 2x lower API cost from this condenser without degraded performance, and also reports what can go wrong: in a 15-day production rollout, V1's SDK errors (29.7 per 1,000 conversations) came mostly from a condensation bug found during the extended-thinking rollout.

## Summaries of summaries

A rolling condenser does not summarise an early instruction once. If the previous summary sits just after the head, as the `summary_offset` field suggests, it falls into the middle at the next pass and is summarised again. The simulation below applies the documented OpenHands defaults to a 600-event run and tracks how many passes the summary has been through.

```python
def condense(view, max_size=120, keep_first=4):
    """One rolling condensation as the OpenHands SDK docs describe it."""
    if len(view) <= max_size:
        return view, None
    target = max_size // 2                      # 60 events after condensing
    tail_len = target - keep_first - 1          # 55 recent events kept verbatim
    head, middle, tail = view[:keep_first], view[keep_first:-tail_len], view[-tail_len:]
    passes = max(e["passes"] for e in middle) + 1
    summary = {"id": f"summary-{passes}", "passes": passes,
               "covers": sorted({i for e in middle for i in e["covers"]})}
    return head + [summary] + tail, summary

view = []
for i in range(600):
    view.append({"id": i, "passes": 0, "covers": [i]})
    view, s = condense(view)
    if s:
        print(f"event {i}: view {len(view)}, summary pass {s['passes']}, event 30 inside: {30 in s['covers']}")
# event 120: view 60, summary pass 1 ... event 547: view 60, summary pass 8
```

The first condensation happens at the 121st event and then every 61 events, so by event 600 an instruction given at event 30 has been through eight summarisations. Each pass is a model deciding again what matters, with only the previous summary as evidence of what the instruction said. Cognition's June 2025 post on multi-agent systems makes the same point about history compression in general: a model that distils history into key details, events and decisions is hard to get right and still eventually hits a limit. The fix is not a better summariser. It is to keep what must survive out of the summarised region: in the head (`keep_first`), on disk (Claude Code's plan file, a progress file the agent rewrites), or re-injected by a hook after every compaction.

## What it costs

Claude Code's prompt-caching page describes the request: it repeats the conversation's system prompt, tools and the history being summarised, then ends with a summarisation instruction. While the cache is warm the history is read at the cache-hit rate. After the cache TTL, it is reprocessed as uncached input.

<p>Cold: 400,000 × $4/M = $1.60 input plus 10,000 × $20/M = $0.20 output, so <b>$1.80</b>. Warm: 400,000 × $0.20/M = $0.08 plus the same $0.20, so $0.28. The input term is twenty times larger cold, and the whole request about six times. The output term is the same in both, which is why a warm compaction spends most of its time generating rather than reading.</p>
</Predict>

Two harness behaviours follow from that arithmetic. Claude Code compacts an idle long session itself: on the one-hour cache, a session past about 200K tokens that sits idle is compacted shortly before the cache expires, so the expensive read happens warm and the user returns to a short, cheap context. And resuming an old session and then compacting it is the most expensive way to compact, because the cache is gone by then. The turn after compaction is cheap either way: it writes a cache entry for the short summary only.

Compaction can also fail to make progress. If a single file or tool output is large enough to refill the context right after each summary, Claude Code stops auto-compacting after a few attempts and reports an error rather than looping. The root cause is an unbounded tool output, not compaction, and the fix belongs in the tool's output cap.

## Testing that the goal survives

A compaction policy is untested until compaction has happened in the test. Four checks, in increasing cost:

1. **Force it.** Run the eval with compaction triggered at fixed points: `/compact` in Claude Code, a `CondensationRequest` event in OpenHands, a low `auto_compact_limit` in Codex. Without this, short eval tasks never compact and the policy is never exercised.
2. **Probe it.** After each forced compaction, ask questions whose answers exist only in the pre-compaction conversation: the user's correction, the rejected approach and why, the file that must not change. Compare with the answers before compaction.
3. **Pair it.** Run the same tasks with and without forced compaction and compare success, steps and cost per task. The difference is the price of the policy.
4. **Move it to disk.** For anything that fails the probes, stop relying on the summary: write it to a file the harness re-injects (the plan in Claude Code, a progress file the agent reads on start), or add a SessionStart hook that matches `compact`.

## When this is wrong

The survival table is Claude Code's as of October 2026, and several rows carry version numbers in the docs (skill descriptions rebuilt after compaction need v2.1.304 or later). The behaviour is a product decision that changes with releases.

The cost arithmetic assumes the compaction request shares its prefix with the conversation. A harness that summarises with a different model, as the OpenHands condenser can, gets no cache hits from the main conversation and pays the cold price every time, at the summariser's rate.

The summary-of-summaries count assumes the previous summary is re-summarised. A condenser that keeps its own summary in the protected head, or a vendor endpoint that compacts into opaque state, behaves differently, and the only evidence is a probe after compaction.

Finally, models change the need. The next lesson covers a published case where one model needed full context resets that compaction could not replace, and its successor did not.
