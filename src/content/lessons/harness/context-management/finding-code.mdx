## Four ways to find the code

Every coding task starts with the agent deciding which files matter. Four mechanisms are in production or published as of October 2026, and they differ on when the cost is paid and what goes stale.

**Agentic lexical search.** The model runs grep, ripgrep, find and file reads in a loop, refining its patterns from what each result shows. No build step, nothing to go stale, exact-match semantics. The cost is turns: each round trip is a model request over the whole context.

**A ranked repository map.** Aider parses every file with tree-sitter, builds a graph of which files reference which definitions, ranks it with personalised PageRank toward the files and identifiers in the current conversation, and sends the top of the ranking, fitted to a token budget, with every change request. The cost is a fixed slice of every request's context.

**An embeddings index.** Chunks of code are embedded, and the agent queries by meaning. The cost moves to index build and refresh, and the result is ranked by a similarity score the model and the user cannot inspect.

**A retrieval sub-agent.** A separate agent, sometimes a separate model, does the searching in its own context and returns a short list. The cost is its own requests and the time to rebuild what the parent knew.

A compiler's lexer against a database index is the analogy for the first and third: one scans every time and is always correct about the bytes, the other answers fast from a structure built earlier. The difference is that both are being driven by a model that decides what to look for, so the quality of the query matters as much as the engine.

## What the vendors published, with dates

This is the part of the module that goes stale fastest, so each claim carries its date.

**Anthropic, September 2025.** The Claude Agent SDK post says semantic search is usually faster than agentic search but less accurate, more difficult to maintain and less transparent, and recommends starting with agentic search and adding semantic search only for faster results or more variations.

**Cognition, October 2025.** Its Windsurf and Devin agents spent more than 60% of the first turn retrieving context. The response was not an embeddings index but SWE-grep, a model trained with reinforcement learning to issue up to eight parallel searches per turn for at most four turns, deployed behind a retrieval sub-agent. Its reward and evaluation favour precision (F-beta with beta 0.5), on the argument that polluting the parent's context costs more than missing a file.

**Cursor, November 2025.** Cursor's semantic-search post reported, from its own offline evaluation, 12.5% higher average accuracy answering questions about codebases with semantic search available, ranging from 6.5% to 23.5% by model. Its online A/B test showed code retention up 0.3% overall and 2.6% on codebases of 1,000 or more files, and 2.2% more dissatisfied follow-up requests when semantic search was off. The post concluded that grep and semantic search together worked best.

**Cursor, current docs (checked 28 October 2026).** The search documentation describes Instant Grep, a search engine whose index is built and queried on the user's machine, and says Cursor does not store embeddings of the codebase for search and does not upload file paths or code to build a search index. Broad exploration runs in an Explore sub-agent on a faster model. The docs do not say when or why the embeddings index was dropped, so the November 2025 numbers describe a product that no longer works that way. Cite them as history.

The pattern across the three vendors is that each converged on fast lexical search, made faster by a local index, a trained model or parallel calls, with a sub-agent to keep the results out of the main context.

## How Aider ranks a repository

Aider's map is the one mechanism whose internals are fully public, and its `repomap.py` shows how much judgement sits in the weights. Each file is a node. For each identifier defined in one file and referenced in another, an edge runs from the referencing file to the defining file, with a weight built from multipliers:

- ×10 if the user mentioned the identifier in the conversation.
- ×10 if it is a snake_case, kebab-case or camelCase name of 8 or more characters (long, specific names).
- ×0.1 if it starts with an underscore (private).
- ×0.1 if it is defined in more than 5 files (generic names like `get` or `run`).
- ×50 if the referencing file is in the chat.
- times the square root of the number of references, so frequent mentions do not dominate.

PageRank then runs with a personalisation vector that gives extra restart probability to files in the chat, files the user named and files whose path contains an identifier the user mentioned. The ranked definitions are fitted to the budget by binary search on how many to include, accepting a result within 15% of the token target. The default budget is 1,024 tokens; with no files in the chat, it is multiplied by 8, capped at the context window minus 4,096. Files already in the chat are left out of the map, because their full text is already in context.

The effect of personalisation is easy to see on a toy graph. The function below is a plain power-iteration PageRank with weighted edges, personalisation and dangling-node mass sent to the personalisation vector, as networkx does when Aider passes both.

```python
def pagerank(edges, personalization=None, d=0.85, iters=100):
    """Weighted PageRank by power iteration; edges = {(src, dst): weight}."""
    nodes = sorted({n for e in edges for n in e})
    p = personalization or {n: 1 for n in nodes}
    total = sum(p.get(n, 0) for n in nodes)
    p = {n: p.get(n, 0) / total for n in nodes}
    out = {n: sum(w for (s, _), w in edges.items() if s == n) for n in nodes}
    rank = dict(p)
    for _ in range(iters):
        nxt = {n: (1 - d) * p[n] for n in nodes}
        for (s, t), w in edges.items():
            nxt[t] += d * rank[s] * w / out[s]
        dangling = sum(rank[n] for n in nodes if out[n] == 0)
        for n in nodes:
            nxt[n] += d * dangling * p[n]
        rank = nxt
    return rank

# referencer to definer: billing.py references a long snake_case name in tax.py that the user mentioned (x10, x10);
# every other edge is a short, unmentioned name; each name is referenced 4 times (sqrt 4 = 2)
edges = {("api.py", "auth.py"): 2, ("api.py", "util.py"): 2, ("billing.py", "util.py"): 2,
         ("billing.py", "tax.py"): 100 * 2, ("auth.py", "util.py"): 2, ("cli.py", "api.py"): 2}
for label, pers in [("no chat files", None), ("billing.py in chat", {"billing.py": 1})]:
    ranked = sorted(pagerank(edges, pers).items(), key=lambda kv: -kv[1])
    print(label + ":", ", ".join(f"{f} {r:.3f}" for f, r in ranked))
# no chat files: util.py 0.307, api.py 0.171, tax.py 0.171, auth.py 0.166, ...
# billing.py in chat: billing.py 0.541, tax.py 0.455, util.py 0.005, api.py 0.000, ...
```

Without a chat file, the shared utility module ranks first, which is what a global ranking always does. With `billing.py` in the chat, the map spends its budget on `tax.py` and nothing unrelated. That is the design working. It is also the failure mode: the map cannot surface a file connected to the task by behaviour rather than by name, such as a configuration file that changes what `tax.py` does.

## Measuring it on your repository

Published comparisons use the vendor's tasks, models and harness. The repository's own history gives a better test set for free.

1. Take 50 to 200 recent merged changes. For each, the task text is the issue or the first commit message, and the relevant set is the files the change modified.
2. Run each candidate retrieval (grep-only agent, repo map, an index, a retrieval sub-agent) from the parent commit, and record which files it surfaces before the first edit.
3. Score recall of the modified files, precision of what was surfaced (Cognition's F-beta with beta 0.5 if pollution worries you more than misses), turns and wall time to the first relevant file, and tokens added to the parent's context.
4. Compare paired, task by task, because task difficulty varies far more than the methods do.
5. Measure freshness separately: how long after a branch switch or a large merge each method returns stale results. Aider's tag cache is keyed by file modification time; an embeddings index is as fresh as its last rebuild.

The modified-files set undercounts what was needed (files read to understand the change but not edited), so treat recall as a floor and spot-check misses by hand.

## When this is wrong

The vendor numbers here are each vendor's own measurement on its own tasks and harness, and the Cursor figures describe a configuration its current docs no longer describe. None is a controlled comparison across mechanisms.

The lexer and index framing assumes one search per need. Agents run dozens of searches per task, so the latency and token cost of agentic search scale with model speed and turn count, and a faster model can make an index unnecessary or a slower one make it essential.

The git-history test assumes the changed files are the right answer. For tasks where the correct fix is in a different place than the one the human chose, retrieval that finds the better place scores as a miss.

Finally, retrieval is upstream of everything in this module: whatever the agent finds lands in its context and stays there until compaction or the end of the session, which is why the sub-agent and precision arguments keep returning.
