## The problem the post solves

Prithvi Rajasekaran's post on Anthropic's engineering blog (24 March 2026) reports a harness for building whole applications over several hours: a planner that expands a one-to-four-sentence prompt into a product spec, a generator that builds it in sprints, and an evaluator that drives the running app through Playwright and grades it against criteria agreed before each sprint. The harness is the subject, but the part that generalises is a side observation about context.

With Claude Sonnet 4.5, the author saw what the post calls context anxiety: the model began wrapping up work prematurely as it approached what it believed was its context limit. The post's conclusion was that Sonnet 4.5 showed this strongly enough that compaction alone was not sufficient for good long-task performance. The harness therefore used context resets. With Claude Opus 4.5 the behaviour had largely gone, the resets were removed entirely, and automatic compaction handled context growth.

The engineering question the post answers is when to restart an agent from a written handoff instead of compacting it in place, and the broader one is how a harness learns that a component it depends on has stopped being needed.

## The mechanism in engineering terms

Compaction is in-place: the same agent continues with a summarised history, keeping continuity but, in the post's words, not giving the agent a clean slate. A reset is a process restart from a checkpoint: the context is cleared, a fresh agent starts, and a structured handoff carries the previous agent's state and next steps. Crash-only software is the closest analogy, where every restart goes through the same recovery path and the checkpoint has to be complete enough to resume from. The difference is that the checkpoint here is prose written by the agent being replaced, so its completeness is a model output, not an invariant.

Why a reset fixes context anxiety when compaction does not is a matter of what the model sees. After compaction the context is smaller but the agent is the same conversation, carrying a summary of a long run. After a reset the new agent sees a short context and a list of remaining work, so the cue that triggered the early wrap-up is gone. The post does not publish the handoff format; it says the handoff must carry enough state for the next agent to pick up the work cleanly.

The post is explicit about the price. Resets solve the problem but add orchestration complexity, token overhead and latency to each run. It does not quantify those, so any number you use for them comes from your own runs.

## What changed in practice

Two removals are documented, and they happened at different model generations.

With Opus 4.5, context resets went. The model no longer wrapped up early, so the harness kept one agent per role and let automatic compaction manage growth. That removed the handoff writing, the restart orchestration and the re-reading a fresh agent does to rebuild its working set.

With Opus 4.6, the second-version harness removed the sprint structure and moved the evaluator from grading each sprint to one pass at the end, on the reasoning that the model could handle the work without that decomposition. The planner stayed, because without it the generator under-scoped; the evaluator stayed for the parts of the build still at the edge of what the generator could do alone.

The principle the post draws is the one to take away: every component in a harness encodes an assumption about what the model cannot do on its own, and those assumptions go stale as models improve. The method that worked was removing one component at a time and reviewing the effect on the result. The author reports that an earlier attempt to simplify radically made it hard to tell which parts mattered.

## Detecting the assumption before it ships

A harness that will run on the next model needs each component's assumption written down and tested, the same way a configuration flag needs an owner and an expiry. Four steps:

1. **Name the assumption per component.** "Resets: the model stops early as its context fills." "Sprint contracts: the model cannot scope a multi-hour build without decomposition." "Evaluator after every sprint: the model's self-assessment is unreliable mid-build." An assumption you cannot state is one you cannot test.
2. **Instrument the symptom, not the outcome.** For context anxiety the symptom is a stop or completion claim that correlates with context fill rather than with remaining work. Log the fill fraction at every voluntary stop and whether the evaluator found unfinished spec items.
3. **Ablate one component per run, per model.** Paired runs on the same specs with and without the component, on each candidate model, as the post did. Compare success, cost and time.
4. **Key the harness configuration by model.** A component that is load-bearing for one model and dead weight for another should be a per-model setting, so an upgrade changes the configuration and the test, not the code.

The symptom check for step 2 can be a few lines over run logs:

```python
from collections import defaultdict

# Scenario log: (context fill when the agent ended its run, evaluator found unfinished spec items)
stops = [(0.35, False), (0.52, False), (0.71, True), (0.78, True), (0.83, True),
         (0.41, False), (0.88, True), (0.66, False), (0.74, True), (0.58, False)]

buckets = defaultdict(lambda: [0, 0])
for fill, unfinished in stops:
    b = min(int(fill * 4), 3) / 4          # quarter of the window the stop fell in
    buckets[b][0] += 1
    buckets[b][1] += unfinished
for b in sorted(buckets):
    n, early = buckets[b]
    print(f"stopped {b:.0%} to {b + 0.25:.0%} full: {early} of {n} ended with work unfinished")
# 25% to 50%: 0 of 2; 50% to 75%: 2 of 5; 75% to 100%: 3 of 3
```

A rate of unfinished stops that climbs with fill, on specs of similar size, is the signature the post describes. A flat rate says the model's stopping is about the work, and a reset component built for the first pattern is overhead. Ten stops are a toy; at real volume, compare the top quarter with the rest using a paired or stratified test, because longer specs both fill the context and are more often left unfinished.

## When this is wrong

The evidence is one author's harness, one application domain and a handful of named runs. The post does not publish success rates across many specs, so "Opus 4.5 did not need resets" is an observation from that harness, not a measured property of the model across tasks.

The cost figures mix model generations and harness versions: the $200 run is Opus 4.5 on the first harness and the $124.70 run is Opus 4.6 on the second. Neither is a controlled comparison of resets against compaction.

Context anxiety as described is a behaviour tied to how a model perceives its remaining context. A harness that hides the context size from the model, or a provider that changes what the model is told about its window, can change the behaviour without a model change.

Resets also have uses unrelated to anxiety: a clean context for an independent check, and a recovery path after a crash. Removing them for one reason does not remove those reasons; the next lesson covers fresh contexts used on purpose.
