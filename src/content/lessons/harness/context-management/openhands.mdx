## What it is and who runs it

OpenHands, formerly OpenDevin, is an open platform for software-development agents released under the MIT licence. The 2024 paper that introduced it lists 24 authors and more than 2,100 contributions from over 188 contributors. In November 2025 the team published a second paper on the OpenHands Software Agent SDK, which it describes as a complete redesign of the agent components, accepted at MLSys 2026. Because the code is public, this teardown can describe internals that the closed harnesses in this module leave unstated; it still relies on the papers and the SDK docs rather than on reading a particular commit.

The design idea to take from OpenHands is that the agent is an event-sourced system. Every action the agent takes and every observation it receives is an event in an append-only log; state is what you get by replaying the log; and context management, persistence and approval are all expressed as events.

**Event stream and conversation state.** The 2024 paper centres the agent's state on a chronological stream of actions and observations, including the user's messages and feedback; at each step the agent maps that state to its next action. The SDK makes the separation strict: the conversation state is the only mutable component, while agents, tools and LLM configurations are immutable, validated models.

**Agent.** The 2024 paper's main agent, CodeActAgent, acts through three action types: running a cell in IPython, running a bash command, and sending browser commands. A Python library of helpers (AgentSkills, with functions such as `edit_file`) is pre-imported into the IPython environment, and the paper's rule is to add a helper only when the model cannot readily write the code itself. One agent can hand a subtask to another with a delegate action, as when CodeActAgent delegates web browsing to a browsing agent.

**LLM.** The SDK reaches more than 100 providers through LiteLLM, using either Chat Completions or the Responses API.

**Workspace.** In the 2024 design each task runs in a Docker container whose action execution server hosts a bash shell, a Jupyter IPython server and a Chromium browser driven by Playwright. The SDK abstracts this as a workspace: `LocalWorkspace` runs in-process against the host's filesystem and shell, and `RemoteWorkspace` (with Docker and hosted-API variants) sends actions over HTTP to an agent server. Switching from local to Docker is a matter of which workspace object the code constructs.

**Condenser.** The default `LLMSummarizingCondenser` runs when the view exceeds 120 events, keeps the first 4 verbatim, keeps the most recent 55, and replaces the middle with one summary, leaving 60. The summariser is a separate LLM instance, often a cheaper model. The compaction lesson in this module traces what this does to an early instruction over a long run.

**Security analyzer and confirmation policy.** Every tool schema gets a required `security_risk` parameter, so the model rates its own call as LOW, MEDIUM or HIGH as part of making it; there is no separate analysis call. The default confirmation policy, `ConfirmRisky`, pauses for the user at HIGH and also for UNKNOWN, which is what the no-op analyzer always returns.

**Event store.** With persistence on, the SDK writes conversation metadata to `base_state.json` and each event to its own JSON file, and resumes a conversation by loading the metadata and replaying the events.

## Context strategy

Context is the condensed view of the event log, rebuilt each step. Three properties follow from making it an event.

Condensation is auditable. A `Condensation` event records exactly which events were dropped from the view and the summary that replaced them, so a bad run can be diagnosed by reading what the summariser kept, which is not possible with an opaque compaction item.

Condensation is a step of its own. When the condenser fires, the agent appends the event and returns early from the step, so the history is never rewritten in the middle of an action, and a manual `CondensationRequest` event (for example after a context-window error from the provider) is handled the same way on the next step.

Nothing is lost from storage. The view shrinks; the log does not. Resuming, replaying or re-condensing with different settings all start from the full history.

## Tools and permission model

The action space is code (IPython), shell and browser, executed in a workspace. Isolation comes from the workspace: a Docker workspace confines actions to the container, and a local workspace runs them on the host with no isolation from OpenHands.

Approval is a policy over a risk label. The design choice that matters is where the label comes from. The LLM analyzer asks the same model that chose the action to rate it, in the same call. That is cheap and fast, and it means the rating fails in the same situations the action does: a model that has been steered by injected content into a harmful command can also label it LOW. The defaults lean safe where they can: UNKNOWN requires confirmation unless switched off, and the threshold cannot be set to UNKNOWN.

## Cost and latency

The 2024 paper gives the clearest cost figure: CodeActAgent v1.8 with Claude 3.5 Sonnet (June 2024) resolved 26.0% of SWE-bench Lite's 300 instances at an average cost of $1.10 per instance.

The SDK paper adds three measurements. The condenser it ships as default is cited as cutting API cost by up to 2x without degrading performance. Event sourcing costs little: across 433 SWE-bench Verified conversations with 39,870 events, persisting an event took a median 0.20 ms (p95 0.31 ms) and replaying a full conversation a median 4.1 ms (p95 9.7 ms). And on matched models, the redesigned SDK scored 72.8% on SWE-bench Verified with Claude Sonnet 4.5 against 64.6% for the previous version. All of these are the authors' own measurements.

## Failure modes

- **Self-rated risk.** The risk label is produced by the model being supervised. Confirmation fires only when that model says HIGH, so it catches honest mistakes and misses steered ones.
- **Local workspace on a developer machine.** `LocalWorkspace` runs actions against the host filesystem and shell. Moving to Docker is one object change, which makes it easy to forget for a quick experiment that later becomes a service.
- **Condensation bugs.** In the SDK paper's 15-day production comparison, system-attributable errors fell from 78.0 to 30.0 per 1,000 conversations, and most of the new version's remaining 29.7 SDK errors per 1,000 came from a condensation bug found during the extended-thinking rollout, since fixed. The condenser is where a model-format change (thinking blocks) met history rewriting.
- **Summaries of summaries.** With the defaults, the summary is re-summarised every 61 events, so an instruction from early in a long run survives only as a repeatedly compressed paraphrase unless it sits in the first four events.

## What is not public

- **Production usage.** There are no published figures for how many teams run OpenHands, on what repositories, or with what success on their own work. The SDK paper reports error rates for a 15-day rollout, not usage or task outcomes.
- **How accurate the risk labels are.** The docs and papers describe the mechanism and give no measured rate of correct, under-rated or over-rated labels. The rating is a hint, not a control, because the model being supervised sets it.
- **The summary quality of the condenser.** The cost reduction is cited; how often a condensation drops something the run later needed is not reported.

## When this is wrong

The 2024 and 2025 papers describe different generations: CodeActAgent and the Docker action server come from the 2024 platform, the immutable models, workspaces and analyzer from the SDK. Which agent a given deployment runs, and with which defaults, depends on its version and configuration.

The benchmark and overhead numbers are the authors' own, on public benchmarks. They describe the harness's capability and cost on those tasks, not on a particular team's repositories.
