## What crosses the boundary

A sub-agent is a second agent loop with its own context window, started by the first through a tool call and returning one message. A child process with captured stdout is the nearest analogy. The difference is that the return value is a summary the child's model writes, so the boundary filters by judgement, not by schema, and the parent cannot tell what was left out.

Claude Code's sub-agent documentation (checked October 2026) defines what crosses in each direction.

**Into the sub-agent.** A non-fork sub-agent does not see the parent's conversation, the skills it has invoked or the files it has read. It starts with its own system prompt, the task message the parent writes, the same CLAUDE.md files the main conversation loads, the git status snapshot and any skills preloaded in its definition. It does not get the parent's auto memory. The built-in Explore and Plan agents skip CLAUDE.md and git status as well. A fork is the opposite case: it inherits the parent's conversation and system prompt, so its first request reads the parent's prompt cache, while a fresh sub-agent builds a cache of its own.

**Out of the sub-agent.** Only the final summary returns. A sub-agent stopped by its `maxTurns` limit returns its output marked as partial, and background sub-agents, the default for those started from the main conversation, report through a completion notification in a later turn.

**What the harness enforces.** The `tools` allowlist and `disallowedTools` denylist are enforced by Claude Code, not requested in a prompt. Explore denies Write and Edit. A custom reviewer with `tools: Read, Grep, Glob` cannot edit anything. Nesting stops three layers below the main conversation by default, and spawning fails once 20 sub-agents are running in a session.

The task message is the only channel from parent to child. Everything the child needs and cannot rediscover from the repository has to be in it.

## What delegation buys, and what it does not

Claude Code's best-practices page lists four situations where sub-agents pay off: independent work in parallel, keeping long output (a full test run, a wide search) out of the main conversation, a reviewer that has not seen how the code was written, and a task that should have fewer tools than the main session. It is equally direct about the limits. A sub-agent is the same model or a smaller one on the same task, so delegation does not produce a smarter answer. A fresh reviewer does help, because it has not seen the reasoning that produced the code, and that is a different benefit from delegation. The costs are tokens, because every sub-agent sends its own requests, and sometimes time, because a fresh sub-agent first has to gather context the conversation already had.

Cognition's June 2025 post sets the other boundary. Its second principle is that actions carry implicit decisions, and conflicting decisions carry bad results: two sub-agents building parts of one game in parallel each made reasonable choices that did not fit together. At the time, the post observed, Claude Code's sub-agents usually answered a question rather than wrote code. The safe pattern that follows is to delegate reads and verdicts, and keep writes that embody decisions in one context.

Retrieval is the case that motivated purpose-built sub-agents. Cognition reported in October 2025 that its Windsurf and Devin agents spent more than 60% of their first turn retrieving context, and trained SWE-grep, a retrieval model behind a Fast Context sub-agent that issues up to eight parallel searches per turn for at most four turns. It scores retrieval with a precision-weighted F-score (beta 0.5) because, in its framing, context pollution does more harm than missing context. That is the right objective for any search sub-agent: what it returns lands in the parent's context for the rest of the session, so a short, precise answer is worth more than a complete one.

## Pricing a delegated search

<Fragment slot="prompt">
<p>Scenario inputs: to plan a rename, the agent reads 12 files of about 3,000 tokens each. Afterwards the session continues for 40 more requests. Inline, the file contents stay in the conversation. Delegated, a sub-agent reads them and returns a 1,500-token summary. Count only the tokens of search material that the later 40 requests re-read.</p>
</Fragment>
<p>Inline: 12 × 3,000 = 36,000 tokens, re-read by 40 requests, so 36,000 × 40 = <b>1.44 million</b>. Delegated: 1,500 × 40 = 60,000. At Claude Opus 5.5's cache-hit rate of $0.20 per million, that is about 29 cents against about 1 cent. The ride-along is only one term; the search turns themselves cost something on both sides, which the model below adds up.</p>
</Predict>

The full comparison needs the search turns too. Inline, each of the 12 search requests re-reads the parent's whole context. Delegated, the sub-agent's requests re-read only its own small context, but it starts cold and pays to write it.

```python
HIT, WRITE, OUT = 0.20e-6, 5.00e-6, 20e-6   # Claude Opus 5.5, dollars per token, 5-minute cache

def turns(ctx, n, add, cached=True):
    """n sequential requests; each reads the context so far and appends `add` new tokens."""
    cost = 0 if cached else ctx * WRITE
    for _ in range(n):
        cost += ctx * HIT + add * WRITE
        ctx += add
    return cost

def inline(main, files, size, later):
    return turns(main, files, size) + later * files * size * HIT

def delegated(files, size, later, sub_start=15_000, summary=1_500):
    return (turns(sub_start, files, size, cached=False)
            + summary * OUT + summary * WRITE + later * summary * HIT)

for main, later in [(80_000, 40), (20_000, 5)]:
    print(f"main {main:,}, {later} later requests: "
          f"inline ${inline(main, 12, 3_000, later):.2f}, delegated ${delegated(12, 3_000, later):.2f}")
# main 80,000, 40 later requests: inline $0.70, delegated $0.38
# main 20,000, 5 later requests: inline $0.30, delegated $0.37
```

The model ignores the model's own short outputs on each search turn, which are similar on both sides, and assumes a 15,000-token starting context for the sub-agent (scenario). Two results come out of it. With a large parent context and a long remaining session, delegation is cheaper in dollars, because every inline search turn re-reads 80,000 tokens and the results ride along for 40 requests. With a small parent and a short remaining session, inline is cheaper, because the sub-agent's cold start dominates. Setting the sub-agent's `model: haiku` changes the delegated side by more than an order of magnitude: with Haiku 5.5's prices ($0.125 per million for cache writes, $0.01 for hits, $0.50 output) the same sub-agent run costs about a cent, which is why the docs suggest it for simple collection jobs.

Dollars are rarely the deciding term at these sizes. Time is. A sub-agent that must rediscover what the parent knew runs extra turns, and a background sub-agent's answer arrives in a later turn. Context quality is the other term, and it points the other way from the dollars when the parent is about to edit the files: if the parent will read those 12 files anyway to make the change, delegating the reading buys nothing and adds a summary that may disagree with what the parent reads next.

## The decision

Delegate when at least one of these holds and none of the counter-conditions does:

- The output is large and only a conclusion is needed: a wide search, a full test run, a dependency audit.
- The parent's context is large and the session will continue, so material would ride along for many requests.
- The work is a verdict that benefits from not having seen the reasoning: review against a spec, a security pass on a diff. Give the reviewer read-only tools.
- The pieces are independent reads that can run in parallel.

Keep the work in the parent when:

- The parent will need the raw material, typically because it edits the same files next.
- The work makes decisions another part of the task depends on. Parallel writers make inconsistent choices.
- The session is short or the parent context is small, so the cold start costs more than the ride-along.
- The task message cannot carry what the child needs, because the needed context is the conversation itself. That is the case for a fork, not a fresh sub-agent.

## When this is wrong

The cost model assumes Claude Code's caching behaviour as documented in October 2026: sub-agents build their own cache with a five-minute TTL and forks share the parent's. A harness that shares a prefix between parent and child, or a provider without prompt caching, moves the crossover a long way.

The claim that delegation is not smarter holds for the same model on the same task. A sub-agent with a specialised model, as with SWE-grep, or with tools the parent lacks, can produce a better result than the parent would, and the comparison is then between systems, not contexts.

The summary is the weak point in every number above. A sub-agent that omits the one caveat the parent needed costs more than any token arithmetic shows, and nothing in the harness checks a summary's completeness.
