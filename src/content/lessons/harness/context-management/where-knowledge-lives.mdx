## The decision

A team adopting a coding agent accumulates rules, procedures and integrations faster than it decides where they go. Claude Code offers seven homes for a piece of knowledge or policy, and Codex and Cursor have equivalents for most of them: the project memory file, a skill, a path-scoped rule, a hook, a permission rule (with the sandbox behind it), a sub-agent definition, and an MCP server or a CLI the agent already knows how to drive. A personal file (CLAUDE.local.md or the user-level file) and a managed file pushed by IT cover who the rule applies to rather than what it is.

The homes differ on two axes that matter more than their names. The first is who acts: Claude Code's best-practices page splits instructions into those the model reads and may decide not to follow (the prompt, CLAUDE.md, skills) and those the harness executes every time (hooks, deny rules, managed settings). The second is when the content is in context and what that costs on each request.

| Home | In context | Who acts | Survives compaction |
|---|---|---|---|
| Project CLAUDE.md | Every request | Model | Re-injected from disk |
| Skill | Name and description every request; body after it is invoked | Model (or only the user, with `disable-model-invocation`) | Body re-injected, capped at 5,000 tokens per skill and 25,000 in total |
| Path-scoped rule | From the first read or edit of a matching file | Model | Summarised away until a matching file is touched again |
| Hook | Never, unless it returns output | Harness | Not affected |
| Deny rule, sandbox | Never | Harness | Not affected |
| Sub-agent | Its own window; the parent sees only the summary | Model, inside a tool allowlist the harness enforces | Parent keeps only the summary |
| MCP server | Tool names and server instructions every request; definitions deferred by tool search on supported models | Model | Not affected |

## The inputs that change it

**Does it apply to every task?** If not, it should not be in the project memory file. Claude Code's guidance is that every line there takes some of the model's attention on every task, relevant or not.

**Is it a fact or a procedure?** A fact is one line the agent cannot derive: the command to run one test file, the directory that looks unused and is not. A procedure is a sequence: cut a release, rotate a key, run the incident checklist. Procedures go in skills. The Agent Skills specification puts the startup cost of a skill at about 100 tokens of metadata and recommends a body under 5,000 tokens that loads only on activation, with scripts the agent runs without reading their source.

**Must it hold every time?** If a single exception is unacceptable, prose is the wrong home however it is worded. The best-practices page says so directly: a line that keeps being missed after more emphasis belongs in a hook, and a hook for a mere preference should be deleted. Within enforcement, there are three tiers. A `command` or `http` hook is deterministic; a `prompt` or `agent` hook asks another model and is not; a deny rule holds in every permission mode, including `bypassPermissions`, but matches tool calls rather than intent, so a `WebFetch` deny for a domain does nothing about `curl` to it unless the sandbox is on.

**What does it cost per request, and does it survive compaction?** The table above answers both. A rule that must survive a six-hour session should not be path-scoped, because compaction summarises it away until a matching file is touched again.

**Who should it apply to?** Personal preferences go in CLAUDE.local.md or the user-level file; team rules go in the repository; organisation rules go in a managed file or managed settings, which developers cannot exclude.

**Is there a CLI?** For an external system, Claude Code's docs prefer the CLI when one exists (`gh` for GitHub, and `--help` for one the model has not seen) and MCP for systems without one. A connected MCP server adds its tool names and instructions to every session even when unused.

## The options and when each wins

**Project memory file wins** for short facts that apply everywhere and that the agent cannot infer. It loses for anything long, anything area-specific, and anything that must hold every time.

**A skill wins** for procedures and team knowledge that a task needs occasionally. Add `disable-model-invocation: true` when the procedure has side effects, so only a person can start it. It loses when the content is needed on every task, because then it is a memory file with an extra lookup, and when the body is long: after compaction Claude Code re-injects at most 5,000 tokens of it, keeping the start.

**A path-scoped rule wins** for conventions that apply to one area of the tree. It loses for anything that must be present from the first turn of a task or after compaction.

**A hook or deny rule wins** for zero-exception rules with a tool-call shape: never read `.env`, always format after an edit, never touch `migrations/`. It loses for judgement calls, because every hook occasionally fires when it should not and someone maintains each one. The docs suggest that forty enforced rules is a sign most are preferences.

**A sub-agent wins** for noisy work whose conclusion is all the parent needs (a wide search, a full test run) and for independent review, especially with a tool allowlist the harness enforces, such as `tools: Read, Grep, Glob` for a reviewer that cannot edit. It loses on cost and latency, which the sub-agents lesson quantifies.

**A CLI wins** over an MCP server whenever the CLI exists and the model knows it; **an MCP server wins** for systems with no CLI, or where you want per-tool permission rules and structured results.

## A worked decision

The case, all scenario: a 60-engineer team with a TypeScript monorepo, Claude Code as the main agent, GitHub for code review and an observability vendor with no CLI. A platform engineer has collected twenty items from a 700-line CLAUDE.md, Slack threads and the incident wiki. Sorted:

| # | Item | Home | Why |
|---|---|---|---|
| 1 | Run one test file: `pnpm vitest run <path>` | CLAUDE.md | Fact, every task, not inferable reliably |
| 2 | Typecheck must pass before the turn ends | Stop hook, with the command line in CLAUDE.md | Zero exceptions; the model needs the command to check itself |
| 3 | Never read `.env` or `secrets/` | Deny rules plus the sandbox | Zero exceptions; the sandbox also catches shell reads the rule misses |
| 4 | Never edit `src/gen/` (generated client) | PreToolUse hook that exits 2 for that path | Zero exceptions, tool-call shape |
| 5 | Format after every edit | PostToolUse hook | Mechanical; the model need not remember it |
| 6 | Use the helpers in `src/lib/errors.ts`, never throw strings | CLAUDE.md | Decision not visible from the code alone |
| 7 | `src/legacy/` is live; do not copy its patterns | CLAUDE.md | The code misleads |
| 8 | Release procedure, twelve steps | Skill with `disable-model-invocation: true` | Procedure with side effects |
| 9 | Incident triage checklist | Skill the model may invoke | Procedure, occasional |
| 10 | API handler conventions under `src/api/` | Path-scoped rule | Area-specific |
| 11 | Migration file naming under `db/migrations/` | Path-scoped rule | Area-specific |
| 12 | The agent must not run migrations against shared databases | Deny rule on the migrate command, and no shared-database credentials in the sandbox | Enforcement plus removing the capability |
| 13 | Prefer named exports | Delete | The codebase is consistent; the model reads it |
| 14 | Architecture overview of 30 services | Delete; keep a pointer to `docs/architecture.md` | Overviews did not help in the published study; the doc stays for people |
| 15 | Read pull request review comments | `gh` CLI | A CLI exists and the model knows it |
| 16 | Query production logs | MCP server, disabled in sessions that do not need it | No CLI; per-tool permission rules |
| 17 | Find every caller before a cross-package rename | Sub-agent (the built-in Explore agent) | Noisy output, only the list matters |
| 18 | Review the diff against the spec before a pull request | Custom sub-agent with `tools: Read, Grep, Glob` | Fresh reviewer that cannot edit |
| 19 | "Explain diffs in British English" | The engineer's CLAUDE.local.md | Personal preference |
| 20 | Data-handling reminder from compliance | Managed CLAUDE.md | Organisation-wide, cannot be excluded |

Two items show where the homes run out. Item 12 is safer as a missing capability than as a rule: a deny rule matches the command string, so the durable control is that the sandbox has no credentials for a shared database. And "never push to main" (not on the list because the team already has it) belongs in GitHub branch protection, outside the harness, where no permission mode or prompt can reach it.

The resulting CLAUDE.md is items 1, 2 (the command only), 6 and 7 and a few pointers: well under the 200-line target. What the team gives up: the overview no longer primes every session, items 10 and 11 are absent until a matching file is touched, and four enforced rules each need an owner.

## What to measure after deciding

- Context by category from `/context` at session start and after the first compaction, compared with the old file.
- Violations per rule, from transcripts: any edit under `src/gen/`, any read of `.env`, any thrown string. Enforced rules should show zero; prose rules show their real adherence.
- False blocks per hook per week. A hook that blocks legitimate work trains people to disable it.
- Skill invocation rate. A skill the model never picks has a description that does not match how tasks are phrased; one invoked on unrelated tasks has a description that is too broad.
- Usage share per MCP server from `/usage`, to decide which servers stay connected by default.
- Rule presence after compaction for long sessions, by probing the agent with a question only the rule answers.

<p>Hooks and deny rules only for rules with zero exceptions and a tool-call shape: secrets, generated code, protected paths, destructive commands, the stop condition. <Fragment slot="long">
<p>The two constraints are both legitimate. Security is right that prose is followed nearly every time, not every time. Platform is right that each hook fires wrongly some of the time and needs an owner, and that a hook for a preference blocks work that the model would have judged correctly.</p>
<p>I would sort the 45 by two questions: is a single violation unacceptable, and can the rule be checked from a tool call's name and arguments? Rules that pass both become deny rules first (no code to maintain) and hooks second. Rules that are unacceptable to violate but cannot be checked from the call (do not exfiltrate customer data) need a different layer: the sandbox's network and filesystem limits, or removing the credential. Rules with exceptions stay non-deterministic, in the cheapest home that still has them in context when needed.</p>
<p>What I give up: around thirty rules will be followed nearly always rather than always. I write each one down with a measured violation rate from a month of transcripts and a trigger to promote it to a hook if the rate passes a level security agrees to.</p>

## When this is wrong

The table of homes is Claude Code's as of October 2026. Other harnesses have memory files, scoped rules and sandboxes with different loading, enforcement and compaction behaviour. The sorting questions carry over; the specific mechanisms do not.

The deterministic and non-deterministic split assumes a deterministic hook is correct. A hook is code with bugs and timeouts, and Claude Code's `onFailure: "block"` exists because a crashed hook otherwise lets the action through.

The context arithmetic assumes a warm cache. On a cold cache, or with a provider that does not cache tool definitions, the per-request cost of a large memory file or many MCP servers is twenty times higher on Opus 5.5 pricing, and the bill becomes a real reason on its own.
