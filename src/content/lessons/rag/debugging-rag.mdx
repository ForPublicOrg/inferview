## "The bot feels dumb"

Scenario, not a real company: the ticket says only that the internal assistant "feels dumb lately". Someone has already tried a bigger model, a longer system prompt telling it to "only use the provided context", and a higher top-k. Each change helped one example and broke another. Nobody can say whether things are better, because nobody measured where the answers were going wrong.

That is the normal state of a RAG system without stage-level instrumentation. The pipeline has five or so stages, a wrong answer can start in any of them, and the fixes for different stages conflict: raising k helps a retrieval miss and hurts a distraction problem. Debugging RAG is the same discipline as debugging a distributed request: trace one request through every hop, find the first hop where the data is wrong, and fix that hop.

## A failure taxonomy you can cite

Barnett et al. (2024) studied three RAG systems in research, education and biomedical settings and named seven failure points. Use their names; interviewers who know the paper will hear the difference.

"Missing Content" in the paper means the corpus never had the answer. In practice there is a neighbouring failure the paper's list folds into it: the source had the answer and parsing or chunking lost it, as in the table cut in the ingestion module. Check the index, not just the source documents.

## Find the first failing stage

For each question in your eval set you need a label: which chunk ids contain the answer (the gold ids). Then log, for every run, what the index holds, what retrieval returned, what actually went into the prompt, and whether the answer was right. The first stage where the gold ids disappear is the stage to fix.

```python
def triage(gold_ids, index_ids, retrieved_ids, context_ids, answer_correct):
    """Name the first pipeline stage that lost the gold evidence for one eval question."""
    gold = set(gold_ids)
    if not gold & set(index_ids):
        return "missing from index"
    if not gold & set(retrieved_ids):
        return "missed by retrieval"
    if not gold & set(context_ids):
        return "not in context"
    if not answer_correct:
        return "not extracted"
    return "ok"
```

Count the labels across the eval set and you have a ranked bug list. Compare it with where the effort has been going; in the scenario above, three rounds of prompt and model changes went to a stage nobody had measured. Note the distinction between "retrieved" and "in context": rerankers, deduplication, token budgets and truncation all sit between them, and they are where a recall@k that looks healthy hides a broken prompt.

## Oracle context: separate retrieval from generation

The cleanest experiment in RAG debugging is to replace the retrieved chunks with the gold chunks and rerun generation. If the answer is still wrong, retrieval was never the problem. If it becomes right, everything upstream of the prompt is.

<Predict id="rag-oracle-recover" question="At most how many of the 8 failures can retrieval and context fixes recover?" answer={5} tolerance={0} unit="questions">
<Fragment slot="prompt">
<p>A 20-question eval set. The pipeline as deployed answers 12 correctly. You rerun all 20 with oracle context, the gold chunks placed directly in the prompt, and 17 come back correct.</p>
</Fragment>
<p>Oracle context is the best retrieval could ever do, so 17 is the ceiling for any retrieval or context fix: <b>17 - 12 = 5</b> questions. The other 3 fail even with perfect evidence, so they are generation problems (Not Extracted, Wrong Format, Incorrect Specificity or Incomplete) and need prompt, model or output-format work. A team that spends the week on the prompt can recover at most 3 of the 8 and may lose some of the 5.</p>
</Predict>

Anthropic's contextual retrieval work uses the same separation: it reports retrieval quality on its own, as 1 minus recall@20, before any answer is generated. Do that first, because it is cheap and deterministic, and only then grade answers.

## Faithfulness, answer relevance and judge noise

Generated answers need two different checks. **Faithfulness** asks whether every claim in the answer is supported by the retrieved context. Ragas defines it as the number of supported claims divided by the total number of claims, from 0 to 1; its docs work an example where one of two claims is supported, scoring 0.5. Claim extraction and verification are done by an LLM, or in Ragas's `FaithfulnesswithHHEM` variant by Vectara's HHEM-2.1-Open classifier. **Answer relevance** asks whether the answer addresses the question at all; a perfectly faithful answer to a different question scores well on the first and badly on the second.

Three traps:

1. **Faithful is not correct.** Faithfulness measures agreement with the retrieved context. If retrieval returned last year's policy, a faithful answer is faithfully wrong. You still need a correctness check against a reference answer for the eval set.
2. **The judge is noisy.** An LLM verifier disagrees with itself and with humans on borderline claims. Sample its verdicts, label them by hand, and report the agreement rate next to the score. A faithfulness drop of a few points may be judge noise.
3. **Library APIs move.** Ragas's own docs say of the legacy metrics API: "This API will be deprecated in version 0.4 and removed in version 1.0." Pin versions in your eval harness, or the metric changes under you.

## The take-home, end to end

A take-home described by techinterview.org in July 2026 reads: here are 50 markdown documents; build a Q&A system, write an eval set of 20 questions, and report recall@5 and faithfulness. What separates strong submissions is the evaluation, not the retriever.

1. **Write the eval set before tuning anything.** Read the documents, write 20 questions with gold chunk ids and reference answers. Include a few that need two documents, a few with exact identifiers, and two or three that the corpus cannot answer, where the right output is a refusal.
2. **Build the simplest pipeline that could work.** Chunk along Markdown headings, index with BM25 and embeddings, fuse with RRF, put the top 5 in a prompt that asks for citations by chunk id.
3. **Report retrieval first.** recall@5 per question, stating that it is recall (fraction of gold chunks found) rather than hit rate.
4. **Report faithfulness and correctness separately**, with the judge's prompt and a small hand-checked sample.
5. **Triage every failure** with the first-failing-stage function, and run oracle context on the failures.
6. **Write up trade-offs and next steps** in a page: what you would change first, and the measurement that would tell you it worked.

The take-home coding problem in this track's bank builds the scoring part of steps 3 to 5 against a fixed eval set.

<p>Triage. First failing stage per question, counted. Oracle context on the failures: questions that pass with gold context are retrieval or context problems; the rest are generation problems.</p>
<p>Fix in order of impact. Missing content means adding documents or saying "I don't know". Retrieval misses mean hybrid search, better chunking or query rewriting. ## When this is wrong

The triage model assumes a linear pipeline with labelled gold evidence. Agentic systems that retrieve several times blur the stages; trace each retrieval call separately. Questions whose answer is spread across many documents have no small gold set, and global questions may have no single right answer, so faithfulness and coverage matter more than recall. And gold labels themselves go stale as documents change, so the eval set needs the same freshness discipline as the index.

The taxonomy comes from three case studies in one 2024 paper, and the faithfulness definition from one library's documentation. They give you a shared vocabulary, not a guarantee that your system fails the same way.
