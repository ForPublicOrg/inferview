## Two retrievers, two blind spots

BM25 scores a document from three corpus statistics: how rare each query term is, how often it occurs in the document, and how long the document is relative to the average. A bi-encoder scores a document from one learned vector per text. The first keeps exact rare strings and has no idea that "times out" and "timeout" mean the same thing. The second handles paraphrase and loses strings it never learned to represent, such as an error code, a SKU or a hostname. The design question is which failures your query mix can afford, and the levers are mostly not the model: IDF, two BM25 parameters, the text analysis configuration, and whether a cross-encoder gets a look at the shortlist.

## What BM25 actually computes

Lucene 9's `BM25Similarity` adds, for each query term present in a document,

`idf * f / (f + k1 * (1 - b + b * dl / avgdl))`

with `idf = ln(1 + (N - df + 0.5) / (df + 0.5))`, `k1 = 1.2` and `b = 0.75` by default. The source computes the term-frequency part as exactly that fraction, without the `(k1 + 1)` numerator found in textbook BM25; the factor is constant across documents, so rankings do not change, but it means a term's contribution never exceeds its IDF. The `1 +` inside the logarithm keeps IDF positive for a term that appears in every document.

The three tunable parts behave differently. IDF is not a parameter at all: it comes from the corpus, so it changes when the corpus does. In a million documents, a term in one document gets `ln(1 + 999,999.5 / 1.5) = 13.41` and a term in half of them gets `ln 2 = 0.693`, a ratio of about 19. That ratio is why an exact error code dominates a query it shares with common words. `k1` sets how quickly repeated occurrences stop paying. `b` sets how much a long document is penalised, from 0 (length ignored) to 1 (full normalisation). One implementation detail matters when you debug scores: Lucene encodes field length in a single byte, decoded from a 256-entry table, and its explain output labels lengths above the first 40 codes as approximate. Long fields share quantised lengths, so two documents of slightly different length can normalise identically.

## What a bi-encoder misses

A bi-encoder encodes queries and documents separately, so every document vector is computed at index time and a query costs one encoder call plus a nearest-neighbour search. The price is that everything the model will ever know about a document has to survive pooling into one fixed-length vector, by a model trained on someone else's distribution.

BEIR measured what that costs out of domain. Across 18 zero-shot datasets, the average nDCG@10 relative to BM25 was minus 47.7% for DPR, minus 7.4% for ANCE and minus 2.8% for TAS-B, the best dense model in the study. The losses concentrate where the domain or task shifts: on BioASQ, BM25 scored 0.465, TAS-B 0.383 and DPR 0.127; on Touché-2020, BM25 scored 0.367 and TAS-B 0.162. The paper also found a length preference baked in by the training loss: on TREC-COVID, TAS-B retrieved documents with a median length of 10 words against 160 for ANCE.

The 2025 LIMIT paper (revised March 2026, ICLR 2026) makes the identifier case sharper. It proves that the number of distinct top-k sets a single vector can return is bounded by its dimension, and builds a dataset to hit the bound: 50,000 short profiles and 1,000 queries of the form "who likes X". BM25 reaches recall@100 of 93.6; the late-interaction GTE-ModernColBERT reaches 54.8; the best single-vector model, a 4,096-dimension Promptriever on Llama 3 8B, reaches 18.9. LIMIT is built to break single vectors, but its queries are exactly the shape of "which runbook mentions E1234": a rare token whose only job is to match.

The fix that BEIR found most robust is not a better bi-encoder. BM25 followed by a cross-encoder re-ranking its top 100 beat BM25 on 16 of 18 datasets and averaged 11% above it; ColBERT, which keeps one vector per token, beat it on 9 of 18. Both read query and document tokens against each other, which is the thing pooling discards.

## What the cross-encoder costs

A cross-encoder scores one query and document pair per forward pass and caches nothing. Sentence-BERT's paper put a number on it: finding the most similar pair among 10,000 sentences takes n(n - 1)/2 = 49,995,000 BERT inferences, about 65 hours on a V100, against about 5 seconds with SBERT's separate encodings.

## Postgres full-text search is not BM25

Teams that already run Postgres often pair pgvector with `tsvector` and call the lexical side BM25. Four details of the PostgreSQL 18 documentation break that assumption.

- The ranking functions "do not use any global information". `ts_rank` and `ts_rank_cd` have no IDF, so `e1234` and `timeout` carry the same weight per occurrence, and the effect the widget shows for the error code does not exist. The default normalisation option, 0, also ignores document length; length handling is a bit mask you pass explicitly.
- An expression index built with `to_tsvector('english', body)` is used only by queries that call the two-argument form with the same configuration. A query written as `to_tsvector(body)` resolves through `default_text_search_config` and does not use the index. A stored generated `tsvector` column removes the trap and avoids recomputing the vector to recheck matches.
- `to_tsquery` raises a syntax error on tokens not joined by an operator, so raw user input fails; `plainto_tsquery` discards punctuation and operators; `websearch_to_tsquery` never raises a syntax error and is the one built for user input.
- The default parser decides what an identifier becomes before any ranking runs. `foo-bar-beta1` is emitted as the whole hyphenated word and as each part, `8.3.0` is a version token, `/usr/local/foo.txt` a file token, and words then pass through the configuration's dictionaries. Run `ts_debug` on twenty real identifiers from your corpus before you rely on lexical recall for them. `ts_rank_cd` also needs positions: on a stripped `tsvector` it returns zero.

The docs add two costs: ranking reads the `tsvector` of every matching document, which can be I/O bound, and `ts_headline` reads the original document. BM25 scoring next to Postgres data means an extension or an external engine; that choice belongs to the hybrid-search module, but it starts here, with knowing that `ts_rank` is a different scoring function.

## The scorer in code

The scorer is short enough to keep next to your evaluation set so you can check what a parameter change does before touching the production analyser. Problem [rag-002](/problems/rag-002) asks for it from scratch with hidden property tests.

```python
import math
import re
from collections import Counter


def tokens(text):
    return re.findall(r"[a-z0-9]+", text.lower())


class BM25:
    """Lucene 9 scoring: idf * f / (f + k1 * (1 - b + b * dl / avgdl))."""

    def __init__(self, docs, k1=1.2, b=0.75):
        self.k1, self.b = k1, b
        self.tf = {d: Counter(tokens(t)) for d, t in docs.items()}
        self.len = {d: sum(c.values()) for d, c in self.tf.items()}
        self.avgdl = sum(self.len.values()) / len(docs)
        self.df = Counter(term for c in self.tf.values() for term in c)

    def idf(self, term):
        n, df = len(self.tf), self.df[term]
        return math.log(1 + (n - df + 0.5) / (df + 0.5))

    def search(self, query, k=3):
        scores = {}
        for d, c in self.tf.items():
            norm = self.k1 * (1 - self.b + self.b * self.len[d] / self.avgdl)
            s = sum(self.idf(t) * c[t] / (c[t] + norm) for t in set(tokens(query)) if c[t])
            if s:
                scores[d] = round(s, 3)
        return sorted(scores.items(), key=lambda x: -x[1])[:k]


# docs = the six widget documents, keyed "A" to "F"
# BM25(docs).search("E1234 timeout")       [('A', 0.952), ('B', 0.528), ('C', 0.392)]
# BM25(docs).search("timeout retry")       [('C', 0.711), ('B', 0.644), ('E', 0.573)]
# BM25(docs, b=0.5).search("timeout retry")  [('B', 0.688), ('C', 0.666), ('E', 0.553)]
# BM25(docs).search("gateway timeout")     [('B', 0.71), ('A', 0.428), ('F', 0.423)]
```

## When this is wrong

The BEIR comparisons are 2021 models, and embedding models have been retrained many times since; the only number that settles your case is one measured on your corpus. BEIR itself warns that its labels favour lexical systems: on TREC-COVID, 31.8% of TAS-B's top-10 results had never been judged, against 6.4% for BM25, and annotating them raised TAS-B's nDCG@10 from 0.481 to 0.555 while BM25 moved from 0.656 to 0.668. If your relevance labels were pooled from your current BM25 system, your evaluation carries the same bias.

IDF is a corpus statistic, and the corpus is whatever the scoring node can see. Elasticsearch's default `query_then_fetch` scores with per-shard frequencies; Elastic's own 2013 explanation is that this evens out on large shards and misleads on small ones, and `dfs_query_then_fetch` buys global statistics for an extra round trip. A per-tenant index has the same effect by design: a term that is rare across the company may be common inside one tenant.

LIMIT is synthetic and adversarial; it shows a ceiling for single vectors, not that embeddings fail on ordinary prose. And the widget's corpus has six documents, where one occurrence moves IDF a lot. At production scale, the analyser (tokenisation, stemming, synonyms, how identifiers are split) changes recall on identifier queries more than any setting of k1 and b.
