## The decision

An approximate index returns the nearest candidates it found, then the database applies everything else in the query. For a single-tenant corpus where every user sees everything, that order is harmless. With per-user permissions, deletes and freshness requirements it is the main source of wrong answers: rows the user may not see, rows that were deleted, and pages with three results where the caller asked for ten. The design has three parts: where the permission predicate runs relative to the scan (before, during or after), how the index is partitioned, and which mechanism enforces each of three clocks, content freshness, permission revocation and deletion, whose acceptable lag differs by orders of magnitude.

The closest database analogy is the planner choosing between an index on the filter column and an index on the sort key. The difference is that the vector index is approximate and bounded: unless told to scan iteratively, it does not keep producing rows until the `LIMIT` is satisfied, it hands back a fixed-size candidate list.

## Why filtering after the scan starves

The pgvector README states the behaviour and the arithmetic. With approximate indexes, filtering is applied after the index is scanned; if a condition matches 10% of rows, with HNSW and the default `hnsw.ef_search` of 40, "only 4 rows will match on average". The general form is candidates times the visible fraction, assuming the predicate is independent of distance to the query. The expectation hides the tail, which is what a user experiences as a short page:

```python
from math import comb


def p_full_page(k, candidates, visible):
    """Chance that at least k of the ANN candidates pass a permission filter keeping fraction `visible`.
    Assumes the filter is independent of distance to the query."""
    short = sum(comb(candidates, i) * visible**i * (1 - visible) ** (candidates - i) for i in range(k))
    return 1 - short


for candidates, visible in [(40, 0.10), (100, 0.10), (200, 0.10), (1000, 0.01), (2000, 0.01), (20000, 0.0005)]:
    print(f"candidates={candidates:6d} visible={visible:7.2%} expected={candidates * visible:5.1f} "
          f"P(10 rows)={p_full_page(10, candidates, visible):.3f}")
# candidates=    40 visible= 10.00% expected=  4.0 P(10 rows)=0.005
# candidates=   100 visible= 10.00% expected= 10.0 P(10 rows)=0.549
# candidates=   200 visible= 10.00% expected= 20.0 P(10 rows)=0.996
# candidates=  1000 visible=  1.00% expected= 10.0 P(10 rows)=0.543
# candidates=  2000 visible=  1.00% expected= 20.0 P(10 rows)=0.995
# candidates= 20000 visible=  0.05% expected= 10.0 P(10 rows)=0.542
```

Setting the candidate count to exactly k divided by the visible fraction fills the page about half the time. Twice that fills it almost always, which is the oversampling factor to start from when you post-filter on purpose.

Since 0.8.0 (October 2024), pgvector can scan iteratively: with `hnsw.iterative_scan` set to `strict_order` or `relaxed_order`, it keeps scanning the index until enough rows pass the filter or until `hnsw.max_scan_tuples` (20,000 by default) or the memory cap (`hnsw.scan_mem_multiplier` times `work_mem`) stops it. Relaxed order returns results slightly out of distance order with better recall; a materialised CTE re-sorts them. The cap is approximate and does not count the initial scan, but it still bounds what a narrow filter can return.

## Before the scan, when the visible set is small

The other plan is metadata-first: find the rows the user may see, then compute exact distances over that set. pgvector's README recommends starting with an ordinary index on the filter column, which gives exact nearest-neighbour search and works well for conditions that match a low percentage of rows; 0.8.0 also improved the planner's cost estimates for choosing between the two when filtering. The Faiss paper describes the same choice as vector-first versus metadata-first. In the BigANN filtered-search track, Faiss estimates the subset size from term frequencies and switches to metadata-first with brute force when the subset is below 3 x 10<sup>-4</sup> of the database, a threshold the authors call empirical. At 10M vectors that is 3,000 vectors; at 40M it is 12,000.

So the selectivity bands map to plans. A visible set below a few thousand vectors goes metadata-first: exact, cheap, perfect recall. A large visible fraction, say above 10%, goes through the ANN index with iterative scans and a modest `ef_search`. The middle band is where neither works well, and it is the band that a partitioning decision should remove. Your application already knows the visible count for a user, from the ACL tables it joins against, so the routing decision can be made before the query is planned rather than left entirely to the planner's estimates.

## Partitions for tenants, filters for documents

Tenant boundaries and document ACLs are different shapes and deserve different mechanisms. pgvector's README says a shared approximate index lets one tenant's vectors affect another tenant's recall and speed, and recommends list partitioning or separate tables for tenant isolation; partial HNSW indexes fit a filter column with only a few values. A partition per tenant turns a 0.1% tenant filter into a 100% scan of a small index, which removes the middle band for the most common predicate.

Pinecone's multitenancy guide (API version 2026-07) makes the same split with a price attached. One namespace per tenant gives physical isolation, every read or write targets exactly one namespace, and a tenant is offboarded by deleting its namespace. Metadata filtering in one shared namespace scans the whole namespace regardless of the filter, and a query costs 1 read unit per GB of namespace: the guide's own example is 100 tenants of 1 GB each, where a tenant query costs 1 RU in its namespace and 100 RU in a shared one. The limits matter for document ACLs too: an `$in` or `$nin` filter takes at most 10,000 values, and a serverless index allows from 100 namespaces on the Starter plan to 1,000,000 on Enterprise.

Inside a tenant, document permissions become a filter on allowed principals stored with each chunk, matched against the user's expanded group list. Two things break this in practice. Group expansion grows without bound in large directories, and a user in thousands of groups hits filter-size limits. And source systems express permissions the allow-list cannot: inheritance, deny entries, sharing links. When the index cannot represent the rule, the index can only narrow the candidates; the final decision has to come from the source of truth.

## A public reference: Microsoft Copilot

Microsoft's privacy documentation for Microsoft Copilot (renamed from Microsoft 365 Copilot; page dated 9 July 2026) states the contract rather than the mechanism. Copilot surfaces only organisational data the user has at least view permission to; the Semantic Index honours the user's identity-based access boundary so that grounding reaches only content the user is authorised to access; content encrypted through Microsoft Purview is subject to the usage rights granted to the user. The same page asks administrators to use the Microsoft 365 permission models to make sure the right users have access to the right content.

The engineering consequence is that retrieval inherits the source system's permissions, including every overshared site. Before a model sat on top, a file shared with the whole company was reachable but rarely found; ranked retrieval finds it on the first relevant question. A permission-correct design is therefore not the same as a safe rollout, and an access review of the most broadly shared sources belongs in the launch plan. The page does not say whether trimming happens before or after ranking or how quickly a revoked permission takes effect in the Semantic Index, and nothing here assumes either.

## Three clocks

Content freshness is a quality property: a runbook edited ten minutes ago and still served in its old form produces a stale answer. Revocation and deletion are security and compliance properties: a user removed from a group, or a document deleted under a legal request, must stop appearing within a stated bound. They need separate mechanisms because the cheap one for content is wrong for the other two.

- **Index write visibility.** Pinecone is eventually consistent. Each write returns `x-pinecone-request-lsn` and each query returns `x-pinecone-max-indexed-lsn`; when the second is at least the first, the query reflects that write. Postgres with pgvector is transactional: a committed delete is invisible to later queries. Neither tells you anything about permission changes in the source system, which reach the index only through your sync.
- **Deletes inside the graph.** In pgvector, deleted rows remain as dead tuples until vacuum, and the README lists dead tuples next to filters as a reason an HNSW query returns fewer rows. Vacuuming HNSW indexes is slow; the README suggests reindexing concurrently first. Version 0.8.3 (17 June 2026) fixed possible index corruption during HNSW vacuuming and 0.8.4 fixed a "hnsw graph not repaired" error, so a delete-heavy workload needs 0.8.3 at least; the README installs 0.8.7 as of 28 October 2026. Faiss's HNSW does not support removal at all; HNSWlib and FreshDiskANN implement rebuild heuristics.
- **Revocation.** The bound that matters is from the change in the source system to the first query that no longer returns the document. A sync pipeline's bound is its schedule plus its backlog on the worst day. A read-time check of the final candidates against the source system, or a permissions cache with its own short TTL, bounds it by that TTL, at the cost of k lookups per query and dropped rows that the retriever must over-fetch to replace.

## When this is wrong

The arithmetic assumes the permission predicate is independent of distance to the query. It rarely is. A team's documents cluster together, and a user usually searches for their own team's material, so real pages are often fuller than the binomial predicts. The opposite case is the dangerous one: a user whose visible documents are all far from the query gets a short page that looks like a retrieval failure. Measure filtered recall on real user and query pairs, not on random filters.

Partitioning by tenant has costs this lesson does not count: cross-tenant queries for internal support staff become fan-outs, per-tenant lexical statistics change BM25 scores for hybrid search, and thousands of partitions add planning time and maintenance work in Postgres. Pinecone's prices, namespace limits and filter limits are from its documentation for API version 2026-07 and change with plans.

Finally, a correct permission filter is the floor, not the whole control. Prompt injection through a document the user is allowed to read, and answers that combine several permitted documents into something no single document would disclose, pass every check described here; the safety and security tracks cover them.
