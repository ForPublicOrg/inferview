## The decision

Queries per second from a published benchmark is the least useful input to this choice, because a benchmark fixes the four things that decide it: how large the index is against the RAM you will pay for, how selective your filters are, how fast the corpus changes, and who is on call for it. Each of the four can be computed or measured for a stated corpus and growth rate, and when they are, the answer is usually obvious. pgvector keeps vectors next to the rows that own them, inside transactions, backups and access rules you already run. A dedicated or managed engine earns its place when one of the four exceeds what one Postgres primary and its replicas can carry, or when nobody on the team wants to tune Postgres for this workload.

## Index size against RAM

Storage per row is documented. pgvector's `vector` type takes 4 x dims + 8 bytes and `halfvec` takes 2 x dims + 8. The HNSW graph adds its links. Faiss's guidelines give an estimate of (d x 4 + M x 2 x 4) bytes per vector for its in-memory HNSW: the vector, plus 2M four-byte neighbour ids on the bottom layer, with the sparse upper layers ignored. pgvector's on-disk pages carry their own headers and neighbour encoding, so treat the formula as a floor and check the real size with `pg_relation_size` after a trial build on a sample.

The pgvector README is explicit that indexes do not have to fit in memory, but perform better when they do, and its tuning advice starts `shared_buffers` at 25% of server memory, with the operating system's page cache holding the rest. Build time follows the same rule: HNSW builds are much faster while the graph fits in `maintenance_work_mem`, and the server prints a notice when it stops fitting. The levers the README lists, in order of effect on size, are `halfvec` for the table, half-precision or binary-quantised expression indexes, and re-ranking the shortlist with the full vectors.

How much quality quantisation costs depends on the model. Hugging Face's measurement with mixedbread's 1,024-dimension model sized 250M embeddings at 953.67 GB as float32, 238.41 GB as int8 and 29.80 GB as binary (the figures are GiB), and reported that binary retrieval with rescoring kept about 96% of float32 NDCG@10 on MTEB retrieval tasks, int8 about 99.3%. Those numbers are the authors' own and for one model; run the same comparison on your labelled queries before you size hardware for the binary case.

Dimension limits decide some designs before size does. A pgvector index on `vector` stops at 2,000 dimensions, on `halfvec` at 4,000 and on `bit` at 64,000; `sparsevec` indexes take up to 1,000 non-zero elements. OpenAI's text-embedding-3-large returns 3,072 dimensions, so it needs a `halfvec` index or a shorter output through the API's `dimensions` parameter; shortening by hand needs renormalising. Its embeddings are normalised to length 1, so the README's advice to use the inner-product operator applies.

## Filters, writes and the version floor

Filter selectivity is the previous lesson: post-filtering starves below about 0.05% visibility at default iterative-scan limits, partitions remove the tenant predicate, and exact search covers small visible sets. The question for any dedicated engine is the same one, asked of its implementation: how does it execute a top-10 query whose filter keeps 0.1% of rows, and what recall does it reach against exact search at that selectivity? Ask for the mechanism and measure the recall, because the answer differs by engine and by version.

Write rate shapes the index type. HNSW has no training step and can be built on an empty table, but inserts cost more than IVFFlat's and grow with `ef_construction`. IVFFlat builds faster and uses less memory, but its lists come from k-means over the data present at build time: the README says to create it after the table has data and to start with rows / 1,000 lists up to 1M rows and the square root of the row count above that. A corpus that doubles after the build is searched with lists chosen for half of it. Deletes are the other write cost. HNSW vacuuming is slow and the README suggests `REINDEX INDEX CONCURRENTLY` first; Faiss's HNSW does not support removal at all, so engines built on HNSW graphs carry tombstones and rebuild heuristics of their own.

The version floor is 0.8.3, released 17 June 2026, which fixed possible index corruption during HNSW vacuuming; 0.8.4 fixed two more vacuum errors. As of 28 October 2026 the README installs 0.8.7 (released 1 October 2026). The unreleased 0.9.0 adds asynchronous I/O for HNSW and drops Postgres 13 and 14, so a team on Postgres 14 should plan the Postgres upgrade with the extension upgrade. On a managed Postgres service, check which pgvector version it offers before anything else.

## Who operates it

pgvector rides on the write-ahead log, so streaming replication and point-in-time recovery work as they do for every other table, and the vectors commit in the same transaction as the rows and ACLs that own them. The README's scaling path is vertical first, then read replicas, then sharding through Citus or PgDog; a non-partitioned table stops at 32 TB by default. The cost is that vector workloads change the shape of a Postgres instance: large `maintenance_work_mem` for builds, memory for the graph, long vacuums.

A dedicated engine removes that tuning and adds a second source of truth. Every write now has to reach two systems, and every clock from the previous lesson (content, permission, deletion) gets a sync lag that Postgres alone did not have.

## When a managed service pays for itself

Managed pricing turns the four inputs into a bill, and the formula is published. Pinecone's serverless Standard plan (pricing checked 28 October 2026) charges $0.33 per GB-month of storage, $16 to $18 per million read units and $4 to $4.50 per million write units depending on cloud and region, with a $50 monthly minimum. A query costs 1 read unit per GB of the namespace it searches, at least 0.25; an upsert costs 1 write unit per KB, at least 5 per request, and replacing a record bills the old record's size as well. Pinecone's own table puts 1,000 records of 1,536 dimensions at 7.14 KB each.

Take 10M such records: 71.4 GB, about $24 a month to store. In one namespace, every query costs 71.4 read units. One query per second sustained for a 30-day month is 2,592,000 queries, 185M read units, $2,961 at $16 per million. Split the same records into 1,000 tenant namespaces of 71.4 MB and each query costs the 0.25 minimum: $10.37 per sustained query per second per month, 285 times less, for the same data. Re-embedding the corpus once is 71.4M write units for the new records and as many again for the replaced ones, about $571.

```python
def hnsw_gb(n, dims, elem_bytes=2, m=16):
    """Faiss's HNSW estimate (vector plus 2 * m four-byte links) in decimal GB; a floor for pgvector."""
    return n * (dims * elem_bytes + m * 2 * 4) / 1e9


def pinecone_month(namespace_gb, qps, usd_per_m_ru=16.0, usd_per_gb_month=0.33):
    """Serverless on-demand reads and storage for one namespace: 1 RU per GB per query, minimum 0.25."""
    ru = max(0.25, namespace_gb) * qps * 30 * 24 * 3600
    return ru / 1e6 * usd_per_m_ru + namespace_gb * usd_per_gb_month


print(round(hnsw_gb(20_000_000, 1024), 1))       # 43.5   halfvec
print(round(hnsw_gb(20_000_000, 1024, 4), 1))    # 84.5   float32
print(round(pinecone_month(71.4, 1)))            # 2985   one namespace, 1 QPS
print(round(pinecone_month(71.4, 5)))            # 14829  one namespace, 5 QPS
```

The break-even is that bill against the Postgres capacity you would add for the same workload, priced by you: the memory to hold a 43.5 GB graph on the primary and each replica that serves queries, plus the engineering time for builds and vacuums. Read-heavy traffic over one large namespace makes the managed bill climb linearly with queries; many small tenants with modest traffic make it small. The decision follows from your numbers, not from either product's benchmark.

## When this is wrong

The size formula is Faiss's in-memory layout, not pgvector's pages, and it ignores upper layers, tuple headers and fill factor. It is a floor for planning; the trial build on a sample is the number to budget with. The quantisation retention figures come from one model on public retrieval tasks, and a corpus of identifiers and short records can lose more.

Pinecone's figures are list prices for one plan, varying by cloud and region, from pages checked on 28 October 2026; other managed services price by provisioned capacity instead of per query, which changes the break-even shape entirely. And the cost that dominates for most teams is neither memory nor read units but engineers: a team with no Postgres operator gains more from a managed engine than any table here shows, and a team with a strong Postgres platform gains more from keeping one system than the bill suggests.
