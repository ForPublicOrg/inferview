## The question top-k cannot answer

Scenario, not a real company: a product team has transcripts of 400 customer interviews in a well-tuned hybrid index. "What did the Acme interview say about onboarding?" works beautifully. "What are the recurring complaints across all the interviews?" returns five chunks from five interviews, and the model writes a confident summary of those five. Nothing failed in the usual sense. The question needed the whole corpus, and top-k retrieval returns a handful of chunks by construction.

The basic pipeline from the earlier modules is a lookup: find the few chunks most similar to the question. Some questions are not lookups. This module sorts them by shape and gives each shape the pattern built for it, along with what it costs.

## Late interaction and multimodal retrieval

The hybrid-search module introduced ColBERT: one vector per token, scored by summing each query token's best match. The same idea extends to pages. ColPali (ICLR 2025) embeds each page image with a vision language model into a grid of patch vectors and scores them against query tokens the same way, so retrieval works on slides, forms and charts without first extracting text. Its authors report it outperforms text-extraction pipelines on their ViDoRe benchmark. Cohere's embed-v4.0 takes the single-vector route and accepts images and mixed text-and-image inputs such as PDF pages.

The engineering trade is storage for robustness: many vectors per page instead of one per chunk, in exchange for not depending on a PDF parser to get the table right. The generator still needs something it can read, either the page image passed to a multimodal model or extracted text for the pages that were retrieved.

## GraphRAG: precompute the corpus-wide view

Microsoft's GraphRAG (Edge et al., revised February 2025) runs an LLM over every chunk at index time to extract entities and relationships, builds a graph, detects communities of closely connected entities, and writes a summary of each community. A global question is answered by mapping over those community summaries and reducing the partial answers. The paper targets "global sensemaking" questions over corpora of about a million tokens and reports more comprehensive and diverse answers than a vector RAG baseline.

In database terms, GraphRAG is a materialised aggregate: it pays at write time so that a full-corpus question does not scan every row at read time. The documentation lists four query modes: Global (community summaries), Local (an entity and its neighbourhood, for specific questions), DRIFT (local search widened with community context) and Basic (plain top-k vectors).

The cost is the index. Every chunk passes through an LLM, and the project's README warns that "GraphRAG indexing can be an expensive operation". Re-indexing after document changes is the operational pain. Two responses:

- **LazyGraphRAG** (Microsoft, November 2024) builds the index with cheap NLP noun-phrase extraction and defers LLM work to query time. Microsoft reports indexing cost "identical to vector RAG and 0.1% of the costs of full GraphRAG", and global-query quality comparable to GraphRAG Global Search at more than 700 times lower query cost. These are Microsoft's own figures.
- **LightRAG** (Guo et al., revised April 2025) combines graph and vector retrieval at two levels, specific entities and broader themes, with an incremental update path so new documents do not force a rebuild. Its gains are self-reported.

Use a graph when questions are about relationships and the whole corpus. For "what does clause 7 say?", it is an expensive way to do a lookup.

## Agentic RAG: retrieval as a tool in a loop

In the basic pipeline, retrieval always runs once, before generation. Agentic RAG turns retrieval into a tool the model can call zero, one or several times, with checks between calls. The 2025 survey by Singh et al. classifies these systems by how many agents they use, how control flows, and how much autonomy they have.

LangGraph's agentic RAG tutorial is a compact reference design. Its graph has four nodes, `generate_query_or_respond` (decide whether to retrieve at all), `retrieve` (a tool node), `rewrite_question` and `generate_answer`, plus a conditional edge, `grade_documents`, that gives a yes or no relevance judgement with structured output. A "no" routes to `rewrite_question`, whose output goes back to `generate_query_or_respond` for another retrieval. The tutorial sets no retry cap. Two research designs push the same idea further: Self-RAG trains the model to decide when to retrieve and to emit reflection tokens that critique passages and its own output, and CRAG adds a lightweight retrieval evaluator whose confidence triggers different actions, including falling back to web search.

The loop needs a cap. Rewrite and retrieve can cycle forever on a question the corpus cannot answer, and every cycle is a model call. The plain-Python version below makes the cap and the give-up answer explicit; the model calls are stubs.

```python
INDEX = {
    "refund annual plan": ["Annual plans are refundable within 30 days of purchase."],
    "money back yearly subscription": [],
}

def retrieve(query):
    return INDEX.get(query, [])

def grade(question, doc):
    # Stands in for a model call that returns a yes/no relevance judgement.
    return "refund" in doc.lower()

def rewrite(question, previous_query):
    # Stands in for a model call that rephrases the query.
    return {"money back yearly subscription": "refund annual plan"}.get(previous_query, previous_query)

def generate(question, docs):
    return f"Answer based on {len(docs)} document(s): {docs[0]}"

def agentic_answer(question, max_retries=2):
    query = question
    for attempt in range(max_retries + 1):
        relevant = [d for d in retrieve(query) if grade(question, d)]
        if relevant:
            return generate(question, relevant), attempt + 1
        query = rewrite(question, query)
    return "I could not find this in the documents.", max_retries + 1

print(agentic_answer("money back yearly subscription"))
# ('Answer based on 1 document(s): Annual plans are refundable within 30 days of purchase.', 2)
print(agentic_answer("can I pause my plan"))
# ('I could not find this in the documents.', 3)
```

The first question succeeds on the second retrieval, after the rewrite. The second never finds anything and stops after three attempts with an honest refusal. In LangGraph the same guard is the graph's recursion limit plus a retry counter in state; set both explicitly.

<Callout kind="gotcha" label="The grader is a model too">
A relevance grader that says "no" too often turns every question into three retrievals and a refusal; one that says "yes" too often makes the loop decorative. Measure the grader's agreement with human labels on a sample before trusting it to gate retrieval, exactly as you would calibrate an LLM judge.
</Callout>

## Long context, RAG, and cache-augmented generation

Context windows of hundreds of thousands of tokens raise the obvious question: why retrieve at all? The research says it depends, and gives reasons.

Li et al. (December 2024) found long context generally beat RAG on question answering, especially Wikipedia-based QA, while RAG did better on dialogue-based and general queries. LaRA (February 2025) tested 11 models on 2,326 cases and concluded the better choice "depends on a complex interplay of factors". Chroma's Context Rot report (July 2025) tested 18 models and found that "model performance consistently degrades with increasing input length", that a single distractor already hurts, and, in its setup, no notable effect of where the relevant text sat. The older "lost in the middle" result (a U-shaped accuracy curve by position) was measured on 2023 models; treat length and distractors as the consistent finding and position as model-dependent. Anthropic's guidance is practical: put long documents first and the question last, and below about 200,000 tokens consider putting the whole knowledge base in the prompt.

**Cache-augmented generation** (CAG) is that last idea made systematic: load the entire corpus into the context once and reuse it across queries through the provider's prompt cache, so there is no retriever to build or tune. Cost is where it gets interesting.

So the decision runs on four questions. Does the corpus fit with room to spare, and is it stable enough to stay cached? Are the questions global (favouring long context or a graph) or lookups (favouring retrieval)? Does quality hold up at that length on your own eval set, given context rot? And do you need per-user access control, which is far easier to enforce on retrieved chunks than inside one shared cached prompt?

<Fragment slot="short">
<p>Make retrieval a tool in a bounded loop. The model first decides whether to retrieve at all; after retrieval a grader judges whether the passages answer the question; if not, the query is rewritten and retrieval runs again, up to a fixed number of attempts, after which the system says it could not find the answer. That is LangGraph's agentic RAG graph, with an explicit retry cap and a calibrated grader.</p>
</Fragment>
<Fragment slot="long">
<p>Decide. A first model call with the retrieval tool available either answers directly (greetings, questions about the conversation) or emits a query. This is cheaper than retrieving on every turn and is the "generate_query_or_respond" node in LangGraph's tutorial.</p>
<p>Judge sufficiency. A small model grades each passage, or the set, for whether it answers the question, with structured yes or no output. CRAG's version returns a confidence that maps to actions: use the passages, discard them and search elsewhere, or combine both.</p>
<p>Retry. On "no", rewrite the query (expand acronyms, split a compound question, use the conversation for missing referents) and retrieve again. Cap attempts at two or three and keep the count in graph state; set the recursion limit as a backstop.</p>
<p>Give up honestly. After the cap, answer "not found in the documents" and log the question; those logs are the best source of missing-content bugs.</p>
<p>Measure. Grader agreement with human labels, retrieval calls per question, latency per extra loop, and answer accuracy against a single-shot baseline. If the loop rarely changes the answer, it is cost without benefit.</p>
</Fragment>

## When this is wrong

Every pattern here adds model calls, latency and something new to evaluate. Most production questions are lookups, and a tuned hybrid retriever with a reranker answers them better and more cheaply than a graph or an agent loop. Reach for these patterns when your eval set shows a class of question failing for the reason the pattern addresses, not because the architecture diagram looks more current.

The evidence is also uneven. GraphRAG's comparison is against one vector baseline on the authors' question set; LazyGraphRAG's and LightRAG's numbers are self-reported; the long-context studies tested specific models at specific dates, and context windows and caching prices move every few months. The cost example uses one provider's list prices on 2026-10-28.
