## The decision

Every document corpus is parsed once at ingest, and the parsing route fixes what retrieval can ever match and what the generator can ever quote. Three routes are in production use as of October 2026.

**Text extraction with OCR.** Read the PDF text layer where it exists, run layout detection and OCR where it does not, reconstruct tables, and optionally caption figures. Output is text, which is chunked and embedded like any other text. This is a compiler front end with several passes, and each pass has its own failure: reading order across columns, table cells emitted as a flat stream, running headers repeated into every chunk, stamps and handwriting dropped.

**VLM parsing.** Render each page to an image and ask a vision-language model to transcribe it into a structured format. The Qwen2.5-VL report (February 2025) defines an HTML output where every paragraph, table, chart and formula carries a `data-bbox` with its coordinates on the page. The output is still text, so the rest of the pipeline is unchanged, but the model reads the page the way a person does: tables come out with their headers, and a stamp can be described instead of skipped.

**Page-image retrieval.** Skip text at index time. ColPali (ICLR 2025) embeds each page image as a set of vectors, about one per image patch, and scores a query against a page with late interaction: each query token takes its best-matching patch, and the page score sums those maxima. Retrieval returns pages; the generator then reads the page image, or text extracted for the pages that were retrieved.

The routes are not exclusive. Most production designs route pages, not corpora. The playbook below is about which pages take which route and what evidence decides it.

## The inputs that change it

**What the answer must quote.** If an answer must cite a clause verbatim and a reviewer checks the citation against the source, the quoted span has to exist as text that matches the document byte for byte. A born-digital text layer gives that for free. VLM transcription gives text that is usually right and occasionally paraphrased or misread, and nothing in the output marks which. Page-image retrieval gives no text at all until something extracts it.

**The page mix.** Count pages with no usable text layer (scans), pages with tables, and pages whose meaning is visual (stamps, signatures, charts, diagrams). The ColPali paper's measured pipeline spent 7.22 seconds per page, of which OCR took 2.67 and captioning 3.71. Those two steps exist only for pages that need them. A corpus that is 95% born-digital prose and a corpus of scanned forms are different decisions, and the share is a measurement, not a guess.

**Retrieval quality on visual pages.** On ViDoRe, the benchmark the ColPali authors built, ColPali scored an average nDCG@5 of 81.3 against 67.0 for the best text pipeline they tested (Unstructured with captioning, embedded with BGE-M3) and 66.1 for the same pipeline with OCR and no captions. That is the authors' benchmark and their pipelines, chosen because the pages are visually rich. It shows that text extraction loses information on those pages. It does not show that page images win on prose.

**Token bill per page.** VLM parsing and any route that sends pages to a hosted model pay per page, and every figure must name the model family because they count differently (checked 2026-10-28):

- Claude converts each PDF page to an image and also extracts its text; the docs say the text typically costs 1,500 to 3,000 tokens per page, and the image is charged as an image. Claude counts an image as ⌈width/28⌉ × ⌈height/28⌉ visual tokens, capped at 1,568 on the standard tier and 4,784 on Claude 4.7 and later. The docs do not state the resolution a PDF page is rendered at, so the per-page image figure is a cap, not a value.
- Gemini 3 and 4 charge a PDF page 560 tokens at the default and medium settings, 280 at low and 1,120 at high, and on Gemini 3 the natively extracted text is not charged. The media-resolution page says medium is the right setting for documents and that high rarely improves OCR on standard documents. The document-processing page still states 258 tokens per page, which matches neither row of that table; count tokens on your own files before budgeting.

**Storage per page.** ColPali stores 1,030 vectors per page: 1,024 image patches plus the text-prompt tokens, at 128 dimensions in float16. A single-vector text embedding stores one.

## The options and when each wins

**Text extraction wins** when most pages are born-digital, answers must quote text exactly, and the corpus is large enough that per-page model calls dominate the budget. Its known failures are tables and visual content, and both can be routed elsewhere page by page. It loses when the text layer is absent or wrong (scans, image-only PDFs, PDFs whose text layer came from a poor OCR pass years ago) and when the answer lives in layout.

**VLM parsing wins** for pages where structure carries meaning and a text route breaks it: tables whose rows mean nothing without the header, forms, stamped and signed pages, scans. The output feeds the same chunker, index and citation path as everything else, which keeps one retrieval system. The cost is per page and dominated by output, because the model writes the page back out as text. It loses on exactness: a transcription can misread a digit in a fee table, and the error is silent unless you compare it against something. The Qwen2.5-VL report's own OmniDocBench table puts English edit distance between 0.226 and 0.330 across four early-2025 models, so the parser model is a choice to evaluate, not a constant.

**Page-image retrieval wins** when queries are about what a page looks like or contains visually (charts, diagrams, slide decks, infographics), when the corpus is modest, and when indexing speed matters: 0.39 seconds per page in the paper against 7.22 for the full extraction pipeline. It loses on storage, on queries that need a quoted span, and on the evidence base, which is one benchmark whose retrieval pools are 500 to 1,600 pages per subset, with an English-only training set.

## A worked decision

The case, all scenario: a legal-operations team indexes 5,000 executed supplier contracts of about 200 pages each, one million pages in total. Most are born-digital; an unknown share are scans of signed copies. Fee schedules sit in tables in the annexes. The final pages carry company stamps and signatures. The questions are clause lookups ("what notice does the Acme agreement require for termination"), table lookups ("the monthly fee for tier 2 support") and execution status ("is this copy stamped by both parties"). Clause answers must quote the clause and cite the page.

First, the bill for VLM-parsing everything on Gemini 3.5 Flash-Lite, the newest Flash-Lite model on the pricing page. Input: 200 pages × 560 tokens = 112,000 tokens per contract, $0.034 at $0.30 per million. Output is the transcription. Assume, as a scenario input, that each page writes back about as many tokens as Claude's docs say a page of text costs, 1,500 to 3,000: that is 300,000 to 600,000 output tokens per contract, $0.75 to $1.50 at $2.50 per million. Output is 22 to 44 times the input cost, so the dominant term is how much text the parser writes, not how the page image is billed. On the batch tier ($0.15 and $1.25) the whole corpus comes to 5,000 × ($0.017 + $0.375 to $0.75), about $1,960 to $3,840.

On Claude, the same contract cannot go in one request on a model with a context window under 1M tokens: the limit is 100 pages, and 200 pages at 1,500 or more text tokens each is at least 300,000 tokens before images. At most 200 × (3,000 + 1,568) = 913,600 input tokens per contract on a standard-tier model, about $0.91 at Claude Haiku 4.5's $1 per million, before output. The figure that matters is measured with token counting on ten real contracts.

Second, page-image retrieval over everything: about 264 GB of vectors before pooling (the Predict above), and at 0.39 seconds per page about 108 hours of encoding on the paper's hardware (1,000,000 × 0.39 / 3,600). Feasible, but it buys page retrieval for a workload whose main query type needs quoted clause text.

The decision:

1. Every page goes through text-layer extraction first. Pages with a usable text layer and no detected table keep it; this is the route clause lookups and citations use.
2. Pages with no usable text layer, pages where table detection fires, and the final pages of each contract go to a VLM parser that emits HTML with bounding boxes. Tables are stored with their header attached to every row. Stamps and signatures become page-level fields (`stamped_by`, `signed_by`) extracted from the transcription, and execution-status questions are answered from those fields, not from retrieval.
3. Page-image retrieval is not built now. It is the fallback if the evaluation in the next section shows table or visual queries failing after VLM parsing.

The VLM bill scales with the share of pages routed to it, so that share is the first number to measure. If it turns out that 10% of pages are routed, the parse bill is a tenth of the full-corpus figure. If most contracts are scans, the decision reverts to VLM parsing everywhere and the clause citations need a verification step, because there is no text layer to check against.

What the team gives up: one pipeline. There are now two parsers whose outputs must chunk the same way, and a router whose mistakes (a table page sent down the text route) look like retrieval failures later.

## What to measure after choosing

- Route shares: pages per route, and the share of pages with no text layer. These set the bill.
- Parse quality per route, on a stratified sample of pages transcribed by hand (prose, table, scan, stamp page): character edit distance, as OmniDocBench uses, and table cell accuracy with the header-row association checked.
- Citation exactness: the share of quoted spans in answers that occur verbatim in the stored text for the cited page.
- Retrieval recall on labelled questions split by page type, so a regression on table pages is not averaged away by prose.
- Router errors: table or stamp pages that went down the text route, found by sampling the text route's output.
- Measured tokens and cost per contract, and pages per second through each route.

## When this is wrong

The evidence for page-image retrieval comes from one benchmark built by the method's authors, with retrieval pools of 500 to 1,600 pages per subset. A million-page corpus is 625 to 2,000 times larger, and nDCG@5 on a small pool says little about ranking among that many more distractors. The decision procedure above applies to any page-image retriever; the numbers are ColPali's alone.

The VLM numbers move every quarter. The OmniDocBench figures here compare early-2025 models as reported by one of the vendors in the table. The token counts per page are checked as of October 2026 and already disagree between two pages of Gemini's own documentation.

The cost model assumes the parse runs once. It does not: a parser upgrade, a schema change in the HTML output or a chunking change re-runs the routed pages, so budget the parse as a recurring cost with a version, which is the subject of the pipeline lesson in this module.

Some corpora have no text to protect. For slide decks, engineering drawings or scanned forms where nobody needs a verbatim quote, page-image retrieval plus a VLM reading the retrieved page can be the whole design.
