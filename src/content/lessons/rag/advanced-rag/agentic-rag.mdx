## A retry policy with an unreliable error classifier

In a fixed pipeline, retrieval runs once and generation uses whatever came back. Agentic retrieval inserts a judgement after retrieval: is this context sufficient? If not, rewrite the query and try again. Structurally it is a retry loop, and it inherits the usual retry question, which failures are worth retrying, with one difference that dominates its cost profile. The "error" is a model's verdict, and the verdict "not relevant" does not say whether the failure is transient (the query was phrased badly; a rewrite can fix it) or permanent (the corpus does not contain the answer; no rewrite can). An unanswerable question looks exactly like a badly phrased one, every time, until the budget runs out.

So the design questions are: what judges sufficiency and how well, what the loop does between attempts, when it stops, and what it says when it stops. The metric that ties them together is cost per answered question, because a loop that answers 2% more questions at three times the spend may be a regression.

## Self-RAG: the model decides when to retrieve

Self-RAG (Asai et al., 2023) trains the generator to emit reflection tokens inline. `Retrieve` (yes, no, continue) decides whether to fetch passages at all; `IsRel` judges each passage's relevance; `IsSup` judges whether the generated segment is fully, partially or not supported by the passage; `IsUse` rates overall usefulness from 1 to 5. Retrieval fires when the normalised probability of `Retrieve=Yes` exceeds a threshold, 0.2 on most tasks. At decode time it runs a segment-level beam search scored by generation probability plus weighted critique scores, so the reflection tokens are also a ranking signal.

The training cost is the catch. A critic model (initialised from Llama 2-7B) learns the reflection tokens from GPT-4 labels, inserts them into 150,000 training examples offline, and the generator (Llama 2 7B or 13B) is fine-tuned on the result. The paper reports PopQA accuracy of 54.9 (7B) and 55.8 (13B) against 51.8 for retrieval-augmented Llama2-chat 13B and 50.8 for retrieval-augmented ChatGPT, and PubHealth 72.4 and 74.5 against 54.7 for retrieval-augmented ChatGPT. It is not uniformly ahead: on ARC-Challenge ChatGPT scored 75.3 against Self-RAG 13B's 73.1. For a team calling a hosted model, Self-RAG's lasting contribution is the decomposition of the judgement into four separate questions, each of which can be a prompted grader.

## CRAG: a small evaluator with three actions

Corrective RAG (Yan et al., 2024) puts the judgement in a separate, cheap model. A T5-large evaluator (0.77B parameters) scores each retrieved document, and the scores map to three actions. **Correct**: at least one document clears an upper threshold, so refine the documents (split into strips, drop low-scoring strips) and generate. **Incorrect**: every document falls below a lower threshold, so discard them and search the web with a rewritten keyword query. **Ambiguous**: anything else, so combine both sources. The thresholds were tuned per dataset, for example 0.59 and -0.99 on PopQA.

Two numbers make CRAG's case. Its evaluator judged PopQA relevance with 84.3% accuracy against 58.0% for prompted ChatGPT, so a small trained grader beat a large prompted one at this task. And plugged into a plain RAG pipeline on LLaMA2-hf-7b, PopQA accuracy went from 50.5 to 54.9; on the Self-RAG generator, from 52.8 to 59.8. The overhead table is the other half: execution time per PopQA instance, retrieval excluded, was 0.363 s for RAG, 0.512 s for CRAG and 0.741 s for Self-RAG. The fallback carries its own risk, which the authors name: web results can be biased or unreliable, and a web search is a data egress decision for a private corpus.

## The LangGraph tutorial loop

LangGraph's agentic RAG tutorial (checked 2026-10-28) is the shape most teams copy. Four nodes: `generate_query_or_respond` (the model, with a retriever tool bound, answers directly or calls the tool), `retrieve` (a tool node), `rewrite_question` and `generate_answer`. After `retrieve`, a conditional edge `grade_documents` asks a model for a structured `binary_score` of yes or no. Yes goes to `generate_answer`; no goes to `rewrite_question`, which routes back to `generate_query_or_respond` for another retrieval.

The tutorial sets no retry counter and passes no recursion limit. LangGraph's own backstop is the graph recursion limit, which the docs give as 1,000 steps by default from version 1.0.6, after which the graph raises `GraphRecursionError`.

## A loop with a budget, a progress check and an abstain path

The fix is three pieces of state: a rewrite cap, a check that a rewrite changed anything, and a terminal node that answers "not found in the documents" and logs the question. In LangGraph the cap is a counter in graph state checked by the routing function; `RemainingSteps` is the documented way to route to a fallback before the recursion limit instead of catching the exception outside the graph. The progress check compares the retrieved document ids across attempts: if the rewrite returns the same set, a further rewrite is unlikely to help, so stop early.

The accounting below makes the effect of the cap measurable. The model calls are stubs; a question is the number of rewrites it needs before retrieval finds support, or `None` if the corpus cannot answer it.

```python
PRICE_PER_MTOK = 2.00    # Claude Sonnet 5.5 input, checked 2026-10-28
TOKENS_PER_CALL = 2_000  # scenario: prompt plus retrieved context per model call


def run(question, max_rewrites):
    """question = attempts needed before retrieval finds support, or None if the corpus cannot answer.
    Returns (answered, model_calls)."""
    calls = 0
    for attempt in range(max_rewrites + 1):
        calls += 1                       # decide: answer directly or emit a retrieval query
        calls += 1                       # grade the retrieved documents
        if question is not None and attempt >= question:
            return True, calls + 1       # generate the grounded answer
        if attempt < max_rewrites:
            calls += 1                   # rewrite the question
    return False, calls + 1              # abstain: "not found in the documents"


def cost_per_answered(workload, max_rewrites):
    results = [run(q, max_rewrites) for q in workload]
    answered = sum(ok for ok, _ in results)
    calls = sum(c for _, c in results)
    dollars = calls * TOKENS_PER_CALL * PRICE_PER_MTOK / 1e6
    return answered, calls, round(dollars / answered, 4)


workload = [0] * 80 + [1] * 10 + [None] * 10   # 80 first try, 10 after one rewrite, 10 unanswerable
for cap in (0, 1, 2, 5, 332):
    print(cap, cost_per_answered(workload, cap))
# 0 (80, 300, 0.015)
# 1 (90, 360, 0.016)
# 2 (90, 390, 0.0173)
# 5 (90, 480, 0.0213)
# 332 (90, 10290, 0.4573)
```

On this scenario workload one rewrite buys ten more answered questions for 7% more cost per answer. Every rewrite after that buys nothing and is paid entirely by the ten unanswerable questions. With 332 rewrites, roughly the tutorial graph under the default recursion limit, those ten questions account for 9,990 of 10,290 calls and the cost per answered question is about 29 times the cost with a cap of one. The unanswerable share of real traffic, not the average question, sets the bill, and it is a number you can measure from abstain logs once an abstain path exists.

<Callout kind="gotcha" label="The grader's error rates are the loop's control law">
A grader that says "no" to relevant documents turns answerable questions into retries and, at the cap, into false abstentions. A grader that says "yes" to irrelevant ones makes the loop decorative and passes weak context to generation. CRAG's 84.3% against 58.0% is a reminder that a prompted model is not automatically a good relevance judge. Label a few hundred (question, documents) pairs, measure both error rates, and set the cap with them in hand.
</Callout>

What to measure after shipping: cost per answered question; the distribution of model calls per question (p50 and p95, since the tail is the unanswerable set); abstention rate on a held-out set of questions known to be unanswerable; accuracy against a single-shot baseline on the same questions; and the share of answers that changed because of a retry. If the last number is small, the loop is cost without benefit.

## When this is wrong

The research numbers come from 7B and 13B Llama 2 models and ChatGPT on short-form QA benchmarks (PopQA, PubHealth, ARC-Challenge) in 2023 and 2024. A current hosted model with native tool calling already decides when to call a retriever, and the gap between it and a trained reflection-token model on your task is unmeasured until you measure it. Read Self-RAG and CRAG for their decomposition of the judgement and their overhead accounting, not for their accuracy deltas.

The cost model assumes calls are sequential and equally sized. Real loops grow the context on each attempt (earlier documents and rewrites stay in the message history), so later attempts cost more than earlier ones and the tail is worse than the uniform estimate. Parallel decomposition changes the latency picture without changing the token bill.

Finally, abstaining is not always the right terminal state. For some products a best-effort answer with a visible caveat is better than "not found", and for regulated ones even a caveated answer from weak context is unacceptable. The abstain policy is a product decision with a cost on each side; the loop only makes it enforceable.
