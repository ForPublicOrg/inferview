## Three ways to get the corpus into the answer

When the corpus fits the window, retrieval becomes optional, and the choice is among three designs. **RAG** sends a few retrieved chunks per query and can miss. **Long context** sends the whole corpus on every query and cannot miss at the retrieval step, but the model can still fail to use what it was given. **Cache-augmented generation** (CAG; Chan et al., WWW 2025) is long context with the corpus loaded once as a cached prefix, so repeated queries pay a read price rather than the full input price. The paper positions it for knowledge of "limited and manageable size".

A window large enough to hold the corpus is now the default rather than the exception: Claude 4.6 and later models other than Haiku 5.5 bill the full 1M-token window at standard rates (checked 2026-10-28). Capacity is no longer the question. The questions are what happens to quality at that length, what each query costs once the cache is accounted for, and which workloads break the cache.

## What happens to quality at length

**Position.** Lost in the Middle (Liu et al., TACL) measured multi-document QA with the answering document moved through the context. Accuracy was U-shaped: best at the start or end, worst in the middle. For GPT-3.5-Turbo, closed-book accuracy with no documents was 56.1% and oracle accuracy with only the right document was 88.3%; with 20 or 30 documents and the answer in the middle, accuracy fell below closed-book. More context also stopped helping early: retrieving 50 documents instead of 20 improved GPT-3.5-Turbo by 1.5% and claude-1.3 by 1%. These are 2023 models with 4K to 100K windows.

**Length and distractors.** Chroma's Context Rot report (July 2025) tested 18 models, including Claude Opus 4, GPT-4.1, o3, Gemini 2.5 Pro and Qwen3. Performance degraded with input length across experiments, unevenly by model and task. A single distractor (a passage similar to the answer but wrong) lowered accuracy against the needle alone, and four lowered it further. On LongMemEval, every model scored significantly higher with a focused prompt of about 300 tokens than with the full history of about 113,000 tokens containing the same answer. Two findings cut against intuition: in their needle task position made no notable difference, and every model did better when the haystack's sentences were shuffled than when they formed coherent text.

**Benchmarks that predict.** HELMET (ICLR 2025) evaluated 59 models across seven task categories at 8K to 128K tokens and found that synthetic needle-in-a-haystack scores do not reliably predict downstream performance: no synthetic task averaged a correlation above 0.8 with the real categories, and most models score near perfectly on needles. Re-ranking and generation with citations degraded with length even for the strongest models. A vendor's needle chart is therefore not evidence that a model can use 500,000 tokens of policy documents; RULER-, NoLiMa- or HELMET-style tasks, or your own eval, are.

The comparison studies do not hand a winner to either side. Li et al. (December 2024) found long context generally ahead on QA benchmarks, especially Wikipedia-based ones, with summarisation-based retrieval about level and chunk-based retrieval behind; RAG did better on dialogue-based and general queries. Retrieval is also a filter for distractors, which is the failure Chroma measured. Anthropic's prompting guidance (checked 2026-10-28) is the cheap mitigation if you do send the corpus: documents at the top, the query at the end (a vendor test claim of up to 30% better responses), and a request for relevant quotes before the answer.

## What a query costs

Scenario: a 150,000-token handbook. RAG sends 5 chunks of 800 tokens. Instructions and the question are the same in both and ignored. Prices are Claude Sonnet 5.5 list prices checked 2026-10-28: $2 per million base input tokens, $2.50 for a 5-minute cache write, $0.10 for a cache hit (Sonnet 5.5 and Opus 5.5 read at 0.05x base; most other models at 0.1x).

Uncached, the handbook costs 150,000 × $2 / 1M = $0.30 per query against 4,000 × $2 / 1M = $0.008 for RAG, 37.5 times as much. A cache write costs $0.375.

Caching closes the 37.5 times gap to under two, because the read price on this model is 5% of base. The ratio is the corpus size times the read multiplier divided by the retrieved tokens: at a 0.1x read multiplier it would be 3.75, and a 900,000-token corpus on Sonnet 5.5 would be 11.25. Latency and quality are not in this number.</p>

The warm-cache figure holds only when the cache is warm. The 5-minute lifetime is refreshed by each hit, measured from the start of the request; any change to the cached prefix, such as one edited paragraph near the top of the handbook, invalidates it and the next query pays the write. The accounting below shows what traffic and edits do to the per-query cost.

```python
# Claude Sonnet 5.5 list prices per million tokens, checked 2026-10-28
BASE, WRITE_5M, HIT = 2.00, 2.50, 0.10


def stuffed_cost_per_query(corpus_tokens, queries_per_hour, corpus_edits_per_hour=0):
    """Whole corpus as a cached prefix with the 5-minute TTL; queries evenly spaced."""
    if queries_per_hour == 0:
        return 0.0
    gap_minutes = 60 / queries_per_hour
    if gap_minutes >= 5:                       # cache expires between queries: every query writes
        writes = queries_per_hour
    else:                                      # one write per hour plus one per corpus edit
        writes = min(queries_per_hour, 1 + corpus_edits_per_hour)
    hits = queries_per_hour - writes
    dollars = (writes * WRITE_5M + hits * HIT) * corpus_tokens / 1e6
    return dollars / queries_per_hour


def rag_cost_per_query(chunks=5, chunk_tokens=800):
    return chunks * chunk_tokens * BASE / 1e6


print("rag", rag_cost_per_query())                    # 0.008
for qph in (6, 20, 60, 600):
    print(qph, round(stuffed_cost_per_query(150_000, qph), 4),
          round(stuffed_cost_per_query(150_000, qph, corpus_edits_per_hour=4), 4))
# 6 0.375 0.375
# 20 0.033 0.105
# 60 0.021 0.045
# 600 0.0156 0.018
```

At six queries an hour the cache never survives and every query pays the write, 47 times RAG. At 600 an hour it approaches the 1.875 floor. Four edits an hour triple the cost at 20 queries an hour. The function is a lower bound on misses: real traffic is bursty, so a stream averaging 20 an hour still has gaps longer than five minutes. The 1-hour TTL ($4 per million to write here) moves the threshold but doubles the price of every miss.

Two properties of the cache make it a poor fit for some workloads regardless of price. Matching is on identical prefixes, so per-user document sets mean per-user prefixes and per-user writes; and isolation is per organisation and, on the Claude API, per workspace, which is a tenancy boundary, not an authorisation model. Retrieval filters chunks by the caller's permissions before they reach the model; a shared stuffed prompt shows every caller the whole corpus. The price structure is also model-specific: Haiku 5.5 bills every prompt over 100,000 tokens at higher rates ($0.50 instead of $0.10 per million input tokens, $0.05 instead of $0.01 for cache hits), so the same handbook crosses a price step on that model.

## Deciding per workload

| Workload (scenario) | Fits and stable? | Traffic keeps cache warm? | Per-user access? | Default |
|---|---|---|---|---|
| 150k-token employee handbook, edited monthly, 300 queries an hour | Yes | Yes | No | CAG, with an eval at full length using realistic distractors |
| 40M-token support corpus, edited hourly | No | n/a | Partly | RAG; long context only for the retrieved set |
| 600k-token contract bundle, one analyst, 15 questions over an afternoon, questions span documents | Yes | Bursty | No | Long context with the 1-hour TTL, quotes first; RAG for lookups within it |

The decision runs on five inputs: corpus size against the window; how often the corpus changes against the cache lifetime; query rate against the cache lifetime; whether access differs by user; and whether questions synthesise across documents (favouring long context) or look up facts (favouring retrieval, which also removes distractors). The fifth input is measured on your own eval set at the real length, not inferred from a needle score.

## When this is wrong

Model generations move this decision faster than any other in the module. Lost in the Middle measured 2023 models, Context Rot measured mid-2025 models, and the window, price and read multiplier used here were checked on 2026-10-28 for one provider. Re-run the cost function with current prices and re-run the length eval with the current model before reusing either conclusion.

The cost model ignores output tokens, latency and the retrieval system's own cost (embedding, index hosting, reranking), which for a small corpus can exceed the token savings. It also assumes the provider's cache behaves as documented under load; measure cache hit rates from the usage fields in responses rather than inferring them from traffic.

Finally, the categories blur in practice. Production designs usually combine them: retrieval to choose documents, long context to read them whole, and caching for the stable instructions and the most-used documents. The useful question is which of the five inputs decides your workload, not which architecture wins in general.
