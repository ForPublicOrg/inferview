## The problem the paper took on

In 2020 the quality frontier for passage ranking was the BERT cross-encoder: concatenate query and passage, run the full model, read a score. Table 1 of the ColBERT paper puts BERT-base re-ranking of the BM25 top 1,000 on MS MARCO at 10,700 ms per query and 97 trillion FLOPs. A bi-encoder with one vector per passage is cheap and indexable, but it compresses a passage into a single point and loses term-level matching. ColBERT (Khattab and Zaharia, SIGIR 2020) asked whether a ranker can keep per-token matching while precomputing everything on the document side.

Its answer was to delay the interaction. Encode the query and the passage separately, keep every contextualised token vector, and compare them with a cheap operator at query time. On the same re-ranking task the paper reports 61 ms and 7 billion FLOPs; the "over 170 times faster, 14,000 times fewer FLOPs" headline is 10,700 / 61 and 97T / 7B. The cost moved from compute to storage, and every later paper in this lineage is about paying that bill.

## The mechanism, in engineering terms

Each query is padded or truncated to Nq = 32 tokens (padding uses BERT's mask token, which the paper calls query augmentation and shows matters in its ablation). Each passage token becomes one 128-dimensional vector. The score is MaxSim: for every query vector, take its highest similarity against any passage vector, then sum those 32 maxima. It behaves like a join in which each query term picks its best partner and the partners never compete with each other.

Two properties follow. Document vectors are computed once at index time, as with a bi-encoder. And each query vector's best match can be found with an approximate nearest-neighbour index over all token vectors, which makes end-to-end retrieval possible: ColBERT issues 32 ANN searches (faiss IVFPQ, 2,000 partitions, 10 probed, 1,000 hits per query vector), maps hits back to passage ids, and scores the union exactly. End to end it reached 36.0 MRR@10 on MS MARCO dev at 458 ms, against 18.7 for Anserini BM25.

```python
import math
import random


def maxsim(query, doc):
    """For each query vector, the best dot product against any document vector, summed."""
    return sum(max(sum(a * b for a, b in zip(q, d)) for d in doc) for q in query)


def index_bytes(passages, tokens_per_passage, dim=128, residual_bits=None, float_bytes=2):
    vectors = passages * tokens_per_passage
    if residual_bits is None:                      # ColBERT: every dimension stored as a float
        per_vector = dim * float_bytes
    else:                                          # ColBERTv2: 4-byte centroid id + b bits per dimension
        per_vector = 4 + dim * residual_bits // 8
    return vectors * per_vector


def unit(rng, dim=128):
    v = [rng.gauss(0, 1) for _ in range(dim)]
    norm = math.sqrt(sum(x * x for x in v))
    return [x / norm for x in v]


rng = random.Random(0)
query = [unit(rng) for _ in range(32)]
docs = {f"p{i}": [unit(rng) for _ in range(68)] for i in range(3)}
docs["p3"] = query[:8] + [unit(rng) for _ in range(60)]   # 8 token vectors close to the query's
print({name: round(maxsim(query, vecs), 2) for name, vecs in docs.items()})
# {'p0': 6.82, 'p1': 6.69, 'p2': 6.64, 'p3': 12.77}

for label, kwargs in [("ColBERT, fp16", {}), ("ColBERTv2, 2-bit", {"residual_bits": 2}), ("ColBERTv2, 1-bit", {"residual_bits": 1})]:
    print(label, round(index_bytes(8_800_000, 68, **kwargs) / 2**30, 1), "GiB before the inverted list")
# 142.7, 20.1 and 11.1 GiB
```

The passage that shares eight token vectors with the query scores almost twice the random ones, because eight of its 32 maxima are 1.0. A single pooled vector cannot express that: a short exact match inside a long passage keeps its full weight.

The scoring cost is visible in the function too. One 68-token passage against a 32-token query is 32 × 68 × 128 = 278,528 multiply-adds. Scoring all 8.8 million MS MARCO passages exhaustively would be about 2.5 × 10¹² per query, which is why every system in this lineage is a candidate generator followed by exact MaxSim on a few thousand passages.

## The storage numbers, reproduced

The 68 in the code is measured, not guessed. PLAID's Table 1 lists 597.9 million token vectors for MS MARCO v1's 8.8 million passages, an average of 597.9M / 8.8M = 67.9 tokens per passage. With that count the published footprints can be recomputed from the encoding alone:

| Encoding | Bytes per vector | 597.9M vectors | Paper reports |
|---|---|---|---|
| ColBERT, 32-bit floats | 128 × 4 = 512 | 285.1 GiB | 286 GiB (ColBERT Table 4) |
| ColBERT, 16-bit floats | 128 × 2 = 256 | 142.5 GiB | 143 GiB re-rank, 154 GiB with the end-to-end index (ColBERT Table 4) |
| ColBERTv2, 2-bit residual | 4 + 32 = 36 | 20.0 GiB | 25 GiB including a 4.5 GiB inverted list |
| ColBERTv2, 1-bit residual | 4 + 16 = 20 | 11.1 GiB | 16 GiB including a 4.5 GiB inverted list |

ColBERTv2 (Santhanam et al., NAACL 2022) gets there with residual compression. It runs k-means over a sample of token vectors, with the number of centroids proportional to the square root of the number of embeddings, then stores each vector as the id of its nearest centroid (4 bytes) plus the residual from that centroid quantised to 1 or 2 bits per dimension. The bet, which the paper supports with a clustering analysis, is that ColBERT's token vectors cluster tightly by word sense, so the residual carries little information. Applied to a vanilla ColBERT model, 2-bit compression left MRR@10 at 36.2 and 1-bit dropped it to 35.5. With its other change, distillation from a cross-encoder with hard negatives, ColBERTv2 reached 39.7 MRR@10 on MS MARCO dev against ColBERT's 36.0.

The paper's own comparison point matters for the decision: one 768-dimensional float32 vector per passage for about 9 million passages is "a little over 25 GiB", the size of the 2-bit ColBERTv2 index. Compression turned late interaction's footprint from an order of magnitude above a bi-encoder into roughly the same.

## PLAID: the latency half of the bill

Compression made the index small but not fast. PLAID (Santhanam et al., 2022) profiled vanilla ColBERTv2 on a GPU and found that index lookup and residual decompression dominated query time: the initial candidate set for an MS MARCO query ran to roughly 10,000 to 40,000 passages, each with tens of vectors to gather and decompress before MaxSim.

PLAID's observation is that the centroid id alone is a usable proxy. Replace every passage token by its centroid and the passage becomes a bag of centroid ids, scored against the query with the same MaxSim but through a query-to-centroid score table computed once per query. The paper shows that retrieving 10 × k passages with centroids alone still contains over 99% of vanilla ColBERTv2's top k. The engine runs four stages: candidate generation from the nearest centroids per query token, centroid interaction with pruning (centroids far from every query vector are skipped), centroid interaction without pruning, and full decompression and MaxSim for the survivors only. It also stores the inverted list as centroid to passage ids instead of embedding ids, which on MS MARCO v2 shrank it from 71 GB to 27 GB.

On MS MARCO v1 at its most conservative setting (k = 1000), PLAID matched vanilla ColBERTv2's 39.7 MRR@10 at 38.4 ms on a GPU against 259.6 ms, and at 101.3 ms on 8 CPU threads against 4,568.5 ms. Those are the abstract's "up to 7 times on GPU and 45 times on CPU" (259.6 / 38.4 = 6.8, 4,568.5 / 101.3 = 45.1). The largest index it evaluated, MS MARCO v2 with 138.4 million passages and 9.4 billion tokens, was 246.0 GiB under vanilla ColBERTv2 and 202.2 GiB under PLAID. The ColBERT repository's main branch is described as ColBERTv2 plus PLAID, and its indexing example uses `nbits=2`.

## MUVERA: make it look like single-vector search

PLAID is a bespoke engine. MUVERA (Dhulipala et al., Google, 2024, revised June 2026) asks how to run multi-vector retrieval on the single-vector ANN infrastructure most teams already operate. It builds a Fixed Dimensional Encoding per query and per document: partition the vector space into buckets with SimHash, sum the query's vectors per bucket (average them for documents), optionally project each block down, repeat with independent partitions and concatenate. The inner product of a query FDE and a document FDE approximates the MaxSim score (the paper calls it Chamfer similarity) with a proven error bound. Retrieval is then one MIPS query over FDEs, followed by exact MaxSim re-ranking of the candidates.

On six BEIR datasets against PLAID the paper reports, averaged, about 10% higher recall and 90% lower latency, with recall within 0.4% of PLAID on MS MARCO. The end-to-end system uses 10,240-dimensional FDEs, and product quantisation (PQ-256-8) compresses each to 1,280 bytes.

Do the storage arithmetic before reading MUVERA as a storage win. An uncompressed 10,240-dimensional float32 FDE is 40,960 bytes per document, against 68 × 36 = 2,448 bytes for an average MS MARCO passage under 2-bit ColBERTv2. Even after PQ the FDE is an extra 1,280 bytes per document, and the exact re-ranking step still needs the token vectors. MUVERA buys latency and reuse of existing MIPS infrastructure; it adds to the footprint. The v2 revision also corrects the dimension bound in Theorem 2.1, so quote the bound from the current version.

## What changed in practice

Late interaction stopped being only a research ranking model and became an index type. Qdrant exposes multivector fields with a `max_sim` comparator, so a common production shape is a cheap dense or hybrid first stage that prefetches candidates and a MaxSim re-score on a multivector field. That keeps the MaxSim quality on the candidate pool without serving every token vector from an ANN index. The same operator moved to page images: ColPali (ICLR 2025) embeds each page image as a grid of patch vectors and scores them against query tokens with late interaction, which takes the PDF parser out of the retrieval path at the cost of many vectors per page.

## When this is wrong

Every number here comes from MS MARCO-trained models evaluated in English, mostly on MS MARCO itself, on 2020 to 2022 hardware (V100 and Titan V GPUs, Xeon Gold CPUs). The relative claims (compression ratio, the share of top k recovered by centroids, the order of magnitude of the speedup) are the durable part. Absolute latency on current hardware, and quality on a domain corpus, have to be measured.

The storage arithmetic assumes the ColBERTv2 encoding at 128 dimensions. Other late-interaction models use different dimensions or prune tokens, and vector databases add their own overheads (graph links, payloads, replicas) that can dominate. Recompute with your encoder's dimension and your measured tokens per chunk.

The comparison point has also moved. The single-vector models ColBERTv2 beat in 2021 have been replaced by larger embedding models, and many pipelines now put a cross-encoder or an LLM reranker behind a hybrid first stage. Whether late interaction still earns its index is a question for your eval set, run against that pipeline rather than against the 2021 baselines.
