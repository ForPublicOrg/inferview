## The question shape top-k cannot answer

"What are the recurring themes across these 400 interview transcripts?" has no top five chunks. Its answer is an aggregate over the whole corpus, and a retriever that returns k chunks by construction answers a question about those k chunks. The model writes a fluent summary of them and nothing in the pipeline reports that 395 transcripts were never read.

GraphRAG (Edge et al., Microsoft, revised February 2025) is a materialised view for that query class: pay at write time so that a corpus-wide read does not scan every chunk. The paper calls these questions global sensemaking. The decision this lesson is about is whether enough of your traffic has that shape, and whether the corpus changes slowly enough, to justify an LLM pass over every chunk before the first query arrives.

## What the index contains

The pipeline in the paper and in Microsoft's open-source implementation has five stages.

1. **Chunk.** The paper used 600-token chunks with 100 tokens of overlap; the library's default TextUnit is 1,200 tokens. The paper reports that GPT-4 extracted almost twice as many entity references from 600-token chunks as from 2,400-token chunks on a HotPotQA sample, so chunk size is a recall knob for extraction, not only a cost knob.
2. **Extract.** An LLM call per chunk returns entities (name, type, description) and relationships (source, target, description, strength), optionally claims. "Gleaning" re-prompts the model to find entities it missed, up to a configured number of rounds, which multiplies the calls.
3. **Merge and summarise.** Entities are matched by exact name string; duplicate descriptions are summarised into one by another LLM call.
4. **Detect communities.** Hierarchical Leiden partitions the graph recursively into levels, from a few root communities (C0) down to many leaf communities (C3 in the paper).
5. **Write community reports.** An LLM summarises each community at each level. These reports are what a global query reads.

Global search is then map-reduce. The reports at a chosen level are shuffled into 8,000-token windows; each window produces a partial answer with a helpfulness score from 0 to 100; zero-scored answers are dropped; the rest are sorted and packed into a final context for the reduce call. The library also exposes Local search (an entity and its graph neighbourhood, for specific questions), DRIFT (local search widened with community context) and Basic search (plain top-k vectors).

The index sizes are small next to the corpus. The Podcast set (about 1 million tokens, 1,669 chunks) produced a graph of 8,564 nodes and 20,691 edges; the News set (about 1.7 million tokens) produced 15,754 nodes and 19,520 edges.

## What a global query costs

Table 2 of the paper reports the context tokens each condition reads per query. Priced at Claude Sonnet 5.5's $2 per million input tokens (checked 2026-10-28), counting only the map step's input:

| Condition (Podcast set) | Context tokens per query | 8k map windows | Input cost per query |
|---|---|---|---|
| C0, root communities | 26,657 | 3.3 | $0.053 |
| C3, leaf communities | 746,100 | 93.3 | $1.49 |
| TS, map-reduce over the source text itself | 1,014,611 | 126.8 | $2.03 |
| Top-k vector RAG with an 8k context | 8,000 | 1 | $0.016 |

Two readings matter. Root-level summaries are where the index pays off at query time: 26,657 tokens is 2.6% of the source-text map-reduce. Leaf-level summaries save only 26% (Podcast) to 33% (News) against map-reduce over the raw chunks, which needs no index at all. A team that reaches for the leaf level for detail is paying the indexing bill to save a quarter of a brute-force scan.

## What the evaluation shows, and what it does not

Against a vector RAG baseline, the global conditions won on comprehensiveness 72 to 83% of the time on Podcast and 72 to 80% on News, and on diversity 75 to 82% and 62 to 71%. Even the cheap C0 condition won 72% on comprehensiveness. Vector RAG won on directness, the control metric: C0 against it was 35.12 to 64.88 on Podcast.

Read the setup before quoting those win rates. The questions were generated by an LLM (5 personas, 5 tasks each, 5 questions per task: 125 per dataset) specifically to require corpus-wide understanding. The judge was an LLM comparing pairs of answers. There were two corpora of about a million tokens each. The paper does not measure fabrication, and it does not test lookup questions, where the directness result points the other way. The evidence supports "on questions designed to be global, graph summaries beat top-k"; it does not say what happens to a workload where most questions are lookups.

## The indexing bill

The library's README states that indexing "can be an expensive operation" and recommends prompt tuning before a full run. The docs estimate graph extraction at about 75% of indexing cost. The paper's only timing is 281 minutes to index the 1-million-token Podcast set with gpt-4-turbo over the public endpoint.

The operational cost is the one that recurs. Documents change, entity descriptions and communities shift, and community reports go stale. The CLI has an `update` command for an existing index; how much of the community layer it regenerates for a given change is something to measure on your corpus before committing to a refresh schedule. The docs also ask for `graphrag init --force` between minor versions, which overwrites prompts, so tuned prompts need to live in version control.

## Cheaper variants

**FastGraphRAG**, an indexing method in the same library, replaces LLM extraction with NLP noun phrases (NLTK, spaCy) and co-occurrence edges, and uses the LLM only for community reports. The docs call it much cheaper and say its graph is noisier and less useful outside GraphRAG; it suits summary-style questions through global search.

**LazyGraphRAG** (Microsoft Research, November 2024) builds a noun-phrase concept graph and defers all LLM work to query time, spending a "relevance test budget" (100, 500 or 1,500 in the post) per query. Microsoft reports indexing cost "identical to vector RAG and 0.1% of the costs of full GraphRAG", global-query quality comparable to GraphRAG global search at more than 700 times lower query cost, and, at budget 500, better results than every compared method at 4% of the query cost of GraphRAG's C2 level. These are the vendor's numbers, on 5,590 AP news articles and 100 synthetic queries judged by an LLM. The blog's June 2025 note says it was integrated into Microsoft Discovery and Azure Local; it does not say it shipped in the open-source library.

**LightRAG** (Guo et al., revised April 2025) combines graph and vector retrieval at two levels, specific entities and broad themes, with an incremental update path that avoids rebuilding. Its gains are self-reported.

The direction across all three is the same: move LLM spend from indexing to query time, or remove it, and accept a noisier graph.

## Which questions a graph changes

| Question shape | Example | What answers it |
|---|---|---|
| Lookup | "What does clause 7 of the Acme MSA say?" | Hybrid retrieval and a reranker; a graph adds cost and loses on directness |
| Corpus-wide aggregate | "What are the recurring complaints across all interviews?" | Global search over root or mid-level community reports, or map-reduce over chunks if the corpus is small |
| Entity neighbourhood | "Which suppliers are connected to the delayed component?" | Local search, or a plain graph query if the entities are already structured data |
| Multi-hop with a fixed schema | "Who manages the team that owns billing?" | A join over the HR and service-catalogue tables, not an LLM-extracted graph |

The last row is the common mistake. If the relationships already exist in a system of record, an extracted graph is a lossy, expensive copy of a table you can query exactly.

## When this is wrong

The quality evidence is narrow. Two corpora of about a million tokens, LLM-generated global questions and an LLM judge establish that community summaries help on that question class at that scale. Corpora a hundred times larger, domains where entity names are ambiguous (exact string matching merges "Apple" the company and the fruit), and workloads mixing lookups and aggregates are not tested in the paper.

The cost figures in this lesson are input-token floors at one provider's list prices on 2026-10-28, and the vendor figures for LazyGraphRAG are relative ratios on the vendor's own benchmark. Long context changes the arithmetic as well: if the whole corpus fits a window at an acceptable price and quality, map-reduce over raw chunks or a single long-context pass may beat any index for occasional global questions. The long-context lesson in this module covers where that stops holding.
