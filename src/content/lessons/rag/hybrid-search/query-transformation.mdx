## A model call in front of the index

Query transformation rewrites what the user typed before retrieval sees it. Every variant adds a generation that retrieval must wait for, so its latency lands on the critical path in full, and it adds a failure mode the pipeline did not have: a rewrite that drops a constraint or invents one retrieves confidently for the wrong question. The decision is therefore per query segment, not per system. A transformation ships for the segments where it buys more recall per added millisecond than a stated bar, and stays off elsewhere. Some segments should not reach retrieval at all.

## Four transformations and the failure each fixes

**Conversational rewriting** turns a turn that depends on history ("and for contractors?") into a standalone query. Without it, the retriever searches for the literal words. It is the cheapest transformation, a short generation over the last few turns, and on its segment the untransformed query can be close to useless, because the words that carry the topic are in earlier turns. Its failure is silent loss of a constraint from earlier in the conversation, such as a region or a date.

**HyDE** asks an instruction-following model to write a passage that answers the question, embeds that passage, and searches near it. The paper samples several hypothetical documents (text-davinci-003 at temperature 0.7), encodes each with the same encoder as the corpus, and averages their vectors together with the query's own vector. The bet is that answer-shaped text sits nearer answer-shaped documents than a short question does, and that the encoder discards the invented specifics. It fails when the model's guess is wrong in a way the encoder keeps, which pulls retrieval toward documents about the wrong thing.

**Multi-query** generates several phrasings, retrieves for each and fuses the lists with RRF. It multiplies retrieval load by the number of phrasings, which matters more than the generation when the vector database is near capacity.

**Decomposition** splits a question into sub-questions and retrieves for each. When the parts are independent ("compare the EU and US refund policies"), the retrievals run in parallel. When the second depends on the first answer ("who approved the vendor that caused the March outage?"), they are sequential, and the latency is a chain of generate, retrieve, generate.

## What HyDE's numbers say, and against what

HyDE's headline result is large, and its baseline explains why.

| TREC DL19 / DL20, nDCG@10 | DL19 | DL20 |
|---|---|---|
| BM25 | 50.6 | 48.0 |
| Contriever, unsupervised | 44.5 | 42.1 |
| HyDE over Contriever | 61.3 | 57.9 |
| ContrieverFT, fine-tuned on MS MARCO | 62.1 | 63.2 |
| HyDE over ContrieverFT, GPT (175b) generator | 67.4 | 63.5 |
| HyDE over ContrieverFT, Flan-T5 (11b) generator | 60.2 | 62.1 |

Against the unsupervised encoder it was designed for, HyDE adds 16.8 points on DL19 and 15.8 on DL20, and recall@1k on DL19 rises from 74.6 to 88.0. Against an encoder fine-tuned on in-domain labels, the same method with the strongest generator adds 5.3 points on DL19 and 0.3 on DL20, and with the 11B generator it subtracts 1.9 and 1.1. The low-resource BEIR results show the same pattern: on TREC-COVID HyDE scored 59.3 against BM25's 59.5, and on FiQA it trailed the fine-tuned encoder by 5.6 points (27.3 against 32.9).

Check which row your embedding model resembles: if it was trained on supervised retrieval pairs, the fine-tuned rows are the relevant comparison, and the expected gain is the small one until your own eval says otherwise. The authors draw the same conclusion about deployment: HyDE is most useful early in a search system's life, and as query logs grow a supervised retriever should take over, with only less common and emerging queries routed to HyDE.

## Gain per added call, by segment

The measurement is recall with and without the transformation on each segment of a labelled eval set, plus the p95 the extra call adds on that segment, measured, not estimated from token counts. The bar is a number of recall points per 100 ms that the team agrees before looking at results. The code applies it.

```python
# Scenario eval results per query segment: recall@10 without and with a transformation,
# share of traffic, and the p95 the extra model call adds on that segment.
segments = {
    #  name          share  base  with  added_p95_ms
    "navigational": (0.55, 0.93, 0.91, 610),
    "conversational": (0.25, 0.58, 0.79, 420),   # rewrite with chat history
    "underspecified": (0.15, 0.61, 0.70, 640),   # HyDE
    "multi-hop": (0.05, 0.34, 0.52, 1150),        # decomposition, two retrievals
}

def plan(segments, min_points_per_100ms):
    routed, total_gain, calls = [], 0.0, 0.0
    for name, (share, base, with_t, added) in segments.items():
        gain = (with_t - base) * 100            # recall points on this segment
        efficiency = gain / (added / 100)       # points per 100 ms of added p95
        if efficiency >= min_points_per_100ms:
            routed.append(name)
            total_gain += share * gain
            calls += share
        print(f"{name:15} gain {gain:+5.1f} pts, {efficiency:+5.2f} pts per 100 ms")
    print(f"transform {routed}: {total_gain:+.2f} pts overall, extra call on {calls:.0%} of traffic")

plan(segments, min_points_per_100ms=1.0)
# navigational    gain  -2.0 pts, -0.33 pts per 100 ms
# conversational  gain +21.0 pts, +5.00 pts per 100 ms
# underspecified  gain  +9.0 pts, +1.41 pts per 100 ms
# multi-hop       gain +18.0 pts, +1.57 pts per 100 ms
# transform ['conversational', 'underspecified', 'multi-hop']: +7.50 pts overall, extra call on 45% of traffic
```

The plan only works if the segment is known before the transformation runs, which makes the router part of the cost. Some signals are free: a turn with prior history goes to rewriting; a query matching an identifier pattern skips HyDE. A model-based classifier is itself a call on 100% of traffic, and its misroutes move queries into segments where the transformation hurts, so its accuracy belongs in the same table. The multi-hop segment clears the bar here with 1.57 points per 100 ms, but its 1,150 ms may break the end-to-end p95 on its own; a per-segment latency ceiling sits next to the efficiency bar.

## Routing away from retrieval

Some queries should not reach the vector index. "How many open tickets does customer 4411 have?" is a structured query; retrieving prose about tickets and asking the model to count produces a fluent wrong number. Greetings and acknowledgements need no retrieval. Hard constraints such as tenant, date range and permissions belong in metadata filters applied with the search, not in the query text a model may rewrite away.

The other design moves the routing decision into the model: retrieval becomes a tool, and the model decides whether to call it and writes the query. On Claude, a search tool can return `search_result` blocks carrying a source, a title and text content, and the response cites them. Citations are off by default, and the setting must be the same for every search result in a request. A citation identifies a slice of the result's content blocks by start and exclusive end index, so the model cites whole blocks: the granularity of your chunks is the granularity of your citations. The feature left beta on the Claude API and Vertex AI on 2025-08-08 and reached Amazon Bedrock on 2025-11-21; the documentation lists every active model except Claude Haiku 3.

Tool-based retrieval does not remove the transformation cost; it moves it. The model's turn that emits the tool call is the rewrite, so it adds the same generation before retrieval, plus a second model call to answer. What it adds is the option to skip retrieval, issue several queries or search again after reading results. What it removes is a deterministic routing rule you can test in isolation. Measure the tool-call rate, the queries the model writes and the recall of those queries, segment by segment, the same way.

## When this is wrong

The HyDE comparisons are from 2022 encoders and generators on web and BEIR collections. The direction (large gains over unsupervised encoders, small or negative over fine-tuned ones) is the transferable part; the magnitudes are not.

Recall is the wrong objective when the transformation changes the question. A rewrite that retrieves better documents for a slightly different question raises recall against labels built for the rewrite and lowers answer correctness for the user. Evaluate transformed queries end to end on answers, not only on retrieval, at least for the segments you ship.

The segment table assumes stable traffic. Query mix shifts with product changes and seasons, and a segment that did not clear the bar can grow until it matters; the routing rules need the same recurring review as any other threshold.
