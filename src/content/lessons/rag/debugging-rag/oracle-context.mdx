## What an oracle run measures

An oracle run replaces the retrieved context with the gold passages for each question and reruns generation with everything else held fixed: same model, same prompt template, same decoding settings. If the answer is still wrong, no retrieval change can fix that question. If it becomes right, the loss happened upstream of the prompt. It is the move of swapping a dependency for a known-good stub in a differential test.

The difference from a stub is that gold context is not neutral. It is shorter than any real retrieval, carries no distractors, and puts the evidence wherever you placed it. Oracle accuracy is therefore the ceiling for a pipeline with perfect ranking and perfect assembly, which overstates what a real retriever reaches. Liu et al. measured both ends on NaturalQuestions-Open with GPT-3.5-Turbo: 56.1% with no documents at all, 88.3% with only the answer-bearing document, and, with 20 or 30 documents and the answer placed in the middle, a worst case below the 56.1% closed-book score. The same evidence, surrounded by distractors in the wrong position, was worse than no evidence. One oracle number cannot separate those effects, so the useful experiment is a small matrix of conditions.

The closed-book row is the one teams skip and the one that most often changes the plan. A question the model answers correctly with no context is not testing retrieval. On a private corpus a high closed-book score means the eval set drifted toward general knowledge or the documents are public, and either way the other rows overstate how well retrieval is doing.

## Attribute per question, not per total

Subtracting totals assumes every question moves the same way across conditions, and some do not. A question can pass in production and fail with oracle context, because sampling varied, because a neighbouring chunk supplied a fact the gold set lacks, or because the gold label is wrong. Attribute each question from its paired results and count the exceptions.

```python
from collections import Counter

def attribute(prod, injected, oracle):
    """Per-question label from three paired runs of the same generator.
    prod: as deployed; injected: production context with the gold passages swapped in
    for the lowest-ranked chunks; oracle: gold passages only."""
    if prod:
        return "ok" if oracle else "non-monotonic"
    if injected:
        return "retrieval"    # gold was absent; putting it in the same context fixed it
    if oracle:
        return "distraction"  # gold present but buried; removing the rest fixed it
    return "generation"       # fails even with only the gold passages

runs = {  # question id: (prod, injected, oracle)
    "q01": (True, True, True),   "q02": (False, True, True),
    "q03": (False, False, True), "q04": (False, False, False),
    "q05": (True, True, False),  "q06": (False, True, True),
}
labels = {q: attribute(*r) for q, r in runs.items()}
print(Counter(labels.values()))
# Counter({'retrieval': 2, 'ok': 1, 'distraction': 1, 'generation': 1, 'non-monotonic': 1})
```

A handful of non-monotonic questions is noise. Many of them mean the gold labels are incomplete or the conditions are not paired properly, and the decomposition should not be trusted until someone reads them. Read the generation bucket by hand as well before acting on it: oracle failures caused by a wrong or partial gold label look exactly like generator failures in the counts.

Size the noise before reading small gaps. Run the production condition twice with identical settings and count the questions whose result changed; that count is the floor under every comparison. At the production temperature, run each condition several times and count a question as passing by majority. The unpaired standard error at 75% accuracy on 200 questions is √(0.75 × 0.25 / 200) ≈ 3.1 points, about 6 questions. Gaps of 20 or more questions, as in the example, are well clear of it; a gap of 5 is not, and needs the paired flip count or more questions.

## Contextual retrieval: a fix for one specific loss

One cause of retrieval loss is a chunk that does not name what it is about. Anthropic's example is a chunk from a quarterly filing that says revenue grew over the previous quarter without naming the company or the quarter; it cannot match a query that names either, by embedding or by BM25. Barnett et al. saw the same effect from the other side: adding the file name and chunk number to each chunk helped in their tutor system.

Anthropic's contextual retrieval generalises that fix. Before indexing, a model reads the whole document and the chunk and writes a short context, usually 50 to 100 tokens, which is prepended to the chunk for both the embedding and the BM25 index. Anthropic generated it with Claude 3 Haiku and reports, as its own measurement, the share of relevant documents missing from the top 20 chunks (1 minus recall@20), averaged across codebases, fiction, ArXiv papers and science papers with Gemini Text 004 embeddings:

The cost is an indexing job, not a per-query cost. Anthropic quotes $1.02 per million document tokens with prompt caching, assuming 800-token chunks, 8k-token documents, 50 tokens of instructions and 100 tokens of generated context per chunk. Under those assumptions each document is 8,000 / 800 = 10 chunks and 10 model calls that share one cached document prefix, and a 30-million-token corpus costs 30 × $1.02 = $30.60 to contextualise once. The recurring costs are elsewhere: every changed document regenerates context for all its chunks, the prompt is model-specific and needs its own evaluation, and if the prefix is also rendered into the generator's prompt, each chunk grows by 100 / 800 = 12.5% under the same assumptions.

The ablation says when this is the right fix. Contextual retrieval moves the retrieval-loss bucket. If triage shows the missed gold chunks are ones whose text lacks the entity or section the query names, it is a strong candidate. If the loss is distraction or generation, it does nothing for those questions and adds index-time cost. After shipping it, rerun the whole matrix: retrieval loss should fall, and distraction loss may rise, because more relevant-looking chunks now reach the prompt.

## The k question has no portable answer

Anthropic reports that passing 20 chunks to the model beat 10 and 5 in its tests. Liu et al. found that 50 retrieved documents instead of 20 improved GPT-3.5-Turbo by about 1.5% and Claude-1.3 by about 1%, and Chroma's context-rot report found that one distractor already lowered accuracy across 18 models. These are not in conflict. They measure different models, tasks and context lengths, and they agree that the gain from more recall shrinks while the cost from more distractors continues. The k sweep in the matrix finds the point for your generator and your questions, and a model upgrade moves it.

## When this is wrong

Gold labels are someone else's retrieval. Annotators find passages with a search tool and stop when they find one that answers; for questions with several valid sources, the oracle set is incomplete and oracle failures overstate the generation ceiling. Multi-hop questions need every hop in the gold set, and partial gold looks like a generator that cannot reason.

Oracle context is cleaner than anything production delivers. A generator tuned until oracle accuracy is high has been tuned on short, relevant contexts, and those gains may not survive real retrieval. Treat the gold-injected condition as the realistic upper bound and oracle only as the theoretical one.

Closed-book near zero is an assumption about the corpus. Internal documents often restate public material (vendor documentation, regulations, open-source READMEs), and those questions pass closed-book. Rerun the closed-book condition when the model changes; a newer model knows more.

The conditions interact. Swapping gold into the lowest-ranked slots changes the order and length of the context as well as its content, so the retrieval and distraction losses are estimates, not exact partitions. The non-monotonic count is the measure of how far to trust them.

When the whole corpus fits in the context window, the matrix changes shape. Anthropic suggests skipping retrieval for knowledge bases under 200,000 tokens, about 500 pages; there the questions become position and distraction within one long prompt, and the position sweep is the only row that still applies. The contextual-retrieval numbers above are the vendor's, on its own four domains and embedding model; they say what is possible, and only the rerun of the matrix on your questions says what happened.
