## What it is and who runs it

Perplexity runs an answer engine: a question goes in, and an answer with citations comes out. Since 2025 it also sells the retrieval layer underneath as a Search API that returns ranked results with extracted page text and no generated answer. This teardown is assembled from Perplexity's September 2025 research post on that search system, its Deep Research launch post, its API documentation, and one independent 2023 audit of citation quality. Perplexity's system is closed, so where those sources are silent, this page says so.

Two numbers set the scale, both from Perplexity's post. The production search infrastructure processes 200 million queries a day, and the index tracks over 200 billion unique URLs. The post also gives the reason the system exists: Perplexity's first answer engine, in late 2022, called third-party search APIs, one of which charged $200 per thousand queries. At today's 200 million queries a day that rate would come to 200,000 x $200 = $40 million a day, which shows why the post lists cost first among the problems with renting search.

The design idea that matters for this module is the unit of retrieval. Search engines built for people return documents and let the reader find the passage. Perplexity's system splits documents into self-contained spans at indexing time and ranks spans, so what reaches the model, and what an answer can cite, is already passage-sized.

**Refresh scheduler.** Two models decide crawling. One predicts whether a candidate URL needs indexing at all, trained on importance and expected update frequency. The other decides when, deferring work on sites with a regular publishing cadence until the update is most useful. The post frames freshness and completeness as competing for one fixed budget of indexing operations, and the models as the way to spend it.

**Crawler fleet.** Crawling and indexing run on fleets the post sizes at tens of thousands of CPUs and hundreds of terabytes of RAM, doing tens of thousands of indexing operations per second over an exabyte-scale store split into hot and cold tiers. The crawler, PerplexityBot, follows robots.txt limits, falls back to common request-rate norms where a site sets none, and backs off when a site is unavailable.

**Content understanding and the ruleset improver.** Pages are parsed with dynamic rulesets that differ by site structure, for example a listings page against a forum thread. The rulesets are tuned by a loop: observe parsing outputs across the queries the system serves, have frontier LLMs grade each extraction for completeness (the meaningful content captured, nothing spurious) and quality (substance and structure kept), generate ruleset changes aimed at the largest error classes, validate them, deploy to the indexer, then reindex high-traffic documents. This is an LLM assessor used upstream of retrieval rather than at evaluation time, and it carries the same calibration question as the assessors in the previous lesson.

**Span segmentation.** The same parsing rules split each document into self-contained spans, each retrieved and ranked on its own at query time. The point, in the post's framing, is that only the relevant part of a page reaches the model.

**Index.** Over 200 billion unique URLs tracked, with hot documents from authoritative domains and under-covered topics kept in faster storage.

**Hybrid retrieval and prefilter.** A query goes to the index through lexical and semantic retrieval, and the results merge into one candidate set. The post says this stage favours comprehensiveness: it is the recall stage, and anything it misses no later stage can recover. Heuristics then remove clearly non-responsive or stale content.

**Early rankers.** Lexical and embedding-based scorers, chosen for speed, narrow the candidates.

**Cross-encoder rerankers.** More expensive cross-encoder models produce the final set, scoring at both document and span level. The post credits inference optimisations, without detail, for keeping this stage within the latency budget.

**Answer with citations, Search API, Deep Research.** The ranked spans go to answer generation in the product, to API callers as results with title, URL, snippet and dates, or to Deep Research, which searches, reads and refines its plan repeatedly before writing a report.

**Feedback.** The post says the system serves millions of user requests each hour, that each generated answer is an empirical quality signal, and that AI-driven evaluations and live human feedback enrich the training data for the embedding and ranking models.

## Context strategy

The context decision is made at indexing time. Because spans are self-contained and ranked individually, the generator receives passages rather than pages, and a citation can point at the passage that carries the claim. That is the property the citation-quality lesson asks for, and the Claude citation documentation reaches the same place from the other side: the citable unit is whatever block you hand the model. Perplexity has moved that choice into the parser, which also means a parsing error becomes a context error. A span cut mid-table or one that lost its heading reaches the model as a fragment, and the answer cites it faithfully.

For API callers the context budget is theirs to set. `max_results` runs from 1 to 20 (default 10), `max_tokens_per_page` caps extracted text per result, and `max_tokens` caps the total, up to 1,000,000 tokens. The response has no answer; the caller's own model reads the snippets.

## Tools and permission model

On the supply side, the permission model is the crawler's: robots.txt is honoured, default rate norms apply where a site sets none, and the crawler backs off from unavailable sites. On the API side, callers constrain sources rather than actions: `search_domain_filter` takes an allowlist or a denylist (prefix `-`), not both, of at most 20 domains or paths, and `search_language_filter` up to 20 language codes. One request can carry up to five queries, billed as one request and counted separately against rate limits.

## Cost and latency

Perplexity's API pricing page lists $5.00 per 1,000 Search API requests and $1.00 per 1,000 with `search_type` set to fast. Against the $200 per thousand third-party rate the post cites from 2022, that is 40 times cheaper at the standard tier, for a product that returns results rather than an answer.

Latency is published only as Perplexity's own measurement, from AWS us-east-1, with no request count:

| Provider | p50 ms | p95 ms |
|---|---|---|
| Perplexity | 358 | 763 |
| Brave | 513 | 808 |
| SERP-based (Google results via Tavily) | 1,342 | 1,790 |
| Exa | 1,375 | 2,188 |

The quality comparison is also vendor-run, through Perplexity's own `search_evals` harness, with the same agent harness across providers and the original benchmarks' grading prompts. Perplexity scored .930 on SimpleQA, .453 on FRAMES, .371 on BrowseComp and .288 on HLE; the closest competitor, the SERP-based API, scored .890, .437, .348 and .248. The post reports no query counts, repeated runs or variance, so whether a gap of .016 on FRAMES exceeds run-to-run noise cannot be judged from it. The repository has since changed: as checked on 28 October 2026, its README describes a runner for deep-research agent APIs on BrowseComp, DeepSearchQA, an HLE subset and WideSearch, not the September 2025 search API comparison.

Deep Research trades latency for coverage: the launch post gives 2 to 4 minutes per task, with most under 3. Its benchmark figures (21.1% on Humanity's Last Exam, 93.9% on SimpleQA) are Perplexity's own, from February 2025.

## Failure modes

- **Recall loss at the first stage.** Every later ranker sees only the merged candidate set. A span that neither the lexical nor the semantic leg retrieves never reaches a cross-encoder, however good it is; the post's emphasis on comprehensiveness at this stage is the acknowledgement.
- **Segmentation errors become citation errors.** If a span loses its heading, its table header or the sentence that qualifies it, the answer can cite it accurately and still mislead. Span-level citation precision checks the claim against the span, not against the page the span came from.
- **An LLM grading its own pipeline.** The parsing loop uses frontier LLMs to grade extraction. If the grader shares a blind spot with the rulesets it tunes, the error class it misses never becomes a target. The post says changes are validated before deployment but not how, or whether people check the grader.
- **Feedback loops in ranking data.** Answers are used as quality signals for training rankers. Documents the current ranker never surfaces generate no signal, the same pooling bias the search-evaluation lesson measures, here in training data rather than evaluation labels.
- **Measured citation quality, then.** The 2023 audit by Liu and colleagues found perplexity.ai's answers had 68.7% of sentences fully supported by citations and 72.7% of citations supporting their sentence. That predates the September 2025 architecture and says nothing about the current product, but it is the only independent span-level measurement in the sources here.

## What is not public

- **Models per stage.** Which embedding models, lexical scorers and cross-encoders run at each stage, their sizes, and how many candidates each stage passes on.
- **Ranking features and weights.** How lexical and semantic results are merged, what the prefilter heuristics are, and which signals beyond text the rankers use.
- **How product signals become training data.** The post says answers, AI evaluations and human feedback enrich training data, and stops there: no description of labelling, sampling, or how position bias in user signals is handled.
- **How spans are defined.** The size, overlap and boundary rules of a span, and how span and document scores combine.
- **Independent verification of the comparisons.** The latency and quality tables are Perplexity's own measurements on its own harness, without query counts or variance.

## When this is wrong

Everything in the architecture section is Perplexity's description of its own system in September 2025. It describes components and their order, not sizes, models or the share of traffic each path takes, and the system has had a year to change. The repository's shift from search API comparison to agent API comparison is a reminder that the evaluation surface moves too.

The diagram draws one search path serving the answer engine, the API and Deep Research. The post describes a single search infrastructure, but it does not say whether every product path uses every stage, or with the same depth.
