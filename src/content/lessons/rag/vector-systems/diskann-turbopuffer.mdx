## What it is and who runs it

Two systems that move vector search off RAM, by different routes. DiskANN is a research system from a NeurIPS 2019 paper by authors at Microsoft Research India, Carnegie Mellon and UT Austin: a graph index, Vamana, laid out so that a query on a local SSD needs few reads, with compressed vectors in RAM to steer it. turbopuffer is a hosted search engine run by the company of the same name; its architecture page describes a design in which object storage is the only durable tier and NVMe and memory are caches. Everything below comes from the paper and from turbopuffer's architecture and limits pages as checked on 28 October 2026. turbopuffer's engine is closed source, so where its docs stop, this page stops.

The two are not competitors in the usual sense. DiskANN is an index layout for one machine with an SSD; turbopuffer is a service whose page names DiskANN as an example of the graph indexes it chose not to use on object storage. Reading them together shows what each storage tier punishes: SSD punishes dependent reads by hundreds of microseconds, object storage by about 100 ms.

**Vamana graph on SSD.** A single-layer proximity graph. Its pruning rule has a parameter alpha; the paper notes that HNSW and NSG implicitly use alpha = 1, and that a larger alpha keeps long-range edges and gives the graph a smaller diameter, so the walk needs fewer hops. Fewer hops is the whole goal, because each hop is an SSD round trip. On disk each node is a fixed-size record: its full-precision vector followed by up to R neighbour ids, padded, so a node's offset is computed rather than looked up.

**PQ codes in RAM.** Every point's product-quantised code (32 bytes per point in the paper's example, so 32 GB for a billion points) stays in memory. The walk uses these approximate distances to choose which nodes to read next; the paper notes that the graph itself was built with full-precision vectors, which is why compressed distances can still steer it to the right region.

**Beam search.** Instead of reading one node per step, the search reads the neighbourhoods of the W closest unvisited candidates in one batch; the paper says fetching a few random sectors takes almost the same time as one. W of 2, 4 or 8 balanced latency and throughput in their runs, with the SSD at a 30 to 40% load factor; W of 16 or more wasted compute and bandwidth.

**Cached nodes.** The nodes within 3 or 4 hops of the starting point, or chosen from a known query distribution, are held in RAM, which removes the first few round trips of every query. The node count grows exponentially with the hop radius, which bounds how far this goes.

**Re-ranking for free.** A node's neighbour list (4 x 128 bytes at degree 128) and its full vector fit in one 4 KB sector, and reading 4 KB costs no more than reading 512 bytes. So every node the walk reads also delivers its full vector, and the final top k is ranked by exact distance without extra reads. This is the verification pass from the quantisation lesson, folded into the walk.

**WAL per namespace on object storage.** Each namespace is a prefix in object storage, and its write-ahead log is a directory under it; every committed batch adds a file. A write that returns has been durably stored. A namespace commits at most one log entry per second, so concurrent writes in the same second are batched, and the docs give a write p50 of 165 ms for 500 kB.

**Indexer.** Separate processes read the log and build indexes asynchronously. Until they catch up, the committed tail is searchable by an exhaustive scan, and the limits page caps ingested, unindexed data at 2 GB per namespace.

**Centroid index.** The vector index is based on SPFresh, a partition (centroid) design with in-place updates: clusters split as they grow and only vectors near partition boundaries are reassigned. The architecture page gives the reason for choosing it over a graph: centroid indexes need fewer round trips and less write amplification on object storage than HNSW or DiskANN. A graph walk is a chain of dependent reads; a centroid lookup is "read the centroids, then read the chosen clusters together". Full-text search uses a BM25 inverted index, and metadata filters use exact indexes.

**NVMe and memory caches.** After a namespace's first query, a query node caches its data on NVMe and in memory, and routing sends later queries for that namespace to the same node, although any node can serve any namespace. The binaries are multi-tenant; the docs say enterprise customers can request single-tenant clusters or run it in their own cloud.

The DiskANN equivalent has no cold tier in the same sense: the index is on a local SSD and the paper reports a mean under 3 ms at 95%+ 1-recall@1 on a billion points. Its first query still pays SSD reads for every hop beyond the cached nodes, which the beam search batches into a handful of round trips.

## Data placement

The two designs answer one question, which bytes must be in RAM, with different answers. DiskANN keeps a compressed copy of every vector in RAM, permanently, plus a small set of hot nodes; RAM scales with the corpus at 32 bytes per point in the paper's setup, and the SSD holds the rest. turbopuffer keeps nothing in RAM permanently; RAM and NVMe hold whichever namespaces were queried recently, so RAM scales with the active working set, not the corpus. That difference is why the second design suits many small tenants and the first suits one large corpus queried continuously.

The Faiss paper describes the same split from the other side: in flash-backed or distributed settings the metric is I/O operations rather than distance computations, because every read fetches a whole page. Both designs are page-aware; they differ in how expensive one page is.

## Writes, consistency and tenancy

DiskANN, as published, is a build-then-serve index: the single billion-point build took about 2 days with a peak memory of 1,100 GB, and the merged alternative (40 overlapping k-means partitions, each point sent to its 2 nearest, graphs merged by edge union) took about 5 days on the 64 GB workstation and produced a 348 GB index. Incremental updates are outside the 2019 paper.

turbopuffer's write path is the log. Strong consistency is the default, so a query after a successful write sees it; eventual consistency is an option that lowers warm latency and can be stale by up to about an hour. Tenancy is the namespace: one prefix per namespace in object storage, unlimited namespaces in the limits page, at most 16 concurrent queries per unpinned namespace, and up to 256 pinned namespaces. A namespace too large for one index is sharded internally across indexes sharing one log, up to 500M documents per shard and 256 shards.

## Cost and latency

DiskANN's numbers are the paper's, on SIFT1B (128-dimension uint8 vectors) and 2019 hardware: over 5,000 queries per second on 16 cores with mean latency under 3 ms at 95%+ 1-recall@1, and 98.68% 1-recall@1 under 5 ms for the single index. At the same memory footprint, the paper reports IVFOADC+G+P with 32-byte codes plateauing at 62.74% 1-recall@1 while DiskANN passed 95% in under 3.5 ms, and 5 to 10 times more points per node than in-memory HNSW and NSG at high recall. The reason is the free re-ranking: compression-only indexes are capped by the error of their codes, while DiskANN reads full vectors on the way.

turbopuffer's latency numbers are its own, at 1M documents: cold p50 874 ms, warm p50 14 ms, with an object-storage round trip of about 100 ms. The limits page states a vector search recall@10 of 90 to 100%. The cost argument is structural: object storage is the durable tier, so the price of a stored gigabyte is set by object storage plus whatever fraction is cached, and a namespace nobody queries costs only its stored bytes.

## Failure modes

- **Cold-start bursts.** On the object-storage design, many namespaces going warm at once (a time zone starting work) means many concurrent cold paths, each several round trips long. The pre-flight warm query moves the cost earlier; it does not remove it.
- **A large unindexed tail.** Strong consistency scans the unindexed log exhaustively. A write burst that outruns the indexer turns cheap queries into scans until the tail is indexed, with the 2 GB cap as the hard stop.
- **Per-namespace write ceiling.** One commit per second per namespace and 10k writes a second per namespace mean a single hot tenant's write rate is bounded by its namespace, whatever the cluster's capacity.
- **SSD queue depth.** DiskANN's own analysis: an SSD driven at peak throughput with backlogged queues serves reads in over a millisecond, so the design runs at a 30 to 40% load factor. A co-located workload that fills the queues raises every query's latency.
- **Rebuild time.** The billion-point builds took days. A new embedding model, or a delete-heavy period that degrades the graph, has a recovery time measured in those days unless the index supports in-place updates.

## What is not public

The cost per query of either design is not published. DiskANN's paper reports hardware and throughput, not a price, and turbopuffer's architecture and limits pages give no per-query cost; a cost per query derived from them would require pricing inputs this page does not use.

turbopuffer's cache sizing and eviction policies are not described beyond the architecture page: how much NVMe and memory a node has, how namespaces are evicted, and the limits page's "hours" of maximum inactive time in cache, without a number. The routing algorithm beyond cache locality, the parameters of its SPFresh-based index (cluster sizes, number of centroids, probe counts), how it differs from the SPFresh paper, and which percentiles beyond p50 hold for cold and warm queries are also not stated. Production deployments of DiskANN beyond the paper are outside the sources used here.

<p>Working set. A corpus queried at 2,000 QPS across its whole range has a working set equal to the corpus. On an object-storage engine it would live in the cache tier permanently, so the bill is the cache plus the storage, and every cache loss is a 100 ms-per-round-trip cold path against a 20 ms p95.</p>
<p>The SSD layout. What changes is the steering: 32-byte codes compress a 3,072-byte vector 96 times instead of a 128-byte one 4 times, so the walk may need a wider beam or more hops, and that is the first thing I would measure.</p>
