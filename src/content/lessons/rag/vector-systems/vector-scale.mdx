## The decision

Once the vectors outgrow the RAM of the machines you are willing to pay for, the algorithm matters less than where the bytes a query touches live. Three published designs mark the range. A RAM-resident graph (HNSW) keeps everything in memory and pays for it in RAM. An SSD-resident graph (DiskANN) keeps compressed codes in RAM and the graph with full vectors on local SSD. An object-storage engine (turbopuffer) keeps everything durable in S3-compatible storage and caches what is being queried on NVMe and in memory. Each step down the list cuts the cost per stored gigabyte and raises the latency of the first query that finds nothing in a faster tier.

The tenant layout and the freshness bound follow from that choice. With many small tenants, most tenants are cold most of the time, so the cold-query latency of the tier is the latency those tenants see. With a write path that commits to a log and indexes later, freshness is the commit interval plus whatever it costs to search the part of the log not yet indexed.

## The three tiers, with their published numbers

**RAM.** HNSW's graph adds about 151 bytes per node at M = 16 to the vector itself, so RAM is set by vector bytes, and the quantisation lesson's budget arithmetic applies. Latency is a few distance computations per hop and no I/O. The HNSW paper notes a limit for scale-out: search always starts at the single top layer, so the structure is distributed by partitioning the data across nodes, and the authors report that total throughput then does not scale well with node count. With data partitioned by hash, every query has to search every partition.

**Local SSD.** DiskANN (NeurIPS 2019) indexed a billion SIFT vectors on one workstation with 64 GB of RAM and an inexpensive SSD, serving over 5,000 queries per second with mean latency under 3 ms at 95%+ 1-recall@1 on 16 cores. The layout is the point: product-quantised codes (32 bytes per point in the paper's example, so 32 GB for a billion points) stay in RAM to steer the walk, and each node's full vector and neighbour list sit together on SSD so one read returns both. The authors set the design target as a few dozen random reads and fewer than ten round trips per query, preferably five, because each SSD round trip costs a few hundred microseconds.

**Object storage behind caches.** turbopuffer's architecture page describes a write-ahead log per namespace in object storage, indexers that build indexes asynchronously from it, and query nodes that cache a namespace's data on NVMe and in memory after its first query, with later queries routed to the same node. Its published latencies at 1M documents are a cold p50 of 874 ms and a warm p50 of 14 ms. An object-storage round trip is about 100 ms, and a cold vector query takes 3 to 4 of them (often about 400 ms, per the same page): fetch the centroid index, find the nearest centroids, then fetch all the needed clusters in one large request, plus consistency checks. That is why the vector index is centroid-based (derived from SPFresh) rather than a graph: the docs state centroid indexes need fewer round trips and less write amplification than HNSW or DiskANN, whose walks are sequences of dependent reads.

The analogy for the object-storage design is a log-structured store with its log in S3. The difference that matters is the read path: an LSM read touches a few sorted files by key, while a cold vector query must first learn which clusters to read, which is one extra round trip that no key layout removes.

## Tenants

There are three layouts, and every engine offers some combination.

**An index per tenant.** Pinecone recommends one namespace per tenant on serverless indexes, with physical isolation, and prices queries at 1 read unit per GB of the namespace searched: its own example is 100 tenants of 1 GB, where a tenant's query costs 1 RU in its namespace and 100 RU through a metadata filter on a shared 100 GB namespace. Offboarding is deleting the namespace. The limit is a count: 100 namespaces per serverless index on Starter up to 1,000,000 on Enterprise (API version 2026-07). turbopuffer lists namespaces as unlimited, having seen more than 250M, with each namespace its own prefix in object storage.

**A shared index with a tenant filter.** Cheapest to operate and the worst for isolation: one tenant's data shapes the graph every other tenant searches, and a small tenant's predicate is the narrow-filter case from the filtered-search playbook.

**A shared collection laid out by tenant.** Qdrant's guide says a collection per tenant is rarely efficient and caps Qdrant Cloud clusters at 1,000 collections by default; instead it co-locates each tenant's vectors with an `is_tenant` payload index and, from version 1.16, promotes a tenant that grows past about 20,000 points from a shared fallback shard to a dedicated one without application changes.

The cost the per-tenant layout hides is cold start. A tenant that queries once a day pays the cold path once a day, and on an object-storage engine that is the first query of that tenant's session.

Engines offer two levers on cold start, and both are trades. A pre-flight query (turbopuffer documents one) warms a namespace when the application knows a session is starting, such as at login, which moves the cold path off the user's first search. Pinning or provisioning keeps chosen namespaces resident and turns a latency problem into a cost line; turbopuffer's limits page lists up to 256 pinned namespaces and 16 concurrent queries per unpinned namespace, and does not state how long an idle namespace stays cached beyond "hours".

## Sharding a large tenant

Many small tenants is a placement problem; one large tenant is a sharding problem, and the costs are the usual fan-out costs plus one specific to graphs. Partition by vector neighbourhood and a query must still visit several partitions, because its neighbours straddle boundaries; partition by hash and every query visits every shard, which is the throughput ceiling the HNSW authors describe.

DiskANN's merged index is a published middle path: k-means into 40 partitions, each point sent to its 2 nearest centres, a graph built per partition in memory, and the graphs merged into one by taking the union of edges. The build stayed under 64 GB of RAM, and the merged index needed no more than 20% extra latency for a target recall compared with a single-shot build. turbopuffer shards a namespace that is too large for one index across several internal indexes that share one log, with a stated ceiling of 500M documents per shard and 256 shards per namespace.

## Freshness

On the object-storage design, a write is durable when it is in the log. turbopuffer commits at most one log entry per namespace per second, batching writes that arrive in the same window, and reports a write p50 of 165 ms for 500 kB. Queries are strongly consistent by default, so a query after a successful write sees it: the committed but unindexed tail of the log is searched exhaustively until the indexers catch up, with at most 2 GB of ingested, unindexed data per namespace in the limits. The bound on freshness is therefore the commit interval, and its price is the exhaustive scan of the tail, which grows with write bursts. Eventual consistency is the opt-out: warm queries get faster and may be stale by up to about an hour.

On graph indexes, freshness is a delete problem. Inserts go into the graph, but updates and deletes become tombstones that degrade recall until a rebuild, which is the HNSW lesson's policy question at a larger scale. SPFresh is the published alternative for centroid indexes: instead of buffering updates and rebuilding globally, it splits partitions that grow and reassigns only the vectors near partition boundaries. The paper reports needing 1% of the DRAM and under 10% of the cores of the state of the art at peak, on a billion-scale index with a 1% daily update rate.

```python
def cold_starts_per_second(tenants, active_share_per_hour):
    """First queries per second if each active tenant goes cold between hours."""
    return tenants * active_share_per_hour / 3600


def warm_set_gb(tenants, active_share_per_hour, chunks, bytes_per_vector):
    return tenants * active_share_per_hour * chunks * bytes_per_vector / 1e9


print(round(cold_starts_per_second(1_000_000, 0.03), 1))           # 8.3
print(round(warm_set_gb(1_000_000, 0.03, 2_000, 4_096), 1))        # 245.8
print(round(warm_set_gb(1_000_000, 0.03, 2_000, 4_096 // 32), 1))  # 7.7 with binary codes
```

## When this is wrong

The latencies here are from vendor documentation and one paper, each under its own conditions: turbopuffer's at 1M documents with unstated dimensions and percentiles beyond p50, DiskANN's on SIFT1B with 128-dimension vectors on 2019 hardware. They show the ratios between tiers, roughly 100 ms per object-storage round trip against hundreds of microseconds per SSD read against nothing for RAM; your numbers come from running your namespace sizes on your hardware.

The tenant arithmetic assumes tenants go cold independently. Real activity is correlated by time zone and working hours, so first queries arrive in a burst at the start of each business day, and the warm-up path has to absorb that burst. Finally, the cheapest tier is only cheap while the workload matches it: a tenant that queries constantly lives in the cache tier anyway and gains nothing from cheap cold bytes, and the right layout moves tenants between tiers as their traffic changes, which is what tenant promotion in Qdrant and pinning in turbopuffer are for.
