## The decision

Where the predicate runs relative to the graph walk: before it (scan the passing rows exactly), after it (walk, then discard), during it (a walk that knows the predicate), or nowhere at query time because the data was partitioned by it. Every engine implements several of these and a planner chooses between them, so the decision for a team is which mechanisms to make available, which indexes to build before ingestion, and which queries to route by hand when the planner's estimate is wrong.

The answer is per filter, not per system. A tenant predicate on every query, a document-type filter with a dozen values and a free-form date range in a third of queries each land in a different place, and a design that picks one mechanism for all three gets at least one of them wrong.

## The inputs that change it

**Selectivity, as a distribution.** The fraction of rows a filter passes, measured over real queries rather than averaged. A filter that passes 30% for most users and 0.01% for a few is two filters for this purpose.

**Correlation between filter and query.** The ACORN paper bounds post-filtering between O(log n + K), when the passing vectors sit near the query, and O(n) when they are far, and names negative correlation as the hardest case. Qdrant's own benchmark (below) shows the effect at the same 10% selectivity: plain HNSW with a post-filter reached 20.6% recall@10 when the filter was independent of position and 88.4% when it was correlated.

**Predicate shape.** An equality on a low-cardinality field known when the index is built can get index-time help. A range, a regular expression, or an AND of fields the index has never seen together cannot.

**Tenants.** How many there are, how skewed their sizes are, and whether every query carries the tenant predicate. A predicate that is always present and always an equality is better handled by layout than by search.

**Write and rebuild budget.** Index-time mechanisms cost build time and require the filter field to be indexed before the graph is built; Qdrant's docs say a payload index created after ingestion needs an HNSW rebuild before its filter-aware edges exist.

## Why the graph breaks under a filter

A filter does not just remove results; it removes nodes from the walk. Qdrant measured about 21 links per node on layer 0 at its default m of 16, on a 1M-vector collection.

## The options and when each wins

**Exact scan of the passing rows.** Find the rows that pass with an ordinary index, then compute every distance. Recall is perfect and the cost is proportional to the passing set, so it wins whenever that set is small. pgvector's README recommends a B-tree on the filter column for conditions that match a low percentage of rows. Qdrant's planner does this automatically when its estimate of matching vectors falls below `full_scan_threshold`, 10,000 KB in the config example, where 1 KB is one 256-dimension vector. The cutoff in your system is a latency budget divided by the cost of one distance computation, and you should know it as a row count.

**Post-filter, with oversampling.** Walk with a larger candidate list and discard failures. It wins when the filter passes a large fraction or correlates positively with the query, and it costs nothing at build time. pgvector applies filters after the index scan; its README's arithmetic (10% at `ef_search` 40 gives about 4 rows) is the reason the candidate list has to grow as the filter narrows.

**Iterative scan.** A post-filter that keeps going. Since pgvector 0.8.0 (October 2024), `hnsw.iterative_scan` continues the scan until enough rows pass or `hnsw.max_scan_tuples` (20,000 by default) stops it; `relaxed_order` returns slightly out-of-order results with better recall. It extends the post-filter band downward without a rebuild, and its floor is set by the scan cap: at 20,000 visited tuples and a filter keeping 0.05%, the expected number of passing rows is 10.

**Filter-aware traversal, built at query time.** ACORN-1 builds an ordinary HNSW and, at query time, looks past filtered-out neighbours to their neighbours before discarding, which reconnects the predicate subgraph without index changes. Qdrant added it in version 1.16 as a per-query option that applies only when the planner estimates the filter passes no more than `max_selectivity` of points, 0.4 by default, and is off by default. The cost is latency: in Qdrant's benchmark, turning it on took a 10% filter from 1.7 ms to 4.3 ms.

**Filter-aware traversal, built at index time.** Two forms. ACORN-γ collects M x γ candidate edges per node during construction, with γ set to 1 over the smallest selectivity it will serve, and falls back to pre-filtering below that; the paper reports time-to-index up to about 11 times HNSW's and index size up to about 1.3 times, and 2 to 1,000 times the throughput of prior methods at 0.9 recall. Qdrant's filterable HNSW instead adds edges between points that share a value of an indexed payload field. Its costs and limits are documented: build time went from 116 s to between 507 and 652 s in the benchmark; edges are built per field, not per combination, so an AND of two fields lands on intersections no edge set covers; and a value shared by more than (points / average links) x 4 points gets no edges, about 19% of the collection at 21 links.

**Partitions.** Make the predicate disappear. pgvector's README recommends partial indexes when filtering on a few distinct values and partitioning when filtering on many. Qdrant's multitenancy guide sets `payload_m` with `m` = 0, which disables the global graph and builds links per tenant for indexed payload fields, and from version 1.16 can promote a tenant that grows (the guide suggests about 20,000 points) to a dedicated shard. A partition turns a 0.1% predicate into a 100% scan of a small index; its cost is one index per value to build, vacuum and monitor.

The benchmark behind several of the figures above is Qdrant's own, published 7 August 2026 against version 1.18.2: 1M 96-dimension vectors, 500 queries per filter, recall@10 against brute force, `hnsw_ef` 64, one laptop-class machine queried serially.

## A worked decision

Scenario: document search over 40M chunks for 3,000 tenants, with the largest tenant at 15% of rows. Every query carries a tenant predicate. Most add a document-type filter with 12 values, and about a third add a date range. The engine is Qdrant 1.18, run by a team of three, and the collection takes most of a weekend to rebuild.

Tenant: layout, not search. A keyword payload index with `is_tenant` before ingestion, `payload_m` set and `m` = 0 so each tenant gets its own links, and the largest tenants promoted to dedicated shards. The 15% tenant has 6M chunks, far above the promotion guideline. After this, no query walks another tenant's nodes.

Document type: index-time edges. Twelve values known in advance, equality only, present on most queries; create the payload index before the first ingest so the graph is built with it. A type that covers more than about 19% of a tenant's rows will get no extra edges, and does not need them, because a post-filter at that selectivity returns full pages.

Date range: query time. Ranges combined with type are intersections, which per-field edges do not cover, so queries with a date range turn on ACORN and let the planner choose an exact scan when the estimate is under the full-scan threshold. The latency cost is paid only by the third of queries that carry a range.

The same design on Postgres: list partitions per tenant (separate tables for the largest), partial HNSW indexes per document type within large partitions, iterative scans with `relaxed_order` for date ranges, and a B-tree path for narrow ranges, chosen by the application when it can count the passing rows cheaply.

What this gives up: a weekend rebuild every time a new filter field needs index-time edges, and a few milliseconds on range queries. Written down: the list of fields with index-time edges and the date each was added, so a rebuild is planned rather than discovered.

## What to measure after deciding

Recall@10 against exact filtered search, on real (user, query, filter) triples sampled from logs, bucketed by the filter's actual selectivity: below 0.1%, 0.1 to 1%, 1 to 10% and above 10%. Random filters understate the correlated case and miss the negatively correlated one, which is where post-filters fail.

Per bucket, also measure the short-page rate (queries returning fewer than k rows), p95 latency and the vectors visited per query. The short-page rate is the user-visible symptom and should alert on its own. After any change to payload indexes, measure build time and index size against the previous build, and rerun the buckets; a field indexed after ingestion silently has no edges until the next rebuild.

## When this is wrong

The Qdrant tables are the vendor's own, on 96-dimension vectors and one machine queried serially; the ordering of mechanisms is informative, the milliseconds are not transferable. The ACORN results are the paper's, on its datasets and against the baselines it chose. Both measure recall against exact filtered search, which says nothing about whether the filtered results are relevant; a filter that is wrong for the user's intent produces perfect recall of the wrong rows.

Planners estimate selectivity from statistics and samples. When a filter's estimate is badly off, as with a user-specific ACL list or a freshly added field, the planner routes to the wrong mechanism and nothing in the result says so. That is why the application, which often knows the passing count from its own tables, should route the cases it can count. And none of this is a security control: a filter that enforces permissions has to be exact for the rows it returns, which the retrieval-foundations lesson on permissions covers.
