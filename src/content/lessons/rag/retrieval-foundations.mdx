export const metrics = `import math

def recall_at_k(ranked, relevant, k):
    """Fraction of all relevant docs that appear in the top k."""
    return len(set(ranked[:k]) & relevant) / len(relevant)

def hit_at_k(ranked, relevant, k):
    """1 if at least one relevant doc is in the top k. Often mislabelled as recall@k."""
    return 1.0 if set(ranked[:k]) & relevant else 0.0

def reciprocal_rank(ranked, relevant):
    for i, doc in enumerate(ranked, start=1):
        if doc in relevant:
            return 1.0 / i
    return 0.0

def ndcg_at_k(ranked, gains, k):
    """gains maps doc id to graded relevance. DCG uses gain / log2(rank + 1)."""
    dcg = sum(gains.get(d, 0) / math.log2(i + 1) for i, d in enumerate(ranked[:k], start=1))
    ideal = sorted(gains.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 1) for i, g in enumerate(ideal, start=1))
    return dcg / idcg if idcg else 0.0

## The error code nobody could find

Scenario, not a real company: a team ships a support assistant over its runbooks. It answers "why is checkout slow?" well. Then an on-call engineer pastes `E1234`, an error code that appears in exactly one runbook, and the assistant answers with a confident paragraph about payment timeouts in general. The right runbook was in the index. The retriever never returned it.

Nothing about that failure involves the language model. It is a search bug, and the fix comes from search engineering: an inverted index that rewards rare exact terms, sitting next to the embedding index rather than being replaced by it. This module covers the parts a retrieval system is built from and the metrics that tell you which part is failing. Everything after it in the track (chunking, hybrid search, reranking, agentic retrieval) assumes you can reason about these pieces the way you reason about a database query plan.

<Callout kind="interview" label="Interview tip">
Interviewers who ask "explain how RAG works" are listening for whether you treat retrieval as its own system with its own metrics. Say "retrieve, then generate, and I measure the two separately" in the first sentence.
</Callout>

## Lexical search: BM25 is a scoring function over an inverted index

You already know the inverted index: a map from term to the list of documents containing it, the same structure behind every log search tool you have used. BM25 is the function that turns those postings into a score. For each query term that appears in a document it adds

`idf(term) * tf * (k1 + 1) / (tf + k1 * (1 - b + b * doc_len / avg_doc_len))`

Three ideas sit in that line. IDF rewards rare terms: a term in one document out of a million is worth far more than "the". Term frequency saturates: the second occurrence helps less than the first, and `k1` controls how fast it flattens. Length normalisation, controlled by `b`, stops long documents winning just because they contain more words. Lucene's `BM25Similarity` defaults to `k1 = 1.2` and `b = 0.75`, and its IDF is `log(1 + (N - df + 0.5) / (df + 0.5))`; the `1 +` keeps the IDF positive even for a term in every document.

Run that on four tiny documents with the query "E1234 timeout" and the scores come out as 1.183, 0, 0.681 and 0.681. The runbook that contains `E1234` wins even though "timeout" appears in two other documents, because `E1234` appears in only one. That is exactly the query the scenario above lost.

<Callout kind="gotcha">
Postgres full-text search is not BM25. The Postgres docs say its ranking functions "do not use any global information", so `ts_rank` and `ts_rank_cd` have no corpus-wide IDF. A hybrid design that says "BM25 via tsvector" is wrong on that detail, and interviewers who have built it will notice.
</Callout>

BM25 is not a historical curiosity. The BEIR benchmark (18 datasets, zero-shot) calls it "a robust baseline"; rerankers and late-interaction models beat it on average, at a much higher compute cost. And a 2025 paper from Google DeepMind proved that the set of top-k results a single embedding vector can return is bounded by its dimension.

## Dense retrieval: bi-encoders and cross-encoders

An embedding model turns text into a fixed-length vector, and similar meanings land near each other. Used for retrieval this way it is a **bi-encoder**: queries and documents are encoded separately, so every document vector can be computed once at index time, like a materialised view. A query costs one encoder call plus a nearest-neighbour lookup.

A **cross-encoder** takes the query and one document together and outputs a single relevance score. It reads both texts at once, so it can notice that "not refundable" contradicts "refund", which a pair of independent vectors can miss. The price is that nothing can be precomputed: every query and document pair is a fresh model call.

<Fragment slot="prompt">
<p>The Sentence-BERT paper asks a concrete question: find the most similar pair of sentences in a collection of 10,000. With BERT as a cross-encoder, every pair is one inference, which is 10,000 times 9,999 divided by 2, about 50 million inferences.</p>
</Fragment>
<p>The paper reports <b>about 65 hours</b> with BERT, and about 5 seconds with Sentence-BERT, which encodes each sentence once and compares vectors. That gap is why production systems retrieve with a bi-encoder or BM25 and only run a cross-encoder over a short candidate list, the retrieve-then-rerank pattern the Sentence Transformers docs describe with "e.g. 100 possible hits".</p>
</Predict>

Two practical details come up in interviews. OpenAI's embeddings are normalised to length 1, so dot product and cosine similarity give identical rankings; that is not true of every model, so check before you pick a distance operator. And text-embedding-3-small returns 1,536 dimensions while text-embedding-3-large returns 3,072, which matters as soon as you size an index.

## ANN indexes: trading recall for speed, on purpose

Exact nearest-neighbour search compares the query with every vector. It is a full table scan: perfect recall, linear cost. pgvector does exactly this unless you build an index, and its README says so: exact search "provides perfect recall". For a few hundred thousand vectors that is often fine.

Approximate nearest neighbour (ANN) indexes give up a little recall for a large speedup, and the three families you should be able to sketch are these.

**IVF** (inverted file) clusters the vectors with k-means, stores each vector in its nearest cluster's list, and at query time scans only the `probes` closest lists. It is a hash index with fuzzy buckets. In pgvector you choose `lists` yourself; the README suggests rows / 1000 up to a million rows and the square root of rows above that, and `probes` starts at the square root of `lists`.

**HNSW** builds a multi-layer proximity graph. Each vector gets a top layer drawn from an exponentially decaying distribution, so upper layers are sparse, like the express lanes of a skip list. A search enters at the top, walks greedily towards the query, drops a layer, and repeats; on the bottom layer it keeps a candidate list of size `ef_search`. `m` caps the connections per node per layer and `ef_construction` sets the candidate list size during the build. pgvector's defaults are `m` 16, `ef_construction` 64 and `ef_search` 40. Those are one engine's choices, not properties of the algorithm.

**Product quantization** compresses vectors instead of skipping them: split each vector into sub-vectors and replace each with the id of its nearest centroid. Qdrant documents up to 64x compression for PQ, with slower search than scalar quantization. Binary quantization is the blunt version: one bit per dimension, so a 1,536-dimension float32 vector drops from 6,144 bytes to 192, a 32x cut. Recall suffers without help, so engines oversample with the bits and rescore the shortlist with full-precision vectors.

<Callout kind="gotcha" label="Filters and approximate indexes">
pgvector applies a `WHERE` clause after the HNSW scan returns its candidates. The README's own example: if a condition matches 10% of rows, with the default `ef_search` of 40, "only 4 rows will match on average". Iterative index scans (0.8.0 and later), a higher `ef_search`, partial indexes or partitions are the fixes. "Just add a WHERE clause" is the answer that fails.
</Callout>

### When Postgres with pgvector is enough

If your vectors fit comfortably on one Postgres node, pgvector buys you transactions, joins against the rows that own the vectors, access-control filters in SQL, and the backups you already run. Two limits to know: an HNSW or IVFFlat index on the `vector` type stops at 2,000 dimensions (`halfvec` goes to 4,000), so 3,072-dimension text-embedding-3-large needs `halfvec` or a shorter `dimensions` setting before it can be indexed. And pin 0.8.3 or later, which fixed possible HNSW index corruption during vacuum. A dedicated engine earns its place when you need built-in quantization, multi-vector (late interaction) search, rank fusion inside one query, or sharding you would rather not build on Postgres yourself. No source gives a row count where the switch happens; measure recall and latency at your own scale.

## Metrics: measure retrieval before you look at a single answer

A retriever returns a ranked list. Four questions about that list, four metrics, and all of them appear in Elasticsearch's ranking evaluation API.

- **recall@k**: of all the relevant documents for this query, what fraction are in the top k? It needs to know how many relevant documents exist, including ones never retrieved.
- **precision@k**: what fraction of the top k is relevant?
- **reciprocal rank**: one over the rank of the first relevant result; averaged over queries it is MRR.
- **nDCG@k**: a discounted sum of relevance in rank order, divided by the best possible ordering, so 1.0 means perfect order. It is the one that handles graded labels ("perfect", "partially useful").

<Callout kind="gotcha" label="recall@k is not hit rate">
Many blog posts compute "at least one relevant document in the top k" and call it recall@k. That is hit rate, sometimes called success@k. Say which one you report. Anthropic's contextual retrieval post, for instance, defines its failure rate as 1 minus recall@20.
</Callout>

## The metrics in code

These four functions are what a retrieval eval script is built on. The cell runs them against the worked examples above and the scikit-learn docs example for nDCG.

```python
import math

def recall_at_k(ranked, relevant, k):
    """Fraction of all relevant docs that appear in the top k."""
    return len(set(ranked[:k]) & relevant) / len(relevant)

def hit_at_k(ranked, relevant, k):
    """1 if at least one relevant doc is in the top k. Often mislabelled as recall@k."""
    return 1.0 if set(ranked[:k]) & relevant else 0.0

def reciprocal_rank(ranked, relevant):
    for i, doc in enumerate(ranked, start=1):
        if doc in relevant:
            return 1.0 / i
    return 0.0

def ndcg_at_k(ranked, gains, k):
    """gains maps doc id to graded relevance. DCG uses gain / log2(rank + 1)."""
    dcg = sum(gains.get(d, 0) / math.log2(i + 1) for i, d in enumerate(ranked[:k], start=1))
    ideal = sorted(gains.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 1) for i, g in enumerate(ideal, start=1))
    return dcg / idcg if idcg else 0.0
```

<Fragment slot="short">
<p>HNSW is a layered proximity graph, a skip list for vectors. Search enters at a sparse top layer, walks greedily towards the query, and drops down a layer at a time; on the bottom layer it keeps `ef_search` candidates. M is how many neighbours each node keeps, so a larger M means better recall and more memory and build time. ef_search is a per-query knob: larger means better recall and slower queries. pgvector defaults to 16 and 40.</p>
</Fragment>
<Fragment slot="long">
<p>Structure. Every vector is inserted at layer 0 and also at higher layers with exponentially decreasing probability, so the top layers hold few nodes with long-range links. Each node keeps up to M links per layer, chosen during the build from a candidate list of size ef_construction.</p>
<p>Search. Start at the entry point on the top layer, move to whichever neighbour is closer to the query until nothing improves, then drop a layer. At layer 0, run a best-first search that keeps the best ef_search candidates and return the top k of them. That is why ef_search must be at least k, and why recall rises with it.</p>
<p>Trade-offs. M is fixed at build time: more links mean better connectivity and recall, a bigger index and slower inserts. ef_construction also costs build time for a better graph. ef_search is the knob you can turn per query. Compared with IVF, HNSW gives a better speed-recall trade-off but builds slower and uses more memory, per the pgvector README.</p>
<p>The production catch. Filters run after the graph returns its candidates, so a selective filter starves the result set: with ef_search 40 and a 10% filter you get about 4 rows. Iterative scans or partitioning fix that.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How do you verify the index is good enough?</em> Run the same queries with exact search (pgvector does that with no index) and compute recall@k of the ANN results against the exact ones, at the ef_search you plan to ship.</li>
<li><em>How does it fail?</em> Heavy deletes and updates degrade the graph, filtered queries return too few rows, and the index stops fitting in memory, at which point latency jumps.</li>
<li><em>What is the alternative?</em> IVF with product or binary quantization when memory is the binding constraint, or exact search when the corpus is small enough.</li>
</ul>

## When this is wrong

The model here treats retrieval as "find the k nearest chunks". Real queries break it in three ways. Some questions need many documents at once ("what changed across all Q3 incident reports?"), and no top-k list answers them; that is the GraphRAG territory of a later module. Some need exact constraints (dates, tenants, permissions) that belong in filters, not in similarity. And some should not trigger retrieval at all.

The numbers are engine defaults and benchmark results, not laws. Lucene's k1 and b suit general text; heavily templated documents may want different values. pgvector's HNSW defaults are a starting point. The LIMIT result shows a limit of single vectors, not that embeddings are bad. Every figure in this lesson should be re-measured on your own corpus with your own labelled queries before it drives a design decision.
