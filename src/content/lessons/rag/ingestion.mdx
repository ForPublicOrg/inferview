## Fourteen days, or ninety

Scenario, not a real company: an HR assistant is asked how much notice a contractor must give. It answers 90 days. The policy says 14. The table with the answer was in the index, but the chunker had cut it after the "Manager | 90 days" row, so one chunk held the header and the first three rows, and the next held "Contractor | 14 days" with no header at all. Retrieval returned the chunk that mentioned notice periods. The model read the last number it could see.

Nobody would ship a database migration that silently split rows from their column names. Chunking does exactly that when it is configured by a default and never looked at. This module is about the index-time pipeline: parse, chunk, enrich, label, and keep the index consistent with its sources as they change.

## Parsing: a PDF is a drawing of a document

A PDF stores glyphs at coordinates, not paragraphs and tables. Text extraction has to rebuild reading order, and it fails in predictable places: two-column layouts read across the columns, running headers and footers repeat inside every chunk, tables come out as a stream of cells, and scanned pages have no text at all until OCR runs. Slides are worse, because the meaning often sits in the arrangement of boxes.

Treat parsing as a stage with its own tests, like a compiler front end. The usual options, in increasing cost:

- A text extractor plus cleanup rules (drop repeated headers, join hyphenated lines). Cheap, fine for prose.
- A layout-aware parser that detects tables and emits them as Markdown or HTML, so each row can be kept with its header.
- Embedding the page image itself. ColPali (ICLR 2025) embeds page images with a vision language model and scores them with multi-vector late interaction, and its authors report it beats text-extraction pipelines on their ViDoRe benchmark. Cohere's embed-v4.0 accepts mixed text and images, such as PDF pages. You still need text for the model to quote, but retrieval no longer depends on extraction getting the table right.

For tables specifically, a reliable pattern is to write each row out as a sentence or a mini-table that repeats the header ("Role: Contractor. Notice period: 14 days."), and keep the full table as a parent the generator can see.

## Chunking: the unit of retrieval

The chunk is the unit you embed, retrieve, rank and pay for in the prompt. Too large and one vector has to represent several topics, so it matches none of them well and wastes context. Too small and the answer loses the sentence that gives it meaning. The strategies:

**Fixed size** cuts every N tokens with an optional overlap. Simple, predictable, and blind to structure. OpenAI's vector stores use this by default with 800-token chunks and a 400-token overlap.

**Recursive** splitting tries separators in order (paragraph, line, space, character) and only falls back to the next when a piece is still too long. LangChain's `RecursiveCharacterTextSplitter` is the common implementation.

**Structure-aware** splitting follows headings, list items and table boundaries, then packs small sections together up to a size limit. It needs a parser that kept the structure.

**Semantic** splitting embeds sentences and cuts where consecutive sentences stop being similar. It costs an embedding call per sentence at index time.

**Parent-child** (small-to-big) retrieval indexes small chunks for precise matching but returns their parent section to the model. It separates the unit of matching from the unit of reading, which is often the real fix.

<Callout kind="gotcha" label="Characters, not tokens">
LangChain's base `TextSplitter` defaults to `chunk_size=4000`, `chunk_overlap=200` and `length_function=len`. That is 4,000 characters, not tokens, unless you pass a token counter. Code that says "1,000-token chunks" while using `len` is off by the characters-per-token ratio, which the tokens lesson showed varies by language.
</Callout>

There is no sourced "best chunk size". The most careful public comparison is Chroma's 2024 report, which measured token-level recall and intersection over union (how much of the retrieved text was actually needed) with text-embedding-3-large and 5 retrieved chunks.

That is one benchmark with one embedding model, so the lesson is the method: build a labelled set from your own documents and measure, rather than adopting anyone's default.

## Context before embedding: contextual retrieval and late chunking

A chunk that says "Revenue grew 3% over the previous quarter" does not say which company or which quarter. Two techniques put that context back.

**Contextual retrieval** (Anthropic, September 2024) asks a model to write 50 to 100 tokens explaining where each chunk sits in its document, prepends it, and indexes the result for both embeddings and BM25. On Anthropic's datasets the top-20 retrieval failure rate fell from 5.7% to 3.7% with contextual embeddings (35% fewer failures), to 2.9% adding contextual BM25 (49%), and to 1.9% adding a reranker (67%). Those percentages are reductions in a failure rate from a 5.7% baseline, not "67% better retrieval". The one-time cost was $1.02 per million document tokens using prompt caching. The same post notes that a knowledge base under about 200,000 tokens can simply go in the prompt.

**Late chunking** (Jina, 2024; revised July 2025) runs a long-context embedding model over the whole document first, then averages the token embeddings inside each chunk's span. Each chunk vector has seen the surrounding text, with no extra model calls and no training. It needs token-level outputs from the embedding model, so it does not work through an API that returns one pooled vector per input unless the provider exposes it as an option.

## Metadata, access control and freshness

Every chunk should carry its source id, a version or content hash, its position, the section heading path, timestamps, and the access-control labels of its source. Metadata is what lets you filter by tenant or date, cite the source, and delete precisely.

Freshness is a change-data-capture problem. An ingestion job that only lists files changed since the last run and upserts their chunks has two classic bugs:

1. **Deletes never propagate.** A deleted file is not in the "changed" list, so its chunks stay searchable forever. You need tombstones from the source, or a periodic full diff of source ids against index ids.
2. **Edits leave orphans.** If chunk ids are `doc_id + chunk_number` and an edit shortens a document from 12 chunks to 9, chunks 10 to 12 survive with stale text. Delete all chunks for a document version before inserting the new ones, or key chunks by version.

Changing the embedding model is a migration, not an update. Vectors from two models live in different spaces and cannot be compared, so build a new index alongside the old one, backfill it, compare recall on your eval set, and switch reads over, the same blue-green pattern you would use for a schema change. The embedding bill is the small part: 10 million chunks of 800 tokens is 8 billion tokens, which at text-embedding-3-small's $0.02 per million tokens is $160 for one pass. The backfill time, the double storage during the cutover and the eval run are the real costs.

## A chunker in code

The chunker below is the fixed-size strategy with overlap. Its tests include the 800/400 arithmetic from the Predict block.

```python
def chunk(tokens, size, overlap):
    """Fixed-size windows over a token list. Each chunk starts size - overlap after the last."""
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    step = size - overlap
    out = []
    for start in range(0, len(tokens), step):
        out.append(tokens[start:start + size])
        if start + size >= len(tokens):
            break
    return out
```

**"How do you keep a RAG index fresh when the source documents change every day?"**

<Depth>
<Fragment slot="short">
<p>Treat it as change data capture. Each source document has a stable id and a content hash; ingestion compares hashes, re-chunks and re-embeds only what changed, deletes all chunks of the old version before writing the new ones, and processes deletes as tombstones. A nightly reconciliation diffs source ids against index ids to catch anything the incremental path missed, and freshness lag is a metric with an alert.</p>
</Fragment>
<Fragment slot="long">
<p>Change detection. Prefer events from the source (webhooks, a change feed) and fall back to polling with content hashes. Hashing the normalised text, not the file bytes, avoids re-embedding when only metadata changed.</p>
<p>Write path. Chunk ids include the document version, so an update is "insert the new version, then delete the old version" and a reader never sees a half-written document. Deletes come from tombstones; if the source cannot emit them, a periodic full listing finds ids that disappeared.</p>
<p>Consistency with access control. Permission changes are changes too: if a document's ACL changes, its chunks' labels must change in the same job, or the index leaks documents to users who lost access.</p>
<p>Model upgrades. A new embedding model means a parallel index, a backfill, an eval comparison and a cutover, because vectors from different models cannot be mixed.</p>
<p>Observability. Track the lag between a source change and the index reflecting it, the count of orphaned chunks found by reconciliation, and recall on a small set of questions whose answers changed recently.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>How would you verify it?</em> Seed the eval set with questions about recently edited and deleted documents and assert the old answers no longer come back.</li>
<li><em>How does it fail?</em> Upsert-only jobs keep deleted content searchable; positional chunk ids leave stale tails after an edit; a cache in front of retrieval serves the old answer after the index is fixed.</li>

## When this is wrong

This lesson treats the chunk as the unit of meaning. For some corpora it is not. Code is better split along functions and classes than by size. Conversations need speaker turns kept together. Highly cross-referenced documents (contracts that say "as defined in section 2.1") need the referenced text pulled in, which no chunker does on its own.

The evidence here is thin in a specific way: Chroma's comparison is one benchmark with one embedding model, and Anthropic's contextual retrieval figures come from Anthropic's own datasets in 2024. Neither has a public 2025 or 2026 replication that this lesson could find. They tell you what to measure, not what you will get.
