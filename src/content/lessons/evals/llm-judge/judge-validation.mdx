## The number a judge produces is a measurement

An LLM judge exists to turn unlabelled traffic into a pass rate that someone gates a release on. That pass rate passes through an instrument with two error rates: how often the judge passes an output a human would pass, and how often it fails an output a human would fail. Validation measures those two rates on human labels. The correction uses them to remove the instrument's bias from the production number. Raw agreement does neither, because it folds the two error rates together with the class balance of whatever set it was measured on.

Write the human-labelled true pass rate as θ, the judge's pass rate on outputs humans passed as *s*, and its fail rate on outputs humans failed as *f*. Agreement on a labelled set is θ·*s* + (1 − θ)·*f*. On a set where 90% of outputs pass, *f* carries a tenth of the weight. A judge with *s* = 0.98 and *f* = 0.40 agrees 0.9 × 0.98 + 0.1 × 0.40 = 92.2% of the time and lets six in ten failures through. It is the reason a fraud model is never accepted on accuracy; the difference is that this classifier's source is a prompt that changes weekly.

## Two conventions for the same two numbers

The LLM Evals FAQ treats a failure as the positive class: TPR is the share of real failures the judge catches (its example is 8 of 10) and TNR is the share of good outputs it passes (95 of 100). The judgy library, which implements the correction, encodes 1 = Pass and 0 = Fail, so its TPR is the judge's pass rate on human passes. judgy's TPR is the FAQ's TNR. The README does not name the positive class; the code does. Put the FAQ's numbers into judgy's formula without swapping them and the corrected pass rate is wrong with no error raised.

This lesson writes *s* for the pass-side rate and *f* for the fail-side rate to stay out of that trap. The widget below follows the FAQ and treats a failure as the positive class, so its TPR is *f* and its TNR is *s*. The convention belongs in the header of every judge report.

The preset "A useful judge" catches 8 of 10 failures and wrongly fails 6 of 90 good traces: agreement 92%, kappa 0.623. "Judge that always passes" agrees 90% of the time and catches nothing. Drag "traces that really fail" down to 2 and almost any judge's agreement climbs. The two pass rates at the bottom differ whenever either error rate is nonzero, and the sign of the gap depends on which error dominates.

## The correction and its precondition

The judge's observed pass rate on production traffic is the mix of the two error rates at the true pass rate:

p_obs = θ·*s* + (1 − θ)·(1 − *f*)

Solve for θ:

θ = (p_obs + *f* − 1) / (*s* + *f* − 1)

That is judgy's estimator, which its README bases on the Rogan-Gladen correction, the epidemiologists' adjustment of a prevalence measured with an imperfect test. The denominator *s* + *f* − 1 is the precondition. When it is zero the judge's verdicts carry no information about the label and θ is undefined; when it is negative the judge is inverted. judgy's code raises `ValueError` when *s* + *f* ≤ 1 and clips θ to [0, 1] otherwise.

The denominator also sets the noise gain: an error in p_obs reaches θ divided by (*s* + *f* − 1). At *s* = 0.95 and *f* = 0.60 the denominator is 0.55, so a one-point error in the observed rate becomes almost two in the corrected one. A judge barely better than chance is valid input to the formula and useless output from it.

## The interval, and what judgy leaves out of it

The point estimate inherits uncertainty from three samples: the human passes behind *s*, the human fails behind *f*, and the production sample behind p_obs. judgy's bootstrap resamples the labelled test set, recomputes *s* and *f*, and recomputes θ with p_obs held fixed. It defaults to 20,000 iterations and a 95% percentile interval, and it skips any resample that lacks one of the classes or falls to *s* + *f* ≤ 1. Reading the code rather than the README gives two consequences.

First, the production sample's own error is not in the interval, which matters when the judge scores a few hundred traces. The half-width it would add at 95% is about 1.96 × √(p_obs(1 − p_obs)/n) / (*s* + *f* − 1). With p_obs = 0.785 and a denominator of 0.55, that is 1.5 points at n = 10,000 and 10.4 points at n = 200.

Second, the skipped resamples are the ones where the judge looks worst. On a small test set with few failures, dropping them narrows the interval on the side where the truth may be. When far fewer resamples survive than were run, the test set is too small for the claim.

The function below is a standard-library version that resamples both samples. The labelled set is 100 human passes (the judge passes 95) and 50 human fails (the judge fails 30), so *s* = 0.95 and *f* = 0.60.

```python
import random

def rates(labels, preds):
    """1 = pass, 0 = fail, as in judgy. Returns (s, f)."""
    n_pass = sum(labels)
    n_fail = len(labels) - n_pass
    s = sum(1 for y, p in zip(labels, preds) if y == 1 and p == 1) / n_pass
    f = sum(1 for y, p in zip(labels, preds) if y == 0 and p == 0) / n_fail
    return s, f

def corrected(p_obs, s, f):
    j = s + f - 1
    if j <= 0:
        raise ValueError(f"judge no better than chance: s + f = {s + f:.3f}")
    return min(1.0, max(0.0, (p_obs + f - 1) / j))

def interval(labels, preds, prod_preds, iters=2000, seed=0):
    """Percentile bootstrap over the labelled set and the production sample."""
    rng = random.Random(seed)
    test = list(zip(labels, preds))
    out = []
    for _ in range(iters):
        ys, ps = zip(*rng.choices(test, k=len(test)))
        prod = rng.choices(prod_preds, k=len(prod_preds))
        if 0 < sum(ys) < len(ys):
            s, f = rates(ys, ps)
            if s + f > 1:
                out.append(corrected(sum(prod) / len(prod), s, f))
    out.sort()
    return out[int(0.025 * len(out))], out[int(0.975 * len(out)) - 1], len(out)

labels = [1] * 100 + [0] * 50
preds = [1] * 95 + [0] * 5 + [0] * 30 + [1] * 20
for n in (200, 2000):
    prod = [1] * round(0.785 * n) + [0] * (n - round(0.785 * n))
    s, f = rates(labels, preds)
    lo, hi, kept = interval(labels, preds, prod)
    print(n, round(corrected(0.785, s, f), 3), round(lo, 3), round(hi, 3), kept)
```

Run with seed 0, the corrected rate is 0.700 in both cases, with an interval of [0.586, 0.789] at n = 2,000 and [0.531, 0.827] at n = 200. The same calculation with p_obs fixed and 20,000 resamples, which is what judgy does, gives [0.588, 0.784] whatever the production sample size. At n = 200 that interval is 0.196 wide against 0.296, so holding p_obs fixed hides about a third of the width.

## How many labels the validation needs

The FAQ asks for 30 to 50 Pass and 30 to 50 Fail examples in each of the dev and test sets, and 100 to 200 labelled examples per failure mode; Hamel Husain's judge write-up puts the target at about 100 per failure mode and says intervals are often too wide below 60. The arithmetic behind those floors: with *f* = 0.6 estimated from n human fails, the 95% half-width on *f* is 1.96 × √(0.24/n), which is 17.5 points at n = 30, 13.6 at n = 50 and 9.6 at n = 100.

Those points do not reach θ one for one. Differentiate the estimator: ∂θ/∂*f* = (*s* − p_obs)/(*s* + *f* − 1)² and ∂θ/∂*s* = −θ/(*s* + *f* − 1). At the example's values they are 0.165/0.3025 = 0.55 and −0.70/0.55 = −1.27. An error in *s* moves the corrected rate more than an error of the same size in *f*, so the pass side cannot be skimped either, even though failures are the scarce class.

The scarce class sets the labelling bill: if 5% of traffic fails, a random sample needs about 1,000 traces to contain 50 failures. Oversampling likely failures for labelling is safe because *s* and *f* are rates conditional on the human label: the share of failures in the labelled set does not enter them. It stops being safe when the oversampling uses the judge's own verdict. Pick candidates from traces the judge failed and the labelled failures are the ones the judge already catches, so *f* comes out high. Select on a signal independent of the judge (user thumbs-down, escalations, a code check, a different model), or label a random slice alongside the targeted one and compare *f* on the two.

## When to re-validate

*s* and *f* are properties of the judge prompt, the judge model and the mix of outputs being judged. Change any of the three and the old numbers describe a different instrument.

**Judge prompt.** Iterate on dev and measure on test once, after the prompt is frozen, as Husain's write-up specifies. Re-tuning and re-measuring on the same test set turns it into a second dev set, and the reported rates drift upward without the judge improving.

**Judge model.** A provider's model upgrade or a switch to a cheaper judge is a new classifier. Husain's rule is "if I update a model, I'll run the process again." Pin the judge model version, so that the change is a decision rather than an event.

**The system being judged.** *f* is an average over failure types weighted by how often each occurs. Suppose the judge catches 90% of failure type A and 30% of type B. At a mix of 80% A and 20% B, *f* = 0.8 × 0.9 + 0.2 × 0.3 = 0.78. After a prompt change that fixes most A failures the mix is 40% A and 60% B, and *f* = 0.4 × 0.9 + 0.6 × 0.3 = 0.54, with no change to the judge. The release that fixed A also degraded the instrument measuring it. Keep the test set's failures tagged by type from error analysis, report *f* per type, and recompute the blend from the current mix.

## When this is wrong

The correction assumes *s* and *f* measured on the test set hold on the production sample. That holds only if production failures are drawn from the same types in the same proportions. A failure type absent from the test set has an unknown *f*, and the corrected rate is wrong by an amount nothing in the calculation reveals. New categories from each round of error analysis go into the test set before the next correction is trusted.

The human labels are treated as ground truth, but they are one expert's judgement. When two labellers disagree on a material share of traces, the judge's measured rates are bounded by that disagreement, and a judge that matches expert A may look worse against expert B. The FAQ recommends a single domain expert as the final authority for small and mid-sized teams, and an agreement statistic such as Cohen's kappa where several annotators are unavoidable.

The estimator treats each trace as one independent binary outcome. Multi-turn sessions judged turn by turn, or several traces per user, are clustered, and a bootstrap that resamples traces instead of sessions or users understates the interval.

Published agreement figures, such as the Honeycomb query assistant's more than 90% after three iterations in Husain's post, describe one product's judge and are not *s* and *f* for another.
