## Seventy-five percent, three times

Scenario, not a real company: a team demos a refund agent. On their eval of support tasks it succeeds 75% of the time, each task run once. A pilot customer sends the same kind of request every day and expects it handled every day. The agent's reliability on that customer's workload is not 75%.

## A flaky test you run on purpose

You know flaky tests. A test that passes 75% of the time will usually go green if CI retries it three times, and that is exactly the problem: the retry hides the flakiness. A flaky-test detector does the opposite. It runs the test many times and flags anything that does not pass every time.

Agents are flaky by construction. The same task can succeed or fail depending on sampling, on a tool's latency, on which document came back first. So an agent eval runs each task several times, and the two ways of summarising those runs mirror the two CI behaviours.

Anthropic's guide gives the vocabulary interviewers now use. A **task** is one problem with its success criteria. A **trial** is one attempt at it. The **transcript** is everything that happened in the trial, the **outcome** is the final state of the world, and a **grader** scores one or the other. The **eval harness** runs tasks and graders; the **agent harness** is the scaffold around the model (tools, loop, prompts). Change the agent harness and you change the agent, even with the same model.

- **pass@k** is the probability that at least one of k trials succeeds. It is the CI retry. It answers "can the agent do this at all?", which matters when a human or a verifier picks the best of several attempts.
- **pass^k** (read "pass hat k") is the probability that all k trials succeed. It is the flaky-test detector. It answers "will it do this every time?", which is what a customer-facing agent has to promise.

With a constant per-trial success rate p and independent trials, pass@k = 1 - (1 - p)^k and pass^k = p^k. Slide k up and watch the two lines separate.

At p = 0.75 and k = 8, pass@8 is above 99.9% while pass^8 is 0.75^8, about 10%. The same agent looks nearly perfect or nearly useless depending on which question you ask, which is why a reliability claim without the metric named is meaningless.

## Estimating them from real trials

The widget assumes one success rate for every task. Real suites mix easy and hard tasks, and the estimator matters. tau-bench, which introduced pass^k for agents, computes it per task from n trials with c successes as C(c, k) / C(n, k), the chance that k trials drawn from the n are all successes, and then averages over tasks. pass@k uses the unbiased estimator from the Codex paper, 1 - C(n - c, k) / C(n, k).

```python
from math import comb

def pass_at_k(n, c, k):
    # at least one of k trials succeeds; needs n >= k
    if n - c < k:
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n, c, k):
    # all k trials succeed
    return comb(c, k) / comb(n, k)

tasks = [(8, 8), (8, 6), (8, 2)]          # (trials, successes) for three tasks
print(sum(pass_hat_k(n, c, 4) for n, c in tasks) / len(tasks))   # 0.405
pooled = sum(c for _, c in tasks) / sum(n for n, _ in tasks)      # 16/24
print(pooled ** 4)                                                # 0.198
```

Worked through: the first task always succeeds, so its pass^4 is 1. The second has C(6, 4) / C(8, 4) = 15 / 70 = 0.214. The third, with only 2 successes, cannot produce four in a row, so 0. The average is 1.214 / 3 = 0.405. Pooling all 24 trials into one rate of 0.667 and raising it to the fourth power gives 0.198, less than half the right answer, because the pooled shortcut pretends every task is equally flaky. Reliability is concentrated: some tasks are solid and some are hopeless, and that shape is what you want to see.

The same care applies to pass@k. Plugging a single-trial rate into 1 - (1 - p)^k is biased; for one task with 6 successes in 8 trials, the estimator gives pass@2 = 1 - C(2, 2) / C(8, 2) = 1 - 1/28 = 0.964, while the shortcut gives 1 - 0.25² = 0.9375.

The real numbers are sobering. In the tau-bench paper, gpt-4o with function calling had a pass^1 of 61.2% on the retail domain (115 tasks) and 35.2% on airline (50 tasks), and its retail pass^8 was under 25%. Those are 2024 results; the benchmark has since grown into tau2-bench, whose v2.0.0 release in October 2026 adds languages and voice and keeps its results on a separate leaderboard tab from 1.x, because the two are not comparable.

## Grade the outcome, diagnose the path

What should a grader look at? Anthropic's advice is that it is often better to grade what the agent produced, not the path it took. A refund agent succeeded if the right refund exists in the database and the customer got a correct message, whether it looked up the order first or second. Exact trajectory matching penalises valid alternatives and rewards agents that mimic your reference run.

Trajectories still matter, for two jobs. The first is diagnosis. The FAQ's transition failure matrix takes every failed trace, records the last state that succeeded and the state where the first failure happened, and counts the pairs. In its text-to-SQL example, failures between generating SQL and executing it numbered 12, against 2 between choosing a tool and planning a calendar action, which tells you where to work. The second job is efficiency and safety: an agent that reaches the right outcome in 40 tool calls, or by calling a tool it should never touch, should fail a separate check. Libraries such as LangChain's agentevals offer trajectory matching in strict, unordered, subset and superset modes for exactly these constraints.

The guide's suggestions by agent type are a good checklist. Coding agents: run the tests, add static analysis, and use a rubric for the rest. Conversational agents: check the end state, add constraints on the transcript, and use a simulated user. Research agents: groundedness, coverage and source quality. Computer-use agents: check the final state of the sandbox.

Two warnings from the same guide. A task with 0% success over many trials is most often a broken task or grader, not an incapable agent, so read those transcripts first. And for conversations, the FAQ adds that a trace does not end at a handoff to a human; it ends when the user's need is resolved, so log why the handoff happened and how it ended.

Three habits keep you honest with these. Quote the date and harness with every number, because the 2023 figures above say nothing about today's models. Read how the grader works: BrowseComp's short verifiable answers make grading cheap and unambiguous, while SWE-bench's quality depends on its tests. And remember contamination: public tasks leak into training data, which is part of why OpenAI dropped SWE-bench Verified, and why the strongest signal for your product comes from a private set of your own hard tasks.

## Cost is part of the score

Two agents with similar pass rates can differ a lot in cost, and a pass rate alone hides it. Report cost and tokens per task next to success, and compare cost per successful task. An illustrative pair: agent A passes 70% of tasks at $0.40 per attempt, agent B passes 74% at $1.20. Cost per success is 0.40 / 0.70 = $0.57 for A and 1.20 / 0.74 = $1.62 for B. Whether 4 points of success are worth nearly three times the cost per success is a product decision, but nobody can make it if the eval reports only the pass rate. Count tool calls and turns too; a regression that doubles them often shows up there before it shows up anywhere else.

<Fragment slot="long">
<p>Definitions. For one task with n trials and c successes, the tau-bench estimator of pass^k is C(c, k) / C(n, k), averaged over tasks; pass@k uses 1 - C(n - c, k) / C(n, k). As k grows, pass@k rises towards 1 and pass^k falls towards 0, so the same agent can look excellent or unusable.</p>
<p>Why per task. Reliability is uneven. Three tasks at 8, 6 and 2 successes out of 8 give a pass^4 of 0.405, but the pooled rate of 0.667 to the fourth is 0.198. The per-task view also tells you which tasks to fix.</p>
<p>When each applies. pass@k fits workflows with a verifier or human picking the best of several attempts, such as code with tests. pass^k fits anything a user relies on repeatedly, such as support, operations and payments. I would put pass^k, with k chosen from expected repeat usage, in the reliability target, next to cost per task.</p>
<p>Caveats. Trials are not always independent: cached responses, a fixed seed or shared state between runs inflate pass^k. And a task with 0% over many trials is usually a broken grader, so I read those transcripts before reporting.</p>
</Fragment>

<ul>
<li><em>How many trials per task?</em> At least k, and more if you want a stable estimate; the estimator is undefined for n below k. The cost scales with trials times tasks, so run the large k suite before releases, not on every commit.</li>
<li><em>How would you raise pass^k without a better model?</em> Read the inconsistent tasks' transcripts: unclear tool descriptions, missing validation and ambiguous policies cause variance more often than model capability.</li>

## When this is wrong

The flaky-test picture treats trials as independent coin flips. They often are not: provider-side caching, deterministic decoding or state left over from a previous trial make repeated runs more alike than real usage, and the estimate comes out too optimistic. Reset environments between trials and vary what you can.

It also treats success as binary. Many agent tasks have partial credit, such as three of four requested changes made, and forcing them into pass or fail throws information away. Keep the binary verdict for gating, and record the sub-checks underneath it.

And a benchmark table like the one above ages quickly. The leaders change month to month, so link to the leaderboard rather than memorising a top score, and expect an interviewer to care more about why a score might mislead than about the score itself.
