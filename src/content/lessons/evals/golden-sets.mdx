export const solution = String.raw`import json, re

REQUIRED = {"invoice_id": str, "total": (int, float), "currency": str, "due_date": str}

def check(output, source_text):
    """Return a list of failure strings; an empty list means the output passes."""
    try:
        data = json.loads(output)
    except json.JSONDecodeError as e:
        return ["not valid JSON: %s" % e.msg]
    if not isinstance(data, dict):
        return ["not a JSON object"]
    failures = []
    for key, typ in REQUIRED.items():
        if key not in data:
            failures.append("missing " + key)
        elif isinstance(data[key], bool) or not isinstance(data[key], typ):
            failures.append("wrong type for " + key)
    extra = set(data) - set(REQUIRED)
    if extra:
        failures.append("unexpected keys " + ",".join(sorted(extra)))
    if isinstance(data.get("currency"), str) and not re.fullmatch(r"[A-Z]{3}", data["currency"]):
        failures.append("currency is not a 3-letter code")
    if isinstance(data.get("due_date"), str) and not re.fullmatch(r"\d{4}-\d{2}-\d{2}", data["due_date"]):
        failures.append("due_date is not YYYY-MM-DD")
    if isinstance(data.get("invoice_id"), str) and data["invoice_id"] not in source_text:
        failures.append("invoice_id not found in source")
    return failures
`;

## Four hundred questions nobody asked

Scenario, not a real company: a team builds a contract question-answering assistant for an in-house legal department. Before launch they ask a model to write 400 questions from the contracts, one per clause, and the assistant passes 97% of them. In the first week, the lawyers ask things the set never contained: "does this contract have a non-compete at all?", "which of these three agreements renews first?", "is the liability cap in the MSA or the order form?" Questions about absent clauses, questions across documents, questions about where something lives. The assistant fails most of them, and the 97% stays on the dashboard.

Nothing was wrong with the 400 questions individually. The set was wrong as a sample. It measured what was easy to generate, which was one clause at a time, present in exactly one document.

## A fixture file with opinions

In ordinary code, a golden file is the expected output you diff against. For an LLM feature, a golden set is closer to a table of test fixtures: each row is an input, plus whatever you need to judge the output. Sometimes that is a reference answer, more often it is a set of properties the answer must have ("cites clause 14.2", "says no non-compete exists") or must not have ("does not invent a renewal date"). The difference from unit tests is that you cannot enumerate the input space, so the hard part is choosing rows that represent it.

The sources, in the order I reach for them:

**Real failures from error analysis.** Every category you found in the previous lesson gets its own cases, taken from the traces where you saw it. Anthropic's January 2026 guide to agent evals puts the starting point bluntly: "20-50 simple tasks drawn from real failures is a great start." Small and real beats large and invented.

**Real successes.** A set made only of failures rewards a system that refuses everything. The same guide recommends testing both sides of a behaviour: cases where the assistant should search, and cases where it should not; questions it should answer, and questions it should decline.

**Synthetic inputs to fill holes.** Write down the dimensions that matter for your product, here question type (single clause, absent clause, cross-document, location), document type and user role, and generate inputs for the combinations your real traffic has not covered yet. Generating per combination is what keeps a model from writing 400 variations of its favourite question.

**Adversarial cases.** Prompt injection inside a contract, a question in another language, a contract with a clause numbered twice.

The guide also separates two suites that grow from the same rows. A **capability** suite holds tasks the system mostly fails today; its pass rate starts low and tells you whether you are improving. A **regression** suite holds tasks it reliably passes; its pass rate should sit near 100% and any drop blocks a release. When a capability task passes reliably, it graduates into the regression suite. Hamel Husain and Shreya Shankar's FAQ makes a similar split by where the set runs: a small purpose-built set, on the order of 100 or more examples, with deterministic checks where possible, runs in CI, while production evaluation samples live traces and feeds new failures back into the CI set.

## Level 1: assertions you can run on every commit

The cheapest eval is code. If the output is supposed to be JSON with four fields, check that, and check it on every change before anything more expensive runs. Assertions catch a whole class of real failures: prose wrapped around the JSON, a total returned as a string, a date in the wrong format, an identifier the model invented.

That last one is worth dwelling on. "The invoice id in the output appears verbatim in the source document" is a one-line check that catches a class of fabrication no schema validator can see.

## Retrieval metrics and answer metrics

If your system retrieves before it answers, measure the two halves separately, because they fail separately and are fixed by different people.

Retrieval metrics need a labelled set of relevant documents per query. Here is one query, a ranked list of five retrieved documents, and the labels.

<p>Two of the three relevant documents (d2 and d4) are in the top five, so recall@5 is 2/3, about 67%. Precision@5 is 2/5 = 40%, because three of the five slots hold irrelevant documents. The reciprocal rank is 1/2, because the first relevant document sits at position 2. Notice that d8 is never retrieved at all. No amount of reranking fixes recall that the first stage never had.</p>
</Predict>

The rest of the family, on the same example: nDCG@5 rewards relevant documents near the top with a log discount, here (1/log2(3) + 1/log2(5)) divided by the ideal (1 + 1/log2(3) + 1/log2(4)), which is 1.062 / 2.131 = 0.498. RAGAS's context precision averages precision@k over the positions that hold relevant items: precision@2 = 0.5 and precision@4 = 0.5, so the score is 0.5.

Answer metrics are where most teams reach for a library. RAGAS defines the common ones, and their definitions are worth knowing exactly, because each measures less than its name suggests:

- **Faithfulness** is the number of claims in the response supported by the retrieved context divided by the total number of claims. Two claims, one unsupported, scores 0.5. It measures support by the context, not truth: if retrieval fetched an outdated contract, a faithful answer is faithfully wrong.
- **Response relevancy** has a model generate questions from the response (three by default) and averages the cosine similarity between their embeddings and the user's question. It checks that the answer is on topic. It does not check a single fact.
- **Context recall** is the share of claims in a reference answer that the retrieved context supports. It needs a reference answer, so it is an offline metric.

Two cautions. The RAGAS library itself has been changing: its legacy metric classes are deprecated in 0.4 and slated for removal in 1.0, and the repository moved to `vibrantlabsai/ragas`. Pin the version and know the formula, so a library upgrade cannot silently change your numbers. And the FAQ's verdict on BERTScore, ROUGE and cosine similarity is that they are generally not useful as quality measures for LLM output, and that generic scores used that way create false confidence. They are still handy as filters for finding traces worth reading.

## Benchmarks are someone else's golden set

A public benchmark is a golden set built for a different product, published, and then trained on by accident. HumanEval has 164 problems; when it was released in 2021, Codex solved 28.8% of them with one sample and 70.2% when allowed 100 samples per problem. That second number is a reminder that the scoring rule is part of the benchmark: the same model gets very different scores depending on how many tries it is allowed.

Contamination is the other trap. Once problems and solutions are public, they leak into training data, and the score starts measuring recall instead of ability. In February 2026 OpenAI announced that it no longer reports SWE-bench Verified, citing contamination and tests that reject correct solutions, and pointed to SWE-bench Pro instead. The lesson for your own work is not about one benchmark. It is that a score on a public set says little about your contracts, your users or your repository.

Practical defences for your own sets: keep a held-out slice nobody tunes prompts against; date-stamp cases and prefer ones created after the model's training cutoff; rephrase a sample of cases and check whether the score drops, which is a sign of memorised wording; and when you fine-tune on production data, deduplicate the eval set against the training set before every run.

## Versioning, drift and staleness

Treat the golden set as code. It lives in version control, every change is reviewed, and every score you record carries the set version it came from. Suppose you add 30 hard cases to a 200-case set that scored 182, and the new cases pass 6 times: the score goes from 182/200 (91%) to 188/230 (about 82%) without the system changing at all. The denominator changed. Re-run the baseline on the new version before you compare anything.

Sets go stale in two ways. The world changes under the labels: a refund policy is updated and last quarter's "correct" answer is now wrong. And traffic drifts away from the set: a new feature launches, a new customer segment arrives, and the set keeps measuring last year's questions. The remedy is the loop from the previous lesson. Each error-analysis cycle adds fresh failures, and on a fixed schedule someone reads a sample of the set itself and retires cases whose labels no longer hold.

## When this is wrong

The fixture-file picture assumes you can say what a good answer contains. For open-ended work, such as drafting an email or summarising a negotiation, there is no single reference, and properties get vague. There you lean more on pairwise comparison and calibrated judges, which is the next lesson, and on outcome metrics from real usage.

It also assumes the set stays independent of the system. Every time you tune a prompt until the golden set passes, you leak a little of the set into the prompt. Keep a held-out slice, look at it rarely, and expect it to score lower than the slice you iterate on. When the two numbers diverge sharply, you have been fitting your test.
