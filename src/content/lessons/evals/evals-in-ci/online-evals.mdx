## The decision

Every check that runs against production traffic has a placement, and the placement fixes its cost model. Four are available.

**Inline**, in the request path, before the user sees the output. The check pays latency on every request and its errors become user-visible errors. In return it can block, redact or regenerate.

**On every trace, asynchronously.** The check runs after the response, on all traffic, and blocks nothing. Code checks belong here: they cost a few CPU milliseconds per trace and see every request, so a rare failure is counted rather than estimated.

**On a sample**, usually a judge, run on a filtered and sampled subset of traces. It sees nuanced quality that code cannot score, costs a model call per sampled trace, and sees only a fraction of traffic.

**Nightly or on a schedule**, against a fixed input set sent through the production configuration. It sees the same inputs every run, so a change in output is a change in the system, not in the traffic.

The decision for each failure mode is which of these, and it turns on four properties: how bad one occurrence is, whether code can recognise it, how often it occurs, and whether the team is allowed to read the traffic that contains it.

## Guardrails and evaluators are different components

The AI Evals FAQ draws the line by latency and determinism. Guardrails sit inline, are fast and deterministic, have a few milliseconds of latency budget, and are reserved for clear-cut, high-impact failures: a leaked personal identifier, profanity, malformed JSON. When one fires it redacts, refuses or regenerates. Evaluators run after the response, usually asynchronously or in batch, and measure qualities such as correctness and completeness without blocking anything. The FAQ's view is that a slow or non-deterministic judge would almost never be used as a synchronous guardrail.

The reason is not only latency. An inline judge is a second model dependency in the request path, so its outages, rate limits and timeouts become the product's, and its false positives become refusals of good answers. If a judge seems necessary inline, the usual better answer is to make the decision structural: constrain the output format so a parser can check it, or narrow the tool permissions so the dangerous action cannot be taken, and leave the judge in the asynchronous path.

The middle placement, every trace and asynchronous, is easy to skip because its checks are too blunt to block on. Code checks that would be too blunt to block on are cheap enough to count on all traffic: output language differs from input language, response length outside the usual band for the route, a structured field missing, a refusal phrase in a route that should never refuse, a tool call that returned an error the model then ignored. They are counters with alerts, not gates.

## Sampled judges: what the configuration controls

LangSmith's online evaluators are a representative implementation. A rule has a filter (runs with negative user feedback, runs that called a given tool, runs with a metadata value such as plan type, or runs where another evaluator scored correctness below 0.5), and a sampling rate applied to the filtered runs, where 0.1 means 10%. A weekly LLM spend limit per evaluator pauses that evaluator when reached and resets on Monday at 00:00 UTC. Backfill over past traces is available only when the rule is created. Attaching an evaluator to a trace upgrades it to extended retention, which changes trace storage pricing, so an evaluator with a broad filter has a storage cost on top of its judge cost.

Two configuration choices are the ones that go wrong.

**Filtering only on negative feedback.** It concentrates judge spend on traces likely to be bad, which is useful for finding failure modes, and it makes the judged pass rate meaningless as a quality metric because the denominator is selected. The FAQ's advice for review batches applies to evaluators too: keep a random slice, because selecting on negative feedback misses problems users do not report. Run two rules: a filtered one for discovery, and a uniform random one whose pass rate is the number on the dashboard.

**A spend limit with no alert.** When the weekly limit pauses an evaluator on Thursday, the dashboard shows no new failures until Monday. Alert on evaluator pauses the way you would alert on a stopped consumer.

## How much a sample can see

Anthropic's postmortem of August and September 2025 is the reference case for what production quality evaluation misses. Three infrastructure bugs degraded responses on different platforms, at different rates, with different symptoms. A context-window routing error sent about 0.8% of Sonnet 4 requests to servers configured for the upcoming 1M-token context window from 5 August; a load-balancing change on 29 August raised that to 16% at the worst hour on 31 August. A TPU misconfiguration from 25 August produced unexpected characters, such as Thai or Chinese text in English replies. An approximate top-k miscompilation affected other models. The postmortem says the evaluations Anthropic ran did not capture the degradation users were reporting, partly because Claude often recovers well from isolated mistakes.

The arithmetic shows why a sampled judge is the wrong detector for the first phase of that incident.

Three properties of that incident make the gap wider than the arithmetic suggests. The routing was sticky: once a request was served by a wrong server, follow-ups were likely to be served by it too, so about 30% of Claude Code users who made requests in the period had at least one misrouted message even while the per-request rate was low. A per-request sample measures the per-request rate; users experience the per-user rate. Second, the bugs differed by platform, so a global average mixes affected and unaffected slices and dilutes each. Third, the model recovering from isolated mistakes means a judge scoring the final answer sees fewer failures than occurred.

The fixes follow from the arithmetic. Slice the judged rate by every dimension the serving path varies on (platform, region, model version, routing tier, context-length bucket), because a 0.8% global effect concentrated in one slice is a large effect in that slice. Count deterministic symptoms on every trace: an English request answered in another script is a code check, and on all traffic it turns the output-corruption bug into a counter that moves on the first day. And send known inputs through the production paths on a schedule.

## Quality probes

Anthropic's list of changes after the postmortem includes more sensitive evaluations, quality evaluations in more places run continuously on production systems, and faster debugging tooling for community feedback that protects user privacy. The postmortem also names what validation relied on before: benchmarks, safety evaluations, performance metrics, spot checks and small canary groups. Read side by side, the two lists move quality evaluation from the model toward the serving paths the model runs on.

A quality probe is the eval-suite version of synthetic monitoring: a fixed set of prompts with checkable answers, sent through each production path (every platform, region and routing tier, not the one the eval harness happens to call), scored by code where possible, and compared run over run. It answers a question no sampled judge can: did the same input get a worse answer through this path than yesterday. Its limits are the usual ones for synthetic checks. It covers the inputs someone chose, and a bug triggered by long contexts or by a particular load-balancer state is only found if a probe reaches that state, which is an argument for including long-context and multi-turn probes and for running them often enough to catch hourly variation.

## Judge drift

A sampled judge is itself a model behind an API, so its own behaviour can move. When the judge model or its prompt changes, the judged fail rate shifts with no change in the product, and a dashboard that plots one line across the change reports a regression or an improvement that did not happen. Pin the judge model version, record the judge version and prompt hash with every score, and treat a judge change as a deploy with its own annotation. Keep a fixed calibration set of human-labelled traces and score it on every judge change and on a schedule; if the judge's agreement with the labels moves, re-establish it before trusting the production line. The llm-judge module covers how to measure that agreement.

## Privacy limits

Online evaluation reads production traffic, and that is often the binding constraint. The Anthropic postmortem names it directly: internal privacy and security controls limit how and when engineers can access user interactions, especially those not submitted as feedback, and that made the cases hard to examine. A design that assumes engineers can read sampled traces will not survive review in a regulated deployment.

The workable patterns: run judges inside the boundary that already holds the data (same region, same processor terms, same retention), and export scores and labels rather than text. Redact identifiers before a trace reaches a judge, and accept that redaction changes what the judge sees. Restrict human reading to traces the user submitted as feedback, plus an audited access path for incidents. Prefer evaluators whose outputs are categorical (failure mode, language mismatch, schema miss), because a category can be aggregated and shared where text cannot. When even judging is not allowed, the every-trace code checks and the probes still work, since probes run on inputs the team wrote.

## When this is wrong

Uniform sampling under-represents rare routes. A route with 0.5% of traffic gets a handful of judged traces a day at a 1% sample, and its fail rate is noise. Stratify the sample by route, with a floor per slice, and accept that the stratified rate needs reweighting before it represents total traffic.

The sample-size arithmetic assumes judged outcomes are independent. Traces from one user or one conversation are not, so the effective sample is smaller than the count; group by user or conversation when computing intervals.

Some failures are invisible to any per-trace judge because each response looks acceptable on its own: an assistant that has become more agreeable across all users passes groundedness and tone checks one trace at a time. Those failures show up in outcome metrics over users and weeks, which is the subject of the next lesson.

Finally, every placement here assumes the failure produces a symptom someone thought to check. Probes cover chosen inputs, counters cover chosen symptoms and judges cover chosen rubrics. The evaluation surface has to match the serving surface, and user reports remain a detector that needs its own triage path.
