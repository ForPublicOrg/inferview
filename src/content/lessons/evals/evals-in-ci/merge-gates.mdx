## The decision

A pull request to a prompt repository changes a system prompt, a tool description, a model version or a retrieval setting. CI runs the eval suites against the base branch and the candidate on the same cases. The gate has to decide, without a human, whether the change merges.

Three kinds of evidence come back from that run, and each needs a different rule. Some cases encode a requirement: the output parses against the schema, a request for another customer's data is refused, a card number is redacted. One failure is a defect, and statistics have nothing to add. Some cases are judged or noisy: a judge decides whether the answer was grounded in the retrieved policy, and the same case can pass and fail on two identical runs. A single failure there is weak evidence, and the question is whether the pattern of changes is larger than noise. And some numbers are context for the reviewer: cost per case, latency, tool calls, the pass rate on a capability suite that is meant to be hard. Gating on those blocks good changes for reasons nobody wrote down.

The common mistake is to apply one rule to all three: a pass-rate threshold over everything, or a significance test over everything. Both fail in predictable ways.

## Why a pass-rate threshold is the wrong statistic

promptfoo's CI documentation shows the usual starting point: run the eval, parse `results.json`, compute passes over passes plus failures, and exit 1 below a fixed number, 95% in their example. Take a 200-case suite where main passes 198. A candidate breaks 8 cases and fixes 1, so it passes 191, which is 95.5%. The threshold merges it.

The run carries more information than two pass rates. Both sides ran on the same 200 cases, so the comparison is paired, and the only cases that say anything about the difference are the ones that changed outcome. Here 9 cases flipped and 8 of them went the wrong way. If each flip were a fair coin, the chance of 8 or more of 9 going one way is (9 + 1) / 2^9 = 10 / 512 = 0.0195. That is the exact one-sided sign test on the discordant pairs, which is McNemar's test in its exact form, and it blocks the change.

The threshold also fails in the other direction. A suite that sits at 94% on main fails every pull request until someone lowers the number, and once a threshold has been lowered by hand it stops being a gate.

Evan Miller's paper on error bars for evals makes the general case for pairing: compute the standard error on question-level differences rather than combining two independent standard errors, because the two models' scores on the same question are correlated. In the paper's worked example, a correlation of 0.5 cuts the variance of the difference from 1/6 to 1/9. The paper calls that reduction free and recommends reporting pairwise differences, their standard errors and the score correlation whenever two models are compared.

## Three tiers

**Hard gates.** Assertions and must-pass cases: schema validity, refusals that are policy, redaction, the tool call that must never fire without approval. The rule is that every case passes, in every trial, and a failure blocks with the case id in the log. The flip test is the wrong tool here for a concrete reason: a candidate that breaks four must-refuse cases and fixes nothing has p = 0.0625 and merges at alpha 0.05. No sample size argument makes that acceptable, so these cases never enter the statistical tier.

The hard tier only works if its cases are deterministic enough to fail for one reason. A must-pass case that flakes once in twenty runs will fail roughly one pull request in twenty on its own, and the pressure to add a retry or loosen the case follows. Score hard cases with code (a parser, a regex, an exact tool-call check) where possible. When a judge is unavoidable, separate the two sources of flakiness. If the model sometimes complies with a request it must refuse, that is a real defect, and every generation must pass. If the judge sometimes misreads a correct refusal, judge each output three times and take the majority: with a 5% judge error per call, a majority of three is wrong 3 × 0.05^2 × 0.95 + 0.05^3 = 0.7% of the time, at three times the judge cost for those cases only.

**Statistical gates.** Judged metrics on the regression suite, compared case by case against main with the exact sign test on the flips. Two parameters need a written choice. Alpha sets how often a change with no real effect is blocked; at 0.05 and one gated metric, about one null change in twenty is blocked. The number of gated metrics multiplies that: five independent gated metrics at 0.05 each block a null change with probability 1 − 0.95^5 = 0.226. Gate on one or two metrics that name the failure the suite exists to catch, and report the rest.

**Report-only.** Everything else goes into a pull-request comment as diffs with the flipped cases linked: capability-suite pass rates, cost per case, p95 latency, output tokens, tool calls per case. The capability suite belongs here on purpose. The AI Evals FAQ by Husain and Shankar warns that passing 100% of evals suggests the system is not being challenged and that a 70% pass rate might indicate a more meaningful evaluation; a suite designed to sit near 70% will move by several points between identical runs, and gating on it turns hill-climbing work into merge friction. Braintrust's `eval-action` is one ready-made version of the comment: it posts score differences from the previous run with counts of improvements and regressions, and needs `pull-requests: write` permission.

## Noise floor and the limits of 200 cases

Run main against itself before trusting any statistical gate. Cases that flip between two identical runs are noise in the flip count, and the sign test treats them as signal. If 6 cases flip with no code change, a candidate with 9 broke and 2 fixed is a weaker result than its p-value says. Three responses, in order of preference: fix the source of nondeterminism if it is in your code (unordered retrieval results, timestamps in prompts); sample each case k times and score the majority; or exclude cases that flipped in either of the last two main-against-main runs and list them in the comment so someone fixes them.

Do not respond by setting temperature to 0 in CI. Miller's section on temperature is titled "Don't touch the thermostat!": lowering temperature to reduce variance moves the variance into the question-level means or adds bias, and in CI it also means the gate evaluates a configuration that production does not run.

Miller's power analysis says what a suite of this size can and cannot see. With a variance of paired differences of 1/9, detecting a 3-point change in the mean at 80% power and alpha 0.05 needs (1.96 + 0.84)^2 × (1/9) / 0.03^2 ≈ 969 questions, and the paper recommends at least 1,000 for new evals. At n = 198 with correlation 0.5, resampling each question 10 times lowers the minimum detectable effect from 13.2% to 7.5%. The Evals FAQ describes CI datasets as small, in many cases 100 or more examples. Put together: a CI regression suite detects concentrated regressions (several cases broken the same way), not a diffuse 2-point slide in average quality. The diffuse slide is the job of a larger suite run nightly or pre-release, and of the online evaluation in the next lesson.

## The gate policy, written down

The policy belongs in the repository next to the prompts, versioned, so a change to the gate is reviewed like a change to the code it guards. A version for a prompt repository with a support assistant:

```yaml
# evals/gate.yaml
hard:                      # any failure blocks; scored by code unless noted
  suites: [schema, must_refuse, pii_redaction, approval_required_tools]
  judged_cases: every generation must pass; each output judged 3 times, majority decides
statistical:
  suite: regression        # 220 cases, paired against main at the merge base
  metric: grounded_in_policy   # one gated metric
  test: exact one-sided sign test on flipped cases
  alpha: 0.05
  unstable: exclude cases that flipped in either of the last two main-vs-main runs
report_only: [capability_pass_rate, cost_per_case, p95_latency_ms, output_tokens, tool_calls]
schedule:
  per_pr: hard + statistical; cached generations; re-judge only changed outputs
  nightly: regression at 3 trials, capability suite, main-vs-main noise run
  pre_release: every suite, 3 trials, per model in the routing table
override: two approvals including an eval owner; reason and accepted risk recorded in the PR
retire: a suite that has passed every run for 60 days moves from per_pr to nightly
```

A gate in code, returning the lists a reviewer needs rather than only a verdict:

```python
from math import comb

def one_sided_p(broke, fixed):
    n = broke + fixed
    return sum(comb(n, i) for i in range(broke, n + 1)) / 2 ** n

def gate(base, cand, must_pass=frozenset(), unstable=frozenset(), alpha=0.05):
    ids = [i for i in base if i not in unstable]
    broke = [i for i in ids if base[i] and not cand[i]]
    fixed = [i for i in ids if cand[i] and not base[i]]
    hard = sorted(i for i in must_pass if not cand[i])
    p = one_sided_p(len(broke), len(fixed)) if broke else 1.0
    ok = not hard and p >= alpha
    return ok, {"hard": hard, "broke": broke, "fixed": fixed, "p": round(p, 4)}

base = {f"c{i}": i >= 30 for i in range(200)}           # 170 pass
cand = dict(base, **{f"c{i}": False for i in range(30, 39)}, c0=True, c1=True)
print(gate(base, cand))   # blocks: 9 broke, 2 fixed, p = 0.0327
```

"Cases c30 to c38 broke" sends a reviewer to nine transcripts. "p = 0.0327" sends them nowhere.

## What the gate costs

Eval cost scales with cases × (generations + judge calls) × trials × runs. Take the policy above with 220 regression cases, one generation and two judge calls each, one trial per PR, 40 pull-request pushes a day: 220 × 3 × 40 = 26,400 calls a day before the hard tier or nightly runs. The levers are the ones used on any slow suite. Cache generations keyed by prompt, model, parameters and input, so a change to one of six templates regenerates only the cases that use it; promptfoo reads the cache location and TTL from `PROMPTFOO_CACHE_PATH` and `PROMPTFOO_CACHE_TTL`, and Braintrust's action routes calls through a caching proxy by default. Re-judge only outputs whose text changed. Run judges per PR only for the gated metric. The FAQ's rule for frequency is cost to run, saturation and the value of the error caught, and it advises favouring assertions over judges in CI.

A cache keyed without the model version is a correctness bug, not a cost win: a model upgrade will show zero flips because nothing was regenerated.

## Tooling, as of 2026-10-28

The choice of runner matters less than the gate logic, but the landscape changed this year. OpenAI announced on 2026-03-09 that it would acquire Promptfoo and integrate it into its Frontier platform; Promptfoo's own site now says it is part of OpenAI and remains open source. OpenAI's Evals platform becomes read-only on 2026-10-31 under the deprecation announced on 2026-06-03, shuts down on 2026-11-30, and the migration guide points to Promptfoo. Langfuse joined ClickHouse in January 2026 with no planned licensing changes. Braintrust and LangSmith remain hosted options with CI integrations.

Two consequences for the design. Keep the gate statistic in your own code, reading the runner's JSON output, so swapping runners changes an adapter rather than the policy. And when the gate compares models from several providers, a runner owned by one of them is a neutrality question someone will raise in review; owning the statistic and the case data answers most of it.

## When this is wrong

The sign test assumes cases are independent and equally important. Near-duplicate cases, or many cases drawn from one conversation, make a regression look more significant than it is; Miller reports clustered standard errors more than three times the naive ones on DROP, where questions share passages. Deduplicate before gating, or count flips per cluster.

The test throws away the non-flipped cases, so it says nothing about how much better or worse the candidate is, only whether the flips are lopsided. A change that fixes 30 cases and breaks 10 passes the gate, and the 10 still need a reviewer.

With few flips the test has little power. Two broken cases and no fixes happen by chance a quarter of the time. If those two cases matter, they belong in the hard tier, which is the reason the tiers exist.

The regression suite only covers failures someone has already seen. A green gate says the change did not break what the team knows about; the next failure comes from traces nobody has read yet.
