## Two metrics, two promises

Run each task k times. pass@k is the probability that at least one of the k trials succeeds; pass^k, introduced for agents by tau-bench, is the probability that all k succeed. They answer different questions. pass@k asks whether the agent can do the task at all, which is the right question when something downstream picks the good attempt: a test suite, a reviewer, a verifier. pass^k asks whether it does the task every time, which is the question for an agent a customer runs again and again with nobody checking each run.

The CI analogy is a retry policy against a flake detector: retrying a test three times turns a 75% test green almost always, while running it until it fails exposes it. The difference is that a flaky test is a defect you remove, whereas run-to-run variance is a property of every agent, and the metric has to price it rather than hide it.

With one success rate p for every trial and independent trials, pass@k = 1 − (1 − p)^k and pass^k = p^k. Anthropic's guide uses p = 0.75 and k = 3: (0.75)^3 is about 42%. Move the sliders to see how fast the two separate.

At p = 0.9 and k = 8, pass^8 = 0.9^8 = 0.430: an agent that succeeds nine times in ten fails at least once in 57% of eight-run sequences, while its pass@8 rounds to 100%. The same agent reads as solved or as unreliable depending on which promise the number stands for.

## Estimating both from trials

Suites do not have one p. Estimate each task from n trials with c successes, then average over tasks. The Codex paper (Chen et al., 2021) gives the unbiased pass@k estimator, 1 − C(n − c, k) / C(n, k), drawn from n = 200 samples per problem for k up to 100, and shows in its appendix that plugging the observed rate into 1 − (1 − p̂)^k is biased. tau-bench uses the matching form for pass^k: C(c, k) / C(n, k), the chance that k trials drawn without replacement from the n are all successes. Both need n ≥ k.

<p>C(8, 4) / C(10, 4) = 70 / 210 = <b>33.3%</b>. Plugging the observed rate into p^k gives 0.8^4 = 41.0%, which overstates it: the shortcut treats the 0.8 as known exactly, while the estimator accounts for drawing 4 of the 10 trials that actually happened. At n = k the estimate is 1 if every trial passed and 0 otherwise, so a task needs well over k trials before its pass^k estimate is more than a single bit.</p>
</Predict>

Averaging per task matters as much as the estimator. Three tasks with 10, 7 and 3 successes in 10 trials have per-task pass^3 of 1, 35/120 = 0.292 and 1/120 = 0.008, an average of 0.433. Pooling the 30 trials into a rate of 20/30 and cubing it gives 0.296, a third too low, because pooling pretends every task is equally flaky. Reliability is lumpy: some tasks always pass, some never do, and the middle is where the work is. BrowseComp measured the shape directly: over 64 trials per question, Deep Research solved 16% of the 1,266 questions every time and 14% never.

## Published numbers and their conditions

tau-bench's headline is the drop. gpt-4o with function calling reached pass^1 of 61.2% in retail and 35.2% in airline in June 2024, and its retail pass^8 was under 25%: an agent that resolves most tasks on a single run resolves fewer than a quarter of them on eight runs in a row. Main results use at least three trials per task; the paper's task-difficulty analysis ran more than 40 gpt-4-turbo trials per retail task. tau2-bench runs each task four times at temperature 0, and reports that telecom pass^k falls faster with k than airline does. Temperature 0 does not make an agent deterministic: the simulated user, tool timing and provider-side nondeterminism still vary between trials.

The Codex paper shows the other side, and the condition under which pass@k is honest. Codex-12B solved 28.8% of HumanEval's 164 problems with one sample and 70.2% with 100. That 70.2% is only reachable if something picks the right sample. For Codex-S, choosing the sample with the highest mean log-probability of 100 solved 44.5%, while choosing the sample that passed the unit tests solved 77.5%. pass@k is a real capability when a verifier is in the loop, and you pay for k attempts each time.

## How many trials, and how many tasks

The budget is tasks × trials, and the two buy different things. Trials per task narrow each task's estimate and must be at least k. Tasks narrow the suite-level number, and on small suites the task sample dominates. A 50-task suite run once per task at 60% has a 95% half-width of 1.96 × √(0.6 × 0.4 / 50) = 13.6 points. tau-bench's airline domain has 50 tasks.

A bootstrap over tasks shows it for pass^k, using a toy suite of 50 tasks with 8 trials each:

```python
from math import comb
import random

def pass_hat_k(n, c, k):
    return comb(c, k) / comb(n, k)

def pass_at_k(n, c, k):
    if n - c < k:
        return 1.0
    return 1.0 - comb(n - c, k) / comb(n, k)

# successes out of 8 trials for each of 50 tasks (toy data)
suite = [8] * 20 + [7] * 8 + [6] * 6 + [4] * 6 + [2] * 5 + [0] * 5
for k in (1, 2, 4, 8):
    hat = sum(pass_hat_k(8, c, k) for c in suite) / len(suite)
    at = sum(pass_at_k(8, c, k) for c in suite) / len(suite)
    print(k, round(hat, 3), round(at, 3))
# 1 0.715 0.715 / 2 0.614 0.816 / 4 0.507 0.877 / 8 0.4 0.9

rng = random.Random(7)
def interval(k, B=2000):
    vals = sorted(sum(pass_hat_k(8, c, k) for c in (rng.choice(suite) for _ in suite)) / 50
                  for _ in range(B))
    return round(vals[int(0.025 * B)], 3), round(vals[int(0.975 * B) - 1], 3)
print(interval(1), interval(8))
# (0.618, 0.81) (0.26, 0.54)
```

pass^1 is 71.5% with an interval about 19 points wide; pass^8 is 40% with an interval 28 points wide, and pass@8 is 90%. This bootstrap resamples tasks and keeps each task's successes fixed, so it understates the uncertainty; resampling trials within each task as well widens it further. The five tasks at 0 of 8 deserve a transcript read before anything else: Anthropic's guide says a 0% rate over many trials most often means a broken task.

Two consequences for planning. Comparing two configurations is a paired comparison over the same tasks, which is far tighter than comparing two suite-level intervals; the per-task view also names the tasks that moved. And k is a product parameter, not a statistical one: it is the number of times a user relies on the same flow before one failure costs the trust or the money you care about. Choose it from the product, then buy at least 2k trials for the tasks that matter so each per-task estimate is more than a pass-or-fail bit.

## Which one gates the release

pass^k gates any agent whose runs users see one at a time: support, operations, anything that moves money. pass@k gates only when a verifier you trust selects among attempts in production, and then the gate also carries the cost of k attempts and the verifier's own false-accept rate. Report both, because the gap between them is the variance budget: a configuration that raises pass@k while lowering pass^k has become less predictable, which is a regression for a customer-facing agent even when the headline improves.

## When this is wrong

Both estimators assume trials are independent draws. They often are not: cached responses, a fixed seed, or state left behind by an earlier trial make runs more alike than real use, and pass^k comes out optimistic. Anthropic's guide insists on a clean environment per trial for this reason. The reverse also happens: real repeats are not identical prompts, so a pass^k measured on one phrasing of a task says nothing about sensitivity to the paraphrases users actually send. Vary the simulated user's phrasing across trials if the claim is about users rather than about sampling.

An unweighted average over tasks treats a rare edge case and the most common request as equally important. A gate built on production traffic weights each task by how often its kind of request arrives, and reports the unweighted number beside it so the rare cases stay visible.

And success is binary here. A run that resolved two of three requests counts as a failure in pass^k, which is right for a gate and wasteful for diagnosis; keep the sub-scores underneath the binary verdict.
