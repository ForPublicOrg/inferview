## What the grader reads

Every agent trial leaves three things a grader can read: the final messages to the user, the transcript of turns and tool calls, and the state of the systems the agent touched. Anthropic's January 2026 guide to agent evals calls the last one the outcome and gives the gap in one line: a flight-booking agent can say "Your flight has been booked" while no reservation exists in the database. The message is the agent's claim. The state is the fact.

The rule for this module: grade the end state wherever one exists, and grade the path only where the path is itself the requirement. The analogy is an integration test that asserts on database rows rather than on the order of calls to mocks. The difference is twofold. An agent's implementation changes on every run, so a check pinned to one call sequence fails correct runs. And some agent actions cannot be undone, so for those actions the order of calls is the requirement, not an implementation detail.

## State checks: tau-bench and tau2

tau-bench (June 2024) made the state check the core of its reward. Each task has one ground-truth database, the one outcome its domain policy allows. A trial scores 1 only if the final database equals it and the agent's replies contain every required piece of information, such as the amounts "54.04" and "41.64" in the paper's example. The reward is the product of the two checks, so a run that writes the right rows and tells the user the wrong figure fails, and so does a run that quotes the right figure and writes nothing. Retail has 115 tasks and airline 50, with gpt-4-0613 playing the customer.

Comparing whole databases has two consequences. The grader is order-independent: any sequence of tool calls that ends in the goal state passes, so looking up the order before the customer profile costs nothing. And it is single-outcome: the task author must write down the one state the policy allows, which is expensive work and the place where task bugs live. Anthropic reports that Claude Opus 4.5, on a tau2-bench flight task, found a loophole in the airline policy that served the user better than the reference outcome, and failed the task as written. An equality check cannot tell a better outcome from a wrong one.

tau2-bench (June 2025) adds dual control. In its telecom domain the customer also has tools, acting on a simulated phone, and the agent can only ask the customer to use them. Telecom success is judged by assertion functions over state, including the state of the user's device: "no mobile data" is fixed when the device says it is. The tasks come from a compositional generator that produced 2,285 of them; the paper evaluates a balanced subsample of 114, runs each four times at temperature 0, and uses gpt-4.1-2025-04-14 as the customer. Shared control has a measured price. gpt-4.1's pass^1 is 74% in retail and 56% in airline but 34% in telecom, and moving from a mode where the agent operates every tool itself to the default dual-control mode costs gpt-4.1 18 points and o4-mini 25.

The simulated customer is part of the grader. tau2 audited its own simulator: in airline, 13 of 100 conversations had an error the paper classes as critical and 47 had some error; retail had 6 critical of 50, telecom 3 of 50. When the customer misstates their booking, the trial's verdict says something about the simulator, not the agent. Budget for reading failed transcripts with that in mind.

## Trajectory checks: where the path is the requirement

State equality misses everything that happened on the way to the right state. A refund agent that issues the correct refund without verifying the caller leaves the same database as one that verified first. The violated rule is about order, and only the transcript shows it. The path is the requirement in three cases:

- Forbidden actions: a tool the agent must never call in this context, or a call with arguments outside policy, such as a refund above the agent's limit.
- Preconditions on irreversible actions: identity verified, eligibility checked or approval recorded before the refund call.
- Budgets on turns, tool calls and tokens, because an agent that reaches the goal in 40 calls is a different product from one that takes 6.

Anthropic's refund example combines all three kinds of check: state (ticket resolved, refund processed), a tool-call assertion that `process_refund` is called with an amount of at most 100, a limit of 10 turns, and an LLM rubric for tone and for grounding replies in the fetched policy.

Write trajectory checks as invariants over the trace, in the shape of a property-based test, rather than as a match against a reference run. Reference matching is available off the shelf: LangChain's agentevals compares a run with a reference trajectory in strict, unordered, subset and superset modes, where subset asserts that the agent called no tool beyond the expected ones. Subset is a cheap forbidden-action check when the reference lists every allowed tool. Strict mode fails every correct run that takes a different route, which is the brittleness behind Anthropic's advice to grade what the agent produced rather than the path it took.

## Diagnosis is a separate job

A gating grader gives you a rate. It does not tell you where runs break, and the transcript's second use is diagnosis, which never gates. Husain and Shankar's evals FAQ orders the work: end-to-end task success first, with the agent as a black box, then step-level diagnostics of tool choice and argument extraction. For multi-step pipelines it recommends a transition failure matrix: for each failed trace, record the last state that succeeded and the state of the first failure, and count the pairs. In its text-to-SQL example, failures between generating SQL and executing it number 12, against 2 between choosing a tool and planning a calendar action. The FAQ also fixes the trace boundary for agents that hand off to people: the trace runs until the user's need is resolved or the session ends, not until the handoff, because handoffs that come too early, too late or without context are where many failures sit.

tau-bench's own failure analysis shows why the first pass over failures is a task audit. Of gpt-4o's 40 failed retail trials (one trial per task), 4 came from typos or ambiguity in the simulated user's instructions, which are task bugs. Of all failures, the paper attributes 25% to wrong decisions about domain rules and 19% to partially resolving compound requests.

## Cost is part of the score

Two agents with the same pass rate are different products if one costs three times as much per task. tau-bench published its costs: the gpt-4o agent cost $0.38 per retail task and the gpt-4 user simulator $0.23, and input tokens were 95.9% of the agent's cost. At a pass^1 of 61.2%, the agent's cost per resolved task is 0.38 / 0.612 = $0.62. The simulator's $0.23 is eval spend, not product cost; it belongs in the eval budget and never in the unit economics. Report, for each configuration, success under the full gate, cost per trial and cost per successful trial, with turns and tool calls beside them, since a regression that doubles tool calls usually shows there before it moves the pass rate.

## Designing the eval for a refund agent

Start with the task set. Anthropic suggests 20 to 50 tasks drawn from real failures as a first suite, taken from support queues and bug reports. Include tasks where the correct end state contains no refund: an ineligible order, a caller who cannot be verified, an amount above the agent's authority where the right outcome is an escalation ticket. The same guide warns that one-sided evals produce one-sided optimisation; a suite of refundable cases only rewards an agent that refunds everything.

Then the checks, each with a decision about whether it gates:

Two harness requirements make the numbers mean anything. Each trial starts from a fresh database: Anthropic saw Claude gain an unfair advantage by reading git history left by earlier trials, and the refund equivalent is a refund row from trial one that trial two's duplicate check finds. And multi-part tasks get partial credit recorded underneath the binary verdict, as Anthropic recommends: an agent that verified the caller and found the order but never refunded is better than one that failed at the first step, and the sub-scores show which.

The grader for one trial, with the invariants as plain code:

```python
def grade(trial, goal):
    calls = trial["calls"]                       # [(tool, args), ...] in call order
    names = [tool for tool, _ in calls]
    state_ok = trial["refunds"] == goal["refunds"] and trial["ticket"] == goal["ticket"]
    said_ok = all(s in trial["final_message"] for s in goal["must_say"])
    violations = []
    for i, (tool, args) in enumerate(calls):
        if tool == "process_refund":
            if "verify_identity" not in names[:i]:
                violations.append(f"step {i}: refund before identity check")
            if args["amount"] > goal["cap"]:
                violations.append(f"step {i}: refund {args['amount']} above cap {goal['cap']}")
    if len(calls) > goal["max_calls"]:
        violations.append(f"{len(calls)} tool calls, budget {goal['max_calls']}")
    return {"pass": state_ok and said_ok and not violations,
            "state_ok": state_ok, "said_ok": said_ok, "violations": violations}

goal = {"refunds": [("A-1001", 42.50)], "ticket": "resolved",
        "must_say": ["42.50"], "cap": 100, "max_calls": 8}
trial = {"calls": [("get_order", {"id": "A-1001"}),
                   ("process_refund", {"order": "A-1001", "amount": 42.50}),
                   ("verify_identity", {"customer": "C-7"}),
                   ("close_ticket", {"status": "resolved"})],
         "refunds": [("A-1001", 42.50)], "ticket": "resolved",
         "final_message": "Refunded 42.50 to your card."}
print(grade(trial, goal))
# {'pass': False, 'state_ok': True, 'said_ok': True,
#  'violations': ['step 1: refund before identity check']}
```

The state check passes and the trial fails, which is the case the state-only grader cannot see. The invariant is a predicate over the call list, so it accepts any order of lookups and any number of retries of `get_order`.

## When this is wrong

Some agents leave no state to check. A research agent's output is an answer, and an advice agent's is a recommendation; the outcome check falls back to exact match where the answer is short and to a validated judge where it is not, which is a different and weaker instrument.

Equality against one goal state assumes the policy allows one outcome. The Opus 4.5 loophole is the counterexample: a better outcome fails. Where several states are acceptable, write the goal as a set of predicates over the state (refund exists, amount at most the eligible total, ticket closed) rather than a snapshot, and read every failure where the agent's state differs from the reference but satisfies the user.

Trajectory invariants catch the violations someone wrote down. A novel unsafe path, such as refunding through a store-credit tool nobody listed, passes every invariant. That is a reason to keep reading transcripts, and a reason to put the rule in the tool where you can: an invariant enforced by the refund service holds for every path, while one enforced by the grader only describes the paths you tested.
