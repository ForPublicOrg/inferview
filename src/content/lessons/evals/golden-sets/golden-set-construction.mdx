export const solution = String.raw`import json, re

STATUSES = {"answered", "absent", "declined"}

def check(output, case):
    """Return failure strings for one golden-set case; an empty list means the output passes."""
    try:
        data = json.loads(output)
    except json.JSONDecodeError as e:
        return ["not valid JSON: %s" % e.msg]
    if not isinstance(data, dict):
        return ["not a JSON object"]
    failures = []
    status = data.get("status")
    if status not in STATUSES:
        failures.append("unknown status %r" % (status,))
    elif status != case["expect"]:
        failures.append("expected %s, got %s" % (case["expect"], status))
    cites = data.get("citations", [])
    if not isinstance(cites, list):
        failures.append("citations is not a list")
        cites = []
    cited = []
    for c in cites:
        doc = c.get("doc") if isinstance(c, dict) else None
        clause = c.get("clause") if isinstance(c, dict) else None
        text = case["docs"].get(doc, {}).get(clause)
        if text is None:
            failures.append("cites missing clause %s %s" % (doc, clause))
        else:
            cited.append(text)
    if status == "answered" and not cites:
        failures.append("answered without a citation")
    answer = data.get("answer", "")
    if not isinstance(answer, str):
        failures.append("answer is not a string")
        answer = ""
    for date in re.findall(r"\d{4}-\d{2}-\d{2}", answer):
        if not any(date in t for t in cited):
            failures.append("date %s not in a cited clause" % date)
    return failures
`;

## A golden set is a designed sample

A golden set answers one question: does this system still handle the failure modes we know about? That makes it a designed sample, not a random one. A uniform draw from traffic reproduces the traffic mix, which suits estimating production quality and fails at exposing known failures, because the expensive failures sit in thin slices of traffic. Each row exists because it defends a named failure mode or a behaviour that must not regress; a row nobody can attach to one is noise in the pass rate.

Anthropic's January 2026 guide to agent evals puts a good start at 20 to 50 simple tasks drawn from real failures, and Husain and Shankar's FAQ describes purpose-built sets that often grow to 100 or more examples. Neither is a statistical target.

## Strata: intent crossed with expected outcome

Stratify on intent, what the user asks the system to do, and on expected outcome, which for most assistants includes at least "answer", "say the thing does not exist" and "decline or hand off". Anthropic's guide warns against skipping the second axis: test where a behaviour should occur and where it should not, because a one-sided set optimises for one side. A set where every question has an answer rewards a system that always answers.

The reason to stratify instead of sampling uniformly is arithmetic.

<p>Each draw misses the slice with probability 0.98, so the chance of missing it 100 times is 0.98<sup>100</sup> = 0.133, about <b>13%</b>. Even when it appears, the expected 2 cases move its pass rate in steps of 50 points. Designed allocation has a cost: the overall pass rate no longer estimates production quality. Report per stratum, and for a production estimate weight each stratum's pass rate by its traffic share. Say a set holds 60 lookup questions, 60 absent-clause questions and 60 cross-document questions, passing 95%, 50% and 60% of them. The unweighted pass rate is (57 + 30 + 36) / 180 = 68.3%. If traffic is 70% lookups, 10% absent-clause and 20% cross-document, the weighted estimate is 0.70 × 0.95 + 0.10 × 0.50 + 0.20 × 0.60 = 83.5%. Both are correct answers to different questions, and the weights come from production, since synthetic data cannot tell you how common a failure is.

## Where the rows come from

**Production traces.** The FAQ lists sampling methods from random through clustering, outliers and classifier flags to negative user feedback, and recommends keeping some random traces in every batch, because feedback only surfaces failures users report and targeted sampling only finds what you already suspect. The pipeline from logs to candidate cases is in [LLMOps data curation](/learn/llmops/data-curation). A trace earns a row when error analysis attached a failure category to it, or when it is a success in a stratum that would otherwise have none.

**Expert-written cases.** For thin strata, a domain expert writes the input and the expected properties. Anthropic's test for whether a task is well specified: two domain experts would independently reach the same pass or fail verdict. A case that fails that test measures the labeller, not the system.

**Synthetic inputs with a filter.** The FAQ's procedure: name the dimensions (for a contract assistant, question type, document type and number of documents), write about 20 tuples by hand, generate more tuples, then turn each into a question in a separate prompt, which avoids the repetitive phrasing of one-shot generation. The filter is a person reading every generated case and running it through the real system. The FAQ lists complex domain documents and high-stakes domains among the places synthetic data is unreliable, and contracts are both: generation fills cells, it does not replace the lawyer.

**Adversarial cases.** Instructions embedded in contract text, a clause numbered twice, an exhibit with OCR errors: these come from the threat model, not traffic.

## What a row holds

A row is the input, the exact document versions it runs against, and the properties a correct output must have or must not have. Properties beat reference strings: "cites MSA 9.1", "contains no date absent from the cited clauses". Anthropic also recommends a reference solution per task, an output known to pass every grader, and notes that a 0% pass rate across many trials more often signals a broken task than an incapable agent.

Grade each property as pass or fail. Binary labels are more consistent across labellers than Likert scales, a point both the FAQ and the 2024 applied-LLMs report make, and the FAQ's headline is a pass-all rate with drill-down to each check, not a weighted composite nobody can invert into a failure.

## Level one: assertions that run on every change

The cheapest checks are code. The applied-LLMs report recommends assertion tests built from production samples, with at least three criteria per sample, run on any change to the pipeline, and Anthropic's guide prefers deterministic graders where possible. Whatever code can decide is decided before a judge sees the output, because a judge is slower, costs money per case and needs its own validation (see the [judge module](/learn/evals/llm-judge)).

## A 20-question set for a contract assistant

The module's running case is the first set for an in-house contract question-answering assistant. One defensible allocation:

| Slice | Cases | Expected outcome | Failure it defends |
|---|---|---|---|
| Single-clause lookup | 4 | answered, cites one clause | wrong clause cited, paraphrase changes meaning |
| Clause absent from every document | 4 | absent | confident answer about a clause that is not there |
| Cross-document (MSA against order form) | 3 | answered, cites both | precedence ignored, only one document read |
| Amendment supersedes base clause | 2 | answered, cites the amendment | stale clause quoted |
| Date arithmetic (notice deadline from renewal date) | 2 | answered with a computed date | invented or miscomputed date |
| Where a term is defined | 2 | answered, cites the definition | definition confused with first use |
| Request for legal advice ("should we sign") | 2 | declined, hands off | advice given outside scope |
| Instruction embedded in contract text | 1 | answered, instruction ignored | injected instruction followed |

Six of the 20 expect "absent" or "declined", so a system that always answers fails at least 6 before any quality question arises. The injected-instruction slice has one case because it only shows the defence exists; how often it holds is a red-team measurement.

Twenty cases support per-case review, not rates. At a true pass rate of 85% the 95% interval half-width is 1.96 × √(0.85 × 0.15 / 20) = 15.6 points, so this set detects a slice that broke, not a three-point regression. Sizing for regressions is done in the [CI gates module](/learn/evals/evals-in-ci).

## Versioning the set with its scores

The set lives in version control, changes go through review, and every score carries the set version it was computed on, because of the denominator. Add 30 hard cases to a 200-case set that scored 182, and suppose 6 of the new cases pass: the score moves from 182/200 (91.0%) to 188/230 (81.7%) with no change to the system. Scores on a changed set may not be comparable with older ones, which the FAQ accepts; a trend line crossing a version boundary without a marker is not acceptable. Re-run the production configuration on the new version and start a new baseline.

Labels go stale when a policy or contract template is replaced, and coverage goes stale when a new document type arrives. Each error-analysis round adds rows for new failure categories, and on a schedule someone re-reads a sample of rows against current documents and retires those whose labels no longer hold. A set that passes everything gives no new information: in Anthropic's lifecycle, capability suites start at a low pass rate, regression suites sit near 100%, and a capability task that passes reliably graduates into the regression suite.

## When this is wrong

Stratification assumes you already know the failure modes. A new model or document type brings failures no stratum anticipates, and the set passes while production degrades, which is why it is paired with error analysis on fresh traces and with online evaluation.

Properties assume a correct output can be described. For drafting and summarisation there may be no property list short enough to check, and the set shifts toward pairwise comparison against the previous version with a validated judge.

The set also leaks into the prompt tuned against it; a held-out slice that nobody iterates on is the check, and the [contamination lesson](/learn/evals/golden-sets/contamination) covers it.
