## Two halves, measured separately

A RAG system fails in the retriever or in the generator, and the fixes belong to different code and often different people. The metric set therefore splits the same way. Retrieval metrics compare a ranked list with relevance labels and need no model at evaluation time. Generation metrics in the RAGAS family run an evaluator model that extracts claims, generates questions or judges relevance, so every one of them inherits that model's error rate and needs the validation covered in the [judge module](/learn/evals/llm-judge).

The decision this lesson ends on is the minimum set for a release gate. Each metric earns a place by answering a question the others cannot, and loses it when the failure it would catch is already caught more cheaply.

## Retrieval: the labels are the hard part

Three metrics cover nearly every retrieval question. Recall@k asks whether the evidence reached the context window, and for a generator that reads all k chunks it is the one that matters: a document outside the window cannot be used, and reranking cannot recover a document the first stage never returned. Reciprocal rank, averaged over queries as MRR, asks how far down the first relevant result sits, which matters when a person or a downstream step reads only the top. nDCG@k discounts each relevant result by log2 of its position and divides by the best possible ordering; it is the only one of the three that uses graded relevance.

BEIR's authors chose nDCG@10 as the single metric for 18 datasets on that basis: precision and recall ignore rank, and MRR and MAP cannot use graded judgements. That reasoning applies to a leaderboard that must compare systems across tasks. For a RAG gate with a fixed window it is weaker, because rank inside the window matters only as much as the generator is sensitive to position, which you measure on your own system instead of assuming.

That second point is the failure retrieval metrics hide most often. Labels are built by pooling: annotators judge the documents some set of systems returned, and every document outside the pool counts as irrelevant. BEIR measured what that does on TREC-COVID, whose pool came from many participating systems. The share of each system's top 10 that annotators had never seen (Hole@10) was 6.4% for BM25 and 2.8% for docT5query, but 14.4% for ANCE and 31.8% for TAS-B, two dense retrievers. After the authors judged the 980 missing query-document pairs, BM25's nDCG@10 moved from 0.656 to 0.668 and docT5query's from 0.713 to 0.714, while ANCE rose from 0.654 to 0.735 and TAS-B from 0.481 to 0.555. Before the holes were filled ANCE looked slightly worse than BM25; after, it was 6.7 points better.

The same thing happens to a golden set whose relevance labels were collected from the BM25 system in production: the dense or hybrid replacement retrieves documents nobody judged, and the metric reports a regression that may be an improvement. The defence is to report the hole rate beside every retrieval metric and to judge new top-k documents before a comparison is accepted.

```python
import math

def retrieval_metrics(ranked, qrels, k):
    """ranked: doc ids, best first. qrels: {doc_id: grade}, grade 0 means judged not relevant.
    Documents missing from qrels are unjudged; they count as not relevant, and the hole rate says how many."""
    top = ranked[:k]
    relevant = {d for d, g in qrels.items() if g > 0}
    if not relevant:
        return {"recall": None, "rr": None, "ndcg": None, "holes": sum(d not in qrels for d in top) / k}
    hits = [d for d in top if d in relevant]
    rr = next((1 / (i + 1) for i, d in enumerate(top) if d in relevant), 0.0)
    dcg = sum(qrels.get(d, 0) / math.log2(i + 2) for i, d in enumerate(top))
    ideal = sorted((g for g in qrels.values() if g > 0), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 2) for i, g in enumerate(ideal))
    return {"recall": len(hits) / len(relevant), "rr": rr, "ndcg": dcg / idcg,
            "holes": sum(d not in qrels for d in top) / k}

qrels = {"d2": 1, "d4": 1, "d8": 1, "d7": 0, "d9": 0}
print(retrieval_metrics(["d7", "d2", "d9", "d4", "d1"], qrels, 5))
# {'recall': 0.666..., 'rr': 0.5, 'ndcg': 0.498..., 'holes': 0.2}
```

The `None` branch is deliberate. A question about a clause that does not exist has no relevant documents, so recall is 0/0. Decide in the harness what such a query contributes (it is excluded from retrieval metrics and scored only on the answer's abstention) rather than letting a library's default decide. The previous lesson put four such cases in a 20-case set; silently scoring them as 0 or 1 moves recall by up to 20 points.

## Generation: what the RAGAS definitions measure

RAGAS (the paper is from 2023; the library's latest release on PyPI is 0.4.3 from January 2026, and the repository now lives at vibrantlabsai/ragas) defines the metrics most teams start with. Each measures less than its name suggests, and the definitions are short enough to hold exactly.

**Faithfulness** is the number of claims in the response that the retrieved context supports, divided by the total number of claims. An evaluator model extracts the claims and verifies each one. The documentation's example answer has two claims, one supported, and scores 0.5. It measures support by the retrieved context, not truth: when retrieval returns a superseded version of a contract, a faithful answer is faithfully wrong, and the score is 1.0.

**Answer relevancy** has the evaluator generate questions from the response (three by default) and averages the cosine similarity between their embeddings and the user's input. The documentation says directly that it does not consider factual accuracy. It also depends on the embedding model: the paper used text-embedding-ada-002, the current documentation's example uses text-embedding-3-small, and a score computed with one is not comparable with a score computed with the other.

**Context precision** at K sums precision@k at each position holding a relevant chunk and divides by the number of relevant chunks in the top K, so it rewards ranking relevant chunks first. The ID-based variant with the same name is the share of retrieved ids that appear in the reference ids, which ignores rank entirely. Two dashboards both labelled "context precision" can be reporting different quantities.

**Context recall**, in its LLM-based form, splits a reference answer into claims and counts how many the retrieved context supports. It needs a reference, so it runs offline on the golden set. The documentation's own example shows how the evaluator can fill gaps: the retrieved context is "Paris is the capital of France.", the reference is "The Eiffel Tower is located in Paris.", and the output is 1.0, although the context never mentions the tower. The judge supplied the link from its own knowledge, which is the opposite of what a recall metric is for.

The paper's validation is the reason to treat these as instruments needing calibration rather than ground truth. On WikiEval, 50 questions built from Wikipedia pages about events from 2022 onward, the RAGAS metrics agreed with human pairwise judgements 95% of the time on faithfulness, 78% on answer relevance and 70% on context relevance, with gpt-3.5-turbo-16k as the evaluator. Fifty items, one evaluator model, encyclopedic text: none of those conditions match a contract assistant, so the agreement on your data is unknown until you measure it.

## Averages hide the answer that matters

Continuous scores averaged over a set hide the distribution. Take 100 answers with a mean faithfulness of 0.95. If every answer has 20 claims and exactly one is unsupported, every answer scores 0.95 and every answer contains an unsupported statement. If 95 answers score 1.0 and 5 score 0.0, the mean is the same and 95 answers are clean. For a legal assistant the first product is unshippable and the second may be fine, and the mean cannot tell them apart.

The fix is the one the FAQ recommends for every eval: turn each metric into a binary per-answer check and report the share that passes. "No unsupported claim" (faithfulness equal to 1.0 under a validated judge) is a check a lawyer can read; 0.95 is not. The same holds for retrieval: "every reference clause is in the window" per question, reported as a rate per stratum, is more useful in review than mean recall.

## The minimum set for a RAG release

| Check | Question it answers | Gate or diagnostic |
|---|---|---|
| Level-one assertions (format, citations exist, dates appear in cited text) | Is the output well formed and are its citations real? | Gate, every case |
| Recall@k per question, k equal to the chunks actually placed in the prompt, with hole rate | Did the evidence reach the generator? | Gate per stratum; comparisons rejected while holes are unjudged |
| No unsupported claim, judged by a validated judge | Did the answer add anything the context does not support? | Gate |
| Golden-set properties, including absent and declined cases | Is the answer right, and does it abstain when it should? | Gate per stratum |
| MRR or nDCG | Is the best evidence near the top? | Diagnostic, unless a ranked list is shown to a person |
| Answer relevancy | Is the answer on topic? | Diagnostic only; it cannot see a wrong fact |
| ROUGE, BLEU, BERTScore, embedding similarity to a reference | Does the text resemble a reference? | Not used; the FAQ's verdict is that generic metrics used as quality measures create false confidence |

Four gates, each tied to a different failure. Faithfulness alone passes a confidently wrong answer from a stale document; the property checks catch it. Property checks alone cannot tell a retrieval miss from a generation error; recall separates them. Recall alone scores absent-clause questions as undefined; the abstention properties cover them.

## When this is wrong

The retrieval half assumes one retrieval call with a fixed window. Agentic RAG issues several searches, rewrites queries and reads selectively, so recall@k per call says little; the useful quantity is whether the evidence appeared anywhere in the trajectory, and that belongs with [agent evaluation](/learn/evals/agent-evals).

Long-context designs that put whole documents in the prompt shrink the retrieval question to document selection, and recall over chunks stops being meaningful. The generation half still applies, and faithfulness becomes harder to judge as the context grows, because the evaluator must find support across far more text.

Every generation metric here is a judge with a formula around it. When the judge model changes, the metric changes, even if the library version and formula do not. Pin the evaluator model and the embedding model together with the library, and re-validate after any change to them.
