## The bot is bad, says everyone

Scenario, not a real company: a property-search assistant has been live for six weeks. The head of product forwards three screenshots and writes "it feels worse since the prompt change". Support says customers complain about wrong viewing dates. The founder asks for "an accuracy number by Friday". Nobody can say what accuracy would mean here, and there is no eval suite, only a folder of prompts and a dashboard of request counts.

The tempting move is to pick a metric off the shelf, wire up a judge that scores helpfulness from 1 to 5, and report the average. That number can rise while customers get angrier, because it measures something nobody chose on purpose. The move that works is slower and much less glamorous: open the logs, read what the assistant actually did, and write down what went wrong in plain words. Treat every eval you build as something that starts life as a note written while reading a trace.

<Callout kind="interview" label="Interview tip">
"The bot is live and stakeholders say it is bad. Where do you start?" shows up in public interview guides in several wordings. Say "I would read traces" before you say the word "metric".
</Callout>

## Crash reports before regression tests

You already know this loop from ordinary software. When a service starts failing in production, you do not begin by writing a test suite. You read crash reports and logs, group them by stack trace, fix the most common cause, and only then write a regression test so that cause never comes back. The tests encode failures you have already seen.

Evals for LLM systems are the same loop with one difference: there is no stack trace. A bad answer is a 200 OK with fluent text in it. The grouping step, which a crash reporter does for you by hashing stack frames, you have to do by hand, by reading. That is error analysis, and it has three steps.

**Open coding.** Take a sample of real traces (the full record of one request: input, retrieved context, tool calls, output). For each one, write a short free-text note about the first thing that went wrong, or "fine". Do not use a predefined list of categories. The note for a trace might be "said the viewing is Tuesday, listing says Wednesday" or "promised a refund it has no authority to give".

**Axial coding.** Read your notes back and cluster them into categories: `wrong_date`, `ignored_policy`, `hallucinated_listing`, `tone`. Rename and merge as you go. This is where the notes turn into a taxonomy specific to your product, which no off-the-shelf metric will hand you.

**Count.** Tally the categories. Now you have a ranked list of what is actually broken, with real examples attached to each. That list is your eval plan.

Two rules from practitioners make the reading go better. In a multi-step trace, record the *first* upstream failure, because later errors often follow from it: if retrieval fetched the wrong listing, the wrong date downstream is a symptom. And if you use an agent or a model to help read traces at scale, annotate the first 30 yourself before you let it propose categories, so its guesses do not shape what you see. Both come from the AI Evals FAQ by Hamel Husain and Shreya Shankar, which this track leans on heavily.

## When do you stop reading?

The FAQ's guidance is to review at least 100 traces, and to keep going while you are still learning something. The stopping signal is saturation: new traces stop revealing new failure categories or changing your understanding of the old ones. It is the same signal qualitative researchers use when they stop interviewing.

<Callout kind="aside" label="Production reality">
Error analysis is not a one-off. The FAQ suggests at least 100 fresh traces per cycle, cycles every 2 to 4 weeks, and 10 to 20 traces a week in between. The authors also report spending 60 to 80% of their own development time on error analysis and evaluation. That is their experience on their projects, not a survey, but it tells you where the work is.
</Callout>

## Binary labels, not 1 to 5

When you turn a category into a check, make the check pass or fail. A Likert scale feels more nuanced, but the nuance is noise: two annotators disagree about the difference between a 3 and a 4, the same annotator drifts over a week, and everyone gravitates to the middle. A binary label forces a decision about one specific thing, such as "the viewing date matches the listing". If you want to see gradual progress, split the quality you care about into several binary sub-checks and track the pass rate of each.

The other thing binary labels force is a definition. You cannot label "date correct: yes or no" without deciding what correct means when the listing has two viewing slots. Researchers studying evaluation tools named this effect criteria drift: "users need criteria to grade outputs, but grading outputs helps users define criteria" (Shankar et al., 2024). Your definitions will change as you read. That is the process working, so version your rubric like code.

## From failure modes to checks

Each category from the count becomes one eval, and the cheapest check that can detect it wins. Hamel Husain's 2024 essay on evals describes three levels, which map neatly onto a testing pyramid:

- **Level 1, assertions.** Code that runs on every change: the date in the answer appears in the listing, the JSON parses, no phone numbers leak. Fast, deterministic, free.
- **Level 2, human and model review.** A labelled sample read by a person, and an LLM judge validated against those labels for the failures code cannot see, such as tone. Run on a cadence.
- **Level 3, A/B tests.** Real users, real outcomes, after significant product changes.

`wrong_date` is a Level 1 check: parse the date out of the answer and compare it with the listing record. `tone` needs Level 2. The promised refund can be a regex on refund language plus a judge for paraphrases. The next two modules build those checks; this one is about knowing which ones to build.

For multi-turn conversations, the FAQ suggests N-1 testing: take a real conversation, replay its first N-1 turns as fixed history, and test only the model's reply at turn N. You keep the realistic prefix a user actually produced and still get a repeatable test, which fully simulated users often fail to give you.

## What to log for every model call

None of this works if you cannot find the trace. Instrumentation for LLM systems is ordinary distributed tracing with a few extra fields, and the industry vocabulary for those fields is the OpenTelemetry GenAI semantic conventions. Three facts to have straight before an interview:

1. They are still marked **Development**, not Stable, and in June 2026 they moved to their own repository (`semantic-conventions-genai`); the main repository's GenAI pages read "Moved" from release v1.42.0 on 2026-06-12. Names have changed before and may change again.
2. The provider attribute is `gen_ai.provider.name`. The older `gen_ai.system` was deprecated in v1.37.0. If an interviewer hears `gen_ai.system`, they know when you last read the spec.
3. Prompt and completion **content is opt-in**. Attributes such as `gen_ai.input.messages` and `gen_ai.output.messages` may contain personal data, so instrumentations do not record them by default. There are `_ref` variants that store a URI to external storage instead of the content.

An inference span is named `{gen_ai.operation.name} {gen_ai.request.model}`, for example `chat some-model`. Agent frameworks add `invoke_agent`, `execute_tool` and `invoke_workflow` spans, so a multi-step run becomes a tree you can walk to find which tool call went sideways. Here is what I record per call, as a plain dict so it runs anywhere:

```python
def record_llm_call(model, resolved_model, prompt_version, input_tokens, output_tokens,
                    cache_read_tokens, duration_s, finish_reason,
                    price_in, price_out, price_cache_read):
    # Prices are USD per million tokens, read from the provider's price page on the day.
    # OTel says input_tokens SHOULD include cached tokens, so price the uncached part separately.
    uncached = input_tokens - cache_read_tokens
    cost = (uncached * price_in + cache_read_tokens * price_cache_read
            + output_tokens * price_out) / 1e6
    return {
        "name": "chat " + model,
        "gen_ai.operation.name": "chat",
        "gen_ai.provider.name": "example-provider",
        "gen_ai.request.model": model,
        "gen_ai.response.model": resolved_model,   # the dated version, not only the alias
        "gen_ai.usage.input_tokens": input_tokens,
        "gen_ai.usage.output_tokens": output_tokens,
        "gen_ai.usage.cache_read.input_tokens": cache_read_tokens,
        "gen_ai.response.finish_reasons": [finish_reason],
        "gen_ai.prompt.name": "support-answer",
        "gen_ai.prompt.version": prompt_version,
        "duration_s": duration_s,
        "app.cost_usd": round(cost, 6),            # app-specific, not a GenAI convention
    }

span = record_llm_call("example-model", "example-model-2026-01-01", "support-v14",
                       12000, 450, 10000, 2.4, "stop",
                       price_in=3.0, price_out=15.0, price_cache_read=0.3)
print(span["app.cost_usd"])   # 0.01575
```

The cost line, worked out: 2,000 uncached input tokens at $3 per million is $0.006, 10,000 cached tokens at $0.30 per million is $0.003, and 450 output tokens at $15 per million is $0.00675, for $0.01575 in total. The prices are placeholders, not any provider's list price. The trap the comment guards against is real: some provider APIs report cached tokens in a separate field from the total, while OTel's `input_tokens` should include them. Mix the two conventions and you either double count the cache or drop it.

Three fields earn their place in incident reviews. `gen_ai.response.model` catches the day a provider moves an alias to a new snapshot. `gen_ai.prompt.version` lets you split every metric by prompt release. And `finish_reasons` separates "the model chose to stop" from "it hit the token limit", which look identical in a dashboard of response lengths.

## When this is wrong

Reading traces assumes you have traffic. Before launch you have none, so you generate inputs: write down the dimensions that matter (user type, task, edge case), combine them into realistic queries, and read the outputs exactly as you would read production traces. Expect the categories to change once real users arrive.

Saturation can mislead in both directions. A uniform sample under-represents rare, severe failures, so sample deliberately from complaints, escalations and long conversations as well. And if your outputs are mechanically checkable, such as code with tests or SQL with a known result, you can lean on automated checks much earlier and read fewer traces by hand.

Finally, the OpenTelemetry names in this lesson are the ones in the Development-status documents as of October 2026. Check the current spec before you hard-code them into a schema, because they have already been renamed once.
