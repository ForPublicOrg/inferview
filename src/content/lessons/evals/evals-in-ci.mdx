## The intervals overlap, so ship it

Scenario, not a real company: a pull request rewrites the system prompt of a support assistant. CI runs the 200-case regression suite. The baseline passed 170 cases; the candidate passes 163. Someone computes 95% confidence intervals, 0.794 to 0.893 for the baseline and 0.755 to 0.863 for the candidate, sees that they overlap, writes "within noise" and merges.

Both runs used the same 200 cases, so the useful question is not whether the averages are close. It is which cases changed. Nine cases that passed before now fail. Two that failed now pass.

<Predict id="evl-sign-test" question="If each of those 11 flips were a fair coin, what is the chance that 9 or more of them go the wrong way, in percent?" answer={3.3} tolerance={0.5} unit="%">
<p>About 3.3%. The number of ways to choose 9, 10 or 11 regressions out of 11 flips is 55 + 11 + 1 = 67, out of 2^11 = 2,048 equally likely patterns, so 67 / 2,048 = 0.0327. That is unlikely enough to block the merge at the usual 5% level, even though the two intervals overlap. Overlapping intervals from two independent samples are the wrong test for a paired comparison, because they throw away the information that the cases were identical.</p>
</Predict>

## What blocks a merge

You already run a test pyramid and probably a performance-regression check that compares benchmark runs between commits. An eval gate is the same idea with noisier tests. I split it into three tiers, by how certain the signal is.

**Hard gates.** Assertions and must-pass cases. If the JSON schema check fails or a must-refuse prompt is answered, the build fails, no statistics involved. The regression suite from the golden-sets lesson lives here; it should pass at or near 100%, so any new failure is news.

**Statistical gates.** For judged or noisy metrics, compare baseline and candidate on the same cases and test the flips. Evan Miller's 2024 paper on error bars for evals makes the general argument: treat the questions as a sample from a larger population and compare models with that in mind. For paired pass or fail data, the simplest version is the exact sign test on the flipped cases (McNemar's test in its exact form), and it fits in a dozen lines.

**Report-only.** The capability suite, cost per case, tokens, latency and tool-call counts go into a pull-request comment as diffs, with the flipped cases linked, for a human to judge. Several tools do the comment for you: Braintrust's `eval-action` posts score differences on the pull request, Langfuse documents a GitHub Action that fails a pull request below a score threshold, and promptfoo's CLI runs with `--fail-on-error` and writes a `results.json` you can gate on with your own script.

Try the gate. The defaults reproduce the scenario. Then set 11 broke and 9 fixed: 20 cases flip, the candidate passes 168, and the gate lets it through, because 11 against 9 is what noise looks like.

<EvalsFlipGate />

The gate in code, with a must-pass list for the hard tier:

```python
from math import comb

def one_sided_p(broke, fixed):
    # chance of at least `broke` regressions among the flips if each flip were a fair coin
    n = broke + fixed
    return sum(comb(n, i) for i in range(broke, n + 1)) / 2 ** n

def gate(base, cand, must_pass=(), alpha=0.05):
    broke = [i for i, (b, c) in enumerate(zip(base, cand)) if b and not c]
    fixed = [i for i, (b, c) in enumerate(zip(base, cand)) if c and not b]
    hard = [i for i in must_pass if not cand[i]]
    p = one_sided_p(len(broke), len(fixed)) if broke else 1.0
    return (not hard and p >= alpha), {"broke": broke, "fixed": fixed, "hard": hard, "p": round(p, 4)}
```

Return the lists, not just the verdict. "Cases 3, 10 and 25 broke" sends a reviewer straight to three transcripts; "p = 0.0327" sends them nowhere.

<Callout kind="gotcha" label="Measure your noise floor">
Run the baseline against itself twice before you trust any gate. At non-zero temperature, and sometimes even at zero, some cases flip between identical runs. If 6 cases flip with no code change, a candidate with 9 broke and 2 fixed is a weaker signal than it looks. Either fix the nondeterminism, run each case several times and take the majority, or count only cases that flip consistently.
</Callout>

## Offline, shadow, canary, A/B

CI tells you a change did not break known cases. It cannot tell you how the change behaves on traffic nobody has labelled. That takes three more stages, each closer to real users:

- **Shadow.** Copy live requests to the candidate, discard its answers, and evaluate them with reference-free checks: assertions, judges that need no reference answer, cost and latency. No user sees anything.
- **Canary.** Serve a small share of real users and watch guardrail metrics: errors, escalations, complaints, cost per conversation. Roll back automatically when they cross a threshold.
- **A/B test.** Hamel Husain's Level 3: after significant changes, compare outcome metrics such as resolution rate across randomised groups.

Online evaluation runs judges on sampled production traces. LangSmith's version is typical: a filter picks which runs to evaluate (negative feedback, runs with tool calls, a metadata tag), a sampling rate such as 0.1 evaluates 10% of matching runs, and a weekly per-evaluator spend cap stops a judge from becoming the largest line on the bill. Reference-based evaluators work only offline, since production traffic has no reference answers.

## Guardrails are not evaluators

A guardrail runs inline, before the output reaches the user, and blocks or rewrites it. It must be fast and deterministic; the FAQ describes guardrails as taking a few milliseconds and reserving them for clear, high-impact failures such as leaked personal data or malformed JSON. An evaluator runs after the fact, usually asynchronously, and measures nuanced quality such as tone or faithfulness. Putting a slow LLM judge in the request path does not make it a guardrail; it makes it a latency and availability dependency whose errors your users now see.

## Drift, feedback and success metrics

Three things drift after you merge.

**The model.** Providers update models behind aliases. Log `gen_ai.response.model`, the resolved version the provider reports, next to `gen_ai.request.model`, pin dated model versions in production, and run the regression suite on a schedule against the production configuration so a silent change shows up as flipped cases the morning after.

**The traffic.** New features and new users bring questions your golden set never had. Watch the mix of topics and intents, and feed new categories from error analysis into the set.

**The judges.** A judge's model gets updated too, and its TPR and TNR on your failures can move. Keep labelling a small fresh sample each cycle and recompute them.

User feedback is data, with care. Only some users click a thumb, and they are not a random sample, so a thumbs-up rate is a poor metric. It is an excellent filter: negative feedback is the first place to look for traces worth reading, and each confirmed failure becomes a golden case.

When someone asks how you would define success for a new AI feature, answer in three layers: an outcome metric tied to the user's goal (the support question resolved without a human), guardrail metrics that must not get worse (cost per task, latency, escalations, policy violations), and leading indicators you can read before outcome labels arrive (judge pass rates per failure mode, retries, how much users edit the output, abandonment).

## Keeping the bill sane

Eval cost scales with cases, graders and pull requests. A 200-case suite with four binary judges is 200 generation calls plus 800 judge calls per run; at 30 pull requests a week that is 30,000 calls a week before any repeated trials. The levers are the ones you would use for a slow test suite: run cheap assertions on every commit and expensive judges on merge or nightly; cache outputs so unchanged cases are not regenerated (promptfoo has `PROMPTFOO_CACHE_PATH` and `PROMPTFOO_CACHE_TTL` for this); re-judge only cases whose output changed; sample online traffic instead of judging all of it; and retire saturated evals that have passed for months, or move them to a slower schedule.

## When this is wrong

The sign test treats cases as independent and equally important. Near-duplicate cases make a regression look more significant than it is, and one broken must-refuse case can matter more than ten broken tone cases, which is why the hard tier exists. It also tests one metric. Gate on many judged metrics at once and something will look significant by chance, so choose the few that gate and leave the rest report-only.

Small numbers of flips have limited power. A change that breaks two cases and fixes none passes the statistical gate, because two regressions out of two flips happen by chance a quarter of the time. With no fixes at all, it takes five regressions to get below 5% (1/32 = 0.031). If those two cases matter, they belong in the must-pass list.

Finally, a green CI run says the change did not break what you already know about. It says nothing about the failure nobody has seen yet, which is why the loop ends where the first lesson began: read new traces, find the next category, add it to the set.
