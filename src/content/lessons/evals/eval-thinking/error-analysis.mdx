## The decision

Which checks go into an eval suite is decided by counting failures in traces, not by choosing metrics before anyone has read an output. The AI Evals FAQ by Hamel Husain and Shreya Shankar (published 18 September 2026) sets the order: read at least 100 traces, keep going past 100 while you are still learning something, write a note on each, group the notes into a taxonomy, count. The deliverable is one artefact: a ranked list of failure modes, each with a count, a binary definition and two or three trace ids that show it. The golden set, the judges and the merge gates in the rest of this track all read from that list.

The nearest systems practice is crash triage: bucket reports by signature, fix the largest bucket, then write the regression test. The difference is that a model failure has no signature. A wrong answer arrives as a successful response with fluent text in it, so the bucketing key is written by a person reading the trace, and that person's idea of the key changes while they read.

## Open coding, then axial coding

**Open coding** is a free-text note per trace on what went wrong, written without a category list. "Quoted the viewing date from the cached listing, not the updated one" is a usable note, because someone can later check a trace against it. "Accuracy issue" is not. The FAQ compares this stage to journaling and asks for at least 30 traces annotated by hand before an agent or a model proposes anything, so that the model's guesses do not set your categories before you have your own.

**Axial coding** reads the notes back and clusters them into categories, merging and splitting until each category has one fix owner and one check that could detect it. The FAQ calls this the most important step. A model can propose clusters once you have notes of your own to judge them against. Two tests decide whether a category is finished. Two people who read its definition label the same trace the same way. Its fix names a component, such as the listing lookup, the date formatter or the escalation rule, and "improve the prompt" does not count as a component.

**Binary labels** come last: each trace gets pass or fail per failure mode. The FAQ's case against a 1 to 5 scale is practical. The gap between a 3 and a 4 is a matter of taste, annotators drift to the middle, and detecting a change on a five-point scale needs a larger sample than detecting a change in a pass rate. A quality that seems to need a gradient splits into several binary checks, each with its own pass rate. Husain's 2024 essay on the Rechat assistant shows the working form: the domain expert graded 25 to 50 examples at a time and recorded a critique, a pass or fail outcome and the response he wanted instead. The critique is what later becomes the judge prompt and the label definition.

## Label the first upstream failure

In a multi-step trace, one fault produces several visible symptoms. A lookup that returns the wrong listing produces a wrong date, a wrong price and a wrong address in the answer. If every symptom is tagged, the taxonomy ranks symptoms, and the top fix lands on the component that was handed bad input. The FAQ's rule is to record the first failure in each trace because upstream errors cause downstream ones; tagging every independent failure is fine when you can afford it, where independent means not caused by an earlier step.

For agents the same rule becomes a table. The FAQ's transition failure matrix puts the last successful state on the rows and the state where the first failure occurred on the columns, so each cell counts failures at one hand-off. Its worked example has 12 failures at the step from generating SQL to executing it, against 2 at the step from choosing a tool to planning a calendar action. The matrix tells you which transition to instrument and test first, which a flat list of symptoms cannot.

## When to stop reading

The stopping rule is saturation: new traces stop revealing new failure modes or changing the definitions of existing ones. The FAQ's floor is 100 traces. The widget holds 50 synthetic labelled traces from the property-search assistant; read them ten at a time and watch the bar for each batch.

<EvalsSaturation />

Traces 1 to 20 surface five categories. Traces 21 to 40 add none, which looks like saturation after 40 traces. Trace 47 then adds a promised refund the assistant had no authority to give. The set has 14 failing traces, 6 of them wrong_date, so wrong_date is the first fix by count. The refund appears once in 50, and whether one occurrence deserves its own check is a severity decision the counts do not make for you.

The arithmetic behind the floor is short. A failure mode present in 1% of traffic is absent from 100 uniformly sampled traces with probability 0.99<sup>100</sup> = 0.37. Seeing it at least once with 95% probability takes n with 0.99<sup>n</sup> ≤ 0.05, so n = ln 0.05 / ln 0.99 ≈ 298 traces. Saturation on a uniform sample of 100 is therefore a statement about modes that occur in a few percent of traffic or more. Rare and severe modes come from deliberate sampling: the FAQ prioritises traces flagged by guardrails, by CI failures or by automated evaluators, and clustering by user persona finds groups a uniform sample under-represents.

## From the taxonomy to checks

The ranked list is a table with counts and intervals, because a rank between two close categories is not settled at 100 traces. The script below takes first-upstream labels and prints each mode with its count, rate, 95% Wilson interval and example trace ids.

```python
from collections import Counter
from math import sqrt


def wilson(k, n, z=1.96):
    """95% Wilson interval for k failures in n traces."""
    p = k / n
    d = 1 + z * z / n
    mid = (p + z * z / (2 * n)) / d
    half = z * sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return max(0.0, mid - half), min(1.0, mid + half)


def rank(labels):
    """labels: {trace_id: first upstream failure mode, or None}. Returns rows sorted by count."""
    n = len(labels)
    counts = Counter(m for m in labels.values() if m)
    rows = []
    for mode, k in counts.most_common():
        lo, hi = wilson(k, n)
        examples = sorted(t for t, m in labels.items() if m == mode)[:3]
        rows.append((mode, k, f"{k / n:.0%}", f"{lo:.0%} to {hi:.0%}", examples))
    return rows


# The 100 traces from the Predict above: 12 lookup failures, 9 wrong dates, 5 policy misses.
labels = {f"t{i:03d}": None for i in range(100)}
for i in range(12):
    labels[f"t{i:03d}"] = "wrong_listing"
for i in range(12, 21):
    labels[f"t{i:03d}"] = "wrong_date"
for i in range(21, 26):
    labels[f"t{i:03d}"] = "ignored_policy"

for row in rank(labels):
    print(row)
# ('wrong_listing', 12, '12%', '7% to 20%', ['t000', 't001', 't002'])
# ('wrong_date', 9, '9%', '5% to 16%', ['t012', 't013', 't014'])
# ('ignored_policy', 5, '5%', '2% to 11%', ['t021', 't022', 't023'])
```

The first two intervals overlap almost entirely, so at 100 traces the order between wrong_listing and wrong_date rests on cost of the fix and severity, not on the counts. A third column for severity belongs in the same table.

Each row then maps to the cheapest check that can detect it, using the three levels from Husain's 2024 essay, where Level 3 costs more than Level 2 and Level 2 more than Level 1. Level 1 is code that runs on every change: wrong_date becomes a parser that pulls the date out of the answer and compares it with the listing record; Rechat's suite holds hundreds of these, including a regex that fails any output exposing a UUID. Level 2 is human and model review on a cadence, for modes code cannot see, such as ignoring the spirit of a policy while quoting it. Level 3 is an A/B test after significant product changes. The same essay makes the target a product decision: the pass rate you accept depends on which failures you are willing to tolerate, and a regression check on a structured field and a judge on tone do not share one.

The taxonomy is versioned like a schema. Shankar and co-authors named the effect criteria drift: users need criteria to grade outputs, but grading outputs helps users define criteria. In their study of nine practitioners, participants added criteria after seeing new kinds of bad output and reinterpreted existing ones; two relaxed a proper-noun criterion so that most entities, rather than all, had to qualify. A definition that changes after 60 traces means the first 60 labels were made under a different rule, which the next lesson turns into a relabelling budget.

## When this is wrong

Before launch there are no traces. The FAQ's substitute is synthetic input built from dimensions that describe how queries vary, such as issue type, customer mood and prior context for a support bot: about 20 tuples written by hand, more generated by a model, each turned into a natural-language query in a separate prompt. The taxonomy from synthetic traffic is a draft; expect new categories in the first weeks of real use.

First-upstream counts rank fixes; they do not predict the failure rate after a fix. If the answer formatter would also have mangled the date in some of the 12 lookup failures, fixing the lookup leaves those traces failing under wrong_date. After each fix, read a fresh sample instead of subtracting.

When outputs are mechanically verifiable, such as code with tests or SQL with a known result, execution checks find most failures and reading can shrink to the cases the checks pass but users reject.

The taxonomy reflects the reader. One expert's categories carry that expert's sense of the product; a second reader on the same 100 traces produces a different split, and the definitions move while reading, as the criteria-drift study found. The counts are only as stable as the definitions, which is why the labelling operation in the next lesson treats agreement and relabelling as part of the cost.
