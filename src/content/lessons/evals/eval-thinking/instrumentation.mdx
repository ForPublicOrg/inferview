## The decision

Error analysis reads traces, so what a trace contains decides what can be analysed later. Two decisions are made once and early. The first is the set of fields every model call records, which is cheap and mostly settled by the OpenTelemetry GenAI semantic conventions. The second is the content-capture policy per environment: where prompts, completions, tool arguments and results go, who can read them, and how long they live. That policy is the expensive one, because the content is what error analysis needs and also what a privacy review objects to. Written down before launch, it is a design decision; written during an incident, it is whatever the on-call engineer could switch on.

## The span tree

The conventions are tracing with a vocabulary for model calls. The difference from ordinary RPC tracing is that the payload, not the status code, carries the failure, and the payload is personal data.

Three facts about the documents themselves. Every GenAI document is marked Development, not Stable. Since release v1.42.0 of the main semantic-conventions repository (12 June 2026), all `gen_ai.*` attributes, metrics, events and spans there are deprecated and live in a separate repository, `semantic-conventions-genai`. And names have changed before: the v1.37.0 registry (August 2025) replaced `gen_ai.system` with `gen_ai.provider.name` and `gen_ai.usage.prompt_tokens` with `gen_ai.usage.input_tokens`. Pin the version your instrumentation emits and record it.

A support agent's request becomes this tree:

```text
invoke_workflow support-triage             INTERNAL  the user-facing entry point that composes agents
  invoke_agent triage                      INTERNAL  in-process agent; CLIENT when the agent is remote
    chat example-model                     CLIENT    one inference call: {operation} {request.model}
    execute_tool lookup_order              INTERNAL  one tool execution: execute_tool {tool.name}
    chat example-model                     CLIENT
  invoke_agent refunds                     INTERNAL
    ...
```

The agent document limits `invoke_workflow` to composed processes such as graphs and orchestrators that a user or application starts; it is not reported for a standalone agent invocation, nor when a framework spins up a runner internally to delegate to a sub-agent. That rule matters for analysis: the root span is the unit you sample and label, so it should be the unit a user experienced.

## What every call records

The table lists what each inference span carries, with the requirement level the conventions assign. A team policy promotes several Recommended attributes to mandatory, because error analysis cannot use a trace without them.

| Field | Attribute | Spec level | Why it is mandatory here |
|---|---|---|---|
| Operation and provider | `gen_ai.operation.name`, `gen_ai.provider.name` | Required | Splits chat, embeddings and tool spans |
| Requested model | `gen_ai.request.model` | Conditionally Required | The alias your code asked for |
| Resolved model | `gen_ai.response.model` | Recommended | The snapshot that answered; catches an alias moving under you |
| Prompt version | `gen_ai.prompt.name`, `gen_ai.prompt.version` | Conditionally Required when a named template is used | Every failure count splits by prompt release |
| Tokens | `gen_ai.usage.input_tokens`, `output_tokens`, `cache_read.input_tokens`, `cache_write.input_tokens`, `reasoning.output_tokens` | Recommended (cache and reasoning when non-zero) | Cost, cache hit rate, context growth |
| Latency | span duration; `gen_ai.response.time_to_first_chunk` | Recommended for streaming | Time to first chunk and total time fail differently |
| Stop reason | `gen_ai.response.finish_reasons` | Recommended | A truncation at the token limit looks like a short answer otherwise |
| Errors | `error.type` | Conditionally Required on error | Separates provider and tool errors from model failures |
| Conversation | `gen_ai.conversation.id` | Conditionally Required when available | Joins turns for multi-turn analysis |
| Tool calls | `execute_tool` spans with `gen_ai.tool.name`, `gen_ai.tool.call.id` | Required; call id when the provider supplies one | Ties a tool result to the model call that requested it |
| Cost | none in the conventions | | An application attribute plus the price-table version used |

The AI Evals FAQ adds fields that matter for reading rather than for dashboards: a trace or session id per request, the source of each message (agent or tool) and its position in the sequence, and for hand-offs to a person, the decision and its reason, the context transferred, the wait, what the person did, the resolution and whether the person had enough context. Without the last one, a failure after a hand-off cannot be charged to the model or to the process.

## Token accounting across providers

The conventions say `gen_ai.usage.input_tokens` SHOULD include all input tokens, cached ones included, with cache reads and writes as subsets. Providers disagree with each other. Anthropic's `input_tokens` counts only tokens after the last cache breakpoint, and its docs give total input as `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`. OpenAI's Responses API `input_tokens` already includes `cached_tokens` and `cache_write_tokens`; its documented example is 12,000 input tokens, of which 4,000 are cache reads and 7,000 cache writes, leaving 1,000 ordinary. The mapping lives in one function per provider, tested against both shapes.

```python
def otel_usage(provider, usage):
    """Map a provider usage object to OTel GenAI usage attributes (input_tokens includes cached tokens)."""
    if provider == "anthropic":
        # input_tokens counts only tokens after the last cache breakpoint.
        read = usage.get("cache_read_input_tokens", 0)
        write = usage.get("cache_creation_input_tokens", 0)
        total_in = usage["input_tokens"] + read + write
    elif provider == "openai":
        # input_tokens already includes cached reads and cache writes.
        details = usage.get("input_tokens_details", {})
        read = details.get("cached_tokens", 0)
        write = details.get("cache_write_tokens", 0)
        total_in = usage["input_tokens"]
    else:
        raise ValueError(f"no usage mapping for {provider}")
    attrs = {"gen_ai.usage.input_tokens": total_in, "gen_ai.usage.output_tokens": usage["output_tokens"]}
    if read:
        attrs["gen_ai.usage.cache_read.input_tokens"] = read
    if write:
        attrs["gen_ai.usage.cache_write.input_tokens"] = write
    return attrs


def cost_usd(attrs, price):
    """price: USD per million tokens for uncached input, cache read, cache write and output, from a dated price table."""
    read = attrs.get("gen_ai.usage.cache_read.input_tokens", 0)
    write = attrs.get("gen_ai.usage.cache_write.input_tokens", 0)
    plain = attrs["gen_ai.usage.input_tokens"] - read - write
    return (plain * price["in"] + read * price["read"] + write * price["write"]
            + attrs["gen_ai.usage.output_tokens"] * price["out"]) / 1e6


# The same 12,000-token prompt as each provider reports it: 4,000 read from cache, 7,000 written, 1,000 plain.
anthropic = {"input_tokens": 1000, "cache_read_input_tokens": 4000,
             "cache_creation_input_tokens": 7000, "output_tokens": 500}
openai = {"input_tokens": 12000, "output_tokens": 500,
          "input_tokens_details": {"cached_tokens": 4000, "cache_write_tokens": 7000}}
price = {"in": 3.0, "read": 0.3, "write": 3.75, "out": 15.0}  # placeholder prices, not a provider's list

for name, usage in [("anthropic", anthropic), ("openai", openai)]:
    attrs = otel_usage(name, usage)
    print(name, attrs["gen_ai.usage.input_tokens"], round(cost_usd(attrs, price), 6))
# anthropic 12000 0.03795
# openai 12000 0.03795
```

The failure this prevents is silent. An exporter that copies Anthropic's raw `input_tokens` (1,000) into the OTel attribute makes `plain` equal 1,000 − 4,000 − 7,000 = −10,000, and the cost becomes (−10,000 × 3 + 4,000 × 0.3 + 7,000 × 3.75 + 500 × 15) / 10<sup>6</sup> = $0.00495, which is 13% of the true $0.03795. Nothing errors; the dashboard reports that caching made the feature nearly free. A test asserting that `input_tokens` is at least `cache_read + cache_write` on every span catches it.

## Content: off by default, and where it goes instead

The conventions mark `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions` and `gen_ai.tool.definitions` as Opt-In, and so are `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result` and the prompt template variables. Instrumentations SHOULD NOT capture content by default. If the switch is an environment variable it is `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT`, with `NO_CONTENT` as the default, then `SPAN_ONLY`, `EVENT_ONLY` and `SPAN_AND_EVENT`; an invalid value falls back to `NO_CONTENT`. Tool definitions are schemas rather than payloads and are not governed by that switch.

The spec names three patterns: record nothing; record content on span attributes, suited to pre-production or to storage that already meets the privacy rules; or upload content to external storage and put a reference on the span (`gen_ai.input.messages_ref` and its siblings), which it recommends for production because the store can carry its own access control. Two details change the design. The upload hook, when configured, is invoked regardless of the span sampling decision, so the content store sees every call even when only a fraction of spans are kept. And the hook can modify the messages before the instrumentation records any attribute, which makes it the single place for redaction: both the stored copy and any on-span copy get the redacted values. Reference URIs should not embed credentials such as signed query parameters.

The policy, written per environment:

| Environment | Capture switch | Content destination | Who reads it |
|---|---|---|---|
| Local and CI | `SPAN_ONLY` | On spans; test data only | Engineers |
| Staging with internal users | `SPAN_ONLY` | On spans, short retention | Engineers and the labelling expert |
| Production | `NO_CONTENT` on spans | Upload hook: redact, then store with a reference on the span | A labelling group with its own access grant |
| Labelling pool | Copied from the production store | The annotation tool | The expert and second labeller, under the privacy owner's terms |

Two rules sit beside the table. Content never goes into a custom attribute or a span name: an `app.user_query` attribute bypasses the capture switch, and the spec forbids reporting a content attribute on a signal whose conventions do not reference it. And retention periods are set by whoever signs for privacy, in the same document, so error analysis knows how far back it can read.

## Sampling a trace whose failure is not an error

<Fragment slot="prompt">
<p>Scenario: 50,000 requests a day, head sampling keeps 10% of traces, and a failure mode the error analysis cares about occurs in 0.2% of requests. The failure is a fluent wrong answer, so its span status is OK.</p>
</Fragment>
<p>50,000 × 7 × 0.002 = 700 failing requests a week, and 10% of them survive: <b>70</b>. They are mixed into 35,000 kept traces with nothing marking them, because the span status is OK. The OpenTelemetry sampling docs state the general limit: head sampling alone cannot ensure that every trace with an error is kept, and here the failure is not even an error.</p>
</Predict>

Tail sampling in the Collector decides after seeing the trace, at the cost of stateful components that the OpenTelemetry docs say must accept and store large volumes. It only helps if something on the trace marks the failure before the decision: a guardrail verdict, a cheap assertion result, a user's thumbs-down or an escalation flag recorded as an attribute. The useful rule keeps every trace carrying such a mark, plus a uniform slice for the error analysis that finds modes nobody has a mark for yet.

## When this is wrong

The attribute names are from Development-status documents as of 28 October 2026, and they have been renamed before. Check the version your instrumentation library emits before writing queries against the names here; a library that predates the move may still emit names the current documents mark as deprecated.

Structured content may not be supported on spans in your language yet; the spec then asks for a JSON string on spans and the structured form on events, and large payloads can exceed backend limits on attribute size. Measure payload sizes before choosing `SPAN_ONLY` anywhere.

Provider-specific documents may set different span names; the conventions allow it. A mixed-provider system needs a check that the names it queries actually appear.

Cost is not a convention. Prices change and cache multipliers vary by model, so the cost attribute is only as good as the dated price table behind it, and recomputing history after a price change is a reason to store tokens rather than only dollars.
