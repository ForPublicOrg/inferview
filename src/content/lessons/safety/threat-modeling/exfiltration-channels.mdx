## Any request the model can shape is a send tool

A capability review that lists tools finds `send_email` and `http_post`. It misses most of the channels that have leaked data in public incidents, because those channels are requests made by something other than a tool: the user's browser rendering an image, a chat platform unfurling a link, a fetch tool following a link on the page it fetched, an allowlisted API that happens to accept uploads. The test for a channel is one question: can text the model wrote end up in a request, or in a place, that the attacker can read? If yes, the system has external communication, whether or not anyone called it a tool.

The model only has to write a URL. The secret goes in the path or query string, and the attacker reads it from their server log.

<Predict id="sfe-exfil-bytes" question="How many bytes of private data leave per answer?" answer={15000} tolerance={500} unit="bytes">
<Fragment slot="prompt">
<p>Scenario: a chat client renders every Markdown image the model writes. An injected instruction makes the model emit 10 image references per answer, each URL carrying 2,000 characters of base64url-encoded data in its query string.</p>
</Fragment>
<p>Base64 packs 3 bytes into 4 characters, so 2,000 characters carry 1,500 bytes, and 10 images carry <b>15,000 bytes</b> per answer, with no click. That is a page of email or a few hundred lines of a credentials file each time the user asks a question. The bandwidth is not the point; the point is that a channel this wide exists in every client that renders untrusted image URLs.</p>

Two design notes in the same tag show the pattern applied in advance. OpenAI's Codex cloud agent shipped with internet off by default, a domain allowlist, and only `GET`, `HEAD` and `OPTIONS` permitted. Anthropic's API web fetch tool, as described in September 2025, only fetches URLs that already appear in the conversation, so the model cannot compose a URL carrying data; the July 2026 case is what happened when fetched pages could supply the next URL.

## An allowlist is a list of functions

The common failure in the table is an allowlist written as hosts. Anthropic's containment post puts it in one line: "Every function reachable through any domain on an allowlist is now an attack surface." In the Cowork case, the sandbox and egress proxy behaved as designed: the destination was `api.anthropic.com`, which the product needs, so the proxy let it through. The planted file carried the attacker's API key, and the upload landed in the attacker's account. The host was right and the principal was wrong.

The fix Anthropic describes is a proxy inside the VM that intercepts traffic to its API and forwards only requests carrying the VM's own provisioned session token, and blocks headers that would make the API fetch a URL server-side. It runs inside the VM because only the VM knows where a request came from. Two properties make it a construction control: it does not depend on what the model wrote, and it checks the credential's provenance, not the destination alone.

The same reasoning covers the GET-that-writes case. `docs.google.com` on a CSP image allowlist admits every Google Form, including one the attacker owns, because a form submission can be a GET. The allowlist entry that would have held is a path, not a host.

```python
from urllib.parse import urlsplit

SESSION_TOKEN = "sess-7f3a"   # minted for this sandbox; the only credential allowed out

# A function allowlist: (host, method, path prefix), not a host allowlist.
ALLOW = [
    ("pypi.org", "GET", "/simple/"),
    ("files.pythonhosted.org", "GET", "/packages/"),
    ("api.vendor.example", "POST", "/v1/messages"),
]
CREDENTIALED = {"api.vendor.example"}

def egress(method: str, url: str, headers: dict) -> bool:
    u = urlsplit(url)
    if u.scheme != "https" or u.username or u.password:
        return False
    if not any(u.hostname == h and method == m and u.path.startswith(p) for h, m, p in ALLOW):
        return False
    if u.hostname in CREDENTIALED and headers.get("authorization") != f"Bearer {SESSION_TOKEN}":
        return False              # provenance: a key found in a file is not ours
    return True

ours = {"authorization": f"Bearer {SESSION_TOKEN}"}
planted = {"authorization": "Bearer sk-attacker"}
assert egress("GET", "https://pypi.org/simple/requests/", {})
assert egress("POST", "https://api.vendor.example/v1/messages", ours)
assert not egress("POST", "https://api.vendor.example/v1/messages", planted)
assert not egress("POST", "https://api.vendor.example/v1/files", ours)
assert not egress("GET", "https://docs.google.com/forms/d/e/x/formResponse?entry.1=secret", {})
print("ok")
```

In production this runs in the egress proxy, with TLS interception for the credentialed hosts, because a check inside the agent process is bypassed by any code the agent runs. Path matching also has to follow the host's own routing: a prefix that looks read-only can include an endpoint that writes.

## Deterministic blocks and probabilistic layers

Microsoft's MSRC post on indirect injection (July 2025) separates the two kinds explicitly. Hardened system prompts, spotlighting (delimiting, datamarking and encoding untrusted text) and the Prompt Shields classifier lower the likelihood of a successful injection. For data exfiltration through Markdown image injection, reported to MSRC by Johann Rehberger, the post says Microsoft "took steps to deterministically block the security impact (i.e., the data exfiltration technique)", and did the same for certain untrusted links. Its human-in-the-loop example is Draft with Copilot in Outlook, where the user sends the email.

That ordering is the fix pattern: assume the injection succeeds and make the channel unable to carry the result. For rendering, the block is a renderer that does not fetch untrusted image URLs plus a CSP `img-src` the browser enforces whatever the model writes, applied to the rendered output so that every Markdown syntax is covered. EchoLeak is the case where both existed and each had a gap: the filter handled inline links but not reference-style ones, and the CSP allowed a Microsoft domain that would fetch any URL. The [EchoLeak teardown](/learn/safety/threat-modeling/echoleak) follows that chain step by step.

<p>Images are allowed only if the URL appears verbatim in a document retrieved for this answer, and they are fetched by our own image proxy at ingestion time and served from our host. The model never composes a URL the browser fetches, so it cannot encode data into one, and the CSP allows only our host. </Fragment>
<Fragment slot="long">
<p>The exfiltration risk is a URL that carries data written in this session. An image URL that was already in a stored document cannot contain the user's secrets, because it was written before the session. So the rule is provenance: the renderer resolves an image reference only to an asset ID the retrieval layer returned for this answer, and anything else is dropped.</p>
<p>Fetching at ingestion rather than at render has two reasons. A proxy that fetches arbitrary URLs at render time is the EchoLeak Teams endpoint under another name. And fetching once per image means a document's author cannot learn when a given user read it, which a live fetch would tell them.</p>
<p>What I give up: freshness, storage cost, and images from documents that link to dynamic charts. The failure mode is the ingestion fetcher itself, which runs on customer-supplied URLs and is an SSRF surface, so it runs with no access to internal networks and with private ranges blocked. If five weeks is not enough for ingestion-time fetch, the fallback is to ship with images shown as links the user clicks, labelled with the host, and add inline images after.</p>
</Fragment>

## When this is wrong

Blocking network channels does not close channels that need no network. A model can write data into an artefact the user forwards, into a commit message, a shared document or a ticket the attacker can see. The trifecta audit catches these only if writes to attacker-readable places are listed as external communication.

User-mediated channels sit between construction and rate. A link the user must click is one action away from a leak, and the same injection writes the sentence that asks for the click. Treating links as safe because they need a click is the Slack AI position, and it is a product decision, not a security property.

The allowlist reasoning assumes the endpoints on it are stable. Hosts change owners, domains expire as in ForcedLeak, and services add upload or fetch features after you allowlisted them. A function allowlist needs an owner and a review date like any firewall rule.

Finally, the table is a record of what has been reported and published. Channels in proprietary clients that nobody has disclosed are not in it, and the absence of a case for a channel is not evidence that the channel is closed.
