## A taxonomy, read as a review checklist

The OWASP Top 10 for LLM applications is a consensus list of risk categories. Reciting it answers nothing. Used well it is a review checklist with three columns per entry: the control that holds by construction, the control that lowers a rate, and the test that would fail if either regressed. An entry with only a rate-lowering control and no test is an accepted risk that nobody wrote down.

The numbers need a year. OWASP published the 2026 edition in August 2026, and the order moved. OWASP's own announcement says Excessive Agency is now third. The full 2026 order below is from the Cloud Security Alliance's republication of an analysis by Aembit, because the OWASP resource page links the document without listing the entries; check the PDF before quoting a number in writing. That analysis reports that all ten 2025 areas were kept, that System Prompt Leakage was renamed and broadened to Hidden Context Exposure, and that the ranking weighted a community vote at 75% and incident data at 25%.

"LLM05" is Improper Output Handling in 2025 and Data and Model Poisoning in 2026. A risk register, a pentest report or a vendor questionnaire that writes "LLM05" without the year is ambiguous from August 2026 on. Write `LLM05:2025` or name the risk.

## Each entry as control and test

The controls below are taken from the 2025 entry pages, which remain the most detailed OWASP text for each risk. The split into construction and rate is this lesson's, and it is the column reviewers skip.

<div class="tablewrap">
<table>
<thead><tr><th>Risk</th><th>Holds by construction</th><th>Lowers a rate</th><th>Test that fails on regression</th></tr></thead>
<tbody>
<tr><td>Prompt Injection</td><td>Session capability set kept to two Rule of Two properties; privilege control</td><td>Segregating and marking external content; input and output filters</td><td>Injected-document suite, run on every prompt or model change, asserting no unapproved tool call or outbound request</td></tr>
<tr><td>Sensitive Information Disclosure</td><td>Retrieval filtered by the requesting user's identity in the data layer; restricted data sources</td><td>Output redaction and tokenization</td><td>User A's queries never return user B's documents, checked against an ACL oracle</td></tr>
<tr><td>Excessive Agency</td><td>Only the tools and functions the task needs; downstream calls in the user's context; authorisation enforced by the downstream system</td><td>Logging and rate limits, which OWASP says limit damage rather than prevent it</td><td>Each tool called as a user without the permission returns a denial from the downstream system, not from the prompt</td></tr>
<tr><td>Supply Chain</td><td>Verifiable sources with signatures and hashes; pinned MCP server versions and description hashes; signed SBOM or AI BOM</td><td>Scanning third-party models and adapters</td><td>Build fails on an unpinned or unsigned model, adapter or server</td></tr>
<tr><td>Data and Model Poisoning</td><td>Known writers for every indexed or training document; versioned datasets</td><td>Anomaly detection on data and training metrics</td><td>Every document in the index traces to an allowed writer; a planted document from an unlisted source is rejected</td></tr>
<tr><td>Unbounded Consumption</td><td>Input size limits, per-principal token budgets, timeouts, caps on queued actions</td><td>Anomaly detection on usage</td><td>Max-size and max-rate load test hits the budget and stops</td></tr>
<tr><td>Misinformation</td><td>For checkable artefacts (packages, citations, IDs), existence checks before use</td><td>Grounding, cross-verification</td><td>Labelled eval set with a regression gate</td></tr>
<tr><td>Hidden Context Exposure</td><td>No credentials in prompts; every rule in the prompt also enforced outside the model</td><td>Instructions not to reveal the prompt</td><td>CI scan of prompts and tool schemas for secrets; red-team extraction attempts treated as expected to succeed</td></tr>

<tr><td>Improper Output Handling</td><td>Model treated as an untrusted user: parameterised queries, context-aware encoding, strict CSP</td><td>Output monitoring</td><td>XSS, SQL and path-traversal payloads through every output sink come out encoded</td></tr>

Three rows carry most of the design work. Excessive Agency is where the trust-boundaries lesson lands: OWASP's own example is a mail-summarising extension that can also send, fixed by a read-only scope and a human who sends each draft. Its "complete mediation" mitigation means the database or API refuses the call, so a confused model cannot authorise itself. Hidden Context Exposure inherits the 2025 entry's position that a system prompt "should not be considered a secret, nor should it be used as a security control"; the test is written on the assumption that extraction works. Misinformation becomes a supply-chain risk for code: Spracklen et al. (USENIX Security 2025) found at least 5.2% of packages suggested by commercial models and 21.7% by open-source models did not exist, across 576,000 samples from 16 models, with 205,474 unique invented names. OWASP's Misinformation entry describes attackers registering those names. The construction control is a registry or allowlist check before any install the model proposes.

Unbounded Consumption is the entry where a rate limit that looks adequate is not.

At a scenario price of $3 per million input tokens that is $345.60 per key-hour, multiplied by however many free keys an attacker can create. A request-count limit bounds requests, not cost. ## The agentic list and the enforcement layer

The OWASP Top 10 for Agentic Applications, released on 9 December 2025, adds entries the LLM list reaches only through Excessive Agency. Names below are as reported by BleepingComputer, a secondary source. The controls are this lesson's mapping, not OWASP text.

<table>
<thead><tr><th>Entry</th><th>Control that holds by construction</th></tr></thead>
<tbody>
<tr><td>ASI01 Agent Goal Hijack</td><td>Capability set per session; plans fixed before untrusted data is read where the task allows</td></tr>
<tr><td>ASI02 Tool Misuse and Exploitation</td><td>Narrow tools with validated parameters instead of shell or open fetch</td></tr>
<tr><td>ASI03 Identity and Privilege Abuse</td><td>Per-agent identity, short-lived scoped credentials, actions in the user's context</td></tr>
<tr><td>ASI04 Supply Chain Vulnerabilities</td><td>Pinned and verified tools, servers and packages</td></tr>
<tr><td>ASI05 Unexpected Code Execution</td><td>Sandboxed execution with no ambient credentials and egress control</td></tr>
<tr><td>ASI06 Memory and Context Poisoning</td><td>Provenance on memory writes; untrusted sessions cannot write long-term memory</td></tr>
<tr><td>ASI07 Insecure Inter-Agent Communication</td><td>Authenticated agent identities; structured, validated messages between agents</td></tr>

The lists name risks; they do not say where a control runs. The Agent Control Standard, donated to the OWASP GenAI Security Project and announced with the 2026 list, is an attempt to standardise that. Its README describes specification v0.1.0 with nineteen lifecycle hooks, covering session start and end, before and after a turn, knowledge retrieval, memory reads and writes, and tool calls (`steps/toolCallRequest` and `steps/toolCallResult` are the two named methods), and five dispositions a policy can return: `allow`, `deny`, `modify`, `ask` and `defer`. The CSA research note on it says implementation samples were not yet released and treats it as an architecture to plan around. What it gives a design review today is vocabulary: for each row above, name the hook where the control runs and the disposition it returns.

The tool-call hook is where most of the construction column lives. This gate enforces Excessive Agency's complete mediation and the Rule of Two in one place, and returns ACS-style dispositions:

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Call:
    tool: str
    args: dict
    user: str       # principal from the verified token, never from model output
    tainted: bool   # this session has read untrusted input

# tool: (permission the user must hold downstream, changes state)
POLICY = {
    "get_invoice":  ("billing:read", False),
    "issue_credit": ("billing:write", True),
}

def decide(call: Call, grants: dict, approved: bool = False) -> str:
    if call.tool not in POLICY:
        return "deny"                      # no tool the task does not need
    perm, mutates = POLICY[call.tool]
    if perm not in grants.get(call.user, set()):
        return "deny"                      # complete mediation in the user's context
    if mutates and call.tainted and not approved:
        return "ask"                       # untrusted input plus state change needs a person
    return "allow"

grants = {"u_17": {"billing:read"}, "u_42": {"billing:read", "billing:write"}}

assert decide(Call("get_invoice", {"id": 9}, "u_17", True), grants) == "allow"
assert decide(Call("issue_credit", {"amount": 40}, "u_17", False), grants) == "deny"
assert decide(Call("issue_credit", {"amount": 40}, "u_42", True), grants) == "ask"
assert decide(Call("issue_credit", {"amount": 40}, "u_42", True), grants, approved=True) == "allow"
assert decide(Call("run_sql", {"q": "..."}, "u_42", False), grants) == "deny"
print("ok")
```

The asserts are the test column for two rows. In production the grant lookup belongs to the downstream service, not to a dictionary in the agent, so that a bug in the gate cannot widen access.

<p>So I would triage first. Features whose sessions score three Rule of Two properties, or that render model output into HTML or SQL, get the full treatment. ## When this is wrong

The lists are categories ranked by consensus, and the 2026 ranking was mostly a vote. A rank says how many practitioners worry about a risk, not how likely it is in your system; a batch summariser with no tools has little Excessive Agency whatever its rank.

The construction-or-rate split depends on the deployment. Partitioning a vector store per tenant holds by construction only if every index, cache and evaluation log is partitioned too. Output encoding holds for the sinks you listed, and the next feature that writes model output into a new sink is outside it.

Some rows have no construction control. Misinformation on free-text answers is reduced, not prevented, and Prompt Injection's construction control is a limit on what an injection can do, not a way to stop one.

The 2026 order and the agentic names in this lesson come from secondary sources, and the Agent Control Standard is at v0.1.0. Recheck the order against the OWASP document and the ACS hook list against its current release before writing either into a contract.
