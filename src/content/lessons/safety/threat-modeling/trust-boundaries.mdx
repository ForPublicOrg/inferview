## One channel, many writers

The system prompt, the user's turn, a retrieved chunk, a tool result and an MCP tool description reach the model as one token sequence. Role markers and delimiters are hints to a trained network, not a grammar a parser enforces. SQL injection had the same shape and was closed by parameterised queries, which give data a channel the parser never executes; a model has no such channel, and no vendor has shipped one. OWASP's prompt injection cheat sheet says of input screening that "it is not a security boundary", because the model does not enforce a boundary between instructions and data. OWASP's LLM01:2025 entry adds that RAG and fine-tuning do not fully mitigate injection.

Two consequences follow, and they are the whole method of this lesson. First, every input path is an instruction path, so the question for each input is who can write it. Second, every capability is judged by what an injected instruction could do with it: read something the attacker cannot, change something, or carry bytes to a place the attacker can read. The trust boundary in a model system is drawn around text sources and capabilities, not around network zones or services.

## Scoring a session

Simon Willison's lethal trifecta (June 2025) names the combination that makes data theft possible in one agent: access to private data, exposure to untrusted content, and a way to communicate externally. With all three present, an instruction planted in the untrusted content can read the private data and send it out. Remove one leg and that path closes.

Meta's Agents Rule of Two (October 2025) generalises the score. Within one session an agent should satisfy no more than two of:

- **[A]** it processes untrustworthy inputs,
- **[B]** it has access to sensitive systems or private data,
- **[C]** it can change state or communicate externally.

A task that needs all three should not run autonomously: Meta's post says it needs a new session with a fresh context window, or supervision such as human approval or another reliable validation step.

The two scores differ in two places. The Rule of Two counts state change in [C], so an injection that approves a refund or deletes records counts even though nothing is stolen; the trifecta only covers exfiltration. And [B] is any sensitive system, not only private data, a clarification Willison records from one of the authors. Willison also objected that Meta's diagram labelled the [A]+[C] pair as safe, since untrusted input driving state changes can still do harm; Meta relabelled it "lower risk". Meta's post calls the rule a supplement to least privilege, not a substitute, and lists what it leaves out: spam, agent mistakes, hallucinations and excessive privileges.

The unit is the session, meaning one context window. That is the lever teams under-use. Meta's email-bot example shows three ways to bring a read-and-send inbox agent to two properties: process mail only from trusted senders (drop [A]), run it where there is no sensitive data (drop [B]), or let it send only to trusted recipients or after a human approves the draft (drop [C]). Each costs product scope in a different place, which is why the choice is a design decision and not a checkbox.

## Drawing the boundaries

The procedure fits in a design review. For each input path, write down who can author the text: the user, staff, any customer, anyone with an email address, anyone who can open a GitHub issue or publish a web page, whoever ships an MCP server. For each capability, write down what it reads, what it changes, and whether anything the model controls ends up in a request: a URL, a header, a file upload, a write to a table someone else reads. Then mark which session each input and capability lives in, and score each session.

Three classes of capability are routinely missed. Rendering is one: a client that renders Markdown images fetches the URL the model wrote, with no tool call in the logs. Writes are another: a row in a table, a comment on a public issue or a reply on a ticket is external communication when the attacker can read it. Credentials are the third: a token that reaches both public and private repositories turns one integration into all three legs.

"Sensitive" is relative to the writer of the untrusted input. A support agent that reads a customer's ticket and queries only that customer's orders holds no data the ticket's author cannot already see, so the session scores [A] and [C] only. The same agent on a service account that reads every customer's orders scores all three. Scoping the credential to the principal who wrote the untrusted text is often the cheapest leg to remove, and the code below makes that visible.

```python
from itertools import combinations

# Each tool or channel is tagged with the Rule of Two properties it supplies:
# A = processes untrusted input, B = reaches sensitive data or systems,
# C = changes state or communicates externally.
TOOLS = {
    "read_ticket":   {"A"},        # customer-written text
    "orders_db_all": {"B"},        # service account, every customer's orders
    "orders_db_own": set(),        # scoped to the ticket author: nothing they cannot already see
    "issue_refund":  {"C"},
    "md_images":     {"C"},        # renderer fetches any image URL
}

def properties(session):
    return set().union(*(TOOLS[t] for t in session))

def violates_rule_of_two(session):
    return properties(session) >= {"A", "B", "C"}

def smallest_fixes(session):
    """Smallest sets of tools whose removal brings the session to two properties or fewer."""
    for k in range(1, len(session) + 1):
        fixes = [set(c) for c in combinations(sorted(session), k)
                 if not violates_rule_of_two(set(session) - set(c))]
        if fixes:
            return fixes
    return []

session = {"read_ticket", "orders_db_all", "issue_refund", "md_images"}
print(sorted(properties(session)), violates_rule_of_two(session))  # ['A', 'B', 'C'] True
print(smallest_fixes(session))  # [{'orders_db_all'}, {'read_ticket'}]

scoped = {"read_ticket", "orders_db_own", "issue_refund"}
print(sorted(properties(scoped)), violates_rule_of_two(scoped))    # ['A', 'C'] False
```

Removing `issue_refund` alone does not fix the first session, because `md_images` still supplies [C]. Two tools supplying one leg is the common case in production, and it is why the review lists channels, not only tools.

## A rate is not a boundary

Classifiers, spotlighting and system-prompt rules lower the probability that one injection works. An attacker who can send many inputs is not trying once.

<p>Scenario: an inbound classifier stops 99% of injection attempts, and each attempt is independent. An attacker sends 100 differently worded emails to one inbox the agent reads.</p>

<p>The chance all 100 are stopped is 0.99<sup>100</sup> = 0.366, so at least one gets through with probability 1 − 0.366 = <b>63.4%</b>. Independence flatters the classifier: an adaptive attacker learns from each failure, so later attempts are better than random draws. Willison's write-up of The Attacker Moves Second (October 2025) reports that adaptive attacks beat 12 published defences, above 90% for most, and that spotlighting went from 28% attack success against static attacks to 99% against automated ones. Anthropic reports, for its own model on Gray Swan's benchmark, about 0.1% success for a single attempt and about 5 to 6% after 100 adaptive attempts. Willison's line on vendor guardrails is that 95% is a failing grade in web security.</p>
</Predict>

The design conclusion is the one Meta draws: until injection can be detected reliably, the guarantee comes from the session's capability set, and the rate-lowering layers sit on top of it. Supervision is a control only when it works as one. Anthropic's containment post reports that users approved about 93% of permission prompts, which is why an approval step has to show the real arguments and fire rarely.

## MCP moves the boundary into the tool list

MCP lets a user assemble a session's capabilities from servers written by different people, which is how the trifecta gets assembled without anyone designing it. Three public cases mark the attack surface.

Tool descriptions are model input. Invariant Labs (April 2025) showed an `add` tool whose description told the model to read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass them in a `sidenote` parameter. The same post named the rug pull, where a server changes a description after the user approved it, and shadowing, where one server's description redirects another server's trusted `send_email` to the attacker. Their mitigations are pinning server and tool versions with a hash of the description, and showing users what the model sees.

The server can be correct and the session still lethal. Invariant's GitHub MCP case (May 2025) used a malicious issue on a public repository to make the agent read the user's private repositories and publish the contents in a pull request on the public one. Invariant states the server code had no flaw; the token reached both repositories. Their policy fix is one repository per session, which is the session split from above.

One server can supply all three legs. In the Supabase case Willison described in July 2025, the agent held a `service_role` key that bypasses row-level security, read support tickets written by customers, and could insert rows into `support_messages`, which the ticket's author reads. An injected ticket asked it to copy `integration_tokens` into a new message. Supabase's documentation recommends read-only, project-scoped mode, which removes the write leg.

The specification's own security page, revision `2026-07-28`, lists the protocol-level classes: the confused deputy through an OAuth proxy with a static client ID, token passthrough (servers MUST NOT accept tokens not issued for them), SSRF during OAuth metadata discovery, state handle hijacking, local server compromise through one-click installs, OAuth authorization URL validation, stdio escalation in proxy architectures, mix-up attacks, localhost redirect impersonation and scope minimisation. State handle hijacking exists because this revision has no protocol-level sessions: a server that needs state mints a handle and receives it back as a tool argument, so it MUST NOT treat possession of the handle as authentication. The tools page says a human SHOULD be able to deny tool invocations, clients SHOULD show tool inputs before calling, and clients MUST treat tool annotations as untrusted unless the server is trusted. The security track's [MCP attacks lesson](/learn/security/mcp-security/mcp-attacks) maps each published MCP attack to its clause.

The reference case for this whole module is EchoLeak (CVE-2025-32711, CVSS 3.1 base 9.3), where one email to a Microsoft 365 Copilot user became a zero-click exfiltration through four small bypasses. The [EchoLeak teardown](/learn/safety/threat-modeling/echoleak) walks it step by step.

## When this is wrong

The trifecta and the Rule of Two are models of one attacker: someone who can put text in front of the model. They say nothing about the model making a mistake on clean input, about a user who is the attacker using their own permissions, or about harm that needs no capability at all, such as a summary that tells a user a fraudulent invoice is legitimate. Integrity attacks on what the user is told sit outside both scores.

The legs are less binary than the widget makes them. Whether data is sensitive depends on who wrote the untrusted text, as the scoped-credential case shows. Whether content is trusted depends on who can edit it, and an internal wiki with broad edit rights is untrusted. Whether there is a way out depends on channels that are not in any tool list: image fetches, link previews, a fetch tool following links on a page, a write to a row someone else reads.

Session splitting assumes the boundary between sessions holds. A summary passed from the reading session to the acting session is model output that carries whatever the injection wrote, so the acting session has [A] again unless what crosses is structured and validated: an order ID checked against the database, not free text.

Finally, the published attack-success numbers are measured on specific models, benchmarks and dates, and Anthropic's are the vendor's own. They support the shape of the argument, that rates fall with effort and never reach zero, not a figure to put in a risk register.
