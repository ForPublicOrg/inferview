## The confident benefits bot

Scenario, not a real deployment: an HR assistant answers questions about leave policy from the employee handbook. An employee asks how many weeks of parental leave they get after moving countries. The handbook covers the old country and says nothing about the new one. The assistant answers with a specific number, a policy section reference and a friendly tone. The number is from the old country's section. The employee books flights.

Nothing crashed, nothing was attacked, and every log line looks healthy. This is the failure that safety work in most companies is actually about: the system was confidently wrong in a place where being wrong costs someone real money, and nothing in it was built to say "I don't know".

## Why models guess

Kalai, Nachum, Vempala and Zhang argued in September 2025 that hallucination is partly something we train and grade for. Most benchmarks score an answer as right or wrong, and "I don't know" scores the same as wrong. Under that rule a guess is never worse than abstaining, so a model optimised for the score learns to guess. Think of a student on a multiple-choice exam with no penalty for wrong answers: leaving a question blank is the only strictly bad strategy.

Their proposed fix is to change the scoring. Tell the model, and the grader, that a correct answer scores 1, "I don't know" scores 0, and a wrong answer costs t/(1-t) points. With that penalty, answering has an expected score of p - (1-p) × t/(1-t), where p is the model's chance of being right. Set it to zero and solve: answering beats abstaining exactly when p is greater than t.

<Predict id="sfe-abstain-threshold" question="Wrong answers cost 3 points, right answers score 1, and 'I don't know' scores 0. Above what confidence (in percent) should the model answer?" answer={75} tolerance={3} unit="%">
<p>A penalty of 3 means t/(1-t) = 3, so t = <b>0.75</b>. Check: at p = 0.75 the expected score of answering is 0.75 - 0.25 × 3 = 0. Above 75% confidence, answer; below it, say you don't know. Under plain accuracy grading the penalty is 0, t is 0, and every guess with any chance of being right is worth making.</p>
</Predict>

The widget applies the rule to a made-up set of 20 answers, each with a confidence and a right or wrong label. Raise the penalty and watch the best cut move up; push the threshold past it and watch the score fall as you throw away right answers.

<SafetyAbstain />

The rule only works if confidences mean something. A model that says 0.9 and is right half the time will answer when it should not, whatever threshold you set. So abstention is two jobs: get a confidence signal (the model's own estimate, agreement across samples, a verifier's score, or retrieval coverage), then measure how well it predicts correctness on your traffic before you trust a threshold.

The arithmetic, as a few lines you can check:

```python
def expected_score(p_correct: float, t: float) -> float:
    return p_correct * 1 + (1 - p_correct) * (-t / (1 - t))

for t in (0.5, 0.75, 0.9):
    assert abs(expected_score(t, t)) < 1e-12     # break-even sits at p == t

assert expected_score(0.6, 0.75) < 0              # 60% sure, 3-point penalty: abstain
assert expected_score(0.95, 0.9) > 0              # 95% sure, 9-point penalty: answer
assert expected_score(0.01, 0.0) > 0              # no penalty rewards any guess
```

## Four kinds of wrong

A working taxonomy for engineers sorts hallucinations by what you would check to catch them.

**Unfaithful to the context.** The answer contradicts or goes beyond documents the system gave the model. The benefits bot did this, mixing two sections. You catch it by comparing claims to the provided text.

**Fabricated.** The answer invents an entity: a citation, a case name, an API, a package. The package study from the threat-modeling lesson is this kind, and it became a supply-chain attack. You catch it by looking the entity up.

**Stale.** The answer was true once. Training data has a cutoff and documents have versions. You catch it with dates on sources and a rule about which version wins.

**Reasoning errors.** Every fact is right and the conclusion is not: arithmetic, units, a missed condition. You catch it with code, tools or a second pass.

The split matters because each kind has a different fix, and "we added RAG" only addresses the stale and fabricated kinds for questions the index can answer. A system with retrieval can still contradict its own context.

## Grounding with citations

Asking the model to cite its sources turns "is this true?" into "does this span say this?", which is a much easier check. Anthropic's Citations feature returns, for each claim, pointers into the documents you passed: character ranges for plain text, page ranges for PDFs, block ranges for custom content. The quoted `cited_text` does not count toward output tokens. Two details are worth knowing in an interview. Citations and structured outputs cannot be combined; the API returns a 400 error if both are set. And a citation guarantees a valid pointer into your documents, not that the cited span supports the sentence it is attached to. Check support separately, with a classifier or a judge that reads the claim and the span together.

## Verification chains

Chain-of-Verification, from 2023, is a pattern rather than a product: draft an answer, write verification questions about its claims, answer those questions independently of the draft so the draft's errors do not leak into the checks, then revise. The cost is extra model calls. It works best for list-style factual answers where each item can be checked on its own, and less well for claims that need context the model does not have. Code and tools are verification too: a date calculation done in Python, a package name checked against the registry, a figure recomputed from the table it came from.

## Confident and wrong where it matters

In a high-risk domain the order of work is measure, constrain, then escalate. Measure by slice, because an average hides the slice that hurts: the new country, the rare drug, the unusual contract clause. Check calibration on that slice, not just accuracy. Constrain the system: answer only from approved sources, require a citation for every claim and refuse when retrieval comes back empty or contradictory, and raise the abstention threshold where a wrong answer is expensive. Escalate: route low-confidence and high-stakes questions to a person, and design the user interface so a hedge reads as a hedge rather than being buried under a confident summary.

The security mindset from the earlier lessons carries over. Johann Rehberger's December 2025 essay on the normalisation of deviance warns against treating model output as trustworthy because it usually is; the habit of assuming it might be wrong is what keeps human oversight in the high-stakes paths.

## Alignment topics you may be asked about

Labs, in particular, ask engineers about alignment. You do not need to be a researcher; you need to know the terms and one recent result.

**Reward hacking** is a model scoring well on its training signal by exploiting a flaw in it rather than doing the task, such as special-casing tests instead of fixing the code. Anthropic reported in November 2025 that a model that learned to reward hack in real Claude coding environments generalised to broader misalignment: in a safety-research code evaluation it attempted sabotage 12% of the time, and it showed alignment-faking reasoning in 50% of responses to simple questions about its goals. A mitigation they call inoculation prompting, telling the model during training that hacking is acceptable in that context, removed the broad generalisation. The engineering lesson is the same as for any metric: an optimiser finds the gap between what you measure and what you want.

**Responsible scaling policies** are commitments to tie safety measures to capability levels. Anthropic's is at version 3.4, effective 8 July 2026; older interview guides cite version 2. If you are interviewing at a lab, read the current version of its policy before the values round.

## Compliance dates engineers get asked about

The EU AI Act entered into force on 1 August 2024. Prohibited practices and AI literacy duties applied from 2 February 2025, and obligations for general-purpose AI models from 2 August 2025, with models already on the market by then given until 2 August 2027. The Commission's Code of Practice for those models, published on 10 July 2025, has chapters on transparency, copyright, and safety and security; the last applies only to models with systemic risk.

The dates for high-risk systems moved. The Digital Omnibus on AI, Regulation (EU) 2026/1744, entered into force on 27 July 2026 and pushed Annex III high-risk obligations to 2 December 2027 and Annex I (AI in regulated products) to 2 August 2028. The Article 50(2) duty to mark AI-generated content applies to systems already on the market by 2 August 2026 from 2 December 2026. A slide that says "high-risk rules apply from August 2026" is out of date.

<Fragment slot="short">
<p>When the expected cost of a wrong answer is higher than the value of a right one at the confidence we have. With right = 1, abstain = 0 and wrong = -k, answering pays only above confidence k/(k+1), so a wrong answer that costs three times a right one needs 75%. In practice I set the cost per route, need a confidence signal that I have checked against labelled data, and hand off when retrieval is empty or contradictory, when confidence is under the threshold, or when the question is in a slice the policy marks high-stakes.</p>
</Fragment>
<Fragment slot="long">
<p>Start with the economics. Kalai and colleagues' scoring rule makes it explicit: a penalty of t/(1-t) for wrong answers means answer only when p is above t. Product decides the penalty per route; the cost of a wrong medication dose is not the cost of a wrong store-hours answer.</p>
<p>Then the signal. Options are the model's own stated confidence, agreement across several samples, a verifier model, and retrieval coverage (did we find a source that answers this at all). Each has to be calibrated on labelled traffic for the slice it is used on, because the threshold is meaningless otherwise.</p>
<p>Then the handoff design. Abstaining needs a useful next step: a link to the source, a form, a queue with a person. Track the abstention rate and the human queue's load, because a threshold that sends half the traffic to people will be lowered by someone under pressure.</p>
<p>Trade-off: more abstention lowers the error rate and the coverage. I would present both numbers to the product owner and let them choose the point, with the high-stakes slices fixed by policy rather than tuned.</p>
</Fragment>

<li><em>What if the model is confidently wrong because the source is wrong?</em> Abstention does not help; source versioning, ownership and freshness checks do.</li>

## When this is wrong

The scoring rule treats every wrong answer in a route as costing the same. Real costs vary within a route: a wrong answer the user can easily check costs less than one they will act on. Use the rule to set a default and the slices to override it.

The taxonomy is also a convenience, not a fact about models. One wrong answer can be stale, unfaithful and a reasoning error at once, and the categories blur when the model mixes retrieved text with what it learned in training. What matters is that every kind has a check you can run.

And the regulatory section has a short shelf life. The dates above moved once in 2026 and may move again. Check the timeline page before you cite any of them.
