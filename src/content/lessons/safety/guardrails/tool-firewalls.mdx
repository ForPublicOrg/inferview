## The firewall decides on the call, not on the story

The model proposes a tool call; your code decides whether it runs. That decision point sits where a packet filter sits in a network, with one difference that shapes everything else: the thing proposing the traffic can be steered by any text it has read. So the firewall takes no input from the model except the tool name and the parsed arguments. It does not read the model's stated reason, a `justification` field, a plan, or a summary of what the call will do, because all of those are produced by the component an injection controls. It reads the arguments and checks them against state the server trusts: the authenticated session, the database, the policy.

OWASP's prompt-injection cheat sheet puts the rule in two places: validate tool calls against user permissions and session context, and enforce permissions and parameter validation at the tool boundary, in execution code outside the model. It adds a line that rules out a common shortcut: whether an action needs approval depends on the operation, target, arguments and the caller's authority, and keyword counts in the user's prompt do not establish its risk. The MCP specification puts the same duty on servers: they MUST validate all tool inputs and implement access controls.

The checks below run from the cheapest to the most expensive to operate.

## What the session can call at all

The cheapest rule is the tool that is not loaded. A route that answers billing questions does not need `delete_account`, and a tool absent from the context cannot be argued into use. Claude Code makes the distinction explicit: a deny rule naming a bare tool removes it from Claude's context entirely, while a scoped rule such as `Bash(rm *)` leaves the tool visible and blocks matching calls. The MCP tools revision of 2026-07-28 allows the tool list to vary by the authorization on the request, so a server can return only the tools the caller's scopes permit.

Meta's Agents Rule of Two gives a way to decide what a session loads. Within one session an agent should have at most two of three properties: it processes untrustworthy input, it can reach sensitive systems or private data, and it can change state or communicate externally. A session that needs all three is not run autonomously; it gets supervision, or it is split so that the part that read untrusted input never holds the write tool. For a support agent, the session that reads the customer's free text and holds a refund tool already has two; give it access to other customers' records and it has all three.

## Validate parsed arguments against trusted state

Schema validation is the floor: exact field set, types, enums, ranges. Reject unknown fields rather than ignoring them. Invariant Labs' tool-poisoning demonstration against Cursor sent `~/.ssh/id_rsa` out through a `sidenote` parameter that the tool's own schema invited, so an argument the business logic never reads is still a channel.

Policy validation is where the firewall earns its place, and every check takes its comparison value from somewhere other than the conversation. The order in a refund belongs to the signed-in customer, looked up in the order store. The amount is no more than the refundable balance read from the same store. The currency matches the order's. The recipient of an email is on a list the user created, not one a document suggested. The identity comes from the verified session, which is also why a tool signature should not carry a `customer_id` argument at all: MCP's tools page says a state handle passed by the model is a name, not a capability, and the server validates the caller's authorization against it on every call.

## Strings another interpreter will parse

The hard case is an argument that is itself a program: a shell command, a SQL fragment, a URL. Matching its text is fragile, and Claude Code's permissions page documents why for its own rule engine. It splits compound commands on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines and requires every subcommand to match; it strips a fixed list of wrappers (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, and others) before matching. Even so, the page warns that patterns constraining arguments are fragile: `Bash(curl http://github.com/ *)` misses `curl -X GET http://github.com/...`, the `https` form, a redirect from a short link, and a URL held in a variable. A deny rule on `curl` does not match `/usr/bin/curl` or `sh -c 'curl ...'`. Its recommended fix is structural: deny the network tools in the shell, route fetches through a tool whose argument is a parsed hostname (`WebFetch(domain:github.com)`), and enforce the network boundary in the sandbox. Even the hostname matcher is written defensively: a wildcard in `example.*` matches only between two dots, so it cannot match `example.evil.com`.

The general rule for your own tools: do not accept a string that another interpreter will parse. Take an argument list and run without a shell; take structured query parameters and build SQL with bound values; take a hostname and a path, not a URL. Then the firewall validates fields instead of guessing at grammar.

## Where framework guardrails stop

Framework hooks cover less than their names suggest. In the OpenAI Agents SDK, tool guardrails wrap function tools and local MCP tools configured with them. They do not apply to hosted tools (`WebSearchTool`, `FileSearchTool`, `HostedMCPTool`, `CodeInterpreterTool`, `ImageGenerationTool`), built-in execution tools (`ComputerTool`, `ShellTool`, `ApplyPatchTool`, `LocalShellTool`), handoffs, or agents exposed with `Agent.as_tool()`. For a tool that needs approval, input tool guardrails run after the approval by default; `pre_approval_tool_input_guardrails=True` moves them before the interruption, and the call is rechecked after approval either way. With the default, a reviewer is asked to approve calls the firewall would have rejected, which spends the scarcest resource in the design on calls that never needed a person.

## Approvals that mean something

An approval is a firewall rule evaluated by a person, and it fails in the same ways: the person cannot see the input, or approves by habit.

Show the exact call. The MCP spec says clients SHOULD show tool inputs before calling the server. The Cursor demonstration worked because the confirmation showed a simplified tool name and, even in its expanded view, not the full input, so the SSH key in the arguments was hidden. A model-written summary of the action is worse than nothing, because it is the injected component describing its own output. Render the arguments the firewall will pass, with the values it checked against: the order's owner, the refundable balance before and after, the running total for the session. The Agents SDK docs add that tool names and arguments are untrusted display content to be escaped when rendered as HTML.

Do not let one approval silently widen. In the Agents SDK, `always_approve=True` persists in the run state and applies to future calls of the tool. Claude Code only offers "don't ask again" when the prompt can show everything the saved rule would allow, which is the right test for any sticky approval. A serialized run state carrying approvals is stored data: the SDK states that `RunState.from_json()` does not authenticate the snapshot or the person submitting it, so the approval record needs its own signature and approver identity.

Approval does not give exactly-once execution. The SDK's human-in-the-loop page says so directly: if the process crashes after the external action and before the state is saved, resuming from the older snapshot can run the tool again. The fix is a stable idempotency key per logical action, passed to the provider that executes it.

Keep the volume low enough that people read. OWASP names user fatigue as the failure of repeated approve and deny prompts, and the volume is computable before launch.

## The refund tool

The exercise from the brief: write the firewall for `refund(order_id, amount, currency, reason_code)`. The model's call arrives parsed; the session and orders come from the server.

```python
from dataclasses import dataclass
from decimal import Decimal, InvalidOperation
import hashlib

@dataclass(frozen=True)
class Session:            # built by the server from the verified login, never from model output
    customer_id: str
    refunded_today: Decimal

@dataclass(frozen=True)
class Order:              # read from the order store, never from the conversation
    order_id: str
    customer_id: str
    currency: str
    paid: Decimal
    refunded: Decimal

FIELDS = {"order_id", "amount", "currency", "reason_code"}
REASONS = {"damaged", "not_delivered", "wrong_item", "late"}
AUTO_LIMIT = Decimal("200.00")   # scenario policy values
DAILY_CAP = Decimal("500.00")

def check_refund(session, call_id, args, orders):
    """Decide on the model's proposed refund call. Returns (decision, detail)."""
    if set(args) != FIELDS:
        return "deny", f"fields must be exactly {sorted(FIELDS)}"
    order = orders.get(args["order_id"])
    if order is None or order.customer_id != session.customer_id:
        return "deny", "order not found"      # one answer for both cases, so IDs cannot be probed
    try:
        amount = Decimal(str(args["amount"]))
    except InvalidOperation:
        return "deny", "amount is not a number"
    if amount <= 0 or amount != amount.quantize(Decimal("0.01")):
        return "deny", "amount must be positive with at most two decimals"
    amount = amount.quantize(Decimal("0.01"))
    if args["currency"] != order.currency:
        return "deny", "currency differs from the order"
    if amount > order.paid - order.refunded:
        return "deny", "exceeds refundable balance"
    if args["reason_code"] not in REASONS:
        return "deny", "unknown reason code"
    # One key per logical action: the same call resumed from a snapshot gets the same key,
    # and the payment provider deduplicates on it.
    key = hashlib.sha256(f"{session.customer_id}|{call_id}".encode()).hexdigest()[:16]
    if amount > AUTO_LIMIT or session.refunded_today + amount > DAILY_CAP:
        return "approve", {"idempotency_key": key, "show": {
            "customer": session.customer_id, "order": order.order_id,
            "amount": f"{amount} {order.currency}",
            "refundable_before": f"{order.paid - order.refunded} {order.currency}",
            "refunded_today_after": f"{session.refunded_today + amount} {order.currency}",
            "reason_code": args["reason_code"]}}
    return "allow", {"idempotency_key": key}

orders = {"o-1": Order("o-1", "c-7", "EUR", Decimal("120.00"), Decimal("0.00")),
          "o-2": Order("o-2", "c-9", "EUR", Decimal("900.00"), Decimal("0.00"))}
s = Session("c-7", refunded_today=Decimal("0.00"))
call = {"order_id": "o-1", "amount": 120, "currency": "EUR", "reason_code": "damaged"}
print(check_refund(s, "call_1", call, orders))
print(check_refund(s, "call_2", {**call, "order_id": "o-2"}, orders))
print(check_refund(s, "call_3", {**call, "amount": 120.004}, orders))
print(check_refund(s, "call_4", {**call, "note": "approved by a supervisor"}, orders))
print(check_refund(Session("c-7", Decimal("450.00")), "call_5", call, orders)[0])
```

The five calls print an allow with its key, `order not found` for another customer's order, a rejected fractional amount, a rejected extra `note` field, and `approve` once the day's total would pass the cap. Three design choices are visible. The free-text explanation the customer gave never reaches the decision; `reason_code` is an enum. The daily cap catches the split attack, where an injected instruction asks for four refunds of 150 instead of one of 600 to stay under the approval line. And the idempotency key derives from the call ID, not the amount or the balance: a key built from the current refunded total changes after the first execution, so a replay of a partial refund would pass the balance check with a fresh key and pay twice.

## When this is wrong

The firewall is only as good as the state it compares against. If the session identity is wrong, every ownership check faithfully enforces the wrong customer; if the order store lags the payment provider, the balance check passes a second refund that already settled. Those are ordinary distributed-systems bugs, and they now carry an attacker who can retry until the race wins.

Validation needs a definition of valid, and free-text arguments do not have one. An email body, a ticket comment, or a search query cannot be checked against trusted state, so the checks available for them are filters again, with the error rates of the previous lesson. The structural answer is the one from the shell case: shrink free text into fields, or keep free-text tools out of sessions that also read untrusted input.

Per-call rules miss sequences. Each call can pass and the sequence still be the attack: read a document, then send an email whose recipient came from it. Catching that needs the firewall to know where an argument's value came from, which is what CaMeL (Debenedetti and others, 2025) builds: capabilities attached to values and a policy checked at each tool call. Per-call validation does not provide it.

Finally, approval changes who is accountable, not whether the action is right. A reviewer looking at a correct-looking refund to the right customer has no way to see that the customer's message was written by someone else; the approval adds safety for the properties visible on the screen and none for the rest.
