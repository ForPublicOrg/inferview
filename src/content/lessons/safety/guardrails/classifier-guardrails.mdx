## The product decision is the threshold

A guardrail classifier emits a score, and the system blocks when the score crosses a threshold. The model is a vendor's choice; the threshold is yours, and it sets two rates at once: the share of attacks or harmful outputs that get through, and the share of legitimate traffic you refuse. A model card reports one or two points on that curve, measured on the vendor's data. Your job is to find the point on your own traffic that minimises what the errors cost you, and to know what happens to both rates when you put two guards in a row.

The two Meta cards that come up most often report different kinds of points, and the difference matters when you compare them.

**Llama Prompt Guard 2** is a classifier (mDeBERTa base for the 86M model, DeBERTa-xsmall for the 22M) that labels text benign or malicious, where malicious means an explicit attempt to override instructions. It reads 512 tokens at a time, so long inputs are split and each window scored. Meta dropped the separate injection label of version 1 because it found that objective too broad to be useful, so it is a jailbreak-pattern detector, not a detector of instructions hidden in retrieved documents. The card fixes the false positive rate and reports recall there:

| Model | AUC (English) | Recall at 1% FPR (English) | Latency, 512 tokens, A100 |
|---|---|---|---|
| Prompt Guard 1 | .987 | 21.2% | 92.4 ms |
| Prompt Guard 2 86M | .998 | 97.5% | 92.4 ms |
| Prompt Guard 2 22M | .995 | 88.7% | 19.3 ms |

On AgentDojo, Meta reports an attack prevention rate at a 3% utility reduction of 81.2% for the 86M model and 78.4% for the 22M. These are Meta's measurements on Meta's evaluation sets. The card's own limitations section says adaptive attackers can build inputs to evade it and that performance shifts with application-specific benign and malicious distributions.

**Llama Guard 4** is a 12B model fine-tuned from Llama 4 that generates `safe` or `unsafe` followed by the violated categories, S1 Violent Crimes through S14 Code Interpreter Abuse. Its card reports the model's default decision on an in-house output-filtering set: English recall 69% at an 11% false positive rate (F1 61%), multilingual recall 43% at 3%. That is one point, not a curve, and it is not directly comparable with Prompt Guard's recall at 1% FPR. To move along the curve you need a score, and the original Llama Guard paper gives it: the classifier score is the probability of the first generated token. Request logprobs for that token, threshold it yourself, and the default decision becomes one setting among many.

A third design point is Anthropic's Constitutional Classifiers, which guard Claude against universal jailbreaks. Anthropic's own figures show the price of the first generation: 23.7% more compute and 0.38% more refusals of harmless queries. The January 2026 version changed the architecture rather than the threshold. An exchange classifier judges the output together with its input; a linear probe on the model's activations screens all traffic; flagged exchanges go to a more expensive second stage. Anthropic reports a 0.05% refusal rate on harmless queries over a month of Claude Sonnet 4.5 traffic and about 1% added compute if applied to Claude Opus 4.0 traffic, and the paper reports a 40x compute reduction against the baseline exchange classifier. Its red team spent 1,700 hours over 198,000 attempts and found one high-risk vulnerability. The cascade is the part to steal, and the stacking section shows why it is cheap.

## Choosing the point from two costs

The expected cost per request at a threshold is the benign share times the false positive rate times the cost of a false block, plus the attack share times the miss rate times the cost of a miss. The base rate decides which term dominates, and in most products attacks are rare.

<p>There are 100 attacks and 999,900 benign requests. Point A blocks 9,999 benign requests and misses 10 attacks. Point B blocks 49,995 benign requests and misses 3. Moving from A to B adds 39,996 false blocks to avoid 7 misses, so B wins only if a miss costs more than 39,996 / 7 = 5,714 false blocks. At A, the blocks are 90 attacks and 9,999 benign requests, so 90 / 10,089 = 0.9% of blocked requests are attacks. A review queue of blocked requests is almost entirely legitimate users.</p>
</Predict>

That ratio is the argument for a low false positive rate on the classifier and for putting expensive misses somewhere else. The cost of a miss is not a property of the classifier. It is set by what a successful attack can do after it passes: if the refund tool checks that the order belongs to the signed-in customer, a missed injection costs a confused reply, and point A is cheap. If the tool trusts the model's arguments, the same miss can cost a refund to a stranger, and no threshold makes the classifier the right control. The tool layer is the subject of [the next lesson](/learn/safety/guardrails/tool-firewalls); OWASP's cheat sheet states the same position, that input screening is not a security boundary.

The procedure, run per category and per route rather than once for the product:

```python
import random

def operating_point(benign, attacks, base_rate, cost_false_block, cost_miss):
    """Threshold with the lowest expected cost per request, from scores on your own labelled traffic.
    A request is blocked when its score is at or above the threshold."""
    events = sorted([(s, 0) for s in benign] + [(s, 1) for s in attacks], reverse=True)
    fp = tp = 0
    best = (base_rate * cost_miss, float("inf"), 0.0, 0.0)  # threshold above every score: block nothing
    for i, (score, is_attack) in enumerate(events):
        tp += is_attack
        fp += 1 - is_attack
        if i + 1 < len(events) and events[i + 1][0] == score:
            continue  # tied scores share one threshold
        fpr, recall = fp / len(benign), tp / len(attacks)
        cost = (1 - base_rate) * fpr * cost_false_block + base_rate * (1 - recall) * cost_miss
        if cost < best[0]:
            best = (cost, score, fpr, recall)
    return best

def stacked_fpr(flags_a, flags_b):
    """OR-stack false block rate measured on the same benign requests, and the independence estimate."""
    n = len(flags_a)
    measured = sum(a or b for a, b in zip(flags_a, flags_b)) / n
    pa, pb = sum(flags_a) / n, sum(flags_b) / n
    return measured, 1 - (1 - pa) * (1 - pb)

rng = random.Random(7)
benign = [rng.betavariate(2, 8) for _ in range(20_000)]
attacks = [rng.betavariate(6, 2) for _ in range(400)]
for miss in (50, 5_000):
    _, t, fpr, rec = operating_point(benign, attacks, base_rate=1e-4, cost_false_block=2, cost_miss=miss)
    print(f"miss costs {miss}: threshold {t:.3f}, FPR {fpr:.4f}, recall {rec:.3f}")

# Two guards with a shared blind spot: 3% of benign requests are hard, and both guards flag most of them.
hard = [rng.random() < 0.03 for _ in range(20_000)]
a = [(h and rng.random() < 0.8) or rng.random() < 0.01 for h in hard]
b = [(h and rng.random() < 0.8) or rng.random() < 0.01 for h in hard]
measured, independent = stacked_fpr(a, b)
print(f"OR stack: measured FPR {measured:.4f}, independence estimate {independent:.4f}")
```

The scores are synthetic. With a miss priced at 50 false blocks the cheapest threshold is 0.731, at 0.02% FPR and 59.5% recall; at 5,000 it drops to 0.552, at 0.87% FPR and 89.2% recall. A hundredfold change in the miss cost moved recall by 30 points, which is why the miss cost has to be argued with the people who own the downstream damage, not picked by the team that owns the classifier. The last line prints a measured stack FPR of 4.80% against an independence estimate of 6.66%, the subject of the next section.

## Stacking: OR, cascade and latency

Two guards can be combined in two ways, and they move the rates in opposite directions.

An **OR stack** blocks when any guard fires. Recall rises and false blocks compound: with independent errors the stack passes a benign request with probability equal to the product of each guard's pass rate, so the false block rate is 1 minus that product, a little under the sum. The widget uses toy rates and latencies to show the shape.

<SafetyGuardStack />

A **cascade** blocks only when both stages agree, with the second stage run only on what the first flagged. Take toy numbers on the same million requests: stage one at 99% recall and 5% FPR flags 49,995 benign requests and 99 attacks. Stage two, measured on what stage one flags, blocks 2% of those benign requests and catches 95% of those attacks. The cascade blocks about 1,000 benign requests (0.1% FPR) and catches 94 attacks (94% recall), and the expensive model runs on 50,094 requests, 5% of traffic. Compare point B above: 97% recall at 5% FPR. The cascade gives up three points of recall for a fiftyfold drop in false blocks, and it is why Anthropic can say the first stage "can afford a higher false-positive rate". Measuring stage two on stage one's flagged set, rather than on the whole distribution, also removes the independence assumption from the arithmetic.

Latency follows placement. Input guards can run in parallel with each other and with the model call. The OpenAI Agents SDK does this by default (`run_in_parallel=True`), and its docs state the consequence: the agent may already have consumed tokens and executed tools before the tripwire cancels it. Set `run_in_parallel=False` on any route where the agent has tools with side effects. Output guards cannot overlap the generation they check, so their latency lands after the last token; with streaming you either check chunks as they arrive and accept retracting text already shown, or hold back output. In the same SDK, input guardrails run only for the first agent in a chain and output guardrails only for the agent producing the final output, so agents reached by handoff in the middle of a chain are not covered by either.

A guard built on a chat model is also an injection target. OWASP's cheat sheet says a guardrail LLM is itself susceptible to prompt injection and recommends a guardrail with a different attack surface from the primary model, such as a purpose-trained classifier rather than a general model from the same family.

## When this is wrong

The cost formula assumes you know the base rate and that it is stable. Attacks arrive in campaigns: a jailbreak posted publicly can raise the attack share by orders of magnitude for a week, and the threshold that was optimal at 1 in 10,000 is no longer optimal. Thresholds set from a quiet month need a review trigger tied to the measured attack rate.

The OR arithmetic assumes independent errors. Two classifiers trained on similar data fail on the same unusual but legitimate requests: security researchers' questions, medical content, languages both handle badly. The combined false block rate is then lower than the formula predicts, as in the code above, but concentrated on the same users, who get blocked by every guard. Measure the stack on real traffic and report false blocks per user segment, not one rate.

Recall from a fixed evaluation set is an upper bound against an adaptive attacker. Meta's card says so directly, and Anthropic's red-teaming figures are a measure of effort spent, not a proof. A threshold chosen on yesterday's attack set protects against yesterday's attacks; the attacker chooses inputs after seeing your threshold behave.

Finally, the score distribution belongs to one model version. A new checkpoint of the guard, or of the model whose outputs it reads, moves both curves, and a threshold copied across versions is a guess.
