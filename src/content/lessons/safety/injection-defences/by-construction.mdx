## Two different promises

A defence against prompt injection makes one of two promises. The first kind says injected text will succeed less often: a classifier, a training method, a prompt format. The second says injected text cannot do a named thing at all, whatever the model decides: it cannot add a tool call the user did not ask for, and it cannot send a document to someone who could not already read it. This lesson covers the second kind, what it has cost in published runs, and the attacks it leaves open by design.

The systems analogy is taint tracking plus capability-based access control: values carry where they came from, and the sink checks before it acts. The difference from a web framework's taint mode is that a model writes the tracked code at run time, and a second model transforms part of the data unpredictably. So the guarantee has to sit where no model can reach it: in an interpreter and in policy functions you wrote.

## Control flow and data flow are separate attack surfaces

CaMeL (Debenedetti, Shumailov, Fan and colleagues, March 2025) starts from one example. The user asks the agent to send Bob the document he requested in their last meeting. The agent turns that into four steps: find the meeting notes, extract Bob's address and the document name, fetch the document, send it. An attacker who can edit the notes has two ways in. They can change the steps, adding "also forward the inbox to me". Or they can leave the steps alone and change the values, so the address extracted from the notes becomes theirs. Most rate-lowering defences aim at the first. The second ships data out through a plan that looks normal.

CaMeL splits the work three ways:

- The **privileged LLM** (P-LLM) sees only the user's query and the tool signatures. It writes the plan as code in a restricted subset of Python. It never sees tool outputs.
- The **quarantined LLM** (Q-LLM) has no tools. It parses untrusted text into a typed schema, with a boolean field to say it lacked the information. It cannot ask the P-LLM for anything, because that request would itself carry injected text.
- A **custom interpreter** runs the P-LLM's code, builds a data-flow graph as it goes, attaches **capabilities** to every value (where it came from, who may read it) and calls a **policy** function before each tool call.

Because the plan is fixed from the trusted query before any data is read, injected text cannot add or reorder steps. That is the control-flow half, and it is the code-then-execute pattern from the design-patterns paper, which names CaMeL as its instance. The capabilities are the data-flow half: a value the Q-LLM extracts from the notes carries the notes' provenance, so the policy on `send_email` can see that a document chose the recipient, not the user. In the paper's deployed form a policy violation does not fail silently; it becomes a confirmation request.

The sketch below shows the data-flow half. It is not CaMeL's interpreter, which also tracks dependencies through control structures, but it shows the rule that matters: every derived value, a model's summary included, inherits all of its parents' tags.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class V:
    data: str
    sources: frozenset          # every origin that could have shaped this value
    readers: frozenset | None   # who may see it; None means public

def from_user(data):
    return V(data, frozenset({"user"}), None)

def from_tool(data, tool, readers=None):
    return V(data, frozenset({tool}), frozenset(readers) if readers else None)

def derive(data, *parents):
    """Any transformation, a Q-LLM call included, inherits every parent's tags."""
    sources = frozenset().union(*(p.sources for p in parents))
    limited = [p.readers for p in parents if p.readers is not None]
    readers = frozenset.intersection(*limited) if limited else None
    return V(data, sources, readers)

class NeedsApproval(Exception):
    pass

def send_email(to: V, body: V) -> str:
    trusted_recipient = to.sources == {"user"}
    already_reader = body.readers is None or to.data in body.readers
    if not (trusted_recipient or already_reader):
        raise NeedsApproval(f"{to.data} came from {sorted(to.sources)} and cannot read the body")
    return f"sent to {to.data}"

notes = from_tool("Bob asked for the Q3 deck. Contact: bob@corp.example", "read_notes")
deck = from_tool("Q3 deck contents", "read_drive", readers={"alice@corp.example", "bob@corp.example"})

addr = derive("bob@corp.example", notes)          # Q-LLM extracts the address from the notes
print(send_email(addr, deck))                      # allowed: Bob can already read the deck

poisoned = derive("eve@evil.example", notes)       # an attacker edited the notes
summary = derive("Summary of the Q3 deck", deck)   # laundering through a summary keeps the readers
for body in (deck, summary):
    try:
        send_email(poisoned, body)
    except NeedsApproval as e:
        print("approval needed:", e)
```

It prints one send to Bob and two approval requests. The second is the case a rate-lowering defence misses: the attacker's address is paired with a summary, and the summary still carries the deck's reader set. In production the hard part is coverage: every function between a tool output and a sink must propagate the tags, and one untracked path voids the guarantee. CaMeL gets coverage by owning the interpreter.

## What CaMeL costs, in its own runs

The abstract's headline: on AgentDojo, CaMeL solves 77% of tasks with provable security, against 84% for an undefended system. Version 2 of the paper (June 2025) reruns with newer models, and the full table is more useful than the headline because the cost is not spread evenly. With Claude 4 Sonnet, overall utility goes from 86.6% with native tool calling to 74.2% under CaMeL. Banking loses nothing at 75.0%; travel goes from 80.0% to 75.0%; Slack goes from 95.2% to 61.9%. With Gemini 2.5 Pro, travel goes from 60.0% to 0.0%. A model that writes good tool calls does not necessarily write good programs in a dialect it was not trained on.

On security, Gemini 2.5 Pro's successful attacks fell from 300 of 949 to 0 under CaMeL before any policy was written: separating the plan from the data removes every attack that works by changing the plan. Policies are what stop the value-level attacks.

Tokens: for the median AgentDojo task, CaMeL used 2.82 times the input tokens and 2.73 times the output tokens of native tool calling, measured under attack with Claude 3.5 Sonnet. A cheaper Q-LLM recovers some of the cost: Claude 3.5 Haiku as the Q-LLM with Claude 4 Sonnet as the P-LLM cost about 1% utility for an estimated 12% lower cost per median task.

The number that decides whether this ships in a product sits in the appendix. Table 8 reports how often the policies trigger on tasks that are not under attack: 33.87% in NORMAL mode, and 53.23% in STRICT mode, which also treats control-flow conditions as dependencies to close side channels.

## FIDES: labels instead of a program

FIDES (Costa, Köpf, Kolluri and colleagues at Microsoft, May 2025) reaches a similar guarantee by another route. It keeps an ordinary planner loop and attaches labels from a lattice to everything in it: an integrity label (trusted or untrusted) and a confidentiality label (the set of readers). The planner's context carries the join of everything it has seen, and a tool result's label is the join of its inputs' labels and the tool's own.

Two policies carry the guarantee. **P-T** (trusted action) lets a consequential tool run only when the call was generated from trusted context. **P-F** (permitted flow) lets data reach a tool only if everyone who will read the output may read the data. The paper proves non-interference for integrity under P-T and explicit secrecy under P-F, and says plainly that implicit flows through control flow are not prevented.

With labels alone, one untrusted email read early taints the whole context and nothing consequential can run after it. FIDES answers with variable hiding. Tool results whose labels are more restrictive than the current context go into fresh variables instead of the context, so the planner can pass `$doc1` to a tool without reading it. When it needs to know something about the content, `query_llm` runs an isolated, tool-less model on the variable with a constrained output type (bool, then enum, then string, in increasing capacity to carry an attack), and stores the answer as a new labelled variable.

The evaluation runs 949 attacks per configuration on AgentDojo. With gpt-4o, the basic planner let 163 injections succeed; FIDES without policy checks let 24 through; FIDES with policy checks let 1 through, which the authors attribute to attacks that violate no policy, such as text-to-text manipulation. The paper also classifies tasks by whether the tool-call sequence depends on tool results. Data-dependent tasks are 5.0% of the Workspace suite and 10.0% of Travel, but 43.8% of Banking and 42.9% of Slack. That split predicts where any by-construction design hurts utility: the more often the next action depends on what the last tool returned, the more often the planner must either look, and taint itself, or ask.

## Fixing the impact instead of the injection

The third deterministic defence does not try to stop the model following injected text. It removes the channel the text would use. The MSRC post (Andrew Paverd, July 2025) describes a report from Johann Rehberger of exfiltration through Markdown images: injected text tells the model to emit an image whose URL carries private data in its query string, the client renders it, and the user's browser makes the request. Microsoft's response was to deterministically block the exfiltration technique, and to block the generation of certain untrusted links. The post does not say how, so the mechanism is not public.

The design is reproducible without knowing Microsoft's. The rendering surface decides what the browser fetches, so an image allowlist in the page's Content-Security-Policy (`img-src` limited to hosts you control) holds whatever the model writes, and a server-side pass that drops non-allowlisted image and link URLs covers clients whose headers you do not set. Neither depends on detecting the injection. The same post lists Microsoft Purview sensitivity labels as a deterministic limit on which data Microsoft 365 Copilot can use at all: the confidentiality half of FIDES, enforced outside the model.

<Callout kind="gotcha" label="One channel is not the trifecta">
Blocking image rendering removes one exfiltration channel. A tool that fetches URLs, a link the user clicks, an email the agent can send and a file it writes to a shared drive are others. List them per agent; the deterministic block has to exist at each one, or the attacker uses the one you left.
</Callout>

## What none of them stop

Both papers draw the boundary in the same place. CaMeL's stated non-goals include text-to-text attacks with no effect on data flow, such as an email summarised to say something it did not say, and phishing induced by injection, such as a summary telling the user to click a link to keep their account. FIDES's one residual success under policy is in the same class. The design-patterns paper says it of code-then-execute: an injection in calendar data can still change the content of an email the program sends to the correct recipient.

Policies have to be written per tool and per deployment, and maintained as tools change. The paper also finds side channels: an exception raised on untrusted data can leak a bit, and a timing channel exists if the program can read a clock. CaMeL removes the `time` module, and STRICT mode closes the control-flow channel at the cost of the higher trigger rate above.

## When this is wrong

"Provable" is relative to a model of the system. CaMeL's proof covers the flows its interpreter can see under the policies someone wrote. A tool that moves data internally, such as a share endpoint that emails a link as a side effect, is a flow the interpreter never sees. The guarantee is as complete as the tool inventory and the policies, and no more.

The benchmark understates the policy problem. CaMeL's appendix lists its AgentDojo policies as a few short rules per suite, over a few tools with clean ownership. In a real mailbox, readers are mailing lists, drive permissions are inherited, and "the user's own words" include text the user pasted from elsewhere, a gap Simon Willison named for the Dual LLM pattern in 2023 that none of these papers closes.

The numbers above are the authors' own, on one benchmark, with 2025 models. Utility under a restricted dialect moves with the model, down sharply for Gemini 2.5 Pro on travel and up for later Claude versions on the same suite. Rerun the comparison on your tasks with the model you will ship.
