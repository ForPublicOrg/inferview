## The decision

For one agent: which structural pattern it runs under, which rate-lowering layers sit in front, and where a person confirms. The output is a short design note that names the guarantee, the residual risk and the person who accepted it. The decision is per agent and often per session, because the same product can run a research session and an action session with different properties.

## The inputs that change it

**Which trifecta legs the session holds.** Willison's lethal trifecta is private data, untrusted content and a way to communicate externally. Meta's Rule of Two (October 2025) generalises the third leg to changing state or communicating externally, and says a session should hold no more than two of the three unless it is supervised. Count legs per session, not per product; a session that starts as research and later touches private data has all three unless the outbound leg is closed before the switch, which Meta's post allows within one session.

**Whether actions can be undone.** A draft, a label or a reversible database write costs a review when an injection lands. A sent email, a payment or a deleted file costs an incident. Irreversible actions get a deterministic control or a person every time; reversible ones can run under a rate.

**How much the next action depends on data.** A task whose tool sequence is fixed by the request fits plan-then-execute or an action-selector at little cost. A task that must read a result to choose the next step pushes toward dual LLM or code-then-execute, where utility falls; the FIDES paper classified 5.0% of AgentDojo's Workspace tasks as data-dependent and 43.8% of its Banking tasks.

**The residual rate the business has accepted in writing.** Rate-lowering layers leave a residual. Someone with authority over the product signs a number: successful injections per period at a stated attacker volume, and the worst impact of one. Without that signature, the choice between patterns turns into an argument about taste.

## The options and when each wins

| Option | Wins when | Gives up |
|---|---|---|
| Drop a leg (Rule of Two) | One leg is not needed for the task, or the task splits into sessions | Whatever the dropped leg did: browsing with your login, sending without review |
| Action-selector | The useful actions fit a fixed menu | The model's reasoning over data |
| Plan-then-execute or code-then-execute | The tool sequence is known from the request | Data-dependent steps; injections in arguments remain |
| Map-reduce | Items are independent and the output per item can be typed | Reasoning across items |
| Dual LLM | The privileged side can work on references | Orchestration effort; the quarantined output still reaches people |
| Provenance policies at sinks (CaMeL, FIDES) | Data must flow but recipients and destinations are checkable | Policy writing, and confirmations on a third of benign tasks in CaMeL's runs |
| Confirmation with full arguments | Actions are rare and consequential | Throughput, and attention if prompts are frequent |
| Spotlighting, classifiers, adversarially trained models | Always, as a layer in front | Latency and false positives; no bound on impact |

The last row is never the only row. In the adaptive-attack paper, most of the 12 published defences it tested went above 90% attack success once the attacker adapted.

## A worked decision: the email agent

The agent summarises a user's inbox and drafts replies. Tick what the first design gave it:

<SafetyTrifecta title="Email agent, first design" checked={['read_inbox', 'send_email', 'md_images']} />

All three legs, through two exits: a send tool and rendered images in the summary pane. The product requirement does not need either. Copilot in Outlook, per Microsoft's MSRC post, drafts and leaves sending to the user; the same split works here.

Decisions, in order:

1. **Close the exits deterministically.** Remove `send_email`; the agent writes drafts only. The summary pane renders no remote images or links (a Content-Security-Policy `img-src` limited to your own hosts, and links shown as text). With no way out, the session holds two legs.
2. **Set draft recipients in code.** The draft's recipients are the thread's existing participants, read from headers by code. No model chooses a recipient, so no injected text can.
3. **Minimise the private data in each drafting call.** The drafting model sees only the thread it replies to, not the rest of the inbox. An injected instruction to paste other mail into the draft has nothing to paste, and what it could copy is already known to the thread's participants.
4. **Dual LLM for summaries.** The model that plans the inbox view handles messages by reference; a quarantined model writes each summary. Summaries are shown, never executed.
5. **Rate layers for quality, not safety.** Datamarking on email text and a classifier that flags suspicious messages in the UI, so users see a warning on the phishing summaries that remain.

Residual risk, written down: a summary or draft can say what an attacker wants, including a phishing link shown as text. CaMeL and FIDES leave the same class open. Accepted because a person reads each draft before sending and links are not clickable; signed by the product owner and the security lead, with the number of flagged messages reviewed monthly.

## A worked decision: the travel agent

The agent browses for flights and hotels and books them. The task needs all three legs: open-web content, the traveller's profile and payment details, and a booking that spends money. Meta's post works the same example and drops the outbound leg: reservations and deposits need confirmation, and web requests go only to URLs from trusted sources.

A stronger version splits the session along the Rule of Two:

1. **Research session, holding untrusted input and outbound requests but no private data.** It browses in a sandbox with no saved sessions, no profile and no payment method. Its output is a typed shortlist: provider ID, flight or room ID, dates. Free text from pages does not cross.
2. **Booking session, holding private data and state changes but no untrusted input.** It reads the shortlist IDs, re-fetches price and terms from the provider's API (never from the page), and books through an egress allowlist of provider APIs only. The confirmation shows the provider, the dates, the traveller and the amount from the API.
3. **Plan-then-execute in the booking session.** The plan is fixed from the request: quote, confirm, book. Arguments come from the user and the provider API; the tests below enforce that.

Residual risk, written down: the research session can be steered to recommend a worse option, because a page can lie about itself and rank well. Money can only go to allowlisted providers at prices their APIs quote, and a person approves each booking.

## What to measure after deciding

**Unit tests for the deterministic controls.** These must pass at 100%, in CI, on every change to tools or policies. They cover the refusals, the lookalike inputs and the benign path, so a control that blocks everything also fails.

```python
from urllib.parse import urlparse

EGRESS = {"api.flights.example", "api.hotels.example"}

def allow_request(url: str, args_sources: set) -> bool:
    host = (urlparse(url).hostname or "").lower().rstrip(".")
    if host not in EGRESS:
        return False
    return args_sources <= {"user", "provider_api"}   # nothing derived from a web page

def test_egress_blocks_unknown_host():
    assert not allow_request("https://evil.example/c?d=passport", {"user"})

def test_egress_blocks_lookalike_hosts():
    assert not allow_request("https://api.flights.example.evil.example/x", {"user"})
    assert not allow_request("https://api.flights.example@evil.example/x", {"user"})

def test_egress_normalises_case_and_trailing_dot():
    assert allow_request("https://API.FLIGHTS.EXAMPLE./search", {"user"})

def test_allowlisted_host_with_laundered_argument():
    assert not allow_request("https://api.flights.example/book", {"user", "web_page"})

def test_benign_booking_still_passes():
    assert allow_request("https://api.flights.example/book", {"user", "provider_api"})
```

**An adaptive suite for the probabilistic layers.** AgentDojo, with 97 tasks and 629 security test cases, is a starting point for the static half. The adaptive half is an attacker that sees each layer's response and searches: report attack success per attempt and per period at a stated volume, and track it as a trend across model and prompt changes. A falling static number with a flat adaptive one means the layer learned the test set.

**The confirmation rate and the approval rate.** If people approve nearly everything, the confirmation is not a control. CaMeL's policies fired on a third of benign tasks in its own runs; tune until prompts are rare and approvals are not automatic.

**Utility by task family.** The by-construction lesson showed that utility loss concentrates in some task families. Measure task success per family before and after, so a pattern that broke one family is visible.

## When this is wrong

The playbook treats legs as binary. In practice "private data" ranges from a public profile to payment credentials, and "untrusted" ranges from a vetted partner feed to an anonymous web page. A team that counts a partner API as untrusted ends up with every session supervised; a team that counts it as trusted inherits the partner's compromise. Write down the classification of each source, with the reason, and revisit it when the source changes owner.

Splitting sessions assumes the typed boundary between them holds. A shortlist with a free-text "notes" field, added later for a product reason, reopens the path from web page to booking session. The tests should assert the schema of what crosses, not only the egress rules.

And the residual numbers in a design note are estimates built on someone else's benchmark. Replace them with your own adaptive-suite results as soon as you have them, and expect them to move with every model upgrade.
