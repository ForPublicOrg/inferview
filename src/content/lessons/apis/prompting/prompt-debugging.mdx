## Failures cluster, rewording does not find the cluster

A prompt that fails in production rarely fails uniformly. It fails on long inputs, on one language, on tickets that mention two products, on the template version a single customer still sends. Rewording the prompt against the three examples in the bug report changes behaviour everywhere to fix a cluster nobody has measured, so the next report comes from a slice the rewording broke.

The method is the one used for any production defect with a long tail: sample, classify, count by dimension, fix the largest cluster, add a regression test. What differs for prompts is that the classification step is manual reading, the system under test is non-deterministic, and part of the system is versioned by someone else.

## The loop

**Sample traces, not complaints.** Hamel Husain and Shreya Shankar's evals FAQ starts error analysis at 100 diverse traces, with at least the first 30 annotated by a person who knows the domain. Complaints over-sample angry users and the visible failure; a stratified sample of traffic, plus every complaint, gives both the rate and the worst cases.

**Code the first failure in each trace.** Open coding is a free-text note on what went wrong; upstream errors cause downstream ones, so the FAQ notes only the first. Axial coding then groups the notes into a taxonomy and counts each category. Keep reading until new traces stop producing new categories.

**Label pass or fail.** The FAQ recommends binary labels over 1-to-5 scales, which invite middle values and need larger samples to compare. Several specific binary checks track progress better than one scale.

**One owner for "correct".** A single domain expert decides what passes. Disagreement between labellers is a specification bug and the expert resolves it into a rule.

**Fix obvious gaps directly.** A missing length or format rule is a prompt edit, not an evaluator. The FAQ's advice is to build automated evaluators only for failures that persist after the prompt fix.

The authors report spending 60 to 80% of their development time on error analysis and evaluation. That is their practice, not a benchmark, but it calibrates the expectation: the reading is the work.

## Slicing by input feature

Once failures are coded, count them against features of the input and the request: input length bucket, language, input source or template, presence and size of retrieved context, tool results, customer tier, prompt version, model ID, API version, time. The question for each feature is whether the failure rate in one value is far from the rest and whether that slice is a large share of all failures.

A slice table is short code once traces carry their features.

```python
from collections import defaultdict

def slice_table(traces, feature, min_count=30):
    total_fail = sum(1 for t in traces if not t["pass"])
    groups = defaultdict(lambda: [0, 0])          # value -> [count, failures]
    for t in traces:
        g = groups[feature(t)]
        g[0] += 1
        g[1] += 0 if t["pass"] else 1
    rows = []
    for value, (n, f) in groups.items():
        if n >= min_count:
            rows.append((value, n, round(f / n, 3), round(f / max(total_fail, 1), 3)))
    return sorted(rows, key=lambda r: -r[3])     # largest share of failures first

def length_bucket(t):
    return "over 2k" if t["input_tokens"] > 2000 else "2k or less"

traces = ([{"input_tokens": 2500, "pass": i % 10 >= 3} for i in range(800)] +
          [{"input_tokens": 400, "pass": i % 50 != 0} for i in range(9200)])
for row in slice_table(traces, length_bucket):
    print(row)
```

It prints `('over 2k', 800, 0.3, 0.566)` then `('2k or less', 9200, 0.02, 0.434)`: value, count, failure rate, share of failures. The `min_count` floor matters: with a few dozen traces per value, a slice's failure rate has a wide confidence interval and the table ranks noise.

## Near ties: when the label is a coin the server flips

Some failures are not consistent. The same input passes on one run and fails on the next, and a team without a method rewrites the prompt until the one bad run goes away.

Thinking Machines measured how far identical requests diverge. Running Qwen3-235B 1,000 times at temperature 0 with one prompt gave 80 distinct completions; all were identical for 102 tokens, and at token 103 992 runs wrote one continuation and 8 another. The cause was kernels whose numerics depend on batch size, while server load changes batch size from request to request; batch-invariant kernels made all 1,000 identical, at a cost (26 s by default against 42 s with the improved deterministic kernels, on Qwen3-8B in their test). On a hosted API that choice is the provider's. And under Anthropic's API version 2026-10-21, temperature cannot be set at all; requests sample at 1.0.

The practical reading: a decision that flips between runs sat on a near tie, where two outputs were almost equally likely. A near tie is evidence about the input and the specification, not about the wording. Measure it per input:

- Repeat each failing input k times (10 is enough to separate 10-of-10 from 6-of-10) and record the agreement rate. The applied-llms.org authors make the same point for tests: run each input several times, because rare anomalies only appear occasionally.
- Where the API returns token log probabilities, the margin between the top two label tokens measures the same thing in one call.

Consistent errors (10 of 10 wrong) are specification or capability problems and respond to prompt or example changes. Near ties (6 of 10) on inputs that are genuinely ambiguous respond to a tie-break rule, a new label, or routing to a person; rewording only moves which side of the tie wins this week.

## Changes behind a name

Some slices are not about the input at all; they are about time. Chen, Zaharia and Zou compared GPT-3.5 and GPT-4 between March and June 2023 under the same names: GPT-4's accuracy on identifying prime numbers went from 84% to 51%, both models made more formatting mistakes in generated code, and GPT-4 became less willing to answer sensitive questions. The applied-llms.org authors report that Voiceflow saw roughly a 10% drop in intent classification after switching model versions, and caught it because they had evals.

The debugging consequences:

- Log the model identifier the provider reports back, the API version, the SDK version and the rendered prompt hash on every request. A failure-rate step on a date then lines up with exactly one of: your deploy, the provider's model or API change, or a traffic mix change.
- Pin dated model versions where the provider offers them and treat moving the pin as a release.
- Watch client-side adaptations. Under API version 2026-10-21, sending `temperature` returns a 400. A wrapper that silently drops the parameter to avoid the error changes sampling for any older model that previously ran at a lower temperature; Anthropic notes that Claude 4.7 and later already accept only the defaults and sample as before.

## From failure to gated fix

A fix is done when it is a test. Each confirmed failure category becomes eval cases built from the real traces, with the expected property written as the weakest assertion any valid answer would satisfy (the label set, a cited clause, a forbidden phrase), because exact-string expectations fail on valid rephrasings.

For failures a code check cannot detect, the FAQ's guidance for an LLM judge is 100 to 200 labelled examples per failure mode, split so the judge is tuned on one part and measured on a held-out part. That is a real cost; most categories in a first pass are cheaper to catch with code.

The gate compares old and new prompts on the same cases, so the comparison is paired: count the cases that flip from fail to pass and from pass to fail. A change that fixes 15 long-ticket cases and breaks 6 short-ticket cases has a net of 9 and a regression in a slice that may carry more revenue. Report flips per slice and let the owner of each slice decide, rather than reporting one pass rate.

<Callout kind="gotcha">
A case that fails 4 of 10 runs passes a single-run gate 60% of the time. Run the slice's cases several times in the gate, or the gate's verdict is itself a near tie.
</Callout>

## When this is wrong

Slicing finds clusters only along features you logged. A failure driven by something absent from the trace, such as a cache serving a stale retrieved document, shows up as a uniform rate across every slice you have. When no feature separates the failures, the next step is adding features to the trace, not more slicing.

The 100-trace starting point assumes failures are common enough to appear in 100 traces. For a 0.5% failure, 100 random traces contain about one failure; sample from complaints, low agreement rates or judge flags instead, and keep the random sample for estimating the rate.

Repeat-run agreement separates near ties from consistent errors only if the repeats are independent. Repeats sent in one burst may share batch composition, server and cache state, and agree more than separate production requests would.
