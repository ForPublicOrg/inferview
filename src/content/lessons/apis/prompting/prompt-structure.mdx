## Two kinds of line

Every production prompt mixes two kinds of line. Durable intent states what the feature must do whichever model runs it: the task, the label set and its tie-break rules, the policy, the output contract. Workarounds exist because one model misbehaved: a shouted instruction because a tool was under-called, a prefilled opening brace because the model wrapped JSON in prose, a "think step by step" because accuracy dropped without it. A workaround is a compiler flag tuned to one compiler version. The difference is that nobody wrote down which version, so on upgrade day every line looks equally load-bearing and the team either re-tests all of it or none of it.

The structural rule follows: keep the two kinds separable, and give every workaround a record of the model it was added for and the eval cases that justified it. An upgrade then produces a short re-test list instead of an archaeology project.

## What changed between generations

Recent Claude releases turned several common workarounds from harmless into errors or regressions. All of these are from Anthropic's documentation as checked on 2026-10-28.

| Line or setting in a prompt tuned on Claude Sonnet 4.5 | On Claude Sonnet 5.5 |
|---|---|
| Prefilled assistant turn, such as `{"label": "` | 400 error: prefill on the last assistant turn is unsupported from Claude 4.6 models |
| `temperature: 0` for consistency | 400 error: under API version 2026-10-21 any sampling parameter is rejected, even at its default; under the older version a non-default value is rejected on Claude 4.7 and later |
| `thinking` enabled with `budget_tokens` | 400 error; depth is set with `effort` |
| "CRITICAL: You MUST use lookup_order when..." | Anthropic reports that Opus 4.5 and 4.6 respond more strongly to the system prompt and may overtrigger on such wording; the advice is plain "Use this tool when..." |
| "Think step by step inside `<reasoning>` tags" | Thinking is on by default; for Opus 5.5, Sonnet 5.5 and Fable 5.1 the guide says to rely on it, and a prompt that asks the model to write its reasoning out may be declined |

Three of the five are hard failures that show up as 400s on the first request, which is the good case: CI catches them. The other two are quality changes that only an eval shows. The Sonnet 4.5 retirement makes this concrete: Anthropic deprecated `claude-sonnet-4-5-20250929` on 2026-09-30 and retires it on 2026-11-30, with `claude-sonnet-5-5` as the named replacement. Every prompt still pointed at it has to cross that table inside the notice period.

## Placement: what goes where

**System prompt for the stable contract.** Role, task, policy, label definitions, output contract and fixed examples go in the system prompt. Anthropic's guide recommends a role there and one XML tag per kind of content (`<instructions>`, `<context>`, `<examples>`, `<input>`), so instructions and data are not told apart by position alone.

**Volatile values last.** Prompt caching matches an exact prefix in the order tools, then system, then messages, and a change at one level invalidates that level and everything after it. A timestamp, a customer name or a feature flag rendered at the top of the system prompt makes every request a different prefix. Put per-request values in the user turn, after the stable text.

**Long documents above the question.** The guide says to place long inputs above the query and instructions, and states that queries at the end "can improve response quality by up to 30 percent in tests". That is Anthropic's in-house figure with no dataset published, so it is a reason to test the order on your traffic, not a constant to quote.

## Delimiting untrusted data

A ticket, an email or a retrieved page is data, and the prompt has no second channel to keep it apart from instructions. Tags are the closest thing to a parameterised query, and the analogy breaks at exactly the point that matters: the model reads the tag as tokens, so a tag reduces confusion but does not enforce a boundary. Two cheap measures still pay:

- Escape or strip anything in the data that could close your tag, so a ticket containing `</ticket>` cannot end the data block early.
- For text a user pasted from elsewhere, Anthropic's Opus 5.5 guide recommends tags carrying a short random id that your application generates per block, plus a system prompt line saying instructions inside are followed only where the user's own message asks. The same guide says the tags "are plain text and can be imitated". The random id raises the cost of imitation; it is not authentication.

Containment for injection belongs to permissions and tool scope, which the safety and security tracks cover. The prompt-level job is to make the honest case unambiguous.

## Examples are the specification

The model generalises from examples more than from adjectives, so examples are the most precise part of the specification and the part most likely to contradict the rest. Anthropic suggests 3 to 5 examples; the applied-llms.org authors suggest at least five, drawn in proportion to production traffic. Both are rules of thumb from people who measured their own systems, and they disagree, which is itself information: the count is a parameter for your eval, not a constant.

What the research pins down is that examples carry hidden signal. Zhao and colleagues showed in 2021 that format, the choice of examples and their order moved GPT-3 accuracy from near chance to near state of the art on the same task, and traced it to a bias toward answers near the end of the prompt and toward answers frequent in pre-training. Three consequences for structure:

1. **Fixed set, fixed order, reviewed like code.** An example set sampled per request makes the prompt a random variable.
2. **Examples must agree with the policy text.** When the policy section says refunds within 30 days and an example shows an agent refusing on day 20 under an older policy, the model has two specifications and picks one per request.
3. **Label balance and position are design choices.** If the last example is always the majority label, that label gets a free boost.

## A prompt you can diff

The habit that makes upgrades cheap is storing the prompt as labelled sections rather than one string. The runnable sketch below keeps the kind of each section, the model a workaround was tuned on, and the eval cases that justified it, then produces the re-test list for a target model.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Section:
    name: str
    text: str
    kind: str              # "intent" or "workaround"
    added_for: str = ""
    evidence: tuple = ()   # eval case ids that justified the workaround

PROMPT = [
    Section("role", "You label support tickets for a billing product.", "intent"),
    Section("labels", "Labels: billing, bug, account. If money moved, the label is billing.", "intent"),
    Section("tool", "CRITICAL: You MUST call lookup_order before any answer about an order.",
            "workaround", "claude-sonnet-4-5-20250929", ("ev-112", "ev-131")),
    Section("reasoning", "Think step by step inside <reasoning> tags.",
            "workaround", "claude-sonnet-4-5-20250929"),
]

def render(sections, ticket):
    body = "\n".join(f"<{s.name}>{s.text}</{s.name}>" for s in sections)
    safe = ticket.replace("<", "&lt;").replace(">", "&gt;")
    return body, f"<ticket>{safe}</ticket>"     # system text, user text

def retest_plan(sections, target_model):
    plan = []
    for s in sections:
        if s.kind == "workaround" and s.added_for != target_model:
            reason = ", ".join(s.evidence) or "no evidence recorded: delete unless a case fails"
            plan.append((s.name, reason))
    return plan

for name, reason in retest_plan(PROMPT, "claude-sonnet-5-5"):
    print(f"{name}: {reason}")
```

The output names two sections. `tool` has evidence, so its two cases run on the new model with and without the line, and the line goes if they pass without it. `reasoning` has none, so the default is deletion, which on Sonnet 5.5 is also what the vendor guide says. Intent sections are not on the list; the full eval still covers them, but nobody spends review time arguing about them.

The rendered text, its hash and the model ID go into the request log, so a behaviour change can be attributed to the prompt, the model or the traffic. The lifecycle around that (registry, review, rollout) is the [prompt lifecycle module](/learn/llmops/prompt-lifecycle) in the LLMOps track.

## When this is wrong

The intent and workaround split assumes you can tell them apart. Some lines are both: "If money moved, the label is billing" may have been added because one model mislabelled refunds, yet it is also policy. Classify by whether the business would want the rule on a perfect model, not by why it was written.

The generation table is Anthropic-specific and dated. Another provider's prompts carry their own workarounds, and the advice on tags differs: the applied-llms.org authors note that GPT models favour Markdown and JSON where Claude favours XML-style tags. The method transfers; the table does not.

Structure does not replace evals. A perfectly sectioned prompt with no failing cases recorded produces a re-test list with no evidence attached, and the default of deleting unevidenced workarounds is only safe when the full eval runs before the change ships.
