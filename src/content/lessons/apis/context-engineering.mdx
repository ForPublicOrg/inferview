## One line of text, a much bigger bill

Scenario: a support assistant has a long, stable system prompt with product documentation, and prompt caching keeps its input bill low. A developer adds "Current date and time:" with a timestamp as the first line of the system prompt so the model can answer "is my order late?". Answers improve slightly. The input bill jumps several times over and nobody connects it to a one-line change, because the cost dashboard sums `input_tokens` and that field went up only a little.

Both effects come from the same fact: the model reads a sequence, and position matters. This lesson treats the context window the way you treat memory in a constrained system: a budget, allocated deliberately, with a cache in front of it.

## Context is a budget, not a bucket

The analogy is a fixed-size buffer that you fill on every call. A large window feels like a bucket you can keep pouring into. It behaves like a budget, for two reasons.

**Cost and latency scale with it.** Every token is billed and processed on every call, because the API is stateless.

**Quality degrades with it.** Chroma's July 2025 study tested 18 models and found reliability falls as input grows, even on simple tasks, and that a single distracting passage already hurts. The older "lost in the middle" result from 2023 found accuracy was highest when the relevant text sat at the start or end of the context; it was measured on 2023-era models, so treat the U-shape as history and the general lesson, that more context is not free, as current. Anthropic's September 2025 post on context engineering calls this an "attention budget" and names the decline "context rot".

So on every call you are allocating a budget across five consumers: the system prompt, the conversation history, retrieved documents, tool definitions and results, and room for the output (including any thinking). The engineering question is what earns a place.

LangChain's July 2025 post sorts the techniques into four verbs: **write** context outside the window (notes, files, memory), **select** what to bring in (retrieval, just-in-time loading), **compress** what is there (summaries, trimming tool results), and **isolate** work in separate contexts (sub-agents). It also names the failure modes, credited to Drew Breunig: poisoning (a wrong fact gets in and is repeated), distraction, confusion (irrelevant tools or text) and clash (contradictory information).

### Keeping a long conversation alive

When a conversation outgrows its budget you have four moves, from cheapest to most complex:

- **Sliding window.** Keep the last N turns. Trivial and predictable, and it forgets the user's name from turn one.
- **Summarise the old part.** Replace early turns with a running summary. Keeps the gist, loses detail, and costs a model call each time you refresh it.
- **Extract facts to notes.** Keep a structured record (decisions, user preferences, open tasks) outside the window and inject it each turn. Anthropic's post calls this structured note-taking.
- **Compaction and clearing.** Providers now do some of this for you. Claude's context editing (`clear_tool_uses_20250919`) clears old tool results once input passes a trigger (100,000 tokens by default), keeps the last 3 tool uses, and leaves the calls visible so the model knows what it did. Server-side compaction is in beta under the `compact-2026-09-04` header.

Isolation is the fifth move for agents: a sub-agent explores with its own large context and returns a condensed summary, about 1,000 to 2,000 tokens in Anthropic's description. Agent Skills apply the same idea to instructions. A skill's name and description, about 100 tokens, sit in context from the start; its `SKILL.md` body, recommended to stay under 5,000 tokens, loads only when the task calls for it.

## Prompt caching is memoisation of a prefix

Here is the mechanism in systems terms. Processing input builds internal state for every token in order. If two requests begin with exactly the same tokens, the provider can reuse the state it built for that shared prefix instead of recomputing it. That is memoisation keyed on a prefix, and it has the property every prefix cache has: the first difference ends the match. Everything after it is computed, and billed, from scratch.

On Claude, the prefix is assembled in a fixed order: `tools`, then `system`, then `messages`. You mark up to 4 cache breakpoints, or turn on automatic caching. A cached prefix lives for 5 minutes by default, refreshed at no charge each time it is used; a 1-hour lifetime is available at a higher write price. For Opus 5.5, the prices per million input tokens are:

| | Price | Multiple of base input |
|---|---|---|
| Base input | $4.00 | 1x |
| Cache write, 5 minutes | $5.00 | 1.25x |
| Cache write, 1 hour | $8.00 | 2x |
| Cache read | $0.20 | 0.05x |

A write costs more than a normal input token and a read costs a twentieth. One write plus one read ($5.20) is already cheaper than sending the same prefix twice uncached ($8.00), so caching pays from the second request inside the lifetime. Now play with order:

Move the timestamp, the retrieved passages and the new message below the documentation and the conversation, and the cached prefix grows to 49,500 tokens and the same 1,000 requests cost $30.58. The text the model reads is the same; only the order changed. That is the answer to "why does reordering your prompt change your bill?"

### What breaks the cache

On Claude, changing tool definitions invalidates everything, because tools come first. Changing `tool_choice`, adding images, or changing thinking settings or the `effort` level invalidates the cached messages. Changing the structured-output format invalidates the prompt cache for the thread. Context editing that clears tool results changes the prefix too, so it trades a smaller context for a cache miss at that point. And a prompt shorter than the model's minimum is simply not cached, with no error: 512 tokens on Opus 5.5, up to 4,096 on some older models.

Two measurement traps. Claude's `input_tokens` counts only the tokens after the last breakpoint; total input is `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`, and a dashboard that reads only the last field undercounts exactly the cost the scenario above hid. And on most Claude models, cache reads do not count toward your input-tokens-per-minute limit, so caching raises your rate ceiling as well as cutting the bill.

### Other providers

OpenAI caches automatically, with a 1,024-token minimum on GPT-5.6 and later. On those models reads cost 0.1x input (0.05x for GPT-6.1 Sol and Terra) and writes now cost 1.25x for a 30-minute lifetime or 2.5x for 12 hours. On models before GPT-5.6 a `prompt_cache_key` steers requests that share a prefix toward the same cache; on GPT-5.6 and later routing is automatic and the key only separates cache accounting. The docs also warn that traffic above 15 requests per minute for one prefix can overflow to machines that do not hold the cached prefix. Gemini 2.5 and newer cache implicitly, with a 2,048-token minimum on 2.5 Flash and Pro. "Caching saves 90%" is true for some models on some days; state the model and the date.

### The arithmetic

Scenario numbers: a 50,000-token shared prefix, 500 new tokens per request, 200 requests inside the cache lifetime, Opus 5.5 prices. Output is left out because caching does not change it.

```python
BASE, WRITE_5M, READ = 4.00, 5.00, 0.20   # Opus 5.5, USD per million input tokens

def cost(prefix, suffix, n_requests, cached):
    if not cached:
        return n_requests * (prefix + suffix) * BASE / 1e6
    first = prefix * WRITE_5M / 1e6 + suffix * BASE / 1e6
    rest = (n_requests - 1) * (prefix * READ / 1e6 + suffix * BASE / 1e6)
    return first + rest

print(f"{cost(50_000, 500, 200, False):.2f}")   # 40.40
print(f"{cost(50_000, 500, 200, True):.2f}")    # 2.64
```

$40.40 without caching, $2.64 with it. For a single request the cached version costs more ($0.252 against $0.202), because of the write premium. That is the case for not caching a prefix you will use once.

## Semantic caching: when it is a bug

Prompt caching reuses computation and still runs the model, so the answer is always for the actual question. Semantic caching is different: it stores whole answers and returns a stored answer when a new question is "similar enough" by embedding distance. That skips the model entirely, which is why it is cheaper, and why it can be wrong.

A constructed example with a toy bag-of-words similarity: "cancel my subscription" and "do not cancel my subscription" share three of their words, and their cosine similarity is 3 / √(3 × 5) ≈ 0.775. Real embeddings are better than bag-of-words, but negation, a different account, a different date or a different region are all small changes in text and large changes in meaning. Semantic caching is safe for questions whose answer does not depend on who is asking or when, such as a static FAQ, scoped per tenant and with a short lifetime. It is a bug for anything personalised, stateful or time-sensitive. No source we found measures how often it returns a wrong answer in production, which is itself a reason to measure yours before turning it on.

## The allocator round

One third-party guide to Anthropic's applied AI interviews lists a token-budget allocator as a phone-screen task. The usual shape: given a budget, a mandatory system prompt, an output reserve, a conversation history and scored documents, return what fits. The decisions that make it a design question rather than a loop are the priority order (system, then recent history, then documents by score is one policy; fixed shares per section is another), whether history must stay contiguous (dropping turn 3 but keeping turn 2 confuses the model), and whether a large high-scoring document that does not fit should block smaller ones behind it. Practise it as the allocator problem in this track's bank, and use the provider's token counter rather than characters divided by four when the budget is real.

## When this is wrong

The prefix widget is a teaching model of exact-prefix matching, not any provider's algorithm. Claude checks block-level breakpoints with a 20-block lookback, OpenAI routes on a hash of the initial tokens. Hit rates in production depend on traffic shape as much as on prompt order.

Prices and multipliers here are Claude and OpenAI list prices read on 28 October 2026, and they already differ by model: Claude reads cost 0.1x, 0.05x or 0.025x of base input depending on the model, and OpenAI charges for cache writes only on its newer models. Recompute before you put a saving in a design doc.

The context-rot and lost-in-the-middle findings come from specific benchmarks and model generations. They justify keeping context lean and testing order, not a rule such as "never exceed N tokens". The only reliable number is the one from your own eval at your own context length.
