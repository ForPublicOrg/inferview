## The string "yes" in a boolean column

Scenario: a lead-capture pipeline asks a model to "return JSON with name, email and demo_requested". It works for weeks. Then one reply comes back as `"demo_requested": "yes"`, another wraps the JSON in a Markdown code fence, and a third stops halfway because the reply hit `max_tokens`. The nightly import crashes on the first, silently drops the second and stores garbage from the third.

Every one of those failures has a different fix. This lesson is about knowing which.

## Three levels of "return JSON"

Think of it as type checking, and ask when the check runs.

**Asking.** The prompt describes the format. Nothing checks it. This is a dynamically typed language with no tests: it works until it doesn't.

**JSON mode.** The provider guarantees the output parses as JSON, but not that it matches your shape. OpenAI documents two sharp edges: the API throws an error if the string "JSON" does not appear somewhere in the context, and without an instruction to produce JSON "the model may generate an unending stream of whitespace". A truncated reply can still be incomplete JSON.

**Schema-constrained decoding.** You pass a JSON Schema; the provider compiles it into a grammar and, at every step of generation, masks out tokens that would break it. The closest analogy is a parser generator wired into the token sampler: the model can only take paths the grammar allows. OpenAI calls this Structured Outputs (`text.format` with `type: "json_schema"` and `strict: true` on the Responses API, `response_format` on Chat Completions). Anthropic exposes it as `output_config.format` with `type: "json_schema"`, plus `strict: true` on tool definitions, and is explicit that it works by compiling the schema into a grammar.

Below all three sits the fallback you still need for any provider or schema without constrained decoding: **validate and repair**. Parse, validate against the schema, and on failure send the errors back and ask for a corrected reply, with a cap on attempts.

### The compiler has a subset

A grammar compiler supports a subset of JSON Schema, and the subsets differ by provider.

| | OpenAI strict mode | Claude structured outputs |
|---|---|---|
| Objects | `additionalProperties: false` on every object, every field listed in `required`, optional fields written as a union with `null` | `additionalProperties` other than `false` not supported |
| Recursion and `$ref` | `$defs`, `$ref` and recursion supported | Recursive schemas and external `$ref` not supported |
| Keywords left out | `allOf`, `not`, `dependentRequired`, `dependentSchemas`, `if`/`then`/`else` | `minimum`, `maximum`, `multipleOf`, string length, array constraints beyond `minItems` of 0 or 1 |
| First use | Extra latency for a new schema | Grammar compiled on first use, cached 24 hours from last use; compilation times out after 180 seconds |

OpenAI also requires the root to be an object rather than `anyOf`, and caps a schema at 5,000 object properties and 10 levels of nesting. A practical consequence: a Zod discriminated union at the root fails OpenAI's strict mode, and a `minimum: 0` that you rely on is not something Claude's grammar can enforce. Anthropic's SDK helpers move such constraints into field descriptions and validate them locally after the call. Do the same yourself.

### It parses. Is it right?

Constrained decoding guarantees syntax, not success. Three cases still break a strict pipeline:

- **Refusal.** Claude returns `stop_reason: "refusal"` with HTTP 200, the call is billed, and the output may not match the schema. OpenAI returns a `refusal` content item.
- **Truncation.** `stop_reason: "max_tokens"` on Claude, or `status: "incomplete"` with `max_output_tokens` on OpenAI. The grammar cannot finish an object it ran out of room for.
- **Valid but wrong.** An enum value that differs only in case, an email that is a valid string but not an address, a date in the wrong year. The schema says "string"; your business rule says more.

So the order in code is fixed: check the stop reason, then parse, then validate business rules. One more Claude-specific trap: citations and `output_config.format` cannot be combined in one request; it returns a 400. A RAG feature that wants both needs two calls or has to choose.

### Does forcing a format hurt reasoning?

A 2024 paper by Tam and colleagues reported that reasoning declined under format restrictions. dottxt, which builds a constrained-decoding library, re-ran some of the same tasks with Llama-3-8B-Instruct and argued the gap came from mismatched prompts and the parser used to grade answers.

## Tool calling: the model proposes, your code disposes

Function calling is structured output with a dispatcher attached. You send tool definitions (name, description, JSON Schema for arguments). The model either answers or returns a request to call a tool. Your code decides whether to run it, runs it, and sends the result back, and the model continues. The model never executes anything.

The wire formats differ but the protocol is the same:

- **Claude:** the assistant turn contains `tool_use` blocks, each with an `id`; you reply with a user turn of `tool_result` blocks carrying the matching `tool_use_id`, and `is_error: true` when the tool failed.
- **OpenAI Responses:** output items of type `function_call` with a `call_id`; you send back `function_call_output` items with the same `call_id`.

The pairing by id is the contract. Miss a result, or attach it to the wrong id, and the API rejects the request or the model reasons about the wrong data.

Control knobs also differ. OpenAI's `tool_choice` takes `auto`, `required`, a named function, `allowed_tools` or `none`, and `parallel_tool_calls: false` limits a turn to zero or one call. On Claude Opus 5.5, Sonnet 5.5 and Fable 5.1, `tool_choice` of `any` or a named tool returns a 400; use `auto` with strict tools, or structured outputs if you need a guaranteed shape. Definitions differ in shape too: Chat Completions nests a function under `function` and is non-strict by default, while Responses puts `name` and `parameters` at the top level and tries strict mode by default. Code that mixes the two shapes fails in confusing ways.

### Tool definitions are prompts

The model chooses tools by reading their names and descriptions, so those are prompt text and deserve the same care. Name tools by what they do to what (`search_orders`, not `query`). Give arguments formats and examples in the description, such as an ISO 8601 date with an offset, because a schema type of `string` says nothing about which string. Return errors that tell the model what to change ("amount exceeds the refundable balance of 12.50") rather than "invalid request". Keep results small: Anthropic's tools post reports that Claude Code caps tool responses at 25,000 tokens by default, and that a concise response format used 72 tokens where the detailed one used 206. OpenAI's guide gives a soft suggestion of fewer than 20 functions available at the start of a turn.

### Parallel calls and ordering

When a model returns several tool calls in one turn, it is asserting they are independent. That is not always true. `create_event` and `invite_attendees(event_id=...)` in the same turn means the second call depends on an id the first has not produced yet. Run independent read-only calls concurrently; serialise anything with side effects, or disable parallel calls for the tools that mutate state. Results go back matched by id regardless of completion order.

### Streaming arguments

When you stream, tool arguments arrive as fragments: `input_json_delta` events on Claude, `response.function_call_arguments.delta` on OpenAI. A fragment such as `{"location": "San Fra` does not parse. Buffer per block and parse at the stop event, or use a partial parser if the UI needs to show progress: Pydantic's `from_json(data, allow_partial=True)` turns `'["aa", "bb", "c'` into `['aa', 'bb']`, dropping the incomplete item. Never act on a partial argument object.

## Validate and repair in code

The fallback loop, with a mock model so it runs anywhere. Note that the repair turn is a user message, which matters on Claude 4.6 and later where you cannot prefill the assistant turn.

```python
import json

SCHEMA = {"name": str, "email": str, "demo_requested": bool}

def validate(obj):
    errors = []
    if not isinstance(obj, dict):
        return ["top level must be an object"]
    for key, typ in SCHEMA.items():
        if key not in obj:
            errors.append(f"missing field: {key}")
        elif not isinstance(obj[key], typ):
            errors.append(f"{key} must be {typ.__name__}, got {type(obj[key]).__name__}")
    extra = set(obj) - set(SCHEMA)
    if extra:
        errors.append(f"unexpected fields: {sorted(extra)}")
    return errors

def extract(call_model, text, max_attempts=3):
    messages = [{"role": "user", "content": text}]
    for _ in range(max_attempts):
        raw = call_model(messages)
        try:
            obj = json.loads(raw)
            errors = validate(obj)
        except json.JSONDecodeError as e:
            obj, errors = None, [f"invalid JSON: {e.msg}"]
        if not errors:
            return obj
        messages += [{"role": "assistant", "content": raw},
                     {"role": "user", "content": "Fix these errors and reply with JSON only: " + "; ".join(errors)}]
    raise ValueError(f"no valid output after {max_attempts} attempts: {errors}")
```

Every repair round is a full extra call that re-sends the conversation, so the attempt cap is also a cost cap. With constrained decoding available, this loop shrinks to business-rule validation, because syntax and types are already guaranteed.

## Evaluating tool use

"Did it call the right tool with the right arguments" is a measurable property, and the Berkeley Function Calling Leaderboard is the public reference: version 3 added multi-turn evaluation and version 4 added agentic evaluation, with the page last updated on 12 April 2026. For your own system, log every tool call, sample them, and grade tool choice and arguments separately, because they fail for different reasons: a wrong tool is usually a description problem, a right tool with wrong arguments is usually a schema or format problem.

<Fragment slot="long">
<p>Layer one, the dispatcher. Every tool call passes through code you own. It checks that the tool is allowed for this user and this conversation state, validates arguments beyond the schema, and for destructive actions returns a "needs confirmation" result instead of executing. The model then has to ask the user, and the confirmation comes back as user input, not as model output.</p>
<p>Layer two, the tool. The handler rechecks its own invariants (ownership, limits) because other callers exist. It accepts an idempotency key. It returns errors the model can act on, such as the valid range, rather than a bare failure.</p>
<p>Layer three, the cause. Wrong arguments usually mean an ambiguous schema: a free-form string where an id, an enum or a format belongs, or two similar tools with overlapping descriptions. Tighten the schema with strict mode and enums, make the description say where the value comes from, and add the failing case to the tool-call eval set.</p>
<p>Trade-off: confirmations add friction and a round trip. Gate by impact, not by tool: a refund under a small amount may run automatically while a deletion always asks.</p>

## When this is wrong

The schema rules and limits in this lesson were read from each provider's docs on 28 October 2026. Both providers have expanded their supported subsets before and will again, so check the current list before you design around a missing feature.

Constrained decoding is a provider feature. Some models behind a gateway or on your own serving stack support it through the inference server's grammar backend, and some do not support it at all. Your code should work, more slowly and more expensively, with the validate-and-repair loop alone.

And a schema is not a specification. It cannot say that `end` is after `start`, that a discount is under the list price, or that a summary is faithful to its source. Those checks are yours, and the evals track is where you learn to measure them.
