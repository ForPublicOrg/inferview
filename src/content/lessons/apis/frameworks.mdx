## The prompt nobody wrote

Scenario: a team inherits a support assistant built on an agent framework two major versions ago. After a model upgrade the answers get shorter and start ignoring a formatting rule. The team searches the repository for the rule and finds it, but the model never sees that string on its own: the framework wraps it in a template of its own, adds tool-calling instructions, and on a validation error quietly sends a second request. Nobody on the team has read the final prompt. They have been debugging a function they cannot see.

That is the trade every framework offers. It writes the plumbing for you, and some of the prompt.

## Frameworks are ORMs for model calls

The analogy that holds up is an ORM. An ORM saves you from writing SQL for the common cases, gives you migrations and connection pooling, and lets a team share conventions. It also generates queries you did not write, and when one is slow you need to know SQL to see why. Mature teams use the ORM for the 80% path and drop to SQL when it matters.

Model frameworks are the same deal with one difference: the generated "query" is natural-language prompt text, and a model upgrade changes how that text is interpreted. A framework default that worked on last year's model is a prompt you never reviewed running on this year's.

Anthropic's agent-building post, from December 2024, makes the case for starting without one: many patterns are a few lines of code against the API, frameworks can obscure the underlying prompts and responses, and, in its words, "Incorrect assumptions about what's under the hood are a common source of customer error."

## What is on the shelf in late 2026

**LangChain 1.x.** Version 1.0 shipped on 22 October 2025 with a smaller surface: `create_agent` (built on LangGraph) with `model`, `tools`, `system_prompt`, `response_format`, a `checkpointer` and a `middleware` list, where built-in middleware covers human-in-the-loop approval, summarisation and PII redaction. Older chains moved to a separate `langchain-classic` package, and the release promises no breaking changes until 2.0. Its structured output picks a strategy for you: native provider structured output when the model supports it, tool calling otherwise, and by default it re-prompts the model when validation fails. That last default is exactly the kind of hidden second call from the scenario.

**LangGraph 1.x.** A lower-level library for agents as explicit state machines: a `StateGraph` of nodes and edges that runs in super-steps, a checkpointer that saves state per `thread_id`, and `interrupt()` with `Command(resume=...)` for human-in-the-loop pauses. Two details matter in interviews. On resume, the interrupted node re-runs from its start, so any side effect before the `interrupt()` call must be idempotent. And the step cap, `recursion_limit`, raises `GraphRecursionError` when exceeded; set it explicitly rather than trusting a default, because the documented default and the one in the source code have disagreed. The 1.0 release was 17 October 2025 on PyPI; 1.2.18 was current on 26 October 2026.

**LlamaIndex** starts from the data rather than the loop. Data connectors load documents, an index (usually over a vector store) organises them, and a query or chat engine answers over that index, which its docs describe as getting from documents to answers in a few lines. Agents and event-driven workflows sit on top, with a RAG pipeline as one tool an agent can call. Reach for it when retrieval is most of the work; what it hides is the chunking, embedding and ranking choices, which the RAG track takes apart.

**Agent SDKs from the model providers.** The OpenAI Agents SDK runs a loop of model calls, tool calls and handoffs with a default cap of 10 turns. The Claude Agent SDK packages the same tools, loop and context management as Claude Code. Both were still pre-1.0 on PyPI in October 2026 (0.24.0 and 0.2.174), so expect API changes between minor versions. The agents track covers them in depth.

**The Vercel AI SDK** is the TypeScript option. Version 7, released 25 June 2026, added a durable `WorkflowAgent`, an experimental `HarnessAgent`, and separate timeouts for the whole call, each step and each tool. Its `generateText` retries twice by default and stops after one step unless you set `stopWhen`, so a tool-calling loop does nothing past the first tool call until you configure it. Code written for older versions used `maxSteps`; a codemod migrates from version 6.

**LiteLLM** sits at a different layer: one interface over many providers, plus a router and proxy for retries, fallbacks and quotas. The router's default strategy is `simple-shuffle`, it puts a deployment in cooldown after 3 failures for 5 seconds by default, and the proxy tries retries first and then fallbacks in the order you list them, including fallbacks for context-window and content-policy errors.

**DSPy** takes the opposite view of prompts: you declare modules with input and output signatures, and an optimiser searches for prompts and examples that maximise a metric on your data. It is worth knowing as the answer to "what if prompts were compiled rather than written", and it only pays off when you have an eval metric you trust.

## The core in plain code

Interviewers ask you to rebuild a framework feature without the framework, partly to see whether you know what it does. A chain, a router and a retriever fit in forty lines:

```python
import re
from collections import Counter

DOCS = {
    "refunds": "Refunds are issued to the original payment method within 5 business days.",
    "shipping": "Standard shipping takes 3 to 7 days. Express shipping takes 1 to 2 days.",
    "returns": "Items can be returned within 30 days if unused and in original packaging.",
}

def words(text):
    return re.findall(r"[a-z0-9]+", text.lower())

def retrieve(query, k=1):
    """Toy retriever: rank documents by word overlap with the query."""
    q = Counter(words(query))
    scored = [(sum(min(q[w], c) for w, c in Counter(words(d)).items()), name)
              for name, d in DOCS.items()]
    return [name for score, name in sorted(scored, reverse=True)[:k] if score > 0]

def route(query, classify):
    """Router: one cheap call picks the branch; plain code dispatches."""
    label = classify(f"Label this as 'policy' or 'chitchat': {query}").strip()
    return {"policy": answer_from_docs, "chitchat": small_talk}.get(label, small_talk)

def answer_from_docs(query, llm):
    """Chain: retrieve, build the prompt, call the model. Every step is visible."""
    names = retrieve(query)
    context = "\n".join(f"<doc name='{n}'>{DOCS[n]}</doc>" for n in names)
    return llm(f"{context}\n<question>{query}</question>\nAnswer from the docs only.")

def small_talk(query, llm):
    return llm(f"Reply briefly and politely: {query}")
```

The policy documents in the listing are made up for the example. Pass in fake `classify` and `llm` functions and the whole pipeline runs in a unit test. What the framework would add on top: a real retriever with embeddings and a vector store, streaming, retries, tracing, a standard message format across providers, and conventions a team can share. What it would take away: the ability to read the exact prompt in one place, and the guarantee that nothing calls the model unless your code does.

## Choosing, and the cost of leaving

A framework earns its place when it solves a problem you actually have and would otherwise build: durable state with pauses for human approval (LangGraph's checkpointer and interrupts), a provider gateway with fallbacks and quotas across many services (LiteLLM), streaming UI plumbing in a TypeScript app (the AI SDK), or prompt optimisation against a metric (DSPy). It costs more than it saves when the application is a few calls in a fixed order, when the team cannot read the prompts it sends, or when its abstractions do not match your provider's newest features.

Abstractions leak at the edges, and the edges move:

- **Provider features arrive before framework support.** Prompt-cache breakpoints, adaptive thinking settings and strict tools appear in the provider API first. Until the framework exposes them, you either drop to the raw client or go without.
- **Defaults change with versions.** The deprecation of `langgraph.prebuilt` in favour of `langchain.agents`, the move of old chains to `langchain-classic`, and the AI SDK's switch from `maxSteps` to `stopWhen` all break code copied from older tutorials.
- **The transport changes under you.** Anthropic's SDK 2.x sends the API key as `Authorization: Bearer` rather than `X-Api-Key`; an internal gateway that only reads the old header fails after an innocent dependency bump.

Keep the exit cheap: your own thin interface for "call a model with these messages and tools", with the framework behind it; prompts in your repository rather than in framework defaults; and an eval set that runs against whichever implementation is live.

<Callout kind="gotcha">
Copied tutorial code is an easy way for stale framework APIs to reach production. `create_react_agent` from `langgraph.prebuilt` is deprecated in favour of `create_agent`, and AI SDK code using `maxSteps` predates `stopWhen`. Check the version a snippet was written for before you paste it.
</Callout>

**"How do you debug an opaque framework chain in production?"**

<Depth>
<Fragment slot="short">
<p>Make it transparent first: turn on the framework's tracing or wrap the model client so every request and response is logged in full, with the final rendered prompt, tool definitions, parameters, token usage and the framework version. Then replay the failing input outside the framework against the raw API. If the raw call behaves, the bug is in what the framework added; if it does not, it is in the prompt or the model.</p>
</Fragment>
<Fragment slot="long">
<p>Visibility. Frameworks expose callback or tracing hooks, and you can always wrap the underlying HTTP client. Log the exact request body, not your template. Count model calls per user request, because hidden retries and re-prompts show up there first.</p>
<p>Isolation. Take one failing trace and replay its final request against the provider API directly. Then bisect: remove middleware, switch the structured-output strategy, pin the previous framework version. A framework upgrade, a model upgrade and a prompt edit landing in the same week is the usual cause of "it just started failing".</p>
<p>Fix in the right layer. If the framework's default prompt is the problem, override it explicitly and add a test that asserts on the rendered prompt. If the framework cannot express what you need (a cache breakpoint, a provider-specific parameter), drop to the raw client for that call behind your own interface.</p>
<p>Trade-off: full request logging captures user data, so redact it, and sample it if traffic is heavy. Tracing that stores prompts is a data store with retention and access rules.</p>
</Fragment>

## When this is wrong

The version numbers and defaults here were read on 28 October 2026 and several of these projects ship weekly. The two provider agent SDKs were still pre-1.0. Treat the specifics as a snapshot and the method, read what is sent and keep an exit, as the lesson.

The ORM analogy also undersells some frameworks. LangGraph's durable execution, with checkpoints, resumable interrupts and recovery after a crash, is real infrastructure, and rebuilding it to avoid a dependency is usually the wrong call. "No framework" is a sound default for a few model calls, not a principle.

Job-description counts measure what employers wrote in 2026 postings in five cities, not what teams run in production or what an interviewer will prefer. Ask in the loop which stack the team uses, and argue from the problem rather than from popularity.
