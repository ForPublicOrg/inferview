## Choose the loss, not the technique

A conversation that outgrows its window has to lose something. Truncation loses the oldest turns entirely. A summary loses detail and adds the summariser's errors. Clearing tool results loses raw outputs the model already acted on. Structured notes lose everything that was not written down. None of these is lossless, so the decision is per product: which facts are pinned and must survive verbatim, which are summarised, and which are dropped, and how a test shows the pinned ones are still honoured at turn 40.

The window is not the only reason to shrink. Chroma's July 2025 report tested 18 models and found that performance drops as input grows even on simple tasks. A single distractor lowered performance against the baseline and four lowered it further. On LongMemEval, with 306 prompts, the full prompts averaged about 113,000 tokens and the focused prompts, holding only the relevant part, about 300; every model did significantly better on the focused version. Anthropic's September 2025 post calls the effect context rot. A context kept small answers better, so compression is also a quality decision, not only a cost one.

## Five mechanisms and what each drops

**Truncation** keeps the last *N* turns, or the last *N* tokens. It is deterministic and cheap, but it is not cache-friendly: dropping the oldest turn changes the start of the messages array, so the request after every drop rewrites the whole conversation into the cache. Truncating in chunks (ten turns at once) makes the rewrite rare. What it drops is the constraint stated in turn 3.

**Summaries** replace older turns with a model-written digest. They keep the gist and lose specifics: exact numbers, identifiers, the wording of a commitment. They also introduce a new failure, a fact the user never said, which then persists because it sits in every later prompt.

**Context editing** clears content by rule on the server. Claude's `clear_tool_uses_20250919` strategy triggers when input passes a threshold (100,000 tokens by default), keeps the most recent tool uses (3 by default), and replaces older results with a placeholder while leaving the calls visible, so the model knows a lookup happened. `exclude_tools` protects results that must stay, `clear_tool_inputs` clears call parameters too, and `clear_at_least` refuses to clear unless a minimum number of tokens goes. A separate `clear_thinking_20251015` strategy drops old thinking blocks. The client keeps the full history; the edit is applied before the prompt reaches the model, and the response reports `applied_edits` with `cleared_input_tokens`. Anthropic's post calls tool-result clearing the lightest form of compaction, since a result deep in history is rarely needed raw again.

**Compaction** has the model summarise the older part of the conversation into a block that replaces it. Claude offers it on demand (beta header `compact-2026-09-04`, where your code decides when and can keep recent turns verbatim or compact in the background) and at a token threshold (`compact_20260112`, default trigger 150,000 input tokens, minimum 50,000, run inside the request that crosses it). Custom `instructions` replace the default summarisation prompt entirely, so a custom prompt has to restate everything the default kept. Compaction's own tokens appear in `usage.iterations` and are not included in the top-level `input_tokens`, so cost dashboards that read the top-level fields undercount it.

**Structured notes** are the one mechanism that does not depend on the model choosing what to keep at compression time. The application, or the model through a tool, writes durable facts into a record (Anthropic's examples are a to-do list in Claude Code and a NOTES.md file) that is injected every turn. Notes are explicit and auditable, and they drop whatever nobody thought to record.

## What each costs at the cache

Every mechanism that edits the middle or start of the prompt invalidates the cached prefix from that point. Claude's context-editing page says so directly: clearing tool results invalidates cached prefixes and incurs cache writes, which is why `clear_at_least` exists. The compaction page recommends a breakpoint at the end of the system prompt so that only the summary is written as a new entry, and allows `cache_control` on the compaction block itself.

Whether clearing pays for itself in money is arithmetic. Scenario numbers, Opus 5.5 prices from the pricing page: a conversation at 120,000 tokens, fully cached. The first tool result to clear starts at token 20,000, and clearing removes 50,000 tokens, leaving 70,000. Prices in base-input units: read 0.05, 5-minute write 1.25.

Without clearing, the next request reads 120,000 tokens: 6,000 units. With clearing, it reads the untouched 20,000 (1,000 units) and writes the remaining 50,000 (62,500 units): 63,500 units. Clearing costs 57,500 units extra on that request. Every later request then reads 70,000 instead of 120,000 tokens, saving 50,000 × 0.05 = 2,500 units.

<Predict id="ce-clear-breakeven" question="How many later requests does it take for the clearing in this scenario to pay back its extra cost?" answer={23} tolerance={1} unit="requests">
57,500 / 2,500 = 23 requests. At $4 per million base tokens the one-off cost is 57,500 × $4 / 1,000,000 = $0.23 and the saving is $0.01 a request. On a model whose reads cost 0.1 times base, the extra is 64,500 − 12,000 = 52,500 units and the saving 5,000 a request, so the payback is 11 requests. With cheap cache reads, clearing is a quality and window decision far more than a cost one.
</Predict>

The same arithmetic, as a function to run against your own layout:

```python
def clearing_payback(context, cleared_from, cleared, read=0.05, write=1.25):
    """Requests until clearing `cleared` tokens starting at token `cleared_from` pays back.
    Multipliers are relative to base input; assumes the whole context was cached before clearing."""
    after = context - cleared
    keep_reading = context * read
    clear_now = cleared_from * read + (after - cleared_from) * write
    saving = cleared * read
    return (clear_now - keep_reading) / saving

print(clearing_payback(120_000, 20_000, 50_000))            # 23.0  (Opus 5.5 multipliers)
print(clearing_payback(120_000, 20_000, 50_000, read=0.1))  # 10.5
```

Two things move the answer more than the price table. Clearing earlier in the conversation (a smaller `cleared_from`) makes the rewrite larger. And if the conversation will hit the window limit anyway, there is no comparison: the only choice is which mechanism drops what.

## Deciding per product

Write the decision down as a table of information classes, not as a choice of technique. For a travel-planning assistant:

| Information | Treatment | Why |
|---|---|---|
| User constraints ("no overnight flights", dietary needs), confirmed bookings | Pinned in structured notes, with the turn each came from | A wrong or missing one breaks the product; must survive any compression |
| Discussion of options the user rejected | Summarised | The gist prevents re-suggesting; the detail is not needed |
| Raw search and pricing tool results | Cleared once used, call kept visible | Large, stale within hours, and re-fetchable |
| The last several turns | Verbatim | References like "the second hotel" resolve only against exact text |

For a coding agent the table changes: file contents are re-readable and can be cleared aggressively, while decisions about architecture and unresolved bugs are what Claude Code's compaction preserves, together with the five most recently accessed files, according to Anthropic's post. For sub-agent fan-out the post describes the isolation variant: the sub-agent spends tens of thousands of tokens exploring and returns a summary of often 1,000 to 2,000 tokens.

The table also defines the test. Recall of pinned facts is measured with scripted conversations that plant a fact early, push the conversation through whatever compression the design uses, and probe late; a second set changes a pinned fact mid-conversation and checks the old value is gone. The pass rate on those probes is the number that goes in the design document, per mechanism and per conversation length.

Needle-in-a-haystack scores do not substitute for that test. HELMET evaluated 59 long-context models and reports that synthetic tasks like needle retrieval do not reliably predict downstream performance; most models score near perfectly on needles while differing on tasks that need reasoning over the full context. A product test that plants facts in realistic conversation is closer to the task than any public needle score.

## When this is wrong

The context-rot and lost-in-the-middle results come from specific benchmarks and model generations. Lost in the Middle measured 2023 models on multi-document QA and key-value retrieval; Chroma notes that its two haystack topics are not enough to generalise from. They justify keeping context focused and testing order, not a rule such as "never exceed N tokens".

The payback arithmetic assumes the whole context was cached before clearing and that requests arrive inside the cache lifetime. If the session is idle for longer than the lifetime, the next request rewrites everything anyway and clearing just before it is free.

Server-side compaction and context editing are beta features with dated headers. Their defaults (100,000 and 150,000 tokens, 3 kept tool uses) are the documented values on 28 October 2026 and are the kind of setting that changes between header versions.
