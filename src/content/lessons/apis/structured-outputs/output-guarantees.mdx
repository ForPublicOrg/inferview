## Four guarantees, chosen per field

A structured response is a set of fields, and each field needs a different guarantee. The `currency` of an invoice needs to be one of twelve codes or the row is useless. The `total` needs to be a non-negative number that matches the line items. The `notes` field needs only to be a string. Treating the response as one object with one guarantee is how teams end up paying for strict decoding and still loading bad rows.

There are four mechanisms, and they guarantee different things:

| Mechanism | Guarantees | Does not guarantee | Cost |
|---|---|---|---|
| Strict schema decoding | The output matches the schema keywords the provider's grammar supports | Keywords outside the supported subset; values that are valid and wrong; completion after a refusal or truncation | First-request compile latency; a schema subset per provider |
| JSON mode | The output parses as JSON | Any field, type or required key | An instruction in the prompt; your own validation |
| Tool call | The arguments of a call the model chose to make, under the same grammar if the tool is strict | That the model calls the tool at all, or calls it once | A round trip and an executor |
| Validate and repair | Whatever your validator checks, on any model | That the repair converges; bounded cost | One full extra call per attempt |

Strict decoding is a grammar compiled from the schema that masks tokens during sampling, the same idea as a parser generator wired into the sampler. Claude's documentation says this directly: the schema is compiled into a grammar, cached for 24 hours from last use, with a compile timeout of 180 seconds. OpenAI calls the feature Structured Outputs and recommends it over JSON mode whenever it is available.

JSON mode is the weaker contract. OpenAI's version throws an error unless the string "JSON" appears somewhere in the context, and without an instruction to produce JSON the model "may generate an unending stream of whitespace" until it hits the token limit. Syntax is all you get.

## The subsets differ, and the differences are fields

The grammar compiler supports a subset of JSON Schema, and the two subsets disagree on exactly the keywords that matter for business fields.

| | OpenAI strict mode | Claude structured outputs |
|---|---|---|
| Numbers | `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf` supported | `minimum`, `maximum`, `multipleOf` not supported |
| Strings | `pattern`; `format` of date-time, time, date, duration, email, hostname, ipv4, ipv6, uuid | Regex without backreferences, lookaround or word boundaries; the same formats plus `uri`; no `minLength` or `maxLength` |
| Arrays | `minItems`, `maxItems` | `minItems` of 0 or 1 only |
| Objects | Root must be an object, not `anyOf`; every field in `required`, optional as a union with null; `additionalProperties: false` | `additionalProperties` must be `false`; no recursive schemas; no external `$ref` |
| Composition | No `allOf`, `not`, `if`/`then`/`else`, `dependentRequired`, `dependentSchemas` | `anyOf` and `allOf` (not `allOf` with `$ref`) |
| Size | 5,000 properties, 10 levels, 120,000 characters of names and enum values, 1,000 enum values | Per request: 20 strict tools, 24 optional parameters, 16 union-typed parameters |
| Key order | Schema order | Required properties first, then optional, each in schema order |

Three consequences are easy to miss. A `minimum: 0` on `total` is enforced by one provider's grammar and not by the other's; Claude's SDK helpers remove the constraint from the wire schema, copy it into the field description and validate the response locally, which is the honest version of what every client should do. The size limits on Claude are counted across every strict schema in the request, tools and output format together, so a feature that adds a strict tool can push an unrelated output schema over the limit. And key order differs: a schema that puts a `reasoning` field before `answer` to make the model write its reasoning first gets that order on OpenAI, gets it on Claude only if both are required, and on Claude can trigger a `reasoning_extraction` refusal; the docs suggest asking for a short explanation instead.

## What a strict response can still be

The grammar guarantees syntax and shape on the tokens the model emits. It cannot guarantee the model emits them.

**Refusal.** Claude returns `stop_reason: "refusal"` with a 200, bills the generated tokens, and the output may not match the schema because the refusal takes precedence. OpenAI adds a `refusal` field; in the Responses API you check each content item for `type: "refusal"` before parsing.

**Truncation.** `stop_reason: "max_tokens"` on Claude, or `status: "incomplete"` with reason `max_output_tokens` on OpenAI. The grammar cannot close an object it ran out of room for.

**Valid and wrong.** Claude may change the capitalisation of an enum value, typically the first letter after a space, with no error and no special stop reason; the documentation's advice is to compare case-insensitively and avoid enum values that differ only in case. A `date-time` string can name the wrong instant. A total can be the subtotal.

**Incompatible features.** On Claude, citations with `output_config.format` return a 400, prefill is incompatible with JSON outputs, and changing `output_config.format` invalidates the prompt cache for that conversation. A retrieval feature that wants citations and a typed response needs two calls or a choice.

So the order in code is fixed: stop reason, then parse, then validate every keyword including the ones the grammar ignored, then business rules, then write.

## Per field: the guarantee and the log line

Take the invoice schema from [the problem that opens this module](/problems/api-006) and decide field by field, assuming the primary provider has strict decoding.

| Field | Guarantee needed | Mechanism | On failure, log |
|---|---|---|---|
| `invoice_id` | Matches `^INV-[0-9]{8}$` | Grammar `pattern` on both providers | Never fails under strict; under JSON mode, the raw value and the pattern |
| `currency` | One of 12 codes, exact | Grammar `enum`, plus case-insensitive compare on Claude | The returned value, and whether it matched after case folding |
| `total` | Number, not negative, equals the line items within rounding | Grammar type; `minimum` by grammar on OpenAI, locally on Claude; the sum locally | The total, the computed sum, the difference |
| `due_date` | A date after the invoice date | Grammar `format: date`; the ordering locally | Both dates |
| `line_items` | Non-empty array of typed objects | Grammar for the item shape; `minItems: 1` works on both | Count, and which item failed |
| `notes` | Any string or null | Union with null | Nothing; this field never blocks a write |

The log line matters as much as the check. A failure record should carry the stop reason, the schema version, the field path, the failing value, the attempt number and the model. Without the field path, a dashboard shows "validation failures up" and nobody can tell whether the cause is a model change, a schema change or a new vendor's invoice layout.

## The bounded repair loop

Validate-and-repair is the mechanism that works everywhere: on a model without constrained decoding, on keywords the grammar ignores, and on business rules no grammar can express. The repair goes back as a user turn listing the errors. On Claude 4.6 and later a prefilled final assistant message returns a 400, so a user turn is also the only form that works there.

```python
import json

def extract(call_model, validate, invoice_text, max_repairs=2):
    """call_model(messages) -> (stop_reason, text). validate(obj) -> list of (path, message)."""
    messages = [{"role": "user", "content": invoice_text}]
    for attempt in range(max_repairs + 1):
        stop, raw = call_model(messages)
        if stop in ("refusal", "max_tokens"):
            return None, {"attempt": attempt, "stop": stop}          # repair cannot fix these
        try:
            obj = json.loads(raw)
            errors = validate(obj)
        except json.JSONDecodeError as e:
            obj, errors = None, [("$", f"invalid JSON at char {e.pos}")]
        if not errors:
            return obj, None
        messages += [{"role": "assistant", "content": raw},
                     {"role": "user", "content": "Fix only these fields and return the whole object as JSON:\n"
                      + "\n".join(f"{p}: {m}" for p, m in errors)}]
    return None, {"attempt": attempt, "errors": errors}              # to the dead-letter table
```

Two decisions are in that code. Refusal and truncation are not repaired: a refusal repeated with an error list is still a refusal, and truncation is fixed by a larger `max_tokens` or a smaller schema, not by asking again. And the cap is a cost cap, because each attempt re-sends the invoice and the growing conversation.

Expected calls per document follow from the per-attempt failure rate. With a failure rate f per attempt and attempts independent, the expected number of calls with two repairs is 1 + f + f². At a toy rate of f = 0.08, that is 1 + 0.08 + 0.0064 = 1.0864 calls per document, and the share that ends in the dead-letter table is f³ = 0.000512. Attempts on one document are unlikely to be independent: the layout that misled the first attempt is still in the context for the second, so expect the measured dead-letter rate to sit above f³ and the second repair to buy less than the first. Measure the per-attempt success rate on your own failures before raising the cap.

Validate the JSON text, not a converted object. Pydantic's strict mode accepts `"1987-01-28"` for a date field in `model_validate_json`, because JSON has no date type, and rejects the same string passed to `model_validate`. A pipeline that parses with `json.loads` and then validates the dict in strict mode rejects every date. For progressive display of a streamed object, `from_json(data, allow_partial=True)` returns `['aa', 'bb']` for `'["aa", "bb", "c'`, dropping the incomplete item; it is reliable only when every field has a default, and it is for display, never for acting on the value.

## When this is wrong

The schema limits and supported keywords here were read from both providers' documentation on 28 October 2026. Both lists have grown before, and a keyword missing today may be enforced next quarter, so the local validator should check everything regardless and the table above should be re-read before designing around a gap.

Constrained decoding is a provider feature, and a model behind your own gateway may or may not have a grammar backend. Code that assumes strict decoding everywhere fails on the first failover; code that validates everything locally works on all of them, more slowly.

A per-field table assumes the fields are independent. Many business rules span fields (dates in order, totals that sum), and those live in the business-rule step whatever the per-field mechanism is.

Finally, a schema is not a specification. It cannot say a summary is faithful to its source or that a vendor exists. Those checks belong to evaluation, which this track covers in the tool-evaluation lesson and the evals track covers in depth.
