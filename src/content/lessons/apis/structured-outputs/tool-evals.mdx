## Four questions, four checks

"Did the agent use the tools correctly" is four questions, and each fails for different reasons and needs a different check.

| Question | Typical cause of failure | Check | What the check misses |
|---|---|---|---|
| Selection: right tool, or no tool | Overlapping descriptions; a missing tool the model improvises around | Compare the tool name (or "no call") with the expected one | Whether the arguments were right |
| Arguments: right values | Ambiguous parameters, missing context, unit and format mismatches | Match each argument against a set of acceptable values | Equivalent values you did not list; effects of the call |
| Sequencing: right order | Dependencies the model did not see; a write before a confirmation | Partial-order constraints over the call sequence | Whether the final state is right |
| End state: right outcome | Everything above, plus the user's behaviour | Compare the system's state after the conversation with a goal state | Which step went wrong |

The last column is why one check is never enough. An end-state check tells you the refund did not happen; it does not tell you whether the model picked the wrong tool or the right tool with the wrong order id. A per-call check tells you the arguments matched; it does not tell you the agent then cancelled the order it just refunded. Run the cheap per-call checks on every case and the end-state check on the conversations that have an end state.

## Matching a call: the AST approach

The Berkeley Function Calling Leaderboard introduced AST matching as a metric in its first version: parse the model's call into a function name and a set of arguments, and compare that structure, not the text, with the expected call. The engineering detail that makes it work is that the expected value of each argument is a set, not a value. "Tomorrow at 3pm" for a user in Pune can legitimately be `2026-10-29T15:00:00+05:30` or `2026-10-29T09:30:00Z`; both are correct, and an exact-string match fails one of them.

```python
from datetime import datetime

def norm(v):
    """Canonicalise values that have several correct spellings."""
    if isinstance(v, str):
        try:
            return ("instant", datetime.fromisoformat(v.replace("Z", "+00:00")).timestamp())
        except ValueError:
            return ("str", v.strip().casefold())
    return ("val", v)

def match_call(call, expected):
    """call: {"name", "args"}. expected: {"name", "args": {param: [acceptable values]}, "optional": set}.
    Returns a list of (kind, detail) mismatches; empty means a match."""
    if call["name"] != expected["name"]:
        return [("selection", f"{call['name']} instead of {expected['name']}")]
    problems = []
    for param, allowed in expected["args"].items():
        if param not in call["args"]:
            if param not in expected.get("optional", set()):
                problems.append(("missing", param))
        elif norm(call["args"][param]) not in {norm(a) for a in allowed}:
            problems.append(("value", f"{param}={call['args'][param]!r}"))
    for param in call["args"].keys() - expected["args"].keys():
        problems.append(("unexpected", param))
    return problems
```

The mismatch kinds are the point. A single argument-accuracy percentage is less useful than a report that says most failures are `value` mismatches on one parameter, because that points at a description or a missing piece of context, and the fix is different from a `selection` failure.

Normalisation is a decision, not plumbing. Case-folding strings is right for a city name and wrong for an order id. Comparing instants is right for a meeting start and wrong when the user's zone is the thing under test, because `09:30Z` and `15:00+05:30` are the same instant and only one of them shows that the model used the user's zone. Each parameter needs its own comparator, chosen by what the downstream code does with the value.

## Executable checks and end state

An executable check runs the call against a sandboxed or faked backend and compares the result, not the call. It accepts argument spellings you did not anticipate, as long as the backend treats them the same way, and it catches calls that match the expected structure but fail at runtime. It costs a backend you can reset between cases.

End-state checks go one level up. τ-bench, published in 2024, simulates the user with a language model, gives the agent domain API tools and policy rules, and scores a conversation by comparing the database state at the end with an annotated goal state. That scoring is indifferent to the path: two calls or five, in any order that reaches the goal, score the same. It also makes the user part of the test, which is where single-turn benchmarks are silent. The paper's abstract reports that gpt-4o, then a leading function-calling model, succeeded on fewer than 50 percent of tasks.

τ²-bench, from 2025, goes further: in its telecom domain the user also has tools and acts on a shared environment, so the agent has to guide a person through steps it cannot take itself. The abstract reports significant drops when agents move from the no-user setting to this dual-control one, without a figure in the abstract. For an internal agent whose users click things while it works, that is the setting that matches production.

## Reliability is a different number

τ-bench also proposes pass^k: the probability that all k independent trials of the same task succeed. The paper's abstract reports pass^8 below 25 percent in its retail domain. The quantity matters because a customer who asks the same thing twice expects the same outcome twice. The evals track covers the estimator in [pass@k and pass^k](/learn/evals/agent-evals/pass-hat-k); the arithmetic needed here is short.

## Reading a leaderboard number

BFCL is the public reference for function calling. Version 4 (last updated 12 April 2026 when checked) adds holistic agentic evaluation to the single-turn, enterprise and multi-turn categories of earlier versions, and reports cost and latency next to accuracy. Its Overall Accuracy is the unweighted average of all sub-categories. That is a sensible public number and a poor proxy for your workload, and a toy calculation shows why. Suppose a model scores 90 on single-turn categories and 40 on multi-turn ones, and suppose for simplicity those are the only two. The unweighted average is (90 + 40) / 2 = 65. If 95 percent of your traffic is multi-turn, the score that predicts your experience is 0.05 × 90 + 0.95 × 40 = 42.5. Read the sub-category that matches your traffic, and the cost and latency columns next to it.

Format matters too: BFCL's format-sensitivity cases apply only to models prompted to write calls as text, not to native function-calling. If your stack prompts a model to emit calls in text, the native-mode numbers do not describe it.

## Building the eval for one internal API

Take one internal API the agent calls, say the calendar service.

1. **Cases from logs.** Sample real requests that led to calendar calls, stratified by product and by the parameters that vary (zones, recurrence, attendees). Hold out a test split before anyone tunes a description; Anthropic's tools post describes relying on held-out sets for exactly this reason, because descriptions tuned on the eval stop measuring anything.
2. **Labels as sets.** For each case, the expected tool (or "no call", or "ask the user"), and per parameter the set of acceptable values with its comparator. "Ask the user" is a label: a request with no time zone and no profile zone should produce a question, not a guess.
3. **Constraints, not sequences.** For multi-call cases, write the partial order (find slots before schedule; confirm before cancel) and the forbidden calls, rather than one expected sequence.
4. **End state where it exists.** For cases that change the calendar, a reset-able sandbox and the expected events afterwards.
5. **Report by failure kind.** Selection, missing, value, unexpected, order, end state, each as a rate with a confidence interval, plus the operational metrics Anthropic lists: runtime, number of tool calls, tokens and tool errors. A change that keeps accuracy and doubles the calls per task is a regression.

Then put the suite on the path of every change that can move it: tool descriptions, schemas, the system prompt, the model version. The same post reports that whether tools were namespaced by prefix or suffix had non-trivial effects on its evaluations, which is the kind of change nobody would think to test without a suite already running.

## When this is wrong

Per-call matching assumes there is a right call. For open-ended tasks (research, triage) several different call sequences are equally good, and argument sets cannot enumerate them; end-state checks or graded rubrics fit better, at the cost of the diagnosis that per-call checks give.

LM-simulated users, as in τ-bench and τ²-bench, are themselves models with failure modes. A simulator that is more cooperative than real users inflates scores; one that drifts off script deflates them. Calibrate the simulator on recorded conversations before trusting a score that depends on it.

And benchmark facts age quickly. The BFCL version, its categories and its averaging rule were read on 28 October 2026; τ-bench and τ²-bench results are those in the abstracts, for the models tested then. Use them to choose the shape of your eval, not to predict how your model will score on it.
