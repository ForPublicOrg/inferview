## What it is and who runs it

The OpenAI Agents SDK is an open-source Python library from OpenAI for building agent applications, installed as `openai-agents` (0.24.0 on PyPI on 15 October 2026, still pre-1.0). It runs in your process. OpenAI runs the models behind it, using the Responses API by default for OpenAI models, and by default receives the traces. Non-OpenAI providers plug in through a model provider.

Its docs name two design principles: enough features to be worth using with few enough primitives to learn quickly, and good behaviour out of the box with every step customisable. The primitives are agents (a model with instructions and tools), delegation between agents (as handoffs or as tools), and guardrails. Sessions, human-in-the-loop approvals, tracing and sandbox agents are built on those. This teardown covers the Python SDK from its public documentation and source; everything on OpenAI's side of the API is outside it.

**Runner loop.** `Runner.run`, `run_sync` and `run_streamed` drive one loop: call the current agent's model; if the output is final (the desired type and no tool calls), return it; if it is a handoff, switch the current agent and loop; if it contains tool calls, run them, append the results and loop. The loop is client-side, so every turn is a separate model request from your process. Turns are capped by `max_turns`, which defaults to `DEFAULT_MAX_TURNS = 10` in `run_config.py`; past the cap the runner raises `MaxTurnsExceeded` unless an error handler for `max_turns` returns a controlled final output instead.

**Agents and agents as tools.** An agent is a model, instructions and tools. Delegation takes two shapes. With agents as tools (`Agent.as_tool`), a manager agent calls a specialist like any tool and gets its output back as a tool result, so the manager stays in control of the conversation. With a handoff, the specialist takes over the rest of the run.

**Handoffs with input filters.** A handoff is presented to the model as a tool named `transfer_to_<agent_name>`. `input_type` gives it a schema for arguments, `on_handoff` runs a callback, and `is_enabled` hides it at runtime. By default the receiving agent sees the entire previous history. An `input_filter` rewrites that history before the specialist sees it, for example `handoff_filters.remove_all_tools` to drop tool items. Nested handoff history, which compacts earlier turns into summary segments, is an opt-in beta and off by default. Neither the filter nor nesting redacts data that appears in ordinary messages.

**Guardrails.** Input guardrails run on the user's input for the first agent only; output guardrails run on the final output of the last agent only. Input guardrails run in parallel with the agent by default (`run_in_parallel=True`) for latency, with a blocking mode that finishes the check before the agent starts. Tool guardrails wrap individual function tools and run on every call, before and after execution. A tripped guardrail raises a tripwire exception.

**Tools and approvals.** Function tools, MCP servers, shell and patch tools. Any of them can require approval: `needs_approval=True`, or a callable that decides per call from the parsed arguments and fails closed if the arguments cannot be inspected. Local `ShellTool` and `ApplyPatchTool` default to no approval.

**Sessions.** A session loads history before a run and appends to it after. `SQLiteSession` is the default and is in memory unless given a file path; Redis, SQLAlchemy, MongoDB, Dapr and an OpenAI Conversations-backed session are alternatives, and an encrypted wrapper adds encryption and TTL. A session cannot be combined with the server-side `conversation_id` or `previous_response_id` in the same run; mixing them duplicates context.

**Human-in-the-loop with serialisable run state.** When a tool needs approval and no decision is stored, the run pauses and returns `interruptions`. `result.to_state()` produces a `RunState` that serialises with `to_json()` or `to_string()`, survives a process exit, and resumes with `Runner.run(agent, state)` after `state.approve(...)` or `state.reject(...)`.

**Tracing.** On by default, with spans for the run, each agent, each model generation, function tools, guardrails and handoffs, exported in batches to OpenAI's Traces dashboard. Inputs and outputs are included by default. A custom processor can be added beside the default exporter or replace it.

**Temporal integration.** For durability, Temporal's integration runs each agent invocation as a Temporal Activity, with orchestration as ordinary Python in a Workflow, so a crash resumes from recorded Activity results. Handoff targets run as their own Activities. The Python integration has been generally available since 23 March 2026.

## Context strategy

The SDK's default is to carry everything: the session supplies prior turns, and a handoff passes the whole history to the next agent. The levers are explicit. `input_filter` per handoff or `handoff_input_filter` in `RunConfig` prunes what a specialist sees; nested handoff history compacts earlier turns into summary segments; `call_model_input_filter` edits the prepared input immediately before every model call; and `OpenAIResponsesCompactionSession` wraps a session to compact long histories through the Responses API. Agents as tools are the other context tool: the specialist gets only the input the manager writes, and the manager gets only its output, so long specialist work does not enter the manager's context.

## Tools and permission model

Permissions are per tool call. Approval policies can be static or decided from parsed arguments, and decisions can be sticky (`always_approve`, `always_reject`) and survive serialisation. Approval decisions for shell and file-edit tools are shared by tool type and name rather than by agent, so they carry across handoffs. Tool guardrails are the only checks that run around every function-tool call when work is delegated, because agent-level guardrails cover only the first agent's input and the last agent's output, and tool guardrails do not apply to the handoff call itself. For tools that need approval, tool input guardrails run after approval unless `pre_approval_tool_input_guardrails` is set.

## Cost and latency

Every turn is a model request, and with the default handoff behaviour each specialist re-reads the full history, so token cost grows with the number of handoffs as well as the number of turns. Parallel input guardrails trade cost for latency: the agent starts immediately, and when the guardrail trips, the tokens and any tool calls already made are spent. Blocking mode costs the guardrail's latency on every request and saves that waste. Default-on tracing adds a background export from your process to OpenAI. The Temporal integration adds an Activity per agent invocation, which buys recovery after a crash at the cost of Temporal's own scheduling and storage.

## Failure modes

- **Loops that stop quietly.** A `max_turns` error handler that returns a final output, kept in history by default, turns a runaway loop into an ordinary answer. Count those separately.
- **Guardrail gaps.** A guardrail placed on a specialist reached by handoff never runs on the user's input, because input guardrails run only for the first agent.
- **Double execution.** A process that stops after a tool's external action but before the state is saved resumes from an older approved snapshot and runs the tool again. The docs prescribe idempotency keys, or reconciliation and a recorded unknown outcome when keys are not possible.
- **Forged approvals.** Restoring `RunState` from client-supplied JSON lets a caller submit a snapshot with decisions already recorded. The docs require server-side storage of the snapshot, server-side authentication of the reviewer, and atomic, owner-checked consumption of each pending item.
- **Data leaving by default.** Traces include inputs and outputs and go to OpenAI unless configured otherwise; under Zero Data Retention tracing is unavailable, so a ZDR organisation that never configured its own processor has no traces at all.
- **Duplicated context.** A session combined with server-managed conversation state is rejected in one run, but mixing them across runs duplicates history.

## What is not public

The SDK is open source; what happens behind the API it calls is not. Hosted-side behaviour, such as how the Responses API and the Conversations API store and process state, how long OpenAI retains trace data beyond what account settings document, and how hosted tools execute, is not described in the SDK docs, and this lesson does not guess at it. The human-in-the-loop docs are explicit about one boundary that teams assume the SDK covers: `RunState.from_json()` and `RunState.from_string()` "do not authenticate the snapshot or the person submitting it." Authentication of reviewers and integrity of snapshots are the application's job, and nothing public describes a hosted service that does it for you.

## When this is wrong

This teardown describes a pre-1.0 SDK as documented on 28 October 2026; the turn default, the beta for nested history and the list of session classes are the parts most likely to change. It covers the Python SDK only. The trace is a scenario built from documented behaviour, not a recorded production run.
