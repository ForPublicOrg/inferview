## Four things someone has to own

An agent harness is a loop around a model plus four pieces of state and infrastructure: the session log (every message, tool call and result), the sandbox where tools run, the credentials those tools use, and the upgrade schedule of the loop itself. Build-versus-rent is the choice of who holds each one. The comparison that matters is not features on the day you decide; it is what each option makes hard to change two years later.

Four options span the space as of 28 October 2026:

- **Your own loop** on a provider's client SDK. The Claude docs describe this path as calling the API directly and writing the tool loop yourself (or using the client SDK's beta tool runner).
- **Claude Agent SDK**: a library that runs the Claude Code binary in a process you operate, with Claude Code's tools, permissions, sessions and hooks.
- **OpenAI Agents SDK**: a library with agents, handoffs, guardrails, pluggable sessions, human-in-the-loop and tracing, running in your process.
- **Claude Managed Agents**: a hosted harness, in beta behind `managed-agents-2026-04-01`, where Anthropic runs the loop and stores the session, with a cloud sandbox or a self-hosted one.

## Who holds what

| | Session log | Sandbox | Credentials | Upgrades |
|---|---|---|---|---|
| Own loop | Your store, your schema | Yours | Yours | When you ship |
| Claude Agent SDK | JSONL files on the host's disk, or your backend through a `SessionStore` adapter | The host or container you run it in | Your environment | SDK releases that bundle a CLI version |
| OpenAI Agents SDK | Your choice of session class (SQLite, Redis, SQLAlchemy and others) or OpenAI's Conversations API | Yours, or a sandbox client for sandbox agents | Your environment | SDK releases; traces go to OpenAI unless redirected |
| Claude Managed Agents | Anthropic, server-side, fetchable in full | Anthropic cloud or self-hosted | Vaults and a proxy run by Anthropic | Anthropic's schedule; the docs say behaviours may be refined between releases |

Read the table by column, because each column fails differently.

**The session log is the hardest to move.** It is the audit record, the resume point and, for a regulated business, a data store with retention rules. The Claude Agent SDK writes transcripts to `~/.claude/projects/<encoded-cwd>/*.jsonl` on the machine that ran the session; resuming on another host requires shipping the file or attaching a `SessionStore` adapter that mirrors transcripts to your backend. That is a local file system holding regulated data unless you plan for it. The OpenAI Agents SDK's default `SQLiteSession` is in memory and lost when the process ends unless you give it a file path; production means choosing Redis, SQLAlchemy or a custom class with four history methods. Managed Agents stores conversation history, sandbox state and outputs server-side, which is why it is not currently eligible for Zero Data Retention or HIPAA BAA coverage. You can delete sessions through the API, but the data lives with Anthropic while the session exists.

**The sandbox decides your network topology.** Anthropic's April 2026 post on Managed Agents explains why its first design failed: the harness ran inside the container, so a customer who wanted Claude to reach resources in their own network had to peer it with Anthropic's or run the harness themselves. The rebuilt design puts the sandbox behind one `execute(name, input)` call, provisions containers only when a tool first needs one, and reports that p50 time to first token fell by roughly 60 percent and p95 by over 90 percent. The self-hosted sandbox option keeps execution on your infrastructure; the loop and the log still run at Anthropic.

**Credentials move from your secrets manager to someone's vault.** In Managed Agents, MCP OAuth tokens sit in a vault behind a proxy, and the harness never sees them; a repository token is used once to clone and wire the remote. A hand-written loop that passes tokens in environment variables gives them to any code the model writes and runs. It also means the credential store your security team audits is one they do not operate.

**Upgrades arrive on someone else's schedule.** An SDK pins to a version you choose; a hosted harness changes under you. The Claude Agent SDK is pre-1.0 (0.2.174 on PyPI on 24 October 2026) and the OpenAI Agents SDK too (0.24.0 on 15 October 2026), so pinning is necessary but each upgrade is a reviewed change with an eval run. With a hosted harness, the eval run is the only control left: you cannot hold back an improvement to compaction that changes your agent's behaviour.

## What renting costs, computed

Managed Agents bills tokens at the model's rates with the same caching multipliers as the Messages API, plus $0.08 per session-hour, measured only while a session's status is `running`. Time spent idle, waiting for your next message or a tool confirmation, is not billed.

<Predict id="api-rent-runtime" question="A team runs 3,000 agent sessions a day. Each session spends 6 minutes in running status and waits another 40 minutes idle for a human approval. At $0.08 per running session-hour, what is the runtime charge for a 30-day month, in dollars?" answer={720} tolerance={5} unit="$">
<p><b>$720.</b> Running time per day is 3,000 × 6 / 60 = 300 session-hours, which is 300 × $0.08 = $24 a day and $720 over 30 days. The 40 idle minutes add nothing, because idle time is not billed. Tokens are the same line item whether you rent the harness or run your own loop on the same model, so the comparable cost is $720 a month against the compute, storage and on-call time of running your own loop, sandboxes and session store.</p>
</Predict>

At this scale the runtime fee is small next to one engineer's time. That makes the cost argument for building weak unless volume is very large, and it moves the decision to the controls column.

## The memo for a regulated enterprise

Scenario, labelled as such: a bank's operations group runs a hand-written agent loop that reconciles disputed card transactions. It reads customer records, drafts a resolution and files it after an analyst approves. Leadership wants to stop maintaining the loop. The compliance team requires that customer data is not retained by vendors beyond the request, that every tool call is logged in the bank's own audit store, and that no credential for the core banking system leaves the bank's network.

A memo that survives review states the controls first and then tests each option against them.

**Data retention.** Managed Agents is ruled out for this workload today: it stores session history and outputs server-side and is not eligible for Zero Data Retention, as of 28 October 2026. If the bank's agreement with its model vendor depends on ZDR, the OpenAI Agents SDK's tracing must be disabled or replaced, because the docs say tracing is unavailable under ZDR and exports inputs and outputs by default.

**Audit log in the bank's store.** Both SDKs can satisfy this with work: a `SessionStore` adapter for the Claude Agent SDK, a custom session class or trace processor for the OpenAI Agents SDK. The own loop satisfies it by construction.

**Credentials inside the network.** An SDK running in the bank's network keeps credentials there, but its tools run with the process's privileges, so the sandbox boundary is the bank's to build. The vault-and-proxy pattern from the Managed Agents post is worth copying into whichever runtime the bank chooses: the model's code never sees a token, and outbound calls get credentials injected at the edge.

**Recommendation in the memo.** Rent the loop as a library, not as a service: adopt one agent SDK inside the bank's network with sessions mirrored to the bank's store, tracing redirected to the bank's own collector, and a credential proxy in front of the core banking API. Keep the bank's own eval set as the gate on every SDK upgrade. Revisit the hosted option when it is eligible for the bank's retention terms, and record that condition in the memo.

What the bank gives up: Anthropic's managed sandbox, on-demand provisioning and the vault it does not have to build, plus a recurring cost in SDK upgrades it must qualify itself. The failure mode of the recommendation is that the adapters (session store, trace processor, credential proxy) become a private harness of their own, with none of the vendor's maintenance and all of the framework's coupling. Budget them as owned code with an owner.

## When this is wrong

The table describes products in beta or pre-1.0 as of 28 October 2026. Eligibility for retention programmes, sandbox options and session storage are the facts most likely to change, and any of them flips the memo. Recheck them on the day you decide and date the memo.

The framing assumes the harness is a commodity you either run or rent. For coding agents the harness is part of the product's quality, and the vendor's harness may be better tuned to its model than anything a three-person team writes. Then the build option costs quality, not just engineering time, and the comparison needs an eval on your tasks, not a controls table.

Finally, the four options are not exclusive. Teams run a provider SDK for the agent and their own loop for fixed pipelines, or rent a hosted harness for internal tools while keeping customer-facing agents in-house. The memo is per workload, and the data classification of each workload usually decides it.
