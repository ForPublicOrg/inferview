## The flaky eval

Scenario, not a real company: a team runs a 200-case regression suite against a self-hosted model every night with temperature set to 0. Most nights 200 pass. Some nights 197 do, and the three failures are different cases each time. Nobody changed the prompt, the weights or the code. Someone files a bug titled "GPU randomness".

It is not randomness in the sense they mean, and the fix is not where they are looking. To see why, you need the last step of every generation: how a vector of scores becomes one token.

## Scores, then a policy

At each step the model outputs one number per vocabulary entry, called a logit. For o200k that is about 200,000 numbers. Higher means more likely. Logits are not probabilities: they can be negative and they do not sum to anything.

Softmax converts them: exponentiate each logit, divide by the sum. Temperature divides the logits before the softmax. Below 1 it stretches the gaps, so the top token takes more of the mass. Above 1 it squeezes them, so the tail gets more. Temperature 0 would divide by zero, so libraries treat it as a special case meaning "take the argmax", which is greedy decoding.

Everything after softmax is a policy you choose, the way a load balancer's algorithm is a policy on top of the same backend health scores. Here are the common ones:

- **Greedy:** always take the top token. Repeatable on paper, and prone to loops in long outputs. Holtzman et al. found that decoding which maximises likelihood produces text that is bland and repetitive.
- **Top-k:** keep the k most likely tokens, renormalise, sample. Fixed k is blunt: when the model is confident, k = 40 still admits 39 bad options; when it is unsure, 40 may cut good ones.
- **Top-p (nucleus):** keep the smallest set of top tokens whose probabilities add up to at least p, renormalise, sample. The set grows when the model is unsure and shrinks when it is confident. This is Holtzman et al.'s proposal for cutting the unreliable tail.
- **Min-p:** keep tokens whose probability is at least p times the top token's probability. The bar moves with the model's confidence. The min-p paper reports the largest gains at high temperature, where top-p lets in more junk.

One detail interviewers like: the order of the filters is not standard. ## Why temperature 0 still drifts

Back to the flaky eval. Floating-point addition is not associative: in Python, (0.1 + 0.2) + 0.3 gives 0.6000000000000001 and 0.1 + (0.2 + 0.3) gives 0.6. A GPU kernel that sums thousands of numbers in a different order gets a slightly different result. When the top two logits are nearly tied, a difference in the last bits flips the argmax, and from that token on the two outputs diverge.

The 2025 finding from Thinking Machines is about which kernels change their order and when. They ran the same prompt 1,000 times through Qwen3-235B-A22B-Instruct-2507 at temperature 0 and got 80 distinct completions. All agreed for the first 102 tokens and split at token 103: 992 said "Queens, New York" and 8 said "New York City". The cause they identify is that common inference kernels are not batch-invariant: the reduction order inside matrix multiplication, attention and normalisation depends on the batch size, and the batch size depends on how many other requests the server is handling at that moment. Your request's numbers depend on other people's traffic.

With batch-invariant kernels all 1,000 completions matched. It costs speed: on Qwen3-8B their test took 26 seconds with default vLLM and 42 seconds with their improved deterministic kernels.

<Callout kind="gotcha">
"Set temperature to 0 for determinism" is wrong twice in 2026. Server load still changes greedy outputs on most stacks, and current hosted reasoning models will not accept the parameter at all.
</Callout>

## The knobs are leaving the hosted APIs

That second point is recent. Claude's docs say current models return a 400 error for a non-default temperature, top_p or top_k, and from API version 2026-10-21 setting any of the three returns 400 on every Claude model. OpenAI's guide for its latest models says to remove temperature, top_p and top_logprobs when reasoning effort is anything other than none. Open-weight model cards still publish settings, and they differ by model: DeepSeek-R1 recommends temperature 0.6, while the Qwen3.8-27B card recommends temperature 1.0, top_p 0.95 and top_k 20 in thinking mode. A single "best temperature" is not a thing.

So "how do you make output repeatable" now has a different answer. Pin the model snapshot. Make the eval tolerate variation (score properties of the answer, run each case several times and track the pass rate). Cache responses you need to replay. Use structured outputs where the shape matters. And if you self-host and truly need bit-identical outputs, use batch-invariant kernels and pay the latency.

## Constrained decoding

Structured outputs work by editing the policy, not the model. Before sampling each token, the engine computes which tokens can extend the output and still match a grammar (compiled from your JSON schema or regex) and sets every other token's logit to minus infinity. The model cannot emit an invalid character because invalid characters have probability 0.

The hard part is that tokens do not line up with grammar symbols: one token can close a string and open the next key. XGrammar's answer is to split the vocabulary into tokens whose validity can be checked ahead of time and a smaller set that must be checked at runtime against the parser state. In vLLM you pick a backend (xgrammar or guidance) and a constraint type: choice, regex, json, grammar or structural_tag.

What it does not do is make the content right. Mask a model that wanted to answer "Sure!" into a JSON label and you get valid JSON with whichever label the masked logits favour. Claude's docs list how a constrained response can still miss the schema: a refusal, or hitting max_tokens mid-object. They also list schema features the grammar compiler does not support, and note that the first request with a new schema pays a compile cost while compiled grammars are cached for 24 hours. Validate the parsed object anyway.

Claude 4.6 and later also reject a prefilled final assistant turn, the old trick of starting the reply with an opening brace. Structured outputs replaced it.

## Logprobs as a debugging tool

Where you can get them, the log-probabilities of the chosen tokens are cheap instrumentation. Sum them for the sequence log-probability; exponentiate the negative mean for perplexity; flag tokens below a probability threshold to find where the model was unsure.

```python
import math

token_logprobs = [("The", -0.01), (" invoice", -0.20), (" total", -0.05), (" is", -0.02),
                  (" $", -0.30), ("4", -2.30), ("12", -1.60), (".", -0.10)]
total = sum(lp for _, lp in token_logprobs)
ppl = math.exp(-total / len(token_logprobs))
print(round(total, 2), round(ppl, 2))                     # -4.58 1.77
print([(t, round(math.exp(lp), 2)) for t, lp in token_logprobs if lp < math.log(0.5)])
# [('4', 0.1), ('12', 0.2)]: the digits of the amount are where the model was guessing
```

The numbers above are invented to show the arithmetic. The limit is availability: OpenAI's guide for its latest models tells callers to remove logprobs and top_logprobs when reasoning effort is anything other than none, and reasoning tokens you never see are billed as output and occupy context. Logprob tooling is easiest on a self-hosted server such as vLLM or on a non-reasoning setting.

## A sampler in code

```python
import math, random

def softmax(logits, temperature=1.0):
    scaled = {t: v / temperature for t, v in logits.items()}
    m = max(scaled.values())                        # subtract the max before exp
    exps = {t: math.exp(v - m) for t, v in scaled.items()}
    z = sum(exps.values())
    return {t: e / z for t, e in exps.items()}

def top_p(probs, p):
    kept, total = {}, 0.0
    for t, q in sorted(probs.items(), key=lambda kv: -kv[1]):
        kept[t] = q
        total += q
        if total >= p:                              # smallest set that reaches p
            break
    z = sum(kept.values())
    return {t: q / z for t, q in kept.items()}

logits = {"Paris": 6.1, "the": 3.4, "a": 3.0, "Lyon": 2.2, "located": 2.0, "Marseille": 1.1}
for T in (1.0, 2.0):
    print(T, sorted(top_p(softmax(logits, T), 0.9)))
# 1.0 ['Paris', 'the']
# 2.0 ['Lyon', 'Paris', 'a', 'located', 'the']
rng = random.Random(0)
dist = top_p(softmax(logits, 1.0), 0.9)
print(rng.choices(list(dist), weights=list(dist.values()), k=5))
```

## When this is wrong

This lesson treats the logits as the model's honest belief and sampling as a separate, swappable layer. On reasoning models that line blurs: the visible answer comes after hidden reasoning tokens that were themselves sampled, the provider chooses the policy, and you may not be allowed to change it. Your levers there are effort settings, output limits and structured outputs, not temperature.

Constrained decoding also has a cost the toy hides. Very large or recursive schemas can be slow to compile or unsupported, and forcing a format the model would not naturally produce can lower answer quality. Measure accuracy with and without the constraint on your own task before declaring it free.
