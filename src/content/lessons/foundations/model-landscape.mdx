## The cheaper model that cost more

Scenario, not a real company: a team moves a document-tagging job from one hosted model to another whose list price per million tokens is a fifth of the old one. The next invoice is lower but nowhere near a fifth. The new model writes longer answers, runs a reasoning phase by default, and its tokenizer cuts the same documents into more pieces. Per token it is cheaper. Per task it is not cheap enough to justify the drop in accuracy that the team only noticed a week later.

Everything in that scenario is something you can read off a model card and a price page before switching, and everything else is something you can measure in an afternoon with a small bake-off. That is this lesson. The model names will be out of date by the time you read it; the reading skill will not.

## Three kinds of model

**Frontier hosted models** are the largest models from OpenAI, Anthropic, Google and others, reached only through an API. You get the best general quality, no weights, and terms that change on the vendor's schedule.

**Open-weight models** publish their weights and a config file, so you can run them on your own hardware or through any host. Licences differ: Apache 2.0 for Qwen3, gpt-oss and Gemma 4, MIT for DeepSeek-R1, a modified MIT for Kimi K2. "Open weights" is not the same as "open source", and the licence is part of the selection.

**Small models** (a few billion active parameters or fewer, hosted or open) trade general ability for cost and latency. For a narrow task with a good eval, a small model, possibly fine-tuned, is often the right answer.

## Reading an open-weight model card

The analogy I use is a hardware spec sheet. The headline number is never the one that decides whether it fits your rack.

Most large open models released since 2024 are mixture-of-experts (MoE). Each layer has many feed-forward "experts" and a router that sends each token to a few of them. Two parameter counts matter, and they answer different questions:

- **Active parameters** set compute per token, so they drive latency and throughput.
- **Total parameters** set memory, because every expert must be loaded even if a given token uses only a few. Google's Gemma 4 docs say this directly: the 26B A4B model activates about 4B parameters but all 26B must be in memory.

Beyond parameters, read: the context length and how it was reached (a config's maximum positions is a ceiling, see the attention lesson), the attention type (GQA, MLA, sliding-window, hybrid linear) because it sets KV cache per token, the quantization the weights ship in, the chat template, and the recommended sampling settings.

## Reading a hosted price page

Hosted models are priced per million input and output tokens, with discounts for cached input. A snapshot from 28 October 2026:

<p class="tiny">From the vendors' model and pricing pages, checked 28 Oct 2026. Two of the six rows already have a scheduled price change, which is the point: date every price you quote.</p>

Three traps sit in that table. Output prices include reasoning tokens for all three vendors, so a model with a high default effort can produce several times more billed output than visible text. Tokenizers differ, so a per-token price is not comparable across vendors or even across versions: Anthropic says Claude 4.7 and later produce about 30% more tokens for the same text than earlier models. And the model with the lowest price per token is not the model with the lowest price per correct answer. The unit to compare is cost per successful task.

## Benchmarks versus your task

Public benchmarks tell you which models are worth testing. They do not tell you which one to ship. Two 2025 results make the case. The Leaderboard Illusion paper documented that Meta tested 27 private model variants on Chatbot Arena before the Llama 4 release and that some providers had far more access to Arena data than others, so leaderboard position partly measures how much a provider tuned for the leaderboard.

Your task has its own distribution: your documents, your users' phrasing, your output format, your definition of correct. A 50 to 200 case eval set built from real traffic beats any leaderboard for the decision in front of you. The evals track covers how to build one.

## Advertised context versus effective context

A 1M-token context window means the API will accept 1M tokens. It does not mean the model uses all of them well.

- **Lost in the Middle** found accuracy highest when the relevant passage was at the start or end of the input and lower in the middle, even for long-context models.
- **RULER** tested 17 models that all claimed at least 32K tokens; only half kept satisfactory performance at 32K.
- **NoLiMa** removed the literal word overlap between question and answer. At 32K tokens, 11 of 13 models fell below half their short-context score; GPT-4o went from 99.3% to 69.7%.
- **Context Rot** from Chroma tested 18 models and found performance dropping as input grew even on simple tasks. On LongMemEval, focused prompts of about 300 tokens beat full prompts of about 113,000 tokens.

The engineering reading: retrieval and pruning still matter with a large window. Put the instructions and the most relevant material at the edges, send less rather than more, and measure accuracy at the context lengths you will actually use.

## Routing

The price-latency-quality triangle rarely has one winner, so production systems often route. Send each request to the cheapest model that is likely to handle it, and escalate when a check fails: the output does not parse, a validator rejects it, or a classifier marks the request as hard. The routing logic is ordinary code, and it needs its own eval, because a router that escalates too rarely saves money by quietly losing accuracy.

## A bake-off in 20 lines

The models below are stubs so the harness runs anywhere; swap `call` for your client. The prices are the snapshot above, and the token counts are made up for the illustration.

```python
CASES = [("Where is my refund for order 1042?", "refund"), ("Cancel my plan", "cancel"),
         ("App crashes on login", "bug"), ("Do you ship to Pune?", "other")]
MODELS = {  # name: (USD per 1M input, USD per 1M output, stub answers)
    "big":   (4.00, 20.00, {"refund", "cancel", "bug", "other"}),
    "small": (0.10, 0.50, {"refund", "cancel", "other"}),
}
IN_TOK, OUT_TOK = 400, 60          # illustrative tokens per call

def call(name, text, label):
    knows = MODELS[name][2]
    return label if label in knows else "other"

for name, (p_in, p_out, _) in MODELS.items():
    correct = sum(call(name, q, gold) == gold for q, gold in CASES)
    cost = len(CASES) * (IN_TOK * p_in + OUT_TOK * p_out) / 1e6
    per_success = cost / correct if correct else float("inf")
    print(f"{name}: {correct}/{len(CASES)} correct, ${cost:.6f}, ${per_success:.6f} per success")
# big: 4/4 correct, $0.011200, $0.002800 per success
# small: 3/4 correct, $0.000280, $0.000093 per success
```

The real version adds latency percentiles, several runs per case, and a breakdown of which cases each model fails. The decision is then a product question you can actually answer: is the small model's failure on "bug" tickets acceptable at a 40th of the cost, or does that category get routed to the large one?

<p>Measure. Same eval set, several runs per case because outputs vary, scored on the properties we care about. ## When this is wrong

Every specific in this lesson has a shelf life. Two of the six hosted prices already have announced changes, and model generations turn over within a year. Treat the tables as a dated example of what to read, and re-check the vendor pages before any decision.

The bake-off also has limits. A small eval set has wide error bars: with 50 cases, one case is 2 percentage points. Differences of a few points between two models may be noise; run more cases or more repeats before you call a winner.
