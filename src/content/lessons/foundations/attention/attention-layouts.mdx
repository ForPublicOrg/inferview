## The decision this lesson drives

At long context the KV cache, not the weights, decides how many sequences a GPU decodes together, and the cache's size per token is fixed by the attention layout the model was trained with. Choosing a layout, or an open model because of its layout, is like choosing a storage format for the hottest table you own: it is decided at schema time and cannot be changed by a flag at serving time. The difference from a storage format is that changing it means training, and that each layout's saving comes with a quality claim you have to check on your own task.

The four layouts in current open models fit one formula, applied per layer and summed:

- **Multi-head or grouped-query attention (MHA, GQA)**: 2 × KV heads × head_dim × bytes per token per layer. GQA lowers the KV head count below the query head count; multi-query attention lowers it to one.
- **Multi-head latent attention (MLA)**: (latent width + rotary key width) × bytes per token per layer. Keys and values are reconstructed from one cached latent.
- **Sliding-window layers**: the same per-token cost as GQA, but the layer stops growing at the window w.
- **Hybrids**: a stack that mixes the above, and in some models layers with no growing cache at all.

## The numbers from four configs

Each figure below is computed from the published config, in bf16, for one sequence of 131,072 tokens.

**Llama 3.1 70B, GQA.** 80 layers, 64 query heads, 8 KV heads, head_dim 8,192 / 64 = 128. Per token: 2 × 80 × 8 × 128 × 2 = 327,680 bytes. Per sequence: 40 GiB. With one KV head per query head the same model would need 8 times as much, 320 GiB, which is the gap GQA closed. The GQA paper reports quality close to multi-head attention at speed close to multi-query, and that an existing multi-head checkpoint can be uptrained to it with 5% of the original pre-training compute.

**DeepSeek-V3, MLA.** 61 layers, kv_lora_rank 512, qk_rope_head_dim 64. Per token: 61 × (512 + 64) × 2 = 70,272 bytes. Per sequence: 8.58 GiB. The comparison inside the model is starker: its 128 heads with 192-wide keys (128 + 64) and 128-wide values would cache 128 × 320 = 40,960 values per layer per token under plain multi-head attention, against 576, about 71 times less. The DeepSeek-V2 paper, which introduced MLA, reports a 93.3% smaller KV cache and 5.76 times the maximum generation throughput of DeepSeek 67B; those are the authors' own measurements against their own earlier dense model.

**Gemma 3 27B, local and global.** 62 layers with sliding_window_pattern 6: every sixth layer is global, so 10 global and 52 local with a 1,024-token window. Each layer caches 2 × 16 × 128 × 2 = 8,192 bytes per token. Global layers: 10 × 8,192 × 131,072 = 10 GiB. Local layers: 52 × 8,192 × 1,024 = 416 MiB, the same at any context above 1,024.

## What changed in the last two years and why

Llama 3.1 (2024) reached 128K with GQA in every layer and no change to the layout: its config stretches 8,192 original positions by a factor of 8 to 131,072 with RoPE scaling, plus long-context training. Several open models since have changed the layout instead. DeepSeek moved to MLA with V2 in 2024 and kept it in V3. Gemma 3 (March 2025) raised its local-to-global ratio to 5:1 with a 1,024-token window, raised the global layers' RoPE base to 1M and kept the local layers at 10k. gpt-oss (August 2025) alternates 128-token windows with full layers and adds a learned bias to each head's softmax denominator, so a head can attend to nothing.

The reason is the arithmetic above. At 128K, Llama 3.1 70B needs 40 GiB of cache per sequence against about 130 GiB of bf16 weights (70 billion × 2 bytes), so three long sequences cost about as much memory as the model, and the number of concurrent long sequences per GPU is the cost of the product. Windowing makes most layers' cost constant in context; MLA makes every layer's cost small.

## Quality evidence and its conditions

Each layout's saving is measured; its quality claim is measured on something other than your task.

- GQA's claim is close-to-multi-head quality on the paper's benchmarks after uptraining. It is the most widely deployed of the four, which is evidence of a different kind.
- Gemma 3's ablations in section 5.2 report minimal perplexity impact from changing the local-to-global ratio and from shrinking the window. Perplexity averages over every token's prediction, most of which depend on nearby text; it says little about whether a fact on page 3 is used correctly on page 300. The memory measurement is also on a 2B model at 32K with a 1:3 ratio, not the shipped 5:1.
- MLA's claims are DeepSeek's comparisons with its own previous models.
- gpt-oss's model card describes the layout; the long-context behaviour you need has to be measured.

The test that decides between layouts for a 128K product is a long-context evaluation on your own documents, with the evidence for each question placed at controlled depths in the window. A windowed model that holds up at the first and last quarter and fails in the middle is telling you how much information its global layers carry.

## A function that reads any of the four configs

```python
def kv_bytes(cfg, n_tokens, dtype_bytes=2):
    """KV cache bytes for one sequence of n_tokens, from a Hugging Face style config dict."""
    layers = cfg["num_hidden_layers"]
    if "kv_lora_rank" in cfg:                                   # MLA: one latent plus one shared rotary key
        return layers * (cfg["kv_lora_rank"] + cfg["qk_rope_head_dim"]) * dtype_bytes * n_tokens
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    per_layer_token = 2 * cfg["num_key_value_heads"] * head_dim * dtype_bytes
    types = cfg.get("layer_types")
    if types is None and cfg.get("sliding_window_pattern"):    # Gemma 3: every p-th layer is global
        p = cfg["sliding_window_pattern"]
        types = ["full_attention" if (i + 1) % p == 0 else "sliding_attention" for i in range(layers)]
    types = types or ["full_attention"] * layers
    window = cfg.get("sliding_window") or n_tokens
    return sum(per_layer_token * (n_tokens if t == "full_attention" else min(n_tokens, window)) for t in types)
```

Fed the fields above, it prints 40.00, 8.58, 10.41 and 4.50 GiB at 131,072 tokens. Config conventions differ by model family and by library version, so check each new model's field names before trusting the function with it; Llama 3.1 70B's config has no head_dim field, which is why the code falls back to hidden size over head count.

## The decision procedure for a 128K target

1. **Weights fit first.** DeepSeek-V3's 671 billion parameters in its released FP8 are at least 671 GB, more than a node of eight 80 GB GPUs holds, whatever its cache costs.
2. **Bytes per token for the layers that grow.** Multiply by your token distribution, not the maximum context, to get memory per session.
3. **Whether the engine realises the saving.** A windowed layer saves memory only if the engine allocates it at the window. FlashAttention has supported sliding-window attention since version 2.3 and a paged cache since 2.5; whether your engine combines them per layer is a question for its owners, answered with a measured peak at 128K.
4. **Kernel maturity.** A layout your team has not operated adds a class of incidents during the launch window.
5. **Quality on your task**, at controlled depths, against a full-attention baseline.
6. **Write down what reverses it**: a quality gap at depth beyond an agreed margin, or a measured cache size above the computed one.

## When this is wrong

Bytes per token is a memory figure, not a throughput figure. MLA reconstructs keys and values from the latent, which adds arithmetic per decode step; whether that costs time depends on the kernel. Windowed layers make the cache smaller and the attention kernel more complex. The capacity number is real; the latency number has to be measured.

Tensor parallelism changes the per-GPU figure. A GQA cache splits by KV head across GPUs, which works while there are at least as many KV heads as GPUs; with 8 KV heads and 16-way tensor parallelism, heads are replicated. An MLA latent is shared by all heads, so splitting by head does not split it at all; engines handle it by splitting the batch or the sequence instead.

Linear-attention layers in hybrid models keep a fixed-size state rather than a growing cache. The formula gives them zero growth, which is correct for memory and silent about what such a layer can recall from far back.

Prefix sharing and paging change what a session costs: a shared system prompt is stored once, and pages waste up to one partly filled page per sequence. The per-sequence figures above are the upper bound for unshared sessions.
