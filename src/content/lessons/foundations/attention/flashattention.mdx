## The problem the paper solves

The standard attention kernel is three kernels: a matrix multiply that writes the n × n scores to high-bandwidth memory (HBM), a softmax that reads them and writes the weights, and a second multiply that reads the weights and V. Each intermediate is the full score matrix, so at long sequence lengths the kernel spends its time moving that matrix between HBM and the chip, and its memory footprint grows with n² per head.

<Predict id="score-matrix" question="Standard attention at n = 8,192 tokens, 32 heads, fp16 scores. How many GiB does the score matrix take for one layer of one sequence?" answer={4} tolerance={0.3} unit="GiB">
<p>8,192 × 8,192 × 2 bytes = 128 MiB per head. Times 32 heads = <b>4 GiB</b>, written and read back at least once per layer, for scores that exist only to be normalised and multiplied by V. Training keeps them for the backward pass as well.</p>
</Predict>

Approximate attention methods, sparse or low-rank, attacked the arithmetic. The FlashAttention paper's argument is that arithmetic was not the bottleneck: on GPUs at these sizes, attention is bound by memory traffic, and a kernel that reduces traffic can be exact and faster at once.

## The mechanism in engineering terms

It is a blocked algorithm, like a tiled matrix multiply or an external sort that streams runs through a buffer that fits in fast memory. The fast memory is on-chip SRAM; the slow one is HBM.

**Tiling.** Load a block of queries into SRAM. Stream blocks of keys and values past it. For each key block, compute the block of scores, update each query row's running maximum, running normaliser and unnormalised output with the online softmax rule from the mechanics lesson, and discard the scores. After the last key block, divide by the normaliser and write the output once. The n × n matrix never exists in HBM; the extra memory is the per-row maximum and normaliser, linear in n.

**Recomputation.** The backward pass needs the attention weights. Instead of storing them, the kernel stores the per-row statistics and recomputes each block of scores from Q and K when the backward pass reaches it. That is more arithmetic than reading a stored matrix, and less time, because reading the matrix from HBM was the expensive part.

**IO accounting.** The paper's analysis counts HBM accesses rather than FLOPs and shows that the tiled kernel needs fewer of them than the standard one for realistic head dimensions and SRAM sizes. That change of unit is the paper's lasting contribution: an attention kernel is judged by bytes moved per useful FLOP.

The result is exact attention: the same function, computed with a different summation order, so outputs match the standard kernel to rounding, not bitwise.

## The numbers, with their conditions

The first paper's headline results are training speedups on its own benchmarks: 15% end to end on BERT-large at sequence length 512 against the MLPerf 1.1 training record, 3 times on GPT-2 at 1K, and 2.4 times on Long-Range Arena at 1K to 4K. Its capability result matters more for this module: because memory became linear, it trained the first transformers to reach better-than-chance accuracy on Path-X at 16K (61.4%) and Path-256 at 64K (63.1%).

FlashAttention-2 kept the algorithm and rearranged the work. The paper reports the first version at 25 to 40% of the A100's theoretical peak FLOPs/s and the second at 50 to 73%, about twice as fast, by cutting non-matmul operations, parallelising a single head across thread blocks along the sequence, and splitting work between warps to reduce shared-memory traffic. Training GPT-style models end to end it reports 225 TFLOPs/s per A100, 72% model FLOPs utilisation.

FlashAttention-3 targets H100, where the paper reports FlashAttention-2 reaching only 35% utilisation. It uses the asynchrony of Hopper's tensor cores and memory-copy engine through warp specialisation, overlaps the softmax of one block with the matrix multiply of the next, and adds FP8 with block quantisation and incoherent processing. Reported: 1.5 to 2.0 times faster, FP16 up to 740 TFLOPs/s (75% utilisation), FP8 close to 1.2 PFLOPs/s, and 2.6 times lower numerical error than a baseline FP8 attention. Each figure is the authors' measurement on their kernels and GPUs.

## What changed in practice

Attention cost became an IO question. Before, long-context cost discussions started from O(n²) memory and treated attention as the reason long sequences were infeasible; after, the score matrix dropped out of the memory plan and the questions became how close a kernel runs to peak and how much KV cache a GPU holds. The quadratic arithmetic did not go away: a 64K-token prefill still does 4 times the attention work of a 32K one.

The library became the place where serving semantics are decided. The README records the changes engineers depend on: from version 2.1 the causal mask is aligned bottom-right when query and key lengths differ, the alignment chunked prefill and speculative verification need; 2.2 added an inference entry point that updates a KV cache in place; 2.3 added sliding-window attention; 2.5 added a paged KV cache. A pinned version is a pinned set of semantics.

Decode needed its own answer. FlashAttention parallelises over batch, heads and query blocks; a decode step has one query per sequence, so at small batch and long context most of the GPU sits idle. Flash-Decoding splits the cache along the sequence, computes partial states in parallel and merges them with the same log-sum-exp rescaling. Its authors report up to 8 times faster generation for very long sequences on CodeLlama 34B, and the attention itself up to 50 times faster than FlashAttention at batch size 1 on A100.

## When this is wrong

"Exact" means the same mathematical function. Summation order differs from the standard kernel and between FlashAttention versions, and FP8 variants change precision, so "exact" never means bitwise reproducible across kernels.

The speedups are attention-kernel or training-run figures on the authors' hardware. At short sequence lengths attention is a small share of a step, and the end-to-end gain shrinks with it.

The memory saving is in the scores, not in the KV cache. A decode server's long-context memory problem is unchanged by FlashAttention; it is solved, or not, by the attention layout and the cache's precision and paging.
