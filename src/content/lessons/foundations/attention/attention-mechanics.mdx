## The operation, stated once

Attention is softmax(QKᵀ / √d_k) V, a weighted gather over values whose weights come from query-key dot products. The √d_k is there because, for independent unit-variance components, q·k has variance d_k, and unscaled scores at realistic head sizes push the softmax towards one-hot. That is the whole of the definition this module needs.

Two costs follow from it. Prefill computes all n queries against all n keys, so the score work is O(n² d) per layer, the figure in Table 1 of the 2017 paper. Decode computes one new query against n cached keys, so once keys and values are kept, each generated token costs O(n d) attention work and the cache costs memory proportional to n. Every serving decision in this module is a choice about one of those two terms.

The widget runs the arithmetic on four tokens with 2-dimensional vectors. Pick "sat" as the query: the raw dot products against The, cat and sat are 0.26, 1.12 and 0.90, the scaled weights are 0.227, 0.417 and 0.357, and "down" gets exactly 0 because the mask set its score to minus infinity before the softmax.

The rest of this lesson is about the two places where serving code departs from that picture: the mask when the queries are not the whole sequence, and the normaliser when the scores are not all in memory at once.

## The causal mask at training versus inference

In training and in a single-pass prefill, query i may read keys 0 to i. The mask is the lower triangle of a square, and it is what lets one forward pass produce n next-token losses without any position reading its own future. Nothing about it is subtle while the query count equals the key count.

Serving breaks that equality in three common paths.

- **Decode with a cache.** One query, n keys. The query is the newest position, every cached key is in its past, and no mask is needed for causality. A mask is still needed for padding when rows of different lengths share a batch, and the positions fed to the rotary embedding must count real tokens, not padded columns; that is the bug in fnd-029.
- **Chunked prefill.** A 100,000-token prompt is processed in chunks, so a chunk of c queries attends over all keys written so far plus its own. The queries are the last c positions of a longer sequence.
- **Speculative verification.** The target model scores k drafted tokens in one call against a cache of n tokens. Again the queries are the last k positions.

For the last two, the mask must be aligned to the bottom-right corner of the c × (n + c) score matrix: query i reads key j when j ≤ i + (n_k − n_q). Aligned to the top-left instead, query 0 of the chunk reads only key 0, and the outputs are wrong without any error being raised. This is a version-sensitive fact: the FlashAttention README states that from version 2.1, with unequal query and key lengths and causal=True, the mask is aligned bottom-right, where earlier versions aligned it top-left. A serving stack that pinned an older version, or a hand-written reference kernel used in tests, can disagree with production on exactly these paths.

The property that makes chunking and verification correct is simple to test and worth testing in CI: running only the last c queries against all keys must give the same rows as the full square computation. Step 2 of the lab tests it.

## The online softmax normaliser

The textbook stable softmax reads a row three times: once for the maximum, once for the sum of exponentials, once to normalise. Milakov and Gimelshein showed that the first two passes fold into one. Keep a running maximum m and a running denominator l. For each new score s:

m' = max(m, s), l' = l × exp(m − m') + exp(s − m')

When the maximum rises, every term already in l was computed relative to the old maximum, so l is rescaled by exp(m − m') and the result is exact. The paper reports the softmax alone up to 1.3 times faster and, fused with top-k, up to 5 times, part of which it attributes to the fusion.

Attention adds one more running quantity, the unnormalised output acc, rescaled the same way: acc' = acc × exp(m − m') + exp(s − m') × v. The output is acc / l at the end. That triple (m, l, acc) is the state FlashAttention carries for each query row while key and value tiles stream past, and it is why the n × n score matrix never has to exist in high-bandwidth memory.

The same rule merges two finished states. Given (m_a, l_a, acc_a) over one set of keys and (m_b, l_b, acc_b) over a disjoint set, rescale both to m = max(m_a, m_b) and add. Flash-Decoding uses exactly this for long-context decode: it splits the cache into chunks, computes a partial state per chunk in parallel, keeps one log-sum-exp per split and combines them in a final reduction, so a single long row can occupy the whole GPU.

## A decode step that equals the recompute

Decode output at step t must equal row t of a full causal recompute, because row t reads keys 0 to t only and a key depends only on its own position's input. The code below computes both: a full recompute with the three-pass softmax, and a decode loop that appends to a cache and uses the one-pass normaliser.

```python
import math, random

def full(Q, K, V):
    out = []
    for t, q in enumerate(Q):
        s = [sum(a * b for a, b in zip(q, K[j])) / math.sqrt(len(q)) for j in range(t + 1)]
        m = max(s)
        w = [math.exp(x - m) for x in s]
        z = sum(w)
        out.append([sum(w[j] * V[j][c] for j in range(t + 1)) / z for c in range(len(V[0]))])
    return out

def decode(Q, K, V):
    keys, values, out = [], [], []
    for q, k, v in zip(Q, K, V):
        keys.append(k)
        values.append(v)
        m, l, acc = float("-inf"), 0.0, [0.0] * len(v)
        for kj, vj in zip(keys, values):
            s = sum(a * b for a, b in zip(q, kj)) / math.sqrt(len(q))
            m_new = max(m, s)
            c = math.exp(m - m_new)
            p = math.exp(s - m_new)
            l = l * c + p
            acc = [x * c + p * y for x, y in zip(acc, vj)]
            m = m_new
        out.append([x / l for x in acc])
    return out

rng = random.Random(0)
T, d = 200, 16
Q, K, V = ([[rng.gauss(0, 3) for _ in range(d)] for _ in range(T)] for _ in range(3))
diff = max(abs(a - b) for r1, r2 in zip(full(Q, K, V), decode(Q, K, V)) for a, b in zip(r1, r2))
print(f"max abs difference over {T} steps: {diff:.1e}")   # 1.2e-14 with Python 3.12 floats
```

The two agree to 1.2e-14, not exactly. The arithmetic is the same in exact terms and the order of operations is not: one path divides once at the end, the other rescales as it goes. Production kernels differ in the same way and more, because a prefill kernel and a split-sequence decode kernel reduce in different orders, and the order can depend on batch size. Tests that compare decode with recompute need a tolerance chosen for the dtype, and a bitwise comparison belongs only in a mode that fixes the reduction order.

## Where the per-token cost goes

The quadratic term is real and it is not the whole layer. For one token at context n in Llama 3.1 8B, per layer: the four attention projections cost 2 × (2 × 4,096 × 4,096 + 2 × 4,096 × 1,024) = 83,886,080 floating-point operations, because the key and value projections are 1,024 wide with 8 key-value heads of 128. The gated MLP costs 2 × 3 × 4,096 × 14,336 = 352,321,536. The score and weighted-sum products cost 2 × 2 × 4,096 × n = 16,384n.

That count is arithmetic, not time. Decode at short context is limited by reading the weights from memory, and at long context by reading the cache, so measured step time follows bytes moved more closely than FLOPs. Measure at your real prompt lengths before quoting a scaling law to anyone.

## When this is wrong

The normaliser above starts from l = 0. gpt-oss gives each head a learned bias in the softmax denominator, so a head can put weight on no token at all; its state starts from that bias instead, and a kernel or reference that drops it computes a different function while every shape still matches.

Linear-attention layers, used in several hybrid models, have no softmax over the history and no growing cache; they keep a fixed-size state. Nothing in this lesson about masks, normalisers or quadratic cost applies to those layers, and a model that mixes them with full attention needs the analysis per layer type.

"Decode equals recompute" is a statement about exact arithmetic on one sequence. With a sliding window, both paths must apply the same window, or the test compares two wrong answers that agree. With batch-dependent kernels, the same prompt can produce different outputs depending on what else is in the batch, which no single-sequence equality test will catch.

The FLOP crossover ignores memory traffic and assumes the published Llama 3.1 8B shapes. For a model with a different MLP width or head layout, recompute it from the config.
