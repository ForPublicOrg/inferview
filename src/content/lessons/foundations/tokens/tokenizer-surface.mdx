## The unit is chosen by the vendor

Every term of an LLM bill is denominated in the tokens of one tokenizer: input, cache writes, cache reads, output. So are the rate limits and the context window. A model change that ships a new tokenizer therefore changes the unit of all three while the price list stays the same, which is the situation Anthropic documents for Claude 4.7 and later: a newer tokenizer that produces approximately 30% more tokens for the same text, with per-token prices for Opus 4.6 and Opus 4.7 identical. The decision this lesson teaches is how to price that change before migrating, and when prompt caching or per-language pricing absorbs it.

The analogy is a metered resource whose meter changes granularity, like a storage bill moving to a larger block size. The difference is that the multiplier is not a constant. It depends on the script, the ratio of code to prose, digits and whitespace, and the vendor says so explicitly.

## Three places the multiplier lands

Write the cost of one request as prefix tokens P (system prompt, tools, examples), dynamic input D and output O, with prices p_in, p_out, p_write and p_hit. A tokenizer change multiplies each count by its own factor. For a first estimate use one factor r, then replace it with per-term measurements.

**The bill.** Without caching, cost scales by r. With caching, a hit is billed at p_hit and a miss becomes a write at p_write, which on Anthropic's list is 1.25 times the uncached input price. Solving for the prefix hit rate h at which the new bill equals the old one:

```python
def break_even_hit_rate(P, D, O, r, p_in, p_out, p_write, p_hit):
    """Hit rate on a cached prefix at which cost after a token multiplier r equals the uncached cost before it."""
    old = (P + D) * p_in + O * p_out
    left_for_prefix = old - r * D * p_in - r * O * p_out
    return (p_write - left_for_prefix / (r * P)) / (p_write - p_hit)

# 6,000-token prefix, 1,500 dynamic, 400 output, r = 1.3, Opus 4.7 list prices per token
print(round(break_even_hit_rate(6000, 1500, 400, 1.3, 5e-6, 25e-6, 6.25e-6, 0.5e-6), 3))  # 0.535
```

With r = 1.0 the same function returns 0.217: caching has to earn back its own write premium before it offsets anything. That is the number to have in hand before proposing caching as the answer to a tokenizer change.

**The rate limit.** Anthropic counts only uncached input and cache writes toward input tokens per minute for most models; cache reads do not count. A migration without caching raises ITPM pressure by r. A migration with caching can lower it, because the prefix moves out of the limit on every hit.

**The context window.** Capacity in characters shrinks by 1 / r. Anything that packs a window by a token budget measured on the old tokenizer, a retriever's chunk count or a conversation-history trimmer, silently overflows or truncates after the switch.

## Where the multiplier comes from

Two layers produce a token count: a pre-tokenizer regex that cuts text into chunks, and BPE merges that run inside each chunk and never across a boundary. Either layer can change between encodings, and the language skew comes from both.

<TokenStrip preset="hindi" />

The Hindi preset shows both layers at once. cl100k_base matches letters with `\p{L}` only, so every Devanagari vowel sign, a combining mark in `\p{M}`, ends the chunk: the first word `तेज़` becomes three chunks before any merge runs. o200k_base added `\p{M}` to its letter classes and has more Devanagari merges; the same sentence drops from 71 tokens to 28 with no change to the text. The pre-tokenizer also changed contractions: cl100k splits `they're` into `they` and `'re`, while o200k keeps the contraction in the same chunk as the word.

Petrov et al. measured the skew across languages and report differences up to 15 times for the same text, and over 4 times for some language pairs even with character- and byte-level models, which have no learned vocabulary to blame. Llama 3 took the other route to the same problem: it kept 100K tokens from tiktoken and added 28K for non-English languages, and the paper reports English compression rising from 3.17 to 3.94 characters per token against the Llama 2 tokenizer.

## The procedure

Price a tokenizer change in four measurements, each on your own traffic. First, count a stratified sample of real requests under both model IDs with the vendor's token-counting endpoint or published tokenizer, split by prefix, dynamic input and output, and by language and content type. Second, recompute the bill per term with the measured factors; output deserves its own factor, because the new model's verbosity changes too and the two effects are confounded. Third, recompute peak ITPM and OTPM against the limit, remembering that some vendors share one limit across a model family, so a canary on the new model draws from production's bucket. Fourth, recompute every token budget in code: retrieval packing, history trimming, max_tokens.

Then decide which absorber fits. Caching absorbs a multiplier on the prefix when traffic per prefix is dense enough to keep the hit rate above break-even in every hour, not on average. Per-language or per-character pricing absorbs a skew that is stable and large, at the cost of exposing a vendor's internal choice in your price list. Neither absorbs a multiplier on output.

## When this is wrong

The single factor r is a planning device. Vendors describe the increase as dependent on content, and a factor measured on prose says little about JSON, code, base64 or a script the new tokenizer handles differently. Measure per segment or the estimate inherits the error of the average.

Token count is also not the only thing a model change moves. Output length depends on the model's behaviour as much as its tokenizer, so a migration can change output tokens by more or less than the input multiplier; measure output tokens per completed task, not per request.

For closed models the tokenizer is not published, so the regex and merge explanations in this lesson describe the open encodings only. The vendor's counting endpoint is the only ground truth, and it may differ from what a local approximation predicts. Finally, the cache arithmetic assumes the vendor's discount and write premium as listed on the date checked; both are pricing decisions that can change independently of the tokenizer.
