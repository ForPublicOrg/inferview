## Two loops, two cost models

BPE has two algorithms that share one artefact. Training is a greedy loop: count every adjacent pair in the corpus, merge the most frequent into a new symbol, record it, repeat until the vocabulary reaches its target. Encoding never repeats that search. It looks up each adjacent pair of the input in a table from pair to rank, merges the lowest-ranked pair present, and repeats until no adjacent pair has a rank. tiktoken ships an encoding as exactly that table, token bytes to rank; o200k_base has 199,998 entries.

The costs follow. A naive trainer rescans the corpus for every merge, so its cost is merges times corpus size, which is why production trainers keep pair counts incrementally, touching only the words that contain the pair just merged, and pick the next merge from a priority queue. The encoder's cost depends on the length of each pre-tokenised chunk and not on the size of the table, which is what lets a 200,000-entry vocabulary encode at request time. An encoder that replays the merge list in order gives the same output on ordinary tables and costs one pass per merge per word: correct in a notebook, unusable in a gateway.

The failure modes differ as well. Training failures are silent and permanent: a tie-break that depends on dictionary order produces a different vocabulary from the same counts, and every token id after the first divergence shifts, invalidating embeddings and anything keyed by id. Encoding failures are visible and per request: a chunk boundary in the wrong place, a special-token string parsed as control, a multi-byte character split across a streaming boundary.

## The training loop on the paper's toy corpus

The stepper runs the training loop on the dictionary from Sennrich et al.: low 5, lower 2, newest 6, widest 3, with an end-of-word marker shown as a dot. The first merges are `e+s`, `es+t` and `est+·`, because the pairs inside "est" occur 9 times (6 from newest plus 3 from widest) and nothing else reaches 9. Note that `e+s` and `s+t` tie at 9 on the first step; the result depends on the tie-break, and a production trainer has to make that choice explicit.

Each merge makes the corpus shorter and the vocabulary larger by one. The stopping point is a resource decision, covered below.

## Encoding by rank, and predicting a split

```python
def encode_chunk(symbols, ranks):
    """symbols: list of base symbols for one pre-tokenised chunk; ranks: pair -> merge position."""
    symbols = list(symbols)
    while len(symbols) > 1:
        candidates = [(ranks[p], i) for i, p in enumerate(zip(symbols, symbols[1:])) if p in ranks]
        if not candidates:
            break
        _, i = min(candidates)
        symbols[i:i + 2] = [symbols[i] + symbols[i + 1]]
    return symbols
```

That loop is quadratic in the chunk length and independent of the table, and it is the specification: when a merged symbol can be built by two paths (a table that learned `a+bc` and later `ab+c`), rank order and replay order can disagree, and tiktoken's behaviour is rank order.

To predict how an unseen word splits, apply the two layers in order. First the regex decides the chunks; then, inside each chunk, the earliest-learned merges win. On the toy corpus, "lowest" never appears in training but encodes as `low` and `est·`, because both pieces were learned. In cl100k_base the fox sentence ends with ` re`, `cons`, `iders`: the leading space stays with `re` because the pattern attaches an optional space to a letter run, and ` re` is an early merge.

## Bytes underneath: byte-level and byte fallback

The tiktoken encodings start from the 256 byte values, so nothing is out of vocabulary and the only cost of unfamiliar text is length. Llama 3 inherits that base by reusing 100K tiktoken tokens. SentencePiece tokenizers start from characters and fall back to bytes for characters outside the vocabulary; the Gemma 3 report describes its tokenizer as SentencePiece with byte-level encodings. Either way, a single token can end in the middle of a multi-byte character. Decoding the full id sequence is fine; decoding token by token, which is what a naive streaming client does, emits replacement characters the full text never had. Streaming decoders hold back an incomplete UTF-8 suffix until the next token completes it.

## Pre-splitting decides the visible failures

**Digits.** cl100k_base and o200k_base both match `\p{N}{1,3}`: digit runs are cut into groups of at most three, left to right, before any merge. Measured, `1234567` is `123`, `456`, `7` in both encodings, and `7654321` is `765`, `432`, `1`. Grouping from the left means the last token of a seven-digit number is the units digit alone and the token before it spans thousands to tens, while the last token of a six-digit number spans hundreds to units. Token positions carry no consistent place value across operands of different lengths. Gemma 3 takes the other choice and splits digits individually, which costs more tokens per number and gives every digit its own position.

**Whitespace.** The pattern attaches one leading space to a letter run, so ` strawberry` with its space is a single token in both encodings, while `strawberry` alone is three: `str`, `aw`, `berry` in cl100k_base and `st`, `raw`, `berry` in o200k_base. A model asked to count letters sees one id for the common form and must answer from what it learned about that id's spelling. Tokenization is one cause of letter-counting failures, not the whole explanation, but it is the one you can show from the encoder's output.

## Vocabulary size against embedding and softmax cost

A larger vocabulary compresses text into fewer tokens, so each document costs fewer forward passes. Each entry also adds a row to the input embedding and a column to the output projection, and the output projection runs for every generated token.

The other side of the ledger is compression. Meta reports that moving from the Llama 2 tokenizer to Llama 3's 128K vocabulary raised English compression from 3.17 to 3.94 characters per token. The same English text then needs 3.17 / 3.94 = 0.80 times the tokens, about 20% fewer forward passes through every layer, which is why a 128K vocabulary pays for its larger embedding at 8B parameters. At much smaller model sizes the embedding share grows and the trade can reverse. Rare tokens are a separate cost: an entry's embedding is trained only on that token's occurrences, so a vocabulary grown to cover rare strings carries rows that saw few updates.

## When this is wrong

This lesson's model is byte-level BPE behind a regex pre-tokenizer, the tiktoken family. SentencePiece tokenizers preserve whitespace as part of the text and have no regex step, so the leading-space and digit examples behave differently there; the Gemma 3 report's split digits are a choice made inside that model, not a property of BPE.

The rank-order encoder equals replay only when every merged symbol has one construction path. Tables trained with unusual tie-breaks, or edited by hand to add tokens, can break that, and then the two encoders disagree on a small set of strings. If two systems must agree on ids, they must share the encoder, not just the table.

The vocabulary arithmetic assumes untied embeddings and a dense output projection. Tied embeddings halve the parameter cost; serving tricks that sample from a restricted vocabulary change the per-token compute. And compression gains measured on one corpus do not transfer: Meta's 3.17 to 3.94 is for a sample of English data, and your traffic may be code, tables or another script.
