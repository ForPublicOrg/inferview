## A leaderboard makes a shortlist, not a decision

Public rankings answer "which models are worth an afternoon of testing". They do not answer "which model ships on this route", for two reasons that have both moved rankings in public.

Contamination. In February 2026 OpenAI stopped reporting SWE-bench Verified, saying the benchmark had become contaminated (models could reproduce problem statements and the reference fixes) and that some of its tests reject functionally correct solutions; it recommends SWE-bench Pro until it has uncontaminated replacements. A benchmark that was a fair signal in 2024 measured partly training exposure by 2026, and nothing in a leaderboard row tells you when that crossover happened.

Task mismatch. BRIGHT built 1,384 retrieval queries that need reasoning to match a document, and the paper reports that the embedding model leading MTEB at 59.0 nDCG@10 scores 18.3 on BRIGHT. Same model, same metric, a different notion of relevance. HELMET found the long-context version of the same effect: needle-in-a-haystack scores do not reliably predict downstream long-context performance. Your task has its own distribution of inputs, its own output contract and its own definition of correct, and only your traffic samples it.

## Build the set from traffic, and record its clusters

The eval set comes from production logs or, before launch, from the closest proxy you have (support tickets, a pilot, the documents the product will see). Three properties matter more than size.

Stratified by route. If 10% of traffic is long documents and that is where models differ, a uniform sample of 300 gives about 30 long documents, too few to see a difference there. Sample each route to the size its decision needs and weight back to traffic when you report the blended number.

Graded by the contract. Score what the route needs: the extracted fields match, the JSON validates, the cited clause exists. Where a human or a model judge grades, the grader's own error becomes part of the noise and belongs in the report.

Clustered honestly. Questions that share a document, a conversation or a customer are not independent: when a model misreads a contract, it tends to miss every question about that contract. Anthropic's statistics post recommends clustering standard errors on the unit that was sampled and reports that clustered errors can be over three times as large as naive ones on popular evals. A bake-off of 400 questions over 100 contracts has far fewer than 400 independent observations.

## Pair the comparison

Both models answer the same questions, so the comparison is on per-question differences, not on two independent accuracies. Pairing removes the variance that comes from question difficulty, which both models share. For per-question scores with variances σ²_A and σ²_B and correlation ρ, the variance of the mean difference over n questions is (σ²_A + σ²_B − 2ρσ_Aσ_B) / n instead of (σ²_A + σ²_B) / n. Anthropic reports per-question correlations between frontier models of 0.3 to 0.7, so the reduction is real for any pair of capable models.

At ρ = 0.7 the variance of the difference is about 30% of the unpaired variance, which is the same precision as roughly three times as many questions analysed unpaired. That is the cheapest precision a bake-off can buy.

Two more variance terms are worth handling. Sampling noise inside a question: if the model thinks before answering or runs at non-zero temperature, the same question can pass on one run and fail on the next. The post's recommendation is to sample each question several times and score its mean, which shrinks this term before any between-question analysis. And the cluster term above, which pairing does not remove when one model fails whole documents that the other handles.

The cluster-robust version of the paired analysis is twenty lines with the standard library. The data below is synthetic: model B is better on some documents and worse on others, as a whole document at a time.

```python
import math, random
from collections import defaultdict

def paired_report(rows):
    """rows: (cluster_id, score_a, score_b) per question, scores in [0, 1]."""
    n = len(rows)
    d = [b - a for _, a, b in rows]
    mean = sum(d) / n
    naive_se = math.sqrt(sum((x - mean) ** 2 for x in d) / (n - 1) / n)
    by_cluster = defaultdict(float)          # sum residuals within each cluster
    for (c, _, _), x in zip(rows, d):
        by_cluster[c] += x - mean
    g = len(by_cluster)
    clustered_se = math.sqrt(g / (g - 1) * sum(s * s for s in by_cluster.values())) / n
    return mean, naive_se, clustered_se

random.seed(37)
rows = []
for doc in range(100):                       # 100 documents, 4 questions each
    p_a = random.choice((0.55, 0.90))        # document difficulty for model A
    p_b = min(1.0, max(0.0, p_a + random.choice((-0.3, 0.0, 0.0, 0.3))))  # B wins or loses whole documents
    for q in range(4):
        a = int(random.random() < p_a)
        b = int(random.random() < p_b)
        rows.append((doc, a, b))

mean, naive, clustered = paired_report(rows)
print(f"B - A = {mean:+.3f}, naive SE {naive:.3f}, clustered SE {clustered:.3f}")
# B - A = -0.058, naive SE 0.029, clustered SE 0.034
```

The naive analysis puts the difference at 2.0 standard errors and calls model B worse. Clustered by document, it is 1.7 standard errors, and the honest reading is "B may be worse; we have 100 documents, not 400 questions, of evidence". The decision that follows is to sample more documents, not more questions per document.

## Report cost per successful task next to accuracy

Price per token is an input. The output that decides a route is cost per successful task: everything spent on attempts (input, output including thinking tokens, retries) divided by the tasks that succeeded. On the Claude price list, checked 28 October 2026, Sonnet 5.5 is $2 / $10 per million input and output tokens and Haiku 5.5 is $0.10 / $0.50 for prompts up to 100,000 tokens.

Scenario, measured in a bake-off on 1,500-token prompts: Sonnet 5.5 succeeds on 92% with 400 output tokens per attempt including thinking; Haiku 5.5 succeeds on 85% with 250. Per attempt, Sonnet costs (1,500 × 2 + 400 × 10) / 10⁶ = $0.0070 and Haiku (1,500 × 0.10 + 250 × 0.50) / 10⁶ = $0.000275. Per success: $0.0070 / 0.92 = $0.0076 and $0.000275 / 0.85 = $0.00032, a factor of about 24.

That factor is not the decision either, because the 8% and 15% that fail go somewhere: a retry, an escalation to a larger model, a human queue, or a wrong answer a customer sees. The report states what happens to a failure and what it costs, and the comparison is total cost per task including failure handling. When failure handling costs cents, the small model wins on almost any accuracy gap; when it costs a support agent's time, a few points of accuracy can pay for a model ten times the price. Problem fnd-035 works that crossover with retry data.

Count tokens on each model's own tokenizer and report output tokens measured, not assumed: thinking is billed as output, and its length varies by model, effort setting and input.

## What the report contains

A bake-off report that survives review fits on one page:

| Item | Why the reviewer asks |
|---|---|
| Set provenance: traffic window, routes, sample sizes per route, clusters | rules out a set built to flatter one model |
| Grader and its measured agreement with humans | separates model error from grader error |
| Per-route score with clustered 95% interval, both models | shows where the models differ, not only whether |
| Paired difference with clustered SE and the per-question correlation | the actual test of the decision |
| Cost per successful task and per task including failure handling | turns accuracy into money |
| p50 and p95 latency on the production client path | catches thinking-length and queueing differences |
| Ten failures from each model, read by a person | catches a grader that rewards the wrong thing |

## When this is wrong

A set built from current traffic tests the product you have. For a new product or a route whose inputs will shift (a new market, a new document type), the set is a guess, and a bake-off on it can be confidently wrong; mix in synthetic cases for the expected shift and say which numbers come from them.

Model-judged scoring leaks preference. A judge from the same family as one candidate can favour that candidate's style, which shows up as a gain with no corresponding gain in human-graded samples. Measure judge agreement on both candidates' outputs separately.

Mean accuracy can hide the decision. For a route where one class of error is unacceptable (a wrong refund, a leaked record), the comparison is the rate of that error with its interval, and a model that wins on the mean can lose on the tail.
