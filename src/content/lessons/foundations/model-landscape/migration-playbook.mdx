## The decision

A vendor ships a new version and puts a retirement date on the one you run. From that moment there is no option called "do nothing": requests to a retired Claude model fail, and the same is true of an OpenAI model after shutdown. The decision is which routes move to which model, on what evidence, by which date, and who signs off on the routes that move degraded.

The notice is shorter than a quarter's planning cycle more often than teams expect. Anthropic commits to at least 60 days' notice before retirement for publicly released models. Its most recent case: `claude-sonnet-4-5-20250929` was deprecated on 30 September 2026 and retires on 30 November 2026, 61 days later, with `claude-sonnet-5-5` as the recommended replacement. OpenAI's policy floor is at least six months for generally available models, three for specialised variants and as little as two weeks for previews, with an exception for safety or compliance; its 14 October 2026 notice for GPT-4o, GPT-4o mini, GPT-4.1 and GPT-4.1 mini sets shutdown on 14 January 2027, 92 days later. Plan from the date in the vendor's table, not from the policy.

The dates also depend on where you call the model. Anthropic's dates apply to the platforms it operates; Amazon Bedrock and Google-managed Claude set their own schedules, so the same model can retire on different days on different clouds. The first input to the decision is therefore an inventory: which keys and services call which model IDs on which platforms. Anthropic's Console exports usage by API key and model, which is usually faster than grepping configuration.

## The inputs that change it

Regressions per prompt, not per model. A new version is better on average and worse on some prompts, and the aggregate hides which. Applied LLMs reports Voiceflow's 10% drop on intent classification moving between two gpt-3.5-turbo snapshots, a same-family version change caught only because they had evals. Run the current eval suite per prompt or per route on both versions and list the ones that regress beyond the tolerance each route has.

Cost and latency change, measured. Price per token changes, and so does the token count. Claude 4.7 and later use a tokenizer that produces approximately 30% more tokens for the same text, and Sonnet 5.5 thinks adaptively at a default effort of high, so output length moves too.

Behaviour changes that are not quality scores. Refusal rate, verbosity, format adherence, tool-call patterns and tone change across versions and break downstream parsers or user expectations without moving an accuracy number. Run behaviour evals (schema validity, length distribution, refusal rate on a fixed set of borderline prompts) alongside the task evals.

Interface changes. Claude 4.7 and later reject non-default `temperature`, `top_p` and `top_k`, and API version 2026-10-21 removes them with a 400 error on every model. A migration that changes the model ID without changing client code can fail on its first request.

The deadline, as days of engineering. Count the days between today and retirement, subtract the days a staged rollout needs (shadow, canary, full), and the remainder is the time available to fix regressions.

## The options and when each wins

Migrate all routes at once. Wins when the per-route eval shows no regression beyond tolerance anywhere, the interface changes are mechanical, and the cost change is acceptable everywhere. Cost: a single rollout with a single rollback switch, which is also its risk, because one bad route forces rolling back all of them.

Migrate per route. Wins when regressions concentrate in a few routes. Each route moves when its own eval passes; routes that cannot be fixed in time move to a different model (a larger one, or another vendor's) or move degraded with a written sign-off. Cost: several model IDs in production for a while, per-route config and dashboards, and more prompt variants to maintain.

Hold until retirement. Wins only when the replacement regresses on routes that matter and something else will change before the date: the vendor ships a better point release, or the route is being retired. Cost: all the migration work lands in the last weeks, with no slack for a surprise, and the old model is less supported while you wait; Anthropic's docs say deprecated models are likely to be less reliable than active ones. Hold is a decision with a date and an owner, not a default.

Change platform for the same model. Wins only if another platform you already use publishes a later retirement date for the same model and the integration cost is lower than fixing the regressions. Cost: a second integration and its data-handling review, to buy a few weeks.

## Worked decision

Scenario. A support product calls `claude-sonnet-4-5-20250929` on the Claude API across 5 routes and 40 prompts. Today is 28 October 2026, so 33 days remain before the 30 November retirement. A staged rollout (two days of shadow traffic, a 10% canary for three days, then full) takes about a week per batch of routes, which leaves roughly three weeks for regression work.

The per-prompt eval on `claude-sonnet-5-5`: 28 prompts hold or improve, 12 regress beyond their route's tolerance. One afternoon of prompt edits recovers 9 of the 12 (most were format instructions the new model followed more literally). The remaining 3 are all on the contract-summary route, where the new model omits a liability clause the old one included; on that route an omission is the costly error.

The decision: migrate per route. Four routes move in the first batch after the client code drops `temperature` and the shadow run confirms no 400s. The contract-summary route moves to `claude-opus-5-5` ($4 / $20) as a stopgap if its eval passes there, which the route's volume makes affordable, while prompt work on Sonnet 5.5 continues; if Opus also omits the clause, the route ships on Sonnet 5.5 with a post-check that flags summaries missing a liability section for human review, and the product owner signs the degraded-route note with that check named. Holding is rejected because the remaining work does not fit in the last week, and the hold buys nothing: no newer Sonnet point release is announced.

What this gives up: one more model ID in production on one route, at twice Sonnet 5.5's per-token price, until the Sonnet prompt work lands.

## What to measure after deciding

For the first two weeks after each batch switches, watch per route, against the last two weeks on the old model:

| Signal | Why it moves after a migration |
|---|---|
| 4xx error rate by error type | removed parameters and changed limits fail at request time |
| Output tokens per request, p50 and p95 | thinking and verbosity change cost and latency |
| Cost per successful task | price, tokenizer and output length combine here, not in any one of them |
| Schema-valid rate and parser failures | format adherence changes break downstream code silently |
| Refusal rate on the borderline set | a safety-tuning change shows here first |
| Escalations and user corrections per 1,000 sessions | the regression your eval set did not contain |
| The per-prompt eval, re-run daily on sampled traffic | catches drift as traffic differs from the eval set |

Keep the old model reachable behind the same flag until two weeks pass without a rollback trigger, or until its retirement date, whichever comes first, and write the triggers down before the switch: for example, a route's schema-valid rate below its pre-switch floor for a day, or escalations above the pre-switch rate by more than the week-to-week variation you measured.

## When this is wrong

The playbook assumes a per-route eval suite exists before the notice arrives. With 33 or 60 days, there is no time to build one and run a migration; a team without one should spend the first week building the smallest per-route set that covers the costly errors, and accept that everything else is checked in production.

Self-hosted open-weight models have no retirement date, which removes the deadline but not the decision: security fixes, serving-stack upgrades and hardware changes force the same evaluation on your own schedule, and nobody sends the notice.

The cost arithmetic above holds for the same text. Routes whose inputs are mostly images, code or non-English text can see a different token change from the tokenizer, and only counting tokens on real requests with each model's counter settles it.
