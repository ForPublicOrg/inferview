## A card is a list of decisions someone else made for you

Read a model card the way you read a datasheet before a procurement: each line either fits your hardware, your contract and your traffic, or it becomes a risk you test. The output of reading a card is not a preference. It is a short list of things that could disqualify the model, each with the cheapest test that would show it.

Five lines carry most of the consequences: the two parameter counts, the context numbers, the cut-off, the format the weights and prompts must use, and the licence. Hosted models hide some of these lines and add others (tokenizer, accepted parameters, retirement date), so the same reading applies with a different set of columns.

## Parameters: total sets memory, active sets compute

Most large open-weight releases since 2024 are mixture-of-experts. A router sends each token through a few expert feed-forward blocks per layer, so the card states two counts, and they answer different serving questions.

Total parameters set the memory floor, because every expert must be resident even if a given token uses a few of them. Active parameters set the arithmetic per token: a forward pass costs about two FLOPs per active parameter, before attention. From the cards: Llama 4 Scout is 109B total and 17B active with 16 experts, Maverick is 400B total and 17B active with 128 experts, DeepSeek-V3 is 671B total and 37B active, and gpt-oss-120b is 117B total and 5.1B active.

<p>400 × 10⁹ × 2 bytes = <b>800 GB</b>. An 8-GPU host of 80 GB cards holds 640 GB, so the bf16 weights do not fit before a single byte of KV cache. At 1 byte per parameter the weights are 400 GB, which leaves 240 GB of that host for KV cache and activations. Meta's statement that Maverick "fits on a single H100 host" is a statement about some quantized format; the parameter count is what lets you check which one.</p>

<p>Dense: 2 × 671B ≈ 1,342 GFLOPs per token. MoE: 2 × 37B = 74 GFLOPs. The ratio is 671 / 37 ≈ <b>18</b>. The memory bill does not shrink at all: the full 671B must be resident.</p>

The arithmetic fits in a few lines and belongs in the first hour of any evaluation:

```python
CARDS = {  # name: (total params, active params), from the model cards
    "Llama 4 Scout":    (109e9, 17e9),
    "Llama 4 Maverick": (400e9, 17e9),
    "DeepSeek-V3":      (671e9, 37e9),
    "gpt-oss-120b":     (117e9, 5.1e9),
}
HOST_GB = 8 * 80        # one 8-GPU host of 80 GB cards

def card_to_risks(total, active, bytes_per_param):
    weights_gb = total * bytes_per_param / 1e9
    gflops_per_token = 2 * active / 1e9      # forward pass, attention ignored
    return weights_gb, gflops_per_token, weights_gb / HOST_GB

for name, (total, active) in CARDS.items():
    for label, b in (("bf16", 2), ("8-bit", 1)):
        w, f, share = card_to_risks(total, active, b)
        print(f"{name:17} {label:5} weights {w:6.0f} GB  {share:4.0%} of host  {f:5.1f} GFLOPs/token")
# Llama 4 Maverick  bf16  weights    800 GB  125% of host   34.0 GFLOPs/token
# Llama 4 Maverick  8-bit weights    400 GB   62% of host   34.0 GFLOPs/token
# DeepSeek-V3       8-bit weights    671 GB  105% of host   74.0 GFLOPs/token
# gpt-oss-120b      8-bit weights    117 GB   18% of host   10.2 GFLOPs/token
```

Three consequences follow. First, an MoE model's cost advantage is in compute, so it shows up where you are compute-bound (prefill, large batches) and fades where you are bound by reading weights: at large decode batches the tokens in a batch spread across experts, so most experts are read each step anyway. Second, the expert count matters for parallelism: 128 experts across 8 GPUs is 16 per GPU under expert parallelism, and routing skew on your traffic becomes a load-balancing problem you operate. Third, the shipped number format is part of the claim. gpt-oss-120b fits one 80 GB GPU because its MoE weights were post-trained in MXFP4; neither row in the table above is that format, and a serving stack without MXFP4 kernels has to hold the weights in a wider format, at which point the one-GPU claim no longer holds.

## Context: the trained length and the served length

The Llama 4 post states two different numbers for Scout: it was "pre-trained and post-trained with a 256K context length", and inference supports 10M tokens. The second is a capability of the position scheme and the serving code. The first is the longest span the model was optimised on. Anything between them is extrapolation, and the risk list should say "quality between 256K and the lengths we will send is untested".

The vendor's long-context evidence is usually a needle-in-a-haystack chart. HELMET evaluated 59 long-context models across 7 categories up to 128K tokens and reports that synthetic tasks like needle-in-a-haystack do not reliably predict downstream performance; most models score near perfectly on the needle while differing widely on tasks that need the whole context. A needle chart on a card is evidence that the plumbing works at that length, not that your task does.

The attention layout is the other context line that matters for serving. DeepSeek-V3 uses Multi-head Latent Attention, which caches a compressed latent per token instead of full per-head keys and values; that changes KV cache per token, which sets how many concurrent long requests fit next to the weights. When a card names the attention type (grouped-query, latent, sliding-window, hybrid), the KV cache arithmetic from the attention module applies, and once contexts are long it decides concurrency more than the parameter count does.

## Cut-off: two dates, and sometimes none

Anthropic's model pages list two dates per model: a reliable knowledge cut-off, through which knowledge is "most extensive and reliable", and a training data cut-off covering the broader range of data used. For the current 5.x lineup both are June 2026. The distinction matters for code generation: an SDK released after the reliable cut-off gets written in the style of its predecessor, confidently. The serving consequence is that anything newer than the cut-off (your library versions, a changed API, this quarter's policy) must arrive through retrieval, tools or the prompt, and the test is a small set of questions whose answers changed after the cut-off.

The Llama 4 launch post states no cut-off, and the gpt-oss-120b card page does not state one either. An absent line goes on the risk list as "unknown; measure with questions whose answers changed recently", not as "probably recent".

## Format: the line that fails silently

The gpt-oss-120b card says the model "should only be used with the harmony format as it will not work correctly otherwise", and reasoning effort (low, medium, high) is set inside the system prompt. Rendered with a generic chat template, the model still answers, only worse. That is the worst kind of integration failure because nothing raises an error; the test on the risk list is a golden set run through your own serving stack's template and compared with the reference implementation's output on the same inputs.

Hosted models have the same line under a different name. Claude 4.7 and later models reject non-default `temperature`, `top_p` and `top_k`, and API version 2026-10-21 removes those parameters with a 400 error on every model. A client that has set temperature to 0 for years breaks on the upgrade, not at the bake-off, unless the bake-off runs through production client code. The tokenizer is the other hosted line: Anthropic says Claude 4.7 and later produce approximately 30% more tokens for the same text, so a 1M-token window holds about 555k words where it used to hold about 750k, and a per-token price comparison across that boundary is off by the same factor.

## Licence: the line that can end the project

gpt-oss-120b is Apache 2.0. Llama 4 ships under the Llama 4 Community License, and four of its clauses change engineering plans:

- Section 2: if the licensee's products, with affiliates, had more than 700 million monthly active users in the calendar month before the Llama 4 release date (5 April 2025), the licensee must request a licence from Meta and has no rights under the agreement until Meta grants one. The test is fixed at the release date, so later growth does not trigger it and a cohort-sized rollout does not avoid it.
- Distributing a model built with Llama 4 materials or outputs requires "Llama" at the start of the model name and a prominent "Built with Llama" notice.
- The acceptable use policy is incorporated by reference, so a policy change binds you without a new licence version.
- Filing IP litigation against Meta that concerns the materials ends the licence on the date of filing, which is a conversation for legal before adoption rather than after.

None of these clauses is unusual for a large company's legal review. All of them are invisible in a benchmark table, and the 700M clause can rule a model out for exactly the companies with the traffic to justify self-hosting.

## From card to risk list

The reading ends in a table with one row per line that could disqualify the model and the test that would show it. For Maverick on a single 8-GPU host serving 100K-token contract reviews, the list has five rows:

| Card line | Consequence | Test before the bake-off |
|---|---|---|
| 400B total parameters | bf16 does not fit 640 GB; 8-bit leaves 240 GB for KV cache | KV cache at 100K tokens per request against 240 GB, then concurrency |
| 128 experts | expert-parallel load imbalance on skewed traffic | per-GPU utilisation on a replay of real prompts |
| 256K trained, 10M served | 100K is inside the trained length; nothing above 256K is | none at 100K; required before any longer route |
| no stated cut-off | stale answers on recent law or products | 20 questions whose answers changed in 2025 and 2026 |
| Llama 4 licence | 700M clause, naming and attribution duties, AUP by reference | legal sign-off on the clauses, recorded before engineering spend |

A bake-off only runs on models that clear this table.

## When this is wrong

Every number on a card is the vendor's own claim, made under conditions the card may not state. "Fits on a single H100 host" does not say at what precision, batch or context length, and a serving stack can miss it by a margin only measurement shows.

The two-FLOPs-per-parameter rule ignores attention, which grows with context length and dominates prefill at 100K tokens and beyond. For long-context routes, active parameters understate compute and the attention layout decides cost.

Cards are revised after release and licences are versioned. A risk list is dated, and the date belongs in the memo next to each row.
