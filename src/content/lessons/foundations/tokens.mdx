export const bpe = `from collections import Counter

def train_bpe(text, num_merges):
    words = [tuple(w) + ("</w>",) for w in text.split()]
    merges = []
    for _ in range(num_merges):
        pairs = Counter()
        for w in words:
            for a, b in zip(w, w[1:]):
                pairs[(a, b)] += 1
        if not pairs:
            break
        best = max(pairs, key=pairs.get)
        merges.append(best)
        words = [merge(w, best) for w in words]
    return merges

def merge(word, pair):
    out, i = [], 0
    while i < len(word):
        if i < len(word) - 1 and (word[i], word[i+1]) == pair:
            out.append(word[i] + word[i+1]); i += 2
        else:
            out.append(word[i]); i += 1
    return tuple(out)

def encode(word, merges):
    w = tuple(word) + ("</w>",)
    for pair in merges:          # apply in training order
        w = merge(w, pair)
    return list(w)
`;

## The 4x invoice

Scenario, not a real company: a support bot launches in the US and in India on the same day. Same prompts, same model, same number of conversations. The India bill comes in several times higher. Finance asks whether Indian customers write longer messages. They don't. The model is simply *seeing* more.

Models don't read characters and they don't read words. They read **tokens**: chunks of text chosen by a compression algorithm that was trained mostly on English. Cost, context limits and the strange arithmetic failures all fall out of that one decision. The numbers in this lesson are measured, not estimated: an 11-word English sentence is 15 tokens under the cl100k tokenizer that GPT-4 used, and the same sentence in Hindi is 71.

## A tokenizer is a lexer that was trained, not written

You have used a lexer. It takes a character stream and emits symbols: `IDENT`, `NUMBER`, `LPAREN`. The grammar is hand-written. A tokenizer does the same job for a language model with one twist: nobody wrote the grammar. It was *learned* by counting which adjacent chunks of text appear together most often in a training corpus and merging them, over and over, until the vocabulary reaches a target size. The algorithm is byte-pair encoding, BPE.

Three consequences, each of which becomes an interview question:

- **Frequent strings become one token.** In cl100k, `" strawberry"` with its leading space is a single token. The model never sees the letters, so counting the r's means recalling the spelling from training data, not reading it. Tokenization is one cause of letter-counting failures, not the whole story, but it is the one you can show on a whiteboard. The word on its own, with no space, is three tokens: `str`, `aw`, `berry`. Same word, different tokens, because the space is part of the token.
- **The corpus decides the economy.** Train mostly on English and English compresses well, about 4 characters per token in the sentence above. Under cl100k, Hindi lands at about 1 character per token for two reasons: the pre-tokenizer splits words at every vowel sign before BPE runs, and many Devanagari sequences have no merges, so they fall back to their UTF-8 bytes.
- **Numbers are chunked by position.** cl100k splits digits into groups of up to three: `1234567` becomes `123`, `456`, `7`. The model does arithmetic on chunks it did not choose, which is one reason long arithmetic is unreliable.

## BPE, step by step

Here is the training algorithm on a corpus small enough to watch. Start with characters. Count every adjacent pair. Merge the most frequent pair into a new symbol. Repeat. The first three merges are `e+s`, `es+t` and `est+·` (the dot marks end of word), because "newest" and "widest" together outnumber everything else.

<BpeStepper />

Watch the two numbers move in opposite directions. Every merge makes the corpus shorter (cheaper to process) and the vocabulary larger (a bigger embedding table and a bigger final softmax). Production tokenizers stop somewhere between 32k symbols (Llama 2) and 262k (Gemma 3). "Why not a million-symbol vocabulary?" is a fair follow-up, and the answer is that rare tokens get too few training examples to learn good embeddings, while every token adds a row to the embedding table and a column to the output layer.

## BPE in 30 lines

You will be asked to write this at some point, usually as "implement a simple tokenizer" with a hint. This version fits in your head.

```python
from collections import Counter

def train_bpe(text, num_merges):
    words = [tuple(w) + ("</w>",) for w in text.split()]
    merges = []
    for _ in range(num_merges):
        pairs = Counter()
        for w in words:
            for a, b in zip(w, w[1:]):
                pairs[(a, b)] += 1
        if not pairs:
            break
        best = max(pairs, key=pairs.get)
        merges.append(best)
        words = [merge(w, best) for w in words]
    return merges

def merge(word, pair):
    out, i = [], 0
    while i < len(word):
        if i < len(word) - 1 and (word[i], word[i+1]) == pair:
            out.append(word[i] + word[i+1]); i += 2
        else:
            out.append(word[i]); i += 1
    return tuple(out)

def encode(word, merges):
    w = tuple(word) + ("</w>",)
    for pair in merges:          # apply in training order
        w = merge(w, pair)
    return list(w)
```

## Special tokens, templates and version changes

Three more quirks show up in production rather than in a notebook.

**Special tokens are control characters.** Besides its 100,256 learned tokens, cl100k defines five special ones, including `<|endoftext|>`, and its n_vocab is 100,277, which is the highest id plus one; the ids are not contiguous. Chat APIs wrap each message in special tokens like these through a chat template before the model sees anything. tiktoken refuses to encode the text `<|endoftext|>` by default, and that default is a security control: if you encode untrusted user text with special tokens allowed, a user can type a control token, which is the tokenizer's version of building SQL by string concatenation.

**Templates must match.** An open-weight model expects the exact template it was trained with; gpt-oss, for example, only works with its harmony format. A wrong template produces no error, just worse answers.

**Tokenizers change between versions of the same product.** Anthropic's pricing page says Claude 4.7 and later use a tokenizer that produces about 30% more tokens for the same text. The price per token can stay the same while the price per request rises, so compare cost per task, not per token, and re-measure after every model upgrade. Across languages the spread is larger still: Petrov et al. found the same text differing in token length by up to 15 times between languages.

All of this is why I treat the context window as a memory budget, the way you would budget heap in a constrained process. The system prompt, the examples, the retrieved context, the conversation so far and the reserved output tokens all draw from one fixed pool, measured in the tokenizer of the model you call.

## When this is wrong

"Characters divided by four" is fine for English prose and wrong by 4x for Devanagari, wrong for code with many symbols, and wrong for base64 blobs. If you are sizing a context window, use the real tokenizer. Every major provider publishes one or a token-counting endpoint, and the JavaScript port of tiktoken runs in the browser, which is how the real strips above were made.

The model in this lesson is byte-level BPE with a regex pre-tokenizer, the tiktoken family. SentencePiece tokenizers such as Gemma's skip the regex step and treat whitespace as a symbol, so the strawberry and digit-grouping examples behave differently there. Check the tokenizer of the model you actually ship.
