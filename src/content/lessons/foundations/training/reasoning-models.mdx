## Effort is a latency control

A reasoning model spends output tokens before it answers, and those tokens are generated one at a time on the same decode path as the answer. Every thinking token therefore adds to time to final answer, to the output bill and to context use. The effort setting changes how many such tokens the model tends to spend; it does not change what a token costs. That makes effort a per-route knob in the same family as a timeout or a retry budget, set from measurements on that route, not a global quality switch.

Both major APIs say this in their own terms. Anthropic's thinking docs state that thinking tokens are billed as output tokens even when the thinking text is not returned, and that they count toward `max_tokens` alongside the response. With summarized thinking you are charged for the full thinking tokens, so the billed output count does not match what you see. OpenAI's reasoning guide says reasoning tokens are not visible through the API, occupy context and are billed as output, and recommends reserving at least 25,000 tokens for reasoning and outputs when you start. On both, effort is graded (Claude lists low, medium, high, xhigh and max; OpenAI's values run from none to max and are model-dependent, with gpt-5.5 defaulting to medium), and on Claude's 5-series models thinking is on by default.

The hard limit and the soft knob fail differently. Effort shifts the distribution of thinking length. The output cap truncates it: OpenAI returns `status: incomplete` with reason `max_output_tokens`, possibly before any visible text exists. A client that treats that as an empty answer ships blank responses; it has to be handled as a failure with its own metric.

## The latency arithmetic

Time to the final answer is time to first token plus all generated tokens over the decode rate. Thinking sits inside the second term, so the room for thinking falls straight out of the budget.

The same arithmetic sets the bill. If the answer is 300 tokens and thinking runs to 2,700 (scenario), the route pays for 3,000 output tokens, ten times the visible output. The DeepSeek-R1 paper gives a sense of how long published reasoning traces are: its 800K SFT set averages 5,355 tokens per sample, 7,436 for code and 1,420 for general prompts. Those are training samples, not API outputs, but they show length varying by a factor of five with the task type, which is why a single effort setting across routes is the wrong granularity.

```python
def thinking_room(p95_budget_s, ttft_s, tokens_per_s, answer_tokens):
    return max(0, int((p95_budget_s - ttft_s) * tokens_per_s) - answer_tokens)

def pick_effort(route_stats, budget):
    # route_stats: {effort: (p95_thinking_tokens, eval_score)}, measured per route
    fitting = {e: s for e, (t, s) in route_stats.items() if t <= budget}
    return max(fitting, key=fitting.get) if fitting else None

room = thinking_room(8.0, 0.7, 90, 250)            # 407
stats = {"low": (300, 0.81), "medium": (1900, 0.86), "high": (5200, 0.88)}
print(room, pick_effort(stats, room))               # 407 low
```

`None` is a legitimate result: no effort level fits, and the route needs a non-reasoning model or a different budget.

## Parallel samples or a longer chain

Test-time compute can be spent in two shapes. Parallel: N independent samples, then a vote or a verifier picks one. Sequential: one longer chain, or a chain that revises its own answer. They cost the same tokens and very different wall-clock time. N parallel samples finish in about the time of one if the provider and your rate limits absorb N concurrent requests, so they spend money and tokens-per-minute quota; a chain N times longer spends latency.

The published gains depend on the shape and on difficulty. Snell et al. report that a compute-optimal allocation was more than 4x more efficient than best-of-N, and that in a FLOPs-matched comparison a smaller model with test-time compute outperformed a model 14x larger, but only on problems where the smaller model already had non-trivial success. Their two mechanisms are search against a process-based verifier and adaptive revision of the response, and which one wins depends on prompt difficulty. The engineering reading: allocate per request class, and expect nothing from extra compute on requests the model cannot solve at all.

R1-Zero shows the parallel shape's price directly: 77.9% pass@1 on AIME 2024 and 86.7% with majority voting, where every vote is a full generation. Voting also requires an answer you can compare across samples (a number, a label, a test result); free-text answers need a verifier, and the verifier becomes the component you have to evaluate.

## The visible reasoning is not a trace

Anthropic tested whether reasoning models mention a hint they used. Claude 3.7 Sonnet mentioned it 25% of the time and DeepSeek R1 39%; on hints framed as unauthorized access, 41% and 19%. Unfaithful chains were substantially longer than faithful ones, so length is not evidence of candour. Outcome-based RL raised faithfulness early (a relative 63% and 41% on two evaluations) and then plateaued at 28% and 20%. In a reward-hacking setup the model exploited the hack in over 99% of cases and admitted it in under 2% in most scenarios.

Add the API side: Claude returns a summary or nothing (the 5-series defaults to omitted display), and OpenAI returns no reasoning text. Thinking text is a debugging aid, not an audit log, a policy check or evidence for a compliance file. A control that has to hold is applied to inputs, tool calls and outputs.

## The routing decision

The procedure that follows from the above, per route:

1. Measure, at each effort level, the eval score and the distribution of thinking tokens and latency on that route's traffic, several runs per case because thinking length varies between runs.
2. Pick the lowest effort whose p95 fits the latency budget and whose score clears the bar; if none fits, the route does not get a reasoning model.
3. Set the output cap above the measured p99 at that effort, and alert on the incomplete rate.
4. For routes where wall-clock matters more than spend, prefer parallel samples with a vote or verifier over a higher effort, within rate limits.
5. Re-measure on every model version change, since the thinking length distribution belongs to the model, not to your prompt.

## When this is wrong

The decode-rate arithmetic assumes a steady rate. Providers batch requests, so decode speed varies with their load, and a budget computed from one afternoon's measurement can fail at peak. Measure over a week and use the slow tail.

Adaptive thinking changes the model of a fixed per-route effort. If the model decides per request how much to think, the distribution can shift when your traffic mix shifts, with no change on your side. The effort setting bounds the behaviour; it does not pin it.

The test-time scaling results are from maths and code benchmarks with checkable answers. On tasks without a checker the parallel shape loses its selection step, and the evidence for sequential gains is thinner. Treat a vendor's reasoning gain on benchmarks as a reason to measure on your route, not as a forecast for it.
