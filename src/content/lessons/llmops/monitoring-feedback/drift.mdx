## Four sources, one line on the dashboard

A model feature's quality depends on the weights, the serving path that samples from them, your prompt, tools and retrieval, and the requests users send. Any of them can move while the quality dashboard shows a single line. They group into four sources of drift, each with a different owner and a different first signal.

**The provider's model.** If the name you send resolves to a snapshot, the snapshot behind it can change. Anthropic's versioning page (checked 2026-10-28) draws the line for Claude: before the 4.6 generation, an alias such as `claude-sonnet-4-5` points to the most recent dated snapshot for that minor version; from the 4.6 generation on, the dateless ID is the snapshot, and Anthropic does not update the weights or configuration of an existing ID. Other providers and gateways have their own rules, and the rule that matters is the one for the exact string in your config.

**The serving path.** The same page says the infrastructure around fixed weights (the request router, safety classifiers and sampling logic) does change, and can produce small differences in behaviour on an unchanged ID. Anthropic's September 2025 postmortem is the worked case: a routing error, a TPU misconfiguration and a compiler bug in approximate top-k degraded answers for weeks with no change to any model ID. [Quality regressions with no model change](/learn/inference/operating/quality-incidents) covers that incident layer by layer.

**Your own changes.** Prompt edits, a new tool schema, a rebuilt index, a new chunker or embedding model. Diagnosing any drift starts from having each of these versioned and logged with the trace, along with the policy, dataset and grader versions.

**The traffic.** A new customer, locale or upstream feature changes what users ask. Per-segment quality can stay fixed while the aggregate moves, in either direction.

## What a provider change looks like

Chen, Zaharia and Zou queried the March 2023 and June 2023 snapshots of GPT-4 and GPT-3.5 through OpenAI's API with the same prompts, the default system prompt and temperature 0.1. On 1,000 prime-or-composite questions (500 primes and 500 composites drawn from 1,000 to 20,000) with a chain-of-thought prompt, GPT-4's accuracy fell from 84.0% to 51.1%, and GPT-3.5's rose from 49.6% to 76.2%. The June GPT-4 had stopped writing the intermediate steps it was asked for: its mean response length fell from 638.3 characters to 3.9, and it called 99.7% of the integers composite. On LeetCode problems, GPT-4 generations that ran and passed went from 52.0% to 10.0%, because the June version wrapped its code in markdown fences; with the non-code text stripped, the same comparison went from 52% to 70%. GPT-4's answer rate on sensitive questions fell from 21.0% to 5.0%.

Three properties of this data matter for monitoring. The accuracy drop on primes arrived with a 164-fold fall in output length (638.3 / 3.9), which a length distribution shows on the first day of traffic, with no labels. The code drop was a format change that an accuracy metric would report as a capability regression, while a parse assertion would fire and name the cause. And the changes went in opposite directions across models and tasks, so one aggregate score can net a regression against an improvement.

OpenTelemetry's GenAI conventions (status Development, checked 2026-10-28) separate `gen_ai.request.model`, the name you asked for, from `gen_ai.response.model`, the name returned, and use `gpt-4` and `gpt-4-0613` as their examples. A shift in the distribution of the returned name is the cheapest provider-drift detector there is. Where a provider returns a backend identifier, log that too: OpenAI's archived seed-parameter cookbook describes `system_fingerprint` as the backend configuration the model runs with, changing when request parameters change or when OpenAI updates the numerical configuration of its serving infrastructure. Neither identifier would have caught Anthropic's three bugs, which left every ID unchanged.

## Leading signals before labels

Ground truth arrives late: a support resolution is known after the re-contact window closes, a code suggestion's value after review. Between a change and its labels you watch proxies, and each proxy has a source it detects first and a blind spot.

| Signal | Fires first for | Blind spot |
|---|---|---|
| Returned model name and backend identifier | A provider snapshot change | Serving changes that keep the ID |
| Output length distribution per route | Instruction-following changes, such as Chen's 638.3 to 3.9 characters | A shorter answer can be a better one |
| Refusal rate | Safety-tuning changes, such as Chen's 21.0% to 5.0% answer rate | Refusals phrased as partial answers |
| Tool calls per task and tool error rate | Prompt, tool-schema and agent-behaviour changes | A correct shorter path reads as a change |
| Assertions on every output: schema, parse, citation exists, language matches | Format drift (Chen's code fences) and corruption (Anthropic's Thai characters in English replies) | Anything well-formed and wrong |
| Sampled judge pass rate | Semantic regressions with volume | Rare segments, and the judge's own drift |
| Request volume per segment | Traffic mix | Says nothing about quality alone |

Everything above the judge runs on every trace for almost nothing. Alert per segment and per serving region, not only globally: the Anthropic routing error began at 0.8% of Sonnet 4 requests, which a global line absorbs.

## The frozen replay set separates model from traffic

A frozen input set removes one of the four sources: its inputs never change, so traffic mix cannot move its results.

The set is a few hundred real requests, stratified by segment, stored with the retrieval results and tool responses they produced at capture time, so an index rebuild does not leak into a model comparison. A scheduled job replays it daily through the production configuration (returned model, prompt version, sampling parameters) and again after each of your own deploys. Each run records Chen's mismatch metric, the share of items whose extracted answer differs from the reference run, alongside the leading signals and assertions above, computed on the replay outputs.

The reference run needs a noise floor. Run the set twice back to back on an unchanged configuration and measure mismatch between the two; the archived OpenAI cookbook says responses can differ even when the seed, the parameters and the fingerprint all match, and the same holds for any provider that does not promise bitwise determinism. Alert on mismatch well above that floor, not on any mismatch.

The replay and production results then read as a two-by-two:

| Production signal | Replay signal | Where to look |
|---|---|---|
| Moved | Moved | Model, serving path or your configuration: check the returned model name and your deploy log; if neither changed, suspect serving |
| Moved | Flat | Traffic mix or live data: decompose by segment and replay current queries against the live index |
| Flat | Moved | A change on inputs current traffic rarely sends, or one offset by mix; investigate before that traffic returns |
| Flat | Flat, with complaints | Your signals do not cover the failure; read the traces behind the complaints |

Splitting the aggregate change into a mix part and a rate part is the standard decomposition from demography, and it is short enough to run on every dashboard refresh:

```python
def decompose(before, after):
    """before, after: {segment: (traffic share, pass rate)} over the same segments.
    Returns (mix effect, rate effect) in percentage points; they sum to the total change."""
    mix = rate = 0.0
    for seg in before:
        w0, p0 = before[seg]
        w1, p1 = after[seg]
        mix += (w1 - w0) * (p0 + p1) / 2    # share moved, valued at the average pass rate
        rate += (p1 - p0) * (w0 + w1) / 2   # pass rate moved, weighted by the average share
    return round(100 * mix, 2), round(100 * rate, 2)

march = {"lookup": (0.80, 0.92), "account_change": (0.20, 0.70)}
mix_only = {"lookup": (0.60, 0.92), "account_change": (0.40, 0.70)}
both = {"lookup": (0.60, 0.92), "account_change": (0.40, 0.64)}
print(decompose(march, mix_only))   # (-4.4, 0.0): traffic drift only
print(decompose(march, both))       # (-5.0, -1.8): traffic drift plus a real regression
```

The second case is the one that costs teams a week: the aggregate fell 6.8 points, most of it mix, and a 6-point regression inside the account-change segment hides in the remainder. The rate effect is what the replay set should confirm; if the replay is flat while the rate effect is negative, the regression is in live data the replay froze out, such as the index.

## Agents and retrieval break the freeze

Recorded tool responses work until the new configuration calls a different tool or passes different arguments, and then the replay has no recording to return. Count an unrecorded call as a divergence in its own right, since a change in tool path is itself a drift signal, and stop that item there rather than calling live systems. Items that need live tools belong in a separate sandboxed suite with its own noise floor.

Retrieval has two halves to separate. Frozen retrieved chunks isolate the model. A second job replays the same queries against the live index and measures recall against the documents known to be relevant, which isolates index drift: stale documents, a re-embedding, a changed chunker.

## The evaluator drifts too

A sampled judge is a model behind an API, exposed to every drift source above. Keep a judge-control set of human-labelled items that includes known ties, verbosity bait and order-swapped pairs, and score it on every change to the judge's model, prompt, rubric or output schema, and on a schedule without any change. Track agreement with the labels by segment, the invalid-output rate and order consistency. When the judge's scores move and the human labels do not, stop plotting the trend across the change, or rescore history under the new judge and record the migration. [Validating a judge](/learn/evals/llm-judge/judge-validation) covers the agreement measurement itself.

The humans drift as well. Shankar and colleagues named it criteria drift: people need criteria to grade outputs, and grading outputs changes the criteria. Husain and Shankar's FAQ warns that the effect is larger than teams expect and recommends repeating error analysis to keep the rubric current. To measure it, re-label a sample of old items blind every quarter and compare against the original labels; disagreement there is drift in the instrument, not in the product.

## When this is wrong

A frozen set ages: it measures the model on last quarter's questions. Refresh it, and run the old version alongside for an overlap period, so a jump in replay results can be attributed to the set change rather than to the model.

Pinning removes provider weight changes and nothing else. Anthropic's own page says serving infrastructure changes on fixed IDs, and every pinned ID carries a retirement date, so a pin turns drift you cannot schedule into a migration you can.

The leading signals are triggers to look, not verdicts. A provider improvement moves length, refusals and tool counts as much as a regression does, and a team that rolls back on every alert will roll back improvements.

The decomposition needs segment labels that existed before the shift. A new kind of request lands in "other", and the decomposition reports it as a rate change in a segment nobody owns.

And in products where labels arrive quickly, such as code whose tests run before merge, most of this apparatus is unnecessary: the label is the monitor, and the lag between a change and its detection is the test run.
