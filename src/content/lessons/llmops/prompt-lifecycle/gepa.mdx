## The problem the paper solves

A compound AI system, one or more model calls wired into a program, has its prompts as learnable parameters. Two ways to improve it were in common use. Reinforcement learning such as GRPO updates the weights from a scalar reward, which needs open weights and thousands of rollouts. Prompt optimisers such as MIPROv2 search instructions and demonstrations against the same scalar. Both reduce a rollout to one number, and the rollout itself (the reasoning, the tool calls, the tool outputs, the compiler error) carries much more information about why it failed.

Agrawal and colleagues ask whether a model reading those trajectories in natural language can learn more per rollout than a policy gradient on the score. The paper's answer is GEPA (Genetic-Pareto), and its headline is that on six tasks it beats GRPO with far fewer rollouts and beats MIPROv2 by a wide margin.

## The mechanism

GEPA keeps a pool of candidate programs, each a full set of module instructions, starting from the seed. The training data is split into a feedback set, used for reflection, and a Pareto set, used for selection. Each iteration does five things.

1. **Pick a parent from the Pareto frontier.** For every example in the Pareto set, record the best score any candidate has achieved. Keep the candidates that achieve that best on at least one example, prune those strictly dominated by another, and sample a parent with probability proportional to the number of examples it leads on.
2. **Run it on a minibatch from the feedback set.** The paper uses a minibatch of 3. Collect the trajectories, the scores and the feedback text.
3. **Reflect on one module.** Modules are chosen round-robin. A reflection model receives the module's current instruction, the inputs and outputs from the trajectories, and the feedback, and writes a new instruction. The meta-prompt asks it to capture niche, domain-specific facts and any strategy that generalises.
4. **Gate cheaply, then evaluate.** Re-run the child on the same minibatch. Only if it improves there is it scored on the full Pareto set and added to the pool.
5. **Optionally merge.** GEPA+Merge combines the best versions of different modules from distinct lineages into one candidate, a crossover that is aware of the program's module structure.

The feedback is the part that differs from earlier optimisers. The paper extends the metric into a feedback function that returns text with the score: compiler error messages, which rubric items failed, per-hop retrieval results in a multi-hop system. Without it, the reflection model sees only outputs and a number.

The frontier is the other part. Selecting on the best average throws away a candidate that solved examples nobody else did, because its average is lower. The frontier keeps it as a parent, so a later child can combine its lesson with others. In code, with a toy Pareto set of five examples:

```python
import random

def pareto_weights(scores):
    """scores: candidate -> per-example scores on the Pareto set.
    Keep candidates that are best on at least one example and not dominated;
    weight each by the number of examples it is best on."""
    names = list(scores)
    n = len(next(iter(scores.values())))
    best = [max(scores[c][i] for c in names) for i in range(n)]
    leaders = {c for c in names if any(scores[c][i] == best[i] for i in range(n))}

    def dominated(a):
        return any(
            all(scores[b][i] >= scores[a][i] for i in range(n))
            and any(scores[b][i] > scores[a][i] for i in range(n))
            for b in leaders if b != a
        )

    front = [c for c in leaders if not dominated(c)]
    return {c: sum(scores[c][i] == best[i] for i in range(n)) for c in sorted(front)}

scores = {
    "seed":   [1, 0, 0, 1, 0],
    "cand_a": [1, 1, 1, 0, 0],  # best average: 3 of 5
    "cand_b": [0, 0, 0, 1, 1],  # wins where cand_a fails
    "cand_c": [1, 1, 0, 0, 0],  # dominated by cand_a
}
w = pareto_weights(scores)
print(w)  # {'cand_a': 3, 'cand_b': 2, 'seed': 2}
rng = random.Random(0)
print(rng.choices(list(w), weights=list(w.values()), k=8))
```

A best-average rule would mutate `cand_a` forever. The frontier also mutates `cand_b`, which holds the only solution to the last example, and the seed, which is the only candidate that solves both the first and fourth. The design resembles keeping several branches alive in a beam search, with the difference that membership is decided per example, not by total score.

## The key numbers

Table 1 of the paper (Qwen3 8B, test-set scores) and Table 2 (GPT-4.1 mini), aggregated over the six tasks:

| Model | Baseline | GRPO | MIPROv2 | TextGrad | GEPA | GEPA+Merge |
|---|---|---|---|---|---|---|
| Qwen3 8B | 45.23 | 48.91 | 47.84 | not run | 54.85 | 52.40 |
| GPT-4.1 mini | 53.03 | not run | 58.67 | 59.14 | 65.22 | 66.36 |

The abstract's "6% on average" over GRPO is the aggregate gap in points: 54.85 − 48.91 = 5.94. Expressed relative to GRPO it is 5.94 / 48.91 = 12.1%. The "over 10%" over MIPROv2 fits a relative reading: on Qwen3 8B, 7.01 points is 14.7% of 47.84; on GPT-4.1 mini, GEPA's 6.55 points is 11.2% of 58.67. The abstract does not say which reading each figure uses, so a citation should give the points. The largest per-task gap over GRPO is HotpotQA, 62.33 against 43.33, 19.0 points.

GRPO ran a fixed 24,000 rollouts per task (LoRA rank 16, 500 steps, validation every 20 steps for early stopping). GEPA's totals per task in Table 1 are 6,871, 3,593, 7,051, 2,426, 1,839 and 1,839.

The paper is explicit that most of GEPA's budget goes to validation, scoring candidates on the Pareto set for selection, and that the rollouts on training data alone would have been 79 to 737 per task to reach the best prompt. Validation set size is therefore the main cost lever, and the paper names smaller or dynamic validation subsets as future work.

Three results cut against the headline. On AIME-2025 with Qwen3 8B, GRPO scored 38.00 and GEPA 32.00. GEPA+Merge, which is a default-on option in DSPy, dropped Qwen3 8B's IFBench score to 28.23, below the unoptimised baseline of 36.90, and lowered the Qwen3 8B aggregate from 54.85 to 52.40, while it raised GPT-4.1 mini's from 65.22 to 66.36. And MIPROv2 on Qwen3 8B fell below baseline on AIME-2025 (20.00 against 27.33), so a single optimiser run can regress a task outright.

The test sets are small. HotpotQA and HoVer test on 300 examples, IFBench on 294, PUPA on 221. Near 50% accuracy, a 300-example test set measures one score to within 1.96 × √(0.25 / 300) = 5.7 points; on 221 examples, 6.6 points. Per-task gaps of 1 to 3 points in the tables (IFBench GEPA 38.61 against baseline 36.90, LiveBench-Math 51.95 against GRPO 51.26) are inside that band on one run; the aggregate gaps of 6 to 7 points are larger than any single task's band but rest on six tasks.

## What changed in practice

Optimisers started asking for text, not just scores. DSPy's `dspy.GEPA` expects the metric to return `dspy.Prediction(score=..., feedback=...)`, and its docs list what feedback can carry: evaluation logs, code traces, failed parses, constraint violations, error messages. MLflow ships `GepaPromptOptimizer` in `mlflow.genai.optimize_prompts` from 3.5.0. Writing a metric now includes writing the explanation a reviewer would give, which most eval code already computes and discards.

Prompt optimisation became a credible alternative to RL fine-tuning for closed-weight models. Table 2 has no GRPO row because GPT-4.1 mini's weights are not available to train; GEPA lifted its aggregate by 12.19 points with prompts alone. Prompts GEPA optimised on Qwen3 8B, evaluated on GPT-4.1 mini, still scored 62.03 against the 53.03 baseline, which is evidence that the instructions encode task knowledge and not only one model's quirks.

Instruction-heavy prompts came back. The paper's Appendix I reports GEPA's prompts around 33% shorter than MIPROv2's on average, and up to 9.2 times shorter, because GEPA spends tokens on instructions and MIPROv2 on few-shot demonstrations. Every production call pays for the prompt, so the length difference is a running cost, not a one-off.

## Using it in DSPy

The DSPy defaults, from the source on the main branch as checked on 2026-10-28, are where a run differs from the paper without anyone deciding it.

```python
import dspy

def metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    missing = [f for f in gold.required_fields if f not in pred.extracted]
    wrong = [f for f in gold.required_fields
             if f in pred.extracted and pred.extracted[f] != gold.values[f]]
    score = 1.0 - (len(missing) + len(wrong)) / len(gold.required_fields)
    feedback = (f"Missing fields: {missing}. Wrong values: {wrong}. "
                f"Expected {gold.values}.") if score < 1 else "All fields correct."
    return dspy.Prediction(score=score, feedback=feedback)

gepa = dspy.GEPA(
    metric=metric,
    auto="light",                     # or max_full_evals / max_metric_calls: exactly one
    reflection_lm=dspy.LM("openai/gpt-4.1"),  # required unless you supply a proposer
    use_merge=False,                  # default True; the paper's Qwen3 8B runs lost with it
    track_stats=True,
)
optimised = gepa.compile(program, trainset=train, valset=pareto_set)
```

Three defaults matter. A metric that returns only a float still runs, and the reflection model is told "This trajectory got a score of &#123;score&#125;.", which removes the signal the method is built on. Without a `valset`, GEPA uses the trainset as the Pareto set and logs a warning, so selection happens on the examples reflection learned from. And `use_merge` defaults to on, which the paper's own tables show helping one model and hurting the other.

## When this is wrong

Every number above is the authors' own, on six public benchmarks and two models. The tables quoted here give one score per method and task with no spread across runs, so a 2-point comparison on 300 examples carries no weight on its own.

The GRPO baseline is one configuration: LoRA rank 16, 500 steps and a fixed 24,000 rollouts. A differently tuned RL run, full-parameter training, or a larger budget could change the comparison; the result is about these budgets.

The reflection model's capability is part of the result. Reflection is a model reading trajectories and writing instructions; a weaker reflection model writes weaker instructions. When the reflection model is stronger than the task model, part of the gain is distillation of the stronger model's knowledge into the prompt, which is useful in production and should be named as such.

The Pareto set does the selecting, so the winner's score on it is biased upward by the same selection effect as any dev set. The paper reports test-set scores, and Appendix H examines the gap between best validation and final test scores; a team reproducing the method has to keep its own held-out set for the same reason.

Tasks without useful feedback text gain less from the method's main idea. A binary pass or fail on a free-form answer, with no reason attached, leaves the reflection model with the same information OPRO had.
