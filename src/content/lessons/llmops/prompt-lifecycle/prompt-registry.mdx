## The decision

Every prompt in production needs an answer to four questions: where its text lives, how a new version reaches traffic, who may make that happen, and how long a rollback takes. Most teams answer the first by accident (a string literal, then a YAML file, then a registry) and never answer the last.

The registry model that most tools converge on is the one Langfuse documents. Each edit creates a new numbered version, versions are immutable, and labels are pointers to versions. Application code asks for a label, `production` by default, and never for a version. Shipping is moving the label; rollback is moving it back. Langfuse's `latest` label follows the newest version automatically, so a client that asks for `latest` in production has turned every save into a deploy.

This is release-by-pointer, the same shape as a container tag or a feature flag. The difference from a container tag is that the artefact is fetched at request time by a client library with its own cache, so the moment the pointer moves is not the moment traffic changes.

## The inputs that change it

**Who edits prompts.** If only engineers edit them, the repository already gives versions, review and blame. If product managers or domain experts edit them weekly, a registry removes a deploy from each edit, and the review has to move into the registry.

**How fast a bad version must leave production.** With a client-side cache, the bound is the cache TTL plus the time to the next request on each process, not the time to click. Langfuse's SDK default TTL is 60 seconds, and after expiry the SDK serves the stale prompt immediately and refreshes in the background, so the first request after expiry still gets the old text.

**How many teams share the registry, and at what risk.** A shared registry with one permission level means anyone who can edit a low-risk marketing prompt can move the production label on the refund-policy prompt. Langfuse's answer is protected labels: once `production` is protected, `viewer` and `member` roles cannot move it, and `admin` and `owner` can. That feature sits on Enterprise and self-hosted Enterprise, and on Pro with the Teams add-on, as of 2026-10-28, so the plan tier is part of the decision.

**Whether the registry is on the request path.** A runtime fetch makes the registry a dependency. The cache covers short outages; a cold process with an empty cache and an unreachable registry needs a fallback prompt baked into the code. Langfuse documents that a fallback creates no link to traces, so requests served from it are invisible in per-version metrics.

**Whether optimisers write versions.** MLflow's `optimize_prompts` (MLflow 3.5.0 or later) reads prompts from its registry by URI and returns optimised prompts with a name, version and URI. An optimiser is a second author that produces versions faster than people review them, so the gate has to be the same for both.

## The options and when each wins

**Prompts in the repository, shipped with the code.** Every change gets code review, CI and the deploy's own rollout and rollback. The cost is that each edit is a deploy and non-engineers need an engineer to ship. It wins when engineers own the prompts, edits are infrequent, and the service already deploys several times a day. Rollback speed equals deploy speed, which is often minutes and always known.

**A runtime registry, fetched by label.** Edits ship without a deploy, versions are diffable in one place, and per-version metrics come from the trace link. It wins when non-engineers iterate on prompts and the team accepts the registry as a production dependency. Its rollback time is the cache TTL, and its review is whatever the registry enforces, which by default is nothing.

**A registry as the source, pinned in the repository.** The registry holds versions and the tooling; the service's config file names the exact version number per environment (`triage: 14`), and a pull request bumps it. Langfuse supports fetching by version number, and a missing label returns a 404 rather than a silent fallback. This gives the registry's diff view and trace metrics with the repository's review and deploy rollback. It loses edit-without-deploy, which is the reason many teams adopted the registry, so it wins where a wrong prompt is expensive: regulated text, actions with money attached, prompts that drive tool calls.

**Mixed by risk tier.** Low-risk prompts ship by label with a short TTL; high-risk prompts are pinned by version in the repository. This is the usual end state for a registry shared by several teams, and it needs an explicit tier per prompt with a named owner, or every prompt drifts to the convenient tier.

Whichever option is chosen, three rules do not change. Every generation records the prompt name and version next to the model ID, or no metric movement can be attributed. A prompt change and a model change never ship in the same release. And the version that runs in CI is the version that ships, not a copy of it.

The second rule comes from attribution. The applied-llms authors report that Voiceflow saw a 10% drop in intent classification moving from `gpt-3.5-turbo-0301` to `gpt-3.5-turbo-1106`, while GoDaddy saw the opposite on the same upgrade. The same model change moved two products in opposite directions; with a prompt edit in the same release, neither team could have said which change did what. Their remedy is to pin model versions and keep a shadow pipeline on the newest model, so the model change is evaluated on its own before any prompt is adapted to it.

## The mechanics in code

The registry's data model and the client cache are small enough to write out. The point of running it is the last line: the rollback happens at second 1 and the bad version is still served at second 60.

```python
class Registry:
    """Immutable versions, movable labels: the Langfuse data model in miniature."""

    def __init__(self):
        self.versions = {}  # name -> list of texts; version n is index n - 1
        self.labels = {}    # (name, label) -> version number

    def create(self, name, text, labels=()):
        self.versions.setdefault(name, []).append(text)
        v = len(self.versions[name])
        for label in ("latest", *labels):
            self.labels[(name, label)] = v
        return v

    def move(self, name, label, version):
        self.labels[(name, label)] = version  # rollback is this line

    def get(self, name, label="production"):
        v = self.labels[(name, label)]  # KeyError, never a silent fallback
        return v, self.versions[name][v - 1]


class CachedClient:
    """Client-side cache with stale-while-revalidate, as the SDKs do it."""

    def __init__(self, registry, ttl):
        self.registry, self.ttl, self.cache = registry, ttl, {}

    def get(self, name, now):
        entry = self.cache.get(name)
        if entry is None:
            entry = self.cache[name] = (self.registry.get(name), now)
        elif now - entry[1] >= self.ttl:
            # Serve the stale entry now; the refresh lands for the next call.
            self.cache[name] = (self.registry.get(name), now)
        return entry[0]


reg = Registry()
reg.create("triage", "v1 text", labels=["production"])
reg.create("triage", "v2 text", labels=["production"])  # the bad release
pod = CachedClient(reg, ttl=60)
pod.get("triage", now=0)             # pod caches v2 at t = 0
reg.move("triage", "production", 1)  # rollback at t = 1
served = [pod.get("triage", now=t)[0] for t in range(1, 121)]
print("last second v2 was served:", max(t for t, v in zip(range(1, 121), served) if v == 2))
# last second v2 was served: 60
```

The real SDK refreshes asynchronously, so the window is the TTL plus the time to the first request after expiry plus one fetch. A process that sees no traffic holds the old version indefinitely and serves it on its next request. Every process has its own cache and its own refresh time, so a fleet does not switch at one instant.

Two consequences follow. A rollback that must be faster than the TTL needs a second path: a kill switch read on every request, a version pin pushed through the service's own config, or a restart. And a TTL of zero, which Langfuse recommends only outside production, moves the registry onto every request's latency and availability.

## Worked decision

A scenario. A support product has 14 prompts owned by three teams: support operations edits reply-tone prompts weekly, the payments team owns a refund-eligibility prompt that drives a `process_refund` tool call, and the platform team owns routing. The service deploys twice a day. Last quarter a reply-tone edit went out on a Friday with no eval, and nobody could tell from traces which version had answered which ticket.

Refund eligibility is pinned by version number in the service's config. A bump is a pull request reviewed by the payments owner, gated on the golden set for that prompt, and rolled back by reverting the config, which takes one deploy. Edit-without-deploy is given up for this prompt; a twice-daily deploy cadence makes the cost small.

Reply-tone and routing prompts ship by label. `production` is protected so that only two named owners can move it, and moving it is a step in a pipeline that first runs the prompt's eval suite against the candidate version and records the score on the version. The TTL stays at 60 seconds and is written into the runbook as the rollback bound, with the arithmetic from the Predict block for current traffic.

Every generation carries the prompt object, so per-version latency, tokens, cost and median score come from the trace link. The fallback prompt in the code is kept in sync with the pinned or labelled version by a CI check that fails when they differ, because a request served from the fallback is not linked to any version.

Model upgrades go through a separate release: the shadow pipeline runs the new model with the current prompt versions, the eval suites run, and only then do prompt owners cut new versions for the new model. The release note names both the model ID and the prompt versions.

What the team gives up, in writing: support operations can no longer ship a tone change in seconds without an eval run; payments cannot hotfix refund wording without a deploy; and the 60-second rollback bound is accepted for prompts that do not move money.

## What to measure after deciding

Per prompt version: the eval score recorded at promotion, the production metrics from linked generations (median latency, input and output tokens, cost, median score), and the count of generations, which tells you whether the version actually took traffic.

Unlinked generations. A rising share of generations with no prompt link means fallbacks are firing, a code path skipped the link, or a framework integration lost the metadata.

Time from label move to the last generation on the old version, measured from traces after every rollback. That is the real rollback time, and it is the number to compare with the TTL.

Label moves per week by actor and tier, and how many skipped the eval gate. A registry whose gate is bypassed under deadline pressure has turned back into string literals with a UI.

## When this is wrong

The playbook assumes a registry with Langfuse's semantics. Other registries differ in exactly the places that matter: whether versions are immutable, whether a missing label falls back to something, what the cache default is, and whether labels can be protected. Check each before reusing the arithmetic.

Label-based release assumes the prompt text is the whole change. Prompts carry config (model parameters, tool definitions, output schemas), and a version that changes the schema is a contract change for the code that parses the output. That change has to ship with code, so it belongs in the pinned path whatever its risk tier.

Pinning by version moves rollback speed to the deploy pipeline. A service that deploys weekly with a slow pipeline has a worse rollback bound pinned than labelled; the tier choice depends on the deploy cadence you actually have.

Per-version production metrics compare versions that ran at different times on different traffic. A version promoted on a Monday and another on a Saturday are not an experiment. When the question is whether version 15 is better than 14, the answer comes from a split of live traffic or an offline eval on the same cases, which the releases module covers.
