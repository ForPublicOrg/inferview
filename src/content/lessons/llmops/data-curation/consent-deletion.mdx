Before a production conversation becomes an eval item or a training example, three questions need written answers: under what basis this use is allowed, how long each copy lives, and how a deletion request reaches every copy, including the ones inside a trained model. The engineering is mostly the third, and it is decided by the answers to the first two.

## Two uses, two policies

Evaluating a model on a conversation and training a model on it are different processing. An eval item is read by reviewers, scored and kept; deleting the row deletes it. A training example changes weights, and what it changed stays in every model trained on it until those models are retired or retrained. A single consent flag labelled "AI improvement" hides that difference and usually ends up too broad for legal or too narrow for the eval team.

The European Data Protection Board's Opinion 28/2024, adopted 18 December 2024 at the Irish supervisory authority's request, is the reference for EU personal data. Three of its positions shape the design.

**A model trained on personal data is not anonymous by default.** It is anonymous only if both the likelihood of extracting personal data from it directly, including probabilistically, and the likelihood of obtaining such data by querying it are insignificant, taking into account all the means reasonably likely to be used. A fine-tuned model that has seen support conversations is not something a team can show passes that test without measurement, so the default assumption is that the model contains the personal data it was trained on.

**Legitimate interest is assessed in three steps.** The interest must be lawful, clearly articulated and real; the processing must be necessary for it, with no less intrusive way; and the interest must not be overridden by the data subjects' rights, where their reasonable expectations count. Whether users of a support product expect their conversations to train a model depends on what they were told and on the context of the service, which is why the terms of service are an engineering input.

**Mitigations are listed.** Paragraphs 101 and 102 list measures that can tip the balance: pseudonymisation, replacing names and email addresses with fake ones where the content does not depend on them, a reasonable period between collecting data and training on it so people can exercise their rights, an unconditional opt-out before processing, honouring erasure beyond the cases the law requires, and a way for people to report that a model regurgitates their data. For deployment, paragraph 107 adds output filters. Each of these is a component someone has to build.

The opinion also states the downside. Where development was unlawful, corrective measures can include erasing the part of the dataset processed unlawfully or, where that is not possible, the whole dataset or the model itself, with retraining as a factor in proportionality (paragraph 114). That is the risk a team takes on when it trains first and documents later.

A workable policy separates the two uses:

| | eval use | training use |
|---|---|---|
| basis | documented legitimate-interest assessment, or consent | consent that names training, or an assessment that survives the balancing test with the mitigations above |
| who is excluded | tenants whose contracts forbid it | the same, plus anyone who has not consented or has opted out |
| content | scrubbed, pseudonymised, reviewed | scrubbed, pseudonymised, personal details replaced where the task allows |
| retention | per row, with a stated limit | per dataset version, plus the life of every model trained on it |
| deletion | delete the row and rebuild the set | exclude from the next build, and bound the time until the served model no longer contains it |

## Where copies live

A deletion request is only as complete as the inventory of copies. For a typical pipeline the copies are: the raw logs; the scrubbed store; every dataset version; the labelling tool's tasks and exports; notebooks and ad hoc samples; files uploaded to a provider for fine-tuning, batch jobs or evals; the provider's own logs; and every model trained on any of those versions.

Provider retention is documented and differs by endpoint, so it belongs in the inventory with a date. OpenAI's data controls page (checked 28 October 2026) states that API data has not been used to train OpenAI's models by default since 1 March 2023, that abuse monitoring logs are kept for up to 30 days by default, and that `/v1/responses` keeps application state for 30 days by default when `store` is true. Files, fine-tuning jobs, evals and batches keep application state until deleted. The engineering consequence is that a training file or an eval dataset uploaded for a job stays until your pipeline deletes it, or until an `expires_after` set at upload. Zero data retention and modified abuse monitoring exist, but need the provider's approval.

## The deletion path

The path has four parts.

**A stable pseudonym.** Every record carries a keyed hash of the user id and the tenant id, computed at the logging boundary with a key held outside the datasets. Presidio's hash operator uses a random salt by default from version 2.2.361, which gives the same user a different pseudonym on every record; its documentation says referential integrity needs a consistent salt. Without a stable pseudonym, a deletion cannot find a user's rows, and a user split cannot keep them on one side.

**A lineage index.** A table from pseudonym to every artefact containing that pseudonym's data: dataset version, labelling task, provider file id, model id. Builds write to it; so does any export from the curated store. Copies made outside the build, such as a sample pasted into a notebook, are exactly the ones it misses, which is why exports go through a job that registers them and raw logs are not readable by people outside the on-call rota.

**Rebuild, never patch.** Dataset versions are immutable, so a deletion adds the pseudonym to an exclusion list that every build applies, the next build produces a new version, and old versions are deleted when the new one replaces them. Provider files from old versions are deleted through the API in the same job.

**A bound for the model.** Deleting a training file does not change weights already trained on it. The served model contains a deleted user's data until a model trained without it replaces it, so the worst case is set by the retraining cadence plus the time to train, evaluate and roll out.

A sketch of the job, run daily:

```python
def process_deletions(requests, index, key, provider, exclusions):
    for req in requests:
        p = pseudonym(key, req.tenant_id, req.user_id)
        exclusions.add(p)
        for art in index.artefacts(p):
            if art.kind == "label_task":
                art.purge(p)
            elif art.kind == "provider_file":
                provider.files.delete(art.file_id)
            elif art.kind == "model":
                index.schedule_replacement(art.model_id, by=next_retrain_date())
        req.record(completed_at=now(), artefacts=index.artefacts(p))
```

Deleting a provider file removes the copy; the dataset version it came from is rebuilt by the next build, which applies the exclusions. The request record lists every artefact touched, which is the evidence when someone asks.

## When this is wrong

The EDPB opinion is the board's reading of the GDPR for supervisory authorities, and it repeats that assessments are case by case. It is not a checklist that guarantees compliance, and other jurisdictions have different bases and deletion rules. The engineering in this lesson, a pseudonym, a lineage index and a bound for weights, is needed under any of them; the policy table is not portable.

Machine unlearning, removing a person's influence from trained weights without retraining, would change the model row of the table. The opinion mentions post-training techniques that attempt to remove or suppress personal data as a deployment measure; this lesson treats them as unproven for a deletion promise and relies on retraining.

For a provider-hosted fine-tune, the weights are not in your infrastructure. Retraining replaces your model, but deleting the old fine-tuned model is a provider API call, and what happens to the provider's copies after that is governed by its terms, which the inventory records with a date.

And if no personal data is needed for the task, the cheapest deletion path is not to have one: replace names, emails and identifiers with fake values before the data reaches the training pool, which the opinion lists among the mitigations, and keep the real values only in the eval rows a reviewer needs to read.
