## The decision

A model id, a prompt version, a decoding setting, a retrieval parameter and an API version are all deploys, and each can change what the feature does without raising an error. The release ladder for them has five rungs: an offline gate, shadow traffic, a canary, an A/B test and the full rollout. The decision is which rungs a given change climbs, and for each rung the entry condition, what it measures, what it costs and the trigger that sends the change back down.

Only one rung answers the question the business asks. The offline gate measures behaviour on cases you chose. Shadow measures the candidate on real inputs, but nobody reads its answers, so it cannot see what users do next. A canary exposes real users, but at a share too small to power an outcome comparison, so it is a health check. The A/B test, with assignment by user and a sample size fixed in advance, is the only rung that measures the outcome metric causally. Rollout is where you find out what the A/B population did not contain.

The offline gate is the one rung every change takes. The applied-llms.org authors report that Voiceflow lost 10% on an intent classification task moving between two snapshots of gpt-3.5-turbo, and that their evals caught it. The gate itself is the [merge gate lesson](/learn/evals/evals-in-ci/merge-gates); this playbook starts where it ends.

## The inputs that change it

**The retirement date.** Anthropic gives at least 60 days' notice before retiring a publicly released model, and requests to a retired model fail. Claude Sonnet 4.5 (`claude-sonnet-4-5-20250929`) was deprecated on 30 September 2026 with retirement on 30 November 2026: 61 days, as of 28 October 33 of them left. OpenAI's policy minimum is six months for generally available models, three for specialised variants and as little as two weeks for previews, unless safety or compliance requires sooner. Its notice of 14 October 2026 removes the dated gpt-4o, gpt-4o-mini, gpt-4.1 and gpt-4.1-mini snapshots on 14 January 2027, which is 92 days. Plan from the date in the deprecation table, not from the policy minimum. Amazon Bedrock and Google-managed Claude set their own schedules, so the same model can have two dates if you call it through two platforms.

**Whether the model is fine-tuned.** OpenAI's fine-tuned versions of the gpt-4o and gpt-4.1 families follow their base models to shutdown on 14 January 2027, and existing customers can no longer create fine-tuning jobs after 6 January 2027. A team serving a fine-tuned gpt-4.1-mini cannot climb the ladder with a retrained fine-tune on the same platform after that date, so the candidate has to be a prompt on a different model, or a fine-tune elsewhere, and the offline gate has to cover what the fine-tune was doing.

**The tokenizer and the price.** Anthropic states that Claude 4.7 and later models produce approximately 30% more tokens for the same text, with the exact increase depending on content. Sonnet 4.5 costs $3 per million input tokens and $15 per million output; Sonnet 5.5 costs $2 and $10. For the same text in and out, the relative cost is 1.3 × 2/3 = 0.867, about 13% cheaper, if the 30% holds for your content and the new model writes the same amount of text. Neither condition is known until shadow traffic measures it. The token increase also moves things that are not money: a `max_tokens` tuned on the old tokenizer now admits about 23% fewer characters (1 / 1.3 = 0.77), a context budget fills sooner, and a tokens-per-minute rate limit admits fewer requests.

**The API surface.** Anthropic's API version 2026-10-21 removed `temperature`, `top_p` and `top_k`, which now return a 400 error, and earlier API versions return the same error when they are set to a non-default value on Claude 4.7 and later models. A feature that sends `temperature: 0.2` fails on every request to Sonnet 5.5 until the parameter is removed. The offline gate catches that on its first case, which is the argument for pinning the API version alongside the model id.

**Side effects.** Shadow traffic is free of user impact only if the candidate's tool calls cannot write. An agent that can send an email, issue a refund or open a ticket needs every write tool stubbed in the shadow path, and a stubbed tool returns a result the real one might not, so shadow measures the agent's behaviour up to its first write and less reliably after it.

**Traffic.** The A/B rung's duration is the sample size divided by eligible traffic. The [next lesson](/learn/llmops/releases-experiments/ab-statistics) derives about 8,080 users per arm to detect 70% to 72% task resolution at alpha 0.05 and power 0.8. A feature with a few hundred new users a day cannot finish that test inside a 61-day notice period.

## Pinned ids and rollback triggers

The configuration that the ladder operates on names everything that can change behaviour, so a rollback is a revert of one file and a diff between two releases is readable.

```yaml
# release config for the support assistant; one change per release
release: 2026-11-04-sonnet-5-5
model:
  production: claude-sonnet-4-5-20250929   # retires 2026-11-30
  candidate: claude-sonnet-5-5             # id from the deprecation table
  fallback: claude-sonnet-4-6              # active, retirement not before 2027-02-17
api_version: pinned                        # the version header value, recorded per release
prompt: support-system@v41                 # unchanged in this release
decoding: {max_tokens: 1300}               # was 1000; 30% more tokens per character
assignment: {unit: user, salt: exp-0412}
rollback:
  shadow: "error rate above production + 0.5 pt, or p95 TTFT above 2.0 s, for 1 h"
  canary: "any guardrail outside its margin for 2 consecutive hours"
  ab: "guardrail fails non-inferiority, or sample ratio p < 0.001"
  rollout: "escalation rate above A/B arm B + 1 pt for 1 day"
```

The thresholds above are scenario values; each team writes its own before the rung starts, because a trigger written after the data arrives is a decision, not a trigger. Two rules carry over to every team. The prompt does not change in the same release as the model, because a regression in a release that changes both cannot be attributed, and the rollback of one reverts the other. And the previous configuration stays callable until its own retirement date: for a hosted model that is a config value, for a self-hosted model it means keeping the old weights loaded, because reloading them during an incident is a cold start you chose.

## A worked decision

The case, all scenario apart from the dates and prices: a support assistant runs on `claude-sonnet-4-5-20250929` with `temperature: 0.2`. Today is 28 October 2026; the model retires on 30 November, 33 days away. The feature sees 1,500 new eligible users a day, resolution is 70%, and the product owner's question is whether Sonnet 5.5 is at least as good.

That question fixes the test. A forced migration is a non-inferiority test, not a search for a lift: one-sided alpha 0.05 (z = 1.6449), power 0.8 (z = 0.8416), a margin of 2 points, both arms assumed at 70%. Users per arm: (1.6449 + 0.8416)² × 2 × 0.7 × 0.3 / 0.02² = 6.183 × 0.42 / 0.0004 = 6,492 after rounding up. Both arms: 12,984 users, at 1,500 a day with everyone in the test, 9 days.

The calendar: days 1 to 3, offline gate, which fails on the first case until `temperature` is removed and passes after `max_tokens` is raised. Days 4 to 8, shadow at 20%, which measures the real token ratio and output length. Days 9 to 10, canary at 5%. Days 11 to 19, the A/B test at 50/50. Days 20 to 22, rollout. That leaves 11 days for anything that goes wrong.

The decision to make before day 1 is what happens if the A/B test fails its margin on day 19: there is no time to iterate the prompt and rerun. The written answer here is the fallback. `claude-sonnet-4-6` is active with retirement not before 17 February 2027, costs the same as Sonnet 4.5 and uses the same tokenizer, so a failed test moves production to Sonnet 4.6 for one more ladder, and the Sonnet 5.5 work continues against a February deadline instead of a November one. What the team gives up: Sonnet 4.6 also needs an offline gate and a canary in the same 33 days, so both candidates run through the first two rungs in parallel, at roughly double the shadow cost.

## What to measure after deciding

- Tokens per request, input and output separately, by release, against the shadow week's measurement.
- Cost per resolved task, not per request, because a cheaper model that resolves less can cost more per outcome.
- The share of responses that hit `max_tokens`, which detects the tokenizer change in a truncation metric before users report it.
- Errors by status code by release; a 400 spike after a model change is usually a request parameter, not the model.
- The model id the API reports on each response, logged next to the configured id, so a platform-side alias change is visible.
- Days until the next retirement date of every configured model id, including the fallback, as a dashboard tile with an owner.

## When this is wrong

The ladder assumes the change can be held back. A provider's retirement removes that option on a fixed date, and a security fix to a prompt, such as closing an injection path, should skip the A/B rung entirely: ship after the offline gate and a canary, with the risk written down.

It assumes traffic. A feature with a few hundred users a week cannot power an A/B test on any realistic effect; the offline gate, shadow and a long canary are all it has, and the decision is made on paired offline evidence plus guardrails, stated as such.

It assumes the model id is the whole model. Anthropic's dates apply to its own platforms, and partner platforms set their own; a gateway that routes one id to two platforms has two retirement dates and possibly two behaviours.

Shadow traffic measures a stateless request well and a stateful session badly. In a multi-turn conversation the candidate's turn 3 is generated from production's turns 1 and 2, so shadow measures how the candidate continues the old model's conversation, not how it would have conducted its own.

The cost arithmetic uses Anthropic's stated average token increase. The 30% is approximate and content-dependent, and code, non-English text and structured data can move differently, which is why the shadow measurement replaces it before anyone signs a budget.
