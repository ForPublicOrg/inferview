## The refund that happened twice

Scenario, not a real incident: a support agent built on a graph framework issues a $40 refund, then pauses for a supervisor to approve a goodwill credit in the same step. The supervisor approves an hour later. The framework resumes the step from its beginning, as documented, and the refund runs again. Nothing crashed. Every component did what its docs say.

Agentic design rounds are about this class of bug. The model is one component. The hard parts are the ones you already know from distributed systems: retries, idempotency, durable state, isolation between tenants, and deploys that do not kill work in flight.

## The idea: a job scheduler with an untrusted planner

Model an agent platform as a workflow engine you have used, such as a job queue with durable steps, with one difference: the next step is chosen by a planner whose output you cannot fully trust. Everything that follows from that sentence is design.

The planner proposes tool calls; the executor validates them against policy, applies budgets, and performs side effects exactly once. State lives outside the model in checkpoints keyed by a thread ID, so a crash or a pause resumes rather than restarts. Tool outputs are untrusted input, because a web page, a ticket or an MCP server can contain instructions. And the whole thing is metered, because the cost is driven by how long the planner keeps going.

<Predict id="sys-agents-browsecomp" question="In Anthropic's analysis of its research agent on BrowseComp, token usage by itself explained about what share of the variance in performance?" answer={80} tolerance={15} unit="percent">

That is why the same write-up reports multi-agent systems using about 15 times the tokens of chat. In a design round, treat token budget as a quality knob and a cost line at the same time, and put a cap on it per task.</p>

## Coding agent

A coding agent reads a repository, edits files, runs commands and proposes a change. Three design points carry the round.

**Context is the scarce resource.** A repository does not fit in a window and should not. Anthropic's context-engineering guidance lists the moves: compact the history when it grows, keep structured notes outside the window, send sub-agents to explore with a clean context and return a condensed summary, and load files just in time by path rather than up front. Agent Skills apply the same idea to instructions: only about 100 tokens of metadata per skill is always loaded, the `SKILL.md` body (under 5k tokens) loads when a task triggers it, and bundled scripts run and return only their output.

**The sandbox is the permission system.** Commands run in a container or VM with no credentials it does not need and, ideally, no network. Skills on Anthropic's API run in a container with no network access, and the docs say to use skills only from trusted sources. Treat any repository content as untrusted, because it is written by whoever opened the pull request.

**Repository text is part of the prompt.** GitHub's code-review agent reads custom instructions, `AGENTS.md` and skills from the pull request's head branch. That means the author of the change controls part of the reviewer's instructions. Raise it as a prompt-injection surface: the reviewer's instructions should come from the base branch, and the reviewer's permissions should not let it approve or merge.

## Multi-tenant agent platform

Now host agents for many customers. Isolation comes first: per-tenant credentials for tools, per-tenant storage for checkpoints and memory, and caches that cannot leak across tenants. Provider prompt caches are already separated by organization and workspace. If you self-host on vLLM, prefix reuse across tenants is a timing side channel, and vLLM documents `cache_salt` to scope reuse to one trust group.

Then budgets. A token bucket per tenant (and per session inside it) caps spend, with estimated tokens charged up front and settled after the call. Long-running agents also change deploys: Anthropic's research system uses rainbow deployments, keeping old versions running until their sessions finish, and resumes agents from checkpoints after errors. Hosted harnesses exist now, such as Claude Managed Agents, which keep the session state for you; that convenience has a compliance cost, because a stateful service is not eligible for zero data retention.

## MCP-based knowledge agent

An agent that answers from a company's systems usually reaches them through MCP servers. The current MCP revision is 2026-07-28, which negotiates the protocol version on each request instead of once in a handshake, and deprecated features stay for at least twelve months. For agent-to-agent delegation across organizations, A2A 1.0.0 defines an Agent Card for discovery and a Task with states that include `TASK_STATE_INPUT_REQUIRED` and `TASK_STATE_AUTH_REQUIRED`, which map cleanly onto "ask the user" and "get a token".

The design questions are about trust, not transport. Which servers are allowed, pinned to which versions? Does the agent act with the user's identity or a service account? (Use the user's, so the source system enforces permissions.) And what happens when a tool result says "ignore previous instructions"? Tool output goes into the context as data, side-effecting tools need confirmation, and the allowed tool list for a task is decided by code, not by the model.

## Customer-service agent with policy tools

A prompt from this family, also the question at the end of this lesson, is "design a support agent that follows policy and can refund money". Put policy in code. The agent calls `get_refund_eligibility(order_id)`, which returns the refundable amount and the rule that applied; `issue_refund` rejects anything else with a typed error. The prompt explains the policy so the model asks good questions, but the tool enforces it.

Approvals use the framework's pause. In LangGraph, an `interrupt()` needs a checkpointer and a `thread_id`, and resuming with `Command(resume=...)` runs the whole node again from the start, which is the scenario's double refund. So side effects go after the approval or in a separate node, and every side effect carries an idempotency key derived from the thread and the order. Guardrails need the same care: in the OpenAI Agents SDK, input guardrails run in parallel with the agent by default, so the agent may already have called tools when the tripwire fires. For an agent with side effects, set `run_in_parallel=False`.

## Eval-gated CI/CD for agents

Every prompt, tool or model change runs the eval set before it ships. Start with about twenty real tasks, as Anthropic did, each with a checkable end state (the refund record, the ticket status), and grow it from production failures. Run each task several times and gate on pass^k, not on one run, because a support agent that succeeds six times in eight will fail the customer who tries twice.

```python
from math import comb

def pass_hat_k(tasks, k):
    """tau-bench's pass^k: chance that k fresh trials of a task all succeed, averaged over tasks."""
    return sum(comb(sum(t), k) / comb(len(t), k) for t in tasks) / len(tasks)

# Three tasks, eight trials each: 8, 6 and 4 successes.
tasks = [[True] * 8, [True] * 6 + [False] * 2, [True] * 4 + [False] * 4]
for k in (1, 2, 4, 8):
    print(f"pass^{k} = {pass_hat_k(tasks, k):.3f}")
```

```text
pass^1 = 0.750
pass^2 = 0.583
pass^4 = 0.410
pass^8 = 0.333
```

Same agent, same tasks: 75 percent looks shippable, 33 percent does not. Report both and gate on the one that matches how users retry.

## Computer-use automation

Computer-use agents drive a browser or desktop from screenshots. They are slower and more expensive per step than API tools: Anthropic's computer toolset adds about 4,500 input tokens to every request that declares it, and its browser toolset about 6,600, before any screenshot. Design for that: use an API when one exists, keep computer use for systems that have none, run it in a disposable VM with an allowlist of sites, and require a human confirmation before anything irreversible (submit, pay, delete).

<Fragment slot="long">
<p>Scope: channels, which systems it can touch (orders, refunds, account), refund limits, and who approves above them. I assume chat, a refund ceiling per order, and supervisors approving goodwill credits.</p>
<p>Architecture: a single agent loop with a small tool set (look up order, get refund eligibility, issue refund, hand off to a human) behind an executor that checks every call against policy and per-session budgets. Conversation and tool state live in a checkpoint store keyed by thread.</p>
<p>The refund path is the deep dive. Eligibility comes from code. The agent proposes; the executor checks the amount against eligibility; below the threshold it executes with an idempotency key of thread plus order; above it, the graph interrupts and waits. Because a LangGraph resume re-runs the node from the top, the refund lives in a node after the approval, and the key makes a second call return the first result.</p>
<p>Safety: input guardrails in blocking mode, because in the OpenAI Agents SDK they run in parallel by default and the agent may already have acted; output checks for promises the policy doesn't allow; tool outputs treated as data.</p>
<p>Evals: real tasks with checkable end states (the refund row, the ticket status), run eight times each, gated on pass^k; a dual-control set where the simulated customer also acts, since tau2-bench showed agents drop when users take actions too; online, refund reversal rate and re-contact rate as guardrails.</p>

## When this is wrong

"Job scheduler with an untrusted planner" fits agents that act on systems of record. Research agents that only read and write a report need far less of it: idempotency matters less when nothing irreversible happens, and the cost and context sections matter more. And for many support products a fixed workflow with one model call per step beats an open agent loop on cost, predictability and evals. Say that when the requirements allow it.

The token ratios and the 80 percent figure come from one company's research system on its own tasks. Framework behaviour (node re-runs, parallel guardrails) is quoted from current docs and has changed between versions before, so check the version you deploy.

What I would say in the room: "The model proposes, the executor decides, and every side effect is idempotent because resumes and retries will happen."
