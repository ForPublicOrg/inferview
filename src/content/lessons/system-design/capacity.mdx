## Caching made the bill go up

Scenario, not a real company: a team reads that cached input tokens cost a tenth of the normal price and turns on prompt caching for its support assistant. The next invoice is slightly higher. Nobody changed the traffic. The team had put the customer's name and the current time near the top of the system prompt, so only about one request in five reused a cached prefix, and every miss paid a premium to write the cache.

Capacity questions in AI design rounds are this kind of question. The interviewer is not checking your arithmetic. They want to see whether you know which terms are in the formula, which ones dominate, and which assumption flips the answer.

## A request is a bill of materials

Treat one model call like a parts list. A typical retrieval-backed request has three parts with different prices:

- a **shared prefix** (system prompt, tool definitions, examples) that is identical across requests and can be cached;
- **per-request input** (retrieved chunks, the user's message, conversation history) that changes every time;
- **output**, which is priced several times higher than input.

Toy numbers, used throughout this lesson: 2,000 prefix tokens, 1,500 per-request input tokens, 300 output tokens, at $2 input and $10 output per million (Claude Sonnet 5 list prices, checked 28 Oct 2026). Without caching, one request costs 3,500 × $2 / 1M + 300 × $10 / 1M = $0.007 + $0.003 = $0.01. At a million requests a day that is $10,000 a day. The prefix is 40 percent of it, per-request input 30 percent, output 30 percent.

## Token budgets per request and per user

The per-request number hides three multipliers that bite in production.

**History is re-sent.** A chat API is stateless. Turn *k* of a conversation sends turns 1 to *k*−1 again, so the input of a long chat grows with every turn and the total grows roughly with the square of its length. Server-side conversation features save you the bookkeeping, not the tokens.

**Agents multiply calls.** Every tool round trip is another model call that re-sends the context. Budget per task, not per call, and cap it: maximum steps, maximum tokens, maximum dollars per session.

**Tokens are not portable across models.** Anthropic states that Claude 4.7 and later produce about 30 percent more tokens for the same text, and declaring tools adds a hidden system prompt of 286 tokens on its newest models. A budget measured on last year's model under-counts this year's.

## Latency budgets

Use the vocabulary from NVIDIA's benchmarking docs: **time to first token** (TTFT), **inter-token latency** (ITL, the average gap between output tokens), and end-to-end latency = TTFT + generation time. With a 0.5 s TTFT and 40 ms per token, a 300-token answer takes 0.5 + 300 × 0.04 = 12.5 s end to end.

Streaming changes what the user waits for, not how long the model works. ElevenLabs puts it plainly in its voice-latency post: streaming does not make the model faster, it starts output sooner. So for chat the budget that matters is TTFT; for anything that needs the whole answer before acting (a JSON tool call, a classifier verdict), it is end to end.

When an interviewer gives you "800 ms", treat it as their convention and decompose it across hops: network, auth and state lookup, retrieval, reranking, TTFT, any output check. Retrieval plus reranking can eat half of it before the model starts. The real-time lesson does this for voice, stage by stage. Two levers buy latency directly with money: OpenAI's Fast tier lists at about 2 times Standard, and Anthropic's fast mode on Opus 5.5 lists at $8 in and $40 out against $4 and $20.

## Caching tiers and the break-even hit rate

Three caches show up in designs, and they behave differently.

**Provider prompt cache.** Reuses the computed prefix. On Anthropic a 5-minute cache write costs 1.25 times the input price, a 1-hour write 2 times, and a read 0.1 times on most models (cheaper on the newest). OpenAI added 12-hour caching in October 2026 with writes at 2.5 times input. Minimum prefix sizes apply: 1,024 tokens on Sonnet 5 and on OpenAI's recent models. And the cache key is the bytes, in order: Anthropic's hierarchy is tools, then system, then messages, so a changed tool definition invalidates everything after it.

**Serving-layer prefix cache.** The same idea inside your own vLLM or SGLang deployment. It saves GPU time, not list price.

**Response cache.** Exact-match (hash of the normalized request) is safe. Semantic (nearest neighbour on an embedding) is not: Redis's own docs say a semantic cache gives up the guarantee that a hit is always correct. Scope keys by tenant and model version, and never serve account-specific answers from a shared semantic cache.

The break-even for a provider cache follows from the multipliers. A miss pays the write price, a hit pays the read price, and caching wins when the blend is below 1: hit rate × 0.1 + (1 − hit rate) × 1.25 under 1, which solves to a hit rate above about 21.7 percent.

## Throughput to GPU count

If you self-host, the binding constraint is usually memory for the KV cache, not FLOPS. Each token in flight stores a key and a value per layer per KV head. For Llama 3.1 70B (80 layers, 8 KV heads, head dimension 128) in BF16 that is 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes, 320 KiB per token, so one 8,192-token sequence holds 2.5 GiB.

On an 8 × 80 GB node, keep 10 percent back for activations and fragmentation and subtract 140 GB of BF16 weights: 436 GB is left, enough for 162 sequences at the full 8,192 tokens. Little's law turns traffic into demand: requests in flight = arrival rate × time in system. A million requests a day with a peak three times the average is 34.7 requests per second; at 12.5 s each, 434 are in flight at peak. Planning each node at 70 percent of its KV-limited concurrency gives 434 / 113 = 3.8, so four nodes.

<Callout kind="gotcha">
Two traps in the GPU math. NVIDIA's 1,979 TFLOPS BF16 figure for the H100 is marked "with sparsity"; dense is half. And decode is usually limited by memory bandwidth (3.35 TB/s on the H100 SXM), so peak FLOPS says little about tokens per second. Size KV heads, not attention heads: Llama 3.1 70B has 64 attention heads but 8 KV heads, and using 64 overstates the cache eightfold.
</Callout>

```python
import math

def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per_value=2):
    return 2 * layers * kv_heads * head_dim * bytes_per_value   # keys and values

# Llama 3.1 70B config.json: 80 layers, 8 KV heads, head dim 8192 / 64 = 128.
per_tok = kv_bytes_per_token(80, 8, 128)
ctx = 8192                                   # worst-case tokens per sequence
free_for_kv = 8 * 80e9 * 0.9 - 70e9 * 2      # 8 x 80 GB, 10% reserve, BF16 weights
per_node = int(free_for_kv // (per_tok * ctx))

# Little's law: requests in flight = arrival rate x time in system.
peak_rps = 1_000_000 / 86_400 * 3            # peak-to-average 3 is an assumption
latency_s = 0.5 + 300 * 0.040                # TTFT + 300 tokens at 40 ms each
in_flight = peak_rps * latency_s
nodes = math.ceil(in_flight / (per_node * 0.7))

print(f"KV per token {per_tok:,} bytes; {per_node} sequences of {ctx} per node")
print(f"peak {peak_rps:.1f} rps x {latency_s} s = {in_flight:.0f} in flight; nodes at 70%: {nodes}")
```

```text
KV per token 327,680 bytes; 162 sequences of 8192 per node
peak 34.7 rps x 12.5 s = 434 in flight; nodes at 70%: 4
```

The 40 ms per token is something you measure on your hardware at your batch size; it gets worse as concurrency rises, which is why the plan stops at 70 percent.

## Rate limits are capacity too

On a hosted API, the provider's limits are your fleet size. Anthropic enforces requests, input tokens and output tokens per minute separately, as token buckets, so a limit of 60 a minute can behave like one a second. Only uncached input counts toward the input-token limit on most models: its own worked example processes 10,000,000 input tokens a minute under a 2,000,000 limit at an 80 percent hit rate. Caching raises throughput as well as cutting cost, and a prompt change that breaks the cache can push you into 429s at the same traffic.

## When this is wrong

The bill-of-materials model assumes the provider bills each request independently. Batch APIs, committed-use discounts, long-context surcharges (OpenAI roughly doubles input above 272K tokens, while Anthropic bills its 1M window at standard rates on recent models) and regional uplifts all change the formula, so read the current price page before you trust a spreadsheet.

The GPU math sizes every sequence at its worst case. Real sequences are shorter on average, PagedAttention-style allocators do not reserve the full context, and prefix sharing lets many sequences share one copy of the system prompt, so the true capacity of a node is usually higher than 162. The inference track covers that. Little's law needs a stable system: if requests arrive faster than you serve them, the queue grows without bound and no replica count from this formula is enough.

What I would say in the room: "Prices are inputs, the formula has three terms, and I'd check which one dominates before I pick a lever."
