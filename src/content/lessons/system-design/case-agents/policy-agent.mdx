## Where the refund limit lives

The first decision in a support agent that can move money is where the limit is enforced. The answer is a tool the model cannot argue with. The prompt describes the policy so the model asks the right questions (which order, what went wrong, when it arrived); the executor enforces it. `get_refund_eligibility(order_id)` returns the refundable amount and the rule that produced it, and `issue_refund(order_id, amount, key)` rejects any amount above that figure with a typed error the model can read. A customer who talks the model into wanting a larger refund changes what the model asks for, not what the executor allows.

Three more decisions follow from that one: what pauses for a person, what the person receives when the agent gives up, and how you know the agent follows policy before it reaches customers. The rest of this lesson takes them in order, then turns to the event that tests all four: a model upgrade that changes how often the agent escalates.

## Risk tiers come from the tool, not the conversation

OpenAI's agent-building guide asks for a low, medium or high rating on every tool, based on read-only versus write access, reversibility, the permissions the tool needs and its financial impact, and for the rating to decide what runs automatically. It names two triggers for a human: exceeding a failure threshold (the agent cannot work out the intent after several attempts) and high-risk actions, with authorizing large refunds as its example. Translated into a support product:

| Tier | Examples | What the executor does |
|---|---|---|
| Read | look up order, explain a charge, track a parcel | runs |
| Reversible write | resend a receipt, reset a password, change a delivery slot | runs, logged |
| Money within policy | refund up to the eligible amount | runs with an idempotency key |
| Out of policy | goodwill credit, refund above eligibility, refund on a closed order | pauses for approval |
| Irreversible account change | close account, merge accounts | hands off |

The tier belongs to the call with its arguments, not to the tool name. A refund of the eligible amount and a refund twice that size go through the same function and land in different rows. That is why the eligibility check sits in the executor and not in a guardrail model reading the conversation: it compares two numbers from systems of record.

## Approvals are a pause in a durable workflow

An out-of-policy request becomes a proposed action with its evidence (order, eligibility result, the rule that blocked it, the customer's stated reason) written to a durable store, and the run waits. Supervisors approve in a console; approval can take hours, so the conversation tells the customer the request is pending and the session can end.

Two framework behaviours decide whether the resumed run is safe. LangGraph's interrupts need a checkpointer and a thread ID, and on resume the node restarts from its beginning, so any code before the interrupt runs again. A refund placed before the interrupt in the same node runs twice. The documented fix is to put side effects after the interrupt or in their own node. The OpenAI Agents SDK states the general rule: approval permits a call, it does not guarantee the call executes once. Each logical action gets a stable idempotency key, for example a hash of thread, order and action, written down before the call and reused on every retry.

Guardrails need the same reading. In the OpenAI Agents SDK, input guardrails run concurrently with the agent by default and only for the first agent in a chain, so a tool can already have been called when a tripwire fires. For an agent with money-moving tools, set `run_in_parallel=False` on the input guardrails, and put tool guardrails on the refund and credit tools themselves, which run on every guarded call. Tool guardrails do not cover handoffs, so the handoff path needs its own check if a handoff can carry an action.

## The handoff is a product, not a failure path

A handoff that makes the human re-ask everything costs more than no agent. The payload is the same shape as an approval request: a summary, the verified identity, the eligibility result, what the agent tried, the rule that stopped it, and a proposed resolution. Handoffs carry a reason code from a fixed list (policy requires a person, failure threshold, customer asked, model chose to stop) so the escalation rate can be read by cause later. Without the reason code, the next section's problem has no answer.

## Evaluation by end state over repeated trials

tau-bench built the evaluation shape for this product: a simulated user with a hidden goal, a policy document, domain tools over a database, and success judged by comparing the database's end state with the annotated goal state. Grading the end state matters because the transcript can sound right while the wrong refund lands, and the right refund can follow an awkward conversation. Anthropic's eval guidance says the same: grade the outcome, not the path, start each trial from a clean environment, and start with 20 to 50 tasks drawn from real failures.

The paper's headline is about consistency. It reports that function-calling agents such as gpt-4o succeed on under half the tasks, and that pass^8 in the retail domain is under 25 percent. pass^k is the chance that k independent trials of the same task all succeed; a customer who contacts support twice meets the agent twice. The unbiased estimator from n trials with c successes is C(c, k) / C(n, k), averaged over tasks:

```python
from math import comb

def pass_hat_k(results, k):
    """results: one list of booleans per task, n trials each; returns tau-bench's pass^k."""
    return sum(comb(sum(r), k) / comb(len(r), k) for r in results) / len(results)

# Three tasks, eight trials each: 8, 6 and 4 successes.
tasks = [[True] * 8, [True] * 6 + [False] * 2, [True] * 4 + [False] * 4]
for k in (1, 2, 4, 8):
    print(f"pass^{k} = {pass_hat_k(tasks, k):.3f}")
```

```text
pass^1 = 0.750
pass^2 = 0.583
pass^4 = 0.410
pass^8 = 0.333
```

The same agent on the same tasks reads as 75 percent or 33 percent depending on k. Pick k from how often customers come back about the same issue, and report both.

tau2-bench adds the case most support products actually have: the user also acts. In its telecom domain the simulated customer toggles settings and reboots devices on the agent's instruction, and the paper reports significant drops when agents move from settings where they act alone to this dual-control setting, with errors split into reasoning and coordination. If your customers change their own plan, card or address mid-conversation, a no-user eval overstates what ships.

## The model upgrade that changes the escalation rate

The provider announces a retirement. Anthropic gives at least 60 days' notice for publicly released models, so the migration has a deadline whether or not the new model is better. You run the eval set on the candidate, and the end-state pass rate holds, but in a shadow run the escalation rate doubles.

<Predict id="sys-case-agents-escalation-hours" question="Scenario: 20,000 conversations a day, escalation rate 6% on the old model and 12% on the new one, 9 minutes of human time per escalation. How many extra human hours per day does the upgrade cost?" answer={180} tolerance={5} unit="hours">
<p>20,000 × 0.06 = 1,200 escalations today; 20,000 × 0.12 = 2,400 after. The extra 1,200 escalations at 9 minutes each are 10,800 minutes, or <b>180 hours</b> a day: about 22 eight-hour shifts that the support team did not plan for. Whether that cost is a regression or a fix depends on which escalations grew, which is the next paragraph.</p>
</Predict>

The total rate cannot tell you whether to ship. Split it by reason code and compare against what the policy requires:

- **Policy-required escalations grew.** The new model is catching out-of-policy requests the old one resolved, which may mean the old model was issuing refunds the executor should have blocked; check the executor's rejection logs before calling it a regression.
- **Failure-threshold escalations grew.** The new model is worse at intent or tool use on some intents; the eval set should show it per intent, and if it does not, the set is missing those intents.
- **Model-chose escalations grew.** The model is more cautious than policy requires. This is the cheapest to fix (instructions that say which requests are in policy, examples from the eval set) and the most tempting to fix badly, by telling the model to escalate less in general.

Two errors trade against each other: escalating something the agent could resolve costs human time; resolving something that needed a person costs money or trust. The eval set needs tasks where the correct end state is a handoff, scored like any other end state, or a model that never escalates looks perfect.

## When this is wrong

Policy in code assumes the policy can be written as a function of order data. Goodwill credits, fraud suspicion and complaints about tone are judgement calls; for those the executor can only enforce a ceiling and an approval, and the eval needs human-graded cases.

An agent loop is not always the right shape. If most contacts fall into a few intents with fixed steps, a workflow with one model call per step for classification and wording is cheaper, easier to evaluate and easier to explain to an auditor. OpenAI's guide recommends getting the most out of a single agent before splitting into many; the step before that is asking whether the product needs an agent at all.

tau-bench's users are simulated by a model, and pass^k assumes independent trials. Real customers who come back after a failure are not independent of the first attempt: they arrive angrier and with a different story. Treat pass^k as a lower bound on how inconsistent the agent is, not as a forecast of re-contact.
