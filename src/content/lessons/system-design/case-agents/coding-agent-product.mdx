## The shape of the product

A hosted coding agent takes a task (an issue, a comment, an API call), runs a model-driven loop against a copy of a repository, and returns a change for review. It is a job system: a queue, workers, a session record, logs, a result. The difference from a CI runner is the planner. A CI job runs a script someone reviewed; the agent's next command is chosen by a model that has read the issue, the repository and whatever its tools fetched, any of which can carry instructions. Every design decision below follows from treating that planner as untrusted while still letting it do useful work.

Six components carry the design: the trigger and who may pull it, the session and its limits, the sandbox, the credentials, the egress path, and the review path into the default branch. GitHub's Copilot cloud agent (GitHub's current name for what it used to call its coding agent) publishes enough of its limits to serve as a reference design, and Anthropic's account of containing Claude publishes the failures that the reference design's gaps allow.

## Trigger: who can start a job, and whose text the agent reads

GitHub lets only users with write access trigger the agent, and comments from users without write access are never shown to it. The first rule protects compute; the second is an injection control, because issue and comment text goes straight into the prompt. GitHub also strips hidden characters before the text reaches the model; an HTML comment in an issue, invisible on the rendered page, is not passed through.

The gap is the repository itself. The agent reads README files, configuration and code written by anyone whose pull request was ever merged, and dependencies written by strangers. Anthropic reports three vulnerabilities, fixed by January 2026, in which a hook in a cloned repository's `.claude/settings.json` ran at startup, before the "do you trust this folder" prompt. The fix was ordering: project configuration is not parsed or executed until the user accepts trust. The product rule is the same for a hosted agent: repository-controlled configuration that can run code (setup scripts, hooks, task files) runs only after a decision about whose repository this is, and never with credentials beyond the session's.

## Session: one branch, one pull request, a time cap

GitHub's agent works on one branch at a time and opens one pull request per task. A session on GitHub Actions changes only the repository it was started in and stops at 59 minutes, a cap the docs say cannot be extended; cloud sandbox sessions can span repositories in one organization. These limits bound the blast radius of a session the same way a job timeout and a working-directory scope bound a CI job, and they also bound the product: a task that needs two hours or three repositories is out of scope, and the product has to say so before it starts, not at minute 59.

## Sandbox: isolation strength matched to oversight

Anthropic describes three containment patterns: a gVisor container on isolated servers for claude.ai code execution; an OS-level sandbox for Claude Code (Seatbelt on macOS, bubblewrap on Linux) that allows writes inside the workspace and denies network by default; and a full VM for Cowork with only the selected folders mounted. The principle it states is to match isolation strength to how much oversight the user can give. A hosted agent that runs unattended for up to an hour gets the strongest boundary you can operate: a VM or a gVisor-class sandbox per session, an ephemeral filesystem, nothing shared between sessions.

The approval numbers explain why an unattended product cannot lean on prompts. Anthropic reports that users approved about 93 percent of Claude Code's permission prompts, and that the sandbox cut prompts by 84 percent. A control that is approved almost every time is not a control; a boundary that holds without asking is.

## Credentials: the agent never holds the push token

GitHub's agent cannot run `git push` or other Git commands directly; it performs simple push operations through a path the platform controls, and only to its one branch. Anthropic's Cowork keeps credentials in the host keychain and never inside the guest, and issues each session a scoped token that can be revoked without touching the user's own. The design is a broker: the sandbox holds a session token that means "this session may push to branch X of repository Y until time T", and the broker holds the real credential. A prompt-injected agent can misuse the session token only within that scope, and revoking a session does not log anyone out.

## Egress: an allowlist is a list of capabilities

The agent needs the network to install dependencies, and every reachable host is a place data can go. GitHub's firewall has a recommended allowlist on by default (package registries, container registries, certificate authorities). Its documented scope is narrower than most readers assume: it applies only to processes started through the agent's Bash tool, not directly to MCP server processes or to setup steps, and the docs warn that sophisticated attacks may bypass it.

Anthropic's incidents show why the destination list is the wrong mental model. In a red-team exercise, a phished employee ran a prompt that told Claude to read `~/.aws/credentials` and post them out; the model complied in 24 of 25 attempts, and what held was the egress and filesystem boundary. In a third-party disclosure, a malicious file carried hidden instructions and an attacker's API key, and the agent uploaded workspace files to the attacker's account through the Files API on `api.anthropic.com`, a domain on the allowlist. Anthropic's phrasing is that allowlists act as capability grants: every function reachable through an allowed domain is attack surface. The fix was a proxy that forwards only requests carrying the VM's own session token. For a coding agent, the same reasoning applies to package registries: a registry that accepts downloads also accepts uploads with someone's token, so the egress proxy allows the read methods and paths the build needs and nothing else.

## Verification and the review path

The change is the product, and nobody should have to trust it. GitHub runs CodeQL, checks new dependencies against its advisory database for malware and high or critical vulnerabilities, and runs secret scanning on the agent's changes, with the analysis recorded in the session log. Then the review path:

- The agent opens a draft pull request and cannot mark it ready, approve it or merge it.
- The person who requested the change cannot approve it, so required-approval rules still mean a second person.
- Actions workflows on the agent's branch do not run until a user with write access approves them, which keeps repository secrets in CI away from code the agent wrote.
- Commits are signed, authored by the agent with the requester as co-author, and link to the session log.

The requester rule is the subtle one. Without it, a developer delegates the change and then approves it, and the second pair of eyes that branch protection was meant to guarantee becomes the same pair. The workflow rule is the other one teams disable first, because waiting for a click is slow; disabling it hands the agent's branch the CI secrets.

## The security review, as a table

The review the reader of this lesson would write lists entry points, what the planner can do from each, and the control that holds when the model does not:

| Entry point | Example | Control that does not depend on the model |
|---|---|---|
| Task text | issue body with hidden instructions | write-access trigger, hidden-character filter |
| Repository content | setup hook, poisoned README | no repository-controlled execution before trust; sandbox |
| Dependencies | install script in a package | sandbox, egress proxy, no credentials in the guest |
| Tool servers | MCP server with network access | runs inside the egress proxy, not beside it |
| Output | change that weakens auth or leaks a secret | CodeQL, secret scanning, human review, requester cannot approve |
| CI | workflow on the agent branch reading secrets | workflow approval by a write-access user |

The MCP row is where GitHub's published firewall scope leaves a gap that the product owner has to close, by running tool servers inside the same egress path or by allowing only servers that need no network.

## When this is wrong

The model of a hosted job system fits agents that run unattended on shared infrastructure. A developer running an agent in a local terminal is supervising it, and Anthropic's own pattern there is a lighter OS sandbox plus prompts; building a VM fleet for that use case buys little. The opposite error is also common: treating a local, supervised tool's controls as sufficient when the same agent is moved into CI with no one watching.

GitHub's product names, environments and limits changed during 2026 (the 59-minute cap applies to GitHub Actions sessions, and cloud sandbox sessions have different scope), and Anthropic's figures are its own measurements on its own users. Check the version and date of every limit you design against.

The review path assumes reviewers read the change. A team that approves agent pull requests at the rate users approve permission prompts has rebuilt approval fatigue one level up, and the controls above it are all that is left.
