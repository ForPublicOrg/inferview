## The product decision is the task list

A computer-use agent drives a browser or desktop from screenshots: look, decide, click or type, look again. It is the integration of last resort, the screen-scraper with a model in the loop, and it inherits screen-scraping's properties: each step is slow, layouts change under it, and it reads whatever the page shows, including text written by people who want it to do something else. Better models move the numbers but not the shape.

So the central design decision is not the agent loop. It is which customer tasks the product accepts, which actions inside an accepted task need a person, and how a run that fails at step 23 is checked and resumed. The rest of this lesson builds the criteria for that decision from three sets of published facts: what each step costs, how often the agent fails, and how often injected instructions succeed.

## What a step costs

Anthropic's pricing page gives the fixed overhead: declaring `computer_toolset_20260801` adds about 4,500 input tokens to every request, and `browser_toolset_20260801` about 6,600, before any screenshot. Screenshots are billed as image input, and Claude counts images in 28-pixel patches, so a 1920×1080 screenshot is ⌈1920/28⌉ × ⌈1080/28⌉ = 69 × 39 = 2,691 visual tokens on the high-resolution tier of Claude 4.7 and later models. Image-token counts are per model family; OpenAI and Gemini count differently, so every figure here is Claude's.

The arithmetic gives the first criterion. A task that has an API costs one call; the same task through the screen costs dozens of image-laden requests and minutes of wall time. The product uses an API when one exists, uses computer use only for systems that have none, and quotes customers a price per task that depends on step count.

## How often it fails

OSWorld, published in 2024, ran 369 tasks in real operating-system environments and reported humans completing over 72.36 percent against 12.24 percent for the best model, which failed mainly on GUI grounding (clicking the right element) and operational knowledge (knowing how the application works). It is a 2024 baseline, not a current score; what carries forward is the failure classes, because they decide where to put checks. Grounding errors produce a plausible action on the wrong element. Knowledge errors produce a confident path through the wrong menu. Neither announces itself.

The second criterion follows: the product accepts a task only if the end state can be checked without trusting the agent's own account of it. For data entry into a system the customer owns, the check is a read through that system's API or database. For a form on a third-party site, the check is a confirmation number captured from the page and verified later, or a person.

## How often injection succeeds

Every page the agent reads is input. Anthropic's browser-use measurement used an internal adaptive attacker trying 100 attempts per environment and reports, as its own figures, an attack success rate of 1.4 percent for Claude Opus 4.5 with its improved safeguards, against 8.0 percent for the model alone. The same page says 1 percent still represents meaningful risk and that no browser agent is immune. Anthropic's containment post adds a second shape for a later model: about 0.1 percent on single attempts and about 5 to 6 percent after 100 adaptive attempts on Gray Swan's agent red-teaming benchmark.

Read those numbers as the vendor's measurements under the vendor's attacker. Their use in design is directional: the per-attempt rate is small, a patient attacker gets many attempts, and the product sees every page on every task. The third criterion: a task is accepted only if a successful injection on any page it visits cannot cause an action the product cannot reverse or a disclosure the customer cannot accept.

## The controls OpenAI shipped

ChatGPT agent's launch post (July 2025, now marked by OpenAI as outdated) lists a set of controls that map onto those criteria:

- **Explicit confirmation** before actions with real-world consequences, with a purchase as the example.
- **Watch Mode**: certain critical tasks, such as sending email, require the user's active oversight with the tab in view.
- **Refusal** of high-risk tasks, with bank transfers named.
- **Takeover mode**: the user types credentials into the browser directly, and OpenAI says it does not collect what is entered.
- **Session hygiene**: one click deletes browsing data and logs out of every site.
- **Injection defences**: training to resist injected instructions plus monitoring, and the user can pause or take over at any point.

Each control removes a class of task from fully autonomous operation rather than making the agent better at it. That is the pattern to copy for a product that runs for customers rather than for the person watching. One difference: in a back-office product there is often no user watching, so Watch Mode becomes a queue of pending actions approved by a person who sees the action itself (the form fields and the destination), not the agent's summary of it.

## Turning criteria into an intake decision

Scenario: an insurer wants an automation product for its claims operations team. Five candidate tasks, sorted by the three criteria:

| Task | API exists? | End state checkable? | Worst case under injection | Decision |
|---|---|---|---|---|
| Copy claim data from a legacy portal into the claims system | no for the portal | yes, read back from the claims system | wrong data in a record a person reviews | take |
| Download repair estimates from repairer portals | no | yes, file present and parsed | malware in a download | take, files scanned outside the session |
| Submit a claim form on a government portal | no | partly, confirmation number | wrong submission in the insured's name | take with per-submission approval |
| Pay repairers through the bank's portal | the bank has an API | yes | money sent to an attacker | refuse; use the bank's API with its own controls |
| Reply to policyholder emails | yes | no | data disclosed to the wrong person | not a computer-use task |

The refusal is the row people argue with. The bank portal is technically within reach, and the customer asks for it because the API integration is a project. The answer is the cost asymmetry: payments are the action OpenAI's own product refuses, and the API path has controls (payee allowlists, dual authorisation) that a screen-driving agent bypasses by construction.

## Recovering from failure

A 40-step run fails often enough that recovery is a feature. The session is checkpointed per step with the screenshot and the action. On failure the run classifies the last action the way a durable workflow classifies an in-flight tool call: read-only steps replay; a form submission is checked first (is there a confirmation page, a record, an email?) and only resubmitted when the check says it did not happen; anything that cannot be checked goes to a person. A human takeover is a resume path, not an abort: the operator finishes the step in the same browser session and hands control back.

Each session runs in a disposable VM or container with only the sites the task needs allowed, credentials injected per task through takeover or a vault the agent cannot read back, and the browser profile destroyed after the run.

<p>Two defensible answers for the ERP form. Full automation with a post-hoc audit: fastest, and the cost is that a fraudulent vendor's bank details sit in the master data until the audit, with the first payment possibly already sent. Draft plus approval of the bank fields only: one human step per vendor, and the agent still does the typing for every other field. I choose the second, because the failure it prevents is irreversible and the control is narrow.</p>

## When this is wrong

The criteria assume the customer can say what each task's worst case is. Some cannot, and the honest product response is a pilot on read-only tasks while the worst cases are mapped.

The injection and failure numbers here are vendor measurements and a 2024 benchmark. They decide the direction of the design, not its thresholds; a product that sets an approval threshold from a vendor's attack-success rate is treating a lab number as a production one. Measure your own completion and intervention rates per task type in the pilot.

Finally, computer use is sometimes chosen because an API project is politically hard, not technically missing. When the API exists, the right design is often to fund the integration and keep the agent for the systems that truly have no other way in.
