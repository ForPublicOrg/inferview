## The specification, from two job descriptions

Staff job descriptions are the most precise public statement of what these platforms must do. Decagon's Agent Platform role defines the agent harness as "the routing, execution logic, tool orchestration, and control-plane systems" that decide how an agent behaves in a live conversation, owned across the whole execution lifecycle: selecting workflows, orchestrating several models in router, planner and supervisor patterns, coordinating tool calls, enforcing safety constraints and replying to the user. The same team runs real-time voice with strict latency and longer-horizon work, and improves both through offline evaluation and online A/B tests.

Perplexity's Enterprise Agent Evals and Efficiency role names the metrics and the gate. Its outcomes are task success, latency and "cost per successful task", and it asks for "regression gates and launch-readiness signals for model, connector, tool, skill, and harness changes". Its evaluation environments include user roles, permissions and reproducible system state, and its graders are calibrated against human judgement.

Put together, the design brief is: many tenants run agents on one shared runtime; five kinds of change reach those agents; each change must be gated before it reaches customers; and the gate measures success, latency and cost per successful task together.

## The control plane: an agent run is a pure function of versioned inputs

The core decision is to make every input to an agent run an immutable, versioned artefact, and to record the full set of versions on every run. Treat it like a build: a run's output depends on a manifest, and two runs with the same manifest differ only by sampling.

The manifest for one conversation has these entries:

| Input | Owner | Who it affects when it changes |
| --- | --- | --- |
| Harness version (loop, routing, retries, context assembly) | Platform team | Every tenant |
| Model and effort per role (router, planner, executor) | Platform team, sometimes tenant | Every tenant on that route |
| Tool and connector versions (schema, description, result handling) | Connector owner | Tenants using that connector |
| Skills and shared instructions | Platform or tenant | Tenants loading them |
| Tenant workflow and policy configuration | Tenant | One tenant |

The table is the gating policy. A tenant's workflow edit has a blast radius of one tenant and can be gated by that tenant's own scenarios. A harness change has a blast radius of every tenant at once, and it is the change Anthropic's eval guide warns about: evaluating an agent evaluates the harness and model together, so a harness change can regress behaviour that no tenant changed and no connector owner can see.

The data plane is the runtime from the previous lesson: stateless harness workers, sessions as logs, sandboxes and tool proxies. What the control plane adds is resolution. When a conversation starts, the control plane resolves the tenant's pinned manifest, writes it as the session's first event, and every later event refers to it. A conversation never changes manifest midway, so a rollout that flips a harness version mid-conversation cannot produce a run that matches neither version's eval results.

## The gate per change class

**Offline, per change.** Each change class has a suite. Regression suites sit near 100 percent and exist to catch backsliding; capability suites start low and measure improvement. Anthropic's guide recommends graduating capability tasks that saturate into the regression suite. Each task runs from a clean environment, because shared state between trials produces correlated failures or inflated scores; Anthropic saw a model read the git history left by earlier trials.

Agents are stochastic, so the gate runs each task several times and reports two numbers: pass@k, the chance at least one of k trials succeeds, and pass^k, the chance all k succeed. A customer-facing agent that handles the same intent thousands of times a day lives on pass^k. Anthropic's worked example: 75 percent per-trial success over 3 trials gives 0.75³, about 42 percent.

**Online, per tenant ring.** Changes that pass offline roll out by tenant ring: internal tenants, then tenants who opted into early versions, then the rest. Within a ring, conversations are assigned by stable hash, and the comparison is the A/B test the Decagon role describes. The metrics are task success from the outcome (the ticket state, the refund row), latency per channel, and cost per successful task.

**Why cost per successful task, not pass rate and cost separately.** A change can raise success and still lose money, and a cheaper change can be more expensive per outcome.

$0.55 / 0.84 = $0.655, against $0.50 / 0.80 = $0.625 today. The change is better for customers and about 5 percent worse per outcome. Whether to ship is a business decision, which is why the gate reports the two numbers together and the launch decision states which one it trades.
</Predict>

**How big a regression the gate can see.** The offline suite is a sample. With 200 tasks at an 80 percent pass rate, the standard error of the pass rate is √(0.8 × 0.2 / 200) ≈ 0.028, so a 2-point drop sits inside one standard error of noise. Two things shrink it without buying more tasks. Pairing: compare old and new on the same tasks and analyse per-task differences, which removes task difficulty from the variance. Repeats: running each task k times averages out sampling noise inside each task. A gate whose thresholds are smaller than its measurement error blocks good changes at random and passes bad ones at random.

## Multi-tenancy inside the runtime

Tenants share workers, model quota and connectors, so isolation is a runtime property as well as a data property.

- **Quota.** Model rate limits are per provider account, and one tenant's batch job can exhaust them for everyone. The runtime enforces per-tenant concurrency and token budgets ahead of the provider's limits, and reserves headroom for latency-critical channels.
- **Channels.** Voice and chat share the harness code but not a latency budget. A planner step that costs a second is acceptable in an email workflow and breaks a voice turn. Routing policy is therefore per channel: the router picks model and effort per role from the channel's budget, and the gate measures latency per channel, not overall.
- **Data.** Each run's manifest names the tenant; tool proxies check that every credential and data source a run touches belongs to that tenant. Tenant-supplied skills and instructions are data for that tenant's runs only and never enter the shared prompt prefix.
- **Pinning.** Each tenant pins a manifest. The platform moves tenants forward by ring and keeps the previous harness version deployable until the last pinned tenant moves, so a rollback is a pin change, not a redeploy.

## Where the gate fails

Offline suites miss what they do not contain. Anthropic's guide describes Qodo underestimating a model because its one-shot evals missed gains on longer tasks. The platform equivalent is a harness change that helps long conversations and hurts short ones, measured on a suite of short ones. The defence is to sample tasks from production traffic by length and channel, and to refresh the sample on a schedule.

Online tests are slow for rare intents. A tenant whose refunds are a small share of traffic accumulates refund conversations slowly, and a ring-based rollout can reach full traffic before a refund regression is visible. For high-consequence intents, the gate needs a dedicated offline set with enough repeats, and the rollout plan states which intents were not measurable online.

"You own the agent platform for 300 enterprise tenants on one harness. A harness change improves long-horizon workflows in offline evals, the voice team says it adds latency they cannot absorb, and the quarterly release is in two weeks. How do you gate it?"
</Callout>

<Depth>
<Fragment slot="short">
<p>Make the change a new harness version, not an edit, and record the version on every run. Gate it offline on the regression suite with repeats and paired comparison, reporting success, pass^k, latency per channel and cost per successful task. If voice latency regresses, ship it for non-voice channels only, by routing on channel, and roll out by tenant ring with the old version pinned for rollback. What I give up is one harness for every channel: two versions in production until voice is fixed.</p>
</Fragment>
<Fragment slot="long">
<p>The conflict is a measured improvement for one workload against a latency regression for another, under a deadline. Two defensible answers. One: hold the change until it is fast enough for voice, keeping one harness version and one gate, at the cost of a quarter's improvement for long-horizon tenants. Two: ship it per channel, which delivers the improvement now but doubles the versions to test, operate and reason about during incidents, and risks drift if voice never catches up.</p>
<p>I would take the second with an expiry. The written artefact is a rollout plan: rings (internal tenants, early-access tenants, then everyone), the metrics read at each ring (success, cost per successful task, p95 latency per channel), rollback triggers stated as numbers the team agrees on before the first ring, and a date by which the voice path either adopts the new harness or the split is reviewed.</p>
<p>The failure mode of this answer: per-channel routing is now part of the manifest, so a tenant whose workflow spans chat and voice gets two harness versions in one customer journey. Hand-off state between them must be version-independent, and the gate needs a cross-channel scenario that it did not need before.</p>

## When this is wrong

Versioned manifests and tenant rings pay off with many tenants on one runtime. With five large tenants, each with its own engineers, a per-tenant deployment is simpler and the gate is that tenant's acceptance test.

Cost per successful task assumes success is observable. For open-ended work (drafting, research) the outcome is a judgement, and the metric inherits every error of the grader that decides success. In that case the grader's own agreement with human labels belongs on the release report next to the metric.

The job descriptions describe what two companies hire for, not how their systems are built. The design here is one way to meet that specification, not a description of Decagon's or Perplexity's internals, which are not public.
