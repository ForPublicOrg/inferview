## Three parts, each with an owner

An AI design that ends at the model call is missing the three parts that decide whether it can ship: the evidence before launch, the measurement after launch, and what happens when the model is wrong. Each needs an owner and a number. Without the first, nobody can say whether a prompt change helped; without the second, the first is never checked against users; without the third, a wrong answer has nowhere to go but the customer.

## Before launch: a small set that grows from failures

Anthropic's guidance on agent evals is direct about size: "20-50 simple tasks drawn from real failures is a great start". The reason a small set works early is that early changes have large effects, and the reason it must grow is that later changes have small ones. Every failure triaged after launch becomes a case.

The same guidance splits the set by purpose. Capability evals ask what the system can do and should start at a low pass rate, so there is room to see progress. Regression evals ask whether it still does what it used to and should sit near 100%, so a drop is a signal rather than noise. A capability case that passes reliably graduates into the regression set. The split matters in a design because the two sets gate different things: regressions block a release, capability scores inform a roadmap.

Graders come in three kinds, each with a cost. Code checks are cheap, reproducible and brittle to valid variation: a regex on the refund amount, a check that every citation was in the retrieved set. Model graders handle nuance and need calibration against human labels before anyone trusts them. Human graders are the reference and the bottleneck. A design uses code wherever the property is checkable by lookup, a model grader where it is not, and humans to calibrate the model grader.

One rule from the guidance catches a common design gap: test where a behaviour should not occur as well as where it should. A support assistant evaluated only on questions it should answer will learn, through prompt iteration, to answer everything, including the questions it should hand off. The eval set for a design with a fallback includes cases whose correct outcome is the handoff.

## Before launch: repeated trials and pass^k

A single run per case measures whether the system can succeed. Users experience whether it succeeds every time. tau-bench introduced pass^k for this: run each task n times, count c successes, estimate the chance that k independent trials all succeed as C(c, k) / C(n, k), and average over tasks. pass@k, the code-generation metric, asks the opposite question: whether at least one of k trials succeeds.

<p>0.9<sup>8</sup> = <b>0.430</b>, about 43%. A system that is right nine times in ten on each task gets all eight trials right on fewer than half of them. At 0.95 per trial pass^8 is 66%; at 0.99 it is 92%. Anthropic's guidance gives the same shape with 0.75<sup>3</sup> ≈ 42%.</p>
</Predict>

The published numbers have that shape. The tau-bench paper reports gpt-4o at pass^1 of 61.2% in its retail domain and pass^8 below 25%. tau2-bench added a dual-control setting, where the simulated user also changes state with tools, the way a customer toggles a setting while the agent troubleshoots. The paper reports telecom pass^1 of 34% for gpt-4.1 and 42% for o4-mini, drops of 18 and 25 points from the setting where the agent acts alone. For a support design the dual-control case is the normal one: the customer is doing things while the assistant talks.

In a design, pass^k sets the trial count and the cost of the pre-launch run. Fifty tasks at eight trials is 400 runs per candidate change. If that is too slow for every prompt edit, the plan runs one trial per task on every change and the full k on release candidates.

## After launch: one outcome, its guardrails, a comparison group

Offline evals measure the cases someone thought of. Production measures the rest. The guidance describes the layers (automated evals, production monitoring, A/B tests, user feedback, transcript review) as a stack in which no single layer catches everything, and recommends automated evals for iteration, monitoring for ground truth and periodic human review for calibration.

In a design that becomes three commitments. One outcome metric tied to the business, such as resolution without a human. Guardrail metrics that move when the outcome is gamed: same-issue re-contact within a fixed window, escalation after an assistant answer, complaints. A comparison group with stable assignment, so that the season and the launch are separated. A judge model scoring a daily sample of transcripts adds a quality signal, after its agreement with human labels has been measured on cases from this product.

## The fallback is a component with a capacity

"Escalate to a human" is a queue with an arrival rate, a handle time and a staff count. Scenario: at peak the assistant handles 3,000 conversations an hour and hands off 15% of them, 450 an hour. At a 10-minute handle time, Little's law gives 450 × 10 / 60 = 75 agents busy at any moment; at a target occupancy of 85% the roster needs 75 / 0.85 ≈ 89 agents on shift. Those figures go into the design because they decide two things.

First, the escalation threshold is a staffing decision. Lowering the confidence threshold so that 25% of conversations hand off instead of 15% raises the busy count from 75 to 125 at the same handle time. The threshold is set jointly with whoever owns the roster, and changing it is a change to their plan.

Second, the fallback for a model outage cannot be "escalate everything". At 100% handoff the same peak needs 3,000 × 10 / 60 = 500 agents busy, more than five times the roster. The outage path is a degraded mode: static answers for the top intents, a form that queues a callback, a banner with the expected wait, and handoff only for the topics where waiting causes harm.

The handoff itself needs a trigger list (a low retrieval score, a topic on the never-answer list, an explicit request, two turns without progress), a summary written for the human so the customer does not repeat themselves, and a measurement: the share of handoffs a human resolves without contacting the customer again.

## In the room

"You have four weeks to launch a support agent that can change customers' plans. Your eval set has 30 cases and each run takes two minutes. The support director will not add staff. What is your eval and fallback plan?"
</Callout>

<Fragment slot="short">
<p>Grow the set to about 50 cases drawn from real tickets, including cases whose correct outcome is a handoff and cases where the customer changes something mid-conversation. Every prompt change runs one trial per case; release candidates run eight, so pass^8 is measured on the plan-change cases specifically. Plan changes go through a tool that checks policy and, for the first weeks, a human confirms each change. After launch: resolution with re-contact and wrong-plan-change rate as guardrails, against a holdout. The handoff threshold is set so the added escalations fit inside the current roster, which I compute with the support director before launch. What I give up: some resolution rate, because with no added staff the threshold, not quality, caps how much the agent hands off.</p>
</Fragment>
<Fragment slot="long">
<p>The run cost first. 50 cases at eight trials is 400 runs; at two minutes each, sequentially, that is about 13 hours, so release candidates run overnight or in parallel, and per-change runs use one trial. The plan-change cases get their own pass^8 because a wrong change is the costly failure; an answer-only case that fails one trial in ten is a different risk.</p>
<p>The human confirmation on plan changes conflicts with the no-new-staff constraint. I size it: if the agent proposes 200 plan changes an hour at peak and a confirmation takes one minute, that is 200 / 60 ≈ 3.3 agents busy. If the roster can absorb that, confirmations stay for four weeks after launch and are removed by change type once each type's wrong-change rate is measured. If it cannot, plan changes start with downgrades excluded, since those are the ones a customer disputes.</p>
<p>The failure mode of this plan is that confirmations become a rubber stamp at volume. I track the confirmation rejection rate per change type; a type approved nearly every time either graduates to no confirmation with a guardrail, or the confirmation screen is not showing the human what they need to see.</p>
</Fragment>

## When this is wrong

pass^k from independent trials assumes the trials are independent. Runs at temperature 0 against the same provider can be correlated, so repeated trials understate variation that users see across days and model versions; tau2-bench ran each task four times at temperature 0, and its pass^k numbers carry that condition. In the other direction, the formula 0.9<sup>8</sup> assumes every task has the same success rate. Real sets mix tasks that always pass with tasks that often fail: two tasks at 1.0 and 0.5 average 0.75 per trial, yet pass^3 is (1 + 0.125) / 2 ≈ 56%, not 0.75<sup>3</sup> ≈ 42%. Report pass^k per task group, not one number.

The staffing arithmetic uses averages. Arrivals are bursty and handle times have long tails, so the 85% occupancy figure is a planning assumption the support team should replace with its own queueing model. The published benchmark figures come from simulated users in airline, retail and telecom domains, measured on models that have since been replaced; they show the gap between single-trial and repeated-trial success, not the gap a given product will see.
