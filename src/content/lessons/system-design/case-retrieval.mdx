## The intern can read the board minutes

Scenario, not a real incident: a company ships internal search over its wiki, drive and ticket system. Retrieval is good. On day three an intern asks "what did the board decide about layoffs" and gets a fluent, cited summary of a document only five people were meant to see. The vector index held every chunk, and the permission check ran after retrieval on the top 10 results, except in one code path that built the prompt before the check.

Retrieval-centric design rounds are mostly about this kind of boundary. The RAG track teaches how to find the right chunk. This lesson is about everything around the retriever: who may see what, what the system does when it cannot answer, and what a page of PDF costs before anyone asks it a question.

## The idea: a search engine with a compiler in front of the user

Think of the system as two halves you already know. The back half is a search engine: ingestion, an index, a query path and ranking. The front half is a code generator: it turns retrieved text into an answer, and like any generator its output is only as trustworthy as its input. Everything you know about search (freshness, recall, ACLs on documents) still applies, and the generator adds two new failure modes: it can phrase a wrong or forbidden passage convincingly, and it can answer when it should have said "I don't know".

So the order of the design is: who can see what, then how documents get in, then how a query finds them, then what the model does with them, then how you know it worked.

## Enterprise search with permissions

Microsoft describes the reference behaviour for its Copilot: it only surfaces organizational data the user has at least view permission for, and its index honours the user's access boundary during grounding. That is the requirement to restate in the room. Permissions are applied before the model sees text, never after.

There are three ways to enforce it, and the interviewer will ask you to choose.

**Partition by tenant.** One namespace or index per customer. Pinecone recommends this for multi-tenant products, and its own cost example (next) shows why it is cheaper as well as safer.

**Filter inside the query by ACL.** Store each chunk with the groups allowed to read it, expand the user to their groups at query time, and filter in the vector search, not after it. Pinecone's `$in` filter takes at most 10,000 values, and its docs call filtering on long lists of user IDs an anti-pattern, so filter on groups, not people.

**Post-filter the results.** Retrieve the top *k*, drop what the user cannot read. It is easy and it is the bug in the scenario: one missed code path leaks, and a user with narrow access gets an empty answer because all *k* results were filtered out.

Use the first for tenants and the second for users inside a tenant. Then say the hard part out loud: permission changes. When someone is removed from a group, the index has to forget them on the same schedule as the source system, so ACL sync is its own pipeline with its own freshness target.

## Customer-support assistant with escalation

The support case adds two things to search: a conversation, and a human who takes over. Design the handoff as a component. It needs a trigger (low retrieval confidence, a policy topic, the user asking, repeated failure), a summary the human can read in seconds, and a way back if the human resolves it.

The eval question is reliability across repeats, not a single success rate. tau-bench introduced pass^k, the chance that all *k* attempts at the same task succeed, and found GPT-4o-based agents inconsistent, with pass^8 under 25 percent in its retail domain. tau2-bench added a dual-control setting where the user also takes actions with tools, and agents dropped noticeably when they had to coordinate with that user. A support assistant that answers correctly most of the time but differently each time is the one customers call flaky.

## Insurance claims with token cost control

A claims assistant reads heterogeneous files (PDF forms, photos, scanned letters, the policy wording) and proposes a decision. The cost trap is the PDF. Claude bills each page as 1,500 to 3,000 text tokens plus an image, because every page is also rendered as an image; Gemini counts 258 tokens a page. A 40-page claim file is therefore 60,000 to 120,000 text tokens on the first and 10,320 on the second, before any question is asked. Re-sending that file on every turn of a review conversation is where budgets go.

Three moves control it. **Extract once at ingestion.** Pull the structured fields (claimant, dates, amounts, damage codes) into a record, and keep the page images only for the pages a reviewer opens. **Retrieve policy clauses, not policies.** Contextual retrieval (prepending a short document-level context to each chunk before embedding) cut top-20 retrieval failures by 35 percent in Anthropic's tests, 49 percent with contextual BM25 added and 67 percent with reranking on top, for a one-off cost of $1.02 per million document tokens with caching. **Skip retrieval when the corpus is small.** The same write-up suggests putting a knowledge base under 200,000 tokens straight into a cached prompt.

The decision itself stays with a person or with rules. The model drafts a recommendation with citations to the extracted fields and policy clauses; a rules engine checks hard limits; an adjuster approves.

## Compliance and document-heavy workflows

Regulated workflows add an audit requirement: for any answer, you must be able to show which documents, which versions and which model produced it. Store the retrieval set and the prompt version with every response, keep document versions immutable, and make citations point to a version, not a URL that can change. Data residency is a line item, not a footnote: Anthropic's US-only inference option multiplies every token price by 1.1 on its recent models.

## Real-time search at scale

When the corpus changes by the minute (tickets, chat, listings), the bottleneck moves to ingestion. Treat it as a stream: change events, chunk and embed, upsert, with a lag metric from source write to searchable. Keep a keyword index next to the vector index, because exact identifiers (order numbers, error codes) are what users paste and what dense vectors handle worst. Then size the index before the interviewer does.

```python
# Vector index size and one-off embedding cost for enterprise search.
docs = 100_000_000
chunks_per_doc = 8            # assumption: state it, then show what happens if it doubles
tokens_per_chunk = 400        # assumption
dims = 1536                   # text-embedding-3-small default output size
bytes_per_float = 4           # float32 before any quantization

vectors = docs * chunks_per_doc
raw_tb = vectors * dims * bytes_per_float / 1e12
print(f"{vectors:,} vectors, {raw_tb:.1f} TB of float32 vectors before index overhead")
print(f"at 256 dims and int8: {vectors * 256 * 1 / 1e12:.2f} TB")

price_per_m = 0.02            # text-embedding-3-small, USD per 1M tokens (checked 2026-10-28)
embed_cost = vectors * tokens_per_chunk / 1e6 * price_per_m
print(f"one full embedding pass: ${embed_cost:,.0f}")
```

```text
800,000,000 vectors, 4.9 TB of float32 vectors before index overhead
at 256 dims and int8: 0.20 TB
one full embedding pass: $6,400
```

Two conclusions. Embedding the whole corpus is cheap, so re-embedding when you change models is a budget line, not a project. Storage is not cheap at full precision, so shortened vectors and quantization are worth evaluating on your own recall set before you buy hardware for 4.9 TB.

## When this is wrong

The permission patterns assume your sources expose ACLs you can copy. Some do not (shared links, inherited folder rights, external guests), and then the honest design checks permissions against the source system at query time for the final few chunks, at a latency cost. The index-size numbers assume eight 400-token chunks per document; an archive of short tickets and one of long contracts give very different totals, so redo the arithmetic with the real distribution.

Contextual retrieval's percentages come from Anthropic's own test sets in 2024. They show the direction and rough size of each step, not what you will get on your corpus. And "under 200,000 tokens, skip retrieval" depends on each provider's long-context pricing, which differs and changes.

What I would say in the room: "Permissions live in the query, not after it, and I'll size the index and the PDF tokens before I pick a database."
