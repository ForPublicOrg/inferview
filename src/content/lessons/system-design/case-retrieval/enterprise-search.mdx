## The order it fails in

Enterprise search over a company's wiki, drive and tickets fails on permissions first, freshness second, identifier-heavy queries third, and model quality last. A leaked board memo ends the project; a revoked contractor who can still search for a week is a security finding; a support engineer who pastes `ERR-40917` and gets three paragraphs about error handling stops using the tool. A better model fixes none of these, so the design is ordered the same way: the permission boundary, the revocation path, the lexical path, then generation and the eval.

The case below is one tenant: 2 million documents, 5,000 employees, a vector store billed by data scanned, and a mid-tier model writing cited answers. Every number in it is either sourced or computed here, and the scenario inputs are labelled.

## The boundary is enforced before text reaches the model

Microsoft states the reference behaviour for its Copilot (now named Microsoft Copilot, formerly Microsoft 365 Copilot): it only surfaces organizational data the user has at least view permission for, and its Semantic Index honours the user's identity-based access boundary during grounding. Two further details matter for a design. Content encrypted with Purview sensitivity labels is used only within the usage rights granted to that user, so a label is a second permission system beside the file ACL. And data from Graph connectors (third-party sources) comes back only if the user has permission to it, which means every connector has to carry ACLs, not just content.

There are four places to enforce that boundary, and an enterprise design uses at least two of them.

**Partition per tenant.** One namespace per customer. On Pinecone serverless, a query costs 1 read unit per GB of the namespace it touches (minimum 0.25), so the docs' own example is 1 RU for a query in one tenant's 1 GB namespace against 100 RU for the same query filtered inside a shared 100 GB namespace. A serverless index holds from 100 namespaces on the Starter plan to 1,000,000 on Enterprise, and offboarding a tenant is deleting its namespace. Isolation and cost point the same way.

**Filter inside the query on groups.** Inside a tenant, each chunk carries the IDs of the groups that may read it, and the query passes the user's expanded groups as a metadata filter. Pinecone caps `$in` at 10,000 values and calls filtering on long user-ID lists an anti-pattern, which is a second reason to store groups, not people: membership changes then never touch the index.

**Post-filter after retrieval.** Retrieve the top *k*, drop what the user cannot read. This is the cheapest to build and fails twice: one code path that builds the prompt before the filter is a leak, and narrow users get nothing back.

**Check against the source at query time.** For sources whose permissions cannot be copied (shared links, inherited folder rights, external guests), call the source's permission API on the final candidates. It is always current and costs a network round trip per candidate batch on the latency path.

## Revocation is its own pipeline

Content freshness and permission freshness have different owners and different costs of being late. A stale paragraph is a quality bug. A stale grant is a security incident with a duration. So the connectors emit two event streams: content changes, which re-chunk and re-embed, and ACL changes, which rewrite only the group metadata on existing chunks, or nothing at all when the change is a membership change and chunks reference groups.

The metric is revocation lag: time from the source system removing access to the last query that could still retrieve the content, reported at a high percentile and alerted on separately from ingestion lag. The design decision is the bound. A bound of minutes is affordable when chunks reference groups and membership lives in a directory cache with a short TTL. A bound of seconds pushes you to the fourth option above, a source check on the final candidates, for at least the sources where revocation is frequent.

Two edge cases change the design more than they look. Deleting a document must remove its chunks and also any cached answers that cite them. And the contextual prefix described below is generated from the whole document; it inherits that document's ACL, but if it is generated once and stored, a document split into differently permissioned sections leaks the restricted section's summary into every chunk's prefix. Generate prefixes per permission scope, not per file.

## Identifier queries need a lexical path

Users paste ticket numbers, error codes, SKUs, contract IDs and people's names. Dense embeddings place `ERR-40917` near other error codes, which is the wrong neighbourhood. The design keeps BM25 beside the vector index, runs both, and fuses the lists, and the eval reports an identifier slice on its own because an aggregate hides it.

Anthropic's contextual retrieval write-up (2024-09-19, measured on its own sets) is the most quoted evidence for doing both. Its metric is 1 minus recall@20, the share of relevant chunks missing from the top 20. Prepending 50 to 100 tokens of generated document context to each chunk took that failure from 5.7% to 3.7%; adding the same context to a BM25 index took it to 2.9%; reranking the top 150 down to 20 took it to 1.9%. Those are 35%, 49% and 67% reductions. The cost is the part to carry into a design: $1.02 per million document tokens to generate the contexts, at its assumptions of 800-token chunks and 8,000-token documents, with Claude 3 Haiku as the generator.

## Cost per query and per corpus

Scenario inputs: 2,000,000 documents of 6,400 tokens, chunked into eight 800-token chunks; text-embedding-3-small at 1,536 dimensions; about 1,000 bytes of metadata per chunk (group IDs, source, version, path); a 36-byte ID. Pinecone's storage formula is ID + metadata + dimensions × 4 bytes.

```python
docs, chunks, tok = 2_000_000, 8, 800
records = docs * chunks                          # 16,000,000
rec_bytes = 36 + 1_000 + 1_536 * 4               # 7,180 bytes
gb = records * rec_bytes / 1e9                   # 114.9 GB
print(f"storage ${gb * 0.33:,.0f}/month")        # $0.33 per GB-month
tokens = records * tok                           # 12.8 billion
print(f"embed ${tokens / 1e6 * 0.02:,.0f}")      # $0.02 per million
print(f"contexts ${tokens / 1e6 * 1.02:,.0f}")   # Anthropic's 2024 figure
print(f"initial writes ${records * rec_bytes / 1e3 * 4 / 1e6:,.0f}")  # 1 WU per KB, $4 per million

in_tok = 20 * tok + 1_000                        # 20 chunks plus instructions and question
llm = in_tok * 2 / 1e6 + 500 * 10 / 1e6          # Sonnet 5.5, 500 output tokens
vec = gb * 16 / 1e6                              # 1 RU per GB, $16 per million RU
print(f"per query: model ${llm:.4f}, vector ${vec:.4f}")
q = 5_000 * 10 * 21                              # scenario: 10 queries per user per workday
print(f"per month: model ${q * llm:,.0f}, vector ${q * vec:,.0f}")
```

```text
storage $38/month
embed $256
contexts $13,056
initial writes $460
per query: model $0.0390, vector $0.0018
per month: model $40,950, vector $1,930
```

Three things follow. The model call is about 21 times the vector query, so the lever on running cost is how many chunks reach the model, not which vector store you pick; sending 8 chunks instead of 20 cuts input tokens from 17,000 to 7,400. The vector query cost scales with the namespace, so a single 115 GB tenant pays 115 RU a query, and splitting it by source or department only helps if most queries can be routed to one partition. And at ingestion, generating contexts costs 51 times the embedding pass ($1.02 against $0.02 per million tokens), so contextual retrieval, not the embeddings, is the line item that makes re-indexing on a model change a budget decision. The reranker is not in these numbers; it is the next term to price, per candidate set of 150.

Residency is a multiplier on all of this. Microsoft routes Copilot's model calls to the nearest region but may use other regions under load, keeps EU traffic inside the EU Data Boundary, and currently excludes Anthropic models supplied as a subprocessor from that boundary. On Anthropic's own API, `inference_geo: "us"` multiplies every token category by 1.1 on Claude 4.6 and later, so the $40,950 becomes $45,045.

## The eval plan

Four suites, each with an owner and a gate.

- **Permission suite.** Synthetic users in known groups ask questions whose only answer lives in documents they cannot read. Any restricted chunk in the retrieved set fails the build, regardless of what the model wrote. It runs in CI and as a production canary, and it includes connector sources and labelled (encrypted) documents.
- **Revocation lag.** A canary user is removed from a group on a schedule; a prober measures the time until queries stop returning that group's canary document.
- **Retrieval quality per slice.** 1 minus recall@20 on labelled queries, reported for natural-language, identifier and people queries separately, and per source.
- **Answer quality.** Citation precision (every claim maps to a retrieved chunk), a no-answer rate, and a sampled human review of answers that cite more than one source.

## When this is wrong

The partition-first argument assumes a store that bills by data scanned. A self-hosted index on fixed hardware has no per-query scan charge, and there the case for a namespace per tenant rests on isolation and deletion alone. The cost arithmetic assumes eight 800-token chunks per document and 20 chunks per prompt; a corpus of short tickets or a prompt of 8 chunks moves the numbers by large factors, so redo them with the real distribution.

The contextual retrieval percentages come from Anthropic's 2024 test sets and generator. They show the direction and the order of each step, not what your corpus will give, and the $1.02 figure was computed at 2024 prices for Claude 3 Haiku. Microsoft's description is of its own product and its own index; it states the behaviour, not the mechanism, so do not cite it for how the Semantic Index enforces the boundary.
