## One contract, eight implementations

A durable execution engine does not snapshot your process. It keeps a log of the steps that finished and their results, and after a crash, a deploy or a long wait it runs your code again from the top, handing back the logged result each time the code reaches a step that already finished. The first step with no logged result executes for real, and from there the run continues as new.

That gives every engine the same contract, whatever the vendor calls it:

1. A step can execute more than once. The step that was running when the worker died has no logged result, so it runs again.
2. Once a step's result is logged, the log wins. The code is not executed again for that step, and the old result is returned even if the world has changed.
3. Anything external that must happen once needs a key the external system deduplicates on. The OpenAI Agents SDK docs put the same rule plainly for approvals: an approved call is permitted to execute, which does not mean it executes exactly once.

The analogy is a write-ahead log with redo, where the redo is your own code. The difference from database recovery is that the redo runs application code, so the code between steps has to produce the same sequence of steps given the same inputs and logged results. That requirement is the subject of the next lesson; this one is about where each engine keeps its log, what a step costs, and what "replay" means in each product, because the word means three different things.

Two columns decide most architecture choices. The first is where the log lives: DBOS and a LangGraph Postgres checkpointer put it in a database you already operate and back up; Temporal, Restate and Inngest put it in a service you run or rent; Lambda and Cloudflare keep it inside the platform with a retention policy (Lambda's default is 14 days after the run ends, configurable from 1 to 90). The second is granularity. Temporal, Inngest, DBOS, Restate, Lambda and Cloudflare log per step you mark. LangGraph logs per super-step, which is one node in a linear graph and several nodes in a parallel fan-out, so the unit of re-execution is the node, not a call inside it. A node that makes a model call and then a tool call and dies between them runs both again.

The step boundary is also the cost boundary. Every logged step is a write (DBOS), three history events (Temporal), or a request round trip (Inngest in standard orchestration), and every logged result is a payload the engine stores and ships back on each replay. Payload ceilings are real: Temporal errors on a blob above 2 MB and Cloudflare on a step return above 1 MiB. A model step that returns a 200-page document belongs in blob storage with a pointer in the log, which the DBOS docs recommend for large outputs.

## Three meanings of replay

The engines use one word for three operations, and the bill and the blast radius differ for each.

**Resume after a crash.** The run keeps its identity, finished steps come from the log, and only the step in flight runs again. This is what every engine in the table does on recovery, and it is the safe case: one step at risk, and a key derived from the run id and step name deduplicates it.

**Time travel from a checkpoint.** LangGraph lets you pick a checkpoint from `get_state_history` and invoke from it, or fork with `update_state`. Nodes before the checkpoint are not re-executed. Every node after it is, "including any LLM calls, API requests, and interrupts", in the docs' words, so the model answers again and may answer differently. Interrupts fire again and wait for a new resume value. Replaying from a checkpoint is a re-execution, not a cache read; a reproducible replay needs the model outputs pinned, by forking with the recorded values or by moving the model call behind a cache keyed on its inputs.

**Bulk replay of failed runs.** Inngest's Replay selects runs by function, time range and status and re-runs them after a fix. The docs say it creates new executions and tell you to check which charges, messages or records could repeat. They do not say whether results from the original runs are reused, so a design that is safe whichever way that falls assumes every step may run again. A new execution also means a new run id, so an idempotency key built from the run id stops nothing; it has to be built from the business entity (the ticket, the order, the event id).

## Numbers that shape the design

Temporal's history limits matter for long agent runs. The service logs a warning after 10,240 events and terminates the execution above 51,200 events; on self-hosted defaults the history also warns at 10 MB and errors at 50 MB. Since a completed activity is at least three events, a loop that makes one model activity and one tool activity per turn adds at least six events a turn before counting workflow-task events, signals or timers. The next lesson works out what that means and how continue-as-new resets it.

Retries are per step, with different defaults: four after the first attempt for each Inngest `step.run()`, 3 attempts per step in the Workflow SDK. Temporal adds no history events for retries until an attempt reaches a terminal state, so a flapping model provider holds the activity open without growing the history.

Durability is a setting in LangGraph and fixed elsewhere. `sync` persists before the next super-step starts, `async` persists while the next step runs (a crash can lose the last checkpoint), and `exit` persists only when the graph exits, which cannot recover a crash mid-run. A team that chose `exit` for latency has checkpointing that survives restarts between runs and nothing else.

## The contract in forty lines

The sketch below has the parts every engine shares: results matched by position and name, results forced through serialization, and an external call keyed by the business id so the repeated step is harmless.

```python
import hashlib, json

class NonDeterminism(Exception):
    pass

class Run:
    """Re-executes workflow code; a recorded result wins, matched by position and name."""
    def __init__(self, history=None):
        self.history = list(history or [])   # [(step name, result)] from earlier attempts
        self.pos = 0

    def step(self, name, fn):
        if self.pos < len(self.history):
            recorded, result = self.history[self.pos]
            if recorded != name:
                raise NonDeterminism(f"position {self.pos}: history has {recorded}, code asked for {name}")
        else:
            result = json.loads(json.dumps(fn()))   # results must serialize, in every engine
            self.history.append((name, result))
        self.pos += 1
        return result

def key(business_id, step):
    return hashlib.sha256(f"{business_id}:{step}".encode()).hexdigest()[:16]

class Payments:
    def __init__(self):
        self.seen, self.credits = set(), 0
    def credit(self, amount, idempotency_key):
        if idempotency_key not in self.seen:
            self.seen.add(idempotency_key)
            self.credits += 1
        return {"ok": True}

def ticket_flow(run, pay, ticket):
    label = run.step("classify", lambda: "refund")      # a model call in production
    if label == "refund":
        run.step("credit", lambda: pay.credit(20, idempotency_key=key(ticket, "credit")))
    return run.step("summary", lambda: f"credited {ticket}")

pay = Payments()
first = Run()
ticket_flow(first, pay, "T-1")
lost = first.history[:1]          # the credit landed, its result was never saved
ticket_flow(Run(lost), pay, "T-1")
print(pay.credits)                # 1

try:
    Run([("credit", {"ok": True})]).step("classify", lambda: "refund")
except NonDeterminism as e:
    print(e)                      # position 0: history has credit, code asked for classify
```

The `classify` result is the model's decision. On replay it comes from the log, so the branch on `label` takes the same path it took the first time, even though calling the model again might return something else. That is why the model call has to be a step: code outside a step runs on every replay, and a model call there re-decides the path each time.

## When this is wrong

The table compares documented behaviour on 2026-10-28, and several rows are version-sensitive. Inngest's TypeScript SDK v4 runs steps in one request until a retry or a parallel step forces standard orchestration, so "one request per step" is the Python and fallback behaviour, not a constant. Cloudflare and Lambda limits are platform settings that change with releases.

"The log wins" assumes the logged result is still valid. A step that read a price, a permission or an account balance returns the old value on replay, days later after a long wait. When freshness matters, re-read inside a new step after the wait instead of reusing the value from before it.

Restate's page says each invocation runs exactly once. That holds for the invocation's journaled steps; a side-effecting action whose result had not reached the journal when the process died has no record to skip, so the external system still needs a key. The same reasoning applies to every engine whose marketing says exactly-once.

The widget treats a model step as one call with one result. A streaming model call that dies halfway has no result at all, and a step that calls a model and then a tool is two side effects with one log entry. Keep one external effect per step and the contract holds; put two in a step and the first one repeats.
