## What it is and who ran it

Airbnb engineers migrated nearly 3,500 React component test files from Enzyme, in use at Airbnb since 2015, to React Testing Library, which the company had adopted for new tests in 2020. The account is a single engineering blog post by Charles Covey-Brandt, published in March 2025. The team had estimated the work at 1.5 years of engineering time by hand; with a model pipeline it took about six weeks, including a final week of manual fixes.

It is the clearest public example of a model pipeline built as a state machine rather than an agent. The model never chose what happened next. Each file moved through fixed states, and code decided every transition from the output of tools the team already ran in CI. Everything below comes from that post; where the post is silent, the section says so.

**Per-file state machine.** Each file moved through four states: Enzyme refactor, fix Jest, fix lint and tsc, and mark complete. The post's description is that the team "modeled this flow like a state machine, moving the file to the next state only after validation". Because the unit was one file and files were independent, each could be tracked and rerun on its own, and the post says the design made it simple to run hundreds of files concurrently. There is no DAG: no file waited for another.

**Validation-gated transitions.** The gate after each state was an existing tool: the Jest run for the fix-Jest state, the linter and the TypeScript compiler for the lint-and-tsc state. The model's output was a candidate; the file advanced only if the check for its current state passed. This is what made the pipeline safe to run unattended across thousands of files: a model failure stayed in the state where it happened, recorded, instead of flowing into the next step.

**Retries with errors in the prompt.** A failed validation sent the file back through the same state with a new prompt containing the validation errors and the file's latest version, up to a configurable maximum number of attempts. The post says the most effective way to improve outcomes was "simply brute force": retrying with feedback. Most files that succeeded did so within 10 attempts.

**Context builder.** For each call the pipeline assembled the component's source, the test file, the validation failures, sibling tests from the same directory, imports, examples of React Testing Library usage, hand-written few-shot examples and general migration guidelines. Prompts for harder files reached 40,000 to 100,000 tokens and drew in up to 50 related files. The post credits picking the right related files over refining prompt wording.

**Status comment and rerun CLI.** Each file received an automatically generated comment recording the result of each step, such as Jest pass and fail counts. A CLI could rerun files filtered by the step they were stuck on and a path pattern, for example `--step=fix-jest --match=project-abc/**`. Together they turned the repository itself into the pipeline's status table.

**Sample, tune, sweep loop.** For the files left after the first run, engineers grouped common failures, took 5 to 10 example files with one failure, tuned prompts or scripts, checked the change on that sample, and then reran every remaining file. Four days of this moved completion from 75% to 97%.

**Manual long tail.** With just under 100 files left, some retried 50 to 100 times, the team judged it had reached the ceiling of what automation could fix and finished the rest by hand, starting from the failing model output, in about another week.

## Context strategy

The decision that carried the project was what to put in the window, not how to word the instruction. As described, the pipeline did not ask the model to explore the codebase; it pre-fetched what a person migrating the file would open: the component under test, its imports, the tests next to it, and examples of the target style. That is a retrieval problem with a known answer set per file, solved deterministically before the call, which keeps the model step a single call with no tools.

The cost of that choice is window size. Pre-fetching up to 50 related files buys reliability on hard files at 40,000 to 100,000 tokens per attempt, and the hard files are also the ones that take the most attempts. The post does not say whether context grew with attempts or by file difficulty, or whether it was trimmed on retries.

## Tools and permission model

As described, the model had no tools. It received a prompt and returned a file; the pipeline ran Jest, the linter and tsc, and wrote the file. That removes most of the permission questions an agent raises: the model could not run commands, read files outside its context or change anything but the candidate it returned, and every effect passed through a check the team already trusted. How migrated files reached the main branch (one pull request per file, per batch or per directory, and who reviewed them) is not in the post.

## Cost and latency

The post's numbers are elapsed time. The first bulk run migrated 75% of files in about four hours: roughly 2,600 of nearly 3,500 files (0.75 × 3,500 = 2,625), or about 650 files an hour across the concurrent runs. Four days of sweeps reached 97%. The manual tail of just under 100 files took about a week, so the slowest 3% of files took longer than the first 75%.

The headline comparison, six weeks against 1.5 years, mixes two units: 1.5 years is an estimate of engineering effort, six weeks is calendar time, and the post does not give team size, so the effort saved cannot be computed from the post. The post gives no API spend or token totals, describing the combined cost only as far more efficient than the manual estimate. A cost model for a similar project has to supply its own figures: attempts per file from the pass curve, tokens per attempt from the context builder, and the price of the model chosen.

<Callout kind="aside">The four-hour first run and the six-week total describe the same project. The post accounts for four days of sweeps and about a week of manual fixes and does not break down the rest of the six weeks, so the first-run rate says little about the project's rate.</Callout>

## Failure modes

**The long tail does not yield to retries.** Files retried 50 to 100 times still failed. Retries help with variance; they do not supply missing context or a missing rule, and past some attempt number they are spend with no yield. The sample, tune, sweep loop exists because the fix for systematic failures is a pipeline change, not another attempt.

**The validator defines success.** A file passed when its tests ran green and lint and tsc were clean. Green tests after a rewrite show the tests run, not that they assert what the Enzyme versions asserted. The post states that coverage and test intent were preserved but publishes no coverage figures or audit method.

**Context selection fails quietly.** If the builder misses the file that explains a component's behaviour, the model produces a plausible test that fails validation for a reason no amount of retrying fixes. The post's emphasis on picking related files is the positive version of this failure.

**Per-file independence is an assumption.** It held for test files, which rarely import each other. A migration of shared helpers or fixtures would change other files' results mid-run, and per-file retries would chase a moving target.

## What is not public

The prompts are not public, beyond the list of what went into them. The per-state attempt limits are not public: the post says the limit was configurable and that most successes came within 10 attempts, and InfoQ's coverage describes a ten-iteration maximum, a setting the primary source does not state. The specific checks behind the refactor state are not described.

The model and version are not named; the post says only "frontier models". There are no API costs, token totals, concurrency limits or details of the infrastructure that ran hundreds of files at once. The team size, and therefore the engineering effort actually spent, is not given. How migrated files were reviewed and merged, whether flaky tests affected the Jest gate, and any coverage numbers are absent. The Airbnb page itself carries no publication date; the March 2025 date comes from contemporaneous coverage.

## Interview questions about it

  <Fragment slot="short">
    <p>You are asked to run the same approach on 10,000 Python files moving from one internal logging library to another, in a monorepo where every directory has code owners who must approve changes, with a quarter to finish. I would copy the per-file state machine and the validation gates (tests, type checker, a lint rule that bans the old import), add a review-batching state because owner approval is the real bottleneck, and set attempt limits and the stop rule from the first sweep's pass curve.</p>
  </Fragment>
  <Fragment slot="long">
    <p>Two constraints conflict. Owner approval caps throughput far below what the pipeline produces, and the quarter deadline needs the pipeline's speed. So the unit of work for the model stays the file, but the unit of review becomes a batch per owning directory, sized so an owner can approve it in one sitting. A batch is only proposed when all its files are complete, so owners never see half-migrated directories.</p>
    <p>The gate is stronger than Airbnb's needed to be, because logging changes alter behaviour that tests rarely assert: I would add a check that the set of log events emitted by the test suite is unchanged before and after. Attempt limits come from the first sweep: if passes stop arriving after a handful of attempts, the limit sits just past that. What I give up is speed in directories with slow owners; I would publish per-owner queues so the bottleneck is visible, and accept that the last batches finish by hand if owners do not approve in time.</p>
