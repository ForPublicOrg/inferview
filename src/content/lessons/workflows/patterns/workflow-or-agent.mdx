## The decision

For every step of the system, decide who chooses what happens next: your code or the model. That is the whole distinction. Anthropic's December 2024 post draws the line the same way: a workflow orchestrates models and tools "through predefined code paths", and an agent lets the model direct its own process and tool use. Nothing about the model call itself differs. A workflow step and an agent step can send the same prompt to the same model; what differs is whether the next transition is a branch in your source or a token the model emitted.

Two consequences follow, and both are operational rather than philosophical. When code owns control flow, the set of reachable states is finite and you can enumerate it in a test plan, a runbook and an audit log. When the model owns it, the set of reachable states is whatever the model's tools can compose, and your controls move from the graph to its edges: budgets, permission checks on each tool, approval gates and stop conditions.

The unit of decision is the step, not the system. Most production systems that ship as "agents" are workflows with one or two steps where the model chooses the path, and HumanLayer's 12-factor agents makes the same observation from the author's own conversations with builders: mostly deterministic code with model steps at chosen points. Factor 8 of that guide is "Own your control flow", which is this playbook's default.

## The inputs that change it

Five inputs move a step from code-owned to model-owned or back.

**Can the steps be drawn in advance?** If you can write the step list for nearly every real input before seeing it, write it. The test is empirical: take a sample of real inputs and try to draw the path each one needs. Anthropic's guidance reserves agents for open-ended problems "where it's difficult or impossible to predict the required number of steps". OpenAI's guide lists the same condition from the other side: workflows that resisted automation because rule engines could not express them.

**Is the step reversible?** A wrong label on a ticket is cheap to undo. A wrong refund, a sent email or a merged migration is not. Irreversible steps stay code-owned or human-approved even when the decision leading to them is model-owned. OpenAI's guide names high-risk actions, including authorising large refunds and making payments, as one of the two triggers for human intervention; the other is exceeding a failure threshold.

**Does the step need judgement over unstructured input?** This is OpenAI's strongest condition: heavy reliance on unstructured data (their example is a home insurance claim) and complex decisions with exceptions (their example is refund approval). Judgement over unstructured input is a reason for a model call. It is not by itself a reason for the model to also own control flow: a single call that returns a label from a fixed enum is judgement inside a workflow.

**How long does the run wait?** A process that waits two days for an approval needs durable state whether the decision steps are model-owned or not. Long waits push toward explicit, persisted control flow, because an agent loop that holds its plan in a context window does not survive a deploy or a two-day pause without the same checkpointing a workflow engine gives you for free. The durable-execution module covers the engines.

**What does a run cost, and who pays for variance?** Anthropic's post states the trade plainly: agentic systems "often trade latency and cost for better task performance". A fixed path has a cost per item you can compute before launch; a model-owned loop has a distribution with a tail, and the tail is set by your step budget, not by the model.

## One prompt or a chain

Below the workflow-or-agent decision sits a smaller one: one large prompt, or several calls in a fixed sequence. A chain is a pipeline of small functions and one big prompt is a monolith. The pipeline is easier to test, because each step has its own contract and its own golden set, and easier to debug, because the trace shows which step went wrong. It costs latency, since calls run in series, and some context, since each step sees only what you pass it.

Split when one prompt is doing two jobs that fail differently, for example extracting facts and then writing prose about them: extraction failures are caught by a schema check, prose failures by a reviewer, and mixing them means neither check can run. Keep it whole when every step needs the full context and the latency budget is tight. The next lesson adds the condition that matters most: a chain only beats one prompt when a deterministic gate sits between steps.

## The options and when each wins

**One call.** Retrieval plus in-context examples plus a schema-constrained output. Wins when the task is a single judgement with a fixed output shape. Anthropic's post says many applications need nothing more, and it is the baseline every other option has to beat on your eval set.

**Workflow.** A fixed graph of code steps and model calls with gates between them. Wins when the steps can be drawn in advance for nearly all inputs and some steps are irreversible. You get enumerable states, a cost per item you can compute, and failures that land on a named state.

**Workflow with a bounded agent step.** The graph is fixed except for one node where the model runs a tool loop, with read-only tools, a step budget, a token budget and an output schema the next node validates. Wins when one step is an investigation whose length varies (read a vendor thread, look up past invoices, compare contract terms) and every step that writes is still code-owned. This is the common production shape.

**Agent with code-owned guardrails.** The model owns the loop and the sequence of tools; code owns the permission check on every tool call, the approval gate on irreversible tools, the budget and the stop condition. Wins when inputs are open-ended enough that drawing the graph fails for a large share of them, and the environment gives ground truth at each step (tests pass or fail, a query returns rows).

**Agent end to end.** The model owns control flow and the effects. Rarely the right first build for a back-office process; the cases where it wins are sandboxes where every effect is reversible, such as a coding agent working on a branch.

<Callout kind="gotcha">An agent SDK does not make a system an agent. If the handoffs between agents are fixed edges chosen by code, the system is a workflow written in an agent framework, and it should be tested and operated as one.</Callout>

## Worked decision: vendor-invoice intake with a refund branch

Scenario (a constructed case, not a company): an accounts-payable team receives vendor invoices as PDF attachments. Each invoice must match a purchase order and a goods receipt. When an invoice exceeds the purchase order, the team either short-pays and asks the vendor for a credit note or, if the invoice was already paid, asks for a refund. A refund request above a set amount needs a controller's approval, which takes up to two days.

Apply the inputs per step.

| Step | Owner | Reason |
|---|---|---|
| Receive email, store the PDF, derive the idempotency key from vendor id and invoice number | code | deterministic, and duplicates arrive |
| Extract header and line items into a schema | model, one call | unstructured input, fixed output shape |
| Check totals, tax and vendor against the vendor master | code gate | arithmetic and lookups |
| Three-way match against purchase order and receipt | code | stable rules that audit reads |
| Classify the discrepancy (price change, duplicate, partial delivery, freight, other) | model, router over a fixed enum | judgement over line items and the email thread |
| Draft the credit-note or refund request | model, one call | prose |
| Approve a refund above the threshold | human, durable wait | irreversible money movement |
| Send the request and post the ledger entry | code, idempotent on the invoice key | effects |

The only candidate for model-owned control flow is the classification step, and only for the "other" bucket: discrepancies where the cause sits in a long correspondence, a contract amendment or an earlier credit note. There the steps cannot be drawn in advance. The option that fits is a bounded agent step with read-only tools (search the vendor thread, fetch past invoices, fetch the contract), a budget, and an output that must be one of the same enum values plus cited evidence. Everything that writes stays in code or behind the approval.

Whether that agent step is worth it is a cost question, and the cost that dominates is not the model.

Workflow cost per invoice: 1.2 + 0.15 × 200 = 31.2 cents. Agent cost: 6 + r × 200 cents. Setting them equal gives r = (31.2 − 6) / 200 = 0.126, so 12.6%. The model bill moves by 4.8 cents; each percentage point of review rate moves the total by 2 cents. The agent step earns its place only if it removes at least 2.4 points of review on a held-out set without adding uncaught errors, and that is the measurement to run before building it.
</Predict>

The decision for this case: ship the workflow first, with the "other" bucket routed to a human. Log every "other" item with the reviewer's resolution. That log is the eval set for the bounded agent step, and its size tells you whether the step is worth building at all.

## What to measure after deciding

**Share of inputs that leave the happy path,** by branch and by reason. This is the number that says whether the graph you drew matches the traffic. A rising "other" share means the input distribution moved or the extraction step degraded; the trace tells you which.

**Cost per item, including human time.** Model spend per invoice is the smaller term in the worked case. Report model cost, review cost and rework cost per item together, or the team will optimise the wrong one.

**Human-review rate and reviewer override rate.** The review rate is the cost driver; the override rate (how often the reviewer changes the model's answer) is the quality signal on the reviewed slice. An override rate near zero on a large review volume says the threshold is too conservative.

**Uncaught error rate from an audit sample.** Items that passed every gate and were still wrong. Without a sampled audit this number is invisible, and it is the one that decides whether an agent step made things worse while lowering review rate.

**Wait time on the approval step.** The p95 wait, because it sets how long runs stay open and how much in-flight state a deploy has to carry.

## When this is wrong

The playbook assumes the step graph is stable. If the discrepancy taxonomy changes every month because the business keeps adding vendors with new contract terms, the workflow becomes a rules engine you maintain by hand, which is exactly OpenAI's second condition (rules that are costly or error-prone to update). At that point the model-owned option wins on maintenance cost even if it loses on per-item cost.

It assumes volume. At a few hundred items a month, cost per item is noise and engineering time dominates; a simpler build with more human review can be the right answer, and the measurements above are still worth logging for when volume grows.

It treats the boundary as fixed. A step that needs an agent today can become a single call when a model improves at reading long correspondence, and the reverse happens when a model is retired. The decision is a per-step setting you revisit on each model change, with the review log as the eval set.

Finally, the definitions are about control flow, not about quality. A workflow with a bad extraction prompt fails as surely as an agent with a bad tool; it fails on a named step, which is the property this playbook buys, and that property is worth less if nobody reads the trace.
