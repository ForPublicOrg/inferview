## What it is and who runs it

PARSE is Instacart's internal platform for extracting product attributes (sheet count, flavor, size, fat content, organic, low sugar, gluten-free) from catalog data with multimodal models. Instacart's engineering post by Shih-Ting Lin, published 1 August 2025, describes it. The catalog holds millions of SKUs across thousands of categories, and the attributes feed search filters, variant selection and badges such as "Low Sugar".

The post explains why the earlier approaches stopped scaling. SQL rules handled keyword cases such as an organic claim and failed when context mattered, for example picking the primary flavor when a description lists several variants. Per-attribute ML models handled more but needed a labelled dataset, training and maintenance for every attribute. Both read only product text, so they missed facts printed only on the packaging image.

PARSE's design answer is to make an attribute a configuration rather than a project. That is the part worth studying: it is a workflow platform whose unit of deployment is a prompt plus a data query.

**Platform UI with attribute configs and versioned prompts.** A user defines the attribute's name, type (string, dictionary, number, boolean) and description, chooses the extraction algorithm and its parameters, picks a prompt template, writes the input SQL that selects the product features, and can add few-shot examples. Every configuration is versioned, so changes can be traced to a contributor and earlier versions restored. The config is the deployable artefact; changing a prompt is a config change with history, not a code release.

**Algorithm choice and the model cascade.** Users choose among several extraction algorithms to trade cost against accuracy; the options appear in a figure the post's text does not reproduce. The post names an "LLM cascade algorithm" as a way to balance cost and accuracy and gives no mechanics, model tiers or results for it.

**Backend orchestration.** Runs the config's input SQL to fetch product data and passes it, with the other parameters, to the extraction endpoint.

**Multimodal extraction.** The endpoint fills the prompt template with the product's features and the attribute definition, runs the selected algorithm on text, images or both, and returns a value with a confidence score. For sheet count, the post reports that multimodal models raised recall by 10% over text-only models; it does not say whether that is ten points or a relative gain.

**Self-verification confidence.** A second "scoring" prompt asks the model whether the extracted value is correct given the product features and the attribute definition, an entailment question, and instructs it to answer yes or no first. The probability of "yes" on the first generated token is the confidence. The post cites AutoMix for the approach; AutoMix itself treats self-verification as noisy and adds a router on top.

**Human audit queue.** In production, values with low confidence are treated as possibly wrong and go to human auditors, who review and correct them before ingestion.

**Quality screening.** In development, a team submits a small product sample; auditors label gold values in an evaluation interface that computes metrics, and LLM-as-judge speeds the evaluation up. In production, a periodic sample of new results is judged by humans or a model to catch quality drops. Results then flow into the catalog data pipeline.

## Context strategy

Each extraction call's context is assembled from the config: the template, the attribute definition, the few-shot examples and the product features the SQL returned, including images when the algorithm is multimodal. The SQL is part of the prompt in effect, because it decides which product fields the model ever sees. Versioning the SQL with the prompt is what makes a regression traceable to a change.

The future-work section points at the cost levers of this design: batching several attributes into one prompt per product, batching several products into one prompt, and an approximation cache that reuses results for similar products, which needs a similarity function the team had not defined. Each of these trades isolation for cost. One prompt per product and attribute makes errors independent and easy to attribute; packing several into one call makes one bad input able to corrupt several values.

## Tools and permission model

The models have no tools and write nothing directly. Values reach the catalog through the pipeline, after the audit queue for low-confidence values. The control that matters is on configs: a production config change alters every value of an attribute across millions of products. The post says configs are versioned and revertable and that validated configs are deployed to production; it does not describe who can deploy one or how a rollback is triggered.

## Cost and latency

The post's figures are about development time and model choice, not unit cost. An initial prompt for the organic claim reached 95% accuracy, and building that attribute took one day with PARSE against one week with the previous methods. The harder low-sugar attribute needed several prompt iterations and took three days. A cheaper model on simpler attributes gave similar quality at a 70% cost reduction; a less powerful model on difficult attributes showed a 60% accuracy drop. There are no per-call prices, volumes or latencies, so the cost per product cannot be derived.

Those two model figures are the case for a cascade. Suppose, with prices relative to the large model's cost per value, the cheap model costs 0.3 (the 70% reduction), the verify call costs <i>v</i>, and a fraction <i>e</i> of values escalates to the large model. The cascade costs 0.3 + <i>v</i> + <i>e</i>, against 1 for the large model alone, so it saves money only while <i>e</i> &lt; 0.7 − <i>v</i>. On an attribute where the cheap model shows a 60% accuracy drop, the escalation rate approaches 1 and the cascade costs more than calling the large model directly. A cascade is a per-attribute decision, which fits a platform where the algorithm is a field in the config.

## Failure modes

The post names two: smaller models fail badly on hard attributes, and quality can drop silently in production, which the periodic sampling is there to catch. The architecture implies two more, as questions rather than reported incidents. The verifier is the same kind of model reading the same inputs as the extractor, so an image it cannot read produces a confident wrong value and a confident "yes". And long-tail attributes such as flavor have values the few-shot examples never show, where self-verification has least to anchor on.

## What is not public

- The confidence threshold for the audit queue and how it was chosen.
- The cascade: which models, what triggers escalation, and any results.
- Which models PARSE uses for extraction and verification.
- Volumes: products processed, values audited per week, auditor headcount.
- Whether the verifier's scores were checked for calibration, and on what sample.
- How the evaluation set behind the 95% organic accuracy was built, and whether the 10% recall gain is relative or absolute.
- Who can deploy a config to production and how rollback works.

## Interview questions

<Callout kind="interview" label="Staff question">
You run PARSE. Merchandising wants a new "contains added sugar" attribute live in two weeks for a promotion. The auditors' capacity is already fully used by existing attributes. The cheap model is fine on organic and poor on nutrition attributes. Design the extraction, scoring and routing for the new attribute, and say what you cut.
</Callout>

<Depth>
<Fragment slot="short">
<p>Treat it as a hard attribute: large model for extraction, verify score for routing, no cascade until a labelled sample shows the cheap model's escalation rate is well under 0.7. With no spare auditor time, the audit queue cannot absorb a new stream, so in development the auditors label a sample once, the threshold is set from it, and in production values below the threshold are withheld (no badge) instead of queued. What I cut is coverage at launch, and I say so in the launch note.</p>
</Fragment>
<Fragment slot="long">
<p>Two weeks and zero auditor capacity are the binding constraints; model cost is not. In week one I would build the config, have auditors label a stratified sample (the scarce resource spent once instead of continuously), and measure the large model's accuracy and the verifier's ranking on it. If the score ranks errors, the threshold is chosen for the error rate merchandising will accept on shown values, and everything below it is withheld rather than audited.</p>
<p>The cascade waits. With a cheap model at 0.3 of the cost, a cascade pays only while fewer than 70% of values escalate, less the verify cost; on a nutrition attribute where the cheap model is known to fail, the first evidence I want is that escalation rate on the labelled sample, not a guess.</p>
<p>What I give up: products whose added sugar is only implied (an ingredient list without a claim) may be withheld at launch, and the promotion shows fewer products. The failure mode of the design is a withheld set that is not random: if the model is least confident on one brand or category, the filter under-represents it, which merchandising should see before launch as a coverage-by-category table.</p>
</Fragment>
