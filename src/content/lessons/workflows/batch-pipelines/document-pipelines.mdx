## Eight stages, eight contracts

A document pipeline turns files nobody controls into rows in a system that other teams treat as true: an ERP, a catalog, a data-governance registry. The model call is one stage of eight, and rarely the one that causes the incident. Each stage has an input contract, an output contract and a failure mode that shows up in production, and the design work is choosing where each failure is caught.

<div class="tablewrap">
<table>
<thead><tr><th>Stage</th><th>Output contract</th><th>Failure mode</th></tr></thead>
<tbody>
<tr><td>Intake</td><td>a document record: content hash, channel, received time, sender</td><td>the same invoice arrives by email and by upload and is paid twice</td></tr>
<tr><td>Preprocess</td><td>pages ready for reading, or a reject reason</td><td>encrypted PDFs, files over the request limits, one PDF holding three invoices</td></tr>
<tr><td>Read</td><td>OCR text, or native PDF input (text plus page images)</td><td>table rows shifted by one; handwriting and low-resolution scans</td></tr>
<tr><td>Extract</td><td>JSON that validates against the schema</td><td>valid JSON with wrong values; line items cut off by the output limit</td></tr>
<tr><td>Validate</td><td>field-level rule results</td><td>a rule that fails open when a field is missing</td></tr>
<tr><td>Score</td><td>a confidence per field or per document</td><td>scores that are not calibrated (the next lesson)</td></tr>
<tr><td>Route</td><td>auto-accept, or a review task with the evidence attached</td><td>a review queue that grows faster than the reviewers clear it</td></tr>
<tr><td>Write back</td><td>one record in the system of record per document</td><td>a retried write that posts the invoice twice</td></tr>
</tbody>
</table>
</div>

Intake and write-back are the two ends that must be idempotent, and they need different keys. Intake dedupes on the content hash, which catches byte-identical resubmissions and nothing else; the same invoice scanned twice has two hashes. Write-back dedupes on the business key the system of record already understands, for an invoice the vendor id plus the vendor's invoice number, so that a second copy that slipped through intake is rejected at the boundary that moves money. Everything between them can be retried freely, because it writes only to the pipeline's own state.

## What public pipelines look like

Uber's TextSense, described on the Uber engineering blog in April 2025, follows this shape for supplier invoices: ingestion from email, PDFs and ticketing systems into object storage; pre-processing for low-resolution scans, handwriting and multi-page documents; OCR on Uber's Vision Gateway; model extraction; post-processing with business rules; validation with human review; and monitoring of speed, accuracy and cost. Cadence orchestrates the steps. Reviewers work in a side-by-side UI that shows the PDF next to the extracted values, with alerts and soft warnings, and approved invoices go to the ERP for approval and payment. Invoices arrive in more than 25 languages, each with 15 to 20 header attributes plus line items. A fine-tuned Flan T5 reached over 90% accuracy on header fields but degraded on line items after the first line, and the team chose GPT-4 for its line-item results. The teardown in this module walks it stage by stage.

Grab's data classification pipeline, published in 2023, makes the opposite routing choice. An orchestration service groups classification requests into mini-batches at fixed intervals behind a workflow-level rate limiter, because every Azure OpenAI deployment shared one quota of 240K tokens per minute. Predictions are published to Kafka for the data platforms to consume, and data owners are notified weekly to verify the tags. Nothing waits for a human before the write. Grab reports more than 20,000 entities scanned within a month of rollout and that, for tables owners acknowledged, users changed less than one tag on average.

Instacart's catalog extraction sits between the two: low-confidence values go to human auditors, who correct them before ingestion, and the rest flow straight in.

What separates the three designs is the cost of a wrong write. A wrong PII tag on a table is cheap to correct next week. A wrong amount posted to an ERP that will pay it, or that cannot amend a posted invoice, is not. **Gate before the write when the write is expensive to reverse; verify after the write when it is cheap to correct.** That one decision sets the reviewer headcount, the latency floor and whether the pipeline can run in a batch window at all.

## Reading the page: OCR text or native PDF

Claude accepts PDFs directly: the docs say each page is converted to an image and its extracted text is provided alongside. Text costs 1,500 to 3,000 tokens per page depending on density, and the page image is charged by the vision rules, which on Claude count 28-pixel patches: ⌈width / 28⌉ × ⌈height / 28⌉ visual tokens, capped at 4,784 per image on the high-resolution tier (Claude 4.7 and later) and 1,568 on the standard tier. Other model families count image tokens differently, so every figure here is Claude-specific. A request is limited to 32 MB and 600 pages (100 when the context window is under 1M tokens), and encrypted or password-protected PDFs are not accepted, which makes the encryption check a preprocessing rule rather than a model error.

The docs do not state the resolution at which a page is rendered, so the image cost per page is known only up to the tier's cap. The Bedrock section of the same page gives approximate totals for Amazon's Converse API: about 1,000 tokens for a 3-page PDF in text-only mode and about 7,000 with page images, for Claude models on Bedrock up to Opus 4.6.

The trade is visible in Uber's model comparison. Headers are easy in any representation; line items in tables are where models failed. Page images carry the table layout that extracted text loses, at a cost of up to a few thousand tokens per page. The common middle design sends extracted text first and adds page images only for pages with tables, or only for documents whose line items failed validation.

## Cost and throughput per document

Take a stated workload: 30,000 invoices a day, 4 pages on average, a 2,000-token prefix of instructions and schema, 1,200 output tokens of JSON, Sonnet 5.5 on the Build tier. Sonnet 5.5 is a high-resolution-tier model, so a page costs at most 3,000 text tokens plus 4,784 image tokens.

Batch prices are $1 per million input tokens and $5 per million output tokens. The text rows assume your OCR yields about as many tokens as Claude's own text extraction and leave the OCR bill out, so they are a lower bound on that route. Output is 15% to 43% of the per-document cost, which is why trimming the JSON (no echoed source text, short keys for line items) moves the bill as much as dropping page images on sparse documents.

Throughput is bounded by different limits on each lane. In a batch, the 256 MB cap binds long before the 100,000-request cap when each request carries a PDF.

Both numbers feed the review side: if 20% of 30,000 invoices route to people, 6,000 review tasks a day arrive at the speed of the extraction lane, and the reviewers' throughput, not the model's, sets the end-to-end latency.

## Validation is the cheapest confidence signal

Business rules give field-level evidence that does not come from the model. Rules that cross-check fields catch exactly the errors that page reading produces: a line item read twice, a row shifted onto the next amount, a tax line read as a product.

```python
from decimal import Decimal

def validate_invoice(inv, vendor_ids, tol=Decimal("0.01")):
    """Returns (field, reason) pairs; an empty list means every rule passed."""
    issues = []
    if not inv.get("lines"):
        return [("lines", "no line items extracted")]   # fail closed, not open
    lines = sum((Decimal(l["amount"]) for l in inv["lines"]), Decimal("0"))
    if abs(lines - Decimal(inv["subtotal"])) > tol:
        issues.append(("lines", f"lines sum to {lines}, subtotal is {inv['subtotal']}"))
    total = Decimal(inv["subtotal"]) + Decimal(inv["tax"])
    if abs(total - Decimal(inv["total"])) > tol:
        issues.append(("total", f"subtotal + tax = {total}, total is {inv['total']}"))
    if inv["vendor_id"] not in vendor_ids:
        issues.append(("vendor_id", "not in the vendor master"))
    return issues

inv = {"vendor_id": "V-118", "subtotal": "1200.00", "tax": "96.00", "total": "1296.00",
       "lines": [{"amount": "800.00"}, {"amount": "400.00"}, {"amount": "400.00"}]}
print(validate_invoice(inv, {"V-118"}))
# [('lines', 'lines sum to 1600.00, subtotal is 1200.00')]
```

A rule failure is a better routing signal than a low model score because it names the field and the reason, which is what the reviewer needs on screen. Route on rule failures first and on confidence second. The [batch extraction lab](/labs/batch-extraction) builds this validator, a batch submitter that accounts for every document, a confidence score and a review threshold into one pipeline.

<p>Synchronous extraction, not batch, because a 24-hour window cannot meet a four-hour target. Gate before the write, because the ERP cannot amend. Route to review on any rule failure, on low field confidence and on amount over $10,000, and write back idempotently on vendor id plus invoice number. The reviewers are the bottleneck, so the routing thresholds are set from their capacity at month-end, and the four-hour promise holds for auto-accepted invoices only.</p>

<Fragment slot="long">
<p>Lanes: synchronous calls for new invoices; a batch lane for reprocessing after a prompt or schema change, where nobody is waiting. Reading: text first, page images for pages with tables or after a line-item rule failure, since line items are where Uber's published comparison shows models failing.</p>
<p>Routing has three inputs. The amount rule is fixed by the controller. Rule failures are mandatory. Confidence is the adjustable one, and it is the only lever left when month-end volume exceeds what six reviewers clear in four hours. I would measure minutes per review in the first two weeks, compute the month-end review capacity, and set the confidence threshold so the predicted review load fits it, rather than the reverse.</p>
<p>What I give up, in writing: on month-end days, invoices routed to review can miss four hours; the rollout plan states the expected count and the trigger for adding temporary reviewers (review queue age over two hours). The failure mode of the design is that rule failures cluster on a few vendors with odd templates; those vendors' invoices will be reviewed every time until someone fixes their template handling, and the dashboard should show review load by vendor so that is visible.</p>

## When this is wrong

The eight stages assume each document stands alone. Contracts with exhibits, invoices that reference purchase orders in another system and statements that summarise other documents need a join stage before extraction, and the confidence of a field then depends on a document the pipeline did not read.

The cost table assumes page count is the cost driver. Dense pages can fill the context window before the page limit, as the PDF docs warn, and a 200-page document may need splitting into sections, which reintroduces a join across sections for any field that spans them.

The gate-or-verify rule assumes the cost of a wrong write is known. Often it is not until the first incident: a tag that seemed cheap to correct can feed an access-control decision. Ask the owner of the system of record what a wrong row costs before choosing the side of the write the human sits on.

And at low volume the pipeline is the wrong tool. A few hundred documents a month with a reviewer who sees every one may be cheaper as a review UI with model prefill than as eight stages with their own monitoring.
