## The decision being made

An approval is an authorisation decision: principal R permits action A with arguments X, on behalf of requester U, within run Y. Treat it with the same care as any other grant in the system. The pause mechanics from the previous lesson tell you where execution stops; they say nothing about whether the person who resumed it was allowed to, whether they saw what will execute, or whether the decision can be used twice. The OpenAI Agents SDK is unusually explicit that these are yours: its docs state that `RunState.from_json()` and `RunState.from_string()` "do not authenticate the snapshot or the person submitting it", and that "approval permits a tool call to execute; it does not guarantee exactly-once execution."

A complete design answers six questions, and each has a default that is wrong in production: which calls pause, who may decide, what the reviewer sees, where the pending state lives, what a second or concurrent decision does, and what happens when nobody decides.

## Which calls pause

OpenAI's practical guide to building agents names two triggers for human intervention: exceeding failure thresholds (an agent that fails to understand intent after multiple attempts, or exceeds a retry or action limit), and high-risk actions that are "sensitive, irreversible, or have high stakes", with cancelling orders, authorising large refunds and making payments as its examples. It also suggests rating each tool low, medium or high from four inputs: read-only versus write access, reversibility, the account permissions it needs, and financial impact.

The two triggers lead to different mechanisms. A failure threshold is an escalation: the agent hands the case to a person, and there is no single call to approve. A high-risk action is a gate on a specific call. Rate the call, not the tool. A refund tool is low risk at a small amount to the original payment method and high risk at a large amount to a new account, so the gate is a function of parsed arguments, which is what `needs_approval` as a callable gives you. Keep the property the SDK documents for it: when arguments cannot be inspected, it fails closed and asks a human.

## Who may decide

Identity comes from your authentication middleware, never from the request body. Authorisation is per run and per pending call; the SDK docs put it as "possession of a run ID or decision ID is not authorization." That rules out the common shortcut of emailing a link that carries the decision id. Dify's email delivery works exactly this way by design (anyone holding the link can respond, no Dify account needed), which is acceptable for a content review and not for a payment.

Separation of duties needs a definition of the requester that fits an agent. The user on whose behalf the agent acted is a requester, and so is anyone who could steer the agent's input, which includes the author of the email or ticket the agent was reading. A support agent approving a refund that the agent proposed from that same agent's own ticket is a reviewer and a requester at once. For amounts above a threshold, two distinct reviewers, neither of them the requester, is the four-eyes rule; the authority to approve should scale with the amount, the same way spending limits do in the finance system the refund lands in.

## What the reviewer sees

Show the exact arguments that will execute, read from the server's pending item (`state.get_interruptions()` in the SDK), not a model-written summary of them. The summary is produced by the same model, from the same context, that proposed the action; an injected instruction that produced a refund to a new account can also produce a summary that calls it "the customer's usual card". Flowise's Human Input node can generate its description with an LLM, which is convenient for low-risk steps and the wrong source of truth for a high-risk one. A model summary can sit next to the arguments as an explanation, labelled as such.

Exact is necessary but not sufficient. A raw account number is exact and unreviewable; resolve it against the system of record and show the holder name and whether it is on file for this customer. The SDK docs add two rendering rules: treat tool names and arguments as untrusted display content and escape them in HTML, and send the reviewer only the details they are authorised to see plus opaque decision identifiers.

Then bind the decision to what was shown. Store a digest of the canonical arguments with the pending item, render it with the form, and require the decision to carry it back. If the run re-planned and the arguments changed between display and click, the digests differ and the decision is refused, so "approved A, executed B" cannot happen.

## Where pending state lives

Keep the full run state in server-controlled storage, keyed to the run, and accept from the client only a decision about an item the server already holds. The SDK docs list what does not make an untrusted snapshot safe: overriding context, setting `strict_context=True`, or deleting approval records from it. They also note that anything put in the run context travels with the serialised state, so a snapshot stored client-side carries whatever secrets the tools needed.

LangGraph keeps the checkpoint on the server by construction, but the resume value is whatever the caller sends, and it becomes the return value of `interrupt()`. A `response_schema` (langgraph 1.2.12 and later) checks the shape of that value, not who sent it. The endpoint that calls `Command(resume=...)` is the authorisation point and needs the same checks as any other write endpoint.

## Replays, races and sticky grants

A double click, a retried HTTP request, a sweeper that rejects stale items, and a second reviewer opening the same link are four routes to two decisions on one item. The SDK docs prescribe "atomic owner-checked transitions"; in practice that is a single conditional update from `pending` to a terminal state, guarded by the reviewer's authority and the arguments digest. The caller whose update changed a row resumes the run; every other caller gets a conflict and resumes nothing.

```python
import hashlib, json, sqlite3, time

def digest(tool, args):
    canon = json.dumps({"tool": tool, "args": args}, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canon.encode()).hexdigest()

db = sqlite3.connect(":memory:")
db.execute("""create table pending (id text primary key, run_id text, tool text, args text,
              digest text, requester text, status text, reviewer text, decided_at real)""")

def open_item(item_id, run_id, tool, args, requester):
    db.execute("insert into pending values (?,?,?,?,?,?,'pending',null,null)",
               (item_id, run_id, tool, json.dumps(args), digest(tool, args), requester))

def decide(item_id, reviewer, approved, shown_digest, may_approve):
    # reviewer comes from the auth middleware, never from the request body
    row = db.execute("select tool, args, requester from pending where id=?", (item_id,)).fetchone()
    if row is None or reviewer == row[2] or not may_approve(reviewer, row[0], json.loads(row[1])):
        return "forbidden"
    cur = db.execute("""update pending set status=?, reviewer=?, decided_at=?
                        where id=? and status='pending' and digest=?""",
                     ("approved" if approved else "rejected", reviewer, time.time(),
                      item_id, shown_digest))
    db.commit()
    return "recorded" if cur.rowcount == 1 else "conflict"

open_item("it-1", "run-9", "refund", {"order": "A17", "amount_cents": 4200}, "user-3")
d = digest("refund", {"order": "A17", "amount_cents": 4200})
ok = lambda who, tool, args: who.startswith("fin-")
print(decide("it-1", "fin-7", True, d, ok))   # recorded
print(decide("it-1", "fin-8", True, d, ok))   # conflict: already decided
```

Only the `recorded` caller calls `Runner.run(agent, state)` or `Command(resume=...)`. For two approvers, the row needs a second reviewer column and the transition to `approved` happens on the second distinct decision, still as one conditional update.

Sticky decisions are a replay surface of their own. `always_approve=True` turns one approval into a standing grant for every later call to that tool identity in the run, and for the SDK's shell and file-edit tools that identity is tool type and name, so the grant crosses handoffs to other agents. A sticky approval is a policy change and deserves the reviewer's explicit consent to that scope, not a checkbox next to "approve".

## Approval does not make execution exactly-once

The approved call runs at least once, not exactly once: a crash after the destination accepts the call and before the run records the result re-runs the tool on recovery. Durable execution engines give the same at-least-once guarantee per step. Exactly-once outcomes need a stable idempotency key on every write the tool makes, where the destination supports one, and a reconcile step (read the destination's state before retrying) where it does not. Derive the key from the decided item (`it-1` above), never from the attempt, so every retry presents the same key.

## When nobody decides

A timeout has three possible outcomes: reject, escalate, or auto-approve. Auto-approval converts reviewer unavailability into authorisation, and the moments reviewers are unavailable (nights, holidays, incidents) are the moments an attacker who can trigger the action would choose. For anything that moves money, the terminal state after escalation is reject with a notice to the requester. Dify's default is close to this: a request expires after 3 days, and if no timeout branch is wired the workflow ends. LangGraph's interrupt API and the Agents SDK provide no timeout, so the policy is code you write and test.

## When this is wrong

An approval is a control only if the reviewer can evaluate the arguments. A long patch or a raw SQL statement is exact and still unreviewable in the time a queue allows; for those, deterministic checks (allowlisted statements, diff size limits, tests that must pass) carry more of the weight and the human reviews what the checks flag. When reviewers approve without opening the detail, the step has become ceremony, and hard limits on amount, rate and destination do more than another reviewer.

For high-volume, low-value, reversible actions, a blocking gate can cost more in delay than the losses it prevents. Executing immediately under a spend cap and sampling decisions for review afterwards is a defensible design there, provided the cap is enforced outside the model and the sampled errors feed back into the gating rule.

The design here assumes the approval service and its database are trusted. An insider who can write to the pending table can approve anything; the separate append-only decision log and a reconcile against executed actions are what detect that, not the transition logic.
