## What it is and who runs it

Duolingo's engineering organisation runs internal coding and operations agents (fixing CI failures, addressing code review comments, a Slack bot that composes agents to help release managers investigate crashes) on a shared platform built on Temporal. Two posts on Duolingo's engineering blog describe it. The first, from December 2025, covers a single agent that removes stale feature flags and the Temporal patterns the team settled on. The second, from August 2026, describes the platform that generalised those patterns: an agent registry, one workflow that wraps every agent run, tool calls as activities, and evals that run as workflows.

The problem the platform addresses is stated plainly in the second post: each team was rebuilding the same infrastructure (MCP server setup, credentials, repository cloning, project context), and what one team built could not easily be reused by another. The platform's answer is to make an agent a definition, and to make everything around the model call shared code on a durable engine.

It is a useful case for this module because it is a workflow platform whose steps happen to be agents, which is the shape most production agent systems end up in.

**Callers.** An agent can be started from Slack, internal sites, a CLI or another Temporal workflow, and every caller passes the same two things: an agent name and a prompt. Making "another workflow" a first-class caller is what lets agents compose, as in the release-manager bot that combines specialised agents.

**Agent registry.** An agent is a definition: name, description, owner, system prompt, model, the MCP servers it may use, the repositories cloned into its workspace, and an output type. The post's example is an `incident_summary` agent using `gpt-5.5` with GitHub and Sentry MCP servers and a typed output. The owner field matters operationally: every definition names who answers for it.

**AgentWorkflow.** The post says the wrapper's goal is not to be the agent itself. It does four things: load the definition, prepare the execution environment, run the agent through a provider SDK, and return the output. Temporal was chosen because agent runs take minutes, call external tools, may wait for human input and need retries. Temporal queries expose the run's status while it executes, so a Slack thread or an internal page can show progress without a separate status store.

**Workspace activities.** Side effects such as preparing a workspace, cloning repositories and saving results are activities. Activities are where Temporal applies retry policies and where results are recorded in history, so a retried run does not redo work that already completed.

**Agent runtime.** Three runtimes sit behind the same workflow: the platform started with the Claude Agent SDK and Codex CLI, and the post says adding the OpenAI Agents SDK later did not change how agents are defined or invoked. The runtime is a plug-in point, not part of an agent's identity.

**MCP tool calls as activities.** With Temporal's plugin for the OpenAI Agents SDK, MCP tool calls become Temporal activities with the same retry policies and failure handling as other activities, and each call's inputs, outputs, failures and retries are visible in the Temporal UI. Temporal's own documentation for the plugin adds that model calls also run as activities, so they retry durably and are not repeated when the workflow replays. That granularity applies to the OpenAI Agents SDK runtime; the posts do not say how fine-grained the other two runtimes are.

**LLM gateway.** Model traffic goes through an internal gateway that provides cost tracking, usage tracking and provider abstraction. The post notes the OpenAI Agents SDK can be pointed at the gateway through a proxy, so switching providers happens behind one interface.

**Eval suite workflow.** Evals run the real agent against authored scenarios and capture its output, changed files and git diff before grading. The suite is itself a workflow: it loads cases, starts a child workflow per case and repetition, runs repetitions in parallel, aggregates results, renders a report and can save runs for a dashboard.

The flag-removal agent from the December 2025 post predates the platform and shows the coarser shape that came first.

**Flag-removal agent in one activity.** The second activity clones the repository into a temporary directory, runs Codex CLI as a Python subprocess, and, if the agent changed anything, opens a pull request assigned to the person who asked. The post gives the reason all three live in one activity: in Temporal each activity may run on a separate worker, so cloning in a separate activity would leave the agent operating on an instance that does not have the code. The agent runs on an ECS instance separate from other Temporal tasks, which the team says makes bypassing Codex's approvals and sandbox safer.

## Context strategy

An agent's context is fixed by its definition: a system prompt, the repositories cloned into its workspace and the MCP servers it may call. The flag-removal post explains a preference for local code over remote access: most AI coding tools work efficiently on a local checkout, and a GitHub MCP server is unnecessary for tasks that do not involve open PRs or history, so git operations happen before the agent is called. The same post describes the prompt evolving from three prompts run in loops (in a LangChain version with an internal toolset, and a fast-agent version with the GitHub MCP server) to a single prompt once Codex was available.

## Tools and permission model

Tools are scoped per agent by listing MCP servers in the definition. Running MCP calls as activities puts every tool call on a durable, retried and inspectable path, and also records tool arguments and results in workflow history, which then becomes data with retention implications.

For the flag remover, the permission boundary is the machine, not the agent: Codex CLI runs with its approvals and sandbox bypassed on an ECS instance kept separate from other Temporal tasks. The posts do not describe how credentials reach MCP servers or agents beyond naming credential setup as one of the jobs the platform took over.

## Cost and latency

The posts give no cost or latency figures. Runs are described as taking minutes. Cost and usage are tracked through the LLM gateway, with no numbers published. The figures that are published are about engineering time and are Duolingo's own: the flag remover took about a day to prototype and about a week to productionise, and the platform post says creating a production-ready agent went from several weeks to about 10 minutes.

## Failure modes

**Non-deterministic agents.** The flag-removal post lists what a prompted agent does when it goes wrong: crashes, produces no changes, hangs or fails to complete. The post gives three reasons for choosing Temporal: easy local testing for prompt iteration, strong retry logic for that non-determinism, and composing several activities into one workflow. Retrying a whole agent run is the coarse remedy; the platform's activity-per-call shape lets a failed tool call retry without re-running the model calls before it.

**Side effects inside a retried activity.** Durable execution is at-least-once per activity. In the coarse shape, the activity that opens a pull request also clones and runs the agent, so a failure after the PR is created and before the activity completes would retry the whole activity. The posts do not say how a duplicate PR is prevented. This is the question to ask of any design that puts an external effect inside a long activity: what is the idempotency key, and who checks it.

**Claims that do not match the diff.** The `no_op_consistency` grader exists because an agent can say it changed nothing while files changed, or claim a fix with an empty diff. Deterministic graders (`structured_output`, `diff_assertions` and `no_op_consistency`) are the base, with an optional LLM judge where exact assertions are too brittle; the post says the team does not want its only signal to be one model judging another.

**Unvalidated output.** At the time of the December 2025 post, flag-removal PRs were sent without running CI, pre-commit or tests first; the stated plan was to run them before sending, or to mark PRs that need manual work. Codex CLI also could not return structured JSON, so output format relied on prompting.

## What is not public

The posts do not publish run counts, failure rates, retry counts or how often agent runs end with no change. They give no timeouts, retry policies or heartbeat settings for any activity. They do not say where the registry is stored, how credentials are issued to MCP servers, whether platform runs execute in containers or sandboxes, or how fine-grained the Claude Agent SDK and Codex CLI runtimes are inside AgentWorkflow. Eval repetition counts, pass thresholds and how results gate a change are not described. There are no cost or latency numbers. Anything said about these in an interview is a design proposal, not a description of Duolingo's system.

## Interview questions

<Callout kind="interview" label="Interview question">
**"Duolingo clones the repository, runs the agent and opens the pull request in one Temporal activity. Defend or change that design for a platform where workers do not share disks and agents take several minutes."**
</Callout>

<Depth>
<Fragment slot="short">
<p>Keep the clone and the agent run together, because the checkout is local state and a separate activity may land on a different worker. Change the PR step: make it its own activity that pushes from a deterministic branch name derived from the run, or keep it in the same activity but make creation idempotent by looking up an existing PR for that branch first. The cost of one big activity is that any failure retries the clone and the whole agent run, so heartbeats and a timeout sized to the agent are required.</p>
</Fragment>
<Fragment slot="long">
<p>The constraint is data locality. Temporal schedules each activity on any worker polling the task queue, so local disk does not survive between activities. Three ways out: one activity for everything (Duolingo's choice), worker-specific task queues so follow-up activities are routed to the same host, or moving state off the disk by pushing the agent's changes to a branch before the activity ends.</p>
<p>The push option splits the work cleanly. Activity one clones, runs the agent and pushes to a branch named from the workflow and run ids. Activity two opens the PR from that branch, which needs no checkout and is idempotent if it first checks for an existing PR on the branch. A retry of activity two cannot create a second PR, and a retry of activity one force-pushes the same branch.</p>
<p>What remains expensive is retrying the agent. A run that crashes after several minutes of model calls repeats them all unless model calls are activities, which is what the OpenAI Agents SDK plugin provides and the CLI subprocess shape does not. That is the trade the platform post makes in moving from the coarse shape to activities per call.</p>
</Fragment>
<Fragment slot="followups">
<ul>
<li><em>The agent run is the expensive part. How do you stop a retry from paying for it twice?</em> Make model calls activities so completed calls come from history, or checkpoint the agent's transcript and resume from it; the CLI subprocess shape offers neither.</li>
<li><em>Tool calls as activities put arguments and results in workflow history. Who decides retention?</em> The platform team sets history retention per namespace with security; tools that return secrets or personal data need payload encryption or a reference instead of the value.</li>
<li><em>When is one coarse activity the right answer?</em> When the run is short, the effect at the end is idempotent, and the team needs it working this week; the flag remover went from prototype to production in about a week in that shape.</li>
</ul>
</Fragment>
</Depth>
