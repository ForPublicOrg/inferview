## Four layers, each catching a different bug

A workflow with model steps has four kinds of defect that service tests miss: a step that mishandles a model response, a code change that no longer matches the history of runs in flight, a branch that only executes after a long timer, and a side effect that happens twice when a worker dies at the wrong moment. Each needs its own layer.

| Layer | Catches | Runs against | Cost per CI run |
|---|---|---|---|
| Step tests with recorded model responses | parsing, validation, routing on a known output | fixtures | no model calls |
| Replay of recent histories | non-deterministic changes to workflow code | exported production histories | no model calls, no activities |
| Time skipping | timeout and escalation branches | a test server with a virtual clock | no real waiting |
| Crash injection | duplicate or missing side effects | a fake provider that counts effects | one run per crash point |

Model quality is a fifth concern and belongs to evals; this lesson ends where the evals track starts, with one exception covered below: running evals as workflows.

## Layer 1: steps against recorded responses

A model step is an activity (or node, or step function) that calls a model and returns a validated value. Test it with the model call replaced by a recorded response; Temporal's docs require a mocked activity to keep the real activity's name and input and output signature.

Fixtures are real responses from production or staging, stored with the model id, prompt version and date. Include the ugly ones: a response that fails schema validation, a refusal, a truncated output with a length finish reason, an answer in the wrong language. Most workflow bugs are in what the step does with those, not in the happy path.

Recorded responses go stale on a model upgrade: re-record a sample as part of the upgrade change and diff the new responses against the old before regenerating the rest.

## Layer 2: replay, and its three meanings

Three engines use the word replay for three different operations.

| Engine | What "replay" does | Re-executes side effects? |
|---|---|---|
| Temporal `Replayer` | re-runs workflow code against a recorded event history to check the code still produces the same commands | no: activity results come from the history |
| LangGraph time travel | resumes from a saved checkpoint and runs every node after it | yes: nodes after the checkpoint re-execute, including LLM calls, API requests and interrupts |
| Inngest Replay | starts new executions of failed runs in bulk after a fix | yes: the docs warn that charges, messages or records could repeat |

Only the first is a test. Temporal's version succeeds only if the new workflow definition is deterministically compatible with the history, and raises an error otherwise. It is the CI check for "this change is safe for runs already in flight". The documented recipe has four steps: find the workflow types or task queues the changed worker code targets, download histories of representative recent open and closed runs for each, replay them, and fail CI on any error. Passing `fail_fast=False` to `replay_workflows` reports every failing history instead of the first. Replaying production histories needs Advanced Visibility to list them (server 1.18 or later).

LangGraph's time travel is a debugging and recovery tool: nodes after the checkpoint re-execute and may return different results, and `update_state` forks from a checkpoint rather than rolling the thread back. As a regression test it spends tokens, calls tools for real and is non-deterministic. If your graph needs a determinism test, the equivalent is a test that loads saved checkpoints into the new graph and asserts that the next node and the state schema still line up, with every node after it mocked.

Inngest's Replay is an operation, not a test: the docs present it as recovering many affected runs after an incident without restarting them one by one, and tell you to check idempotency before running it, because each replay is a new execution. That makes the crash-injection layer below a precondition for using it safely.

## Layer 3: time skipping

A refund workflow that waits three days for an approval and then escalates has a branch nobody will exercise by waiting. Three days is 3 times 86,400, or 259,200 seconds of wall-clock time per test.

Temporal's `WorkflowEnvironment.start_time_skipping()` starts a test server that fast-forwards timers, including sleeps and condition timeouts, except while activities are running. `env.sleep(seconds)` advances the clock by a chosen amount when the test needs to land between two timers, for example to send the approval signal one hour before the deadline and assert that escalation never fires. `start_local()` runs a full local server with real time, for tests where the timer is not the point.

Time is global to one environment. Tests that skip time automatically can run in parallel against one server; tests that advance time manually must run in series or each get their own server. Mixing them in one parallel suite produces failures that depend on test order.

## Layer 4: crash injection

Durable execution is at-least-once per step. An engine that records "activity completed" after the activity returns will re-run the activity if the worker dies between the side effect and the record. Exactly-once outcomes come from an idempotency key the provider deduplicates on, never from the engine or from a human approval in front of the step.

Crash injection makes that testable. For each step, kill the run at three boundaries: before the step starts, after its external effect but before the engine records the result, and after the record. Then resume and assert two invariants: every step completed, and every external effect happened exactly once at the provider.

The harness fits in the standard library. The journal stands in for the engine's history and survives the crash; the fake provider deduplicates on the idempotency key, as a payment API with idempotent requests does.

```python
import itertools

class Crash(Exception):
    pass

class FakePayments:
    def __init__(self):
        self.refunds = {}     # idempotency key -> amount, as the provider stores it
        self.calls = 0        # every request that reached the provider
    def refund(self, key, amount):
        self.calls += 1
        self.refunds.setdefault(key, amount)
        return {"refund_id": "r-" + key}

STEPS = ["load_order", "classify", "await_approval", "issue_refund", "notify"]
BOUNDARIES = ["before", "after_effect", "after_record"]

def run(run_id, journal, payments, crash_at=None):
    for step in STEPS:
        if step in journal:                       # resumed: result already recorded
            continue
        if crash_at == (step, "before"):
            raise Crash
        if step == "issue_refund":
            result = payments.refund(key=f"{run_id}:{step}", amount=4200)
        else:
            result = {"ok": True}
        if crash_at == (step, "after_effect"):
            raise Crash
        journal[step] = result
        if crash_at == (step, "after_record"):
            raise Crash

for point in itertools.product(STEPS, BOUNDARIES):
    journal, payments = {}, FakePayments()
    try:
        run("run-1", journal, payments, crash_at=point)
    except Crash:
        pass
    run("run-1", journal, payments)               # the worker restarts and resumes
    assert set(journal) == set(STEPS), point
    assert len(payments.refunds) == 1, point
    if point == ("issue_refund", "after_effect"):
        assert payments.calls == 2                # at-least-once reached the provider twice
print("15 crash points: every run completes with one refund")
```

Change the key to something generated per attempt (a fresh UUID inside the step) and the `after_effect` case fails with two refunds. That assertion is the reason the layer exists; `notify` needs the same treatment against the email provider. The [workflow engine lab](/labs/workflow-engine) builds this journal into an engine step by step and ends with the same crash sweep.

## Golden traces

A golden trace is a recorded run whose structure is the assertion: which steps ran, in what order, which tools were called with which argument shapes, how many model calls each step needed and which branch the router took. It is stored as data (from the engine's history or from spans) and compared structurally, never on generated text.

Golden traces catch regressions that pass every step test: a prompt change that makes the classifier escalate a category it used to handle, a tool dropped from the list in a refactor, a step that now needs three attempts. Keep a small set per workflow covering each branch, and refresh them in reviewed changes, never automatically.

## Evals as workflows

Duolingo runs its agent evals as a Temporal workflow: the suite starts a child workflow per case and per repetition, runs repetitions in parallel, aggregates results and renders a report. Its graders are deterministic first: `structured_output` checks fields in the agent's structured response, `diff_assertions` checks the repository diff for required or forbidden changes, file counts or paths, and `no_op_consistency` fails a run whose output says nothing changed while files did, or claims a fix with an empty diff. An LLM judge is optional, for cases where exact diff assertions are too brittle; the post says the team does not want its only signal to be one model judging another model's work.

Running evals on the production engine gives them the same retries, timeouts and visibility, and lets CI, a schedule or a release workflow start the same suite.

## The CI gate for the refund workflow

| Trigger | Runs | Blocks merge when |
|---|---|---|
| Every change | step tests on fixtures; crash matrix under time skipping; timer branches under time skipping | any assertion fails |
| Change to workflow code | replay of recent open and closed histories for the changed task queue | any history fails to replay |
| Change to a prompt, model or tool list | golden-trace structure diff; eval suite on recorded inputs with deterministic graders | structure diff is not approved; a grader regresses beyond the agreed margin |
| Release | eval suite with repetitions on live model calls | owner sign-off on the report |

The first two rows make no model calls; the live eval runs once per release, which keeps the CI bill flat.

## When this is wrong

Replay checks determinism against the histories you fed it and nothing else. It says nothing about whether the new code is correct, and a history that predates a versioned branch only tests the old path. A replay suite built only from closed runs misses the case that matters most, open runs with timers pending.

Recorded responses make step tests fast and cheap and also make them blind to the model. A suite that never calls a model passes the day the provider changes behaviour. The eval suite on release is the only layer that sees it.

The crash harness here simulates a crash as an exception in one process. Real failures also include a provider that accepted the request while the client timed out, a network partition between worker and provider, and a deploy that kills every worker at once. Those need the same invariant tested against a fake provider over a real network boundary, or fault injection in a staging environment.

Time skipping does not skip time inside activities. An activity that sleeps or polls with real timeouts still takes real time, and a test that mocks it away no longer tests its timeout handling.

For durable-execution internals, determinism rules and versioning, see the [durable execution module](/learn/workflows/durable-execution).
