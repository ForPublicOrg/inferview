## The decision

An operations team asks to build a workflow with model steps in a visual tool instead of waiting for engineering. The decision is not about taste or about which canvas is nicer. It is whether the tool can carry the properties this particular workflow needs (durability, tests, versioning, review, tenancy and a licence that permits the use) and, if only some steps need them, where to cut the workflow so each part runs where it fits.

Low-code wins for internal automations owned by operations, with few steps and a human downstream who will notice a bad output. Code wins when the workflow is the product, needs tests that block a deploy, serves more than one tenant, or moves money. Most real requests are mixed, and the useful answer is usually a split.

## The inputs that change it

**Who owns it on a bad day.** A flow edited by the operations team at 4 pm is debugged by whoever is paged at 2 am. If that is an engineer who has never opened the tool, the ownership is not real. The first input is the name of the team that will be paged.

**Durability.** What happens to a run when the process restarts mid-flow, and to a run waiting on a human for two days. n8n in queue mode separates a main instance, which receives triggers and creates executions without running them, from workers that run them, with Redis as the broker and a database for state; the docs say a distributed setup over SQLite is not supported. Flowise's Agentflow V2 docs say human-in-the-loop checkpoints are saved so a workflow can resume after an application restart. Neither is the same contract as a durable execution engine that replays a recorded history, and the difference shows up in the at-least-once behaviour of side effects.

**Error semantics.** Dify's LLM, HTTP, Code and Tool nodes offer three behaviours on failure: stop the workflow (the default), continue with a default value, or run a fail branch, with `error_type` and `error_message` available downstream. Its iteration node has three modes, and two of them change data silently: `continue-on-error` puts `null` in the output for a failed item, and `remove-abnormal-output` drops failed items so the output can be shorter than the input. A batch step that reconciles by position will mismatch records without raising anything. Whoever configures that node is making a data-integrity decision on a dropdown.

**Testing.** Can a change be tested before it runs on real inputs, and can a failing test block the change. None of the tool pages cited here describe a test harness that blocks a deploy; Flowise's docs add that features and node parameters may change between versions. If the workflow needs the test layers from the previous lesson (replay, crash injection, time skipping), that requirement alone points to code.

**Versioning and review.** Where the flow definition lives, whether a change is a diff someone approves, and whether you can roll back to last Tuesday's version. Ask the vendor or check your plan's features before deciding; if the history of the flow lives only in the tool's database, a review process has to be built around it.

**Tenancy.** One internal team, or many customers each with their own configuration. This is where the licences bite.

**Licence.** Read the text, not a summary.

- n8n's Sustainable Use License limits use and modification to "your own internal business purposes" or non-commercial and personal use, and distribution to free-of-charge, non-commercial purposes. Files with `.ee.` in the name need an Enterprise licence. n8n's licence FAQ reads "internal business purpose" broadly: n8n inside your product as a silent backend engine is allowed, and so is running pre-built workflows where end users connect their own accounts. Letting external users build or configure workflows through your product is not. The FAQ's test is who controls the workflow logic.
- Dify's licence is Apache 2.0 with added conditions. Commercial use is allowed, including as a backend service, but operating a multi-tenant environment from the Dify source needs written authorisation, with one tenant defined as one workspace, and the console's logo and copyright may not be removed. Contributors also agree the producer can make the licence stricter or more relaxed, so the terms you accept today are not fixed.
- Zapier Agents is a hosted product, so the question is the contract and the usage limits, not a source licence.

**Usage limits on hosted tools.** Zapier meters agents in activities: a trigger, an answer from a knowledge source, an action, a page browse and a web search each count as one. The help centre article updated on 1 October 2026 lists 400 activities a month and 10 per run on Free (where test runs count), and 1,500 a month and 40 per run on Pro (where they do not). At the limit, agents stop running actions and receiving triggers.

## The options and when each wins

**n8n** wins for internal automations that integrate many SaaS systems, owned by an operations or platform team that can run (or pay for) the infrastructure. Self-hosted at scale means queue mode with Redis and a database other than SQLite, workers that share the main instance's encryption key to read stored credentials, and object storage for binary data, since the docs say filesystem binary storage is not supported in queue mode. High availability for the main instance (multi-main) is a self-hosted Enterprise feature that requires every main process in queue mode on Postgres and Redis. It loses when external users need to build or configure their own flows, which the licence FAQ rules out without a commercial agreement.

**Dify** wins for internal LLM applications where the model steps, prompts and knowledge bases are most of the work and one workspace serves one organisation. Its error-handling options are explicit enough to review, provided someone reviews the iteration modes. It loses when you would run it as a multi-tenant service from source, where the licence requires written permission.

**Flowise Agentflow V2** wins for prototyping agent graphs with human checkpoints: a Human Input node pauses the flow with one output path per reviewer decision and optional feedback, and flow state keys are declared up front in the Start node. Its Loop node has a Max Loop Count with a default of 5, a bound worth checking on every loop. Flow state lasts one run, so anything that must persist across runs needs its own store. It loses when the flow must be versioned, tested and reviewed like code, which its agent-flow docs do not cover.

**Zapier Agents** wins when the work is glue across hosted SaaS tools, nobody wants to run infrastructure, and volume fits the activity allowance. It loses on high volume, on anything that needs a test suite, and on steps where a per-run activity cap could stop a run halfway through.

**Code on a durable engine** (Temporal, LangGraph with a checkpointer, Inngest, or your own) wins when the workflow is the product, needs CI gates, serves many tenants, or moves money. It costs an engineering team that owns it, and it loses when the people who understand the process cannot change it without filing a ticket and the process changes weekly.

## Worked decision

Scenario: operations at a marketplace wants refund exceptions handled in n8n. A ticket arrives, a model summarises it and proposes an amount, a team lead approves in Slack, and the refund is issued through the payment provider. Operations has three people, no engineer on call for this flow, and a deadline at the end of the quarter. Finance requires that no refund is ever issued twice and that every refund above a ceiling has a named approver.

Constraints in conflict: speed and ownership favour n8n; the money step needs at-least-once handling with an idempotency key, a hard ceiling and an audit record, which a flow edited on a canvas cannot guarantee by review.

Decision: split at the money boundary. n8n, self-hosted for internal use, runs intake, summarisation, routing and the Slack approval; operations owns and edits it. The refund itself is a small code service owned by the payments team. It accepts an approval id, derives the idempotency key from the ticket and approval, enforces the ceiling and the approver rule, writes the audit record and calls the provider. n8n calls that service and nothing else touches the payment API.

What is given up: changes to the n8n half are not gated by tests in CI, so a bad prompt edit can route tickets wrongly until someone notices. Written down as accepted: misrouting is recoverable because a human approves every refund, and the service rejects anything outside policy regardless of what the flow sends.

Reversal triggers, agreed in advance: a second business unit or an external partner needs its own configuration of the flow; an incident traces to a flow edit that a review would have caught; or the flow grows past what one person can explain on a whiteboard. Any of these moves the orchestration to code, and the refund service does not change.

## What to measure after deciding

- Flow edits per month and incidents traced to an edit. This is the number that triggers the reversal.
- Requests the refund service rejects, by reason: duplicate key, ceiling, missing approver. A rising duplicate count means the flow is retrying; a rising ceiling count means the prompt or routing changed.
- Time from ticket to approval and from approval to refund. The first belongs to operations, the second to payments.
- Executions failing at each node, from the tool's own execution log.
- Requests from outside operations to edit the flow. The first one is the tenancy question arriving early.

## When this is wrong

Licence terms and plan limits change, and Dify's contributor clause says outright that the producer can change its terms. Every licence reading here was taken from the text on 28 October 2026. Before relying on one, read the current text and, for anything near the line, ask the vendor in writing; n8n's FAQ itself treats some shapes as grey areas.

The split assumes the money step can be isolated behind one interface. Some workflows move value in many places (credits, discounts, inventory holds), and each one needs the same treatment; past a handful, the split costs more than moving the orchestration to code.

The playbook treats low-code tools as untestable because the pages cited here do not describe a blocking test harness. A team that exports flow definitions to git, reviews them as diffs and runs them against a staging instance has built part of what code gives, and the argument shifts toward ownership and licence alone.
