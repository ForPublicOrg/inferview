## Three parts and one interface

Every vision-language model in production today has the same three parts, whatever the marketing diagram looks like. An image encoder turns pixels into a sequence of feature vectors. A projector maps those vectors into the embedding space of a language model. The language model reads the projected vectors as if they were token embeddings and generates text. The encoder is a lexer for pixels; the projector is the ABI between two separately built programs. The difference from a compiler front end is that both sides of the ABI are learned, and the training recipe decides which side moves to meet the other.

The question that separates architectures is not "which encoder" but "what was frozen while what was trained, on which data". That choice decides how much text capability the language model keeps, how much visual detail survives, and what the serving stack has to run per image.

## The encoder: patches, not pixels

The Vision Transformer (ViT) cuts an image into fixed squares and treats each square as a token. With patch side *P*, an *H* by *W* image becomes *N = HW / P²* patches. A 224 by 224 image with 16-pixel patches is 14 × 14 = 196 patches; the same image with 14-pixel patches is 16 × 16 = 256. Each patch is flattened, linearly projected, given a learned position embedding, and passed through ordinary transformer layers.

Two consequences matter at serving time. First, the sequence grows with the square of resolution: doubling both sides quadruples *N*, and full self-attention over *N* patches costs *N²* score computations per layer. Second, the ViT paper fine-tunes at higher resolution by keeping the patch size, accepting a longer sequence and interpolating the position embeddings in 2D. A fixed-resolution encoder trained at one size and run at another is relying on that interpolation.

ViT lacks the locality and translation biases of convolutions, and the paper's finding is that it generalises poorly from small datasets and wins when pretrained on large ones (ImageNet-21k with 14M images, JFT-300M with 303M). That is why nobody trains a VLM encoder from scratch on their own product images.

## How encoders learn to align with text: CLIP

CLIP trains an image tower and a text tower together on 400 million image and caption pairs scraped from the internet. For a batch of *N* pairs it computes the *N* × *N* matrix of image-text similarities and applies a symmetric cross-entropy: each image should pick its own caption out of the batch, and each caption its own image. With the paper's batch of 32,768, every step scores 32,768² − 32,768, about 1.07 billion, mismatched pairs against the 32,768 matched ones.

The paper chose this over predicting the caption's words because matching is a much easier target: it reports a further 4x gain in how efficiently zero-shot ImageNet accuracy improves with compute. The cost of that choice is visible in its limitations section. A contrastive objective rewards whatever distinguishes one caption from 32,767 others, and captions rarely state counts or fine-grained part names, so CLIP is weak at counting objects and at fine-grained classes such as car models. Every VLM that inherits a CLIP-style encoder inherits a version of that blind spot, which is why counting shows up again in the failure-modes lesson.

The largest CLIP ViT trained for 12 days on 256 V100s. You will reuse an encoder like this, not train one.

## The projector: LLaVA's ABI

LLaVA connects a pretrained CLIP ViT-L/14 to a pretrained language model with one trainable matrix *W* that maps patch features into the language model's word-embedding space. Training happens in two stages, and the freeze pattern is the design:

1. **Alignment.** 595K image-caption pairs filtered from CC3M. Encoder frozen, language model frozen, only *W* trains. This teaches the projector to emit vectors the frozen language model already knows how to read.
2. **Instruction tuning.** 158K instruction-following samples. Encoder still frozen; *W* and the language model train.

Freezing the encoder keeps its visual features intact and makes the run cheap. Training the language model in stage 2 is what lets it follow visual instructions, and it is also where text capability can regress. One detail interviewers like: LLaVA takes features from the layer before the encoder's last, because the last layer is shaped by CLIP's contrastive objective. On ScienceQA the paper reports 90.92% with the penultimate layer against 89.96% with the last.

A ViT-L/14 at 224 px input emits (224 / 14)² = 256 patch features; at 336 px, (336 / 14)² = 576. In a LLaVA-style model each becomes one language-model token, so the image's cost in the language model is fixed by encoder resolution, not by what is in the picture.

## Native resolution and time: Qwen2.5-VL

A fixed input size forces a choice between squashing a wide screenshot and padding it. Qwen2.5-VL trains its own ViT to accept native dynamic resolution: images are resized to multiples of 28 pixels, cut into 14-pixel patches, and an MLP merger concatenates each 2 × 2 group of neighbouring patches into one language-model token. One token therefore covers a 28 × 28 pixel block, and token count scales with image area.

1344 / 28 = 48 and 756 / 28 = 27, so 48 × 27 = 1,296 tokens. The encoder saw four times as many patches, 96 × 54 = 5,184, before the merger.

Running full attention over thousands of patches is the encoder's cost problem, so Qwen2.5-VL uses window attention in most layers: windows of at most 112 × 112 pixels, which is 8 × 8 = 64 patches, with full attention in only 4 of its 32 layers.

<Predict id="mml-window-ratio" question="For the 5,184-patch screenshot, how many times fewer attention scores does one windowed layer compute than one full-attention layer? Assume every window is full." answer={81} tolerance={1} unit="times">
Full attention scores 5,184² pairs. Each patch in a 64-patch window scores 64 neighbours, so a windowed layer scores 5,184 × 64. The ratio is 5,184 / 64 = 81. The four full-attention layers keep global mixing; the other 28 run at about one eighty-first of the cost.
</Predict>

For video, the same encoder runs on sampled frames, and the temporal component of the model's multimodal rotary position encoding (MRoPE) is aligned to absolute time rather than frame index, so a frame sampled at 2 fps and one sampled at 0.5 fps carry timestamps the model can compare. Training samples the frame rate dynamically. In evaluation the report caps a video at 768 frames and 24,576 video tokens, which works out to 32 tokens per frame at the cap: long video is affordable only because each frame is heavily downsampled.

The freeze pattern changes again. Pretraining phase 1 trains only the ViT; phase 2 unfreezes everything; phase 3 trains at 32,768-token sequences for long documents and video; post-training freezes the ViT. The encoder is co-trained with the language model during pretraining, which a LLaVA-style frozen encoder never is.

## Early fusion: Llama 4

Llama 4 describes its models as early fusion: text and vision tokens enter one backbone and are pretrained together on text, image and video data, instead of attaching vision to a finished text model. The encoder is still separate, based on MetaCLIP and trained separately in conjunction with a frozen Llama model. The post states that pretraining used up to 48 images and that post-training was tested with good results up to eight images. That second number is the one to remember when someone sends forty page images in one request.

## What each part costs at inference

| Part | Work per request | What scales it | Cacheable |
|---|---|---|---|
| Encoder | One forward pass per image or frame | Patches, roughly area / patch², with attention cost depending on windowing | By image hash, if the deployment exposes it |
| Projector | One small MLP or matrix per patch group | Patches | With the encoder output |
| Language model prefill | Attention and MLP over every visual token plus the text | Visual tokens, often more than the text | Through prefix caching, if the image sits in a stable prefix |
| Language model decode | Reads the KV cache of all visual tokens on every output token | Visual tokens times output length | No |

In the open models above the encoder is the smaller network (Qwen2.5-VL's ViT has hidden size 1,280 and 32 layers, attached to language models of 3B to 72B parameters), and every visual token becomes a full-width token in the language model, so for one image the prefill and KV cache over visual tokens tend to outweigh the encoder pass. Measure it on your stack before optimising either. A 1,296-token screenshot is a 1,296-token prompt to a 7B or 72B model. API providers price exactly this: Claude counts ⌈*w* / 28⌉ × ⌈*h* / 28⌉ visual tokens for an image, the same 28-pixel block that Qwen2.5-VL merges to, and the next lesson works through what each provider charges.

<Fragment slot="long">
<p><strong>Two defensible designs.</strong> (1) Frozen encoder, projector, adapters on a frozen 7B. Text regressions are impossible on routes that do not load the adapter, training fits the node, and the risk is visual quality: a contrastive encoder at a fixed resolution loses the small print on receipts. (2) Unfreeze the encoder and the language model, Qwen2.5-VL style. Better OCR and layout, but every text feature must be re-evaluated against the new weights, and the node and eight weeks do not cover pretraining-scale data, so the gain is uncertain and the regression risk is certain.</p>
<p><strong>The conflict.</strong> Text-regression policy against visual quality. Design 1 satisfies the policy by construction; design 2 trades it for accuracy you cannot yet measure. I pick design 1 and spend effort on resolution: tile receipts so each crop goes through the encoder at native size, which multiplies visual tokens per receipt and therefore prefill cost.</p>
<p><strong>Where it fails.</strong> Adapter routing means two serving configurations; if product later wants one request mixing a text feature and an image, the adapter path must pass the text features' evals too, and the original guarantee is gone.</p>

## When this is wrong

The three-part picture describes the open models whose papers say so. Closed providers publish token counting rules, not architectures; a 28-pixel token in Claude's billing is not evidence that Claude uses a 14-pixel ViT with a 2 × 2 merger, and nothing here should be repeated as if it were.

The freeze patterns above are the published recipes for specific model releases. Later versions of the same families change them, and a team fine-tuning an open VLM chooses its own pattern; the published one is a starting point, not a rule.

Token count is a proxy for cost, not for quality. Two models with the same visual token count for an image can differ widely on small text because of encoder resolution, pretraining data and how many layers see the whole image. Measure on your own images.

"Early fusion" is used loosely. Some writers mean that image tokens enter the first layer of the language model, which LLaVA also does; Meta's use means joint pretraining from the start. Ask which one a speaker means before comparing.
