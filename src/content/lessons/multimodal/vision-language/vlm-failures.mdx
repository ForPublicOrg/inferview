## Sort the failures before fixing any

A VLM product's bad answers look alike in a support queue: confident, fluent, wrong. Underneath they come from four mechanisms that need different fixes, and the expensive mistake is applying the fix for one to another, for example raising resolution for a model that is not looking at the image at all. Pull a sample of failures, sort each into one of the four, and only then change the system.

| Failure | Detection test | Change that addresses it |
|---|---|---|
| Answers from the text, not the image | Swap or blank the image and see whether the answer changes | Fix the pipeline, the prompt order or the leading text |
| Miscounts | A labelled set bucketed by true count | Count in code from detections, or tile and count per tile |
| Misreads small or rotated text | Accuracy bucketed by text height after the provider's resize | Crop, a higher-resolution tier, rotation correction, OCR text alongside |
| Loses track across pages | Accuracy by page count and by evidence position | Retrieve the relevant pages, label them, cap pages per request |

## Answering from the text

The model has two sources of evidence and one of them is free: text costs no visual grounding, and the language model was trained on far more text than images. When the text carries a plausible answer, a model that is not getting usable visual evidence will produce it. There are three ways that happens, in the order to rule them out.

**The image never arrives.** A context-trimming step strips image blocks, a URL fetch fails and the client sends text only, a message builder attaches the image to a turn that gets dropped. This is a plain software defect and the most common cause after a release. The detection is cheap: input tokens per request should rise by the image's computed count (on a Claude model, a 1000 × 1000 image adds 36 × 36 = 1,296 tokens); if they do not, the model never saw it.

**The image arrives unreadable.** A standard-tier Claude model resizes anything above 1,568 visual tokens; a phone photo of a form can lose the detail the question needs. The model then answers from the text because the image contains nothing it can use.

**The text outweighs the image.** A long form, a leading question ("confirm the rear bumper is damaged") or prior turns that state an answer give the model a strong prior. Anthropic's vision guide says Claude works best when images come before text, and that images after or interleaved with text still perform well; ordering is a secondary lever, not usually the root cause. Instruction-tuning data is part of this: LLaVA's instruction data was generated by a language-only model from captions and boxes, so the training text describes what captions say an image contains.

The test for all three is a counterfactual image: rerun a labelled sample with each image swapped for another example's image, and with a blank image. If answers barely change, the model is not using the image, whatever the cause. Report the change rate per feature; it is the single number that tells you which of the four rows you are in.

## Counting

CLIP's own paper lists counting among the tasks it struggles with, and a contrastive objective explains why: captions rarely state counts, so nothing rewards the encoder for keeping them. Claude's documentation says counts are approximate, especially with many small objects; OpenAI's says the same. Patch merging adds a mechanical reason: in a model that merges 2 × 2 patches into one 28-pixel token, two small objects inside one token's block share one vector.

Test with a labelled set bucketed by true count (1 to 5, 6 to 20, more than 20) and report accuracy per bucket; a single accuracy number hides that small counts are often fine and large ones are not.

Fixes, in order of reliability: count in code from a detector's boxes; ask the VLM to list each object with coordinates and count the list, accepting that coordinates are approximate; tile the image and count per tile, which needs a rule for objects that straddle tile edges. "Think step by step" is not a fix for a perception limit.

## Small, rotated and non-Latin text

Both vendors list the same weaknesses: very small images (Claude cites images under 200 px), rotated or upside-down text, and for OpenAI non-Latin scripts, graphs with varied line styles, and panoramic or fisheye images. Two causes are inside your pipeline rather than the model. Server-side resizing shrinks text: a 1920-pixel-wide screenshot sent to a standard-tier Claude model becomes 1456 wide, so 12 px text becomes about 9 px. Lossy compression destroys glyph edges, and Anthropic's guide warns specifically that heavy JPEG compression can make text hard to read.

Test with a set bucketed by text height measured after the provider's resize, not in the original file, and include rotated samples if users photograph documents. Fixes: crop the region with the text, use a high-resolution tier, correct orientation before sending, and for dense documents send OCR text alongside the page image so the model can cross-check. Qwen2.5-VL's report shows a further option for document pipelines: train the model to emit structured HTML with a `data-bbox` on every element, so each extracted value carries the region it came from and can be checked.

## Many pages

Single-image accuracy says little about forty pages. Meta's Llama 4 post states that post-training was tested with good results up to eight images; a model evaluated that way has no published evidence at forty. The token arithmetic is also unforgiving: an A4 page at 130 DPI is 2,145 tokens on a high-resolution-tier Claude model.

<Predict id="mml-forty-pages" question="A 40-page contract is sent as 130 DPI page images (1075 by 1520 each) to a high-resolution-tier Claude model. How many image tokens is that, before any text?" answer={85800} tolerance={50} unit="tokens">
40 × 2,145 = 85,800 tokens. Sending only the four pages a retriever ranks highest is 4 × 2,145 = 8,580, a tenth of the prefill, and the model's attention is spread over four pages instead of forty.
</Predict>

Three distinct failures hide under "fails on multi-page documents". The model cannot cite pages it cannot name: unlabelled images give it no page numbers, which is why Claude's guide recommends a text label before each image. The pages can arrive out of order, which breaks any clause that runs across a page break. And the evidence can be diluted across tens of thousands of tokens of irrelevant pages. Test each separately: accuracy by page count, by the evidence's page position, and on questions whose evidence spans two pages.

The structural fix is retrieval over page images. ColPali embeds each page image directly with a VLM into 1,024 patch vectors of 128 dimensions and scores a query by late interaction: for each query vector, the best-matching page vector, summed. On the authors' ViDoRe benchmark it reports average nDCG@5 of 81.3 against 67.0 for the best text-pipeline baseline, and indexing at about 0.39 s per page against about 7.22 s for a pipeline doing layout detection, OCR and captioning. The cost is storage.

<Predict id="mml-colpali-storage" question="At the paper's 257.5 KB per page, how many GB does a ColPali index of 400,000 pages take, before any compression?" answer={103} tolerance={1} unit="GB">
400,000 × 257.5 KB = 103,000,000 KB = 103 GB. A single-vector text index of the same pages at 1,024 float32 dimensions would be 400,000 × 4,096 bytes, about 1.6 GB; multi-vector retrieval buys its accuracy with about sixty times the storage.
</Predict>

<Fragment slot="long">
<p><strong>The conflict.</strong> Three weeks and 300 labels against a regulator who will ask whether accuracy has recovered. Two defensible routes: (1) revert the release now and investigate on the old version, which restores the known accuracy immediately but loses whatever the release fixed and delays the root cause; (2) keep the release, diagnose with the tests above, and ship a targeted fix, which keeps the release's gains but risks arriving at the review with an unverified fix.</p>

## When this is wrong

The four categories are a sorting aid, not a taxonomy of everything a VLM can get wrong. Hallucinated objects, wrong spatial relations and safety refusals on benign images are failures too, and some failures are two categories at once: a miscount on a downscaled image is both counting and resolution.

The counterfactual-image test assumes the right answer depends on the image. For questions the text can answer correctly, an unchanged answer is fine; filter the sample to image-dependent questions first.

Vendor limitation lists are written for their current models and change with releases. Treat them as hypotheses to test on your images, not as properties of the model you deploy next quarter.

ColPali's numbers are the authors' own, on their benchmark, with their baselines. A domain with dense tables or scanned handwriting can rank differently; run the comparison on your own pages before paying for the storage.
