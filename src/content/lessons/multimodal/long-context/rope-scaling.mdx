## The decision

Every long-context open-weight model you can download ships a `rope_scaling` block or an equivalent, and every one of them is a choice about how to bend a position encoding past the lengths the model was trained on. Llama 3.1 ships `rope_type: llama3` with factor 8 from 8,192 original positions. Qwen3 documents a YaRN block with factor 4 from 32,768 and warns that it can hurt short inputs. The engineering decision is which block to apply, to which requests, and what to measure when you do. That needs the mechanism one level down from "RoPE encodes position".

## What RoPE computes

RoPE splits each query and key vector of a head into pairs of coordinates and rotates pair *i* by an angle proportional to the token's position: angle = position × θ<sub>i</sub>, with θ<sub>i</sub> = base<sup>−2i/d</sup> for head dimension *d*. RoFormer's base was 10,000. Rotating `q` at position *m* and `k` at position *n* and taking their dot product leaves, in each pair, the cosine of the original angle between the pair vectors plus (*m* − *n*)θ<sub>i</sub>. The attention score depends on the vectors and their distance, not on where the pair sits in the sequence. That is the whole trick, and it is why a key cache can store keys already rotated: a key's rotation never changes after it is written, as long as the frequencies do not.

The frequencies span a huge range. With *d* = 128 there are 64 pairs. Pair 0 rotates one radian per token, a wavelength of 2π ≈ 6.3 tokens. Pair 63 rotates at base<sup>−126/128</sup>: with base 10,000 its wavelength is 2π · 10,000<sup>126/128</sup> ≈ 54,410 tokens; with Llama 3's base of 500,000 it is about 2.56 million tokens. Fast pairs resolve "which of the last few tokens"; slow pairs carry coarse position over the whole window.

It is a clock with 64 hands at different speeds, and the difference from a clock is what training saw. Any pair whose wavelength is shorter than the training window completed full turns during training, so every angle it can produce was seen. A pair whose wavelength is longer than the window only ever saw a fraction of a turn. Run past the window and those slow pairs produce angles the weights were never trained on. That is the failure of naive extrapolation, and every stretching method is a different answer to it.

## The methods, as operations on frequencies

**Position Interpolation (June 2023)** divides every position by the factor *s*, which is the same as dividing every θ by *s*. No slow pair leaves its trained range, because position *sL* now maps to angle θ*L*. The cost is the fast pairs: their per-token step shrinks by *s*, so neighbouring tokens look *s* times closer than they did in training. The PI paper fine-tuned LLaMA models from 7B to 65B to 32,768 tokens within 1,000 steps and argued that interpolation's error bound is at least about 600 times smaller than extrapolation's.

**NTK-aware scaling** raises the base instead: b′ = b · s<sup>d/(d−2)</sup>. Pair 0 is untouched, the slowest pair slows by exactly *s*, and the pairs between slow by less. The YaRN paper reports that this pushes some dimensions slightly out of bound, so the factor has to be set higher than the extension wanted, and that fine-tuning with it did worse than PI.

**YaRN** (the next lesson walks through it) applies a ramp per pair, using *r* = *L* / λ, the number of full turns a pair made in the trained window. Pairs with *r* above β = 32 are left alone, pairs with *r* below α = 1 are interpolated like PI, and the ones between are blended linearly. It also scales attention logits by a temperature term.

**The llama3 rope type** is the same idea with thresholds in wavelength. From transformers' implementation: wavelengths under `original / high_freq_factor` keep their frequency, wavelengths over `original / low_freq_factor` are divided by the factor, and the band between is smoothed linearly. With Llama 3.1's values, that is: keep below 2,048 tokens, divide by 8 above 8,192.

**LongRoPE** (February 2024) searches per-dimension factors instead of using a formula, reports an 8x extension from the search alone without fine-tuning, fine-tunes at 256K for up to 1,000 steps, extends again to 2,048K, and then readjusts at 8K to recover performance on the original short window. That last step is the paper admitting the cost every method here pays.

## The code

The llama3 transform, written from transformers' `_compute_llama3_parameters`, for one head:

```python
import math

def llama3_inv_freq(d=128, base=500_000.0, factor=8.0, low=1.0, high=4.0, original=8192):
    out = []
    for i in range(d // 2):
        theta = base ** (-2 * i / d)
        wave = 2 * math.pi / theta
        if wave < original / high:          # fast pairs: unchanged
            out.append(theta)
        elif wave > original / low:         # slow pairs: interpolated like PI
            out.append(theta / factor)
        else:                               # the band between: linear blend
            smooth = (original / wave - low) / (high - low)
            out.append((1 - smooth) * theta / factor + smooth * theta)
    return out

freqs = llama3_inv_freq()
print(sum(1 for i, f in enumerate(freqs) if f == 500_000.0 ** (-2 * i / 128)))   # 29
```

## What changed in the last two years

The direction of travel is away from formula-only stretching applied to a model trained short, toward models trained long and configured to match. Meta's Llama 4 post (April 2025) describes Scout as pre-trained and post-trained at 256K, with "iRoPE": interleaved attention layers that use no positional embeddings at all, RoPE in the rest, and inference-time temperature scaling of attention for length generalisation, for a stated 10M-token context. Its supporting evidence includes a needle-in-a-haystack retrieval result; the evaluation lesson in this module explains why that is not evidence of usable context. Qwen3 takes the other route: native 32,768 and a documented YaRN block that the operator adds, with the card's own warning that frameworks apply it statically.

For an operator, the consequence is that `rope_scaling` is now a deployment parameter with a quality cost, chosen per workload. Qwen's card says to add the block only when long contexts are required, and to use factor 2 rather than 4 if typical lengths are around 65,536. Static application means a 1,000-token request pays for a 131,072-token stretch.

## When this is wrong

The frequency picture explains why methods differ; it does not predict quality. Two configurations with similar counts in the widget can behave differently on a given task, because the weights' use of each pair is learned and not uniform. Only measurement at the target lengths settles it.

The "seen in training" test assumes training covered the full trained window evenly. A model pretrained mostly on short documents has seen the late positions of its own window less, so its effective range can be shorter than `original_max_position_embeddings` before any stretching.

Models with layers that use no positional encoding, like Llama 4's interleaved layers, or with sliding-window layers, as in gpt-oss, change the arithmetic: only some layers rotate, and position information also comes from the causal mask. The per-pair analysis applies to the RoPE layers only.

Finally, the numbers here are from configs and papers dated between 2021 and 2025. Engines change how they apply `rope_scaling`, and a dynamic mode in your engine changes the short-input cost entirely. Check the engine's version before reusing any conclusion from this page.
