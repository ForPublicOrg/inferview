## The decision

Weights are a few very large files that many people and services need to use and almost none need to read. The design is three choices made per copy: **which interface** each reader gets (tokens out, activations out, arbitrary code with capped output, or raw bytes), **how many identities** hold each interface, and **how many bytes per unit time** can leave the place the copy lives. Everything else (endpoint control, monitoring, insider programs) supports those three.

RAND's report on securing model weights (Nevo and colleagues, 2024), the benchmark Anthropic's scaling policy refers to, gives the reason weights are the right thing to protect. Training compute, data and algorithmic work all end up in the weights, and once an attacker has them the only remaining prerequisites are inference compute and the architecture. The architecture is the weaker secret (much smaller, and known to many more engineers), but the weights have a property no other secret in the company has: they are large, reaching terabytes, which makes copying them observable and rate-limitable. Most uses also do not need flexible read access, so the weights can sit behind copy-resistant interfaces.

## The threat model sets the bar

RAND counts approximately 38 meaningfully distinct attack vectors and grades attackers in five operational capacity classes, from amateurs (OC1) through cybercrime syndicates and insiders (OC3) to top-priority operations by the most capable states (OC5). About a dozen vectors are likely infeasible for nonstate actors but feasible for states. Each security level SL1 to SL5 is defined as likely to thwart the matching class: SL3 against cybercrime syndicates and insider threats, SL4 against standard operations by leading cyber-capable institutions.

Which level you build for is a written decision, and the published scaling policies show what one looks like. Anthropic's Responsible Scaling Policy version 3.4 (effective 8 July 2026) recommends, at its first capability threshold, precautions against opportunistic theft of weights, and at higher thresholds security "roughly in line with RAND SL4". When Anthropic activated its ASL-3 protections (22 May 2025) it described more than 100 controls aimed at sophisticated non-state attackers and stated what was out of scope: sophisticated insider risk, and nation-state attackers except those using non-novel attack chains. The policy's v2.2 changelog gives the reasoning for the insider exclusion: the relatively small number of employees who could steal the model does not significantly change the risk level for the threats that tier addresses.

A threat model for any other organisation needs the same three parts: the attacker classes in scope, the ones explicitly out, and the argument for the line.

## Where copies live

Every copy is a place weights can leave from.

**Training clusters** write checkpoints. Each checkpoint is a full copy, written to storage the training job can reach, read back by evaluation jobs and moved between clusters. RAND's SL3 benchmark asks that weights live in a small number of centrally managed locations (a training copy, a research copy and a production copy are allowed) and that employees cannot simply make another. Intentional copies, such as standing up a new data centre, require per-instance approval by multiple people including a key executive, a predetermined number of copies, and monitoring. For the checkpoint pipeline that means a transfer is a copy and goes through the same gate, automated rather than exempted.

**Serving fleets** hold the largest number of copies, one per host with the weights in accelerator memory. The interface RAND suggests for production inference is narrow: text in, output tokens (or logits) out. Logits return a vocabulary-sized vector per position instead of one token id, so that choice widens the channel. The host-level controls are egress restriction to response traffic, no interactive access outside a two-party break-glass path, and images built from a reviewed baseline. RAND's SL3 monitoring includes comparing running software against a read-only, hashed gold image.

**Research environments** are where the tension is. RAND notes that many existing workflows, "including popular software for debugging and interpretability research", provide full weight access and satisfy none of its interface alternatives.

**People** hold the remaining copies, and so do agents. RSP version 3.4, at its automated R&D threshold, names concerning behaviour by insiders, "humans as well as AI systems themselves". A coding agent running with a researcher's credentials in the research cluster holds whatever tier the researcher holds. Give agents their own identity and cap them at the inference or forward-pass tier by construction, using the gate and token design from the previous two lessons.

## Interfaces, ordered by what they leak

RAND's SL3 benchmark requires that no one, authorised or not, gets direct read access to any copy, "because this enables trivial copying". It offers alternatives, and they form the access tiers.

<div class="tablewrap">

| Tier | Interface | Who (RAND SL3 example limits) | Holds by construction against | Still leaks through |
|---|---|---|---|---|
| Inference | Text in, tokens or logits out | Broad, indirectly | Direct copying | Distillation and extraction by queries; needs rate limits per credential and monitoring |
| Research service | Forward pass (embeddings in, final layer out) and backward pass (final-layer gradients in, input gradients out) | Trusted researchers | Direct copying | Query-based extraction if the interface is too flexible |
| Output-limited sandbox | Arbitrary code, aggregate output capped | 100 people | Bulk copying above the cap | Anything under the cap |
| Isolated network | Arbitrary code and unlimited output, no network, no removable media | 50 people | Digital exfiltration | People's memory and paper, assumed low-throughput |
| Copy authority | Make a new full copy | 20 people, multi-party approval per copy | Unilateral copying | Collusion among approvers |

</div>

The research service is the hard one to get right. RAND's examples of interfaces that look safe and are not: code that reads a single weight by index can be called repeatedly to read them all, and code that runs the model with an arbitrary loss function and returns the loss can be used to extract the weights. "Certified difficult to abuse" is a security review of the interface's information flow, not a check that it never returns a tensor.

Anthropic's planned ASL-3 safeguards (dated 15 October 2024 and described on the page as non-binding) have the same shape: researcher tooling without direct access to model weights, multi-party authorisation and mandatory code review, manual monitoring of access to weights, and honeypots including fake model weights. The decoy's signal is unusually clean, because no legitimate job should read a decoy checkpoint; backup and inventory jobs have to be kept away from it by design.

## Egress is arithmetic

The output-limited tier only means something if the cap is set from the size of what it protects. RAND's guidance is specific about the size to use: assume 4-bit weights, because 4-bit versions perform decently and an attacker only needs 4 bits of each weight; and add a buffer, assuming an effective size at least an order of magnitude below the in-memory size, since mixture-of-experts models may leak dangerous capability from a fraction of their weights.

Anthropic's ASL-3 activation describes the production version of this idea: egress bandwidth controls that restrict data leaving the environments where weights reside, explicitly using weight size as a security advantage, with the stated aim of making exfiltration before detection very difficult. RAND's SL4 benchmark moves the limit into hardware on every connection of the protected setup, with an aggregate example of 5 percent of the weights' size per year. Its note on inference credentials makes the same point from the API side: even 100 tokens per second per credential would likely take months to move all the weights.

## The design for an organisation that has to move fast

Scenario: a research organisation trains and serves its own models, with researchers who use interpretability notebooks that load full weights today. The plan that keeps them working:

1. **Inventory copies and readers first.** Every bucket, cluster and host image that holds weights or checkpoints, and every identity (human, service, agent) with read access to each. The first number to bring down is identities with raw read access.
2. **Stand up the research service before taking anything away.** A forward and backward service with activation and gradient access covers most interpretability and RL work; build it, have the security team review its information flow, and move teams onto it.
3. **Give the remaining raw-access work an isolated network**, with a named list, and give everyone else the output-limited sandbox with a quota derived from the aggregate target.
4. **Make access just-in-time.** No standing access to any tier above inference; grants expire and are renewed, which RAND lists for SL3.
5. **Two-party everything that changes the boundary**: code of the weights interfaces, egress rules, copy approvals, and the checkpoint pipeline. RAND requires that multi-party authorisation for security-relevant code cannot be bypassed by force-submit or direct file access.
6. **Detect on what the controls cannot stop**: throughput anomalies on every tier, decoy checkpoints, and integrity checks against the gold image.

The decision memo lists what this costs: notebook workflows change, some debugging gets slower, and new clusters wait on copy approval.

## When this is wrong

Every egress control in this lesson leans on weights being large. RAND says so directly: if much smaller models gain capabilities whose spread would be dangerous, rate limiting may stop being tenable. The 4-bit and order-of-magnitude buffers are hedges against today's compression and partial-weight attacks, not a guarantee against next year's.

Weight security does not stop extraction through the product. A model distilled from enough API responses is not a weight theft, and the controls against it are rate limits, query monitoring and terms enforcement on the inference tier.

The tier limits are examples from one report, and its own authors record disagreement: some experts insisted the number of people with weight access must fall to the low tens, others that this was neither necessary nor feasible. RAND's answer to the trade-off is better interfaces, not a number. A design that copies 100, 50 and 20 without asking what its research workflows need will either break the workflows or be routed around, and an unofficial copy on a laptop defeats every control above.

The threat model is a choice with consequences. Excluding sophisticated insiders, as ASL-3 does, is defensible for the threats it addresses and wrong for an organisation whose risk is a state-recruited employee. The scoping paragraph is the part of the design a reviewer should challenge first.
