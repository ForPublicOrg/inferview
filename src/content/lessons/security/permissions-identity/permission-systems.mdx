## Four properties, four published failures

A permission system for agent tools turns a proposed tool call into allow, ask or deny before anything runs. The harness lesson on [rule engines](/learn/harness/permissions-sandboxing/rule-engines) covers how Claude Code and Codex match shell text. This lesson treats the same component as a security control: what it must guarantee, which guarantees hold by construction, and which published vulnerability each missing guarantee produced.

Four properties carry the weight: deny before ask before allow, with nothing downstream able to turn a deny into an allow; a parser rather than a prefix match; paths no rule can approve; and resolution before matching. The CVEs below share one shape. The attacker never needed a tool the gate refused. They needed one approved call whose effect changed what the next call would be allowed to do, or one call the gate misread as something it approves.

## Deny first, and deny is final

Claude Code evaluates deny, then ask, then allow; the first match in that order decides, and a more specific allow rule does not carve an exception out of a broader deny. A PreToolUse hook that returns `"allow"` does not skip a matching deny or ask rule, so an organisation can ship deny rules in managed settings and let teams add hooks without either undoing the other. Project-level allow rules apply only after the user accepts workspace trust for the folder, while project deny and ask rules apply immediately, because they only restrict. A `settings.local.json` that is tracked in git, or a `.claude` directory that is a symlink, is treated as repository-supplied and held until trust.

That asymmetry is the rule to copy: **anything that widens permission needs a trusted author; anything that narrows it can come from anywhere.** A cloned repository is an untrusted author. So is any file the agent itself wrote.

## Parse; never prefix-match

CVE-2025-54795 is the parsing failure. In Claude Code below 1.0.20, the CVE record says, "an error in command parsing" made it possible to bypass the confirmation prompt and run an untrusted command, given untrusted content in the context window. The advisory's title names `echo`, which is in the read-only set that runs without a prompt. Cymulate, who reported it, published the payload template `echo "\"; <COMMAND>; echo \""` and wrote that the technique works with any whitelisted command. Neither the advisory nor the write-up shows the defective parser code, so the precise bug is not public. The class is clear enough to design against: a string the gate classified as one allowed command contained a second command the gate never classified.

Two rules close the class. First, split on every shell separator with a shell-aware tokenizer and require every part to be allowed. Claude Code's docs list the separators it splits on (`&&`, `||`, `;`, `|`, `|&`, `&` and newlines) and apply deny and ask rules to commands nested in subshells, substitutions and loop bodies. Second, **failure to parse is a verdict**. Claude Code asks on a command it cannot fully parse, treats `npm test &&` as unparseable rather than as `npm test`, and always prompts on commands longer than 10,000 characters. A parser that falls back to the raw string and prefix-matches it has turned "I cannot read this" into "this starts with something I trust".

Parsing holds by construction for the commands the parser reads, and for nothing else. The same docs say a Bash rule matches the text Claude writes and "isn't a security boundary around the program": `/usr/bin/curl` and `sh -c 'curl ...'` are other spellings of a denied `curl`. Parsing stops a read-only prefix from smuggling a second command. It does not stop the model from spelling a denied command differently, which is the sandbox's job.

## Paths no rule can approve

CVE-2025-54135 is the self-modification failure. Cursor below 1.3.9 let the agent write files in the workspace without approval. Editing an existing dotfile required approval; **creating** one did not. If `.cursor/mcp.json` did not exist, an indirect prompt injection could have the agent create it with a malicious MCP server entry, and Cursor would start that server: code execution with no prompt. The advisory's remediation blocks the agent from writing MCP-sensitive files without approval.

CVE-2025-53773 is the same class in a different file. The CVE record says only "command injection" in GitHub Copilot and Visual Studio 2022 from 17.14.0 up to, not including, 17.14.12. The researcher's write-up gives the chain: injected instructions make the agent add `"chat.tools.autoApprove": true` to `.vscode/settings.json`, creating the file if needed, which turns off confirmations; after that the agent runs shell commands freely. Agent mode wrote workspace files without approval, and the edits were persisted at once rather than held as a diff for review. The same post names `.vscode/tasks.json`, MCP server entries and other agents' configuration files as having the same property.

The property is not "dotfiles are sensitive". It is: **a file is protected if a later step executes it or reads it as policy.** That list is long and product-specific. Claude Code's protected paths include `.git`, `.vscode`, `.idea`, `.husky`, `.claude`, `.gitconfig`, shell startup files (`.bashrc`, `.zshrc`, `.envrc` and others), package-manager configs such as `.npmrc`, pre-commit and lefthook configs, `.mcp.json`, `.claude.json`, and any file passed to `--settings`, `--mcp-config` or `--agents`. An `Edit(.claude/**)` entry in allow does nothing for those paths, because the safety check runs before allow rules. Codex under `workspace-write` makes `.git` read-only, including the resolved directory when `.git` is a `gitdir:` pointer file, and makes `.agents`, `.codex` and `.aws` read-only recursively.

Two details decide whether the protection holds. The check must apply to **creates**, which is the whole of CVE-2025-54135; Codex's docs condition the `.codex` and `.agents` protection on those paths existing as directories, which is the case a review should test rather than assume. And the protection must survive the modes. In Claude Code, protected-path writes are prompted in default and acceptEdits, routed to the classifier in auto, denied in dontAsk, and allowed in `bypassPermissions`. A protected list is a construction control only in the modes that honour it; in the others it is a convention.

## Resolve, then match

Path rules compare strings, and the filesystem disagrees with strings in two ways.

**Prefix containment.** Cymulate's companion finding, CVE-2025-54794, quoted Claude Code's containment check as `path.resolve(filePath).startsWith(path.resolve(originalCwd))`. With a working directory of `/home/u/app`, the sibling `/home/u/app_evil` passes. The fix is a component test: equal to the root, or starting with the root plus a separator.

**Symlinks.** A link inside the workspace can point anywhere. Claude Code checks both the requested path and the resolved one: an allow rule applies only when both match, a deny rule when either does. With `Read(./project/**)` allowed and `Read(~/.ssh/**)` denied, a link at `./project/key` pointing at `~/.ssh/id_rsa` is denied. Two harder cases remain. A directory on the way can be the link (`vendor -> ~/.config`), so resolution walks components, not just the last one; Claude Code's Edit and Write refuse a path that is itself a link, but a write through a linked directory goes to the per-mode rules for where it resolves. And the link can change between the check and the open, so Claude Code confirms at open time that the path still resolves to the approved location. Without that second check, resolution is a time-of-check to time-of-use race.

## Resolution and protection in code

The write path below combines component containment, component-wise link resolution and a protected check on both paths. `LINKS` stands in for the filesystem so the logic is deterministic; a real gate calls the OS and repeats the check at open time. The [permission gate lab](/labs/permission-gate) grows the full gate, with the matcher, the splitter and the audit record, against tests modelled on these CVEs.

```python
import posixpath

WORKSPACE = "/home/u/app"
LINKS = {"/home/u/app/notes/key": "/home/u/.ssh/id_rsa", "/home/u/app/vendor": "/home/u/.config"}
PROTECTED = {".git", ".claude", ".cursor", ".vscode", ".husky", ".mcp.json", ".bashrc", ".envrc"}


def resolve(path, hops=0):
    """Follow links component by component, so a linked directory on the way counts too."""
    if hops > 8:
        raise OSError("symlink loop: refuse the call")
    parts = posixpath.normpath(path).split("/")
    for i in range(2, len(parts) + 1):
        prefix = "/".join(parts[:i])
        if prefix in LINKS:
            return resolve(posixpath.join(LINKS[prefix], *parts[i:]), hops + 1)
    return posixpath.normpath(path)


def inside(path, root=WORKSPACE):
    return path == root or path.startswith(root + "/")   # by component, not by string prefix


def protected(path):
    rel = posixpath.relpath(path, WORKSPACE) if inside(path) else path
    return any(part in PROTECTED for part in rel.split("/"))


def write_verdict(requested):
    real = resolve(requested)
    if protected(requested) or protected(real):   # no existence check, so creates are covered
        return "ask", real
    if inside(requested) and inside(real):
        return "allow", real
    return "ask", real


assert write_verdict("/home/u/app/src/main.py") == ("allow", "/home/u/app/src/main.py")
assert write_verdict("/home/u/app/.cursor/mcp.json")[0] == "ask"        # CVE-2025-54135 shape
assert write_verdict("/home/u/app/vendor/git/config") == ("ask", "/home/u/.config/git/config")
assert resolve("/home/u/app/notes/key") == "/home/u/.ssh/id_rsa"
assert not inside("/home/u/app_evil/token")                             # CVE-2025-54794 shape
print("5 checks pass")
```

Two choices in it are policy. Protection is checked on the requested and the resolved path, so a link into `.git` from an innocent name is caught. And the protected verdict is `ask`; in an unattended mode the same branch should return `deny`, which is what Claude Code's dontAsk mode does.

## The audit record

Every decision writes one record, whatever the verdict: the actor (which agent session, on whose behalf), the tool, the raw input, the resolved path for file tools, the verdict, and the rule that decided, with the settings source it came from. The resolved path is the field incident response needs and the one most logs drop: "Read /home/u/app/notes/key, allow" and "Read /home/u/app/notes/key, resolved /home/u/.ssh/id_rsa, deny" describe different events.

Log denials and asks, not only executions. A rising count of protected-path asks in one repository is what an injection attempt looks like from the gate's side, and the gate is the only component that sees the attempt rather than the outcome.

## When this is wrong

A gate decides on what the agent asks for, and the dangerous effect can happen in a step the gate approved for a different reason. `pytest` is allowed; `pytest` imports `conftest.py`, which the agent wrote one call earlier into an unprotected path. The protected list covers files that harnesses and editors execute by name; the set of files that some later approved command executes is the whole repository. That gap is why the gate is the first layer, and the sandbox, the credentials the process holds and its network reach are the layers that hold when the gate is wrong.

Resolution assumes the filesystem stays still. A check-then-open sequence without the second check is a race, and network filesystems, bind mounts and Windows junctions each add spellings that a resolver written for one OS will miss. The verdict corpus has to run on every OS the product ships on.

Deny-first assumes rules are the only source of verdicts. Modes, classifiers, hooks and plugins are other sources, and each is a place where a deny can stop being final. Claude Code's own docs show the case: an installed mod that answers the `tool.check` event can approve a call a deny rule refuses, unless the machine has managed settings or the session uses a Team or Enterprise login. Every new way to approve needs one design-review answer, which existing denials it can override, and the answer should be none or a named, managed list.

The audit record shows what the gate decided, not what happened. An allowed `pytest` that ran a hostile `conftest.py` logs as one clean allow. Pair the gate's records with process and network telemetry from the sandbox, or the log will be accurate and useless in the incident that matters.
