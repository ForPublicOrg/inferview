## The decision

When an agent acts for a user against a downstream API, some credential reaches that API. The choice is which one, and there are four answers: the user's own token forwarded as is, a token the agent holds for itself, a new token that says "this is the user" (impersonation), or a new token that says "this is the agent, acting for the user" (delegation). The last one is the only one that passes both tests a security review applies to agent access: **blast radius** (what a stolen or misused token can reach) and **audit** (whether the logs at the resource can tell the agent's actions from the user's).

## Why passthrough fails both tests

Forwarding the user's token needs no new infrastructure, which is why prototypes do it. The MCP specification forbids it in two sentences: servers must validate that a token was issued for them as the audience, and "MCP servers MUST NOT accept or transit any other tokens." The security best-practices page lists why, and the list maps onto the two tests.

On blast radius, a token accepted at several services is a token that works wherever it leaks. The best-practices page puts it as a trust-boundary issue: if one token is accepted by multiple services, compromising one service yields access to the others. RFC 8693 states the arithmetic for multi-service tokens: the access requested is the Cartesian product of the scopes at all target services. A token valid at three services with four scopes each is twelve grants, and whichever hop is weakest holds all twelve.

On audit, the downstream API sees the user. The MCP page's wording is that the resource server's logs "may show requests that appear to come from a different source with a different identity". An agent that issues a refund with the user's token and a user who issues it by hand produce the same log line, and no policy at the payments service can treat them differently because it cannot tell them apart.

The agent's own service credential fails the other way. Audit is clear (the agent did it) but blast radius is the union of every user's data the agent can reach, and the resource can no longer apply the user's own permissions. That is the confused deputy shape: the deputy's authority, used on behalf of a caller who should have had less.

## Impersonation and delegation in token exchange

RFC 8693 (January 2020) defines a token endpoint grant, `urn:ietf:params:oauth:grant-type:token-exchange`, that takes one token and returns another. The request carries a required `subject_token` (whose authority is being used), an optional `actor_token` (who is using it), and optional `resource`, `audience` and `scope` to narrow what comes back.

The RFC's section 1.1 draws the distinction this lesson needs. With impersonation, A "is given all the rights that B has" within the token's context, and downstream parties cannot see A at all. With delegation, A keeps its own identity separate from B and acts as B's agent. The difference shows up in one claim. A delegated token carries `act`, a JSON object naming the current actor:

```json
{
  "iss": "https://auth.example.com",
  "sub": "user:ana",
  "aud": "https://payments.example.com",
  "scope": "payments:read",
  "exp": 1800000300,
  "act": { "sub": "spiffe://example.com/agent-gateway" }
}
```

An impersonation token is the same without `act`. That is the whole difference on the wire, and it decides whether the payments service can write a rule such as "agents may refund up to an amount; above it, a person acts".

Two more parts of the RFC carry design weight. The `may_act` claim (section 4.4) lets the subject token state which party may act for the subject, so the authorisation server can refuse an exchange where the requesting actor is not one the user's token names. And chains nest: if the agent gateway calls a CRM, which calls a mail service, the token at the mail service has an outer `act` for the CRM and a nested `act` for the gateway. Section 4.1 is explicit that the outermost `act` is the current actor and that prior actors in nested claims "are informational only and are not to be considered in access control decisions." The property "an agent is somewhere in this chain" does not travel as an enforceable fact past the first hop. Each service that needs an agent-specific rule must see the agent as its direct caller, or receive that fact some other way it trusts.

## Audience-bound tokens, one per resource

The MCP authorisation spec makes resource binding mandatory on the client-to-server leg. Clients must send the RFC 8707 `resource` parameter, set to the server's canonical URI, in both the authorisation and the token request, whether or not the authorisation server supports it. Servers must reject tokens not issued for them. The result is one token per MCP server, each useless elsewhere.

The core authorisation page does not say how an MCP server then authenticates to the APIs behind it, beyond forbidding passthrough. Token exchange is one way to fill that gap with the same property: the server presents the token it received as `subject_token`, its own workload credential as `actor_token`, and names the upstream API in `resource`, asking for only the scope the current tool call needs. The authorisation server applies policy (is this actor allowed to act for this user, for this resource, with this scope?) and returns a short-lived token bound to one upstream.

## Step-up through the challenge

Minimal scopes only work if raising them is cheap and visible. The MCP spec gives the mechanism. When a token lacks a scope at runtime, the server should answer `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="..."` and the full set of scopes the operation needs in one challenge. A client acting for a user should re-authorise with the union of its previous scopes and the challenged ones, then retry a bounded number of times. The best-practices page frames the whole model as progressive: a minimal initial set of low-risk read scopes, elevation through targeted challenges when a privileged operation is first attempted, no wildcard scopes, and elevation events logged with correlation ids.

For an agent, the step-up is the approval. The user sees a consent screen naming `refunds:write` at the moment the agent first tries a refund, which is a better approval prompt than any the agent harness can draw, because the authorisation server renders it and the agent cannot alter its text.

## The design for three services

Scenario: a support agent acts for a support representative across three internal services: a docs search API, a CRM, and a payments API that can issue refunds. The agent runs behind an MCP gateway the company operates.

1. The agent client authorises the representative at the company's authorisation server with `resource=https://tools.example.com/mcp` and the gateway's baseline scopes (docs and CRM reads). The token's audience is the gateway only.
2. Per tool call, the gateway exchanges: `subject_token` is the token it received, `actor_token` is the gateway's workload identity, `resource` is the one upstream, `scope` is what this call needs. The authorisation server checks that the gateway may act for this user and that the requested scope is within the user's grant.
3. The CRM and payments services validate audience, scope and expiry, and read `act` to apply agent-specific rules and to log the actor.
4. The first refund attempt gets `403 insufficient_scope` with `scope="refunds:write"` from the gateway, which the client turns into a step-up consent for the representative. The next exchange can include the new scope.

A stolen token at any hop is valid at one audience, for one scope set, for minutes. Every log line at payments names both the representative and the gateway.

The resource-server half fits in a few lines. Signature verification is assumed done.

```python
import time

ME = "https://payments.example.com"
AGENTS = {"spiffe://example.com/agent-gateway"}


def authorize(claims, op, amount=0, now=None):
    """Resource-server check on an already signature-verified token. Returns (ok, reason)."""
    now = now if now is not None else time.time()
    aud = claims.get("aud")
    if ME not in (aud if isinstance(aud, list) else [aud]):
        return False, "401: token not issued for this resource"
    if claims["exp"] <= now:
        return False, "401: expired"
    scopes = set(claims.get("scope", "").split())
    need = {"refund": "refunds:write", "read": "payments:read"}[op]
    if need not in scopes:
        return False, f'403: insufficient_scope scope="{need}"'
    actor = claims.get("act", {}).get("sub")       # only the outermost act counts (RFC 8693 4.1)
    if actor is not None and actor not in AGENTS:
        return False, "403: unknown actor"
    if op == "refund" and actor is not None and amount > 200:
        return False, "403: agents refund up to 200; a person must do this one"
    return True, f"ok as {claims['sub']}" + (f" via {actor}" if actor else "")


t = 1_800_000_000
delegated = {"sub": "user:ana", "aud": ME, "exp": t + 300, "scope": "payments:read refunds:write",
             "act": {"sub": "spiffe://example.com/agent-gateway"}}
passthrough = {"sub": "user:ana", "aud": "https://tools.example.com/mcp", "exp": t + 3600, "scope": "refunds:write"}

assert authorize(delegated, "refund", 120, now=t) == (True, "ok as user:ana via spiffe://example.com/agent-gateway")
assert authorize(delegated, "refund", 900, now=t)[1].startswith("403: agents refund")
impersonated = {k: v for k, v in delegated.items() if k != "act"}
assert authorize(impersonated, "refund", 900, now=t) == (True, "ok as user:ana")   # the limit cannot see the agent
assert authorize(passthrough, "refund", 120, now=t)[1].startswith("401")
assert authorize({**delegated, "scope": "payments:read"}, "refund", 50, now=t)[1] == '403: insufficient_scope scope="refunds:write"'
assert authorize(delegated, "read", now=t + 301)[1] == "401: expired"
print("6 checks pass")
```

The third assertion is the argument for delegation in one line: strip `act` and the same refund of 900 goes through, because the agent limit has nothing to read.

## What the lifetime costs

Short lifetimes are the substitute for revocation of self-contained tokens, and RFC 8693's security considerations suggest limited lifetime alongside scope for delegated rights. The cost lands on the authorisation server.

Exchanging on every tool call instead of caching multiplies by calls per task, not by services. The dominant term is the cache key: per task and service is what bounds a token to one user's work at one audience, and widening it to per service across tasks saves exchanges by putting several users' authority behind one cached token, which is the passthrough problem again.</p>

## When this is wrong

Token exchange needs an authorisation server you control, trusted by the resource. Third-party SaaS APIs trust their own authorisation servers, which will not honour your `act` claims. For those, the gateway holds a token the provider issued to it for the user, which is the MCP proxy pattern, and the best-practices page's confused-deputy section applies in full: per-client consent before forwarding to the third party, exact redirect URI matching, `state` set only after consent. Audit of agent actions at that provider lives only in your own logs.

The `act` claim is only as useful as the resource that reads it. Most APIs ignore unknown claims, so delegation can be minted correctly and enforced nowhere. The design review question is not "do our tokens carry the actor?" but "which services have a rule or a log field that uses it?".

Local MCP servers over stdio are outside this design. The spec tells them to take credentials from the environment, which in practice means long-lived keys with the user's full authority sitting in a process the agent can start. The permission gate and the sandbox are the controls there, not the token.

Delegation records who acted; it does not decide whether the act was what the user wanted. A prompt-injected agent with a correctly delegated, minimally scoped token will still issue the refund the injection asked for, and the log will attribute it accurately. Identity bounds the blast radius and fixes the audit trail; the injection defences in the safety track are what lower the rate.
