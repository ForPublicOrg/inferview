## The boundary is drawn around commands, not the agent

The sandboxes that ship with coding agents wrap the shell commands the agent runs and their children. The agent process, its built-in tools and the helpers it starts sit outside. That is a deliberate trade, since it keeps file edits fast and lets the harness talk to the model API, but it means "the agent runs in a sandbox" is false for every product in this lesson as configured by default. Claude Code's documentation says it directly: sandboxing reduces risk but is not a complete isolation boundary.

The rest of this lesson is the inventory of what stays outside, product by product, and the three leak paths that inventory implies.

## Claude Code

**Off until enabled.** The sandbox starts when you run `/sandbox` or set `sandbox.enabled`. It uses Seatbelt on macOS and bubblewrap on Linux and WSL2; native Windows runs commands unsandboxed and WSL1 is not supported. If a dependency is missing, commands run unsandboxed unless `sandbox.failIfUnavailable` is set, so a fleet rollout that only sets `enabled` fails open on machines without bubblewrap.

**Writes are narrow, reads are not.** Sandboxed commands may write the working directory, added directories and the per-user temporary directory `$TMPDIR` points to. They may read "the entire computer, except certain denied directories", and the documentation lists `~/.ssh` and `~/.aws/credentials` as readable by default. There is no built-in credential deny list: only the files and variables you name under `sandbox.credentials` or `filesystem.denyRead` are hidden.

**Network goes through a hostname check.** Commands have no direct route out. On Linux they run in their own network namespace; traffic goes through a proxy on the host that checks the requested hostname against `allowedDomains`, which starts empty. The proxy does not terminate or inspect TLS by default, so its decision is based on the hostname the client supplies, and the documentation warns that domain fronting can reach hosts outside the list. After a hostname passes, the proxy refuses it if it resolves only to loopback, link-local (including `169.254.169.254`) or the machine's own addresses. Private ranges such as `10.0.0.0/8` connect, and the check is skipped when traffic goes through an upstream corporate proxy.

**What runs outside.** The documentation lists:

- the built-in Read, Edit, Write, WebFetch and WebSearch tools, which follow permission rules instead, so `denyRead` does not stop the Read tool and `allowedDomains` does not limit WebFetch;
- command hooks, local MCP servers, plugin monitors, LSP servers, the status line command and `apiKeyHelper`, all "with your full access";
- commands typed at the `!` prompt in most sessions, commands matching `excludedCommands`, and retries the model requests with `dangerouslyDisableSandbox` unless `allowUnsandboxedCommands` is `false`.

A custom proxy port takes the rest of the network policy with it: once `httpProxyPort` or `socksProxyPort` applies, the allowlist, deny list and local-address check stop applying to that traffic.

Anthropic's October 2025 post reports the result that made all this worth shipping: in its internal usage, sandboxing cut permission prompts by 84%. The prompts that disappear are the ones the sandbox now answers, which is why the sandbox's gaps matter more once it is on: nobody is looking at those commands any more.

## Codex

Codex's modes are `read-only`, `workspace-write` and `danger-full-access`, with Seatbelt on macOS, bubblewrap on Linux and WSL2, and a Windows sandbox natively. The sandbox applies to spawned commands. Network is off by default; `workspace-write` keeps it off unless `network_access = true` is set. The optional `network_proxy` only constrains traffic once network is on, rules are allowlist-first, `deny` beats `allow`, and `allow_local_binding = false` blocks loopback, link-local and private destinations.

Two lines in OpenAI's own documentation define the edges. The DNS check before a connection "reduces DNS rebinding risk, but it does not eliminate it": a name that resolves to a public address at check time and a private one at connect time is the case it cannot close. And the command proxy does not filter MCP server connections, web search, connectors, browser or Computer Use activity, or cloud tasks. Codex does protect `.git`, `.agents`, `.codex` and `.aws` as read-only inside writable roots, which stops the agent rewriting its own configuration but not reading.

## Gemini CLI

Since 18 June 2026 Gemini CLI serves only enterprise licences and paid API keys; individual users moved to Antigravity CLI, whose sandbox this lesson does not cover. Gemini CLI's sandbox is opt-in through `-s`, `GEMINI_SANDBOX` or settings. On macOS the default Seatbelt profile, `permissive-open`, confines writes to the project directory and allows broad reads and network access. The stronger options are a Docker or Podman container, gVisor's `runsc`, or LXC. By default `security.toolSandboxing` isolates individual tool executions rather than the CLI process; setting it to `false` moves the whole process inside, which shows the other side of the trade: with `runsc` and `--network=none` the sandboxed CLI cannot reach the Gemini API, because the harness itself now needs an egress rule.

| | Default | Reads by default | Network by default | Outside the boundary |
|---|---|---|---|---|
| Claude Code | off | whole machine except denied paths | allowlist starts empty | file and web tools, hooks, local MCP servers, helpers |
| Codex | sandboxed in default mode | no read limit stated; protected paths are write-protected only | off | MCP connections, web search, connectors, browser |
| Gemini CLI (macOS) | off | broad | allowed under `permissive-open` | the CLI process unless `toolSandboxing` is off |

## Three ways a sandboxed agent still leaks a secret

**1. Through an allowed destination.** Every allowed host is a channel. A broad entry such as `github.com` admits gists, issues and pushes to any repository the token or an attacker's token can write; an API host admits uploads to whichever account the request authenticates as. Anthropic's containment post records the case: a file in a Cowork workspace carried hidden instructions and an attacker's API key, and Claude uploaded workspace files through `api.anthropic.com`, an allowed domain, into the attacker's account. The control is to treat each allowlist entry as a capability grant: narrow to the API host rather than the apex, and where the host accepts data, put a proxy that terminates TLS and checks whose account the request acts for. The fix Anthropic shipped passes only requests carrying the VM's own session token.

**2. Through a process outside the boundary.** The Read tool is governed by permission rules, not by the sandbox, so `denyRead` on `~/.ssh` does not stop it; only a `Read(...)` deny rule does. A local MCP server or hook runs with the user's full access. The control is to deny the same paths twice, once as `sandbox.credentials` or `denyRead` and once as a `Read(...)` deny rule; to set `allowUnsandboxedCommands: false` and `failIfUnavailable: true` in managed settings; and, where hooks and MCP servers must be bounded too, to run the whole agent inside the sandbox runtime or a dev container, which the documentation offers for that purpose.

**3. Through the context.** Whatever a command prints or the agent reads becomes part of the next model request and the transcript. From there it can leave in a commit message, a pull request description, a comment, or a URL the client renders. The model API call is made by the harness, outside the sandbox, so no egress rule applies to it. The control is to keep the value out of reach: deny the file, or mask it so the agent only ever sees a placeholder, and scan agent output for secret formats before it is pushed or posted.

## Masking narrows path 3 and can widen path 1

Claude Code's `mask` mode shows sandboxed commands a per-session placeholder, the sentinel, and the proxy substitutes the real value on outbound requests. It needs `network.tlsTerminate`, because the substitution happens inside request contents, and it is honoured only from user, managed or `--settings` configuration. Each entry can list `injectHosts`; an entry without them is substituted on requests to every host in `allowedDomains`.

## When this is wrong

The inventory is version-sensitive. Claude Code's sandboxing page ties many behaviours to specific v2.1 releases, and Codex changed its Linux sandbox at 0.115. Re-check the documentation at the version you deploy; this lesson was checked on 2026-10-28.

Outside the sandbox is not the same as uncontrolled. The Read tool and WebFetch follow permission rules and, in auto mode, a classifier. A deny rule on a credential path holds for the Read tool whether or not the sandbox is on. The gap is that those controls are separate configuration, and teams that enable the sandbox often assume it covers them.

Hostname-based egress is weaker than it looks against a hostile command and fine against a confused model. Domain fronting and DNS rebinding need code written to exploit them, which a prompt-injected agent can produce. For a careless agent following a bad instruction, a hostname allowlist stops most accidental exfiltration. Pick the control by which of those you are defending against.

And none of these sandboxes address path 3 alone. A secret that the agent can read reaches the model provider and the transcript before any egress rule is consulted.
