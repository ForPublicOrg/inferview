## The decision

When an AI feature is under attack or has been, the first decision is which switch to pull, and the second is what to preserve before pulling it. The wrong order either leaves the attacker running while you collect evidence, or destroys the evidence that would tell you whether the attacker still is.

The frame comes from two documents. NIST SP 800-61 Rev. 3 (April 2025) replaced the 2012 Rev. 2 and recast incident response as a profile of the CSF 2.0 functions rather than a standalone lifecycle. CoSAI's AI Incident Response Framework V1.0 maps AI-specific considerations onto those six functions and adds what the NIST document does not have: a taxonomy of AI incidents in five domains (data, model, deployment, infrastructure, user interaction), containment by architecture pattern, AI forensics, and six sample playbooks written in the OASIS CACAO format: training-data poisoning, multi-channel prompt injection, memory injection (MINJA), Poison-RAG, SSRF-based metadata credential abuse, and AGENTPOISON memory and RAG injection.

## The inputs that change it

**Where the attacker's instructions live.** CoSAI's multi-channel injection playbook branches on the vector: user input leads to quarantining the session, injected web or retrieved context to re-scoring or filtering what was retrieved, a compromised agent configuration to taking the agent offline. The audit log is how you tell which branch applies.

**Whether the instructions persist.** An injection in one session dies with the session. An injection written into memory or an index reaches every later session that reads it. CoSAI's containment table separates these: for an LLM with memory, reset memory, isolate sessions, purge conversation history; for RAG, quarantine the data source and validate retrieval results; for an agent, disable tools and tighten authorisation.

**What credentials the agent held.** If the agent could act with a credential, assume the attacker could, for the window the agent was compromised. The SSRF playbook's second step after detection is to quarantine the instance and disable its IAM keys, before the IAM audit and before measuring what was taken.

**Whether you ship the code that runs the agent.** A hosted feature can be fixed for everyone with one deploy. A client, an IDE extension or an on-premises agent cannot: the vendor can stop distribution, but installed copies keep running until each customer acts.

## The options and when each wins

<div class="tablewrap">

| Switch | Stops | Breaks | Propagation | Wins when |
|---|---|---|---|---|
| Disable one tool | that capability, for every session | flows that need the tool | as fast as the dispatcher reads the flag | the harm path goes through one tool and the rest of the feature is safe |
| Revoke a connector or MCP server's credential | everything that server can reach | every tool on that server | token lifetime unless revocation is checked per call | a third-party server or its credential is the compromised part |
| Roll back a model or prompt version | behaviour introduced by the change | improvements in the change | one deploy, if versions are pinned by hash | the incident started with a version change you can name |
| Quarantine memory entries or index items | persistent injected instructions | answers that relied on those items | one read-path filter update | the payload persists across sessions |
| Turn off the feature | everything | everything | one flag | you do not yet know the vector, and the capability is high-consequence |
| Withdraw a client release | new installs of a bad build | nothing installed | none for existing installs | you ship the agent's code; always paired with a customer action |

</div>

Two of these only exist if built beforehand. OWASP's Top 10 for Agentic Applications (ASI04) asks for pinning prompts, tools and configs by content hash and commit id with automatic rollback on hash drift, and for a supply-chain kill switch that can disable specific tools, prompts or agent connections across all deployments. A prompt that lives in a database row edited in place has no version to roll back to; a tool registry without a per-tool flag has only the whole-feature switch.

### Evidence before or after containment

CoSAI lists evidence preservation alongside containment: forensic copies before containment, documented containment actions, the state of the vector database, copies of model weights. Containment by flag destroys nothing, so it can go first, and containment by deletion destroys evidence, so it waits for the snapshot. Disable the tool, then snapshot. Quarantine index items with a read-path filter, then snapshot the index and the write log, then remove. Revoke the credential, but export its access log first if revocation also deletes the grant's history in the provider's console.

### Credential rotation

Rotate the credentials the agent held, not only those of the user it acted for. In order: the credential the compromised component used for downstream calls; any credential reachable from the agent's context or sandbox (environment variables, config files, cloud profiles on the machine it runs on); the build and release credentials if the vector was the build. For each, record the exposure window and query the downstream system's logs for its use in that window. That query needs the component to have held its own credential, the token passthrough point from the audit lesson.

### Memory and index quarantine

CoSAI's MINJA playbook goes detect, quarantine the agent session, alert, analyse the injected memory, prune or sanitise, then retrain or reset agent state. Poison-RAG goes quarantine the item from the retrieval index, review, clean, rebuild the index. The engineering requirement under both is provenance: which session wrote which memory entry, and which source produced which index item. With provenance, quarantine is a set of ids. Without it, quarantine is everything written since the earliest possible compromise time.

### Customer communication

CoSAI section 3.5.1 lists the reporting regimes that may apply (GDPR, NIS2 and DORA in the EU; CIRCIA, HIPAA, GLBA and 50 state breach laws in the US) and says legal counsel is needed to work out the timelines. The engineering contribution is the content: affected versions or tenants, the window, what the attacker could reach, what the customer must do, and how they verify they did it. Templates for each switch in the table above are written before the incident, per CoSAI's playbook structure.

## Worked decision: Amazon Q Developer for VS Code 1.84.0

The facts that are public, from AWS's bulletin (first published 23 July 2025) and CVE-2025-8217. The extension's CodeBuild configuration held an inappropriately scoped GitHub token. A threat actor used it to commit code to the open-source repository, and that code was automatically included in release 1.84.0. NVD describes the code as inert, injected code designed to call the Q Developer CLI, which ran when the extension launched; a syntax error prevented a successful call. Press reporting (iTnews, 28 July 2025) quotes the injected prompt telling the agent to clean a system to a near-factory state and delete resources. AWS revoked and replaced the credentials, removed the code, released 1.85.0 and withdrew 1.84.0 from distribution. The bulletin notes the code is still present in existing 1.84.0 installations and asks customers to remove that version, update, and verify the package against a published SHA-256. OWASP's agentic list files the case under ASI01, ASI02 and ASI04.

### As the vendor

The vector is the build, so the first switch is the credential: revoke the CI token before anything else, because while it is valid the attacker can commit again. Withdrawing the release stops new installs and nothing more. The second decision is scope: every commit and release made while the token was over-scoped is suspect, not only 1.84.0. The third is the recurrence control. AWS's advice to customers, as reported, was to avoid automatic pull-request builds from untrusted contributors; for the vendor that means CI jobs triggered by outside contributions run without write credentials, and release artefacts are pinned to reviewed commits.

The payload was a prompt aimed at an agent with tool access on developer machines. The agent-side control that would have bounded it is the harness's permission model: a destructive shell or cloud command proposed by the agent needs a human approval that a prompt cannot grant. The build control and the agent control are independent, and the incident shows why both exist; the syntax error, not either control, is what stopped this one.

## What to measure after deciding

CoSAI asks for a post-incident review within one to two weeks of resolution. The review measures:

- Time from first malicious action (from the audit log) to detection, and from detection to the last harmful action. The second interval is the containment the switches bought.
- Propagation time of each switch used, from flip to last call.
- Attribution coverage: the share of the attacker's actions for which the log names the actor, the credential and the approval.
- Evidence completeness: whether content for the first malicious action was still inside the content-tier retention when the incident opened.
- Customer action completion: for a client-side incident, the share of affected installs that took the required action, and by when.
- The recurrence tests added: each root cause becomes a deterministic test where the fix is a construction control, or a pinned case in the release attack suite where it is a rate.

## When this is wrong

The switch table assumes the components are separable. An agent whose tools share one credential, or whose prompt, tool list and model are one deploy unit, has fewer switches than the table, and the first incident collapses to "turn off the feature".

The playbooks CoSAI publishes are samples in a machine-readable format, not tested runbooks for your system. Their detection steps name a "Prompt Sanitizer" or a "Memory Drift Detector" as the implementing software; whether anything in your stack fills that slot is the question.

Flag-first containment assumes the flag is honoured by everything that can take the action. Batch jobs, retries in a durable workflow engine and queued tool calls created before the flip may execute afterwards. The drill should include a queued call.

Vendor findings such as "the code did not execute" are evidence, not proof for your environment. The decision is whether checking costs less than the consequence of being wrong, and for cloud deletions it usually does.
