## Requests are the wrong unit

A rate limit on an ordinary API bounds load because requests cost roughly the same. A model call does not. At Claude Sonnet 5.5 list prices ($2 per million input tokens, $10 per million output, checked 2026-10-28), a chat turn with 500 input and 300 output tokens costs 500 × 2 / 10⁶ + 300 × 10 / 10⁶ = $0.004. A turn that pastes a long document, 150,000 input tokens and 8,000 output, costs $0.30 + $0.08 = $0.38. Same endpoint, same one request, 95 times the cost. A limit of 60 requests a minute sized for the first turn lets a user spend $22.80 a minute on the second.

OWASP's LLM10:2025 entry, Unbounded Consumption, lists the ways this gets exploited: variable-length input floods, denial of wallet, continuous input overflow beyond the context window, resource-intensive queries, model extraction through the API, functional model replication, and side channels. Its mitigations include input size limits, rate limiting, resource allocation management, timeouts and throttling, limiting exposure of logits and logprobs, and anomaly detection on usage. The engineering question is which of these sits where, and in which unit.

## Meter in cost, per principal

The provider already does part of this, and its design is worth copying. Anthropic's rate-limits documentation says the API uses a token bucket, measures requests, input tokens and output tokens per minute separately per model class, estimates input tokens at the start of a request and adjusts during it, and counts output tokens as they are generated, ignoring `max_tokens`. For most models, tokens read from the prompt cache do not count toward the input limit.

Your limiter has a harder job, because it decides before the call and the expensive part (output) is unknown. The conservative pattern is reserve and settle: charge the bucket the worst case (actual input tokens plus `max_tokens` at output price) before the call, refund the difference after. A tenant cannot overspend by starting many long generations at once, and a well-behaved tenant gets the refund back within the same second. Denominate the bucket in money, not tokens, so a model change or a long-context price tier changes the charge and not the limit.

Above the bucket sits a hard cap per tenant per day or month. The bucket shapes bursts; the cap bounds the loss. They fail differently, so they answer differently: a bucket rejection is a throttle the client may retry after a computed wait, a cap rejection is a stop that pages a person and is never retried.

```python
# Claude Sonnet 5.5 list prices, USD per million tokens (pricing page, checked 2026-10-28).
PRICE_IN, PRICE_OUT = 2.00, 10.00

def cost(tokens_in, tokens_out):
    return (tokens_in * PRICE_IN + tokens_out * PRICE_OUT) / 1e6

class TenantBudget:
    """Cost-denominated bucket plus a hard daily cap. Reserve before the call, settle after."""
    def __init__(self, usd_per_min, burst_usd, daily_cap_usd, clock):
        self.rate, self.cap, self.level = usd_per_min / 60, burst_usd, burst_usd
        self.daily_cap, self.spent_today, self.clock, self.t = daily_cap_usd, 0.0, clock, clock()

    def reserve(self, tokens_in, max_tokens):
        now = self.clock()
        self.level = min(self.cap, self.level + (now - self.t) * self.rate)
        self.t = now
        hold = cost(tokens_in, max_tokens)          # worst case: every allowed output token is generated
        if self.spent_today + hold > self.daily_cap:
            return None, "daily_cap"                # hard stop: page a human, do not retry
        if hold > self.level:
            return None, "throttle"                 # caller may retry after (hold - level) / rate seconds
        self.level -= hold
        self.spent_today += hold
        return hold, "ok"

    def settle(self, hold, tokens_in, tokens_out):
        refund = hold - cost(tokens_in, tokens_out)
        self.level = min(self.cap, self.level + refund)
        self.spent_today -= refund

t = [0.0]
b = TenantBudget(usd_per_min=1.20, burst_usd=2.00, daily_cap_usd=50.00, clock=lambda: t[0])

hold, why = b.reserve(500, 1_000)                   # chat turn: hold $0.011
b.settle(hold, 500, 300)                            # actual $0.004, $0.007 refunded
for _ in range(6):                                  # a burst of long-document turns at t = 0
    hold, why = b.reserve(150_000, 8_000)
print(why, round(b.level, 3), round(b.spent_today, 3))   # throttle 0.096 1.904
t[0] = 60.0                                         # one minute later the bucket has refilled $1.20
print(b.reserve(150_000, 8_000)[1])                 # ok
```

The per-request limits stay in front of the bucket because they bound the single worst call: an input size cap below the model's context window, a `max_tokens` ceiling per route, a cap on tool calls per agent turn, and a wall-clock timeout per turn. An agent loop that may call a model 40 times per user message needs the bucket charged per model call, not per user message, or one message buys 40 calls at the price of one check.

## The provider's limits are shared by your tenants

The provider's limits are per organisation. Every tenant of your product draws from one bucket, so a tenant who exhausts it denies service to all the others. Anthropic's documentation offers workspaces with their own rate and spend limits below the organisation's, which give a coarse partition (a workspace per tier of customer, or one for batch jobs); per-tenant fairness still has to be yours.

The spend cap is the sharper edge. The same page lists monthly caps of $500 for the Start tier, $1,000 for Build and $200,000 for Scale. At the cap, usage pauses until 00:00 UTC on the first of the next month, and requests return HTTP 429 with error type `rate_limit_error`, `error_code` `enforced_spend_limit_reached` and no `retry-after` header. The documentation notes that retries, including the SDK's automatic retries, fail until access resumes, so a client that treats every 429 as retryable now spends the month retrying. Branch on the error code. A spend limit you set yourself below the cap returns 400 `invalid_request_error` instead, which is a different branch again.

## Abuse is account-level behaviour

Cost limits stop volume. They do not stop a patient actor whose every request is cheap and individually acceptable. Anthropic's November 2025 report on an espionage campaign is the public case. Anthropic assesses with high confidence that a Chinese state-sponsored group manipulated Claude Code into attempting infiltration of roughly thirty targets, succeeding in a small number. The report says AI performed 80-90% of the campaign, with perhaps 4-6 critical human decision points per campaign. The operators got past the model's safeguards by splitting the attack into small, seemingly innocent tasks and by telling Claude it worked for a legitimate cybersecurity firm doing defensive testing. At peak the system made thousands of requests, often multiple per second.

Each prompt in that campaign could pass a single-prompt classifier, because each was a plausible fragment of a security engagement. What did not look plausible was the account: request rates no human operator sustains, a sequence that runs reconnaissance, then exploit development, then credential harvesting, then data extraction, across many unrelated external organisations. Anthropic's response, over ten days, was account bans, notification of affected entities and coordination with authorities, then expanded detection and better classifiers for malicious activity.

The engineering consequence is a second detection path that is stateful and runs off the request path:

- **Features per account and per linked group of accounts**: sustained request rate against a human-plausible ceiling, distinct external targets touched by tool calls, the sequence of task categories within a session and across sessions, tool mix, and shared payment instruments or network origins across accounts.
- **A stream job, not a middleware**: the inline filter sees one request; the abuse detector sees an account's last hour and last month, and its decisions arrive seconds to hours later.
- **Graded actions**: throttle, step-up verification, human review, suspension. Each action is logged with the features that triggered it, because the account owner will appeal and the reviewer needs the evidence.

<Callout kind="gotcha">
"We are a security firm running an authorised test" is what the attackers in Anthropic's report said, and it is also what your legitimate security customers say. A detector that keys on that claim, in either direction, has learned the cover story. Key on behaviour the cover story does not change: rate, breadth of targets, and whether the targets are the customer's own.
</Callout>

## Extraction and replication

Two of OWASP's examples are about the model rather than the bill: extraction through the API and functional replication, where an attacker uses your outputs as training data for an equivalent model. The extraction risk is not theoretical. Carlini and colleagues (2024) report extracting the embedding projection layer of OpenAI's Ada and Babbage models for under $20 in queries with typical API access, confirming hidden dimensions of 1024 and 2048, and estimate under $2,000 for the full matrix of gpt-3.5-turbo. OWASP's matching mitigation is to limit exposure of logits and logprobs: every extra number per token you return is information per query.

For a product that serves its own fine-tuned model, the controls fall into two kinds. Some hold by construction: return no logprobs or only top-1, no logit bias parameter, a fixed decoding configuration per route. Others lower a rate: detectors for query sets with the shape of dataset generation (high volume, broad and systematic coverage of a task space, outputs never used in the product's own flows). Replication through ordinary outputs cannot be prevented by construction if the product's purpose is to produce those outputs; it can be priced, rate-limited and made contractually expensive.

## When this is wrong

Reserve and settle assumes you know the price at decision time. Cache reads on Sonnet 5.5 bill at 0.05 times the base input price, reasoning tokens are unknown until the call ends, and long-context pricing changes the rate above a prompt-size threshold on some models (Haiku 5.5 above 100,000 tokens). A bucket charged at list input price over-reserves cached traffic, which is the safe direction; a bucket that ignores reasoning tokens under-reserves, which is not.

Cost metering protects a usage-billed product. A product sold per seat absorbs the cost itself, and there the cap is a margin control that users will experience as a feature limit. The number then comes from unit economics, not security.

Account-level detection assumes accounts mean something. Free tiers with cheap sign-up let an actor spread behaviour across hundreds of accounts, each under every threshold. The linked-account features (payment, origin, timing) carry the load there, and they have high false-positive rates for customers behind shared corporate egress.

The provider figures in this lesson (tiers, caps, error codes) come from Anthropic's documentation checked on 2026-10-28. Other providers name and enforce limits differently, and the same provider changes them; read the current page before building on an error code.
