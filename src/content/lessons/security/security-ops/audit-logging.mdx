## The record is the evidence

An audit log for an agent answers four questions after the fact: which principal caused this action, under which credential, which policy allowed it, and what the model had in front of it when it chose. Operational traces answer a different question (what ran, how long it took, what failed) and are sampled, truncated and kept for days. The audit record is written for every action, kept for months, and read by someone who was not on the team that wrote it.

For a deterministic service an investigator can often rebuild a decision from the inputs and the code version. For a model step that route is closed. CoSAI's AI Incident Response Framework (section 3.3.3.1) notes that the same input and system prompt will not in general produce the same output, so the raw output has to be preserved to reconstruct an incident. The log is not a pointer to the evidence; for the model's part of the decision it is the only evidence.

The content an investigator wants (prompts, completions, tool arguments and results) is the content most likely to hold personal data. OpenTelemetry's GenAI conventions treat it that way: capture is gated by an explicit opt-in, the environment variable `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT` defaults to `NO_CONTENT`, and `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result` are Opt-In attributes carrying a warning that they may contain sensitive information. Turn content capture on in the trace pipeline and the trace backend becomes a personal-data store with no retention rule, readable by everyone who can read latency dashboards.

## What the investigator needs

CoSAI section 3.2 lists the attributes it treats as essential for detection and response: timestamp, identity, `prompt_text`, `completion_text`, `model_name/version`, `token_usage`, `latency_ms`, `retrieved_docs`, `tool_calls`, `confidence_score`, `drift_metrics` and `trace_id/session_id`. For an agent it misses the three fields that answer "who allowed this": the approval, the policy decision and the credential the tool call ran under.

<div class="tablewrap">

| Field group | Contents | Where it comes from |
|---|---|---|
| Model | requested model id, served model id, prompt template name and version, digest of the system instructions | `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.prompt.name`, `gen_ai.prompt.version` (OTel client inference) |
| Tool call | tool name, provider call id, structural summary of arguments, digests of arguments and result | `gen_ai.tool.name`, `gen_ai.tool.call.id` (OTel execute_tool span); the summary is yours |
| Actor chain | end user, agent identity and version, conversation id | `gen_ai.conversation.id`, `gen_ai.agent.name`; the user is yours |
| Credential | subject, audience, client id and token id of the credential the tool ran under | your auth layer |
| Approval | approver, digest of what was shown, decision, time to decide | your approval service |
| Policy | policy bundle version, rule id that matched, effect | your policy engine |
| Retrieval | document ids and the index snapshot they came from | your retriever |
| Content | a reference to the stored prompt, completion, arguments and result | `*_ref` attributes or your own store |

</div>

The requested and served model ids are separate fields because they differ whenever the request names an alias. An investigator asking "did the regression start with the model change" needs the served id, and the alias hides it. The prompt version and the instructions digest answer the same question for your own changes.

The conventions are marked Development, so attribute names can change under you; the audit schema should be your own, populated from the spans, with the semconv version recorded. The conversation id must not be synthesised: the spec says a new UUID, a trace id or a content hash should not be used as a fallback. If the framework does not hand you a conversation id, your application has to mint one at session start and propagate it, or the actor chain falls apart at the first async boundary.

## Content: inline, digest, or reference

OTel describes three patterns. The default records no content. The second records content on span attributes, which the spec calls suitable when telemetry volume is manageable and either privacy rules do not apply or the storage complies with them, for example pre-production. The third uploads content to external storage and records a reference on the span; the spec recommends it for production because separate storage allows separate access controls, and it leaves the URI scheme, layout, retention and access mechanism to you.

The audit design built on the third pattern has two tiers:

- **The audit tier** holds structure only: ids, versions, digests, summaries, decisions. It is append-only and kept long.
- **The content tier** holds prompts, completions, tool arguments and results per tenant, encrypted under a per-tenant key, kept short, readable by a small incident-response group, with every read itself logged.

The digests join the tiers. A plain SHA-256 of a short, low-entropy argument is reversible by guessing (the set of plausible refund amounts for one order is small), so the digest is an HMAC under the same per-tenant key. Destroying that key unlinks every digest for the tenant, which is how an erasure request is honoured without rewriting an append-only log.

The structural summary is the part teams skip. An investigator rarely needs the body of an email the agent sent; they need the recipient domain, the attachment count and whether the user approved exactly what was sent. Each tool registers a summary function next to its schema, and the summary is reviewed like the tool: whatever the summary keeps in clear is now in the long-lived tier.

```python
import hashlib, hmac, json

# Per-tenant key held in a KMS; destroying it unlinks every digest for that tenant.
TENANT_KEYS = {"t-42": b"kms-managed-secret"}

# Structural summaries per tool: what an investigator needs without the free text.
SUMMARY = {
    "send_email": lambda a: {"recipient_domain": a["to"].split("@")[1], "attachments": len(a.get("files", []))},
    "refund": lambda a: {"order_id": a["order_id"], "amount_cents": a["amount_cents"]},
}

def digest(tenant, obj):
    blob = json.dumps(obj, sort_keys=True, separators=(",", ":")).encode()
    return hmac.new(TENANT_KEYS[tenant], blob, hashlib.sha256).hexdigest()

def audit_event(tenant, ts, conv_id, user, agent, cred, model, tool, args, result, approval, policy, content_ref):
    return {
        "ts": ts, "tenant": tenant, "conversation_id": conv_id,
        "actor": {"user": digest(tenant, user), "agent": agent},
        "credential": {"sub": digest(tenant, cred["sub"]), "aud": cred["aud"],
                       "client_id": cred["client_id"], "jti": cred["jti"]},
        "model": model,
        "tool": {"name": tool, "summary": SUMMARY[tool](args),
                 "args_hmac": digest(tenant, args), "result_hmac": digest(tenant, result)},
        "approval": {**approval, "approver": digest(tenant, approval["approver"])},
        "policy": policy, "content_ref": content_ref,
    }

args = {"to": "ana@example.org", "subject": "Your refund", "body": "Hi Ana, your card ending 4242 ...", "files": []}
ev = audit_event(
    "t-42", "2026-10-28T09:14:03Z", "conv_8f2", "user-1187", "support-agent@v14",
    {"sub": "user-1187", "aud": "https://mail-mcp.internal", "client_id": "support-agent", "jti": "tok_77a"},
    {"requested": "support-default", "served": "vendor-model-2026-09-15", "prompt_version": "support/31",
     "instructions_hmac": digest("t-42", "system prompt v31")},
    "send_email", args, {"status": "queued"},
    {"approver": "user-1187", "shown_hmac": digest("t-42", args), "decision": "approve", "ms_to_decide": 4200},
    {"bundle": "policy@2026-10-20", "rule": "email.external.requires_approval", "effect": "allow"},
    "s3://audit-content-t-42/conv_8f2/turn-7.json",
)
flat = json.dumps(ev)
assert "card ending" not in flat and "ana@" not in flat and "user-1187" not in flat
assert ev["tool"]["args_hmac"] == ev["approval"]["shown_hmac"]  # what was approved is what ran
print(json.dumps(ev["tool"], indent=1))
```

The second assertion is the one worth putting in CI. If the digest of what the approver was shown differs from the digest of what executed, either the client rendered something other than the call, or something rewrote the arguments between approval and dispatch. Both are findings, and neither is visible in a log that records only "approved: true".

## Retention as a written rule

Two legal pressures pull in opposite directions. GDPR Article 5 requires personal data to be limited to what is necessary (5(1)(c)) and kept in identifiable form no longer than necessary for the purpose (5(1)(e)). The EU AI Act, Article 19, requires providers of high-risk AI systems to keep the logs under their control for a period appropriate to the intended purpose, of at least six months, unless Union or national law, in particular on personal data, provides otherwise; the provision applies from 2 December 2027 for Annex III systems. CoSAI's advice is to set retention objectives at design time rather than discover them during an incident.

The two-tier split lets both hold:

<div class="tablewrap">

| Tier | Holds | Retention (choices to defend) | Deletion |
|---|---|---|---|
| Audit | ids, versions, HMACs, summaries, approvals, policy decisions | at least the regulatory floor where one applies; the example below uses 400 days | append-only; erasure by destroying the tenant key |
| Content | prompts, completions, tool arguments and results | longer than your measured time to detect plus time to start an investigation; the example uses 30 days | TTL; legal hold by incident id extends it for the objects an incident names |

</div>

The content window has a lower bound that comes from operations, not law. If incidents are typically noticed three weeks after the first malicious action, a 14-day content TTL means the evidence of the first actions is gone on the day the incident opens.

## Token passthrough breaks the trail

The credential fields in the record only mean something if the component that made the downstream call held a credential of its own. The MCP security best practices (revision 2026-07-28) forbid token passthrough, where an MCP server accepts a token not issued to it and forwards it unchanged to a downstream API, and list the audit consequences: the server cannot identify or distinguish the clients calling it with an upstream-issued token, the downstream resource server's logs show requests from a different source with a different identity, and both make investigation and auditing harder. The mitigation is a MUST NOT: servers must not accept tokens that were not explicitly issued for them.

With passthrough, the downstream API log says "user 1187's token deleted these records". It does not say that an agent did it, which agent version, in which conversation, or after which approval. The MCP server's own log, if it logs at all, has an opaque token it never validated. Two logs, no shared key.

With audience validation and a server-held downstream credential, the chain has a join at every hop. The MCP server validates that the inbound token's audience is itself, logs the inbound subject, client id and token id with the conversation id the client sent, then calls the downstream API with its own credential and logs that credential's id against the same event. The downstream log names the MCP server; the MCP server's log maps that call to the user, the agent and the conversation. The investigator walks from the deleted record to the approval in three lookups.

Scope design shows up in the same records. The MCP guidance notes that a single omnibus scope masks user intent per operation, and asks servers to log elevation events (scope requested, granted subset) with correlation ids. A record whose credential carries `files:*` says nothing about what the user meant to allow.

<Callout kind="gotcha">
Logging the bearer token itself, or a reversible fragment of it, turns the audit store into a credential store. Log the token id (`jti`), subject, audience and client id. The investigator needs to know which credential acted, not to be able to use it.
</Callout>

## Tamper evidence

OWASP's Top 10 for Agentic Applications (December 2025) asks for immutable logs of tool invocations and parameter changes (ASI02) and immutable, signed audit logs of agent actions, tool calls and inter-agent communication (ASI10). For an audit tier that means a write path the agent's own credentials cannot reach: the agent emits events to a collector, and only the collector can write to object storage with retention lock or to a hash-chained table. An agent compromised by injection that can call `delete_logs` has made its own log optional.

## When this is wrong

Digests prove that recovered content matches what ran; they do not recover it. After the content TTL, an HMAC answers "was this the prompt" only if someone produces the prompt from elsewhere. For an incident discovered late, the structural summary is all there is.

Per-tenant HMACs of user ids are still linkable by anyone holding the key, and the audit tier with its long retention is still a store of data about people. The two-tier design shrinks what the long-lived tier holds; it does not take the tier out of privacy review.

Retrieved document ids are evidence only while the index they point into still exists in that form. A nightly re-index that renumbers chunks, or a quarantine that deletes them, leaves the record pointing at nothing. Record the index snapshot id, and keep snapshots referenced by an open incident.

The model provider's own retention of your prompts is outside this design. A provider copy kept for abuse monitoring has its own retention and access rules, and key destruction does not reach it.
