## What the review adds

A design review for an AI feature runs the usual review (identity, authorisation, data classification, dependencies, logging, failure handling) and adds four questions. Each question has an artefact the design owner brings, and the review's output is a list of findings with a label and an owner for each.

1. **What is untrusted text?** Every source that reaches the context, with who can write it.
2. **What can it cause?** The capability matrix per session, including side channels and output sinks.
3. **What does a successful attack cost?** The blast radius per tool, in units the business uses, with the caps that bound it.
4. **Which control is deterministic?** Each control labelled as holding by construction or lowering a rate.

The fourth question changes how the other three are answered. Since Nasr and colleagues (October 2025) bypassed 12 published injection defenses with adaptive attacks, reaching success above 90% for most of them, a review assumes injection succeeds and judges the design by what an injected model can reach.

## Question 1: what is untrusted text

OWASP's 2026 LLM01 entry gives the review a vocabulary: delivery surface (direct input, retrieved content, tool output, tool connection channel, persistent memory), propagation (single shot, multi-step, cross-session through memory or RAG, self-replicating across agents) and encoding (plain text, base64, invisible Unicode, images, low-resource languages). It also sorts surfaces by trust and warns that trusted surfaces are fed by low-privilege channels: a public form that becomes a ticket, a community pull request that lands in your repository.

The evidence to request is the code that assembles the context, not the system prompt. Prompts describe intent; the assembly code shows that the retrieval step also pulls ticket comments, that tool results are appended unfiltered, and that a memory file from the last session is prepended. A review that reads only the prompt reviews the author's model of the system.

## Question 2: what can it cause

Two artefacts. The capability matrix scores each session type on the Rule of Two. The tool manifest lists, for each tool, the identity it runs as and that identity's downstream permissions: OAuth scopes, database grants, payment API roles.

The manifest is where OWASP 2026 LLM03 (Excessive Agency, now third on the list) finds its three root causes: excessive functionality (a read tool that also deletes), excessive permissions (a tool that reads one user's documents with an identity that can read everyone's), excessive autonomy (a high-impact action with no independent check). Its mitigations read as review questions: is each tool executed in the user's context, preserved across chained calls; is authorisation enforced in code by the tool, a policy point or the downstream system, never by the model.

Output sinks belong here too. Improper Output Handling fell from fifth to tenth in 2026, but OWASP widened it to cover the insecure code assistants generate. Any place model output is interpreted (a Markdown renderer, an HTML template, a SQL string, a shell, a code review bot that merges) is a capability.

## Question 3: what does a successful attack cost

For each tool with C, write the worst outcome of one call and of one session in the business's units: money, records, recipients, deploys. Then mark reversibility. A refund can be clawed back at a cost; a sent mail cannot be unsent; a deleted record without a tombstone is gone. The caps that bound the blast radius are part of the design, and a cap per call without a cap per session is a common gap.

## Question 4: which control is deterministic

Each control gets one of two labels. **By construction**: the action is impossible whatever the model emits, because the tool is not loaded, the identity lacks the permission, the service rejects the argument, or the renderer drops the sink. **By rate**: the model is less likely to emit the action, as with prompt instructions, spotlighting, classifiers and approval prompts. OWASP 2026 LLM01 says the second kind degrades against adaptive attackers and the first kind survives.

A finding is not "add a guardrail". A finding names the boundary, the control, its label, and, for rate controls, the residual risk someone must accept in writing.

## The standard questions, with the AI-specific answer

**Logging.** CoSAI's AI Incident Response Framework lists baseline telemetry: input and output logging, system prompt and configuration versioning, tool usage tracking, authentication events and vector query patterns. Its attribute list adds identity, model name and version, retrieved documents, tool calls and a trace or session id. Without tool calls and the prompt version, an investigation cannot say what the agent did or why. Logging prompts in full conflicts with data minimisation, so retention and access for prompt logs is a decision, not a default.

**Containment.** CoSAI's containment step is to disable tools or roll back to a prior model and gate high-risk features. Ask for a kill switch per tool, who can flip it, and when it was last exercised.

**Supply chain.** OWASP 2026 LLM01 asks for MCP servers and tool packages to be pinned, signed and verified, and notes that pinning does not stop a payload shipped in the pinned version or a description change that leaves the version alone. The model version is a dependency with the same review.

**Memory.** OWASP 2026 treats memory writes as privileged: log the prompt that caused each write and require approval before instruction-bearing memories persist across sessions.

**Which list.** OWASP's 2026 LLM list states its boundary: it owns the model as a component, and once the model is an actor with tools, memory and downstream effects, the Agentic Top 10 (ASI01 Agent Goal Hijack to ASI10 Rogue Agents) covers it. Cite findings by edition and number, since the 2025 and 2026 LLM numbering differ.

## A worked review

A hypothetical design: a support agent reads a customer's ticket, looks up orders through a service account that can read all orders, issues refunds through the payments API with the $200 per-call cap above, and posts its reply to the customer portal, which renders Markdown. One session type. An injection classifier screens tickets. Logs keep the final reply.

| Finding | Reference | Control | Label | Owner |
|---|---|---|---|---|
| Order lookup reads every customer's orders; an order id in a ticket returns another customer's data | LLM03:2026 excessive permissions; LLM02:2026 | Lookup runs with the customer's session token; orders service enforces ownership | Construction | Orders team |

| Refund inside the bounds that the customer did not deserve | LLM01:2026 | Classifier plus refunds above a threshold queued for staff | Rate; residual risk | Support lead signs |
| Replies rendered as Markdown in the portal | LLM10:2026 | Render replies as plain text; links only to an allowlisted domain | Construction | Portal team |
| Logs hold the reply only | CoSAI section 3.2 | Log tool calls with arguments, prompt version, model version, session id | Detection | Platform team |
| No way to stop refunds without a deploy | CoSAI containment | Per-tool kill switch, owned by the on-call, exercised in a game day | Containment | On-call lead |

</div>

The classifier is still in the design. Once the first, second and fourth findings land, it stops being the only control between a ticket and a refund and becomes a detector whose alerts the security queue reads. The third finding is the one the review cannot close: an attacker who stays inside every bound can still talk the agent into a refund for their own order. That is a business decision about fraud tolerance, and it is written as one, with the support lead's name on it.

## What gets written down

The review closes when each of these has an owner and a date:

- Residual risk for every boundary held only by rate controls, in a sentence a non-engineer can read.
- Which session types run supervised, and what the supervisor sees (the exact action, not a summary).
- Caps per call, per session and per day for each tool with C, and where each is enforced.
- Prompt-log retention and who can read the logs.
- The kill switch per tool and its owner.
- Re-review triggers: a new tool, a new data source, a new crossing between sessions, a model change, a change to the context assembly code.

## When this is wrong

A review checks a design, and the risky changes in AI features rarely touch the design. A new retrieval source added to the context assembly, a model upgrade that changes how often the model follows embedded instructions, a tool description edited by a vendor: none of these reopens a design review unless the re-review triggers name them and something in CI notices.

Mapping a design onto the OWASP entries is not a threat model. A document that lists all ten entries with "mitigated" beside each one, and no control, label or test, passes a superficial review and fails the first incident. The lists are taxonomies for naming findings.

Rate controls are sometimes the right answer. When the bounded cost of a successful attack is small and reversible (a support reply with a wrong tone, a refund within a tight daily cap), a classifier and monitoring can be acceptable, and the review should say "acceptable if" with the bound that makes it so rather than demanding construction everywhere.

The four questions assume the harm comes from someone else's text. The same agent can issue a wrong refund on a misread ticket with no attacker at all, and OWASP's LLM03 lists hallucination as a trigger for Excessive Agency beside injection. The caps found under question 3 protect against both; the labels under question 4 describe only the attacker.
