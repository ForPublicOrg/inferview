## The unit of review is the session

A per-tool review approves `read_inbox` because it is read-only and approves `fetch_url` because it is read-only. Together, in one context window, they are an exfiltration path: text in a mail tells the model to fetch a URL with the inbox in its query string. Neither tool changed. The context they share did.

Meta's Agents Rule of Two (31 October 2025) is stated per session for this reason: no more than two of [A] processing untrustworthy input, [B] access to sensitive systems or private data, [C] changing state or communicating externally. Willison's lethal trifecta (June 2025) is the exfiltration subset: private data, untrusted content, and a way to send it out. Both are properties of a set of capabilities in one context, so the artefact a review needs is a matrix with one row per session type, not a list of tools with a verdict each.

The OWASP Top 10 for Agentic Applications (December 2025) gives two ASI02 scenarios that a per-tool review passes. An internal-only CRM tool is chained with an external email tool to send a customer list out. A coding agent's auto-approved `ping` tool, judged harmless, exfiltrates data through DNS queries. Each tool was fine alone.

## Building the matrix

**Rows are session types.** A session type is one combination of entry point, context contents and tool set. The same agent usually has several: an interactive chat, a scheduled job, a run triggered by a webhook, a subagent spawned with a narrower tool list. Two runs belong to the same row only if the same principals can write into their context and the same tools are loaded.

**Column A: who writes the context.** Mark A for any text whose writer is outside the principals you trust for this session: retrieved documents, tool results, tool descriptions from a third-party server, other agents' output, and memory written by an earlier session. Derived text inherits the mark. A summary of a hostile mail is hostile text, because the model that wrote it was reading the mail.

**Column B: what the session can read or reach that the writer of A cannot.** This is the column teams mark too generously and too narrowly at once. Too generously: a customer-facing chat scoped by the customer's own token gives the customer nothing an injection could not get by asking, so their own order history is not B relative to them. Too narrowly: B covers any sensitive system, not only private data, which is how Meta clarified it after Willison's critique.

**Column C: every state change and every channel by which bytes leave.** Send tools are the obvious entries. The ones a review misses: a GET whose URL the model chooses, a DNS lookup, an image or link the client renders and fetches, a file written to a synced or public location, a calendar invitation, a comment on a public issue, a log line an outsider can read. The ASI02 `ping` scenario is this column in one sentence.

A session with three marks needs supervision or a split. A session with A, B and an outbound channel in C is also a trifecta and can leak data without changing any state.

<Callout kind="gotcha">
Tools that load at runtime break a matrix drawn from the deployment manifest. If users enable connectors mid-session, the row is the set they could enable, not the set they usually do.
</Callout>

## Combinations, not tools

Willison's point about MCP is that users mix tools from different sources, and a vendor can fix its own product's exfiltration path but cannot protect a user who combines connectors. The matrix makes the size of that problem countable.

## Splitting sessions

A split removes a leg from each session and then controls what crosses between them. Meta's post gives one example per pair:

- **Travel agent [A, B].** It drops C by requiring human confirmation before bookings or deposits, and by letting the agent request only URLs from trusted sources, not URLs it constructs.
- **Browsing research assistant [A, C].** It drops B by running the browser in a sandbox with no preloaded session data and limiting access to private information beyond the initial prompt.
- **Internal coder [B, C].** It drops A by filtering every source in the context by author lineage, with a human review process to grant access to data outside that filter.

The post also allows a one-way move within a session: start in [A, C] with internet access, then disable external communication before touching internal systems, ending in [B] plus the untrusted text already read. The move is one-way because re-enabling C would complete the set.

The part of a split that fails in review is the crossing. If session 2 reads session 1's free text and session 1 had A, session 2 now has A. A split holds only when what crosses is constrained to a type that cannot carry instructions: an enum, a boolean, an identifier that must resolve in a store you own. That is the dual LLM and map-reduce idea from the design-patterns paper Willison summarises: the session that reads hostile text returns symbols or constrained results, never prose, to the session that acts.

<SecuritySecureArchitectureSessionSplit />

Start from the default, where session 1 holds the inbox, the fetcher, the send tool and image rendering. Move `send_email` and image rendering to "Not given" and session 1 still scores 3 of 3, because `fetch_url` supplies both A and C. Move the fetcher to session 2: both sessions drop to two properties, session 2 as [A, C] because of the fetcher. Now set the fetcher to "Not given", so session 2 holds only `create_event`, and tick the free-text crossing: session 2 picks up A from session 1's summary. It still scores two, but text an attacker mailed to session 1 now chooses who receives invitations from session 2, which is the [A, C] harm Willison objected to Meta calling safe.

## The matrix as code

Keeping the matrix in the repository, generated from the tool registry, means a new tool or a new crossing fails a check instead of waiting for the next review.

```python
TOOLS = {  # tool: properties it supplies; "out" marks an outbound channel
    "read_inbox": {"A", "B"}, "read_calendar_freebusy": {"B"},
    "fetch_url": {"A", "C", "out"}, "send_email": {"C", "out"},
    "create_event": {"C", "out"}, "render_images": {"C", "out"},
}
SESSIONS = {
    "triage": ["read_inbox"],
    "reader": ["fetch_url"],
    "scheduler": ["read_calendar_freebusy", "create_event"],
}
CROSSINGS = [("triage", "scheduler", "typed")]  # ("free" would carry A across)

def props(session):
    p = set().union(*(TOOLS[t] for t in SESSIONS[session]))
    for src, dst, kind in CROSSINGS:
        if dst == session and kind == "free" and "A" in props(src):
            p.add("A")
    return p

for s in SESSIONS:
    p = props(s)
    legs = len(p & {"A", "B", "C"})
    trifecta = {"A", "B", "out"} <= p
    print(f"{s:10} {sorted(p & {'A','B','C'})} legs={legs} trifecta={trifecta}")
    assert legs <= 2, f"{s} needs supervision or a split"
```

Change the crossing to `"free"` and the scheduler fails the assertion. Add `fetch_url` to triage and triage fails. The check is deliberately dumb: it encodes the review's decisions so that changing them is a visible diff.

<p>Stop treating user-chosen connector sets as session types. Classify each connector by the legs it supplies, then offer a small number of session profiles, each with at most two properties, and route a request to a profile instead of loading every enabled connector. </Fragment>
<Fragment slot="long">
<p>With twelve connectors, the number of user-built combinations is too large to review one by one, and most of them hold all three properties if even a few connectors supply A and C. The quarter is enough to change the unit of configuration, not to review combinations.</p>
<p>First pass: label every connector with what it supplies, including side channels (a fetcher is A and C; a mailbox is A and B; a chat client rendering images is C). Second: define profiles such as "read and summarise" [A, B] with no outbound, "research" [A, C] with no internal data, and "act on internal systems" [B, C] whose input is the user's request and typed fields. Third: the router picks a profile per request; crossings between profiles are typed.</p>
<p>The cost is real. Some workflows that used to be one turn become two, and a few need approval on the send. I would measure how many requests need the all-three path in the first month and put that number in front of product. What I give up in writing: a profile's B and C are coarse, and an [A, C] research session can still be steered into posting attacker text publicly.</p>

## When this is wrong

The marks are binary and the harm is not. An [A, C] session that can post to a public channel and one that can only append to a log the user reads score the same. Meta changed the label on the untrusted-input-plus-state-change intersection from "safe" to "lower risk" after Willison objected that an injection can still do harm there without any sensitive access. Read two marks as "no injection-driven data theft through this session", not as "safe".

The rule says nothing about how far an agent can go before anyone looks. OWASP's 2026 LLM01 entry notes the Rule of Two is silent on autonomy depth: a [B, C] session that runs two hundred steps unattended is scored the same as one that runs two.

Session boundaries are only as fresh as the state they share. A memory store, a scratch file or a cache that one session writes and another reads is a crossing, and an untyped one. OWASP 2026 makes the point for memory: one poisoned write reaches every later session that reads the store.

The matrix covers injection-driven harm. Meta says the rule is not sufficient for agent mistakes, hallucinations or excessive privilege, and a session with one property can still delete the wrong records on a misunderstood request. And no split removes the A leg's rate problem: with adaptive attack success above 90% for most of the 12 defenses Nasr and colleagues tested, the matrix assumes injection succeeds and asks only what it can reach.
