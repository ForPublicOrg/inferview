## Three controls, three different promises

A data-protection review of an LLM feature usually ends with three lines in the design document: "PII is redacted", "we do not log prompts", and "data stays in region". Each is a different kind of control, and the review goes wrong when they are read as the same kind.

Redaction is a detector. It lowers the rate at which personal data reaches the place downstream of it, and its miss rate is a number you measure on your own traffic. Not recording content in a telemetry pipeline holds by construction for that pipeline, and only that one: the prompt still exists in the provider's request, your application logs, your eval set and the conversation store. Residency is a configuration on a vendor's system plus a contract, and it holds for exactly the data and processing the setting names, which on the Claude API is two settings with different scopes.

## Where personal data goes

Personal data flows through more places in an LLM system than in a typical CRUD service: the prompt, the provider's API, your application logs, your traces, the eval set someone built from production traffic, the conversation history the product stores, and the model's answers, which can repeat anything in the context. Redact before data leaves the boundary you control, and treat logs and traces as a separate path, because they usually hold the full prompt and they are copied to more vendors and more people than the primary store.

The eval set is the copy teams forget. A set built by sampling production conversations is a second database of user content with weaker access control, longer retention and no deletion path, and it is the one most likely to be pasted into a notebook or sent to a labelling vendor.

## Redaction is a detector with a miss rate

Presidio's own site says there is no guarantee it will find all sensitive information and that other protections should be used. Its recognisers combine named-entity recognition, regular expressions, rule-based logic, checksums and context words. Each method has a known blind spot. A regular expression with a Luhn checksum catches a card number and misses "jane dot doe at corp dot example". NER finds names in prose and misses them in a CSV pasted into the chat. Context words help when the user writes "my IBAN is" and not when the IBAN arrives in a tool result.

Per-entity recall is not the number that matters, because a transcript is clean only if every entity in it was caught.

Hashing is not anonymisation for low-entropy values. There are at most 10<sup>10</sup> ten-digit phone numbers; at a scenario rate of 10<sup>9</sup> SHA-256 hashes per second, hashing every candidate takes 10<sup>10</sup> / 10<sup>9</sup> = 10 seconds, after which every unsalted hash in the log is reversed. If you need to join on a value across systems, use a keyed hash (HMAC with a key held in a KMS and never written to the log) or a tokenisation service, and treat the key as the thing that makes the log personal data again.

## Telemetry content is opt-in in the standard

The OpenTelemetry semantic conventions for generative AI (status Development, checked 28 October 2026) mark the content attributes as Opt-In: `gen_ai.input.messages`, `gen_ai.output.messages` and `gen_ai.system_instructions` on inference spans, and `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result` on tool spans. The convention says instrumentations SHOULD NOT capture prompts, completions, retrieval queries, prompt template variables or memory records by default and SHOULD offer an opt-in, and the default mode is no content on spans or events. It also defines an external path: content is stored elsewhere and the span carries a reference such as `gen_ai.input.messages_ref`, with upload enabled independently of the capture flags.

That design gives you the split a policy needs. Metadata (operation, provider, model, token counts, finish reasons) is Recommended and safe to send to a shared tracing vendor. Content goes, if anywhere, to a store you choose with its own access control, retention and region, and the trace points at it. Two things break the split in practice. Auto-instrumentation libraries ship with their own defaults, and a library upgrade can turn capture on; the check belongs in CI against the exported spans, not in a config review. And tool arguments carry content too: an agent's `send_email` call has the email body in its arguments.

## What logs must never contain

The list that survives review is short, and each item has a reason other than "it is sensitive":

- **Message content, system prompts and tool arguments or results** in any log or trace shipped to a shared backend, because the backend's access list, retention and region are not the conversation store's.
- **Secrets that reached the context**: API keys a user pasted, tokens in tool results, connection strings in a system prompt. Redaction for secrets is a detector too, so the control is keeping secrets out of context in the first place.
- **Raw user identifiers** where a keyed pseudonym serves the join.
- **The pseudonym key** in any system that also holds the pseudonyms.

What logs should contain is the reverse: everything needed to debug cost, latency and failure without reading a conversation.

```python
import hashlib, hmac, json, os

PSEUDONYM_KEY = os.urandom(32)   # in production: from a KMS, rotated, never in logs or prompts

def pseudonym(value: str) -> str:
    return hmac.new(PSEUDONYM_KEY, value.encode(), hashlib.sha256).hexdigest()[:16]

KEEP = {"gen_ai.operation.name", "gen_ai.provider.name", "gen_ai.request.model",
        "gen_ai.response.finish_reasons", "gen_ai.usage.input_tokens",
        "gen_ai.usage.output_tokens", "inference_geo"}
PSEUDONYMISE = {"tenant", "user"}

def log_record(span: dict) -> str:
    out = {k: v for k, v in span.items() if k in KEEP}          # allowlist, not denylist
    out.update({k: pseudonym(span[k]) for k in PSEUDONYMISE if k in span})
    return json.dumps(out, sort_keys=True)

span = {
    "gen_ai.operation.name": "chat", "gen_ai.provider.name": "anthropic",
    "gen_ai.request.model": "claude-opus-5-5", "gen_ai.response.finish_reasons": ["end_turn"],
    "gen_ai.usage.input_tokens": 1830, "gen_ai.usage.output_tokens": 212,
    "gen_ai.input.messages": [{"role": "user", "content": "My IBAN is DE89 3704 0044 0532 0130 00"}],
    "gen_ai.tool.call.arguments": {"email": "jane.doe@corp.example"},
    "inference_geo": "us", "tenant": "acme-gmbh", "user": "jane.doe@corp.example",
}
line = log_record(span)
print(line)
assert "IBAN" not in line and "jane" not in line and "acme" not in line
assert pseudonym("jane.doe@corp.example") == json.loads(line)["user"]
```

The allowlist is the control that holds: a new attribute added by a library upgrade is dropped until someone adds it to `KEEP` in a reviewed diff. A denylist of content attributes would pass the next attribute name the convention adds, and the convention is still in Development status.

## Residency on the Claude API is two settings

Anthropic's data residency page (checked 28 October 2026) describes two independent controls.

**Inference geo** is per request: the `inference_geo` parameter on `POST /v1/messages`, with `"global"` as the default and `"us"` to keep inference on US infrastructure. The response's `usage.inference_geo` reports where inference ran, which is the field to log and alert on. A workspace can set `default_inference_geo` and restrict `allowed_inference_geos`, and a request outside the allowed list is rejected. The parameter works on Claude 4.6 and later models; older models return a 400 if it is set. US-only inference is priced at 1.1x on every token category, cache reads and writes included, and rate limits are shared across geos.

**Workspace geo** governs data at rest and endpoint processing such as image transcoding and code execution. It is set when the workspace is created and cannot be changed afterwards, and `"us"` is the only value offered. So a workspace created without thinking about residency stays that way; migrating means a new workspace, new keys and anything stored in the old one left behind or moved by you.

The page also marks where the parameter does not apply. On Amazon Bedrock and on Google-managed Claude models on Google Cloud, the endpoint URL or inference profile sets the region and `inference_geo` is not used; on Microsoft Foundry the US Data Zone Standard deployment type plays that role.

OpenAI's model differs enough to be worth holding side by side. Region is chosen per project and addressed by domain prefix (`eu.api.openai.com` for the EEA and Switzerland). The US, Europe and UAE regions offer both storage and processing; Australia, Canada, Japan, India, Singapore, South Korea and the UK offer storage only. Non-US regions require approval for Modified Abuse Monitoring or Zero Data Retention plus a signed Modified Retention amendment; Europe also accepts some other retention arrangements, and the UAE needs separate approval through sales. Abuse-monitoring logs are kept up to 30 days by default, and several stateful endpoints (`/v1/files`, `/v1/vector_stores`, `/v1/conversations`, `/v1/batches`) are not eligible for zero retention at all.

## Worked policy: an EU customer

Scenario: a German customer's contract requires that conversation content is processed and stored only in the EEA, and that your support staff cannot read it without a ticket. The policy that follows from the sources above:

1. **Provider.** As of 28 October 2026 the Claude API's first-party settings offer `"us"` and `"global"` for inference and `"us"` for the workspace, so neither setting satisfies EEA-only processing; the options are a cloud endpoint in an EEA region where the partner offers one (checked against that partner's region list, not assumed), or OpenAI's Europe region with the required retention approval. Record which, and the date checked.
2. **Stateful features.** Every provider feature that stores state (files, vector stores, conversations, batches, stored responses) is listed with its retention and region, and the ones outside the contract are disabled in code.
3. **Telemetry.** Spans carry metadata only; the CI check fails on any `gen_ai.*.messages`, `system_instructions` or `tool.call.*` attribute in exported spans. Content, if kept, goes to a store in the EEA by reference.
4. **Logs and evals.** Application logs pass through the allowlist; eval sets from this customer's traffic stay in the EEA store, redacted, with the same deletion path as the conversations.
5. **Verification.** The region actually used is logged per request where the provider reports it, and an alert fires on any value outside policy.

The cost the policy accepts: one provider's newest models may not be available in the endpoint you can use, and debugging a bad answer for this customer needs a ticketed read of the content store instead of a trace view.

## When this is wrong

The lesson treats the provider's documentation as the guarantee. It is the description of a configuration; the guarantee is the contract and the provider's audit evidence, and the page can change. That is why the policy records the date checked and logs the region the response reports.

Residency answers where data is processed and stored, not who can be compelled to hand it over or who at the provider can access it; those are legal and contractual questions this lesson does not settle. It also says nothing about your own subprocessors: the tracing vendor, the log platform, the labelling vendor and the error tracker each have their own region, and the error tracker is the one that captures a stack frame with the prompt in a local variable.

Finally, the hard line between metadata and content is softer than the attribute names suggest. Token counts, timing and cache-hit counts can reveal something about content, and a conversation id joined across systems can re-identify a user that each system alone could not.
