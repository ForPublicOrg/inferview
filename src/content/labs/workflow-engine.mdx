  - title: A journal of step results
    brief: |
      The journal is the only part of a run that survives a crash. Record each step's result under its name, as JSON text, in the order the steps ran. Refuse anything that is not JSON when it is recorded (sets, objects, NaN), not later when a replay reads it back, and refuse a name that is already recorded. record returns the value a later read would return, so a tuple comes back as a list and an integer dict key as a string. lookup returns (True, value) or (False, None), so a recorded None is not mistaken for a missing step, and a value handed out must not let the caller change what is stored.

    solution: |
      import json


      class Journal:
          def __init__(self):
              self.entries = []   # [name, json_text], oldest first
              self.index = {}     # name -> position in entries

          def record(self, name, result):
              if name in self.index:
                  raise ValueError(f"step {name!r} is already recorded")
              text = json.dumps(result, allow_nan=False)   # TypeError for sets and objects, ValueError for NaN
              self.index[name] = len(self.entries)
              self.entries.append([name, text])
              return json.loads(text)

          def lookup(self, name):
              if name not in self.index:
                  return False, None
              return True, json.loads(self.entries[self.index[name]][1])

          def names(self):
              return [name for name, _ in self.entries]

          def __len__(self):
              return len(self.entries)
  - title: Replay from the top
    brief: |
      A run is the workflow function called with a Run object. run.step(name, fn, *args) returns the journalled result when the name is recorded, and otherwise calls fn, records the result and returns the recorded value. After a crash, execute calls the workflow again from the first line with the same journal, so finished steps return their saved results and only the unfinished one runs. Return the recorded value even on the first run: code that sees a tuple the first time and a list on replay behaves differently on the two paths. Crash derives from BaseException in this lab so that `except Exception` in workflow code cannot swallow a simulated process death. Accept extra keyword options in Run and execute; later steps add them.

  - title: Catch non-determinism
    brief: |
      Looking results up by name lets a reordered workflow replay without complaint and pair results with the wrong code. Match steps by position instead: the k-th step call must have the k-th recorded name, or raise NonDeterminismError naming both, before the step's function runs. Calls past the end of the journal are new steps and run normally, which is why a run that crashed before a step can pick up a changed version of that step. If the workflow returns while recorded steps are left unconsumed, a step was removed: raise as well. This is the check that fails a Temporal deploy that swaps a timer and an activity. Later steps redefine Run as a subclass of the previous one, so keep the matching in a helper they can call.

    solution: |
      class NonDeterminismError(Exception):
          """The code asked for a different step sequence than the one the journal recorded."""


      class Run(Run):
          def __init__(self, run_id, journal, **options):
              super().__init__(run_id, journal, **options)
              self.position = 0
              self.recorded = journal.names()

          def step(self, name, fn, *args):
              return self._next(name, lambda: fn(*args))

          def _next(self, name, produce):
              """Match the next step against the journal by position; run produce() only past the journal's end."""
              if self.position < len(self.recorded):
                  expected = self.recorded[self.position]
                  if expected != name:
                      raise NonDeterminismError(
                          f"step {self.position + 1}: the journal has {expected!r}, the code asked for {name!r}")
                  self.position += 1
                  return self.journal.lookup(name)[1]
              value = self.journal.record(name, produce())
              self.recorded.append(name)
              self.position += 1
              return value


      def execute(workflow, run_id, journal, **options):
          run = Run(run_id, journal, **options)
          result = workflow(run)
          if run.position < len(run.recorded):
              raise NonDeterminismError(
                  f"the code finished at step {run.position}, the journal still has {run.recorded[run.position]!r}")
          return result
  - title: Retries with a policy
    brief: |
      run.step takes retry=RetryPolicy(...). A failed attempt waits delay(attempt) seconds through the injected sleep and tries again, up to max_attempts; the delay starts at initial_interval, multiplies by backoff and is capped at max_interval, and jitter takes off up to that fraction using the injected random. Exception types in non_retryable are raised on the first failure, as is Crash, which is not an Exception. Only a success is journalled, and a replay of a journalled step never retries or sleeps. With no policy a step gets one attempt. Clock and random are injected so the tests can assert the exact waits.

      class RetryPolicy:
          def __init__(self, max_attempts=3, initial_interval=1.0, backoff=2.0, max_interval=60.0, jitter=0.0,
                       non_retryable=()):
              if max_attempts < 1:
                  raise ValueError("max_attempts is at least 1")
              if not 0.0 <= jitter <= 1.0:
                  raise ValueError("jitter is a fraction between 0 and 1")
              self.max_attempts = max_attempts
              self.initial_interval = initial_interval
              self.backoff = backoff
              self.max_interval = max_interval
              self.jitter = jitter
              self.non_retryable = tuple(non_retryable)

          def delay(self, attempt, rand):
              base = min(self.max_interval, self.initial_interval * self.backoff ** (attempt - 1))
              return base * (1.0 - self.jitter * rand())


      ONE_ATTEMPT = RetryPolicy(max_attempts=1)


      class Run(Run):
          def __init__(self, run_id, journal, sleep=None, random=None, **options):
              super().__init__(run_id, journal, **options)
              self.sleep = sleep or (lambda seconds: None)
              self.random = random or (lambda: 0.0)

          def step(self, name, fn, *args, retry=None):
              return self._next(name, lambda: self._attempt(fn, args, retry or ONE_ATTEMPT))

          def _attempt(self, fn, args, policy):
              attempt = 1
              while True:
                  try:
                      return fn(*args)
                  except policy.non_retryable:
                      raise
                  except Exception:   # Crash is a BaseException, so process death is never retried here
                      if attempt >= policy.max_attempts:
                          raise
                      self.sleep(policy.delay(attempt, self.random))
                      attempt += 1
  - title: Idempotency keys for external effects
    brief: |
      Retries and replays mean a step can run more than once; the journal only helps once the result is written, and the crash that matters comes between the provider charging and the journal write. run.effect(name, fn, *args, retry=None) calls fn(*args, idempotency_key=key) where run.key(name) depends only on the run id and the step name, so every attempt and every re-run sends the same key and the deduplicating provider returns the first charge. Different runs or different steps must never share a key, even when ids contain separators such as "/". Keep keys at most 255 characters and free of the raw run id, which in production is often a customer or order identifier. FakePayments is the provider; the starter gives it to you.
    starter: |
      import hashlib


      class Timeout(Exception):
          """The provider did not answer in time. The charge may or may not have happened."""


      class FakePayments:
          """A deterministic stand-in for a payment API that deduplicates by idempotency key.
          lose_responses: the next n calls apply the charge, then raise Timeout (the response is lost).
          fail_before:    the next n calls raise Timeout without charging."""

          def __init__(self, lose_responses=0, fail_before=0):
              self.charges = {}   # idempotency key -> {"id", "amount"}
              self.keys_seen = []
              self.lose_responses = lose_responses
              self.fail_before = fail_before

          def charge(self, amount, idempotency_key):
              self.keys_seen.append(idempotency_key)
              if self.fail_before:
                  self.fail_before -= 1
                  raise Timeout("connection reset before the request was read")
              if idempotency_key in self.charges:
                  saved = self.charges[idempotency_key]
                  if saved["amount"] != amount:
                      raise ValueError("idempotency key reused with different parameters")
                  return dict(saved)
              self.charges[idempotency_key] = {"id": f"ch_{len(self.charges) + 1}", "amount": amount}
              if self.lose_responses:
                  self.lose_responses -= 1
                  raise Timeout("read timed out after the charge was applied")
              return dict(self.charges[idempotency_key])

          def count(self):
              return len(self.charges)


      class Run(Run):
          def key(self, name):
              """An idempotency key for step `name` of this run."""
              raise NotImplementedError

          def effect(self, name, fn, *args, retry=None):
              """Like step, but calls fn(*args, idempotency_key=...)."""
              raise NotImplementedError

                  if saved["amount"] != amount:
                      raise ValueError("idempotency key reused with different parameters")
                  return dict(saved)
              self.charges[idempotency_key] = {"id": f"ch_{len(self.charges) + 1}", "amount": amount}
              if self.lose_responses:
                  self.lose_responses -= 1
                  raise Timeout("read timed out after the charge was applied")
              return dict(self.charges[idempotency_key])

              return len(self.charges)

              return hashlib.sha256(raw.encode("utf-8")).hexdigest()

              return self.step(name, lambda: fn(*args, idempotency_key=key), retry=retry)

      class Boundaries:

              self.crash_at = crash_at

          def hit(self):
              self.count += 1
              if self.count == self.crash_at:
                  raise Crash(f"injected at boundary {self.count}")

This lab builds the engine behind the durable-execution lessons as one program. Each step adds to the same file and runs its own tests against everything you have written so far, so step 8 drives the journal from step 1, the retries from step 4 and the keys from step 5.

The design is the journal-and-replay model that Temporal, Inngest and DBOS share in different forms: the workflow function runs from the top on every resume, steps that finished return their saved results, and anything that touches the outside world needs a key, because a step can run more than once. Steps 1 to 3 build that core and the check that rejects code whose step sequence no longer matches its history. Steps 4 to 7 add what a model-driven workflow needs: retries that tell transient errors from permanent ones, idempotent payments, a human approval with a timeout, and a spend limit that a crash cannot reset.

Time, randomness and the model are injected or scripted, so every test is deterministic and asserts behaviour (calls made, keys sent, budgets respected), never model text. Step 8 turns the tests on the engine itself: it crashes a run at every boundary and counts the side effects.

The engine keeps the journal in memory. A real one writes each entry durably before returning, which is where most of its cost goes; the lab skips that so the interesting failures stay visible.

Your code is saved with your progress as you type. Passing a step's tests unlocks the next step and counts toward your streak. Python runs in your browser with the standard library only.
