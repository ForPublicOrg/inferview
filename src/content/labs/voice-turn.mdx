  - title: The serial baseline
    brief: |
      A cascaded voice turn is a chain: audio travels up to your server, the transcriber and endpointer decide the user has finished, the LLM produces its first token and then the rest, TTS produces its first audio, and the audio travels back and plays. The starter gives you Dist (a lognormal stage time set by its median and 95th percentile; equal values mean fixed), a Pipeline whose fixed defaults are the stage medians from the Pipecat maintainers' round-trip table, with the transport rows summed to 114 ms up and 89 ms down, and draw(), which samples every stage of one turn in a fixed order so that two pipelines given the same seed see the same turn. Token speed (10 ms per token) and the 60-token reply are scenario values. Write run_turn(sample, cfg) to return a Turn whose events map each event name to its time in ms after the user stopped speaking, and simulate(cfg, n, seed). In this step nothing overlaps: TTS starts when the last token arrives. The fields the later steps use are already in Pipeline and stay off by default.

      import bisect
      import math
      import random
      from dataclasses import dataclass, field, replace


      class Dist:
          """A stage time in ms: lognormal with this median and 95th percentile. p95 equal to p50 means fixed."""

          def __init__(self, p50, p95=None):

              return self.p50 * math.exp(self.sigma * z)

      class Pipeline:
          uplink: Dist = field(default_factory=lambda: Dist(114))
          endpoint: Dist = field(default_factory=lambda: Dist(300))
          llm_ttfb: Dist = field(default_factory=lambda: Dist(650))
          ms_per_token: Dist = field(default_factory=lambda: Dist(10))
          tts_ttfb: Dist = field(default_factory=lambda: Dist(120))
          downlink: Dist = field(default_factory=lambda: Dist(89))

          clause_tokens: int = 8
          interim_lead: Dist = field(default_factory=lambda: Dist(200))
          p_interim_match: float = 0.0
          p_tool: float = 0.0
          tool_ms: Dist = field(default_factory=lambda: Dist(800))
          filler_ms: float = 1200.0
          streaming_tts: bool = False
          speculative: bool = False
          watchdog_ms: object = None


      def draw(cfg, rng):
          return {
              'uplink': cfg.uplink.sample(rng), 'endpoint': cfg.endpoint.sample(rng),
              'llm_ttfb': cfg.llm_ttfb.sample(rng), 'llm_ttfb2': cfg.llm_ttfb.sample(rng),
              'ms_per_token': cfg.ms_per_token.sample(rng), 'tts_ttfb': cfg.tts_ttfb.sample(rng),
              'downlink': cfg.downlink.sample(rng), 'lead': cfg.interim_lead.sample(rng),
              'interim_ok': rng.random() < cfg.p_interim_match, 'tool': rng.random() < cfg.p_tool,
              'tool_ms': cfg.tool_ms.sample(rng),
          }


      @dataclass
      class Turn:
          events: dict
          llm_calls: int = 1

          @property
          def latency(self):
              return self.events['heard']

          @property
          def answer_latency(self):
              return self.events.get('answer_heard', self.events['heard'])


      def run_turn(s, cfg):
          t = {'speech_end': 0.0}
          t['at_server'] = s['uplink']
          t['endpoint'] = t['at_server'] + s['endpoint']
          t['llm_first'] = t['endpoint'] + s['llm_ttfb']
          t['llm_done'] = t['llm_first'] + cfg.reply_tokens * s['ms_per_token']
          t['tts_start'] = t['llm_done']
          t['tts_first'] = t['tts_start'] + s['tts_ttfb']
          t['heard'] = t['tts_first'] + s['downlink']
          return Turn(t)


      def simulate(cfg, n, seed=0):
          rng = random.Random(seed)
          return [run_turn(draw(cfg, rng), cfg) for _ in range(n)]

  - title: Speculative LLM start
    brief: |
      The endpointer waits for silence before it commits the transcript, but the interim transcript is often already final. When cfg.speculative is on, start an LLM request at spec_start, which is s['lead'] ms before the endpoint and never before the audio reached the server. If s['interim_ok'], the final transcript matched and that request's tokens are used. If not, the speculative request is thrown away and a second one starts at the endpoint, so the turn is no faster and llm_calls is 2: that is the cost of speculation, paid in tokens on every miss. Either way nothing is spoken before the endpoint confirms the user has finished, so tts_start is never earlier than the endpoint. The interim match rate is a property of your transcriber and your users; measure it before you enable this.

  - title: A watchdog filler for slow tools
    brief: |
      When s['tool'] is true the first inference returns a tool call at llm_first instead of an answer. The tool runs for s['tool_ms'], then a second inference takes s['llm_ttfb2'] to its first token, and the answer streams or waits from there as before; count that inference in llm_calls. Silence through all of it reads as a dropped call. The Pipecat primer offers two fixes, a spoken message before the function call or a watchdog timer, and this step builds the watchdog: when cfg.watchdog_ms is set and the tool is still running that long after it started, play a cached filler clip (no TTS, so it is heard one downlink later) of cfg.filler_ms. Record filler_heard, keep the answer from talking over the clip, record answer_heard for the answer's first audio, and set heard to whichever audio came first. Choosing watchdog_ms is the policy decision: too low and quick tools get a filler they did not need, too high and the silence is back.

      def run_turn(s, cfg):
          t = {'speech_end': 0.0}
          t['at_server'] = s['uplink']
          t['endpoint'] = t['at_server'] + s['endpoint']
          calls, start = 1, t['endpoint']
          if cfg.speculative:
              t['spec_start'] = max(t['at_server'], t['endpoint'] - s['lead'])
              if s['interim_ok']:
                  start = t['spec_start']
              else:
                  calls = 2
          t['llm_first'] = start + s['llm_ttfb']
          answer_first = t['llm_first']
          if s['tool']:
              t['tool_done'] = t['llm_first'] + s['tool_ms']
              answer_first = t['llm_first2'] = t['tool_done'] + s['llm_ttfb2']
              calls += 1
          ms = s['ms_per_token']
          t['llm_done'] = answer_first + cfg.reply_tokens * ms
          if cfg.streaming_tts:
              t['tts_start'] = min(answer_first + cfg.clause_tokens * ms, t['llm_done'])
          else:
              t['tts_start'] = t['llm_done']
          t['tts_start'] = max(t['tts_start'], t['endpoint'])
          t['tts_first'] = t['tts_start'] + s['tts_ttfb']
          t['answer_heard'] = t['tts_first'] + s['downlink']
          if s['tool'] and cfg.watchdog_ms is not None and s['tool_ms'] > cfg.watchdog_ms:
              t['filler_heard'] = t['llm_first'] + cfg.watchdog_ms + s['downlink']
              t['answer_heard'] = max(t['answer_heard'], t['filler_heard'] + cfg.filler_ms)
          t['heard'] = min(t['answer_heard'], t.get('filler_heard', math.inf))
          return Turn(t, calls)
  - title: Barge-in truncation
    brief: |
      When the user talks over the agent, the pipeline cancels generation and playback, and the conversation history must hold what the user heard rather than what the LLM wrote, or the next turn answers as if the user heard a sentence they interrupted. The primer assembles the assistant message from word-level timestamps for this reason. Given each word's playout start in ms after the agent's audio began (non-decreasing, ties allowed), the moment the interruption was detected, and stop_ms (the time from detection until playback has actually stopped, which includes whatever the client's jitter buffer still holds), heard_count returns how many words began playing before playback stopped. apply_barge_in returns a new history whose last assistant message keeps only those words; whether you add an interruption marker, and what you do when nothing was heard, is your decision, and the tests accept either as long as no unheard word survives. heard_count runs once per interruption across long sessions, so it must answer in logarithmic time: the tests call it thousands of times on a 200,000-word timeline.

      def heard_count(starts, interrupt_at, stop_ms):
          return bisect.bisect_left(starts, interrupt_at + stop_ms)


      def apply_barge_in(history, words, starts, interrupt_at, stop_ms):
          k = heard_count(starts, interrupt_at, stop_ms)
          out = [dict(m) for m in history]
          if k == 0:
              return out[:-1]
          text = ' '.join(words[:k])
          out[-1]['content'] = text if k == len(words) else text + ' [interrupted by the user]'
          return out

This lab builds a simulator of one cascaded voice turn, the kind the Pipecat maintainers measure in their primer: microphone, encoding, network and jitter buffer on the way up, transcription and endpointing, LLM time to first token, sentence aggregation, TTS time to first audio, and the same transport on the way back. Their table sums to 1,293 ms for a typical stack, and their June 2026 update sets 1,500 ms as the target and warns against spikes above it. Every step adds to one program and runs its tests against everything written so far.

Nothing calls a model. Each stage is a seeded distribution, and `draw()` samples every stage of a turn in a fixed order, so a pipeline with streaming on and one with streaming off see the same turn and the tests can compare them turn by turn. The stage medians come from the primer's table and the per-model LLM and TTS latencies from its measurements; the tails, the tool-call rate and the interim-transcript match rate are scenario values, labelled as such where they appear. The tests check behaviour: event order, which stage a feature removes from the critical path, how many LLM calls a turn costs, and whether p50 and p95 meet the targets you set on seeds you did not tune against.

The simulator models a cascaded pipeline only. A speech-to-speech model such as Moshi, which the paper reports at 160 ms theoretical and 200 ms practical latency, has no endpoint, LLM and TTS stages to overlap, and its tuning levers are different. The last step leaves you with two numbers that disagree: first audio can meet a p95 target with a filler, while answer audio cannot get under 1,500 ms at p95 with any option in the primer's table.
