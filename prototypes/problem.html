Agent loops forever: find and fix

Mediumdebug25 minmid, senior Anthropic CR 2026 · Sierra CR 2026 · OpenAI CR 2025Core 100
The round, as candidates describe it

You are handed a running agent and a trace. "It never finishes. Find out why and fix it. Talk me through it." Twenty-five minutes, screen share, you may read any code.

The agent

A support agent with three tools: search_orders(customer_id), get_order(order_id), issue_refund(order_id, amount). The loop is the usual one: send messages, execute any tool call the model returns, append the result, repeat until the model returns plain text or max_steps is hit.

async def run(messages, tools, max_steps=20):
    for step in range(max_steps):
        resp = await llm(messages, tools=tools)
        if resp.tool_calls is None:
            return resp.text
        for call in resp.tool_calls:
            try:
                result = await tools[call.name](**call.args)
            except Exception as e:
                result = {"error": str(e)}
            messages.append(tool_result(call.id, result))
    raise RuntimeError("max steps")

The answer, three depths

30-second what you say first

The refund tool rejects the amount with a permanent validation error. The loop catches every exception the same way, appends the error as a tool result, and the model reads "error" as "retry". Nothing distinguishes a retryable failure from a terminal one, and nothing caps repeated identical calls. Fix: typed tool errors (retryable versus terminal), a guard on repeated identical calls, and terminal errors surfaced to the user instead of handed back to the model.

3-minute how you found it, trade-offs

Reading the trace. Steps 1 to 4 are healthy: search, read the order, decide. From step 5 the same issue_refund(order_id="A-1042", amount=49.0) repeats with the same opaque error, refund rejected (code 422). The model's text between calls says "let me retry". The search result showed "refunded": 36.50, so the correct amount was 12.50; the model missed that, but it was never told why the refund failed, so it had no way to correct itself.

Why fault B reproduces it. A transient 500 (the first injection) also loops, but with different errors, and retrying is correct there. Results appended as user messages produce a different symptom: the model says it got no result. The prompt-cycle fault would show a get_order between refunds, and the recorded trace has none.

The fix has layers. Tools return structured errors with a retryable flag, and terminal errors end the loop with a user-facing message. A guard breaks the loop when the same (tool, args) call repeats more than twice. The refund tool should say what is wrong in its error (the refundable balance), and get_order should expose that balance, so the model can propose a valid amount. And a metric on repeated identical calls, because this class of bug is invisible in averages and obvious in a histogram.

Trade-off. Breaking on identical calls stops legitimate polling. Make the threshold per tool, and exempt tools declared as polling tools.

Follow-ups verify, fail, alternative
  • How do you verify the fix? Replay the recorded trace against the fixed loop in CI and assert it terminates within six steps with a user-facing error. Keep the trace as a regression test.
  • How does the fix fail? A tool that is flaky but retryable now has to say so, or you have turned a self-healing loop into a hard error. Audit every tool's error contract.
  • What is the alternative? Put the retry policy in the tool layer, like an HTTP client, so the model never sees transient errors at all. The model should only ever see terminal outcomes.

The fix

async def run(messages, tools, max_steps=20, max_repeat=2):
    seen = Counter()
    for step in range(max_steps):
        resp = await llm(messages, tools=tools)
        if resp.tool_calls is None:
            return resp.text
        for call in resp.tool_calls:
            key = (call.name, json.dumps(call.args, sort_keys=True))
            seen[key] += 1
            if seen[key] > max_repeat:
                return f"I couldn't complete this: {call.name} keeps failing the same way."
            try:
                result = await tools[call.name](**call.args)
            except RetryableToolError as e:
                result = {"error": str(e), "retryable": True}
            except ToolError as e:
                return f"I couldn't complete this: {e.user_message}"
            except Exception as e:
                result = {"error": str(e)}
                log.exception("tool %s crashed", call.name)   # unknown tool, bad args, bugs
                return "Something went wrong on our side. A human will follow up."
            messages.append(tool_result(call.id, result))
    raise RuntimeError("max steps")

The final except Exception stays: a hallucinated tool name raises KeyError and bad arguments raise TypeError, and neither should escape the loop or go back to the model.
